# Verifying Web Shell changes

Bind the development server to loopback and open the shell in a browser that can reach it. Use the same workspace configuration and browser steps on base and head.

## Exercise an older daemon's capability fallback

Run the scenario once with the daemon's advertised capabilities. For the second run, open a fresh page and register `page.route('**/capabilities', handler)` before the first navigation. In the handler, count the request, fetch the real response with `route.fetch()`, remove only the feature under test, and return the edited response with `route.fulfill()`. Verify that the handler ran at least once and that the browser received the edited feature list before reporting an emulated older daemon. In [the secondary-workspace status check](https://github.com/QwenLM/qwen-code/pull/12943#issuecomment-5988053379), removing `workspace_session_live_state` exercised the fallback while the real daemon handled the session.

## Verify a partially applied settings change

Start each arm with isolated user settings, Live disabled, and no stored key. Select a model with `keySource: settings`. In the test daemon, let credential validation succeed for a test key and make the controller's `setEnabled(true)` reject. Enter the key in the form, enable Live, save, and confirm if the native Host dialog opens. The single `POST /live/setup` validates the key before writing settings. A validation failure returns 409 before the write. An activation failure after the write rolls back only `enabled`. On the client's subsequent `GET /live/setup`, verify that the daemon reports `storedKey: true`, `keyConfigured: true`, and `enabled: false`. Then inspect the form. In [the Live settings regression](https://github.com/QwenLM/qwen-code/pull/12943#issuecomment-5988053379), the base showed “Settings changed elsewhere” and disabled Save. The fix showed “Configured” and kept Save available.

## Create a channel session through its adapter

Follow the [example channel's quick start](../../../../packages/channels/plugin-example/README.md) to link the extension and start its mock messaging server. For unattended verification, review the example extension source first. In an isolated test home, run `echo Y | qwen extensions link ./node_modules/@qwen-code/channel-plugin-example` and check that the CLI reports the extension was linked and enabled. Set the channel's working directory to a registered, trusted test workspace. Start the daemon with `qwen serve --channel my-plugin-test` and send a uniquely identifiable message through the mock server. Check that the channel session appears in the intended workspace and that the reply reaches the sender. This exercises the daemon and its channel worker without an external messaging account. [Channel verification report](https://github.com/QwenLM/qwen-code/pull/12943#issuecomment-5988053379)

## Prove that a model turn completed

The prompt can appear in the user bubble, session title, and sidebar as soon as you send it. Capture the session ID and prompt ID for the turn under test. Require a backend turn status of `completed` for that prompt in that session. If the turn is still running at the deadline, cancelled, or in error, record that outcome. A tool-call-only round can emit usage before the turn finishes. To corroborate the model used on a completed turn, enable OpenAI logging and inspect the matching `openai-*.json` in the configured log directory (default `<cwd>/logs/openai`). Match `context.sessionId` and `request.model` and check `response.usage.completion_tokens` for output usage. In [the ordinary and Hosted session check](https://github.com/QwenLM/qwen-code/pull/13218#issuecomment-5970660737), all three Hosted turns completed and their session IDs matched usage records for `qwen3.8-max`.
