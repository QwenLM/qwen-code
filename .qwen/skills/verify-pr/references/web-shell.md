# Verifying Web Shell changes

Bind the development server to loopback and open the shell in a browser that can reach it. Use the same workspace configuration and browser steps on base and head.

## Exercise an older daemon's capability fallback

Run the scenario once with the daemon's advertised capabilities. For the second run, open a fresh page and register `page.route('**/capabilities', handler)` before the first navigation. In the handler, count the request, fetch the real response with `route.fetch()`, remove only the feature under test, and return the edited response with `route.fulfill()`. Verify that the handler ran at least once and that the browser received the edited feature list before reporting an emulated older daemon. In [the secondary-workspace status check](https://github.com/QwenLM/qwen-code/pull/12943#issuecomment-5988053379), remove `workspace_session_live_state` and load the secondary workspace's session. Keep its folder expanded on Home while a turn finishes, then switch to Plugins. Verify that no stale Finished badge appears for Home.

## Verify a partially applied settings change

Start each arm with isolated user settings, Live disabled, and no stored key. Select a model with `keySource: settings`. In the test daemon, let credential validation succeed for a test key and make the controller's `setEnabled(true)` reject. Enter the key in the form, enable Live, save, and confirm if the native Host dialog opens. The single `POST /live/setup` validates the key before writing settings. A validation failure returns 409 before the write. An activation failure after the write rolls back only `enabled`. On the client's subsequent `GET /live/setup`, verify that the daemon reports `storedKey: true`, `keyConfigured: true`, and `enabled: false`. Then inspect the form. In [the Live settings regression](https://github.com/QwenLM/qwen-code/pull/12943#issuecomment-5988053379), the base showed “Settings changed elsewhere” and disabled Save. The fix showed “Configured” and kept Save available.

## Create a channel session through its adapter

Use the same isolated `QWEN_HOME` for extension linking, channel settings, workspace trust, and the daemon. From a built repository checkout, review the example extension, run `npm run build --workspace=@qwen-code/channel-plugin-example`, and verify that `packages/channels/plugin-example/dist/index.js` exists. For an unattended run, link the reviewed local package with `echo Y | qwen extensions link ./packages/channels/plugin-example` and confirm that the CLI reports it enabled.

Copy the channel entry from the [example channel's quick start](../../../../packages/channels/plugin-example/README.md) into `$QWEN_HOME/settings.json`. Name the entry `my-plugin-test`, set `type` to `plugin-example`, and set `cwd` to the registered, trusted test workspace. From the repository root, run `node packages/channels/plugin-example/dist/start-server.js`. From the test workspace, run `qwen serve --channel my-plugin-test` and send a uniquely identifiable message through the mock server. Check that the channel session appears in the intended workspace and that the reply reaches the sender. This exercises the daemon and its channel worker without an external messaging account. [Channel verification report](https://github.com/QwenLM/qwen-code/pull/12943#issuecomment-5988053379)

## Prove that a model turn completed

The prompt can appear in the user bubble, session title, and sidebar as soon as you send it. Capture the session ID and prompt ID for the turn under test. Using the session owner's read credentials, request `GET /session/<sessionId>/turns/<promptId>` with the IDs URL-encoded. Require the response to report `state: completed` for that prompt in that session. If the turn is still running at the deadline, cancelled, or in error, record that outcome. A tool-call-only round can emit usage before the turn finishes. To corroborate the model used on a completed turn, enable OpenAI logging and inspect the matching `openai-*.json` in the configured log directory (default `<cwd>/logs/openai`). Match `context.sessionId` and `request.model` and check `response.usage.completion_tokens` for output usage. In [the ordinary and Hosted session check](https://github.com/QwenLM/qwen-code/pull/13218#issuecomment-5970660737), all three Hosted turns completed and their session IDs matched usage records for `qwen3.8-max`.
