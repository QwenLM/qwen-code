# `/batch-api` 实测结果与结论（2026-09-23）

- 分支 / commit：`feat/agent-prepared-batch` @ `06a1278572`
- 环境：macOS arm64 / Node 22；模型 qwen-plus（另有 qwen3.7-max / qwen3.7-plus 对照）
- 费用口径：token 为服务商返回的实测 usage；价格 = usage × 百炼官方刊例价（北京地域），
  qwen-plus 按输入 0.8、缓存命中 0.16、输出 2 元/百万 token，Batch 减半。经网关扣费的
  以资源包账单为准。
- 数据由人工测试会话产出；本文件第三节起为对数据的分析。

## 一、测试方案

| 方案                           | 做法                                                                    | 用户输入                                                                                     |
| ------------------------------ | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| A：`/batch-api`                | agent 预检 + 抽样 + 写计划，`qwen batch run` 提交，Batch 生成，程序交付 | `/batch-api 把 src 下的 N 个英文文档翻译成中文，写到 out/ 目录，文件名保持一致`              |
| B：`/batch` 并行 worker        | 主 agent 分组，派 5 个实时子 agent 并行处理                             | `/batch 把 src 下的 N 个英文文档翻译成中文，写到 out/ 目录，文件名保持一致`                  |
| C：普通会话（实时 agent loop） | 模型逐轮读写                                                            | `把 src 下的 N 个英文文档全部翻译成中文，写到 out/ 目录，文件名保持一致，保持 Markdown 结构` |

A 的计划文件由 agent 生成：共享 system 与指令 + 条目列表（source → target）。执行器把它
组装成每条独立请求 `[system: 规则] [user: 指令 + <document>原文</document>]`，条目之间零
共享历史。

**费用复核**（按上述单价重算，与测试报告一致）：

- C（50 篇）：未命中 52,041 × 0.8 + 命中 2,407,360 × 0.16 + 输出 7,143 × 2 ≈ ¥0.441。
- A（50 篇）：准备约 ¥0.0496 + Batch 生成约 ¥0.0034 ≈ ¥0.0529。

**其他实测：**

- **思考模式**：同一个 2 篇任务的 Batch 生成，qwen-plus（不思考）274 / 29 token，¥0.00014；
  qwen3.7-max（开思考）294 / 约 1,150 token，约 ¥0.022，相差约 160 倍。C 侧同任务
  qwen-plus ¥0.0431，qwen3.7-max ¥0.3099。
- **缓存探针**（实时，同一前缀连发 3 次）：738 token 的前缀 3 次都没命中；2,390 token 的
  前缀第 2、3 次命中 96.4%，单次从 ¥0.029 降到 ¥0.0069。
- **Batch 延迟**：执行本身 2–7 秒；qwen3.7-plus 排队 53 分钟；失败请求实测费用为 0。
- **路由**：不输入 `/batch-api` 时，没有任何自然语言措辞能让模型走到 Batch 执行器
  （`disable-model-invocation` 按设计生效）。明确说"用 qwen batch 命令"时，模型会把它映射
  成 `/batch` 并行 skill，甚至编造不存在的 `qwen batch translate` 语法。

## 四、分析：哪些结论成立，哪些还不能外推

**成立的：**

1. 功能与设计约定逐条一致。
2. 方向与设计判断一致：
   - A 的成本由固定的准备开销主导（约 99%），生成部分的增量极小；
   - C 每一轮都要重付会话基底，总价超线性增长；
   - 规模小时（2 篇）实时更便宜，与 skill 里"只有几条不适合"的判断一致；
   - 长共享前缀时实时加缓存更便宜，与盈亏平衡模型一致。
3. 费用数字内部自洽（见上文复核）。

**还不能外推的：**

1. **样本是玩具文档。** A 在 50 篇时 Batch 侧总输入只有 6,191 token，每条约 124 token
   （还含系统提示和指令），每篇输出约 18 token，即每篇只有一两句话。这组数据测到的主要是
   固定开销，而不是翻译本身。换成真实长文档，生成费用会成为主要部分，C 的上下文也会膨胀、
   可能触发压缩。方向大概率成立，但"便宜 8.3 倍""N=1000 时省 98.7%"不能外推。
2. **质量没有评估。** "交付 N/N"只说明文件写出来了；设计把"同等质量"列为成功条件。
3. **速度不是 A 的优势。** 这次 A 很快，是因为 qwen-plus 队列刚好空；同一轮测试里
   qwen3.7-plus 排了 53 分钟，服务商承诺窗口是 24 小时。
4. **第一层对照没有做。** 表中的 B 是 `/batch` 并行 worker，不是设计里"把 A 的请求原样发一遍
   实时接口"的对照组。"Batch 五折"仍是按刊例价推算的。
5. **每个格子只跑了一次。** A 在 2 篇时准备了 8 轮、20 篇时 6 轮，说明轮次本身有波动；
   "拐点 N≈3~5"是按三个点估的。

**对外口径**：在真实文档实测完成前，只说"在小文档批量翻译上显著更省"，不给倍数。

## 五、发现的问题与处理

| #   | 问题                                                                                                                                                      | 判断                                                 | 处理                                                                                              |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 1   | `check` 看不出模型有没有 Batch 资格：某模型 `check` 通过，创建后服务端按行拒绝；`collect` 只报笼统的 `no result line`，真正原因要看 `batch status --json` | 真 bug                                               | 待修：`collect` 透出作业级 `errors`；`run` 提交后短暂轮询越过 `validating` 状态，校验失败当场报出 |
| 2   | 直接用 `node dist/cli.js` 启动时不设置 `QWEN_CODE_CLI`，skill 里的命令会回落到 PATH 上的旧版 `qwen`                                                       | 真实存在的边缘情况                                   | 待修：文档注明；skill 第 0 步遇到"未知命令"时明确提示 PATH 上的 `qwen` 版本过旧                   |
| 3   | qwen-plus 作为准备模型，在失败后自作主张改为会话内直接翻译                                                                                                | 违反 skill 约定                                      | 待修：措辞加硬——任何 `qwen batch` 命令失败都只汇报并停止，绝不在会话内自己做                      |
| 4   | 模型完全看不到 `/batch-api`，连建议都提不出                                                                                                               | 与设计 §3.1 不符（设计允许模型建议、不允许模型切换） | 待修：在 `/batch` 的描述里注明"异步半价请让用户输入 `/batch-api`，你不能调用它"                   |
| 5   | 收取需要用户手动触发                                                                                                                                      | 体验缺口                                             | 方案见[概览第 5 节](../../design/2026-09-23-batch-api-overview.zh-CN.md#5-待决策自动收取)，待决策 |

## 六、后续实测方法

**P0：决定"省钱"能否成立**

1. **真实文档，按篇幅分层**：从本仓库 `docs/` 选英文文档，按小于 2k、2–6k、6–15k token
   分三档，每档 15–20 篇、合计约 50 篇；样本冻结后 A / B / C 用同一份术语表和指令。额外
   记录 C 的上下文压缩次数和各组截断率。
2. **质量**：全部产出跑 `stage-b-structure-check.mjs`；按预注册名单抽 20% 盲评（随机编号，
   准确、通顺、术语一致各 1–5 分，判定"可交付 / 需返工"）。可以先用另一个模型批量打分，
   再人工复核 5 篇校准。A 的"需返工"篇数不比 C 多 1 篇以上，才能谈"同等质量下更省"。
3. **第一层对照**：用 `stage-b-realtime-replay.mjs` 把 A 的 `input.jsonl` 原样发给实时接口，
   实测这批请求的缓存命中率和同请求级的价差。两路最好用独立的 API key 或 workspace，便于
   在账单上分开；分不开的按"usage × 刊例价"推算并注明口径。
4. **重复**：50 篇的每组重复 3 次，报告中位数和范围。拐点通过拟合"A = 准备固定费 + n ×
   每篇 Batch 费"和 C 的每篇边际费用得出，再在 2、5、10、20 篇各取一点验证。

**P1：决定结论能否指导使用**

5. **排队分布**：用 `03-queue-timing.mjs` 对要用的 2–3 个模型各跑 24 小时，给出排队的
   p50 / p90；报告里把"用户需要守着的时间"和"墙钟时间"分开。
6. **准备阶段实验**：同一个 50 篇任务，对比现有 skill、精简版 skill（同类转换跳过抽样）、
   思考与非思考的准备模型，记录轮数、token、计划质量和返工率。按设计不自动换模型，实验只
   用于决定是否提供"用户可选的准备模型"或由程序展开文件列表以减少轮次。
7. **补救成本**：主动制造截断（`maxOutputTokens` 偏小）和目标冲突，记录补救费用和介入次数。

**P2：产品体验**

8. 可发现性（问题 4 修复后）：重跑三种措辞 × 三种规模的路由矩阵，期望大规模、能等的任务里
   模型**建议**用户输入 `/batch-api`，N=2 时不建议，且不再编造命令。
9. 模型维度：在 20 篇真实文档上只比较"qwen-plus 不思考"和"qwen3.7-max 思考"两格。
10. Windows：锁文件、`link()` 写文件、权限位，跑一遍单元测试和端到端脚本。

**预算**（qwen-plus 刊例价，50 篇、平均约 5k token）：A 的 Batch 生成约 ¥0.35；第一层
重放约 ¥0.7；B / C 取决于上下文增长，粗估各 ¥2–10。含 3 次重复和 24 小时排队探针，合计
几十元量级；思考模型那一格另算，会贵一个数量级。
