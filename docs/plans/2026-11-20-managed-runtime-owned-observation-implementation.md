### Key contracts already pinned

- `captureId = sha256(JSON.stringify([sessionKey, executionCallId, bindingGeneration])).slice(0,32)`, `sessionKey = {tenantId, workspaceId, sessionId}`. The worker computes it from `capture.tenantId/sessionId` + `observation.workspaceId`; the applier's admission recomputes the same value.
- Segment content resource ID = `sha256(JSON.stringify([captureId, streamId, ordinal]))`; seal uses `'seal'`. `ResourceToolResultSegmentStore` is reused verbatim over the worker-local resource store, so segment/seal behavior is identical.
- An entry carries every resource introduced since the previous entry (`WorkerDeliveryResourceStore.since(marker)`); the manifest revision's `onRevision` hook snapshots them. Republish under same ID+digest is a no-op.
- A failed push is never `failCapture()`; it switches to held and keeps entries. The terminal entry bypasses the byte budget so a forced stop always produces exit proof.

## Slice 4 — acceptance & measurement (in progress)

Design §7, §10. H2 alone is not acceptance: the staging, settlement, wake and fault cases must also pass on MySQL 8.4 with a real Harness and worker.

### Landed

- **Real-process quiet exit** (`packages/cli/src/serve/managed-background-delivery.process.test.ts`): a real `bash` child exits silently while the publisher is detached; the worker holds the terminal entry, a fresh applier re-attaches at a newer writer generation, and the record settles with exit proof and a manifest declaring zero bytes on every stream.
- **Real-process Harness restart mid-stream** (same file): a real producer crosses segment boundaries while the first applier applies a prefix, then that applier dies and a fresh one re-attaches at generation 2. The settled manifest declares the exact byte length and SHA-256 of the whole output through one lineage — the §10 "Harness restart" case on real pipes.

  The re-attach fixture had to mirror the production protocol exactly: hold live pushes (`holdDeliveries`), install, then seed the cursor from the `observedRuns` watermark the install response reports. Without the seed the first post-acknowledgement entry is refused as `Delivery sequence is not contiguous`, because the worker already trimmed the acked prefix — the product was right and the fixture was wrong. `reattachAndDrainBackgroundDeliveries` already does this in production.

- **Delivery batch bound (defect found by acceptance).** A revision used to carry up to 1024 segments of 256 KiB, so one output entry could exceed `MANAGED_DELIVERY_REQUEST_LIMIT_BYTES` (512 KiB) once base64-encoded. `deliverRpc` rejects an oversized request **before** any HTTP call, so such an entry could never be pushed and the run stayed in held mode forever — a violation of §11's "budgets bounded below by the largest flush batch". Background capture now uses 128 KiB segments and publishes a revision per segment, so a revision carries at most one new segment per stream (~175 KB encoded) and even both streams sealing into one entry stays under the limit. Output visibility improves as a side effect: a revision per 128 KiB instead of per page of 1024 segments. The first version did this with one segment per page, which let idle partial flushes exhaust the page bound; see Review fixes (#17953).

- **Forced stop under backpressure (defect found by acceptance).** With the outbox full and the run held, the capture's write queue parks inside `waitForRoom`, and the stop's `finish`/`finalize` queue behind it — the reserved terminal slot was unreachable, so the registry's completion coroutine would hang forever and the Runtime hold would never release. That is the §4.4 violation ("a full outbox must never keep a stopped process from producing its exit proof"); the earlier hypothesis about a broken-capture manifest that cannot chain was downstream of it — the terminal entry was never emitted at all. The fix implements the design's drop-tail contract:
  - `WorkerBackgroundCaptureSink.setStopRequested()` calls `BackgroundDeliveryRun.requestStop()`, which releases every parked room waiter so the stop never waits on the parked queue.
  - `waitForRoom` drops an entry only while stopping **and** the outbox is actually full; the first drop latches `tailDropped`, so the dropped tail is one contiguous suffix and a later entry can never resume past it (which would break the sequence contiguity the consumer enforces). A stop with room to spare keeps delivering and sealing exactly as before — the existing stop tests still see `complete`.
  - A dropped entry consumes no `deliverySeq`: the sequence is drawn at enqueue, not at construction, so the terminal entry stays contiguous with the last enqueued entry.
  - The sink's revision hook marks the capture broken with the new `cancelled` reason on the first dropped revision (`LocalShellStreamCapture.cancelCapture()`), freezing the buffered tail; the final revision declares the gap through `missingRanges`.
  - The resource marker advances only for enqueued entries, so the terminal entry carries the full closure of everything the final manifest names — including the dropped revisions' segments, pages and manifests. The applier needed no change: the terminal manifest chains from the last applied revision (`isToolResultManifestChainLink` admits the revision gap), and the settle verifies every carried ref.

  The acceptance test (same process file) fills the held outbox with a real unbounded producer, waits until the write queue parks (the entry count stays stable while the producer is still writing), freezes the producer with SIGSTOP and kills it with SIGKILL, then runs the registry's completion order. The settled record is `cancelled`/`stop_requested` with no exit status; the manifest is `partial`/`cancelled`, the retained prefix's digest matches the producer's exact bytes, and the dropped tail is a declared gap. Fixture gotcha: freezing the producer before the outbox parks can land on a segment boundary with nothing left to lose — the capture then honestly seals `complete`, so the test waits for the park rather than a fixed entry count.

### §7 measurement — worker/applier half (LANDED)

`scripts/measure-background-observation.mjs` (run after `npm run build`; ~8 min, dominated by the 10,000-observation drain) prints a JSON report per measurement. Capture lanes run over an in-memory resource store to isolate capture overhead from store I/O; the drain commits through a real on-disk session authority. Local numbers (Apple Silicon, node 24, loopback):

- **M1 resident equivalence (§7 item 4).** 6 MiB stdout: worker lane 129–158 MB/s with 49 manifest revisions / 147 resources / 12.7 KB final manifest; resident Harness lane 455–523 MB/s with 2 revisions / 11 resources / 1.3 KB manifest. The worker lane is ~3.5× slower in pure capture overhead, but both far outrun any real pipe producer; the cost is the per-revision manifest churn that buys 128 KiB output visibility.
- **M2 entry sizing (§11 Q1/Q3).** Output entries encode to 178–192 KB (median 185 KB); 45 fill the 8 MiB outbox. The forced-stop terminal closure — dropped revisions' segments/pages/manifests plus the announcement and final manifests — measures **226 KB (5 resources), comfortably under the 512 KiB request limit** (~2.3× headroom).
- **M3 backpressure (§7 item 2, worker half).** Engages at 45 parked entries (~8 MiB); drain-resume plus full completion takes **20 ms** over 36 staging pulls. Bounded and promptly released on acknowledgement.
- **M4 applier drain cost (§7 item 3).** Committing observation revisions plus notification inputs through the real authority: **30 ms for 1, 31 ms/obs at 100, 48 ms/obs at 10,000** (476 s total, degrading as the journal grows). A drain-only wake that commits 10,000 observations is ~8 minutes of silent-load work; the backstop's scan limit paces the burst (§8).
- **M5 total output cap (§11 Q3 finding, confirmed).** The worker lane admits exactly **8 MiB** (64 pages × 1 segment × 128 KiB), then `size_limit` breaks it and the envelope degrades to `unavailable` with the last durable revision (64) standing. The foreground lane's 512-segment pages reach ~32 GiB.

**Constants settled by this evidence:** `RUN_OUTBOX_BYTES` 8 MiB (about 16× the largest possible entry of ~506 KB; the terminal closure fits with headroom), `BACKGROUND_SEGMENT_BYTES` 128 KiB with a revision per segment growing an open page of up to `BACKGROUND_SEGMENTS_PER_PAGE` 256 (every entry and the worst-case terminal closure fit the request limit; see Review fixes), `PARTIAL_FLUSH_MS` 250 (idle-flush overhead is negligible beside the 30 ms/obs commit cost). **The per-stream cap is 16,384 segments (2 GiB of full segments):** packing more segments per page would have pushed a two-stream dropped-tail closure to ~700 KB, but growing the open page keeps one segment per stream in each entry, so the cap rose without touching the protocol limits. Raising it further needs coordinated `maxPagesPerStream`/`maxManifestBytes`/request-limit changes — a maintainer design decision (§11 Q3 stays open with this evidence). The Java-side pull wait, staged-bytes watermark and hard cap, and the wake→load latency, need the Broker + MySQL + daemon measurement below.

### Review fixes (#17953)

The PR review found thirteen defects on the enabled path: ten that wedge or lose deliveries and three of resources and scale. Each fix has a regression test that fails on the pre-fix code.

- **Staging dropped null fields.** The Broker serialized staged entries without `WriteNulls`, so a terminal's `exitSignal: null` vanished and every later wake load failed to parse the entry. Staging now writes nulls.
- **Monitor notifications could not stage.** The staging allowlist named a kind nothing produces and omitted `managed-input` and `managed-admission`.
- **Idle partial flushes exhausted the page bound.** With one segment per page, every 250 ms flush spent one of the 64 pages, so a command printing a line per second hit `size_limit` after about 64 lines. The capture's `revisionPerSegment` option now re-publishes the open last page with each segment, up to 256 segments; the descriptor successor rule already admits a grown last page. The terminal closure carries only the settled manifest, so the dropped revisions' manifests cannot push it over the request limit.
- **A failed partial flush wedged the stream.** It now latches the capture as broken, like a failed write.
- **The Monitor tail could deadlock.** When the tail window reached `maxEvents`, `flushTail` awaited `terminate`, which awaits the unit completion that awaits `flushTail`. The tail now never stops the unit; as in the resident loop, it is skipped after a quota or idle stop, and the physical exit outranks the quota.
- **A re-attach during an in-flight push left the run held.** The old push no longer switches the run to held, and the newer publisher takes over once it returns.
- **A held run never retried.** A failed push now retries the installed publisher with backoff (1 s, doubling to 30 s) and returns to attached on the first acknowledged batch. This also settles a terminal entry that arrives before its start receipt.
- **Staging acknowledgements trimmed entries a Harness still owed.** While a publisher is installed (attached, or held after a failed push), the worker ignores `ackThrough`; only a run no Harness holds trims on staging. Otherwise entries staged during a re-attach drain were lost, and a retry after staging was refused as non-contiguous.
- **Push batches are sized as sent**, request wrapper and separators included.
- **Observation entries carried the capture's output.** The Monitor policy now publishes into its own resource store, so an observation carries only its notification.
- **The worker never forgot a run.** A run now leaves the registry once a consumer acknowledged its terminal entry and its exit took the receipt, so a registration's `observedRuns` lists only runs still in flight. Each resource store also drops the bytes of everything an enqueued entry already carries, except the newest manifest, which the capture reads back at finalize. Without this, growing the open page would have let one long run keep gigabytes in the worker.
- **A replica that could not use a lease locked out one that could.** The Broker now checks the binding's lease with its own provisioner before claiming the puller, so a replica that cannot pull a binding never holds its claim.
- **A woken Session could not suspend again.** A reload now re-derives what dispatch records: when a re-registration reports observation ownership, the binding of every unsettled run that worker reports holding joins the lane's `observationBindings`, so the suspension certificate can pass while the run is still live.

## Notes / gotchas

- The applier requires the capture registered via `HostedShellPublisher.register()` even in worker mode (the prepare RPC is skipped, but `applyDelivery` looks up the registered capture). Production registers it at background admission in `hosted-workspace-tool-turn.ts`.
- Test resource stores must land bytes in the session resource root layout (`<runtimeBaseDir>/resources/<sessionId>/<kind>/<resourceId>`) and read via `session.resources`, or the authority's `verifyExtensionResources` refuses the record refs.
- `LocalManagedSessionResourceStore.publish` always generates a UUID; a `DurableToolResultResourceStore` that honors client-chosen IDs must write the layout directly (see the test double).
- The Monitor tail cycle once suspected here was real and is fixed; see Review fixes (#17953). The tail must never call `terminate`, because `registry.terminate` returns the `entry.completion` that the tail runs inside.
