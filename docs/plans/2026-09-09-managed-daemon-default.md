# Managed daemon 默认实现：首阶段实施计划

更新日期：2026-09-15；本次切片父提交 `306cf17546`，历史段落中的基线与验证范围仅适用于各自阶段。完整范围与 C01～C18 能力/入口/状态/验收总表见[默认替换总方案](../design/managed-agent-daemon-default.md)，三层责任与接口见[Session / Harness / Runtime 全局架构](../design/managed-agent-session-harness-runtime.md)，实施依照[全量详细设计](../design/managed-agent-full-design.md)。历史 D1～D5 不再单独决定当前执行顺序。在保留当前 4170 预览、用户数据和已验证能力的前提下，先抽出权威 Session 服务并接入完整 Harness，再完成创建时的兼容选择与普通 factory，让兼容范围明确的新 daemon 会话使用 Managed 默认实现。保持现有 Agent 行为，不把局部验收扩大为全部默认替换完成。

## 当前优先顺序

| 顺序 | 工作                                                             | 完成证据                                                                                                                                                              |
| ---- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1   | 固定 owner 和配对 Bridge                                         | 持久引擎、共享准入、实际回执和发送/取消/恢复归属保持；已有专项验收，不等同普通默认接通                                                                                |
| R2   | Session/Harness/Runtime 拆分、有效配置与四处 factory 接线        | 先证明独立 Session 权威、完整 Harness 重建、持久等待与原调用回执恢复，再验证 selector 和四处普通接线；生命周期与共享预算一致                                          |
| R3   | 普通 Web Shell/SDK 核心链路和必要故障验收                        | create/prompt/events/transcript/cancel、队列、权限、重连、冷恢复、写失败、取消/关闭、重复请求和多工作区通过；MCP/Hooks 依赖及 Channels 来源保留原路径                 |
| R4   | 有限范围默认启用                                                 | primary/secondary/replacement/直接嵌入四处默认工厂策略一致，只有兼容范围明确的新会话默认 Managed；现有会话 owner 稳定，延期能力继续原路径，代码/方案/指定远端分支一致 |
| R5   | 按后续优先级接入定时任务核心链路及补齐延期能力，扩大默认适用范围 | 手动和自动定时任务均符合实际执行/取消/恢复契约；每种新增能力独立验收后再扩大默认选择，不将有限启用等同全量迁移                                                        |

R1/R2 原对应旁支十项清单的第 6 项，R3 对应其第 7 项普通 Web Shell/SDK；本轮按最新要求在 R2 前半段加入三层拆分，不能继续只按旧旁支顺序接 factory。正确工作目录、信任状态、模型与权限配置，有效 MCP/Hooks 依赖和 Channels 来源的识别，以及权威会话持久化与恢复是必要基础，不能一并延期。

## 延期范围与保留行为

首阶段不新增 MCP、Hooks、Channels 的 Managed 接入迁移。旁支第 2～5 项的完整迁移也暂缓：图片展示/产物访问；工作区初始化、Skills 与有效配置；后台进程/子任务/自动记忆；文件历史/撤销/分支/历史迁移。已经验证通过的现有实现保留。最小配置和 owner 恢复属于当前必要基础，与这些完整迁移区分。

当前 PDF 物理取消修复及在途验证已经收尾；Harness PDF 转写等媒体设计保留，不把完整媒体迁移作为开始执行引擎选择调查或实现的额外门槛。依赖延期能力或兼容性不明的会话在创建时固定 legacy。旧实现的保留是明确的入口/配置兼容策略，不是失败后的隐式降级；运行中配置变化不能悄悄更换 owner。

**R2.S1b 独立审查发现两处必修并已修复**：其一，`commit()` 没有事务级串行——lease 只按行串行，两个未交错 `await` 的事务都通过了序号检查，随后各自的行在 lease 队列里交叉排队，实测产生重复序号且该会话**永久不可打开**，走的还不是有既定补救语义的坏尾错误。现已由 authority 自有串行尾包住整个事务，序号在锁内读取。其二，activation fence 原先只做单调 epoch 比较：日志从未提交任何 activation 时，harness 自报任意 epoch 被接受；activation 转为 released/revoked 后仍可继续追加；coordinator 还能自报 epoch。现改为按已提交事实授权——必须存在已提交 activation，`activationId` 与 epoch 精确相等，phase 仍为 installing/active；`activation.changed` 的 epoch 由 authority 判定（新 activation 必须为当前 +1，同一 activation 改 phase 不得改 epoch）。同轮另修四项：恢复扫描不再静默跳过 header 之后的未知 subtype 与中段空行（§4 规则 6）；`eventId` 全局与事务内唯一（原先同一 `inputId` 换 `commandId` 可追加出重复事件，与验收行「重复 ID 唯一」不符）；重放回执改报当前 `committedSequence`（原先返回历史值，调用方据此设 `expectedSequence` 必然冲突）；类文档不再声称本类提供了它当时并未提供的事务边界。

**该切片的独立审查发现一处阻塞级数据销毁并已修复**：header 独立成行且其后没有 commit marker，因此会话第一个事务崩溃时 `committedBytes` 仍为 0，`truncateTo(0)` 会清空整个文件——header 承载 sessionKey 与 definition/rootSnapshot 引用，删掉后会话永久无法打开（审查者实测 1591 字节 → 0 字节）。现扫描额外记录 `headerBytes`，恢复保留 `max(committedBytes, headerBytes)`；两者皆为 0 时明确拒绝而不是清空。同轮另修三项：诊断副本改为先写 `.pending`、截断成功后才改名发布，截断失败即清理，避免留下孤儿诊断文件并覆盖上一份；被丢弃字节改为按 `Buffer` 切片而非解码后的字符串（撕裂在多字节字符中间时字节数不符）；`truncateTo` 补齐 append 路径的错误归一化（原始 errno 不再逃出 `SessionWriterError` 体系）与重建 pin 时的 `sameFileSecurityMetadata` 校验。新增用例覆盖「第一个事务未提交 → 恢复后 header 仍在、会话可重开、序号从 1 继续」与「无前缀可保留时拒绝」。

**静止期防写屏障已交付，并修正了对 schema 3 的定位**：实测（一次性探针）发现三件事——`release()` 会把锁整个删掉，Managed 会话静止时**锁目录为空**；因此任何 writer 都能 acquire 并往权威日志里追加 legacy 记录；追加之后 authority 再也打不开该日志（`unknown subtype ... after the Managed header`），会话被永久废掉，且这条外来记录不计入未提交尾部，坏尾恢复也救不了。**结论：仅把锁版本升到 schema 3 在静止期没有任何作用，因为静止期根本没有锁。**规范 §1 真正承载屏障的是「Managed 关闭保留经过核验的 sealed 锁」，schema 版本只是在此之上再挡掉懂得认证接管的旧二进制。据此本轮先交付 sealing：`LocalManagedSessionAuthority.close()` 用 `sealForHandoff()` 取代 `release()`，`acquireWriter()` 统一以 `takeoverPolicy: 'certified'` 取回自己的封存锁——封存锁遇到默认策略的 acquire 会直接 `SessionWriterConflictError`，认证接管则会拿 sealed proof 与实际文件核对。证据：3 项定向单测——封存后普通 acquire 被拒且 transcript 行数不变；Managed writer 能接管自己的封存锁并从序号 3 续写、再封存、再冷接管读到 4；封存后被外部追加则接管被拒。顺带修正 authority 测试夹具：封存会记录相对 runtimeBaseDir 的 transcript 路径，原夹具把 transcript 放在 runtimeBaseDir 之外（append 能过、seal 不能过），现改为经 `Storage` 派生的真实布局。`managed-runtime` 44/141 项与 `session-writer-lease`、`sessionService` 合计 478 项通过、3 项跳过，仓库 build/typecheck 与 eslint 通过。

**释放的时机只有一个安全窗口**：`beginClose()` 已经把 `acceptingWrites` 置假，所以 `closeSessionWriter` 内、recorder `close()` 之前，是唯一「不会再有新记录到来」的位置——若在此之后才释放，任何仍在队列里的记录都会指名一个已 released 的 activation 而被 fence 拒绝，`flush()` 抛错、recorder 进 `integrity_failed`。因此 Config 在该窗口内先 `flush()` 再释放，并把失败**收集**而不是抛出：下面的封存才是静止期屏障，丢掉它比留下一个看起来被遗弃的 activation 更糟。装配的 `close()` 同理补齐了对称性——自己持有整个生命周期时先释放再封存，否则独立打开的会话会永远留下未释放的 activation。证据：新增 1 项端到端单测（真实 `Config.initialize()` + 真实 lease）断言 activation 事件恰好是 `['active','released']`、`workerId` 为会话身份、`installRef`/`boundaryRef` 均非空、且 `message.committed` 的 subject 指向该 activation；装配用例改为断言「打开即安装、记录自动归 harness」，不再手工构造 coordinator 事件。**反向对照**：去掉 Config 的释放后该用例立即失败。`managed-runtime` 全量、`src/services` 全量、`src/config` 与 `sessionStorageUtils` 合计 3547 项通过、21 项跳过，仓库 build/typecheck、eslint 与 prettier 通过。**仍未覆盖**：过期不被强制、没有续租与撤销（`revoked` 从未被写入）；`FileManagedActivationStore`／`EmbeddedHarnessScheduler` 这条**队列侧**仍未接线，本片只打通了「谁在推进日志」的记账；`chat_compression` 映射至此解除阻塞但尚未实现。

**读取侧同时改对了一处会造成错误历史的写法**：只读投影现在也返回压缩通道（`summaryRef` → 原 `chat_compression` 记录）；更关键的是 `SessionApiHistoryAccumulator` 本身就会在看到压缩快照时**重置**已累积的历史，而我之前在 Managed restore 分支里写的是 `if (record.type !== 'system') apiHistory.add(record)`——压缩记录正是 system，于是会被静默丢掉、把压缩**之前**的全量历史当成模型历史重建。现改为逐条全交累加器（它自己会忽略非压缩的 system 记录），与 legacy 语义一致。同时删掉 sink 里一个只写不读的计数器（我自己早前留下的死字段）。

证据：sink 层新增 1 项（提交出恰好一条 `context.compacted`、`replacedMessageIds` 等于区间内的消息 id、`fromSequence` 为 1、`summaryRef` 读回等于原记录、且压缩**不出现在消息投影里**、缺 `compressedHistory` 被拒）；端到端新增 1 项：真实 `Config` 下 `recordChatCompression` + `flush()` 不报错（未映射时这里就会抛），且 restore 的 `apiHistory` 等于压缩快照而不是被替掉的那一轮。**两项反向对照**：把 `chat_compression` 从 allow-list 去掉后该端到端用例失败；把 restore 分支改回按 type 过滤后同一用例也失败。`src/managed-runtime`、`src/services`、`src/config`、`src/utils` 全量 186 个文件 7620 项通过、24 项跳过（本轮 storage 环境失败未出现），仓库 build/typecheck、eslint 与 prettier 通过。**仍未覆盖**：`replacedMessageIds` 在极长会话上会接近事件字节上限（1 MiB，约两万多条消息），到时会是一次响亮的解析失败而不是静默损坏，但需在默认启用前处理；`goal_state`/`goal_runtime` 与 `file_history_snapshot` 仍未映射。

**`goal_state` 与两类带 subtype 的用户消息已映射**：`goal_state` 是 system 记录、承载 Goal 快照，因此走 `goal_state` domain（该 domain 本轮从注册表里启用；自动任务规范说明 Goal 正文即「原完整 Goal 状态」）。正文**嵌套**在 `{record: …}` 下而不是展开——authority 会把 `operationId/revision/previousRecordRef` 与 content 平铺在同一个对象里，展开整条记录会让它与这三个字段并列并可能撞名。actor 用 `trusted_entry` 而不是当前 harness：`domain.committed` 的 actor 表只允许前者（**实测被拒后才发现**，报文 `domain.committed must not be requested by harness`），这与规范一致——领域记录由受权入口提交，activation 只是资格条件，不是作者。

**`goal_runtime` 与 `mid_turn_user_message` 不是领域状态而是消息**：两者都是 `type: 'user'` 加一个 subtype，标记消息「从哪儿来」，因此走消息通道即可，投影会原样还原 subtype（此前 sink 只允许 `subtype === undefined` 的用户记录，会把它们全部拒掉）。

**读取侧同步补上 Goal 恢复**：Goal 快照现在会被只读投影带出来（`domain.committed` 中仅 `goal_state` 域的正文是「整条记录」，其它域各有自己的正文形状，故只投影这一个域），Managed restore 分支据此按与 legacy 相同的方式收集 `isGoalRecoveryCandidate` 并 `selectGoalRecoveryFromRecords` 选出恢复源——否则会出现「Goal 写进了日志、恢复时静默丢掉」。证据：sink 层新增 2 项（Goal 快照提交为 `domain.committed`、domain 为 `goal_state`、正文里的 `record` 等于原记录且 `revision` 为 1、且**不出现在消息投影里**；带 subtype 的用户消息经投影后逐字段等于原记录），端到端新增 1 项（真实 `Config` 下 `recordGoalState` 不再失败，且 restore 的 `goalRecords` 恰好是一条 `goal_state`）。**反向对照**：去掉 restore 分支里的 Goal 收集后该端到端用例立即失败。`managed-runtime` 全量 179 项通过；`src/managed-runtime`/`src/services`/`src/config`/`src/utils`/`src/goals` 全量除下述既有环境失败外全绿，仓库 build/typecheck、eslint 与 prettier 通过。

**两处仍未覆盖，均已定位到具体原因**：其一，**Goal 证据窗口未投影**——legacy restore 会用 `GoalEvidenceCheckpointAccumulator` 按选出的 pending goal 再扫一遍证据记录产出 `goalCheckpointWindow`，Managed 分支目前不产出，因此恢复后 Goal 的证据 cursor 无法校验；这需要在选出恢复源后做第二遍扫描，是独立的一片。其二，**`file_history_snapshot` 仍被拒**，原因不是漏做而是**封闭 domain 注册表里没有它的位置**：存储规范说会话保存 backup manifest/revision，工具与历史规范把它挂在 `history_rewind` 操作下，而注册表里的 `history_rewind`/`history_copy`/`history_maintenance` 都是「维护操作」而非快照仓库。所以它需要一次设计判断（归入某个既有 domain，或修订注册表），不应由实现私自选名。

**Goal 证据窗口已补上**：上一片留下的缺口是 Managed restore 不产出 `goalCheckpointWindow`，于是恢复后 Goal 的证据 cursor 无法校验。该窗口的作用域是「选中的 pending goal 加它的 permit」，因此只能在恢复源选出之后再算一遍；而 Managed 分支手里已经有全部投影记录，所以直接把它们交给既有的 `buildGoalEvidenceCheckpointWindow()`——**没有另写一份**：那个函数本身就做「记录→hint、取候选、capture、finish」四步，自己再驱动一遍累加器等于留下两份要同步的实现。证据源不可用时按 legacy 同样的方式降级（`EvidenceSourceUnavailableError` 记 warn 并返回 undefined，其它错误继续抛）。

`readAggregatedRecords` 对 Managed 改从投影取正文。抽出来之后 `readPage`、turn 导航、分支点、goal 位置会一起变成投影可用，属于独立一片。

**自审发现并修掉两处「分页当全量」的截断**（同一根因，都在本轮及上一轮自己写的 sink 里）：`authority.readEvents()` 是**有界前缀读**（默认 100、上限 256，从序号 1 开始），不是「取全部事件」。①`commitBranchCheckpoint` 原本用它找上一条 `checkpoint.committed` 来串链，于是**第一条 checkpoint 一旦落在 100 之后，第二条就把 `previousCheckpointId` 写成 null**，日志里的链断掉且不报错。②更早落地的 `commitContextCompacted` 用它算 `replacedMessageIds`，于是一次压缩会**声明替换整段区间、却只列出其中前一页**。已证明的是事件的替换 ID 集合不完整，尚未用该变异验证下游是否残留消息。修法是给 authority 加两个明确的访问器：`lastEventOfKind(kind)`（从尾部倒查）与 `eventsInSequenceRange(from,to)`（整段），并在注释里写清「需要最新/整段的调用方不能走分页读」。证据：一条用例先写 110 条消息、再写 checkpoint#1、再写 2 条、再写 checkpoint#2，最后写一次压缩；断言 `previousCheckpointId === checkpoint#1` 且 `replacedMessageIds.length === 112`。**反向对照**：把两处分别改回分页读，前者得到 `null`（期望 checkpoint#1），后者得到 `99`（期望 112）。`managed-runtime` 全量 180 项通过。**方法论**：这条的第一版用例把 110 条填充写在 checkpoint#1 **之后**，于是改回分页读时用例照旧通过——**反向对照通过并不等于代码没问题，也可能是用例没复现出场景**；必须先确认用例真的把目标事实推到了越界位置，再拿它当证据。

**CLI 宽范围验证仍未通过，不能取消验收门槛**：`src/serve` 与 channel 批次有 12 个文件、32 例失败（真实退出码 1）；全 CLI 批次有 42 个文件、273 例失败和 26 个未处理 RPC 超时。此前测试输出经过管道过滤，工具显示的退出码 0 不代表 vitest 成功。带与不带 `@qwen-code/acp-bridge/channel` alias 的同组 12 文件复跑分别有 104 与 103 例失败，目前只比较了按文件汇总的数量，没有完成逐用例归因；这既不能证明失败集合一致，也不能证明 alias 无回归，更不能仅凭数量变化认定为资源争用。alias 修复后的 Managed channel 定向测试通过只证明该窄范围。宽范围失败仍须复现、与基线对照并修复或明确归因，不作为豁免条件。

**R2.3 的四处 factory 已定位，但拓扑差异必须先在方案里写明**：`runtime.createSpawnChannelFactory` 出现在 `run-qwen-serve.ts:5473`（primary）、`:6397`（secondary）、`:7377`（新增/替换 workspace）与 `server.ts:1221`（直接嵌入），这就是「四处」。它们都生成**子进程** channel（processRegistry、childHeapPolicy、pipe 限额与指标、崩溃隔离都建立在「有子进程」之上），而 `createManagedAgentChannelFactory` 生成的是**同进程内的 in-memory channel + 本地 ACP host**。因此 R2.3 不是把一个 factory 换成另一个的一行改动，而是要同时回答：子进程堆预算在无子进程时如何记账（`limits.memory.enforced` 不能声明未发生的强制）、processRegistry 与诊断行如何归属、崩溃半径由进程隔离变为同进程后如何限制、以及验收行里那条「并发预算不翻倍」。这四处任一处切换都会改变 daemon 默认路径，因此在方案给出上述答案并逐处验收前不切换。

**`managedSessionLogEnabled` 现在由 host 事实推导，不再是只有测试会设的开关**：`loadCliConfig` 从来没有把这个参数传给 core，于是一个装了 `managedToolSessionFactory` 的 host 会在四处地方声明 `sessionExecutionEngine: 'managed'`（CLI 侧 `config.ts:2114` 的恢复守卫期望值，以及 `acpAgent.ts` 的 new/load/resume 三处），而 `Config.activateChatRecording` 因为 `managedSessionLogEnabled` 为假走进 legacy 分支，**把一条 `managed` 引擎记录写进 legacy transcript**——声明与物理格式不一致，且没有任何 Managed reader 能解释它。现在 `loadCliConfig` 用同一个事实推导（`hostPolicy?.managedToolSessionFactory !== undefined`）：两处推导同源，就不可能互相矛盾。回滚开关在上一层——入口是否装 Managed factory——而不是再加一个可能与引擎声明不一致的布尔。core 侧的 `params.managedSessionLogEnabled` 保留，其「关掉即逐字节 legacy」的反向对照用例照旧成立。证据：CLI `config.test.ts` 两条新用例（装了 factory + 开 writer lease → `managedSessionLogEnabled: true`；不装 factory → false），把参数中和掉后正向用例失败。

**顺带修回一处合并回归（只有测试能发现）**：`packages/cli/vitest.config.ts` 里本分支自己加的 `@qwen-code/acp-bridge/channel` 源码 alias 在上游合并中被丢掉了（上游从未有这一条，故 `--ignore-whitespace` 回放不会补上）。后果不是导入失败而是**类身份分裂**：`/bridge` 走源码、`/channel` 走 `dist`，于是 bridge 内部 `error instanceof AcpChannelTeardownError` 对 factory 抛出的同名错误一律为 false。表现为 `managed-agent-channel.test.ts` 两项失败：一项 `toBeInstanceOf` 直接不匹配，另一项更隐蔽——`bridge.shutdown()` **正常 resolve** 而不是把 teardown 失败带出来。在本轮修复前 HEAD 上复现了这两项失败，检查合并父提交确认合并前有该 alias、上游没有、合并结果丢失；补回后 18 项全绿。没有实际运行合并前完整检出，不能把其测试状态记作已验证。**教训写进方法论**：合并完整性不能只靠反向 patch 审计，也不能只跑被冲突文件自己的测试——本分支独有的构建/测试配置项最容易在「取本方版本再回放上游补丁」时静默丢失。

**Managed 会话的 turn 导航已交付**（合并后复核 read-path 时发现的静默缺口）：`readTurnIndexPage` 的 turn 来自物理记录上的 `navigationKind`，而 Managed 日志里只有 wrapper 记录，没有任何记录带该标记——于是一个有历史的 Managed 会话被报成 `totalTurns: 0`，Web Shell 的 turn 列表会是空的，而且不报错。先用真实夹具复现（真实 `Config` + 真实临时目录，录两轮后读到 0 个 turn），再修：`readTurnIndexPage` 在索引带 Managed header 时改从投影取 turn，规则与索引构建器一致——带 `navigationKind` 的 user 记录开一个 turn，assistant 预览候选挂成该 turn 的 `finalAssistantRecordId`（`realtime_message` 挂到 realtime turn），`turn_result` 盖上 `promptId` 并关闭该 prompt turn；投影就是 replay，所以记录在投影中的位置即 `replayPosition`。`start`/`limit`/snapshot 校验/标签/详情全部沿用 legacy 那条路径，**只有 turn 与预览的来源不同**，因此 legacy 行为逐字不变。证据：该用例断言两个 turn 的标签、序号，以及「默认 limit=1 取到最新 → 用它的 snapshot 加 start=0 取到最早」的分页往返；`managed-session-log` 10/10，`session-transcript-reader` 与 `sessionService` 391/391 无回归，仓库 typecheck 与该两文件 eslint/prettier 通过。

**该切片的已知代价**：turn-index 与分页都从投影取记录。物理索引仍对 wrapper 无法回答导航问题；投影现按物理索引弱引用缓存，并受该索引冻结的 `snapshotSize` 约束（见本次切片）。覆盖面也与 legacy 相同：只有用户提示与 realtime 两类 turn，Managed 会话看到的 turn 集合与它作为 legacy 时一致。

**文件历史已交付，`file_history` 成为第 31 个 domain（契约变更，已获确认）**：`file_history_snapshot` 是 sink 最后一个仍拒绝的形态，也是开启 `managedSessionLogEnabled` 的最后一个阻塞项——一旦启用，任何做过文件快照的会话都会在写入时抛错。封闭的 30 个名字里没有文件历史：`history_rewind`/`history_copy`/`history_maintenance` 分别是回退、复制与归档维护，都不是「某一轮提示为哪些文件留了备份」。三个选项里，复用 `resource` 需要连带实现尚未落地的 admit/commit/pin/release/collect 生命周期；暂缓则让 Managed 会话静默失去文件回退，与「保持现有功能」和 S06 冲突。因此按规范自己的规则（新名字必须新增显式 schema/producer/consumer）补一个 `file_history`：producer 是 recorder 的 sink，consumer 是消息投影加既有 `SessionFileHistoryAccumulator`。

**每个批次是独立记录，而不是折叠后的 latest-wins 正文**：折叠正文会迫使 writer 在每次冷重开后先读回已累积的快照，否则用部分知识写出的正文会静默丢掉更早提示的备份——这正是本方案反复标记的那类缺陷。现在每批快照作为一条 `domain.committed(file_history)` 提交，reader 用与 legacy 完全相同的有界累加器折叠，因此恢复出的快照集合逐项一致。证据：新增用例录两批快照、关闭、冷读恢复投影，断言 `fileHistorySnapshots` 为 `['prompt-1','prompt-2']`（折叠正文会只剩后者）、transcript 里**没有** legacy `file_history_snapshot` 记录、日志里恰好两条 `file_history` domain 事件；变异验证：去掉 sink 的接受分支后该用例以「no mapping yet for a system record with subtype file_history_snapshot」失败，说明断言确实在检验这条通路。同轮把 Managed 恢复投影接上累加器（此前只有 legacy 路径折叠文件历史）。`managed-runtime` 全量、`managed-session-log`、`session-transcript-reader`、`sessionService`、`chatRecordingService` 合计 715 项通过，仓库 typecheck 0 error。两条原有契约断言按新事实改判：sink 的「仍未映射即拒」用例改用 `rewind` 与 `session_source`，domain 索引用例改为 31 且显式断言含 `file_history`。

R4 仅是兼容范围的有限默认，不结束总目标。R5 继续手动/自动定时、内部自动执行、媒体/产物、Skills/本地初始化、MCP/Hooks/Channels、后台 Shell/PTY/子任务/记忆、物理历史与全部客户端/平台组合。各项调用者、协议、状态转换和迁移/失败策略已经补齐；实施时落实相应 validator、适配与可执行验收计划，完成后更新总表状态和允许范围。
