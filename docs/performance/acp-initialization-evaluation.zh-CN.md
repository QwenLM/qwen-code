# ACP 初始化性能评估

[English](acp-initialization-evaluation.md) | [简体中文](acp-initialization-evaluation.zh-CN.md)

最终整合源码与同版本干净 main 进行八对交错对照，首个完整 SDK create 中位数从 **815.994 ms 降至 706.277 ms**，均值从 **833.257 ms 降至 719.861 ms**。第 7 对候选更慢，仍完整保留。**两侧均无首 SDK 低于 500 ms 的结果（各 0/8），目标仍未完成。**

本报告覆盖 [PR #17177](https://github.com/QwenLM/qwen-code/pull/17177) 独立合并 watcher 优化之后、本地重建私有安装负载的测量，不代表已部署预发实例的时延。公开内容不包含私有正文、安装名称、manifest、标识、路径或原始日志。先列当前源码对照，后续旧组件、运行时及缓存队列分别保留各自条件与观测。

## 当前整合源码范围

当前对照使用干净 main 6f754be6548903e545e6ff0ed43a34927fe3bfb9 与 42 文件的测量快照：**25 个生产文件、11 个测试文件及六份双语文档**。PR 随后更新一份既有受管初始化测试，以匹配新增的可选私有参数；25 个生产文件与测量快照保持不变。两侧均已包含合并的 watcher 修改。源码组合包括初始化内 ripgrep 重叠/取消、单个 Extension 内独立资源并行发现、attach/export 和定时任务来源的导入削减、有界重复 YAML 解析，以及顶层 CLI 命令按需注册。后文六文件保守初始化实验属于较早的组件队列，不是本轮最终候选。

YAML 缓存最多准入 256 个成功的原始对象，单个输入不超过 16,384 个 UTF-16 代码单元。每次返回均重新创建清理结果；诊断、无效输入和动态调试变量保留既有解析路径。CLI 注册保留 15 个原命令的语法和顺序、auth 的早期翻译快照、update 的 getter，以及选中命令原有同步 builder/handler。原始名称及补全标记的保守匹配可能额外加载实现，但不会派发执行。

不新增设置或 daemon 路由。既有 readiness、认证、信任、工作区激活和工具决策保留原路径。本源码候选不包含 resolver hook、已安装 AOT 缓存、launcher/GC 策略、minification 修改或首次工具初始化延迟。测量结果属于整个源码组合，不能拆为各项单独贡献。

主时钟包含完整 await SDK create-or-attach：capabilities GET、session POST、JSON 解码及 SDK 身份校验。开始时 daemon 已就绪，但没有会话或 ACP 子进程，真实子进程在调用内启动。另行计量 daemon spawn 到首 SDK 完成；等待 daemon 就绪不等于通道预热。

##### 修正父子进程缓存 namespace

后续检查确认，上述诊断的 V8 缓存标识不同：父进程启动时没有 `--expose-gc`，生产 ACP launcher 为子进程增加了该参数。[Node v26.7.0 实现](https://github.com/nodejs/node/blob/v26.7.0/src/compile_cache.cc) 将 V8 cached-data version tag 纳入缓存 namespace。在本机 runtime 上，GC 参数会改变该 tag，单独调整子进程 heap 上限则不会。隔离原生 trace 证实，参数不一致时查找 miss，一致时缓存被接受。因此，上述配置没有测到成功共享缓存的场景；它的负面时延结果仍对该配置有效。

新的三臂诊断固定相同冻结组合 bundle、完整资源及 SDK。A 使用原父进程参数且不 flush；B 为父进程增加标准 `--expose-gc`，不 flush；C 使用相同父参数，在产品 `runtimeReady` 之后、harness 就绪之前 flush daemon 已经需要的模块。没有为填充 ACP 缓存额外导入模块，也没有预加载 channel 或会话。顺序轮换为 A/B/C、B/C/A、C/A/B，每行均使用全新 runtime 与缓存根目录。

另一项无 trace 资格试验仅按候选构建 metadata 选择全部 **787** 个符合条件的生成 main-build ESM 输出，不依赖私有运行 trace 选择目标。一个固定 Node26.7/default-flags producer 在应用正文求值前到达标准 loader 的精确 missing-export 屏障。787 个源码均有独立 cold lookup、write 和 rename 证据；缓存为 788 文件 / 20,342,704 字节，包含一个编排辅助模块。该资格试验仅复核符合条件的源码、固定输入和 Node 二进制，没有重新审计六棵完整应用/SDK/seed 树。

源码 PR 尚未实现受管安装和 launcher 启用。实际集成必须在最终安装路径落定后生成与源码/运行时绑定的缓存，验证真实消费后才能宣称优化模式生效。生成成本位于会话时钟外，但仍需报告。下游 Dockerfile 固定 Node22.23.4，这只是 checkout 证据，不是运行中实例版本。本地 Node26.7/macOS/arm64 结果不证明该镜像行为或已部署预发时延。

## 复现与剩余验收

[PR #17177](https://github.com/QwenLM/qwen-code/pull/17177) 仍提供公开合成生成器及无预热 SDK 流程。测量前为各冻结条件准备独立全新 fixture；串行交错条件，保留全部失败/慢观测，并执行完整会话、关闭和完整性门禁。合成数据能复现方法和规模调查，但与私有清单的目录结构、字节和激活准备不同，不能复现其精确时延。

当前纯源码对照的首 SDK 中位数改善 **109.717 ms / 13.45%**，均值改善 **113.396 ms / 13.61%**；总时钟中位数改善 **71.314 ms / 4.90%**，均值改善 **133.252 ms / 8.78%**。两个条件中位数之差不同于同对差值的中位数。两侧均未达到 500 ms，每侧八个本地首会话也不能建立尾延迟 SLA。后续优化必须保留完整 readiness，同时报告移至安装、启动、菜单或首次工具使用的工作。当前源码、历史组件及手动选择缓存的结果必须保持独立。
