Grep 引擎性能基准报告

main GrepTool（git grep → system grep → JS 回退）vs v1.0.0-preview RipGrepTool（ripgrep）

测量日期：2026-11-17 · Apple M4 / 10 核 · git 2.50.1 (Apple Git-155) · BSD grep 2.6.0-FreeBSD · ripgrep 15.0.0

语料：qwen-code 工作树（15,131 个 git 跟踪文件 + 138MB gitignore 的 dist/）。node_modules 不在实测语料内：修复前的 system grep 与 JS 回退都已排除它（前者用 §1 列出的 --exclude-dir，后者把同一份列表交给 globStream 的 ignore），初版此行把它算进“污染”是错的。

配套 PR：GrepTool 回退链 gitignore scope 修复 · 原始数据见同目录 bench-grep-*.json · scope 边界复现见 scope-repro.sh

1 · 方法

  • argv 逐字取自两边工具源码：main git grep 含 NO_EXEC_CONFIG（-c core.fsmonitor= -c log.showSignature=false）+ --untracked -n -z -E --ignore-case -e P；main system grep 含 5 个 --exclude-dir（node_modules/.git/bower_components/.svn/.hg）+ -r -n -H -E --null -e P .；preview rg 含 --hidden + 6 个 VCS --glob（!.git/!.svn/!.hg/!.bzr/!.jj/!.sl）+ --max-columns 500，files 模式 -l --null、content 模式 --json -n，路径操作数 .。
  • rg 必须带路径操作数：无路径且 stdin 非 TTY 时 rg 读 stdin，会永久阻塞（基准 harness 曾踩此坑；preview 源码在 -- 后传 searchTarget）。
  • 采样：快引擎 1 预热 + 5 测量取中位；system grep（单轮 ~60s）与 JS 回退 1 预热 + 1 测量（样本量已披露）。每项完成即增量落盘。
  • 归一化组：rg 加 -i 对齐 main 的忽略大小写默认，隔离"引擎速度"与"默认语义"两个变量。评审前该默认并不覆盖策略 2：策略 1（git grep）传 --ignore-case、策略 3（JS）用 new RegExp(pattern, 'i')，而策略 2 的两条 system grep argv 都不含 -i，与工具描述承诺的 “Case-insensitive by default” 相矛盾（实测同一语料上 12.6% 的匹配集仅因大小写而不同）。 评审后已给 scoped argv 补上 --ignore-case，因此下文“修复后”的 system grep 计数就是 shipped 行为；只在无 git 环境才会走的递归 argv 仍缺该标志，属 main 既有缺口，列为 follow-up。
  • 计时含 stdout 传输与流式计数（不累积全文：system grep 单轮输出 1.2GB，超 V8 字符串上限）。
  • 子进程生命周期：harness 对每个 child 挂 abort/超时 SIGKILL，并在父进程退出时清理——被 SIGKILL 的父进程不会运行 exit handler，孤儿 rg 会阻塞在写满的管道上（实测挂起 1h+、0 CPU）。

  • rg vs main 回退链：快 380–900×。回退的慢 主要源于 scope 错误（不尊重 gitignore，扫 dist/），但初版"不是引擎慢"这句不成立：§3 在同一份语料上修掉 scope 之后，回退仍是 git grep 的 11.1×/5.5×/14.8×（7,386.9/11,292.1/5,687.8 ms vs 666.6/2,066.1/385.2 ms），残余开销与修复后的总耗时同数量级。
  • scope 等价实证（仅限匹配计数）：rg -i 匹配数与 git grep 逐模式完全相等（50,567 / 114 / 0）；system grep 20× 污染、absent 模式在 ignored 文件命中 3 次。文件数并不相等：git grep -l -i = 7,237 而 rg files -i = 7,228，这 9 个文件的差本页未逐项对账（最可能来自二进制与符号链接的处理 差异，见 §3 的 (2) 与 §4 的符号链接行），因此"等价"只在匹配计数层面 成立。
  • absent 模式合并后不可复现（披露）：本页把标记 zzqxx_absent_token_9f3e 原样印出，而本页与同目录 JSON 都是被 git 跟踪的文件，合并后该 token 就进入了语料 （git ls-files --cached --others --exclude-standard 会列出本页，策略 1 的 git grep --untracked 也会命中）。fixed-results 中 absent string 各行记为 matches: 0，在合并后的 commit 上重跑会得到 1，无法据此区分"正常"与 scope 回归。复现请改用未写入仓库的 token。
  • --json 代价：同匹配集 16.7MB vs git -z 5.5MB（~3× 传输/解码），但引擎优势覆盖格式开销。
  • 默认大小写：rg 敏感 47,678 vs -i 50,567（差 2,889）——采用 preview 默认会改变匹配集（行为 breaking）。

3 · 修复 main 回退链后的对照

修复（本 PR，含评审后修正）：回退策略 2/3 改用 git ls-files -z --cached --others --exclude-standard 语料（与策略 1 同集合），再按 lstat 只保留常规文件——git 同时会列出符号链接、submodule gitlink 与索引里已消失的条目，而 grep 对显式操作数会解引用符号链接，读到搜索根之外的内容；语料还要按 getGlobExcludes() 导出的目录名过滤，因为 --exclude-dir 对显式操作数无效（已实测），而策略 3 把同一份列表交给 globStream 的 ignore，两条回退必须同集合。 策略 2 用显式文件列表 + 128KB ARG_MAX 分批，argv 补上 --ignore-case 以符合工具描述与策略 1；持续消费 stderr（否则逐文件诊断写满管道后子进程永久阻塞），只把 Permission denied 与 Is a directory 之外的诊断留作有界摘要（与递归分支同一套容忍规则），并在 exit ≥ 2 而诊断均属可容忍时保留 grep 已产出的匹配；失败时落到策略 3 而不是回到未限定语料的递归 grep，取消则直接抛出而不降级成“没有 git”。策略 3 按语料身份过滤 globStream，并在会折叠大小写的平台上（darwin/win32）对两侧一并折叠 ——此时 git 报索引拼写、遍历报磁盘拼写，且 --others 视二者为同一文件只列前者。新 spawn 均挂 abort kill。git 不可用时保留原递归行为。

本节 system grep 的测量命令：修复后 scoped argv 为 grep -n -H -E --null --ignore-case -e P -- <语料分批>，与 harness 逐字一致，因此下表“修复后”的匹配数与耗时即 shipped 行为。“修复前”那一列则不是：修复前的递归 argv 没有 -i（当时 shipped 也没有），所以两列的大小写口径并不相同， 详见本节末尾的 (1)。

残留不等价（披露，评审后更正）：修复后文件集等价，匹配计数仍有两处口径问题。

(1) 大小写：已在评审后关闭。 scoped argv 现在传 --ignore-case，与策略 1 和工具描述的 “Case-insensitive by default” 一致，因此下表 50,572 就是 shipped 行为，“vs git grep 50,567（+5）”的等价结论成立（残差来自二进制处理，见 (2)）。但上表“修复前”那一列不是同口径：1,022,948 是当时 shipped 的递归 argv（不含 -i）测得的。统一为都不加 -i 后是 1,022,948 → 47,796（21.4× 缩减，比表中数字更大）；统一为都加才是表中的 50,572。附带实测（2026-11-17， 本 PR 工作树，模式 function，语料 15,197 条、 lstat 过滤剔除 0 条、8 批；原始测量时为 15,134 条）：不加 -i 得 47,796 匹配、grep 累计 3,689 ms；加 --ignore-case 得 50,690 匹配、grep 累计 6,884 ms。只在无 git 环境才走的递归 argv 仍缺 -i，属 main 既有缺口，列为 follow-up。

(2) 二进制处理：初版把原因写反了，此处更正。 初版称“git grep 跳过二进制文件；BSD grep 未加 -I 会报告二进制匹配”。实测（macOS，BSD grep 2.6.0-FreeBSD）：git grep 并不跳过，它对每个二进制文件在 stdout 输出一行 不带 NUL 框架的 Binary file <path> matches（-l 计入该文件、-c 记 1）；BSD grep 不加 -I 时同样把这行写到 stdout。而 GNU grep 把它写到 stderr（grep: <path>: binary file matches），对 stdout 贡献 0——所以同一份代码在 macOS 与 Linux 上的计数本就不同，这也是 fixed-results JSON 必须记录 grep 实现的原因。JS 回退把一切当 utf8 读，是第三个口径（50,734，+167）。初版给的 follow-up “grep 加 -I”不会收敛反而会扩大分歧：加 -I 后 grep 对二进制输出 0 条，而策略 1 仍每个二进制文件输出 1 条。真正的对齐有两条路：让策略 2/3 也按“每个二进制文件计一条”处理，或让三条策略统一忽略二进制。两者均为 follow-up，不在本 PR 范围。

4 · 换引擎的副作用清单（决策输入）

隔离临时仓库实证。复现范围（更正）：scope-repro.sh 覆盖下表的 force-add、.rgignore 与符号链接三行；submodule 那一行没有任何复现路径 ——脚本里不存在 submodule 步骤，所以初版"复现见 scope-repro.sh"对本表整体成立的说法不成立，该行只是阅读 git 文档与代码得到的推断，未经实证。

场景 main git grep preview rg（含 --hidden）
force-add 的被 ignore 文件（git add -f） 策略 1 搜不到（实测更正，git 2.50.1： --untracked 对跟踪文件也套用排除规则；不带它、或用 --cached 才搜到。初版写作"搜到"，而当时脚本的 fixture 里 .gitignore 根本没列 force.txt， git add -f 是空操作，这一行从未被真正复现过） 搜不到（rg 不读 index）
仓库植入 .rgignore/.ignore 不受影响 文件被隐藏（新的仓库可控搜索排除面）
submodule 内容 默认不递归 当普通目录扫
符号链接 整个条目跳过：链接文本与目标都不搜（实测更正， 初版写作"读链接文本当内容"） 递归遇到时跳过；作为显式操作数则跟随（--follow 才在递归中搜目标）

本 PR 修复后的回退链落在哪一侧：符号链接与 submodule gitlink 都被 lstat 过滤掉，语料里根本不会出现它们，因此与 git grep 的"整个条目跳过"一致，也不会跟随目标。修复前更糟——grep 对显式操作数会解引用符号链接（rg 在同样位置也一样），把搜索根之外文件的内容当作仓库内匹配返回， 既破坏与策略 1 的等价，也绕过只校验搜索根的权限边界。

一处修好 fixture 后才暴露的反向差异：语料取自 ls-files --cached，它会列出 force-add 的被 ignore 文件，而策略 1 的 git grep --untracked 不会（见上表实测更正）。所以在这一个边界上回退搜到的是主策略的 超集，"文件集完全等价"的说法在此不成立。本 PR 不做进一步收窄——收窄需要再跑一次 ls-files --cached -i --exclude-standard 并从语料里减掉该集合，属独立改动，列为 follow-up。

  • 依赖（勘误：初版此项写错了 main 现状）：初版称 "main 现状零外部二进制、无 rg 发布管线"，不成立。 main 已 vendor 五平台二进制 packages/core/vendor/ripgrep/{arm64-darwin,arm64-linux, x64-darwin,x64-linux,x64-win32}；useRipgrep 与 useBuiltinRipgrep 默认均为 true；rg 可用时把 RipGrepTool 注册到 ToolNames.GREP，不可用时才回落到 legacy GrepTool；resolveRipgrep 先 bundled 后系统 rg，并含 exec 位修复、健康检查与 macOS 签名。所以"换引擎"在 main 已默认发生，不要据此重复迁移。真正待比较的是 仍会落到 legacy GrepTool 的消费者与剩余差异：rg 缺失或健康检查失败的环境、显式 useRipgrep=false，以及下条列出的集成不匹配。这正是本 PR 修复 legacy 回退链的理由：它是无 rg 环境的唯一兜底。preview 特意用命令名 rg 而非解析路径防 PATH 劫持，这一点仍适用于 main 的系统 rg 分支。
  • 性能正副作用：rg 不刷新 git index——消除冷 index 延迟与 core.fsmonitor helper 执行面（main 现以 NO_EXEC_CONFIG 防护）。
  • 性能负副作用：--json ~3× 字节；files 模式 mtime 排序 = O(匹配文件数) stat；保留 -i 放弃 rg 大小写敏感 SIMD 优化。
  • 生命周期：main 现 grep.ts 的 spawn 无 abort/timeout kill（孤儿风险）；本 PR 已为新 spawn 补 kill；换引擎需把 kill 接入调度器 abort 路径并映射 RipgrepTimeoutError。
  • 集成不匹配（整体照搬 preview 工具的成本）：权限 API（config.permission vs getPermissionManager）、执行契约（defineDeclarativeTool/executeWithContext vs class/execute(signal)）、grepReadTracking 缺失、声明 bundle 基础设施缺失、默认大小写与参数面 breaking。

5 · 结论

本 PR 范围：修复回退链 scope（必要但不充分）——消除 20× 污染与 8–11× 无效扫描；修复后回退 5.5–11.3s，仍比 rg 慢 32–78×，应作无 rg 环境兜底。注：本节倍数与耗时取自带 -i 的测量组；shipped argv 的大小写敏感口径（污染缩减 21.4×、grep 累计 3.7s）见 §3 披露。
  • 建议后续（不在本 PR）：main 已默认把 RipGrepTool 注册为 GREP 工具（见 §4 依赖勘误），所以剩下的不是"换引擎"，而是补齐 rg 路径与 legacy 集成层的差异，让仍会落到 legacy 的消费者不必依赖它：把 PermissionManager、grepReadTracking、截断、策略 1/3 的默认忽略大小写与 -z null 输出格式（模型契约）以及超时与 deny 结果过滤接到 rg 路径上；git grep 降二级、修复后 grep/JS 作三级回退。不整体照搬 preview 的工具实现。
  • follow-up：回退链大小写对齐（策略 2 是否补 -i，见 §3 披露）；grep 回退加 -I、JS 回退二进制嗅探（匹配计数对齐）；deny 结果过滤移植；四类 scope 边界的接受/补偿决策。

验证：packages/core grep.test.ts 61/61 通过（含新增 scope 回归测试）；core tsc --noEmit 退出 0。原始数据：bench-grep-results.json（修复前矩阵，中位转录自完整运行日志 bench-grep-unfixed-run.log，逐样本数组未保留，json 内含 provenance）、bench-grep-js-results.json（JS 修复前 + scope 计数，含样本）、bench-grep-fixed-results.json（修复后矩阵，含样本）。
