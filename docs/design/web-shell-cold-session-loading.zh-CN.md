# Web Shell 冷会话初始化

[English](web-shell-cold-session-loading.md) | [简体中文](web-shell-cold-session-loading.zh-CN.md)

打开没有显式工作区的已有会话时，会话 Provider 会在工作区 capabilities 返回之前挂载。
随后发布主工作区信息会改变会话上下文，重新触发恢复。
使用真实 Providers 和 SDK 的复现观察到，一次导航发起了两次加载、建立了两条事件流，
并断开了过期的客户端连接。

等待首次 capabilities 响应后再挂载已有会话，复用现有的加载与重试状态。
空白输入界面在发现期间仍可挂载；后续发现失败不得卸载 capabilities 已知且未显式指定
工作区的会话。

即使失败的 promise 已从缓存移除，首次发现失败也必须发布工作区错误。
跟踪请求代次，避免迟到的错误覆盖更新一次刷新或其他客户端的状态。
缓存读取不发布工作区状态；其他读取方在请求失败后立即重试时，不得阻止首次错误发布。
错误界面的重试操作会重新发起发现请求；只有该请求成功后，才开始恢复会话。
显示当前错误消息，让首次失败和重试失败都保留可供诊断的原因。

在会话连接的首次渲染中提供已取得的 capabilities。
否则，活动消费者会在发现实时状态支持之前短暂选择完整列表回退路径，
导致多发一次完整会话列表请求。

React StrictMode 还会丢弃并立即重新创建首次连接 effect。
在没有保留会话的情况下，开始连接前先让出一个微任务，并检查该 effect 是否已销毁。
已有连接保留原有的同步启动顺序，以便恢复逻辑在受控 props 的 effect 执行之前，
认领保留的 attachment。

回归测试框架延迟 capabilities 响应，通过真实 Providers 和 SDK 恢复一个保存的历史块。
普通 React 和 StrictMode 挂载都必须只发起一次加载和一次事件流请求，
达到已连接状态并显示保存的历史块，且中途不发生 detach。
现有 Provider 测试覆盖保留的 attachment、上下文变化、重新连接和历史分页。

挂载等待逻辑属于 Web Shell 的产品组合层。
直接组合已导出的工作区和会话 Provider 的宿主，必须等待首次 capabilities 后再挂载
已有会话，并在等待逻辑上方提供发现错误和重试入口。
包 README 中的共享 Provider 示例展示了这一顺序。
本次修改没有移除直接使用会话 Provider 时由上下文变化触发的重启；
实际工作区变化仍必须重新触发恢复。

用户报告会话的隔离副本在 daemon 子进程退出后，恢复耗时约为 1.2–1.4 秒。
本次修改移除重复的前端恢复，不改变 daemon 冷启动或历史存储行为。
