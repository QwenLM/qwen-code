# 延迟工具调用桥接

[English](deferred-tool-call-bridge.md) | [简体中文](deferred-tool-call-bridge.zh-CN.md)

## 问题

此前 `tool_search` 会暴露匹配的延迟工具并刷新模型的工具列表。模型随后可以直接
调用该工具，但每次暴露都会改变请求前缀，provider 无法复用之前的提示词缓存。

## 设计

增加始终可见的 `tool_call` 桥接，保持模型工具列表稳定。延迟工具分两步使用：

1. `tool_search` 将工具名称、说明和参数 schema 作为信息返回，不暴露工具或刷新
   活跃声明列表。
2. 模型通过 `tool_call` 传入准确的延迟工具名称及参数。

两半以相同方式解析请求的名称，因此 `tool_search` 返回的 schema 就是 `tool_call`
调用的工具：先规范化历史别名（`search_file_content` → `grep_search`、
`replace` → `edit`、`task` → `agent`），再按已注册名称精确匹配，最后才是唯一一次
大小写不敏感匹配。若某名称与多个已注册工具仅大小写不同，则不解析到其中任何一个
（注册顺序不起决定作用），两半都拒绝它：`tool_search` 报告歧义并列出确实可解析
的拼写，`tool_call` 拒绝并要求准确名称。仅解析名称不能允许调用：调用者历史中必须
仍然保留 `tool_search` schema 块，以及由该聊天审阅完整 schema 后建立的记录。

`tool_search` 返回工具时，会记录该工具调用契约的指纹——所属 MCP server
（内置工具为空）、schema 中的名称，以及它的 `parametersJsonSchema`。`tool_call`
重新计算指纹，若隐藏工具的当前值不同则拒绝，并提示模型用 `select:<name>` 重新
执行 `tool_search`；重新审阅会覆盖记录，因此该循环一次往返即可闭合。记录不以审阅
时该工具是否隐藏为前提：已 reveal 的工具之后可能重新变为隐藏，把记录挂在 reveal
状态上会让比对的覆盖面取决于模型既不能控制也观察不到的状态。自由文本
`description` 不计入指纹：已发布的延迟工具在每次访问 `schema` 时都会基于可变状态
重建它（`web_search` 插入当前月份，`read_file` 使用当前生效的输入模态），把这段
文字纳入哈希会拒绝那些参数仍与已审阅 schema 一致的调用。

调用时从当前代理聊天重建审阅证据；代理执行之外则使用已初始化的主聊天。这复用
已有代理执行上下文，不把 registry 实例视为会话所有者。继承的历史可以在新 registry
中建立审阅记录；共享 registry 的独立聊天不能借用或清除彼此仍驻留的 schema 证据。
截断块只能保留该聊天自身此前审阅的指纹；新的或独立的聊天不能从片段建立审阅。
调用者历史完全移除该块后，桥接会再次拒绝调用。
查询及未找到名称的回显会转义标签分隔符，防止其中伪造的 `<function>` 块建立
schema 证据。

Schema 结果不经过通用字符、行数和批次输出截断：不完整 JSON 块和持久化输出预览
都不能建立审阅证据。已有 `max_results` 限制一次搜索最多返回 20 个 schema。
单个大 schema 完整返回，仍消耗模型上下文预算；正常的请求上下文限制继续适用。

已有的延迟工具启动提醒提供精简的实时目录（名称和简短说明）。目录不嵌入任一桥接
schema：即使 MCP 工具增删或更新，`tool_search` 和 `tool_call` 的声明仍保持字节
稳定。后续目录变化继续作为尾部提醒发送，不修改模型工具声明。

核心 scheduler 在权限、审批、hook、调用护栏、并发、遥测和执行前解包 `tool_call`。
ACP session executor 也在对应的逐调用策略及执行前解包；其外层批处理对桥接调用
仍保守地顺序执行。无头 CLI 使用解析后的目标处理并发、进度、完成跟踪和输出
收尾。这些消费者接收实际工具名称和参数；返回给模型的 function response 保留
桥接名称和原始 call id，以匹配模型发出的调用。

桥接仅接受隐藏的延迟工具。即时、预加载及显式可见工具仍应直接调用。未知工具、
桥接递归及当前子智能体上下文中不可用的工具都会在执行前被拒绝。

## 兼容性

registry 保留现有 reveal 状态，用于启动预加载、显式可见工具、plan 生命周期配置
和含有延迟工具直接调用的旧历史回放。只有 `tool_search` 不再新增 reveal 状态。

启动预加载改为主动启用：`tools.toolSearch.threshold` 默认值为 `0`。此前默认
预加载用于避免 reveal 重写声明列表并破坏提示词缓存前缀；桥接 reveal 不会重写
列表，因此始终延迟加载的额外成本仅是首次使用前的一次 `tool_search` 往返。
参见 [ToolSearch 预加载阈值](toolsearch-preload-threshold.md)。

在直接工具模式下，禁用 `tools.toolSearch` 也会禁用 `tool_call`；现有回退会即时
声明普通延迟工具的 schema。由 `tools.eager` 降级的工具仍保持隐藏，除非另有暴露
规则；每会话警告说明桥接不可用，但按名称直接调用仍经过正常校验和权限检查。
CodeModeOnly 则通过顶层 `tool_search` 发现延迟工具的 schema，并通过 `exec`
调用它们；`tool_call` 保持隐藏。它会跳过延迟提醒和这条警告。当前作用域无法搜索
时，`exec` 会包含所有允许工具的签名。权限 allowlist 会保留两个桥接工具，除非有
显式 deny 规则移除它们。

在直接工具模式下，子智能体显式 `tools` 列表不会隐式加入桥接工具（Code Mode 会在
`exec` 旁加入 `tool_search`）。列出普通延迟目标会直接声明它，
但 `tools.eager` 的降级仍有效。同时使用发现和桥接调用时，目标本身及两个桥接工具
都要在允许范围内；已有子智能体排除项和 deny 规则仍然优先。恢复 fork 时根据发起它的主会话
重建实时能力，再应用持久化的 fork 策略，不受唤醒调用者的环境 allowlist 影响。
压缩后的文件恢复只在匹配外层响应 ID 后解包成功桥接调用。ACP 参数错误循环计数
使用经过校验的桥接目标名称；格式不合法的 envelope 仍计入桥接工具自身，任何解析
不到目标的拒绝也是如此——歧义名称没有可计数的已校验目标，因此它的那次计数与
格式不合法的 envelope 落在同一个 `tool_call` 桶里。

## 已知限制

审阅证据用于检查 schema 是否可用，不授予权限。即使启动目录列出了名称，调用者
历史中没有自身保留的 schema 审阅记录时，隐藏工具仍会被拒绝。已有权限检查继续决定已审阅工具
能否执行。

仅涉及 `description` 的变化不会被检测到，这是有意为之：这些 getter 必须继续按
当前状态重算，长驻进程才不会跨月或跨会话内切换模型后使用过期文案。

指纹中唯一的服务端成分是 server 的名称标签，因此一个以相同工具名和 schema 重新
发布的替代 server 会被接受，而参数是针对上一次连接写的。要把连接身份与名称标签
区分开，需要 registry 目前不具备的通道；该问题在 #11321 的讨论中跟踪，这里不做
近似实现。

审阅指纹按聊天分别缓存，但调用时以调用者当前历史为准。`/clear` 清空全部审阅；
压缩和历史替换移除块已不存在的记录。保留的截断块只能沿用该聊天自身此前的指纹，
另一聊天的重新审阅不能授权变化的参数契约或 MCP server；调用者仍须重新获取
`tool_search` 结果。

## 验证

- `tool_search` 返回 schema，但不调用 `setTools()` 或修改声明列表。
- `tool_call` 拒绝格式错误、未知、可见、递归和当前上下文禁止的目标。
- 合法桥接调用执行底层 invocation，应用目标的权限及 hook 身份，同时返回名称
  为 `tool_call` 的 function response。
- 直接调用和启动预加载继续正常工作。
- 历史别名在两半解析到同一个已注册工具；`select:` 同时列出别名和其注册名称时，
  该工具只被审阅一次。
- 与多个已注册工具仅大小写不同的名称：`tool_call` 拒绝，`tool_search` 报告歧义并
  列出可解析的拼写，AUTO 分类器转录中仅投影名称，显式列出两种拼写时按两个工具
  分别审阅。
- 已记录指纹与当前指纹不一致的隐藏工具会被拒绝，直到 `tool_search` 再次返回它。
- 聊天保留截断 schema 时，即使另一聊天重审替代工具，变化的参数契约或 MCP server 仍被拒绝。
- 继承历史的聊天及共享 registry 的聊天使用各自驻留的 schema 证据；仅包含任务的
  聊天不能借用父会话审阅记录。
- 超过通用输出预算的 schema 在逐工具截断和批次收尾后仍完整且可调用。
