## 1. Single Container and Version Decisions

Ordinary Managed continues using the original Session JSONL path under its owning workspace/runtimeBaseDir, not a competing history. Add three ChatRecord system subtypes: `managed_session_header_v1`, `managed_session_event_v1`, and `managed_session_commit_v1`. Retain `uuid/parentUuid/sessionId/timestamp`. Domain content inside events is the sole source of truth; readers project ordinary user/assistant/tool/Goal/artifact content instead of appending equivalent old records too. Legacy and experimental logs retain their original formats.

The header records `formatVersion=1, minimumReader=managed-session/1, sessionKey, engine=managed, definitionRef, rootSnapshotRef, createdBy, baseTranscriptProof?`. History import retains the sealed old-record prefix, with its length, hash, and active tail referenced by the header. New events begin at sequence=1; every new reader reconstructs both prefix and committed increments. Empty-session creation commits only the header and triggers neither prompt nor tools.

Compatibility protection does not depend on old readers understanding new subtypes. Managed authority's physical writer uses new lock schema 3 in both active and sealed states. Closing Managed retains a verified sealed-3 lock; only an authority supporting it may authenticate takeover, rather than deleting it via old release into an unlocked state. Current schema-1/2 readers report unknown schemas as malformed and reject, providing a write barrier for baseline old binaries. Display-only old binaries may ignore new subtypes; report “unsupported version” explicitly and never use their partial view as a complete recovery basis.

Acquiring schema 3 must retain an exclusion barrier recognized by old writers too; do not call ordinary `release()` first and leave an unlocked gap. Existing `readOwnedLock` pins both inode and raw lock bytes, so the old lease cannot continue after rewriting its lock. Original authenticated `sealForHandoff` / `takeOverSealed` use `<lockPath>.claim` and exact file replacement; old acquire checks that claim before and after installing its lock. Schema-3 upgrade extends this handoff path, creates a new lease, and does not change the old lease's ownership checks.

Container upgrade order is fixed: no active execution, old writer drained/sealed → authority obtains the same `.claim` → validate old sealed lock/transcript prefix and persist original operationId plan/proof plus schema-3 candidate → identity-protected main-lock replacement inside the claim, with file/directory sync → commit header and migration-completion transaction through the new schema-3 lease → after verifying durable main lock/log, release claim by exact owner. The plan records old lock/prefix proof, target owner/schema/candidate digest, and phase; it is validation material, not exclusion. Exclusion comes from claim and schema-3 main lock. An old binary can win before claim acquisition; then upgrade must not rewrite files, returns conflict, and drains/revalidates again. Old writers reject lock acquisition while claim exists; after claim removal, schema-3 main lock continues preventing writes.

Crashes at every sync/replacement window retain original plan, claim, candidate, and verified copies. A new authority may authenticate claim takeover and resume only after proving original-owner exit and all identities/proofs; never delete claim first and retry. Before schema-3 publication, it may validate/restore the original sealed lock inside the same barrier. Once schema 3 is published or new-format writes exist, complete through the new format or remain blocked, never downgrade to schema 2. Unproven phase/owner retains the barrier; lease timeout, empty PID query, or prefix hash is not takeover proof. This upgrade changes only an existing Managed record container, not a legacy engine in place.

Migration completion uses registered history_maintenance with `operation=format_upgrade, phase=committed`, retaining old/new formats and complete source-prefix proof; its controlled recordRef may serve as section 2.2 restoreProofRef. A pre-header plan is only that operation's handoff material, not a second Session journal or independently committed recovery starting point.

Lock schema 3 adds `formatVersion`; the sealed variant also has `lastCommitSequence, committedPrefixHash`, retaining original owner, process-start identity, and sealed transcript proof. Active locks do not rewrite these commit digests on every transaction: the log commit marker is the current position. Sealing first flushes the log and verifies the complete prefix, then atomically replaces/syncs lock and parent directory. If a crash occurs between them, the new authority authenticates original active owner and log rather than treating stale lock digests as latest commit. Unknown versions cannot be reclaimed as stale. Older programs bypassing the writer protocol are outside compatibility guarantees. Format conversion into an independent new Session follows [tools and history](managed-agent-tools-history.md), without switching executionEngine in place.

Retained sealed schema-3 locks directly affect existing maintenance orchestration: archive, unarchive, delete, rename, and fork take the same lock's maintenance-lease branch, whose malformed-unknown-schema check fails the entire operation. These paths must therefore understand schema 3 first (read sealed variants, verify `lastCommitSequence/committedPrefixHash`, and write back the same schema after completion) before enabling Managed writes; otherwise explicitly reject maintenance with a reason. Removing the lock via old release is forbidden because it loses both sealing proof and write barrier. Managed maintenance admission also follows section 3 lifecycle: close active Sessions first; unknown physical owner cannot advance to closed/deleted.

### 2.1 Resource Storage, Enumeration, and Collection

`DurableRef` wire fields remain unchanged. The owning workspace's trusted registry uniquely reserves resourceId, binds it as `session_owned {sessionKey}` or `workspace_owned {workspaceKey}`, and retains producer, holdings, and access policy. Server establishes ownership; callers cannot self-assert it in payload. Session authority manages only its own refs, resolving shared configuration/pinned content through the authorized workspace registry. Configuration/content operations without Session use actual WorkspaceKey, not a fabricated Session.

### 2.2 Recovery Basis and Null Checkpoints

`restoreBasis` is the closed set `checkpoint | initial | history_rewind | history_copy | format_upgrade`, selected by authority from current active history and committed maintenance proof; Harness cannot choose its own downgrade.

| restoreBasis                                   | Required combination and admission                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| checkpoint                                     | Non-null checkpointRef, restoreProofRef=null. Validate nine state groups, coverage, versions/resources and reconcile subsequent events/original calls. A referenced checkpoint that is absent, corrupt, or mismatched is blocked, not replaced with null                                                                                                                                                                           |
| initial                                        | checkpointRef=null, restoreProofRef=null; complete header/create and original input/queue facts, with no model attempt, tool intent, or other execution continuation. Allows empty creation and cold recovery before first execution, not treating an executed Session as empty                                                                                                                                                    |
| history_rewind / history_copy / format_upgrade | checkpointRef=null and non-null restoreProofRef referencing the committed operation's full proof; baseProjectionRef points to verified selected-target history/recovery basis. Model/tool relationships, configuration, budgets, parent chain, resources, and consumption positions must be reconstructible, without pending continuation; copy includes fork/convert/import. Missing entries/unsettled effects reject this branch |

For the latter three bases, prefer checkpoint when a legal compatible one exists. Null is not the default for failed reads. Legal checkpoint-free recovery initializes only a proven execution starting point without replaying tools. The next valid activation's Harness builds/commits a new before_model checkpoint from it before model requests or new tool dispatch. Maintenance OperationGrant commits only maintenance proof, not manufactured checkpoints; initial create/read starts no Harness. Approval/tool waits within model continuation still need corresponding checkpoint and original receipts. Non-tool actions outside the model restore display/decisions directly from Session facts without requiring Harness/checkpoint merely to await confirmation.

### 2.3 RestoreBundle and Cross-Store RestoreSet

RestoreBundle is authority-provided **single-Session execution recovery input**, not deployment-wide disaster backup. A valid checkpoint does not automatically grant restored read/execution eligibility. RestoreSet is an application-consistent backup set spanning stores. Complete disaster-backup creation, restoration, safety watermarks, and copy deletion normatively follow [storage-event architecture](2026-09-20-managed-agent-storage-event-architecture.md) sections 9.1–9.4. This document fixes its interfaces with local journals, resources, and lifecycle without another Session authority, general service, or MQ.

A versioned RestoreSet manifest binds at least the following to one proven application-consistent boundary, not merely locations or “latest” objects:

| Scope                 | Required proof                                                                                                                                                                                                                            |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Java SQL              | Consistent backup and binlog/GTID boundary; Session/Turn/Command, binding/execution ledger, original idempotency/commits, and Workspace occupancy facts                                                                                   |
| qwen private state    | Complete committed journal prefix/revision, checkpoint and coverage, original command/call mapping, actual model-consumed result bytes/conversions and consumption positions; not model inputs guessed from public cards/SSE              |
| Object resources      | Actual backend, exact object version, digest, byteLength, access/retention owner, and full reference closure including large tool results, media, backups, pin/fork/export/publication holds; delete marker is not a referenced version   |
| Workspace             | PVC/Workspace snapshot, corresponding file history/commit proof, trusted storage identity and bindings. Physical key remains backend domain + CSI driver + opaque volumeHandle, not split by alias/tenant/Session/generation/subdirectory |
| Runtime compatibility | Bundle, template, build/format/reader versions and required key-version refs; retain refs/compatibility evidence without leaking keys/credentials into the manifest                                                                       |

The initial backup profile uses a maintenance barrier: fence new inputs, wakes, dispatch, and related maintenance writes; drain writers and in-flight result intake/commits; freeze/flush at a safe boundary; then each owner verifies snapshots/references and publishes the same set's manifest. Freezing only the volume while SQL/journal keeps changing is insufficient. Do not synthesize pending effects as success/not-executed to manufacture a boundary. Shared timestamp, GTID, or an isolated VolumeSnapshot cannot prove cross-component application consistency; GTID is not an external-effect receipt. A combination that cannot freeze and prove consistency does not support automatic continuation.

Before complete disaster recovery opens, recovery eligibility, deletion, and key-revocation records must have a verifiable complete safety watermark **outside the backup and not rollbackable with the business DB**. Prefer existing protected backup/audit storage for these narrow facts, not a copy of Session history. The interface must prove returned results are part of the current complete state. Signatures/hashes prove content, not freshness by themselves. Old-backup assertions of “not deleted,” “key still present,” or “permission valid” cannot prove current validity. A single Session tombstone, sealed lock, or RestoreBundle does not replace this evidence.

Recovery starts isolated, with dispatch, automation, and GC disabled. First fence old Java/Harness/Runtime writers' commit and physical-write rights, then verify the restore set, compatible versions, exact objects, and complete safety watermark. Missing/stale/incomplete safety evidence also blocks ordinary restored reads (history, SSE, Range, export, resource downloads); permit only explicitly authorized isolated diagnosis. Do not restore visibility before checking deletion. The model restores only through established authority/resource interfaces; Harness does not mount Workspace. Actual volume access follows [tools/history §4.4](managed-agent-tools-history.md#csi-volume-serialization); physical fencing follows [Endpoint](2026-09-21-managed-runtime-endpoint-recovery.md) section 17.

Before continuing, query original durable execution ledgers/results and verifiable external evidence for the unknown execution interval from backup until old-writer isolation. If that interval cannot be fully enumerated, expand blocking across affected Sessions/Workspaces. Missing restored-DB records, 404, timeout, or absent Pod do not prove nonexecution in reality. Do not re-prepare/execute or create a Runtime to query an old call. Proven complete prefix and old-owner isolation are prerequisites for concluding an operation never started. Existing-effect UNKNOWN still settles through original recovery, never snapshot/new-epoch automatic replay.

RestoreSet, safety-watermark proofs, and deletion completion are new versioned closed records. Do not insert the table's entries directly into current RestoreBundle/Event or strict Tool v2/attestation v2. Before implementation define producers/consumers, required/nullable fields, versions/reference closure, and negotiate minimumReader/capability under section 3. Recovery-required facts cannot be declared ignorable by old readers. Unsupported old peers reject that recovery capability; this revision changes no existing formatVersion=1, schema, or configuration.

### 2.4 Delete Acceptance, Reference Settlement, and Copy Completion

Reuse original operation, history_maintenance, lifecycle.changed, and real resource owners without a second executable Session history. Complete copy erasure and old-backup anti-resurrection also follow storage-event architecture sections 9.1–9.4.

1. Durably accept a delete plan and immediately fence new input, dispatch, and ordinary reads. ACK confirms acceptance only; online read revocation confirms no further byte delivery and cannot retract bytes already sent. Neither means stopped execution or deleted.
2. Retain `idle/active/recovery_blocked → closing → closed`; only actual original-work cancellation, drain, and trusted stop proof permit closed. Then allow `closed/archived → deleting → deleted`. Failure retains intendedState/recovery_blocked. Active cannot jump directly to deleting/deleted, and deletion cannot bypass unknown physical owners through timeout.
3. Check original-result delivery, in-flight readers/model consumption, pins, fork/export holdings, publication holds, investigation and legal holds. Revoked streams terminate immediately and await actual handle exit; original owners durably manage lawful holdings. Original binding/operation grants narrow system query, cancel, late-receipt intake, and cleanup eligibility, without restoring revoked-user reads, redispatching, or waking a closed model. Conflict/UNKNOWN retains necessary sole evidence; uncertain references stay pending/blocked.
4. Durably commit this Session's reference unregistration, tombstone, and cleanup plan. Across owners, obtain durable release proofs and deduplicate by original operationId before actual owners clean conditionally by revision/identity. Missing files, network ACK, or object delete markers are not commit/cleanup proof. This preserves section 2.1 and tools/history section 5's preservation-before-intake, publication holds, independent fork refs, and pin/unpin rules.
5. Session releases only its own refs, never shared Workspace/PVC, another fork, user pin, installed configuration, or remote publication. Whole Workspace/tenant deletion needs separate authorization and checks of all source refs, readers, executions, holds, and copies; Session delete cannot be elevated into volume-delete authorization.
6. Commit original `deleted` under existing Session-terminal and owner-cleanup conditions. Do not reduce it to acceptance/online invisibility or silently expand it into “all backup and vendor copies are gone.” Record the separate completion dimensions and outstanding obligations below. If required Session cleanup remains blocked by hold/UNKNOWN, do not prematurely commit deleted. Session termination does not erase lawful independent holdings under other owners.

| Completion dimension                | Evidence and limits of the claim                                                                                                                                                                 |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Online read revocation              | New requests and existing streams closed under current ACL; does not prove process termination or copy erasure                                                                                   |
| Execution stopped                   | Trusted supervision proves original processes/descendants exited; report node/storage isolation separately, without fabricating exit or proving external effects did not happen                  |
| Online cleanup                      | Session refs and reclaimable online resources settle under owner conditions; independent shared refs are not deleted                                                                             |
| Backup cleanup pending              | Explicit backup/snapshot/export/historical-object-version inventory and recovery-disable evidence; not complete erasure                                                                          |
| Hold or vendor confirmation pending | Actual retention basis/approval and provider conclusion; API ACK does not prove complete remote erasure                                                                                          |
| Fully complete                      | All copies subject to deletion or all their decryptability have been verifiably removed under contract, with no pending cleanup/hold/vendor unknown; Session deleted alone cannot establish this |

An OSS delete marker does not delete every historical version. Check exact versions, replicas, backups, snapshots, exports, and vendor data. cryptoshred holds only when all decryptable copies and relevant key versions/wrapping or backup recovery paths are irrecoverable. Do not destroy others' shared keys or simultaneously promise complete erasure and full recovery of that data. Validate effective deletion/key-revocation safety evidence before disaster recovery opens reads.

RPO/RTO, retention periods, concrete CSI driver, and vendor deletion contracts are not selected; do not invent values. Unconfigured/unverified contracts disable related automatic recovery or GC. UNKNOWN is not a legal basis for indefinitely retaining sensitive data and requires authorized investigation/compliance retention handling; neither does it justify timeout deletion of sole evidence. D supplies public completion projections; G/W1/O4 supply complete cross-failure-domain recovery/backup deletion. Internal read-revocation, stop, reference, and evidence gates cannot wait for UI release.

## 3. Event Union and Producer/Consumer Chain

“Legal producer” means the **actor initiating a command**, not the physical writer. Session authority validates and appends every event in a single-writer queue. Actors can request, not write directly or record another actor class's facts. The following three actor classes have fixed permitted kinds; reject all other combinations before effects:

- **Current-activation Harness** (activation fence): `model.attempt`, `message.committed` (user-input variants come from the input-projection adapter below), `tool.intent`, `context.compacted`, `checkpoint.committed`, and the tool_call requested branch of `action.changed`. It requests through `appendExecution`/`commitCheckpoint`; authority checks fence/expectedSequence and commits.
- **coordinator** (activation-management eligibility): `activation.changed`, through `claimActivation`/`completeActivationInstall`/`renewActivation`/`releaseActivation`. Authority decides/writes epoch and phase; coordinator cannot fabricate epochs or commit checkpoints/terminal states for Harness.
- **Trusted entry points/domain adapters**: `input.accepted` (ordinary input/internal trigger; authority internally generates same-transaction `wake.requested`, so entry points may request a wake but not write that fact), `cancel.requested` (user/lifecycle owner), non-tool requested branches of `action.changed` (requestAction under the source matrix below) and final decisions (original arbitration entry), `tool.receipt` (original Runtime receipt entry or registered domain/orchestration adapter), `config.bound`/`lifecycle.changed` (configuration/maintenance owner with OperationGrant), `domain.committed` (registered domain adapter), and `turn.settled` (authority validates Harness terminal submission or recovery settlement).

The workspace-physical branch of `tool.receipt` enters only through `acceptRuntimeReceipt`, never piggybacked on Harness `appendExecution`: Harness is not a trusted physical-result source.

Action-request sources and eligibility are fixed below. `requestAction` allows only registered domain adapters to request confirmation for an original accepted operation. Cross-Session actions first receive fixed identity through the original outbox; shared workspace does not grant extra authority.

| source         | Request actor and validation basis                                                                                                                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| tool_call      | Current Harness through appendExecution, validating activation fence and committed tool.intent/inputRevision; Runtime permissions separately validate original prepare/ref                                                           |
| automation_run | Trusted scheduler/manual-run adapter through requestAction, validating original runId/occurrenceId, frozen target, and controlling Session authorization; missed one-shot confirmation starts no model                               |
| team_plan      | Trusted team-plan adapter through requestAction, validating original team_plan record, childRunId/planRevision, and leader routing; model-generated plans still require original activation submission, not fabricated adapter plans |

All final decisions enter original arbitration through resolveAction. Creating a request grants no approval authority; revision changes, late/duplicate/expired decisions use conditional commit under the same requestId. Action creation only publishes a waiting projection. A lawful final decision and required subsequent input/wake or outbox advance the original operation. Workspace maintenance without Session retains existing workspace interaction rather than fabricating a Session for this table.

Legal lifecycle transitions: create→idle; accepted input makes idle→active; all turns terminal and no running queue makes active→idle; idle/active/recovery_blocked→closing, then closing→closed after actual owned-work drain; closed↔archived (unarchive returns closed without automatic model run); closed/archived→deleting→deleted. Failures may move non-deleted states to recovery_blocked with intendedState, returning to the legal phase after verification. Unknown physical owner forbids closing→closed and deleting→deleted. Model waiting belongs to turn/checkpoint, not lifecycle closed.

**Extension rules.** This is a closed union. An unknown committed kind always fails execution recovery (section 4 rule 6), never skipped. Adding a kind or a `domain.committed` domain requires all of: raise header `minimumReader`, or explicitly declare the addition within `formatVersion` as safely ignorable by old readers, recording the chosen option here; specify producer, consumer, and atomic requirements; update validators and section 7 acceptance. No fields-first/specification-later changes or arbitrary `domain.committed` escape hatch: its domain set is also closed. An old-reader-ignorable kind cannot contain recovery-required facts, or an old reader would execute with incomplete state.

**Placement of old subtypes.** Existing transcripts contain nonexecution ChatRecord subtypes. They add no top-level kinds and map as follows, avoiding an unrepresented/no-dual-write gap: titles/rename use `domain.committed` domain `session_metadata`; user-input forms such as `slash_command`/`at_command`, UI telemetry, and attribution snapshots remain within the `message.committed` `contentRef` union, whose reader restores old subtypes as nonessential recovery facts. Model provenance and parent/child accounting are covered by header, `config.bound`, `message.committed.parentMessageId`, and checkpoint, without new records. Realtime voice has no v1 placement; realtime-enabled entry points remain legacy until the [ordinary client design](managed-agent-full-design.md) completes that slice. Do not stuff them into `message.committed` in the meantime.

**Branch points are not execution checkpoints.** New `branch_checkpoint` retains the full original ChatRecord (uuid, parentUuid, v1 systemPayload), submitted by original Harness/recorder through `message.committed` system content and projected unchanged by branch/transcript readers. No new kind/domain or dual-write; formatVersion=1 and minimumReader=`managed-session/1` remain, since existing message readers support this shape. Preserve `commitBranchCheckpoint` operation, `recorder:<uuid>`, and SHA-256 of original JSON bytes so retries after upgrade return the old transaction rather than another branch record. Compaction replacedMessageIds includes every message event in range, including branch system content; original events/display branch points remain.

For historical committed `checkpoint.committed` referencing schemaVersion=1 `managed-branch-checkpoint`, hot commit, cold open, and projection validate reference format, resource length/digest, strict JSON, record sessionId/uuid/type/subtype, parentUuid shape, and v1 payload. boundary must be null, coveredSequence the preceding committed tail. Retain original events, markers, resources, and predecessors without log rewrite. It restores branch display and proves prior execution only, never updates latestCheckpoint; missing execution state blocks rather than falling back to initial. Predecessors may reference only already-seen checkpoint IDs within coverage; reject duplicates, dangling, and forward references. Historical state may reference a verified branch ID; new state links only the previous state. All checkpoint coverage must not exceed committedSequence before transaction start. `managed-checkpoint` resources are not decoded as ChatRecord/JSON or read during classification; corrupted/missing execution state still fails when actually read. This slice preserves that behavior, with formal blocked mapping delivered by the recovery slice. Unknown kinds/versions fail explicitly. This does not claim to fix old binaries or equate classification isolation with nine-group Harness state/tail-reconciliation acceptance.

## 4. Successful Commits, Corruption, and Restart

1. Inside the write queue validate actor, scope, schema, idempotency key, fence, sequence, capacity, and reference closure. Original success for the same operation+commandId returns only its original receipt; changed business content conflicts. A failed sequence conflict may reread and resubmit unchanged business content.
2. Write large resources to controlled temporary files, hash while streaming, sync files, atomically publish and sync owning directories before transactions may reference them. Failure sends no ACK. Publication precedes commit marker: failed final transactions leave **published** orphans, not temporary files, so temporary-directory cleanup is insufficient. Under section 2.1 published-orphan rules, actual Session/workspace resource owners recover/collect only after checking original commandId, commits, and all holdings. Temporary-file orphans also belong only to their own cleanup owner.
3. Append consecutive event records, then commit marker. Initial implementation retains the writer's per-line sync rather than unproven batch acceleration. One authority queue prevents interleaved transactions. Sync parent directories for header/first directory creation and necessary renames. Per-line sync times the 256-event hard maximum determines worst-case latency: a full transaction performs 257 syncs, serializes one Session, and occupies its entire authority queue. v1 therefore requires single-digit event counts per logical transaction (typically 1–3, such as input+wake or model.attempt+message.committed); 256 is a hard ceiling, not a routine batch. Measure full-transaction latency per deployment profile. Above 2 seconds, that profile is unsuitable for per-line sync; first reduce transaction events or move content into resources, never adopt unproven batch sync or skip pre-marker sync for speed.
4. Advance visible committedSequence, projections, and ACK only after marker/all events/resources validate and sync completes. Existing writer strict append already syncs files; the new guarantees mainly concern multirecord transaction visibility, reference closure, and all critical producers waiting. Do not claim the original writer lacked sync entirely.
5. On lost ACK, find marker by original commandId. Write failure stops new progress. A complete persisted marker may be confirmed after recovery validation; partial lines/no marker prove neither acceptance nor terminal outcome.
6. Read the complete committed prefix, never skipping corrupt middle or unknown committed kinds to continue execution. Truncate an incomplete tail only under an exclusive writer after proving no marker and a complete prefix; retain a diagnostic bad-tail copy. Read-only owner/compatibility probes never repair. **Measured supplement (2026-09-11):** existing `SessionWriterLease.acquire` rejects transcripts modified outside an active writer with `SessionTranscriptChangedError`, so authority cannot directly truncate files; truncation must be a lease capability. That capability is implemented: `SessionWriterLease.truncateTo(byteLength)` truncates under the same `runExclusive` barrier and per-step ownership checks, rebuilding pinned transcript proof (rolling hash cannot rewind, so reread/rehash the retained prefix). Authority explicitly invokes `LocalManagedSessionAuthority.recoverUncommittedTail`: first scan for an unmarked tail and complete committed prefix, save discarded bytes to `<transcript>.uncommitted-tail`, then truncate. Repair is explicit; `open()` still raises `ManagedSessionUncommittedTailError` and rejects writes. Read-only owner/compatibility probes do not repair. Externally torn tails are still rejected by the lease below authority evaluation.
7. Unacknowledged incomplete input may retry by original ID. If physical work was permitted but its receipt did not commit, recovery queries the original execution ledger; missing Session tail never proves nonexecution.

Node filehandle.sync synchronizes a file; directory/filesystem/hardware guarantees still require deployment-profile validation and do not cover every power-loss device. [Node.js 22 file API](https://nodejs.org/docs/latest-v22.x/api/fs.html#filehandlesync)

## 5. Fixed Initial Limits and Compatibility Paths

New values below are design decisions, not currently effective configuration; old values come from the source baseline above. Count encoded UTF-8 bytes, with media-resource raw bytes counted separately. Both peers advertise limits version=1 during new-private-capability handshake and use the smaller values. Reject installation below the minimum legal envelope.

Reject capacity before input ACK. Committed input does not disappear when the projection queue temporarily fills: authority retains wake and pauses new admission. Storage adds no automatic user-history expiry. New input/resource allocation checks actual scope disk budget, retaining at least 64 MiB settlement reserve, shared once per workspace rather than per Session. Low space stops new work; admitted receipts use the reserve. If exhausted anyway, explicitly return storage_unavailable and retain original copies, never release early. Existing stricter administrator disk limits take precedence; deployments unable to meet the reserve cannot enable Managed writes.

New Managed negotiates writer schema/Session reader/Runtime control before create. Legacy never changes engine in place.
