# 部署管理扩展目录

[English](managed-extension-directory.md) | [简体中文](managed-extension-directory.zh-CN.md)

## 问题与范围

不可变镜像、共享安装和托管运行环境需要向多个用户及工作区提供相同的 Qwen Code
扩展。即使扩展包已经位于磁盘上，要求在每个用户 home 中执行安装或链接，仍会使
扩展发现依赖可变的逐用户初始化步骤。

可选的 `--managed-extensions <root>` 让 CLI 和 serve 直接加载这些包，也适用于全新的
用户 home。包内容由部署方管理，启用偏好和运行时状态仍写入用户存储。每个直接
子目录复用现有 `qwen-extension.json` 格式及贡献加载器，扩展作者无需维护第二套
包格式。

该选项在进程启动时选择一个集合根目录。不增加递归扫描、公开环境变量或 settings
入口、watcher、新包格式、商店、状态格式迁移或部署专用装配。

## 启动者授权

显式进程启动参数授权加载由部署方维护的来源，包括后续通过该来源交付的包和版本。个人使用时启动者就是用户；托管产品中，部署方将该来源作为 Agent 运行时的一部分提供。会话元数据、项目设置和项目环境文件不能选择或替换该来源。首版接口不新增公开环境变量，规范化后的启动值通过现有子进程启动参数显式传递。

Managed 表示包的管理归属，不表示由 Qwen 官方编写，也不代表执行隔离。宿主产品应说明提供方及定制属性。既有工作区信任、safe/bare mode 和工具权限各自保持原有控制；来源授权不代表每个 hook 或 MCP 启动都会经过工具调用确认。用户保留默认及工作区启用控制。授权模型与同名优先级仍是 issue [#12147](https://github.com/QwenLM/qwen-code/issues/12147) 中待审查的规则选择。

## 发现与状态

CLI 按启动 cwd 一次性解析绝对根目录。显式目录不存在、不是目录或不可读时报告配置
错误；空目录有效。ExtensionManager 接收 `managedExtensionsDir`，与可写的
ExtensionStore 分离。容器沙箱（docker/podman）以只读方式挂载解析后的根目录，并以
容器内路径转发该参数；bwrap 与 seatbelt 后端本身已对宿主机文件系统开放读取。拒绝与可写扩展/状态目录重叠（包括符号链接和文件系统大小写别名），保证只读边界。发现和名称查找共用解析逻辑：沿用既有名称校验，忽略大小写的
重复部署管理名称报错，部署管理优先于用户包并诊断遮蔽。先确定归属再判断启用状态，禁用部署管理
不会激活被遮蔽的用户包。单份无效 manifest 沿用现有诊断。 daemon 目录查询只读 manifest，同时采用相同的来源优先级和身份。重复读取未变化的目录时，保留已有策略与存储 generation，不加载扩展贡献。

加载结果带有 `source`（`managed` 或 `user`）。部署管理身份根据规范化名称生成，不依赖
版本或部署路径。部署管理默认启用；显式启用状态和工作区偏好保存在用户状态层，版本更新
后继续生效；既有同名用户偏好通过存储层已有的名称迁移机制继承。workspace trust、safe mode、名称筛选（`-e/--extensions`）和工具审批
保持既有的、按贡献类型区分的行为。部署管理扩展不要求、也不跟随安装元数据。

部署管理包的 CLI User scope 启用/禁用修改存储中的默认启用状态，覆盖所有工作区，
包括用户 home 以外的工作区。显式部署管理 User scope 操作和管理 API 的默认启用状态
变更（包括批量操作）清除继承的旧路径规则，
避免旧规则悄悄覆盖当前操作；精确工作区覆盖规则保留既有优先级。存储默认值让用户
对部署托管包的显式选择在各工作区一致生效。用户安装扩展保留原有 home 路径范围
语义，以保持兼容性。

发现时将每份扩展的来源传给状态存储。现有 V2 policy 增加可选的 `managed: true` 标记，用于区分外部发现的包与安装器管理的文件，不迁移状态路径，也不改变状态版本。保留已有启用偏好和继承的安装记录。批量启停只对非 managed 策略检查用户安装文件是否缺失；重新发现用户包，或完成安装/更新事务时清除该标记。仅有偏好声明的 managed 包被发现时，不虚构安装器 generation。这样旧用户副本移除后，批量及单项启停仍保持一致，无需等待后续刷新修复状态。

## 贡献与刷新

复用扩展 skills、subagents、hooks、MCP、context、commands 和既有运行时刷新链路。已有根目录
变量在内存中按实际扩展目录替换，包括过去在安装阶段改写的文本，不改写部署管理文件。
子代理 YAML 先解析，再递归替换结构化字符串值；替换后保留现有最终配置校验。
这样部署路径中的反斜杠和引号不会被 YAML 重新解释。
来源指纹覆盖部署管理 manifest 元数据及成员变化，沿用现有重新校验机制；显式全量刷新
重新读取贡献，包括仅内容变化、替换及移除。正文变化、禁用或移除（包括版本回滚）时，刷新使已加载 skill 的当前名称缓存失效；
未变化的正文继续沿用已有去重。历史会话记录和上下文统计保持完整。重复刷新不能重复注册
贡献；禁用或移除后按现有刷新语义撤销旧贡献。部署管理目录不加入用户扩展的文件 watcher；部署变化后使用显式刷新或重启。

## CLI、daemon 与 API

常规解析和 serve fast path 接收相同字符串参数，将同一绝对路径传入运行时创建。
每个 workspace 和 ACP 子进程的新建、加载/恢复、替换都通过现有启动配置和参数继承。
会话请求不能覆盖进程级目录选择。既有选定工作区管理和活跃会话协调机制负责刷新实际
Agent，不只刷新父进程缓存。既有 channel worker 和独立 channel ACP 启动链路
也传递同一目录，不改变 channel 生命周期或刷新行为。`-e/--extensions` 保持普通 CLI
的名称筛选语义，serve 不新增独立筛选选项。

管理 CLI、daemon 状态和既有扩展 UI 显示来源及 manifest 版本。API 增加可选的
`extensionSource` 判别字段，保留已有表示 URL 的 `source`。核心操作拒绝部署管理卸载、
更新和替换，不依赖权限或 UI。update-all 清楚报告跳过部署管理并继续更新用户包。配置及
启用状态只写用户状态。Web UI 隐藏部署管理包路径及不支持的包管理菜单，context 文件
显示相对名称；保留启用/禁用控件。CLI/API 继续保留路径供诊断。

## 实现区域

- CLI config/扩展命令、serve 解析/选项/运行时创建/ACP 参数。
- 核心 ExtensionManager 的发现、身份、指纹及管理保护；共用 ExtensionStore
  启用状态存储，并为部署管理包处理默认启用状态。
- 原先依赖安装阶段文本改写的贡献读取器，改用只读的运行时替换。
- daemon 扩展状态及 SDK 类型、既有管理 UI 和列表输出。
- 就近单元测试、集成测试和扩展使用文档。

## 验证与验收

使用独立依赖、临时 home/workspace、随机 loopback 端口、假模型和 HTTP MCP 服务。
只读验证同时使用权限和前后文件内容清单。验证实际 skill 读取、hook 执行、MCP 工具
调用、context/commands、CLI/fast path 一致性、ACP 新建/恢复/多工作区、活跃刷新、
同名冲突、持久化禁用/重新启用、重复名称、错误根目录和管理保护。运行 build、
typecheck、定向测试及完整 preflight；失败必须与精确未修改基线在相同条件下对照，
如实报告未完成检查，不沿用历史失败作为豁免。

## 风险与后续

部署管理优先确保出现同名用户包时，仍由部署方选定的包提供实现。遮蔽警告让冲突可见；
禁用部署管理包不会切换到另一份实现。需要同时使用两份包时，应为它们使用不同的名称。

按名称保持身份，使启用偏好在包升级或根目录移动后仍然有效。这也意味着另一份包
如果复用相同名称，就会继承已有偏好。部署方应保持名称稳定，避免将旧名称用于无关
扩展。

managed 包从来源中撤除后，若没有已安装的用户包，显式安装同名用户包可以接管保留的启用状态和资源偏好。安装提交前会再次检查 managed 来源，预先准备的安装也不例外；不能把过滤后的发现结果当作来源已撤除的证据。存储层原子地把策略转移到用户身份，并移除 managed 标记。原先已安装而被遮蔽的用户包按正常发现流程恢复。过期的 managed 身份不能卸载替换后的用户包。 若安装目标仅为配置目录，且为空或只包含普通 `.env` 文件，则可接管；保留已有值，显式准备的新值优先。未知内容、符号链接、既有包和秘密 selector 元数据仍视为冲突；提交失败时恢复原目录和策略。

只读加载不会让部署变更具备原子性，也不新增 watcher。部署工具仍需负责发布完整
包内容，并显式刷新受影响的工作区或重启进程。包分发和自动部署更新不在本设计范围内。
