# Web Shell 工作区信任授权

[English](2026-10-01-web-shell-workspace-trust-grant.md) | [简体中文](2026-10-01-web-shell-workspace-trust-grant.zh-CN.md)

## 状态

已为 QwenLM/qwen-code#13130 实现。

## 问题

文件夹信任是失败关闭（fail-closed）的。一旦设置了
`security.folderTrust.enabled`，没有任何规则裁决的文件夹即为不可信：工作区
设置、项目环境变量文件、扩展、自动接受以及自动记忆加载都会保持关闭，直到
用户记录一次决定。

而记录这一决定目前只能在终端里完成。Ink 的文件夹信任弹窗和 `/permissions`
会写入 `trustedFolders.json`；没有任何守护进程路由接受信任决定。
`POST /workspace/trust/request` 只是发布 `trust_change_requested`，仍然需要
本地操作者介入，因此当所有已注册工作区都被判定为不可信时，Web Shell 客户端
（包括 Desktop 应用）没有任何出路。于是，缺失、不可读或仅存在于某台机器的
`trustedFolders.json` 会把整个产品锁在它自己的界面之外，且应用内没有恢复
路径（#13130）。

## 目标

- 让具备操作者权限（operator authority）的客户端能够直接、经认证地为单个
  工作区记录信任。
- 保持 `POST /workspace/trust/request` 只做请求转发；它仍是"需要有人来看看"
  的通道。
- 失败关闭。新路由复用现有的严格变更闸门（strict mutation gate）和现有的
  受信任文件夹写入器；既不扩大攻击面，也不扩大可触达的文件范围。

## 非目标

- 远程撤销信任。远程取消信任会关闭一个正在运行的运行时世代，并可能破坏正在
  进行的会话；终端和信任文件仍是完成该操作的途径，而 #13130 的恢复问题是
  单向的。
- 由守护进程修复格式错误或不可读的 `trustedFolders.json`。写入会失败并上报，
  而不是去猜测操作者的文件。
- 零停机应用信任变更。运行时替换仍是有损的。
- 改变独立 CLI 的信任选项或优先级。`/permissions` 与信任弹窗保留原有选项；
  共享读取器接受写入器已经保留的 JSONC 格式。

## 设计

### 端点

| 暴露面     | 路由                                      | ACP 方法                      |
| ---------- | ----------------------------------------- | ----------------------------- |
| 主工作区   | `POST /workspace/trust/grant`             | `_qwen/workspace/trust/grant` |
| 指定工作区 | `POST /workspaces/:workspace/trust/grant` | `_qwen/workspace/trust/grant` |

不读取请求体，也不使用客户端 id。响应是写入之后该工作区上报的信任状态，
因此调用方看到的是它刚刚记录的决定，而不是一个预测值。

「指定工作区」这一行的 ACP 列带有 REST 路由没有的前提。工作区限定的 ACP
连接需要次级 mount，而只有受信任的非主运行时才会获得 mount：未受信任的非主
工作区会在 mount 解析处被拒为 `403 untrusted_workspace`，此时任何 dispatcher
都还不存在，HTTP 与 WS 两条路径皆然。因此对本设计要恢复的那个状态——被锁住
的次级工作区——该 ACP 方法根本无法被派发，恢复只能经 REST 完成。主工作区
那一行对该方法不做信任门禁。

### 权限与边界

该路由与其他特权 REST 变更走同一个严格变更闸门：需要凭据，或者在
trusted-loopback 模式下来自主监听器（primary listener）的请求。没有操作者
权限的调用方会在写入器运行之前被拒绝。原生应用客户端正是通过该主 loopback
监听器访问守护进程，因此 Desktop 与 Web Shell 无需令牌即可工作；LAN 或
`--require-auth` 部署则需要真实凭据。

被写入的路径永远不由调用方提供。它就是该请求已经解析到的工作区，因此这个
端点无法被指向任意目录。新规则只信任该文件夹；写入锁内会保留已有的
`TRUST_FOLDER` 或 `TRUST_PARENT` 规则。SSH 工作区记录的是守护进程宿主自身的
信任记录，也就是守护进程实际评估的那份记录。

### 拒绝情况

| 条件                                        | 结果                                |
| ------------------------------------------- | ----------------------------------- |
| 选择符未指向任何已注册工作区                | 400 `workspace_mismatch`            |
| 该工作区未启用文件夹信任                    | 409 `folder_trust_disabled`         |
| 工作区是托管暂存区（managed scratch）       | 409 `managed_scratch_trust_fixed`   |
| 工作区拥有进行中的会话（live conversation） | 409 `live_conversation_trust_fixed` |
| 运行时未激活                                | 503 `workspace_runtime_unavailable` |
| 信任文件格式错误、不可读或不是普通文件      | 500 `trusted_folders_invalid`       |
| 授权已记录但策略或上报状态仍不受信任        | 409 `trust_grant_ineffective`       |
| 请求过程中世代被关闭                        | 与其他路由一致的世代关闭响应        |
| 已经是受信任状态且运行时激活                | 200，幂等                           |

这一行信任文件的拒绝条件比字面更窄。悬空符号链接会被读作「文件不存在」，因此
授权会把它替换成一个只含新规则的普通文件并返回 200。由写入过程自身发现的损坏
大多返回 500 `trusted_folders_invalid`：符号链接或其他非普通文件的信任文件、
根节点不是 JSON 对象的文档、以及带有非法信任等级的规则，都会由写入方抛出
`FatalConfigError`。只有「语法非法的 JSONC，且守护进程首次缓存它时还是合法的」
这一种情况会以普通解析错误抵达写入路径，返回 500 `internal_error`。而
「格式错误 / 不可读」的裁决来自一次被缓存的加载，生产环境中没有任何代码会清除
它，因此事后被修复的文件仍会持续返回 500，直到守护进程重启。

「已经是受信任状态」这一行同样以运行时激活为前提。一次成功的授权会触发重建，
把条目置为 `transitioning`；在此期间两条授权路由都会返回 503
`workspace_runtime_unavailable` 并带 `Retry-After: 1`，即使信任记录已经写入。
该 503 是「可重试直到生效」，而不是一次失败的决定；但参考实现的 Web Shell
面板目前并不这样读它：`handleGrantTrust` 对每一种拒绝都上报同一句
"Could not trust the workspace"，既不按 status 分支，也不按 `code` 分支。
客户端应把该 503 视为在自己那段有界等待内可重试，且不得无限重置截止时间；
让面板与该约定对齐一事已在 #13186 跟踪。

以最深匹配深度写入工作区的精确路径，同时也能覆盖更浅层的父级
`DO_NOT_TRUST` 规则。已有的受信任规则会保留；同一拼写下同深度的
`DO_NOT_TRUST` 会被替换。若竞争规则是以同一目录的另一种拼写（符号链接别名）
记录的，它会在写入之后继续存活，并在同深度打平时胜出，因此这类授权虽已记录却不会生效，返回
409 `trust_grant_ineffective`。策略加载错误或 IDE 拒绝也可产生相同响应；错误
会指出所检查的状态与来源，不会假定存在阻塞的文件规则。两条信任读取路径均接受
JSONC 写入器所保留的注释和尾逗号。

写入本身使用的就是终端所用的既有原语：获取 `proper-lockfile`、在锁内重新
读取、保留注释，并以原子方式替换一个普通 0600 文件、且不跟随符号链接。

### 能力通告

只有当运行时无需重启即可接收信任变更时，守护进程才会通告
`workspace_trust_grant`。路由注册是无条件的，因此该能力标签与 REST 暴露面
保持一致——在热重载不可用的地方写入该文件本身就是安全的，只是需要重启，正如
`/permissions` 那样。ACP 对应项不在这份一致性之内：它需要一个受信任的次级
mount（见「端点」）。该能力标签告诉客户端在哪些环境中授权会立即生效。较旧
的守护进程不会通告该标签，客户端也就不得提供该入口。

### 生效过程

信任记录立即改变；实际生效状态则在协调器（reconciler）重建运行时后才改变，
这是异步的。客户端会持续刷新能力信息，直到工作区上报为受信任，并在有限等待
后放弃，使重建失败时该行重新变为可交互。这里不引入新的事件类型：工作区清单
本身已经携带每个工作区的受信任标志，而 GET 状态是唯一事实来源。

## 验证

- 服务层：对绑定的工作区授权可覆盖已存在的不可信规则，并返回受信任状态。
- 路由层：两条路由都能授权；未启用文件夹信任时返回 409；信任文件非法时返回
  500。
- 协议层：ACP 分发、未启用文件夹信任时的拒绝，以及 mutation 层级分类；SDK
  路由映射与客户端 URL 形态。
- Web Shell：仅在具备该能力时显示入口；针对该行的工作区发起授权；刷新能力
  信息；并在工作区上报受信任后让该行恢复可用。

## 验收标准

- 用户当前无法进入的工作区可以在 Web Shell 中被信任，无需终端；运行时重建
  后完整的工作区功能可用。
- 未认证、非操作者的调用方无法记录信任。
- `POST /workspace/trust/request` 保持其仅请求的行为。
- 不通告该能力的守护进程不会显示任何入口。
