# Managed GitHub ledger registration-identity keying

- **Status:** proposed
- **Date:** 2026-11-19
- **Scope:** `packages/channels/github` (state store + adapter), `channel-base` contract comment, tests
- **Related:** the WeCom adapter's P1-D/E fix (PR #17441) and the DingTalk keying (PR #17742); the shared `destinationKey` contract in `channel-base`; [Chinese version](2026-11-19-managed-github-registration-identity.zh-CN.md)

## Problem

The managed GitHub state store keys its single ledger file by the configured entry only — channel name + endpoint `baseUrl`, per workspace scope. A comment staged as a pending claim under one control-plane registration (tenant A) is therefore loaded when the same configured entry is restarted against a different registration (tenant B, or a different actor/workspace/cwd-relative within one tenant). The persisted event carries the full text and no tenant identity; `resubmitPending()` forwards it through the HTTP client, which supplies the new registration's tenant header and channel id, so an event already admitted by A whose answer was lost can create an input under B. This is the same cross-ownership replay the WeCom adapter closed in P1-E and the DingTalk adapter closed in #17742.

## Current state

`ManagedGithubStateStore(name, cwd, baseUrl)` hashes `name\0baseUrl` into a per-entry directory `~/.qwen/channels/<workspace-scope>/github-<hash>` and stores a single `managed-state.json` beneath it. The directory lock (`proper-lockfile`) serializes concurrent managed instances of the name + endpoint. The adapter constructs the store with three arguments and never passes the control-plane destination. `load()` collapses an I/O failure and corrupt content into one unnamed error.

The shared `ManagedChannelControlPlane.destinationKey` already binds the full registration identity — base URL + tenant + channel + actor + workspace + cwd-relative — and `HttpManagedChannelControlPlane`, the only production implementation, populates it on every real path. The base interface comment names the GitHub store as a sibling that does not yet bind it.

## Proposed change

Mirror the WeCom / DingTalk shape exactly:

- **Store constructor** gains a fourth parameter `identityKey = ''`. The lock directory stays keyed by the configured entry (`name\0baseUrl`) per workspace scope — NOT by destination — so two instances of the same name + endpoint contend for one connection lock even when they target different control-plane destinations. The ledger FILE beneath that directory is keyed separately by `ledgerKey = sha256(identityKey).slice(0, 16)` (the first 16 hex chars, matching the store): `managed-state-<ledgerKey>.json`. A pending ledger staged under one registration is never loaded or replayed under another registration of the same entry.
- **Adapter constructor** passes `options.controlPlane.destinationKey ?? ''` as the fourth argument. The `?? ''` fallback only spares non-persisting test doubles that omit the optional field; the production HTTP client always supplies it.
- **`load()`** splits the read / parse / validate arms, names `this.file`, and keeps the fs `{ cause }`, so an operator facing several `<hash>.json` ledgers can tell which registration is unreadable versus merely invalid.

The lock stays per-entry deliberately: a per-destination lock would let two registrations of one configured name + endpoint each acquire a lock and run concurrently, duplicating inbound processing. The ledger keying adds cross-registration isolation without narrowing the lock.

The shared `destinationKey` comment in `channel-base` is updated to name WeCom, DingTalk **and GitHub** as the adapters that bind the registration identity, leaving email (a separate variant) as the remaining follow-up.

## Upgrade consequence and diagnostics

The ledger file is renamed from `managed-state.json` to `managed-state-<ledgerKey>.json` with **no adoption**: the first restart after upgrading starts on a pristine identity-keyed ledger. A claim that was staged (persisted) but not yet admitted is stranded — the control plane never saw it (only `submitInbound` makes a claim visible), so only this client's own ledger could re-drive it, and the new ledger does not contain it. Unlike DingTalk's stream, GitHub does not ack a frame to the provider; the loss comes from the notification window: a thread holding a claim is never marked read and freezes the watermark, but the fresh ledger's cursor is null, so the first poll's `since` is the connect time and the old notification is not re-listed. The same reset drops the cursor (notification watermark + dispatched-comment ring) and the un-receipted outbound segments. This is the deliberate stranding tradeoff the WeCom / DingTalk designs record: adopting the legacy ledger would replay one registration's pending into another, the cross-ownership hazard the keying prevents. The one exception is the durable per-PR `watch.episodes` counter map, carried entry-scoped into whatever ledger was loaded — a fresh one, or an existing keyed ledger on a roll-forward after a rollback. `entryWatchEpisodes()` merges the counters `Math.max` per key across every ledger in the entry directory (the live legacy, each registration's identity-keyed ledger, and the `.stranded-*` archives), sanitized to safe integers >= 1; a counter whose only home is a `watch.prs` baseline (its watermark was evicted by the live cap) is carried too. The carry SOURCE is not capped — the adapter merges it into the loaded ledger non-destructively under the validator's 1024 bound (capping at the source would discard recoverable counters before the adapter can place them). Reading the archives is what makes the carry survive the first start's rename: registration A adopts the counters and archives the legacy, then registration B still resumes them instead of restarting at 0 and re-deriving an already-admitted input id. The admission ledger is permanent, so restarting the counter would silently dedupe a genuine post-upgrade recurrence; the counter is monotone and the input id already binds tenant/channel, so carrying it only errs toward a new id. A counter source that cannot be read is skipped — never a startup failure — but its path is returned and logged, so the operator knows the carry may be incomplete rather than losing it silently. The carry is NON-DESTRUCTIVE: `persist()` writes this map back over the loaded ledger, so it never evicts the loaded registration's own counters (that loss would be permanent); it only raises existing counters and adds carried ones while there is room, each floored at its `watch.prs` baseline — the seed is `episodes ?? prs.episode ?? 0`, so a watermark shadows the baseline and a stale archive must never lower the effective seed to an already-admitted id. Iteration is sorted, so the result is independent of directory enumeration order. At the hard bound, overflow carried counters are bounded-and-accepted (the same tradeoff as the live watermark eviction): their source files persist and are re-read next start, but they are not promised a slot this start. `watch.prs` re-baselines silently and its queued transitions are NOT adopted — injecting one registration's detected events under another is the cross-ownership replay the keying prevents — so they are stranded work the notice names (below). The "fresh window" loss clauses are emitted only when the loaded keyed ledger has no watermark of its own — on a roll-forward after a rollback the keyed cursor re-lists from its own watermark, so claiming a skipped window there would report a loss that does not exist.

To make the drop explicit rather than silent, `connect()` detects a sibling `managed-state.json` (`strandedLegacyLedger()`) and logs one line naming that path and its pending/outbound counts; it does not adopt it. The pending count folds in the legacy `watch.prs` queues (`watchPending`, the number of PR entries whose detected-but-undelivered queue is non-empty): those queued PR-watch transitions are stranded work too, so a legacy holding only a queued transition must not render as a quiescent "0 pending", and a dedicated clause names that they were not adopted. That clause is decided PER stranded PR by the loaded baselines (`watchPendingKeys`), not the window alone: a PR with a loaded `watch.prs` baseline may be re-derived if its edge recurs, while a PR without one is dropped (neither replayed nor re-derived); a mixed queue names both subsets rather than reading as wholly lost or blanket re-derivable. Re-detection is conditional on the edge RECURRING — a baseline already past the edge does not re-fire it, so baseline presence alone never promises re-derivation. A fresh ledger, or a roll-forward whose ledger has a cursor but no baseline for the stranded PR (the PR was bound only during the rollback window, or the earlier run never finished a watch pass), takes the dropped arm: there the first observation detects nothing and only records a baseline, so promising re-detection would page the operator about work that never arrives. Detection is deliberately NOT gated on the identity-keyed ledger being absent: a rollback to the pre-upgrade build can stage fresh claims into `managed-state.json` after a keyed ledger already exists, and those claims must still be reported, not vanish silently. The record carries a `readable` flag: a legacy whose contents cannot be read or parsed — OR that parses but is not a ledger shape (`{}`, `[]`, `null`, or an object without the pending/outbound arrays) — is reported with `unknown` counts and an explicit "any staged claims it held are stranded" warning, never rendered as a quiescent empty ledger (a parseable non-ledger is an unrecognized file, not a loss-free 0/0). For a readable legacy the inbound and outbound consequences are named separately — the inbound clause only when `pending > 0`, the outbound clause only when `outbound > 0` — so an outbound-only strand does not report lost inbound comments. The outbound count includes only segments whose delivery status is UNKNOWN: a definitive receipt (accepted/rejected) proves the outcome, but an absent receipt — or one whose outcome is `unknown` — does not, so both count toward the unknown-status clause (an `{outcome:'unknown'}` receipt is not a known outcome). Even a 0/0 legacy with a non-null notification watermark gets a separate clause naming the skipped offline window — "unread notifications updated after the watermark and before this start were never listed, so mentions received since then were not admitted" — because the fresh null cursor drops that backlog; this is an independent sentence, not a loosening of the pending gate, and a genuinely cursor-less 0/0 legacy reports no loss. A corrupt legacy never throws, so a damaged legacy never turns the upgrade into a hard startup failure. The archive is deferred until the start succeeds: after the client identity resolves, registration and the ownership re-check, `archiveStrandedLegacy()` renames the legacy to `managed-state.json.stranded-<id>` — never deletes it, so the stranded claims stay inspectable — and a second log line names the archived path so an operator following the notice can find the claims. A failed first start leaves the legacy untouched so a rollback to the pre-upgrade build can still recover it (the notice simply repeats on the retry); a rollback that stages a fresh `managed-state.json` is detected again on the next upgrade. The reverse direction is bounded too: after a successful upgrade, rolling back to the pre-upgrade build starts on a fresh ledger because that build loads only `managed-state.json`, which the new build never writes; the claims are not destroyed (the identity-keyed ledger keeps them and a later roll-forward reloads them), but while the rollback stands the pre-upgrade build gives no signal that a previous registration is holding staged-but-unadmitted comments.

## Scope boundaries

- The GitHub notification polling, admission/outbound discipline, and mark-read/window-freeze mechanism are unchanged. Beyond the ledger file name and the upgrade diagnostics, the one behavioral addition is the entry-scoped episode carry: `connect()` merges the entry's durable PR-watch counters into the loaded `watch.episodes` NON-DESTRUCTIVELY — it never evicts the loaded ledger's own counters, never lowers a counter below its `watch.prs` baseline, and adds carried counters only while there is room under the 1024 bound (overflow is bounded-and-accepted, the same tradeoff as the live watermark eviction). The PR-watch detection/injection logic itself is unchanged.
- The `disconnect()` row-deregistration gate is a separate concern and is not touched here.
- The stranding diagnostic covers only the pre-upgrade `managed-state.json`. After the upgrade, an identity change abandons the previous registration's identity-keyed ledger (`managed-state-<hash>.json`) with no notice — the same gap as the DingTalk sibling, tracked as item 1 of #17769 and not implemented here; the diagnostic should not be read as covering every stranding case.
- No control-plane (Java) change; no `channel-base` contract/API change — only the `destinationKey` doc comment is updated.
- The email store is out of scope (a separate variant); it is the remaining follow-up.

## Open questions
