# 子会话完成 TTL

[English](subsession-completion-ttl.md) | [简体中文](subsession-completion-ttl.zh-CN.md)

## 问题

`create_sub_session` 会派生调用方不再跟踪的后台子会话。每个已完成的子会话都保留一个
活动 bridge 条目和一条持久化 transcript 行，因此守护进程的会话名册无限增长，
已完成、无法继续的子会话会在磁盘上永久累积。该 issue
（[QwenLM/qwen-code#14289](https://github.com/QwenLM/qwen-code/issues/14289)）
要求为已完成的子会话提供可自选的自动清理。

## 目标

- 提供一个守护进程设置，在可配置的保留窗口之后删除已完成的子会话，
  且默认行为保持不变。
- 绝不删除正在运行、有未完成工作、或用户希望保留 transcript（已归档行、
  失败/已取消的回合留作诊断）的子会话。
- 在守护进程重启后依然有效：之前已完成的子会话不能因为完成时钟是
  进程本地的而永久逃离保留策略。
- 实现保持精简，收敛在子会话启动器层内。

## 非目标

- 不提供按会话的保留策略，也没有用户可见的“保留此子会话”标志；
  归档或删除 transcript 是既有的永久保留手段。
- 不引入新的持久化格式；删除复用 `SessionService.removeSession`。
- 不为本次改动之前写入的 transcript 回填 stop reason。

## 设计

### 设置项

`serve.subSessionCompletionTtlHours`（integer，单位小时，最小值 `0`，
`requiresRestart: true`）。默认值为 `0`：自动删除是 opt-in，
内置默认值永久保留已完成的子会话，逐位保持特性引入前的行为
（不做完成标记、不安装清扫定时器）。非负整数会被采用；
其他任何值都会产生警告并回退到默认值（与
`serve.maxConcurrentSubSessions*` 设置共享同一个整数设置 helper 的契约）。

### 哪些完成会启动时钟

只有干净的回合结束（`stopReason === 'end_turn'`）会记录完成时间戳。
失败、被取消或因其他非干净原因结束的回合绝不是删除候选：
它们的 transcript 是用户应当可以查看的诊断记录，因此会保留，
直到用户归档或删除。三个观察者侧的 stop reason
（`timeout`、`incomplete`、`shutdown`）表示“观察者不再看到该回合”，
而不是“回合烂尾”——它们对时钟仍保持非终结状态；而子会话的活动条目
随后被空闲回收器关闭时，仍属于可证明已终结（回收器只关闭无工作的会话），
其时钟从持久化的最后写入时间启动。

### 清扫与候选集

启动器运行一个清扫 `setInterval`（固定 5 分钟节拍，
`unref`，用 in-flight 标志串行化）。删除候选是完成时钟（`completedAt`）
加上从未获得时钟的被跟踪名册 id。清扫遍历的是时钟而不是名册集合，
因此被名册 FIFO 上限（1024）逐出的已完成 id 永远不会丢失——
它的 transcript 不会因一次不相关的逐出而活得比保留期更久。

活动条目只有在没有工作时才可删除：已接纳的 prompt、
运行中的后台任务或 active 工作状态都会保住 transcript。
完成后的 `send_message` 复活（一个新的已接纳 prompt）
会从最新活动重启时钟。用户在此期间归档的活动行会
从候选集中移除。

### 删除与终结状态

删除在该会话的独占生命周期通道下执行——即归档、删除、恢复所持有、
prompt 接纳共享的 `SessionArchiveCoordinator` 守卫。通道已被占用
（正在接纳的 prompt、归档或删除）时删除被拒绝，时钟保持待发，
下一次清扫重试；删除持有通道期间不会接纳任何 prompt。
在通道内删除会重新判定“仍为终态且无活动”（工作状态、归档状态，
以及比时钟更新的活动——它会重启时钟），随后不经任何 await
直接关闭活动条目（容忍 `SessionNotFoundError`——空闲回收器
通常赢得这场竞速），在持久化变更之前同步地重新校验
没有复活重新创建该条目，通过 `SessionService.removeSession`
删除 transcript（在启动器的 runtime base dir 下解析，
确保删除的是磁盘扫描列表读取到的那一行），并且只在
确实删除了 transcript 时才打印操作者日志行。一旦活动条目
确认已消失且 transcript 已消失，该 id 同时离开完成时钟和名册集合——
终结状态——后续清扫不会重复处理它、也不会重复打印删除日志。
到达该点之前的任何失败都会保留时钟的待发状态，下一次清扫重试。
深度 1 派生门仍然安全：其持久化回退
（`caller.parentSessionId !== undefined`）覆盖被恢复的子会话，
且已被删除的会话不可能是活动调用方。

### 重启后的发现

完成时钟是进程本地的，因此守护进程重启会把所有之前已完成的
子会话 transcript 变成孤儿。第一次清扫执行一次性的磁盘发现：
遍历本 workspace 持久化的所有活动会话
（`SessionService.listAllProjectSessionIds('active')` —— 穷尽式
枚举；分页的 mtime 游标 `mtime < cursor` 会静默跳过与某页最后
mtime 相同的行，这类行从此永远不会被重试），并为每个带有
`parentSessionId` 且最后一条持久化的 turn 结果是干净完成
（`state: 'completed'` + `stopReason: 'end_turn'`）的行重新上发
时钟——时钟从 transcript 的 `mtime` 启动。重启路径只收割可证明
的干净完成：最后一条 turn 是失败或取消的 transcript（以及无法
判定的 transcript）留在用户手中。发现的行只注入完成时钟，
绝不注入名册集合（深度 1 门只应计数活动名册）。
扫描失败会为下一次清扫重新武装发现。

## 设计决策与理由

- **opt-in 默认值（`0`）。** issue 分诊与维护者裁定明确要求
  会话数据的自动删除不得成为默认行为。
- **在启动器内通过发现实现持久性，而不是层迁移。**
  策略的所有者保留在子会话启动器中；一次性的磁盘扫描让
  保留策略拥有者在重启后能够重新发现合格的 transcript。
  把策略移入 `SessionService` housekeeping 会把守护进程的内存生命周期
  耦合到每日文件保留流程上，且无法满足小于一天的 TTL
  （见“未决问题”）。
- **终结完成用允许列表而不是拒绝列表。** 删除 transcript
  是破坏性操作；安全默认值只删除可证明的干净完成，
  保留一切诊断性内容。
- **候选集 = 完成时钟。** 把保留时钟与名册的 FIFO 上限解耦，
  消除了“被逐出但未过期”的 transcript 类别——
  否则它们会永久留存。

## 约束与风险

- 资格判定与变更是该会话独占生命周期通道内的同一个决定，
  因此经由 serve 路由的 prompt 接纳无法在检查与关闭/删除之间复活会话。
  绕过该通道的复活路径仍会被删除 transcript 之前的关闭后重新校验拦住。
- 发现每次启动器生命周期只运行一次；
  当前进程生命周期内完成的 transcript 在内存中跟踪，
  无需重复扫描。
- `nonCleanTerminal` 记录集合的规模受进程生命周期内观察到的
  失败/取消回合数约束，且永不修剪（有文档说明，仅内存）。

## 验收标准

- 默认设置下行为与特性引入前完全一致：任何子会话都不会被删除，
  也不安装清扫器。
- 配置了正 TTL 时，以干净回合结束完成的子会话在 TTL 到期后
  被删除（活动条目关闭、transcript 删除、一条操作者日志行），
  且在此之前绝不被删除；复活会重启时钟；失败/已取消的子会话
  绝不被删除；守护进程重启不会使之前已完成的 transcript 成为
  孤儿——重启路径只收割最后一条持久化的 turn 结果为干净完成
  的行，失败、取消或无法判定的行保留。

## 未决问题

- 长期归属：保留策略最终是否应迁移到持久化会话生命周期
  （`SessionService` housekeeping，与文件历史保留并列），
  从而完全不需要守护进程侧定时器？本 PR 采取的是较小的一步：
  带一次性发现的启动器内清扫器；housekeeping 流程是一个
  候选后续项（H4b 交接）。
