# 已有事务快照下的审批配置变更

[English](2026-11-04-managed-approval-repeatable-read.md) | [简体中文](2026-11-04-managed-approval-repeatable-read.zh-CN.md)

## 问题与范围

嵌入式调用方可以在已有的 MySQL REPEATABLE READ 事务内变更审批配置。如果前面的
一致性读已经建立快照，获取 Session 行锁不会刷新后续的非锁定读。因此，审批版本、
未显式指定时沿用的权限规则和计划模式，以及幂等回执，都可能来自较早的已提交状态。

两个事务先读到版本 0 后，都可能把版本 1 作为新的成功结果返回：第二个条件更新没有
修改任何行，但未检查更新行数，仍然允许写入成功回执和事件。相同幂等键的重试则可能
看不到已提交的回执，再次尝试插入。

普通 HTTP 路径会新建 Store 事务，并在一致性读之前锁住 Session。本次修改面向加入
已有旧快照事务的调用方，不代表已经复现了两个普通 HTTP 请求的相同故障。

## 决策

保留现有的 Session 行锁和事务边界。获取该锁并完成鉴权后，通过普通 `INSERT` 预留
按所有者隔离的回执，使用现有的 `COMPLETED` 状态，结果暂不填充。这条记录在配置、
结果和事件一起提交之前，仅在当前事务内可见。使用 `PENDING` 预留会错误触发现有的
待处理命令屏障。在变更方法内部捕获重复键错误，然后使用已有的
`FOR UPDATE` 查询读取并校验已存在的回执，以返回重放结果。如果找不到对应作用域的
回执，重新抛出原重复键错误。不对不存在的回执进行锁定查询：在 REPEATABLE READ 下，
这种查询可能持有可共享的索引间隙锁，导致无关 Session 插入回执时发生死锁。

通过同一个 `FOR UPDATE` 查询读取 `approval_revision`、
`permission_rules_json` 和 `is_plan_enabled`。即使事务仍保留较早的一致性读快照，
这些当前读也能看到已提交的变更。未显式指定的权限规则和计划模式都从这条已锁定的
配置记录中获取。

只有条件更新恰好影响一行，才能填充预留回执的结果，以及追加
`session.approval.changed`。
否则返回 `409 approval_selection_conflict`，由现有事务边界回滚本次操作。同步更新
SQL 所有者清单。回滚同时清除预留回执，其他校验失败也必须回滚该预留记录。

不同幂等键竞争同一个预期版本时，只允许一个成功，另一个返回版本冲突。相同幂等键
和内容返回原始结果，并标记为重放。同键不同内容继续返回 `idempotency_conflict`。
租户隔离、当前所有者和 Workspace 鉴权、能力检查以及已准入 Turn 的快照保持现有语义。

## 约束与风险

使用现有的每 Session 加锁顺序和回执查询，不变更 schema、API、隔离级别、连接池，
也不引入租户级锁。只有重复回执路径使用锁定查询，Session 锁已经串行化同一回执
作用域内的调用。重放请求在读取原始结果之前，会有一次重复插入的开销。
移除单独查询计划模式的语句。本次以针对性的并发覆盖验证正确性，不作为吞吐量基准
测试。模型选择和其他配置变更路径不在此次范围内。

## 验证与验收

分别为内置 Agent 和已存储定义创建 Session，让两个事务都读到版本 0 后再同步执行。
不同幂等键必须得到一个版本 1 结果和一个 `approval_selection_conflict`；相同幂等键
及内容必须得到两个版本 1 结果，且恰好一个标记为重放。两种情况下，持久化版本都必须
为 1，恰好存在一条 SET_APPROVAL 回执和一个 `session.approval.changed` 事件。
等待必须有超时，避免同步失败时测试悄然阻塞。

还需让两个不同 Session 的缺失回执哈希落在同一个已有索引间隙内。在缺失回执查询
或首次插入处同步，要求两个变更都能提交，生成两条完成回执和两个事件，且没有待处理
回执残留。已有的拒绝变更和版本冲突测试也必须验证不残留预留回执。

在使用 REPEATABLE READ 的真实 MySQL 8.4 上运行这些回归及已有的审批行为测试。
H2 验证兼容性，不能证明 MySQL 的快照行为。检查 SQL 所有者和事务契约，以及生产
代码的 Checkstyle。在 PR 测试报告中记录复现、针对性测试结果和环境差异。完整的
MySQL/Hosted profile、SpotBugs 和平台检查仍是 CI 验收要求，本地针对性通过不能替代。
