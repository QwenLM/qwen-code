## 1. Responsibilities, Authorization, and the Single Commit Container

Session stores identity, authorization decisions, domain-operation state, and resource references. Harness performs the original model calls, scheduling, orchestration, interaction, and result conversion. Runtime operates files, processes, LSP, and network transfers in its assigned workspace. A staged tool still has one model-visible invocation; internal stages do not create another tool vocabulary or a reduced model loop. Section 3 contains the full registry. Dynamic MCP, Skills, and Hooks use [configuration and extensions](managed-agent-config-extensions.md), not a second registration authority here.

All Session domain changes use `domain.committed {domain, version, operationId, recordRef}`, with `recordRef` pointing to a persisted, closed-schema domain payload. This document adds neither top-level events such as `rewind.committed` or `session_conversion` nor another Session journal. Existing `tool.intent/tool.receipt/checkpoint.committed/lifecycle.changed` represent invocation, settlement, checkpoint, and lifecycle respectively; domain payloads link them by reference rather than duplicating independently mutable facts. Runtime physical intents, per-stage/per-file outcomes, and recovery logs are stored separately in [RuntimeReceiptStore](managed-agent-recovery-operations.md). Session must accept their results before they drive the model or official history.

Reuse `SessionKey/CommandMeta/DurableRef/InvocationBinding/ToolOutcomeRef/CommitReceipt`; field encoding, digests, limits, and reference closure follow the storage specification. `DurableRef` remains `resourceId/kind/schemaVersion/byteLength/digest`; MIME, provenance, retention purpose, and file attributes belong in the corresponding resource-description body, not an incompatible ContentRef. Do not add fields in place to existing owned Tool v2 or InvocationContextV1: new execution stages and eligibility belong in a negotiated control envelope, retaining the complete, immutable original invocation reference inside it.

New model-generated tool intents must come from the current activation. Subsequent maintenance, publication, and release for accepted domain operations may use an authority-issued `OperationGrant` without starting a model. The grant binds the original SessionKey, operationId/domain/revision, owner, workspaceGeneration, resourceScope, and lease. Runtime admits only original planned stages through a monotonic per-operation gate. Maintenance first acquires the corresponding barrier; new eligibility cannot reexecute a revoked stage. Original receipt queries/intake use the original binding or operation proof without manufacturing an activation. User cancellation, revocation, or transport EOF cannot erase completed effects; unknown retains `recovery_blocked` and is not automatically retried by renewing a grant.

### 1.1 Domain Registry for This Design

The following domains apply to Managed Session, with event `version=1`, `recordRef.kind='managed-<domain>'`, and `schemaVersion=1`. Each body contains operationId, operationRevision, the preceding record reference, an explicit operation/phase, and input/result references. The server validates the listed producer, legal state transitions, scope, and reference closure. New names require explicit schema/producer/consumer registration; arbitrary JSON append is not allowed. Legacy format does not append these events; section 7.2 defines creation control for conversion to legacy.

These seven domains belong to the single name index in [storage §3.1](managed-agent-session-storage.md#31-domain-注册索引). Registration does not enable an unimplemented stage; history_operation is not an alias for the three history domains below.

### 1.2 Initial Hosted Scope and General Compatibility

The selected deployment is Linux/Kubernetes, a Java control plane plus qwen serve sidecar, a Session-exclusive Runtime Pod, and a CSI-exclusive Workspace volume. Initial Hosted tool acceptance covers only Read/Write/Edit/foregroundShell; the 47 entries in section 3 are the complete tool-placement target, not an initial enabled set. Unaccepted Hooks, MCP, background tasks, client callbacks, and similar paths are explicitly rejected in Hosted, with neither auto-local nor Legacy fallback. Ordinary general-purpose entry points retain the existing Legacy compatibility choice in section 3.1; this is not a global Legacy ban.

Harness does not mount Workspace. Startup configuration comes from an immutable Bundle, and its own Session state is read through established storage interfaces. Compaction attachments and path content come only from committed, still-authorized result resources or an official Runtime read; the latter also acquires section 4.4 occupancy. An identical path on Harness local storage is not usable input. new/spawn/restore, derived Config, child/workflow, recovery, and compaction cannot bypass profile validation or actual Runtime routing. Disabled paths reject explicitly; being constructible through another entry point grants no capability.

This revision does not design new quotas/billing; existing section 5 limits and resource-retention rules remain. Tenant trust tiers and strong-isolation runtime selection are deferred, not evidence of completed production multitenant security. General credential boundaries, revocation, and narrow original-call eligibility follow the [private protocol](managed-agent-control-protocol.md) and [recovery operations](managed-agent-recovery-operations.md), without another execution authority.

### 3.1 One Catalog, Three Result Sources

The complete registry is the sole model catalog. A trusted internal execution plan supplies `executionOwner=session|harness|runtime|staged`, planVersion, and definition digest for each actually registered tool. eager/deferred/alwaysLoad/aliases/maxOutput/truncate/ToolSearch use the same registration result. Runtime manifests contain only actual Runtime capabilities; Session tools need not masquerade as Runtime descriptors. ImageGen's separate factory, derived Config, and child/workflow registration must all connect.

If initialization finds an enabled tool without an execution plan, it cannot silently remove the tool, use Harness-native fallback, or change the owner after creation. New-session compatibility selection retains its original legacy scope; an already Managed Session explicitly rejects that configuration. Full admission requires implementation/acceptance of every actual entry. FS_PATH_TOOL_NAMES, path-conditional permissions, Skill triggers, and resultFilePaths each use the real scope, rather than merely expanding the nine-proxy table.

Direct physical tools use `ToolOutcomeRef.source=runtime`; pure domain tools use domain; Harness structured results and registered staged orchestration use orchestration. Staged results reference every real Runtime/domain/model outcome and compose one original ToolResult using the fixed plan. orchestration is not a bypass for Harness to self-report physical success. Invocation IDs, batch ordinal, and result-consumption positions remain in HarnessCheckpoint v1, without another model-checkpoint format.

## 4. Concrete Contracts for Staged Tools and Workspace Operations

### 4.1 Stages and File Proofs

The new `ToolStageEnvelope` contains the original CommandMeta, original InvocationBinding (needed only for physical tool stages), planRef, stageId, ordinal, effectId/effectRevision, inputRef, and invocation eligibility. The control protocol distinguishes an original activation fence from an accepted operation's OperationGrant. Embed the original v2 payload unchanged; do not append stage fields to the old reference. Mixed stages are registered segments under the original execute; model bridging does not turn into Runtime model execution. Each segment's effectId/effectRevision fixes actual input and prerequisite proofs; phaseOperationId follows the recovery design. Renewed grant operationRevision changes only admission/CAS, not the original effect ID. Changed arguments require acceptance of an explicit new effect, never overwriting unknown. Runtime also validates declared stages, prerequisite receipts, args/policy/media/Hook versions, and the actual resource scope.

File identity uses the explicit union `FileProof = absent | file{digest,byteLength,mode,identityRef}`. identityRef is a Runtime-generated dev/ino or platform-equivalent identity, not model input. Missing, unchecked, and originally absent are distinct; omitted optional fields cannot mean absent. Normalize workspace paths only within verified scope, rejecting symlink/ancestor-replacement escapes. Large file sets use paginated manifest refs within storage limits.

Physical stages reuse RuntimeReceiptStore's intent→dispatch_started→phase_settled→accepted→released/tombstone. Bodies distinguish `not_started_proven/running_attached/settled/unknown/corrupt`, while native status retains not_started/success/error/cancelled. Staged success must satisfy the original whole-tool contract; later model failure cannot rewrite an earlier successful physical stage as unexecuted.

### 4.3 Git/Worktree and Non-Tool Entry Points

In addition to enter/exit tools, cover `packages/cli/src/serve/routes/workspace-git*.ts`, `workspace-github-prs.ts`, `packages/cli/src/serve/server/git-branch-ops.ts`, Shell Git, and Agent/Workflow worktree creation. The owning runtime's cwd/env/trust/filesystem must match; unknown/removed/draining cannot fall back to primary.

Runtime read-only operations are git status/diff/log/branches and GitHub PR list/default-branch. Mutations are checkout/branch-create/push/pull (including fetchOnly/rebase)/commit, PR-create, and worktree prepareCreate/commitCreate/inspect/remove. Reuse original route DTOs, binding trusted repoId/worktreeId, expectedHead, expectedStatusDigest, owner, and generation; Runtime resolves paths. PR/Git network credentials go only to the corresponding provider, not model keys. Shell retains original commands and permissions; new APIs do not bypass authorization for push, dirty-tree cleanup, or similar actions.

Session-owned worktree operations use workspace_operation and OperationGrant from this design. Workspace routes without Session use `WorkspaceOperationGrant`: WorkspaceKey (tenantId/workspaceId), generation, operationId/domain/operationRevision, ownerId/resourceScope/lease. The workspace control owner stores maintenance records, and RuntimeReceiptStore stores physical results; no fabricated SessionKey, temporary Harness, or attachment to an existing Session's fact log. Their physical key is `(WorkspaceKey,generation,effectId,phase,effectRevision)`, a separate type from Session operations. They remain subject to per-operation gates, workspace maintenance barriers, physical ownership, and shared capacity; rename/checkout cannot corrupt context by running concurrently with other Session writes.

Worktree creation proceeds: accept plan/fix ref and target path→actual git creation→owner marker and sidecar→verify real object→register usable handle. Marker/sidecar failure cannot yield a fully owned success receipt; resume their writes under the original plan, or clean up only after verifying continued ownership and no user changes. Removal checks owner, HEAD, dirty digest, live children/downloads/file requests and never deletes another owner's worktree. Multistep Git is not a database transaction; record completed steps explicitly. If push/PR-create occurred but ACK was lost, inspect the original remote ref/PR identity rather than repeat network effects automatically.

enter_worktree retains return-path semantics. Commit context_change only for an explicit cwd switch: pause new work, wait for old-generation in-flight calls/background file owners to reach a safe boundary, then bind new read cache/fileHistory/ignore/LSP/permissions/Runtime capability. Admit only after the new generation commits. If shared writers cannot be stopped, return busy/recovery_blocked rather than mixing old and new cwd.

### 4.4 CSI Volume Serialization: First Access Through Model-Consumption Commit

This is an initial Hosted supplemental safety gate, unimplemented and unaccepted. The complete physical fencing and stop/unmount-proof contract is normatively defined in section 17 of the [Endpoint recovery design](2026-09-21-managed-runtime-endpoint-recovery.md). This section fixes tool/history integration with that barrier without another lock service.

- Initially one Workspace uses one writable CSI volume and requires ReadWriteOncePod (RWOP). ReadWriteOnce (RWO) limits nodes, not Pods, and cannot substitute for RWOP.
- A trusted Registry resolves the physical conflict key `storage backend domain + CSI driver + opaque volumeHandle`, retaining cluster, PV UID, PVC UID, and binding relationships as resolution evidence. Clients cannot self-assert it; reject duplicate PV aliases that cannot be reliably identified. tenant, Session, generation, Workspace alias, subdirectory, mount path, and same-volume worktree cannot split the lock. Distinct physical volumes can run concurrently. No directory-level concurrency or new worktree-creation feature is introduced; section 4.3 remains the existing full target.
- Existing Java Workspace/Broker storage persists occupancy through short CAS transactions, never a database transaction held across RPC. Phases are `reserved → active → draining → released`, with separate `blockedReason`; blocking does not clear the holder. Record original Session/turn, operation, binding, revision, and history/stop/unmount proof references. qwen remains authoritative for Session history/checkpoint and Runtime supplies physical evidence.
- An occupancy lease grants coordination responsibility, not timed automatic volume release. Controller loss transfers investigation responsibility, not new execution rights; a new DB epoch, expired grant, or human acceptance of UNKNOWN risk does not release physical occupancy. New records/envelopes require closed schemas and version/capability negotiation, not silent additions to strict Tool v2/attestation v2 or InvocationContextV1.

Execution and handoff must follow this order:

1. Model first: tool-free inference neither acquires nor waits for the volume. After qwen commits the original tool intent, Java validates persistent Workspace binding and reserves occupancy; environment warm-up that never accesses Workspace may run concurrently. If initialization precedes a tool intent and might access Workspace, it first acquires the same occupancy through the original accepted initialization operation, rather than mounting under the guise of warm-up.
2. Acquire occupancy before the first potentially Workspace-accessing initialization, history bind, prepare, snapshot, or read. Broker verifies the actual Runtime, mount, and ContextBinding and installs the existing gate before opening access; restore has no read-first/lock-later exception.
3. The same occupancy continuously covers first initialization/snapshot, history bind, prepare, reads, approval waiting, final admission, and execution. Approval waiting must not release occupancy and later continue from an old snapshot/approval. If the original operation is cancelled and safely exits, continuation needs new lawful acceptance and revalidation, not reused prepare state.
4. At turn end, fence new dispatch, drain owned processes/descendants and output, and durably accept original results and required media/backups. qwen commits corresponding history/checkpoint, including the results actually consumed by the model and their consumption positions. execute success, receipt ACK, or display-card completion alone does not permit release; unknown model-consumption/history commit retains `draining` with `blockedReason`. Cancellation/closure cannot wake the model; original narrow eligibility instead persists result settlement and an explicit no-further-consumption state, never fabricating model consumption for release.
5. The same Session may retain an idlePod, but keeps volume occupancy. Another Session's request requires trusted stop proof for the old Pod/owned processes, normal CSI unmount and necessary storage-handoff proof, and verified history settlement before CAS transfer. Different Sessions' Runtimes cannot keep the same volume hot-mounted simultaneously; idle state, no current tool, or lease expiry is no exemption.
6. Pod NotReady, force-delete, successful API deletion, disappearance of VolumeAttachment, or observation timeout alone does not prove stopping. Partitions retain the barrier under Endpoint section 17; only verifiable node physical fencing or reliable backend revocation of the old write channel allows subsequent volume/history checks. Stopping still does not prove external effects did not occur; original UNKNOWN requires reconciliation.

Other Sessions waiting for the volume are awaiting admission, not fabricated execution UNKNOWN. Initial release does not enable H-stage shared-write children: no borrowing the parent's lock, and no parent holding the lock while waiting for a same-volume child. Reuse original-call status/cancel/intake; do not create another Runtime, re-prepare, or execute to query it. CSI/profiles lacking provably safe handoff disable automatic takeover; do not bypass this by changing cluster force-detach settings.

## 5. C06: Complete Content Access, Media, and Retention

### 5.1 Content Identity and Access

Under storage §2.1, the resource registry binds DurableRef to session_owned or workspace_owned, producer invocation/operation, original Runtime generation, purpose, access policy, actual backend, and holding references. Session resource tables retain their private resources and authorized workspace refs. Workspace configuration and explicit pins are not subordinate to the source Session's lifecycle. resourceId carries no path; digest proves bytes, not authorization. Unguessable IDs do not replace permission checks; global content hashes cannot expose cross-tenant existence queries.

Internal `resource.read` takes ref, offset, length, and purpose, validating owner/purpose and current retention state from the trusted connection. Each chunk is at most 1 MiB, each manifest page at most 256 entries/1 MiB. Chunks have digests; full reads verify total length/digest. A range cannot falsely claim whole-content verification. Retain existing small inlineData; large media/backups use the negotiated resource protocol, without silently turning original tool-argument limits into arbitrary file-read capability.

Add ordinary owner-routed `GET /session/:id/artifacts/:artifactId/content`, retaining existing client/Session read authorization and resource-download capability checks; parameters accept no arbitrary path/URL. Return safe MIME, Content-Disposition, range/total length. Metadata without proven readability cannot return successful download. Separate HTML preview origin and sandbox CSP prevent generated scripts from acquiring daemon-trusted origin. Neither file:// nor Runtime paths replace browser content URLs. Include the new endpoint in [client adaptation](managed-agent-client-surfaces.md); existing artifact list/register/delete and input attachments remain unchanged.

workspace/external_url/managed/published retain distinct semantics: workspace identifies the current file, returning changed on identity change and missing on disappearance; managed is an immutable controlled copy; external_url registers without fetching; published references an actual publication receipt. Metadata-only recovery is unverified, not downloadable. Actual Runtime checks symlinks, ancestors, and replacement during reads. To share content with another Session, private content gets an independent target copy and workspace_owned content an independent authorized target holding, rather than forwarding a bare ID. Resource-content type and registry lifecycle owner are separate dimensions.

### 5.2 Media Processing and Budgets

Runtime handles Read/Zoom physical validation, PDF info/text/render, and image transformations; Harness handles media and model calls according to real model modalities. The new `PdfReadCandidate` body contains sourceRef/sourceDigest, page numbers and page-image resource manifest, fallbackTextRef, and original conversion parameters/capability revision. Complete candidates may be paginated, but Harness waits until all selected pages transcribe successfully without inline/fileData before replacing text fallback; one successful page cannot represent the entire PDF.

Legal empty base64 means 0 bytes; image/audio/video/native PDF retain original native-result semantics. DisplayImage consumes display content only; recovery cannot add display-only images to the model. HarnessCheckpoint references full model content and the resource set; existing in-memory image markers/short hashes are not recoverable, authorized storage.

The storage specification is the sole limits authority. Do not raise original Runtime input 256 KiB/depth 64, ordinary results 8 MiB, media 64 MiB minus 64 KiB, ACP frame/total queued bytes 64 MiB, or 256 entries. Meter decoded bytes, wire bytes, queued bytes, model in-flight bytes, and durable-resource quota separately. Small inline content also reserves concurrent capacity; large legal results become refs, and window backpressure cannot lose completed receipts. Storage uses the effective workspace disk budget and shared 64 MiB settlement reserve, not per-Session duplicate reserves or unlimited intake.

If wrapping/transport exceeds limits after successful native execution, retain the original physical status and resource copy and deliver refs through status/reconcile. Repeated execute/status/cancel errors must not lose release evidence. For recoverable model history, provider adapters record modelInvocationId→resourceId and actual converted bytes/digest. Restart, compaction, and reuse reconstruct from controlled resources rather than duplicating whole base64 content in every event. Validate Runtime, Session resources, and provider payload separately; one successful >8 MiB result proves neither complete upper bounds nor concurrency.

### 5.3 Lifecycle, Pins, and Collection

Resource states are staged→committed→retired→collected. staged requires a producer owner; preserve the sole content before Session result commit. Runtime cannot release the only copy before Session accepts complete results/required media and backups, commits the related checkpoint, and has no other child/waiting references. release unbinds execution lease; it does not delete user workspace files or published pages.

The full target explicitly implements quota-bound `pin/unpin`: ephemeral follows its original ephemeral owner, restorable a recoverable Session/branch, and pinned an explicit user retention reference. The workspace content owner first validates and persists the immutable controlled copy and user holding, then Session resource domain references its receipt. Reconcile cross-owner registration/lost ACK by original operationId; no Session-ACK-before-preservation gap. Charge actual length to the owning workspace's effective storage budget. Failed reservation returns resource_limit, not empty metadata pin. External links are not automatically downloaded; unavailable actual content cannot be pinned as recoverable. Until capability is enabled, continue explicitly rejecting pinned rather than merely relaxing the old validator.

Session close retains restorable/pinned; archive does not reduce holdings. Session deletion releases ordinary history references. Pinned references release only by explicit unpin or an explicit user choice to delete pinned content too. From the outset the pin holder is the workspace content service's user holding; Session domain only references its receipt. Deleting the source Session does not delete that holding. The content service provides authorized list/read/unpin handles; operations outside the model use WorkspaceOperationGrant without duplicating Session history. Cancellation, fork, or source deletion never silently unpins. During downloads/model consumption, retire first and stop new reads; collect after authorized streams drain. Revoked streams stop immediately, with accounting deducted after handles actually exit.

GC applies only to managed content with zero retained references, zero in-flight users, and no unsettled physical operations/recovery dependencies, rechecking revision before execution. Each fork has independent references, so source deletion cannot damage it. Reference GC does not delete user workspace files or remote published content; remote unpublish requires independent authorization and an actual receipt. No automatic user-history TTL; log references and original-call digests cannot disappear with Runtime cache expiry.

Publication holds, fork/export pins, in-flight readers, and investigation/legal holds must all be checked before collection. Cross-owner publication with unsettled reference ACK cannot lose its sole copy. Source Session deletion does not remove these grounds. UNKNOWN is not a legal basis for indefinitely retaining sensitive data: use authorized investigation/retention policy, but do not fabricate settlement through timeout GC. Backups, snapshots, object versions, key revocation, and vendor erasure follow [storage](managed-agent-session-storage.md) sections 2.3 and 2.4.

## 6. C13: Checkpoint, Diff, and Physical Rewind

### 6.1 Verifiable Plans

File-history backup manifests require backupId, original owner/workspace, normalized relative path, preimage existence, digest/byteLength/mode/identity proof, and content DurableRef. Session stores manifest/revision; recovery bind verifies actual bytes first. Missing backup cannot silently select an older version. Arbitrary Shell/Git/external-process workspace changes are not inherently tracked. diff/rewind explicitly list included files and uncovered scope, without claiming automatic rollback of the whole workspace.

Internal commands are fixed as `prepareRewind`, `commitRewind`, and `readRewindStatus`. prepare returns `RewindPlan{operationId,sourceHistoryRevision,sourceProofRef,targetPromptId,targetRecordId,mode,filesManifestRef,artifactPlanRef,planDigest}`; mode is conversation or conversation_and_files. File entries include path, current/target FileProof, targetBackupRef, and restore/delete/unchanged. Resource manifests contain complete missing/conflict results. prepare only reads history/workspace and may persist a plan in controlled resources; it neither truncates chat nor restores files.

Execution uses the original history operation's OperationGrant, binding authorization to planDigest/target/mode/resourceScope. The history gate preserves existing synchronous busy admission and rejects in-flight turns by default, without secretly cancelling others' work. Physical file mutation additionally requires a maintenance barrier over all controlled writers to that workspace. Reject if another Session/Monitor/child can still write and cannot drain. External editors are outside the gate, so apply/compensation recheck identity and digest per file.

### 6.2 Commit, Cancellation, and Recovery

1. Acquire maintenance eligibility and validate the sole writer, complete source revision, target active boundary, Runtime history, and backup closure; do not guess a compacted target from turnIndex. conversation-only also fixes the original revision but does not mutate workspace files.
2. Commit history_rewind prepared/applying facts. Before each effect, Runtime syncs intent, undo copies, and target staging. Its physical ledger records explicit phaseOperationId and every file step; absent Session events do not imply no execution.
3. Atomically replace/delete each file within the same filesystem, preserve before/after proofs, and sync directory changes. This is not an instantaneous cross-file physical transaction; external programs can see intermediate states. The platform must meet the recovery design's identity/sync profile; cross-volume rename is not assumed atomic.
4. After verifying all target files and required artifact/backup refs, authority commits the committed body and target projection binding in one history_rewind transaction. Reference only an existing checkpointRef that covers the target without revoked state. If none exists and storage §2.2's verified, no-continuation conditions hold, use checkpointRef=null, restoreBasis=history_rewind, and restoreProofRef=the committed operation proof with the complete target active history/recovery basis. Missing resources or corrupted checkpoint reads never justify null. A maintenance OperationGrant cannot manufacture checkpoint.committed or rewrite an old checkpoint's coveredSequence. Do not physically truncate original chat facts: the new branch projects only the target chain, excluding old continuations, unconsumed results, and revoked child/budget refs. After the next lawful Harness switches model history, recording parent chain, file history, and artifact timeline, it first commits a before_model checkpoint before execution. Release the original maintenance barrier after target closure commits and existing views are acknowledged or isolated; do not fabricate model activation to produce a checkpoint.
5. On physical-stage failure, do not switch chat projection first. Runtime compensates changed files using undo, first checking that each current file still equals this operation's postimage. Stop on external new writes; retain affected files and recovery_blocked rather than overwrite later user content. Complete rollback still means this rewind failed, not that its target was reached.
6. A prepared operation that has not changed files may settle cancelled. Cancellation during applying first persists the request, then waits for the original operation to converge at a safe stage to committed, rolled_back, or recovery_blocked. Client deadline does not release the barrier/original physical owner. Proven completion retains success; a late receipt is not rewritten cancelled.
7. Crash recovery validates original RuntimeReceiptStore, current file pre/postimages, and Session commit marker. If physical work completed without Session commit, idempotently finish committing only when the target still fully matches and source revision is unchanged; otherwise block without overwriting again. If Session committed, restore its projection. Lost ACK returns the original conclusion for the same operationId, never a new restore. Unknown owner retains close/delete barriers.

Read-only snapshot/diff also use the owning Runtime and immutable backup resources, never Gateway local disk as a substitute for remote storage. Retain backup/undo until recovery operations and fork references settle. Post-success background GC follows the resource protocol and is not synchronous cleanup required for success.

### 6.3 The 268-Member Mapping and Existing Public Returns

Preserve both original methods in the [268 public-member mapping](managed-agent-session-method-map.md): getRewindSnapshots returns `{snapshots: RewindSnapshotInfo[]}`, and rewindSession retains `Promise<RewindResponse>`. Preserve request promptId/rewindFiles, synchronous busy/closing admission, and queue semantics waiting for the actual reply after dispatch. Do not substitute internal RewindRecord/CommitReceipt into REST/ACP/SDK.

```ts
interface RewindResponse {
  rewound: boolean;
  targetTurnIndex: number;
  filesChanged: string[];
  filesFailed: string[];
  warnings?: string[];
}
```

Legacy retains best-effort adaptation; existing void rewindRecording is not globally changed into a strongly committed Promise. Managed `rewound:true` requires the committed result, target projection, and complete necessary physical/resource closure above. Neither ACP success:true nor empty filesFailed proves success for the new capability. Determinate per-file failures may adapt to rewound:false, actual filesChanged/filesFailed, and bounded warnings. filesChanged describes actual changes involved; warnings describe rollback results/unrestored scope. Do not fabricate filenames to represent storage errors.

When unknown storage commit, missing required artifact/backup, unisolated owner, or similar conditions prevent a determinate old-format result, reject the original Promise through its existing error channel and retain internal recoveryRef, rather than return correctly shaped but false success. Committed results with only noncritical display warnings may retain warnings. Clients publish successful session_rewound and switch projection only after actual commit; explicit failure/blocked cannot masquerade as the new completed capability using old success:true.

Preserve legacy export errors/returns through adaptation; enable new recoverable packages only after capability negotiation.
