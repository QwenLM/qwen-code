# Skills at Managed Session creation

[English](2026-10-20-managed-session-creation-skills.md) | [简体中文](2026-10-20-managed-session-creation-skills.zh-CN.md)

## Problem and scope

Managed Sessions currently obtain static Skills only from a stored AgentDefinition. Session creation cannot add instructions for one conversation, and the built-in `qwen-code` agent has no stored definition. Add optional static Skills to public and WebShell Workspace Session creation using the existing Skills management page. Direct discovery by the Managed execution Runtime remains future work.

## Design

Creation accepts an optional `skills` array with the existing `name`, `description`, `body`, and optional `base_directory` fields. Omission and an empty array preserve existing behavior. Nonempty additions require an authorized Workspace binding and a Harness advertising `session-skills/2`. Skills do not change tools, permissions, models, or Hook configuration. Asset paths remain relative to the Session working directory and are accessed through the selected Runtime.

Admission resolves the original AgentDefinition pin, concatenates its Skills with the additions, and validates the complete catalog using the existing limits: at most 256 unique names, 2 MiB compact JSON, 4 KiB descriptions, and 512 KiB bodies. Duplicate names are rejected. AgentDefinition admission retains its existing 16-entry, 32-KiB/body and 48-KiB limits; the larger format is gated by the Session creation capability. Both origins use the same `managed-agent-skills` resource kind, whose shared resource validators apply the 2-MiB bound; the smaller definition limits are enforced at admission. The request digest includes normalized additions, so changing the content under the same idempotency key conflicts; retries do not resolve a newer definition.

In the creation transaction, store the effective catalog and its SHA-256 digest in the Workspace creation receipt's existing `result_json`. This is immutable Session configuration, not a change to the AgentDefinition identity. No SQL schema changes are needed. Read the receipt through the existing Session index with tenant and Session identity checks and validate its digest. Child admission copies the effective catalog into its own creation receipt, avoiding a later dependency on the parent. Existing Sessions without a snapshot keep their original definition-based behavior.

The connector publishes the saved catalog as the existing immutable `managed-agent-skills` resource. A new top-level `sessionSkillsRef` on Hosted create/load carries that exact reference for built-in and custom agents. Hosted persists it in `managed-definition`, verifies the bytes, includes it in the resource closure, and rejects conflicting load requests, including omission of a saved reference. When present, this effective catalog supersedes the definition's Skill catalog. The original AgentDefinition, model, approval selection, and Hook pins remain unchanged. Recovery and resource inventory readers traverse the new reference; missing or corrupt bytes fail loading.

The read-only Session Skill catalog uses the same saved effective catalog. Its authorization remains persisted-Workspace scoped: readable Session, tenant isolation, current Workspace grant, and metadata-only responses. Session creation remains persisted-Workspace scoped; the new export route belongs only to the explicitly selected daemon Workspace.

The existing Skills page is the configuration source. Its enabled entries are imported automatically before a new Managed creation attempt; upload and enable/disable controls stay there, and the separate creation form is removed. The App shares the selected daemon Workspace explicitly between the Skills page and creation. This is an explicit import from that trusted source, not a claim that a Java Workspace ID identifies the same filesystem or Runtime. There is no fallback to the primary daemon when the chosen source is unknown, untrusted, starting, draining or removed.

Before admission, the composer Skills menu lazily reads metadata from that same selected source and lists enabled user-invocable entries, including manual-only Skills. Reopening refreshes the creation menu after configuration changes; source changes discard late results, and failures stay visible. Opening the menu does not export bodies or create a Session. Submission still reads a fresh complete snapshot and freezes the exact creation request. Admitted Sessions use only their pinned catalog, with no fallback to this live source. Extensions and MCP keep their separate capability checks.

The `/` entry uses the same catalog as the plus menu. Managed composers map each Skill to a Skill-category slash suggestion; typing `/` starts lazy loading, and `/name` filters the results. Arrow keys navigate, while Tab, Enter or clicking complete `/<name> ` without sending. This mapping applies to both creation and pinned Session catalogs and does not advertise daemon built-in commands.

A new selected-workspace-scoped, authenticated, read-only `/workspaces/:workspace/config/skills/snapshot` endpoint exports enabled instruction bodies on demand. It reuses the configuration status provider's SkillManager and disablement decisions, rejects incomplete discovery, and verifies the selected generation after asynchronous reads. Existing event/status responses remain metadata-only. Frontmatter grants, Hooks, model overrides and source filesystem paths are not imported. These remain static instructions; asset directories are not copied or reinterpreted as target Workspace paths.

The catalog preserves optional `model_invocable` and `user_invocable` flags. Manual-only Skills stay enabled and support a leading user slash invocation, while model advertisements and actual model calls cannot invoke them. User-hidden Skills stay available to the model and are omitted from the slash menu. The larger bounds cover the observed 42 enabled Skills (approximately 928 KiB, with a 395 KiB body). Only the `managed-agent-skills` inline resource kind receives the 2 MiB bound; generic inline resources retain 64 KiB. Large invoked bodies are limited by the selected model's tool output budget before the model-facing result is committed through existing Managed message chunking. Later Turns and cold recovery read that same result without restoring discarded text. The immutable catalog resource still retains the full original body. Generated leading user invocations persist their origin with the assistant record; interrupted batches retain invocation restrictions and their shared output budget, including when only some results committed. Recovery treats records without a trusted user-origin marker as model calls.

The exact array is saved with the existing pending creation in IndexedDB, so an uncertain request is retried without rediscovering Skills after a reload. The selected source must still match when preparation completes. Later management changes affect new Sessions; existing Session catalogs remain fixed. The creation page links back to Skills management instead of duplicating its controls.

## Components

Public/WebShell request models and OpenAPI; Session service and creation persistence; Skill snapshot reader and catalog; selected daemon Workspace export and shared Skills-page selection; Hosted connector and Java SDK; Hosted definition validation, resource traversal and execution; WebShell provider, creation import, pending request storage and translations.

## Validation and acceptance

1. Built-in and custom Workspace Sessions accept valid Skills through both APIs. Merging retains definition Skills; conflicts and combined limits reject atomically.
2. Same-key retries return the original Session; changed Skill bytes conflict. Definition updates, reconnects, and child creation retain the original snapshot.
3. The real Hosted process advertises, loads, and supplies the selected instruction body before inference, including leading `/name` and Plan mode. Conflicting/missing/corrupt references fail explicitly.
4. An unauthorized actor cannot create or read the catalog. Snapshot-read children expose no Skills. Unbound requests reject additions, and incompatible Harness versions reject admission.
5. The existing Skills page controls enabled entries. Creation imports all enabled entries from the selected trusted source, excludes disabled entries, preserves manual/user invocation flags, refuses source drift, and retains the exact request on pending restoration. Before creation, the composer lists enabled user-invocable Skills, refreshes them on reopening, and reports metadata failures without creating a Session.
6. Run focused Java/TypeScript tests, API generation, build/typecheck/bundle, Maven verify, disposable MySQL integration, and applicable Hosted process tests. Record unavailable environments separately.
7. Complete two clean self-audit passes and independent code review, then deploy the tested local artifacts using the existing private configuration and database. Verify health, an existing Session, and a new Skill-enabled Session through the deployed UI/API.
