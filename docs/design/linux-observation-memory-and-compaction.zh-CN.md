# Linux 观察内存与紧凑化

[English](linux-observation-memory-and-compaction.md)

## 范围

在现有 Linux 第二轮候选上只补两项：可访问性树紧凑展示、LibreOffice 观察资源限制。
App API、剪贴板和 OSWorld 代码不在范围内。补齐 SDK/driver 0.20.9 及其版本引用；
正式发布另行执行。SDK 到原生 AT-SPI 的调用结构、权限和安装方式保持不变。

## 紧凑展示

此前候选只缩短了单行字段，没有迁移 macOS 0.20.6 已包含的结构投影。
Linux 的 revision 还只包含可操作节点，导致静态状态和说明文本丢失。

保留观察到的静态上下文，再折叠空布局容器、去掉父子重复标签、合并同一父节点下
相邻的静态文本。保留窗口、对话框、菜单、列表、表格和文档边界，区分网页正文与
应用界面，保留焦点、选择、禁用状态及全部可操作节点。投影采用迭代实现，避免深树
消耗调用栈。原生索引、身份和结构化动作列表不变。revision 比较包含保留下来的
静态文字和可编辑字段清空后的空值。紧凑化仅用于模型观察输出；浏览器内部设置和
授权提示的精确匹配仍使用原始静态标签边界。

## 内存调查

Task035 原始工作簿的表格暴露 1,073,741,824 个子项，并声明 `manages-descendants`。
受控单次 `GetChildren` 请求使 LibreOffice RSS 在 24.14 秒内增加 107.75 MiB，
拟合速率 4.45 MiB/s，请求进程内存不变。达到软限制后主动停止独立实例，无须真正
触发 OOM 即可复现增长。这是直接 AT-SPI 请求的复现，不是历史沙箱重启根因的证明。

增加请求日志的原 b30 候选也通过实际 SDK 调用复现了增长：三次观察均退回 X11，
日志停在表格 GetChildren 且未返回；第三次调用期间 LibreOffice 约增长 4.52 MiB/s，
Node RSS 不变。调用方返回并不能取消应用已经开始的全量枚举。

普通节点改用 `ChildCount` 和惰性的 `GetChildAtIndex`，每层只保存下一兄弟游标；在请求
子节点之前检查节点、深度和时间预算。快照与动作共用前序遍历及可操作索引计算。达到
深度限制时只读元数据，不展开子项；子项请求失败时标记捕获不完整。修复不禁用
Calc 可访问性，也不会先分配完整数组再截断。

实测证明仅按索引读取仍不够：对相同 512 个真实单元格连续读三轮，每轮约 2.8 秒
返回，但 LibreOffice 每轮仍保留约 3.3–3.4 MiB 内存，部分单元格每次产生新的 AX
对象路径。AT-SPI 明确说明不应枚举 `ManagesDescendants` 节点的子项。因此不展开
这类虚拟子项，保留表格和其他界面，并以 `managed_descendants_omitted` 标记有界
观察；已捕获控件仍保留稳定身份，但不声称包含完整工作表。缺失内容用截图查看。
不引入应用重启或新的可访问性事件处理系统。

## 普通布局采集

普通 Calc 窗口还暴露了庞大的隐藏菜单树。独立有界普查读到 1,861 个节点，其中
1,638 个未显示；11,188 次明确的 D-Bus 请求均无错误。带计时的 final3 SDK 在
25 秒截止前完成 770 个节点，其中 752 个未显示，没有单次调用超时。因此剩余
问题是大量正常遍历工作累积，不能归因为 LibreOffice 的某个方法卡死。
原生计时包含点对点调用，计时包装次数不是总线消息数；独立普查的串行请求统计
也不能直接当作原生并发遍历耗时。

并发读取角色、状态和接口后，在名称、详情和子项读取之前跳过隐藏原生菜单及其
子树。保留已显示、聚焦、选中或展开的菜单；不对网页正文或未知可见性套用规则。
打开菜单后的下一次观察会读取其内容。以 `hidden_menu_subtrees_omitted` 明确标记
有界捕获，仅对实际读到的控件保留身份。
省略的命令不占可操作索引；token 按捕获的 AT-SPI 身份解析，打开菜单不会因行号
变化把已有 token 指向其他控件。

采集共享整个快照的绝对截止时间，包含准备和后续坐标阶段。累计节点和坐标保存在
可取消 future 之外，后续慢请求超时不会抹掉先前结果。时间预算耗尽仍是读取不完整，
不能保留稳定 revision token。原生 25 秒上限保持不变。facade 遇到
`walk_deadline_reached` 或 `element_bounds_timeout` 时直接返回，不再自动重读；
短暂读取失败仍保留一次重试。真实故障注入发现，对耗尽预算的捕获自动重试会产生
两次原生读取、约 51 秒等待。后续显式观察仍可正常恢复。

## 验证

将紧凑输出与同一份完整捕获树比较，同时检查必要内容、可操作身份以及行数和字符
变化。覆盖静态文本变化、无变化 revision、字段清空、表格行、网页边界、当前 token
和深层布局。在独占的 Linux 测试桌面执行真实 SDK 观察和独立应用状态回读。

采集单次及重复观察之前、期间、之后的 LibreOffice 与 SDK 进程内存，保留原始采样
及操作状态；基线和候选使用相同文档。不能从文本变短或调用超时推断模型计费下降
或历史 OOM 根因。

只修复内存的候选（`6babbd96`）通过四次全屏观察，但三次普通布局观察分别在
25.762、25.042、25.048 秒超时。这组精确二进制对照及上文计时验证，确认了
独立的隐藏菜单遍历问题。

普通布局修复版（`d4ba57b6`）在同一 Task035 文档上四次分别耗时 11.570、10.989、
13.454、10.815 秒，返回 157/157/190/157 个可操作元素。每次均到达真实表格，表格
token 保持不变；第二次未变化读取返回 `no_change`。点击 File 后出现 33 个新增
菜单标签，Escape 后恢复初始菜单标签集合。两项主动省略均明确报告，
`captureReadComplete=true`、`captureComplete=false`。连续 68.986 秒采样中，
LibreOffice RSS 在 340644–340652 KiB 之间，最大采样间隔 0.163 秒。
这是有界的真实应用验收，不是长期泄漏压测或完整 benchmark。

同一 native 的真实 GTK 对照也通过：legacy 树逐字一致，控件深度从 10 降到 2，
静态说明保留，token 点击、字段替换读回、无变化及 token 稳定性均正常。
revision 字符从 352 增至 554，因为基线遗漏了静态信息；这不是 token 成本下降
的测量结论。

受控 AT-SPI provider 验证了已完成节点和坐标保留、单个子项失败后继续读取后续
兄弟节点、状态读取失败后不枚举子项。旧 facade 在元数据超时场景读取两次，耗时
50.785 秒；坐标超时场景读取两次，耗时 50.965 秒。这些是修复前的重试测量，
不是 0.20.9 的预期延迟。

最终 0.20.9 包（native `3554fe81`、facade `f0ba1e38`）在同一元数据超时场景
耗时 25.833 秒，仅产生一次原生快照，保留 26 个控件，采集超时后没有发起坐标
请求。新的普通最大化 Calc 验证在 11.084 秒返回 157 个控件，随后在 10.492 秒
返回 `no_change`；表格 token 相同，两项有界捕获原因均明确报告。23.471 秒采样
中 LibreOffice RSS 固定为 340228 KiB，最大采样间隔 0.153 秒。该最终 smoke
使用打包后的 0.20.9 SDK，并核验了 native、JavaScript、包和固定 skill 的 hash。

最终版本检查：Linux 单元测试 294 通过、4 忽略；SDK 测试 164 通过、6 项依赖环境
的测试跳过；固定 skill 7 通过；发布流程测试 68 通过、1 跳过。release build 和
包验证通过，覆盖 pack、publish dry-run、checksum 校验的全新安装、固定 skill
逐字比较和原生加载（60 个工具、支持 revision）。Node REPL 保持 0.1.5；这些
检查没有执行正式发布。
