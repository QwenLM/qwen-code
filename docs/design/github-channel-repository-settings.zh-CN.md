# 在 Web Shell 编辑器里配置 GitHub 渠道的仓库级设置

[English](github-channel-repository-settings.md) | [简体中文](github-channel-repository-settings.zh-CN.md)

状态：提案。承接已合入的编辑器可用性工作（#16096），补上该 PR 在 Risk & Scope 里列出的
「按仓库设置仍只能改 `settings.json`」这一缺口。

## 问题陈述

有三项设置决定 GitHub 渠道的行为，而它们都无法从 Web Shell 修改：

| 设置                                              | 作用域 | 控制什么                               |
| :------------------------------------------------ | :----- | :------------------------------------- |
| `groups["<owner/repo>"].senders` + `allowedUsers` | 按仓库 | 哪些 GitHub 账号可以在该仓库里发起任务 |
| `groups["<owner/repo>"].requireMention`           | 按仓库 | 未被 @ 的评论是否会被处理              |
| `pollInterval`                                    | 渠道级 | 轮询通知 API 的间隔，单位毫秒          |

今天的编辑器只暴露渠道级发言人默认值（`groups["*"].senders` / `allowedUsers`）与仓库允许列表本身。
操作者若想把某个仓库限制给两位维护者，或让某个仓库无需 @ 就响应，就必须到 daemon 宿主机上手改
`settings.json`——表单里根本看不到这个值。

实际后果是放开的默认值一直留在原地。渠道级发言人默认是 `open`，所以收窄它等于一次性收窄所有仓库；
只收窄一个仓库的唯一途径，就是表单不展示的那个文件。

## 现状

- `packages/channels/github/src/index.ts` 声明了 `token`、`useLocalGh`、`baseUrl`、`groupPolicy`、
  `reasonFilter`，没有声明 `pollInterval`，所以描述符驱动的表单永远不会渲染它。Email 插件已经把同一个键
  声明为 `number` 字段，带 `exclusiveMinimum: 0` 与 `default: '60000'`，这就是要照搬的先例。
- `GithubChannel extends PollingChannelBase`，其 `pollInterval` getter 读取 `config.pollInterval`，
  在缺失、非有限数值或非正数时回落到 `60_000`。
- `GroupGate.check()` 解析 `requireMention` 的顺序是
  `groupConfigFor(chatId)?.requireMention ?? groups["*"]?.requireMention ?? true`，
  发言人策略则是按仓库的 `senders` 回落到 `"*"` 再回落到 `open`。两处查表都走 #16096 加入的
  大小写不敏感群组匹配。
- `channel-editor-state.ts` 由允许列表字符串构建 `groups`，逐字保留每个已列仓库的既存设置，
  并把渠道级发言人默认值写进 `groups["*"]`。按仓库的条目原样带过，没有对应的草稿状态。
- daemon 已经接受本设计需要的全部编辑。`channel-settings-store.ts` 把
  `groups.<id>.requireMention` 校验为布尔、`senders` 校验为 `open` 或 `allowlist`、
  `allowedUsers` 校验为字符串数组，并按 `exclusiveMinimum` 校验描述符声明的 number 字段。
  **不需要改 daemon、SDK 或描述符 schema。**

## 目标

1. 在渠道编辑器里修改单个已列仓库的发言人策略与允许列表。
2. 在同一处修改单个已列仓库的 `requireMention`。
3. 在同一张表单里修改渠道的轮询间隔。
4. 保持继承语义：操作者没有自定义过的仓库必须仍是一个空覆盖，从 `"*"` 再回落到内置默认。

## 非目标

- 不改任何默认值。群组策略默认值的分歧单独记录在 #16144，有意不在本次范围内。
- 不编辑 `groups["*"].requireMention`、`dispatchMode`、`groupHistoryLimit`。这些键继续原样往返。
- 不新增描述符字段类型、不改 SDK，也不为非仓库型平台提供按仓库 UI。聊天平台保持现有表单。
- 不做基于 GitHub API 的仓库选择器。仓库仍在允许列表字段里按 `owner/repo` 手填。

## 方案

### 渠道层：声明轮询间隔

在 GitHub 插件的管理描述符里加一个字段，照搬 Email：

```json
{
  "key": "pollInterval",
  "label": "Poll Interval (ms)",
  "kind": "number",
  "exclusiveMinimum": 0,
  "default": "60000"
}
```

随后既有的描述符驱动路径就会渲染、校验并持久化它，无需编辑器代码。编辑器的分区映射把它放进
**连接**（与 `baseUrl` 同区），因为它描述的是渠道如何连到 GitHub，而不是谁可以使用它。

分区映射按字段名而不是按平台生效，所以 **Email 既有的 `pollInterval` 字段也会从「应用凭据」移到「连接」**。
那是第二个轮询平台上含义相同的同一个设置，而它本来就该在那里；把映射限定到 GitHub 只会为了
让一个放错位置的字段继续放错而多加一个条件判断。没有其它平台声明这个键。

新渠道的间隔保持**为空**：编辑器不会用描述符默认值预填 number 字段，所以在操作者输入之前不会持久化任何值，
60 秒默认仍归运行时所有。声明的 `default` 用于在线上契约里记录生效值，与 Email 一致。

### 编辑器状态：每个仓库一份三态覆盖

新增一个草稿字段：

```ts
export interface ChannelGroupOverrideDraft {
  /** '' 表示继承；否则是显式布尔的字符串形式。 */
  requireMention: '' | 'true' | 'false';
  /** '' 表示继承；否则是显式策略。 */
  senders: '' | 'open' | 'allowlist';
  allowedUsers: string;
}

// 挂在 ChannelEditorDraft 上
groupOverrides: Record<string, ChannelGroupOverrideDraft>;
```

键是规范小写的仓库 ID，与 `assignGroups` 已经为仓库型渠道写入的键一致。

- **读取。** `createChannelEditorDraft` 为每个已存仓库键（排除 `"*"`）生成一条，把已存的
  `requireMention` 布尔翻译成 `'true'` / `'false'`，键缺失翻译成 `''`。已存的 `senders` 原样取用，
  缺失取 `''`。`allowedUsers` 用 `, ` 连接，与渠道级字段完全一致。该读取函数是模块私有的，并与保存路径共用。
- **写入。** `assignGroups` 把草稿覆盖合并到已存群组对象之上，**逐字段与「对已存对象的同一份读取」比对**。
  草稿值仍等于已存读取的字段，原样保留它的已存键；只有发生变化的字段才写入，而变回 `''` 的字段删除其键。
  编辑器不建模的键（`dispatchMode`、`groupHistoryLimit` 以及任何未知键）原样复制。
  从允许列表里删掉的仓库会失去条目，与今天一致。
- **为什么比对而不是覆盖。** 有两种已存形态无法用「三态控件 + 文本框」表达：空允许列表
  （`allowedUsers: []`，意为*没有人*），以及只有列表没有策略（有 `allowedUsers` 而无 `senders`，
  意为*继承策略、覆盖成员*）。简单的「写入解析出的列表，空则删除」规则会在操作者本想无操作的保存里
  把这两种形态都改成别的东西。与初始读取比对，让未触碰的字段在构造上就不可能被改动，
  于是无需脏标记也能保证往返精确。
- **显式允许列表拥有自己的列表。** 当该行自己的策略是 `allowlist` 时，空文本框写入 `[]`——没有人——
  而不是删除该键、悄悄继承渠道级列表。当该行继承时，清空文本删除按仓库的列表，让渠道级列表重新生效。
  两种情况由合并后群组的 `senders` 区分。
- **选择策略本身也拥有列表，即使文本从未改动。** 这是新加一行的默认状态，所以它是最可能走到的路径而不是边角：
  操作者选「仅允许列表」、输入框留空，此时 `allowedUsers` 的两份读取都是 `''`。
  只在*文本*变化时才触发的守卫会跳过写入，落盘成没有列表的 `{senders: 'allowlist'}`，
  运行时的 `??` 会把渠道级列表原样交回来——操作者手上最严格的那个操作变成一次空操作，而界面报告成功。
  所以当操作者**把策略改成** `allowlist` 且已存群组没有列表时，也要写入空列表。
- **这条规则有意只作用于「策略被改过」的情形。** 已存的 `{senders: 'allowlist'}` 而没有 `allowedUsers`
  是一种合法的手写形态，意为「允许列表策略、成员从 `'*'` 继承」。在那里写 `[]` 会收窄一个没人编辑过的渠道——
  正是「与初始读取比对」这条规则要防的那类静默迁移。两个方向各有自己的用例与自己的变异钉住。
- **继承是默认。** 没有自定义的仓库写出 `{}` 并继续继承。编辑器绝不能把 `requireMention: true`
  或 `senders: 'open'` 物化进未触碰的仓库：那会把今天的默认冻进配置，并让之后对 `"*"` 的修改
  悄悄无法到达该仓库。

### 编辑器 UI：每个已列仓库一行

在既有的「访问控制」分区内、仓库允许列表字段正下方，且仅当群组策略为 `allowlist` 时，
按允许列表字符串解析出的每个仓库渲染一个块（用与保存路径相同的 `toList` + 小写化 + 去重）。
每块以仓库 ID 为标题，含三个控件：

| 控件         | 组件     | 取值                                                                                  |
| :----------- | :------- | :------------------------------------------------------------------------------------ |
| 需要 @       | 下拉     | 继承 / 需要 @ / 无需 @ 也响应                                                         |
| 谁可以发言   | 下拉     | 继承 / 任何人 / 仅允许列表                                                            |
| 允许的发言人 | 文本输入 | 逗号分隔的 GitHub 登录名，当该行的*生效*策略是 `allowlist` 时显示——自己的，或继承来的 |

继承值写在选项标签里，让操作者看见自己继承的是什么——例如当 `"*"` 或内置默认解析为 `true` 时显示
`继承（需要 @）`。展示的解析顺序与运行时一致：按仓库 → `"*"` → 内置。发言人输入按生效策略而不是
该行自己的策略把门，因为继承允许列表的仓库仍然有一份值得编辑的成员列表；它的辅助文案说明留空即沿用渠道级列表。

行内的选项标签与占位符是仓库专属的（`任何人`、`仅允许列表`、`alice, bob`）。复用共享的群组成员字符串
会把 `Any group member`、`Listed members only`、`user-a, user-b` 带回 GitHub 表单——
正是 #16096 消除的那种群聊/仓库错配。

每一行都是一个 `role="group"`，由它自己的仓库标题标注。否则所有行的控件都会共用
「需要 @」「谁可以发言」这两个可访问名称，一旦列出多个仓库，读屏用户就分不清自己在编辑哪个仓库。

行在每次渲染时由允许列表推导，所以输入一个仓库会立刻出现它的行，删掉则行消失。被删仓库的覆盖状态
在保存时由 `assignGroups` 丢弃，不需要单独的清理步骤。

如果更想用布尔开关而不是下拉，必须用原生 `<input type="checkbox">`；#16096 已经确认 Radix 的
`Checkbox` 放进这个 `<form>` 与 `Dialog` 会触发无限更新循环。本设计两个三态控件都用下拉，
既绕开这个问题，也把「继承」表达成一等取值。

## 设计决策与理由

1. **按仓库设置只改编辑器，轮询间隔走描述符字段。** 新增描述符字段类型会波及 SDK、daemon 的校验镜像，
   以及所有渲染描述符的客户端，而它服务的形态只有一个平台家族在用。编辑器本来就对仓库型渠道做特判、
   本来就写 `groups`，所以按仓库的行属于这里。轮询间隔是普通的渠道级标量，因此走普通的描述符路径。
2. **三态，而不是布尔。** `GroupConfig` 区分「缺失」与 `false`。两态控件无法表达「继承」，
   而把它默认成解析后的值，会在第一次保存时把该值写进每个仓库——这是一次静默迁移，
   方向取决于渠道，可能放开也可能收窄。
3. **行由允许列表推导，不单独存储。** 成员关系只有一个真相来源，意味着一个仓库不可能「有设置却未被放行」，
   而 #16096 的别名冲突与 `owner/repo` 校验继续作用于同一个字符串。
4. **小写键。** GitHub 仓库路径不区分大小写，#16096 已让运行时按此匹配。覆盖键使用同一规范形式，
   所以重打大小写不会让某个仓库的设置变成孤儿。
5. **不为空的发言人允许列表新增校验。** 在显式 `allowlist` 下，空列表意味着「没有人」，
   这是合法配置，也已经是渠道级字段的行为。在继承策略下，空文本框意味着「没有按仓库的列表」，
   于是渠道级列表生效。在这里加拒绝会让两个控件互相矛盾。
6. **`inherit` 是哨兵值，不是空字符串。** Radix 的 `Select.Item` 拒绝空 `value`，
   所以控件在组件边界把 `''` 映射成 `'inherit'`，变更时再映射回来。草稿保留 `''`，
   这正是与已存读取做比对得以直截了当的原因。
7. **把一行切到「任何人」会保留它已存的发言人列表。** 该列表在开放策略下不起作用，
   而删掉它会毁掉操作者改回允许列表时可能还想用的内容。只写入操作者真正改动的那个字段，
   这与「未触碰的保存是 no-op」是同一条规则。

## 约束

- daemon 的既存值守卫会拒绝非法的嵌套类型，所以编辑器必须为 `requireMention` 写真布尔、
  为 `allowedUsers` 写真字符串数组，而不是字符串。
- 既有测试钉住「未触碰的按仓库键在一次保存后存活」（`dispatchMode`、`groupHistoryLimit`、
  `requireMention`）。合并必须是在已存对象之上做加法，绝不能整体替换。
- 操作者输入过程中，仓库允许列表可能为空或含非法条目。行只为能解析成 `owner/repo` 的条目渲染；
  既有的校验错误仍然阻止保存。
- `pollInterval` 必须保持可选。空输入删除该键，让运行时保留它自己的 60 秒默认，
  而不是持久化一个操作者从未选过的数字。

## 风险

- **意外放开访问。** 给一个原本继承允许列表的仓库选「任何人」会放开它。选项标签写明继承值，
  让改动在保存前可见；行里展示的是生效策略，而不只是草稿。
- **冻结默认值。** 物化继承值会是一次静默迁移。三态模型与一条「未触碰的仓库仍保存为 `{}`」的测试
  共同防住它。
- **丢掉手写设置。** 合并保留未知键；既有保留性测试就是守卫，并新增一条用例覆盖
  「同一仓库既有未知键又有被编辑的已知键」。
- **范围蔓延到其它平台。** 这些行由 #16096 引入的同一个 `isRepositoryOnlyChannelType` 助手把门，
  所以聊天平台在构造上就不受影响。

## 验证计划

- 单测：状态往返（未触碰的渠道读取→保存是 no-op）、显式覆盖写入、继承删除键、未知键保留、
  被删仓库丢弃条目、重打大小写的仓库保留设置、空允许列表、非法仓库条目。
- 组件：每个已列仓库出现行、输入仓库即新增行、发言人输入仅在显式允许列表时出现、
  继承提示反映 `"*"`、轮询间隔渲染在「连接」区。
- 变异：上面每条行为主张都用「引入对应变异并确认恰好描述它的用例变红」钉住。
- 构建守卫：三个 vite 构建加 `client/build-artifact.test.ts`，因为新文案会进入 transcript 产物。
- 视觉：仓库自带的 visuals 装置，两套主题，截图前断言按仓库的行存在。
- 手工：对真实 daemon 保存一次仓库覆盖，确认落盘的 `settings.json` 里是 store 会校验的布尔与数组形态。

## 验收标准

1. GitHub 渠道的轮询间隔可以在编辑器里设置、清空与校验，空输入让该键保持缺失。
2. 每个已列仓库显示「需要 @」控件与发言人控件，默认都是「继承」。
3. 保存一个未触碰的渠道，写出的 `groups` 对象与读到的完全一致。
4. 显式覆盖写出布尔 `requireMention`，允许列表写出字符串数组 `allowedUsers`；
   把控件改回「继承」会再次删除该键。
5. 编辑器不建模的键在一次保存后原样存活。
6. 任何聊天平台的表单都不变。Email 的轮询间隔与 GitHub 的一起移到「连接」，因为分区映射按字段名生效。
7. 两种语言都渲染新文案，且构建产物守卫通过。

## 待决问题

- 渠道级 `"*"` 的「需要 @」默认值是否也应该可编辑？它是每个仓库继承的值，而今天只能改
  `settings.json`。本次不做，以保持 diff 聚焦在按仓库控制；值得后续单独决定。
- 轮询间隔在 UI 里是否应该用秒表示？毫秒与存储键以及 Email 插件既有标签一致，
  所以本设计为保持一致仍用毫秒。
