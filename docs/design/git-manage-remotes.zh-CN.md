# Web Shell Manage Remotes（管理远程仓库）

[English](git-manage-remotes.md) | [简体中文](git-manage-remotes.zh-CN.md)

## 问题陈述

Web Shell 工作区的 git 弹出面板（`BranchPickerPopover`，从左侧栏工作区 git 胶囊按钮或 composer 分支 chip 打开）可以 pull、commit、push、创建/检出分支，并按 remote 名分组列出远程跟踪分支——但无法管理 remote 本身。从 zip 克隆（没有 `origin`）的用户、采用三角工作流（fork + upstream）的用户、或想删除过期 remote 的用户，都必须离开 Web Shell 去用终端。

目前不存在任何面向 git remote 的 daemon 路由、SDK 方法或 core CRUD 辅助函数（2026-09-06 经 grep 验证）。除此之外，`git remote` 还出现在：shell 只读分类器、worktree-service 的一条错误消息、`gitPush` 内部的 push-remote 解析，以及 `packages/cli/src/commands/review/` 下两个只读的 `git remote -v` 解析器（`lib/remote-match.ts`、`match-remote.ts`），再加上 `packages/core/src/extension/github.ts` 中 simple-git 的 `getRemotes`——这些先例说明渲染出来的 `git remote -v` 界面并不稳定（remote-match 已经带有一个针对部分克隆 `[filter]` 标注的回归测试），这也是下方新读取器直接读取仓库的配置 scope、而不读任何渲染输出或按名称访问器输出的又一个原因。

范围（已与维护者确认）：**list + add + remove**，以 **BranchPicker 弹出面板内的一个面板**形式呈现。不做 set-url、rename、fetch/prune。

## 变更方案

### 1. Core —— 新增 `packages/core/src/utils/git-remotes.ts`

```ts
export interface GitRemoteInfo {
  name: string;
  fetchUrl: string;
  pushUrl: string;
  extraFetchUrls: number;
  extraPushUrls: number;
  promisor: boolean;
  partialCloneFilter?: string;
  customRefspec: boolean;
  otherSettings: number;
}

export function isValidRemoteName(name: string): boolean;
export function isValidRemoteUrl(url: string): boolean;
export function isRemovableRemoteName(name: string): boolean;
export async function fetchGitRemotes(cwd, env?): Promise<GitRemoteInfo[]>;
export async function gitRemoteAdd(
  cwd,
  name,
  url,
  env?,
): Promise<GitRemoteInfo[]>;
export async function gitRemoteRemove(
  cwd,
  name,
  env?,
): Promise<GitRemoteInfo[]>;
```

- `fetchGitRemotes` 用单次 `git config --list --show-scope -z` 读取仓库**自身可编辑的 scope**，只保留 `local` 与 `worktree` scope 的记录。单独的 `git config --local` 比该 scope 更窄：`.git/config` 中一条 `include.path` 条目所贡献的键仍被 git 标记为 `local`，而 `extensions.worktreeConfig` 的 remote 存放在 `config.worktree` 中，因此仅 `--local` 的读取会少列条目、让 `git remote add` 走入死局（git 的重复检查会看到被 include 进来的名字）、并让 `git remote remove` 对一个拆分 section 报告成功（其被 include 的另一半仍然存活）。继承来的（`global`/`system`/`unknown`/`command`）remote 保持不列出（git 也无法删除它们，声称列出它们就等于为一次永远不会发生的删除背书）。读取配置而非 `git remote` + `get-url`，使列表不受 `insteadOf` 重写影响、对多值 `url`/`pushurl` 完整（以 `extraFetchUrls`/`extraPushUrls` 携带）、且没有 `git remote` + `get-url` 那种对每个 remote 两次的访问器扇出（列表本身是一次 git 进程调用；每个携带 promisor 的 section 额外一次 `--type=bool` 读取，此类 section 仅出现在 partial clone 中）。Section 附加信息（`promisor`、`partialclonefilter`、非默认 fetch refspec，以及作为 `otherSettings` 的其他 `remote.<name>.*` 设置计数）随结果一并携带，以便 UI 能说清删除会毁掉什么。`promisor` 的**值**由宿主机 git 自己解析（对每个携带 promisor 的 section 执行 `git config --type=bool --get-all`）：git 的整数布尔文法（strtoimax 拼写规则、单位因子、`maybe_bool` 界限）只能由宿主机 git 回答——在模块内维护一张解析表等于复制一个无法对齐版本的解析器——并且该键按累加方式读取（`--get-all`），因为 git 在 ANY 为 true 的记录上就会注册 promisor remote，而不是只看最后一条。记录以 NUL 分帧：在 `-z --show-scope` 下每条记录是 `scope\0key\nvalue\0`（无值的键是 `scope\0key\0`），这样带空格的 subsection 名和带转义换行的值都可解析。先运行一次 `rev-parse --git-dir` 探测：在仓库之外，其 stderr 携带 git 标准的 "not a git repository" 文本，路由分类器以此为准；而 `--list` 本身在未配置任何 remote 时会以退出码 0 返回仓库的其他键，所以空列表来自 scope 过滤。
- `gitRemoteAdd` / `gitRemoteRemove` 执行 `git remote add -- <name> <url>` / `git remote remove -- <name>`（`--` 终止符使删除能作用于 add 谓词所拒绝的、存在于配置中的名字），然后返回 `fetchGitRemotes`，因此每次变更响应都携带最新列表。Add 会先跨 ALL 配置 scope 对名字做预检：git 的 remote 家族的写入（add/remote 的重复检查、remove 的 section 编辑）只写仓库 scope（local、include 来源、worktree），而 fetch/push 跨所有 scope 解析名字——因此重复检查看不到继承来的（`global`/`system`/`unknown`/`command`）section，面板自己的 Add 否则会静默制造同名冲突：git 随后会从面板不显示的记录解析 fetch/push，多值 url 会同时推送到两个目的地。这种形态以 409 `remote_shadows_inherited` 拒绝（刻意的 shadow 属于终端）。删除运行镜像对称的预检，来自 ONE 份带 origin 标注的全 scope 转储（`--show-origin --show-scope`），在启动 `git remote remove` 之前完成：git 的 rm 在可能失败之前就会先删除跟踪引用并 unset 指向它的分支的键，所以任何表明该 section 有一部分活在删除所能编辑的两个文件之外的记录都必须预先拒绝——继承 scope 的记录（`global`/`system`/`unknown`/`command`）与仓库 scope 记录并存时（split-section 情形，git 会在毁掉 local 一半后以退出码 0 收场，而存活的一半继续让名字可解析）拒绝为 409 `remote_shadows_inherited`——仅存在于继承 scope 的 section 没有仓库一半可毁，因此落到 git 自己的 no-such-remote 404（客户端的过期行收敛正是以它为键）；origin 是 `include.path` 文件的仓库 scope 记录（scope 标签是 `local`，仅靠 scope 读取无法区分）拒绝为 409 `remote_section_in_included_file`。两种拒绝都不做任何改动。预检的「是否在仓库内」顺序来自其内部的读取：配置转储在仓库外会以退出码 0 返回（带着继承配置），但其 `rev-parse` 探测会在检查任何记录之前就在那里抛错，所以 git 标准的 not-a-repository 答案始终占优（add 路径钉死同样的顺序）。相对形式的 origin 相对 worktree 顶层目录（TOPLEVEL）解析（git 在 setup 期间 chdir），所以子目录 cwd 也能正常删除。删除之后验证该 section 已从仓库 scope 消失，AND 该名字完全不再解析——验证取两者的并集：全 scope 的 section 读取（一个继承来的 pushurl-only section 在 fetch 侧会以裸名解析，解析器看不见它）与 git 自己的解析器（`ls-remote --get-url`，从不接触远端）：任一 scope 中的配置幸存者、遗留的 `$GIT_DIR/remotes/<name>` 文件、`branches/<name>` 文件、或 insteadOf 别名，都会让一个「已删除」的名字仍可 fetch。被拒绝的删除——包括被 include 一半存活的拆分 section——永远不会被报告为成功。有一个 scope 需要补救：`git remote remove` 无法编辑每个 worktree 自己的 `config.worktree`，并且会在删除跟踪引用 AFTER 才以 "Could not remove config section" 失败，于是一个 worktree scope 的行会被列出却永远无法删除，每次重试都重复破坏。当存活的 section ONLY 位于 worktree scope 时，删除用 `git config --worktree --remove-section` 完成收尾并重新验证；local scope 的幸存者继续回答 `remote_still_configured`（兜底——include 形态已被上面的预检拒绝）；任何其他 scope 的幸存者按删除本身失败的方式上报——`git remote remove` 本身失败时 git 的拒绝以 409 `git_config_write_failed` 呈现，git 退出码 0 但名字仍可解析时由全 scope 验证回答 `remote_still_configured`——并且在没有 `extensions.worktreeConfig` 时收尾永不运行（那里 `--worktree` 选择器会静默等同于 `--local`）。收尾也绝不会在 git 尚未做任何变更就失败时触发：git 会在其 fatal 行内逐字回显配置选出的 refspec 值，而该值可以携带真实换行，所以收尾只在行首匹配其拒绝短语，任何行首出现 `error:`/`fatal: invalid refspec` 都直接否决收尾——该拒绝有自己的答案（409 `remote_config_unparsable`；该行保留，以便用户修复 refspec），一次被收尾的「删除」会把它掩埋。剩下的 `Could not remove config section` 失败是配置写入失败——锁竞争，或一个根本不存在、无从改名的 section（上文遗留 `$GIT_DIR/remotes|branches` 形态，git 在 unset 分支键后以此消息作答）——以 409 `git_config_write_failed` 呈现。删除还会先清扫 git 的 rm 可能留下的孤儿跟踪引用——rm 只通过它能解析的 fetch refspec 删除它们，所以一次已认证的删除还会清扫无 refspec section 留下的 `refs/remotes/<name>/*` 命名空间（每个引用 `update-ref --no-deref -d`，归属按配置集合加被删名的最长前缀判定，含精确的裸引用——前缀兄弟的命名空间不动），并重新验证；no-such-remote 重试路径上同样收敛该清扫。删除还会清理 `git remote remove` 够不到的 upstream 键：git 只在它能写的文件里 unset 指向该 remote 的分支的 `branch.<b>.remote`、`merge` 与 `pushRemote` 键，并对多值键跳过且仅告警，因此存放在 `config.worktree` 的键——以及多值的 local 键——会存活成悬空的 `branch.<b>.remote = <gone>`（下次 pull 直接 fatal）。删除前快照记录指向该 remote 的分支——fetch 指向由 `branch.<b>.remote` 判定、push 指向由 `branch.<b>.pushRemote` 判定（各自按 worktree 覆盖 local、最后值胜出解析，因此实际上跟踪着某个 SURVIVING remote 的分支绝不被触碰）——在删除被确认后，unset local 与 worktree scope 的键（remote/pushRemote 条目用 `--fixed-value --unset-all`——多值键只贡献指名被删 remote 的条目——merge 用 `--unset-all`，且仅当同一 scope 的 remote 键不持有指名某个存活 remote 的条目时才动 merge——否则分支在那里保留其 upstream，merge 一半留下），并仅对按值匹配的键重新验证（merge 幸存者解析为 "." 且是惰性的，所以清扫无法编辑的、由 include 持有的 merge 键不得拒绝一次已完成的删除）。独立于指向快照之外，ANY 按值匹配到被删 remote 的 branch.<b>.remote/pushRemote 条目都要清除：多值键的非生效条目是残渣，日后浮现会成为悬空。链接 worktree（linked worktree）携带发起 worktree 的读取永远看不到的各自 config.worktree 文件，所以清扫遍历每个链接 worktree——`git worktree list --porcelain -z`，NUL 分帧字段——并清理它们——跳过 `prunable` 记录（目录已不在；无可读内容），并在某个兄弟 worktree 持有该名字的 per-worktree `remote.<name>.*` section 覆盖时拒绝（名字在那里仍可解析；属于面板不得摧毁的刻意状态），对每个存活 worktree fail-closed——同时容忍两种否定答案：尚无 `config.worktree` 的兄弟，以及 `extensions.worktreeConfig` 关闭时 git 的 `--worktree cannot be used` 拒绝（此时该文件在全仓库范围都是惰性的）。兄弟的 merge 键仅当同一文件的 remote 键正被按值清扫时才清扫——remote 存在共享配置里的 merge 不由这个文件决定。而 git rm 的生效值匹配可能删掉一个 LOCAL [branch <b>] section，其被遮蔽的副本指名的是某个 SURVIVING remote；删除前快照携带每个分支的 local 值列表，这些记录在 rm 之后立即恢复，BEFORE 一切事后门控（这样任何后续拒绝——门控侧或兄弟侧——都无法跳过对 git 自身破坏的回滚；rm 与恢复之间被 kill 是记录在案的残余风险——重试的新快照晚于破坏发生）。只重写缺失的键，且「缺失」用快照捕获的同一集合来读：scope 转储把 include.path 文件的记录标记为 `local`，所以存在性检查读 `--local --includes`——裸 `--local`（关闭 includes）会把 include 持有的幸存者重新加进 `.git/config`，复制它并永远遮蔽 include（`--add` 追加在 include 指令之后并在最后值解析中胜出）：存活键回答 `remote_still_configured`，而不是确认出一个悬空状态，清理失败后的重试会收敛到 no-such-remote 路径而非走入死局。push 指向的分支只失去其 pushRemote——它的 merge 键属于其存活的 FETCH upstream。解析到被删 remote 的 local 或 worktree scope `remote.pushDefault` 以同样方式清扫，因为 `git push` 否则会解析到已消失的 remote。存放在 git rm 无法写入的文件中的同类 upstream 键——`include.path` 文件（scope-local）或继承的 global/system 文件——也会存活为同样的悬空状态，而这些文件不在本模块会编辑的范围内，所以幸存者拒绝为 `remote_still_configured` 而不是被清扫。幸存者检查按 git 的方式解析每个 `branch.<b>.remote`/`pushRemote` 与 `remote.pushDefault`（scope 链上最后值胜出），所以被更高优先级 scope 中指向 SURVIVING remote 的记录所遮蔽的记录永不拒绝——git 的 rm 自己在 unset 前也比较生效值——而其 rm 所 unset 的 `.git/config` 遮蔽副本可能把一个同值的继承记录 UNMASK 成活生生的悬空状态，解析检查能抓到这一点。unmask 检查同样遵循删除前快照：一个被指向的分支，其遮蔽记录被删除 unset 后，可能回退到一个继承记录，其指名的 remote 在任何地方都没有存活 section（更早已删除，或在此从未存在）——分支的 upstream 从被删 remote 变成了悬空名，所以删除拒绝而不是为之背书。这里的「解析」是 git 自己的答案，而不是记录集合：裸词值用 `ls-remote --get-url` 探测（从不接触远端；仅在没有任何东西应答时逐字回显名字），因为一条无 URL 的 `[remote "foo"] proxy = …` 记录什么也解析不出来，而遗留的 `$GIT_DIR/remotes/<name>` 文件在没有任何记录的情况下也能解析——记录集合在两个极性上都是错的。探测是 FETCH 侧的（`ls-remote --get-url` 看不到 pushurl-only 的 section），所以两个 PUSH 侧分支（分支 pushRemote、remote.pushDefault）还把已取转储中的 `remote.<value>.pushurl` 记录或 `url.*.pushInsteadOf` 别名前缀计为可解析——仅 push 侧的 upstream 在 fetch 侧悬空但 push 侧可解析。以裸词命名 worktree 内目录仓库的值也计为可解析——git 的路径传输能应答它而解析器看不到——经 `ls-remote -- <值>` 探测（git 自己的传输按魔数识别目录仓库与 bundle，与扩展名无关；name 键的认证门从不做此探测：碰巧同名的目录不得让一个已配置的 remote 变得不可删）。只检查快照指向的条目——被指向的分支 AND 删除前的 `remote.pushDefault` 解析：快照证明它们的值 WAS 被删 remote，所以变化的值就是这次删除造成的——别处的既有悬空 upstream 不由这次删除来拒绝。git 无需 section 即可解析的无 section 值（本地仓库的 `.`、URL、scp 风格 `host:path`、本地路径 `/abs`/`./rel`/`a/b`）是合法 upstream，不是悬空名，在探测之前短路。同样的值也以「不予处理」的方式被拒绝作为删除目标：no-such-remote 收敛分支（section 已消失的重试）以名字是否可能是 section 名为门，所以 `remove(".")` 回答 git 的 404，而不会清扫按值匹配到 `.` 的存活跟踪键。裸词名在事后是可区分的，所以该闸门还会咨询 git 自己的解析器：一个没有任何 section 却仍解析的名字（insteadOf 别名——经探测会以 no-such-remote 失败且 git 不动任何东西）同样跳过清扫；worktree 内以裸词命名的目录仓库（解析器看不到的存活本地路径 upstream——经 `ls-remote -- <名>` 探测）也跳过清扫；push 侧别名（`url.*.pushInsteadOf`，即 `gh:` 形态）让裸名在 push 侧可解析而 fetch 侧无任何应答，此时由转储本身回答（git 没有 push 侧解析器探测）；遗留的 `$GIT_DIR/remotes|branches` 文件则会让 git 自己的 rm 在 unset 分支键之后因 section 缺失而失败（git 的自身行为，如实呈现——不在收敛分支内）。收敛清理会像认证路径一样重新验证引用清扫（幸存的引用——残留的锁——会被拒绝，而不是把该命名空间遗弃给 404）。该跳过的已接受残余：git 同样接受带冒号（或 `.`/`/` 形态）的 SECTION 名，因此一个手工创建的、名字形如无 section 值的 remote，若首次尝试的清理在清扫中途夭折，重试时不会收敛任何内容——两种状态（从未有 section 的存活 upstream 与删除失败留下的孤儿）在 section 消失后无法区分，而清扫有毁掉存活配置的风险。
- `runGit` 仍是唯一的 exec 封装：从 `git-branches.ts` 导出它（加一个关键字）并在此处导入；`gitEnv` 已经导出。
- `isValidRemoteName` 刻意保守——单个 refname 风格组件；它同时继承共享 `isValidRefName` 的分支名拒绝，包括 `HEAD`（git 自己的 remote 名检查会接受它：`refs/remotes/HEAD/foo` 是普通 refname）——拒绝它是刻意的保守，由谓词表钉死，而非对 git remote 规则的镜像。单个 refname 风格组件：复用 `isValidRefName`（控制字符/空格与 `~^:?*[\` 拒绝、点/`.lock`/`..`/`@{` 规则、每组件上限），并追加 `no /`、`no leading -`（flag 注入防护）与不可见字符类（渲染后与现有 remote 完全一样的名字是一个删除欺骗面）。git 在 `remote add` 时会再验证一次；这个谓词的存在是为了让路由能在启动 git 之前回答 400。
- `isValidRemoteUrl` 接受 git 接受的几乎所有东西（https/ssh/scp 风格/本地路径，含空格），拒绝空白、前导 `-`（exec 向量）、一般形式的会执行命令的 transport-helper 形态（锚定的 `<scheme>::` 前缀，无字母开头规则——`7z::archive` 会像任何其他 helper 一样执行 `git-remote-7z`），以及不可见字符类。helper 拒绝是必要的，尽管 git 默认策略也拒绝它们：该策略可被配置文件覆盖，任何按调用清洗环境变量的手段都够不到，也可被 `GIT_ALLOW_PROTOCOL` 环境变量覆盖，后者由 `gitEnv` 通过归一化中和——继承来的列表在剥掉会执行 helper 的条目（`ext`、`fd`）后保持其默认拒绝效力，过滤成空的列表保持已设置状态（全部拒绝）而不是变成 undefined。前缀锚定在开头，所以 IPv6 字面量（`ssh://git@[::1]/repo.git`）或 scp 风格路径永不匹配；原生 git 不带 `git-remote-ssh`，所以普通的 ssh/scp 风格/ssh:// URL 从不携带 `::` 分隔符，保持被接受。
- 不可见字符类派生自 Unicode 属性（`\p{Cc}` C0/C1 控制字符、`\p{Cf}` 格式字符、`\p{Default_Ignorable_Code_Point}`，加上行/段分隔符 U+2028/U+2029），而不是手工清单——属性随 Unicode 增长，枚举永远存在未列出的角落。
- `isRemovableRemoteName` 是删除谓词，刻意比 add 谓词**更宽松**：删除针对的是 git 已经配置的 remote（手工编辑的 `.git/config` 可以持有 add 谓词拒绝的名字，包括被清洗器剥离的不可见字符名），所以它唯一的底线是非空、execFile 无法在 argv 条目中携带的 NUL 字节、以及不含 `/`（带斜杠名字的跟踪命名空间会与前缀 remote 的冲突，清扫无法区分归属——见 §2）；`--` 终止符守护其余一切的 exec 向量，而不是靠拒绝名字。配置键永不为空且永不携带 NUL，所以 `/` 底线是列出行唯一可能失败的底线（带斜杠的 remote 会被列出但拒绝删除——终端的 `git remote remove` 仍是它的工具，见 §2）；路由仍会对客户端提供的名字应用该谓词（在任何 git 启动之前回答 400 `invalid_remote_name`）。
- 新文件加入 `packages/core/src/index.ts`，紧邻 `git-branches.js` 导出行。

- 错误映射：`workspace-git-branches.ts` 中共享的 `sendGitError`（已导出；其 `redactGitMessage` 辅助函数保持私有）新增七个 remote 专属分支，位置在**每个关键字分支之前**，因为 git 在这些消息中逐字回显用户选择的 remote 名（以及配置写入失败时的 URL）。每个分支 ONLY 在组合后 detail 的开头——第 1 行——匹配；config-write 分支额外接受 git 文档化的两行 `could not lock config file …` 链（lock 行是 git 自己的，不是回显内容）。表中的模式按 git 自己的大小写转写，而交付的代码大小写不敏感地匹配——这是为宽松遗留关键字分支预留的双保险余量（这些分支匹配截断到上限的切片——无界扫描会把超过上限的、URL 中携带关键字的长 push/pull 输出重新归类），针对的是同一分类器携带的关键字形态，而不是声称 git 会改变这些消息的大小写：配置选出的名字可以携带任何关键字，配置选出的值（URL 或 fetch refspec）可以携带真实换行——git 会反转义带引号值中的 `\n`——所以任何更深的行首文本都是攻击者可控的，绝不可认领：
  - `^(?:error|fatal): Could not remove config section ` /
    `^(?:error|fatal): could not set 'remote\.` /
    `^(?:error|fatal): could not unset 'branch\.` → 409
    `git_config_write_failed`（配置写入失败——锁竞争，或 section 位于 git 不愿编辑的文件——而非脏工作区；`git remote remove` 在删除引用和移除 section 之前先 unset 指向它的分支的 `branch.*.remote` 键，所以锁可能以三种形态中的任何一种浮现）
  - `^(?:error|fatal): remote .+ already exists\.?\s*$` → 409
    `remote_already_exists`
  - `^(?:error|fatal): No such remote: ` → 404 `no_such_remote`
  - `^remote still configured after removal$` → 409
    `remote_still_configured`（删除验证失败——存活的 section，OR 清理无法 unset 的 worktree upstream 键，OR 仍从 git rm 无法写入的文件（`include.path` 文件或继承的 global/system 文件，包括被 unmask 的同值继承记录）RESOLVING 到被删 remote 的 upstream 键，OR section 消失后名字仍可通过 git 自己的解析器解析（遗留的 `$GIT_DIR/remotes/<name>` 文件、`branches/<name>` 文件、insteadOf 别名），OR 兄弟 worktree 的 config.worktree 持有被删 remote 的键——或 per-worktree section 覆盖；该消息不携带名字，所以没有任何关键字分支可以认领它）
  - `^remote section lives in an included config file$` → 409
    `remote_section_in_included_file`（remove 预检拒绝；无 git 前缀的普通 Error，在 `git remote remove` 运行之前抛出，所以没有任何东西被破坏）
  - `^(?:error|fatal): invalid refspec` → 409 `remote_config_unparsable`（git 在变更任何东西之前解析配置的 fetch refspec 时就死掉：行保留，无破坏，原因可指名）
  - `^remote already configured in an inherited scope$` → 409
    `remote_shadows_inherited`（add AND remove 的预检拒绝——remove 在启动 git rm 之前运行同样的继承 scope 检查，因为 git 会在毁掉 local 一半后以退出码 0 收场——事后只有模块自己的全 scope 验证会拒绝；无 git 前缀的普通 Error）
    remotes 路由原样委托给它；其他一切（not-a-repo → 404 `not_a_git_repository`、脱敏后的 500 兜底）保持现有分类。影响面：该分类器被所有 git 路由共享，所以该表由属主文件里一个同目录的 `sendGitError` 分类表测试钉死（消息进 → 状态/码出），包括携带关键字的 remote 名与被分类 detail 的 stdout 一半。

- 数据流：进入视图时 fetch `workspaceGitRemotes(gitCwd)`；add / remove 直接使用变更响应返回的列表。只有 **remove** 随后在后台调用 `fetchBranches(true)`——`git remote remove` 删除 `refs/remotes/<name>/*`，所以 branches 视图的 remote 分组必须在用户返回前刷新；add 不创建远程跟踪引用，所以不刷。被 404 `no_such_remote`、409 `git_config_write_failed` 或 `remote_still_configured` 拒绝的 remove 也刷新分支列表与状态：git 在写 section BEFORE 就删除跟踪引用（以及指向它们的分支的跟踪配置），所以任何证明或留下该破坏的拒绝——另一个客户端先删了 remote、写入锁失败、或拆分 section 的另一半在验证后存活——否则会让屏幕上留下已消失的引用。**被拒绝的**变更**静默**重读 remotes 列表（无加载占位、无错误替换），且**仅当** daemon 的错误码表明列表已过时（`remote_already_exists`、`no_such_remote`、`remote_still_configured`）；其他一切拒绝（400 验证、503 draining、传输失败）保留可用行与已输入草稿在屏幕上，只通过底部状态栏发声。变更错误落进现有底部状态栏（`statusType: 'error'`）。
- 焦点：进入视图聚焦返回按钮；离开恢复 manage-remotes 行（其被禁用时恢复搜索框）。为进行中的变更禁用 add 输入框或删除按钮会在真实浏览器中使聚焦控件失焦，成功的删除会把聚焦的行整体卸载，所以焦点在变更落定时恢复：成功 add 后恢复到名字输入框，否则恢复到记住的字段或提交按钮。删除在行存活时恢复该行的删除按钮——包括静默重读使其保留的被拒删除——在行消失时恢复面板返回按钮，无论删除成功还是被拒删除所等待的重读把它收敛掉了。每次捕获与查找都从弹出面板内容自己的根解析（`getShadowAwareActiveElement` / 以根为作用域的 `querySelector`）：在 shadow-portal 嵌入中 `document.activeElement` 会重定向到宿主，`document.body` 查找无法跨越边界，否则整个恢复在那里都是惰性的。
- i18n（en + zh），跟随现有 `branchPicker.*` 区块：`branchPicker.action.manageRemotes`、`branchPicker.remotes.title`、`.empty`、`.noMatches`、`.loading`、`.namePlaceholder`、`.urlPlaceholder`、`.add`、`.back`、`.remove`、`.removeConfirm`、`.removeConfirmFor`、`.invisibleName`、`.hiddenChars`、`.lookalikeName`、`.searchPlaceholder`、`.urlTooltipFetch`、`.urlTooltipPush`、`.promisor`、`.partialClone`、`.customRefspec`、`.extraUrls`、`.otherSettings`、`.added`、`.removed`、`.invalidInput`（空值/前导横杠输入的客户端防护；daemon 仍是验证权威）。
- CSS：`BranchPickerPopover.module.css` 新增类（`.remotesHeader`、`.backButton`、`.remotesTitle`、`.remoteRow`、`.remoteName`、`.remoteBadge`、`.remoteUrl`、`.remoteRemove`、`.remoteRemoveConfirm`、`.addRemoteForm`、`.addRemoteButton`），构建在同样的 `--border` / `--muted-foreground` / `--destructive` 变量之上；头部与 add 表单在滚动盒内吸附，表单以 `min-width: 0` 输入框换行，不会溢出定宽弹出面板。

## 安全说明

- 所有 git 调用经由 `runGit`（execFile 参数向量，无 shell）；变更用 `--` 终止选项，使配置中的名字永不可能被读成 flag，`url` 拒绝 C1 控制字符与不可见字符类，是为了不让面板写入一个与兄弟行着墨相同的 URL（配置卫生；变更请求与 git 自己的输出仍携带原始值）。渲染边界的控制是显示清洗器，它同时覆盖写入谓词永远看不到的配置既有/继承 URL。
- 会执行命令的 transport helper（锚定的 `<scheme>::` 形态，如 `ext::`、`fd::`）被**写入谓词拒绝**。git 的默认策略（`protocol.ext.allow=never`）在连接时同样拒绝它们，但该策略可被配置**文件**覆盖（包括全局 `[protocol] allow = always`——`file://` clone 被拒时的标准手工修复），任何按调用的环境清洗都无法移除它，所以默认策略本身不是保证。环境变量覆盖（`GIT_ALLOW_PROTOCOL`）通过归一化而非删除来中和：继承的列表在剥掉会执行 helper 的条目后保持默认拒绝效力，因为直接删除会把最终决定权交给工作区控制的 `protocol.<name>.allow`。前缀按 git 的 transport 名字符集锚定在开头，所以 IPv6 字面量或 scp 风格路径永不匹配；原生 git 不带 `git-remote-ssh`，所以 `::` 分隔符把普通 URL 形态（ssh://、scp 风格、https）与 helper 形态分开，拒绝它不破坏任何合法 remote。
- 不可见字符类在写入谓词与显示清洗器两侧都派生自 Unicode 属性（`\p{Default_Ignorable_Code_Point}`）而非枚举，因为集合随 Unicode 增长，手工清单永远存在未列出的角落（Tag 区块 U+E0000-E0FFF 零宽零墨，所以一个未列出的码位会让两个不同的 remote 渲染得完全一样）。
- 变更继承完整严格链：变更门 → 可信运行时解析 → 代数守卫 → 工作区包含的 `cwd`。
- 错误响应经过现有脱敏（`redactGitMessage`），绝对路径永不到达客户端。脱敏替换工作区路径、git 根，AND 任何位于 cwd 树之外的 gitdir——linked worktree 共享的主 `.git` 目录（git 在配置锁失败时回显该绝对路径——`could not lock config file /srv/main/.git/config`）或位于上层项目 `.git/modules` 下的子模块 gitdir——从 git 根处的 `.git` FILE 解析（cwd 可能是子目录），包括相对 `gitdir:` 值，外加 gitdir 内 git 自己的 `commondir` 文件（迁移过的管理目录没有名为 `worktrees` 的父目录）。`.git` 文件用刻意宽松接受的文法解析（git 只接受同行目标；脱敏绝不可对 git 可能解析的形态少接受），两次读取都有头部限长——这些文件是 daemon 共享错误路径上的工作区可控内容。构建期 system gitconfig（`<prefix>/etc/gitconfig`，Homebrew/源码构建位置）按空白分隔词元脱敏——无界 `\S*` 前缀分支会在一个长无空白串上耗费 O(L²) 的同步事件循环 CPU（被拒 push 的 sideband 数据绕过 git 的 `vreportf` 上限），在 512 字符切片生效之前。而 git 的 config-error 家族是渲染形态的开放集合（`bad numeric/boolean/date config value … in file %s`，随版本措辞漂移），枚举没有最后的角落：`in file` 分支以该家族的共享短语为键，脱敏到行尾（带空格的 include 目标不留尾巴），最后的 fail-closed 清扫移除任何其他句子中任何存活的绝对路径词元——其空白词元边界是形态分支所拥有的记录在案的边界，清扫永不越界。transport URL 在两者中都存活：其斜杠跟在 scheme 的 `:` 或单词字符之后，永不落在清扫的前缀类上。在此之上，配置读取自己的失败路径在错误离开 core 之前剥离其 stdout：被杀的 `git config --list --show-scope -z` 可能携带 EVERY scope 记录的部分转储（global/system URL、凭据 helper、身份），只有 git 的 stderr 诊断属于客户端可见消息。
- 删除经过验证：`git remote remove` 之后重读仓库 scope 列表，存活 section 抛错，AND 检查名字跨 ALL scope 的解析——同名继承（`global`/`system`/`unknown`/`command`）幸存者会在一次看似成功的删除之后继续接收 push，所以该形态同样抛 `remote_still_configured`。两侧都预先拒绝同样的冲突（`remote_shadows_inherited`——只要存在可毁的仓库 scope 一半，删除侧就拒绝；git 的重复检查看不到继承 section，而 git rm 会在毁掉 local 一半后以退出码 0 收场），事后验证则作为预检之后竞入幸存者的兜底。仅由 worktree scope 持有的幸存者在那里完成收尾（`git config --worktree --remove-section`），因为 `git remote remove` 无法编辑 `config.worktree`，否则会在毁掉其引用后留下一个永远无法删除的列出行。删除谓词的唯一底线是非空、NUL 字节（execFile 拒绝携带 NUL 的 argv 条目，否则会浮现为未分类的 500）与不含 `/`（带斜杠名字的跟踪命名空间与前缀 remote 的冲突）；其他所有配置中的名字保持可删除，`--` 终止符守护 exec 向量。
