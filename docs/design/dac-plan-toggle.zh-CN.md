# DAC Chat Plan 开关

[English](dac-plan-toggle.md) | [简体中文](dac-plan-toggle.zh-CN.md)

## 问题与范围

Web Shell 用同一个 approval-mode 值同时表示规划和执行权限。Plan 出现在权限菜单里，确认计划时还可能选中另一种执行策略。DAC Chat 需要一个独立于权限控件的 Plan 开关。现有的单行响应式工具栏保持不变：窄屏把文字折叠成图标。其它工具栏控件都不移动，也不改变 CLI/TUI 语义。

生成计划后 Plan 保持开启，直到用户批准。批准会退出规划，并按用户确认时选中的策略执行。拒绝则继续保持规划。规划期间修改权限只更新执行时采用的策略，绝不会自动确认计划。手动关闭开关会在所选权限下退出规划，不会提交待处理的计划批准。现有的运行中轮次切换时机保持不变；本功能不增加取消或模型引导能力。

## 运行时与传输

保留运行时的 ApprovalMode.PLAN 及其现有工具限制。在 Config 上增加一个可选的、仅 DAC 使用的「所选执行策略」，它只由现有会话 approval-mode 控制上显式的 planMode 布尔值写入。旧请求不带该标志，行为不变。校验该标志，并拒绝把 PLAN 当作执行策略。Core 在改变状态前应用现有的派生配置与文件夹信任约束。已处于规划中时更新执行策略，不会结束或重启规划生命周期。

对 DAC 的选择，RestorePrevious 在确认回调里捕获所选执行策略。旧的确认仍恢复其原始快照。执行阶段保留取消检查与 approval-mode 修订号检查。确认之后再选的策略不得悄悄改变已经批准的决定。

现有路由仍通过 withOwnerMutableSession 限定在存活会话的所有者范围内。全程使用它解析出的 runtime、bridge 和 Config，并保留现有的 unknown/removed/draining 失败行为。不引入主 runtime 回退、新的 workspace 路由或权限持久化。所选策略随批准响应、模式通知和会话模式元数据传输；在 bridge 对账、快照和客户端水合过程中保持不丢。Plan 开关是否开启，仍以生效的运行时模式为准。

## Web Shell

Plan 很少被选用，所以它的入口是 Composer 添加菜单（`+`）末尾的一个勾选项，而不是常驻的工具栏控件。Plan 开启期间，approvalMode 之后会出现一个可关闭的 Plan 标签（chip），让状态保持可见；点击它即退出规划，它的说明文字会写明批准后采用哪种执行策略。Plan 关闭时工具栏上没有任何 Plan 控件。宿主必须在 `composerToolbarActions` 或 `composerToolbarAdditionalActions` 中显式包含 `plan`；未配置时主窗口和分屏都隐藏它。独立浏览器宿主显式开启，分屏始终带有添加菜单。这条规则按单个 Composer 生效：宿主列出了 `plan` 但没有 `addMenu` 的 Composer 没有菜单可以承载该入口，此时保留早先位于 approvalMode 之后、基于共享 Switch 基元的 Plan Switch。因此这样的宿主在主 Composer 里显示开关，在分屏里显示菜单入口；列出 `addMenu` 即可让两者一致。Plan 永远不回退到权限菜单里。宽布局显示 Plan 文字；窄布局去掉文字，标签只剩图标，开关只剩图标和开关。标签静止时不带关闭标记：该标记与图标共用一个槽位，在悬停或键盘聚焦时取代图标，因此显示它不会改变标签的宽度。在主指针无法悬停的设备上，该标记改为常显，但只在有文字时如此。在这类设备上，窄到放不下文字的标签在静止时保留 Plan 图标，而不是变成一个什么都没说明的孤零零的关闭标记：除非获得键盘焦点，否则它不显示标记，就作为一个处于按下状态的按钮工作，点按即可松开。在强制颜色模式下，遮罩式图标改用系统颜色重绘，从而得以保留。保持单行、tooltip、无障碍名称以及 checked/pressed 状态；`data-web-shell-plan-control` 与 `data-web-shell-plan-button` 在标签和开关上都保留，并用 `data-web-shell-plan-chip` 标记标签。用这些钩子定位 Plan 控件的宿主，拿到的是带 `aria-pressed` 的 `button`，而不是带 `aria-checked` 的 `role="switch"`；Plan 关闭时什么也拿不到，因为标签只在开启时存在。从添加菜单或标签发起的切换会把焦点留在编辑器里，因此不同于获得焦点时会自己报告状态的开关，这次变化不会播报给读屏软件；用户把焦点移到标签上时，标签仍然承载着状态。要补上这个缺口，需要一个「哪些 Plan 变化是用户发起的」信号，本次改动没有引入，见 [Composer 添加菜单](web-shell/web-shell-composer-add-menu.zh-CN.md) 里的延后条目。添加菜单随 Composer 输入一起禁用，因此输入被禁用时无法进入规划。标签不随输入一起禁用，但它只在宿主接受模式变更的地方才起作用：会话写入被阻塞、或正在加载会话记录时，两种 Composer 都会拒绝，此时标签是静默的空操作，这一点与被它取代的开关完全相同。读取这些钩子的宿主还需注意：标签是用原生 `disabled` 属性表示交接中，而开关是把 `data-disabled` 放在它的 label 上。模式控件忙碌期间，菜单项被禁用并写明原因，标签和回退开关被禁用；与所有工具栏按钮一样，标签外观不变，而它本身就是 tooltip 的触发元素，所以在这一短暂状态下不显示 tooltip。计划等待批准期间隐藏整个 Composer 及其状态区，与普通权限和 AskUserQuestion 浮层一致。浮层结束后恢复。浮动的计划卡片只滚动计划正文，标题和批准按钮保持可见，纯文本计划也一样。在批准浮层出现之前，规划期间仍可调整执行权限。只从 Web Shell 的权限菜单/循环切换中移除 Plan。Auto 与 Default、Auto Edit、YOLO 一起保留。不修改共享 SDK 的 approval 枚举，也不修改 agent 定义编辑器。

主窗口与分屏使用相同的 daemon action 契约。计划确认只暴露一个标注了所选执行策略的批准动作和一个拒绝动作。Plan 期间修改权限不能自动提交待处理的批准。模式更新未完成时短暂禁用计划确认；计划批准交接期间禁止新的模式更新，直到运行时退出 Plan 或交接失败；两个请求谁也不能越过对方。按钮只反映成功的状态变化；失败时保持原状态。会话所有者守卫防止迟到的响应更新到替换后的会话上。

/plan 切换，/plan on 开启，/plan off 关闭，都走同一个动作。保留 `/plan <prompt>` 的「进入并发送」语义，保留 /plan exit 作为 off 的兼容别名。新会话先以其执行策略创建，随后在提交第一条 prompt 之前应用 Plan；准备失败则不发送该 prompt。

## 影响范围

- Core Config 与退出计划确认，含旧路径与 DAC 的回归覆盖。
- Daemon 会话 approval 路由、ACP 控制处理器以及模式元数据/通知。
- ACP bridge 控制、缓存快照以及模式事件转发。
- TypeScript daemon 客户端/状态类型以及 Web Shell 会话同步。
- Web Shell Composer、批准对话框、主窗口/分屏的命令与权限接线、翻译以及聚焦的组件测试。

## 验证

用每一种非 Plan 权限搭配 Plan 进行操作；在计划等待确认之前和期间修改权限；批准/拒绝/手动退出；斜杠命令；欢迎页会话准备；会话切换以及重连水合。确认 core 的旧确认快照保持不变。校验工具栏顺序与单行紧凑布局，覆盖 Plan 关闭（工具栏无控件）、开启（标签位于 approvalMode 之后，放得下时显示文字，挂载后才开启 Plan 时也一样）以及宿主没有 `addMenu`（开关）三种情况。确认添加菜单入口位于最后、反映勾选状态、只触发一次、把焦点交还编辑器，并在交接期间带原因地禁用。要求通过构建、类型检查、打包、聚焦测试以及两轮干净的全量 diff 审计。

## 未决问题

就所要求的行为而言没有。超出现有会话模式持久化的跨进程恢复，以及新的轮次中引导保证，均不在范围内。

## 评审修正

元数据读取若缺少 modes、失败，或在事件流重启期间被跳过，则同时保留现有模式和执行策略。权威的非 Plan 模式会清除该策略。计划批准只接收 daemon 上报的执行策略；Composer 的显示回退绝不能把批准标注成按 daemon 未上报的权限执行。

对显式的 DAC `planMode` 控制，`persist: true` 只把执行策略保存为该 workspace 后续会话的默认值。发起请求的会话发布其真实的 Plan 状态和所选策略。现有的同级会话既收不到模式事件，也不更新缓存。不带 `planMode` 的请求保留原先的 workspace 默认值广播行为。

回归检查覆盖：prompt 重启后的元数据复用、缺少 mode 的 context 响应之后发生真实的 Plan 退出、主窗口和分屏中带/不带上报执行策略的批准、Plan/非 Plan 同级会话下的 DAC 持久化，以及现有的旧持久化测试。

## 确认策略前置条件

DAC 的 RestorePrevious 响应包含批准方客户端所显示的执行策略。bridge 保留这个权限响应扩展，Session 把它转发给工具。Core 只读取一次当前 DAC 策略，缺失或与预期不同则拒绝，否则冻结该值直到执行。没有 DAC 策略的旧 Plan 保持其规划前快照行为。策略相等即足够：改走再改回同一策略，不会改变用户批准的权限。生命周期修订号仍然独立。

前置条件被拒绝时，会消耗掉旧的权限请求并返回工具错误，同时保持 Plan。模型必须重新请求计划批准；HTTP 确认不代表 Plan 已退出。客户端不会对已被消耗的批准做重试。

Plan 标签和回退用的 Plan Switch 都保留其无障碍名称和 pressed/checked 状态，并直接引用一段常驻、动态的执行策略说明。模式控件变忙时关闭已打开的权限菜单。斜杠补全包含现有的 exit 别名。移除未使用的 Plan & Review 模式文案；agent 编辑器的 Plan 文案和 workflow review 翻译保留。
