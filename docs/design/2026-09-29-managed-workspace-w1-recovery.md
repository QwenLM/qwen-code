# Managed Workspace W1: Verified Restore and Mount Relocation

## 1. Recommended scope

Deliver W1 in three slices. **Start with W1a: verified cold restore at the original location for an already-bound, settled Hosted Session.** W1b adds evidence-backed backfill and validation of externally restored snapshots. W1c adds controlled same-storage mount relocation. This split is proposed here; it is not an existing roadmap assignment.

W0 already persists the binding and provides Runtime adoption and reclamation. W1 adds evidence that the files and private recovery resources still belong to that binding. It must not infer successful restoration from a directory's existence, a freed storage holder, or a readable public transcript.

Cold-opening a Session does not rewind shared files. A Workspace is shared mutable storage: restoring one Session's old file tree could destroy another Session's later work. Disaster recovery is a storage-wide maintenance operation, with a consistent recovery point covering every affected Session.

## 3. Boundaries and invariants

- Preserve `tenantId`, `workspaceId`, `workspaceGeneration`, `workspaceStorageId`, `cwdRelative`, `contextConfigRef` and `contextRevision`. W1 does not change Session cwd, choose another Workspace, or replace storage. A logical change needs separate admission, W2, or a new Session.
- Preserve original command, input and execution identities, result receipts, journal bytes and model-consumed messages. Neither mount relocation nor backfill rewrites committed content or replays tool effects.
- Distinguish three facts: the original execution outcome, proof that old writers cannot return, and proof of usable storage/resources. None implies the other two. `ABANDONED` remains an unknown outcome, not a successful result or an automatic unlock.
- W1a targets process restart in a trusted single-host Linux local-process deployment and the saved `hosted-workspace-files/1` or `hosted-workspace-shell/1` profile. Whole-host restart is accepted only if the registered identity still matches; portable identity across reboot is not promised. Arbitrary configuration snapshots, Legacy import, cross-host takeover, Kubernetes, hostile same-UID writers, disk/VM rollback and online migration are outside its acceptance.
- New execution needs current authorization. Authorized history/export and saved-identity cleanup do not require a working mount. Revocation must block new work without preventing trusted cleanup.
- Published Items/Snapshots cannot reconstruct the private Session authority. O2 result bytes are not a backup of the Workspace filesystem.

## 5. W1a: persistent storage registration

### 5.1 Smallest storage change

Extend the existing `managed_workspace_execution_lease` row, keyed by tenant/storage, rather than adding another lock service. Add exact tenant/storage identifiers for hash verification, a monotonic `mountRevision`, `mountState` (`unverified`, `ready`, `fenced`), a nullable `maintenanceOperationId`, and a versioned mount identity plus its registration receipt. Existing holder fields and their ownership semantics remain unchanged. Large manifests do not belong in this row.

An absent registration is `unverified`, never automatic enrollment of the directory found at startup. W1-enabled execution refuses it. Register an existing deployment only during maintenance, after the operator has checked the original storage, stopped admissions and accounted for every old writer. This establishes a documented W1 starting point; it does not retroactively prove that every historical byte was captured.

The initial Linux identity format records the durable host identity, canonical root, explicit numeric device/inode values, and a randomly assigned storage registration ID. The registration ID is also recorded in an administrator-created, versioned marker at the root, `.qwen-managed-storage.json`; SQL and the marker must agree. Registration validates an existing root and never creates a replacement project directory. Creation uses exclusive/no-follow semantics and durable publication; interrupted registration stays unverified and resumes through its original receipt. An existing conflicting marker is refused, not overwritten.

The marker supplements host and filesystem identity; it is not an authorization credential or proof of file completeness. Copying a marker does not authorize a different root. A missing marker after completed registration blocks recovery; W1a has no repair or re-enrollment command and never regenerates it automatically. This is a trusted-workload continuity check, not protection against a malicious same-UID process, filesystem rollback or an administrator deliberately copying identities. A changed device identity, unsupported identity provider, or ambiguous reboot comparison blocks until maintenance verification. Do not persist `fileKey.toString()` as a portable identity format.

Only a complete validated registration moves `unverified` to `ready`. `fenced` closes admission until the same maintenance operation finishes or explicitly restores the still-verified original mapping. Entering `fenced` compares `ready` and the expected revision and persists the operation ID. Resuming, switching the mapping and lifting the fence compare both that operation ID and revision; a second operation cannot take over merely because the revision matches. Lifting the fence increments the revision and retains a completed-operation receipt, so a lost acknowledgment can be retried and an old fence cannot reopen maintenance. It has no time-based unlock. `mountRevision` versions verified physical placement and maintenance transitions; it does not replace Workspace generation, context revision or Runtime generation.

### 5.2 Enforcement points

Check the saved binding, current authority and registered mount at Hosted attachment and cache reuse, before new model work for a cold-restored Session, and before resolving/provisioning or acquiring a Runtime for new work. Validate the storage guard again in the claim transaction and before a new execute. Broker configuration pointing at a different root must disagree with the persisted identity and fail closed; the revision is the maintenance CAS token, not a new Runtime protocol field.

The final admission check must read the current guard state and verify the original root identity after acquiring the storage row lock. A check performed only before that wait is not sufficient. Normal release and W0e cleanup may clear only their exact holder fields; they must not erase the registration or lift a migration fence. Status/cancel/recovery of original executions continue through their saved generation, including when new execution is refused.

Keep `managed-context/1` unchanged in W1a. Its seven-field logical digest already excludes the mount root; the current attestation/installation receipts bind the physical Runtime. Java's guard check supplements those receipts. Independent Worker validation of a new storage proof would require a negotiated protocol revision, not extra fields in a closed v1 envelope.

### 5.3 Lock order and rollout

Current claim locks Runtime binding → Runtime Session → storage lease. Lost-holder cleanup locks binding → storage lease. Preserve that order. Never hold the storage row while scanning and locking Runtime bindings.

W1a maintenance first closes new-work entry points, settles or cancels original executions, proves every writer stopped, and releases exact holders using the existing ownership protocol. Stop the relevant service and external writer processes and prevent their restart, then commit the short storage-fence CAS at the expected `mountRevision`. Fence requires all holder fields clear; it is not an online drain mechanism. A request already beyond the guard check may still dispatch: the storage fence alone is not proof of quiescence. Do not inspect a supposedly stable tree or change its mapping until worker-level admission is sealed and every relevant execution domain has satisfactory stop evidence.

Old binaries ignore new guard columns. Require all processes with authority over this storage to stop/drain and upgrade together before W1 mutations are enabled. Include ordinary tools and external services able to write the directory in the maintenance proof; a Java upgrade does not fence them. This offline rollout avoids building a new online version-coordination system. Schema migration alone is not a safe rollout. Rollback to an old binary requires services and entry points to remain stopped until explicitly reconciled. A persisted fence or disabling the new option cannot constrain binaries that ignore these columns.

The implementation uses the disabled-by-default `verified-workspace-recovery-enabled` Broker property. Its private `WorkspaceStorageRegistrationMain` entry supports `register`, `inspect`, `fence`, and `restore-original`; mutations require an explicit offline operator assertion and exact operation ID. The [server README](../../packages/sdk-java/managed-agent-server/README.md) gives the invocation and rollout order. The assertion does not itself stop external writers. Registration and execution require a trusted Linux identity provider; local H2 tests use a synthetic provider and cannot substitute for Linux acceptance.

### 5.4 Confirmed W1a recovery contract (2026-09-30)

The owner selected internal Java → Hosted → Runtime recovery, process restart, and strict retained-history integrity. Public restore/next-turn admission remains a separate integration. Passive Hosted attachment preserves Session, Registry, grants and profile authorization and skips only physical mount verification; original-execution cleanup continues through saved Broker identities. Only already-bound, settled Sessions are accepted; W0e/G2 still own exact old-execution reconciliation. No physical holder is cleared by opening a Session.

After acquiring the exclusive writer and installing activation, capture `S = restoreBundle.throughSequence`. Check unsettled inputs, all retained event/resource roots and message projection through the same S. Add a used optional `throughSequence` parameter to the existing record sink/projection; unbounded callers retain their current behavior. Activation renewal may advance the transport cursor while validation runs, so an unchanged raw journal head is not required. Revalidate writer ownership before publishing the attachment. Failed loading may append lease-management records, but accepts no business input and runs no model/tool effects; close only leases acquired by this attempt.

Validate header references, schema-declared event references, checkpoint typed references and projected messages. The built-in session-metadata title records and their previous-record references remain supported; extension domains remain refused. Check every promised complete Shell manifest, page, segment, seal, length and full-stream digest; empty streams also require a seal. Deduplicate resource IDs while rejecting conflicting reference metadata. Read output in bounded chunks, never downgrade to latest-checkpoint-only validation. Missing resources from an older settled Turn also refuse cold load. Unsupported extension domains, legacy file-history backups and external attachment layouts refuse rather than pretending a top-level read verifies their closure. W1a is not a generic JSON-reference crawler or a snapshot engine.

Registration persists its prepared identity before durable marker publication and only then commits READY. Same-operation concurrent retries must converge, including final-commit acknowledgment loss. Completed registration/restore retries recheck current identity and marker without advancing revision again. Inspect reports state, revision, operation receipts, holder presence and physical verification even when FENCED. A root marker is continuity evidence, not file-content completeness.

## 6. Cold-restore sequence

1. Read the saved Session and original creation receipt. Recheck current access, exact Registry generation/storage, fixed config/policy references, and enabled profile. Do not consult the current default to fill gaps.
2. Validate the registered storage identity and original relative cwd. Missing directories, aliases, symlink substitution, changed identity or fenced storage keep execution closed. Do not `mkdir`, clone, or fall back to `.`.
3. Acquire the existing private Session writer lease, restore the authoritative journal and required resource closure, and check the original definition. Reuse the reader's strict corruption handling. At the baseline, load checks the definition/checkpoint, but message projection is lazy and occurs after a later input is accepted. W1a verifies the supported profile's typed message/checkpoint/result closure and rejects unsupported domains at the same committed cut before reporting load success or accepting that next input; a later lazy-read failure is not a successful restore. Reject an unsettled input with the existing `hosted_turn_recovery_required`; do not replay it as fresh work. On refusal, relinquish only the newly acquired writer lease, not physical holders.
4. Reconcile any original Runtime binding before considering another generation. G2 may recover a conclusive original result; W0e may prove loss and physical release. An unknown or abandoned result does not make a previously interrupted Hosted Turn resumable.
5. For a future admitted tool Turn, resolve the same storage/cwd, acquire its exact storage holder, and install the original logical context and supported frozen profile. Verify attestation, context and activation receipts against this Runtime. A prior incarnation's receipt cannot activate a new one.
6. Recheck the physical guard and current authority before admitting effects. Record or return success only for the guarantees actually proved: private history opened, storage verified, and—separately—Runtime activated. Keep logical binding readiness distinct from physical readiness.

Steps 2 and 3 add restore checks, not a requirement to warm a worker before every model request. Once the cold-restore checks succeed, normal model-first behavior remains; provisioning can run in parallel and only tools await activation. History-only queries bypass this execution sequence and preserve current access rules.

W1a uses existing outward `workspace_unavailable` and `hosted_turn_recovery_required` errors. The private inspector distinguishes registration state, revision, operation receipts, holder presence and independent root/marker checks. Missing cwd, stale mapping, unresolved execution, missing private resources and unsupported profiles remain refusal conditions; no detailed public diagnostics endpoint is added. No new public restore or arbitrary-path registration endpoint is introduced.

## 7. W1b: honest backfill and consistent recovery manifests

### 7.1 What can be backfilled

For a bound Session, reconstruct derived recovery metadata only from its original creation receipt, exact binding, authoritative journal, immutable referenced resources and retained file-history bytes. Save source digests and a fixed committed sequence. Page by stable identities, checkpoint progress, and recheck the source version before committing each derived record. Retrying the same operation must not produce new authority events or duplicate resource references.

Do not infer a binding from local path hashes, a `ChatRecord.cwd`, the Harness `managed-root`, current Registry defaults, or public transcript contents. Old unbound Sessions retain their old behavior. A separate explicit migration can be designed later if authoritative import evidence exists.

File-history metadata and backup bytes must be checked together. A recorded absence of a file is different from a missing backup. Never substitute the current file for a lost old version. For the existing Hosted file profile, record that historical undo capture was not provided; do not manufacture snapshots or claim undo availability. A new storage snapshot can protect a future recovery point without inventing prior file versions.

### 7.2 Minimum manifest

Use a versioned immutable recovery manifest with a digest, referenced from a durable maintenance receipt. It describes a recovery point, not the current continuously changing tree.

| Part                     | Required evidence                                                                                                                                                                                                                                                                   |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity                 | Tenant/storage, original registration and mount revision, Workspace generations, snapshot provider ID and immutable snapshot identity.                                                                                                                                              |
| Consistency cut          | Maintenance operation and fence; complete paged set of affected Session IDs, exact bindings, authority committed sequences and definition/resource roots; confirmation that no accepted work remains unsettled.                                                                     |
| Files                    | Provider inventory of normalized storage-relative paths, entry types, lengths/digests and required mode/symlink metadata; a digest of that inventory and verification of restored bytes. Reject unsupported special files, escaping links, ambiguous names or incomplete inventory. |
| Private recovery closure | Journal receipts and all required checkpoint/message/domain resources, including resources outside the Workspace root. Existing digests are verified; a list of object names is not enough.                                                                                         |
| History and results      | File-history backup closure when the profile has it; accepted result references and the storage that owns their bytes; explicit unavailable/not-captured states.                                                                                                                    |
| Placement and completion | Original mapping, target identity, verification results, and a completion receipt bound to the operation and expected mount revision.                                                                                                                                               |

Do not recursively copy storage through the Java request path or place file bytes in SQL metadata/SSE. The first integration consumes a trusted external immutable snapshot and streams verification with bounded memory. Choose and document the first concrete snapshot provider before implementing W1b; the contract is not a claim that such an adapter already exists.

### 7.3 Recovery point rules

Fence the whole tenant/storage domain, including every Workspace and Session that shares it, before capturing the cut. First close Session creation, prompt/model-only input admission and background dispatch for that storage. Finish or cancel and settle every accepted input and its tool/history/result commits; merely marking work blocked does not meet this gate. A diagnostic snapshot may retain blocked work, but it is not an activatable recovery point.

For the first offline implementation, stop the relevant Harness and Session Store writer processes, release or expire their writer leases, and prevent renewal/restart. Only then enumerate the final Session membership and fixed journal watermarks. Existing tool claim/execute guards alone do not freeze either: current Session Store writer acquisition does not read a storage guard. Keep the product entry and writers stopped through snapshot capture or migration completion; a private maintenance process performs the operation. Account for writers outside the Broker as well. A provider claiming atomic filesystem snapshots still cannot establish SQL/journal consistency on its own.

A cold open against surviving storage reads its current files; it does not apply this manifest. A disaster restore first stages and verifies the selected snapshot away from a live target, restores/verifies its private resource closure, and compares its watermarks with current authority. If any affected Session has a later accepted state or missing closure incompatible with the recovery point, refuse promotion and un-fencing of the entire shared storage, not only that Session. Retain the staged snapshot for inspection without overwriting the live tree. W1 does not replay Shell to catch files up, roll the authority backward, or erase newer work. An explicitly divergent recovery requires a separate operator/product decision, not ordinary resume.

Content digests at an old snapshot are never used as the expected digest of a Workspace that has legitimately changed since then. SQL backup/restore, VM rollback, or loss of the registration authority itself requires an independent disaster-recovery/fencing contract and is not automatically accepted by this slice.

## 8. W1c: controlled same-storage relocation

### 8.1 Supported first case

Move an already verified storage tree to another root on the same trusted host during maintenance. Preserve logical storage and all seven Session binding fields. Keep the private Session Store key unchanged: it is not interchangeable with the product Workspace ID. The target must be authorized deployment data, never a caller-provided browser path.

Start with settled Hosted relative-path file-tool Sessions. Their new file calls already require paths relative to saved cwd, so committed messages do not need rewriting. Inventory all Sessions and resources sharing the storage, including archived Sessions. If any profile or retained asset lacks safe relocation semantics, keep the old mount or block migration. Do not strand an older Session simply because the currently selected one can move.

Shell commands, MCP/Hook configurations, file-history references outside the Workspace, Memory roots and other opaque absolute-path dependencies are excluded from the first migration capability. They require profile-specific support. W1c does not upgrade an existing Session's immutable definition to bypass that check.

### 8.2 Durable operation

1. Inspect the original storage registration, all referencing Sessions and all old placements. Record an operation ID, expected mount revision and request digest. A changed payload under the same ID conflicts.
2. Commit the storage fence and establish the full offline admission/journal quiescence from section 7.3, then drain and prove every old writer cannot resume. Use existing normal/W0e/operator evidence. Null holder, expired lease, a completed public Turn or root-PID death is insufficient for arbitrary Shell descendants.
3. Capture/verify the consistent manifest. Restore or relocate files using the trusted storage procedure, then verify the target identity and complete contents. No new Runtime starts yet.
4. Validate all path-sensitive consumers. For future supported history adapters, map typed paths by verified source-root membership and target containment; preserve backup identifiers and bytes. Do not use string-prefix replacement (`/old/a` is not `/old/ab`), rewrite raw Shell strings, or modify committed messages, resources, hashes and execution references. Derived mappings are immutable side records, not edits to evidence.
5. Confirm old placements are retired and original holders are cleared through their exact-owner protocols. CAS the expected storage revision to the new registered mapping while still fenced, and persist the completion evidence. Stale Brokers continue to fail their mapping comparison.
6. Open new admission only after the target and all required evidence are committed. A later authorized tool Turn gets a fresh Runtime placement and fresh attestation/context/activation receipts. The unchanged binding digest is not permission to reuse an old physical receipt.

Every durable boundary is restartable with the same operation and evidence. Failure retains the fence and original records. After a mapping switch, rollback is another verified transition with a higher mount revision; never decrement a revision or blindly restore the old SQL row. Original status/cancel and cleanup continue to address the saved old execution, not the new root.

Do not edit `canonical_cwd`, request keys, durable handles or attestation in an old Runtime record. They are immutable evidence. Old and new placement records coexist; only the verified registration identifies where new work may run.

## 11. Alternatives and decisions before each slice

- **Just re-read deployment roots on restart:** rejected; that recreates today's in-memory baseline and can accept replacement storage.
- **Only add a root marker or tree hash:** rejected as the sole authority. The marker must match persisted registration and physical identity; a snapshot digest proves one content version, not continuous identity or writer exclusion.
- **Recover through a new Session/default directory:** rejected; it loses the binding and can duplicate effects.
- **Implement backup, migration and G1 together:** rejected; it obscures the distinction between file recovery, process cleanup and logical Turn continuation.
- **Rewrite all old absolute paths:** rejected; paths also appear inside arbitrary model content, Shell and configuration, and rewriting would invalidate immutable evidence.

W1a's trusted Linux/original-location, internal-only, process-restart, offline-registration and strict-history scope is confirmed; choose a concrete immutable snapshot provider before W1b; approve W1c's relative-path file-profile restriction before migration work. If broader platform, profile or live-migration support is required, revise the affected slice and fault gates before implementation.
