### Public API feasibility checkpoint

On 2026-11-17, the isolated public-API witness completed under Bun 1.4.4 and OpenTUI 0.5.10 using real PTY input `ab`, Tab, `c`, Enter. Two real InputRenderables changed focus and value; the existing plain writer appended output. All 131 captured bytes across setup, interaction and teardown contained no ESC, graphical marker or alternate-screen switch; the process exited naturally with code 0 and no cleanup signal. This establishes that real keyboard input and plain output can coexist in this bounded configuration, not production screen-reader acceptance.

The separate completed-frame witness 21033/3bc55b/0 retained those inputs and qualified public `frameId: 2` after the mutations; the public `frame` event follows native render returning `rendered`. Its 131 captured bytes contained no ESC or graphical marker and it exited naturally. This qualifies this Bun/macOS public API lane only. Native application state, reader usability and other platforms require their own evidence. `pause()`/`stop()` are not paint-off contracts and `suspend()` detaches input. The candidate therefore uses `bufferedOutput: 'memory'`, `screenMode: 'main-screen'`, passthrough output, disabled mouse/console overlay and no shutdown clear.

## Goal and boundaries

Provide a real DOM-free Native presentation for the core keyboard conversation: prompt input, completed and streaming messages, tool permission decisions, focus changes, errors, help, cancellation and exit. Use existing command, permission, session and model owners. Do not replace these with canned announcements or a second dispatcher.

The first engineering gate is this core workflow in an actual strict Native process. It is not all accessibility, all dialogs, VoiceOver/NVDA acceptance or completion of the Ink removal. Uncovered interactive capabilities must stay explicit acceptance gaps; no silent permission action or claim that a truncated feature set is complete.

## Presentation and input

The entry owns one `ScreenReaderPresentation` and writer for its real renderer. At a completed public frame it reads semantic public getters (`TextBufferRenderable.plainText`, editable value/cursor, `MarkdownRenderable.content`, select options/index and table content); it never samples the painted cell buffer or interprets colors. The existing shell, composer and dialogs continue to own all input and permission actions. Explicit IDs bound to the real selected state label custom tabs/options; user-provided arrow text does not imply selection.

The existing transcript components remain the history presentation source, including Mod replacements, tool results, warnings, images' textual placeholders and help notices. Screen-reader mode uses the existing row window and spacers, including the 400-item native mounting backstop; the complete history remains in the session model. Existing scroll commands (Shift+Up/Down, PageUp/Down and Ctrl+Home/End) navigate that same scrollbox without moving composer focus, and the actual displayed item range is announced on window changes, while the invariant navigation help beside it is announced once. Dialogs, pending permissions and a focused shell retain their keys. Older messages are read from their original Mod-rendered subtrees when their window is mounted, not from a parallel formatter. Kind/ID/tool-segment identity binds the exact semantic subtree; unchanged text is suppressed. Assistant bodies wait for streaming=false, and thought/tool bodies wait for done=true; the completed frame then publishes the complete current semantic subtree once. Task and retry cards have no settled form — the model removes them when they finish — so each is spoken once and its later progress ticks or countdown redraws are held. Existing cancel/error settlement preserves produced partial text. Later substantive edits to a settled item can append a labelled Revision. Arbitrary substring deltas are not written because newline-terminated output can split a word (Hel → Hello). Active tool output is not repeatedly replayed; its real permission dialog and working controls remain live. Actual keyboard-history PTY and reader usability still require validation before claiming full accessibility. Existing card-level expansion and content limits remain; this is not an uncapped export. History and settled controls use the writer's appendStatic and never erase lines; live editable values (the composer and dialog input lines) use its dynamic block, which replaces only its own previous lines so a keystroke cannot append another copy of the whole field. Static output is hard-wrapped at the terminal width. Controls compare real renderable owners within the Config/session scope and append only their changed semantic values, suppressing unchanged options and spinner/time chatter, with explicit dialog open/close and actual focus return to the prompt. API-key inputs and sensitive extension settings emit Protected input before walking their children, without reading the value; existing preview API-key/header masking remains intact.
Reuse existing Native key parsing and input/submission models. Printable text, cursor/editing keys, Enter, Tab/arrows, Escape and exit must reach the same application callbacks as the graphical route. Permission approval/denial must settle the original pending request exactly once. Never infer approval from the output channel.

The screen-reader branch keeps the existing real controller/renderable tree in memory; graphical output must not be written alongside the plain writer. `screenMode: main-screen`, `useMouse: false` and passthrough external output are available public OpenTUI options, but are not themselves proof of non-destructive output. The public component witness first qualified the memory lane; the real entry cases below verify the writer and actual state/actions together for bounded flows. They do not establish every reachable interaction or terminal combination. Do not invent a fake WriteStream or use private renderer internals to force this. If a required flow cannot use the public 0.5.10 lane, retain Ink for that release boundary and document the missing capability for upstream review.

The writer sanitizes untrusted model/tool escapes. The only line-erasure controls this candidate generates are the dynamic block's own replacement of the live editable value; history and settled controls remain append-only. Existing terminal protocol probes before this presentation remain separate; this is not a whole-process zero-ANSI claim. No alternate-screen switch, mouse reporting, decorative repaint or optimization wrapper may disturb the readable history. Real reader validation determines whether dynamic updates are usable.

## Session and cleanup

Keep one writer per live Config/session owner. Ignore stale async completions after owner replacement or unmount, including A→B→A. Preserve clear/resume semantics deliberately: a new owner receives its own replay once; resize does not replay unchanged semantic text; layout-dependent card text may still be announced as a revision; clear removes the current semantic transcript without silently reviving an old owner's messages. Do not change persistence or tool authorization to satisfy output tests.

Dispose exact keyboard/focus/output subscriptions before exit; no new keepalive timer. Reuse existing quit, Ctrl+C/Ctrl+D and OS-signal policies. Existing Native signal failures remain separate, and a screen-reader implementation cannot relax their windows.

## Gate coordination and safe fallback

Do not ship deletion of either veto by itself. In the same candidate that supplies the real presentation path, update renderer selection and the npm handoff together, covering direct Bun and public npm/Node→private Bun entry. Remove an obsolete screenReader parameter only if all its reads disappear; do not retain a dead capability switch.

On an unsupported runtime or Native boot failure, preserve existing non-strict Ink fallback and strict failure. Strict Native success must record Native, not serve Ink while only announcing a Native label. Current supported Ink users must keep their working route during development. Any release of a smaller capability subset needs explicit maintainer agreement and an honest scope; it cannot close the full Native screen-reader gate.

## Validation and acceptance

1. Before implementation, a global installed qwen dry-run records the actually supported Ink screen-reader interaction; if the old version does not support the experimental selector, it cannot establish that selector's fallback/strict contract with isolated settings and no real credentials. This validates the plan, not the candidate.
2. Test actual entry/shell consumption and real Native key events: flag precedence, policy options, history/stream ownership, focused prompt/permission/help, cancel and cleanup. Pure conversion tests remain supporting evidence.
3. Run build, typecheck, affected whole files, lint/format and bundle. A bounded strict-Bun public PTY case must verify Native identity, one controlled response and a genuine permission settlement, readable ordered output, dedupe, owner reset and ordinary exit. Verify the public npm handoff separately, without hand-written GC flags.
4. Verify unsupported-runtime fallback and ordinary graphical Native behavior remain unchanged. Do not infer Windows or Linux coverage from synthetic policy descriptors.
5. A real VoiceOver/Terminal or NVDA/terminal session checks spoken order, prompt/focus discoverability, double announcements and keyboard-only completion. Record device/terminal/reader versions and untested combinations. PTY assertions cannot establish this result.

## Implementation sequence and decisions

First build the real terminal-output/input feasibility witness using public APIs. Then wire the existing semantic owners and writer for the core workflow with focused regression tests. Finally coordinate launch gates and run public/assistive acceptance. These are sequential gates, not permission to implement every dialog at once.
