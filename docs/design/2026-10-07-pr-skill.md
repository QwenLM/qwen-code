# `/pr` Bundled Skill

[English](2026-10-07-pr-skill.md) | [简体中文](2026-10-07-pr-skill.zh-CN.md)

## Status

Implemented in this PR (issue #13509). The E2E plan in
`.qwen/e2e-tests/2026-10-07-pr-skill.md` is partially executed: `prepare`, the
non-GitHub preflight stop and the usage path pass against a disposable local
repository, and `create` from the default branch and from a feature branch, plus
the idempotent re-run, pass interactively against real GitHub repositories. The
update-after-asking branch, dirty-tree choices and AUTO mode are pending.

## Problem

The issue side of the contribution flow is covered from draft to submit by
`/create-issue`. Publishing a pull request, the least reversible step, has no
interactive owner: the user either writes the title and body by hand, or the
model improvises a `git push` and `gh pr create` with no consistent rules about
templates, dirty trees, existing PRs, or which commands need confirmation. The
existing `.qwen/skills/prepare-pr` skill is a non-interactive CI contract (it
writes `pr-title.txt` and `pr-body.md` for autofix and repo-hygiene) and
deliberately never pushes.

## Goals / Non-goals

Goals:

- A user-triggered `/pr` skill that drafts a PR title and body from the current
  branch, and optionally pushes and creates or updates the PR.
- Works in any repository: it reads the repository's own conventions instead of
  hardcoding a format.
- Every mutating command stays behind normal confirmation.
- Re-running after review feedback neither fails nor creates a duplicate PR.

Non-goals:

- GitLab / `glab`, and a `/mr` alias (`SkillConfig` has no alias support).
- A no-`gh` fallback (push plus a `compare` / `pull/new` link).
- `/pr edit` and `/pr view`.
- Flag-level exclusion in permission rules (a separate core change).
- Changes to `.qwen/skills/prepare-pr`, which keeps its CI contract.
- Committing. `/pr` never commits.

## Design

### Commands

The skill is bundled at `packages/core/src/skills/bundled/pr/SKILL.md`, so it is
available in every repository.

| Command                                  | Behavior                                                                                               |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `/pr`, `/pr prepare`                     | Draft the title and body and show them. Publishes nothing.                                             |
| `/pr create [--draft] [--base <branch>]` | Push the branch and create the PR, or update the existing PR after asking. `--draft` opens a draft PR. |

Any other argument prints usage and executes nothing.

### Flow

`prepare`:

1. Gather the branch's status, upstream, remotes and repository metadata in one
   read-only batch, then resolve the base branch (see below).
2. Read the repository conventions (see below) and the branch's commits and
   diff against the base branch.
3. Draft a title and body that follow the PR template and commit style, write
   the body to `.qwen/tmp/qwen-pr-body.md`, and print the draft. Nothing is
   pushed or created. If `gh` is unavailable, `prepare` skips the `gh` lookups,
   says so, and continues with `git` data.

`create`:

1. Preflight, with no mutation yet: `gh` is installed, `gh auth status`
   succeeds, and the push remote is a GitHub remote. Otherwise print a clear
   message and stop.
2. Working tree, checked before any drafting: a detached HEAD or an
   in-progress merge or rebase stops the run. If there are uncommitted changes
   (other than the CLI's own `.qwen/tmp/` scratch), list the files and ask.
   "Commit first" stops and prints a ready-to-copy `/commit ...` line;
   "continue without them" proceeds and lists the excluded files in the output.
3. Run the `prepare` steps to get the draft.
4. Branch: on the default branch, propose a branch name and run
   `git switch -c` after confirmation.
5. Push the branch (confirmed).
6. Look up the PR for the branch with `gh pr view`. A lookup error is distinct
   from a proved absence; on error, stop.
7. No PR exists: run `gh pr create --body-file ...` as a standalone foreground
   command (confirmed).
8. An open PR exists: show its URL and how its title and body differ from the
   draft, ask, and run `gh pr edit` only on "yes".
9. A closed or merged PR exists: ask whether to create a new one.
10. Print the URL, title, base branch, and any files left out of the PR.

Base branch resolution: `--base`, else the existing PR's base, else the
repository default branch from `gh repo view` (the parent repository for
forks), else the remote's `HEAD` when `gh` is unavailable. `origin/main` is
never hardcoded.

Push remote resolution: `branch.<b>.pushRemote`, then `remote.pushDefault`, then
the upstream's remote, then the only remote, otherwise ask. `--force`,
`--no-verify` and `--amend` are never used, and failing hooks are never bypassed.

### Permissions model

`allowedTools` is additive-only (`packages/core/src/skills/types.ts`): it grants
rules and never restricts. Matching is prefix-based with no exclusion syntax
(`matchesCommandPattern` in `packages/core/src/permissions/rule-parser.ts`), so
`Bash(git push)` also matches `git push --force`, and `Bash(gh pr create)`
matches any flags. The allowlist therefore cannot separate safe shapes from
dangerous flags, and the skill grants only read-only rules:

- `gh auth status`, `gh repo view`, `gh pr view`, `git config --get`
- read, glob and grep tools
- `Write(/.qwen/tmp/**)`: `write_file` only, under the project root's
  `.qwen/tmp/` scratch directory (a leading `/` is project-root-relative)

Every mutating command (`git switch -c`, `git push`, `gh pr create`,
`gh pr edit`) goes through normal confirmation. Read-only git commands
(`status`, `diff`, `log`, `rev-parse`, `remote`, `branch`) are already
auto-allowed by `shellReadOnlyChecker.ts`. A bare `run_shell_command` rule is
classified dangerous (`isDangerousBashRule` in `dangerousRules.ts`) and is
stashed in AUTO approval mode, so it is not used. The skill sets
`disable-model-invocation: true`, so only the user can trigger it.

### Integration with session PR binding

The skill drives `gh` through the shell tool rather than
`packages/core/src/utils/github-prs.ts`. Running `gh pr create` through the
shell tool is the instrumented path: `commandRunsGhPrCreate`
(`packages/core/src/services/session-pr-service.ts`) takes a pre-run branch
snapshot and `bindGhPrCreate` (`packages/core/src/tools/shell.ts`) binds the
created PR to the session. The skill therefore instructs the model to run
`gh pr create` as a standalone foreground command, not wrapped in a subshell,
chained with `&&`, or backgrounded. `gh pr edit` is not bound; on the update
path the session keeps its existing binding, which is acceptable.

`github-prs.ts` is used as a reference only: the `gh pr view --json` field set,
and the `none` / `error` distinction of `BranchPullRequestSnapshot`, where
`none` is a proved absence and `error` is not.

### Repository conventions discovery

The skill reads the current repository at run time: the PR template
(`.github/pull_request_template.md` and variants), `CONTRIBUTING`,
`AGENTS.md` / `CLAUDE.md`, and the commit message style from `git log`. It never
hardcodes a body format; if no template exists it writes a short prose
description of what changed and why.

## Decisions and rationale

- **Bundled skill, not a project skill.** Works in any repository and ships with
  the CLI. Alternative: a `.qwen/skills` entry, which would exist only in this
  repository.
- **`gh` through the shell tool, not `github-prs.ts`.** A skill is a prompt and
  cannot import modules; reaching the module needs a new core tool.
  `createGitHubPullRequest` is create-only, with no edit wrapper, so the update
  half would shell out anyway. An in-process create would also bypass
  `commandRunsGhPrCreate` and `bindGhPrCreate`, losing session PR attribution.
  Alternative: a new agent-facing core tool.
- **Read-only allowlist.** Prefix matching without exclusion cannot express
  "push yes, force-push no". Alternatives: narrow-looking mutating rules
  (`Bash(git push)`), which still match `--force`; bare `run_shell_command`,
  which is dangerous and stashed in AUTO mode; flag-level exclusion in the
  permission system, which is a separate core change.
- **`--body-file .qwen/tmp/qwen-pr-body.md`.** Avoids quoting problems with
  markdown, `$(...)` and quotes. The command prompts anyway, so the file adds no
  approval surface. Alternative: an inline `--body`.
- **`disable-model-invocation: true`.** Publishing is irreversible and should
  need explicit user intent. Alternative: model-invocable, rejected.
- **Ask before updating an existing PR.** Other people may already be reading
  it. Alternatives: update silently, or fail; the first surprises reviewers and
  the second breaks the review-feedback loop.
- **`/pr` never commits; it points to `/commit`.** The built-in `/commit`
  (`packages/cli/src/ui/commands/commit-command.ts`) already does selective
  staging and the hook and secret policy. Precedent for printing another slash
  command: `/goal-draft` prints `/goal set`, `/batch` suggests `/batch-api`,
  `/review` suggests `/review --fix`. Alternative: committing inside `/pr`,
  which duplicates that policy.
- **GitHub only.** Resolved before any mutation; non-GitHub remotes get a clear
  message. Alternative: `glab` support or a no-`gh` link fallback, deferred.
- **Base from `--base`, existing PR, then `gh repo view`.** Handles forks and
  non-`main` default branches. Alternative: hardcoded `origin/main`.

## Risks

- Model drift from prose rules. Mitigated: every mutating command is always
  confirmed, and the allowlist is read-only.
- Session binding missed if the model wraps `gh pr create`. Mitigated by an
  explicit instruction to run it standalone.
- Template-filling quality varies by repository.
- Known limitation: skill commands are refused when `tools.executionSandbox` is
  set (`packages/cli/src/services/BundledSkillLoader.ts`).
- `gh pr edit` is not bound to the session; the update path keeps its existing
  binding.
- PR attribution: the shell tool appends the `gitCoAuthor.pr` line ("Generated
  with Qwen Code") only to an inline `--body`/`-b`, not to `--body-file`
  (`addAttributionToPR` in `packages/core/src/tools/shell.ts`). PRs opened by
  `/pr` therefore carry no attribution line even when the setting is on. This
  suits repositories that forbid AI mentions in PRs, but it is a behavior
  difference from a hand-typed `gh pr create --body`. Honoring the setting would
  need either the shell tool to support `--body-file` or the skill to append the
  line itself; left as a follow-up.
- A `cd <dir> &&` prefix makes read-only `git status` / `git diff` ask for
  confirmation, because after a directory change the target repository's git
  config (for example `core.fsmonitor`) could run commands
  (`packages/core/src/utils/shellAstParser.ts`). Observed in a real run; the
  skill now tells the model to run every command from the current directory
  without a `cd` prefix.

## Validation

- A unit test in `packages/core/src/skills/bundled-skills.integration.test.ts`
  pins the safety invariants: `disable-model-invocation` is set, the allowlist
  is exactly the read-only set, and no dangerous rules are present. A test in
  `packages/core/src/permissions/rule-parser.test.ts` pins that
  `Write(/.qwen/tmp/**)` matches only `write_file` under the project root's
  `.qwen/tmp/`.
- Manual E2E per `.qwen/e2e-tests/2026-10-07-pr-skill.md`, against a disposable repository
  or fork. Partially executed; see that file for results.

## Follow-ups

- No-`gh` fallback: push and print a `compare` / `pull/new` link.
- GitLab support via `glab`, and a `/mr` alias once skills support aliases.
- Flag-level exclusion in permission rules, so `git push` and `gh pr create`
  could be allowlisted safely.
- Bind `gh pr edit` results to the session if the update path needs it.
- Honor `gitCoAuthor.pr` for `--body-file` PRs.
