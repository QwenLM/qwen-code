# Background agent status and details

[English](background-agent-status-and-details.md) | [简体中文](background-agent-status-and-details.zh-CN.md)

## Problem

An Agent tool call returns as soon as a background agent is launched. Its transcript block therefore has a terminal tool event whose payload says `status: background`. The Web Shell intentionally maps that launch result back to a pending tool card, but nothing later reconciles the card with the live background-task registry. The footer task list reaches a terminal state while the original Agent card remains running.

Foreground agents already open in the shared subagent detail panel. Background agents have the same `toolUseId`, task registry entry, JSONL transcript, and virtual-session resolver, but this path lacks explicit coverage.

## Design

Keep the launch projection unchanged: a launch result with `status: background` remains pending until authoritative task state arrives. The daemon already emits terminal background-agent notifications over the session SSE stream with the task `status` and `toolUseId`. The Web Shell consumes that hidden notification metadata and reconciles it back into the projected Agent tool card.

- `completed` and `cancelled` complete the card.
- `failed` fails the card.
- The notification timestamp becomes the card end time.
- Notifications without `toolUseId`, non-agent notifications, and unrelated tool calls do not directly change messages.

The existing subagent detail provider remains the only UI path. Background Agent cards stay clickable while pending and after terminal reconciliation. The virtual-session resolver continues to stream the task JSONL and obtain live status from the task registry without filtering on foreground/background mode. For legacy tasks without `toolUseId`, it matches the launch record to the persisted sidecar and keeps a terminal sidecar status when the original background launch result still says `running`.

While detached work is active, its main-list card uses a dedicated static `background task` label instead of the foreground `running` label. The card does not use the running shimmer or a ticking elapsed timer. It does tint its icon with the active-agent colour and pulse it slowly, gated to the case where nothing else on the row is animating, so a detached card stays distinguishable from a finished one without a JS interval or foreground-grade visual weight. Reduced-motion preferences drop the pulse but keep the tint, which is not motion. Terminal notifications replace that label with the normal completed, failed, or cancelled presentation.

Unfinished background work is shown as chips directly above the composer, one per kind (for example `1 workflow`, `2 shells`, `1 monitor`, `1 local agent`), using the existing `tasks.pill.*` strings. A chip exists only while its work is unfinished: running shells and monitors, running, pausing, or paused workflows, and running background agents. Finished tasks drop out, so no "done" residue can linger; they remain in the full Tasks panel and, in the shipped entry, the environment panel. A paused agent gets no chip: parked agents are retained for the whole session and stay visible in the environment panel's subagents section, so a chip for them would pin a stale count. Background agents get a chip only where the environment panel is reachable (the shipped entry); headerless embeds keep agents out of their task surfaces. A chip that stands for one task opens it directly: a workflow chip scrolls the transcript to the call that started the run and opens its inline view (or, when the run has no row in the loaded transcript, opens the Tasks panel), a shell or monitor chip opens its output panel, and an agent chip opens the shared subagent detail panel. A chip that stands for several tasks lists them above the row to pick from. Each task also offers a "?" affordance — beside a single-task chip and on every row of a multi-task list — that asks the model to explain the task as a side question without opening it; see [Web Shell composer task explanation](web-shell-composer-task-explain.md). A direct activation of a single-task chip toggles its visible detail surface: another activation closes the active panel. When a Workflow opens a task-dialog request, its run and tool-call identity are tracked from that request until the dialog is closed or the request is invalidated, so a rapid second activation of that same target can cancel it before it appears. A newer activation carrying a different tool-call identity does not cancel the pending dialog as though it were a repeat of the same target. A displayed tasks dialog remains modal and closes through its own controls; the underlying chip is not expected to be pointer-reachable through that modal. Plan/tasks dialogs opened through another entry do not mark a particular Workflow chip expanded. A Workflow with a transcript row still uses transcript reveal navigation rather than changing the graph's local expansion state.

Selecting a row in a multi-task list never collapses an existing selected panel. Direct single-task activation is distinguished from row selection in the callback contract, so clicking an already-selected row keeps its detail open. When a hidden or inactive task is opened again, its existing detail tab is reactivated by task identity rather than duplicated under a new tab id. This covers shell and monitor output, background detail tabs, and local agents whose background tab is still hydrating or has already remained after closure. Reuse goes through ordinary tab activation, so a pending detail resumes or retries hydration instead of preserving a stale loading or error state. Open-state is based on an active compatible alias, not the first matching tab, so coexisting canonical and background aliases cannot make a repeat activation miss the collapse.

While the list is open, mouse presses on its buttons preserve the current focus so a row cannot be unmounted by a focus change before it receives its click. While a multi-task list has a pointer gesture in progress, an unresolved blur target (`relatedTarget: null`) does not by itself destroy the list and immediately reopen it. A known focus destination outside the component closes it immediately, as do an outside pointer press and window blur. Pointer release or cancellation re-checks the current focus through the shared shadow-aware focus helper and closes the list when it has moved outside. Gesture protection follows the real `openGroup` boolean across task-object replacement during polling; when the group is gone, all outside-pointer and window-blur listeners are removed.

Host-provided footers receive composer tasks plus background agents and render them as they see fit; the chips are not shown when a host supplies a footer. The chips add no polling: they read the task snapshot the Web Shell already polls while background work is active (`hasActiveTaskActivity` counts background sub-agent tool calls).

Persisted notification records do not always retain a `toolUseId`. When a loaded transcript contains an active background Agent card, the Web Shell therefore resolves each pending card through the existing subagent endpoint after transcript catch-up. It repeats this one-shot check after a reconnect and when any terminal Agent notification arrives, even if that notification cannot identify the card directly. It never starts an interval. Input focus and ordinary streaming do not change the pending Agent call IDs or terminal-notification key and therefore do not trigger another request.

The docked detail panel expands from the right edge so the chat is pushed left continuously instead of resizing before a separate panel motion. Reduced-motion preferences disable the docked animation. Panel tabs keep a fixed width, truncate long titles, and scroll horizontally when the tab list exceeds the available space.

## Scope

This change updates the Web Shell projection and the daemon's virtual-subagent status resolver. It does not rewrite persisted parent transcripts, alter the task lifecycle, add task polling for background agents, remove agents from the full Tasks panel, or add a second subagent viewer.
