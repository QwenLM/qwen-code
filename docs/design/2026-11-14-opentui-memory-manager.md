## Scope and existing behavior

Restore all four controls: `memory.enableManagedAutoMemory`, `memory.enableManagedAutoDream`, `memory.enableAutoSkill`, and `memory.autoSkillConfirm`. Initial values come from live merged settings, default on and gated off by existing bare/safe display semantics. Keep Ink navigation: initial user/project list; Up from first item enters confirmation, then auto-skill, dream, memory; Down reverses; Enter toggles/activates; numeric shortcuts activate targets; Escape closes. Persist each explicit toggle immediately in `SettingScope.Workspace`, preserving unrelated workspace keys and every user/system scope. Reopening reads merged settings; an Escape without activation writes nothing.

After a successful auto-skill setting write, call the existing public `Config.setAutoSkillEnabled(newValue)` for that same selected Config. Its public getter remains gated by sandbox/bare/safe/provisional-workspace policy. Existing readers are Config's startup curator gate, the Core client skill-review scheduler and the Ink AppContainer pending-review gate; the existing SkillReviewDialog can disable the same flag. Do not modify these consumers/writers or claim Native skill-review presentation parity. The other controls only persist/local-display in Ink; notably `getAutoSkillConfirmEnabled()` is a startup snapshot with no corresponding public setter. Preserve that behavior and prove cold reconstruction; do not promise live confirmation-policy changes or invent Core setters.

The target kind follows `config.isManagedMemoryAvailable()`, as Ink does. A hot auto-memory toggle does not rewrite that startup Config snapshot; a later cold launch may select a different target kind. When managed memory is available, user/project actions resolve the existing managed roots and show the existing dream metadata/relative-time status. Otherwise they resolve the first accessible configured memory filename in order, falling back to the first name or `QWEN.md`. Use actual selected working/project roots and public memory-path helpers, never hardcoded `memory.md` or primary cwd.

## Real target actions and errors

Only explicit target selection may create a missing directory/file. Legacy actions open the actual selected context file. Managed actions create the selected root then launch the platform folder opener on macOS/Windows or graphical Linux; headless Linux ensures and edits its `MEMORY.md` index. Preferred editor, platform defaults, argv handling and shell policy follow the existing CLI launcher. The folder opener's public contract is successful spawn, not successful GUI completion or a zero exit code. Editor spawn/nonzero/signal errors remain visible and keep the panel usable. A failed opener/editor may already have created its requested empty target; do not promise rollback that Ink does not perform.

Native cannot directly mount Ink's `useLaunchEditor` because it consumes Ink stdin/settings context. Reuse the existing native renderer suspend/resume and restoration pattern with a small actual-file launch path, preserving raw-mode/program-status restoration on success and failure. `editTextInExternalEditor` edits and removes a temporary draft buffer; it is not the Memory target launcher and must not silently replace file actions. Prefer a narrowly shared existing CLI launcher if it genuinely serves both consumers; no general opener framework. Do not add automatic memory refresh, model turns, dream runs or skill generation as a side effect.

## Ownership and boundaries

The mount supplies selected Config/settings/host plus native renderer ownership. Capture Config/settings/host identity, session, actual working/project roots, actual Workspace settings path, relevant user/runtime memory roots, and a per-generation active guard. Revalidate before a setting write, target creation, launching an external process, reporting error, closing, and after each asynchronous path/metadata lookup. Host must match Config/settings. Unknown or replaced owner and runtime mismatch fail explicitly; existing writer/trust/sandbox policy governs target authority; never fall back to primary runtime or ambient cwd.

Close/unmount/observed replacement permanently revokes the captured generation, including A→B→A. Old completion cannot close, report into, mutate or poison a new legitimate generation. One explicit action is pending; same-read navigation/Enter follows the actual advanced focus and cannot duplicate a pending launch. Known numbered catalog shortcuts 1/2 preserve Ink immediate activation while the file list is focused, even when the viewport is scrolled; zero-height or unusably narrow regions do not activate targets. Authorized settings deltas must not revoke their own owner: do not fingerprint the entire merged settings or memory corpus as identity. Existing writer/trust and sandbox rules stay authoritative. Guards cannot undo an already completed synchronous write or launched external process; no external-FS atomicity claim.

## Limits and open questions

Effective auto-skill scheduler behavior is separate from proving its existing public setter call. The native automatic SkillReview approval dialog is still an unimplemented follow-up: these controls do not qualify generated-skill approval or silently accept pending skills. Cold confirmation state is required; live policy has the existing snapshot limit.
