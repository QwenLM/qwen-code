# 最终交互退出前准备文件监听器

[English](2026-11-13-interactive-file-watcher-exit.md) | [简体中文](2026-11-13-interactive-file-watcher-exit.zh-CN.md)

## 问题与证据

在 macOS arm64、Bun 1.4.4 上，公开 `/quit` 可能打印总结后仍超过既有 E2E 的 12 秒等待而不退出。扩展桥接重放记录了三个通过案例和三个失败案例，已到达的热、冷会话合计七次自然退出；失败保留原始清理状态。另一个未修改的 `83cd18ac` 诊断也复现了卡住，因此无需扩展桥接就能发生该现象。

干净 main 的采样中，主线程全部 888 次观察均等待原生 unfair lock，同时 `CFThreadLoop` 等待 FSEvents 注册 RPC。未符号化的 Bun 栈不能识别具体 JavaScript 监听器、close 调用者、锁环或永久死锁。这些证据支持受控验证既有最终退出监听器策略，不能宣称已证实精确原生根因。

## 变更与范围

在两个 CLI 入口调用既有 `prepareFileWatchersForProcessExit()`：OpenTUI 共享 `exitSession` 的既有单次闩锁之后、`requestShutdown` 之前；以及 Ink 的公开退出动作中，取消请求、更新总结状态和关闭客户端之前。取消操作可能同步进入资源清理，因此必须先准备监听器。

该 helper 已用于 ACP 的最终进程退出。在 macOS 上，它让监听器清理仅移除事件监听，而不再同步重建原生 FSEvents 流；进程退出时由操作系统回收句柄。其他平台保留正常关闭监听器的行为。不修改 Core 行为或 helper 合同。准备状态是进程全局的，仅适用于 CLI 已决定最终退出的时刻；不得用于进程内恢复、切换渲染器、普通卸载或替换会话。

OpenTUI 既有闩锁继续决定退出所有权，第二次调用不会再次准备监听器、通知关闭、清理或退出。Ink 不新增闩锁，其既有 100 ms 总结延迟及清理、退出顺序保持不变。不新增运行参数，不延长清理或 E2E 等待，不强制成功退出，也不修改公开案例断言。其他信号处理器和渲染器致命错误路径没有由此变更单独取得资格。
