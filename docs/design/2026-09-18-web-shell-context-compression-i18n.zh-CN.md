# 给自持 UI 语言的宿主渲染压缩结果

[English](2026-09-18-web-shell-context-compression-i18n.md) | [简体中文](2026-09-18-web-shell-context-compression-i18n.zh-CN.md)

状态：已实现（2026-09-18）

## 问题

`/compress` 与 `/compress-fast` 把结果作为英文句子报给 ACP 客户端。自持 UI
语言的宿主因此只能显示英文；句子里的 token 数还带着 daemon 的分组方式和
`~` 估算标记，宿主既不能按自己的语言分组，也无法解释这个标记。

另外两条与语言无关的行为本来就是错的：

- `/compress-fast` 在无可压缩内容时复用了 pending 阶段作为终态，轮次结束后这
  一行被丢弃，用户永远不知道无需压缩。
- 打开一个"最后一次操作是压缩"的会话时，composer 的上下文环会停在压缩前的占
  用上，直到下一轮模型输出才纠正。会话从回放里播种的计数是回放中最后一条带用量
  的帧，而压缩本身不发用量帧，所以它描述的是刚被压缩替换掉的那份上下文。

## 目标

- 自持 UI 语言的宿主用该语言渲染压缩结果，数字由宿主自己格式化。
- 命令能产生的每种结果都可表达，包括终态的无需压缩。
- 原样渲染文本的宿主看到的句子与改动前一致。

## 非目标

- 不改变任何其他客户端的渲染。下面的兼容性分析是设计的一部分，不是后续项。
- 不结构化自动压缩那条诊断信息——它由会话作为普通 assistant 文本打印，而不是
  作为命令结果。
- 不为慢路径的无需压缩选择新文案：它仍然报告一次计数相等的压缩。记在后续项里。

## 设计

**D1 —— 结果与句子并列，走 `_meta`。** 每条流式消息保留英文 `content` 供纯文
本宿主使用，同时在一个新键下携带机器可读的结果：进度阶段、终态的无需压缩，或
带原始计数与可选服务端附注的结果。对任何不读该键的宿主，句子仍是完整的用户可见
文本；该键对所有人都是可选的。

**D2 —— 调用提示独占一个键。** "指令被截断"的提示在压缩开始前发出，因此与结果
落在同一轮。daemon 的 UI reducer 会把一轮的文本帧折成一个块，并按 key 逐键
spread `_meta`，所以与结果共用同一个键的提示会被紧随其后的帧覆盖。单独占键后，
消费方可以把它渲染成压缩所属结果之前的一行。

**D3 —— 无需压缩是终态，而不是复用 pending 阶段。** 无需压缩的结果与压缩结果
一样就地替换 pending 那一行，因此该行能活过轮次结束并说明结果。轮次结束时只是
"不再更新"的 pending 行会被丢弃。

**D4 —— 计数以原始数值传输。** 结果携带数字而非格式化字符串，估算标记单独携带。
分组方式与是否标注估算由消费方决定，服务端不决定计数长什么样。

**D5 —— 只加惰性键，不复用其他客户端会解读的标记。** discrete message 标记在别处
是承重的：一些桥接会丢弃这类帧（除两个特定来源外），一些客户端会把它们排除在答案
缓冲之外。为了突出提示而复用它，会让提示在这些客户端里静默消失。新键在构造上就是
惰性的：不读它的客户端观察不到它。

**D6 —— 提示作为独立记录项落盘。** transcript 记录要在回放时重建同样的行，因此
提示与拼接后的结果文本分开记录，而不是拼进同一条。记录里提示文本保留尾部换行，
这样消费方拼接帧时，回放出的文本与改动前逐字节相同。

**D7 —— 环在连接稳定后再调和。** 会话从回放播种的计数可能早于记录里已有的压缩，
而压缩不发用量帧。因此结果会按会话读取一次用量来调和 composer 的计数，但只在会话
处于 live 时：只有会话已连接、不在追赶、不在加载中，且模型与上下文窗口自读取发出
以来未变，结果才写得回去，被拒的写入不会重试。调和正以这些字段作为 key，所以撞上
attach 自身解析模型与窗口的那次读取，会在它们落定后重读一次。

## 与其他客户端的兼容性

每个压缩帧的线上文本与改动前逐字节相同，没有任何帧新增或去掉 discrete message
标记，新键的读取方只有产出侧的 CLI、回放透传与 web shell。逐客户端：

- 渠道（ACP 桥与 daemon 桥两套一致）把斜杠命令输出按"后到覆盖先到"收集，显示最后
  一帧，因此显示的是结果句——本来也是如此，因为提示句与进度句早已被其后的帧覆盖。
- IDE companion 只对 discrete 标记与 background-notification 来源做单独持久化，其
  余一律当作普通流式文本。
- live 客户端把每个非 discrete 帧都算作答案缓冲的一部分，因此它看到的句子不变。
- SDK 收集器只跳过 discrete 帧。
- TUI 的恢复历史渲染对这些记录项的形状没有渲染分支，因此多出的那一项不会被渲染——
  改动前所有其他命令的记录项同样如此。
- 模型历史不受影响：把本地命令输出从模型历史里摘掉的判据要求记录项全部是 assistant
  项，两项仍然都是。

## 风险与限制

- 一帧一行的消费方会把回放出的提示与结果看成两行。今天唯一这样的消费方就是
  web shell，而这个拆分正是目标行为。
- 环的调和以写入守卫所看的字段为 key，因此由其他原因造成的拒绝不会重试。已观察到
  的原因只是模型与上下文窗口在会话转 live 之后才落定。
- 以压缩结尾的会话在被打开时会多一次上下文用量读取；若模型与窗口在第一次尝试之后
  才落定，则再多一次。

## 验证

- 单测：压缩命令产出的键值（含附注与终态无需压缩）、解析器对未知与破损结果的容错、
  行拆分及其在结果无法解析时退回原始文本、行渲染的文案、调和 hook 的延后与重读。
- 端到端（Playwright，模拟 daemon）：同一个折成的块产出提示行与结果行、结果行在随后
  的命令之后仍在、终态无需压缩行、以及环落到压缩后的数值。
- 端到端真实 daemon 探针，覆盖"记录里已有压缩"的 attach 两种时序：压缩已在 attach
  快照里，以及压缩在 transcript 仍在追赶时到达。两者都必须落在压缩后的占用上，且
  连接仍在解析模型时第一次读取可能被拒。

## 验收标准

- 读该键的宿主用自身语言渲染结果、自行格式化计数；不读该键的宿主渲染与改动前相同的
  句子。
- 消费方读不懂的结果退回原始句子，而不是渲染半块内容或直接丢弃。
- `/compress-fast` 在无可压缩内容时留下一行可见的终态结果。
- 打开"最后一次操作是压缩"的会话后，环在不需要等到下一轮模型输出时即落到压缩后的
  占用。
- 其他任何客户端的渲染都不变。

## 后续项

- 慢路径的无需压缩仍报告一次计数相等的压缩；给它终态无需压缩阶段是对称的修法。
- 自动压缩的诊断没有结构化，因此非英文 UI 下仍是英文。
- 省略估算标记时的默认值与 core 压缩路径不同；这处分歧是有意为之并已注释，但尚未拉
  齐。
