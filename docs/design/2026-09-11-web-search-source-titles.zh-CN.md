# 网页搜索来源标题

[English](2026-09-11-web-search-source-titles.md) | [简体中文](2026-09-11-web-search-source-titles.zh-CN.md)

状态：已由添加本文档的 PR 实现。设计讨论：#11564。

## 问题与范围

内置 `web_search` 工具要求模型在回答末尾给出由 markdown 链接组成的 `Sources:` 段，示例写的是 `[title](url)`。但模型收到的工具结果只列出裸 URL，因为 DashScope 的 `web_search_call` 条目只含 `{type, url}`。模型要么编造标题，要么把原始链接贴进回答。

本设计为被引用的页面提供真实标题，涵盖标题从哪里来、如何与页面匹配、如何渲染进工具结果，以及如何告知模型。不修改搜索请求的时间预算，不增加其他供应商的搜索后端，也不提供逐条摘要。

## 现状

DashScope 后端（`packages/core/src/tools/web-search-dashscope.ts`）收集搜索代理的旁白、extractor 打开的页面和搜索返回的页面。工具（`packages/core/src/tools/web-search.ts`）先输出旁白，再输出"已打开页面"段和"候选"段，每行为 `- <url>`，最后附上引用策略和安全脚注。

#11490 中的第一版实现从侧模型写的清单中读取标题，然后围绕清单编辑旁白：剥离清单块、为证据段会省略的页面保留行、恢复标题行、剥离后答案为空时回退到提取正文。端到端可用，但评审意见从 16 条增长到 29 条，几乎都落在这套编辑机制上，因此该功能被拆到 #11564。

## 目标

- 有可用标题的页面在工具结果中列为 `[title](url)`，其余页面保持裸 URL。
- 解析出错最多丢失或错配一个标题，绝不改写旁白。
- 标题只能挂到搜索返回过或代理打开过的页面上。
- 没有标题时，页面列表与之前的输出一致，只多了按页面身份去重；引用策略的措辞对所有结果都有变化。
- 链接文字能在 CLI 中正确渲染。

## 设计

### 标题来源

标题有两个来源。第一是转述标题，来自侧模型：它的指令要求在回复开头写一行只含 `Sources:` 的内容，紧接着为它依据的每个页面写一行 `- <页面标题> — <url>`，清单内不留空行，只列出搜索结果中出现过或它打开过的 URL，然后空一行再给出答案。清单放在开头，是因为侧请求有固定的 60 秒预算，被截断的流会从已经到达的内容中抢救结果。

第二是声明标题，即搜索响应自身在 `action.sources[].title` 上携带的标题，目前尚未观察到。同一 URL 两者都有时转述标题优先，因为代理读过页面，而搜索索引只是列出了它。

转述标题只从侧模型自己写的内容中读取——即它的旁白或流式文本。抢救出来的 extractor 正文从不用于读取标题，因为页面可以在其中伪造自己的引用。

结构化输出已考虑但不可用：开启 `web_search` 时，DashScope Responses API 会忽略 `text.format` 的 `json_schema` 和 `json_object`（2026-09-11 探测；HTTP 200、搜索照常执行、回复仍是普通 markdown）。在提示词中要求只输出 JSON，会使被预算截断的回复整体无法解析。

### 读取清单

`readSideModelTitles(narration, knownKeys)` 返回转述标题，从不修改旁白。旁白以未经编辑的内容交给模型，包括代理自己的清单。只读取指令所要求的那张清单：

1. 标题行必须是回复的第一个非空行：去掉首尾空白后不超过 32 个字符，且匹配带可选标题符号、加粗符号和冒号的 `Sources:`。出现在其他位置的清单——答案之后，或代码围栏之内——一律不读，因此不需要跟踪代码围栏。
2. 标题行与第一个条目之间可以有空行。出现第一个条目之后，空行会结束清单，任何非条目行也会结束清单，因此其后的答案永远不会被读取。
3. 条目是以列表标记（`-`、`*`、`+`、`•`、`‣`、`1.`、`1)`）开头、且恰好含一个 `http(s)` URL 的行；标题是该行除 URL 之外的其余部分，可在 URL 的任一侧。没有列表标记、或含多个 URL 的行都不是条目。
4. 紧贴 URL 的括号（`(url)`、`<url>`、`[url]`）、包住整个条目的括号，以及 markdown 链接的标签（`[title](url)`，链接之后的文字视为附注）都会被拆开。URL 末尾的标点，以及 URL 自身并未打开的右括号会被去掉。
5. URL 不在搜索返回页面或代理打开页面之中的条目会被忽略；没有标题的条目仍会延续清单。
6. 两个来源的标题都会被清洗：折叠空白；去掉首尾分隔符（空格、制表符、`—`、`–`、`-`、`:`、`|`、`·`、`•`）以及包裹的强调符号、引号和括号；只剩强调符号的标题视为空；最多 200 个 UTF-16 码元，在字符边界处截断。空标题不贡献任何内容。
7. 标题按"页面身份 + URL 的 fragment"索引，同一索引以第一个标题为准。为带 fragment 的 URL 给出的标题只标注该小节；不带 fragment 给出的标题可标注该页面的任一小节。
8. 超过 2,000 个字符的行永远不是条目。标题行正则是唯一可能回溯的正则，且只作用于不超过 32 个字符的行；其余每一步都是对单行的一次线性扫描，因此无论页面文本如何塑造，读取清单的耗时都与其长度成线性关系。

### 页面身份

`packages/core/src/tools/web-search-backend.ts` 中的 `sourceKey(url)` 是把标题匹配到页面、以及页面去重时使用的唯一身份。对 `http(s)` URL 而言，scheme、主机大小写、末尾斜杠、路径中普通字符的百分号编码和 fragment 不区分页面；非默认端口、查询串，以及路径中编码的 `/`、`?`、`#`、`%` 区分页面，因为解码它们会移动路径与查询的边界或合并不同的路径段。其他 scheme 保留 scheme，无法解析为 URL 的文本使用独立的命名空间。

每一层都按身份去重，保留第一种写法。已打开页面排在前面；与某个已列出的已打开页面为同一页面的候选不再重复列出，而已打开写法因超过 25 页上限未被列出的页面仍会作为候选列出，因此不会有页面同时从两个列表中消失。

### 渲染

`renderSource` 仅在以下条件全部满足时列出 `- [text](url)`，否则列出 `- url`：

- 存在标题，且净化后非空、不等于 URL 本身。净化会把 `[` 和 `]` 替换为 `(` 和 `)`，并去掉反斜杠和反引号，因为 CLI 从不反转义链接文字，并在第一个 `]` 处结束链接文字。
- URL 能解析为带主机的 `http(s)`、不含空白，且最多一层成对括号，与 CLI 的行内链接模式（`packages/cli/src/ui/utils/osc8.ts` 中的 `MD_LINK_CAPTURE`）一致。URL 从不重新编码。
- 标题读起来不像另一个目的地。标题先做 NFKC 归一（使形近点号和全角字符变为 ASCII）；含 `://` 则拒绝。若不含空白且带主机标记（点、冒号或括号），则在规范化带方括号或圆括号的 IPv6 authority 之后，按浏览器解析"不带 scheme 的地址"的方式解析为 authority。若解析出主机，该主机必须是页面自身的主机或其上级域名（忽略开头的 `www.`）；若标题带路径，路径也必须是页面自身的路径。

没有标题的页面不做域名回退。

### 告知模型的内容

引用策略要求使用两个页面列表（已打开的证据页面与其他搜索候选）中显示的标题作为 markdown 链接文字，说明只出现在叙述性答案中的标题未经校验，并要求这类页面——以及列出时没有标题的页面——用裸 URL 引用，绝不编造标题或 URL。工具描述说明每个来源页面在有可用标题时会带标题列出，并说明旁白自带的 `Sources:` 清单不是权威的页面列表。

## 决策与理由

| 决策             | 选择                                                                       | 理由                                                                                                                                       |
| ---------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 编辑旁白还是只读 | 只读                                                                       | 针对编辑机制的所有意见随机制一起消失；解析错误只会丢失或错配标题，而不会改动旁白。代价是代理清单中命名的页面会同时出现在旁白和页面列表中。 |
| 解析哪些文本     | 只读回复开头的清单，遇空行或非条目行结束；条目需有列表标记且恰好含一个 URL | 所要求清单之外的一切——答案散文、引用的页面文本、代码围栏——都无法被采集，语法也不需要围栏或散文启发式。                                     |
| 标题来源         | 转述清单，其次响应声明标题，否则无                                         | 搜索条目至今未携带标题；端点忽略结构化输出。                                                                                               |
| URL 身份         | 所有地方统一使用 `sourceKey`；标题额外按 fragment 索引                     | 第一版实现混用精确键和归一化键，导致标题错配以及页面重复或被合并；某小节的标题不应标注另一个小节。                                         |
| 渲染             | 按 CLI 渲染器净化；拒绝能解析为其他目的地的标题；不做域名回退              | 见下方说明。                                                                                                                               |
| 清单位置         | 放在答案之前                                                               | 被预算截断的回复仍保留已流出的标题。                                                                                                       |

有意没有复刻 CLI 的 `labelMayDeceive` 检查。该检查在 CLI 中故意宽松，因为误判只会在渲染回复时保留可见的 `(url)` 后缀。放到工具层，同样的误判会直接丢弃标题，而且它会拒绝 `Node.js Releases`（`node.js` 看起来像主机名）、`Qwen3.6-Plus: Towards Real World Agents`（看起来像 scheme）这类普通标题——约占真实运行中观察到的标题的一半。工具改为按浏览器的方式解析标题：带空白的散文保留，凡能解析为 URL、主机、地址或带路径主机的标题都必须与页面一致。由此接受两个后果：恰好能解析为其他主机的单个带点词元（仅以 `Node.js` 为标题的页面）会回退为裸 URL；不带点的整数地址（`2130706433`）会被保留，因为它读起来不像地址。其他不做目的地检查、只渲染链接标签的前端（例如 web-shell 的 markdown 链接），对这些工具提供的标题与对模型写出的任何链接文字一视同仁。

## 约束与风险

- 侧请求的回复格式随指令变化。忽略格式的回复会得到裸 URL 且旁白完整；清单中用描述代替页面标题的回复，会以该描述作为链接文字。
- 代理命名的页面会在工具结果中出现两次，一次在旁白中，一次在页面列表中。
- 标题会占用 100,000 字符结果的空间。在体积压力下旁白会先被截断，因此带标题的页面列表会比无标题时少保留一些旁白。
- 侧请求的 60 秒预算未改动。实测侧请求耗时 13–107 秒，因此部分搜索仍会进入部分结果路径，此时只有已经流出的清单中的标题能保留。

## 验证

- `sourceKey` 的单元测试（scheme、大小写、斜杠、fragment、查询串、默认与非默认端口、编码括号与分隔符、无法解码的路径、其他 scheme、无法解析的输入），以及每条读取规则的单元测试，包括代码围栏、答案散文、URL 在前与带括号包裹的条目、字符边界安全的截断、超长标题行，以及长度闸门以内 1,000 个条目的清单按线性时间读取。
- 工具层测试：带标题渲染且旁白不变、丢弃未返回的 URL、响应标题及优先级、不从 extractor 正文取标题、从流式文本读取标题、跨层级与不同写法去重（含已打开页面上限）、按小节限定的标题、链接文字净化、读起来像其他目的地的标题（URL、主机、IP 形式、形近字符、同主机不同路径）及与之并列应保留的标题、不可作为链接目标的 URL、带括号的 URL、限定范围的引用策略、固定的条目格式，以及截断时保留带标题的来源。
- 刻意引入的回归已确认会让这些测试变红。
- 使用 `qwen3.8-flash` 对 Token Plan 端点的真实运行，并用本读取器解析真实回复：5 个查询共 7 次回复中，6 次以独占一行的 `Sources:` 开头；这 6 次中挂上的标题数与整条回复中 URL 数之比为：两次 Node.js 运行分别为 6/6 和 5/5，TypeScript 为 8/10，Rust 为 5/5，Mercury 为 4/4，Python 为 3/3。有一次 Node.js 回复把第一个条目写在了 `Sources:` 同一行，该清单未被读取，其页面回退为裸 URL。端到端运行中工具结果和模型最终的 `Sources:` 段都出现了带标题的链接。

## 验收标准

- 工具结果中的旁白内容就是侧模型的文本，只会被去掉首尾空白，并在超过结果上限时带提示截断。
- 只有搜索返回过或代理打开过的 URL 会获得标题；转述标题从不来自 extractor 输出，且只读取回复开头的清单。
- 没有标题时，页面列表与之前的输出一致，只多了页面去重。
- 所有页面比较都经过 `sourceKey`；标题只会标注为其给出的小节或整个页面。
- 渲染出的链接符合 CLI 的行内链接模式；读起来像其他目的地的标题回退为裸 URL。
