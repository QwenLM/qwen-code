# Hosted Workspace Runtime confinement

## Background and scope

#15081 calls for explicit operator opt-in, filesystem and process-tree containment, and actionable refusal reasons. #12380 assigns Workspace side effects and uncertain results to the selected Runtime, with a separate acceptance gate for deployments serving untrusted users. #15163 selects a private filesystem view and Broker-verifiable stop evidence for Linux `local-process`. #14667 tracks process containment that remains verifiable after the Worker dies.

At baseline `0cfbdac07b`, the general Core bwrap executor limits writes with `--ro-bind / /`. Host permissions still allow reads outside the Workspace except at masked paths. Hosted file and foreground Shell paths use Worker permissions, and `serve` rejects public execution sandbox settings. Linux cgroup stop receipts in the local provisioner cover Managed extension profiles and require proof from a live Runtime. The stdio MCP supervisor reaps process groups, which descendants can leave by creating a new session. Durable local provisioning checks the original Worker PID and start identity, and its ordinary receipt covers that Worker.

This delivery has three stages. Core supplies a private-root executor. The Broker verifies that a durable local Runtime cgroup has stopped. Selected Hosted Workspace Runtimes combine both to run foreground Shell. Durable cgroups cover the Worker and descendants that inherit its cgroup, including stdio MCP and descendants that leave the original process group. Shared Runtimes, processes launched by external services, MCP supervisor memory management, default enablement, and Windows support have separate scope.

The Broker can opt local, durable, Session-exclusive Hosted Workspace Runtimes into Linux private-root execution. The dedicated `hosted-workspace-confined-shell/1` profile provides bounded Tool v2 results for built-in Agent Sessions bound to a registered Workspace root. Commands see the authorized `/workspace`, a read-only deployment image, and a private temporary directory. Networking is disabled. Native file tools, process services, and executable extensions require separate admission designs.

The selected Worker remains a trusted host control process and uses the existing authenticated loopback protocol. The private-root launcher runs each admitted command. The Worker, launcher, and command occupy the original Runtime cgroup so lifecycle cleanup can prove the Runtime stopped even if the Worker becomes unresponsive.

## Deployment and trust boundary

Operators set `qwen.managed-agent.runtime-broker.provider-options.cgroup-root` to a dedicated, canonical, delegated cgroup v2 directory. The local provider accepts it in durable Linux mode. A new Managed binding needs associated storage, an admitted isolation class and capability digest from `WorkspaceExecutionProfile`, and a profile outside Managed extension execution. Non-Managed workers follow the existing path. Unsupported Managed placements fail before Worker allocation or startup. Existing version 2 handles follow their recorded profile. Version 3 bindings retain the original cgroup across configuration changes.

The Broker and Worker are trusted service processes. The deployment controls the state directory, cgroup hierarchy, and mount namespace. It must prevent tools, untrusted host processes sharing the UID, and other administrators from moving processes into or out of a Runtime cgroup or altering recovery records. The delegated root and its ancestors must remain stable. Only the Broker creates and deletes its units under the resource lock. Operators must keep other mounts off those paths. Version 3 Workers omit `QWEN_MANAGED_HOOK_CGROUP_ROOT` from their launch environment. Foreground tools and stdio MCP inherit the unit. Command Hooks, background Shell, and Monitor that require an independently delegated supervisor retain their isolation-unavailable refusal. The confined Hosted profile hides the cgroup control plane from the payload.

The deployment owns the root image, bwrap binary, interpreters, relay, state directory, and Workspace mount sources. It protects every component of those source paths and keeps the image immutable for the binding lifetime. Host processes sharing the Worker UID are trusted because they can access host control files and receipts. Build the image separately and exclude host credentials and other Workspace data. Both mounted source trees require continuous protection against submounts, device nodes, pathname sockets to external services, and inode aliases to files outside the tree. Copy imports to independent inodes. These constraints apply to every host process that can write the Workspace. The executor checks its launch inputs and the caller maintains the mount sources.

## Bubblewrap private-root execution contract

Core provides `executePrivateRootBwrap` beside the general bwrap adapter. Its inputs are explicit absolute paths for rootfs, Workspace, installation, and state, plus the Workspace access mode. It uses the bundled bwrap relay and existing path, scratch directory, receipt, and cleanup checks. It requires Linux, a non-root Worker, a directory rootfs, and empty real mount points in the image. It rejects relative paths and missing or symlinked mount points. Canonical path checks cover equality and nesting in both directions. Both Workspace access modes reject overlap with the image, installation, state, or launcher directory. The image is checked against the same protected host paths. The deployment-owned bwrap launcher must be canonical, executable, and free of setuid and setgid bits.

The mount table contains the read-only image at `/`, the selected Workspace at `/workspace` in its admitted mode, private tmpfs at `/tmp`, and bwrap's minimal `/dev`. The image supplies empty directories for the latter three. The view omits procfs, host home, installation, and state mounts. The launcher enables a private user namespace, disables nested user namespaces, isolates PID, network, IPC, and UTS namespaces, drops capabilities, and uses `--new-session` and `--die-with-parent`.

The executable is a literal absolute path in the private view, its argument vector follows `--`, and cwd is `/workspace`. Stdin may be piped. Descriptors 0–2 carry controlled standard streams. The dedicated status descriptor closes before payload exec, and stdout and stderr carry no status evidence. The adapter omits PTY, caller environment, and Shell background promotion inputs. The relay starts from the host control directory with the adapter's environment. `--clearenv` precedes a private `PATH`, `LANG`, `HOME`, `PWD`, and temporary directory settings. The shared relay's host temporary paths are removed. All abort reasons become ordinary cancellation.

Invalid inputs fail before relay launch. Namespace setup or image exec failures after launch give an unconfirmed result. Failures have no host fallback. A confirmed nonzero exit is a confirmed payload result. The receipt protocol retains interrupted and unknown outcomes. A missing, unreadable, or mismatched receipt cannot authorize a retry. An empty process unit proves only that processes stopped. Replay follows the selected Runtime's durable execution state and reconciliation policy. A never-started disposition requires explicit pre-execution evidence.

## Durable cgroup identity and stop proof

### Resource identity and launch order

The existing provision request lock serializes allocation, launch, recovery, and stop. A new qualifying intent creates a leaf under the delegation, named from the provision request digest. A pre-existing name is refused. Validation requires cgroup v2 domain mode, readable `cgroup.procs` and `cgroup.events`, and writable `cgroup.procs` and `cgroup.kill`.

Version 3 local resource handles retain host, boot, PID and time namespace, and request identities, tied to the provision request, Runtime instance, lease epoch, and Workspace generation. They add the canonical delegation, cgroup namespace, and kernel filesystem identities of the root and leaf. The provider fsyncs the handle into local registration before the Broker persists the same handle. Retries reuse it. Version 2 registrations require version 3 handles. Version 1 registrations continue to hold version 2 handles. Operators inspect directories left before registration sync. Recovery does not adopt a directory by name. Missing or conflicting state keeps the original binding fenced.

The provisioner records `LAUNCHING`, inspects the exact unit, and starts a fixed shell trampoline with a literal argument vector. The trampoline joins the unit and waits on the Broker's stdin pipe. Under the same resource lock, the Broker reopens and verifies the unit, observes the live PID in it, persists `REGISTERED`, then sends the start line and the existing boot envelope. The start line authorizes exec. EOF, failed migration, or failed membership checks prevent exec. A crash leaving `LAUNCHING` stays blocked because an unregistered trampoline can still be joining. Adopting a ready Worker verifies the unit and its live membership again. Registered and retired identities cannot launch another Worker.

### Stop and recovery

The Broker closes admission and holds the binding's operation authority before calling the provider. Version 3 terminal binding drains, including resource drain and storage retirement, use the existing proof-first path for members still held at drain start. Work must be settled and the receipt persisted before Session or member release. Without a receipt, the stopped-only path still requires matching Worker absence evidence. The Broker checks the drain claim and lifecycle authority again before kernel I/O. An expired claim cannot persist a receipt or release a member. A late stop can leave a local fact for a later claim.

Under the original registration lock, the provider reopens the exact unit, verifies its directory descriptor, and opens files by relative path with no-follow. The kill file opens without create or truncate. After verifying identity, the provider writes `1` to `cgroup.kill` when the unit is populated and waits within a deadline for recursive `populated 0` from `cgroup.events`. It also establishes the original Worker exited. A successful write or PID absence alone cannot prove stop. Missing, unreadable, replaced, or populated units retain the storage holder unless there is prior proof. Observation can independently prove journal loss. An absent Worker and an already empty original unit let observation persist stop and return both facts without signaling. Otherwise it supplies no writer stop evidence.

The provider persists `RETIRED` under the registration lock only after it verifies the empty unit and Worker exit, or validates the existing trusted host reboot proof. For version 3 this is durable evidence for the original unit. The provider then attempts to remove the verified empty leaf. Later retries use the saved proof. Trusted reboot recovery does not open a same-name unit on the new boot. Offline verification on the same boot must inspect the original empty unit when saved evidence is absent. Observation, adoption, and malformed ready-envelope cleanup need verified stop evidence to write version 3 `RETIRED`. Reopening a retired registration supplies proof to existing LOST reconciliation. A populated LOST unit requires fenced operator recovery that stops the original unit before proof. A version 3 binding released through verified LOST recovery can answer a later resource drain with its exact stop and loss evidence. Maintenance uses the saved handle after configuration changes.

The design reuses the Broker receipt, generation checks, receipt persistence, and fenced Session/member release transaction. The version 3 retired transport tail checks for absence of members. Live detach, ordinary Turn handback, and parking on trusted Harness deployments keep the live-owner rules. Their successful completion does not depend on Worker retirement proof. Live handback for confined Hosted Sessions follows the verification below.

A receipt carries the exact durable handle of the original provision request. If SQL has no handle and the Worker never received launch authority, the provider uses the original intent under its lock. Launch and stop reuse the public API and TypeScript boot envelope. The canonical V1 catalog indexes local version 3 recovery candidates and initializes new development catalogs under the existing V1 policy. Kernel emptiness proves stop. Existing gates still govern journal loss, unknown results, and replay.

## Hosted selection, configuration, and qualification

Set `qwen.managed-agent.runtime-broker.provider-options.private-rootfs` explicitly to the canonical absolute path of a deployment-owned image with executable `/bin/sh`. Prerequisites include canonical `/usr/bin/bwrap`, the cgroup-root option, a durable local-process provider, Linux, an unprivileged service account, and Session-exclusive placement. Disable publication, executable extensions, child Workspaces, child Agents, and Web terminals. The initial profile supports the built-in Agent without model-side extensions, Hooks, MCP, client files, Skills, or process services. Ineligible local placements return typed refusals. External and SSH placements keep their own capabilities. The setting is immutable while the Broker runs. This delivery uses Bubblewrap 0.8.0 for verification. Pause admission and clear existing local Runtime leases before switching the setting. The image, Workspace mount sources, and executables follow the deployment rules above.

With confinement enabled, creation of a local built-in Agent Workspace Session persists `hosted-workspace-confined-shell/1` under the Workspace creation lock. Built-in admission rejects missing prerequisites, a non-root cwd, and optional tool configurations. The control plane selects the reserved capability digest for an eligible local Workspace with the saved confined profile. Existing ordinary Sessions retain their profile and can recover and clean up original work on affected local deployments. New warm, acquire, prepare, and dispatch require the confined profile. Disabling confinement prevents a saved confined Session from warming or acquiring a fallback Runtime. Durable scope, Worker boot, and attestation use a capability distinct from ordinary, external, SSH, resident, and extension modes. Compatibility rules between ordinary capabilities do not allow a switch in either direction. The existing schema accommodates the profile name.

Version 3 registration records the private-root recipe alongside the original cgroup identity. The recipe contains the canonical image path, device and inode identities for the image and fixed bwrap binary, and the protocol version. Initial registration uses current configuration. Reading a registration reconstructs its handle from the saved recipe and compares it with the Broker handle. Boot and attestation use the same recipe. The server and Worker compare saved and current configuration during boot, adoption, and admission. The deployment keeps image contents immutable. Path identity detects replacement of the object.

A confined binding requires a version 3 cgroup handle for startup. A confined stop request lacking that handle cannot take the legacy PID path. Placement verifies Workspace storage identity. Admission for new and existing bindings compares the resolved scope. Cleanup uses saved scope and the original cgroup handle after configuration changes.

The trusted boot protocol conveys the recipe. The Worker verifies the capability, configuration, and Workspace root and runs a bounded sandboxed no-op before attestation can succeed. The ready record exposes only the control endpoint. An authenticated attestation with matching identity gets the precise qualification failure, which the Java transport preserves. A failed qualification keeps context installation and tool admission sealed, returns `managed_runtime_confinement_unavailable`, and retains binding ownership. A later launch failure cannot retry the command through the ordinary executor.

## Tool admission and results

The Hosted Connector passes the saved confined profile during create, load, and recovery, including after startup is disabled. For a live attachment, the Harness enables only foreground Tool v2 Shell and checks the exact Broker capability before warm and tool admission. Harness and Java independently recognize the profile in lifecycle v2 negotiation. Cleanup attachments need neither warm nor current startup capability discovery. The control-plane gate and narrow Worker routes also prevent a downgrade by older Harnesses. Cleanup and cancellation use saved scope. Models see only the Shell declaration. Other names are refused before a reservation, extensible-tool resolution, or host helper action. The Broker and selected Worker each enforce the allowlist, including for direct Tool v2 requests. The saved Session cwd is `.`. Shell disallows directory selection, background execution, and monitor mode. The Harness skips file history binding and recovery and skips project instruction reads. Foreground Shell uses saved default or auto-edit approval, prompts for approval, and accepts answers only from the owner. The profile omits Plan mode and dynamic approval switching. Unsupported admission operations return `managed_runtime_confinement_denied`. Undeclared endpoints return the existing route-not-found response.

The confined Worker exposes attestation, installation, activation, and Tool v2 execute, result, cancel, and acknowledge endpoints. Activation release closes the logical Session without a Provider request. Provider dispatch, Tool v3/v4, file and revert, MCP, Hook, background and publication, extension, Monitor, and terminal endpoints are unavailable, including through a substitute Worker. Bubblewrap runs fixed `/bin/sh -c` as PID 1 in the new PID namespace. Bubblewrap reports correlated status after the namespace init exits, and Linux reaps the remaining namespace processes during exit. The Worker returns bounded v2 output for confirmed results. Ordinary nonzero exits are Shell results. A known pre-launch refusal can return a typed not-started v2 result. Interrupted, missing, or unreadable outcomes without evidence excluding execution stay unknown and cannot be replayed. Raw launcher diagnostics remain internal.

A future file or other tool must derive access mode from frozen admission, map admitted Workspace-relative paths into the private view, and use a trusted file Worker and interpreter from the immutable image. Review `Config.includeDirectories`, file history and revert, tool preparation, checkpoints, recovery, and executable-extension initialization. Hooks, MCP, extensions, and LSP stay refused until admission supports them. Verify the actual image and toolchain for each supported deployment. Typed refusals should help operators repair configuration or move inputs into the Workspace without exposing host paths.

## Session handback and retirement

A normal Turn can release its mount through live handback. As the Runtime Session enters RELEASING, the authenticated original Worker closes its tool and activation admission and checks for pending starts, active or unknown commands, and commands whose PID namespace reaping is unconfirmed. The Broker checks original registration and reads the descriptor-bound cgroup. It refuses handback if the Worker is not the only direct member or if child groups exist. A concurrent Turn can therefore block handback. This check supplements the Session fence and per-command namespace evidence. The ownership transaction locks the binding and Runtime Session and compares the exact versioned handle, generation, and RELEASING owner before clearing membership. Active or unknown work, missing or changed identity, additional members, and a missing Worker response retain ownership. Mount-only handback after a recovery block returns `workspace_writer_unproven` and leaves the Session active or RELEASING until there is proof for the original identity.

Terminal cleanup renews the matching claim, stops the original descriptor-bound unit, verifies `populated 0` and absence of the recorded Worker, then persists retirement and generates the existing receipt. The release transaction checks binding, generation, claim, and handle. UNKNOWN executions may block ordinary cleanup. A populated LOST unit follows fenced stop and reconciliation. Matching JOURNAL_LOST and WRITERS_STOPPED supply the existing alternative proof of stop for that unit. Unconfirmed stop retains ownership and returns `workspace_close_stop_unconfirmed` or an existing typed identity or recovery error. A same-name replacement cannot prove the original unit empty or receive a kill under its claim.

## Acceptance

### Core private root

On Linux, run the focused tests against the built Core adapter and relay plus `node --test scripts/tests/managed-private-root-bwrap-linux.test.mjs` as a non-root Worker with non-setuid Bubblewrap and static BusyBox. Record OS distribution, kernel, architecture, and Bubblewrap version. The environment must qualify and the cases must run.

- Use Workspace read/write positive controls while verifying that sibling and host sentinels are hidden, including via absolute and relative symlinks. Check image and Workspace read-only mode, fresh tmpfs on each launch, fixed cwd and environment, piped stdin, and a confirmed nonzero exit. Reject direct and symlink-alias overlap in both access modes.
- Start an outer process that stays live before and after the isolation check. Verify signal 0 and external listener connectivity as positive controls, then confirm the private check and absence of any received connection. Check that the parent environment sentinel is hidden and the payload cannot write the status descriptor. Show the outer process can create a user namespace and the inner process cannot nest one.
- Wait for a payload start marker, then abort with a background-promotion reason. Bound startup and settlement waits. Verify cancellation, interruption receipt, no background promotion, and relay control-directory cleanup. This covers local executor cancellation and cleanup.
- Verify refusal when the launcher is missing. Use a successful qualified payload and a host executable that can write a marker as controls. Confirm that a missing image executable or an unavailable namespace gives neither a confirmed exit nor a payload marker. Run namespace denial separately and check the kernel or bwrap diagnostic. Verify public `serve` still refuses the same sandbox setting.

These checks cover the exercised executor configuration. Hosted wiring, Broker stop and recovery, and additional deployment toolchains have their own acceptance runs.

### Broker stop and recovery

Use a dedicated test delegation, the real Linux provisioner, Broker, and Workspace transport, and a disposable MySQL catalog. Inspect the original Session's execution storage key and physical member count.

- Verify the Worker and a test descendant in a separate process session join before executing. Kill the Worker, confirm the descendant and a populated original unit remain, and reopen registration with a new provisioner. PID absence alone retains the holder.
- Bind-mount another live test cgroup over the original path. Verify both units stay alive with no receipt and no holder release. Restore the path and prove the original stops and empties before recording its receipt and releasing its holder. The sibling control remains alive.
- Verify the same proof before terminal drain of a live Worker, idempotent retry after leaf removal, no Worker side effect after a membership failure or gate EOF, compatibility with legacy registration, and the claim fence on a late stop. Record environment limits.

### Hosted end to end

- With the option disabled, preserve existing Hosted selection and result behavior. Refuse confined execution from ineligible placement or unmet prerequisites without switching to an ordinary Worker.
- Run a selected eligible Hosted Runtime against a real Linux private image and cgroup v2. Foreground Shell reads and writes its Workspace. Host and sibling sentinels, host environment, and network are unavailable. Prove a detached descendant started, closed inherited standard streams, and exited by confirmed command completion. Check typed qualification refusal and distinguish an ordinary nonzero exit, admission refusal, and uncertain execution.
- Verify Harness, Broker, and Worker refuse unsupported tools, cwd, background execution, and substitute routes. Replayed or stale identity cannot cross capability, generation, or configuration changes.
- An early handback retains the holder when the Worker has died and members remain. With terminal preconditions satisfied, the Broker independently proves stop. UNKNOWN work retains ownership. Missing or replaced units cannot issue a receipt for the original handle.
- Check that an existing ordinary Session can recover existing work during opt-in and cannot admit new execution. After restarting with the setting disabled, a confined Session's new execution is refused and cleanup still uses the original cgroup identity.
