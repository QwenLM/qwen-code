# 会话注册表中的 daemon 托管会话

[English](2026-09-09-daemon-sessions-in-directory.md) | [简体中文](2026-09-09-daemon-sessions-in-directory.zh-CN.md)

状态：与本文档一同实现。让 `qwen serve` 驱动的会话可以像其他会话一样被发现和寻址，并且可以发送消息。

## 问题

此前只有交互式 UI 会注册。daemon 驱动的会话对 `qwen sessions ps`
不可见，缺席于每个对端的 `list_agents`，并且无法发送消息：
`sendToPeer` 要读取本进程自己的注册表记录来获取回执地址，没有记录时
它会报告该功能未启用。一个用户开着终端、同时有 daemon 会话在同一个
仓库里工作时，两者完全无法对话。

有三个障碍。

### 一个进程、多个会话——却只有一条记录

注册表以 PID 为键，每个进程一条 `<pid>.json`。在"一个进程即一个
会话"的时代这完全正确。daemon 派生的 `qwen --acp` 子进程同时托管
多达 32 个会话，每个会话有自己的 id、名称和工作目录，一条记录无法
描述它们。

### 回执地址不再意味着"同一个会话"

发送路径和 `list_agents` 此前通过匹配会话 id **或**回执地址来把
"本会话"从候选对端中排除。地址曾是 id 的代理——在一个进程只持有
一个会话、只绑定一个 socket 的时代，这个代理是成立的。同一进程里的
多个会话共享一个收件箱，代理随之失效：发送会话的每个兄弟会话都会被
当作发送者自己过滤掉，同一进程内的会话彼此完全不可见。

### 未钉选的帧没有唯一答案

不携带 `toSessionId` 的帧曾经是可投递的：只有一个会话时，它只可能
指向那一个。而当帧到达一个持有多个会话的进程时，它什么也没指向。

## 设计

**每个会话一条记录，放在铸造的槽位里。**托管多个会话的进程为每个
会话写一条 `<pid>-<8 hex>.json`。后缀在注册时铸造，永不改变。它刻意
不从会话 id 派生：id 可能在存活会话底下被换掉（`/clear`、会话加载），
而自己改名的记录会让所有持有旧名字的读者 stranded——记录改为原地
修补（patch），这正是注册表对其他一切会话中途变更已有的做法。

记录的其他方面完全不变，这正是要点：后缀前面的 PID 是存活性检查、
清扫和命名空间防护读取的东西，所以铸造的记录与共享记录被同样地回收；
而太老、不认识新名字的读者只是看不到它（其文件名模式不匹配），而不会
把它误认为待删除的垃圾。

调用方指的是哪条记录由一个 `slot` 表达，贯穿 `patch`、`unregister`
和自身记录读取。`Config` 从注册本身得知自己的槽位，并把它传给每一次
排队的写入，于是会话的 `/clear`、`/cd` 和退出各自只触碰自己的记录，
不碰兄弟会话的。

**一个收件箱，靠帧区分会话。**进程绑定一个 socket，并把该地址写进
它拥有的每条记录。发送方通过它本就在每帧上钉选的 `toSessionId` 来
选择会话；指向本进程不持有的会话、或没有指向任何会话的帧，会被应答
`misaddressed`。按会话绑定 socket 会让文件描述符数量乘以会话数，而且
毫无收益，因为帧本身已经携带了区分信息。

**按会话 id 排除自己，共享地址时重新读取。**地址不再是身份的证据，
所以它退出了过滤条件。孪生会话——同一会话 id 运行在第二个进程下，
即 `qwen --resume` 所产生的那种——仍然被排除，因为这正是 id 能捕获
的。还剩一个窗口：id 过滤先于目录读取本会话的记录，而一次重命名修补
（`/clear`，或由 misaddressed 帧触发的重断言）可能落在两次读取之间，
让本会话的记录以新 id 重新混入候选。重命名时地址不会变，所以在相信
某个对端是兄弟会话之前，凡落在本会话自己收件箱上的对端都要对照记录
的新读取再核对一次——发送路径和 `list_agents` 都如此。

**入站一律拒绝，而不是挂起。**挂起是向人提出的问题，而没有人替
daemon 托管的会话盯着挂起消息列表：挂起会让每个发送方干等五分钟的
过期却一无所获。`refused` 会立即说明。挂起的消息*应该*在这些会话的
哪里浮现——ACP 客户端、daemon 自己的 API——是个真实的问题，回答它
是另一项工作。

**会话自己的设置打开消息功能时才注册。**交互式 UI 无条件注册，因为
它的记录还要回答"现在有什么在运行"。托管会话的记录存在是为了被寻址；
消息功能关闭时注册它，会在每个对端的列表里放上一个可以寻址却永远
不应答的名字。这个决定读的是会话自己的 `LoadedSettings`，而不是进程
的启动设置：一个进程可以托管来自多个工作区的会话，每个会话是否出现
在目录里——或保持不可见——由它自己的设置决定。

**第一个会话绑回收件箱，每条退出路径都关闭。**收件箱由第一个需要它
的会话绑定——没有会话的 ACP 进程没有什么可广告的。失败的绑定不算
"已启动"：下一个托管会话会重试，而迟来的成功会把地址扇出到进程已经
写出的每条记录。关闭同时注册为退出清理，并在两个拆解方法里运行，因为
裸信号两者都到不了；一旦关闭就保持关闭，重试不会在拆解之后复活
socket。在 `disposeSessions` 中，关闭在生成 abort 之后等待——缓慢的
排空不应让仍在运行的轮次在客户端已走后继续执行工具——又在记录拆解
之前，因为它扇出的地址清除是一次修补，记录必须还在原处。

传输层是刻意静态导入的。它自己的导入都位于 agent 现有静态闭包之内，
惰性加载省不了什么；而对 core 桶的动态导入会让该桶成为代码分割入口，
重新划分共享 chunk，可能把 ACP 快速路径不得加载的模块（iconv-lite 的
编码表）落到 agent 随后又静态导入的 chunk 里——启动 bundle 闭包检查
的存在正是为了抓住这种情况。

**每个进程一次绑定，每个会话各自决定。**收件箱为整个进程绑定一次，
由它托管的所有会话共享——但一个会话是否注册，是该会话自己的决定，
读的是其工作区加载的设置。agent 上的 `this.settings` 会被重新指向
正在处理的会话，所以这个决定通过 `createAndStoreSession` 显式穿线，
而不是从进程级快照读取。

## 取舍

**被直接杀掉的进程会留下记录。**下一次列表会清扫它，这与所有其他
会话一直以来的保证相同；优雅关闭会立即移除记录。

**`qwen -p` 仍然不注册。**以秒计的一次性运行多半只会贡献过期记录。

**仅出站。**托管会话可以发送，也能收到自己的回执；它不能做的是接收
消息。那是下一步，协议页面写明了这一点，而不是留给读者自己去发现。

**`kind` 仍是自我声明。**`serve` 来自 daemon 在其子进程上设置的环境
标记，进程自己也可以设置它。它只是列表的标签；没有任何东西依据它做
决定。

## 涉及文件

- `packages/core/src/services/session-registry.ts`——槽位、铸造的文件名，
  以及按槽位的路径捕获。
- `packages/core/src/config/config.ts`——记住会话的槽位，并把它传给
  每一次注册表写入。
- `packages/core/src/ipc/peer-send.ts`——读取发送会话自己的记录，按 id
  排除自己并在共享地址时用新读取复核，以及按收件箱地址限速发送。
- `packages/core/src/tools/list-agents.ts`、`send-message.ts`——把槽位
  传递下去。
- `packages/core/src/ipc/inbound-gate.ts`、
  `packages/cli/src/peerMessaging/peer-messaging.ts`——为托管多个会话
  的进程提供 `ownsSessionId`。
- `packages/cli/src/acp-integration/acpAgent.ts`——绑定收件箱，注册和
  移除每个托管会话的记录。
