# Managed email ledger registration-identity keying

- **Status:** proposed
- **Date:** 2026-11-20
- **Scope:** `packages/channels/email` (managed state store + adapter), tests
- **Related:** the WeCom P1-D/E fix (PR #17441), the DingTalk keying (PR #17742), and the GitHub keying (PR #17775); the shared `destinationKey` contract in `channel-base`; [Chinese version](2026-11-20-managed-email-registration-identity.zh-CN.md)

## Problem

The managed email state store keeps a single ledger file `managed-state.json` in the mailbox directory, keyed only by the configured mailbox (name + IMAP host/port/user/folder/address). A claim staged under one control-plane registration (tenant A) is therefore loaded when the same configured mailbox is restarted against a different registration (tenant B, or a different actor/workspace/cwd-relative within one tenant). The persisted pending event carries the UID and event text but no tenant identity; `resubmitPending()` forwards it through the HTTP client, which supplies the new registration's tenant header and channel id, so an event already admitted by A whose answer was lost can create an input under B. This is the same cross-ownership replay the WeCom adapter closed in P1-E and the DingTalk / GitHub adapters closed in #17742 / #17775.

## Current state

`ManagedEmailStateStore(name, cwd, settings)` reuses the Legacy `EmailStateStore` directory (`email-<digest(mailbox)>`) so the lock keeps one owner per mailbox, managed or Legacy, and writes `managed-state.json` beneath it. `load()` returns `undefined` on ENOENT and otherwise throws a single opaque "unreadable or invalid" error. There is no upgrade diagnostic: after the ledger is renamed, a pre-upgrade `managed-state.json` left beside it would be silently ignored.

## Design

Mirror the WeCom / DingTalk / GitHub shape exactly, with the email-specific lock and cursor semantics:

- **Store constructor** gains a fourth parameter `identityKey = ''`. The lock directory is UNCHANGED — it stays the Legacy mailbox directory (`email-<digest(mailbox)>`), so the lock still keeps one owner per mailbox, managed or Legacy; identity keying must not narrow that lock or split managed from Legacy. The ledger FILE beneath that directory is keyed separately by `ledgerKey = sha256(identityKey).slice(0, 16)`: `managed-state-<ledgerKey>.json`. A pending ledger staged under one registration is never loaded or replayed under another registration of the same mailbox. Credentials never define identity.
- **Adapter constructor** passes `options.controlPlane.destinationKey ?? ''` as the fourth argument. The `?? ''` fallback only spares non-persisting test doubles that omit the optional field; the production HTTP client always supplies it.
- **`load()`** splits the read / parse / validate arms, names `this.file`, and keeps the fs `{ cause }`, so an operator facing several `managed-state-<hash>.json` ledgers can tell which registration is unreadable versus merely invalid.
- **Upgrade diagnostic** — `strandedLegacyLedger()` reports a sibling pre-upgrade `managed-state.json` (path + pending/outbound counts + a `readable` flag + the legacy `lastUid` and `generation`), and `archiveStrandedLegacy()` renames it to `managed-state.json.stranded-<uuid>` (never deletes) once the start succeeds. Detection is NOT gated on the identity-keyed ledger being absent: a rollback to the pre-upgrade build can stage fresh claims into `managed-state.json` after a keyed ledger already exists, and those must still be reported. The legacy ledger is NOT adopted — adopting it would replay one registration's pending into another, the cross-ownership hazard the keying prevents. The outbound count includes only segments whose delivery status is UNKNOWN: a definitive accepted/rejected receipt proves the outcome, but an absent receipt — or one whose outcome is `unknown` — does not, so both still count. A parseable non-ledger (`{}`, `[]`, `null`, or an object without the pending/outbound arrays) is flagged unreadable too — an unrecognized file, not a loss-free 0/0. The notice's loss clauses are reporting gates keyed on the cursors, not on load-ness, so the retry after a first start that failed once `openMailbox` pinned a fresh ledger to the tip still reports a permanently skipped window. The inbound "does not re-fetch them" clause fires when no ledger was loaded OR the loaded cursor sits at/above the legacy cursor (`loaded.lastUid >= legacy.lastUid`): the staged claims sit at/below that cursor, below the search floor of cursor + 1. The offline-window clause uses a STRICT `>` (`loaded.lastUid > legacy.lastUid`): the window begins at legacy cursor + 1, so at equality the next poll admits that mail and claiming a loss would be a false alarm. A roll-forward whose keyed cursor still sits below the legacy cursor re-fetches the window and is told no loss. The cursor itself is never seeded from the legacy.
- **Generation seed** — a fresh ledger starts at `generation: 1`, but the control plane's `account_generation` never moves back (`JdbcChannelInstanceStore` fences a lower one with `channel_generation_stale`) on a `(tenant_id, channel_id)` row that EVERY registration identity of the mailbox shares. A mailbox that already re-keyed (a UIDVALIDITY change incremented and persisted `generation`) would register a lower generation after the upgrade and be refused on every start, so managed email would never come up again. The counter is healed to the highest safe-integer `generation` durable anywhere in the mailbox directory — the live legacy, every sibling identity-keyed ledger, and the `.stranded-*` archives (`highestSiblingGeneration()`, mirroring the GitHub store's entry-scoped `entryWatchEpisodes` carry) — and the healing happens BEFORE any register, in both places a generation is established. `openMailbox()` clamps a fresh ledger to `max(1, highWater)` and an epoch-changed ledger to `max(generation + 1, highWater)`, so a ledger that missed several epoch changes while down jumps to the row instead of registering a `+1` that is still below it and being refused before any later seed could run. `connect()` then heals a loaded ledger whose epoch already matches but whose generation still lags the row. Reading the archives and siblings, not just the literal legacy, is what lets a SECOND registration meet the high-water after the first archived the legacy. The heal only raises, never lowers, so it is idempotent on a current ledger. Because the row is monotonic and `>=` every sibling generation, a staged claim below the high-water is already dead — its generation can never be registered — so healing drops it visibly (a log line names the count, mirroring the epoch branch) rather than re-offering it at a raised generation, which would change its dedupe key; this also gives a lagging ledger with staged claims an exit instead of a permanent `channel_generation_stale` wedge. A non-integer or out-of-range value is not carried: the state validator requires a safe integer `>= 1`, so seeding one would persist a ledger the next `load()` rejects, bricking it. An unreadable generation source contributes nothing to the number but its path is returned and logged, never dropped silently. This is the one exception to no-adoption: the generation is a counter the control plane already knows, not pending/cursor state, so healing it adopts no live claim and a fresh ledger still starts at the mailbox tip with empty pending.

### Upgrade consequence

The ledger file is renamed from `managed-state.json` to `managed-state-<ledgerKey>.json` with **no adoption of pending or cursor state** (the monotonic `generation` counter is the one exception, seeded back so a previously re-keyed mailbox still registers — see Design): the first restart after upgrading starts on a pristine identity-keyed ledger. A claim that was staged (persisted) but not yet admitted is stranded — the control plane never saw it (only `submitInbound` makes a claim visible), so only this client's own ledger could re-drive it, and the new ledger does not contain it. Unlike DingTalk's acked stream, email does not ack a frame to the provider; the loss comes from the cursor: a fresh ledger's `openMailbox` sets `lastUid = mailbox.uidNext - 1` (the current mailbox tip), so the stranded claims' older UIDs are below the fresh search floor and are never re-fetched. The same reset drops the dedupe window (`recent`), the reply routes, and the un-receipted outbound segments. This is the deliberate stranding tradeoff the WeCom / DingTalk / GitHub designs record.

The notice names the inbound and outbound consequences separately (an outbound-only strand does not report lost inbound mail), and an unreadable legacy is reported with `unknown` counts and an explicit "any staged claims it held are stranded" warning, never a quiescent empty ledger. Even a quiescent 0/0 legacy with a cursor gets an independent clause naming the skipped offline window — mail received after the legacy `lastUid` and before this start was never listed and will not be admitted — because the fresh tip cursor drops that backlog; a genuinely cursor-less 0/0 legacy reports no loss. The inbound and offline-window clauses are emitted only on a fresh window (no ledger loaded, or the loaded cursor already at/above the legacy cursor), so a roll-forward after a rollback whose keyed cursor still re-fetches the legacy window is not told a loss that does not happen, while the retry after a failed first start (whose ledger is already pinned to the tip) still repeats them. The archive is deferred until the start succeeds (after mailbox open, the generation seed, registration, and the ownership re-check), so a failed first start leaves the legacy for a rollback to recover; a second log line names the archived path. A failed archive rename is logged and leaves the legacy in place (degraded, never a startup failure).

The reverse direction is bounded too, and for email it is worse than a fresh start: after a successful upgrade `archiveStrandedLegacy()` has renamed `managed-state.json` away, and the pre-upgrade build reads only that literal name. A rollback therefore creates a fresh `generation: 1` ledger and is refused `channel_generation_stale` for as long as the shared `(tenant_id, channel_id)` row sits above 1 — the channel stays down for the duration of the rollback, and the generation survives only inside the `.stranded-<uuid>` archive, a name no build reads. Recovery is to restore the archived ledger as `managed-state.json` (or reset the control-plane row). The claims themselves are not destroyed — the identity-keyed ledger keeps them and a later roll-forward reloads them.

- `packages/channels/email/src/managed-state.test.ts` and `managed-email-adapter.test.ts` — keying, isolation, stranding, offline-window, generation-seed, corrupt-legacy, archive, ownership-during-connect, and failed-start archive witnesses.
- This design doc and its Chinese version.

## Scope boundaries

- The email IMAP polling, admission/outbound discipline, mailbox-epoch re-key, and instance-scoped stall are unchanged. Only the ledger file name, the generation seed, and the upgrade diagnostics change.
- The lock stays the shared Legacy mailbox lock deliberately: identity keying adds cross-registration ledger isolation without narrowing the one-owner-per-mailbox lock or splitting managed from Legacy.
- No control-plane (Java) change; no `channel-base` contract/API change (only the `destinationKey` doc comment is updated to list email).
- The email store has no PR-watch, so there is no episode carry (unlike GitHub).
- The stranding diagnostic covers only the pre-upgrade `managed-state.json`. After the upgrade, a registration-identity change (a new actor/workspace of the same mailbox) abandons the previous registration's identity-keyed ledger (`managed-state-<hash>.json`) — pending claims included — with no notice, since `strandedLegacyLedger()` only stats the literal `managed-state.json`. This is the same gap as the WeCom / DingTalk / GitHub siblings, tracked as item 1 of #17769 and not implemented here; the diagnostic should not be read as covering every stranding case.
