# 验证存在歧义的 Linux Workspace 出生时间

[English](managed-workspace-birth-time-verification.md) | [简体中文](managed-workspace-birth-time-verification.zh-CN.md)

## 问题与范围

Issue #14453 记录了原生 Workspace 注册失败：发布存储 marker 时修改目录 mtime，可能与目录创建发生在同一个内核时钟 tick。第二次身份读取将合法的 `creationTime == lastModifiedTime` 误判为 JDK 可能用 mtime 替代出生时间。生产 Workspace 创建使用同一流程。

本次只修改原生 Linux 身份验证。注册、恢复、迁移与退役的现有调用通过共用身份读取器获得修复。注入的读取器、macOS、SSH 存储、持久化身份字节及 SQL 所有权检查保持现有契约。

## 决策与安全契约

非正创建时间仍然拒绝。正创建时间与 mtime 不同的情况沿用现有路径。只有正值且相等时，才直接对同一个规范根目录调用 `/usr/bin/stat`，不经过 shell。GNU stat 在 `LC_ALL=C`、`TZ=UTC` 下返回 `%d|%i|%w`。

原生 device 与 inode 必须和已读取的 JDK 值相同。出生时间由 JDK 严格日期时间解析器解析，并与已读取的创建时间精确匹配至纳秒。未知出生时间、格式错误、身份或时间戳不匹配、命令失败、超时、中断均安全拒绝。进程限制为五秒、输出限制为 256 字节；退出时终止进程并关闭流，中断时恢复线程中断状态。

持久化出生时间仍为原有 `FileTime.toInstant().toString()`。如果只比较整秒，同一秒中的替代 mtime 或复用 inode 就可能冒充已记录身份。没有原生证据便放宽相等检查，会移除对缺少出生时间的文件系统的保护。

该方案不创建探测文件、不缓存跨挂载能力、不在身份读取时修改目录，也不加入重试或 sleep。修复 marker 发布竞态不需要修改现有创建时间变通逻辑。

## 约束与风险

存在歧义的 Linux 身份现在要求 `/usr/bin/stat` 处有 GNU stat。可执行文件缺失或文件系统无法提供可验证出生时间时，注册与恢复继续不可用。只在时间戳存在歧义时执行探测；延迟有界，但本次未测量。现有文件系统所有权与可信主机假设继续适用。

## 验证与验收

现有原生注册回归用例会在验证前将 mtime 显式设为实际出生时间。第二个 guard 实例应接受原目录、容忍后续 mtime 变化，并拒绝 marker 篡改或携带复制 marker 的替换目录。旧的相等检查会确定性拒绝这个强制相等状态。

定向证据解析用例接受完整身份一致的结果，拒绝 device、inode、纳秒、缺失出生时间、非法日期及输出格式错误。Java 模块验证与原生 Linux/MySQL 验收仍然需要执行；仅通过解析用例不能证明生产注册可用。

编写本次修改时没有执行本地 build 或运行时验收。已有 Linux 失败仍归属于 issue 作者；新的复现尝试因执行环境缺少前提而受阻。验证结果必须与本设计分开报告。
