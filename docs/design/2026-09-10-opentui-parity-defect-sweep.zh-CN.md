# OpenTUI 一致性缺陷清扫 —— 与 ink 的逐帧实机验收

[English](2026-09-10-opentui-parity-defect-sweep.md) | [简体中文](2026-09-10-opentui-parity-defect-sweep.zh-CN.md)

本文是 OpenTUI 迁移第十批之后那次缺陷清扫的设计文档。迁移曾依据单元测试与
集成测试全绿被宣告完成，但把运行中的渲染器与 ink 并排一看，界面并不像同一个
产品：没有 banner、footer 对不上、各种 loading 状态缺失。这三块已另行恢复；
本文覆盖的是在它们背后由系统化逐帧对比发现的问题，以及由此产出的修复。计划
段落与滚动维护的缺口台账见
[#8662](https://github.com/QwenLM/qwen-code/issues/8662)。

## 问题

代码正确性已被证明，观感等价性没有。两个渲染器共用命令层、工具层与历史模型，
所以一个断言状态的测试在两边同样通过，而它们画出的屏幕却在分叉。以下三组缺口
全部来自真实 pty 上的观察，而非从源码推断：

1. **确认框替用户做掉的决定。** 所有工具确认都从同一份通用四行列表里回答。
   always-allow 行不说自己允许的是什么；在未受信目录里也照样提供，而那种场合
   根本不该把持久规则摆上桌；plan 与 edit 两类确认则直接给错了结果集合。这些
   背后还有一个静默的进程级故障：每个 OpenTUI 会话都失去了基于 AST 的 shell
   分析，于是权限规则返回为空，命令安全性分类退到保守兜底。
2. **对不齐的外框。** footer 把状态行截成一行；loading 指示器宣称有一个从未
   被任何调用方提供的 token 估算；弹窗从终端一边铺到另一边；补全下拉在计算列
   宽时没有算上它从未填充的来源徽标；footer 宣传了 Shift+Tab，而它没有绑定。
3. **本渲染器从未产出的会话行。** context 文件公告、扩展刷新提示、model 对话
   框的取消提示在 ink 里都存在并且进了 transcript；在这里要么从未发出，要么发
   进了一个不画任何东西的通道。另有两张字形表是被复制而非被引用的，而副本已
   经与 ink 的呈现选择符后缀发生了漂移。

第四组是在修前三组时发现的，属于结构性而非外观性：被移除的布局 prop 不会被
渲染器的 reconciler 复位，于是对话框与 composer —— 两个占据同一槽位的
`<box>` —— 互相泄漏了彼此的 margin 与 width。

## 方法 —— 观察通道是重建后的屏幕，并按序列比较

原始 pty 字节无法直接 diff。一个就地重绘的渲染器会发出光标寻址、擦除与不完整
单元格，于是同一块屏幕会到达为两条不同的字节流，而两块不同的屏幕也可能到达为
同一条。因此 harness 让每个渲染器在 pty 下跑同一段脚本化场景，在每个声明的检
查点重建屏幕，并把重建结果写成定宽文本。比较发生在重建结果上。

每个场景跑两遍，每个渲染器一遍，使用同一个 bundle 与同一组启动参数；检查点由
场景声明而不是按定时器采样，所以两腿是在脚本的同一位置被抓取的，而不是在同一
墙上时刻。二十七个场景覆盖启动、窄终端、输入与补全、`@` 补全、流中指示器、自动
放行下的工具执行、工具确认、slash 对话框、审批模式循环、自动模式启动提示、错误
路径、resize、clear 与退出、一次会遍历 loading 短语的长按、待办卡片、单独一个
问题的提问对话框、同一个对话框跨三个问题并带多选与手打答案、把那条手打答案改到
值的中间、同一个对话框在窄到会把标题截断的终端上的标签行、审批模式变化时被拦下
的确认框的释放、启动时对受门禁服务器的审批、一次参数长到会被截断的工具调用、把
同一次调用在关掉参数行的情况下重跑的对照臂、一份长到溢出终端的回答、在溢出部分
上滚下去再滚回来、两行宽到足以展示折行发生在哪一列的回答，以及一个把两个调用同
时停在审批上的回合 —— 于是第一个要排在第二个的对话框后面。

比较方式有三个性质决定了结果该怎么读。

**垂直锚定是重建方式的属性，不是两块屏幕的属性。** 本渲染器画的是一个终端大
小的窗口，会话尾部落在输入行之上。ink 的 live 区在真实终端里占据同一个位置，
但 harness 是依据 ink 写出了什么来重建它的屏幕的，于是那块内容落在哪里取决于
ink 自己的重绘：在一个高对话框之下，重建结果里对话框占第 6 到 25 行、窗口其余
部分留空，而本渲染器会把同一个对话框贴着最后一行放。因此绝对行号在两腿之间通常
仍然对不上，按行号对齐的 diff 会报告重建方式而不是被测缺陷。比较会先去掉空行，
再用最长公共子序列对两个序列做 diff —— 这对块落在哪里不敏感，对块里有什么敏
感。当内容刚好填满窗口时两个序列确实重合：决定 26 的溢出臂就是逐行比较而不是
按序列比较的。

**归因之前需要对照臂。** OpenTUI 腿跑在与 ink 腿不同的运行时上，所以任何分叉
都同时是「渲染器干的」和「运行时干的」两个候选。在这个歧义要紧的地方，加了第
三条腿：让 ink 跑在 OpenTUI 的运行时上。它在 ink 上复现了缺失的 shell crawler
诊断，于是那条发现被移出了渲染器一栏；它没有复现缺失的扩展刷新提示，于是那条
留在渲染器一栏。

**场景等待所用的通道不是它比较所用的通道。** 到达一个检查点的办法是等待脚本
预期看到的文本，而这个等待扫的是字节流。整行重绘的渲染器能满足它，因为整行是
连续到达的；只重绘变化单元格的渲染器永远不能满足。一个就地从一种措辞改成另一
种的对话框问题，到达字节流时只剩互相差异的那几个单元格，于是等待会在一块其实
已经正确的屏幕上超时 —— 以这种方式失败的那一腿确实画出了它在等的那一行，而字
节流里只携带了它的五个单元格片段。现在等待除了扫字节流也会轮询重建结果，两个
通道一致了。先读字节流并不是冗余：它便宜，而且仍然能看到已经滚出重建窗口的文
本。

## 决定 1 —— 确认框按类型问 ink 的那个问题

对话框现在根据确认自身的类型构造选项列表，而不是一律用同一个形状。执行类确认
会说出它即将允许的命令根，于是「always allow」讲清了之后会覆盖什么；plan 类
确认提供恢复它所替换掉的审批模式；edit 类确认提供 edit 真正支持的会话级
allow-always，而不是它并不支持的 project/user 持久化结果。在未受信目录里，
持久作用域的行会被收起，因为给一个用户尚未信任的工作区加权限规则，不该由对话
框摆到用户面前。各行重新编号，数字键可直接选中，与内联提示一致。

## 决定 2 —— shell AST 解析器必须在渲染器启动前预热

渲染器的构造函数会装一个裸的 `globalThis.window` 来挂它的 animation-frame
垫片。解析器的 UMD 包装在首次求值时会探测 `window.document.currentScript`，
所以那之后的第一次动态 import 会抛错 —— 而解析器会把这个失败锁定到进程结束。
因此 import 被提前到启动阶段强制执行，那时 `window` 仍未定义，早于任何渲染器
构造。

这需要 core 包出一行：在其 index 上加一个再导出，让启动路径能拿到预热 helper
而不必深层 import。解析器在其他所有地方仍是动态 import，所以 deferred-runtime
不变量未变。也因为这个原因，该改动单独成一个提交 —— 它是本次清扫中唯一跨进
core 的编辑。

## 决定 3 —— footer 保留 ink 的状态行，loading 指示器拿到真实估算

状态行改为在两行预算内换行，而不是截断成一行，于是窄终端会像 ink 一样把 model
段推到第二行，而不是丢掉它。提示行仍然截断，因为一个能长高的行会在回合中途改
变 footer 尺寸，把 composer 在用户光标底下挪走。提示行还承载了 composer 不再
绘制的审批模式名：ink 把这段文本用作无障碍标签而不是可见行，而本渲染器没有无
障碍表面，所以这段文字必须在某处可见，否则哪儿都没有。

loading 指示器把字符计数器与 receiving 标志声明成了没有调用方设置的 prop，于是
它的输出 token 估算被钉在 0，方向箭头永久朝下。两者现在都来自 live turn，并按
ink 的方式统计模型文本、思考与工具调用参数，在工具结果回传模型时退回 waiting
阶段。

## 决定 4 —— 下拉列宽是推导出来的，Shift+Tab 是 shell 级绑定

下拉的标签列跟随正在补全的模式。slash 列表共享一个半宽列以便描述对齐；文件列
表不共享，因为 ink 只在某行带有需要对齐的描述时才共享列，而把一条纯路径钳到半
宽会把它在词中间折到第二行。行预算也把「下拉把自己的侧边 margin 嵌在 composer
的 margin 里」这件事算了进去，此前这给描述多留了两列，把它的尾巴折了行。

标签与它的参数提示此前被拼成了一个串，于是一个对列宽而言过长的提示会把整串词
换行，把该行撑到三行。它们现在作为独立子元素布局，并在列边缘断开，于是续行落
在提示自己的偏移上。

Shift+Tab 此前未绑定，所以 footer 宣传了一个什么也不做的快捷键。绑定放在 shell
而不是 composer：ink 把它的模式指示器挂在 app 级，只对一个 tab 视图禁用，所以
当对话框或确认让 composer 未挂载时，循环仍然可用。composer 只保留 Windows 的
裸 Tab 兜底 —— 那是唯一需要知道 Tab 是否已经被用于接受补全的路径。循环顺序取
自共享的模式列表，而不是枚举声明顺序的副本，所以不会与 ink 走的顺序漂移。

## 决定 5 —— 自动模式提示的门禁放在两条进入路径的汇合处

ink 把自动模式的进入提示门禁在「会话尚未持有该模式」上。轮换永远不会违反这一
点，所以该守卫在这里看起来是冗余的，就被省掉了 —— 但审批模式对话框打开时已经
选中了当前模式，所以一次裸 Enter 就是重新选择它。首次提示能在重选中存活，因为
它在 settings 里被确认过；而列出自动模式剥掉了哪些 allow 规则的那条提示不能，
于是每次重选都会重印。门禁现在放在两条路径的汇合处。

## 决定 6 —— 弹窗取得 ink 的几何，help 对话框取得一个可翻页的窗口

此前每个弹窗都从终端一边铺到另一边，而 ink 给弹窗加了两列 margin 并限制了宽
度，于是一条边框从第 2 列跑到第 97 列就停了。包装层现在提供这两者，这正是让一
个对话框读起来像对话框、而不像全屏模式的东西。确认框刻意留在它之外：它们的正
文会测量终端宽度来估算文本如何折行，所以在不缩小该测量的情况下缩小盒子会破坏
这个估算。

help 对话框此前打开在它的命令列表而不是概览上，其 tab 键也与 footer 宣传的不
一致。现在概览是起始 tab，Tab 与 Shift+Tab 按提示承诺的两个方向循环，方向键与
翻页键移动命令窗口、并在没有命令窗口的 tab 上不生效，此外没有任何键会关闭或导
航 —— 此前裸字母键会关闭对话框，意味着一个打字错误就把对话框关掉了。

那个命令窗口此前无论终端多高都固定十八行，而这比正文预算在扣掉该 tab 自己的
引导行、其间距与滚动提示之后所剩的要多。溢出此前的解决方式是丢掉引导行下的间
距并把滚动提示整个裁掉，于是提示所报告的滚动位置干脆不存在。窗口现在按扣掉这
些装饰后预算所剩来定尺寸，翻页按屏幕上真实存在的窗口移动。在低于 42 行的终端
上，这显示的列表比 ink 短，这是较小的损失：ink 保留它的十八行，改为裁掉提示。

model 对话框此前把它的详情分隔线画成二十字符宽，而 ink 是满宽的；并且在一个
model 的标题下不显示任何行。ink 把 runtime 与 discontinued 标记同时折进标题
与行描述，所以一个自身无话可说的 runtime model 仍会得到一行解释；条目现在带上
了它，而分隔线被按框内宽度写满，因为这里没有单边框可以用来画一条。

## 决定 7 —— 工具的流式输出是累积快照，不是增量

承载工具输出的流事件此前被塑造得与它旁边的 text、thinking 增量一样，于是消费
方做追加。但调度器并不流式发增量：它在每个 chunk 上发出到目前为止的整个显示
内容，然后发一个同样携带整个显示内容的最终结果，所以追加会把输出的尾部画两遍。
该事件被改名以说明它承载什么，卡片改为替换而不是累积。

折叠这些事件的 reducer 没有生产调用方 —— 只有它自己的测试文件。这早于本次清
扫；改名迫使了这次编辑，而把该 reducer 接线或移除不在本文范围内。

## 决定 8 —— transcript、composer 与 footer 共用同一个内缩

ink 用同样的两列内缩它的会话、composer 与 footer。这里 transcript 没有内缩，
而 composer 与 footer 各有一个，并且 composer 的外框比 ink 的右移一列、窄一
列。三者现在取同样的内缩，composer 在其上方保留一行间距 —— 那正是把一条已提交
的提示与在它下面到达的回答分开的东西。

## 决定 9 —— 错误行是一行，用 ink 那个字面十字

错误行此前是两行堆叠：消息，然后提示在下面。ink 渲染一行，提示以括号内联，且
其前缀是 U+2715 的字面十字，而不是共享图标表里的 U+2716 —— 两个字形差一个码
点，视觉上可区分，所以在这里引用那张表会是错误种类的复用。该行被压平，提示作
为次色段内联，前缀保持字面量，并加注释说明它为什么不是那个共享常量。

## 决定 10 —— 已武装的退出警告占据 footer 的提示槽

两次按键退出的警告此前画在 transcript 里、composer 之上，于是用户被告知再按一
次 Ctrl+C 的地方，正是他们没有在看的地方。ink 把该警告交给 footer 的底部提示
槽，并在警告期间把状态行门禁掉，所以它就贴在 composer 下方、上面什么都没有。
footer 现在把警告作为 prop 接收，并只返回那一行，按它所替换的提示的同一预算截
断。排队消息段是那个提示的兄弟而不是它的一部分，所以在警告武装期间它仍然可见。

把警告搬进 footer，也把它交给了 footer 自己的那道门禁 —— 该门禁会在对话框、
modal、工具确认或补全下拉出现时把整个 footer 隐藏掉。警告要越过这道门禁。在这里
对话框会让 composer 卸载，所以没有人拦截 Ctrl+C，守卫照样武装；若仍受门禁，第二
次按键就会退出，而那条警告从未上过屏。

做兄弟这件事同时也决定了分隔符。ink 把该徽标渲染成一个独立的文本节点，其内容以
一个字面空格开头，所以这一行读起来是一个空格，而 ink 自己那条提示的各个段之间用
的是 `' · '`。徽标参与的两处拼接 —— 提示行与已武装的警告行 —— 都用单个空格。模式
段保留它内部的 `' · '`，那正是 ink 在那条提示的各段之间所用的。

## 决定 11 —— 被移除的布局 prop 不会复位，所以两个分支需要 key

渲染器的 margin 与 width setter 会忽略它的 reconciler 为被移除 prop 传入的
`null`。对话框分支与 composer 分支都是同一槽位里的一个 `<box>`，所以没有 key
时 React 会复用一个实例并 diff props —— 而上一个分支的布局就卡在了节点上。打
开对话框会留下 composer 的 margin；关闭它会留下对话框的 width。两个分支现在都
带显式 key，而那个必须被放弃而不是被替换的宽度，改为设成它的 auto 值而不是被
移除。

只设置过某个 prop、或只移除过某个 prop 的站点不受影响，这些点被排查过而没有改
动 —— 这个判定在工具卡片的标题上没有成立：折叠分支会设一个展开分支从不设的宽度，
由决定 50 更正。没有添加渲染器级测试：该行为位于 reconciler 内部，复现它需要一个真实渲染
表面，而 pty 矩阵已经覆盖了这一点。

## 决定 12 —— 字形表是引用的，不是复制的

此前有两张状态与消息字形表被复制进了本渲染器。两者都由 ink 的常量模块导出，而
且两份副本都已漂移：消息图标缺了 ink 为强制文本呈现而追加的呈现选择符（那些字
符默认是 emoji 呈现）。副本被删除，改为引用 ink 的表 —— 这才是让漂移不可能发
生、而不只是被修好一次的做法。这些选择符在源码里不可见，所以断言它们的测试用
注释说明了这一点。

## 决定 13 —— ink 会画而本渲染器不画的三条提示

扩展刷新提示此前从不出现，因为 watcher 在启动期间就上闩，早于本渲染器挂载，而
上闩不会重发：只订阅就会丢掉那条告诉用户去跑 `/reload-plugins` 的提示。现在
订阅时会重放该闩。重放以闩的持有者为键，而不是以构造为键，因为 shell 会在其
host 身份变化时重建它的 dispatcher，而该闩比这次重建活得久 —— 没有这个键，提示
会每次重建打印一次，帧把它抓成了两条相同的行。

context 文件公告在 ink 里是一次性闩：文件在整个会话期间都挂着，所以它只在第一
次真正到达模型的提交时公告，而不是每次提示都公告。ink 在三处重新武装该闩 ——
session id 变化、history 被替换、清屏 —— 因为这三者都会抹掉已发出的行，而文件
仍然挂着。这三者在这里都汇流到同一个点：可见 transcript 被清空或被替换，所以
重臂就放在那里。ink 那条替换 history 的重臂路径还会把闩与回放内容做协调；这一
点没有移植，因为本渲染器的 resume 回放根本不携带 info 行，那会让这个协调成为一个
永久为假的分支。

model 对话框的取消提示此前被发进一个不画任何东西的反馈通道，而不是 transcript。
它现在作为 transcript 行落地，与 ink 的「kept model as …」一致。

## 决定 14 —— 行的字形前缀不可被压缩

带字形沟槽的 transcript 行把沟槽做成消息旁边的独立 flex 子节点，而这正是折行后
的消息能获得 ink 那种悬挂缩进的原因。该子节点默认可压缩，而当消息的首个折行刚好
填满该行时，发生的正是压缩：在 60 列下，warning 行在一个 56 列的盒子里量出 57
列，它的前缀被压到 1 列，于是字形后面的空格消失，续行起点比它上方那条 info 行
（有 2 列余量、因而从未被压缩）左移一列。

前缀现在不可压缩。同一帧随后在盒子里量出 55 列，保住了空格，续行也与 info 行一
起落在 ink 的那一列。这是靠重建并重新抓取验证的，不是靠阅读代码：两行只在消息长
度上不同，所以那条被压缩的行正是那条没被压缩的行的对照。

ink 原来也这么做。它的共享状态渲染器把前缀放进一个独立的行子节点，给了它显式的
宽度与显式的不可压缩标记，再让消息占据剩余空间——这正是上面那组测量所重建出来的
排布。所以这不是绕开某个布局引擎默认值的权宜之计，而是参照实现里一处没有被移植
过来的部分；帧证据与源码如今互相印证。

修复应用到 transcript 里使用这一形状的四种行 —— info、warning、error 与 away
recap，最后一种有两个固定前缀，因此两处都要标记。刻意不应用到统计与鉴权对话框里
对应的前缀：它们位于定宽带框盒子内、有自己的宽度预算，那里的抓取没有显示该缺陷，
改动它们属于未经验证的编辑。

## 决定 15 —— model 对话框的三道关闭守卫

在没有选中项的情况下关闭 model 对话框时，每一条关闭路径都会播报那个存活下来的模
型。这把 ink 分开的几种结果混成了一种：离开一个辅助选择器 —— 语音、视觉、压缩、
图像或 fast 模型 —— 也会播报；而第一次 Escape 之后的第二次 Escape、或者落在切换
正在应用期间的那一次，会再播报一遍。

ink 用三份状态守卫这条播报：一份记录切换已提交的标志、一份记录关闭路径已经跑过
的闩锁、以及一份覆盖那个 await 的进行中标志。当闩锁或进行中标志任一被置位时，关
闭路径提前返回；只有在主选择器下、且没有任何东西提交过时才播报。本渲染器现在带着
同样的三份状态与同样的提前返回，而它的辅助判定是「该选择器的模式不是主模式」的
否定式 —— 覆盖的正是 ink 枚举的那五种模式，因为模式是必填字段，不可能静默漏过。
三者都不复位：对话框关闭时这个挂载点会卸载，所以重新打开是从全新状态开始的。

三者中有两者还守卫选取本身：ink 的选取处理器在切换正在应用、或已经提交过时提前
返回，因为在第一次应用落地之前再按一次 Enter 会启动第二次切换，而两次都会播报。
在关闭路径上闩锁总是先触发，所以那个提前返回才是已提交标志真正决定结果的地方。

播报本身也从 shell 的 notify 槽挪进了 transcript。ink 把这个对话框的三种结果
—— 一次选中、一次 escape、一次辅助选中 —— 全都写成 transcript 行，所以行会比
对话框活得更久；而 notify 槽是对话框区域内的一条裸行，随对话框一起关闭。

## 决定 16 —— transcript 条目保留 ink 的按类型上边距

这里的对话行是一条挨着一条打印的，而 ink 会在大多数行的上方留出一个空行。比对工装
此前把这件事抹平了：它把每一帧归一化为一串非空行，于是一次抓取可以在两个渲染器对
条目之间的每一处纵向间距都持不同意见的情况下，仍被报告为逐字节相同。三十九次比对
过的抓取里有十四次的空行总数不同，但这个数字本身不可用 —— 在底部锚定下，本渲染
器把一整块大空白停在输入框上方，而 ink 把它的空行留在屏幕底部。只度量 transcript
区域、并把结果表示为空行与内容行的游程模式，才能把它隔离出来：在四个带有已完成轮
次的场景里，ink 读作 `b1 c5 b1 c1 b1 c1 b1 c2`，而本渲染器读作 `c7 b22 c2` ——
一段不间断的内容游程。

ink 按条目类型决定这个边距。它的 history 渲染器对模型轮次和思考各返回一行，对一
份显式列举的状态、工具、提示与用户行返回零行，对其余一切默认返回一行。用户行经由
另一条路径达到同样的总量：history 渲染器给它零，而它自己的消息组件在内部声明了
这个边距。shell 行与两张 arena 卡片不在那份显式为零的列表里，因此走默认值。没有
首条目或末条目的抑制，静态区、待定区与滚动区渲染的都是同一个组件、带着同样的边
距，所以这条规则在全屏是统一的。

本渲染器现在把每个条目包进一个携带该边距的盒子，边距由它的 kind 解析得出：用户
行、助手行、思考、shell 行与两张 arena 卡片为一行；其余一切为零行。有两个 kind
在 ink 里完全没有对应物。task 卡片是本渲染器自己的形状 —— ink 把子 agent 渲染成
派生它的那个工具，走的是为零的那个分支 —— image 行同样是本地形状，因为 ink 把图
像画在携带它的那条消息内部。两者都给了零行，好让它们与身旁渲染的那条工具行保持
齐平；这是一个判断，不是对参照实现的解读，如果这两种形状将来获得了 ink 对应物，
应当随之调整。

边距位于外层包裹盒上，而按条目的行数上限作用于条目自身的内容，所以两者是相加的：
上限不会吃掉分隔行，分隔行也不会导致某个条目被裁切。

## 决定 17 —— 审批模式切换要释放那些它本不会拦下的调用

轮换进入一个自动审批模式后，确认框仍留在屏幕上。按键与对话框两条路径都汇入同一个
采纳点，而那个点只设了本地模式、播报了一次进入 auto 模式，然后就停了：一个已经停在
确认框后面的调用，会停在一个根本不会去问它的模式下面。

ink 把切换与释放配成一对。进入那个什么都批准的模式会确认每一个停着的调用；进入只批
编辑的模式只确认编辑类工具；而被标记为从不提供「始终允许」的调用则被放过，因为那个
标记意味着这道问题存在的意义就是由人来回答。这条选取规则在这里其实已经被移植过来
了，连文档字符串与单元测试都在 —— 它只是没有调用方，所以本渲染器有了规则却没有行为。

采纳点现在会跑这条规则，对每个被选中的调用确认一次，然后上报已结算，让入口把那一行
去掉。有两处细节与参照实现不同，且是刻意的。释放在确认时不逐个等待，而 ink 会一次一
个地 await，以避免一批并行调用乱序结算；在只有一个停着的调用时 —— 那也是任何场景唯
一会产出的情况 —— 两者等价，而且本渲染器在退出级联上本来就是不等待地结算一个停着的
调用。另外，无论确认是解决了还是抛错了，那一行都会被去掉，因为一次被拒绝的确认否则
会把模态框留在一道再没有人会应答的调用上面。

## 决定 18 —— 已提交的思考要报出自己的耗时，而它提示里写的那个键要真的被绑定

折叠的思考行打印了一条按键提示，而那个绑定并不存在。本渲染器里每一个键盘处理器都被
清点过，没有一个接这个键；那一行自己的点击确实能切换，但提示的 clickable 分支是关
的，所以唯一能用的那个可供性，恰恰是那一行从不点名的那个。

ink 在 app 层绑定这个键，旁边还有一个遗留的替代键，绑到一个强制展开所有思考的单一
标志上。它把一个思考解析为「该标志，或者用户逐个点开的那个 id」，这正是为什么把全局
关回去之后，被手工点开的那个思考仍然是开的。移植保留了两半：标志放在入口 —— 也就是
ink 那个 app 层拥有者的对应物 —— 所以当一个对话框或一个确认框占据屏幕时按键仍然能
落地；而那一行保留自己的点击状态。绑定走共享的匹配器而不是一个字面键名，所以用户的
重绑定与那个遗留替代键都能生效 —— 而且这条命令本来就已经在本渲染器的优先级表里占了
位，只是没有任何东西消费它。

标签错的原因相同：耗时在思考结束时就被测出来了，也一路带到了视图，而视图从不读它。
它唯一的读取者是 arena 卡片。ink 会报出耗时 —— 不到一秒读作「短暂思考」，超过就报
出时间 —— 并对一个从未上报过耗时的思考退回进行中的措辞。用哪个格式化函数是要紧的：
这里存在两个，一个四舍五入到整秒，一个保留一位小数，而 ink 的思考用的是整秒那个。

## 决定 19 —— 工具结果的结构化载荷只有一套优先级

一个待办列表以它的原始 JSON 到达了工具卡片。消费侧什么都不缺：事件带着一个 todos
字段，模型会把它折叠进去，卡片有一个勾选列表渲染器并把它排在所有其他正文之前。整条
链路都建好了，却没有任何东西往里生产。

有六条路径会把一个结果展示转成事件。其中一条会先检查那些结构化载荷 —— 文件 diff、
待办列表、ANSI 网格 —— 再退回到文本；另外五条直接压平成文本，所以它们每一条都会把
待办列表 dump 成 JSON。它们现在共用一个持有这套优先级的 helper，而压平退回的部分未
变，所以一个没有结构化形态的展示渲染得与之前完全一致。

六条中有两条保留自己的约定：一个实时分片与一份恢复出来的 transcript，会把压平后的
文本作为增量输出事件发出，而不是作为结果事件 —— 它们的测试钉住了这一点，而折叠器对
文本的处理两者完全相同。所以这两条只共用结构化的那一半，保留各自的退回分支。对它们
而言改变的是载荷而不是事件类型 —— 执行中的待办列表、以及恢复时的 shell 结果 ANSI
网格，现在会渲染出来而不是 dump。

## 决定 20 —— 受门禁的服务器审批复用策略，只移植视图

一份签入项目的服务器列表在这里从来不会被拿出来征求审批。ink 在其审批队列非空时就打开
那个对话框，而本渲染器完全没有对应物，于是一个受门禁的服务器会静默地保持未连接，而且
没有任何东西告诉用户为什么、以及该怎么办。

队列、那份按配置哈希持久化的决定、本次会话内的解除门禁、以及重连，全部住在一个只接受
config、返回普通数据外加一个处理器的 hook 里。它与 provider 安装流程一样是与渲染器无关
的，而本渲染器本来就逐字复用了后者，所以这次移植是一个视图加一个挂载点，而不是策略的
第二份副本。这里没有任何东西决定谁需要被询问、或者一个回答意味着什么。

挂载点是可能出错的那部分。ink 把这个审批排在 shell 确认框与工具确认框两者之上，所以它
在这里也直接占据那个槽位，而更新提示在它占屏期间保持被抑制，与其他弹层抑制它的做法完
全一致。

逐行读那一帧时，发现了这次移植自己引入的一个缺陷。ink 的布局在任何它计为可见的对话框面
前都会把整个 Composer —— 连它的 footer 一起 —— 卸掉，而这个审批就在其中；这里对话框占
据了 Composer 的槽位，footer 却仍走自己那道独立的门禁、不知道槽位换了主人，于是 ink 不
画的两行继续印在盒子下面。给那道门禁补上一个条件，这个检查点现在只剩下面两处残余。

几何是照着 ink 量出来的，不是假定的，而第一版有两处错：它把盒子画在终端左边缘、占满整
宽，并且不印行号。ink 把这个盒子比对话框区域已经定位好的那些弹层再往里缩一列，因为它
在那个区域内部又加了一道自己的边距，这使它比共享的弹层宽度窄一列；而它的单选行是带编
号的。两者现在在 100 列终端上量出来一致，且拒绝之后两腿都落在同一个 composer 与同一行
footer 上。

有两处残余是记录而不去追的，其中第二处此后已经关闭。ink 的盒子没有右边框 —— 它自己那道
边距把一个全宽盒子推出了它父级能打印的范围一列，右边缘被裁掉了；那是一个溢出产物而不是
一个选择，而这里的每一个弹层都画闭合的盒子。已关闭的那一处：正文里某一行在这里多带一个
前导空格，而在验收帧上重新量它，这个空格落在段落的**首**行而不是它的续行上 —— 在
`@opentui` 0.5.8 下，那一行比 ink 靠右一列（`│  Approval is bound…` 对 ink 的
`│ Approval is bound…`），而续行本来就是对齐的。从 0.5.9 起两行都与 ink 逐列一致，所以
这次改钉版本在不动我们自己任何布局代码的前提下就消掉了这处残余。

## 决定 21 —— 提问对话框整体移植，只在 ink 自己错的地方不跟随

向用户提问的那个对话框此前被削减到只剩它的字面选项。它不画自由文本行，于是一个答案只
能是模型恰好发明出来的某个选项；不在每个选项下画描述，于是一个标签必须承载全部含义；
也不画数字键，于是一次选择要花一次导航加一次确认，而不是一次按键。它的标题与提示措辞
也和 ink 不同。答案本身的传递是正确的，这正是状态层测试套件从来抓不到其中任何一条的
原因：一旦做出选择，两个渲染器就逐字打印同一张已结算的卡片。

ink 会画的东西现在这里都画了，而几何是推导出来的，不是猜的。那条命名每个问题并标出已
答问题的 chip 行，其上限由一个从 ink 自己的对话框引用过来、而非重新实现的水位填充助手
给出，然后再扣掉这一行在标题文字之外花掉的每一个单元格：内边距、当前 tab 标记、submit
chip、每个 chip 之间一道间隙、每个标题两列前缀，以及每个已答标记再多两列。它在每次渲
染时重算，因为作答会改变那些标记。

ink 的那些开销项是逐行照搬的，而从中被减去它们的那个宽度也一并搬了过来；一轮评审发现
那第二个数字是错的：它属于 ink 画这一行所在的那个盒子，而这一行坐在另一个盒子里，后者
花掉两列外边距（只在左侧）与每侧一列内边距 —— 而内边距已经是上面那些开销之一。把那一
列内边距算两次，再算上 ink 的 transcript 缩进，就从一个只花四列的行上扣掉了八列，于
是标题在行里还有空间时就被省略号截断了。修正后的基数确实是这一行的真实宽度，而不只是
一个更大的数字 —— 这一点是拿一帧排好版的画面定下来的，而不是它当初所来自的那些 JSX
prop：在五十八列的终端里放三个十二格的标题，这里会在盒子留下的 54 格里整行打印出 52
格，并且没有任何一行到达终端的最后一列。ink 在同样的宽度下把三个都省略号化了；那个区
间记录在下面，而照着它做意味着裁掉这一行本来就放得下的文字。

有两处分叉是有意的，而且性质不同。第一处是 ink 自己有、这个移植没有的缺陷。ink 对一次
按键把手打的自由文本答案提交两遍 —— 对话框自己的按键处理器与它挂载的输入控件都订阅
了，而按键层向每个订阅者广播、没有焦点栈来仲裁 —— 每次提交都推进一个 tab，于是紧随
其后那个问题在从未被画出来的情况下被跳过。这不是仅凭源码推断出来的：验收运行的 ink
腿在等一个始终没有出现的问题时超时，而它自己的复核 tab 随后把那个问题列为未作答。
这里一次按键推进一个 tab。跟随 ink 会复现一个缺陷而不是复现那种体验，而修 ink 会移
动整轮清扫用来度量的参照物，所以这处分叉被记录下来。场景被重排为在最后一个问题上使
行自由文本行，那里 tab 下标会被钳住，两腿一起到达复核 tab。

第二处分叉是这个移植失去的东西。选项行是手动画出来的，而不是用共用的 select 控件，那个
控件的指针接线没有跟着过来：点击一个选项不再作答，悬停也不再高亮。这个对话框里并没有一
个还留着那个控件的列表 —— 这一分支只带着问题流程返回 —— 所以要比的是它的兄弟确认类型，
那些类型的结果行仍然是那个控件，仍然响应点击。按键能回答 ink 这个对话框能回答的每一个问
题，这正是本清扫设定的标准；指针因此被留给它自己的改动，而不是被论证掉。点击需要在
chip、自由文本行以及 submit 与 cancel 行上各有各的含义，而它们回答的是不同的问题；并且
这些行刚经历过的那一类隐患同样是指针隐患 —— 一次落在同一次读取里的点击，只是换了来源
的一串连击。这条也没有任何一腿在度量：工装每次 stdin 写入一个字符，从不发出鼠标序列；
而报告这一条的那次运行在它自己的环境里起不动本渲染器。

自由文本行把它的值保存在一个与状态更新并排、同步写入的镜像里。按键事件可能在一个
React 批次内到达，而一个用其渲染所捕获的值去构造下一个值的处理器，是在往一个已经过期
的快照上追加，于是一串连击只保留最后一个字符。ink 出于同样的原因保留同样的镜像。有一
个测试在单个批次内派发一串连击，而这个修法是通过把镜像取出来验证的：恰好只有那一个测
试失败，且那一行只显示五个已打字符中的一个。在真机上这个隐患没有触发 —— 一个二十字符
的答案在两腿上都完整保留 —— 所以这个镜像是构造上的正确性，而不是对某个已观察到的截断
的修复。

回答一个问题不是就地换 tab，而是在 ink 的那次停顿之后才调度换 tab；而一次落在该停顿
内的第二个答案，过去会覆写已调度的那次换 tab 的句柄却不清掉它。于是两个定时器都会触
发，各自前进一个 tab，夹在它们之间的那道题就从未被画出来地被跳过了 —— 正是本决定要消
除的那个失效，只是从另一条路径到达。ink 也取消不了那次换 tab：它调用 `setTimeout` 时
根本没有保留句柄，所以它同样带着这个孤儿定时器。本渲染器为了在卸载时清掉定时器已经持
有的那个 ref，让取消只花一行。有一个测试在停顿之内把同一道题答两次，并断言下一题仍然
出现；把那次清除取掉，它就失败。不过 150 毫秒内两次 Enter 是打字快，而不是压力用例，
而且任何一腿都没有被观察到因此跳过一道题 —— 这次取消同样是构造上的正确性。

比较了八个检查点。每一行对话框内容都与 ink 逐行逐缩进一致，包括标记在某个 chip 的自由
文本框被勾上时就出现、早于任何东西被提交，包括多选答案那个「逗号加空格」的连接并把手
打条目计入其中，也包括复核 tab 自己的那条提示 —— 它在 ink 丢掉取消子句的地方同样丢
掉。剩下一处分叉：长路径在哪里折行。这里原先记录的第二条 —— 垂直锚定 —— 已在开头撤回：
两块屏幕在终端里占据同一个位置，真正不同的是工装把 ink 的那块内容重建在哪里。原先记录
的第三条 —— 等待行停在哪一帧 —— 已由决定 28 关闭；第四条，启动时的更新提示，已被证
伪：那条提示来自运行时而非本渲染器，而且工装在两条腿上都把它压掉了。

## 决定 22 —— 确认框画在会话所在的地方

一条工具确认原本以一个模态框到达：一个占满宽度的带框盒子、一行报出工具名的标题、
一行单独宣告某个调用正在等待、外加一条关于在列表里导航的提示。ink 一点都不画这些
外框。它的确认是 transcript 里的一个同级节点，直接落在正在等待的那个调用那一行的
下面，没有边框、没有标题行、也没有导航提示。于是批准一条命令在这里读起来像是在回
答一个对话框，而不是在继续这段会话，而且那个盒子把问题和它的选项推到了比 ink 所处
位置靠右好几列的地方。

外框已经去掉，正文、问题与结果清单都落在 ink 使用的那些列上，确认框的行序列现在在一百
列终端下与 ink 逐行一致。

这里对这一改动下过一个判断是错的，是合并把它抓出来的：那个为已被去掉的外框预留空间的
行数预算，曾被说成在 harness 所用的视口高度上不起作用。它并不是不起作用，只是 harness
从未跑到它真正收紧的那个高度。上游是在 80 行终端上，一条超长确认把载荷的尾部连同结果
清单一起推过了屏幕底边，于是用户读不到自己要批准什么、也够不着那些选项，之后抬高了这
同一个预留量。那个修复先合并了，本改动是换基到它之上继续的。

于是这个预留量是被重新推导出来的，而不是照抄：内联之后的确认框在正文上下仍然要花掉的，
是 banner、新会话开屏时的启动公告、带本回合边距的提示回显、卡片自己的隐藏尾行、问题行、
结果清单，以及那条等待行。早先那一版算进去的边框、标题、正文上下边距和底部提示，都随外
框一起没了，所以这个数比它替换掉的数小，小的幅度差不多正是那几行花掉的。然后两边都验了
一遍：跑 80 行 110 列的那条长确认场景，在合入的取值下是绿的，在零值下会等载荷尾部等到
超时 —— 所以这条场景确实还守着这个数。但它守得不紧：比合入值再小四行的取值同样是绿的，
也就是说阈值落在本轮关心的区间之下，钉住合入值的是那套算式而不是这条场景。

还有一处后果是被核对过、而不是被假设的：当一个调用被停住时，loading 指示器会换成 ink
那句等待中的措辞，并去掉它的耗时、token 与取消后缀 —— 既然没有在飞的请求，就没什么可
取消、也没什么 token 可数。这条等待行只为工具确认渲染：服务器启动审批、目录信任门禁与
动作确认全都到达在会话空闲之时，而 ink 自己的指示器在这种情形下什么都不画，抓取的帧在
两半上都与此一致。这一块在纵向上的位置不是这些帧能判定的：上面记录的那处分叉属于重建
方式，而不是任何一块屏幕，因此在这里既没有证实也没有排除。

## 决定 23 —— 卡片的渲染偏好按事件重新导出

工具卡片会优先使用它旁边的结构化载荷而不是那段摊平的文本，正是这个偏好让一次 shell
运行画出带样式的 token 网格、让一份 diff 画出带颜色的行、让一次 todo 写入画出状态清单。
但喂给卡片的历史折叠只会加上这些载荷、从不清掉一个，于是这个偏好可以活得比它所依据的
那个载荷更久。

一条 shell 命令恰好会走到这个状态。它在运行时流式输出带样式的内容，而如果这段流随后触
发了二进制检测，累积下来的输出就会被一个纯字符串替换掉。卡片会一直显示它见过的最后一
个网格，调用结算之后也一样，于是用户既不知道出现了二进制输出，也永远看不到随后那些
字节数。任何显示种类在飞行中途改变的工具有同一个形状，因为一份结果最多只携带一个结构
化载荷。

每个事件都携带完整的显示内容，所以结构化字段现在是从事件里导出的，而不是往卡片上累积。
产出这些事件的三个生产者各自在结构化形式与摊平形式之间挑一个，绝不会为同一个结果同时
发出两者，因此重新导出不会丢失任何东西；而那一次可能在完成之后才送到更新的尾部刷新，
会在调用返回之前被取消，所以没有哪条路径能把后来一个事件合法丢掉载荷再拿回来。出口
披露保留它原有的粘滞行为 —— 它是结果之下一条额外的通知，而不是结果的另一种渲染，也不
参与卡片的这套偏好。

## 决定 24 —— 同一个镜像也守住认证输入

端点与 API key 两步共用一个行输入 helper，而它用「注册它的那次渲染所捕获的值」去构造
下一个值。从同一个 pty 缓冲区里读出的按键可能在单个 React 批次内被派发，中间没有任何
渲染把它们分开，于是这一串连击里的每个字符都追加到同一份已经过期的快照上，输入框最后
只留下最后一个字符。粘贴是安全的，因为一次括起粘贴是携带全文的单个事件；以人类速度打字
也是安全的，因为每次按键都会先冲刷一次渲染 —— 这正是那些一个 act 打一个字符的既有测试
从未看见它的原因。

这个 helper 现在为自己的值保留一份镜像，在每次变更时同步写入、在渲染时重新对齐，于是每
个事件都追加在上一个事件的产出之后，而从别处设进来的值仍然会被取到。两步都通过普通的
state setter 到达它，而 setter 存的就是收到的那个值，所以镜像会在下一次渲染与父级收敛，
修复因此留在 helper 内部，没有改动 ink 自己的向导。把镜像拿掉只会让那个连击测试失败，
一个十二字符的 key 到达为它的最后一个字符。与上面那个对话框的行同理：真机上没有观察到
截断，也没有任何场景走认证向导，所以这是构造上的正确性，只有单元测试覆盖。

## 决定 25 —— 参数行，以及一个箭头而不是每张卡片一行

当 `ui.showToolCallArgs` 打开时，ink 会把这次调用的原始参数写在卡片 header 下面一行暗色
文本里，上限两行折行，余下的折叠成 `… +N chars (ctrl+o)`，并在会话进入那个键所切换的详情
态时完整打印。在这里这个设置没有任何读取点，也根本不存在这样一行。这套策略没有被重新
实现：序列化、与「描述本身就已经是那份载荷」时的去重、按 header 自身内宽缩放的字符预算、
规避代理对安全问题的逐列行走，以及针对提示注入的清洗，全部来自 ink 所用的那个 helper，
而它被拆开是为了让两个渲染器读同一个事实来源。这一行的位置在 header 与正文之间，与 ink
的排序一致。

调查在写下任何一行之前修正了前提。原先的说法是「没有任何路径携带调用的参数」；实际上
实时路径一直都带着，就在打开这张卡片的那个事件里，而它携带的正是 ink 这个设置所读的
那个值。真正缺的只有两个载体 —— 由 `@` 提及文件所引发的转向卡片，以及恢复会话的
transcript —— 而这一行仍然哪儿都不画，因为没有任何东西去读取条目上的那个字段。第一次
尝试载体改动时在调度循环里加了第四个来源，等测试显示它每次调用把同一行发了两遍之后被
回退；它暴露出来的事实是那个既存载体完全没有测试，所以一个把它丢掉的折叠本会通过。
如今那个既存载体被钉住了，新补的两个也是。

在真机上，两腿都画出了这一行，而折叠掉的余数在两腿上是同样的字符数。这一行在本渲染器
占用的物理行数比 ink 多，那是下面记录的折行规则分叉，不是这一行自己的问题。

标记等待调用的那个箭头原本画在每一张待审批卡片上。ink 只画在一个上：它的门禁是第一个
正在等待审批的调用，而本渲染器也只显示那个调用的对话框，所以其余每一个箭头标记的都是
用户无法操作的调用。这个标志现在取自第一个待审批的 id，并且有一个测试断言第二个待审批
的调用拿不到箭头 —— 验证方式是把这道门禁去掉，那会让该测试失败并在屏幕上留下两个箭头。

## 决定 26 —— 会话拿到视口，chrome 保住自己的行

应用按自己内容的高度排布那一列，所以会话每多要一行，输入行就少一行可见性。在一百列
乘三十行的终端上用一个四十九行的回答复现：banner 占住第 1 到 6 行，回答的起始行落在
第 15 行、它下面的十五行把终端填到第 30 行，而 composer、loading 指示器与 footer 被
排到了最后一行之外，完全没有绘制。第二轮对话随后证明了这个后果而不是描述它 —— 脚本往帧
里打字，帧里没有任何东西移动：打字之后抓的那一帧与它之前的两帧逐字节相同，而那一轮的标记
从未进入字节流，于是场景的检查点超时。同一套机制也会裁掉对话框：在一百乘四十下命令帮助
页有三十行高，而承载它的那一帧结束在自己的 footer 提示行上，收口的那道边框掉到了终端之
下。

ink 对此免疫，却并没有解决它。ink 的永久输出进入终端自己的回滚缓冲区，由终端负责滚动；
live 区只保留当前的尾部。库里有等价的东西 —— 把终端切成回滚区域与固定 footer 的屏幕
模式 —— 而它被搁置的原因就写在这个模式自己的几何计算里：渲染树被界定在 footer 那一条
带上，上方区域由捕获到的 stdout 喂进去，所以采用它意味着把每一条 transcript 条目重建
到 React 之外。迁移自身那份「已接受的取舍」早就记录了放弃那个模式、改用单一滚动区；
缺的只是把那个区域接上。这补的是已经写下的设计里的一个洞，不是另起一套方案。

需要四个属性，而它们没有一个能从库的命名里读出来。根列被终端高度界定，因为 flex 子元
素否则就拿自己内容的高度当高度。所有会流动的东西 —— banner、transcript、两行通知 ——
被移进一个随剩余空间伸缩的滚动区。该区域带着一个粘性的底部锚，所以它显示尾部，并在每
次布局后重新咬合，直到用户从底部滚开；这个锚需要同时给出库的那两个 prop，其中单独一个
是无效的。这也是为什么「每次更新时显式滚到底部」被否决 —— 它在静止帧里量出来一模一样的
效果，而用户一碰滚轮它就和滚轮作对。区域之下那些行 —— 每个对话框连同 composer 与
footer —— 被锁住不被压缩：没有这把锁，布局会把区域的内容高度摊派到整列上，把 composer
的三行边框挤成同一行画三遍，因为一行文本不能收缩得比它自己的内容还小，它宁可覆盖邻居也
不裁剪。每个属性在进入应用之前都先在同等尺寸的合成夹具上确立，shell 的测试如今把这四个
都钉住 —— 验证方式是把它们逐个去掉，每去一个就让一个测试失败。

在真机上，溢出臂是一个精确匹配：它的三帧全部与 ink 逐行一致，从回答的最后一行一直往下到
footer 的模式行，差异只有一个字符 —— 本渲染器画在最右列的那格滚动条指示。它是有意留下
的：它是「折叠线以上还有可达内容」的唯一线索，而对话框本来就带着一个。

滚轮随后在同一臂上被测量，而不是被假设，因为「让用户从锚上滚开」这个决定正建立在它之
上。注入二十格把区域往回推了二十行，从回答那串编号行里的第二十五行退回第五行，而
composer 与 footer 一行都没有动；反向六十格让锚重新咬住了尾部。那正是「每帧一次滚动调
用」会毁掉、而键盘绑定必须对上的行为。

本文曾记为刻意的两个分叉作为副产物关闭了，两者都有帧为证。banner 不再常驻：它随会话
增长滚出区域，而 ink 是把它提交进回滚缓冲区。对话框现在也会重排会话：在三十行的帮助页
之下区域缩到了十行，让出了 banner 的最上两行，而对话框本身完整装得下。一个和终端一样
高的对话框把区域压到零行是同一个行为，不是新的缺陷，因为 ink 也把那些行推出视口。这里
没有的是用键盘滚动这个区域。

## 决定 27 —— 长的 shell 卡片为屏幕做压缩，为模型保留原文

ink 把一条 shell 命令的输出写两份。放到转录行的那一份经过共享的历史保留压缩；交给
模型的那一份保持原文。本渲染器在它的两个写入点上都把裸的累加结果放上卡片 —— 节流
后的流式快照与最终结果事件 —— 于是一条长跑命令会把它的完整输出在整个会话剩下的时
间里钉在转录中。在本分支上这不再只是观感问题：决定 26 用终端高度界定了区域，因此那
些 ink 会压缩的行会把更早的内容推到折叠线以上。

两个写入点调用的都是 ink 的历史折叠所用的同一个 helper，所以保留上限只有一个所有者，
而不是一份会各自漂移的副本。工装里没有任何场景产出那么长的输出，因此这件事由单元测
试钉住，而不是由某一帧：两个写入点各自断言卡片显示保持在保留额度之内，而写入历史的
那一份仍然拿到完整字符串。移除压缩恰好让这两个测试失败、其余测试不受影响，失败的断
言里点名了四万一千与三万七千这两个超长的显示长度。

## 决定 28 —— 对话框开着时，等待行静止不动

当一个调用被确认框挂住时，本渲染器仍在持续重画那行等待提示，而 ink 不会。这是量出
来的，不是推断的：一个探针复现了提问对话框场景，在对话框打开的情况下每秒重建一次屏
幕、连续采十五秒；ink 腿每一次采样都是零字节，而本渲染器腿约十二字节，且每一次采样
上那个格子都不是同一帧。十二字节每秒正是该渲染器自己的节奏 —— 共享的转圈间隔是八十
毫秒，而只改动一个格子的重绘大约就是一个字节。两条渲染器在没有打开对话框时都一字节
都不发，所以这不是整棵树在重画。

门禁在 ink 的 `RespondingSpinner` 里：它只在响应态动画，其余状态下画出自己被传入的
`nonRespondingDisplay` 字符串，而 `LoadingIndicator` 在等待确认状态下传给它的就是某
一个静止帧 —— 那个状态下根本没有任何定时器在跑。本渲染器的转圈组件持有一个无条件
的 interval，于是在「只有用户的回答才能让它停下来」的时候这一行还在索取注意力。代
价不只是观感：验收工装靠观察输出变静默来判定一条腿已经落定，于是确认类场景里每一条
被挂住的腿都会吃满六十秒的空闲超时（某场景某一条腿实测 60,088 毫秒、39,798 字节）。
检查点由场景声明而非按定时采样，所以没有任何判定因此失效 —— 只是每条被挂住的腿都付
了这段等待，而帧对比把这些行里的每一行都算成本文档已经记录的那类 spinner 帧差异，
而不是内容差异。

门禁被移植过来了，而它停下时画的那一帧是共享的、不是抄的：它进了两个渲染器本来就从
同一处读取的转圈常量，而 ink 此前把它写成了字面量。两条测试覆盖这一对 —— 回合在飞行
中时帧会推进，调用被挂住时帧停在那一格。它们各自钉住的是显示的那一帧：取出挂住分支只
让「挂住」那条失败，取出 interval 只让「飞行中」那条失败。前者当初没有钉住的是计时器本
身 —— 一条继续走时、却每次都打印同一帧的行是能通过的 —— 所以「挂住」那条现在还会断言
没有 interval 留在运行，那正是本决定在真机上量到的代价。

这一行的短语也服从 ink 为自己 composer 读的那个无障碍设置，而这道门禁必须到达这一行的两处
挂载 —— composer 的那一处，以及挂住的确认框下面等待行的那一处 —— 因为只让其中一处闭嘴的
设置，会让另一处继续轮换词。三条测试钉住它：设置显式关掉时，两处挂载各自的短语都被丢掉；
设置什么都没说时，两处都保留，那正是 ink 对缺失值的读法。把这个比较反过来会让两条都失败，
从任一处挂载上摘掉这个 prop，会让拥有那一处的那条测试失败。

这一行自己的耗时计数也需要同样的处置，而最顺手的接法是错的。共享的计时器会在自己那个
「是否在跑」的旗标由假变真时把已累计的耗时清零，所以把它接成 `streaming && !waiting`
—— 那正是「丢掉后缀」所暗示的接法 —— 会在被挂住的调用恢复时从头开始计数，于是一个已经
跑了半分钟的回合把自己报成四秒。改为把计时器另一个「暂停」旗标交给它，它保住已累计的时
间并从那里继续。差别由一条测试钉住：让调用跑到第三秒时挂住、停三十秒、再恢复，一个节拍
之后读到的是四秒；上面那种接法会让这条测试在断言 `(4s` 的地方失败于 `(1s`。挂住期间这一
行根本不打印耗时，如上文所记，所以这影响的是用户回答之后看到的数字，而不是对话框开着的时
候。

这套接法的好坏，取决于承载它的那个实例，而有一轮评审量到了它的边界：那条测试重渲染的是同
一行，而外壳把这一行挂了两次 —— 一次在挂住的确认框下面，一次在 composer 之上 —— 分处两个
互斥的分支。于是「挂住」这件事本身就会卸载那个累计了耗时的实例、再挂上一个全新的实例，而
新实例上那个旗标的值永远不会变；所以即便暂停旗标接得没错、单元测试也过得去，在外壳里回答
之后耗时计数仍然会从头开始。要让已累计的时间跨过这次交换，就得把它交到两处挂载之上去持有，
这件事记进了后续工作，没有在这里做。

之后重跑全量矩阵，在真机上而不是在测试里确认了它：十一个在对话框挂住时取到的检查点，
每一处两侧各减掉一行，从四行分叉变成三行，那里剩下的行是决定 21 记录过的长路径折行断
点。总分叉行数从 221 行 ink 独有、265 行 opentui 独有，降到 210 与 254。逐字节一致的检
查点数目仍停在那次运行打分的那 69 个里的 22 个 —— 正是那行折行使它们没能并进去，所以
这次冻结在每一处关掉了一行，却没有翻转任何一条判定。

## 决定 29 —— 排在另一个审批之后的已批准调用，用 ink 的等待字形停着

一个模型回合可以返回两个都需要审批的调用。批准第一个并不会让它开始跑：这一批里第二
个的审批还挂着，于是调度器把第一个按在 `scheduled` 里，直到那个回答到达。ink 的卡片
会读出这个状态，并在整段等待里保持 `o`；本渲染器却在回答落地的那一刻就把这一行换成
了 `⊷` —— 那是「正在干活」的字形，可这个调用等的是人。

ink 的状态映射把 `validating` 与 `executing` 归到 Executing 显示态，把 `scheduled` 归
到 Pending；它的指示器把 Pending 画成成功绿的 `TOOL_STATUS.PENDING`，把 Executing 画
成会切换的转圈 `⊷`。两个渲染器读的是同一个调度器，所以这件事要的状态本来就在本渲染器
手里 —— 它订阅的那批更新里，每个调用都带着自己的 `status`。缺的只是那一次读取，不涉及
对共享调度器的任何改动。

让这一行值得停下来的原因是：`TOOL_STATUS.PENDING` 在这一侧根本没有任何生产者。状态表
上方那段注释列出了共享常量定义的六个字形，而这里被产出过的只有五个 —— 所以那一行不是
把正确的状态画成了错误的一帧，它画的是一个本架构没有名字的状态。

找到它的场景是新加进矩阵的：默认审批模式下一个回合里两个 shell 调用，在两次批准之间
抓取屏幕。真机上的受控对照只变一个量 —— 回退读取点，bundle 与场景其余部分不动 —— ink
那一行是 `o Shell touch acceptance-two-a`，本渲染器对应位置是 `⊷ …`，而这一对正是该检
查点四行分叉里的一行。补上读取之后两侧都读 `o`，该检查点降到三行，剩下的就是决定 21
记录过的长路径折行断点。

这个事件是按调用集合触发的：第一次发现某调用进入排队的那次更新发一个事件，同一状态的
重复更新什么都不发，转入 `executing` 时发一次清除 —— 所以从未离开 `awaiting_approval`
的调用既没有事件也没有状态。三个测试撑起这条路径的三层，四个变异让它们各自失败：删掉
字形分支只让渲染那条失败，删掉读取只让调度器那条失败，削弱折叠只让模型那条失败，而去
掉去重守卫会让调度器那条失败 —— 因为它给每一批里的每个调用都打了一次清除。

同一个场景还把另一处分歧记进了后续工作：两个调用同时等待审批时，本渲染器把打开的确认
框接在两张卡片之后，而 ink 把它放在两张卡片之间。

## 决定 30 —— 回合中排队的提示，像 ink 那样列在 composer 之上

一个在回合运行时提交的提示，在这里只被计数、从不被显示。它的长度会到达 footer 徽标，
composer 的上键在顶边也能把一条文本弹回来供编辑，但这些文本本身只能通过排空来读取
—— 而排空就会清空队列。ink 改为把它们列在 composer 上方：一次三条、每条压成一行，
更多在等待时给一个溢出行，外加一条念出按键名字的提示，只在队列前几次被填满时显示。

移植过来的是 ink 的那个组件，逐行照搬，提示也在内，只多加一样：排队的那一行在被量宽度
之前会先被剥掉终端转义，而 ink 的组件把这件事交给终端。此前挡住的是读取而不是渲染。队
列住在一个 ref 里，好让一个回合能在一拍之内把它排空再放回去，而 ref 对一次渲染是不可见
的 —— 于是 ref 仍是那个同步的真相来源，同时移动它的五处各自再往 state 里复制一份：
压入、排空、回合中止时把仍在搭载的文本放回去的恢复、回合中把没有消耗完的余下文本重新排回
队列的那条引导路径，以及为 `/clear`、恢复会话与分支兜底的那次转录重置。composer 那个
「弹出供编辑」自己并不复制一份 —— 它是靠排空来移动 ref 的，所以镜像这条路径的是排空那一
处。转录重置这一处决定了这些行是随清屏一起脱落，而不是活过它。

这是本文档里唯一一件没有帧能作证的改动。两个渲染器都会把一个回合中按普通回车提交的文
本 **转向（steer）**：它在下一个采样边界被排空，作为真实的用户内容进入下一次模型请求，
所以这些行在一个回合之内出现又消失。要一个活得比回合更久的队列，就需要把提交推迟到空
闲，而在 ink 那是 Ctrl+Q —— 本渲染器并没有绑定它：这个命令在 key map 的优先级表里被列
出，但读那张表的解析器没有任何生产调用方，于是这次按键落成普通文本。这些行在这里只在
一个回合的长度内可达，这也正是矩阵里没有任何场景在任一腿上产生持久队列的原因。

有一处范围是被定下来的，不是被发现出来的：这些行列的是引导队列，shell 自己的延迟通道
不在其中。一个在被持住的命令仍在运行时提交的提示，会落在 shell 为自己保留的第二个列表
里，而无论是这些行还是徽标 —— 两者读的都是那份被镜像的队列 —— 都不会说它在等待，于是
那段文本只在它真正开始运行时才出现在屏幕上。ink 只有一个队列，会把两者都列出来。把它们
一起列出，与那个本可让队列持久化的键属于同一次改动：徽标与行必须一起动，否则屏幕上的两
个计数会互相矛盾。

有一处不对称是记录在案、没有修的。这些行挂在 composer 的那个分支里面，而
本渲染器把这一分支的位置交给了一个被挂起的工具确认框 —— 第一个待批准的调用在
那里作为模态对话框打开 —— 于是整个分支被换掉，行连同提示的计数器一起离开画
面，直到那次调用结算。ink 在同样的状态下继续挂着它的 composer：一个被挂起
的调用在它那里是转录区里的一张内联卡片，而它的对话框闸门列的是用户正在作答的
那些弹窗，从来不含工具队列。一个对话框确实会在两边都把 composer 卸掉，所以
一个已经走完的计数在两处的复位方式一样。要让行挺过确认框，就得把它们挂到上面
一层的 chrome 盒子里，代价是它们会落在等待行之上，而 ink 把它们画在转圈提示
之下。

覆盖是三层单元测试：组件的六条（队列为空时什么都不画、每条提示一行且空白被压平、三
行的上限与它的溢出行、前三次填满时出现而第四次不再出现的提示、按终端宽度减掉 ink
缩进截断的一行，以及在到达屏幕之前被剥掉终端转义的一行），hook 在上述每一处对被排队
文本的断言，以及一条钉住位置的 shell 测试 —— 这些行与 composer 一起落在那块不滚动的
chrome 里，而不是随对话滚走，并且落在它的上面而不是下面。十一个变异 —— 从 ink 照搬的
那五个行为各一处、每个镜像点一处、挂载处一处 —— 每个至少让一条测试失败，其中有一处局
限：剥转义这一处加法没有属于它自己的变异。挂载那一处的变异是把排队行移到 composer 下面，
而那条钉住位置的测试现在会把两者在 chrome 自己的文本里排出先后，所以这次移动会让它变红。
五条照搬来的组件行只让
属于自己的那条失败；镜像点做不到一一对应，因为一个从未拿到第一条、或从未被清空的列表，
之后好几个回合还在被断言。逐个抽掉那份复制量出来的结果是：推入时不镜像让四条测试失败，
回合中的重新排队不镜像让两条失败，排空、中止恢复与转录重置各让一条失败。

## 决定 31 —— 模型对话框的结果，既显示也记录

`/model` 对话框留下的那一行 —— 一次选取定下的模型，或是一次退出保住的模型 —— 只到了
转录，没到会话日志，而 ink 在那三处结果点各自都留有一条记录。分发器兜不住：它的那
个 result 阶段在对话框还开着时就结束了，输出列表是空的，而 ink 写的也是同样这一对空
的。所以 ink 把自己三处结果点每一处都再配一条 result 阶段的记录，念出命令名、带上那
一行。本渲染器现在做同样的配对，并且是同一个对象：显示的行与被记录的行是一次构建出
来的同一个值，两者无从分叉。

两处沉默是有意的。一个没能落地的选取什么都不记录 —— ink 会让对话框带着错误继续开着，
记下这一行就会在恢复时重放一次从未发生的切换。而对话框不会补一条 invocation 阶段的
记录：裸命令自己的调用已由分发器写好、且被隐去，再来一条就是重复。

覆盖是单元层加一次磁盘核对。对话框测试套件里三条已有用例现在连同那一行一起断言记录
器 —— 一条管两次到达的退出、一条管仍在应用中的选取、一条管落地之后的重复选取 ——
新增的第四条断言失败的选取在两处都不留下痕迹。五个变异 —— 完全不记录、阶段写错、命
令名写错、负载为空、失败也照记 —— 每个至少让一条测试失败。实机侧，slash 对话框场景在
两条腿上都打开 `/model` 再退出：各自的会话日志现在都有九条 `slash_command` 记录，顺序
与标记一致，第五条正是对话框自己的 result，两边都带着 `Kept model as fake-model`。没
在屏幕上演的是重放。把一个日志重建回 transcript 的那个适配器，只为 slash 命令的
invocation 阶段产出一行，而这是一条 result 阶段；ink 的重放读的是一个 result 阶段所
携带的那些输出行。所以恢复之后 ink 仍然画得出那行「保留原模型」，而本渲染器既画不出
它，也画不出任何其他 slash 结果 —— 正是决定 13 为 info 行整体点出的那条差距。补上它会
改变每一条 slash 命令在恢复之后留下什么，因此它记在「后续工作」之下，而不是在这一轮
接下。

## 决定 32 —— 对话框字段的光标会动了，和 ink 一样

这些对话框里的每一个文本字段都把值存在对话框自己的 state 里，而且只会往后追加。键盘能
做的只有加一个字符、删掉最后一个。← 和 → 什么都不做，Home、End 也一样；值中间任何一处
打错了，唯一的修法是把那之后的内容全擦掉。ink 把同样的字段都交给同一个文本输入组件，
它的编辑逻辑活在一个以码点计量光标的缓冲区里，所以那些键在那里是动得了光标的。受影响的
有两类字段：提问对话框的自由文本行 —— 它自己的提示行把 ← 和 → 宣传成切换标签，而这一
行却把它们整个让了出去 —— 以及认证向导的那四个文本字段。

这个缓冲区不是照着「它应该怎么做」重写的。落地的就是 ink 自己那些操作的一行切片，而测试
里没有一条手写期望：每条夹具把同一串按键并排灌进 ink 的 reducer 和这个模型，在每一步之后
而不是最后比对文本与光标偏移 —— 跨过一次留下换行的粘贴，跨过 ink 记作一格与两格的字
符，也跨过两头那堵动不动了的墙。ink 的分词是按它本身复用的：两个原本只模块内可见的辅助
函数改成了导出，于是 ctrl+W 擦掉的那一段就是 ink 擦掉的那一段，而 ink 自己的行为没有变
动。按键顺序也是 ink 的，只取一个一行字段收得到的那些键，其余每个键都交还给对话框 ——
这正是 ink 需要的，因为它的对话框一旦让字段拥有这一行就不再处理方向键。词跳转、向右删
词、整行删除与撤销重做被记录为未移植，这四样 ink 都绑了键。两处缺席是被迫的：ctrl+D 归
应用的全局退出绑定处理，但它并不吞掉这个键 —— 聚焦的字段同样会看到它，并且原样交回，
所以这个键上没有什么编辑行为可移植；而一个值被另一次按键整体换掉的字段，光标会被
拉回串内，而不是继续指着串外。

键的直觉读法与 ink 的绑定不一致时，留下的是 ink 的绑定，而第一轮评审的一条发现正是把这条
规则较了真。本移植把裸 End 键和 ctrl+E 送到同一个「跳到值尾」。ink 把两者分开：它的 END
绑定只有 ctrl+E，处理函数先派发一次行尾移动、再走到整个缓冲区的末尾；裸 End 越过那个绑定
落进 reducer，那里只认行。于是被 ← 停在粘贴值靠前那一行的光标，下一个字符会落到串的末尾，
而不是用户放下它的地方。这一处现在拆开了，裸键走 Home 本来就在用的按行移动；一个附带的
前提是 ink 的那一行是「可视」行，宽到需要折行的值会把它再切开，而这个模型没有折行可查。
覆盖是在 ctrl+E 那一步旁边补上裸键的差分一步，加上向导里 base-URL 字段粘贴一个两行值、把
字符落回第一行之内的用例，以及一个把裸键送回「跳到值尾」的变异 —— 两个套件各有一条测试为
它失败。这一处拆分的另一个方向有一轮是没有证人的：把 ctrl+E 改走按行移动能活下来，因为按
这个键的每一个夹具拿到的值里都没有换行，而在那种值上两个键落在同一列，路由和它的邻居无从
区分。现在有一条用例在一个带换行、光标不在最后一行的值上把两个键都经过路由按一遍，那个变
异会让它失败。

第二轮评审的另一条发现是一个拼法，而不是一个行为：擦掉光标左边那个词的键。ink 绑定的是
ctrl+W，而本移植除了它，还会为一个带修饰键的退格擦词 —— 那是一个上报修饰键的终端所发的
东西。不上报修饰键的终端发的是裸字节 0x1f，而这个字节到了对话框字段上什么也没发生 ——
既没有被插入，因为控制字符不算可打印；也没有被处理，因为只有 composer 被教过这个字节。
两条字段路径现在都去问 composer 自己的那个谓词，于是它们此前唯一没共享的一种拼法共享了。
把这个改动取掉的变异，只让同一条用例里喂进这个字节的那一个断言失败，而让 ctrl+W 那一臂
保持绿灯 —— 正是这一点让那条用例说的是「这个字节自己走得通」，而不只是「删词能用」。

三处渲染差异保留下来，其中一处比原先窄了。ink 把字段按固定列数开窗，并且只画光标所在的那
一行，所以一次多行粘贴会把它自己看不着的那几行全藏起来。这些行现在也藏同样的那几行，因为
一轮评审找出了整值渲染的代价：这里的光标格是并列在它所标记文本旁边的一帧，于是一个粘贴带
进来的换行会把这一行撑过对话框自身的高度预算，并把那一格留在与光标不同的行上。值仍然留着
那个换行，和 ink 的缓冲区一样，所以送到模型那里的文本没有变。列数仍然没有开窗，这正是上面
裸 End 那一条从另一头撞上的限制。ink 把光标格涂成从终端背景
读出来的灰，并且在实心块会破坏输入法拼字时退到下划线，而这一格带的是主题强调色，和
composer 的光标一致。还有 ink 会跑一个 530 毫秒的定时器，只要字段握着焦点就不断翻转那
一格的可见性，而一格常亮让对话框不必按定时器重绘。这个定时器不只是源码里的一行，它在测量
里看得见：在一个把光标停在自由文本行上的场景里，ink 那条腿每坐在这一行的六十秒里就写出
270 KB，场景的七次静止等待有四次把超时整个烧完，那条腿走了 251 秒，而本渲染器这条是
13 秒。

挂载语义按字段区分，因为 ink 的就是区分的。提问对话框的那一行只在自己的选项被选中时才
被对话框挂载，而且挂载时光标就在所存值之后，所以本移植把「该行被（重新）选中」当作一次
全新挂载，落在值中间的光标就此丢掉。向导里的自定义模型字段在下面那排列表拿到焦点时并不
被卸载，所以 Tab 回来时光标还在原地。

有一个字段的文本也不归模型自己管。上下文窗口的 setter 只留数字，而本移植渲染的就是拿到
的那个值，所以在那里敲一个被该 setter 拒绝的字符 —— 一个字母，或那一步显式绑定的
Space —— 只会推动光标，不会出现在行上。ink 的缓冲区在那里才是唯一来源，且从不回头读
那个属性，于是它会一直显示自己被流程丢掉的东西。两种下落点在同一列，而显示内容在光标
还不存在时就是这个样子 —— ink 显示一个自己的流程已经作废的值，这一条记为后续工作，
没有照搬。

覆盖是模型自己那一套 —— 本分支整份新增的文件里十六条新用例，其中六条把每一次按键都放回
ink 自己的 reducer 做对照，其余直接断言模型的状态 —— 加
上用它的字段那些测试，数目记在决定 33 与决定 37 下，外加十一个变异，每个都让真正拥有
该行为的那几条测试失败：向左键不再移动、上下文窗口字段的输入分支、两个跳至行尾的绑定、
向前删除、带修饰键的 Delete 擦掉一个字符而不是把键交还、ctrl+W、一行不再重新挂载、把裸
End 折回 ctrl+E 的那一跳、把那个遗留的删词字节交还给对话框、一行把粘贴带进来的那个换行
画了出来，以及一个停在换行上的光标去高亮那个
换行本身。实机侧，新增场景在两条腿上都从自由文本行回答一个问题，而且只问
一个问题，这样标签钳制和决定 21 记录的那次双触发都不可能是画面的来源：输入六个字符，
光标往回退两格，再插入一个字符。两条腿都在同一行的同一列显示 `> abcdXef`，也都把
`abcdXef` 记成了答案。带样式的抓取把那一定位钉死了。在 ink 画出那一格的两帧里，它
与本渲染器的那一格落在同一个字符的同一列上，只有两种颜色不同；在它之前的那一帧，光标停
在最后一个字符之后，两条腿各自要画的那一格都是一个被抓取丢掉的尾随空格，所以两边都不见
格；而在最早那一帧，字段还空着、显示的是占位符，ink 的那一格不在而本渲染器的在 ——
那是它的翻转间隔，不是缺了光标。
没有任何场景走到的是认证向导，这一点和从前一样：它那四个字段的编辑只有单元测试套件兜着。
还有一条测试运行时的说明值得写在这里，因为它花掉了一轮排障：
字段测试用的那套 DOM 运行时会把重渲染行的旧渲染留在活的那一行旁边，所以读光标格的探针读
的是最后一个。把同样的 JSX 形状放进真实渲染器改五次状态，行始终只有一行，所以这是脚手架
而不是对话框的问题。

## 决定 33 —— 一次读取里的按键，由它开始时的那次渲染处理

第一轮评审发现：决定 24 为行输入辅助函数关掉的那一类缺陷，还在每一个「读对话框 state
再写回去」的地方等着。渲染器的按键 hook 把处理函数存在一个引用里，并在一次提交的
layout 阶段刷新它；而一次 stdin 读取会把它带回来的按键一个接一个直接派发 —— 按住方向
键的自动重复约 30 毫秒一次，或者一次括起式粘贴连带终端附在末尾的那个 Enter。它们之间
没有任何提交，所以第一个之后的每个按键都由上一次提交装好的闭包处理，它读到的每个值都
慢了一次按键。人手速度看不见这个 bug，因为每次按键都会先冲掉一次渲染；一个逐字符花一
次 act 的套件同样看不见 —— 已有的对话框测试就是这么漏掉它的。

现在，那两个处理函数用来安放下一个按键的每一块 state 都有一份镜像，与它的 setter 在
同一次调用里写入，而处理函数读的是镜像：提问对话框的标签、它的选项光标、每题各自的
复选集合与手输内容；向导的推荐模型集合；行编辑器的文本与光标。提问对话框的处理函数
整个视图都从镜像导出 —— 这是第几题、单选还是多选、有没有自由文本行 —— 而不是从
「这次渲染画了什么」导出，于是没有任何分支能拿一个按键的位置去配另一个按键的值。
关于答案本身还有两处读取是例外，记录在下文。行编辑器交出的是一层读镜像的
getter 而不是快照，因为一个只捕获一次文本的消费者会把这个 bug 原样带回来，只需一行。

有一处读取比镜像更窄。自由文本行只在突发仍然站在「该行被画出来时所属的那个标签」上时，
才收下按键：这一行的缓冲区是在渲染期间重新植入的，所以一次读取里在切标签之后落下的字母，
会追加到那次渲染所画的那一题上，并被存成这串按键到达的那一题的答案。这些按键被丢掉，
和本轮之前一样；一个让方向键跨过标签边界的用例把它钉住。

提交是同一个 bug 反过来指。向导的 endpoint 与 key 两步调用它们的提交函数时不带参数，
所以一个与前面那些字符共享一次读取的 Enter 读的是父组件的 state —— 还是那些字符之前
的值 —— 向导就在一个只输入了一半的 endpoint 上前进，无声无息地退回到协议的默认 host。
它们现在把实时文本作为参数传入，这正是 ink 的文本输入拿缓冲区自己的文本调用 submit 的
方式，也是 ink 的提问对话框声明其提交签名的方式。推荐模型的复选框带着同一个发现而来：
一次读取里按住 Space 的两次勾选，或一次勾选连带提交它的那个 Enter，是一个复选框的两
种状态，以及一次对两者都一无所知的提交 —— 直到镜像被读出来。

这个 hook 与 ink 的向导共用，而 ink 的 endpoint 那一步本来就把缓冲区的文本传给它，
所以在同样的场景下 ink 那条腿现在提交的也是它屏幕上显示的值。离了那次携带多个按键
的读取，两个字符串完全相同；这是本轮唯一一处改到 ink 行为的地方。

两面镜像被读取的地方，没有任何按键序列能让它们显出分歧，这一条写在这里而不算作覆盖。
勾选一个推荐模型会把共享的 model-id 串与该字段的实时文本同步，而提交自由文本行取的是
它所站着的那个标签；但一次突发不可能既编辑字段又勾选列表行 —— 这两个分支由焦点决定，
而焦点是这一批按键自身改变不了的 —— 并且一次手动切标签会把光标放到第一行，而第一行
只有在「没有任何预置选项的问题」上才是自由文本行，这恰恰被工具自己的校验拒绝。保留它
们，是为了让处理函数对每一个事实只有一个来源。同一家族里还有两个同胞，这一轮是关掉而
不是记录：一是多选里手输内容算不算数，二是复核标签页提交时所取的那批已选答案。两处各
补一面镜像，并各有一条测试把那三个键放进同一次读取 —— 在多选的自由文本行输入、提交
它、再从复核标签页提交；答一题、走到复核标签页、在那里提交。两条腿上的任何场景都排不
出这个顺序，所以二者都只由单元测试套件兜着。

本轮停在被点名的那几个处理函数上，而这一类缺陷比它们宽。本渲染器里其余的列表都是用同
一种方式读自己的光标 —— 另有七个对话框文件挂载的共享选择 hook、竞技场对话框的模型列
表、输入框的补全行、向导的协议与 endpoint 两步、推荐模型列表的焦点（它的复选集合已在
上文配了镜像）、它的高级配置行，以及本对话框的主、子菜单。在那里，接键作用在上一轮渲
染画出的那一行，而不是这串按键到达的那一行；而凡是按画出的光标算下一步的地方 —— 共
享 hook、endpoint 选项列表，以及主、子这两个菜单 —— 按住方向键是一次读取走一行，而不
是一个键走一行。收口属于这些控件整体，而不属于本轮修的两个对话框，已记在「后续工作」
里。

覆盖是十六条新单元测试，认证套件五条、确认对话框套件十一条，外加十三个变异，其中十一
个会让真正拥有被拿走行为的那些测试失败：行编辑器退回一次渲染快照、Enter 提交 prop 的
值、模型那一步的复选集合被读两次（勾选与提交各一次）并在提交处再读一次该字段的实时文
本、提问处理函数按已渲染的 state 工作、Space 与 Enter 两个分支各自的选项读取、一次换了
标签的突发去编辑它抛在身后的那一题、复核标签页提交背后那面已选答案的镜像 —— 拿掉它还
会一并让决定 37 那条答案锁的测试失败，因为二者读的都是同一次突发记下的那个答案 —— 以
及多选提交所要的那面手输内容镜像。存活的那两个变异就是上面那些不可达的读取。没有任何
证据走到的是实机：验收 harness 故意每次写只打一个字符，于是一次按键落在自己那一次读取里，
而它从不向这些对话框粘贴 —— 这里每一个突发用例都只由单元测试套件兜着。

## 决定 34 —— 手动切标签会叫停已经排定的那次换题

提问对话框答完一题，暂停 150 毫秒让刚答完那一行的勾选可见，然后换到下一题。ink 排定
这次换题却从不取消它：暂停之内的第二次回答，或用户自己按的左右方向键，都不清那个定时
器，于是两次换题都会跑，中间那一题根本没被画出来。本移植继承了这个行为，而评审轮在
方向键这条路上抓到了它 —— 用户已经翻到某一题，对话框在零点一秒之后又把它带走了。

现在方向键会先取消排定的换题，因为这次按键就是用户对「我在答哪一题」给出的答案。第二次
回答原本也会取消它、并取代第一次排定的那次换题；后来一轮在这条路前面放了一把锁，落在暂停
之内的回答会被整个丢掉（决定 37）。这里已经没有东西留给那次取消去看了：一个还活着的定时器
永远属于光标仍停在上面的那个标签，因为移动只有换题自己那一次和两个方向键，而两个方向键都
先取消。所以这把锁就是那个武装着的定时器本身 —— 还记着换题属于哪个标签的那个 ref，建模的
是一条任何路径都观察不到的区别，它跟着那次死掉的取消一起走了。这是本移植有意与 ink 不一致
的几处之一；同样的 150 毫秒暂停、同样的在最后一个标签
处钳制、同样的先勾选后换题都保留了。ink 的行为作为它自己的缺陷记录在案，而不是照搬，而验
收矩阵已经在 ink 那条腿上看到的双触发，就是同一个缺陷从外面看的样子。

方向键由它自己的一个变异钉住：一次落在暂停之中的右方向键会保住它翻到的那一题，把那次取消
拿掉就只有这一条测试失败。回答路径上的那次取消是被摘掉的，而不是被钉住的 —— 把它放回去什
么都不失败，正是这个量度说明它不可达。那条路留下来的是「丢掉」本身：早于本轮的那条测试仍
然断言暂停之内的两次回答只走一步，而锁自己的变异记在决定 37 下面。实机侧，暂停与方向键已
经被矩阵里那些回答多个问题的场景覆盖了；取消本身在那里没有被观察到，因为它需要 150 毫秒
之内的两次按键。

## 决定 35 —— 光标格印出握着焦点的那个字符

字段那一行把值分三段画：光标之前、光标所在的那一格、之后。高亮那一格的第一个版本只在
字段握着焦点时才打印中间那段，于是一个把光标让给兄弟字段的字段连带丢了一个字符 ——
行显示的值比存着的值短一个码点，这正是那一轮评审的 Critical。字符归值所有，不管谁握着
焦点；只有底色说明光标在哪个字段里 —— ink 也是这样，它的文本输入决定的是要不要画光标
的高亮，而其下的文字始终要画。

同一行的光标现在遵循一条被上一版弄反了的规则。光标索引的是字段的主人认下的那个值，
而不是按键敲出来的那个：两段文本被一起走，光标只为被主人在它前面丢掉的码点计费，这
覆盖了一次拒绝的两种形状 —— 单独一次被拒绝的按键（往只留数字的上下文窗口字段里敲一个
字母）在光标处丢一个码点，于是光标停在原地不动；而一个会过滤粘贴值中间部分的主人
（`1,024` → `1024`）让光标继续跟着被接受的那段尾巴，而不是把它搁在第一个被删掉的字符
上。走不动的值 —— 主人是插入或替换，而不是删除 —— 退回以两段文本共同前缀为界的钳制。
在那之前，每个被拒绝的键都把光标向右推一个码点，一连串之后第一个 backspace 就吃掉一个
真实字符。两段文本相等时，这条规则退化回普通的钳制，所以每一次被接受的编辑行为如旧。

这一行只打印流程接受过的内容，而这正是决定 32 记下的那条对 ink 的分歧，不是新的：ink
的缓冲区才是事实来源，会一直显示它的流程自己丢掉的那个字符，所以同一次按键在那里留下
可见的痕迹。要匹配它就得把显示搬到缓冲区上，那是 ink 该修的缺陷；上面那条光标规则之所
以这么定，是为了让一次被拒绝的按键在两个渲染器的列布局里都不留下自己的痕迹。曾有一条
测试把这个漂移钉成了期望行为，因为它断言的那个光标就是漂移本身；现在它钉的是没有漂移，
而与评审要求的那个形状之间的差别已经写在那条 thread 里。

四个变异，每一个都恰好让拥有被它拿走的那个行为的那条测试失败：字段失焦时丢掉字符的那一
格，让认证套件里那条「光标被让给兄弟字段」的行测试失败；在应当放这条规则的地方改调普通钳
制的重新同步，让同一个套件里上下文窗口字段的编辑测试失败；退化成按长度钳制的那个兜底钳
制，让单独一次被拒绝按键的单元测试失败；而退化成只剩那个钳制的走法 —— 也就是这条决定从前
描述的那个形状 —— 让主人过滤值中间部分的那条单元测试失败。实机腿在这里没有变化 —— 向导渲
染的字段里的光标仍然没有任何场景能够到达，所以这一行的渲染只由单元测试套件兜着。

## 决定 36 —— 箭头指向队列答得了的那个调用

标记待审批调用的箭头原本是从转录里推出来的：第一张 pending 且未完成的卡片。这是拿
ink 的规则去读了错的列表。ink 的标记指向的是「确认框就在屏幕上」的那个调用，而只有等待
队列知道那是哪一个 —— 和决定哪个调用由 Ctrl+C 结算、哪个调用被 shell 对话框点名的，是
同一条规则。PreToolUse 钩子给出的一个 `ask` 决定，会重新武装一个用户已经批准过的调用：
把它 _追加到_ 另一个正在等待的调用之后，而它的卡片在原位回到 pending —— 于是转录顺序
与队列顺序不一致，而箭头就停在了用户根本没有对话框可答的那张卡片上。

现在 shell 把队列的第一个调用 id 传下来，而那一行仍然必须是一张 pending、未完成的工具
卡片才画得出标记。保住第二个条件，正是保住决定 25 那条「只有一个箭头」的规则：队列点名
但转录不再显示为 pending 的卡片没有箭头，别的卡片也都没有。这个 prop 在视图上是可选的，
所以没有队列可查的调用方得到的是「没有标记」，而不是猜一个。

新用例断言：当队列点名的调用不是第一行 pending 时，箭头停在那个调用上，而且画出的箭头
恰好一个 —— 把 id 丢掉、让转录的顺序重新做主，它就失败，一个十八条测试的套件里的一条。
该套件里另有一条钉住这道门禁的另一项：队列仍然点名、但调用已经完成的那张卡片不画箭头，删
掉这一项会让它变红，而它的同门那一项早已被一处已结算调用的渲染钉住。该套件里所有断言这个
标记的渲染都提供这个 id，因为一个必须来自队列的标记，没法由一个不提供队列的渲染去断言。接
线本身 —— shell 把队列的第一个 id 传下来 —— 钉在上一层：由一条挂载入口点渲染出的那棵树、
再读转录收到的 props 的用例负责，因为那个套件里每条用例都把转录 mock 掉了；删掉这条接线会
让它变红。把队列从渲染接缝的依赖数组里摘掉，是唯一一条测试看不见的腿，因为一个过期的 id
在同一次渲染里画出来是一样的：exhaustive-deps 规则会点名那个数组，而 CI 的 lint 通道不允许
任何 warning。实机侧，这里需要的顺序 —— 被重新武装的调用排在等待中的那个之后 —— 没有
复现；矩阵里驱动过箭头的那个场景只有一个待审批调用，此时两条规则一致。

## 决定 37 —— 字段在自己那次读取提交之后就停止接键

让「一次读取中间的提交」能够成功（决定 33），也就让那次读取的下一个按键有了意义，而它
其实没有意义：Enter 已经把向导留在下一步之后，读取里却还有按键没派发完，而这些按键仍归
刚被离开的那一步处理。那一步把值存在 flow 自己的 state 里，而 review 那一步的提交是从
这份 state 重新组装安装计划的，于是一个多余的字母会被写进 `settings.json` —— 密钥那一步
显示的是 `sk-test`，提交的也是 `sk-test`，存下来的却是 `sk-testZ`。

现在字段在自己的 Enter 移动了向导之后就结算，那次读取余下的按键一概不接。闩放在共享的
行编辑模型上，每个会漏的字段本来都经过它；各字段的处理函数在分支之前先查它：端点与密钥
两步经由共享 helper、模型 id 那一步（它的 Enter 同时也阻止空格去勾选身后的推荐列表）、
高级配置步的上下文窗口字段，以及提问对话框的自由文本行。最后这一处是同一个缺陷的另一端：
多选的答案是在 review 标签提交时从字段重新拼出来的，所以跟在 Enter 后面的字母会把用户早已
给出的那个答案加宽。

闩只在接受步「真的动了」的 Enter 上武装。被校验拒绝的 Enter 会把这一步留在屏幕上，这次读取
仍然属于它，所以同一次读取里的 `abc`、Enter、`def` 依旧会在端点字段里留下 `abcdef`。它是一
个跨渲染持有的 ref，而不是每次渲染一个旗标：一次成功提交自己排定的那次渲染原本会把它清掉，
而在提问对话框里，那次渲染会让已提交的那一行继续挂载、继续握着焦点，整整一段 150 毫秒的暂
停，于是下一次读取还会接着编辑一个早已作答的字段。只有挂载键变化才清它 —— 那既是每个字段被
挂载时所用的键，也是让光标重新落到值末尾的那个东西，和 ink 的文本输入在挂载时做的一样。一
个提交被拒绝的字段仍可编辑，因为没有任何东西武装过这把闩；而一个提交被接受、却在晚一步才
失败的字段不再可编辑 —— 那一步还在屏幕上，闩还武装着 —— 所以向导的最后一步需要决定 39 记
下的那个重试计数器。

有意不闩的部分也写下来。提问对话框的左右切题键在决定 34 保护的那段暂停里照常工作，因为那里
的按键就是用户自己对「我在答哪一题」的回答；字段那把闩停住的是字段，不是它周围的对话框。

对话框在那段暂停里确实自己停了一处 —— 停的是答案而不是导航，时长就是一次换题被武装着的那
段。字段自己的闩只够到它的插入分支，而被那次已武装的换题安顿下来的那一行仍在屏幕上、仍握着
按键，于是一次读取里剩下的部分会把同一题再答一遍，并悄悄替换掉已经记下的答案 —— 一个落在
选项分支上的数字，或者一个多选在提交时据以重拼答案的空格。导航原样不动，换题跑完之后的每个
键也原样不动。最后一题那个标签根本不武装换题（它被钳住了），所以它也拿不到这把锁；跟在那里
的一个按键仍旧落在它到达的那一行上。

ink 到不了这个漏。它的缓冲区是在提交时运行的 effect 里通知父级的（`text-buffer.ts`），所以
Enter 之后处理的按键永远等不到一次「自己那一步还挂载着」的提交，它的文本也就永远到不了组装
计划所依据的那份 state。我们这边是同步调用 setter 写回的 —— 这正是「读取中间的提交能读到
实时文本」的原因 —— 所以需要这个显式的停止。

覆盖是八条新单元测试，认证套件四条、确认对话框套件四条，外加八个变异，下面点名的每个行为
对应一个。每个变异恰好让真正拥有被拿走行为的那条测试失败：端点与密钥字段的守卫、把闩连被
拒绝的 Enter 也武装上、模型 id 那一步的守卫、高级配置那一步的守卫、自由文本行突发归属守卫
里的 settled 那一项、数字分支上「单选」那一项 —— 没有它，一个在多选上只移动光标的数字就会
把它点名的那个选项勾上 —— 以及答案锁在答案路径上的那道守卫 —— 没有它，跟在后面的一个数字就会把刚
刚由它所跟随的那个 Enter 记下的 `"xyz"` 报成 `"staging"` —— 以及同一把锁在空格分支上的那
一项，没有它，跟在后面的一个勾选就会把一个早已给出的答案加宽。这里没有任何证
据走到实机，原因记在决定 33：验收 harness 故意每次写只打一个字符，而且从不向这些对话
框粘贴。

## 决定 38 —— 转录区不在焦点链里

在对话区随便左键点一下，composer 就再也编辑不了它已经装着的文本。承载转录的那块区域是
`scrollbox`，而这个渲染器的 `ScrollBoxRenderable` 把基类的 `_focusable = false` 覆盖
成了 `true`（`@opentui/core`：`index.node.js:13859` 对
`chunk-node-kr27pp2p.js:210`）。渲染器在每一次左键按下上沿祖先链往上走，聚焦第一个
focusable 的节点，除非这次点击先被处理掉并 preventDefault
（`chunk-node-kr27pp2p.js:9091-9104`）。于是点击把焦点挪到了滚动区上，
`focusRenderable` 把原本聚焦的编辑器 blur 掉（`:7562-7569`）。blur 不是外观问题：一个
renderable 的按键和粘贴处理函数只在它聚焦期间存在，`blur()` 会把两者一起摘掉
（`:325-381`）。

没有任何东西会把它们装回去。composer 的 `focused` 一直传同一个常量，reconciler 要比较
的 prop 没变，于是这次写入在整个会话里都被跳过。打字看起来仍然正常，这正是差点让它被
驳回的原因：可打印字符走的是 composer 自己的全局按键处理函数，不是编辑器的那份，所以
缓冲区一直在变长，而只有聚焦编辑器才处理的键 —— 每一个光标键、每一次粘贴 —— 落到了没
人听的地方。真正显出差别的是 `Home` 之后跟一个字符，以及一次 bracketed paste。ink 也
解析 SGR 鼠标上报，但只分发按表面订阅、并对该表面自己的行做命中测试的处理函数 —— 滚动
列表上的滚轮、提示输入内部用来定位光标的点击 —— 而它们没有任何一条路能写到 composer
的焦点上，那个焦点是 React 的 prop。在对话区点一下什么也不会改变，这是量出来的，不是
推出来的。

现在这个区域是 `focusable={false}`。两个更宽的做法被否掉了。把 `autoFocus` 关掉是渲染
器全局的设定，而对话框自己的字段依赖它。在区域抢走焦点时把 composer 重新聚焦，等于让
转录区拥有一条「谁该在听」的规则，而 composer 的焦点已经由它自己的 prop 声明过了 ——
一个比特两个主人。给这个本来没道理进焦点链的节点加一个 prop，是同一个事实最窄的说法：
滚动区不是输入目标。

在真实终端上测量，四个臂，只变一个变量 —— 全程同一份 bundle 和同一组启动参数；而 node
下的 `ink` 对着 bun 下的 `opentui` 会把运行时和渲染器混在一起，所以 bun 下的 `ink` 单
列一臂。每个臂先打四个字符，然后 —— 对照臂除外 —— 在转录行上点一下，再量三件事：三个
左方向键加一个字母有没有把光标挪走、`Home` 加一个字母有没有落到最前面、一次 bracketed
paste 有没有进缓冲区。

| 臂                               | 光标会动 | `Home` 生效 | 粘贴落位 |
| -------------------------------- | -------- | ----------- | -------- |
| `ink`，node，点击过              | 是       | 是          | 是       |
| `ink`，bun，点击过               | 是       | 是          | 是       |
| `opentui`，bun，点击过 —— 修之前 | **否**   | **否**      | **否**   |
| `opentui`，bun，没点击 —— 对照   | 是       | 是          | 是       |
| `opentui`，bun，点击过 —— 修之后 | 是       | 是          | 是       |

同样的点击落在 composer 自己那一行时，每一个臂（包括坏掉的那个）粘贴都恢复了，这才是
把丢失归到编辑器焦点、而不是归到按键本身的依据。

修完之后仍然核过的部分：滚轮照样能滚这个区域 —— 专门测滚轮的那个场景在本渲染器上
重跑，粘在最后一行、上滚二十格后能看见折叠线以上的那些行、再滚回来又回到最后一行。那
个场景从头到尾没有点击过，所以「点击之后的滚轮」依靠的是路由而不是帧：滚动事件先做命
中测试，焦点只是兜底（`:9134-9143`）。还有一条单元测试钉住这个 prop，用一个删掉它的变
异证明它会失败。没核的部分：在转录上按住拖动选择文本，这条走的是同一个命中测试路径，
而这个渲染器从未对外声明过它；以及对话框开着时点击 —— 对话框的列表仍然默认
focusable，记在后续工作里。

## 决定 39 —— 作答那一行是有界的，而一次没被接受的提交要让字段开着

有一轮评审翻出四处本移植仍然把门在用户面前关上的地方，外加一处已经不再可达的机构。五
处都记在这里，而不是折进它们各自修饰的那条决定，因为每一处都是本轮量出来的。

提问对话框的自由文本答案，是那个对话框里唯一一处由用户提供、却既没有宽度也没有行界的载
荷。ink 把同一个字段放在一个五十格宽、一行高的文本输入里，而这个对话框所在的确认框自己
也没有正文窗口，于是一次长粘贴会把对话框撑到超过终端高度，把用户还要去选的那些选项推出
屏幕。因此这道界只覆盖用户打出来的内容，别的都不覆盖：问题本身、每个选项的标签、每个选
项的描述都是模型生成的，至今既没有宽度也没有行界，所以模型返回一个较长的问题或较长的描
述，同样会把这个对话框撑高、把同样那些选项推出屏幕，而其中没有任何用户输入。剩下的这部
分记在「后续工作」里。

那一行现在画在自己的窗口里 —— 五十格，减去这一行在它前面印出的标签，落在对话框现有的宽
度上 —— 而光标那一格也在其中：超出窗口它就无处可去，和 ink 那个定宽输入完全一样。同一
个值折叠后的回显以同样的方式设界，因为它印出的正是粘贴可以任意拉长的那个值。界只设在
画上。提交读的是存下来的那个值，所以答案保住每一个字符，包括一段粘贴文字自带的那些换
行。

一次 bracketed paste 是一个事件，不会每字符一个按键，而接手它的处理函数是问画出那一行
的那次渲染「光标在它上面吗」，写的却是当前那个标签。它没问的两件事，按键路径为自己的
那个危险早就都问过了：这波突发是否仍然站在这一行为其而画的那个标签上，以及一个暂停仍
在握着的回答是否已经把这一个锁在外面。一次 stdin 读取会把粘贴和按键一起带进来，所以移
动光标的方向键和跟在它们后面的粘贴是一起到达的 —— 在没有守卫时，一题打了一半的答案会
被和粘贴拼在一起，当成另一题的答案提交出去；或者一个早已记下的答案会在用户背后被加
宽。现在两件事都问的是实时位置。

向导的字段在提交自己的那次 Enter 上闩住，而决定 37 把这把闩记成它实际的样子：只有挂载
键变化才清它。在一个流程的最后一步，提交是异步的，所以那个武装闩的 `true` 只意味着安装
被发出去了。当那次安装被拒绝 —— 或者它只存下服务模型而没有会话模型，那也会把对话框留
着 —— 同一步会在对话框余下的整个生命里继续挂载，每个键都是死的：用户既改不了字段也重
试不了，剩下的唯一出路是退出向导。对话框现在数自己的重试次数，把那个计数器作为挂载键
交给字段，两条路径上都会加一，这会像一次全新挂载那样重新武装闩、重新播种光标。

一次被答案锁拒绝的提交，仍然会把它来自的那一行关上：字段在那个可以拒绝它的调用之前就
结算了，与行模型为自己的闩写下的契约相悖。那个调用现在会报告答案有没有被记下，字段则
按这个结论结算。用户看到的是同一次读取余下的部分 —— 跟在一个被拒绝的 Enter 后面的那些
字母仍会到达字段，于是他们回头给出的是自己打下的全部内容，而不是拒绝之前的那一截。

第五处是一次删除。决定 34 曾在两条路径上取消排定的换题；回答路径上的那次取消已经看不
到任何定时器了，因为决定 37 加的那把锁会在暂停之内的第二次回答到达取消之前就把它丢掉，
而一个还活着的定时器永远属于光标仍停在上面的那个标签 —— 移动只有换题自己那一次和两个
方向键，而方向键先取消。把那个调用放回去不让任何测试失败，正是这个量度说明它不可达；
决定 34 已被改正为这么说。同一个论证把那把锁的第二个条件也一起带走了：记着换题属于哪个
标签的那个 ref，永远不可能与光标所在的那个标签不同，所以这把锁现在就是那个武装着的定时
器本身，而整个套件在这一条件被拿掉之后仍然是绿的。

六条新测试，确认对话框套件四条、认证套件两条，外加上一轮那条粘贴换行测试里新增的折叠
回显断言，以及本轮量出的十个变异。每个变异都恰好让拥有被它拿走的那个行为的那些测试失
败：

| 变异                         | 失败                           |
| ---------------------------- | ------------------------------ |
| 折叠回显重新印出原始值       | 粘贴换行那条测试               |
| 那一行的窗口被拿掉           | 长答案那条测试                 |
| 粘贴不再问「这是谁的字段」   | 跨标签粘贴那条测试             |
| 粘贴不再问「答案有没有被锁」 | 粘贴锁那条测试                 |
| 粘贴处理函数整体还原         | 两条粘贴测试都失败             |
| 安装被拒时不加那个重试计数器 | 认证重试那条测试               |
| 只存下服务模型时不加计数器   | 服务模型重试那条测试           |
| 字段重新在结论之前结算       | 被拒提交那条测试               |
| 把不可达的那次取消还原       | 什么都不失败 —— 这就是那项发现 |
| 把那把锁的标签条件还原       | 什么都不失败 —— 这就是那项发现 |

实机腿已在这个 head 上重跑：二十七个场景各跑两腿，共五十四次运行，没有一次报错。
七十八个检查点里，二十二个的非空内容行完全一致，五十四个有分歧，带着 241 行只有
ink 画得出、282 行只有本移植画得出；余下两个是采样型检查点 —— spinner 的短语轮
转与流中指示器 —— 另行计数，因为里面装的是已耗时间与每拍挑一次的短语。与上一个
head 相比，152 个普通抓取里有 146 个逐字节一致，而不一致的那六个是三个检查点在两
腿上同时不同：流中指示器、`/stats`、以及按住短语那一行 —— 都是同一个二进制两次运
行之间就会变动的内容。

把 main 合并进本分支之后又跑了一遍全量矩阵，上面每一个数字都一样。合并在帧上只
动了一处：banner 印出的版本号 —— main 把它升了，而它在两腿上都位于转录区里，
于是几乎每一个抓取都会带上它。把这一串归一掉之后，152 个普通抓取里仍是 146
个与合并前那次运行逐字节一致，不一致的仍是同样三个检查点。

这条决定里记下的东西没有一个会移动一帧，而这是预期的结果，不是缺漏。答案行那个边界
在值超出窗口之前是恒等变换，而没有哪个场景会打出超出窗口的值；粘贴守卫、重试计数与
提交判定，全都要看单次 stdin 读取在那次提交的按键旁边还带了什么，那是 tty 的性质，
不是任何脚本的性质。与决定 35 的光标规则一样，这五项都只由单元测试套件兜着。

## 决定 40 —— 重新武装属于提交它的那一步，而字段的每一格都要净化

第四轮评审翻出三处此前几轮加进来的机构仍然不对的地方，外加一列从来没被计入的算术。四
处都记在这里，而不是折进它们各自修饰的那条决定，因为每一处都是本轮量出来的。

决定 39 加进来的重试计数器，是由一个异步判定触发加一的。把那次安装挂在飞行中，判定就在
安装结束的那一刻落地，而那可能已经是用户退出触发它的那一步、把光标停在更早某个字段中间
之后了；这一次加一会重新播种当时恰好挂载的那个字段，用户停下的光标跳到行尾，接下来的
一次 Backspace 就删掉一个他并非有意删的字符。现在只有当对话框仍然站在发出那次安装的那
一步上时，计数器才会加一：那一步在渲染期间被镜像进一个 ref，提交开始时读它。这道守卫限
定的是计数器何时移动，绝不是失败的那一步是否移动它 —— 一次被拒绝的安装，与一次只存下服
务模型而没有会话模型的安装，都仍然把它们自己那一步的字段交还回去，这正是决定 39 钉住
的那两条测试。

决定 37 把那把答案锁加在两条上报答案的分支上 —— 选项分支上的数字键，与多选据以重算自己
答案的那个 Space —— 决定 39 又向粘贴路径要了同一件事。这一行的编辑分支被留给字段自己的那
把闩，而那把闩只在一次让对话框移动了的 Enter 上武装：一次在选项行上按下、记下答案的 Enter
武装了那个暂停，却没有武装这把闩，于是整段暂停里这条分支都是开的。而它不只是插入：共享的
行模型在 Backspace、Delete 与删词上同样会写值。在多选上，答案是复核标签提交时由勾选集与打
出来的值重新拼出来的，所以暂停里打进去的字母会加宽一个 Enter 早已记下的答案。现在这条分支
会去问那把锁，并且只在多选上去问：一次被暂停拒绝提交的单选字段仍然可编辑，那是决定 39 的
第四项，也有它自己的测试钉着。

光标那一格，是两个对话框字段里唯一一处不经过净化就画出来的片段，而它两边的片段都经过
了。行模型在插入时施加的过滤会丢掉 C0 与 C1 控制符，却留下双向控制符，所以一次
bracketed paste 就能把它停在一个值里；用户正在注视的那一格于是改写了这一行余下部分的
方向：对话框显示出来的答案，不是即将提交的那个答案。现在两个字段的全部三段都净化。界只
设在画上，与它旁边那道宽度界一样：提交的值保住每一个码点。

那一行的宽度预算计入了确认框的两列外边距，却没计入同一个框花掉的两列内边距，于是在六
十列或更窄的终端上，它画出的最后两格 —— 光标那一格正在其中 —— 落在装着它们的框体之
外，渲染器要么把光标裁掉，要么折行、把对话框撑高一行，而这正是那道界存在要省下的那一
行。上方二十行处 chip 行的预算两者都计入了。这一行现在计入四列，而在终端足够宽时五十
格仍然是生效上限，与 ink 自己的字段宽度一致。

本轮没有改动的是窗口的锚点。值一旦超出窗口，光标那一格就不再画出，后续按键在屏幕上不
再移动任何东西，而截断标记被算作光标可以停的一格，于是高亮格可能画出那个标记，而不是
正在被编辑的字符。ink 的字段在宽度轴上滚动到光标处，正如决定 32 的规则已经让本移植在
换行轴上做的那样。让窗口跟着光标走，是它自己的一次改动、带它自己的测试，记在「后续工
作」里。

五条新单元测试 —— 确认对话框套件里三条，认证对话框套件里两条 —— 以及五个变异，上面每
一项行为一个。两个套件合起来一百条测试，修复就位时全绿；每个变异恰好让拥有它所拿走行
为的那条测试变红，其余不动：

| 变异                           | 变红                       |
| ------------------------------ | -------------------------- |
| 按键分支上摘掉锁的那一条       | 按键跟在答案之后的那条测试 |
| 光标格不再净化（提问对话框）   | 双向控制符光标格测试       |
| 宽度预算退回只计外边距         | 窄终端测试                 |
| 重新武装上摘掉步骤守卫         | 迟到判定的光标测试         |
| 字段三段不再净化（认证对话框） | 双向控制符字段测试         |

机器腿在这个 head 上重跑了一遍：二十七个场景、两条腿、五十四次运行，没有一次报错。七十八
个检查点里，十九个的非空内容行完全一致，五十九个分歧；把两个抽样检查点 —— spinner 的短语轮
换与流中指示符，它们装的是流逝的时间和每次 tick 挑出的短语 —— 单独计开之后，分歧带着 241
行只有 ink 画、285 行只有本移植画。与上一个 head 相比，把 banner 印出的版本号归一化掉之后，
156 个普通抓取里有 143 个逐字节一致。不一致的十三个分成两类：十个属于三族在同一个二进制的
两次运行之间会变的内容 —— 流中指示符、`/stats` 与按住短语那一行，两条腿各一份，其中四个是
抽样文件；另外三个在 `@` 补全场景的 ink 腿上，这一次运行它没有印出另一条腿印出的那条扩展刷
新提示。那条提示是已经记在后续工作里的瞬时项，而这是它第一次落在对比的 ink 一侧，而不是本
移植一侧。

于是完全一致的检查点数读作十九，而上一个 head 读作二十二，而这整段移动就是那三个检查点。

本决定记下的内容没有一处移动了帧，而这一点是量出来的，不是推出来的：提问对话框与认证场景
里没有任何一个抓取与上一个 head 不同。宽度预算只在六十列或更窄、且值长到够得着上限的终端
上才生效，而唯一一个五十八列的场景在打开任何自由文本行之前就抓取了 chip 行。步骤守卫、锁的
新条件与两处净化片段，全都要看一个按键旁边还到了什么、或者光标恰好停在哪个码点上，而没有任何
场景造出这两件事中的任一件。与决定 39 的五项一样，这四项都只由单元测试套件兜着。

## 决定 41 —— 光标从 ref 里读，而列表在 ink 环绕的地方也环绕

本轮有两类缺陷是同一个形状穿着不同的衣服：处理函数从上一次渲染闭包住的值里作答，
以及列表在两端停住而 ink 的继续绕回去。

第一类就是决定 33 的陈旧光标类，那个决定在两个处理函数上闭合了它、在其余所有地方
留着。现在它作为一类闭合了。一个二十八行的 hook 承载这个模式 —— 一个状态值旁边放
一面在渲染期间重新同步的 ref 镜像、一个跨渲染稳定且同步写 ref 的 setter、处理函数读
ref —— 而共享的 select hook 把 ref 与索引一并返回，于是每个挂载它的对话框都以同一
种方式读取。六个对话框的滚轮处理函数也读它。在状态不是光标的地方，同一面镜像被就
写在它所影子的那个值旁边：一个已勾选集合、两个标签页索引，以及认证向导的主菜单与子
菜单，各有自己的写入者。这一类对光标和这些都闭合了；它们旁边的视图与文本状态没有，
已记在后续工作里。

第二类是导航。ink 的选取列表按行数取模步进，所以越过最后一行往下会落到第一行。本移
植是夹紧的。那个跟随 ink 的辅助函数本来就已存在、并已在某个对话框里用着；现在它被
用在五个对话框文件里的十二个调用点上，而它旁边那份本地夹紧副本被删掉了。它的签名从
共享的列表项形状放宽为一个无类型的只读数组，于行是一个对话框即便行不是那个形状也能
用它，禁用判定则在它转换出的那一行上做。有一个对话框在四步里的三步上保持夹紧，因为
ink 在那里夹紧；它在第四步上环绕，而那一步 ink 是构成一个单选列表的。它自己的注释写
清了哪个是哪个，于是这种混合读起来像一个决定，而不是一处疏漏。

以帧验证，而不只靠测试：有一个场景启动时就停在最后一个审批模式上，于是列表的光标从
末端开始，而一次向下的按键必须落到第一行。一个夹紧的实现会产生两帧完全相同的画面，
所以这个场景是有判别力的。两条腿在两个方向上都以同样的方式环绕，而那些帧里唯一的另
一处不同，是决定 34 所豁免的垂直锚定。

## 决定 42 —— ink 的主题被应用了，启动时一次、每次选取时一次

本渲染器过去从不向主题层要任何东西。它的调色板在导入期由一份硬编码的暗色表面建成，
所以设置里的具名主题、对话框里选的主题、以及明暗探测，全都是失效的：无论旁边的 ink
画什么，本移植永远画同一组颜色。这是一个功能缺口，而不是外观缺口，而且它把下游每一
处色差都藏住了。

现在有两个调用点应用当前生效的 ink 主题。一个在启动时，放在延迟的自动主题探测排空
之后，于是它映射的主题就是 ink 最终定下的那个，首帧就已经是正确的。另一个在主题选取
处理函数内部，在共享主题管理器提交之后，于是一次选取无需重启即生效。映射本身补上了
它原先没有携带的五个 token：审批模式外框背后那两个减淡的状态色、shell 模式背后的符
号色，以及 composer 外框与 banner 信息面板背后的聚焦与默认边框色。两个表面上每一个
都有值。

明暗模式的那两个辅助函数仍然没有调用者。主题层是经由 ink 主题到达本移植的，而 ink
主题自己就带着明暗，所以这两个辅助函数是通往同一目的地的第二条路，而没有任何代码在
两者之间做选择。已记在后续工作里。

以帧验证，做法是把一个具名主题钉进隔离的设置目录里。在它之下，本渲染器的调色板与语
法 token 都离开了默认主题那次运行产生的值，所以这条接线被证明确实把一个主题带了过
来，而不只是确实跑了。banner 字标原先被当作这条证据引用，而那是错的：当时它的色标
仍是硬编码的，两项都不跟随主题，这就是决定 47。

## 决定 43 —— 五处 token 级色差，以及一条没有哪个出厂主题能显示出来的分隔线

应用主题之后，下一层显形了：形状画对了、token 用错了的行。找到并改正了五处，每一处
都是靠读画那一行的 ink 组件，而不是靠肉眼配色。

两侧的消息元数据都用了链接 token，而 ink 用的是强调 token；在默认暗色表面下这两者恰
好同色，这就是它一直活到某个主题把它们分开为止的原因。目标卡片的颜色表是在导入期用
调色板对象的值建起来的，所以它装着任何主题被应用之前的那份调色板，此后从不变动；现
在它把卡片的颜色名映射到一个调色板键上，并在绘制时读调色板。footer 的状态行用的是
减淡色，而 ink 用强调 token 画它们。footer 的审批模式标签是一种颜色，而 ink 按模式
着色；它的提示行是作为单个拼接字符串截断的，于是把终端收窄会把那个带颜色的标签整个
丢掉，而不是把它切断；提示现在是一列带颜色的片段，按同一份预算逐片段截断，而 ink 做
的那两处拼接 —— 片段之间那一处，以及排队徽标之前的那个单空格 —— 都只在它们两个邻
居确实都在场时才发出。工具卡片的状态字形过去是粗体，而 ink 的不是。

第六行把同一对 token 用反了：认证向导里的一条分隔线，用减淡 token 画，而 ink 用默认
边框 token。它换过来了。与这次对调一起记下的是，没有哪个出厂主题能把它显示出来。十
五个内置主题里有十一个不向主题构造函数传语义 token，因此走构造函数的推导，而那条推
导把这两个 token 都读作颜色集里同一个灰字段；确实传了一份共享语义集的那四个，把这两
个 token 读作那份语义集里同一个灰字段；省略它们的自定义主题也走推导。于是这次对调只
在某个用户自定义主题恰好只设了两者之一时才可观察。它是一个真实的分歧和一个正确的修
复，而在本仓库出厂的任何主题上它都不移动一帧。

颜色的验证方式是读两腿各自产生的那份带样式抓取。在一个真彩终端里，banner 信息面板
外框在两侧携带同一个源十六进制值，所以决定 42 的接线确实到达了屏幕，而这五处 token
对调确实落在了正确的值上。banner 字标在同一帧上也读过，并且不一致：两侧的色标采样
方式不同，这就是决定 47。在一个 256 色终端里、在一个具名主题下读过的那次，外框分歧
的原因是两侧把十六进制值降采到索引用的是不同的规则，而字标从它第二个着色列起就分歧
—— 索引 212、218、182 对 68、104、103 —— 那是决定 47 那个源色标差异透过降采样显出
来，而不是第二条降采样规则。继决定 32 的光标格之后，本轮清扫只在这几类行上读过颜
色，而它是一个比其余结论所依赖的几何更窄的维度。降采样的分歧属于两个库而不属于本移
植，已记在后续工作里。

## 决定 44 —— 结算的子 agent 就是一行摘要，并且没有花名册卡片

一个跑完的前台子 agent 过去会把它的结果正文整个画出来，而 ink 只画一行：一个字形、
agent 的名字，以及把描述与它的工具数、它自己的子 agent 数、耗时和输出 token 数拼在
一起，未完成时再加上终止原因。本移植既画正文又画卡片，于是一个已结算的 agent 占着
一块 ink 早已交还的屏幕。

摘要在事件适配器里推导，用的是 ink 自己那个辅助函数所用的同一批片段，并且只对到达
三种结算状态之一的运行推导 —— 一个在跑的子 agent 完全不画摘要。统计它的子 agent 数
以 ink 的工具消息所用的同一个名字集合为键，而那个集合被移到一个共享模块里，于是两侧
无法漂移。这一行在屏幕上带三段颜色，与 ink 一致：字形用色调色，名字用主文本色并加
粗，其余减淡并按共享的结果长度规则截断。

花名册卡片随之而去。任务结束事件收窄为一个标识符，两个模型层现在都在它到达时把那张
卡片剪掉，于是结算那一行就是摘要、别无其他。卡片的完成标志与它的统计字符串过去也只
被读来构造摘要现在构造的那一行，而它们旁边那个本地 token 格式化函数有一个共享的等价
物，所以三者都被删掉，而不是留着没人引用。

## 决定 45 —— 思考正文是 markdown，而它的标签带着流逝时间

一个展开的思考过去把它的文本印成一段减淡的连续文本。ink 把同一段文本经 markdown 组
件渲染、并用次级文本色，这会把纯文本*和*标题都画成那个颜色，同时让行内代码与链接保
留它们自己的颜色。于是一个思考里的标题在这里读作正文、在那里读作标题，而一个链接在
这里彻底丢了颜色。

正文现在是 markdown，放在一个由状态字形所占的那同样两列缩进的盒子里，于是正文拿到
的是 ink 自己的宽度，而不是跑到那个沟槽底下。这个宽度是量出来的，不是推出来的：盒子
里一段不断开的连续字符在第 94 列断开，而这正是同一终端宽度下 ink 的正文被给到的宽
度。盒子决定不了的是 markdown 在一段普通散文里把行断在哪里，而那里两侧不同；这处不同
记在后续工作里。因为渲染器自己的行内文本 token 会压过一个元素的前景色，一个减淡的正
文需要它自己的 token 表：在每次应用主题时，就在语法样式旁边建一份，只把行内文本
token 与标题那几个改写成减淡色，代码与链接的 token 不动。一个省略了行内 token 的主
题会让它继续被省略，于是无颜色主题仍然像 ink 一样让那段文本不着色。它改写用的那个减
淡色是在调色板赋值之后读的，不是之前。

同一行上还有两件小事。它的折叠提示缺了说明这一行可以点击的那几个词，而 ink 会印出
来；它读取的那个可点击标志在唯一的调用点上被硬编码为关，所以它被去掉了，而不是被携
带着。还有一个仍在流式的思考没有耗时，所以它的挂起标签印出来时不带 ink 在每次
渲染都推导的那个流逝时间；现在这个标签在没有被盖上耗时戳时，从开始时间戳推导它。

## 决定 46 —— 三个对话框改建在共享外框上，另外两帧被改正

审批模式、思考强度与输出风格这三个对话框各自带着自己的本地外框：自己的边框样式、自
己的内边距、自己的标题颜色、自己的底栏提示位置，以及自己手写的行文本。每一处都分歧，
而没有一处是靠逐对话框修复能保持修好的。三个都改建在其余部分早已在用的共享对话框外
框、列表与底栏提示组件上，行文本由 ink 自己那些对话框所调用的同一批显示名与描述辅助
函数构造 —— 于是带编号的行现在读起来与 ink 一致，而将来对共享外框的一次改动也能到
达它们。

思考强度对话框还补上了 ink 那个用于设定作用域的步骤，由 Tab 抵达，并带着 ink 在工作
区值覆盖了正在改的那个值时印出的工作区优先告警。它在所配置强度对当前模型不可用时的那
条说明，现在带着 ink 的两个分支，而不是一个。

旁边还有两帧被改正。shell 对话框画的是方角边框、强调色标题，以及一条 ink 不印的关闭
提示，两侧还各花了一列 ink 的盒子不花的内边距；它现在画圆角边框、用默认边框色、标题
用加粗的主色、没有关闭提示，并采用 ink 自己对恢复会话的措辞。认证向导的外框比 ink 多
花一列内边距、印了一条 ink 不印的关闭提示，而它的分隔线短了二十四列；三处都改正了，
而它的链接行像 ink 画的那样带下划线并减淡。

机器腿在这个 head 上重跑了一遍，并且先做了加宽：为思考卡片、结算的子 agent、认证向
导、两个陈旧光标突发、环绕列表与一个具名主题新增了七个场景，于是矩阵现在装着三十四
个场景、六十八次运行，没有一次报错。九十七个检查点里，二十六个的非空内容行完全一致，
六十九个分歧；把两个抽样检查点 —— spinner 的短语轮换与流中指示符，它们装的是流逝的
时间和每次 tick 挑出的短语 —— 单独计开之后，分歧带着 365 行只有 ink 画、357 行只有
本移植画。于是完全一致的检查点数读作二十六，而上一个 head 读作十九。

与上一个 head 相比，把 banner 印出的版本号与 footer 印出的分支名都归一化掉之后，两
次运行共有的 152 个普通抓取里有 143 个逐字节一致。不一致的九个，分成上一次运行点名的
那同样四族瞬时项：三个在 `@` 补全场景的 ink 腿上，这一次运行它印出了归档那次没有印的
扩展刷新提示；另外六个分布在流中指示符、`/stats` 与按住短语那一行上，两条腿各一份。
这九个里没有一个属于本轮改动碰到的抓取。

六十九处分歧里多数是决定 34 所豁免的垂直锚定、记在后续工作里的超长 token 换行，或者
一张结算卡片印出的流逝时间。七个新场景的表现符合预期：子 agent 的摘要行在两腿上连它
的分隔符都一致，而环绕列表的三个检查点只在块放在哪里上不同，每一帧里光标都在列表的同
一行上 —— 从最后一行往下一次按键在两腿都落到第一行，这正是那个场景被写出来要做的判
别。思考卡片的两个检查点不一致，而其中不属于超长 token 换行的那部分，就是记在后续工
作里的 markdown 断行点差异。

## 决定 47 —— 字标渐变按行采样，色标取自主题的语义色标

banner 的字标在两腿上都带渐变，而两者不一致。把带样式抓取按格读遍字标的六行 —— 221
个着色格 —— 表明分歧有两个彼此独立的原因，缺了任一个另一个都显不出来。

第一个是用哪些颜色。本移植硬编码了基础亮色与暗色颜色集所声明的那份色标。ink 是从当
前主题的语义 token 上读它的，候选项与顺序都相同：主题自己声明的渐变（当它声明了一份
可用的时候），否则是次级、链接与强调这三个文本色，否则根本没有渐变 —— 这种情况下
ink 把字标画成不着色，而不是抛错。十五个内置主题里有十一个走构造函数的推导，因此确实
带着自己的色标。传了一份共享语义集的那四个 —— 两个 Qwen 主题与两个 ANSI 主题 —— 继
承的是基础色标，它们自己声明的渐变根本到不了 banner。本移植现在从 ink 主题按这同一组
候选项推导色标，用解析调色板的同一方式解析每个色标，并把幸存者少于两个当作没有色标。

第二个是色标怎么采样。ink 的渐变组件包住了渲染器的按节点文本变换，而那个变换每个排
版出来的行只跑一次，所以字标的每一行都在自己宽度对应的步数上建一份自己的色标。两个
色标之间的各步并不是普通插值：它背后的库先给每段播下一个对步数四舍五入的份额，再重
新配平直到各段之和等于步数，然后每段从自己的起始色出发逐步推进。本移植六行共用一份
色标，并且按最宽那一行的普通分数做插值。两个选择都错，而且错法不同：共用色标把中间
那个色标放在每一行的同一列上，而 ink 在 36 列的首行上把它放得比 37 列的那几行早一
列；普通分数则让较短的那行差一步才到最后一个色标。按行采样并用那个库自己的分段算法，
能逐格复现 ink 抓取里全部 221 个格；原先那个公式复现其中 26 个。

这段算法是重新实现而不是引入的 —— 约二十五行的量 —— 因为定义它的那个库只是作为 ink
所用组件的传递依赖到达本包，直接依赖它就意味着要声明它。它由测试钉住，用的是从抓取里
读出的十六进制值，两种行宽都覆盖；并且已经反证过这些测试在原先那个公式下会失败。

## 决定 48 —— ink 会读的两个设置项，在这里没有读取点

一轮针对「会改变 ink 画什么」的设置项排查发现两个：本渲染器从同一份合并后的配置里收下
了它们，然后一次也没看过 —— assistant 行上方那行时钟，以及把一次工具调用折叠成只剩表头
的那个开关。两者都靠读遍本包里对每个键的每一处引用来确认：唯一的读取点是 ink 自己的历
史展示。一个没有读取点的设置项比一个缺失的功能更糟，因为配置界面提供它，看上去还像是生
效了。

时钟需要在共享的条目类型上加一个时间，并且这个时间有两个来源。进行中的一轮没有已记录的
时间可读，所以时间戳是在这一块被打开时打上的，用的是折叠自己的时钟；之后追加到同一个流
式块的分片不动这个时间戳 —— 一条消息，一个时间戳。恢复出来的会话改为从录制重建
transcript，那里每条 assistant 记录带着自己的时间；而一条记录里有好几个文本片段，所以
只有其中第一个文本运行被打上时间戳，开头的一段推理不会把这个时间戳消耗掉。只上实时的那
一半正是后续工作条目警告过的分歧：一个恢复出来的会话会完全不显示时间戳。标签本身是 ink
的，逐字一致 —— 一个 24 小时制、补零、方括号包起来的时钟，取自英文 locale，这正是
`23:00:00` 不会在一台 locale 不同的宿主机上被渲染成 12 小时制的原因。

折叠用的是 ink 的规则，带着 ink 的四个例外。只有在这个设置关着、并且这张卡片没有被点开
过、并且应用级的全量详情开关没有把它按住、并且这次调用不是还在等一个答复的时候，卡片才
折叠。最后那个例外才是要紧的那个：卡片是唯一承载着待批准载荷的表面，所以一张折叠的卡片
等于让用户去批准一个他读不到的东西。ink 按卡片可点与否在两种提示之间做选择，而本渲染器
除屏幕阅读器模式外都开着鼠标追踪，于是取可点的那一支，只提点击 —— 这与思考卡的提示早已
做出的选择是同一个。

两半都由测试钉住，并且已经反证过它们在原先的行为下会失败：去掉设置项这道门、去掉待答
复这个例外、给每一个文本运行都打时间戳而不是只给第一个、读一个 12 小时制的时钟、以及在
只有一种可供性生效的地方把两种都说进提示里 —— 每一处都打破断言，且只打破那些断言。

## 决定 49 —— `@` 补全问遍 ink 会问的每一个来源，并排在 ink 的标签页后面

本渲染器的 `@` 补全只问文件索引，别的什么都不问。ink 还会补全当前项目过往的会话、MCP
服务器及其资源、以及已安装的扩展；并且在超过一类候选在场时，画一条标签栏在它们之间切
换。

搜索本身是复用而不是重新实现的。ink 的补全 hook 收一个模式与两个回调，其余全都归它管：
爬虫的生命周期、承认一次搜索「慢了」之前的那段短延时、取消一次已被更新的按键取代的搜
索，以及它自己写成不变量的合并顺序 —— 会话在每一条路径上都是最后追加的。重新实现它就
意味着在第二个地方把这条不变量抄一遍，而这个 hook 里没有任何与渲染器相关的东西。没有
复用的是 ink 的导航状态：它自己保存高亮下标与可见窗口，而本 composer 两者都已经有了，
并且是按「在一次渲染里处理完的一批按键」下也能成立来建的。所以只移植了分类规则 —— 固
定的标签顺序、一份结果集所蕴含的标签集合、过滤、环绕步进，以及当一份更新的结果集不再包
含屏幕上那一类时退回第一个标签。最后这一条是在渲染期间推导出来的，而不是事后再纠正，这
样省一趟渲染，而看上去完全一样。

复用这个 hook 暴露出一个本地搜索从来没有过的隐患。离开 `@` —— 缓冲区被清空、改为输入
斜杠 —— 会让这个共享 hook 派发一次重置，而那次重置的发布落在同一次按键已经把斜杠结果
发布出去的那趟渲染之后，把它们抹掉。所以两个被转发出去的回调都以本 composer 实际所处的
模式为门，而这个模式是在处理按键时同步更新的。这道门还为 `@` 关上了一个 ink 自己仍然有
的隐患：一次在缓冲区被清空之后才解析完的搜索，再也不能在空 composer 上重新填出一个下拉
并把下一次 Enter 抢走。shell 模式那个按键上的守卫留着，因为斜杠参数补全仍然是本地驱动
的，仍然可能与之竞态。

画法上有两处跟 ink 而不是跟本渲染器的斜杠列表：标签栏只在它自己出现的时候才拥有裸的左
右箭头，并且把每一个修饰键都钉成关，好让按词移动与任何终端绑定仍然到达缓冲区。以及在
mention 模式下，只有带描述的那些行共享标签列 —— 一条裸路径占满整行宽度 —— 而在斜杠模
式下每一行都共享一列。标签文案是从 ink 自己的列表组件里导出的，而不是抄一份，这样两个
渲染器不可能在一处翻译上各自漂移。

## 决定 50 —— 卡片标题是一个换行块，而两个状态共用一个树形

对决定 48 接上的那次折叠做帧验证时，翻出了工具卡片标题上的两个缺陷，其中一个是只有帧才
能显示的回归。

第一个是折叠态卡片自己的树形。折叠与展开返回的结构不同，而本渲染器的 React 绑定按位置
与类型复用子节点、并且从不清除一次重渲染丢弃的 prop —— 也就是决定 11 点名的那个隐患，
而且是它那次普查判定为不受影响的点位之一：折叠分支会设一个展开分支从不设的宽度，正是
移除那一种情形。于是承载两列状态字形的那个盒子被复用到了展开态标题行所用的盒子上，保留着当初给它的宽度，
展开的卡片只画出字形与工具名的第一个字母，其余全被裁掉。两个状态现在返回同一个树形：同
一条标题行，折叠时把名字与提示分成两段、展开时合成一个换行块，卡片正文在折叠时干脆不出
现。有一个测试钉住 jsdom 能看到的那部分 —— 切换前后标题行是同一个元素实例，而字形那个盒
子是唯一一个带宽度的后代 —— 两个树形再分开一次它就会失败。宽度残留本身是单元测试运行时
无法复现的渲染器行为，它是从终端上读出来的，修复之后也用同样的方式确认它消失了，包括经
过一次 resize。

第二个是展开态标题自己的布局。它原本是几个并排的文本节点：名字、描述、标记一个等待中调
用的箭头。flex 兄弟节点复现不出 ink 画出来的东西，因为 ink 把名字与描述当成一个换行块，
其宽度是标题自己的内宽 —— 卡片宽度减去状态字形占掉的那两列。由此带来三个后果，每一个都
在帧里看得见：描述的前导空格丢了，于是名字与命令连在一起；续行缩进八列，而 ink 缩进四
列，因为兄弟节点是从名字之后开始，而不是从名字下方开始；箭头落在这一行结束的地方，而不
是块的最后一个字符之后。标题现在是一个承载内联样式段的文本节点 —— 名字加粗，描述与箭头
暗色，箭头用 ink 给它的主色 —— 于是换行由渲染器自己决定，几何也就对上了。块的宽度与截断
helper 用来算行数上限的那个值同源，这也是上限与绘制现在能一致的原因。

还剩两条残差，它们记在各自的条目下而不在这里：名字与描述之间那一格在 ink 里不着色、在这
个端口里着暗色，也就是未着色文本那条分歧；以及比块还长的 token 在这里仍然断得比 ink 早，
也就是长 token 换行。

带时间戳的助手行拿到了同一个解法，因为它的两个树形以同样的方式相异，而在两者之间做选择
的那个设置可以在对话框里改、且不需要重启 —— 于是一条已经画在屏幕上的行会在会话中途换树
形。它的分支现在各带一个 key，有一个测试钉住要紧的那部分：翻转之后未打戳的那一行是消失了
而不是被就地改造，而这条断言在 key 被拿掉时就会失败。

机器腿在这个 head 上重跑了一遍，先加宽了五个场景：时间戳与折叠卡片同时在场、`@` 的分类、
离开自动 recap、编辑器对话框，以及会话选择器的 Space 预览。矩阵那时有了四十三个场景与八十六次
运行 —— 三十八个在 100×40、三个转录臂在 100×30、窄启动在 60×24、chip 行在 58×40 —— 没有
一次报错。有九次以 idle 超时结束、而不是落在一帧稳定的画面上，而这九次全是一直都会超时的
那几条腿：ink 上认证向导的模型列表（它的 spinner 永远不进入 idle），以及两个多问题臂。

一百三十一个检查点里，三十三条的非空内容行完全一致。其余九十八条由一个家族主导：上下文文件
通知里那条路径长到本身就是一个不可断的 token，两条腿在不同的列上断它，于是几乎每一张画出这条
通知的帧都画得不一样。把通知与它折行成的那些路径碎片从两条腿都丢掉之后，剩下七十三条一致、
五十八条分歧，其中两条是采样型检查点 —— spinner 的短语轮转与流式中途的指示器。把这两条分开
计之后，其余携带 258 条只有 ink 画的行与 288 条只有本端口画的行。这个拆分正是覆盖边界里撤回
的那一个：从这些帧上复现不出来。下面那份家族清点是按它数出来的，作为那一轮自己对家族的判读
保留，而不是一个当前的计数。

这五十六条按主因落在十一个家族里，其中四个是本轮新出现的。九条是非确定性的，任何修复都闭不
掉：两个采样型检查点、两条单帧的 spinner 短语、时间戳场景那三张时钟自己走了的帧，以及子
agent 那两帧上的耗时毫秒数。十九条是决定 26 —— 本端口还显示着 ink 已经滚出去的 banner，于是
同样的内容落在不同的行上。十条带着一个更早的轮次没有显示过的缺陷：通知行留着它顶掉的那条
banner 行的字形，因为渲染器从不重绘一个「新内容是空格」的格子。四条是一个不拉伸的对话框 ——
ink 把它的审批模式框撑到视口剩下的全部高度、并在框内填满空行，本端口按内容撑高，而框内每一行
都逐字相同。四条是卡片标题的长参数折行，四条是行尾那个滚动条字形，两条是一个滚动偏移量，
两条是同一行出现的顺序不同，两条是两条腿对截断的分歧，一条是展开的思考正文的缩进，一条是
受门禁的服务器对话框里段落续行的缩进。

垂直方向的对比不再报告，因为决定 26 已经让它失去意义：本端口把 composer 钉在视口底部，而 ink
钉在顶部，于是 129 对重建帧里有 128 对只在位置上有别。内容行才是那个决定之后仍然成立的对比。

## 决定 51 —— 编辑器对话框在用户看得见的地方报告一次失败的保存，而它的两个列表就是那个共用的带序号窗口

`/editor` 经由共用的 settings 对象持久化一个偏好，而那次写入是可能抛错的 —— 一个只读文件、一个进程够不到的作用域。ink 会接住这个失败并把它打印在对话框内，于是用户读得到为什么什么都没变，而对话框仍然开着、可以换一个作用域再试。本渲染器把它吞掉了：catch 在出错路径上和成功路径上一样把对话框关掉，于是一次失败的保存与一次成功的保存无从分辨，而那个偏好就悄无声息地没有动。写入现在改为记下一个错误字符串而不是关闭，字符串渲染在外框上方的红色里，对话框留在挂载状态。有一个测试驱动一个会抛错的 setter，并断言两半 —— 屏幕上的消息与仍然开着的外框 —— 当 catch 退回到「关闭」时它就会失败。

对话框里那两个列表原本是手画的行，这让它们丢掉了这里其余每个列表都有的序号列与滚动窗口。两者现在都走共用的 select hook 与控件，于是编辑器步骤与 Apply-To 步骤给自己的行编号、把它们开窗而不是撑出外框、并跨过被禁用的那一行而不是落在它上面。这个控件就是确认对话框用的那一个，所以编号、高亮与滚轮都与本移植的其余部分一致，而不是一次性的写法；编辑器列表还会在用户从 Apply-To 回来时，把光标重新落到所选作用域已存的偏好上，这正是 ink 给自己那份列表键控的方式。

对话框原本在两列之上画了一行自己的标题，而它底部的提示会折到第二行，ink 则把它截断在左列之内。标题行没有了 —— 两个列头现在就是顶行，与 ink 一致 —— 提示被裁到该列自己的预算：内容宽度的 45% 再减去两列内边距，这正是 ink 放它的那个 truncate 盒子。测试分别钉住两半：对话框没有自己的 chrome 标题行，且提示被裁进左列、带单个省略号，而不是折行。

## 决定 52 —— `/resume` 与 `/delete` 共用 ink 的会话选择器，而删除提交一组勾选

`/resume` 与 `/delete` 各画各的会话行，两者都不匹配 ink 为二者挂载的那个选择器。这些行现在是同一个组件，建在 ink 的 SessionPicker 所用的同一批部件之上、而不是另起炉灶：共用的过滤器与分页大小、相对时间与消息数格式化器、截断 helper，以及带可打印字符判定的搜索输入 hook。一行携带两列的光标标记 —— 在窗口边缘处是一个上或下箭头 —— 被裁到自己预算的标题，以及一条按 ink 顺序排出的元信息行：相对时间、消息数、分支与禁用提示。可见窗口由终端高度以 ink 派生它的同一方式派生，所以列表会滚动，而不是冲出外框。

删除还缺 ink 的批量路径。它现在以多选打开来挂载选择器，并为单个与批量两种情形复用 ink 自己的删除命令，于是「不许删当前会话」的守卫、互斥锁，以及每一条结果消息都是共用的，而不是重新措辞。Enter 提交那组勾选，按完整列表排序、并过滤到启用的行，所以一次缩窄视图的搜索绝不会悄悄丢掉打字之前做出的勾选；当前会话被就地禁用而非过滤掉，与 ink 一致。resume 保留单选选择器，并在 `/resume <title>` 匹配到多于一个会话时带上该命令预过滤的列表。光标与勾选集合都坐在 ref 镜像之后，于是一次读取里的一串 Space 与方向键提交的是用户真正勾上的那组，而不是上一次渲染画出的那组。

结构与批量路径由针对渲染行的测试钉住 —— 两行形状、未知计数那一例、勾选框提交、被禁用的当前会话、多选关闭时藏起的勾选、窗口边缘标记与分页 —— 每一个都被证明会对着先前手画的行失败。选择器自己的高度仍然是固定的、而非按内容定尺寸；那记在后续工作下、而非在这里改动，因为它属于决定 16 描述的那个间距家族。

## 决定 53 —— 认证向导的模型步骤以颜色聚焦、以八行为窗，装在 ink 的方角外框里

引导向导的模型步骤原本在被聚焦那一行旁画一个 `›` 光标字形、一次列出每一个推荐模型、且没有搜索框。ink 的模型步骤这三样都不做：它只以颜色传达聚焦、把列表开窗到八行、并放一个一次 Tab 之遥的搜索框，随用户打字过滤推荐项。这个步骤现在对上了 —— 字形没有了，被聚焦的行是绿色，而一个已勾但未聚焦的行取 accent 色、一个普通行取正文色；列表是过滤后模型的一个切片，上限为 ink 共用的那个八行常量，并随聚焦移动而滚动；搜索框用 ink 自己的选项标签与搜索文本 helper，所以各行读起来一致、也不可能在一处翻译上各自漂移。那些常量与 helper 是从 ink 的 provider-setup 模块引入的，而不是抄一份。

对话框的外框原本是圆角、和这里其余每个对话框一样，但 ink 用单线边框给它的认证对话框描框，所以向导现在向共用的 shell 要方角、而把本移植的其余部分留成圆角。它还缺 ink 为「一个不带任何推荐模型的 provider」准备的那个分支：在列表本会为空之处，ink 把推荐与搜索整个丢掉，改而在一个自由文本框里要逗号分隔的模型 ID，并以该 provider 自己的默认值作示例。这个分支现在画出来了，而另一个「搜索为空」的结果 —— 模型存在但没有一个匹配查询 —— 用 ink 的措辞说出来，而不是显示一个空列表。

测试钉住 jsdom 看得见的部分：为一个不带模型的 provider 画出无推荐分支、空提交时浮出模型 ID 错误、搜索框在一次 Tab 之遥过滤推荐列表、以及自定义 ID 框保留它自己的光标。这个步骤本就有的那两个连击用例 —— 一次按住的 Space 把每一跳都应用到同一个勾选框、以及一次 Enter 提交在同一次读取里做出的那一勾 —— 在「只靠颜色聚焦」之下仍然通过，而这正是字形回来、或窗口不再滚动时会失败之处。

## 决定 54 —— 描述型列表把描述堆在标签之下，并用绿色标记被选中的那一行

有三个对话框画一种列表，其行携带一个标签、下面跟一段描述 —— 认证向导的那几个 radio 步骤，以及 arena 的停止与选取对话框。三者都把描述多缩进两列、越过它自己的标签，因为描述坐在一个从标记之后开始的兄弟节点里、而不是在标签之下；三者也都用正文色标记被选中的行，而 ink 用绿色。每一行现在是一个两列的盒子：一个固定两列、装着 `›` 或一个空格的标记，旁边一个单一的、增长的列，把标签与描述堆在一起，于是描述与标签对齐、而不是越过它。被选中行的标记与标签取 ink 所用的那个 success 绿，而未选中的行保持正文色、描述为暗色。

这处改动是从三个对话框自己测试里渲染出的行读出来的，那些测试拿描述的列去对比标签的列、并断言被选中行的颜色。行间距没有动 —— 这是缩进与颜色，而不是行与行之间的节奏。

## 决定 55 —— 离开自动 recap 之所以会触发，是因为入口挂载了 ink 容器所挂的那个 hook

ink 会在用户回到一个被闲置超过阈值的会话时触发一次 recap：它的容器挂载一个 hook，盯着聚焦与闲置两个边沿，并在回来时追加一行摘要、把它记录下来。本渲染器从不挂载那个 hook，所以离开自动 recap 从不触发 —— 设置存在、hook 存在，而两者之间什么都没有跑。这个 hook 现在挂在入口里，而那正是实时 transcript 与「流式→闲置」边沿已经在的地方，所以它的门禁读得到它需要的行、无需第二份副本。聚焦来自本渲染器自己的一个新 hook：@opentui/core 已经解析终端的 focus 与 blur 事件，但没有任何东西把焦点上报打开，所以这个 hook 为 OpenTUI 这条腿拥有 `?1004` 模式、以聚焦为起点、并在任何一次按键上重新主张聚焦 —— 这是 ink 自己的 tmux 变通，因为一个不转发焦点事件的会话否则会永远停在 blur 上。任何时候只挂载一条腿，所以两者绝不会都去写这个模式。

hook 返回的那次 recap 落成它自己的一个 transcript 条目，它会先停住一个正在流式的 assistant 块、再追加摘要，所以它不会拼接进一个仍在进行中的回合。这个 hook 自己把那次 recap 记录下来 —— 一个 `/recap` 命令的 result 阶段、绝不是 invocation 阶段 —— 与手动命令一致，于是自动触发的那次摘要以同样的方式到达会话日志。一个恢复出来的会话是否会重画它，是后续工作下那条已经记着的 result 阶段重放缺口，那条覆盖每一个 slash 命令的 result 行、而不单是这一条。

测试覆盖聚焦 hook 的各个边沿 —— 挂载时写入、卸载时清除的那个模式，focus 与 blur 事件，按键重新主张，detach，以及一个会抛错的 stdout —— 还有 recap 条目向 transcript 的投影。hook 自己的触发是 ink 的共用代码、在那边被测；这个决定加的是挂载、聚焦来源与那个条目，各自在这里钉住。

## 决定 56 —— footer 的模型段带上 reasoning effort

ink 的状态行渲染一个 model-with-reasoning 预设项，所以它的模型段在名字旁边带上 reasoning effort —— 或者在模型没有时带 `reasoning off`。本渲染器的 footer 打印的是裸模型 id、丢掉了 effort。这一段现在走 ink 预设所用的同一个共用格式化器，它剥掉一个前导的 provider 标签、在有 effort 时追加它、并在 reasoning 被显式关掉时说 `reasoning off`。effort 来自本移植其余部分所读的同一个显示 helper，所以 footer 与任何其他点名模型的面都一致。

有一个测试拿这一段去对比预设的输出 —— 一个 reasoning off 的模型读作它的名字后跟 `reasoning off` —— 而这正是 footer 退回裸 id 时会失败之处。这处分歧最初是从一张重建帧上读出来的，那时两条腿的模型段恰好差一个 effort 后缀。

## 决定 57 —— 指针跟随 `ui.mouseTracking`，两条展开提示也是

ink 在两处读 `ui.mouseTracking`：它决定渲染器到底抓不抓指针，也决定一张折叠卡片显示两条展开提示里的哪一条 —— 鼠标生效时是 `click to expand`，不生效时是 `ctrl+o to expand`。本渲染器两处都不读。它创建渲染器时指针永远开着，而两条展开提示 —— 折叠工具卡的与思考卡的 —— 都把 clickable 分支硬编码下来，所以它们即便在 `ui.mouseTracking: false` 之下也宣传一次点击，而这个设置在这里根本没有读取点。现在两处都读它：设置关掉时渲染器创建时不抓指针，于是右键菜单与 OSC 8 链接点击被交还给终端、和 ink 一样；并且一个活的鼠标标志被接进 transcript，好让每条提示取匹配的那个分支。

提示跟随 ink 自己的选择、而不是一条新规则 —— 指针生效时可点、不生效时只留按键 —— 这正是思考卡的提示本就做出的那个判断。这个标志默认为生效，所以默认设置在屏幕上什么都不改；把它关掉会一次从两条提示和指针上同时拿掉点击可供性。决定 48 是在「鼠标在这里除了屏幕阅读器之下都是开的」这个假设下取 clickable 分支的；这个决定把那个设置做成该分支上的第二道门，而决定 58 补上屏幕阅读器那条腿。

两个方向都在真机终端上确认过：一个把设置关掉的专门场景在两条腿上都不显示点击可供性 —— 折叠卡与思考卡都读作 `ctrl+o to expand` —— 而同一个 bundle 在默认设置下仍然提供点击。单元测试在它旁边钉住接线：设置关掉时 transcript 收到的标志为 false，且每条提示的文案跟随它。

## 决定 58 —— 屏幕阅读器会话留在 ink 上

屏幕阅读器模式需要主屏幕上的纯文本、只追加、无鼠标的输出，好让屏幕阅读器在每一行落下时读它一次。本渲染器没有为此的路径：它在备用屏幕上原地绘制、带差分重绘和一个活指针，而这些屏幕阅读器解析不了。在这个标志下服务 OpenTUI 会把原地重绘塞给这样一个用户，那是比没用还糟。所以渲染器选择门禁现在把屏幕阅读器模式当成第二项「仅 ink」的能力，与它本就有的运行时探测并列：标志打开时门禁留住 ink，而在 strict 模式下它抛错、而不是静默回退。

这道检查坐在运行时探测之前、并压过它，所以一个跑在无法初始化原生 FFI 的运行时上的屏幕阅读器会话，仍然报屏幕阅读器那个原因、而不是 FFI 那个 —— 是这项能力、而不是平台，才是 ink 在服务的原因。入口把配置好的屏幕阅读器标志传进门禁，所以这是一个活的开关、而不是一个死参数。本渲染器带着的那两个纯文本与屏幕阅读器策略模块仍然没接线：它们只被自己的测试引入，而把它们穿进一条渲染路径是后续工作、不是这次改动。这个决定就是那道门禁，在它们接好之前把这类会话留在 ink 上。

测试钉住回退与它的原因两者，而一个把屏幕阅读器检查挪到运行时探测之后的变异，会让「在不受支持的运行时上屏幕阅读器原因胜出」那个用例失败。在真机上，strict 模式抛错时点名 screen-reader 而不是 FFI；在一个受支持的 bun 运行时上，一个屏幕阅读器会话留在 ink 上，而不带这个标志的同一次运行则服务 OpenTUI。

## 决定 59 —— Space 预览一个会话，并且它是自己的一棵树、而不是装在列表外框里

决定 52 建起来的那个选择器只能对光标之下的那一行动手。ink 的选择器有第二种模式：Space 载入高亮的会话、并用一个预览把列表换掉，好让用户在承诺恢复或删除之前先读一段转录。这个模式在这里是缺席的，于是 `/resume` 成了在一堆标题里盲选，而选择器自己那条 `Space to preview` 提示什么也没在承诺。

预览是作为它自己的一棵树返回的、而不是作为换掉列表外框内正文的结果，因为 ink 的预览根本没有外框，而它的转录铺满整个内宽 —— 装进带框外壳里的一个更窄正文，既对不上几何也对不上阅读宽度。两棵树都带一个 key，而这是承重的、不是装饰性的：本渲染器从不清除一次重渲染丢弃的 prop，那正是决定 11 记录的那个失效，所以只把带框列表那个盒子的 border style 省掉再返回，边框仍然画在屏幕上。给两种形态不同的 key 强制卸载、而不是复用。

转录来自重放被恢复会话的那些事件、且不传 config，于是一个工具组退化成只有它的名字。这不是抄近路 —— ink 的预览把 null config 传给同一个构造器、得到同一种退化，所以两边对「一个预览愿意显示什么」的判断是一致的。那一行元信息在列表条目自带计数时用它、否则在载入的会话里按 user 与 assistant 的唯一 uuid 计数，那是 ink 自己的兜底；而它把各段排成计数在前 —— 与行那条时间在前相反，这也仍然是 ink 的做法。

预览挂起期间它独占整个键盘：选择器的处理器在读任何别的东西之前就返回，所以敲一个字母起不了搜索、按方向键也动不了一个已经看不见的光标。Esc 与 ctrl+c 回到列表，光标、勾选与查询原样不动；Enter 恢复被预览的那个会话。一次在用户已经离开之后才 resolve 的载入会被丢弃、而不是画在他已经转过去看的东西上。这个模式只给 `/resume` 挂上。`/delete` 跑的是多选模式的选择器，那里 Space 是复选框的切换键，而多选打开时预览一律关闭，所以两者从不争同一个键。

ink 的两个守卫没有被移植过来，这是有意的。它的选择器在一个调用方同时要求多选与预览时会抛异常；端口对同一个请求的处理是优先多选。两个生产调用方都没有同时要求两者，而一条优先级规则在可观测层面不损失任何东西，抛异常却会把一次接线错误变成一次崩溃。它的预览还以「会话服务存在」为门，而那个模式已经把选择器自己的按键关掉了，所以服务缺失时 ink 的选择器没有任何办法退出一个它画不出来的模式；这里无论如何 Esc 都回到列表。

ink 自己的预览带一个没有被移植过来的缺陷。它的加载分支是一个普通盒子、而它的就绪分支是一个 static 块，两者的高度差让 ink 擦掉它已经写进 static 区域的内容、并把屏幕滚动好几行：这轮扫查在 ink 腿上抓到的那一帧是空的，而它旁边的原始字节流里带着整段转录。端口让两个状态共用一种形态，于是擦除与滚动都不可能发生。ink 腿的 static 输出仍然被当作意图布局的参照来读，而移植过来的正文在相同的列上换行、在相同的词上断开。

九条用例在渲染出的行上钉住这个模式：换树与它的 Enter、保住光标与查询的那次 Esc、预览对键盘的独占（ctrl+c 是退出而不是取消）、两条错误文案、按 uuid 去重的计数、多选下 Space 仍归复选框、一个没有 opt-in 的流程什么都不画、以及一次迟到的载入被丢弃。两个场景在真机上覆盖它 —— 一个断言预览的帧、它无框的几何与 Esc 之后逐字节相同的列表，另一个断言 Enter 真的把会话恢复进主转录、而不只是关掉对话框。未在真机上验证的：两条错误分支（要触到它们需要一个损坏的会话文件），以及一段比视口更长的预览内部的滚动。

## 决定 60 —— 行字形之后那一格是一个列、而不是一个字符

用户行与助手行都把各自的状态字形和它后面那个空格打在同一个文本节点里，旁边是一个承载正文、并且会生长的兄弟节点。当正文长到要换行时，那个兄弟占满整宽、尾随的空格就被挤掉，于是一条回答读起来是 `◆︎Answer`，一格间隔都没有。帧矩阵此前从没显出过它，因为每一个被播种的正文都短到给那个空格留了地方；决定 59 加进来的预览是第一个把一条刻意会换行的回答放进转录的东西。

那一格现在是一个只装字形的定宽盒子，宽度取自工具卡片状态列用的同一个常量，所以它不能被一个需要地方的兄弟换走。这与 warning 行当初那个失效是同一个，修法也是同一个；这个形状值得有一处归属，而不是每一行重新发现一次。

一条测试在两行上钉住它 —— 字形坐在它自己的两列盒子里、且不带任何首尾空白 —— 而任一行改回内联空格都会让它失败。暴露这个缺陷的那一帧现在显示出那一格，并且在 ink 换行的那些列上换行。同族里有一行是刻意没动的：子 agent 摘要行也把它的字形和空格打在内联，但它那三个兄弟全是纯文本、没有一个会生长，所以挤压够不着它。改它会是在猜一个没有任何帧显示过的缺陷。

## 决定 61 —— harness 按 side query 自己的标记路由它，而不是按主 agent 标记的缺席

对比 harness 用一个假端点应答每一个请求，而这个端点服务的东西比场景脚本里那段对话多得多。一个轮次之后可能跟着一次会话 recap、一条跟进建议、一个标题、一次 next-speaker 判定、一次记忆召回、一次压缩，以及 —— 当工作区打开了托管记忆时 —— 一个会读写文件的抽取子 agent。只有主轮与它派生的子 agent 才该消费场景的响应表；一个吃掉表项的 side query 会把之后每一条回复静默地挪一位，而产出的那一帧看起来像是渲染缺陷、而不是 harness 缺陷。

第一个判据是主 agent 的 system prompt 前缀，不带它的请求被当成 side query。这个判据的形状就是错的，因为那个前缀不是一个字符串：每个子 agent 带的是它自己定义给它的那份 prompt，于是一个内置的 general-purpose agent 与用户的一个 `.md` agent 各不相同，而枚举它们不是 harness 能保持为真的事。子 agent 那一帧丢掉了自己的回复。

替代方案 —— 「流式且带工具声明就是 agent 会话」—— 更糟，因为它看着像一条关于线上的规则、其实不是。托管记忆抽取子 agent 既流式又声明工具；它在每个意义上都是子 agent，只是属于记忆特性而不属于这个轮次。它拿走了场景写给第二条回复的那个表项，于是 recap 场景在等一条已经被花掉的行时超时了。跟进建议从另一侧击穿同一条规则：它逐字复用主 agent 的 prompt，只能靠最后一条 user 消息认出来。

所以判据反过来跑。每类 side query 由它自己拥有的标记认出 —— recap 自己的指令、建议的模式头、压缩的指示语、抽取子 agent 的 system prompt —— 而不带流式的请求就是一个 JSON 类 side query。其余一切都是 agent 会话、吃响应表。side query 拿到的三种应答是 recap 的文本、一个空字符串（空字符串在这里同时意味着「没有建议」与「无需压缩」），以及那份罐头的空召回 JSON。按正向标记而不是按某个标记的缺席来路由，正是让这个 harness 能扛住一类新 side query 的原因：一个没被认出的会落进 agent 桶、把一条回复挪位，而这会在帧上显形；它不会被静默地用一张它本来就不该读的表应答掉。

重跑在行为与路由两侧都确认了这一点。子 agent 场景从两分钟后报错变成十二秒落定，recap 场景从在第二条回复上超时变成十七秒落定。随后全量矩阵发出的每一个请求都被归了类：八十个主轮与两个子 agent 轮吃了表，二十六个 JSON 类 side query、两个 recap 与五十六次建议调用没有。没有任何一个表项落到 agent 会话之外的东西上。

## 决定 62 —— 调色板带上一个版本号，因为 banner 的 memo 看不见一次重绘

决定 42 让主题活了起来，决定 47 把字标的色标从它身上取了下来，而这两者之间留下了一个启动帧不可能显出来的洞：banner 是被 memo 化的，而一次主题选取所改变的东西，没有任何一样出现在它的依赖列表里。调色板是一个被原地改写的对象，所以它的身份在 `/theme` 之后依然存在；主题管理器写入的那个 settings 对象同样是被原地改写的，所以它的身份也依然存在；而 config 根本没被碰过。于是一个已经挂载的 banner 会继续画它被构造时拿到的那条色标与那个边框色，只有一次改尺寸或者一次重启才能把新主题带进来。矩阵抓到的每一帧都是主题已经应用之后启动的，这就是它熬过这轮清扫的原因。

调色板现在带一个版本号，由两个改写函数各自递增，而 banner 的 memo 依赖它。一个模块作用域的计数器不是 hooks lint 认可的依赖 —— 它会警告说改写一个外层值不会让任何东西重渲染 —— 所以这一行带着一条抑制注释，理由就写在它旁边。这条抑制是诚实的，而不是绕过规则的手段：重渲染来自主题选取处理函数自己那次状态写入，而计数器要告诉 memo 的是，它闭包里的那些值已经在它底下被重绘过了。

有一个测试重绘一个已挂载的 banner —— 同一组 config 与 settings 对象在一次主题变更前后被一直握着，而字标的第一格在前后各断言一次。把计数器从依赖列表里摘掉会让它失败，屏上仍是旧色标，而这正是证明该用例有判别力的那次变异。没有在真机上验证过：明暗那个改写函数没有生产调用点（见后续工作），所以被走到的只有具名主题那条路，而且没有抓到过一帧会话中途选取主题的画面。

## 决定 63 —— ref 镜像延伸到了决定 41 漏掉的两个处理函数

决定 41 把「读到过期值」这一类记为对光标已经闭合。它并没有。有两个处理函数在它改造的那个共用 select hook 之外，而这两处都是读源码读出来的，不是读帧读出来的。

rewind 的恢复选项列表把它的光标放在一个 reducer 里，共用 hook 够不着它。它的 Enter 读的是 reducer 的答案，而一次突发还不可能把那个答案送到：一次方向键自动重复后面跟着 Enter，恢复的是方向键移动之前高亮的那个选项。reducer 所施加的那个夹紧现在是一个两边都调用的函数，而处理函数在 dispatch 之前先推进它自己的镜像，因为在一次突发内部 dispatch 不会触发渲染，而一个在渲染期间才重新同步的镜像仍然会握着突发前的那个下标。旁边那次渲染期写入，是让镜像在 reducer 于取消与恢复失败时所做的那些复位之间仍然诚实的东西。

权限对话框的两个自由文本字段 —— 规则与工作区目录 —— 在后续工作里被列为仍从闭包读取的字符串状态，而它们是那份列表里唯一触发条件是单个手势、而不是两个含义不同的键的成员：一次粘贴路径后面跟着 Enter 会在同一次读取里到达，于是字段提交的是它在粘贴之前握着的那个空缓冲，对话框则原地不动。两者现在都坐在光标所用的那个镜像之后，这个镜像放在它自己的一个模块里、而不是塞在某一个对话框内部，而它们的退格与它们的追加也经由镜像写入，所以一次先编辑再提交的突发端到端是自洽的。仍然开着的是那些为分支充当门禁、而不是喂给一次提交的状态 —— 视图名、步骤、搜索词 —— 它们继续记在后续工作里。

三个用例钉住 rewind 的处理函数：一次落在第三个选项上的突发、一次夹紧进 `Never mind` 然后为下一次重新同步镜像的突发，以及在 diff 仍在加载时被丢弃的按键。三个钉住权限字段，其中一个在突发内部做编辑。全部六个都在修复前的代码上跑过并在那里失败 —— rewind 的突发报出第一个选项而不是第三个，而权限字段什么都不提交。两个缺陷都没有在真机上复现过：这次突发需要在一次读取里有一次粘贴或者一个按住的方向键，而 harness 打不出这个。

## 决定 64 —— 镜像延伸到了另外两处读取，而其中一处不是数字

决定 63 关掉了共用 select hook 之外的那两个处理函数。这一类还有两个成员，同样是读源码读出来的，不是读帧读出来的。

认证向导的模型步骤把三个目标里哪一个持有焦点 —— 自定义 ID 字段、搜索字段、列表 —— 放在普通状态里，而它的方向键、它的空格与它的粘贴处理函数全都从闭包里读这个状态。于是一个按住的方向键后面跟着空格，会把一个空格打进方向键早已离开的那个字段里，而不是切换它们到达的那一行。composer 的 `@` 分类标签页则从上一次渲染显示的那个标签页起算步进，所以一次读取里的三个方向键只移动了一个标签页、而不是三个。

光标镜像只搬得动数字，而一个分类是字符串联合，所以镜像被在它旁边推广了：一半管数值光标，一半管任何别的值，两半都把 state 与 ref 一起写。向导的焦点与 composer 的标签页现在坐在这两半上，而共有八个调用点从这一个模块里取镜像、而不是各自长出一个本地形状 —— 共用的 select hook、会话选择器、权限对话框、composer、认证向导，以及 MCP、设置与 arena 三个对话框。

标签页那一处最有教益，因为它本来就已经用了函数式更新，却仍然读到过期值。在一次突发内部，函数式更新是正确串联的 —— 第三个方向键确实看得见第二个方向键写入的值 —— 而处理函数闭包里握着的那个值从来不动，所以一个把两者混在一起的表达式，仍然是从突发前那个标签页起算的。修法是读镜像、并在它上面显式做算术，两个处理函数现在都是这样；向导的方向键尤其不再从渲染那一份副本推导它们的下一个下标。

三个用例钉住这一处：一次三键突发把空格落在同一次读取里方向键到达的那一行上、一次两键突发切换一个方向键移动到的那一行，以及一次读取里的三个方向键把标签页带到 Extensions。全部三个都在修复前的代码上失败 —— 两个向导用例把哪一个单选字形是实心的弄反了，而标签页用例既找不到扩展行也找不到文件行，因为每个方向键都是从 `all` 起算步进的。两个缺陷都没有在真机上复现过，理由是决定 63 给的那一个。向导的 review 行仍然读闭包，继续记在后续工作里。

## 决定 65 —— 审批模式对话框记住方向键到达的那一行

ink 自己保有一份高亮模式的状态，并用它来给列表下标做初值，所以从作用域那一步回来时，恢复的是方向键最后一次高亮的那一行，而不是 config 恰好握着的那个模式。这里则是每当作用域那一步关闭，列表都从 config 取初值，于是光标被放回当前模式上，而方向键走过的那段路被悄悄丢掉了 —— 一个往下移了两行、去核对作用域、再按 Enter 的用户，写入的是他出发时那个模式。

对话框现在按 ink 的做法保住高亮模式，从列表的高亮回调里取它，并用它给列表做初值。作用域保留它自己那个键：作用域是这一趟所改变的东西，而高亮是这一趟之后存活下来的东西。

一个用例把模式列表往下走一行，去作用域那一步切到 Workspace 再回来，然后断言光标停在方向键到达的那一行上。改成从 config 取初值会让它失败。这个用例在那次变异之下起初看起来是绿的，而原因值得留着：在作用域那一步不移动作用域光标就按 Enter，写入的是它本来就有的那个作用域，于是列表据以重新同步的那个键根本没变，列表从没被重新落位，而光标在两个版本下都停在方向键留下的地方。在 Enter 之前移动作用域光标，才是让这个用例具备判别力的东西。一个以某个值为键的重新同步，必须看见那个值真的变了，而一个要用到它的用例也必须让它变。

## 决定 66 —— 弹层槽位是 ink 那个定高、裁剪的区域，而只有 ink 会拉伸的对话框才去填满它

ink 不把弹层叠在 composer 上面：它把 composer 换成一个恰好 `rows − staticExtraHeight − MAIN_CONTENT_HEIGHT_RESERVATION` 行、顶对齐并且裁剪的区域，每个对话框都在这个区域里布局。这两个常量都是 ink 的 —— 前一个是它的容器为「弹层用不到的行」传的那个 `3`，后一个是它的布局为主体内容保留的那个 `2` —— 所以四十行的终端给出的预算是三十五行。

这边的槽位过去是内容高度。由此引出两件事，而它们看起来毫不相关。一个 ink 会拉伸去填满区域的对话框在这里既矮又靠下，因为转录把槽位上方那些空闲行都占了，而内容高度的框落在它们后面；审批模式对话框画了十三行，ink 画三十五行，它的底部提示紧跟在列表下面，而不是落在视口底部。而一个比区域高的选择器会把 composer 顶出屏幕，而不是被区域裁掉。

外壳现在把预算算一次 —— 用它本来就持有的终端高度 —— 并给槽位这个高度、`overflow="hidden"` 和纵向布局。同一个数字作为可用高度交给对话框，这正是 ink 的对话框管理器交给它们的东西，于是一个把窗口按整个终端高度来算的列表不会再把它的底部提示顶出裁剪区。外壳自己那个高度属性被删掉了：外壳读终端尺寸，所以调用方传进来的高度只可能与它不一致，而唯一那个传它的调用点传的正是裸的终端高度。

ink 只有三个对话框会拉伸到给定的高度，而其中只有落在这个槽位里的那一个在这里可达，所以也只有它填满。共享外框为此长出一个开关，接到 `flexGrow` 上，审批模式对话框设了它。开关在外框上，所以这个对话框的两个分支都把边框画满整个区域；差别在里面的内容。只有模式分支把它的内容多套进一个会生长的框里，于是底部提示被推到第 38 行；作用域分支让它的内容保持自身高度，所以提示停在第 13 行，下面的行是空白。两种摆放在帧上都与 ink 逐行一致。effort 与 output-style 两个对话框不设这个开关，因为 ink 也不拉伸它们。这个开关写成三元表达式而不是条件属性，理由就是决定 22 给出的那个：本渲染器的 setter 会忽略它的 reconciler 为「属性被移除」传来的 `null`，所以一个时有时无的属性会把旧值留在节点上。

两个场景承担证据。新加的那个打开审批模式对话框再 Tab 到它的作用域那一步，因为它是槽位里唯一被 ink 拉伸的对话框，所以它同时验证两半 —— 区域的定高，和框去填满区域。在 100 列 40 行的终端上，两腿都把边框画在第 6 行到第 40 行，五个模式落在第 10 到 14 行，提示落在第 38 行；两帧里各自唯一还差着的那一行是 composer 那一行，差在两腿帧都带的那个光标伪影上。Esc 之后那一帧完全一致。另外两个既有场景打开的是同一个对话框，给出前后对照：这个框原先占第 28 到 40 行，现在占第 6 到 40 行，帧的差异行从 27 降到 3。editor 对话框（ink 让它保持内容高度）从第 23 到 40 行上移到第 6 到 23 行，现在也与 ink 一致，下方那些没用到的行是空白。

## 决定 67 —— 一个要求了尺寸的框，必须同样要求可以收缩

ink 的 `Box` 一律把 `flexShrink` 默认为 1。本渲染器只在宽和高都没有显式设置时才默认为 1，否则默认为 0 —— 所以在一个有尺寸的框上，删掉 `flexShrink={0}` 什么也不改变。选择器修复的第一版做的正是这件事，帧回来与修复前那次逐字节相同；把两个库的默认值都读一遍才找到这个分歧。

ink 的会话选择器要求 `height − 1`，并让那个定高区域把它压下去。这边要求了同样的尺寸，而在本渲染器的规则下这同时意味着拒绝被压，于是一个三十九行的框从一个三十五行的区域上方开始画，把转录挤成一行乱码。它的两个分支现在都显式要求收缩。

列表分支还去掉了一个 ink 的选择器没有的上边距，预览分支去掉了 ink 的预览树没有的那一个 —— ink 把那棵树直接返回到区域里，没有边距、没有尺寸、也没有它自己的裁剪，所以它的标题从区域的第一行开始。两个结构性用例钉住这一对：一个断言列表框要求了三十九行的高度、收缩和裁剪，另一个对预览断言同样的东西，并断言它身上没有残留的边距。去掉收缩会让第一个失败；把边距或收缩任一个放回去会让第二个失败，而且每次都失败在它自己那一条断言上。

在真实终端上，选择器场景的八个列表帧从每帧 8 行差异 —— 带多选 footer 的那两帧是 12 行 —— 降到 3 行和 6 行。剩下的是 banner 的行高差、两腿帧都带的那个光标伪影，以及那两帧 footer 上 ink 自己的换行：ink 把它三段之间的空格丢了，并且其中两段在内部断行，这一条按 ink 侧缺陷记录而不是去对齐它。选择器关闭之后抓的那两帧，改动前后都与 ink 完全一致。预览那一帧根本没法比：ink 在那里抓到的是选择器整个消失、只剩 3 行非空内容的画面，再等更长时间仍然是 3 行，也就是已经记录在案的那个良性分歧 —— 所以这个分支靠的是源码直查和那个结构性用例，不是帧。

## 决定 68 —— 补全行的尾部按比例截断，因为本渲染器没有截断式换行

ink 给补全行的参数提示和来源徽标设 `wrap="truncate-end"`，范围是标签列在标签之后剩下的那些列。本渲染器的文本有三种换行模式 —— none、char、word —— 没有一种会截断，所以一个过长的提示会换到第二行，把整行的高度翻倍。截断因此挪进行自己的算术里。

尾部的分法照 ink 自己的布局来，而这个分法不是最先会写下来的那个比例。Yoga 是拿这一列去 measure 每个兄弟的，所以每个兄弟收缩的基准已经被列宽截顶，而不是它自己的完整文本宽度 —— 39 列的列里一个 61 列的提示，是从 39 开始收缩的 —— 溢出量再在这两个基准之间分配。两个结果宽度都是分数，而 ink 的渲染器会把徽标的起始列向下取整，正好落在提示画自己那个省略号的那一列上：有徽标时，提示活下来的是 ceil(宽度 − 1) 个纯列、没有省略号；没有徽标时没人盖住它，省略号就是提示的最后一列。徽标保留自己那份的 ceil，含省略号。把尾部先给提示、剩下的给徽标看起来更简单，但是错的 —— 徽标会彻底消失，而且恰好消失在带徽标的那些行上，也就是 `@` 补全。从未截顶的文本宽度开始收缩则错在另一个方向：它给提示更大的一份，从徽标上吃掉两列。

ink 在这里的行为是实测的，不是推出来的。用 ink-testing-library 渲染 ink 自己的 `SuggestionsDisplay`，取到 23 组提示/徽标/列宽组合下的截断行，上面这套算术复现了全部 23 组。其中两组被钉成 jsdom 用例，一个只有提示，一个提示和徽标同时存在，两个都在修复前的代码上跑过，那里整行是换行的。

这一行在真实终端上也有，因为确实有一个已发布的命令会溢出这一列。`/output-style` 带一个 57 列的提示，而半宽上限在一百列的终端上把这一列定成 49，所以补全场景的那个下拉里一直就有这一行：基准被截顶到 49，12 列的溢出给提示留下 37 的份额，而 37 列的 ` [Concise|Proactive|Explanatory|Lear…` 正是两个渲染器都画出来的东西。修复前这边是换行的 —— `[Concise|Proactive|Explanatory|Learn`，下一行是 `ing|<custom>|default]` —— 于是它下面的每一行都被顶下去一行，那个检查点与 ink 差在二十条内容行里的七条上。修复之后，二十条逐字节一致。

## 决定 69 —— wire API 那一步是决定 64 漏掉的镜像调用点

决定 64 把光标镜像做了泛化，并把向导的焦点移到它上面。在 Chat Completions 和 Responses 两种 wire API 之间做选择的那一步自己持有一个光标，而它不在那些调用点里 —— 它是在那轮改动之后从 main 进到这份代码里的 —— 所以它的 Enter 仍然从武装了处理函数的那次渲染里读光标。一次 stdin 读取里的一个方向键加一个 Enter，保存的是方向键没到达的那个 wire API。

它现在取同一个镜像的数字那一半，它的 Enter 读 ref。一个用例把向导走到那一步，在一次处理函数调用里发出方向键和 Enter，然后断言保存下来的方案带的是 Responses 那个 wire API；在修复前的代码上它保存的是 Chat Completions。

## 覆盖边界

验证了什么，以及验证到哪一层：

- **几何、行内容、行顺序、行数与字形身份**，在重建屏幕上，覆盖四十四个场景 ——
  三十九个 100×40，三条转录臂 100×30，窄终端启动 60×24，标签行 58×40 —— 总计
  一百三十三个检查点，其中按抓取到的非空行有三十五条一致。对比工具还会多报两条，因为它
  把两个场景写在帧旁边的采样副本也一并读了进去；那是计时转储而不是屏幕，另行计数。在其
  余九十八条里，有五十六条的差异行里带着上下文文件通知行：那一行装的是 harness scratch
  目录下的一个绝对路径，所以它在两腿上折在不同的位置，它的续行也跟着不同。两腿出自同一
  个 bundle 与同一组启动参数。
- **颜色读过三类行、两种终端模式，其余未读。** 重建结果是文本；颜色来自它旁边那份
  带样式的抓取，而 harness 除退出之后那一个检查点外，每一个都写了这份抓取。读过的
  三类行是 —— 决定 32 的光标格，以及 banner 字标与 banner 信息面板外框。后两类最初
  是在不同模式的不同帧上读的：默认主题的启动帧在真彩下读，那时只有字标分歧；具名主题
  的启动帧在 256 色下读，外框也分歧 —— 外框那处是两个库的降采样规则，已记在后续工作
  里，字标那处是决定 47。随后两类都在真彩下重读过，一次在默认主题的启动帧上，一次在
  Dracula 的启动帧上。两张帧各自的六行字标里，ink 用色标染的每一格 —— 共 221 格 ——
  与本移植逐格一致，外框也在两腿发出同一个源十六进制值。每张帧上仍然不同的那 25 格全
  是空白格：ink 对它们不发颜色，本移植把它们留在渲染器自己的默认值上，而那是不透明白。
  那是后续工作里那条「不着色文本」的分歧，不是色标的差异，且早于决定 47。其余每一行
  的颜色都没有读，而在决定 43 之前，已知有若干行只在所用主题 token 上不同。
- **滚动条没有从转录里拿走一列。** 在一百列下用两条分别为 95 与 96 字符的回答行
  测量：本渲染器折满 99 列才断行，ink 折满 98 列，所以这一列的差与清单上那条既存的
  换行分歧同向，而不是滚动区域拿走了一列 —— 且整份语料的行长分布在这次改动前后完全
  一致。
- **composer 的一行间距以源码为据，只在两帧确实对齐的地方有帧为据。** 在决定
  26 的溢出臂上，composer 之上那一空行与 ink 逐行吻合，因为那里两腿的内容都刚好
  填满窗口。在别处，它在帧比较里无法与重建把块放在哪里这件事分离。
- **退出警告的排队段、以及决定 30 的队列行，仅有单元测试覆盖。** 没有场景会先排队
  一条消息再武装警告。也没有任何场景会产生一个持久的队列：ink 的徽标只在它自己的提交
  路径里作为一帧瞬态存在于裸流中，两腿都从未进入任何一个抓取帧。活得比回合更久的队列
  需要 ink 放在 Ctrl+Q 后面的那次推迟；本渲染器没有绑定这个键，而没有任何场景在任何一
  条腿上按它 —— 所以这些文本和徽标一样，只存在于一个回合之内。
- **决定 31 记录下来的那一行，只在磁盘上验证过，没在屏幕上验证。** 打开 `/model` 再
  退出它的那个场景在两条腿上都跑过，两份会话日志被逐条记录比对。没有任何场景恢复过会
  话，所以这一行经共用加载器重新回到屏幕 —— 本渲染器的会话切换调用的就是它 —— 只建立
  在读源码之上。
- **不可压缩的行前缀与按条目上边距仅靠重新抓取验证。** 单元测试运行时会桩掉
  渲染器的图形表面，因此无法执行布局；在那里的测试只能把这个 prop 原样回显。
- **纵向间距直到最后一次运行之前都在帧证据之外。** 比对会把每一帧归约为一串非
  空行，这让两个条目之间的间距对它不可见，而本文档此前每一次抓取都是这样比对
  的。所以上面那条边距是本文档里第一个有帧支撑的间距结论，并且它靠的是一份对
  transcript 区域的单独度量 —— 只要重建会把 ink 的那块内容放在它自己选定的行上，
  空行总数就不可用。
- **ink banner 前后的空行刻意不复现。** 有两件事是直接读到的。ink 的抓取流在
  banner 首行之前以一个回车加换行开头。并且 ink 会给它写出的每一批永久输出追加
  恰好一个换行 —— 它自带的注释说明这个换行是为了让下一帧不覆盖该批的最后一行。
  因此空行会落在批次边界所在之处，而这取决于条目在多次渲染之间碰巧如何分组，而不
  取决于任何布局规则。这两者中哪一个产生了哪一行没有被追查，而对齐其中任何一个都
  意味着把写入分批的伪影硬编码下来。
- **两处结构性分叉曾被记录为刻意保留，如今已经关闭。** banner 在本渲染器里
  常驻、在 ink 里会滚出视口，这是从恢复工作继承下来的产品决策，而不是它引入的
  缺陷。同一套浮层模型还有第二个症状：对话框不会重排会话，所以当 ink 打开一个高
  对话框、把若干行顶出视口时，那些行在这里仍然留在浮层下面可见。决定 26 拆掉了
  这两条共同来源的那套浮层模型，它的帧就是这两处关闭的证据。
- **启动时的更新检查通知属于运行时，而本文档之前关于它的说法是错的。** 这条通知
  出现在每一条 OpenTUI 腿的帧上，却从未出现在任何 ink 腿上 —— 在对照臂说明它归属
  哪一侧之前，这种分叉既可能来自渲染器、也可能来自运行时。对照臂跑了：ink 在与
  OpenTUI 腿同一个运行时下复现了这条通知，所以它从渲染器那一栏移出。同一次运行也
  推翻了此处原先记录的解释 —— 即 ink 把一条软警告输给了订阅竞态、转而显示之后那条
  硬更新失败；任何一臂的任何一次运行都没有出现过硬失败。这个检查自己的结果为何在
  两个运行时之间不同，不是这轮排查追的东西。工装现在于两条腿上都抑制更新检查，所以
  这条通知不再向帧对比贡献任何行。
- **一处外观分叉被记录，未修。** 两个渲染器在不同列上断开一行长内容。ink 的默认
  换行是按词换行、但把仍然放不下的部分强行截断且不做裁剪，所以一行会一直填满到
  边缘，续行从该条目自己的缩进处开始；本渲染器的 text 节点按词边界断开，而一条路径
  里的词边界包含其中的斜杠与连字符，所以一个长到放不下当前行的词会被整体挪到下一
  行、把当前行留短。context 文件列表是它的第一个面，工具卡片的 header 与参数行是
  第二个面：在一百列下，同样的参数在两腿上折叠成同样数目的隐藏字符，却仍然比 ink
  多耗一个物理行。要对齐断点就意味着重新实现渲染器已经提供的换行算法。它确实得到了
  一次测量：在三个折行段落的 123 点宽度扫描里，钉住的渲染器现在有 105 点与 ink 断在
  同一位置，而在 `@opentui` 0.5.8 下是 90 点 —— 多出十五个断点，一个没丢。剩下的十八
  个全部落在同一个段落上，出现在 ink 把该行多填一列的那些宽度。整行判定没有一个移动，
  因为承载它的这些行同时还背着别处记录的弹层宽度与缺失的行号，所以这处分叉是被收窄
  了，而不是被关闭了。被折行的
  header 还会丢掉工具显示名与其描述之间的那个空格，而一个把参数行关掉、却抬起同一
  个长 header 的场景会原样复现这一点 —— 正是这条对照把最后这一点与上面新增的那一行
  区分开。
- **一处最后兜底被刻意不复现。**「保留原模型」播报先读运行期快照的标识符，再退到
  配置的那一个，这与 ink 一致。ink 还会第三次兜底 —— 当配置的标识符读出来为空时，
  退到一个硬编码的默认模型标识符。在这里那不会发生，所以这第三层被省掉，而不是为一
  个不可能的场景引入一个常量。
- **回放的扩展提示带不上它的原因。** 本渲染器据以回放的闩锁没有暴露原因访问器，
  所以在本渲染器挂载之前失败的一次重载会以普通的变更措辞播报，而不是失败那一条。
  两种措辞都把用户指向同一条命令，而要恢复原因就意味着为这个背后没有不同动作的
  区别，给共享状态加一个公开访问器。
- **审批释放只有单元测试覆盖。** 没有任何场景会先停住一个确认框、再轮换模式。这条
  接线由一个带反证对照的测试钉住 —— 那个必须什么都不释放的中间模式 —— 而它消费的
  选取规则本来就已被单独覆盖。
- **多数突发用例只有单元证据；光标这一类不是。** 验收 harness 故意每次 pty 写只打
  一个字符，所以一次按键通常落在自己那一次 stdin 读取里，而它从不向对话框输入粘贴。
  现在有两个场景为陈旧光标这一类故意打破这条规则：各自在一次 pty 写里写入三个方向
  键、或两个方向键加一个 Enter，于是这些键落在同一次 stdin 读取里，那个读渲染闭包
  光标的处理函数就会从错误的行上作答。两条腿都逐帧钉住了，在两个不同的对话框上，
  其中第二个同时还是一个环绕用例。仍然只由单元测试套件及其变异兜着的是其余全部：
  决定 37 与 39 描述的粘贴交错、重试计数器的步骤守卫、决定 40 的答案锁与净化片段
  —— 这些都不是单通道 pty 写能造出来的。
- **ink 自己的认证向导套件在本地失败，而本轮改动没有被证明是原因。** 那个文件把十九条
  测试藏在一个由它自己注释解释的检查之后 —— 模拟 TUI 输入在慢速 runner 上不可靠 ——
  并在 CI 与 win32 上跳过它们，所以 CI 从不运行它们。在 CI 之外，这一家里有十三条在这
  里失败，每一条都卡在该套件自己的五秒等待上，十三条全都在被守卫的那一家里。本 head
  上跑了六次，五次得到同一组名单，一次得到其中的十二条，所以随机器漂移的是条数，而不是
  会落到被守卫那一家之外的失败。一个只变一个变量的对照说明，本轮对共享 provider-setup
  hook 的改动不是原因：把 `packages/cli/src/ui/auth/useProviderSetupFlow.ts` —— 那次改动
  唯一动到的文件，也是这套件会走到的那个 —— 放回它在 `origin/main` 上的版本再跑一次，
  跑完核验工作树逐字节还原，失败的还是同样这十三条，列表一字不差。没有观察到的是这个
  环境里一次干净的上游签出：独立的 worktree 在任何测试跑起
  来之前就会停在 workspace 构建前置条件上，所以「它们在那里也失败」是从上面两个臂推出来
  的，不是量出来的。
- **思考开关的那次按键完全没有覆盖。** 入口自己的测试把键盘 hook 换成了空操作，所以
  被断言的只有消费的那一半：标志到达那一行并把它展开。它也没有帧覆盖，因为没有任何
  场景会让模型产出一段思考 —— 新标签与这条绑定都不出现在任何一帧抓取里。
- **ink 那个全量详情开关只绑了思考这一半。** ink 的标志还会取消每一个工具组的截断；
  这里的工具卡片无论它如何都保留自己的行数上限。
- **进行中的思考正文在这里是流式显示的。** ink 会把它藏起来，直到该思考被展开。记录
  而不修改：既然没有场景产出一个进行中的思考，改动它在任一方向上都无法验证。
- **决定 48 接上的那两个设置，只在一个场景、一个尺寸上有帧验证。** 两半都在那个专门场景
  的帧上与 ink 逐帧读过：assistant 行上方的时钟行，以及结算卡片被折叠成只剩标题并带着展开
  提示。没有用帧查过的：其他任何视口尺寸；恢复出来的会话 —— 那里的时间戳来自录制，而不是
  折叠自己的时钟；以及折叠卡片的点击可供性，没有场景点过卡片，所以它靠的是那个钉住提示文案
  与其所指处理器的单元测试。
- **哪些工具真的会在执行中发出结构化载荷，没有被追查。** 这次收敛让每一种载荷在每一
  条路径上都可用，实时分片也包含在内，所以一个在运行时上报 ANSI 网格的 shell 结果现
  在会带颜色渲染；至于是否有工具会在完成之前就这么做，那是关于工具的问题，不是关于
  本渲染器的问题，这里没有回答。
- **受门禁的服务器审批只在一个方向上有帧验证。** 一个场景把一份项目服务器列表丢进工作
  目录；两腿在同样的内缩与同样的宽度上画出同一个对话框，拒绝之后两腿都落在同一个
  composer 与同一行 footer 上。批准没有被执行，因为它会解除该服务器的门禁并重连，而那
  会派生所声明的命令。所以批准与全部批准两个分支都没有帧覆盖，全部批准要打印的那份服务
  器列表也没有 —— 场景只声明了一个服务器，所以渲染那份列表的分支从不被走到。这些分支
  做什么是那个共享 hook 自己的行为，这里没有改动。
- **参数行只在一个宽度上、对一个需要审批的调用做过帧验证。** 打开这个设置的那个场景
  会停住一条 shell 调用，所以它的帧里同时带着：等待中的参数行 —— 以及标记这一条的那
  个唯一箭头 ——、调用结算之后的样子，和那个切换键到达的不截断状态。其余每一个场景都把
  该设置留在默认值，所以这一行在矩阵的其余部分按构造就不存在。没有用帧查过的：一个描述
  本身就已经打印了参数载荷的调用，也就是共享 helper 要去重的那一种 —— 它由一个带正证
  对照的单元测试断言；以及一百列之外的任何宽度。
- **ink 那份按组的预留高度没有移植。** ink 会从该组里每一个结果拿到的预算中，为这一个
  组里每一个将要打印参数行的工具扣掉两行，因为那一行画在结果预算之外。本渲染器不做这种
  分配：每一张卡片拿到的都是同一个按条目算出的上限，它由视口高度导出，所以参数行在这里
  没有可扣的预算、只会额外增加行数。两者只在 ink 本会压缩一条长结果的地方不同，而要补上
  这段差距，就得引入这套架构从来没有过的分配。
- **决定 51 到 58 靠的是它们各自的单元测试套件与变异，而不是在这八条之上重跑一遍
  帧矩阵。** 决定 51、53、56 背后那几处外观分歧 —— 编辑器对话框的行与提示、认证
  外框的方角与它缺失的无推荐分支、footer 的模型段 —— 是在这轮排查里从重建帧上读出
  来的，而决定 57、58 背后那两道门 —— `ui.mouseTracking` 与屏幕阅读器模式 —— 各自
  在真机终端上两个方向都确认过，正如它们的条目所记。其余各条是就 ink 做源码核验。
  一个屏幕阅读器会话根本到不了 OpenTUI 这条腿，因为决定 58 把它留在 ink 上，所以那条
  路径没有矩阵可比的帧。
- **机器腿在这个 head 上重跑了整个矩阵。** 八十八次运行全部完成，没有一次报错，一共写出
  两百六十六帧。九次 idle 超时落在与上一轮相同的三条 ink 腿上、次数也相同：光标编辑臂四
  次，认证向导的模型列表三次（它的 spinner 永远不会 idle），多问题臂两次。一百三十三个
  检查点里，三十五条的非空内容行完全一致；其余九十八条里，五十六条的差异行里带着上下文
  文件通知行。
- **剔除上下文文件通知的那个拆分已撤回。** 它报告的是：把通知与它折行成的路径碎片从两腿
  都去掉之后，有七十三个检查点一致。但从它取自的那些帧上复现不出来：只去掉那些行，计数
  一动不动，因为那一轮没有任何一个检查点只差在通知上 —— 全量里最小的差异是十二行。这个
  数字被丢掉而不是被继续带着走，上面那个计数是本文档现在唯一主张的拆分。
- **整个矩阵在这棵树上跑了两遍，一遍带改动、一遍不带，而本轮主张的每一处变化都在 OpenTUI
  这条腿上。** 两臂都是八十八次运行、两百六十六帧、没有一次报错，九次 idle 超时也落在相同的
  三条 ink 腿上、次数相同。两臂之间，两百一十五帧逐字节相同，四帧只差一个 spinner 字形或一
  个耗时数字。四十七帧有实质差异，其中六帧在 ink 腿上，而这六帧各自只差在一个 spinner 短语、
  一个会话标识、一个墙上耗时或一个时钟戳上 —— ink 腿上没有任何一帧因为别的原因动过，这正是
  剩下四十一帧可以归到本轮的依据。按「与同一检查点的 ink 腿做行 diff 的规模」计分 ——
  只有 ink 画的行加上只有本端口画的行 —— 一百三十三个 OpenTUI 检查点里三十六个变好了，
  九十七个没动，没有一个变差。
- **上面那个计数只动了一格，而它只动一格的原因是光标伪影。** 改动前有三十四个检查点完全一致，
  改动后有三十五个；跨过去的那一个是决定 68 的补全行。另外三十五处改善是真的，但都没有到达
  完全一致，因为 harness 会把 pty 光标写进重建帧里超出终端最后一列的位置，而这个伪影在两臂
  里落在不同的行上：改动前它落在本来就有差异的行上，改动后它落在两行本来与 ink 完全一致的
  行上。把伪影算作差异，会让十一个检查点看起来比原来差两行；在比较之前先剥掉行尾那几个块
  字形，正是把这十一个变成上面那个「零回退」的原因，而这十一个各自剩下的差异行也从三行
  变成一行 —— 那是 banner 的行数，定高的区域同样把它裁得更接近 ink。
- **上面那两臂跑在合并 main 之前的那棵树上；合并之后的那棵树已经重跑过 after 这一臂。**
  合并把 main 带进了这个分支，所以它的帧并不是上面那次对比量到的那些帧。在合并后的树上

  的结论 —— 只有那个计时的 spinner 采样例外，它数的是短语，任意两次运行之间都会动。
  所以本节给出的那些计数在合并后的树上同样成立，而不只是在切出那两臂的那棵树上成立。
- **决定 62 到 65 背后没有帧。** 调色板版本号、那两处镜像读取，以及审批模式对话框记住
  的那一行，全都是就 ink 读源码读出来的，各由一个单元测试钉住，并用变异证明它有判别力。
  这四条没有一条能从抓到的帧上走到：那次突发需要在一次 stdin 读取里有一次粘贴或者一个按
  住的方向键，而 harness 打不出这个；那次主题重绘需要一次会话中途的选取。footer 的提示

  事，但矩阵跑过的最窄视口是五十八列，所以没有一帧显示过一行不得不丢掉某一段的提示。

- 滚动区响应鼠标滚轮，却不响应任何键 —— 而它之所以对键始终不是目标，只是因为决定 38

- 主题明暗模式 helper 没有生产调用方。决定 42 已经把 ink 的主题接通了，所以调色板确实
  跟着当前主题走；这两个 helper 是通往同一终点的第二条路，而没有任何代码在两条路之间做

- 仍有两个对话框列表组件，其实一个就够；合并它们会同时牵动编号、颜色与滚动箭

- 一次针对 ink 组件与渲染源码的逐行对照，翻出了远超本次改动范围的缺口。以及在这里打开
  是只读、而 ink 那边可操作的对话框：信任、回退、diff、子代理的创建与列表、技能、
  hooks、状态栏、记忆、stats 的两个标签页，还有扩展管理器的发现与来源标签页。再加上整

  有对某个子代理发起的审批做行内归属，所以这样一个审批到达时无从说明它是谁的。
- ink 的两个鉴权进度界面曾被报告为这里缺失，理由是缺了它们一次登录无法完成。这一
  条经不起可达性核查，它们不是缺口。注册表里没有任何 provider 声明那个 OAuth 鉴权
  类型，协议选择器只另外提供四种，所以待处理鉴权类型唯一的那个写入点永远产不出它；
  而那两个界面所读的外部鉴权状态，在它仅有的两个写入点上都被赋成 null，从来没有被
  赋过别的值。两个分支在 ink 里都不可达，所以这里省略它们是与其对齐，而不是缺失
  —— 记下来，免得这条省略被再次当成缺口上报。
- footer 没有右侧段。ink 会用竖线把若干指示器接在那里 —— 沙箱、安全模式、调试模
  式、上下文百分比，以及 goal 与 cron 胶囊 —— 还会加上一个 MCP 健康胶囊、一个
  worktree 指示器、一个 workflow 指示器和一条技能待审警告。本渲染器只打印一列左侧
  内容。
- 状态栏相关设置被忽略。ink 会渲染至多两行由用户配置的命令产出的内容，按它自己的
  刷新间隔与颜色选择；本渲染器则硬编码一行目录、会话、分支与模型。
- composer 宣传了一个它并未绑定的排队键。决定 30 把这件事放大了：移植来的提示行会
  把那个键的名字打印到屏幕上，于是这个失效的可供性从「仅有记录」变成「看得见」。它
  的退出键还会在草稿非空时武装那个按两次的窗口，并在这个过程中吃掉一个字符；而 ink
  在缓冲区还有文本时根本不会武装。
- 多数对话框把回答落在一个不会留存的提示位里。arena 的选取与停止对话框、编辑器对话
  框、输出风格对话框，以及认证对话框的成功播报，都经由 shell 的 notice 槽作答，而下一
  次提交就会把它清掉；effort 对话框的选取则什么都不说。ink 为这些结果逐一添加转录行并
  记录，所以恢复会话时那边能重放、这边不能。补这些是决定 31 的形状做两遍 —— 先把行加
  上，再记录；只记录不加行，会在恢复时重放一行用户从未见过的话。`/statusline` 更靠在
  后：本渲染器的 statusline 对话框只列出预设项、按 Escape 关闭，根本没有保存动作可记
  —— 缺口落在一个缺失的功能下游，而不是一条缺失的记录。ink 的 UI 层有十五处记录点，
  其中十三处在分发器自己那对 invocation/result 之外；这十三处里有三处在这里什么都不
  必补：theme 那处只带 `/theme` 的 `NO_COLOR` 消息，而本渲染器已经把它走分发器的记录
  包装（选主题本身两边都不加行）、arena 命令的记录器是两边跑同一份的共用代码、
  away-summary 的记录器现在住在决定 55 里本渲染器挂载的那个 hook 内，所以它触发的
  recap 与 ink 的记录方式一致、在这里不需要自己的一处记录点。
- 一次辅助模型的选取是另一种类型的行。ink 把 fast、voice、vision 的选取报成 success 条
  目 —— 它有自己的字形与颜色 —— 而这里所有模型结果，主要的或辅助的，都走同一条 info
  行，于是它在屏幕上显得更平，自决定 31 记录了被显示的那一行之后，在会话日志里也一
  样。本渲染器这条路径可达：分发器会构造 fast、voice、vision 的对话框请求。要修就得让
  选取助手带出行类型，而不只是一条消息字符串。
- ink 的提问对话框会对一次击键把手打的自由文本答案答两遍：对话框自己的按键处理
  与它挂载的输入控件都订阅了按键，而按键层没有焦点栈在两者之间仲裁。每次回答都
  推进一个标签页，所以多问题对话框上，正被回答那题之后的那题会被跳过、根本没被
  画出来，而复核标签页把它报告为未回答。这是在真机上观察到的，不是推出来的。
  决定 21 不跟随它，而在以 ink 现状行为度量自己的清扫里去修 ink 超出了范围；
  记在这里，免得两个渲染器间的这处分歧被再次当成移植缺口上报。
- 读到过期值这一类缺陷，对光标已经关掉，对光标之外的一切仍然开着。决定 41 把数值光标
  放到了 ref 镜像之后 —— 共用的 select hook 与它暴露出来的那个 ref、composer 的补全
  行，以及每个对话框自己的标签页、已勾选集合与向导菜单 —— 决定 63 又补上了那个论断漏掉
  的两个处理函数，即 rewind 的恢复选项光标与权限对话框的两个自由文本字段，决定 64 再补上
  认证向导模型步骤的焦点与 composer 的 `@` 分类标签页，所以不再有处理
  函数按上一次渲染画出的那一行、或者那一个缓冲作答 —— 唯一例外是向导的 review 行，它们仍
  然读闭包，就记在这条旁边。仍然这样的，是同一个根因落在那些为
  分支充当门禁、而不是喂给一次提交的状态上：对话框的视图名、它的步骤、它的聚焦区、它的
  搜索词，以及它的编辑器偏好作用域，在那些以它们为门禁的分支上全都是从渲染闭包里读出来
  的。这是跨六个对话框读源码读出来的，没有在真机上复现。触发条件比光标那一类更窄：它需
  要在一次 stdin 读取里有两个含义不同的键 —— 一个 Tab 或 Escape 加一个 Enter —— 而 ink
  同构的那份代码同样读它自己的渲染闭包，所以单键行为两边一致。要关掉它，得围绕一个镜像
  重写每个对话框的分支结构，而不是在一个值旁边再加一个镜像，这也是它被记录而不是被做掉的
  原因；如果要做，每个对话框都要有自己的连击用例，因为让一个对话框的门禁失败的变异，对另
  一个什么也没说明。
- 决定 37 的闩停住的是字段，不是步骤。向导的那几个列表步骤和最后的 review 行仍然是
  一个按键跑一个分支。review 行在一次两个 Enter 的突发里会把计划应用两次 —— 两次
  写入调用，本轮一条临时测试直接读到的 —— 而协议行与端点选项行是源码读出的同一形状：
  它们各自的 select 都会前进一步，于是同一次读取里的第二个 Enter 就跳掉中间那一步。
  ink 的步骤也是这个形状，所以这不是一条要走在 ink 前面的分歧，它属于上面那轮对对话框分
  支结构的重写，同一个「一次读取一个动作」的闩一并覆盖它。
- 闩停住的是按键，不是粘贴。每个被它结算的字段同时订阅了渲染器的粘贴事件，而那份订阅
  从不查这个闩：一次读取里先有让向导前进的 Enter、随后再到一个括起式粘贴，粘贴的文字
  就会写进这串按键已经离开的那一步。反过来的顺序 —— 先粘贴、再有提交它的 Enter ——
  才是终端真正会发的那一种，已由一条测试钉住；这一种需要第二个输入通道落在同一次读取
  里，而 harness 的任何一条腿都不会向对话框粘贴。它并入上面那轮控件级的改动，每个字段
  都该带上同一道守卫。
- 一张已结算的卡片会停在它被创建时的位置，而 ink 会把它提交进永久历史、排在期间到
  达的那些提示之后，所以一条在工具调用期间打印的提示，在这里落在卡片之后，在那里
  落在卡片之前。这一条曾经还记着卡片缺少的行内参数行，以及一个画在每张卡片上、而

- 两个调用同时等待审批时，确认框在屏幕上的位置不同。ink 把它直接放在所属那行卡片之
  下，所以画面读起来是卡片、确认框、卡片；这里会话按自己的顺序保留两张卡片，确认框

- 提问对话框的 chip 行在这里比在 ink 里晚两列才开始裁切。决定 21 按这一行被画在其中的

  那个数字来做，会裁掉这一行本来就放得下的文字。
- 对话框字段移植的是 ink 缓冲区里那一行宽的切片，不是全部。ink 文本输入绑定的四族键
  没有移植：词跳转（ctrl/alt+←/→、alt+b/f）、向右删词（alt+d、ctrl/alt+Delete）、
  整行删除（ctrl+k/ctrl+u）与撤销重做（ctrl+z）。前三族需要的操作在这个模型里都已经存
  在，所以那是一次落在行编辑器与其测试上的改动，而不是逐个对话框的改动；撤销重做还需要
  一份这个模型并不保存的历史，所以它要先加一处存储，才谈得上加一个绑定。另有 ink 的两个
  绑定是有意不在此列，而不是漏了：清空输入（ctrl+C），应用级的退出处理函数已经在任何对话
  框占着屏幕时都对这个键动作；以及打开外部编辑器（ctrl+X），本渲染器里没有任何东西绑定它。
- 对话框字段的行开了「行」的窗，没开「列」的窗。ink 的字段画光标所在的那一行，并且在那
  一行里画光标左右的那些列，所以比这一行更宽的值是横着滚过去的。这一行藏起了光标之外的
  其他行，却仍然画出自己这一行的全部列，于是一个比这一行更长的值还是会把它折行 —— 无论
  那些字符是一个个敲进来的，还是一次粘贴进来的。
- 恢复出来的会话显示的行比它的日志里装的少。本渲染器的 transcript 适配器只重放 slash
  命令的 invocation 阶段，别的一概不重放，于是一条 result 阶段的行 —— 其中包含决定 31
  的那行「保留原模型」—— 被记录之后就再也不画出来，而 ink 的恢复会把它们每一行都放回
  去。这比一个对话框更宽：补上它会改变每一条 slash 命令在恢复之后留下什么，而验收矩阵里
  没有任何场景恢复过一次会话。
- 一次被拒绝的按键在屏幕上留下什么，两侧是有分歧的，决定 32 已说过。context-window
  字段只保留数字，而本渲染器打印的是被接受的那个值，于是一个字母 —— 或那一步绑定的
  Space —— 会不留痕迹地消失；ink 的缓冲区才是它显示内容的源头，会一直显示自己流程已经
  丢掉的那个字符。这里刻意选了更安静的一种：要对齐 ink 就得把这行搬到缓冲区上，那是
  ink 该修的缺陷。
- 两个应用级处理函数在「是否认领自己那个键」上不一致。展开思考的处理函数会把这次按键
  标记为已消费，ctrl+C 与 ctrl+D 的退出处理函数不会，于是这两个键也会到达同一次读取里
  挂载着的其他处理函数。ctrl+D 上没有别处动作 —— 共用的行归约器把它原样交回。ctrl+C 上，
  shell 的五个分支是互斥的 —— MCP 审批、工具确认、模态、对话框、composer —— 所以只有屏幕上
  那一个会和退出处理函数一起参与这次读取。composer 清空一个非空缓冲区，并且只在真的清空时
  才认领这个键；设置对话框把它所在的那一行恢复默认，不认领，于是在那里按一次 ctrl+C 会同时
  把那一行恢复默认并武装退出窗口，再按一次就退出。回退浮层绑定同一个键，但本渲染器里没有任何
  文件引入它。让退出处理函数也做出展开思考那个处理函数所做的认领，是另一件独立的事。
- 另有六处钉定被评审以变异量出并不成立。本轮把这六处都重跑并闭合了，每一处都对着属于
  它自己的一个变异。删掉 shell 上等待行的挂载，现在会让决定 28 点名的两条短语测试失败 ——
  指示器自己的套件仍然直接渲染它，什么也看不见。把排队行移到 composer 下面，那条钉住位
  置的测试会失败，因为它现在把两者排出先后，而不只是断言它们落在一起。参数行位置的断言
  不再对比它的 fixture 从不渲染的字符串，把那一行移到表头上面会让它变红。参数行的接线，
  以及 shell 一并传下去的那个待答调用 id，现在由挂载入口点渲染出的那棵树读出来，删掉任
  一条都会让那条用例变红。光标停在选项行上时到达的一次粘贴有了自己的用例，摘掉拒绝它的
  那道守卫会让那条失败。两个根本没有测试的分支 —— 模型对话框自定义 ID 字段的光标，以及
  向左删词的跨行合并分支 —— 现在各有一条：把那个光标钉死在值的开头、或把跨行合并取走，
  各自会让它们变红。同一形状贯穿这六处：断言读的是渲染出来的结果，所以渲染结果不变的改
  动能活下来；每一次闭合都是改为断言位置、接线或状态，而不是断言画面。同一轮评审提出的
  第七处已经重跑并闭合：待处理卡片那个用例曾被调到一个高度，在那里视口预留值与描述下限
  是同样的五行，于是删掉那个下限它的探测值仍然通过。它现在同时钉住两个高度，删掉下限会
  让它变红。
- 提问对话框的答案窗口锚在值的开头，所以超出窗口之后光标那一格不再画出、按键在屏幕上不再
  移动任何东西，而 Enter 仍然提交整个值；截断标记还被算作光标可以停的一格。ink 的字段在宽
  度轴上滚动到光标处，正如决定 32 的规则让本移植在换行轴上做的那样。在这里跟着光标走，意
  味着由截断前的那一行加一个窗口偏移推出光标，而不是由截断后的字符串推出，那是它自己的一
  次改动、带它自己的测试。
- 提问对话框只给用户打出来的内容设界。问题文本、每个选项标签与每个选项描述都是模型生成
  的，既没有宽度也没有行界，所以一个较长的问题或较长的描述会把对话框撑过终端高度、把还要
  去选的选项推出屏幕，其中没有任何用户输入 —— 那正是决定 39 那道界要防止的结果，而它可以
  从一个那道界不覆盖的载荷到达。
- 本渲染器画出的、自己没有颜色的文字仍然带着一个显式前景色，而 ink 的那份不带，并且它的
  覆盖面比空白格更宽。这是从同一帧启动画面在两条腿上带样式的抓包里读出来的：banner logo
  两侧的空白格，ink 发出时前景色不设，交由终端自己的默认色去画，本渲染器则发出一个显式的
  白色。这一部分以现状是看不出来的 —— 那些格是空格，两侧的背景也都不设 —— 但它不是同一条
  指令，而一旦某个选中或反色片段盖住其中一格，在任何默认前景色不是白色的终端上就会显出
  来。看得见的部分是一整类行：同一帧上那条扩展刷新提示，ink 发出时整行没有一格带前景色，
  本渲染器却用自己的暗色 token 画它。ink 之所以不设，是因为那一帧启动所用的主题，它的
  primary 取自暗色基础 token，而那里的前景是空字符串，一个空颜色根本不发指令，于是在默认
  前景比暗色 token 更亮的终端上，这一行在这里读起来更暗。要闭合它，得有一种向渲染器表达
  「没有颜色」的办法，而元素的前景 prop 并不提供这种办法。
- palette 里有一个键身兼两职，这也是上面那个前景色不能被简单地不设的原因。映射里的 `text`
  既是本端口给自己的纯文本上色的那个颜色，又是 markdown 语法 `default` token 的锚点，而
  这里启动的主题把 ink 的 primary 留成空，于是映射退回到该主题自己的 hljs 前景色，把两者一
  起保住。要让 ink 那个「没有颜色」在纯文本上得到尊重，得先把这两个角色拆开；在那之前，本
  渲染器会给未着样的 markdown 指名一个前景色，而 ink 把它交给终端。
- 无颜色主题不被尊重。ink 达到这个主题的办法是把集合里每个颜色都设成空字符串；本渲染器
  的映射保留了这些空字符串，而它随后应用主题时又把它们全部过滤掉，于是调色板留住了初始
  化时那份内置暗色表面，在 ink 什么颜色都不画的地方画出一整套配色。过滤本身是对的 —— 空
  字符串意为「未设」，赋上去会退化成渲染器自己猜的一个颜色 —— 所以缺的是一个分支：认出这
  个主题作为整体是空的，并把那个表面一并丢掉。
- 一个十六进制颜色向下转换到 256 色调色板的索引，两侧用的规则不同。这是量出来的，不是推
  出来的：具名主题下、256 色抓取里的那条 banner 信息面板外框，在 ink 下落在调色板索引
  103，在这里落在 61。默认主题启动帧上、真彩抓取里的同一条外框，在两腿携带完全一致的源
  十六进制值 —— 所以两侧是从同一个颜色出发，在转换里分道的。ink 那个索引正是「每个通道四
  舍五入到六级」的公式对这个十六进制值给出的结果；本渲染器的转换发生在渲染器库的原生层
  里，从 JavaScript 产物中读不出来，所以它的规则没有被确立 —— 只有它的输出被确立。这个移
  植里没有任何地方选择索引，所以这里没有可修的点；改动只能来自那个库。记下来，因为它是本
  轮每一处修复之后仍然存活的那一处量到的色差，也因为任何在非真彩色终端上比对两条腿的人
  都会重新发现它。
- 本渲染器带着的那个自动主题模块没有调用方。只有它自己的测试引入它；主题是通过 ink 的主
  题管理器到达这个移植的，而明暗探测是在那条边界的另一侧解析的。要么它得到一个调用方，要
  么它被删掉，而上面记下的那两个明暗模式 helper 面对的是同一个问题。
- 两份 markdown 实现在不同的地方断行，并把列表项的 bullet 放在不同的列上。两者都是在同
  一份正文上分别经由各自那份渲染量出来的。宽度不是原因：思考正文所在盒子里一段不断开的连
  续字符在这里断在第九十四列，而那正是 ink 自己那份正文拿到的宽度。一份由四字符词组成的
  正文，在这里填满那九十四列中的八十九列，在 ink 下填满九十四列；一份由单字符词组成的正
  文，在这里填满九十三列，而九十四列是放得下的 —— 两者都与「这一侧把一行最后一个词之后的
  那个空格也算进这一行」一致，不过这条规则是从这些测量里推出来的，不是从渲染器里读出来
  的。ink 自己那四行并不遵循这里确立的任何一条规则：它们在第四列放十九个词、在第五列放
  十八个、在第四列放十九个、在第五列放四个。另外，ink 在同一份正文的第五列画出列表项的
  bullet，这一侧画在第四列。两处分歧都属于那两份 markdown 渲染器，而不属于这个移植，这里
  都没有可修的点。记下来，因为决定 45 把思考正文挪到了 markdown 上，所以它们在那里显出
  来，也因为这个移植以 markdown 渲染的任何其他正文同样带着它们。
- 一个不可断的 token 在两侧折在不同的列上，而这是矩阵抓到的几乎每一帧都会碰上的那一处分
  歧。上下文文件通知里那条路径没有空格，于是整条路径就是一个 token。ink 把这个 token 挪
  到单独一行、再在九十八列上硬断；本端口把它起头的那一行填满、在剩下的列数上断 —— 在量过
  的那一帧上是九十五列。两者都说得通，而两者都不是一个可以照抄过去的宽度常量，因为两侧分
  歧的是一条「对当前行放不下的 token，是挪走还是就地断开」的规则。它与上面那条 markdown
  折行一样是记录而不修：规则在布局里，不在本端口选择的某个数字里。
- 渲染器不重绘一个「新内容是空格」的格子。在十帧上量到，而且它不会自愈：会话选择器的九个
  检查点与预览场景的那一个，扩展刷新通知里都有盒线字形站在它的六个空格上 —— 那是选择器把
  banner 行顶出屏幕之前坐在那些格子上的字形。同一条通知在它落到的行本来是空的那些帧上渲
  染干净，同一帧上选择器自己的框也从头到尾干净，所以这不是「没有清屏」；这是一次差分写入
  ，它跳过空格格，前提是底下那一格已经是空的。这个前提只在渲染器自己的缓冲与终端一致时成
  立，而一次把行往上挪的滚动会让那个被顶掉的行上的一致失效。写入发生在渲染器库的原生层，
  所以这里没有可修的位点；记录它，是因为它在真实终端上是看得见的乱码，也是因为一个绕法必
  须在视口每次滚动时强制一次整屏重绘。
- 窄终端上的标签行在 ink 下把每个 chip 的标签裁到省略号，在这里原样打印整个标签，代价是
  它们之间的间距。它没有对着 ink 的截断位点比过，所以那个预算是一个共用常量还是它自己
  的一个，没有确定。它与补全行的参数提示形状相同，后者已由决定 68 闭合。
- 受门禁的服务器对话框的正文段落把它的续行缩进了一列。两侧在段落的第一行上、以及那一行承
  载的八十八列文本上都一致；只有断行之后的那一行在这里多了一格前导空格。它与上面记录的
  markdown 分歧形状相同，也可能同源。
- ink 丢掉了受门禁的服务器对话框那个框的右手角落。那个对话框比 ink 其余的对话框多缩进一
  列，它的顶边与底边画到九十四格横线，而收尾的角落在帧上不存在 —— 框没有闭合。同样的边框
  在审批模式对话框与会话选择器对话框上、在少一列的缩进下，两侧都闭合。本端口画的是一个窄
  一列的闭合框，所以在这一行上对的是本端口，这处分歧被记录而不是被对齐。
- ink 在会话选择器的预览检查点上几乎完全不在场。按下预览键会卸载列表，而在预览体画出来之前
  抓到的那一帧只有三行 —— banner 的最后一行、通知与命令 —— 没有列表、没有预览、也没有
  composer。决定 67 为这一帧在更长的稳定等待之后加了一次抓取，三秒之后它仍然是那三行，所以
  在本 harness 能够到的范围里它不是一帧过渡：选择器就是不回来。下一个检查点又是列表了，而
  本端口在这两个检查点上都画出了完整的预览体。后果是预览那一支没有帧级参照可比，决定 67 对
  它的判断只有源码直查和结构性用例支撑。记录它，是为了让这一帧空画面不要被再次当成移植缺口
  报上来，也是为了不让它被当成一个可用的对照。
- 统计对话框自带一份 ref 镜像的副本，而不是调用那个共用的 hook，并且每次渲染都重建它的写入
  函数。两者都停留在外观层面：副本做的是同一个双写，而写入函数的身份没有任何东西拿去做
  memo 的依赖。它属于那两个对话框列表控件合并的一项，而不是单独落一次。
- 对话框外框声明了一个它从不读取的关闭处理函数。每一个需要关闭的调用方都是从它自己的按键
  处理函数里关的，所以那个 prop 是类型里的一个死可供性，不在屏幕上。外框的测试钉住了圆角
  轮廓以及标题的颜色与字重，却没有钉住认证对话框所要的那个方角轮廓，所以对那一种与众不同
  的边框样式做改动会直接通过。
- 三个分支的形状没有任何一次运行会到达。composer 的失焦边框颜色只被一个测试走到，因为唯一
  的生产挂载点把那个标志留在默认值上。footer 的审批模式颜色给一个枚举没有声明的模式涂上暗
  色，而 ink 让那个标签不着色，且枚举是封闭的，所以两侧都跑不到。共用的列表步进把它的行类型
  写成 unknown，并通过一次 cast 读取 disabled 标志，因为各个调用方的行形状并不相同，而一个
  声明出来的标志会在每一个从不设置它的调用方上触发弱类型检测。
- banner 的渐变数的是码点，而 ink 渲染所经过的那个库数的是 UTF-16 单元，所以一行含有代理对
  的字标会以差一步的方式上渐变。自带的字标一个代理对也没有 —— 它是框线字符，全部在基本平面
  之内 —— 但 banner 也接受一份自定义字标，所以用户字标里的一个 emoji 会在两侧染成不同的
  颜色。
