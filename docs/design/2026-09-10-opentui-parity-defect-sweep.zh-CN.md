# OpenTUI 一致性缺陷清扫 —— 与 ink 的逐帧实机验收

[English](2026-09-10-opentui-parity-defect-sweep.md) | [简体中文](2026-09-10-opentui-parity-defect-sweep.zh-CN.md)

本文是 OpenTUI 迁移第十批之后那次缺陷清扫的设计文档。迁移曾依据单元测试与
集成测试全绿被宣告完成，但把运行中的渲染器与 ink 并排一看，界面并不像同一个
产品：没有 banner、footer 对不上、各种 loading 状态缺失。这三块已另行恢复；
本文覆盖的是在它们背后由系统化逐帧对比发现的问题，以及由此产出的修复。计划
段落与滚动维护的缺口台账见
[#8662](https://github.com/QwenLM/qwen-code/issues/8662)。

## 问题

代码正确性已被证明，观感等价性没有。两个渲染器共用命令层、工具层与历史模型，
所以一个断言状态的测试在两边同样通过，而它们画出的屏幕却在分叉。以下三组缺口
全部来自真实 pty 上的观察，而非从源码推断：

1. **确认框替用户做掉的决定。** 所有工具确认都从同一份通用四行列表里回答。
   always-allow 行不说自己允许的是什么；在未受信目录里也照样提供，而那种场合
   根本不该把持久规则摆上桌；plan 与 edit 两类确认则直接给错了结果集合。这些
   背后还有一个静默的进程级故障：每个 OpenTUI 会话都失去了基于 AST 的 shell
   分析，于是权限规则返回为空，命令安全性分类退到保守兜底。
2. **对不齐的外框。** footer 把状态行截成一行；loading 指示器宣称有一个从未
   被任何调用方提供的 token 估算；弹窗从终端一边铺到另一边；补全下拉在计算列
   宽时没有算上它从未填充的来源徽标；footer 宣传了 Shift+Tab，而它没有绑定。
3. **本渲染器从未产出的会话行。** context 文件公告、扩展刷新提示、model 对话
   框的取消提示在 ink 里都存在并且进了 transcript；在这里要么从未发出，要么发
   进了一个不画任何东西的通道。另有两张字形表是被复制而非被引用的，而副本已
   经与 ink 的呈现选择符后缀发生了漂移。

第四组是在修前三组时发现的，属于结构性而非外观性：被移除的布局 prop 不会被
渲染器的 reconciler 复位，于是对话框与 composer —— 两个占据同一槽位的
`<box>` —— 互相泄漏了彼此的 margin 与 width。

## 方法 —— 观察通道是重建后的屏幕，并按序列比较

原始 pty 字节无法直接 diff。一个就地重绘的渲染器会发出光标寻址、擦除与不完整
单元格，于是同一块屏幕会到达为两条不同的字节流，而两块不同的屏幕也可能到达为
同一条。因此 harness 让每个渲染器在 pty 下跑同一段脚本化场景，在每个声明的检
查点重建屏幕，并把重建结果写成定宽文本。比较发生在重建结果上。

每个场景跑两遍，每个渲染器一遍，使用同一个 bundle 与同一组启动参数；检查点由
场景声明而不是按定时器采样，所以两腿是在脚本的同一位置被抓取的，而不是在同一
墙上时刻。二十六个场景覆盖启动、窄终端、输入与补全、`@` 补全、流中指示器、自动
放行下的工具执行、工具确认、slash 对话框、审批模式循环、自动模式启动提示、错误
路径、resize、clear 与退出、一次会遍历 loading 短语的长按、待办卡片、单独一个
问题的提问对话框、同一个对话框跨三个问题并带多选与手打答案、把那条手打答案改到
值的中间、审批模式变化时被拦下的确认框的释放、启动时对受门禁服务器的审批、一次
参数长到会被截断的工具调用、把同一次调用在关掉参数行的情况下重跑的对照臂、一份
长到溢出终端的回答、在溢出部分上滚下去再滚回来、两行宽到足以展示折行发生在哪一
列的回答，以及一个把两个调用同时停在审批上的回合 —— 于是第一个要排在第二个的
对话框后面。

比较方式有三个性质决定了结果该怎么读。

**垂直锚定是重建方式的属性，不是两块屏幕的属性。** 本渲染器画的是一个终端大
小的窗口，会话尾部落在输入行之上。ink 的 live 区在真实终端里占据同一个位置，
但 harness 是依据 ink 写出了什么来重建它的屏幕的，于是那块内容落在哪里取决于
ink 自己的重绘：在一个高对话框之下，重建结果里对话框占第 6 到 25 行、窗口其余
部分留空，而本渲染器会把同一个对话框贴着最后一行放。因此绝对行号在两腿之间通常
仍然对不上，按行号对齐的 diff 会报告重建方式而不是被测缺陷。比较会先去掉空行，
再用最长公共子序列对两个序列做 diff —— 这对块落在哪里不敏感，对块里有什么敏
感。当内容刚好填满窗口时两个序列确实重合：决定 26 的溢出臂就是逐行比较而不是
按序列比较的。

**归因之前需要对照臂。** OpenTUI 腿跑在与 ink 腿不同的运行时上，所以任何分叉
都同时是「渲染器干的」和「运行时干的」两个候选。在这个歧义要紧的地方，加了第
三条腿：让 ink 跑在 OpenTUI 的运行时上。它在 ink 上复现了缺失的 shell crawler
诊断，于是那条发现被移出了渲染器一栏；它没有复现缺失的扩展刷新提示，于是那条
留在渲染器一栏。

**场景等待所用的通道不是它比较所用的通道。** 到达一个检查点的办法是等待脚本
预期看到的文本，而这个等待扫的是字节流。整行重绘的渲染器能满足它，因为整行是
连续到达的；只重绘变化单元格的渲染器永远不能满足。一个就地从一种措辞改成另一
种的对话框问题，到达字节流时只剩互相差异的那几个单元格，于是等待会在一块其实
已经正确的屏幕上超时 —— 以这种方式失败的那一腿确实画出了它在等的那一行，而字
节流里只携带了它的五个单元格片段。现在等待除了扫字节流也会轮询重建结果，两个
通道一致了。先读字节流并不是冗余：它便宜，而且仍然能看到已经滚出重建窗口的文
本。

## 决定 1 —— 确认框按类型问 ink 的那个问题

对话框现在根据确认自身的类型构造选项列表，而不是一律用同一个形状。执行类确认
会说出它即将允许的命令根，于是「always allow」讲清了之后会覆盖什么；plan 类
确认提供恢复它所替换掉的审批模式；edit 类确认提供 edit 真正支持的会话级
allow-always，而不是它并不支持的 project/user 持久化结果。在未受信目录里，
持久作用域的行会被收起，因为给一个用户尚未信任的工作区加权限规则，不该由对话
框摆到用户面前。各行重新编号，数字键可直接选中，与内联提示一致。

## 决定 2 —— shell AST 解析器必须在渲染器启动前预热

渲染器的构造函数会装一个裸的 `globalThis.window` 来挂它的 animation-frame
垫片。解析器的 UMD 包装在首次求值时会探测 `window.document.currentScript`，
所以那之后的第一次动态 import 会抛错 —— 而解析器会把这个失败锁定到进程结束。
因此 import 被提前到启动阶段强制执行，那时 `window` 仍未定义，早于任何渲染器
构造。

这需要 core 包出一行：在其 index 上加一个再导出，让启动路径能拿到预热 helper
而不必深层 import。解析器在其他所有地方仍是动态 import，所以 deferred-runtime
不变量未变。也因为这个原因，该改动单独成一个提交 —— 它是本次清扫中唯一跨进
core 的编辑。

## 决定 3 —— footer 保留 ink 的状态行，loading 指示器拿到真实估算

状态行改为在两行预算内换行，而不是截断成一行，于是窄终端会像 ink 一样把 model
段推到第二行，而不是丢掉它。提示行仍然截断，因为一个能长高的行会在回合中途改
变 footer 尺寸，把 composer 在用户光标底下挪走。提示行还承载了 composer 不再
绘制的审批模式名：ink 把这段文本用作无障碍标签而不是可见行，而本渲染器没有无
障碍表面，所以这段文字必须在某处可见，否则哪儿都没有。

loading 指示器把字符计数器与 receiving 标志声明成了没有调用方设置的 prop，于是
它的输出 token 估算被钉在 0，方向箭头永久朝下。两者现在都来自 live turn，并按
ink 的方式统计模型文本、思考与工具调用参数，在工具结果回传模型时退回 waiting
阶段。

## 决定 4 —— 下拉列宽是推导出来的，Shift+Tab 是 shell 级绑定

下拉的标签列跟随正在补全的模式。slash 列表共享一个半宽列以便描述对齐；文件列
表不共享，因为 ink 只在某行带有需要对齐的描述时才共享列，而把一条纯路径钳到半
宽会把它在词中间折到第二行。行预算也把「下拉把自己的侧边 margin 嵌在 composer
的 margin 里」这件事算了进去，此前这给描述多留了两列，把它的尾巴折了行。

标签与它的参数提示此前被拼成了一个串，于是一个对列宽而言过长的提示会把整串词
换行，把该行撑到三行。它们现在作为独立子元素布局，并在列边缘断开，于是续行落
在提示自己的偏移上。

Shift+Tab 此前未绑定，所以 footer 宣传了一个什么也不做的快捷键。绑定放在 shell
而不是 composer：ink 把它的模式指示器挂在 app 级，只对一个 tab 视图禁用，所以
当对话框或确认让 composer 未挂载时，循环仍然可用。composer 只保留 Windows 的
裸 Tab 兜底 —— 那是唯一需要知道 Tab 是否已经被用于接受补全的路径。循环顺序取
自共享的模式列表，而不是枚举声明顺序的副本，所以不会与 ink 走的顺序漂移。

## 决定 5 —— 自动模式提示的门禁放在两条进入路径的汇合处

ink 把自动模式的进入提示门禁在「会话尚未持有该模式」上。轮换永远不会违反这一
点，所以该守卫在这里看起来是冗余的，就被省掉了 —— 但审批模式对话框打开时已经
选中了当前模式，所以一次裸 Enter 就是重新选择它。首次提示能在重选中存活，因为
它在 settings 里被确认过；而列出自动模式剥掉了哪些 allow 规则的那条提示不能，
于是每次重选都会重印。门禁现在放在两条路径的汇合处。

## 决定 6 —— 弹窗取得 ink 的几何，help 对话框取得一个可翻页的窗口

此前每个弹窗都从终端一边铺到另一边，而 ink 给弹窗加了两列 margin 并限制了宽
度，于是一条边框从第 2 列跑到第 97 列就停了。包装层现在提供这两者，这正是让一
个对话框读起来像对话框、而不像全屏模式的东西。确认框刻意留在它之外：它们的正
文会测量终端宽度来估算文本如何折行，所以在不缩小该测量的情况下缩小盒子会破坏
这个估算。

help 对话框此前打开在它的命令列表而不是概览上，其 tab 键也与 footer 宣传的不
一致。现在概览是起始 tab，Tab 与 Shift+Tab 按提示承诺的两个方向循环，方向键与
翻页键移动命令窗口、并在没有命令窗口的 tab 上不生效，此外没有任何键会关闭或导
航 —— 此前裸字母键会关闭对话框，意味着一个打字错误就把对话框关掉了。

那个命令窗口此前无论终端多高都固定十八行，而这比正文预算在扣掉该 tab 自己的
引导行、其间距与滚动提示之后所剩的要多。溢出此前的解决方式是丢掉引导行下的间
距并把滚动提示整个裁掉，于是提示所报告的滚动位置干脆不存在。窗口现在按扣掉这
些装饰后预算所剩来定尺寸，翻页按屏幕上真实存在的窗口移动。在低于 42 行的终端
上，这显示的列表比 ink 短，这是较小的损失：ink 保留它的十八行，改为裁掉提示。

model 对话框此前把它的详情分隔线画成二十字符宽，而 ink 是满宽的；并且在一个
model 的标题下不显示任何行。ink 把 runtime 与 discontinued 标记同时折进标题
与行描述，所以一个自身无话可说的 runtime model 仍会得到一行解释；条目现在带上
了它，而分隔线被按框内宽度写满，因为这里没有单边框可以用来画一条。

## 决定 7 —— 工具的流式输出是累积快照，不是增量

承载工具输出的流事件此前被塑造得与它旁边的 text、thinking 增量一样，于是消费
方做追加。但调度器并不流式发增量：它在每个 chunk 上发出到目前为止的整个显示
内容，然后发一个同样携带整个显示内容的最终结果，所以追加会把输出的尾部画两遍。
该事件被改名以说明它承载什么，卡片改为替换而不是累积。

折叠这些事件的 reducer 没有生产调用方 —— 只有它自己的测试文件。这早于本次清
扫；改名迫使了这次编辑，而把该 reducer 接线或移除不在本文范围内。

## 决定 8 —— transcript、composer 与 footer 共用同一个内缩

ink 用同样的两列内缩它的会话、composer 与 footer。这里 transcript 没有内缩，
而 composer 与 footer 各有一个，并且 composer 的外框比 ink 的右移一列、窄一
列。三者现在取同样的内缩，composer 在其上方保留一行间距 —— 那正是把一条已提交
的提示与在它下面到达的回答分开的东西。

## 决定 9 —— 错误行是一行，用 ink 那个字面十字

错误行此前是两行堆叠：消息，然后提示在下面。ink 渲染一行，提示以括号内联，且
其前缀是 U+2715 的字面十字，而不是共享图标表里的 U+2716 —— 两个字形差一个码
点，视觉上可区分，所以在这里引用那张表会是错误种类的复用。该行被压平，提示作
为次色段内联，前缀保持字面量，并加注释说明它为什么不是那个共享常量。

## 决定 10 —— 已武装的退出警告占据 footer 的提示槽

两次按键退出的警告此前画在 transcript 里、composer 之上，于是用户被告知再按一
次 Ctrl+C 的地方，正是他们没有在看的地方。ink 把该警告交给 footer 的底部提示
槽，并在警告期间把状态行门禁掉，所以它就贴在 composer 下方、上面什么都没有。
footer 现在把警告作为 prop 接收，并只返回那一行，按它所替换的提示的同一预算截
断。排队消息段是那个提示的兄弟而不是它的一部分，所以在警告武装期间它仍然可见。

把警告搬进 footer，也把它交给了 footer 自己的那道门禁 —— 该门禁会在对话框、
modal、工具确认或补全下拉出现时把整个 footer 隐藏掉。警告要越过这道门禁。在这里
对话框会让 composer 卸载，所以没有人拦截 Ctrl+C，守卫照样武装；若仍受门禁，第二
次按键就会退出，而那条警告从未上过屏。

做兄弟这件事同时也决定了分隔符。ink 把该徽标渲染成一个独立的文本节点，其内容以
一个字面空格开头，所以这一行读起来是一个空格，而 ink 自己那条提示的各个段之间用
的是 `' · '`。徽标参与的两处拼接 —— 提示行与已武装的警告行 —— 都用单个空格。模式
段保留它内部的 `' · '`，那正是 ink 在那条提示的各段之间所用的。

## 决定 11 —— 被移除的布局 prop 不会复位，所以两个分支需要 key

渲染器的 margin 与 width setter 会忽略它的 reconciler 为被移除 prop 传入的
`null`。对话框分支与 composer 分支都是同一槽位里的一个 `<box>`，所以没有 key
时 React 会复用一个实例并 diff props —— 而上一个分支的布局就卡在了节点上。打
开对话框会留下 composer 的 margin；关闭它会留下对话框的 width。两个分支现在都
带显式 key，而那个必须被放弃而不是被替换的宽度，改为设成它的 auto 值而不是被
移除。

只设置过某个 prop、或只移除过某个 prop 的站点不受影响，这些点被排查过而没有改
动。没有添加渲染器级测试：该行为位于 reconciler 内部，复现它需要一个真实渲染
表面，而 pty 矩阵已经覆盖了这一点。

## 决定 12 —— 字形表是引用的，不是复制的

此前有两张状态与消息字形表被复制进了本渲染器。两者都由 ink 的常量模块导出，而
且两份副本都已漂移：消息图标缺了 ink 为强制文本呈现而追加的呈现选择符（那些字
符默认是 emoji 呈现）。副本被删除，改为引用 ink 的表 —— 这才是让漂移不可能发
生、而不只是被修好一次的做法。这些选择符在源码里不可见，所以断言它们的测试用
注释说明了这一点。

## 决定 13 —— ink 会画而本渲染器不画的三条提示

扩展刷新提示此前从不出现，因为 watcher 在启动期间就上闩，早于本渲染器挂载，而
上闩不会重发：只订阅就会丢掉那条告诉用户去跑 `/reload-plugins` 的提示。现在
订阅时会重放该闩。重放以闩的持有者为键，而不是以构造为键，因为 shell 会在其
host 身份变化时重建它的 dispatcher，而该闩比这次重建活得久 —— 没有这个键，提示
会每次重建打印一次，帧把它抓成了两条相同的行。

context 文件公告在 ink 里是一次性闩：文件在整个会话期间都挂着，所以它只在第一
次真正到达模型的提交时公告，而不是每次提示都公告。ink 在三处重新武装该闩 ——
session id 变化、history 被替换、清屏 —— 因为这三者都会抹掉已发出的行，而文件
仍然挂着。这三者在这里都汇流到同一个点：可见 transcript 被清空或被替换，所以
重臂就放在那里。ink 那条替换 history 的重臂路径还会把闩与回放内容做协调；这一
点没有移植，因为本渲染器的 resume 回放根本不携带 info 行，那会让这个协调成为一个
永久为假的分支。

model 对话框的取消提示此前被发进一个不画任何东西的反馈通道，而不是 transcript。
它现在作为 transcript 行落地，与 ink 的「kept model as …」一致。

## 决定 14 —— 行的字形前缀不可被压缩

带字形沟槽的 transcript 行把沟槽做成消息旁边的独立 flex 子节点，而这正是折行后
的消息能获得 ink 那种悬挂缩进的原因。该子节点默认可压缩，而当消息的首个折行刚好
填满该行时，发生的正是压缩：在 60 列下，warning 行在一个 56 列的盒子里量出 57
列，它的前缀被压到 1 列，于是字形后面的空格消失，续行起点比它上方那条 info 行
（有 2 列余量、因而从未被压缩）左移一列。

前缀现在不可压缩。同一帧随后在盒子里量出 55 列，保住了空格，续行也与 info 行一
起落在 ink 的那一列。这是靠重建并重新抓取验证的，不是靠阅读代码：两行只在消息长
度上不同，所以那条被压缩的行正是那条没被压缩的行的对照。

ink 原来也这么做。它的共享状态渲染器把前缀放进一个独立的行子节点，给了它显式的
宽度与显式的不可压缩标记，再让消息占据剩余空间——这正是上面那组测量所重建出来的
排布。所以这不是绕开某个布局引擎默认值的权宜之计，而是参照实现里一处没有被移植
过来的部分；帧证据与源码如今互相印证。

修复应用到 transcript 里使用这一形状的四种行 —— info、warning、error 与 away
recap，最后一种有两个固定前缀，因此两处都要标记。刻意不应用到统计与鉴权对话框里
对应的前缀：它们位于定宽带框盒子内、有自己的宽度预算，那里的抓取没有显示该缺陷，
改动它们属于未经验证的编辑。

## 决定 15 —— model 对话框的三道关闭守卫

在没有选中项的情况下关闭 model 对话框时，每一条关闭路径都会播报那个存活下来的模
型。这把 ink 分开的几种结果混成了一种：离开一个辅助选择器 —— 语音、视觉、压缩、
图像或 fast 模型 —— 也会播报；而第一次 Escape 之后的第二次 Escape、或者落在切换
正在应用期间的那一次，会再播报一遍。

ink 用三份状态守卫这条播报：一份记录切换已提交的标志、一份记录关闭路径已经跑过
的闩锁、以及一份覆盖那个 await 的进行中标志。当闩锁或进行中标志任一被置位时，关
闭路径提前返回；只有在主选择器下、且没有任何东西提交过时才播报。本渲染器现在带着
同样的三份状态与同样的提前返回，而它的辅助判定是「该选择器的模式不是主模式」的
否定式 —— 覆盖的正是 ink 枚举的那五种模式，因为模式是必填字段，不可能静默漏过。
三者都不复位：对话框关闭时这个挂载点会卸载，所以重新打开是从全新状态开始的。

三者中有两者还守卫选取本身：ink 的选取处理器在切换正在应用、或已经提交过时提前
返回，因为在第一次应用落地之前再按一次 Enter 会启动第二次切换，而两次都会播报。
在关闭路径上闩锁总是先触发，所以那个提前返回才是已提交标志真正决定结果的地方。

播报本身也从 shell 的 notify 槽挪进了 transcript。ink 把这个对话框的三种结果
—— 一次选中、一次 escape、一次辅助选中 —— 全都写成 transcript 行，所以行会比
对话框活得更久；而 notify 槽是对话框区域内的一条裸行，随对话框一起关闭。

## 决定 16 —— transcript 条目保留 ink 的按类型上边距

这里的对话行是一条挨着一条打印的，而 ink 会在大多数行的上方留出一个空行。比对工装
此前把这件事抹平了：它把每一帧归一化为一串非空行，于是一次抓取可以在两个渲染器对
条目之间的每一处纵向间距都持不同意见的情况下，仍被报告为逐字节相同。三十九次比对
过的抓取里有十四次的空行总数不同，但这个数字本身不可用 —— 在底部锚定下，本渲染
器把一整块大空白停在输入框上方，而 ink 把它的空行留在屏幕底部。只度量 transcript
区域、并把结果表示为空行与内容行的游程模式，才能把它隔离出来：在四个带有已完成轮
次的场景里，ink 读作 `b1 c5 b1 c1 b1 c1 b1 c2`，而本渲染器读作 `c7 b22 c2` ——
一段不间断的内容游程。

ink 按条目类型决定这个边距。它的 history 渲染器对模型轮次和思考各返回一行，对一
份显式列举的状态、工具、提示与用户行返回零行，对其余一切默认返回一行。用户行经由
另一条路径达到同样的总量：history 渲染器给它零，而它自己的消息组件在内部声明了
这个边距。shell 行与两张 arena 卡片不在那份显式为零的列表里，因此走默认值。没有
首条目或末条目的抑制，静态区、待定区与滚动区渲染的都是同一个组件、带着同样的边
距，所以这条规则在全屏是统一的。

本渲染器现在把每个条目包进一个携带该边距的盒子，边距由它的 kind 解析得出：用户
行、助手行、思考、shell 行与两张 arena 卡片为一行；其余一切为零行。有两个 kind
在 ink 里完全没有对应物。task 卡片是本渲染器自己的形状 —— ink 把子 agent 渲染成
派生它的那个工具，走的是为零的那个分支 —— image 行同样是本地形状，因为 ink 把图
像画在携带它的那条消息内部。两者都给了零行，好让它们与身旁渲染的那条工具行保持
齐平；这是一个判断，不是对参照实现的解读，如果这两种形状将来获得了 ink 对应物，
应当随之调整。

边距位于外层包裹盒上，而按条目的行数上限作用于条目自身的内容，所以两者是相加的：
上限不会吃掉分隔行，分隔行也不会导致某个条目被裁切。

## 决定 17 —— 审批模式切换要释放那些它本不会拦下的调用

轮换进入一个自动审批模式后，确认框仍留在屏幕上。按键与对话框两条路径都汇入同一个
采纳点，而那个点只设了本地模式、播报了一次进入 auto 模式，然后就停了：一个已经停在
确认框后面的调用，会停在一个根本不会去问它的模式下面。

ink 把切换与释放配成一对。进入那个什么都批准的模式会确认每一个停着的调用；进入只批
编辑的模式只确认编辑类工具；而被标记为从不提供「始终允许」的调用则被放过，因为那个
标记意味着这道问题存在的意义就是由人来回答。这条选取规则在这里其实已经被移植过来
了，连文档字符串与单元测试都在 —— 它只是没有调用方，所以本渲染器有了规则却没有行为。

采纳点现在会跑这条规则，对每个被选中的调用确认一次，然后上报已结算，让入口把那一行
去掉。有两处细节与参照实现不同，且是刻意的。释放在确认时不逐个等待，而 ink 会一次一
个地 await，以避免一批并行调用乱序结算；在只有一个停着的调用时 —— 那也是任何场景唯
一会产出的情况 —— 两者等价，而且本渲染器在退出级联上本来就是不等待地结算一个停着的
调用。另外，无论确认是解决了还是抛错了，那一行都会被去掉，因为一次被拒绝的确认否则
会把模态框留在一道再没有人会应答的调用上面。

## 决定 18 —— 已提交的思考要报出自己的耗时，而它提示里写的那个键要真的被绑定

折叠的思考行打印了一条按键提示，而那个绑定并不存在。本渲染器里每一个键盘处理器都被
清点过，没有一个接这个键；那一行自己的点击确实能切换，但提示的 clickable 分支是关
的，所以唯一能用的那个可供性，恰恰是那一行从不点名的那个。

ink 在 app 层绑定这个键，旁边还有一个遗留的替代键，绑到一个强制展开所有思考的单一
标志上。它把一个思考解析为「该标志，或者用户逐个点开的那个 id」，这正是为什么把全局
关回去之后，被手工点开的那个思考仍然是开的。移植保留了两半：标志放在入口 —— 也就是
ink 那个 app 层拥有者的对应物 —— 所以当一个对话框或一个确认框占据屏幕时按键仍然能
落地；而那一行保留自己的点击状态。绑定走共享的匹配器而不是一个字面键名，所以用户的
重绑定与那个遗留替代键都能生效 —— 而且这条命令本来就已经在本渲染器的优先级表里占了
位，只是没有任何东西消费它。

标签错的原因相同：耗时在思考结束时就被测出来了，也一路带到了视图，而视图从不读它。
它唯一的读取者是 arena 卡片。ink 会报出耗时 —— 不到一秒读作「短暂思考」，超过就报
出时间 —— 并对一个从未上报过耗时的思考退回进行中的措辞。用哪个格式化函数是要紧的：
这里存在两个，一个四舍五入到整秒，一个保留一位小数，而 ink 的思考用的是整秒那个。

## 决定 19 —— 工具结果的结构化载荷只有一套优先级

一个待办列表以它的原始 JSON 到达了工具卡片。消费侧什么都不缺：事件带着一个 todos
字段，模型会把它折叠进去，卡片有一个勾选列表渲染器并把它排在所有其他正文之前。整条
链路都建好了，却没有任何东西往里生产。

有六条路径会把一个结果展示转成事件。其中一条会先检查那些结构化载荷 —— 文件 diff、
待办列表、ANSI 网格 —— 再退回到文本；另外五条直接压平成文本，所以它们每一条都会把
待办列表 dump 成 JSON。它们现在共用一个持有这套优先级的 helper，而压平退回的部分未
变，所以一个没有结构化形态的展示渲染得与之前完全一致。

六条中有两条保留自己的约定：一个实时分片与一份恢复出来的 transcript，会把压平后的
文本作为增量输出事件发出，而不是作为结果事件 —— 它们的测试钉住了这一点，而折叠器对
文本的处理两者完全相同。所以这两条只共用结构化的那一半，保留各自的退回分支。对它们
而言改变的是载荷而不是事件类型 —— 执行中的待办列表、以及恢复时的 shell 结果 ANSI
网格，现在会渲染出来而不是 dump。

## 决定 20 —— 受门禁的服务器审批复用策略，只移植视图

一份签入项目的服务器列表在这里从来不会被拿出来征求审批。ink 在其审批队列非空时就打开
那个对话框，而本渲染器完全没有对应物，于是一个受门禁的服务器会静默地保持未连接，而且
没有任何东西告诉用户为什么、以及该怎么办。

队列、那份按配置哈希持久化的决定、本次会话内的解除门禁、以及重连，全部住在一个只接受
config、返回普通数据外加一个处理器的 hook 里。它与 provider 安装流程一样是与渲染器无关
的，而本渲染器本来就逐字复用了后者，所以这次移植是一个视图加一个挂载点，而不是策略的
第二份副本。这里没有任何东西决定谁需要被询问、或者一个回答意味着什么。

挂载点是可能出错的那部分。ink 把这个审批排在 shell 确认框与工具确认框两者之上，所以它
在这里也直接占据那个槽位，而更新提示在它占屏期间保持被抑制，与其他弹层抑制它的做法完
全一致。

逐行读那一帧时，发现了这次移植自己引入的一个缺陷。ink 的布局在任何它计为可见的对话框面
前都会把整个 Composer —— 连它的 footer 一起 —— 卸掉，而这个审批就在其中；这里对话框占
据了 Composer 的槽位，footer 却仍走自己那道独立的门禁、不知道槽位换了主人，于是 ink 不
画的两行继续印在盒子下面。给那道门禁补上一个条件，这个检查点现在只剩下面两处残余。

几何是照着 ink 量出来的，不是假定的，而第一版有两处错：它把盒子画在终端左边缘、占满整
宽，并且不印行号。ink 把这个盒子比对话框区域已经定位好的那些弹层再往里缩一列，因为它
在那个区域内部又加了一道自己的边距，这使它比共享的弹层宽度窄一列；而它的单选行是带编
号的。两者现在在 100 列终端上量出来一致，且拒绝之后两腿都落在同一个 composer 与同一行
footer 上。

有两处残余是记录而不去追的。ink 的盒子没有右边框 —— 它自己那道边距把一个全宽盒子推出
了它父级能打印的范围一列，右边缘被裁掉了；那是一个溢出产物而不是一个选择，而这里的每
一个弹层都画闭合的盒子。还有正文里某一行折行后的续行在这里多带一个前导空格，这与已经
为上下文文件列表记录过的断行规则差异是同一类；要匹配它就意味着重新实现渲染器已经提供
的折行。

## 决定 21 —— 提问对话框整体移植，只在 ink 自己错的地方不跟随

向用户提问的那个对话框此前被削减到只剩它的字面选项。它不画自由文本行，于是一个答案只
能是模型恰好发明出来的某个选项；不在每个选项下画描述，于是一个标签必须承载全部含义；
也不画数字键，于是一次选择要花一次导航加一次确认，而不是一次按键。它的标题与提示措辞
也和 ink 不同。答案本身的传递是正确的，这正是状态层测试套件从来抓不到其中任何一条的
原因：一旦做出选择，两个渲染器就逐字打印同一张已结算的卡片。

ink 会画的东西现在这里都画了，而几何是推导出来的，不是猜的。那条命名每个问题并标出已
答问题的 chip 行，其上限由一个从 ink 自己的对话框引用过来、而非重新实现的水位填充助手
给出，然后再扣掉这一行在标题文字之外花掉的每一个单元格：内边距、当前 tab 标记、submit
chip、每个 chip 之间一道间隙、每个标题两列前缀，以及每个已答标记再多两列。它在每次渲
染时重算，因为作答会改变那些标记。

ink 的那些开销项是逐行照搬的，而从中被减去它们的那个宽度也一并搬了过来；一轮评审发现
那第二个数字是错的：它属于 ink 画这一行所在的那个盒子，而这一行坐在另一个盒子里，后者
花掉两列外边距（只在左侧）与每侧一列内边距 —— 而内边距已经是上面那些开销之一。把那一
列内边距算两次，再算上 ink 的 transcript 缩进，就从一个只花四列的行上扣掉了八列，于
是标题在行里还有空间时就被省略号截断了。修正后的基数确实是这一行的真实宽度，而不只是
一个更大的数字 —— 这一点是拿一帧排好版的画面定下来的，而不是它当初所来自的那些 JSX
prop：在五十八列的终端里放三个十二格的标题，这里会在盒子留下的 54 格里整行打印出 52
格，并且没有任何一行到达终端的最后一列。ink 在同样的宽度下把三个都省略号化了；那个区
间记录在下面，而照着它做意味着裁掉这一行本来就放得下的文字。

有两处分叉是有意的，而且性质不同。第一处是 ink 自己有、这个移植没有的缺陷。ink 对一次
按键把手打的自由文本答案提交两遍 —— 对话框自己的按键处理器与它挂载的输入控件都订阅
了，而按键层向每个订阅者广播、没有焦点栈来仲裁 —— 每次提交都推进一个 tab，于是紧随
其后那个问题在从未被画出来的情况下被跳过。这不是仅凭源码推断出来的：验收运行的 ink
腿在等一个始终没有出现的问题时超时，而它自己的复核 tab 随后把那个问题列为未作答。
这里一次按键推进一个 tab。跟随 ink 会复现一个缺陷而不是复现那种体验，而修 ink 会移
动整轮清扫用来度量的参照物，所以这处分叉被记录下来。场景被重排为在最后一个问题上使
行自由文本行，那里 tab 下标会被钳住，两腿一起到达复核 tab。

第二处分叉是这个移植失去的东西。选项行是手动画出来的，而不是用共用的 select 控件，那个
控件的指针接线没有跟着过来：点击一个选项不再作答，悬停也不再高亮。这个对话框里并没有一
个还留着那个控件的列表 —— 这一分支只带着问题流程返回 —— 所以要比的是它的兄弟确认类型，
那些类型的结果行仍然是那个控件，仍然响应点击。按键能回答 ink 这个对话框能回答的每一个问
题，这正是本清扫设定的标准；指针因此被留给它自己的改动，而不是被论证掉。点击需要在
chip、自由文本行以及 submit 与 cancel 行上各有各的含义，而它们回答的是不同的问题；并且
这些行刚经历过的那一类隐患同样是指针隐患 —— 一次落在同一次读取里的点击，只是换了来源
的一串连击。这条也没有任何一腿在度量：工装每次 stdin 写入一个字符，从不发出鼠标序列；
而报告这一条的那次运行在它自己的环境里起不动本渲染器。

自由文本行把它的值保存在一个与状态更新并排、同步写入的镜像里。按键事件可能在一个
React 批次内到达，而一个用其渲染所捕获的值去构造下一个值的处理器，是在往一个已经过期
的快照上追加，于是一串连击只保留最后一个字符。ink 出于同样的原因保留同样的镜像。有一
个测试在单个批次内派发一串连击，而这个修法是通过把镜像取出来验证的：恰好只有那一个测
试失败，且那一行只显示五个已打字符中的一个。在真机上这个隐患没有触发 —— 一个二十字符
的答案在两腿上都完整保留 —— 所以这个镜像是构造上的正确性，而不是对某个已观察到的截断
的修复。

回答一个问题不是就地换 tab，而是在 ink 的那次停顿之后才调度换 tab；而一次落在该停顿
内的第二个答案，过去会覆写已调度的那次换 tab 的句柄却不清掉它。于是两个定时器都会触
发，各自前进一个 tab，夹在它们之间的那道题就从未被画出来地被跳过了 —— 正是本决定要消
除的那个失效，只是从另一条路径到达。ink 也取消不了那次换 tab：它调用 `setTimeout` 时
根本没有保留句柄，所以它同样带着这个孤儿定时器。本渲染器为了在卸载时清掉定时器已经持
有的那个 ref，让取消只花一行。有一个测试在停顿之内把同一道题答两次，并断言下一题仍然
出现；把那次清除取掉，它就失败。不过 150 毫秒内两次 Enter 是打字快，而不是压力用例，
而且任何一腿都没有被观察到因此跳过一道题 —— 这次取消同样是构造上的正确性。

比较了八个检查点。每一行对话框内容都与 ink 逐行逐缩进一致，包括标记在某个 chip 的自由
文本框被勾上时就出现、早于任何东西被提交，包括多选答案那个「逗号加空格」的连接并把手
打条目计入其中，也包括复核 tab 自己的那条提示 —— 它在 ink 丢掉取消子句的地方同样丢
掉。剩下一处分叉：长路径在哪里折行。这里原先记录的第二条 —— 垂直锚定 —— 已在开头撤回：
两块屏幕在终端里占据同一个位置，真正不同的是工装把 ink 的那块内容重建在哪里。原先记录
的第三条 —— 等待行停在哪一帧 —— 已由决定 28 关闭；第四条，启动时的更新提示，已被证
伪：那条提示来自运行时而非本渲染器，而且工装在两条腿上都把它压掉了。

## 决定 22 —— 确认框画在会话所在的地方

一条工具确认原本以一个模态框到达：一个占满宽度的带框盒子、一行报出工具名的标题、
一行单独宣告某个调用正在等待、外加一条关于在列表里导航的提示。ink 一点都不画这些
外框。它的确认是 transcript 里的一个同级节点，直接落在正在等待的那个调用那一行的
下面，没有边框、没有标题行、也没有导航提示。于是批准一条命令在这里读起来像是在回
答一个对话框，而不是在继续这段会话，而且那个盒子把问题和它的选项推到了比 ink 所处
位置靠右好几列的地方。

外框已经去掉，正文、问题与结果清单都落在 ink 使用的那些列上，确认框的行序列现在在一百
列终端下与 ink 逐行一致。

这里对这一改动下过一个判断是错的，是合并把它抓出来的：那个为已被去掉的外框预留空间的
行数预算，曾被说成在 harness 所用的视口高度上不起作用。它并不是不起作用，只是 harness
从未跑到它真正收紧的那个高度。上游是在 80 行终端上，一条超长确认把载荷的尾部连同结果
清单一起推过了屏幕底边，于是用户读不到自己要批准什么、也够不着那些选项，之后抬高了这
同一个预留量。那个修复先合并了，本改动是换基到它之上继续的。

于是这个预留量是被重新推导出来的，而不是照抄：内联之后的确认框在正文上下仍然要花掉的，
是 banner、新会话开屏时的启动公告、带本回合边距的提示回显、卡片自己的隐藏尾行、问题行、
结果清单，以及那条等待行。早先那一版算进去的边框、标题、正文上下边距和底部提示，都随外
框一起没了，所以这个数比它替换掉的数小，小的幅度差不多正是那几行花掉的。然后两边都验了
一遍：跑 80 行 110 列的那条长确认场景，在合入的取值下是绿的，在零值下会等载荷尾部等到
超时 —— 所以这条场景确实还守着这个数。但它守得不紧：比合入值再小四行的取值同样是绿的，
也就是说阈值落在本轮关心的区间之下，钉住合入值的是那套算式而不是这条场景。

还有一处后果是被核对过、而不是被假设的：当一个调用被停住时，loading 指示器会换成 ink
那句等待中的措辞，并去掉它的耗时、token 与取消后缀 —— 既然没有在飞的请求，就没什么可
取消、也没什么 token 可数。这条等待行只为工具确认渲染：服务器启动审批、目录信任门禁与
动作确认全都到达在会话空闲之时，而 ink 自己的指示器在这种情形下什么都不画，抓取的帧在
两半上都与此一致。这一块在纵向上的位置不是这些帧能判定的：上面记录的那处分叉属于重建
方式，而不是任何一块屏幕，因此在这里既没有证实也没有排除。

## 决定 23 —— 卡片的渲染偏好按事件重新导出

工具卡片会优先使用它旁边的结构化载荷而不是那段摊平的文本，正是这个偏好让一次 shell
运行画出带样式的 token 网格、让一份 diff 画出带颜色的行、让一次 todo 写入画出状态清单。
但喂给卡片的历史折叠只会加上这些载荷、从不清掉一个，于是这个偏好可以活得比它所依据的
那个载荷更久。

一条 shell 命令恰好会走到这个状态。它在运行时流式输出带样式的内容，而如果这段流随后触
发了二进制检测，累积下来的输出就会被一个纯字符串替换掉。卡片会一直显示它见过的最后一
个网格，调用结算之后也一样，于是用户既不知道出现了二进制输出，也永远看不到随后那些
字节数。任何显示种类在飞行中途改变的工具有同一个形状，因为一份结果最多只携带一个结构
化载荷。

每个事件都携带完整的显示内容，所以结构化字段现在是从事件里导出的，而不是往卡片上累积。
产出这些事件的三个生产者各自在结构化形式与摊平形式之间挑一个，绝不会为同一个结果同时
发出两者，因此重新导出不会丢失任何东西；而那一次可能在完成之后才送到更新的尾部刷新，
会在调用返回之前被取消，所以没有哪条路径能把后来一个事件合法丢掉载荷再拿回来。出口
披露保留它原有的粘滞行为 —— 它是结果之下一条额外的通知，而不是结果的另一种渲染，也不
参与卡片的这套偏好。

## 决定 24 —— 同一个镜像也守住认证输入

端点与 API key 两步共用一个行输入 helper，而它用「注册它的那次渲染所捕获的值」去构造
下一个值。从同一个 pty 缓冲区里读出的按键可能在单个 React 批次内被派发，中间没有任何
渲染把它们分开，于是这一串连击里的每个字符都追加到同一份已经过期的快照上，输入框最后
只留下最后一个字符。粘贴是安全的，因为一次括起粘贴是携带全文的单个事件；以人类速度打字
也是安全的，因为每次按键都会先冲刷一次渲染 —— 这正是那些一个 act 打一个字符的既有测试
从未看见它的原因。

这个 helper 现在为自己的值保留一份镜像，在每次变更时同步写入、在渲染时重新对齐，于是每
个事件都追加在上一个事件的产出之后，而从别处设进来的值仍然会被取到。两步都通过普通的
state setter 到达它，而 setter 存的就是收到的那个值，所以镜像会在下一次渲染与父级收敛，
修复因此留在 helper 内部，没有改动 ink 自己的向导。把镜像拿掉只会让那个连击测试失败，
一个十二字符的 key 到达为它的最后一个字符。与上面那个对话框的行同理：真机上没有观察到
截断，也没有任何场景走认证向导，所以这是构造上的正确性，只有单元测试覆盖。

## 决定 25 —— 参数行，以及一个箭头而不是每张卡片一行

当 `ui.showToolCallArgs` 打开时，ink 会把这次调用的原始参数写在卡片 header 下面一行暗色
文本里，上限两行折行，余下的折叠成 `… +N chars (ctrl+o)`，并在会话进入那个键所切换的详情
态时完整打印。在这里这个设置没有任何读取点，也根本不存在这样一行。这套策略没有被重新
实现：序列化、与「描述本身就已经是那份载荷」时的去重、按 header 自身内宽缩放的字符预算、
规避代理对安全问题的逐列行走，以及针对提示注入的清洗，全部来自 ink 所用的那个 helper，
而它被拆开是为了让两个渲染器读同一个事实来源。这一行的位置在 header 与正文之间，与 ink
的排序一致。

调查在写下任何一行之前修正了前提。原先的说法是「没有任何路径携带调用的参数」；实际上
实时路径一直都带着，就在打开这张卡片的那个事件里，而它携带的正是 ink 这个设置所读的
那个值。真正缺的只有两个载体 —— 由 `@` 提及文件所引发的转向卡片，以及恢复会话的
transcript —— 而这一行仍然哪儿都不画，因为没有任何东西去读取条目上的那个字段。第一次
尝试载体改动时在调度循环里加了第四个来源，等测试显示它每次调用把同一行发了两遍之后被
回退；它暴露出来的事实是那个既存载体完全没有测试，所以一个把它丢掉的折叠本会通过。
如今那个既存载体被钉住了，新补的两个也是。

在真机上，两腿都画出了这一行，而折叠掉的余数在两腿上是同样的字符数。这一行在本渲染器
占用的物理行数比 ink 多，那是下面记录的折行规则分叉，不是这一行自己的问题。

标记等待调用的那个箭头原本画在每一张待审批卡片上。ink 只画在一个上：它的门禁是第一个
正在等待审批的调用，而本渲染器也只显示那个调用的对话框，所以其余每一个箭头标记的都是
用户无法操作的调用。这个标志现在取自第一个待审批的 id，并且有一个测试断言第二个待审批
的调用拿不到箭头 —— 验证方式是把这道门禁去掉，那会让该测试失败并在屏幕上留下两个箭头。

## 决定 26 —— 会话拿到视口，chrome 保住自己的行

应用按自己内容的高度排布那一列，所以会话每多要一行，输入行就少一行可见性。在一百列
乘三十行的终端上用一个四十九行的回答复现：banner 占住第 1 到 6 行，回答的起始行落在
第 15 行、它下面的十五行把终端填到第 30 行，而 composer、loading 指示器与 footer 被
排到了最后一行之外，完全没有绘制。第二轮对话随后证明了这个后果而不是描述它 —— 脚本往帧
里打字，帧里没有任何东西移动：打字之后抓的那一帧与它之前的两帧逐字节相同，而那一轮的标记
从未进入字节流，于是场景的检查点超时。同一套机制也会裁掉对话框：在一百乘四十下命令帮助
页有三十行高，而承载它的那一帧结束在自己的 footer 提示行上，收口的那道边框掉到了终端之
下。

ink 对此免疫，却并没有解决它。ink 的永久输出进入终端自己的回滚缓冲区，由终端负责滚动；
live 区只保留当前的尾部。库里有等价的东西 —— 把终端切成回滚区域与固定 footer 的屏幕
模式 —— 而它被搁置的原因就写在这个模式自己的几何计算里：渲染树被界定在 footer 那一条
带上，上方区域由捕获到的 stdout 喂进去，所以采用它意味着把每一条 transcript 条目重建
到 React 之外。迁移自身那份「已接受的取舍」早就记录了放弃那个模式、改用单一滚动区；
缺的只是把那个区域接上。这补的是已经写下的设计里的一个洞，不是另起一套方案。

需要四个属性，而它们没有一个能从库的命名里读出来。根列被终端高度界定，因为 flex 子元
素否则就拿自己内容的高度当高度。所有会流动的东西 —— banner、transcript、两行通知 ——
被移进一个随剩余空间伸缩的滚动区。该区域带着一个粘性的底部锚，所以它显示尾部，并在每
次布局后重新咬合，直到用户从底部滚开；这个锚需要同时给出库的那两个 prop，其中单独一个
是无效的。这也是为什么「每次更新时显式滚到底部」被否决 —— 它在静止帧里量出来一模一样的
效果，而用户一碰滚轮它就和滚轮作对。区域之下那些行 —— 每个对话框连同 composer 与
footer —— 被锁住不被压缩：没有这把锁，布局会把区域的内容高度摊派到整列上，把 composer
的三行边框挤成同一行画三遍，因为一行文本不能收缩得比它自己的内容还小，它宁可覆盖邻居也
不裁剪。每个属性在进入应用之前都先在同等尺寸的合成夹具上确立，shell 的测试如今把这四个
都钉住 —— 验证方式是把它们逐个去掉，每去一个就让一个测试失败。

在真机上，溢出臂是一个精确匹配：它的三帧全部与 ink 逐行一致，从回答的最后一行一直往下到
footer 的模式行，差异只有一个字符 —— 本渲染器画在最右列的那格滚动条指示。它是有意留下
的：它是「折叠线以上还有可达内容」的唯一线索，而对话框本来就带着一个。

滚轮随后在同一臂上被测量，而不是被假设，因为「让用户从锚上滚开」这个决定正建立在它之
上。注入二十格把区域往回推了二十行，从回答那串编号行里的第二十五行退回第五行，而
composer 与 footer 一行都没有动；反向六十格让锚重新咬住了尾部。那正是「每帧一次滚动调
用」会毁掉、而键盘绑定必须对上的行为。

本文曾记为刻意的两个分叉作为副产物关闭了，两者都有帧为证。banner 不再常驻：它随会话
增长滚出区域，而 ink 是把它提交进回滚缓冲区。对话框现在也会重排会话：在三十行的帮助页
之下区域缩到了十行，让出了 banner 的最上两行，而对话框本身完整装得下。一个和终端一样
高的对话框把区域压到零行是同一个行为，不是新的缺陷，因为 ink 也把那些行推出视口。这里
没有的是用键盘滚动这个区域。

## 决定 27 —— 长的 shell 卡片为屏幕做压缩，为模型保留原文

ink 把一条 shell 命令的输出写两份。放到转录行的那一份经过共享的历史保留压缩；交给
模型的那一份保持原文。本渲染器在它的两个写入点上都把裸的累加结果放上卡片 —— 节流
后的流式快照与最终结果事件 —— 于是一条长跑命令会把它的完整输出在整个会话剩下的时
间里钉在转录中。在本分支上这不再只是观感问题：决定 26 用终端高度界定了区域，因此那
些 ink 会压缩的行会把更早的内容推到折叠线以上。

两个写入点调用的都是 ink 的历史折叠所用的同一个 helper，所以保留上限只有一个所有者，
而不是一份会各自漂移的副本。工装里没有任何场景产出那么长的输出，因此这件事由单元测
试钉住，而不是由某一帧：两个写入点各自断言卡片显示保持在保留额度之内，而写入历史的
那一份仍然拿到完整字符串。移除压缩恰好让这两个测试失败、其余测试不受影响，失败的断
言里点名了四万一千与三万七千这两个超长的显示长度。

## 决定 28 —— 对话框开着时，等待行静止不动

当一个调用被确认框挂住时，本渲染器仍在持续重画那行等待提示，而 ink 不会。这是量出
来的，不是推断的：一个探针复现了提问对话框场景，在对话框打开的情况下每秒重建一次屏
幕、连续采十五秒；ink 腿每一次采样都是零字节，而本渲染器腿约十二字节，且每一次采样
上那个格子都不是同一帧。十二字节每秒正是该渲染器自己的节奏 —— 共享的转圈间隔是八十
毫秒，而只改动一个格子的重绘大约就是一个字节。两条渲染器在没有打开对话框时都一字节
都不发，所以这不是整棵树在重画。

门禁在 ink 的 `RespondingSpinner` 里：它只在响应态动画，其余状态下画出自己被传入的
`nonRespondingDisplay` 字符串，而 `LoadingIndicator` 在等待确认状态下传给它的就是某
一个静止帧 —— 那个状态下根本没有任何定时器在跑。本渲染器的转圈组件持有一个无条件
的 interval，于是在「只有用户的回答才能让它停下来」的时候这一行还在索取注意力。代
价不只是观感：验收工装靠观察输出变静默来判定一条腿已经落定，于是确认类场景里每一条
被挂住的腿都会吃满六十秒的空闲超时（某场景某一条腿实测 60,088 毫秒、39,798 字节）。
检查点由场景声明而非按定时采样，所以没有任何判定因此失效 —— 只是每条被挂住的腿都付
了这段等待，而帧对比把这些行里的每一行都算成本文档已经记录的那类 spinner 帧差异，
而不是内容差异。

门禁被移植过来了，而它停下时画的那一帧是共享的、不是抄的：它进了两个渲染器本来就从
同一处读取的转圈常量，而 ink 此前把它写成了字面量。两条测试覆盖这一对 —— 回合在飞行
中时帧会推进，调用被挂住时帧停在那一格。它们各自钉住的是显示的那一帧：取出挂住分支只
让「挂住」那条失败，取出 interval 只让「飞行中」那条失败。前者当初没有钉住的是计时器本
身 —— 一条继续走时、却每次都打印同一帧的行是能通过的 —— 所以「挂住」那条现在还会断言
没有 interval 留在运行，那正是本决定在真机上量到的代价。

这一行的短语也服从 ink 为自己 composer 读的那个无障碍设置，而这道门禁必须到达这一行的两处
挂载 —— composer 的那一处，以及挂住的确认框下面等待行的那一处 —— 因为只让其中一处闭嘴的
设置，会让另一处继续轮换词。三条测试钉住它：设置显式关掉时，两处挂载各自的短语都被丢掉；
设置什么都没说时，两处都保留，那正是 ink 对缺失值的读法。把这个比较反过来会让两条都失败，
从任一处挂载上摘掉这个 prop，会让拥有那一处的那条测试失败。

这一行自己的耗时计数也需要同样的处置，而最顺手的接法是错的。共享的计时器会在自己那个
「是否在跑」的旗标由假变真时把已累计的耗时清零，所以把它接成 `streaming && !waiting`
—— 那正是「丢掉后缀」所暗示的接法 —— 会在被挂住的调用恢复时从头开始计数，于是一个已经
跑了半分钟的回合把自己报成四秒。改为把计时器另一个「暂停」旗标交给它，它保住已累计的时
间并从那里继续。差别由一条测试钉住：让调用跑到第三秒时挂住、停三十秒、再恢复，一个节拍
之后读到的是四秒；上面那种接法会让这条测试在断言 `(4s` 的地方失败于 `(1s`。挂住期间这一
行根本不打印耗时，如上文所记，所以这影响的是用户回答之后看到的数字，而不是对话框开着的时
候。

之后重跑全量矩阵，在真机上而不是在测试里确认了它：十一个在对话框挂住时取到的检查点，
每一处两侧各减掉一行，从四行分叉变成三行，那里剩下的行是决定 21 记录过的长路径折行断
点。总分叉行数从 221 行 ink 独有、265 行 opentui 独有，降到 210 与 254。逐字节一致的检
查点数目仍停在那次运行打分的那 69 个里的 22 个 —— 正是那行折行使它们没能并进去，所以
这次冻结在每一处关掉了一行，却没有翻转任何一条判定。

## 决定 29 —— 排在另一个审批之后的已批准调用，用 ink 的等待字形停着

一个模型回合可以返回两个都需要审批的调用。批准第一个并不会让它开始跑：这一批里第二
个的审批还挂着，于是调度器把第一个按在 `scheduled` 里，直到那个回答到达。ink 的卡片
会读出这个状态，并在整段等待里保持 `o`；本渲染器却在回答落地的那一刻就把这一行换成
了 `⊷` —— 那是「正在干活」的字形，可这个调用等的是人。

ink 的状态映射把 `validating` 与 `executing` 归到 Executing 显示态，把 `scheduled` 归
到 Pending；它的指示器把 Pending 画成成功绿的 `TOOL_STATUS.PENDING`，把 Executing 画
成会切换的转圈 `⊷`。两个渲染器读的是同一个调度器，所以这件事要的状态本来就在本渲染器
手里 —— 它订阅的那批更新里，每个调用都带着自己的 `status`。缺的只是那一次读取，不涉及
对共享调度器的任何改动。

让这一行值得停下来的原因是：`TOOL_STATUS.PENDING` 在这一侧根本没有任何生产者。状态表
上方那段注释列出了共享常量定义的六个字形，而这里被产出过的只有五个 —— 所以那一行不是
把正确的状态画成了错误的一帧，它画的是一个本架构没有名字的状态。

找到它的场景是新加进矩阵的：默认审批模式下一个回合里两个 shell 调用，在两次批准之间
抓取屏幕。真机上的受控对照只变一个量 —— 回退读取点，bundle 与场景其余部分不动 —— ink
那一行是 `o Shell touch acceptance-two-a`，本渲染器对应位置是 `⊷ …`，而这一对正是该检
查点四行分叉里的一行。补上读取之后两侧都读 `o`，该检查点降到三行，剩下的就是决定 21
记录过的长路径折行断点。

这个事件是按调用集合触发的：第一次发现某调用进入排队的那次更新发一个事件，同一状态的
重复更新什么都不发，转入 `executing` 时发一次清除 —— 所以从未离开 `awaiting_approval`
的调用既没有事件也没有状态。三个测试撑起这条路径的三层，四个变异让它们各自失败：删掉
字形分支只让渲染那条失败，删掉读取只让调度器那条失败，削弱折叠只让模型那条失败，而去
掉去重守卫会让调度器那条失败 —— 因为它给每一批里的每个调用都打了一次清除。

同一个场景还把另一处分歧记进了后续工作：两个调用同时等待审批时，本渲染器把打开的确认
框接在两张卡片之后，而 ink 把它放在两张卡片之间。

## 决定 30 —— 回合中排队的提示，像 ink 那样列在 composer 之上

一个在回合运行时提交的提示，在这里只被计数、从不被显示。它的长度会到达 footer 徽标，
composer 的上键在顶边也能把一条文本弹回来供编辑，但这些文本本身只能通过排空来读取
—— 而排空就会清空队列。ink 改为把它们列在 composer 上方：一次三条、每条压成一行，
更多在等待时给一个溢出行，外加一条念出按键名字的提示，只在队列前几次被填满时显示。

移植过来的是 ink 的那个组件，逐行照搬，提示也在内，只多加一样：排队的那一行在被量宽度
之前会先被剥掉终端转义，而 ink 的组件把这件事交给终端。此前挡住的是读取而不是渲染。队
列住在一个 ref 里，好让一个回合能在一拍之内把它排空再放回去，而 ref 对一次渲染是不可见
的 —— 于是 ref 仍是那个同步的真相来源，同时移动它的五处各自再往 state 里复制一份：
压入、排空、回合中止时把仍在搭载的文本放回去的恢复、供编辑的弹出，以及为 `/clear`、
恢复会话与分支兜底的那次转录重置。最后这一处决定了这些行是随清屏一起脱落，而不是活过它。

这是本文档里唯一一件没有帧能作证的改动。两个渲染器都会把一个回合中按普通回车提交的文
本 **转向（steer）**：它在下一个采样边界被排空，作为真实的用户内容进入下一次模型请求，
所以这些行在一个回合之内出现又消失。要一个活得比回合更久的队列，就需要把提交推迟到空
闲，而在 ink 那是 Ctrl+Q —— 本渲染器并没有绑定它：这个命令在 key map 的优先级表里被列
出，但读那张表的解析器没有任何生产调用方，于是这次按键落成普通文本。这些行在这里只在
一个回合的长度内可达，这也正是矩阵里没有任何场景在任一腿上产生持久队列的原因。

有一处范围是被定下来的，不是被发现出来的：这些行列的是引导队列，shell 自己的延迟通道
不在其中。一个在被持住的命令仍在运行时提交的提示，会落在 shell 为自己保留的第二个列表
里，而无论是这些行还是徽标 —— 两者读的都是那份被镜像的队列 —— 都不会说它在等待，于是
那段文本只在它真正开始运行时才出现在屏幕上。ink 只有一个队列，会把两者都列出来。把它们
一起列出，与那个本可让队列持久化的键属于同一次改动：徽标与行必须一起动，否则屏幕上的两
个计数会互相矛盾。

有一处不对称是记录在案、没有修的。这些行挂在 composer 的那个分支里面，而
本渲染器把这一分支的位置交给了一个被挂起的工具确认框 —— 第一个待批准的调用在
那里作为模态对话框打开 —— 于是整个分支被换掉，行连同提示的计数器一起离开画
面，直到那次调用结算。ink 在同样的状态下继续挂着它的 composer：一个被挂起
的调用在它那里是转录区里的一张内联卡片，而它的对话框闸门列的是用户正在作答的
那些弹窗，从来不含工具队列。一个对话框确实会在两边都把 composer 卸掉，所以
一个已经走完的计数在两处的复位方式一样。要让行挺过确认框，就得把它们挂到上面
一层的 chrome 盒子里，代价是它们会落在等待行之上，而 ink 把它们画在转圈提示
之下。

覆盖是三层单元测试：组件的六条（队列为空时什么都不画、每条提示一行且空白被压平、三
行的上限与它的溢出行、前三次填满时出现而第四次不再出现的提示、按终端宽度减掉 ink
缩进截断的一行，以及在到达屏幕之前被剥掉终端转义的一行），hook 在上述每一处对被排队
文本的断言，以及一条钉住位置的 shell 测试 —— 这些行与 composer 一起落在那块不滚动的
chrome 里，而不是随对话滚走，并且落在它的上面而不是下面。十一个变异 —— 从 ink 照搬的
那五个行为各一处、每个镜像点一处、挂载处一处 —— 每个至少让一条测试失败，其中有一处局
限：剥转义这一处加法没有属于它自己的变异。挂载那一处的变异是把排队行移到 composer 下面，
而那条钉住位置的测试现在会把两者在 chrome 自己的文本里排出先后，所以这次移动会让它变红。
五条照搬来的组件行只让
属于自己的那条失败；镜像点做不到一一对应，因为一个从未拿到第一条、或从未被清空的列表，
之后好几个回合还在被断言：抽干时不镜像让一条断言失败，推入时不镜像让四条失败，弹出编辑
让两条失败。

## 决定 31 —— 模型对话框的结果，既显示也记录

`/model` 对话框留下的那一行 —— 一次选取定下的模型，或是一次退出保住的模型 —— 只到了
转录，没到会话日志，而 ink 在那三处结果点各自都留有一条记录。分发器兜不住：它的那
个 result 阶段在对话框还开着时就结束了，输出列表是空的，而 ink 写的也是同样这一对空
的。所以 ink 把自己三处结果点每一处都再配一条 result 阶段的记录，念出命令名、带上那
一行。本渲染器现在做同样的配对，并且是同一个对象：显示的行与被记录的行是一次构建出
来的同一个值，两者无从分叉。

两处沉默是有意的。一个没能落地的选取什么都不记录 —— ink 会让对话框带着错误继续开着，
记下这一行就会在恢复时重放一次从未发生的切换。而对话框不会补一条 invocation 阶段的
记录：裸命令自己的调用已由分发器写好、且被隐去，再来一条就是重复。

覆盖是单元层加一次磁盘核对。对话框测试套件里三条已有用例现在连同那一行一起断言记录
器 —— 一条管两次到达的退出、一条管仍在应用中的选取、一条管落地之后的重复选取 ——
新增的第四条断言失败的选取在两处都不留下痕迹。五个变异 —— 完全不记录、阶段写错、命
令名写错、负载为空、失败也照记 —— 每个至少让一条测试失败。实机侧，slash 对话框场景在
两条腿上都打开 `/model` 再退出：各自的会话日志现在都有九条 `slash_command` 记录，顺序
与标记一致，第五条正是对话框自己的 result，两边都带着 `Kept model as fake-model`。没
在屏幕上演的是重放。把一个日志重建回 transcript 的那个适配器，只为 slash 命令的
invocation 阶段产出一行，而这是一条 result 阶段；ink 的重放读的是一个 result 阶段所
携带的那些输出行。所以恢复之后 ink 仍然画得出那行「保留原模型」，而本渲染器既画不出
它，也画不出任何其他 slash 结果 —— 正是决定 13 为 info 行整体点出的那条差距。补上它会
改变每一条 slash 命令在恢复之后留下什么，因此它记在「后续工作」之下，而不是在这一轮
接下。

## 决定 32 —— 对话框字段的光标会动了，和 ink 一样

这些对话框里的每一个文本字段都把值存在对话框自己的 state 里，而且只会往后追加。键盘能
做的只有加一个字符、删掉最后一个。← 和 → 什么都不做，Home、End 也一样；值中间任何一处
打错了，唯一的修法是把那之后的内容全擦掉。ink 把同样的字段都交给同一个文本输入组件，
它的编辑逻辑活在一个以码点计量光标的缓冲区里，所以那些键在那里是动得了光标的。受影响的
有两类字段：提问对话框的自由文本行 —— 它自己的提示行把 ← 和 → 宣传成切换标签，而这一
行却把它们整个让了出去 —— 以及认证向导的那四个文本字段。

这个缓冲区不是照着「它应该怎么做」重写的。落地的就是 ink 自己那些操作的一行切片，而测试
里没有一条手写期望：每条夹具把同一串按键并排灌进 ink 的 reducer 和这个模型，在每一步之后
而不是最后比对文本与光标偏移 —— 跨过一次留下换行的粘贴，跨过 ink 记作一格与两格的字
符，也跨过两头那堵动不动了的墙。ink 的分词是按它本身复用的：两个原本只模块内可见的辅助
函数改成了导出，于是 ctrl+W 擦掉的那一段就是 ink 擦掉的那一段，而 ink 自己的行为没有变
动。按键顺序也是 ink 的，只取一个一行字段收得到的那些键，其余每个键都交还给对话框 ——
这正是 ink 需要的，因为它的对话框一旦让字段拥有这一行就不再处理方向键。词跳转、向右删
词、整行删除与撤销重做被记录为未移植，这四样 ink 都绑了键。两处缺席是被迫的：ctrl+D 归
应用的全局退出绑定处理，但它并不吞掉这个键 —— 聚焦的字段同样会看到它，并且原样交回，
所以这个键上没有什么编辑行为可移植；而一个值被另一次按键整体换掉的字段，光标会被
拉回串内，而不是继续指着串外。

键的直觉读法与 ink 的绑定不一致时，留下的是 ink 的绑定，而第一轮评审的一条发现正是把这条
规则较了真。本移植把裸 End 键和 ctrl+E 送到同一个「跳到值尾」。ink 把两者分开：它的 END
绑定只有 ctrl+E，处理函数先派发一次行尾移动、再走到整个缓冲区的末尾；裸 End 越过那个绑定
落进 reducer，那里只认行。于是被 ← 停在粘贴值靠前那一行的光标，下一个字符会落到串的末尾，
而不是用户放下它的地方。这一处现在拆开了，裸键走 Home 本来就在用的按行移动；一个附带的
前提是 ink 的那一行是「可视」行，宽到需要折行的值会把它再切开，而这个模型没有折行可查。
覆盖是在 ctrl+E 那一步旁边补上裸键的差分一步，加上向导里 base-URL 字段粘贴一个两行值、把
字符落回第一行之内的用例，以及一个把裸键送回「跳到值尾」的变异 —— 两个套件各有一条测试为
它失败。这一处拆分的另一个方向有一轮是没有证人的：把 ctrl+E 改走按行移动能活下来，因为按
这个键的每一个夹具拿到的值里都没有换行，而在那种值上两个键落在同一列，路由和它的邻居无从
区分。现在有一条用例在一个带换行、光标不在最后一行的值上把两个键都经过路由按一遍，那个变
异会让它失败。

第二轮评审的另一条发现是一个拼法，而不是一个行为：擦掉光标左边那个词的键。ink 绑定的是
ctrl+W，而本移植除了它，还会为一个带修饰键的退格擦词 —— 那是一个上报修饰键的终端所发的
东西。不上报修饰键的终端发的是裸字节 0x1f，而这个字节到了对话框字段上什么也没发生 ——
既没有被插入，因为控制字符不算可打印；也没有被处理，因为只有 composer 被教过这个字节。
两条字段路径现在都去问 composer 自己的那个谓词，于是它们此前唯一没共享的一种拼法共享了。
把这个改动取掉的变异，只让同一条用例里喂进这个字节的那一个断言失败，而让 ctrl+W 那一臂
保持绿灯 —— 正是这一点让那条用例说的是「这个字节自己走得通」，而不只是「删词能用」。

三处渲染差异保留下来，其中一处比原先窄了。ink 把字段按固定列数开窗，并且只画光标所在的那
一行，所以一次多行粘贴会把它自己看不着的那几行全藏起来。这些行现在也藏同样的那几行，因为
一轮评审找出了整值渲染的代价：这里的光标格是并列在它所标记文本旁边的一帧，于是一个粘贴带
进来的换行会把这一行撑过对话框自身的高度预算，并把那一格留在与光标不同的行上。值仍然留着
那个换行，和 ink 的缓冲区一样，所以送到模型那里的文本没有变。列数仍然没有开窗，这正是上面
裸 End 那一条从另一头撞上的限制。ink 把光标格涂成从终端背景
读出来的灰，并且在实心块会破坏输入法拼字时退到下划线，而这一格带的是主题强调色，和
composer 的光标一致。还有 ink 会跑一个 530 毫秒的定时器，只要字段握着焦点就不断翻转那
一格的可见性，而一格常亮让对话框不必按定时器重绘。这个定时器不只是源码里的一行，它在测量
里看得见：在一个把光标停在自由文本行上的场景里，ink 那条腿每坐在这一行的六十秒里就写出
270 KB，场景的七次静止等待有四次把超时整个烧完，那条腿走了 251 秒，而本渲染器这条是
13 秒。

挂载语义按字段区分，因为 ink 的就是区分的。提问对话框的那一行只在自己的选项被选中时才
被对话框挂载，而且挂载时光标就在所存值之后，所以本移植把「该行被（重新）选中」当作一次
全新挂载，落在值中间的光标就此丢掉。向导里的自定义模型字段在下面那排列表拿到焦点时并不
被卸载，所以 Tab 回来时光标还在原地。

有一个字段的文本也不归模型自己管。上下文窗口的 setter 只留数字，而本移植渲染的就是拿到
的那个值，所以在那里敲一个被该 setter 拒绝的字符 —— 一个字母，或那一步显式绑定的
Space —— 只会推动光标，不会出现在行上。ink 的缓冲区在那里才是唯一来源，且从不回头读
那个属性，于是它会一直显示自己被流程丢掉的东西。两种下落点在同一列，而显示内容在光标
还不存在时就是这个样子 —— ink 显示一个自己的流程已经作废的值，这一条记为后续工作，
没有照搬。

覆盖是模型自己那一套 —— 本分支整份新增的文件里十六条新用例，其中六条把每一次按键都放回
ink 自己的 reducer 做对照，其余直接断言模型的状态 —— 加
上用它的字段那些测试，数目记在决定 33 与决定 37 下，外加十一个变异，每个都让真正拥有
该行为的那几条测试失败：向左键不再移动、上下文窗口字段的输入分支、两个跳至行尾的绑定、
向前删除、带修饰键的 Delete 擦掉一个字符而不是把键交还、ctrl+W、一行不再重新挂载、把裸
End 折回 ctrl+E 的那一跳、把那个遗留的删词字节交还给对话框、一行把粘贴带进来的那个换行
画了出来，以及一个停在换行上的光标去高亮那个
换行本身。实机侧，新增场景在两条腿上都从自由文本行回答一个问题，而且只问
一个问题，这样标签钳制和决定 21 记录的那次双触发都不可能是画面的来源：输入六个字符，
光标往回退两格，再插入一个字符。两条腿都在同一行的同一列显示 `> abcdXef`，也都把
`abcdXef` 记成了答案。带样式的抓取把那一定位钉死了。在 ink 画出那一格的两帧里，它
与本渲染器的那一格落在同一个字符的同一列上，只有两种颜色不同；在它之前的那一帧，光标停
在最后一个字符之后，两条腿各自要画的那一格都是一个被抓取丢掉的尾随空格，所以两边都不见
格；而在最早那一帧，字段还空着、显示的是占位符，ink 的那一格不在而本渲染器的在 ——
那是它的翻转间隔，不是缺了光标。
没有任何场景走到的是认证向导，这一点和从前一样：它那四个字段的编辑只有单元测试套件兜着。
还有一条测试运行时的说明值得写在这里，因为它花掉了一轮排障：
字段测试用的那套 DOM 运行时会把重渲染行的旧渲染留在活的那一行旁边，所以读光标格的探针读
的是最后一个。把同样的 JSX 形状放进真实渲染器改五次状态，行始终只有一行，所以这是脚手架
而不是对话框的问题。

## 决定 33 —— 一次读取里的按键，由它开始时的那次渲染处理

第一轮评审发现：决定 24 为行输入辅助函数关掉的那一类缺陷，还在每一个「读对话框 state
再写回去」的地方等着。渲染器的按键 hook 把处理函数存在一个引用里，并在一次提交的
layout 阶段刷新它；而一次 stdin 读取会把它带回来的按键一个接一个直接派发 —— 按住方向
键的自动重复约 30 毫秒一次，或者一次括起式粘贴连带终端附在末尾的那个 Enter。它们之间
没有任何提交，所以第一个之后的每个按键都由上一次提交装好的闭包处理，它读到的每个值都
慢了一次按键。人手速度看不见这个 bug，因为每次按键都会先冲掉一次渲染；一个逐字符花一
次 act 的套件同样看不见 —— 已有的对话框测试就是这么漏掉它的。

现在，那两个处理函数用来安放下一个按键的每一块 state 都有一份镜像，与它的 setter 在
同一次调用里写入，而处理函数读的是镜像：提问对话框的标签、它的选项光标、每题各自的
复选集合与手输内容；向导的推荐模型集合；行编辑器的文本与光标。提问对话框的处理函数
整个视图都从镜像导出 —— 这是第几题、单选还是多选、有没有自由文本行 —— 而不是从
「这次渲染画了什么」导出，于是没有任何分支能拿一个按键的位置去配另一个按键的值。
关于答案本身还有两处读取是例外，记录在下文。行编辑器交出的是一层读镜像的
getter 而不是快照，因为一个只捕获一次文本的消费者会把这个 bug 原样带回来，只需一行。

有一处读取比镜像更窄。自由文本行只在突发仍然站在「该行被画出来时所属的那个标签」上时，
才收下按键：这一行的缓冲区是在渲染期间重新植入的，所以一次读取里在切标签之后落下的字母，
会追加到那次渲染所画的那一题上，并被存成这串按键到达的那一题的答案。这些按键被丢掉，
和本轮之前一样；一个让方向键跨过标签边界的用例把它钉住。

提交是同一个 bug 反过来指。向导的 endpoint 与 key 两步调用它们的提交函数时不带参数，
所以一个与前面那些字符共享一次读取的 Enter 读的是父组件的 state —— 还是那些字符之前
的值 —— 向导就在一个只输入了一半的 endpoint 上前进，无声无息地退回到协议的默认 host。
它们现在把实时文本作为参数传入，这正是 ink 的文本输入拿缓冲区自己的文本调用 submit 的
方式，也是 ink 的提问对话框声明其提交签名的方式。推荐模型的复选框带着同一个发现而来：
一次读取里按住 Space 的两次勾选，或一次勾选连带提交它的那个 Enter，是一个复选框的两
种状态，以及一次对两者都一无所知的提交 —— 直到镜像被读出来。

这个 hook 与 ink 的向导共用，而 ink 的 endpoint 那一步本来就把缓冲区的文本传给它，
所以在同样的场景下 ink 那条腿现在提交的也是它屏幕上显示的值。离了那次携带多个按键
的读取，两个字符串完全相同；这是本轮唯一一处改到 ink 行为的地方。

两面镜像被读取的地方，没有任何按键序列能让它们显出分歧，这一条写在这里而不算作覆盖。
勾选一个推荐模型会把共享的 model-id 串与该字段的实时文本同步，而提交自由文本行取的是
它所站着的那个标签；但一次突发不可能既编辑字段又勾选列表行 —— 这两个分支由焦点决定，
而焦点是这一批按键自身改变不了的 —— 并且一次手动切标签会把光标放到第一行，而第一行
只有在「没有任何预置选项的问题」上才是自由文本行，这恰恰被工具自己的校验拒绝。保留它
们，是为了让处理函数对每一个事实只有一个来源。同一家族里还有两个同胞，这一轮是关掉而
不是记录：一是多选里手输内容算不算数，二是复核标签页提交时所取的那批已选答案。两处各
补一面镜像，并各有一条测试把那三个键放进同一次读取 —— 在多选的自由文本行输入、提交
它、再从复核标签页提交；答一题、走到复核标签页、在那里提交。两条腿上的任何场景都排不
出这个顺序，所以二者都只由单元测试套件兜着。

本轮停在被点名的那几个处理函数上，而这一类缺陷比它们宽。本渲染器里其余的列表都是用同
一种方式读自己的光标 —— 另有七个对话框文件挂载的共享选择 hook、竞技场对话框的模型列
表、输入框的补全行、向导的协议与 endpoint 两步、推荐模型列表的焦点（它的复选集合已在
上文配了镜像）、它的高级配置行，以及本对话框的主、子菜单。在那里，接键作用在上一轮渲
染画出的那一行，而不是这串按键到达的那一行；而凡是按画出的光标算下一步的地方 —— 共
享 hook、endpoint 选项列表，以及主、子这两个菜单 —— 按住方向键是一次读取走一行，而不
是一个键走一行。收口属于这些控件整体，而不属于本轮修的两个对话框，已记在「后续工作」
里。

覆盖是十六条新单元测试，认证套件五条、确认对话框套件十一条，外加十三个变异，其中十一
个会让真正拥有被拿走行为的那些测试失败：行编辑器退回一次渲染快照、Enter 提交 prop 的
值、模型那一步的复选集合被读两次（勾选与提交各一次）并在提交处再读一次该字段的实时文
本、提问处理函数按已渲染的 state 工作、Space 与 Enter 两个分支各自的选项读取、一次换了
标签的突发去编辑它抛在身后的那一题、复核标签页提交背后那面已选答案的镜像 —— 拿掉它还
会一并让决定 37 那条答案锁的测试失败，因为二者读的都是同一次突发记下的那个答案 —— 以
及多选提交所要的那面手输内容镜像。存活的那两个变异就是上面那些不可达的读取。没有任何
证据走到的是实机：验收 harness 故意每次写只打一个字符，于是一次按键落在自己那一次读取里，
而它从不向这些对话框粘贴 —— 这里每一个突发用例都只由单元测试套件兜着。

## 决定 34 —— 手动切标签会叫停已经排定的那次换题

提问对话框答完一题，暂停 150 毫秒让刚答完那一行的勾选可见，然后换到下一题。ink 排定
这次换题却从不取消它：暂停之内的第二次回答，或用户自己按的左右方向键，都不清那个定时
器，于是两次换题都会跑，中间那一题根本没被画出来。本移植继承了这个行为，而评审轮在
方向键这条路上抓到了它 —— 用户已经翻到某一题，对话框在零点一秒之后又把它带走了。

两条路径现在都会先取消排定的换题：方向键那一条，是因为这次按键就是用户对「我在答哪一
题」给出的答案；第二次回答那一条，是因为它取代了第一次排定的换题。这是本移植有意与
ink 不一致的几处之一；同样的 150 毫秒暂停、同样的在最后一个标签处钳制、同样的先勾选
后换题都保留了。ink 的行为作为它自己的缺陷记录在案，而不是照搬，而验收矩阵已经在 ink
那条腿上看到的双触发，就是同一个缺陷从外面看的样子。

两条路径都在确认对话框的套件里被钉住，各自对应一个自己的变异：一次落在暂停之中的右
方向键会保住它翻到的那一题，把那次取消拿掉就只有这一条测试失败；一次暂停之内的两次
回答只会留下第二次排定的换题，这条测试早于本轮，把回答路径里的取消拿掉就只有它失败。
实机侧，暂停与方向键已经被矩阵里那些回答多个问题的场景覆盖了；取消本身在那里没有被
观察到，因为它需要 150 毫秒之内的两次按键。

## 决定 35 —— 光标格印出握着焦点的那个字符

字段那一行把值分三段画：光标之前、光标所在的那一格、之后。高亮那一格的第一个版本只在
字段握着焦点时才打印中间那段，于是一个把光标让给兄弟字段的字段连带丢了一个字符 ——
行显示的值比存着的值短一个码点，这正是那一轮评审的 Critical。字符归值所有，不管谁握着
焦点；只有底色说明光标在哪个字段里 —— ink 也是这样，它的文本输入决定的是要不要画光标
的高亮，而其下的文字始终要画。

同一行的光标现在遵循一条被上一版弄反了的规则。光标索引的是字段的主人认下的那个值，
而不是按键敲出来的那个：当一次按键到达一个主人会拒绝它的字段 —— 往上下文窗口字段里敲
一个字母，而它只留数字 —— 被接受的值在那个位置上并没有可以承载光标的字符，于是以两段
文本共同前缀为界的钳制会把光标留在原地。在那之前，每个被拒绝的键都把光标向右推一个码
点，一连串之后第一个 backspace 就吃掉一个真实字符。两段文本相等时，这条规则退化回普通
的钳制，所以每一次被接受的编辑行为如旧。

这一行只打印流程接受过的内容，而这正是决定 32 记下的那条对 ink 的分歧，不是新的：ink
的缓冲区才是事实来源，会一直显示它的流程自己丢掉的那个字符，所以同一次按键在那里留下
可见的痕迹。要匹配它就得把显示搬到缓冲区上，那是 ink 该修的缺陷；上面那条光标规则之所
以这么定，是为了让一次被拒绝的按键在两个渲染器的列布局里都不留下自己的痕迹。曾有一条
测试把这个漂移钉成了期望行为，因为它断言的那个光标就是漂移本身；现在它钉的是没有漂移，
而与评审要求的那个形状之间的差别已经写在那条 thread 里。

两条测试、三个变异。字段失焦时丢掉字符的那一格，让认证套件里新增的那条行测试失败；在
应当放共同前缀钳制的地方改用普通钳制的重新同步，以及把那条钳制退化成按长度钳制，分别
让上下文窗口字段的编辑测试、和这条规则本身的新单元测试失败。每个变异都恰好让拥有被
拿走行为的那些测试失败。实机腿在这里没有变化 —— 向导渲染的字段里的光标仍然没有任何
场景能够到达，所以这一行的渲染只由单元测试套件兜着。

## 决定 36 —— 箭头指向队列答得了的那个调用

标记待审批调用的箭头原本是从转录里推出来的：第一张 pending 且未完成的卡片。这是拿
ink 的规则去读了错的列表。ink 的标记指向的是「确认框就在屏幕上」的那个调用，而只有等待
队列知道那是哪一个 —— 和决定哪个调用由 Ctrl+C 结算、哪个调用被 shell 对话框点名的，是
同一条规则。PreToolUse 钩子给出的一个 `ask` 决定，会重新武装一个用户已经批准过的调用：
把它 _追加到_ 另一个正在等待的调用之后，而它的卡片在原位回到 pending —— 于是转录顺序
与队列顺序不一致，而箭头就停在了用户根本没有对话框可答的那张卡片上。

现在 shell 把队列的第一个调用 id 传下来，而那一行仍然必须是一张 pending、未完成的工具
卡片才画得出标记。保住第二个条件，正是保住决定 25 那条「只有一个箭头」的规则：队列点名
但转录不再显示为 pending 的卡片没有箭头，别的卡片也都没有。这个 prop 在视图上是可选的，
所以没有队列可查的调用方得到的是「没有标记」，而不是猜一个。

新用例断言：当队列点名的调用不是第一行 pending 时，箭头停在那个调用上，而且画出的箭头
恰好一个 —— 把 id 丢掉、让转录的顺序重新做主，它就失败，一个十八条测试的套件里的一条。
该套件里另有一条钉住这道门禁的另一项：队列仍然点名、但调用已经完成的那张卡片不画箭头，删
掉这一项会让它变红，而它的同门那一项早已被一处已结算调用的渲染钉住。该套件里所有断言这个
标记的渲染都提供这个 id，因为一个必须来自队列的标记，没法由一个不提供队列的渲染去断言。接
线本身 —— shell 把队列的第一个 id 传下来 —— 钉在上一层：由一条挂载入口点渲染出的那棵树、
再读转录收到的 props 的用例负责，因为那个套件里每条用例都把转录 mock 掉了；删掉这条接线会
让它变红。把队列从渲染接缝的依赖数组里摘掉，是唯一一条测试看不见的腿，因为一个过期的 id
在同一次渲染里画出来是一样的：exhaustive-deps 规则会点名那个数组，而 CI 的 lint 通道不允许
任何 warning。实机侧，这里需要的顺序 —— 被重新武装的调用排在等待中的那个之后 —— 没有
复现；矩阵里驱动过箭头的那个场景只有一个待审批调用，此时两条规则一致。

## 决定 37 —— 字段在自己那次读取提交之后就停止接键

让「一次读取中间的提交」能够成功（决定 33），也就让那次读取的下一个按键有了意义，而它
其实没有意义：Enter 已经把向导留在下一步之后，读取里却还有按键没派发完，而这些按键仍归
刚被离开的那一步处理。那一步把值存在 flow 自己的 state 里，而 review 那一步的提交是从
这份 state 重新组装安装计划的，于是一个多余的字母会被写进 `settings.json` —— 密钥那一步
显示的是 `sk-test`，提交的也是 `sk-test`，存下来的却是 `sk-testZ`。

现在字段在自己的 Enter 移动了向导之后就结算，那次读取余下的按键一概不接。闩放在共享的
行编辑模型上，每个会漏的字段本来都经过它；各字段的处理函数在分支之前先查它：端点与密钥
两步经由共享 helper、模型 id 那一步（它的 Enter 同时也阻止空格去勾选身后的推荐列表）、
高级配置步的上下文窗口字段，以及提问对话框的自由文本行。最后这一处是同一个缺陷的另一端：
多选的答案是在 review 标签提交时从字段重新拼出来的，所以跟在 Enter 后面的字母会把用户早已
给出的那个答案加宽。

闩只在接受步「真的动了」的 Enter 上武装。被校验拒绝的 Enter 会把这一步留在屏幕上，这次读取
仍然属于它，所以同一次读取里的 `abc`、Enter、`def` 依旧会在端点字段里留下 `abcdef`。它是
每次渲染一个旗标，而不是每次挂载一个：渲染器每次提交安装一个新的处理函数，而一次读取不可能
跨越一次提交，于是这个旗标恰好覆盖一次读取；一个提交被拒绝的字段 —— 或者认证在晚一步才失败的
字段 —— 到下一次渲染就又能编辑了。

有意不闩的部分也写下来。提问对话框的左右切题键在决定 34 保护的那段暂停里照常工作，因为那里
的按键就是用户自己对「我在答哪一题」的回答；字段那把闩停住的是字段，不是它周围的对话框。

对话框在那段暂停里确实自己停了一处 —— 停的是答案而不是导航，时长就是一次换题被武装着的那
段。字段自己的闩只够到它的插入分支，而被那次已武装的换题安顿下来的那一行仍在屏幕上、仍握着
按键，于是一次读取里剩下的部分会把同一题再答一遍，并悄悄替换掉已经记下的答案 —— 一个落在
选项分支上的数字，或者一个多选在提交时据以重拼答案的空格。导航原样不动，换题跑完之后的每个
键也原样不动。最后一题那个标签根本不武装换题（它被钳住了），所以它也拿不到这把锁；跟在那里
的一个按键仍旧落在它到达的那一行上。

ink 到不了这个漏。它的缓冲区是在提交时运行的 effect 里通知父级的（`text-buffer.ts`），所以
Enter 之后处理的按键永远等不到一次「自己那一步还挂载着」的提交，它的文本也就永远到不了组装
计划所依据的那份 state。我们这边是同步调用 setter 写回的 —— 这正是「读取中间的提交能读到
实时文本」的原因 —— 所以需要这个显式的停止。

覆盖是八条新单元测试，认证套件四条、确认对话框套件四条，外加八个变异，下面点名的每个行为
对应一个。每个变异恰好让真正拥有被拿走行为的那条测试失败：端点与密钥字段的守卫、把闩连被
拒绝的 Enter 也武装上、模型 id 那一步的守卫、高级配置那一步的守卫、自由文本行突发归属守卫
里的 settled 那一项、数字分支上「单选」那一项 —— 没有它，一个在多选上只移动光标的数字就会
把它点名的那个选项勾上 —— 以及答案锁在答案路径上的那道守卫 —— 没有它，跟在后面的一个数字就会把刚
刚由它所跟随的那个 Enter 记下的 `"xyz"` 报成 `"staging"` —— 以及同一把锁在空格分支上的那
一项，没有它，跟在后面的一个勾选就会把一个早已给出的答案加宽。这里没有任何证
据走到实机，原因记在决定 33：验收 harness 故意每次写只打一个字符，而且从不向这些对话
框粘贴。

## 决定 38 —— 转录区不在焦点链里

在对话区随便左键点一下，composer 就再也编辑不了它已经装着的文本。承载转录的那块区域是
`scrollbox`，而这个渲染器的 `ScrollBoxRenderable` 把基类的 `_focusable = false` 覆盖
成了 `true`（`@opentui/core`：`index.node.js:13859` 对
`chunk-node-kr27pp2p.js:210`）。渲染器在每一次左键按下上沿祖先链往上走，聚焦第一个
focusable 的节点，除非这次点击先被处理掉并 preventDefault
（`chunk-node-kr27pp2p.js:9091-9104`）。于是点击把焦点挪到了滚动区上，
`focusRenderable` 把原本聚焦的编辑器 blur 掉（`:7562-7569`）。blur 不是外观问题：一个
renderable 的按键和粘贴处理函数只在它聚焦期间存在，`blur()` 会把两者一起摘掉
（`:325-381`）。

没有任何东西会把它们装回去。composer 的 `focused` 一直传同一个常量，reconciler 要比较
的 prop 没变，于是这次写入在整个会话里都被跳过。打字看起来仍然正常，这正是差点让它被
驳回的原因：可打印字符走的是 composer 自己的全局按键处理函数，不是编辑器的那份，所以
缓冲区一直在变长，而只有聚焦编辑器才处理的键 —— 每一个光标键、每一次粘贴 —— 落到了没
人听的地方。真正显出差别的是 `Home` 之后跟一个字符，以及一次 bracketed paste。ink 也
解析 SGR 鼠标上报，但只分发按表面订阅、并对该表面自己的行做命中测试的处理函数 —— 滚动
列表上的滚轮、提示输入内部用来定位光标的点击 —— 而它们没有任何一条路能写到 composer
的焦点上，那个焦点是 React 的 prop。在对话区点一下什么也不会改变，这是量出来的，不是
推出来的。

现在这个区域是 `focusable={false}`。两个更宽的做法被否掉了。把 `autoFocus` 关掉是渲染
器全局的设定，而对话框自己的字段依赖它。在区域抢走焦点时把 composer 重新聚焦，等于让
转录区拥有一条「谁该在听」的规则，而 composer 的焦点已经由它自己的 prop 声明过了 ——
一个比特两个主人。给这个本来没道理进焦点链的节点加一个 prop，是同一个事实最窄的说法：
滚动区不是输入目标。

在真实终端上测量，四个臂，只变一个变量 —— 全程同一份 bundle 和同一组启动参数；而 node
下的 `ink` 对着 bun 下的 `opentui` 会把运行时和渲染器混在一起，所以 bun 下的 `ink` 单
列一臂。每个臂先打四个字符，然后 —— 对照臂除外 —— 在转录行上点一下，再量三件事：三个
左方向键加一个字母有没有把光标挪走、`Home` 加一个字母有没有落到最前面、一次 bracketed
paste 有没有进缓冲区。

| 臂                               | 光标会动 | `Home` 生效 | 粘贴落位 |
| -------------------------------- | -------- | ----------- | -------- |
| `ink`，node，点击过              | 是       | 是          | 是       |
| `ink`，bun，点击过               | 是       | 是          | 是       |
| `opentui`，bun，点击过 —— 修之前 | **否**   | **否**      | **否**   |
| `opentui`，bun，没点击 —— 对照   | 是       | 是          | 是       |
| `opentui`，bun，点击过 —— 修之后 | 是       | 是          | 是       |

同样的点击落在 composer 自己那一行时，每一个臂（包括坏掉的那个）粘贴都恢复了，这才是
把丢失归到编辑器焦点、而不是归到按键本身的依据。

修完之后仍然核过的部分：滚轮照样能滚这个区域 —— 专门测滚轮的那个场景在本渲染器上
重跑，粘在最后一行、上滚二十格后能看见折叠线以上的那些行、再滚回来又回到最后一行。那
个场景从头到尾没有点击过，所以「点击之后的滚轮」依靠的是路由而不是帧：滚动事件先做命
中测试，焦点只是兜底（`:9134-9143`）。还有一条单元测试钉住这个 prop，用一个删掉它的变
异证明它会失败。没核的部分：在转录上按住拖动选择文本，这条走的是同一个命中测试路径，
而这个渲染器从未对外声明过它；以及对话框开着时点击 —— 对话框的列表仍然默认
focusable，记在后续工作里。

## 覆盖边界

验证了什么，以及验证到哪一层：

- **几何、行内容、行顺序、行数与字形身份**，在重建屏幕上，覆盖二十六个场景，
  100×40；窄终端与 resize 场景另加 60×24，总计七十七个检查点，其中二十二个
  逐字节一致。两腿出自同一个 bundle 与同一组启动参数。
- **颜色除一类行之外未验证。** 重建结果是文本。已知有若干行只在所用主题 token
  上不同。七十七个检查点里除三个外都有带样式的抓取兜着，而读过的只有一类行 ——
  决定 32 的光标格 —— 其余没有读。
- **滚动条没有从转录里拿走一列。** 在一百列下用两条分别为 95 与 96 字符的回答行
  测量：本渲染器折满 99 列才断行，ink 折满 98 列，所以这一列的差与清单上那条既存的
  换行分歧同向，而不是滚动区域拿走了一列 —— 且整份语料的行长分布在这次改动前后完全
  一致。
- **composer 的一行间距以源码为据，只在两帧确实对齐的地方有帧为据。** 在决定
  26 的溢出臂上，composer 之上那一空行与 ink 逐行吻合，因为那里两腿的内容都刚好
  填满窗口。在别处，它在帧比较里无法与重建把块放在哪里这件事分离。
- **退出警告的排队段、以及决定 30 的队列行，仅有单元测试覆盖。** 没有场景会先排队
  一条消息再武装警告。也没有任何场景会产生一个持久的队列：ink 的徽标只在它自己的提交
  路径里作为一帧瞬态存在于裸流中，两腿都从未进入任何一个抓取帧。活得比回合更久的队列
  需要 ink 放在 Ctrl+Q 后面的那次推迟；本渲染器没有绑定这个键，而没有任何场景在任何一
  条腿上按它 —— 所以这些文本和徽标一样，只存在于一个回合之内。
- **决定 31 记录下来的那一行，只在磁盘上验证过，没在屏幕上验证。** 打开 `/model` 再
  退出它的那个场景在两条腿上都跑过，两份会话日志被逐条记录比对。没有任何场景恢复过会
  话，所以这一行经共用加载器重新回到屏幕 —— 本渲染器的会话切换调用的就是它 —— 只建立
  在读源码之上。
- **不可压缩的行前缀与按条目上边距仅靠重新抓取验证。** 单元测试运行时会桩掉
  渲染器的图形表面，因此无法执行布局；在那里的测试只能把这个 prop 原样回显。
- **纵向间距直到最后一次运行之前都在帧证据之外。** 比对会把每一帧归约为一串非
  空行，这让两个条目之间的间距对它不可见，而本文档此前每一次抓取都是这样比对
  的。所以上面那条边距是本文档里第一个有帧支撑的间距结论，并且它靠的是一份对
  transcript 区域的单独度量 —— 只要重建会把 ink 的那块内容放在它自己选定的行上，
  空行总数就不可用。
- **ink banner 前后的空行刻意不复现。** 有两件事是直接读到的。ink 的抓取流在
  banner 首行之前以一个回车加换行开头。并且 ink 会给它写出的每一批永久输出追加
  恰好一个换行 —— 它自带的注释说明这个换行是为了让下一帧不覆盖该批的最后一行。
  因此空行会落在批次边界所在之处，而这取决于条目在多次渲染之间碰巧如何分组，而不
  取决于任何布局规则。这两者中哪一个产生了哪一行没有被追查，而对齐其中任何一个都
  意味着把写入分批的伪影硬编码下来。
- **两处结构性分叉曾被记录为刻意保留，如今已经关闭。** banner 在本渲染器里
  常驻、在 ink 里会滚出视口，这是从恢复工作继承下来的产品决策，而不是它引入的
  缺陷。同一套浮层模型还有第二个症状：对话框不会重排会话，所以当 ink 打开一个高
  对话框、把若干行顶出视口时，那些行在这里仍然留在浮层下面可见。决定 26 拆掉了
  这两条共同来源的那套浮层模型，它的帧就是这两处关闭的证据。
- **启动时的更新检查通知属于运行时，而本文档之前关于它的说法是错的。** 这条通知
  出现在每一条 OpenTUI 腿的帧上，却从未出现在任何 ink 腿上 —— 在对照臂说明它归属
  哪一侧之前，这种分叉既可能来自渲染器、也可能来自运行时。对照臂跑了：ink 在与
  OpenTUI 腿同一个运行时下复现了这条通知，所以它从渲染器那一栏移出。同一次运行也
  推翻了此处原先记录的解释 —— 即 ink 把一条软警告输给了订阅竞态、转而显示之后那条
  硬更新失败；任何一臂的任何一次运行都没有出现过硬失败。这个检查自己的结果为何在
  两个运行时之间不同，不是这轮排查追的东西。工装现在于两条腿上都抑制更新检查，所以
  这条通知不再向帧对比贡献任何行。
- **一处外观分叉被记录，未修。** 两个渲染器在不同列上断开一行长内容。ink 的默认
  换行是按词换行、但把仍然放不下的部分强行截断且不做裁剪，所以一行会一直填满到
  边缘，续行从该条目自己的缩进处开始；本渲染器的 text 节点按词边界断开，而一条路径
  里的词边界包含其中的斜杠与连字符，所以一个长到放不下当前行的词会被整体挪到下一
  行、把当前行留短。context 文件列表是它的第一个面，工具卡片的 header 与参数行是
  第二个面：在一百列下，同样的参数在两腿上折叠成同样数目的隐藏字符，却仍然比 ink
  多耗一个物理行。要对齐断点就意味着重新实现渲染器已经提供的换行算法。被折行的
  header 还会丢掉工具显示名与其描述之间的那个空格，而一个把参数行关掉、却抬起同一
  个长 header 的场景会原样复现这一点 —— 正是这条对照把最后这一点与上面新增的那一行
  区分开。
- **一处最后兜底被刻意不复现。**「保留原模型」播报先读运行期快照的标识符，再退到
  配置的那一个，这与 ink 一致。ink 还会第三次兜底 —— 当配置的标识符读出来为空时，
  退到一个硬编码的默认模型标识符。在这里那不会发生，所以这第三层被省掉，而不是为一
  个不可能的场景引入一个常量。
- **回放的扩展提示带不上它的原因。** 本渲染器据以回放的闩锁没有暴露原因访问器，
  所以在本渲染器挂载之前失败的一次重载会以普通的变更措辞播报，而不是失败那一条。
  两种措辞都把用户指向同一条命令，而要恢复原因就意味着为这个背后没有不同动作的
  区别，给共享状态加一个公开访问器。
- **审批释放只有单元测试覆盖。** 没有任何场景会先停住一个确认框、再轮换模式。这条
  接线由一个带反证对照的测试钉住 —— 那个必须什么都不释放的中间模式 —— 而它消费的
  选取规则本来就已被单独覆盖。
- **每一个突发用例都只有单元证据。** 验收 harness 故意每次写只打一个字符，所以一次
  按键落在自己那一次 stdin 读取里，而它从不向对话框输入粘贴。因此矩阵的两条腿都产生
  不了决定 33、34、37 所针对的多键读取；这些结论只靠它们新增用例的那两个对话框套件，
  以及那几个决定各自在覆盖段落里点名的变异，背后没有任何屏幕证据。
- **ink 自己的认证向导套件在本地失败，而本轮改动没有被证明是原因。** 那个文件把十九条
  测试藏在一个由它自己注释解释的检查之后 —— 模拟 TUI 输入在慢速 runner 上不可靠 ——
  并在 CI 与 win32 上跳过它们，所以 CI 从不运行它们。在 CI 之外，这一家里有十三条在这
  里失败，每一条都卡在该套件自己的五秒等待上，十三条全都在被守卫的那一家里。本 head
  上跑了六次，五次得到同一组名单，一次得到其中的十二条，所以随机器漂移的是条数，而不是
  会落到被守卫那一家之外的失败。一个只变一个变量的对照说明，本轮对共享 provider-setup
  hook 的改动不是原因：把 `packages/cli/src/ui/auth/useProviderSetupFlow.ts` —— 那次改动
  唯一动到的文件，也是这套件会走到的那个 —— 放回它在 `origin/main` 上的版本再跑一次，
  跑完核验工作树逐字节还原，失败的还是同样这十三条，列表一字不差。没有观察到的是这个
  环境里一次干净的上游签出：独立的 worktree 在任何测试跑起
  来之前就会停在 workspace 构建前置条件上，所以「它们在那里也失败」是从上面两个臂推出来
  的，不是量出来的。
- **思考开关的那次按键完全没有覆盖。** 入口自己的测试把键盘 hook 换成了空操作，所以
  被断言的只有消费的那一半：标志到达那一行并把它展开。它也没有帧覆盖，因为没有任何
  场景会让模型产出一段思考 —— 新标签与这条绑定都不出现在任何一帧抓取里。
- **ink 那个全量详情开关只绑了思考这一半。** ink 的标志还会取消每一个工具组的截断；
  这里的工具卡片无论它如何都保留自己的行数上限。
- **进行中的思考正文在这里是流式显示的。** ink 会把它藏起来，直到该思考被展开。记录
  而不修改：既然没有场景产出一个进行中的思考，改动它在任一方向上都无法验证。
- **`output.showTimestamps` 在这里仍然没有读取点。** 该设置打开时，ink 会在 assistant
  行上方打印一行暗色的时钟。接上它需要在共享的条目类型上加一个时间戳、在条目被创建
  处打上，并且还需要恢复路径上的第二个来源 —— 那条路径是从录制重建 transcript，而不
  是从实时条目。只做实时的一半本身就会成为一个分歧 —— 一个恢复出来的会话会完全不显
  示时间戳 —— 所以它是整体推迟，而不是先上一个半成品。
- **哪些工具真的会在执行中发出结构化载荷，没有被追查。** 这次收敛让每一种载荷在每一
  条路径上都可用，实时分片也包含在内，所以一个在运行时上报 ANSI 网格的 shell 结果现
  在会带颜色渲染；至于是否有工具会在完成之前就这么做，那是关于工具的问题，不是关于
  本渲染器的问题，这里没有回答。
- **受门禁的服务器审批只在一个方向上有帧验证。** 一个场景把一份项目服务器列表丢进工作
  目录；两腿在同样的内缩与同样的宽度上画出同一个对话框，拒绝之后两腿都落在同一个
  composer 与同一行 footer 上。批准没有被执行，因为它会解除该服务器的门禁并重连，而那
  会派生所声明的命令。所以批准与全部批准两个分支都没有帧覆盖，全部批准要打印的那份服务
  器列表也没有 —— 场景只声明了一个服务器，所以渲染那份列表的分支从不被走到。这些分支
  做什么是那个共享 hook 自己的行为，这里没有改动。
- **参数行只在一个宽度上、对一个需要审批的调用做过帧验证。** 打开这个设置的那个场景
  会停住一条 shell 调用，所以它的帧里同时带着：等待中的参数行 —— 以及标记这一条的那
  个唯一箭头 ——、调用结算之后的样子，和那个切换键到达的不截断状态。其余每一个场景都把
  该设置留在默认值，所以这一行在矩阵的其余部分按构造就不存在。没有用帧查过的：一个描述
  本身就已经打印了参数载荷的调用，也就是共享 helper 要去重的那一种 —— 它由一个带正证
  对照的单元测试断言；以及一百列之外的任何宽度。
- **ink 那份按组的预留高度没有移植。** ink 会从该组里每一个结果拿到的预算中，为这一个
  组里每一个将要打印参数行的工具扣掉两行，因为那一行画在结果预算之外。本渲染器不做这种
  分配：每一张卡片拿到的都是同一个按条目算出的上限，它由视口高度导出，所以参数行在这里
  没有可扣的预算、只会额外增加行数。两者只在 ink 本会压缩一条长结果的地方不同，而要补上
  这段差距，就得引入这套架构从来没有过的分配。

## 后续工作

- 滚动区响应鼠标滚轮，却不响应任何键 —— 而它之所以对键始终不是目标，只是因为决定 38
  把它移出了焦点链；一个被聚焦的滚动区确实会拿走那些没人听处理的键。滚动 ink 那份会
  话靠的是终端自己的回滚缓冲区，而本渲染器接管的备用屏幕没有这样东西，所以在那边管用
  的翻页键在这里什么都触及不到，折叠线以上的一行只能靠滚轮回来。把这些键绑到区域自己
  的滚动偏移上是独立的改动。
- 对话框画的每一个滚动区仍然默认 focusable，因为那是类的默认值，被处理掉的只有转录这
  一个。对话框开着时点进它的列表，会不会像决定 38 描述的那样让对话框丢掉光标键，没有量
  过，而代码也没有给出期待一个更温和答案的理由：那五个区域里的行都是手工搭的，不订阅任何
  鼠标事件 —— 只有共用的 select 控件订阅 —— 所以在那里点一下是无人处理的，决定 38 描述
  的那次焦点上溯会沿它在转录里走过的同一条路落到那个 focusable 的区域上。为每个对话框补
  一臂要定的，是一个被聚焦的对话框区域接着会不会吃掉对话框自己的方向键与 esc，还是只在旁
  边滚动。在这个渲染器的鼠标处理被称作完成之前，值得补这一臂。
- 问题对话框的选项行是手动画的，所以点击一个选项不再作答，悬停也不再高亮，而兄弟确认类
  型的结果行 —— 仍然是那个共用的 select 控件 —— 两样都还响应。给 chip、自由文本行以及
  submit 与 cancel 行上的点击各找一个含义，是独立的改动，正如决定 21 所说；在那之前，这
  个对话框只靠按键作答。
- 这里的 `@` 补全只问文件索引。ink 还会补全会话、MCP 资源与扩展，并画一个分类
  栏用于切换。那是功能缺口而不是一致性缺陷，应放进独立的改动。
- 缺少搜索二进制时打印的 shell crawler 诊断现已有解释。渲染器库把全局 console
  替换成一个捕获流，并把 console 输出收进它自己的内置控制台，所以那些警告根本到
  不了终端；ink 没有这类拦截，任由它们落进 scrollback。触发条件是环境性的 ——
  搜索二进制在测试机上只是一个 shell 别名，所以派生查找会失败。诊断并没有丢失，
  但在这里不可达，因为本渲染器从未绑定该库的控制台唤出键。是否要暴露那个控制台是
  一个待定问题。
- help 对话框的保留行数常量并没有描述屏幕上实际观察到的行，且在低于 42 行的终
  端上本渲染器显示的窗口高度是被限制的，而不是被对齐的。
- 内联确认框周围为会话预留视口行的那两个常量是按行清单手工推导的。长确认场景
  显示实际采用的取值为绿、归零时超时，但小四行的取值在那里同样能通过，所以真正
  钉住这两个数字的是单元测试里的算术 —— 而它断言的是常量自己的加总，不是屏幕。
  因此确认框的几何将来发生变化时，这两个数字不会自己报错；重新推导它们应当与那
  次改动一起做。
- loading 指示器没有子代理 token 汇总，也没有 tokens-per-second 段，两者 ink
  都有。
- 主题模式 helper 没有生产调用方，所以本渲染器永远画它的暗色调色板。
- 仍有两个对话框列表组件，其实一个就够；合并它们会同时牵动编号、颜色与滚动箭
  头。
- 一次针对 ink 组件与渲染源码的逐行对照，翻出了远超本次改动范围的缺口。以及在这里打开
  是只读、而 ink 那边可操作的对话框：信任、回退、diff、子代理的创建与列表、技能、
  hooks、状态栏、记忆、stats 的两个标签页，还有扩展管理器的发现与来源标签页。再加上整
  个子代理与后台任务界面 —— 没有实时代理面板，没有后台任务对话框或 footer 胶囊，也没
  有对某个子代理发起的审批做行内归属，所以这样一个审批到达时无从说明它是谁的。
- ink 的两个鉴权进度界面曾被报告为这里缺失，理由是缺了它们一次登录无法完成。这一
  条经不起可达性核查，它们不是缺口。注册表里没有任何 provider 声明那个 OAuth 鉴权
  类型，协议选择器只另外提供四种，所以待处理鉴权类型唯一的那个写入点永远产不出它；
  而那两个界面所读的外部鉴权状态，在它仅有的两个写入点上都被赋成 null，从来没有被
  赋过别的值。两个分支在 ink 里都不可达，所以这里省略它们是与其对齐，而不是缺失
  —— 记下来，免得这条省略被再次当成缺口上报。
- footer 没有右侧段。ink 会用竖线把若干指示器接在那里 —— 沙箱、安全模式、调试模
  式、上下文百分比，以及 goal 与 cron 胶囊 —— 还会加上一个 MCP 健康胶囊、一个
  worktree 指示器、一个 workflow 指示器和一条技能待审警告。本渲染器只打印一列左侧
  内容。
- 状态栏相关设置被忽略。ink 会渲染至多两行由用户配置的命令产出的内容，按它自己的
  刷新间隔与颜色选择；本渲染器则硬编码一行目录、会话、分支与模型。
- composer 宣传了一个它并未绑定的排队键。决定 30 把这件事放大了：移植来的提示行会
  把那个键的名字打印到屏幕上，于是这个失效的可供性从「仅有记录」变成「看得见」。它
  的退出键还会在草稿非空时武装那个按两次的窗口，并在这个过程中吃掉一个字符；而 ink
  在缓冲区还有文本时根本不会武装。
- 多数对话框把回答落在一个不会留存的提示位里。arena 的选取与停止对话框、编辑器对话
  框、输出风格对话框，以及认证对话框的成功播报，都经由 shell 的 notice 槽作答，而下一
  次提交就会把它清掉；effort 对话框的选取则什么都不说。ink 为这些结果逐一添加转录行并
  记录，所以恢复会话时那边能重放、这边不能。补这些是决定 31 的形状做两遍 —— 先把行加
  上，再记录；只记录不加行，会在恢复时重放一行用户从未见过的话。`/statusline` 更靠在
  后：本渲染器的 statusline 对话框只列出预设项、按 Escape 关闭，根本没有保存动作可记
  —— 缺口落在一个缺失的功能下游，而不是一条缺失的记录。ink 的 UI 层有十五处记录点，
  其中十三处在分发器自己那对 invocation/result 之外；这十三处里有三处在这里什么都不
  必补：theme 那处只带 `/theme` 的 `NO_COLOR` 消息，而本渲染器已经把它走分发器的记录
  包装（选主题本身两边都不加行）、arena 命令的记录器是两边跑同一份的共用代码、
  away-summary 那处住在只有 ink 自己的容器会挂载的 hook 里。
- 一次辅助模型的选取是另一种类型的行。ink 把 fast、voice、vision 的选取报成 success 条
  目 —— 它有自己的字形与颜色 —— 而这里所有模型结果，主要的或辅助的，都走同一条 info
  行，于是它在屏幕上显得更平，自决定 31 记录了被显示的那一行之后，在会话日志里也一
  样。本渲染器这条路径可达：分发器会构造 fast、voice、vision 的对话框请求。要修就得让
  选取助手带出行类型，而不只是一条消息字符串。
- ink 的提问对话框会对一次击键把手打的自由文本答案答两遍：对话框自己的按键处理
  与它挂载的输入控件都订阅了按键，而按键层没有焦点栈在两者之间仲裁。每次回答都
  推进一个标签页，所以多问题对话框上，正被回答那题之后的那题会被跳过、根本没被
  画出来，而复核标签页把它报告为未回答。这是在真机上观察到的，不是推出来的。
  决定 21 不跟随它，而在以 ink 现状行为度量自己的清扫里去修 ink 超出了范围；
  记在这里，免得两个渲染器间的这处分歧被再次当成移植缺口上报。
- 读到过期光标这一类缺陷，只在决定 33 动过的那两个处理函数里被关掉。其余读源码即可确认：
  共享选择 hook、竞技场对话框的模型列表、输入框的补全行，以及认证向导的那四个列表步骤
  加它的主、子菜单，全都是按上一次渲染画出的那一行作答。镜像的形状已经由提问流程和行
  编辑器立好，所以这是一次覆盖这些控件本身的改动，而不是逐个对话框各修一遍 —— 并且每
  一处都要有自己的突发用例：一个让提问对话框失败的变异，对一个它不碰的列表什么都没说
  明。
- 决定 37 的闩停住的是字段，不是步骤。向导的那几个列表步骤和最后的 review 行仍然是
  一个按键跑一个分支。review 行在一次两个 Enter 的突发里会把计划应用两次 —— 两次
  写入调用，本轮一条临时测试直接读到的 —— 而协议行与端点选项行是源码读出的同一形状：
  它们各自的 select 都会前进一步，于是同一次读取里的第二个 Enter 就跳掉中间那一步。
  ink 的步骤也是这个形状，所以这不是一条要走在 ink 前面的分歧，它属于上面那轮控件级
  的改动，同一个「一次读取一个动作」的闩一并覆盖它。
- 闩停住的是按键，不是粘贴。每个被它结算的字段同时订阅了渲染器的粘贴事件，而那份订阅
  从不查这个闩：一次读取里先有让向导前进的 Enter、随后再到一个括起式粘贴，粘贴的文字
  就会写进这串按键已经离开的那一步。反过来的顺序 —— 先粘贴、再有提交它的 Enter ——
  才是终端真正会发的那一种，已由一条测试钉住；这一种需要第二个输入通道落在同一次读取
  里，而 harness 的任何一条腿都不会向对话框粘贴。它并入上面那轮控件级的改动，每个字段
  都该带上同一道守卫。
- 一张已结算的卡片会停在它被创建时的位置，而 ink 会把它提交进永久历史、排在期间到
  达的那些提示之后，所以一条在工具调用期间打印的提示，在这里落在卡片之后，在那里
  落在卡片之前。这一条曾经还记着卡片缺少的行内参数行，以及一个画在每张卡片上、而
  非只画在那一个等待审批的调用上的等待指示符；决定 25 关掉了这两点，「工具被禁用」
  的错误在这里读成一张空卡片，也随第一条一起消失了。
- 两个调用同时等待审批时，确认框在屏幕上的位置不同。ink 把它直接放在所属那行卡片之
  下，所以画面读起来是卡片、确认框、卡片；这里会话按自己的顺序保留两张卡片，确认框
  跟在它们后面。差的就是这一行的挪动，同一检查点上两侧本来就已经因为折行断点各失去
  三行。决定 22 改的是行内确认框画什么；这一条是它挂在哪里，需要另一次改动。
- 提问对话框的 chip 行在这里比在 ink 里晚两列才开始裁切。决定 21 按这一行被画在其中的
  那个盒子来记账，而那个盒子比 ink 的宽两列，于是在一段终端宽度区间里，标题在这里整行
  打印，而 ink 已经拿起了省略号 —— 在五十八列、三个十二格标题下两条腿都量过。照 ink 的
  那个数字来做，会裁掉这一行本来就放得下的文字。
- 对话框字段移植的是 ink 缓冲区里那一行宽的切片，不是全部。ink 文本输入绑定的四族键
  没有移植：词跳转（ctrl/alt+←/→、alt+b/f）、向右删词（alt+d、ctrl/alt+Delete）、
  整行删除（ctrl+k/ctrl+u）与撤销重做（ctrl+z）。前三族需要的操作在这个模型里都已经存
  在，所以那是一次落在行编辑器与其测试上的改动，而不是逐个对话框的改动；撤销重做还需要
  一份这个模型并不保存的历史，所以它要先加一处存储，才谈得上加一个绑定。另有 ink 的两个
  绑定是有意不在此列，而不是漏了：清空输入（ctrl+C），应用级的退出处理函数已经在任何对话
  框占着屏幕时都对这个键动作；以及打开外部编辑器（ctrl+X），本渲染器里没有任何东西绑定它。
- 对话框字段的行开了「行」的窗，没开「列」的窗。ink 的字段画光标所在的那一行，并且在那
  一行里画光标左右的那些列，所以比这一行更宽的值是横着滚过去的。这一行藏起了光标之外的
  其他行，却仍然画出自己这一行的全部列，于是一个比这一行更长的值还是会把它折行 —— 无论
  那些字符是一个个敲进来的，还是一次粘贴进来的。
- 恢复出来的会话显示的行比它的日志里装的少。本渲染器的 transcript 适配器只重放 slash
  命令的 invocation 阶段，别的一概不重放，于是一条 result 阶段的行 —— 其中包含决定 31
  的那行「保留原模型」—— 被记录之后就再也不画出来，而 ink 的恢复会把它们每一行都放回
  去。这比一个对话框更宽：补上它会改变每一条 slash 命令在恢复之后留下什么，而验收矩阵里
  没有任何场景恢复过一次会话。
- 一次被拒绝的按键在屏幕上留下什么，两侧是有分歧的，决定 32 已说过。context-window
  字段只保留数字，而本渲染器打印的是被接受的那个值，于是一个字母 —— 或那一步绑定的
  Space —— 会不留痕迹地消失；ink 的缓冲区才是它显示内容的源头，会一直显示自己流程已经
  丢掉的那个字符。这里刻意选了更安静的一种：要对齐 ink 就得把这行搬到缓冲区上，那是
  ink 该修的缺陷。
- 两个应用级处理函数在「是否认领自己那个键」上不一致。展开思考的处理函数会把这次按键
  标记为已消费，ctrl+C 与 ctrl+D 的退出处理函数不会，于是这两个键也会到达同一次读取里
  挂载着的其他处理函数。ctrl+D 上没有别处动作 —— 共用的行归约器把它原样交回。ctrl+C 上，
  shell 的五个分支是互斥的 —— MCP 审批、工具确认、模态、对话框、composer —— 所以只有屏幕上
  那一个会和退出处理函数一起参与这次读取。composer 清空一个非空缓冲区，并且只在真的清空时
  才认领这个键；设置对话框把它所在的那一行恢复默认，不认领，于是在那里按一次 ctrl+C 会同时
  把那一行恢复默认并武装退出窗口，再按一次就退出。回退浮层绑定同一个键，但本渲染器里没有任何
  文件引入它。让退出处理函数也做出展开思考那个处理函数所做的认领，是另一件独立的事。
- 另有六处钉定被评审以变异量出并不成立。本轮把这六处都重跑并闭合了，每一处都对着属于
  它自己的一个变异。删掉 shell 上等待行的挂载，现在会让决定 28 点名的两条短语测试失败 ——
  指示器自己的套件仍然直接渲染它，什么也看不见。把排队行移到 composer 下面，那条钉住位
  置的测试会失败，因为它现在把两者排出先后，而不只是断言它们落在一起。参数行位置的断言
  不再对比它的 fixture 从不渲染的字符串，把那一行移到表头上面会让它变红。参数行的接线，
  以及 shell 一并传下去的那个待答调用 id，现在由挂载入口点渲染出的那棵树读出来，删掉任
  一条都会让那条用例变红。光标停在选项行上时到达的一次粘贴有了自己的用例，摘掉拒绝它的
  那道守卫会让那条失败。两个根本没有测试的分支 —— 模型对话框自定义 ID 字段的光标，以及
  向左删词的跨行合并分支 —— 现在各有一条：把那个光标钉死在值的开头、或把跨行合并取走，
  各自会让它们变红。同一形状贯穿这六处：断言读的是渲染出来的结果，所以渲染结果不变的改
  动能活下来；每一次闭合都是改为断言位置、接线或状态，而不是断言画面。同一轮评审提出的
  第七处已经重跑并闭合：待处理卡片那个用例曾被调到一个高度，在那里视口预留值与描述下限
  是同样的五行，于是删掉那个下限它的探测值仍然通过。它现在同时钉住两个高度，删掉下限会
  让它变红。
