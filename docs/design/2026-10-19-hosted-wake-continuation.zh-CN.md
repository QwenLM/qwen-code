# 后台唤醒中断后的 Hosted 续跑

[English](2026-10-19-hosted-wake-continuation.md) | [简体中文](2026-10-19-hosted-wake-continuation.zh-CN.md)

状态：本变更包含实现；验证结果记录在 PR 中。
关联 [#14047](https://github.com/QwenLM/qwen-code/issues/14047)。

## 问题与范围

替代 Harness 可以恢复已提交工具调用的答复，并结清中断的子结果或 monitor
通知。但此时唤醒泵没有剩余输入，模型直到下一条输入到来才会读取答复。
#14116 的自动加载 Session 能力不会提供这下一轮模型调用。

本变更让这些通知在崩溃后续处理完成后继续。渠道结清、Automation 的失败/未知
结果、Session 消息停止策略、前台接管，以及各工具自身的恢复决策沿用现有规则。
不会迁移已被旧版本结清的通知。

## 持久化交接

恢复已提交调用的答复并处理现有 Runtime 义务后，Harness 在结清中断轮次
**之前**接收一条内部输入。其 ID 为 `wake-recovery:<sha256(interruptedTurnId)>`，
接收命令使用同一稳定 ID；已经提交的接收结果会被复用。
输入保留原来的 `monitor`、`child_agent` 或 `workflow` 来源，因此仍由现有
唤醒发现、写者围栏、唤醒泵及生命周期结清机制负责。不新增 schema、公共端点或来源。

这条小型输入资源包含续跑指令、`interruptedTurnId` 和 `notificationTurnId`。
后者始终指向最初的通知。泵读取续跑时，从原通知资源取得文本，不复制通知载荷，
也不递归包装。资源读取故障走泵的临时读取重试；身份或来源无效时拒绝执行。

接收失败时，旧输入仍然待处理，恢复继续保持阻塞。若进程在接收后、结清前死亡，
下一位所有者复用接收结果并完成后续处理。若在结清后死亡，待处理的续跑输入本身
就能提供下一次唤醒。

## 模型执行与幂等性

旧轮次不会再次执行。续跑开启新轮次，携带已提交历史、恢复出的工具答复及原通知。
指令要求模型在重试未知效果前检查持久状态。恢复代码不会派发工具，也不会把未知
结果推断为成功。工具审批、Workspace 访问和轮次预算仍走正常执行路径。

续跑写入现有的 `turn_attempt` 系统记录，代替第二条用户记录。这既保留单条用户
记录的保证，也能在再次崩溃后证明续跑已经开始。每条中断的续跑只有一个确定性后继，
仍然引用最初的通知。普通模型错误或取消不会生成后继。续跑的调用键与其他唤醒调用键
一样有界，因此恢复后的队长可以启动或续跑成员，而不会使 lineage ID 不断增长。

续跑成功完成后，消费原子任务结果的 acceptance；错误、取消或阻塞时不会声称已送达。
排队中的续跑沿原来源的关闭路径无需模型即可结清。结清日志会写出持久化续跑 ID，
使运维能够区分恢复与永久阻塞。调度不依赖已恢复答复的数量：即使中断的
`send_message` 无法重建答复，也仍需模型作出下一步决策。

## 验证与验收

- 在最新主干上，用真实 Spring/MySQL 和替代 Harness 复现沉默行为。先尝试
  全局安装的 CLI，单独记录构建限制。
- 用聚焦测试验证先接收再结清、接收失败重试、交接间隙重新打开、反复中断、
  原通知上下文有界、来源排除、排队关闭，以及子结果消费。
- 在修复后的 bundle 上，观察没有外部输入时的模型请求读取恢复答复，且只有一条
  原用户记录和一次已提交效果。再次重启后，不应有额外请求或效果。
- 在另一个成员仍运行时，探测中断的成员续跑；要求恰好一次 `continueChildRun`，
  不依赖之后的通知。明确区分脚本注入持久故障状态与运行中工具的故障注入。
- 执行根目录构建/类型检查、受影响包测试及独立 E2E 验证。明确记录未覆盖平台和
  默认禁用的 `team_plan` 探针；仅 monitor 证据不代表完整 P3a/P3W 验收。
