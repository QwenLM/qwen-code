## 1. Problem and current state

Phase 1 suspends an idle Session only when it owes nothing: no pending input (including a loop input whose `notBefore` lies in the future), no live background observation, no unsettled work. Phase 2 lets a suspended Session keep its MCP connections parked. Two classes of Session therefore still cannot suspend, and both pay the full resident cost (writer-lease and activation renewal, restored journal state, timers, Harness memory) for work that is not running:

1. **A Session with queued or deferred wake inputs.** A monitor notification, channel message, child-result acceptance, automation fire, session message, PR event, or self-paced loop wakeup that is committed but not yet consumed keeps the Session resident. A loop wakeup armed for an hour from now pins the Harness for that hour.
2. **A Session with a live background Shell or Monitor.** The physical process lives in the Runtime worker, but the observation loop that turns its output into durable records runs in the Harness, and any non-terminal `child_run`/`monitor_run` record blocks suspension outright.

### 1.1 Wake inputs are already durable; only their clock is resident

An input commits as `input.accepted` (`inputId`, `turnId`, `source`, `contentRef`, `deadline`, `admissionRef`, optional `notBefore`) together with an authority-generated `wake.requested`, in one journal transaction. It is consumed exactly when a `turn.settled` under the same `turnId` commits; nothing else consumes it. The pending set is therefore derivable from the journal alone, any number of restarts later (`pendingSessionInputs`, `packages/cli/src/serve/hosted-wake-intake.ts:37-68`). The wake sources are `monitor`, `channel`, `child_agent`, `workflow`, `automation`, `session_message`, `loop`, `pr_event` (`JdbcWakeRecoveryStore.SOURCES`, `packages/managed-agent-server/persistence/.../JdbcWakeRecoveryStore.java:29-30`; the Harness classifier `isWakeInputSource`, `packages/cli/src/serve/hosted-harness-session.ts:1616-1627`).

The resident delivery mechanism is the embedded pump `HostedMonitorWakeScheduler` (`packages/cli/src/serve/hosted-monitor-wake.ts:117`). It holds nothing in memory: each pass re-reads the journal, runs the oldest due input as an ordinary text turn, and verifies consumption by re-reading. Busy/blocked Sessions retry on a 500 ms cadence; a held approval wait re-derives on a 15 s cadence; a not-yet-due input is skipped per-input and exactly one deferral timer is armed at the earliest future `notBefore` (`deferIfPending`). A kick (a new arm, a cancel, a load) re-evaluates. The pump is rebuilt on every load (`hosted-harness-session.ts:7693`), and the deferral is per-input, not head-of-line (`hosted-harness-session.ts:7711-7724`). The self-paced loop wakeup that produces `notBefore` is implemented (`hosted-loop-session.ts`; the `shell/3` profile declares `loop_wakeup`), despite its design's stale "proposal" status line.

So the input, its due time, and its delivery are all already durable or re-derivable. What is resident is only the **clock**: the pump and its deferral timer live in the Harness process, and the eligibility predicate refuses to let the process go while any input is pending.

### 1.2 The control plane already has two wake paths, neither a due-time scheduler

**Transport fast path (hint-grade).** `JournalCommit.publishJournalAfterCommit` (`persistence/.../JournalCommit.java:305-325`) publishes one envelope per committed event to the per-Session LiteTopic and copies `wake.requested` to a shared wake-bootstrap LiteTopic that every node consumes (`adapters/.../event/LiteTopicEventTransport.java:59-76`). `TransportWakeActivator.onWake` (`control-plane/.../event/TransportWakeActivator.java:118-160`) treats the envelope only as a hint to look at SQL sooner: it re-checks `TransportConsumerStore.wakeFence` (workspace match, `sequence <= committedSequence`, Session open, **no live writer**, Harness available), claims via a CAS watermark `wake_covered_sequence` (`JdbcTransportConsumerStore.java:117-126`) before attempting, and hands the load to a bounded pool (4 threads / 256 queue). A full pool answers `DROPPED`, left to the SQL scan. The load uses `HarnessConnector.activateForWake` (`QwenHostedHarnessConnector.java:1731-1768`), which evicts the stale cached attachment a sealed writer leaves behind and takes the same new-work admission as a Turn. EventTransport delivery is best-effort and never recovery evidence (`contracts/.../event/EventTransport.java:17-19`); TypeScript has no envelope consumer (`packages/core/src/managed-runtime/managed-event-envelope.ts:21-32`).

**SQL backstop (correctness floor).** `WakeRecovery.scan` (`control-plane/.../session/WakeRecovery.java:34-70`) runs every 2 s on a dedicated scheduler, reads up to 8 candidates, and for each: claims, proves the pending set by replaying the journal, stamps the result, and calls `harness.recoverForWake` (a passive load, `QwenHostedHarnessConnector.java:1718-1727`). The claim sets a durable `wake_retry_at = NOW + 30 s` (`JdbcWakeRecoveryStore.claim:113-133`); a proof invocation reads at most 32 journal transactions, one per query, verifying each chunk's digest and sequence continuity (`hasPendingInput`, `PROOF_PAGES = 32`, `JOURNAL_PAGE = 1`, a 128-entry proof cache). Eligibility is an `ACTIVE`, non-retired public Session with an uncompacted journal and an unowned head — `SEALED`, or `ACTIVE` with an expired writer lease (`UNOWNED`, `JdbcWakeRecoveryStore.java:34-35`). The backstop also drops a child Session's wake when its parent run is terminal or stop-requested, clearing the hint **without** a `turn.settled` (`WakeRecovery.java:52-62`). The boundary design is [Hosted wake recovery after writer loss](2026-10-18-hosted-wake-recovery.md) (#14116/#14603).

**The gap.** Neither path fires at a deferred input's `notBefore`. The transport notice is emitted at **arm time**, when the Session is still resident (`OWNED`, no load); no journal event is committed at fire time. The backstop preserves a deferred loop input through a proof-cache latch that never certifies "nothing pending" while a future input exists and expires at the earliest `deferredUntil` (`isDeferredLoopInput`, `JdbcWakeRecoveryStore.java:338-345`), so the input is re-read as due only on a later 2 s scan, paced by the 30 s claim. There is **no Java timer that fires at `notBefore`**. The parent design records the consequence: on a journal of 201 transactions the wake comes at least three minutes after the input is due. The backstop is a crash recovery mechanism, not a general durable scheduler — its own design names "durable incremental proof and catalog cleanup" as remaining capacity work.

### 1.3 Background work: the process is already Runtime-owned; the observation is not

A background Shell (`child_run`, `kind=shell`) and a Monitor watch (`monitor_run`) are child processes of the Runtime worker, each under its own delegated cgroup v2 unit whose name derives from the execution identity, so a replacement worker re-attaches by name ([H3 design](2026-10-03-managed-shell-monitor-runtime.md); `ManagedChildRunSupervisor`, `packages/core/src/managed-runtime/managed-child-run-supervisor.ts:129`). Each process holds a non-terminal Runtime execution until its end is proven; a routine Runtime release with a live hold answers `runtime_session_held` and stops nothing (`RuntimeSessionRelease.java:103-145`, refusal at `:133`); only the close drain arm stops it. The hold is durable in the Broker's ledger and restored at load: `heldRuntimeTurns` carries both the promptIds of turns whose Runtime ended held and the Runtime Session ids restored from the Broker's durable hold rows (`hosted-harness-session.ts:959-970`).

What runs in the Harness is the **observation**:

- `HostedMonitorLoop` (`packages/cli/src/serve/hosted-monitor-loop.ts:100`) aggregates the watch's stdout lines into one observation per debounce window. `flush()` (`:387-415`) commits a `monitor_run` revision **plus a notification `input.accepted` (source `monitor`) in the same transaction** through `HostedMonitorSession.observe` (`hosted-monitor-session.ts:184-207`, commit at `:398-410`), then kicks the wake pump. The notification policy is **one notification per accepted observation** (`hosted-monitor-loop.ts:417-435`); `notifiedThrough` is bookkeeping, not a gate. The watch itself runs in the worker; the Harness-side `HostedMonitorRemoteExecutor` (`hosted-monitor-remote-executor.ts:25-67`) only registers `{onLine, onExit}` on the publisher and asks the worker to stop via the Broker's `monitor-stop` (`managed-monitor-runtime.ts:89-135`).
- Background Shell has no separate loop class; its observation is the `HostedShellPublisher`'s capture forwarding (`fanMonitorLines`, `hosted-shell-publisher.ts:623-664`; `advanceBackgroundManifest` forwards each durable manifest revision to the record).
- The only worker→Harness background-event path is an HTTP POST to a **loopback** server the Harness owns: `HostedShellPublisher` listens on `127.0.0.1:0` with a random 32-byte bearer token (`hosted-shell-publisher.ts:102-193`); the worker's client `rpc()` posts to the descriptor URL (`managed-shell-publisher.ts:72-133`). This server dies with the Harness. Every journal commit it feeds goes through the Harness's writer authority — there is no worker→Store or Broker→journal commit path today (`v3/hooks` is Java→worker dispatch, not a journal writer).

Two facts about the worker side bound what 3b must change:

- **The worker's capture is fail-stop on publisher loss, not retry-or-redirect.** `RemoteShellCapture.append` catches any RPC failure and calls `failCapture()` (`managed-shell-publisher.ts:258-280`); once `failed`, later writes are dropped, `finish` marks the stream incomplete, and `finalize` produces `captureStatus:'unavailable'`, `captureReason:'producer_lost'`, `deliveryStatus:'blocked'` (`:340-378`). Closing the loopback publisher on suspension therefore **permanently fails** an in-flight capture today; it does not fall back to anything. 3b must rework this semantics, not merely add a staging endpoint (§4.4).
- **The Broker already settles a finished background execution without a Harness.** `ManagedBackgroundShellRegistry.complete()` drops the hold when the process end is proven and the finalize/accept chain resolves (`managed-background-shell-registry.ts:200-290`, hold drop at `:280-290`), retaining the finished receipt in worker memory until the worker ends (`:64-70`). The Broker's `settleUnprovenBackgroundRows` sweep queries that retained receipt through the worker's status route (`managed-monitor-runtime.ts:113-127`) and settles the execution row — this is exactly how a `runtime_session_held` refusal is later resolved. 3b inherits this path; it does not invent execution settlement (§4.4).

### 1.4 The guards that pin these Sessions

`suspensionLiveWork` (`hosted-harness-session.ts:4981-5032`) blocks on, among the active-work terms, the live monitor loops (`:5015-5020`) and **any non-terminal `child_run`/`monitor_run` record** (`:5021-5029`) — so even a parked `runtime_lost` record or a background Shell with no live loop blocks. For a background run that outlives its turn, two further terms are the actual pins: `session.heldRuntimeTurns.size > 0` (`:5003`) and `hasHostedCleanupDebt` (`:4999`). A shell-profile turn whose `finish()` meets `runtime_session_held` sets `runtimeHeld` (`hosted-workspace-tool-turn.ts:10749-10758`), which adds to `heldRuntimeTurns` (`hosted-harness-session.ts:4531,13038`); a cleanup-hold path adds the held Runtime Session id (`retainHostedCleanupHolds`, `:2771-2782`). A separate `pendingInputs` check in `attemptSuspend` (`:5050-5060`) counts **all** `pendingSessionInputs` over the committed prefix, with no source or due-time filter, and runs twice per attempt (`hosted-session-suspension.ts:232,242`); any pending input reverts and re-arms. This is the check that blocks a future-`notBefore` loop input. The non-wake-owned unsettled inputs are counted separately by `unsettledInputs` (`:5002`), which excludes wake-owned inputs precisely because the pump owns their consumption (`unsettledInputsThrough`, `:2035-2062`; `isWakeOwnedInput`, `:2006-2016`).

The recovery view's `ready` arm requires, beside a sealed writer, released activation, current projection, no active Turn and no unsettled Runtime execution or cleanup debt, a **wake proof of emptiness**: `is_wake_pending = 0` and `wake_head_revision = journal_revision` (`SessionRecoveryService.java:139-156`; [recovery view addendum](2026-11-18-managed-suspension-recovery-view.md) §2-3). The unsettled-work probe names a non-null `runtime_state` DOMAIN row and a `REFERENCED` `HOSTED_CLEANUP` ref (`JdbcSessionRecoveryRepository.java:34-56`). A Session with a pending input is therefore not `ready` by contract, and the addendum names widening this proof as follow-up work.

## 2. Goals and scope

**Goal.** The control plane decides when a suspended Session has a due input and wakes any pool member to run it; the Harness runs the input and suspends again. Observation of background work moves to the Runtime worker and the control plane, so a Session with a background Shell or Monitor can suspend while its processes keep running and keep their records durable.

**Scope, first increment (3a — wake scheduling).** A Session whose only owed work is unattempted wake inputs (queued or deferred) can suspend. A durable wake-input projection gives the control plane an O(1) due-time scan; a leased, fenced dispatcher wakes due Sessions through the existing wake verbs; the transport fast path and the SQL backstop remain unchanged as hint and correctness floor. The eligibility and recovery-view guards relax accordingly. No background-work change yet.

**Scope, second increment (3b — Runtime-owned observation).** The worker aggregates and supervises its background processes; a Broker-side staging ledger holds observations **and their output bytes** durably while no Harness holds the writer; the Harness publishes the staged resources and commits the staged records on wake. A Session with live background work can suspend; the Runtime hold persists across suspension and is re-attached on reopen. 3b is three hard mechanisms, not one endpoint: the worker capture-pipeline rework (§4.4), the resource-carrying staging drain (§4.4), and the suspension mount-handback tolerance plus the full eligibility-term set (§4.5).

**Out of scope (later increments / other phases).**

- Phase 4 parked approvals: a Turn waiting for an approval still pins the Harness (`session.active`/`recoveredTurn`). The pump's 15 s held cadence is unchanged.
- A second journal writer. All journal commits still go through the Harness writer; 3b stages observations in a Broker ledger and commits them on wake rather than introducing a maintenance writer authority (see §5.3).
- Journal compaction interaction. Live compaction is not enabled today (`compacted_through_revision` advances only for `DELETED` heads in `ManagedSessionRetirementStore`; the TS store refuses a compacted head, `http-managed-session-store.ts:493-495`). The projection is rebuildable by replay so it does not hard-depend on an uncompacted prefix forever, but the compaction-aware rebuild is separate work.
- Background work on `EXTERNAL` storage, detach of a background process to an independent owner, and cross-host-reboot process attach (H3 already defers these).
- The journal-restore cost that grows with history (parent design: Phase 3 does not eliminate it).

## 3. Cost model (analytical estimate, not measured)

### 3.1 What residency costs these Sessions

The parent design's measured idle cost is 51–56 SQL statements per idle minute per Session on the historical rig (renewal-dominated), plus Harness memory and timers; current constants must be re-measured. A Session pinned by a deferred loop input pays this for the whole deferral (up to the 3600 s clamp, or the 24 h chain). A Session pinned by a background Monitor pays it for the life of the watch. Neither is running a Turn.

### 3.2 What 3a eliminates and adds

Eliminated: the residency of a Session whose only owed work is unattempted wake inputs — it suspends after the idle period and stays suspended until an input is due. The wake itself replaces the minutes-late backstop with a due-time dispatch (target: seconds, bounded by the scan period and the cold-open admission).

Added: one projection row per accepted wake input and one delete per settlement, maintained in the commit transaction (§4.1); a periodic due-scan over the projection (§4.2); a wake-driven cold open per due batch. The cold-open MCP component is already removed by Phase 2 parked reuse; the remaining cold-open cost is the MCP-free floor plus journal restore. A wake that finds nothing due (a stale projection row) pays one wasted load and re-suspends — bounded and harmless.

### 3.3 What 3b eliminates and adds

Eliminated: the residency of a Session whose only owed work is live background observation. The worker already owns the processes; 3b removes the Harness-side loop and the loopback dependency while suspended.

Added: a Broker staging write per observation batch (debounced ≥1 s, bounded by the 10,000-observation record bound), **carrying the observation bytes and output segments**; a commit-on-wake drain that publishes those resources before committing records; a task-view read path for staged live state; and the one-time rework of the worker capture pipeline from fail-stop to buffer-and-redirect (§4.4). The notification turn still needs a Harness — 3b does not remove the wake, it removes the residency between wakes. A continuously loud Monitor never goes idle and so never suspends (the idle clock keeps it resident, as today): 3b's residency saving applies to bursty or quiet background work, not to a nonstop stream (§4.4).

### 3.4 Witnesses

- **Residency witness**: `attachedSessions` over a rig of N Sessions each holding one loop input armed at the maximum delay — Phase 1 keeps N resident; 3a suspends N after the idle period and wakes exactly the due ones.
- **Due-latency witness**: arm a loop input at `now + T`, suspend, measure fire-to-turn-start latency against the backstop's ≥3 min on a long journal.
- **Reconnect witness**: Phase 2's `mcp.start` count stays 0 across a 3a wake (parked reuse).
- **Background witness**: a suspended Session's Monitor keeps staging observations and its notification fires a turn on wake; a `cgroup.kill`-proven Shell exit settles its Broker execution while suspended (via the existing sweep); the capture survives suspension with no `producer_lost`.

## 4. Proposal

### 4.1 A durable wake-input projection (3a)

A new projection table `ma_session_wake_input` indexes the pending wake inputs by due time. It is a **rebuildable cache of journal facts, never a second authority** — the same shape as the automation ledger's three rebuildable indexes ([H6 runtime](2026-10-07-managed-automation-runtime.md), decision 12).

| Column                                                                 | Meaning                                                           |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `tenant_key`, `harness_key`, `tenant_id`, `session_id`, `workspace_id` | Session scope, keyed like the head                                |
| `turn_id`                                                              | The input's `turnId` (primary key part); settlement deletes by it |
| `input_id`, `source`                                                   | The accepted input's identity and source                          |
| `not_before`                                                           | Epoch ms; `0` for immediate delivery                              |
| `sequence`, `journal_revision`                                         | The accepting commit's sequence and revision                      |

`JournalCommit` already parses every committed event (`JournalCommit.java:177-199`) and maintains projections transactionally (`extensionRecords.apply`, `actions.apply`, the head's wake hint at `:261-268`). The projection rides the same loop: on an `input.accepted` whose source is a wake source, INSERT a row; on a `turn.settled`, DELETE the row of that `turnId`. Both happen in the commit's own transaction, so the projection is atomic with the journal and current at every revision. Loop replacement and cancel settle the replaced input model-free under its **own** `turnId` (`settleLoopTurn`, `hosted-loop-session.ts:517-546`, `payload.turnId` and event id `turn:<turnId>`), which deletes its row — no spurious wake.

A covering index on `(not_before, tenant_key, harness_key)` makes the due-scan an index range. The existing `is_wake_pending` hint, `wake_head_revision` watermark and generated `is_wake_scan_pending` column (`V1__managed_schema.sql:222-230`, index `idx_ma_head_wake` at `:1474`) are **unchanged**: they remain the backstop's mechanism and the projection's rebuild trigger.

**Rebuild.** A missing or corrupt projection is rebuilt by replaying the committed prefix — exactly the pending-set derivation `hasPendingInput` already performs. The backstop's proof remains the correctness floor: a projection that misses a due input degrades latency to today's backstop, never correctness; a projection that names a settled input causes one wasted load. The projection is therefore allowed to be stale in both directions without losing or duplicating work.

**Invalidation the projection cannot see (dispatcher-side filters).** A pending wake input can be invalidated by state in **another** Session's journal, or by a local delivery policy, neither of which produces a `turn.settled` in this Session:

- A child Session's notification is dropped when its parent run is terminal or stop-requested; the backstop clears the hint without a settle (`WakeRecovery.java:52-62`). The parent's `turn.settled` never touches the child's projection row, so the row would otherwise persist and cause a wake–load–suspend loop. The dispatcher therefore replicates the backstop's child-run terminal/stop-requested check before waking, and skips (the backstop or the load's own settle clears the row).
- A stopped run's `session_message` inputs are skipped by the pump (`stoppedMessage`, `hosted-harness-session.ts:7687-7691,7706-7710`) and settled by the stop relay, not by a turn. The dispatcher must not treat a policy-skipped input as due; the same filter the pump applies (stopped messages, cancelled notifications) gates the dispatch, so a skipped input never spins a wake.

These filters keep the projection a pure due-time index while the dispatcher owns the "is this input still deliverable" judgment the backstop already makes.

### 4.2 Due-time dispatch (3a)

A new `WakeDispatchJob` on a dedicated `wakeDispatchScheduler` bean follows the house scheduler pattern (named single-thread `ThreadPoolTaskScheduler` + `@Scheduled` fixed delay; no leader election exists or is needed — safety is per-row CAS plus fencing, as the wake claim, the transport watermark and the automation ledger already are). Candidate period 1 s, measured before enablement.

Each tick:

1. **Scan due.** Select Sessions with a projection row `not_before <= NOW`, joined to the head for the same eligibility the backstop uses (unowned, `ACTIVE` public, non-retired, matching workspace), ordered by due time, bounded page (candidate 8), then apply the §4.1 deliverability filters.
2. **Claim.** A per-session dispatch claim (lease owner + lease until + monotonic fence, the automation ledger's shape) prevents two nodes from dispatching one Session at once. The claim is fenced by `journal_revision`; a claim whose revision moved re-reads. The lease must be at least the cold-open bound, so a slow load does not expire its own claim and trigger a redundant second dispatch. The backstop's `wake_retry_at` is left untouched so the two mechanisms do not fight over one column.
3. **Wake.** Call the existing `activateForWake` (the transport activator's verb): it evicts the stale attachment, takes new-work admission, and the Harness's writer acquisition is the activation fence. The load rebuilds the pump, which delivers the due inputs and re-arms the deferral timer for any still-future input. No new Harness verb is required for 3a.
4. **Pace failures.** A transient refusal (`hosted_session_open_busy`, `hosted_session_closing`, pool-ownership waits) retries with backoff under the same churn cap #17681 established (`WAIT_CHURN_BUDGET_FACTOR = 4`, `HarnessCoordinator.java:101`); a definitive refusal records its own code and stops dispatching that input until the journal advances. A claimed-but-failed dispatch leaves the input pending for the next tick or the backstop.

**Burst control and the takeover path.** Wake loads inherit the per-instance cold-open cap (`HOSTED_COLD_OPEN_LIMIT = 8`, `hosted-session-suspension.ts:18`; refusal `409 hosted_session_open_busy`, classified transient in `HarnessConflictCodes.java:23-29`). The placement path has two cases, and the distinction matters for the latency target:

- **Sticky route to a reachable owner (the normal case).** A cleanly suspended Session keeps its placement `ACTIVE` on the instance that suspended it. `HarnessPoolConnector.select` routes to that owner without a takeover; the leaf's `activateForWake` loads, and the Store re-acquires the writer on the `SEALED` head **immediately** — the lease-lapse guard applies only to an `ACTIVE` head, while a `SEALED` head falls straight through to a generation-incremented re-acquire (`JournalWriterLifecycle.java:257-292`; the seal itself only sets `state='SEALED'`, leaving `writer_lease_until`, `:399`). So a normal 3a wake is not gated by the writer lease.
- **Cross-instance takeover (owner down or quiescing).** Only when the pool must take the placement over does the `harness_owner_still_live` gate apply: takeover needs the placement `RELEASED` with a release record, or the writer lease lapsed with a known activation (`JdbcHarnessPlacementStore.java:163-171`). A suspended Session whose owner is unreachable therefore waits out the remaining writer lease (≤ the lease duration) before another instance can take it. This is the crash/reassignment path, not the steady-state wake.

The dispatcher's bounded page, claim lease and jitter keep a synchronized due batch from filling one instance's slots; the churn cap ages out a caller that keeps meeting a full instance.

**Relationship to the existing paths.** The transport activator stays the hint-grade fast path for an immediate `wake.requested` notice on an unowned Session; the dispatcher is the due-time primary for deferred inputs and the reliable path when the transport is off or a notice was dropped; the SQL backstop stays the correctness floor and the projection-rebuild trigger. The three share the same wake verbs and the same SQL truth; none is recovery evidence over the journal.

### 4.3 Suspension with pending wake inputs (3a)

The `pendingInputs` gate in `attemptSuspend` is removed **for unattempted wake inputs**. The distinction is already enforced by the active-work guards and the pump itself: a wake input whose turn started is a running Turn (`session.active`), a recovered Turn (`recoveredTurn`), or a blocked aftermath. On a takeover load after a crash mid-wake-turn, the pump's first pass detects the prior transcript attempt (`wakeHasPriorAttempt`) and returns `'recovery'`, setting `session.blocked = true` (`hosted-monitor-wake-turn.ts:122-171`); `suspensionLiveWork` then blocks on `session.blocked`. So an attempted input is never made suspendable — it belongs to the recovery fleet, exactly as today. An unattempted wake input has no Turn and no aftermath; it is schedulable work the dispatcher owns. The non-wake-owned `unsettledInputs` term (`:5002`) is unchanged.

Teardown is unchanged: `wake.close()` already stops the pump **without settling any input** (`hosted-monitor-wake.ts` `close()`), so the inputs stay pending in the journal and the projection; `mcp.suspend()` parks (Phase 2); the writer seals last. The idle clock and the bounded admitted-work wait are unchanged. A Session woken by the dispatcher runs its due inputs, and when it goes idle again Phase 1 re-suspends it — now permitted with pending inputs.

**Rollout control.** Following Phase 2's `mcpParkable` precedent (§5.6 of the Phase 2 design), the control plane advertises a wake-dispatch capability, gated by `qwen.managed-agent.wake-dispatch.enabled` (default off). The Harness relaxes the `pendingInputs` gate only when the capability is advertised; with it off, behavior is exactly Phase 1's. This keeps the eligibility change and the dispatcher coupled, so a suspended Session is never stranded without a scheduler.

### 4.4 Runtime-owned observation (3b)

The observation moves to the worker; its durable commit while suspended goes through a Broker staging ledger, and the journal commit happens on wake. This preserves the single-writer invariant the whole recovery proof rests on (§5.3). 3b is three mechanisms, each named below.

**Mechanism 1 — rework the worker capture pipeline (the largest change).** Today the worker's `RemoteShellCapture` is fail-stop: any publisher RPC failure permanently fails the capture (`managed-shell-publisher.ts:258-280,340-378`), and `ManagedBackgroundShellRegistry.complete()` delivers the terminal envelope through `sink.finish`/`finalize`/`publisher.accept` (`managed-background-shell-registry.ts:200-290`). 3b changes this to **buffer-and-redirect**: when the loopback publisher is absent or refuses (no Harness), the capture writes its output segments and terminal evidence to the Broker staging route instead of failing, and resumes direct loopback delivery when a Harness re-registers the publisher on wake. The aggregation and debounce that `HostedMonitorLoop` does today move into the worker's `ManagedMonitorRuntime` (which already answers status/stop from physical evidence): the worker captures the watch's stdout under its cgroup, aggregates per debounce window, and applies the terminal conditions (observation quota, idle timeout, watch end). This is a rework of the capture state machine, not a new endpoint beside it; the fail-stop semantics that protect a foreground capture must be preserved for the foreground lane while the background lane gains the staging fallback.

**Mechanism 2 — staging carries bytes, and the drain publishes resources before records.** A new Broker maintenance route, fenced by an `OperationGrant` carrying the original `targetOperationId`, binding and generation (the Hook-async / `monitor-stop` pattern), accepts observation batches and terminal evidence and writes them to a bounded per-run staging ledger. The ledger holds **the observation bytes and the output segments/manifest chain**, not only SQL metadata: an observation commit publishes a `managed-monitor-observation` resource (`hosted-monitor-session.ts:194-197`) and the output advances a manifest chain whose lineage is verified (`isToolResultManifestChainLink`, `:225-240`). The worker has no Store writer credential, so while suspended these bytes live in staging; on wake the Harness **first publishes the staged resources, then commits the `monitor_run` revisions and their notification inputs**, idempotent by `observationSequence`. The order matters: the load's recovery pass verifies every `tool.receipt` manifest against the publication owner (`hosted-harness-session.ts:3196-3225`), so a record committed before its resource exists would fail verification. The drain is part of the load's reconcile, ahead of that verification, and the staging bound mirrors the 10,000-observation record bound.

**Notification and wake.** The policy is one notification per accepted observation (§1.3), so every staged observation batch is notification-worthy; staging marks a pending notification for the Session and the dispatcher treats it as a due wake input of source `monitor` (the staging ledger feeds the same due-scan, or sets the wake hint under its own fence). The wake loads the Harness, which drains **all** staged observations (Mechanism 2) and the pump then delivers the notification turns serially — one wake coalesces the whole staged backlog. While the Session is resident the worker posts to the re-established loopback publisher as today, so live observations need no staging round-trip. A continuously loud Monitor keeps the Session resident via the idle clock and never suspends (no saving, no regression); 3b's saving is for bursty or quiet background work, where the Session suspends between bursts and a wake drains the accumulated backlog at once.

**Shell exit and the hold.** Shell exit supervision is already the worker's, and the Broker already settles a finished execution without a Harness through its `settleUnprovenBackgroundRows` sweep querying the worker's retained receipt (§1.3). 3b inherits this: a proven exit while suspended settles the Broker execution and releases the hold via the existing sweep; the terminal **record** revision is staged and committed on the next wake (Mechanism 2). The journal record therefore lags the execution ledger until wake, which the task view accounts for below.

**Task view while suspended.** The execution ledger already projects live `runtime_state`; the public task view reads it for liveness and reads output from the committed Artifact plus the bounded staging tail. First cut accepts that the journal-record state lags until wake; the live indicator comes from the execution ledger, not from a stale record. A fuller staged-output read path is a follow-up if measurement demands it.

**Rollout control.** A separate gate `qwen.managed-agent.runtime-observation.enabled` (default off) plus a worker capability advertisement; the Harness relaxes the background terms of `suspensionLiveWork` only when both the control plane and the worker advertise observation. With it off, background-work Sessions stay resident as today.

### 4.5 Background hold across suspension (3b)

**The full eligibility-term set.** When observation is advertised, 3b removes every term that pins a Session solely for background work: the live monitor loops (`:5015-5020`), the non-terminal `child_run`/`monitor_run` records (`:5021-5029`), **and** the background-hold terms `session.heldRuntimeTurns.size > 0` (`:5003`) and the cleanup debt owed solely to a background hold (`hasHostedCleanupDebt`, `:4999`). The last two are the actual pins for a shell-profile turn that left its Runtime held (§1.4); removing only the loop/record terms would leave the Session un-suspendable. A cleanup debt owed to a genuinely unreleased foreground owner is **not** background work and still blocks. Every active-work, recovery, stream, client-files and lifecycle term stays.

**Teardown must tolerate the mount handback, not just skip the drain.** The processes are the Runtime's and the hold is the Runtime's; the Harness leaving changes neither, and teardown must not stop or drain background work. But the existing teardown steps actively hand the mount back, and that handback refuses while a background execution is live:

- A Hook-configured Session's `hooks.close({terminal:false})` calls `releaseMount` (`hosted-hook-session.ts:2066-2095`), and `releaseMountAfterSweep` refuses `runtime_session_busy` for any active background execution under the owner, with no exclusion (`RuntimeExecutionRecovery.java:388-395`), raising `HostedHookRecoveryRequiredError` and failing the teardown.
- An MCP-profile Session whose turn Runtime is the MCP owner parks via `mcp.suspend()` only when parking succeeds; otherwise `closeResources({terminal:false})` calls the same refusing `releaseMount` (`hosted-mcp-session.ts:1143-1146,1296-1305`). **3b for such Sessions therefore depends on Phase 2 parking being enabled** (so the park keeps membership and never reaches the handback), or on the same tolerance below.

3b adds a suspension-mode handback tolerance: when the only thing holding the mount is a live background execution of this Session, the non-terminal close keeps the membership (as Phase 2's park does) instead of treating the refusal as recovery-required. The held-runtime lease release for a recovered turn already defers a non-terminal handback (`releaseHeldRuntime`, distinct from `releaseLeaseNow` which only handles `runtimeLeaseHeld`, `hosted-harness-session.ts:11332`); the background tolerance is the analogous keep-membership arm for the owner close. The close-path audit must pin this so a later detach change cannot silently stop background work on suspension.

**Reclamation guard.** A suspended Session with live background executions must not be reclaimed. The Runtime Session release is already fenced by the execution ledger: a live background hold answers `runtime_session_held`/`runtime_session_busy` (`RuntimeSessionRelease.java:103-145`), so `RuntimeRetentionJob` and a full release leave it alone. The Phase 2 MCP parked-owner reclamation is **not** automatically covered: its `hasPendingWork` guard is MCP-scoped — pending starts, non-settled MCP operations, MCP connections with pending requests (`managed-mcp-runtime.ts:765-779`) — and does not name background `child_run`/`monitor_run` executions, which live in the execution ledger, not in `ManagedMcpRuntime`. 3b therefore adds an explicit background-execution refusal to the parked-owner reclamation eligibility (reading the execution ledger / supervisor for this Runtime Session), and verifies the mount-membership release is fenced by the same hold. The consequence is named: live background work bounds the park — its MCP connections are not reclaimed while it runs, and its storage membership stays held until the work ends and the idle reclamation applies.

**Reopen.** The load re-attaches to the live executions through H3's replay-tolerant start attachment (the start receipt is set once and kept across a re-attach; a replacement worker re-attaches by cgroup unit name). `heldRuntimeTurns` is restored from the Broker's durable hold rows (`:959-970`), so the reopened Harness owes the hold exactly until close, as today.

**Worker loss while suspended.** A Runtime generation change leaves the Session recovery-required, the processes unproven and their holds blocked; no fresh owner is minted and no second process starts — the same contract Phase 2's `workerKillWhileIdleNeverMintsAFreshOwnerOnMySql` fault gate pins for parked MCP. Staged observations orphaned by the lost generation are reconciled or discarded under the generation fence on the next load, never committed as a rerun.

### 4.6 Recovery-view contract update

The `ready` arm's wake-emptiness guard is replaced by **projection currency**, and (3b) a background carve-out:

- Pending unattempted wake inputs no longer block `ready`. They are scheduled work the dispatcher owns, covered by a projection current at `journal_revision`. The guard becomes "the wake projection covers this revision" rather than "no pending wake input". The backstop still clears its own hint by replay; that hint is no longer a `ready` precondition.
- (3b) A background run provably held by a live Runtime binding no longer blocks `ready` through its non-null `runtime_state`, and a cleanup debt owed solely to such a hold no longer blocks through its `REFERENCED` `HOSTED_CLEANUP` ref (`JdbcSessionRecoveryRepository.java:34-56`). Both are owned work, like a parked MCP owner is owned by the Runtime. The guard names the exception explicitly: no live `runtime_state` and no owed cleanup **except** a `child_run`/`monitor_run` whose execution is held by a live binding of this Session's Runtime (and the cleanup ref naming that same hold).
- The other guards are unchanged: no active Turn, no genuinely owed cleanup debt, sealed writer, released activation, current activation projection. A sealed head that cannot prove these keeps the conservative answer; nothing is relabelled healthy on cache absence.

This is the widening the [recovery view addendum](2026-11-18-managed-suspension-recovery-view.md) §3 names as follow-up work. The [bounded recovery addendum](2026-11-18-managed-suspension-bounded-recovery.md)'s proof is unaffected: it relies on writer fencing (lease expiry → generation + 1), not on "sealed ⟹ resources released"; 3b leaves background resources under Runtime care, the same shape as the crash-recovery branch the proof already declares.

## 5. Design decisions and rationale

### 5.1 A projection table, not a head due-time column

A head-level `wake_due_at` cannot be decremented correctly when an input settles without knowing the remaining pending set; maintaining it would itself require a per-input index. The per-input table is the primitive: settlement deletes a row, the due-scan reads `MIN(not_before)`, and rebuild is the existing replay. A head due-column derived from the table is a later scan optimization, not the source of truth. Cross-session invalidation (a parent run's terminal state) is a dispatcher-side filter, not a projection write, because the invalidating fact lives in another Session's journal (§4.1).

### 5.2 A dispatcher beside the backstop, not a replacement

The backstop is the correctness floor and the projection-rebuild trigger; removing it would make the projection a single point of failure for discovery. The dispatcher is the due-time primary; the transport stays the hint fast path. Three mechanisms, one SQL truth, one journal authority — the same layering the wake-recovery design already uses for MQ-over-SQL. The dispatcher reuses the existing wake verbs and admission, so it adds no new Harness contract for 3a.

### 5.3 Staging, not a maintenance writer

The single-writer invariant is what makes the recovery proof work: two Harnesses advancing one Session would diverge and duplicate side effects. A maintenance writer authority that lets the Broker or worker commit `monitor_run` revisions directly to the journal would need a new fencing story against the writer generation and would touch the H0c authority rules and both recovery proofs. Staging keeps every journal commit under the Harness writer; the Broker ledger is a rebuildable cache of in-flight observations, exactly as the automation ledger is a rebuildable index of journal facts. The cost is real and named: a bounded commit lag (observations are durable in staging immediately, in the journal on next wake), a staging ledger that carries output **bytes** and a drain that publishes resources before records (§4.4 Mechanism 2), a task-view read path, and the one-time rework of the worker capture pipeline from fail-stop to buffer-and-redirect (§4.4 Mechanism 1). The benefit is that 3b does not reopen the single-writer safety project. A maintenance writer is a later increment only if the lag proves unacceptable.

### 5.4 The hold persists; suspension is not a drain

Background processes belong to the Runtime, not the Harness. Stopping them on suspension would cancel the user's work — the same reason Phase 1's suspension does not reuse the detach close path. The hold is already durable in the Broker and restored at load; 3b lets it span suspension unchanged, tolerates the owner mount handback that would otherwise refuse (§4.5), and bounds reclamation by it.

### 5.5 No new journal kind; the contract is closed

The journal kind vocabulary is frozen on both TS and Java sides (`managed-event-envelope.ts`; `ManagedEventEnvelopes`). 3a adds no event: the projection is SQL-side, derived from existing `input.accepted`/`turn.settled`. 3b commits the existing `monitor_run` revisions and `input.accepted` notifications on wake; staging is a Broker ledger, not a journal record. The `notBefore` field is already in the closed `input.accepted` schema (the loop wakeup design added it), so no schema change is needed for due time.

### 5.6 Capability-gated rollout

Phase 1 chose no configuration switch; Phase 2 introduced `mcpParkable` as rollout control because parking changes resource lifetime. Phase 3 changes which Sessions may suspend and who owns their clock and observation, so it follows Phase 2: a control-plane capability for wake dispatch and a worker capability for observation, both default off, both required before the Harness relaxes the corresponding guard. A deployment without the capability behaves exactly as the prior phase.

## 6. Interaction with Phases 1 and 2

- **Eligibility predicate.** 3a removes the `pendingInputs` gate for unattempted wake inputs; 3b removes the live-loop, non-terminal-background-record, `heldRuntimeTurns` and background-only cleanup-debt terms (§4.5). Every active-work, recovery, stream, client-files and lifecycle term stays, as does cleanup debt owed to a genuine foreground owner. The predicate still checks persistent blockers before raising the gate and rechecks in one synchronous section.
- **Teardown order.** Unchanged in sequence: wake → owners (park) → lease + cleanup → publishers → writer seal → stopLocal. 3a's `wake.close()` already settles nothing. 3b's teardown does not drain background, tolerates the owner mount handback for a background-only hold (§4.5), and the publisher close stops only the Harness-side forwarding while the worker capture redirects to staging (§4.4).
- **Parked MCP owners.** A 3a wake takes Phase 2's reuse path (acquire → status → revalidate → replace-then-retire); the `mcp.start` reconnect witness stays 0. A Session with both parked MCP and live background work parks its MCP and holds its background; reclamation of the MCP owner is refused while background work is pending (§4.5). 3b for an MCP-owner Session depends on Phase 2 parking being enabled (§4.5).
- **Bounded recovery.** The #8 proof holds: writer fencing, not resource release, is its premise. A failed 3b teardown follows the existing drain-failure path; background holds persist as blocked, never silently released.
- **Recovery view.** §4.6 widens `ready`; the lag arm (`awaiting_evidence` on a skewed activation projection) and the conservative fall-through are unchanged.

## 7. Measurement plan (enablement gate)

The parent design requires measurement before enablement; §3 is an estimate. Extend the Phase 2 measurement rig (or the WP3 rig it builds on):

1. **Residency**: N Sessions each with one loop input armed at the maximum delay (the 3600 s clamp); measure `attachedSessions` and renewal SQL before/after 3a, and the wake fan-out when they become due together.
2. **Due latency**: fire-to-turn-start for a deferred input on journals of 1/40/200+ transactions, dispatcher vs backstop; choose the scan period and claim lease (lease ≥ cold-open bound).
3. **Projection cost**: commit-path statements added per input/settle; due-scan cost at catalog scale (the wake-recovery design's "large catalogs and histories" capacity concern).
4. **Cold-open burst**: synchronized due batch against `HOSTED_COLD_OPEN_LIMIT`; choose dispatcher page/jitter and confirm the churn cap ages out a saturated caller.
5. **Background (3b)**: staging write rate and byte volume under a loud Monitor; commit-on-wake drain cost (resource publication + record commit); notification latency and wake coalescing; the loud-monitor residency boundary (a nonstop stream stays resident); Shell-exit hold release while suspended via the existing sweep; capture survival across suspension (no `producer_lost`); task-view staleness bound.
6. **Reconnect witness**: `mcp.start` stays 0 across 3a/3b wakes (Phase 2 reuse).

Outputs choose the shipping constants (scan period, claim lease, dispatcher page, staging bound) and confirm the benefit is worth the added commit-path, scan, and capture-rework cost.

## 8. Constraints and risks

- **Projection staleness.** A stale projection degrades wake latency to the backstop (missed due input) or wastes one load (settled input); it never loses or duplicates work. The rebuild path must be exercised, not assumed. Cross-session invalidation and policy-skipped inputs are dispatcher-side filters (§4.1); a missing filter spins a wake–load–suspend loop, so it is acceptance-tested, not assumed.
- **Commit-path cost.** The projection adds SQL to every commit carrying a wake input or settlement. At high input rates this is a hot-path cost; measurement (§7.3) gates it, and a head due-column or batched maintenance is the fallback if it is too high.
- **Capture-pipeline rework (3b).** The worker capture is fail-stop today (§1.3); turning the background lane into buffer-and-redirect while keeping the foreground lane fail-stop is the largest 3b change and the most likely source of output-loss or double-delivery regressions. It needs its own characterization tests before the staging route is wired.
- **Staging carries bytes; drain order (3b).** Staging holds output bytes and the manifest chain, and the drain must publish resources before committing records so the load's receipt verification passes (§4.4). A drain that commits records first, or drops the manifest lineage, fails the load or strands the output. The staging byte bound and retention are open (§10).
- **Mount-handback tolerance (3b).** The owner close actively hands the mount back and refuses on a live background execution (§4.5); 3b's keep-membership tolerance must be scoped to a background-only hold so a genuine foreground owner still refuses. MCP-owner Sessions depend on Phase 2 parking being enabled.
- **Staging lag (3b).** Observations are durable in staging immediately but in the journal only on wake. A reader that assumes journal-currency sees stale state; the task view must read the execution ledger for liveness. The lag is bounded by the wake latency, not unbounded.
- **Staging orphan (3b).** A lost worker generation orphans staged observations; the generation fence must reconcile or discard them, never commit a rerun. The 10,000-observation bound applies to staging as to the record.
- **Background bounds the park (3b).** Live background work refuses MCP reclamation and holds storage membership; a long-lived Monitor delays maintenance until it ends. This is the same tradeoff Phase 2 names for parked members, extended to background holds.
- **Cold-open burst.** Synchronized wakes can overload the shared Session Store even when each instance caps its opens; the churn cap and dispatcher pacing are the mitigation, and the parent design's burst risk remains.
- **Close-path coupling.** Suspension reuses part of the detach close path; 3b's "do not drain background" and mount-handback tolerance must pin every line of the close-path audit so a later detach change cannot silently stop background work on suspension.
- **Single-writer preserved.** 3b deliberately does not introduce a second writer; any future maintenance-writer increment must revisit both recovery proofs and the H0c authority rules.

## 9. Validation and acceptance

- **3a suspension**: a Session whose only owed work is an unattempted queued or deferred wake input suspends after the idle period; its writer seals, activation releases, renewal stops, and the recovery view reports `ready` with the projection current.
- **3a due dispatch**: a deferred input fires within the measured latency bound of its `notBefore` (not the backstop's minutes); an immediate input committed while suspended is dispatched; an overdue input fires exactly once late; no catch-up count. A normal wake to the reachable owner is not gated by the writer lease (§4.2).
- **3a no double run**: two racing dispatchers (or dispatcher + transport + backstop) load one Session once per wake; the writer acquisition fences; the input settles once under its `turnId`.
- **3a attempted work stays resident**: a wake input whose turn started is never made suspendable; the pump's prior-attempt detection blocks the Session (`hosted-monitor-wake-turn.ts:122-171`).
- **3a invalidation filters**: a child notification whose parent run is terminal, and a stopped run's message input, do not spin a wake–load–suspend loop; the dispatcher skips them and the backstop/stop relay clears the row.
- **3a fallback**: with wake-dispatch disabled or the projection missing, behavior is exactly Phase 1 + backstop; no input is lost.
- **3b capture survival**: a background capture in flight when the Session suspends keeps its output (no `producer_lost`), redirecting to staging and resuming loopback on wake; the foreground lane stays fail-stop.
- **3b background suspension**: a Session with a live Monitor or background Shell suspends (including the `heldRuntimeTurns`/cleanup-debt pins removed); the processes keep running under their cgroups; observations stage durably with their bytes; a notification fires a turn on wake; a proven Shell exit settles its Broker execution while suspended via the existing sweep.
- **3b drain order**: the wake drain publishes staged resources before committing records, preserves the manifest chain, and passes the load's receipt verification; it is idempotent by `observationSequence` and commits no rerun.
- **3b mount handback**: a Hook- or MCP-owner Session with a background-only hold suspends without `HostedHookRecoveryRequiredError`/`HostedMcpRecoveryRequiredError`; a genuine foreground owner still refuses the handback.
- **3b reopen**: the load re-attaches to the live executions and restores `heldRuntimeTurns`.
- **3b worker loss**: a worker killed while suspended takes recovery-required, mints no fresh owner, starts no second process, and reconciles or discards orphaned staging under the generation fence.
- **3b reclamation guard**: a suspended Session with live background work is not reclaimed; its MCP owner and storage membership persist until the work ends.
- **Recovery view**: a sealed head with pending scheduled inputs and held background work (and its background-only cleanup ref) reports `ready`; one that owes a Turn, an unheld live execution, or genuine cleanup debt is never `ready`; a skewed projection yields `awaiting_evidence`.
- **Regression**: Phase 1's and Phase 2's existing tests unchanged for Sessions outside the new scope; the non-wake suspension path and the parked-MCP path unchanged.
- **Real-process/MySQL IT**: mirror Phase 1/2 acceptance — run the real Harness + worker + MySQL wake/dispatch/staging/fault matrix at the required CI tier; skipping the Hosted/MySQL gate is not acceptance.
- **Measurement**: §7 proves the constants reasonable and the benefit worth it.

## 10. Open questions

1. The scan period, claim lease, dispatcher page and jitter (chosen by measurement), and whether the due-scan reads the projection table directly or a derived head due-column.
2. Whether the projection is maintained strictly in the commit transaction or batched asynchronously with a bounded lag, if §7.3 shows the hot-path cost is too high.
3. The staging byte bound and retention, the drain batching, and whether the task view needs a staged-output read path beyond the execution-ledger liveness indicator.
4. Whether a notification-worthy staged observation should set the existing wake hint or feed the dispatcher's due-scan directly (one fence vs two).
5. Whether a background run that ends while suspended should wake the Session to commit its terminal revision promptly, or wait for the next load (Shell exit releases the hold either way; the journal record lags).
6. The exact shape of the worker capture rework: a staging fallback inside `RemoteShellCapture` versus a separate background sink, and how the foreground fail-stop guarantee is preserved.
7. The exact shape of the mount-handback tolerance: a suspension-mode flag on the owner close versus a keep-membership arm keyed on the background-only hold.
8. The compaction-aware projection rebuild, once live compaction lands.
9. Whether Phase 4's parked approvals reuse the dispatcher's claim and the projection's currency guard (the held-approval Turn is a different owed-work class).

## 11. Feasibility conclusion

**Worth doing, in two increments; measurement is an enablement gate. 3b is heavier than a single staging endpoint and is sliced accordingly.**

- **3a is mostly assembly of existing parts.** The input contract, the journal-derived pending set, the resident pump, the transport activator, the SQL backstop, the wake verbs, the cold-open cap, the churn cap and the automation ledger's lease/fence pattern all exist. The additions are a commit-time projection table (with dispatcher-side invalidation filters), a due-time dispatcher, and two guard relaxations (eligibility and recovery view). The benefit is removing the residency of every Session pinned only by queued or deferred inputs, and replacing the minutes-late backstop with a seconds-scale due dispatch.
- **3b's crux is the durable commit path while no Harness holds the writer, and it is three mechanisms.** Staging in a Broker ledger with commit-on-wake preserves the single-writer invariant and the recovery proofs, at the cost of a bounded commit lag, a byte-carrying staging drain, a task-view read path, the worker capture-pipeline rework, and the mount-handback tolerance. The worker already owns the processes, the cgroup supervision, the hold ledger, the re-attach path and the execution-settlement sweep; 3b adds worker-side aggregation, the capture rework, the staging route/ledger/drain, and the background guard relaxations.
- **Prerequisites.** Correctness proof of the projection's two-directional staleness, rebuild and invalidation filters; the dispatcher's no-double-run fence; 3b's capture-rework characterization, staging idempotency, drain resource-before-record order, mount-handback tolerance scoping, and generation-fenced orphan reconciliation; the recovery-view widening proved against both addenda; real-process/MySQL fault acceptance; and the §7 measurement.
- **Compatible with Phases 1 and 2.** The eligibility predicate's active-work terms, the teardown order, the parked-MCP reuse, the bounded-recovery proof and the recovery-view lag arm all hold (§6). No new journal kind, no schema change to the journal contract, no second writer. 3b for MCP-owner Sessions depends on Phase 2 parking being enabled.

**Suggested slicing**: (1) wake-input projection + rebuild + invalidation filters + commit-path cost measurement; (2) due-time dispatcher + capability gate + eligibility relaxation + recovery-view widening (3a enablement); (3) worker capture-pipeline rework (fail-stop → buffer-and-redirect) + characterization tests; (4) Broker staging route/ledger carrying bytes + commit-on-wake drain (resource-before-record) + worker-side aggregation; (5) background hold across suspension + mount-handback tolerance + full eligibility-term relaxations + reclamation guard + task-view liveness (3b enablement); (6) real-process/MySQL fault matrix + release-constant selection. A maintenance writer authority and the compaction-aware rebuild are separate follow-up designs.
