## 1. Problem and current state

Phase 1 suspends an idle Session only when it owes nothing: no pending input (including a loop input whose `notBefore` lies in the future), no live background observation, no unsettled work. Phase 2 lets a suspended Session keep its MCP connections parked. Two classes of Session therefore still cannot suspend, and both pay the full resident cost (writer-lease and activation renewal, restored journal state, timers, Harness memory) for work that is not running:

1. **A Session with queued or deferred wake inputs.** A monitor notification, channel message, child-result acceptance, automation fire, session message, PR event, or self-paced loop wakeup that is committed but not yet consumed keeps the Session resident. A loop wakeup armed for an hour from now pins the Harness for that hour.
2. **A Session with a live background Shell or Monitor.** The physical process lives in the Runtime worker, but the observation loop that turns its output into durable records runs in the Harness, and any non-terminal `child_run`/`monitor_run` record blocks suspension outright.

### 1.1 Wake inputs are already durable; only their clock is resident

An input commits as `input.accepted` (`inputId`, `turnId`, `source`, `contentRef`, `deadline`, `admissionRef`, optional `notBefore`) together with an authority-generated `wake.requested`, in one journal transaction. `notBefore` may be an instant, `null`, or absent (`managed-session-records.test.ts:273-285`); an immediate input omits it. It is consumed exactly when a `turn.settled` under the same `turnId` commits; nothing else consumes it. The pending set is therefore derivable from the journal alone, any number of restarts later (`pendingSessionInputs`, `packages/cli/src/serve/hosted-wake-intake.ts:37-68`). The wake sources are `monitor`, `channel`, `child_agent`, `workflow`, `automation`, `session_message`, `loop`, `pr_event` (`JdbcWakeRecoveryStore.SOURCES`, `packages/managed-agent-server/persistence/.../JdbcWakeRecoveryStore.java:29-30`; the Harness classifier `isWakeInputSource`, `packages/cli/src/serve/hosted-harness-session.ts:1616-1627`).

The resident delivery mechanism is the embedded pump `HostedMonitorWakeScheduler` (`packages/cli/src/serve/hosted-monitor-wake.ts:117`). It holds nothing in memory: each pass re-reads the journal, runs the oldest due input as an ordinary text turn, and verifies consumption by re-reading. Busy/blocked Sessions retry on a 500 ms cadence; a held approval wait re-derives on a 15 s cadence; a not-yet-due input is skipped per-input and exactly one deferral timer is armed at the earliest future `notBefore` (`deferIfPending`). A kick (a new arm, a cancel, a load) re-evaluates. The pump is rebuilt on every load (`hosted-harness-session.ts:7693`), and the deferral is per-input, not head-of-line (`hosted-harness-session.ts:7711-7724`). The self-paced loop wakeup that produces `notBefore` is implemented (`hosted-loop-session.ts`; the `shell/3` profile declares `loop_wakeup`), despite its design's stale "proposal" status line.

So the input, its due time, and its delivery are all already durable or re-derivable. What is resident is only the **clock**: the pump and its deferral timer live in the Harness process, and the eligibility predicate refuses to let the process go while any input is pending. The control plane therefore only needs to know **when** to wake a Session, not **which** input is due — the pump re-derives the latter from the journal on load.

### 1.2 The control plane already has two wake paths, neither a due-time scheduler

**Transport fast path (hint-grade).** `JournalCommit.publishJournalAfterCommit` (`persistence/.../JournalCommit.java:305-325`) publishes one envelope per committed event to the per-Session LiteTopic and copies `wake.requested` to a shared wake-bootstrap LiteTopic that every node consumes (`adapters/.../event/LiteTopicEventTransport.java:59-76`). `TransportWakeActivator.onWake` (`control-plane/.../event/TransportWakeActivator.java:118-160`) treats the envelope only as a hint to look at SQL sooner: it re-checks `TransportConsumerStore.wakeFence` (workspace match, `sequence <= committedSequence`, Session open, **no live writer**, Harness available), claims via a CAS watermark `wake_covered_sequence` (`JdbcTransportConsumerStore.java:117-126`) before attempting, and hands the load to a bounded pool (4 threads / 256 queue). A full pool answers `DROPPED`, left to the SQL scan. The load uses `HarnessConnector.activateForWake` (`QwenHostedHarnessConnector.java:1731-1768`), which evicts the stale cached attachment a sealed writer leaves behind and takes the same new-work admission as a Turn. EventTransport delivery is best-effort and never recovery evidence (`contracts/.../event/EventTransport.java:17-19`); TypeScript has no envelope consumer (`packages/core/src/managed-runtime/managed-event-envelope.ts:21-32`).

**SQL backstop (correctness floor).** `WakeRecovery.scan` (`control-plane/.../session/WakeRecovery.java:34-70`) runs every 2 s on a dedicated scheduler, reads up to 8 candidates, and for each: claims, proves the pending set by replaying the journal, stamps the result, and calls `harness.recoverForWake` (a passive load, `QwenHostedHarnessConnector.java:1718-1727`). The claim sets a durable `wake_retry_at = NOW + 30 s` (`JdbcWakeRecoveryStore.claim:113-133`); a proof invocation reads at most 32 journal transactions, one per query, verifying each chunk's digest and sequence continuity (`hasPendingInput`, `PROOF_PAGES = 32`, `JOURNAL_PAGE = 1`, a 128-entry proof cache). The proof already tracks the earliest deferred `notBefore` (`deferredUntil`) and refuses to certify "nothing pending" while a future input exists (`JdbcWakeRecoveryStore.java:249-262`); `recordPending` stamps `is_wake_pending` and the `wake_head_revision` watermark at the proven revision (`:311-319`). Eligibility is an `ACTIVE`, non-retired public Session with an uncompacted journal and an unowned head — `SEALED`, or `ACTIVE` with an expired writer lease (`UNOWNED`, `JdbcWakeRecoveryStore.java:34-35`). The backstop also drops a child Session's wake when its parent run is terminal or stop-requested, clearing the head hint **without** a `turn.settled` (`WakeRecovery.java:52-62`). The boundary design is [Hosted wake recovery after writer loss](2026-10-18-hosted-wake-recovery.md) (#14116/#14603).

**The gap.** Neither path fires promptly at a deferred input's `notBefore`. The transport notice is emitted at **arm time**, when the Session is still resident (`OWNED`, no load); no journal event is committed at fire time. The backstop's deferred latch knows the fire time but is paced by the 30 s claim and the 2 s scan, and proving a long journal takes many 32-page calls. The parent design records the consequence: on a journal of 201 transactions the wake comes at least three minutes after the input is due. The backstop is a crash recovery mechanism, not a general durable scheduler — its own design names "durable incremental proof and catalog cleanup" as remaining capacity work. The fix is a due-time hint the control plane can scan cheaply plus a faster due-prioritized dispatch, **reusing** the existing proof, not a second copy of the pending set.

### 1.3 Background work: the process is already Runtime-owned; the observation is not

A background Shell (`child_run`, `kind=shell`) and a Monitor watch (`monitor_run`) are child processes of the Runtime worker, each under its own delegated cgroup v2 unit whose name derives from the execution identity, so a replacement worker re-attaches by name ([H3 design](2026-10-03-managed-shell-monitor-runtime.md); `ManagedChildRunSupervisor`, `packages/core/src/managed-runtime/managed-child-run-supervisor.ts:129`). Each process holds a non-terminal Runtime execution until its end is proven; a routine Runtime release with a live hold answers `runtime_session_held` and stops nothing (`RuntimeSessionRelease.java:103-145`, refusal at `:133`); only the close drain arm stops it. The hold is durable in the Broker's ledger and restored at load: `heldRuntimeTurns` carries both the promptIds of turns whose Runtime ended held and the Runtime Session ids restored from the Broker's durable hold rows (`hosted-harness-session.ts:959-970`).

What runs in the Harness is the **observation**:

- `HostedMonitorLoop` (`packages/cli/src/serve/hosted-monitor-loop.ts:100`) aggregates the watch's stdout lines into one observation per debounce window. `flush()` (`:387-415`) commits a `monitor_run` revision **plus a notification `input.accepted` (source `monitor`) in the same transaction** through `HostedMonitorSession.observe` (`hosted-monitor-session.ts:184-207`, commit at `:398-410`), then kicks the wake pump. The notification policy is **one notification per accepted observation** (`hosted-monitor-loop.ts:417-435`); `notifiedThrough` is bookkeeping, not a gate. The notification's `inputId`/`turnId` is derived from the observation sequence (`hosted-monitor-notification.ts:77-83`), and the sequence is computed from the previous record at commit time (`hosted-monitor-session.ts:194-205`) — so a replayed observation mints a fresh notification identity unless the staged observation carries a stable one. The watch itself runs in the worker; the Harness-side `HostedMonitorRemoteExecutor` (`hosted-monitor-remote-executor.ts:25-67`) only registers `{onLine, onExit}` on the publisher and asks the worker to stop via the Broker's `monitor-stop` (`managed-monitor-runtime.ts:89-135`).
- Background Shell has no separate loop class; its observation is the `HostedShellPublisher`'s capture forwarding (`fanMonitorLines`, `hosted-shell-publisher.ts:623-664`; `advanceBackgroundManifest` forwards each durable manifest revision to the record).
- The only worker→Harness background-event path is an HTTP POST to a **loopback** server the Harness owns: `HostedShellPublisher` listens on `127.0.0.1:0` with a random 32-byte bearer token (`hosted-shell-publisher.ts:102-193`); the worker's client `rpc()` posts to the descriptor URL (`managed-shell-publisher.ts:72-133`). This server dies with the Harness. Every journal commit it feeds goes through the Harness's writer authority — there is no worker→Store or Broker→journal commit path today (`v3/hooks` is Java→worker dispatch, not a journal writer). The direct path's write handler requires the request to start at exactly the next offset and otherwise calls `sink.failCapture()` (`hosted-shell-publisher.ts:329-338`); it advances the offset on success (`:348`). This is a strict-equality guard, **not** an idempotent accept — a legitimate retransmission at an older offset fails it (§4.4).

Four facts about the worker side bound what 3b must change:

- **The worker's capture is fail-stop on publisher loss, not retry-or-redirect.** `RemoteShellCapture.append` catches any RPC failure and calls `failCapture()` (`managed-shell-publisher.ts:258-280`); once `failed`, later writes are dropped, `finish` marks the stream incomplete, and `finalize` produces `captureStatus:'unavailable'`, `captureReason:'producer_lost'`, `deliveryStatus:'blocked'` (`:340-378`). Closing the loopback publisher on suspension therefore **permanently fails** an in-flight capture today; it does not fall back to anything. 3b must rework this semantics, not merely add a staging endpoint (§4.4).
- **A successful direct write is not yet a durable byte.** The capture buffers into a 1 MiB segment and only publishes when the segment fills (`local-shell-stream-capture.ts:167-180`); a 1 KiB write returns with zero segments published (manifest still revision 1, stdout 0 bytes), yet the publisher answers `accepted` after `sink.write` returns (`hosted-shell-publisher.ts:348-362`). If the worker advances its offset on that ack, a suspension or generation change loses the acknowledged-but-unpublished prefix. 3b must distinguish the **received** position from the **durable-contiguous** position (§4.4).
- **The Broker settles a finished background execution only when an operation triggers its sweep — there is no periodic settler.** `ManagedBackgroundShellRegistry.complete()` drops the hold when the process end is proven and the finalize/accept chain resolves (`managed-background-shell-registry.ts:200-290`, hold drop at `:280-290`), retaining the finished receipt in worker memory until the worker ends (`:64-70`). The Broker's `settleUnprovenBackgroundRows` sweep queries that retained receipt through the worker's status route (`managed-monitor-runtime.ts:113-127`) and settles the execution row — but the sweep is **operation-triggered**: a Session release (`RuntimeSessionRelease.java:85`), the parked-MCP reclamation (`RuntimeBrokerService.java:601`), a maintenance settle (`:1502`), or a drain (`RuntimeDrainCoordinator.java:639`). It is **not a scheduled timer**. A quiet Shell that exits while suspended therefore has no proactive settler: the only periodic path is the incidental parked-MCP reclamation, which §4.5's background-execution refusal blocks, and a pure shell-profile Session with no MCP owner has no periodic trigger at all. 3b must add a proactive settlement trigger that does not reload the Session (§4.4).
- **The cleanup retry reloads the Session for owed debt.** `HostedCleanupRetryCoordinator.retry` calls `harness.recheckRecoveryCleanup` (`HostedCleanupRetryCoordinator.java:126-146`), a load/recheck paced to avoid reloading on every tick. For a background-held Session this is a wake source that defeats suspension; 3b's cleanup scan must recognize Runtime-held background work and not reload it (§4.4, §4.5).

### 1.4 The guards that pin these Sessions

`suspensionLiveWork` (`hosted-harness-session.ts:4981-5032`) blocks on, among the active-work terms, the live monitor loops (`:5015-5020`) and **any non-terminal `child_run`/`monitor_run` record** (`:5021-5029`) — so even a parked `runtime_lost` record or a background Shell with no live loop blocks. For a background run that outlives its turn, two further terms are the actual pins: `session.heldRuntimeTurns.size > 0` (`:5003`) and `hasHostedCleanupDebt` (`:4999`). A shell-profile turn whose `finish()` meets `runtime_session_held` sets `runtimeHeld` (`hosted-workspace-tool-turn.ts:10749-10758`), which adds to `heldRuntimeTurns` (`hosted-harness-session.ts:4531,13038`); a cleanup-hold path adds the held Runtime Session id (`retainHostedCleanupHolds`, `:2771-2782`). A separate `pendingInputs` check in `attemptSuspend` (`:5050-5060`) counts **all** `pendingSessionInputs` over the committed prefix, with no source or due-time filter, and runs twice per attempt (`hosted-session-suspension.ts:232,242`); any pending input reverts and re-arms. This is the check that blocks a future-`notBefore` loop input. The non-wake-owned unsettled inputs are counted separately by `unsettledInputs` (`:5002`), which excludes wake-owned inputs precisely because the pump owns their consumption (`unsettledInputsThrough`, `:2035-2062`; `isWakeOwnedInput`, `:2006-2016`).

The recovery view's `ready` arm requires, beside a sealed writer, released activation, current projection, no active Turn and no unsettled Runtime execution or cleanup debt, a **wake proof of emptiness**: `is_wake_pending = 0` and `wake_head_revision = journal_revision` (`SessionRecoveryService.java:139-156`; [recovery view addendum](2026-11-18-managed-suspension-recovery-view.md) §2-3). The unsettled-work probe names a non-null `runtime_state` DOMAIN row and a `REFERENCED` `HOSTED_CLEANUP` ref (`JdbcSessionRecoveryRepository.java:34-56`). A Session with a pending input is therefore not `ready` by contract, and the addendum names widening this proof as follow-up work.

## 2. Goals and scope

**Goal.** The control plane decides when a suspended Session has a due input and wakes any pool member to run it; the Harness runs the input and suspends again. Observation of background work moves to the Runtime worker and the control plane, so a Session with a background Shell or Monitor can suspend while its processes keep running and keep their records durable.

**Scope, first increment (3a — wake scheduling).** A Session whose only owed work is unattempted wake inputs (queued or deferred) can suspend. A stale-tolerant **head due-time hint** plus a faster due-prioritized dispatcher — both reusing the existing journal proof — replace the minutes-late backstop as the primary wake clock; the transport fast path and the SQL backstop remain as hint and correctness floor. The eligibility and recovery-view guards relax accordingly, with a seal-time per-input unattempted proof that the control plane can re-derive cold. No new table, no background-work change.

**Scope, second increment (3b — Runtime-owned observation, separate follow-up).** The worker aggregates and supervises its background processes; a Broker-side staging ledger holds observations **and their output bytes** durably while no Harness holds the writer; the Harness drains staging on wake (publishing resources before records) and resumes direct delivery. A Session with live background work can suspend; the Runtime hold persists across suspension and is re-attached on reopen. 3b is a capture-state-machine rework plus a staging pipeline with byte-level durability, idempotent retransmission and stable observation identity, a coordinated channel handoff, a proactive settlement trigger with an exited-pending-commit state, a durable binding-scoped staging authorization, and a probe-only/mount-handback teardown tolerance (§4.4–4.5). It is heavy enough to warrant its own design and is not committed to this phase.

**Out of scope (later increments / other phases).**

- Phase 4 parked approvals: a Turn waiting for an approval still pins the Harness (`session.active`/`recoveredTurn`). The pump's 15 s held cadence is unchanged.
- A second journal writer. All journal commits still go through the Harness writer; 3b stages observations in a Broker ledger and commits them on wake rather than introducing a maintenance writer authority (see §5.3).
- A per-input wake projection table. The head hint + proof reuse is the first cut; a per-input index is a later optimization only if measurement shows the on-demand proof replay is prohibitive (§5.1, §7).
- Journal compaction interaction. Live compaction is not enabled today (`compacted_through_revision` advances only for `DELETED` heads in `ManagedSessionRetirementStore`; the TS store refuses a compacted head, `http-managed-session-store.ts:493-495`). The proof's uncompacted-prefix constraint is inherited unchanged; compaction-aware wake proof is separate work.
- Background work on `EXTERNAL` storage, detach of a background process to an independent owner, and cross-host-reboot process attach (H3 already defers these).
- The journal-restore cost that grows with history (parent design: Phase 3 does not eliminate it).

## 3. Cost model (analytical estimate, not measured)

### 3.1 What residency costs these Sessions

The parent design's measured idle cost is 51–56 SQL statements per idle minute per Session on the historical rig (renewal-dominated), plus Harness memory and timers; current constants must be re-measured. A Session pinned by a deferred loop input pays this for the whole deferral (up to the 3600 s clamp, or the 24 h chain). A Session pinned by a background Monitor pays it for the life of the watch. Neither is running a Turn.

### 3.2 What 3a eliminates and adds

Eliminated: the residency of a Session whose only owed work is unattempted wake inputs — it suspends after the idle period and stays suspended until an input is due. The wake itself replaces the minutes-late backstop with a due-time dispatch (target: seconds, bounded by the scan period and the cold-open admission).

Added: one head-column update per accepted wake input (a null-safe minimum decrease of the due-time hint, §4.1); a periodic due-scan over the head hint plus an on-demand proof replay per due candidate (§4.2); a seal-time per-input transcript proof (§4.3); a wake-driven cold open per due batch. The cold-open MCP component is already removed by Phase 2 parked reuse; the remaining cold-open cost is the MCP-free floor plus journal restore. A stale-early hint causes one wasted load that the proof corrects and re-suspends — bounded and harmless. The proof replay is the cost this design trades for simplicity; measurement (§7) gates whether a per-input index is later worth its surface.

### 3.3 What 3b eliminates and adds

Eliminated: the residency of a Session whose only owed work is live background observation. The worker already owns the processes; 3b removes the Harness-side loop and the loopback dependency while suspended.

Added: a Broker staging write per observation batch (debounced ≥1 s, bounded by the 10,000-observation record bound), **carrying the observation bytes and output segments** with a stable observation identity; a drain-then-open wake handoff that publishes staged resources before committing records, tracks received-vs-durable byte positions, and idempotently accepts retransmission; a proactive execution-settlement trigger with an exited-pending-commit state; a task-view read path for staged live state; and the one-time rework of the worker capture pipeline from fail-stop to buffer-and-redirect (§4.4). The notification turn still needs a Harness — 3b does not remove the wake, it removes the residency between wakes. A continuously loud Monitor never goes idle and so never suspends (the idle clock keeps it resident, as today): 3b's residency saving applies to bursty or quiet background work, not to a nonstop stream (§4.4).

### 3.4 Witnesses

- **Residency witness**: `attachedSessions` over a rig of N Sessions each holding one loop input armed at the maximum delay — Phase 1 keeps N resident; 3a suspends N after the idle period and wakes exactly the due ones.
- **Due-latency witness**: arm a loop input at `now + T`, suspend, measure fire-to-turn-start latency against the backstop's ≥3 min on a long journal.
- **Reconnect witness**: Phase 2's `mcp.start` count stays 0 across a 3a wake (parked reuse).
- **Background witness**: a suspended Session's Monitor keeps staging observations and its notification fires a turn on wake; a `cgroup.kill`-proven Shell exit settles its Broker execution while suspended via the proactive trigger (§4.4), without reloading the Session; the capture survives suspension with no `producer_lost` and no lost acknowledged prefix.

## 4. Proposal

### 4.1 A head due-time hint, reusing the existing proof (3a)

The control plane needs a cheap way to find Sessions with a due input. It does **not** need a per-input index: the pump re-derives which inputs are due from the journal on load (§1.1). So 3a adds a single stale-tolerant column to `ma_session_head`, `wake_due_at` (epoch ms; the earliest pending `notBefore`, `0` for immediate, null/absent when nothing pending), maintained like the existing `is_wake_pending` hint but null-safe:

- **On accept, decrease null-safely.** `JournalCommit` already OR-maintains `is_wake_pending` and conditionally advances `wake_head_revision` (`JournalCommit.java:263-264`), and identifies wake inputs in the commit loop (`:175-185`). For the wake inputs accepted in this transaction it normalizes a `null`/absent `notBefore` to `0` and takes the **minimum** over them; it then writes that minimum directly when the head's `wake_due_at` is null, or `LEAST(wake_due_at, min)` otherwise. The normalization is required because MySQL `LEAST` returns NULL if any argument is NULL (verified on 8.4.11: `LEAST(NULL, 3600000) = NULL`), so a naive `LEAST(wake_due_at, notBefore)` would write NULL on the first input to an empty head and let a later immediate input erase an existing future time. The result is monotonic toward earlier, so a newly accepted input is **never missed** (the hint is always ≤ its `notBefore`). It is not increased on settle, so it may be stale-early after the earliest input settles — exactly the staleness `is_wake_pending` already tolerates.
- **On proof, refresh — with a richer proof result.** The backstop's proof already computes the pending set and the earliest deferred `notBefore` (`deferredUntil`), and `recordPending` stamps the head at the proven revision (`JdbcWakeRecoveryStore.java:249-262,311-319`). But today `hasPendingInput` returns `Optional<Boolean>`, where `empty()` conflates "prefix not finished" with "only future inputs remain", and the caller skips `recordPending` on `empty()` (`WakeRecovery.java:44-51`) — so it cannot refresh the head from `0` to a remaining loop's future time `T`. 3a extends the proof to return four explicit outcomes: **prefix-incomplete**, **immediate-due**, **only-future with earliest time T**, and **cleared**. The hint is refreshed (to `0`, to `T`, or cleared) only when the prefix is complete and the head is still at the read revision; an incomplete prefix keeps the old hint and continues reading. The proof remains the correctness floor: a stale-early hint triggers one wasted load that the proof corrects; a hint can never be stale-late, so no due input is lost.

No new table, no per-input commit-path writes, no rebuild, no per-row invalidation. The existing `is_wake_pending`, `wake_head_revision` and generated `is_wake_scan_pending` column (`V1__managed_schema.sql:222-230`, index `idx_ma_head_wake` at `:1474`) keep their roles; `wake_due_at` joins them as another head hint, and the due-scan orders by it.

**Invalidation is the proof's job, as today.** A child notification dropped because its parent run is terminal, or a stopped run's message, is handled by the existing proof: the backstop clears the head hint without a settle (`WakeRecovery.java:52-62`), and the pump skips policy-skipped inputs (`stoppedMessage`, `hosted-harness-session.ts:7687-7691,7706-7710`). Because there are no projection rows, there is nothing to refill a due-page and starve valid Sessions — the invalidated Session's hint is cleared by the proof, and it leaves the candidate set. This is why the head hint is preferred over a per-input table: the table would have needed a separate durable row-cleanup mechanism for exactly these cross-session invalidations.

**Filtering must not drop an input that still owes a writer settle.** "May not call the model" and "still owes a settlement" are different judgments. A stopped `session_message` has the stop relay as its independent settler, so it can leave the candidate set. But an accepted automation or child notification that is cancelled before execution is settled by the wake pump writing a `turn_result` with `state:'cancelled'` (`hosted-monitor-wake-turn.ts:188-206`) — that needs a writer. The dispatcher therefore only removes inputs that have an independent settler or are provably already settled; other cancelled inputs are still dispatched to a path that can write the cancelled result (model calls stay zero). The proof's deliverability filter (§4.2) applies this distinction.

### 4.2 Due-time dispatch (3a)

A new `WakeDispatchJob` on a dedicated `wakeDispatchScheduler` bean follows the house scheduler pattern (named single-thread `ThreadPoolTaskScheduler` + `@Scheduled` fixed delay; no leader election exists or is needed — safety is per-row CAS plus fencing, as the wake claim, the transport watermark and the automation ledger already are). Candidate period 1 s, measured before enablement. Whether to fold this into the backstop scan rather than run a separate job is an implementation choice gated by measurement; the contract below is the same either way.

Each tick:

1. **Scan due — known-and-due only.** The fast scan selects unowned, `ACTIVE` public, non-retired Sessions whose head `wake_due_at IS NOT NULL AND wake_due_at <= NOW`, ordered by `wake_due_at`, bounded page (candidate 8). It does **not** OR-in `is_wake_pending`: a far-future task carries `is_wake_pending = 1` from accept time, so OR-ing it would re-select hour-later tasks every tick (verified on 8.4.11: `wake_due_at <= 100 OR is_wake_pending = 1` selects a `wake_due_at = 3600000` row). Sessions that are pending but whose due time is unknown (hint not yet refreshed) are handled by a separate throttled repair pass or left to the backstop, not the fast scan. A stable cursor pages past the remainder rather than re-reading the same head of the queue. The due-scan index is verified against the actual query plan (§7).
2. **Prove and claim.** Reuse the existing journal proof (with the §4.1 four-outcome result) to confirm a due pending input and refresh the hint; the proof's child-terminal/policy filters drop invalidated candidates before they consume a wake, applying the §4.1 "still owes a settle" distinction. A per-session claim (lease + monotonic fence, the automation ledger's shape) prevents two nodes dispatching one Session at once; the lease is at least the cold-open bound so a slow load does not expire its own claim. The backstop's `wake_retry_at` is left untouched.
3. **Wake.** Call the existing `activateForWake`: it evicts the stale attachment, takes new-work admission, and the Harness's writer acquisition is the activation fence. The load rebuilds the pump, which delivers the due inputs and re-arms the deferral timer for any still-future input. No new Harness verb is required for 3a.
4. **Pace failures.** A transient refusal (`hosted_session_open_busy`, `hosted_session_closing`, pool-ownership waits) retries with backoff under the same churn cap #17681 established (`WAIT_CHURN_BUDGET_FACTOR = 4`, `HarnessCoordinator.java:101`); a definitive refusal records its own code and stops dispatching that Session until the journal advances.

**Burst control and the takeover path.** Wake loads inherit the per-instance cold-open cap (`HOSTED_COLD_OPEN_LIMIT = 8`, `hosted-session-suspension.ts:18`; refusal `409 hosted_session_open_busy`, classified transient in `HarnessConflictCodes.java:23-29`). The placement path has two cases:

- **Sticky route to a reachable owner (the normal case).** A cleanly suspended Session keeps its placement `ACTIVE` on the instance that suspended it. `HarnessPoolConnector.select` routes to that owner without a takeover; the Store re-acquires the writer on the `SEALED` head **immediately** — the lease-lapse guard applies only to an `ACTIVE` head, while a `SEALED` head falls straight through to a generation-incremented re-acquire (`JournalWriterLifecycle.java:257-292`; the seal only sets `state='SEALED'`, leaving `writer_lease_until`, `:399`). So a normal 3a wake is not gated by the writer lease.
- **Cross-instance takeover (owner down or quiescing).** Only when the pool must take the placement over does the `harness_owner_still_live` gate apply: takeover needs the placement `RELEASED` with a release record, or the writer lease lapsed with a known activation (`JdbcHarnessPlacementStore.java:163-171`). This is the crash/reassignment path, not the steady-state wake.

The dispatcher's bounded page, claim lease and jitter keep a synchronized due batch from filling one instance's slots; the churn cap ages out a caller that keeps meeting a full instance.

**Relationship to the existing paths.** The transport activator stays the hint-grade fast path for an immediate `wake.requested` notice on an unowned Session; the dispatcher is the due-time primary for deferred inputs and the reliable path when the transport is off or a notice was dropped; the SQL backstop stays the correctness floor and the hint-refresh trigger. The three share the same wake verbs, the same proof, and the same SQL truth; none is recovery evidence over the journal.

### 4.3 Suspension with pending wake inputs (3a)

The `pendingInputs` gate in `attemptSuspend` is removed **for unattempted wake inputs**, but "unattempted" must be **proved at seal time, not inferred from in-memory state**. The pump's prior-attempt path does not reliably set `session.blocked`: on a takeover load it calls `settleInterrupted`, which can return `'held'` (a durable approval wait) or `'busy'` (a transient channel-recovery fault) **without** setting `blocked`; only the fallthrough sets `blocked = true` and returns `'recovery'` (`hosted-monitor-wake-turn.ts:121-171`). An attempted input whose recovery keeps returning `busy` can therefore cross the idle period with no in-memory flag marking it attempted. So the last suspension check before sealing the writer verifies, at the current revision, that **every pending wake input has no transcript attempt** — the same per-input proof the ownership-release flow already uses (`pending.some(!isWakeInputSource || wakeHasPriorAttempt) → throw`, `hosted-harness-session.ts:4874-4889`). An attempted or under-evidenced input keeps its existing recovery responsibility and blocks suspension. The suspension entry and the recovery-view `ready` (§4.6) share this one unattempted proof, and the proof must be reproducible by the control plane after the Harness leaves (§4.6). The non-wake-owned `unsettledInputs` term (`:5002`) and the active-work guards (`session.active`, `recoveredTurn`, `blocked`) are unchanged.

Teardown is unchanged: `wake.close()` already stops the pump **without settling any input** (`hosted-monitor-wake.ts` `close()`), so the inputs stay pending in the journal and the head hint; `mcp.suspend()` parks (Phase 2); the writer seals last. The idle clock and the bounded admitted-work wait are unchanged. A Session woken by the dispatcher runs its due inputs, and when it goes idle again Phase 1 re-suspends it — now permitted with pending inputs.

**Rollout control and rollback ordering.** Following Phase 2's `mcpParkable` precedent (§5.6 of the Phase 2 design), the control plane advertises a wake-dispatch capability, gated by `qwen.managed-agent.wake-dispatch.enabled` (default off). The Harness relaxes the `pendingInputs` gate only when the capability is advertised; with it off, behavior is exactly Phase 1's. **New-suspension admission is bound to a dispatcher that actually consumes the wake marker**, so a Session is never suspended into a state nothing will wake. Rollback reverses in order: stop admitting new suspensions first, let already-suspended producers finish or hand off, and keep consuming the markers they may still produce; only after the producers have handed off and the backlog is drained does the consumer stop. This covers the window where a Session suspended under the feature produces its first output after the feature is disabled (§4.4 staging marker).

### 4.4 Runtime-owned observation (3b, separate follow-up)

The observation moves to the worker; its durable commit while suspended goes through a Broker staging ledger, and the journal commit happens on wake. This preserves the single-writer invariant the whole recovery proof rests on (§5.3). The byte-retransmission, channel-handoff and raw-byte-retention mechanisms below are the boundary 3b must fit; their exact protocol is finalized in the 3b design.

**Capture rework (the largest change).** Today the worker's `RemoteShellCapture` is fail-stop: any publisher RPC failure permanently fails the capture (`managed-shell-publisher.ts:258-280,340-378`), and `ManagedBackgroundShellRegistry.complete()` delivers the terminal envelope through `sink.finish`/`finalize`/`publisher.accept` (`managed-background-shell-registry.ts:200-290`). 3b changes the **background lane** to buffer-and-redirect: when the loopback publisher is absent or refuses (no Harness), the capture writes its output segments and terminal evidence to the Broker staging route instead of failing, and resumes direct delivery on wake. The aggregation and debounce that `HostedMonitorLoop` does today move into the worker's `ManagedMonitorRuntime`. The foreground lane keeps its fail-stop guarantee. This is a rework of the capture state machine, not a new endpoint beside it, and needs its own characterization tests first.

**Received vs durable byte positions; idempotent retransmission.** A direct `accepted` ack does not mean the bytes are durable: the capture buffers a 1 MiB segment before publishing (§1.3), so an acknowledged prefix may still be only in Harness memory. 3b tracks two positions per stream — the **received** offset (acked to the worker) and the **durable-contiguous** offset (published and committed). The worker retains the bytes between them for retransmission, or the Harness persists them before the handoff; the worker never discards an acknowledged prefix that is not yet durable. Retransmission must be **idempotently accepted**, not rejected: the existing direct write handler fails any request whose offset is not exactly the next one (`hosted-shell-publisher.ts:329-338`), so a legitimate re-send of an already-durable segment (ack lost, worker offset still old) would hit `failCapture`. 3b therefore checks a retransmission that falls within the durable prefix by capture, stream, range and content: identical content returns success with the durable-contiguous position, conflicting content is rejected. On reopen both sides continue from the same confirmed position. A generation switch retains the prior generation's confirmed bytes and refuses further old-generation appends. Cleanup is unified across §4.4/§4.5/§8: a staged or buffered copy is deleted only once it is committed or provably a duplicate of committed bytes — never merely because a generation changed.

**Staging carries bytes; coordinated drain-then-open on wake.** A new Broker maintenance route accepts observation batches and terminal evidence and writes them to a bounded per-run staging ledger holding **the observation bytes and the output segments/manifest chain**, not only metadata: an observation commit publishes a `managed-monitor-observation` resource (`hosted-monitor-session.ts:194-197`) and advances a manifest chain whose lineage is verified (`isToolResultManifestChainLink`, `:215-240`). On wake the Harness drains staging — publishing the staged resources, then committing the `monitor_run` revisions and their notification inputs — and re-opens the direct publisher. Because the worker's writes are queued asynchronously per stream (`managed-shell-publisher.ts:251-272`), a last read-empty can still have in-flight staging requests, and continuous output can keep "fully drained" from completing; so the handoff is a **coordinated freeze**, not a naive drain-then-open: worker, Broker and Harness agree the old path's last position, the Broker closes old-path appends beyond that position, and the Harness drains to the agreed position before opening direct at it. The protocol names who retains and re-sends bytes produced during the switch. The resource-before-record order matters because the load's recovery pass verifies every `tool.receipt` manifest against the publication owner (`hosted-harness-session.ts:3196-3225`). The staging bound mirrors the 10,000-observation record bound.

**Stable observation identity; staging rows are the wake marker.** The first observation reaches staging before any journal `input.accepted` exists, and the old journal hint cannot signal it — the backstop clears `is_wake_pending` when the journal has no pending input (`WakeRecovery.java:44-51`, `JdbcWakeRecoveryStore.java:249-262`). So the dispatcher scans the staging ledger's **uncommitted notification rows directly**; committing a row removes it, which is the clear. No separate marker column or second fence is needed. But the journal commit and the staging-row removal are two steps, and a crash between them must not duplicate the delivery: today the notification `inputId`/`turnId` is derived from the observation sequence computed at commit time (`hosted-monitor-notification.ts:77-83`, `hosted-monitor-session.ts:194-205`), so a replay would mint a fresh identity that byte-digest dedup cannot catch. Each staged observation therefore carries a **stable identity** that determines a replayable journal `commandId` and notification `turnId` (equivalently, the committed staging position is persisted with the journal transaction), so a re-drain after a crash settles the same observation and notification exactly once. The policy is one notification per accepted observation (§1.3), so every staged batch is notification-worthy; one wake drains the whole backlog and the pump delivers the notification turns serially. While resident, the worker posts to the re-established loopback publisher as today. A continuously loud Monitor stays resident via the idle clock (no saving, no regression); the saving is for bursty or quiet work.

**Raw payload is a durable source, not just a cache.** Staging holds the **raw observation payload** durably from the Broker's persistent ack until the corresponding content is committed to the journal (or a provably identical committed copy exists). In the window where the worker has released its copy after the durable ack but the Harness has not yet published the resource and committed the revision, staging may be the **only** copy of the raw bytes — so it is a durable holding area for uncommitted raw data, not merely a rebuildable cache (§5.3). The **derived index** (notification rows, manifest references) is rebuildable from the retained raw payload. Retention and deletion are defined separately for raw payload (keep until committed or provably duplicate) and derived index (rebuildable); a control-plane restart rebuilds the derived index from the raw payload and still reads back the full payload, committing the observation and notification exactly once before the raw copy is cleaned.

**Proactive execution settlement without a reload.** A quiet Shell that exits while suspended has a retained worker receipt but no operation to trigger the Broker's sweep (§1.3). 3b adds a proactive trigger: a terminal staging write asks the Broker to verify the exit evidence and idempotently settle the execution row (reusing `settleUnprovenBackgroundRows`'s observe-and-settle logic, driven by staging rather than by a release), or a dedicated background job discovers proven exits. The hold releases and the task view updates within a bounded latency, **without loading the Session**. The cleanup retry scan must recognize a Runtime-held background run and not reload it (`HostedCleanupRetryCoordinator.java:126-146`); a background-only hold is not a recovery debt. The terminal record revision is still committed on the next wake, so the journal record lags the execution ledger until wake; the interval is bridged by an explicit **exited-pending-commit** state (§4.6) proven by the Broker exit receipt, so the task view shows the exit, the recovery view does not treat the stale non-terminal record as live work, and cleanup does not reload — all converging within a bounded latency (or a bounded maintenance load commits the terminal revision).

**Durable binding-scoped staging authorization.** The staging route must be fenced, but a short-lived per-operation `OperationGrant` is the wrong shape for long-lived background observation: its lease is capped at 300 s (`maxLeaseDurationMs = 300_000`, `managed-extension-record.ts:35-38`), a same-revision renewal may only increase `expiresAt` (`:617-622`), and the Runtime gate's revocation state lives in process memory and is lost on restart (`managed-operation-grant-gate.ts:45-54`). A Monitor quiet longer than the lease would be refused, and a restarted Runtime could not verify revocation. 3b instead uses a **binding-scoped, durable staging authorization** (the same shape as an MCP owner's persistent membership): tied to the Session's Runtime binding and generation, valid for the life of the background run, revoked on generation change. It must name an issuer/renewer reachable **without a full Session load**, and a **durable record** the Broker checks for tenant, Session, operation, generation and revocation (so a restart re-verifies from SQL, not memory); it must also say who retains bytes not yet durably acknowledged across a renewal. The invariant: a same-generation worker can always stage and deliver after a quiet period without a renewal round-trip, while a revoked or superseded generation cannot append. The exact authorization shape is a named design decision (§10).

**Task view while suspended.** The execution ledger already projects live `runtime_state`; the public task view reads it for liveness and reads output from the committed Artifact plus the bounded staging tail. First cut accepts that the journal-record state lags until wake; the live indicator comes from the execution ledger (and the exited-pending-commit state once the hold releases). A fuller staged-output read path is a follow-up if measurement demands it.

**Rollout control.** A separate gate `qwen.managed-agent.runtime-observation.enabled` (default off) plus a worker capability advertisement; the Harness relaxes the background terms of `suspensionLiveWork` only when both the control plane and the worker advertise observation. With it off, background-work Sessions stay resident as today. Rollback follows the same ordering as §4.3: stop new background suspensions, let producers finish/hand off, keep consuming their staging markers, drain, then stop the consumer.

### 4.5 Background hold across suspension (3b)

**The full eligibility-term set, with per-run evidence.** When observation is advertised, 3b removes every term that pins a Session solely for background work: the live monitor loops (`:5015-5020`), the non-terminal `child_run`/`monitor_run` records (`:5021-5029`), **and** the background-hold terms `session.heldRuntimeTurns.size > 0` (`:5003`) and the cleanup debt owed solely to a background hold (`hasHostedCleanupDebt`, `:4999`). The exemption is **per-run, not per-domain**: `child_run` carries `shell`, `child_agent` and `workflow` kinds (`MANAGED_SESSION_ENABLED_CHILD_RUN_KINDS`, `managed-session-records.ts:199-203`), and a non-terminal record may be `runtime_lost`. Only a `child_run(kind=shell)` or `monitor_run` that passes the same evidence check the cleanup path already uses — matching Runtime Session, binding and generation, a start receipt, and a live run state (`hasBackgroundHoldEvidence`, `hosted-turn-cleanup.ts:257-296`) — is exempt. A `child_agent`/`workflow` run, a `runtime_lost` record, or a Shell bound to an old generation is not background observation and still blocks. Suspension eligibility and the recovery-view `ready` (§4.6) use this one shared per-run condition. A cleanup debt owed to a genuinely unreleased foreground owner still blocks. Every active-work, recovery, stream, client-files and lifecycle term stays.

**Teardown must be probe-only for background holds, not a drain.** The processes are the Runtime's and the hold is the Runtime's; the Harness leaving changes neither, and teardown must not stop or drain background work. But the existing suspension teardown actively drains on **two** paths:

- `retryHostedCleanup(session, broker, true)` passes `drain=true` (`hosted-harness-session.ts:5093-5098`), reaching `broker.release({drain:true})` and the Broker's stop branch for live rows (`RuntimeExecutionRecovery.java:330-343`).
- `releaseLeaseNow(session, terminal, rethrowOnFailure)` — whose second argument is `terminal`, **not** `drain` — internally calls `releaseHeldRuntime(session, {...}, lease, true, terminal)` with `drain=true` (`hosted-harness-session.ts:11332-11358`; the `releaseHeldRuntime` signature's fourth parameter is `drain`, `:11219-11224`). Its return handling also throws on any outcome other than `released`/`deferred` (`:11353-11355`), so a background `held` outcome is treated as a cleanup failure even if draining were disabled.

3b therefore defines a **probe-only release** for suspension covering both paths: it observes and retains the background holds verified to belong to this Session's current binding, generation and run, stops nothing, and **accepts a `held` outcome as a successful suspension** when (and only when) the Broker confirms the hold is such a background hold. Foreground cleanup debt still blocks suspension; an explicit close still runs the terminate/drain path. (This corrects the author's earlier reply, which misread `releaseLeaseNow`'s `false` argument as `drain=false`; it is `terminal=false`, and the path does drain.)

**Teardown must also tolerate the mount handback.** The owner close actively hands the mount back, and that handback refuses while a background execution is live:

- A Hook-configured Session's `hooks.close({terminal:false})` calls `releaseMount` (`hosted-hook-session.ts:2066-2095`), and `releaseMountAfterSweep` refuses `runtime_session_busy` for any active background execution under the owner, with no exclusion (`RuntimeExecutionRecovery.java:388-395`), raising `HostedHookRecoveryRequiredError` and failing the teardown.
- An MCP-profile Session whose turn Runtime is the MCP owner parks via `mcp.suspend()` only when parking succeeds; otherwise `closeResources({terminal:false})` calls the same refusing `releaseMount` (`hosted-mcp-session.ts:1143-1146,1296-1305`). **3b for such Sessions therefore depends on Phase 2 parking being enabled**, or on the same tolerance below.

3b adds a suspension-mode handback tolerance: when the only thing holding the mount is a live background execution of this Session (per-run evidence above), the non-terminal close keeps the membership (as Phase 2's park does) instead of treating the refusal as recovery-required. The close-path audit must pin both the probe-only drain and this tolerance so a later detach change cannot silently stop background work on suspension.

**Reclamation guard.** A suspended Session with live background executions must not be reclaimed. The Runtime Session release is already fenced by the execution ledger (`runtime_session_held`/`runtime_session_busy`, `RuntimeSessionRelease.java:103-145`), so `RuntimeRetentionJob` and a full release leave it alone. The Phase 2 MCP parked-owner reclamation is **not** automatically covered: its `hasPendingWork` guard is MCP-scoped (`managed-mcp-runtime.ts:765-779`) and does not name background executions, which live in the execution ledger. 3b adds an explicit background-execution refusal to the parked-owner reclamation eligibility, and verifies the mount-membership release is fenced by the same hold. This refusal also removes the incidental periodic sweep the reclamation used to trigger, which is why the proactive settler (§4.4) is required. Live background work bounds the park until it ends.

**Reopen.** The load re-attaches to the live executions through H3's replay-tolerant start attachment; `heldRuntimeTurns` is restored from the Broker's durable hold rows (`:959-970`), so the reopened Harness owes the hold exactly until close, as today.

**Worker loss while suspended.** A Runtime generation change leaves the Session recovery-required, the processes unproven and their holds blocked; no fresh owner is minted and no second process starts — the same contract Phase 2's `workerKillWhileIdleNeverMintsAFreshOwnerOnMySql` fault gate pins for parked MCP. Staged observations orphaned by the lost generation are reconciled or discarded under the generation fence on the next load, never committed as a rerun; acknowledged-but-durable bytes are retained per §4.4, only provably duplicate or committed copies are removed.

### 4.6 Recovery-view contract update

The `ready` arm's wake-emptiness guard is replaced by **proof currency plus an unattempted-input proof**, and (3b) a per-run background carve-out plus an exited-pending-commit state:

- **Currency reuses the existing watermark, but equality alone is not the proof.** `wake_head_revision == journal_revision` means "the head hint was evaluated at this revision" — yet `JournalCommit` advances `wake_head_revision` when the old watermark equals the old revision **without a replay** (`JournalCommit.java:261-265`), and the seal only writes `SEALED` (`JournalWriterLifecycle.java:395-401`). So watermark equality can hold without any proof of the pending inputs' attempt state. 3a keeps the watermark as a currency condition but drops the `is_wake_pending = 0` emptiness requirement: a pending unattempted wake input is scheduled work, not owed-uncertain. A lagging or incomplete proof keeps the conservative answer.
- **Admitted pending inputs must be provably unattempted, with a cold-reproducible evidence source.** The Harness-side check reads the transcript (`wakeHasPriorAttempt`, `hosted-harness-session.ts:4874-4889`), but after the Harness suspends and leaves, the control-plane `inspect` reads the SQL head (`SessionRecoveryService.java:139-153`), not the transcript. The unattempted proof must therefore be reproducible by the control plane: either re-derived per pending input from the complete committed records, or persisted at successful suspension as a credential bound to the final revision and writer generation. A seal after a refused load, and any later commit, must not reuse a stale credential. Both the seal-time suspension check (§4.3) and the `ready` guard use this one proof; an attempted-but-unsettled input keeps the conservative answer. This is necessary because the pump's in-memory `blocked` flag is not a reliable attempt marker (§4.3) and watermark equality is not an attempt proof.
- **(3b) Per-run background carve-out.** A background run that passes the shared per-run evidence check (§4.5) no longer blocks `ready` through its non-null `runtime_state`, and a cleanup debt owed solely to such a hold no longer blocks through its `REFERENCED` `HOSTED_CLEANUP` ref (`JdbcSessionRecoveryRepository.java:34-56`). The exception is exactly the exempt set, not the whole domain.
- **(3b) Exited-pending-commit state.** Between the Broker releasing a background hold (proven exit) and the journal committing the terminal revision, the database may still hold a non-terminal run or cleanup ref. A Broker-exit-receipt-proven **exited-pending-commit** state lets the task view show the exit, the recovery view stop treating the stale record as live work, and cleanup stop reloading; an old-generation receipt cannot change the current run's state. The state converges within a bounded latency (or a bounded maintenance load commits the terminal revision).
- The other guards are unchanged: no active Turn, no genuinely owed cleanup debt, sealed writer, released activation, current activation projection. A sealed head that cannot prove these keeps the conservative answer; nothing is relabelled healthy on cache absence.

This is the widening the [recovery view addendum](2026-11-18-managed-suspension-recovery-view.md) §3 names as follow-up work. The [bounded recovery addendum](2026-11-18-managed-suspension-bounded-recovery.md)'s proof is unaffected: it relies on writer fencing (lease expiry → generation + 1), not on "sealed ⟹ resources released"; 3b leaves background resources under Runtime care, the same shape as the crash-recovery branch the proof already declares.

## 5. Design decisions and rationale

### 5.1 A head due-time hint, not a per-input projection table

The control plane only needs to know **when** to wake a Session; the pump re-derives **which** input is due from the journal on load. A per-input table would duplicate information the journal already holds and the pump already re-derives, and would add commit-path per-input writes, a rebuild path, and a durable cross-session row-cleanup mechanism (the backstop clears a dropped child's head hint, not a projection row). A single head hint avoids all of that. The earlier objection — "a head column cannot be decremented on settle" — dissolves once the column is a **stale-tolerant hint** rather than an exact projection: accept only decreases it null-safely (never late), and the existing proof (extended to a four-outcome result) refreshes it (corrects stale-early). This is precisely how `is_wake_pending` already works. The tradeoff is an on-demand proof replay per due candidate; measurement (§7) gates whether a per-input index is later worth its surface to avoid that replay. Simplicity first; the table is speculative until measured.

### 5.2 A dispatcher beside the backstop, not a replacement

The backstop is the correctness floor and the hint-refresh trigger; removing it would make the hint a single point of failure for discovery. The dispatcher is the due-time primary; the transport stays the hint fast path. Three mechanisms, one proof, one SQL truth, one journal authority — the same layering the wake-recovery design already uses for MQ-over-SQL. The dispatcher reuses the existing wake verbs, proof and admission, so it adds no new Harness contract for 3a.

### 5.3 Staging, not a maintenance writer

The single-writer invariant is what makes the recovery proof work: two Harnesses advancing one Session would diverge and duplicate side effects. A maintenance writer authority that lets the Broker or worker commit `monitor_run` revisions directly to the journal would need a new fencing story against the writer generation and would touch the H0c authority rules and both recovery proofs. Staging keeps every journal commit under the Harness writer. The Broker ledger is a **durable holding area for uncommitted raw observation bytes plus a rebuildable derived index** — not merely a rebuildable cache like the automation ledger: until the Harness publishes the resource and commits the revision, staging may hold the only copy of the raw payload (§4.4), so the raw bytes are retained until committed or provably duplicate, and the derived index is rebuildable from them. The cost is real and named: a bounded commit lag, a byte-carrying coordinated drain-then-open handoff with received-vs-durable positions, idempotent retransmission and stable observation identity, staging rows as the wake marker, a proactive settlement trigger with an exited-pending-commit state, a durable binding-scoped authorization, a task-view read path, and the one-time capture-pipeline rework (§4.4). The benefit is that 3b does not reopen the single-writer safety project. A maintenance writer is a later increment only if the lag proves unacceptable.

### 5.4 The hold persists; suspension is not a drain

Background processes belong to the Runtime, not the Harness. Stopping them on suspension would cancel the user's work — the same reason Phase 1's suspension does not reuse the detach close path. The hold is already durable in the Broker and restored at load; 3b lets it span suspension unchanged, makes the suspension teardown probe-only (accepting a verified background `held`) and tolerant of the owner mount handback (§4.5), and bounds reclamation by it.

### 5.5 No new journal kind; the contract is closed

The journal kind vocabulary is frozen on both TS and Java sides (`managed-event-envelope.ts`; `ManagedEventEnvelopes`). 3a adds no event: the head hint is SQL-side, derived from existing `input.accepted`/`turn.settled`. 3b commits the existing `monitor_run` revisions and `input.accepted` notifications on wake; staging is a Broker ledger, not a journal record. The `notBefore` field is already in the closed `input.accepted` schema (the loop wakeup design added it), so no schema change is needed for due time.

### 5.6 Capability-gated rollout

Phase 1 chose no configuration switch; Phase 2 introduced `mcpParkable` as rollout control because parking changes resource lifetime. Phase 3 changes which Sessions may suspend and who owns their clock and observation, so it follows Phase 2: a control-plane capability for wake dispatch and a worker capability for observation, both default off, both required before the Harness relaxes the corresponding guard. New-suspension admission is bound to a live consumer, and rollback drains producers before stopping the consumer (§4.3, §4.4). A deployment without the capability behaves exactly as the prior phase.

## 6. Interaction with Phases 1 and 2

- **Eligibility predicate.** 3a removes the `pendingInputs` gate for unattempted wake inputs, proved at seal time per input (§4.3); 3b removes the live-loop, non-terminal-background-record, `heldRuntimeTurns` and background-only cleanup-debt terms, each by the shared per-run evidence check (§4.5). Every active-work, recovery, stream, client-files and lifecycle term stays, as does cleanup debt owed to a genuine foreground owner.
- **Teardown order.** Unchanged in sequence: wake → owners (park) → lease + cleanup → publishers → writer seal → stopLocal. 3a's `wake.close()` already settles nothing. 3b's teardown is probe-only for background holds (no drain stop, accepting a verified `held`), tolerates the owner mount handback for a background-only hold (§4.5), and the publisher close stops only the Harness-side forwarding while the worker capture redirects to staging (§4.4).
- **Parked MCP owners.** A 3a wake takes Phase 2's reuse path (acquire → status → revalidate → replace-then-retire); the `mcp.start` reconnect witness stays 0. A Session with both parked MCP and live background work parks its MCP and holds its background; reclamation of the MCP owner is refused while background work is pending (§4.5). 3b for an MCP-owner Session depends on Phase 2 parking being enabled.
- **Bounded recovery.** The #8 proof holds: writer fencing, not resource release, is its premise. A failed 3b teardown follows the existing drain-failure path; background holds persist as blocked, never silently released.
- **Recovery view.** §4.6 widens `ready`; the lag arm (`awaiting_evidence` on a skewed activation projection) and the conservative fall-through are unchanged.

## 7. Measurement plan (enablement gate)

The parent design requires measurement before enablement; §3 is an estimate. Extend the Phase 2 measurement rig (or the WP3 rig it builds on):

1. **Residency**: N Sessions each with one loop input armed at the maximum delay (the 3600 s clamp); measure `attachedSessions` and renewal SQL before/after 3a, and the wake fan-out when they become due together.
2. **Due latency**: fire-to-turn-start for a deferred input on journals of 1/40/200+ transactions, dispatcher vs backstop; choose the scan period and claim lease (lease ≥ cold-open bound). Include the starvation case: 8 invalidated candidates ahead of a valid one (the proof must clear them, not page them repeatedly).
3. **Proof-replay cost and scan selectivity (the simplicity tradeoff)**: on-demand proof replay cost per due candidate at catalog scale, the head-hint commit-path cost, and the fast-scan candidate count / replay count / immediate-task latency with many far-future Sessions plus a few unknown-time pending ones (far-future Sessions must leave the fast scan before due; unknown-time ones run on a separate budget). Verify the due-scan index against the actual query plan. This is the measurement that decides whether a per-input index (§5.1) is later worth its surface; the head hint ships first.
4. **Cold-open burst**: synchronized due batch against `HOSTED_COLD_OPEN_LIMIT`; choose dispatcher page/jitter and confirm the churn cap ages out a saturated caller.
5. **Background (3b)**: staging write rate and byte volume under a loud Monitor; coordinated drain-then-open handoff cost and convergence under continuous output; notification latency and wake coalescing; the loud-monitor residency boundary; proactive Shell-exit settlement latency while suspended (no Session reload) and exited-pending-commit convergence; capture survival across suspension and across an ack-loss/drain handoff with a sub-segment (1 KiB) acknowledged prefix (no `producer_lost`, no lost bytes, invariant digest); idempotent retransmission of a durable segment (one copy, capture still usable) and rejection of conflicting content at the same offset; stable-identity replay after a crash between commit and marker-clear (exactly one notification); raw-payload read-back and derived-index rebuild after a control-plane restart before journal commit; durable binding-scoped authorization after a quiet period exceeding 300 s and after a Runtime restart; task-view staleness bound.
6. **Reconnect witness**: `mcp.start` stays 0 across 3a/3b wakes (Phase 2 reuse).

Outputs choose the shipping constants (scan period, claim lease, dispatcher page, staging bound, settlement latency bound) and confirm the benefit is worth the added cost.

## 8. Constraints and risks

- **Head-hint null safety and staleness.** `LEAST` with a NULL argument returns NULL, so the accept-time minimum must normalize `null`/absent `notBefore` to `0` and handle an empty head; otherwise the first input writes NULL or an immediate input erases a future time. The hint may be stale-early (one wasted load, proof-corrected) but never stale-late. The proof refresh and the backstop floor must be exercised, not assumed.
- **Proof result must distinguish future-only from incomplete.** `Optional<Boolean>.empty()` conflates "prefix incomplete" with "only future inputs"; the four-outcome result is required to refresh the hint to a remaining future time without clearing it prematurely.
- **Proof-replay cost.** The head hint trades a per-input index for an on-demand proof replay per due candidate. At catalog scale this is the cost measurement (§7.3) gates; a per-input index is the fallback if it is prohibitive, not the first cut.
- **Fast-scan selectivity.** OR-ing `is_wake_pending` into the due predicate re-selects far-future tasks every tick; the fast scan must select known-and-due only, with unknown-time pending Sessions on a separate throttled budget.
- **Cold unattempted proof.** Watermark equality is not an attempt proof (the watermark advances without a replay); the control plane must re-derive the per-input attempt from committed records or use a suspension credential bound to revision + generation, and a refused-load seal must not reuse a stale credential.
- **Attempted-input proof at seal.** The pump's `blocked` flag is not a reliable attempt marker (held/busy branches); suspension must prove unattempted per input at seal, shared with `ready`. A missing proof lets an attempted input suspend and double-run.
- **Cancelled inputs still owe a settle.** Filtering must distinguish "no model call" from "no writer settle owed"; a cancelled automation/child notification still needs a writer to commit its cancelled result.
- **Capture-pipeline rework (3b).** The worker capture is fail-stop today (§1.3); turning the background lane into buffer-and-redirect while keeping the foreground lane fail-stop is the largest 3b change and the most likely source of output-loss or double-delivery regressions. It needs its own characterization tests before the staging route is wired.
- **Ack ≠ durable; retransmission must be idempotent (3b).** A sub-segment write is acked before it is published; the received-vs-durable distinction and retransmit retention are required or an acknowledged prefix is lost. The existing offset guard rejects retransmission, so 3b must idempotently accept identical content within the durable prefix and reject conflicts. Cleanup deletes only committed or provably-duplicate copies.
- **Coordinated channel handoff (3b).** A naive drain-then-open races the worker's async in-flight appends; the handoff needs a three-party agreed last position, a Broker fence on old-path appends beyond it, and a named retainer/re-sender for bytes produced during the switch.
- **Stable observation identity (3b).** A crash between journal commit and staging-row clear must not mint a new notification identity; the staged observation's stable identity (or committed-position persistence) is what makes the re-drain idempotent.
- **Raw payload is a durable source (3b).** Staging may hold the only copy of uncommitted raw bytes; it is not merely a rebuildable cache. Raw payload is retained until committed or provably duplicate; the derived index is rebuildable from it.
- **Staging wake marker and rollback (3b).** The old journal hint cannot signal a staged observation; the dispatcher scans staging's uncommitted rows. New-suspension admission must bind to a live consumer, and rollback must drain producers before stopping the consumer, or a suspended producer's first output is stranded.
- **Proactive settlement and exited-pending-commit (3b).** The Broker sweep is operation-triggered, not periodic; without the proactive trigger a quiet exit's hold lingers and the cleanup retry reloads the Session. The exited-pending-commit state must bridge hold-release to journal-commit so the task view, recovery view and cleanup converge without reload.
- **Mount-handback and drain tolerance (3b).** Both suspension drain paths (`retryHostedCleanup(drain=true)` and `releaseLeaseNow`→`releaseHeldRuntime(drain=true)`) stop a live background execution, and the latter throws on `held`; the probe-only release must accept a verified background `held`, and the keep-membership tolerance must be scoped to a background-only hold. MCP-owner Sessions depend on Phase 2 parking being enabled.
- **Durable binding-scoped authorization (3b).** The per-operation grant's 300 s cap, same-revision renewal constraint and in-memory revocation make it unfit for long-lived observation; the binding-scoped authorization needs a no-load issuer and a durable verification record that survives Runtime restart.
- **Staging lag and orphan (3b).** Observations are durable in staging immediately but in the journal only on wake; the task view reads the execution ledger for liveness. A lost worker generation orphans staged observations; the generation fence reconciles or discards them, never commits a rerun, and retains acknowledged-durable bytes. The 10,000-observation bound applies to staging as to the record.
- **Background bounds the park (3b).** Live background work refuses MCP reclamation and holds storage membership; a long-lived Monitor delays maintenance until it ends.
- **Cold-open burst.** Synchronized wakes can overload the shared Session Store even when each instance caps its opens; the churn cap and dispatcher pacing are the mitigation.
- **Close-path coupling.** Suspension reuses part of the detach close path; 3b's probe-only drain and mount-handback tolerance must pin every line of the close-path audit so a later detach change cannot silently stop background work on suspension.
- **Single-writer preserved.** 3b deliberately does not introduce a second writer; any future maintenance-writer increment must revisit both recovery proofs and the H0c authority rules.

## 9. Validation and acceptance

- **3a suspension**: a Session whose only owed work is an unattempted queued or deferred wake input suspends after the idle period; its writer seals, activation releases, renewal stops, and the recovery view reports `ready` with the proof currency current and the inputs provably unattempted.
- **3a head-hint null safety**: an empty head receiving a first deferred input `T` then an immediate input (no `notBefore`) reads back `T` then `0`; a single transaction accepting several inputs sets the head to their earliest time.
- **3a proof refresh**: a Session with both an immediate input and a loop at `T`, after settling the immediate input and replaying a journal of more than 32 transactions, does not clear the hint at the first batch boundary, writes `T` after the complete replay, and delivers once at `T`.
- **3a due dispatch**: a deferred input fires within the measured latency bound of its `notBefore` (not the backstop's minutes); an immediate input committed while suspended is dispatched; an overdue input fires exactly once late; no catch-up count. A normal wake to the reachable owner is not gated by the writer lease (§4.2).
- **3a fast-scan selectivity**: with many hour-later Sessions, one immediate task and a few unknown-time pending ones, far-future Sessions leave the fast scan before due, unknown-time ones run on a separate budget, and the immediate task's latency stays within bound.
- **3a no double run**: two racing dispatchers (or dispatcher + transport + backstop) load one Session once per wake; the writer acquisition fences; the input settles once under its `turnId`.
- **3a attempted work stays resident**: a channel input with a prior transcript attempt whose recovery keeps returning `busy` across the idle period does not seal the writer; it stays on the recovery path and the dispatcher starts no second turn.
- **3a cold unattempted proof**: two Sessions both `SEALED + released` with watermark equal to journal revision — one a normal suspension with unattempted inputs, one attempted with a refused load — after a control-plane restart, only the former returns `nextTurnAllowed=true`.
- **3a invalidation and no starvation**: a child notification whose parent run is terminal, and a stopped run's message input, leave the candidate set via the proof and do not spin a wake–load–suspend loop; with 8 invalidated candidates ahead of a 9th valid due Session, the 9th starts within the dispatcher's bound.
- **3a cancelled settle**: an automation and a child notification accepted then cancelled before execution, with transport off, produce zero model calls and exactly one cancelled settle each, and leave the candidate set within the bound.
- **3a fallback / rollback**: with wake-dispatch disabled, behavior is exactly Phase 1 + backstop; disabling the feature after a Session suspends still delivers its first output once within the bound (consumer drains before stopping).
- **3b probe-only suspension**: a background Shell and a Monitor each with an owed cleanup record, and a Session with `runtimeLeaseHeld`, suspend; the original processes keep running, the original holds remain, the stop-call count is 0; an explicit close afterwards still terminates them through the normal close drain.
- **3b first observation**: with transport off and the journal empty, a single staged observation still wakes the Session via the staging-row scan even if the old backstop scans first, and delivers exactly one notification within the bound.
- **3b acknowledged prefix durability**: a 1 KiB direct write acked with stdout still open, then an immediate suspension and generation switch, reads back all 1 KiB in order on reopen with invariant manifest and digest; old-generation appends are refused.
- **3b idempotent retransmission**: a segment durably written then its ack dropped, re-sent identically, leaves exactly one copy and the capture still accepts the next segment; the same offset with different content is rejected and the committed prefix stays intact.
- **3b coordinated handoff**: pausing the Harness between the last read-empty and opening direct, letting an in-flight staging append arrive, then resuming with continuous output, completes the switch within the bound with correct final byte order/digest, one notification per observation, and no staging residue.
- **3b stable-identity replay**: terminating the Harness after the observation and notification commit but before the staging marker clears, then restarting and re-scanning, yields exactly one observation and one notification turn, the marker clears, and the next observation delivers normally.
- **3b raw-payload rebuild**: after a durable staging ack but before journal commit, making the worker unavailable and restarting the control plane to rebuild the derived index still reads back the full payload and commits the observation and notification exactly once before the raw copy is cleaned.
- **3b capture survival**: a background capture in flight when the Session suspends keeps its output (no `producer_lost`), redirecting to staging and resuming loopback on wake; the foreground lane stays fail-stop.
- **3b background suspension**: a Session with a live Monitor or background Shell suspends (including the `heldRuntimeTurns`/cleanup-debt pins removed by per-run evidence); the processes keep running under their cgroups; observations stage durably with their bytes; a notification fires a turn on wake.
- **3b proactive settlement / exited-pending-commit**: a quiet long task is not repeatedly woken by the cleanup scan while running; after it naturally exits, the Broker releases the hold and the task view shows the exit within the bound, with no Session access and no release request; during the hold-release-to-journal-commit interval the task view, recovery view and cleanup converge, and an old-generation receipt cannot change the current run's state.
- **3b drain order**: the wake drain publishes staged resources before committing records, preserves the manifest chain, and passes the load's receipt verification; it is idempotent and commits no rerun.
- **3b mount handback**: a Hook- or MCP-owner Session with a background-only hold suspends without `HostedHookRecoveryRequiredError`/`HostedMcpRecoveryRequiredError`; a genuine foreground owner still refuses the handback.
- **3b per-run exemption**: `child_agent`, `workflow`, `runtime_lost`, and an old-generation Shell are not exempt; only a `child_run(kind=shell)`/`monitor_run` with a current hold and receipt is, in both suspension eligibility and `ready`.
- **3b authorization**: a Monitor silent beyond 300 s then emitting its first line stages and delivers on the same-generation worker (no renewal round-trip); after a generation switch or revocation and a Runtime restart, the old worker's appends are refused while confirmed bytes remain readable.
- **3b reopen / worker loss / reclamation guard**: the load re-attaches and restores `heldRuntimeTurns`; a worker killed while suspended takes recovery-required, mints no fresh owner, starts no second process, and reconciles or discards orphaned staging while retaining acknowledged-durable bytes; a suspended Session with live background work is not reclaimed.
- **Recovery view**: of three Sessions otherwise identical — (a) proof-current, unattempted deferred input, (b) attempted-but-unsettled input with a refused load, (c) lagging proof — only (a) returns `nextTurnAllowed=true`; a sealed head with held background work and its background-only cleanup ref reports `ready`; a skewed projection yields `awaiting_evidence`.
- **Regression**: Phase 1's and Phase 2's existing tests unchanged for Sessions outside the new scope; the non-wake suspension path and the parked-MCP path unchanged.
- **Real-process/MySQL IT**: mirror Phase 1/2 acceptance — run the real Harness + worker + MySQL wake/dispatch/staging/fault matrix at the required CI tier; skipping the Hosted/MySQL gate is not acceptance.
- **Measurement**: §7 proves the constants reasonable and the benefit worth it.

## 11. Feasibility conclusion

**Worth doing; 3a ships first (resolve its four third-round findings), 3b is a separate follow-up; measurement is an enablement gate.**

- **3a is small and mostly assembly.** The input contract, the journal-derived pending set, the resident pump, the transport activator, the SQL backstop and its proof, the wake verbs, the cold-open cap, the churn cap, the head-hint pattern and the per-input unattempted proof all exist. The additions are one null-safe stale-tolerant head due-time column (accept-decrease, four-outcome proof-refresh), a known-and-due fast dispatcher reusing the proof, a seal-time per-input unattempted proof with a cold-reproducible evidence source shared with `ready`, and the rollout/rollback ordering. No new table. The benefit is removing the residency of every Session pinned only by queued or deferred inputs, and replacing the minutes-late backstop with a seconds-scale due dispatch.
- **3b's crux is the durable commit path while no Harness holds the writer.** Staging in a Broker ledger with a coordinated drain-then-open wake handoff preserves the single-writer invariant and the recovery proofs, at the cost of a bounded commit lag, a byte-carrying handoff with received-vs-durable positions, idempotent retransmission and stable observation identity, staging rows as the wake marker, raw-payload durable retention with a rebuildable derived index, a proactive settlement trigger with an exited-pending-commit state, a durable binding-scoped authorization, a task-view read path, the capture-pipeline rework, and the probe-only/mount-handback teardown tolerance. The worker already owns the processes, the cgroup supervision, the hold ledger and the re-attach path; the sweep logic exists but is operation-triggered, so 3b adds the proactive driver rather than the settlement itself.
- **Prerequisites.** Correctness proof of the head hint's null safety and never-late staleness, the four-outcome proof refresh, and the cold unattempted-proof source; the dispatcher's no-double-run fence, known-and-due selectivity, no-starvation paging and cancelled-settle distinction; the seal-time unattempted proof; 3b's capture-rework characterization, received-vs-durable retention and idempotent retransmission, coordinated channel handoff, stable-identity replay, raw-payload retention/rebuild, staging-row marker and rollback ordering, proactive settlement and exited-pending-commit convergence, durable binding-scoped authorization, probe-only drain (accepting verified `held`) and mount-handback tolerance scoping, and generation-fenced orphan reconciliation; the recovery-view widening proved against both addenda; real-process/MySQL fault acceptance; and the §7 measurement.
- **Compatible with Phases 1 and 2.** The eligibility predicate's active-work terms, the teardown order, the parked-MCP reuse, the bounded-recovery proof and the recovery-view lag arm all hold (§6). No new journal kind, no schema change to the journal contract, no second writer. 3b for MCP-owner Sessions depends on Phase 2 parking being enabled.

**Suggested slicing**: (1) null-safe head due-time hint + four-outcome proof refresh + known-and-due dispatcher + seal-time cold-reproducible unattempted proof + capability gate + rollback ordering + proof-currency recovery-view widening + proof-replay/scan-selectivity measurement (3a enablement); (2) worker capture-pipeline rework (fail-stop → buffer-and-redirect, received-vs-durable retention, idempotent retransmission) + characterization tests; (3) Broker staging route/ledger carrying raw bytes + stable observation identity + staging-row wake marker + coordinated drain-then-open handoff + raw-payload retention/rebuild + worker-side aggregation; (4) proactive execution settlement + exited-pending-commit state + durable binding-scoped authorization + probe-only/mount-handback teardown tolerance + full per-run eligibility relaxations + reclamation guard + task-view liveness (3b enablement); (5) real-process/MySQL fault matrix + release-constant selection. A per-input wake index, a maintenance writer authority, and the compaction-aware proof are separate follow-up designs gated by measurement.
