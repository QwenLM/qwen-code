# SDK Java 宿主机锁：FIFO 票据队列

[English](2026-10-20-sdk-java-fair-lock-queue.md) | [简体中文](2026-10-20-sdk-java-fair-lock-queue.zh-CN.md)

数据库集成现仅运行 MySQL。下文原 MariaDB 集成站点的相关内容保留历史测量记录；其未变的锁、缓存写回和预算规则适用于保留的 MySQL 任务。参见[当前数据库验证范围](managed-runtime-broker-jdbc.zh-CN.md#数据库验证范围)。

## 问题

`.github/workflows/sdk-java.yml` 通过 `flock --wait` 把所有 self-hosted 的
Maven 步骤串行在一个文件 `~/.cache/qwen-code-ci/sdk-java-tests.lock` 上。
2026-10-18/19 和 2026-10-20 共享 ECS 池反复饥饿：job 在 2400 秒、随后
3600 秒、再随后 5400 秒的预算内等满后失败，一条测试都没有执行，而且至少
三台物理宿主机同时中招（#14566、#14743）。

`flock(2)` 不为等待者排队，也不保证顺序：阻塞等待者获得锁的顺序是未指定
的，而在 Linux 上实测为插入顺序 —— 一个 waiter 只有持续阻塞在同一次调用里
才能保住自己的位置。一旦重新入队（后续 step 再取一次锁、轮询、或把等待切成
小片），它就会排到所有一直驻留的 waiter 之后；在持续有新任务到达时，这种
落后可以反复发生而没有上界。等待预算只约束单次尝试，不约束等待总时长：
2400 → 3600 → 5400 秒只降低失败概率。至少三台宿主机各自挂着多个
runner 注册抢同一把锁，需求随到达率增长而容量一次只能放一个 ——
没有任何常数预算能兜住这个队列。

## 目标与非目标

- 目标：让等待变得确定。一个 waiter 的最坏等待时长是排在它前面的
  工作量，而不是它重新入队的次数。
- 目标：其余语义不变。锁仍按 step 边界自动释放；固定的基础设施
  签名错误文案（`lock not acquired within`）保留，`qwen-autofix.yml`
  里的重跑分类器不受影响。
- 目标：在本次 PR 把 test 通道的整套测试移出锁的同时，保留 9600 秒的
  等待上限。拆分前 test 通道自己的整套测试是最久的持锁（自 #14801 起
  纯套件 925 秒，本 head 的整步骤实测为 1031-1205 秒，上限推导按 1205 秒
  计）；套件不再持锁后，唯一的持锁是有界写回复制，因此 9600 秒是保守的
  队列上限，而不是实测需求。缩短它是另一个队列深度取舍；没有常量能给
  队列封顶（qwen-code#15243）。
- 非目标：降低总占用。按套件分片锁、限制每台宿主机注册数、加机器，
  都是正交工作，可以后续再做；有了公平性，这些工作的剩余价值才
  变得可衡量，而不是紧急。
- 非目标：在本次 PR 中修改任一通道的等待预算或 job 上限。MariaDB 写回
  保留 5400 秒和 310 分钟上限，因为它的持锁只包住一次短复制；缩短 test
  通道现在已属保守的 9600 秒/200 分钟上限是后续的队列深度工作。

## 设计

### 在现有锁外面加一个票据队列

新增一个以 source 方式引入的辅助脚本
`.github/scripts/sdk-java-lock.sh`，替换两处取锁点原来的
`exec 9>lock; flock --wait` 内联块。

- 票据放在 `<lock>.queue/`。每个获取者在 fd 8 上的 `flock` 保护下
  对计数器文件做读取-递增-写入，并在释放该锁之前发布自己的票据，
  因此后发的票不可能先于前一张可见。
- 只有持有最小活动顺序号的 waiter 才尝试拿锁 —— 用一次阻塞式
  `flock --wait` 等满剩余预算。池子是混合编队的：main 和旧分支仍跑
  原生 `flock --wait`，切成小片反复重进内核等待队列的队首会在每次
  释放时输给一直阻塞着的 waiter。只进入一次才能保住到达顺序。
- 票据携带 owner 的 PID。被取消或被 kill 的 step 会留下孤儿票；
  下一次队首检查会回收 owner PID 已死且 mtime 超过 10 秒的票。
  仍在排队的 waiter 每两秒 touch 一次自己的票，阻塞在 `flock` 里的
  队首则由一个后台 keepalive 以同样节奏 touch，因此第二条规则可以回收
  所有 mtime 超过 1800 秒的票 —— 正是它保证 PID 被复用的票不会把空闲
  的锁永久堵死。keepalive 关闭了锁的 fd，因此永远不会持有锁；它用
  `touch -c`，因此无法重新创建一张已被删除的票。
- 成功后立刻删除票据：内核已经持有锁之后，持有者不再需要排队位置，
  而 trap 在 `return` 之后也看不到辅助脚本的局部变量。锁仍以 fd 9
  留在 step 的 shell 里，因此它仍会在 step 边界自动释放 —— 这个
  辅助脚本改变的是**获取顺序**，而不是释放语义。
- 超时则打印
  `::error::sdk-java host lock not acquired within N minutes as queue ticket S (CLASS); head of queue is H`
  并返回 1。`CLASS` 是放弃等待时该票所属的档位（`fast` 或 `normal`）；
  `H` 是那一刻的队首，若本票已是最后一张则为 `(no other ticket queued)`。
  重跑分类器匹配的契约是其中的子串 `lock not acquired within`；sdk-java
  的调用点会在容忍路径上改写它（见下文）。
- 可观测性：先做一次非阻塞探测，只有确实需要等待的 waiter 才会打印
  票据号与剩余预算 —— 在进入阻塞之前打印，之后最多每分钟一次。队首
  阻塞期间无法再打印，但阻塞前那行已经点名了它，因此挂死从 step 的
  头几行日志就能归因。
- 在这里 fail-closed 比回退更糟：`release-sdk-java.yml` 续跑既有
  tag 时会检出那个不可变的 commit，它可能早于本辅助脚本。因此两处
  站点在脚本文件不存在时回退到它们替换掉的裸锁（test 站点为
  `flock --wait 9600 9`，写回站点为 `5400`），而不是在 Maven 之前
  直接失败并让发布永久卡死。

### 持锁范围：只包住写回，而不是整套测试

公平队列也无法约束超过预算的等待。MariaDB 通道曾把锁持在整个 install 和
完整的 MySQL `clean verify` 之上；在池竞争下那次 verify 跑了约三小时
（run 39628985638 在 15:54-18:57 持锁），而 fast 通道用的是同一把锁、
等待预算更短。run 39627609266 的 fast 通道 job 17:38 到达，一直是队首，
19:15 失败，Maven 一次都没启动 —— 约束它的是持锁时长，不是排队顺序。

两次 Maven 运行本来就都从 job 本地仓库解析，不触碰宿主机共享状态。只有
缓存写回会修改 `~/.m2`，因此只有写回取锁。种子复制（`cp -aln`）是只读且
尽力而为的，放在取锁之前；它随后会从 job 本地副本中删除内部固定发布
坐标，使不持锁的 `mvn install` 写入新的 inode，而不是穿透硬链接改写宿主机
缓存。Maven 的跟踪标记（`resolver-status.properties`、`*.lastUpdated`、
`_remote.repositories`、`maven-metadata-local.xml`）会被原地截断重写，
因此播种时也会删除这些硬链接，由 Maven 在 job 本地重新创建；写回从不发布
它们，因此下一个 job 的播种没有宿主机缓存中的 inode 可删除。两次 Maven
运行不持锁；写回只取一次锁，且
它的 `mkdir` 和有界 `find`/`cp` 子进程会关闭 fd 9，避免幸存进程继续持有锁。这样一次持锁
只量一次复制，而不是一整套测试，fast 通道的预算又远大于一次持锁时长。

test job 现在遵循同一规则。它的测试套件曾是另一处长时间持锁：2026-10-22，
run 39771949573 的 fast 档 job 两次在 5400 秒预算处失败，分别在
`ecs-qwen-hk4-21`（第 1 次尝试）与 `ecs-qwen-hk3-11`（第 2 次尝试）。
run 39754414693 的 full 档 Java 21 leg 在 `ecs-qwen-hk3-30` 上运行了
89 分钟——是另一台宿主机，因此按宿主机的锁并不是把它们耦合起来的原因——
而且它本身也是饥饿受害者：第 1 次尝试恰在 5400 秒失败，89 分钟的第 2 次
尝试中约 81 分钟是它自己在等锁、约 6 分钟才是 Maven。时间线支持的持锁方
候选是 #15128 之前的 MariaDB `verify` 持锁（#15128 于 2026-10-22T13:44:46Z
合并，在第 1 次尝试之后、第 2 次尝试等待 17 分钟之后）。无论持锁方是谁，
一次套件持锁以十几分钟到数小时计，而写回上限只有 300 秒；这次拆分要
淘汰的正是这一类持锁。它的 Maven 运行现在从基于 `~/.m2` 播种的 job 本地
仓库解析，只有写回才取锁。

test job 的测试套件也不再持锁后，`sdk-java-tests.lock` 在任何宿主机上都不再
串行化任何测试套件：锁下只剩有界写回，每宿主机的套件并发仅由 runner 注册
数量限制。#14566 的“限制持锁时长”因此不再覆盖这个变量——现在每宿主机上
并发运行的 JVM 套件数量不受上限约束，这才是该机制真正的约束。

写回在其预算内拿不到锁时会告警并跳过复制，而不是让 step 失败。此时上方
的 Maven 门禁结果已经最终确定，且调用点会以大小写不敏感的方式在日志落地
前改写辅助脚本的超时文案，因此这条容忍路径不会把任何重跑分类器签名带到
成功的 step 上。同一策略也覆盖辅助脚本无法自行恢复的宿主机故障：缺少
`flock`，或缓存/队列目录不可用，都会在辅助脚本耗尽预算之前告警并跳过。
在裸锁回退分支中，只容忍 `flock` 的超时状态；其他状态属于未知的安装故障，
仍然致命。

失败的套件仍会走到写回。test 通道的 Maven 运行把失败记入 `mvn_status`，而
不是在 errexit 下中断；失败会停止后续套件，而这个延后的状态会在复制之后让
step 失败。因此失败那次已下载的依赖会被发布，而不是由下一条腿重新拉取；
写回被容忍地跳过时也会报告同一状态，而不会把 step 变成绿色。红色 leg 只会
按复制本身的时限（300 秒）排队，而不是花掉绿色通道的 9600 秒预算去重复一个
已经确定的失败信号。复制只发布构件：失败运行留下的解析标记与中断传输的
`*.tmp` 残片一律不发布——标记一旦发布，宿主缓存的每个后续读者都会继承那次
解析结果。由于写回输出现在位于失败点与日志尾部之间，每条可能结束红色 step
的退出都会用注解点名失败阶段；Maven 几乎所有失败模式都退出 1，光看退出码
无法区分三个套件。

9600 秒的 test 通道预算和 5400 秒的写回预算在本次 PR 中保持不变。
它们约束的是队列而不是持锁时长；test 通道的 9600 秒是从拆分前拓扑继承
的保守上限——当时它的整套测试可能排在多次持锁之后——套件不再持锁后，
唯一的持锁是有界写回，因此这是保守上限（约 32 次排队复制），而不是实测
需求。1200 秒的提升窗口仍远在两者之内。变化在于这段等待现在守护的是
一次可选且有界的复制，因此预算耗尽会跳过复制而不是让 step 失败。
把 test 通道的预算缩短到 1800 秒（六次排队复制）是后续的队列深度取舍。

### fast 档优先

FIFO 队列把 waiter 的等待限制在它的排位内，但 fast 档 job 仍然排在所有
正在等待的 full 档票据之后。2026-10-21 的 run 39562109470 中，`SDK Java
(fast)` job 在成为队首之前，作为非队首 waiter 排在其他票据后面等了最初的
38 分钟（qwen-code#14566）。本节消除的就是这部分等待。现在同一把物理锁上
区分两个档位：

- 票据命名为 `rank-sequence-pid`。`fast` 是 rank 0，`normal` 是 rank 1；
  队首是最小的活动名字，因此每张 fast 票都排在所有尚未被提升的
  full 档票前面。
- test job 把自己的 tier 传给辅助脚本：fast 档进入 fast 类，
  approval、release 和 MariaDB 工作保持 normal。
- 已经阻塞在 `flock(2)` 里的 full 档队首保留它在内核等待队列中的位置；
  在它之后到达的最小 fast 票会成为新的最小值并同样阻塞。为本队列实测
  的 Linux 唤醒顺序是插入顺序（kernel 6.6、util-linux `flock` 2.38.1、
  六个真实 waiter、3/3 次一致；实测记录在 qwen-code#15035），因此先阻塞
  的队首仍赢得下一次释放。在已阻塞的 fast 票存在期间，更晚到达的 fast
  票永远不是最小值，因此它们只会循环并按票据顺序被服务。
- 因此 fast job 等的是当前正在运行的那次持锁、至多一个已阻塞的 full 档
  队首，以及排在它前面的 fast 类票据（更早的 fast 票和被提升的票，不论
  是否已阻塞），而不是仍在用户态等待的 full 档队列。同一时刻至多只有
  一个 full 档队首处于阻塞：normal 票只有成为最小值时才会阻塞，也就是
  队列里没有任何 fast 类票据时；它阻塞期间 keepalive 让它的票一直排在
  所有更晚的 normal 票之前。但同时阻塞的票可以多于两张 —— 一个 full 档
  队首、在它之后到达的 fast 票、以及此后才被提升的一张更早的 normal
  票 —— 内核按它们进入阻塞的顺序服务。
- 等待超过 `SDK_JAVA_LOCK_PROMOTE_AFTER`（默认 1200 秒）的 normal 票
  会被重命名进 fast 类。它保留自己的顺序号，因此仍排在它之后到达的
  fast 票之前，连续的 fast 流量无法饿死 full 档。提升保护的是仍在等待
  的 full 档票，而不是已阻塞的票：已阻塞的队首不会再回到提升检查，也
  不需要，因为它本来就是下一个。
- 提升窗口限制的是超过的范围，而不是单次持锁。提升是逐 waiter 的：
  每张 normal 票在自己的等待越过窗口时重命名自己。在提升之前到达、
  且已经阻塞进 `flock` 的 fast 票保留它更早的内核位置，因此被提升的
  票仍要在它后面多等一次持锁；代价被已经阻塞的票据封顶，不构成饿死。
  只有当单次持锁长于该窗口时，所有正在等待的 normal 票才会一起越过
  阈值；否则它们逐一提升，而在一张更晚的 normal 票越过窗口之前到达的
  fast 票仍可超过它。只有当每张正在等待的 normal 票都各自越过窗口后，
  队列才按顺序号服务。

释放语义和重跑分类器匹配的子串 `lock not acquired within` 都不变；
超时行现在额外标出该票的档位。

优先级不能限制单次持锁的时长，限制它的是上文“持锁范围”的改动。同一个
2026-10-21 的 job 随后作为队首在一次持锁之后等了最后 52 分钟并超时；
在 MariaDB 通道把整套测试移出锁之前，这把锁上实测到 7426 秒和
8685 秒的 full 档 MariaDB 持锁，多次持锁串联同样可以耗尽预算：
2026-10-22 run 39754359013 的 Java 11 与 Java 21 通道各自耗满 5400 秒，
而 MariaDB 通道仍把锁持在 verify 上（qwen-code#15243）——和上面那些更长的
持锁一样，都是 #15128 之前的历史。当前本工作流最久的持锁是有界的
300 秒写回；test 通道的 9600 秒获取预算是从拆分前拓扑继承的保守上限，
其 200 分钟上限覆盖该等待、本 head 最差的整步骤套件实测（1205 秒；925 秒的
纯套件数字来自 #14801，是下界）、写回和约 11 分钟 setup。MariaDB
写回保留 5400 秒和 310 分钟上限：它自己的持锁是短复制，而且它的等待发生在
约三小时的 verify 之后，更大的预算放不进合法的 job 上限。点名持锁者
（一次很长的持票持锁，还是一个从未取票的进程）是 qwen-code#15031 的
诊断，限制持锁时长仍归 #14566。

有了两个档位之后，队首 keepalive 更加重要。没有它时，阻塞超过 1800
秒的队首会被其他 waiter 的回收逻辑删掉票据，队列里的下一张票 —— 不论
档位 —— 成为队首并同样阻塞进内核。在长达两小时的持锁里，这会让多张
normal 票在内核中占到比之后到达的 fast 票更靠前的位置，而这恰恰是本节
要避免的顺序。

### 为什么是公平性，而不是其他方案

- 按套件分片：只降低排队频率，每个分片仍然是一把无序唤醒的裸
  flock。本改动完全移除了套件串行化，因此这条所依赖的未经验证假设 ——
  并发套件在同一宿主机上安全（这池子刚把一次构建 OOM 过）—— 现在已成为
  池上每个套件都必须承担的承重假设。
- 限制每台宿主机注册数：需要仓库之外的池拓扑改造，而且每台宿主机
  内部仍然是同样的反复丢位竞争。
- 加一台宿主机：至少三台同时饥饿过，机器数量已被证明不是瓶颈。

### 有意接受的残余失败模式

- owner 已死但 PID 被一个长寿命进程复用的票，会在 1800 秒的 mtime
  规则命中后被回收；在那之前空闲的锁不可达，最长也就是这段时间，
  排其后的 waiter 仍有剩余预算。如果宿主机仍然卡住，运维恢复命令是
  `rm -rf ~/.cache/qwen-code-ci/sdk-java-tests.lock.queue/`，仓库里没有
  任何代码会执行它。
- 被 SIGKILL 的队首会留下仍在运行的 keepalive，直到 keepalive 下一次
  两秒检查发现 owner 已不在；随后票据照旧由 owner 已死的规则回收，
  `touch -c` 也无法让它复活。
- 计数器由只追加 `.seq` 文件上的 `flock` 串行化，持有者死亡时内核会
  释放该锁，因此没有需要清理的老化路径；在读取-递增-写入之间被 kill
  最多只多一次重试。

## 验证计划

- 辅助脚本的单元行为由 `scripts/tests/sdk-java-lock.test.js` 钉住
  （仅 POSIX）：两个 waiter 的 FIFO 顺序、已阻塞队首之后 fast 票超过
  仍在等待的 normal 票、等待中的 normal 票提升后排在更晚的 fast 票之前、
  被提升的票超时时报告 fast 档、已阻塞队首的票在其他 waiter 的回收逻辑
  下存活、超时的已阻塞队首点名取代它的票据、keepalive 在获取锁时与
  owner 死亡后停止、keepalive 不持有锁文件的 fd（读取 `/proc`，因此仅
  Linux）、过期 owner 的回收、超时签名与票据清理，`flock` 以 PATH stub
  注入。排序用的 stub
  会像内核一样让 `flock --wait` 一直阻塞到释放，因此队首不会循环、
  也不会被超过。
- 工作流的 pin 随机制迁移：`scripts/tests/sdk-java-workflow.test.js`
  pin 的是 source 该辅助脚本、test 通道的 9600 秒预算与 200 分钟上限、
  红色 leg 的 300 秒收紧、MariaDB 写回的 5400 秒预算与 310 分钟上限、
  两处的前导与写回尾部——除三处有意的差异外逐字节相同：等待预算、
  红色路径收紧，以及 test job 延后的 `mvn_status` 退出与阶段上报
  （比较时在前导中归一化为 `exit 0` 并剥离，在尾部于写回之后切掉；
  MariaDB 侧的分支保留 `exit 0` 且从不出现 `mvn_status`，因为它的套件
  就地失败）、两个 job 的 Maven 运行都在取锁之前、test 通道每条 `mvn` 行
  都以 `|| mvn_status=$?` 结尾并带阶段名、容忍跳过分支分别以绿色与红色
  状态各跑一次（红色分支断言阶段注解与 300 秒预算）、写回子进程关闭 fd 9、
  每个播种 job 本地仓库与两处写回 prune 都排除了内部坐标与解析器
  记账文件——`_remote.repositories`、`maven-metadata-local.xml`、
  `resolver-status.properties`、`*.lastUpdated` 与 `*.tmp`、写回在宿主侧
  删除内部坐标、按任意深度 prune、缓存目录创建失败降级为警告、该注解
  保持在 `INFRA_FAILURE_SIGNATURES` 之外，以及每个站点的 seed 删除集合与
  prune 集合一致。故障分支覆盖 `flock` 缺失、`mkdir` 损坏、队列路径被占、
  锁路径是目录、`flock` 超时以及 `flock` 返回意外状态。`.size-baseline`
  条目在最后一次编辑后重新实测到工作流的尺寸。
- 真实宿主机上的浸泡验证就是 CI 本身：合并后第一批池上运行要么
  按票序拿到锁，要么带着可归因的票据号超时。

## 验收标准

- `sdk-java.yml` 的 test 站点以 9600 秒通过该辅助脚本获取，job 上限为
  200 分钟；MariaDB 写回站点保留 5400 秒和 310 分钟上限。test job 传入
  自己的 tier，MariaDB 站点默认 normal。两处都先让 Maven 套件从 job
  本地仓库跑完，再取锁。每个播种 job 本地仓库的 job 都会在运行 Maven
  之前删除内部固定发布坐标。
- `npx vitest run scripts/tests/sdk-java-lock.test.js
scripts/tests/sdk-java-workflow.test.js scripts/tests/workflow-size.test.js`
  通过。
- 辅助脚本的超时行仍包含子串 `lock not acquired within`，因此
  `qwen-autofix.yml` 的 `INFRA_FAILURE_SIGNATURES` 仍能在其他位置匹配
  失败的取锁。两处调用点现在把取锁失败或安装故障降级为告警、跳过写回，
  并以大小写不敏感的方式在日志落地前改写辅助脚本的超时文案，因此本工作流
  现在容忍的取锁不会在成功的 step 上留下分类器签名。只有裸锁回退分支中
  `flock` 的意外状态仍然致命。
