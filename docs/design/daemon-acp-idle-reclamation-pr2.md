# PR2: Reclaim idle ACP processes when admission is full

[English](daemon-acp-idle-reclamation-pr2.md) | [简体中文](daemon-acp-idle-reclamation-pr2.zh-CN.md)

## 1. Status and delivery boundary

Implemented locally with the verification below completed, 2026-09-15. Source baseline: `88347ccca394902262915dde880499976e596cd7`, the merged [PR1 #11911](https://github.com/QwenLM/qwen-code/pull/11911). Delivery tracker: [#11907](https://github.com/QwenLM/qwen-code/issues/11907). This change includes the PR2 implementation and collocated regression tests. Runtime evidence is recorded in the local E2E report.

PR1 delivered opt-in, daemon-wide ACP process-count admission and recognizable capacity errors. PR2 adds on-demand reclamation of eligible idle ACP children. PR3 remains the user-directed choice to close a workspace runtime or cancel when automatic reclamation cannot help. None of these stages applies the modeled per-child heap ceiling or completes [#8182](https://github.com/QwenLM/qwen-code/issues/8182).

**First version: automatically reclaim only an ACP channel with zero live sessions and no pending work.** Keep the existing session reaper responsible for expired abandoned sessions; do not advance its timeout or close a connected conversation just because it has not generated recently. Once that reaper has closed every session, a remaining warm channel can become a candidate.

This deliberately narrows the proposal's broader option of closing idle-but-loaded sessions on demand. That option needs additional persistence, conditional-close and recovery semantics and is outside this PR2. An idle open conversation with an SSE subscriber is protected. So is a loaded session without a subscriber until the existing lifecycle closes it. This boundary should be reflected in the tracker when implementation is submitted; it must not be described as complete support for evicting loaded sessions.

## 3. Trigger and end-to-end flow

Enable reclamation only for the existing fully wired managed `--child-heap-mode admit` path. Keep `off`, `observe`, single-child consumers and injected/unmanaged bridges unchanged. Add no environment variable, CLI mode, public route or idle-timeout setting.

1. An operation needs a new ACP. Existing-child reuse takes its normal fast path and does not trigger reclamation.
2. The factory reserves a slot and evaluates the existing policy. If admitted, spawn normally.
3. If capacity rejects this attempt, cancel that attempt's reservation before any asynchronous reclamation. Otherwise waiting requests themselves would inflate occupancy while trying to free it.
4. Ask the daemon's shared reclamation helper to try once. The helper first checks whether another operation has already released capacity; if so, there is no reason to select a victim.
5. Read eligible runtimes, exclude the requester, sort by last use, and try the oldest candidate. One requested spawn may attempt at most one victim. No candidate, a changed candidate, a failed close or an occupied reclamation target ends this attempt without trying a cascade of other workspaces.
6. The victim bridge validates its current channel/epoch and idle state, synchronously marks that channel dying through the existing path, and awaits normal tracked teardown. Retain its workspace runtime and bridge.
7. After teardown, recheck the request's cancellation and the shared registry. If no slot is available, return the existing capacity error. Do not infer release from a cold lifecycle state, an exited root PID alone, a boolean callback result or a decremented workspace count.
8. Only with available capacity, obtain a fresh reservation and run the same policy again before spawn. A competing request may win the released slot. In that case, refuse normally; do not evict a second victim. There is at most one reclamation opportunity and one subsequent admission attempt per factory invocation.

Do not retry the outer create/load/MCP operation. The same pending factory call resumes before its child exists, so accepted prompts, worktree creation and rollback are not replayed. Generic transport failures, session limits, initialization errors and stale-owner errors do not trigger reclamation.

## 4. Candidate eligibility and ownership

Reuse the activity aggregation currently used by workspace removal, extracting only the shared read logic into a small serve helper without changing removal semantics. Keep the bridge's detailed final guard in the bridge, where its private channel state is authoritative.

| Gate                          | First-version rule                                                                                                                                                                                                                                                                                                            |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ownership                     | Managed, registered, active, trusted workspace runtime whose factory uses the same daemon process registry. Select by runtime identity/workspace ID, never by a guessed cwd alias.                                                                                                                                            |
| Requester                     | Exclude the requesting runtime, including replacement attempts while an older child is retiring. Never await that runtime's own pending spawn while servicing its factory callback.                                                                                                                                           |
| Primary and internal runtimes | The primary workspace may qualify under the same checks; being non-removable is not a resource pin. Exclude internal Conversations, scratch/standalone and other special runtime lifecycles from the initial candidate set. Their starts still use admission and may request reclamation of an eligible registered workspace. |
| Sessions                      | `sessionCount === 0`. Any loaded session blocks selection, including an idle attached session, a running/queued prompt, permission/user-answer wait, background task, or a session with unknown child-work reporting.                                                                                                         |
| Bridge state                  | A current live channel with no starting/stopping overlap, no session spawn/restore or unsettled cleanup, no runtime operation reservations, no workspace control/MCP discovery/authentication and no shutdown/quarantine/condemned-channel state.                                                                             |
| Daemon work                   | No pending session starts, ACP connections, memory tasks, channel workers, voice activity, or queued/running coordinator management work. Missing observation hooks or unsupported reclaim capability make the runtime ineligible; missing data is not zero.                                                                  |
| Warm retention                | A completed preheat's `keepAliveUntil` and a positive channel idle timeout are soft retention, and capacity demand may end them early. Pending preheat and initialization remain protected by their work reservations.                                                                                                        |
| Identity                      | The selected runtime remains active and its channel/epoch matches the candidate. A removed, draining, trust-reconfigured or replaced runtime is skipped.                                                                                                                                                                      |

Keep daemon-owned terminal processes, registrations, saved history, files, configuration, schedulers and service objects intact. Scheduled future work is not a reason to destroy those services; it may need to ensure a new ACP later and goes through the same admission policy. Running work reflected by the activity gates blocks reclamation. Do not claim that unrelated terminal processes or aggregate workspace RSS are released by killing the ACP.

These rules intentionally prioritize protecting sessions over maximum reclamation. They avoid needing a new persistence-in-flight signal or a new contract for closing a session whose only state is in memory. The existing session reaper and its conditional-close behavior remain unchanged.

A known untrusted requesting workspace cannot reclaim another workspace's child. Internal requesters not yet published in the registry retain the shared callback. During replacement, an older child retiring in the requesting workspace still counts until registry release; this overlap may reclaim a different eligible warm child and make its next use cold. The initial request also pays the victim teardown latency within its existing startup budget.

## 5. LRU and timing

Use last actual use of the current ACP channel, not registration age or the time a status page was polled. Add one internal `lastUsedAt` timestamp to the current channel's bookkeeping, initialized when that channel becomes usable and touched when real session activity or workspace control/preheat work is accepted or finishes. Carry a private candidate token containing channel identity/epoch and this timestamp. Do not add a public status field solely for sorting.

The existing `bridge.lastActivityAt` is not a complete substitute: it can remain null on a preheated channel and does not cover workspace-management calls. Preserve its existing external semantics instead of quietly broadening an idle-detection API. Periodic status reads, diagnostics and heartbeat reports that only repeat unchanged state must not keep the new recency timestamp warm; substantive work transitions may update it.

Order eligible candidates by ascending `lastUsedAt`, then by workspace ID for deterministic ties. This is an in-memory ordering, not a distributed or perfectly monotonic clock guarantee. No new grace duration is required for an empty, otherwise safe channel: the existing retention was an optimization, and explicit capacity demand takes precedence. Existing session idle timeout and prompt-settled grace remain unchanged.

## 7. Failure, cancellation and concurrency

Retain the agreed simple eligibility check and existing lifecycle protections. No new atomic eviction transaction, daemon-wide drain protocol or eviction lock is proposed. The bridge's final identity/no-work check and marking the chosen channel dying must have no intervening await; this preserves the existing channel-close invariant without inventing a new protocol.

A request canceled before reclamation selects nothing. If cancellation arrives after victim termination has begun, allow that owned cleanup to finish, but do not spawn the requested child or attempt another victim. Bound waiting by the existing factory startup abort/deadline and termination budgets; a timeout must not permit a late factory result to escape cleanup. Reclamation latency is part of the original startup timeout, not a new unbounded allowance. While the factory awaits reclamation, its optional startup context supplies the capacity error for the bridge deadline; the bridge aborts with that error and retains late-result cleanup. Clear the override as soon as reclamation settles, so unrelated later startup timeouts keep their usual error.

A candidate selected by two callers is not force-closed twice: the existing dying/identity checks make the second attempt skip. No freed slot belongs to a particular requester. Final reserve/decide remains authoritative even if another request has already started. If the shared registry still reports no free slot after teardown, including tracked descendants, keep reporting capacity exhaustion. A teardown error after the registry releases the slot does not itself prevent admission; never manually decrement registry counts or run a broad kill command.

Candidate observation and concurrent external activity are not a transactional snapshot of the whole workspace. The first version relies on existing guards and protects all live sessions; it does not promise an atomic stop of every external actor. A candidate changing during selection may reduce the success rate. Capacity failure is preferable to force-closing it or endlessly searching.

Preserve REST `503`, `acp_child_capacity_exhausted` and ACP error metadata when reclamation cannot make capacity. Preserve PR1's draft retention and no-automatic-retry UX. Successful reclamation requires no workspace-deletion event or confirmation dialog. Existing capability staleness and cold-start status remain the recovery signals; the workspace chooser belongs to PR3.

The existing `refusals` counter records rejected spawn admission attempts. With reclamation, the first rejected attempt can be followed by a successful retry, so it must not be described as the count of user-visible failed operations. Document this distinction; do not add a second public metrics model for this PR. Use the existing diagnostic channel for reclamation attempts and failures; normal channel-exit logging records teardown. No per-poll or per-skip logging is added.

## 8. Recovery behavior

Reclamation retains workspace ID, aliases, registration intent, trust, runtime storage roots, environment bindings and the bridge/coordinator objects. The selected channel exits through normal cleanup. A subsequent ensure or saved-session load starts a new channel and negotiates a newer runtime epoch; stale MCP/Skills state is rebuilt through existing preparation.

There is no live session to migrate in the selected child. Saved conversations remain loadable through their resolved owner runtime. Cold restore may be slower and may still fail admission if every slot is now occupied. Do not fall back to primary, create a replacement conversation on 404, or claim that unsaved in-memory session state was migrated. Background scheduler and worker service lifecycle must remain unchanged by this child-only operation.

## 9. Validation and acceptance

Use the `e2e-testing` workflow with an isolated daemon, deterministic local provider and test-owned child processes. Record the global CLI baseline before implementation; if it already includes later changes, record its exact version rather than inventing an expected failure. The local test plan is `.qwen/e2e-tests/daemon-acp-idle-reclamation-pr2.md`; baseline and implementation results are recorded alongside it.

1. At one slot, warm empty A blocks cold B on the PR1 baseline. With PR2, the same operation succeeds after A's tracked child is released; registration and saved history do not change.
2. With several empty warm candidates, the least recently used one is reclaimed. MCP/control and preheat activity update ordering; repeated status polling does not. Ties are deterministic. Stop after one victim.
3. A loaded session protects A even when no prompt is running. Separately cover running/queued prompts, permission/user-answer waits, background work and disconnected-but-not-yet-reaped sessions. No session-close or kill is sent by PR2.
4. Empty-channel activity gates protect concurrent create/load, queued coordinator work, MCP discovery/OAuth, voice/channel services, ACP connections and memory jobs. Unknown ownership or missing hooks skips reclamation. Completed soft keepalive alone does not block it.
5. Admitted but not yet attached starts plus attached/unreleased children stay within the limit across concurrent starts, delayed root/descendant release, teardown failure, requester cancellation and a competing winner. Reserve-before-decide can transiently count a rejected reservation above the limit; it must be canceled before any await and must never spawn. No reservation leaks, second victim or outer request replay occur.
6. Primary and secondary eligible workspaces work; special/internal candidates remain excluded. Primary, secondary, dynamically created and managed internal requesters all use the shared callback and preserve their owner-specific errors. Cold bootstrap without a candidate remains a normal capacity failure.
7. Re-enter reclaimed A and load saved history: verify workspace identity, environment/storage roots, epoch advancement, MCP/Skills refresh and no duplicate prompt. Terminal/scheduler/service objects and registration survive.
8. Default/off/observe behavior, heap arguments, session limits, zero-slot validation and PR1 error/rollback/UI behavior remain unchanged. Run build, typecheck, focused tests and real daemon/process-tree checks for implementation; do not substitute mocked release for Linux/Windows process-tree evidence.

### Executed verification (2026-09-15)

Full build, typecheck, bundle and focused lint passed. The ACP focused suite passed 80 tests, serve lifecycle/routes passed 696 tests, and standalone server wiring passed 4 tests. Coverage includes the single-victim policy, no spawn before release, cancellation/failure/competition outcomes, candidate identity and activity protection, soft retention, MCP completion recency and status polling without recency updates.

Five real-daemon groups passed 52 assertions on macOS with Node 22: empty warm reclamation, old-PID exit, cold recovery of the original workspace with an increased epoch, history preservation and original session-ID loading, loaded idle session and ACP-connection protection, LRU ordering, dynamic requesters, preserved registration identity and unchanged heap arguments. All test-owned processes exited. The detailed report is `.qwen/e2e-tests/pr2-idle-reclamation/verification-report.md`.

Linux/Windows, real delayed descendant exit and fault injection, real model conversations and all business-service combinations were not exercised. Cancellation and competition use focused unit-test evidence; those tests do not replace process-tree verification on the deployment target. These tests do not prove actual RAM safety or performance improvement.

## 10. Decisions and remaining work

The implemented scope is: reclaim empty warm channels, preserve every live session, use one victim and one admission retry, add no public API or tuning parameter, and leave user choice to PR3. The tracker currently describes a wider idle-session option; reconcile that delivery claim when submitting implementation rather than silently marking the wider option complete.

Implementation must verify the extracted activity helper has all existing sources at every managed construction path, and that every genuine workspace-control entry point updates recency. Tests must establish release-before-spawn and restore correctness on the built artifact. This design makes no measured performance, RAM-safety or cross-platform validation claim.
