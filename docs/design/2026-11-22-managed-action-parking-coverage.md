This follows the [Action parking design](2026-11-21-managed-action-parking.md) (Phase 4, merged in #18115) and is checked against `main` at `5714ee4c53`. ## 1. Problem and current state

### 1.1 The exclusions and their real gates

The first increment parks only waits that cold recovery already accepts (parent §2). The exclusion logic lives in three places: the park eligibility `actionParkCandidate` (`packages/cli/src/serve/hosted-harness-session.ts:5123`), the continuation producer `captureNativeBatch` (`packages/cli/src/serve/hosted-workspace-tool-turn.ts:4498`), and the cold-recovery entry points (the takeover arm `hosted-harness-session.ts:8386`, the approval recovery arm `:8645-8652`, and `resumeSavedNativeBatch` `hosted-workspace-tool-turn.ts:4327`).

### 1.2 One invariant fixes the order of extension

To the journal, a frozen Turn is identical to "the process was SIGKILLed at the wait point" (parent §4.2). **Park coverage can therefore never exceed cold-recovery coverage.** Each slice must first make cold recovery accept the wait, then relax park eligibility in the same slice. It follows that each slice also fixes crash recovery for the same wait: today, a monitor Turn waiting for an approval when its Harness crashes is settled as a crash instead of continuing to wait.

## 2. Goals and scope

Goals:

- Make each wait shape excluded by the first increment parkable, or state explicitly that it stays unsupported and why.
- Reuse the G3 approval-continuation driver and the parent's certificate, CAS and unpark mechanisms for every shape; build no second park/resume protocol.
- Make each slice independently reviewable and revertible, relaxing only its own term of the shared eligibility function.

Non-goals:

- Parking a parent Session that waits on a child result (a parent Turn inside an `agent` call). That is a new kind of wait with no Action and needs its own design (see §9).
- Handing back the Turn's Runtime membership while parked (parent open question 2).
- Sessions on a public Workspace Shell profile with MCP: Phase 1 never suspends them, because detaching them needs a lifecycle authority.
- Recovering v1/v2 waits (§4.8).
- Team plan approvals. The parent's open question 3 lists them, but this design has not analyzed their recovery path, so they stay resident and need their own analysis.

## 3. Overview

1. **P0: fold the eligibility function first.** Extract the Session-shape terms cold recovery requires before it resumes an approval continuation (no Hooks, no MCP, a tool owner) into one function that park eligibility and both cold-recovery entry points (the takeover load and the resident redrive) call. The journal-state terms, the continuation lookup and the original Prompt, are already shared helpers. The terms where parking is stricter than recovery (lineage, wake ownership, command step, the grant capabilities) stay park-only, each with its own reason, and each later slice removes one of them or widens the shared terms. #18115 already lists this fold as a follow-up. Afterwards each slice changes only that function plus its producer or recovery arm, so no second copy of "equivalent-looking" conditions ever exists.
   - **Refusal reasons.** Park eligibility returns a typed reason for every waiting Turn it turns down, and the Harness counts each wait once, under the first reason that kept it resident, in `suspensionStats`, beside the other Phase 1 counters. Today `actionParkCandidate` returns `undefined` without a reason. Worse, a wait whose continuation the producer never captured (Hooks, MCP, a Shell profile, an unsupported tool, an oversize plan) does not register at all, so eligibility cannot even see it. P0 therefore has every durable wait register: the continuation producer returns its refusal reason instead of `undefined`, a wait that can never park registers with that reason, and an extension command-step wait registers as `command_step`. These counts drive the reordering in §6 and answer open question 3.
   - **Exposure.** #18173 reports `suspensionStats`, these counts included, on the instance's internal metrics route.
   - **No Workspace.** A Session with no Workspace never parks, and P0 pins why with a test. On a cache miss, decision delivery reaches such a Session with a plain load unless verified recovery is on, and a plain load refuses an unsettled Turn. But the connector sends no tool profile for it, and a Session with no tool profile gets no approval policy (`hostedApprovalForTurn`): its tool calls never ask, even a memory write, and questions are not admitted, so no Action ever waits and nothing registers to park. The no-Runtime memory continuation exists only on Workspace Sessions, whose decision delivery sends a passive load. If approvals ever reach a Session with no Workspace, its decision delivery must send a passive load first.
2. **Extend slice by slice** (§4). Each slice has three parts: the cold-recovery producer or recovery-arm change, one relaxation in the shared eligibility function, and the matching fault and real-process tests.
3. **Contract changes are gated by a capability bit.** Slices that change the seal certificate's shape (S2, S4) have the control plane advertise one more capability bit in the writer grant, and the Harness sends the new certificate shape only when it sees that bit. No configuration key is added; the bit is advertised together with `qwen.managed-agent.action-parking.enabled`. Rationale: a seal refused after the freeze is an irreversible teardown failure. Bounded recovery does converge, but "mixed versions are unsupported" should not be the safety net.

## 4. Slices

### 4.1 S1: image-only Prompts

- **Change.** Relax `hostedOriginalPromptText`, the check that park eligibility and both recovery arms share. A Prompt whose user record has text is unchanged. When it has none, read the original input back through `readHostedInput`. A `hosted-harness` input that carries attachments restarts from empty text, matching its live Turn, because `executeHostedTurn` reads the attachments back itself. Other sources still require text, because text is their only fallback. Every Prompt-text check in the recovery arms uses this function, including the saved-model-request and the memory or skill results checks that carried their own copies, so an image-only Turn that crashes in those phases also resumes.
- **Confirmed.** The user record restored from the journal carries the inline image, so the text-plus-image Prompts that park today need no tightening. The Harness test "resumes a parked approval with the original image still in its history" parks a text-plus-image Prompt, cold-loads it, allows it, and finds the original image as inline data in the history handed to the model on resume. The test replaces the model function, so it builds no request. Request-time eviction does not change the conclusion: each request moves the images it evicts from its own history into the in-memory `InMemoryImagePayloadStore` (`packages/core/src/services/image-payload-references.ts`) in the same pass and reattaches the most recent ones, so an empty store after a cold load loses nothing; that module's core tests start from a fresh store. The first request after resume therefore treats the restored image as the live Turn's post-tool request would, and this slice's tests check the restored history (§7).
- **Confirmed (#18164).** The consumers of the run option `prompt: text` (`hosted-harness-session.ts:4486`) accept an empty string: the live Turn of an image-only Prompt already runs with empty text, and on resume the option only begins the Turn's budget, which finds no directive in it. The S1 park and crash tests resume with empty text.
- **Surface.** Harness only.

### 4.2 S2: background work + Action

- **Change.** The seal carries both the 3b background hold and `parkedTurn`. A Harness sends the pair only when the writer grant advertises the new `backgroundActionParking` bit, which the control plane advertises together with `actionParking`; the Store accepts the pair without reading the bit, because an older control plane never advertises it and so never receives the pair. A background terminal the Broker stages makes the park due now instead of ending it: the park certificate stays on the head, and its wake time moves to the staging time. This holds on both server paths that meet staged work. The seal's staged-wake path, which until now cleared the parked fields (parent §4.9 item 3), records the certificate with that wake time. The staging transaction (`JdbcRuntimeStageStore.stageBatch`), which today only sets the wake-pending and retry fields, moves the wake time and unparks the Session's `hosted_action_parked` rows with the store method of parent §4.6. The coordinator then redispatches the Turn at once, instead of leaving the resident Turn rebuilt by the wake load with nobody consuming its event stream until `retry_after`.
- **Interleavings.** The staging transaction and the park CAS both lock the Session and head rows first, so they serialize, and three orders remain. (1) Staged before the seal: the seal records the certificate already due, so the CAS parks the Turn with `retry_after` = now. (2) Staged between the seal and the CAS: staging moves the certificate's wake time to now and finds no parked row yet, and the CAS parks with `retry_after` = now. (3) Staged after the CAS: staging moves the wake time and unparks the row. In every order the dispatch sweep picks the Turn up on its next pass, and no order takes the charged `stream ended before terminal` retry, so a background terminal never spends the Turn's retry budget. Each order is an S2 acceptance case (§7). A wake-recovery load that acquires the writer before the CAS clears the certificate, as any acquisition does (parent §8), and that CAS falls back to one ordinary retry.
- **Load path.** A wake-recovery load carries a takeover flag (confirmed): the scan's `recoverForWake` sends only the passive flag and the wake fence's `activateForWake` sends the drive flag, both pinned by `QwenHostedHarnessConnectorTest`, and the Harness tests show that a load with either flag takes a parked approval Turn over. So `takeoverFlags` is true and the load enters the approval recovery arm, which rebuilds the waiter. The coordinator's drive load then converges with it under the #17521 attachment rules and replays from its consumed watermark. The background notification stays pending as a wake input until the Turn settles, and only then does the pump deliver it. Meanwhile another input is pending, so the Session cannot park again. This is bounded: at most one reload per background terminal.
- **Invariant.** The park CAS does not read the background field. The background hold is still proven by 3b, and `parkedTurn` is still proven by "the only live Turn is in a parkable wait". Neither certificate infers the other.
- **Surface.** Store seal validation, the seal's staged-wake path, the staging transaction and the grant bit; on the Harness, relaxing the "no background hold" term of eligibility and sending `backgroundHeld` beside `parkedTurn`.

### 4.3 S3: child Sessions

- **Why the CAS applies as is.** A child Session's Turn is a coordinator-dispatched `ma_turn` row. `ChildResultRelay` acts only on terminal statuses and a few specific error codes when it reads that row, and treats `RUNNING` as a wait. A parked row stays `RUNNING`, and `hosted_action_parked` matches none of those branches. Child Sessions run without the live poll (`hostedApprovalForTurn` turns it off when `lineage` is set, `:997`), so their certificate carries no `approvalRevision`.
- **Prerequisite.** The cold-open admission section of the [stateless Harness design](2026-11-16-managed-stateless-harness.md) lists the relay attempt-budget gap as a Phase 1 prerequisite: session-message delivery, child-result delivery and automation fires still charge waits against their attempt budget, so a cold-open burst can settle a message as cancelled or unknown. A test confirmed the gap open for session-message delivery: a receipt, a reconciliation or a sender step that met `hosted_session_closing` or `hosted_session_open_busy` spent an attempt, and a parked child meets these on every step that reloads it. This slice closes it there as the command arm already does: the relay retries on its heartbeat and spends nothing. The Harness still bounds a closing wait, because a teardown that cannot finish escalates to `hosted_session_teardown_blocked`, which spends the budget; a cold-open slot frees on its own. Child-result delivery and automation fires still charge these waits and stay owed in that design. Child-result delivery calls a child's Harness only for its stop, which #17681 already exempts; every other step goes to the parent, and a child is never a parent because it starts no children of its own.
- **Change.** The eligibility function drops the `lineage` term and keeps every other one. A pending session message is a wake-owned input, so its presence keeps the Session from parking, and the relay's reload brings the Session back.
- **Benefit.** The parent Turn remains resident inside its `agent` call, so this slice frees only the child Session's resident. Zero residency for the whole tree also needs parent-waits-on-child parking, a non-goal in §2.
- **Verified.** A child approval already recovered after its Harness died in the wait, so opening the park needs no recovery change. After cold recovery, a direct public child's single question re-acquires its original Runtime, hands the mount back while it waits and acquires it again on the decision, as a root's does (`questionChild`). `MESSAGE_TURN_WAIT_MS` applies only once the child's Turn row is terminal; a parked row stays `RUNNING`, so a park that outlives the bound with a message waiting is still a wait. Dropping the term also admits a wake-started child Turn under the S4 terms, and the wake-recovery scan already selects child heads.

### 4.4 S4: wake-started Turns

This is the largest slice, delivered in two steps: monitor, loop, automation and child-result notifications first; channel and `pr_event`, which also carry reply plans and channel settlement, follow as S4b.

- **Harness recovery arm.** When the pump handles an "attempted wake input" whose checkpoint is at `await_action` and whose continuation the shared eligibility function accepts, it resumes the wait through the approval-continuation driver instead of calling `settleCrashedWakeTurnAftermath`. Shipped alone, this step already fixes crash recovery for wake Turns that wait for an approval. Implemented in #18170. It also fixes a worse failure found while testing it: the aftermath never moves the checkpoint off `await_action`, so the follow-up continuation Turn it queues cannot start, and the pump fails. The pump runs the continuation as the Turn and settles and consumes the input as after a normal run. It covers native approvals of monitor, automation, loop and child-result Turns; a source cancelled meanwhile resumes already aborted. Every path that still reaches the aftermath (a Session already blocked for another reason, shapes the resume does not cover) is fixed separately by #18172, which teaches the aftermath to end the ask cancelled and advance an `await_action` checkpoint.
- **Certificate.** These Turns have no `ma_turn` row, so only the wake-recovery scan can wake them, and its `findPending` and `claim` select only scan-pending heads whose `wake_retry_at` is due (`JdbcWakeRecoveryStore.java:91-132`). The wake-owned park therefore rides the 3a due-time stamp instead of a new scan branch: the seal records `wake.pending` with `dueAt` set to the park's wake time, so the existing scan and its index claim the head when the park is due. The Store reads `wake.pending` only as "load this head at `dueAt`", which is what the park needs, and the scan's journal replay counts the attempted wake input as pending too. A writer acquisition clears the certificate but keeps `is_wake_pending` and caps `wake_retry_at` at its backstop pace (`JournalWriterLifecycle.java:274`), so a writer that clears it and then crashes leaves the head to the existing scan. Without the stamp it would not: a parked seal writes `is_wake_pending = FALSE`, and the acquisition leaves the head unscanned (confirmed, pinned by `WakeSealStampTest`). `parkedTurn` gains `owner: 'wake'`, kept in a nullable `ma_session_head.wake_seal_parked_owner` column that the same seal UPDATE writes and the acquisition clears; per this module's rules the V1 baseline is edited in place and no migration is added. The Store's rule that a parked Turn cannot share a wake-pending seal becomes "a park claims a wake exactly when its owner is `wake`": a coordinator park must not claim one, and a wake-owned park must, or nothing would ever load it. The Harness sends that shape only when the writer grant advertises the new `wakeActionParking` bit, which the control plane advertises together with `actionParking`, and park eligibility requires that bit in its first pass and in the recheck under the gate. As in S2, the Store does not read the bit: an older control plane never advertises it, so it never receives the shape.
- **Wake sources.** Decision: on a cache miss, `ACTION_RESPONSE` delivery loads the Session (`doResolveAction`), and that load must be a passive takeover load. For a Workspace Session it is (confirmed, see §4.7). A Session with no Workspace never parks, because it has no approval policy (P0), so the plain load decision delivery sends it never meets a park. Cancellation needs no step (confirmed): the public and Web Shell Turn cancel requires an `ma_turn` row, so a wake Turn is cancelled only through its source's own Harness operation (an automation run's `cancel_run`, a child run's stop) or the Session's close, each sent after a load of its own, and that load wakes the park; a plain load attaches such a Session, pinned by the Harness test "attaches a Session whose wake Turn died in its approval wait through a plain load". Approval-mode changes: the policy change is one SQL transaction that unparks `ma_turn` rows and loads nothing (`AgentSessionPolicies`), so it also sets the head's `wake_retry_at` to now in that transaction, and the scan claims the head on its next pass. That transaction first passes the busy gate, whose exemption today requires the certificate to match exactly one active and one parked `ma_turn` row (`AgentActionParking.certificateMatches`). A wake-owned certificate is proved instead by no active `ma_turn` row, with the same seal-revision, approval-revision and no-foreign-requested-Action checks, which keeps the parked wait the Session's only live work. Expiry: the stamp's `dueAt`.
- **Eligibility details.** Eligibility admits exactly what the recovery arm resumes. The source must be one of the four above, through one predicate that the pump's resume and park eligibility share. The plan must be native: an extension command step on a wake Turn stays resident, because the pump does not resume one. The unsettled-input term changes shape: the pump owns wake inputs, so the Session's unsettled prompt inputs never hold the wake Turn's own and must be empty for it, while a second wake input still refuses at the gate, which reads every pending input.
- **Control-plane reads keyed on Turn rows.** Two reads treated an active `ma_turn` row as the sign of a parked Turn, and a wake Turn has none. A native-file Turn records its Runtime cleanup as owed before it reaches the approval wait. (1) The cleanup-debt scan skips a Session with an active Turn row and would otherwise cleanup-load a wake-parked Session, which reopens the park and parks again after the idle period, every scan. It now also skips a head whose current seal carries a park certificate, the same way it already skips one whose seal certified a background hold: the resumed Turn releases its own cleanup when it settles. (2) The recovery view counted that owed cleanup as unsettled work and, with no Harness evidence for a sealed Session, fell through to `operator_required`. A current wake-owned park certificate now certifies the parked Turn's own obligations, as a background certificate does, so the view reads `ready`, the same as a Session sealed with a deferred wake input that the scan loads at its due time.
- **Relation to 3a.** If the same Session also has a deferred, unattempted wake input, this increment still does not park, because the "only pending input" condition is unchanged.
- **S4b: channel and `pr_event` Turns.** Both sources join the predicate that the pump's resume and park eligibility share, so each parks and recovers exactly as the four sources above do. The certificate, the seal rule, the grant bit and the two control-plane reads never look at the source, and the wake-recovery scan already counts both sources, so the control plane does not change. Only what follows the Turn differs. A channel Turn that died in its approval wait went to the channel funnel, which may not mint a second user record: the funnel kept the Action resolvable (`held`), and once the Action was final it advanced the wait and settled the Turn cancelled without a reply, so an Allow never ran the tool. The pump now resumes that wait first, and a resumed Turn that completes plans its reply on the ordinary settled path; the open-path reconcile still covers a crash between the settle and the plan. A `pr_event` Turn is private-only and plans nothing; its crash used to reach the generic aftermath. The channel funnel still settles every wait the pump cannot resume. Session-message Turns, whose consumption the message relay owns, stay excluded.
- **Surface.** The Harness pump and eligibility, the Store seal validation, the approval-mode-change transaction and its busy-gate proof, the grant bit, the cleanup-debt scan and the recovery view.

### 4.5 S5: Hooks

- **Existing basis.** `hook_execution` records persist the input and result of every PreToolUse/PermissionRequest under `${promptId}:${callId}`, and `orderedHookInput` recomputes the effective input from them without rerunning the Hook. The waiting call has already finished PreToolUse and PermissionRequest before it asks for a human decision.
- **Runtime owner** (amended 2026-11-24; from here to the end of §4.5, code references are to `main` at `f2c689c812`). A Hooks Session's native batch does not run on a Turn-scoped Runtime session. The tool Turn takes the Hook owner's broker (`this.mcp?.broker ?? this.hooks?.broker ?? …`, `hosted-workspace-tool-turn.ts:2524-2532`). So the saved plan's `runtime.runtimeSessionId` is the Hook owner's id, the live path acquires through `hooks.acquire()` (`:3403`), and it owes no Turn cleanup debt, because the Hook owner holds the Runtime. Park teardown closes the Hook owner in its owners step (`hooks.close({ terminal: false })`, `hosted-harness-session.ts:5486`), before the lease step. What survives that close depends on the kind of owner:
  - **Config-scoped owner** (`extensions-components-<digest(sessionKey, configRevision)>`). An active extension bundle supplies the Hook catalog. The non-terminal close hands back only the mount and keeps the row re-acquirable under the same id (R13-1), and the next load recomputes that id. The configuration revision cannot change during a park (S7, confirmed). The owner check in `resumeSavedNativeBatch` (`broker.runtimeSessionId === plan.runtime.runtimeSessionId`, `:4337`) therefore passes. The method then reacquires with the plan's binding and generation and owes no Turn cleanup (`:4360`). This is the same path S7's command-step resume takes on a Session with a Hook catalog.
  - **Activation-scoped owner** (`hooks-activation-<digest(activationId, epoch)>`). The Session definition pins the Hook catalog. The close releases the owner's Runtime session (`broker.release({ drain: true })`). On lifecycle v1, the next load derives a new id from its own activation and releases earlier owners on its first acquire, so the owner check declines. Such a wait is not recoverable after a park, nor after a crash. Lifecycle v2 reuses the recorded id, but it is not known whether a released row can be re-acquired with its recorded binding pins.
- **Decision.** S5 admits a native Hooks wait only on a config-scoped Hook owner.
  - The term goes into the shared shape function. The producer, park eligibility and all three recovery entry points (the takeover load, the resident redrive and the wake pump) therefore agree.
  - Any other Hook owner refuses with a new typed reason, `hooks_activation_owner`, both at capture and in the shape function, and P0 counts it.
  - Keeping an activation-scoped owner across the park would need two changes. The owners teardown step would have to skip that owner's release during an Action park, and the resumed batch would have to adopt an earlier owner. Both change the invariants `releaseEarlierOwners` relies on (#13856). This is deferred until the P0 counts show that `hooks_activation_owner` is a real share of load.
  - A Hooks Session that also has MCP keeps refusing as `mcp` until S6, because its Hook owner shares the MCP broker.
- **Change.**
  1. Producer: for a config-scoped owner, lift the Hooks half of `(this.hooks || this.mcp)`. For each call, the continuation records the Hook occurrence IDs completed before the wait, with their result digests.
  2. Recovery: `resumeSavedNativeBatch` accepts a Hooks Session with a config-scoped owner and reacquires it as described above. Completed occurrences are read back through the existing saved-output path. An occurrence that has a record but no result is uncertain, and recovery declines (G3 §4.2 step 5). PostToolUse after an Allow is a new occurrence, proven not started before execution, and runs normally.
  3. Takeover: `takeover` (`!lifecycle && !session.hooks && takeoverFlags`, `hosted-harness-session.ts:8553`) stops excluding `session.hooks` unconditionally and defers to the shared eligibility function. Every non-lifecycle load of a Hooks Session runs an `answerResumedTurnCalls` pass (`:8584-8608`). That pass must skip when a recoverable native continuation exists: it answers interrupted calls as "never run", which would permanently destroy the continuation, the same hazard as command-step R9-1. As with `commandStepPark`, key the skip on a predicate computed before the takeover arm, so a bare load cannot destroy the continuation either.
  4. Eligibility: the waiting call's PreToolUse and PermissionRequest have both completed, or are provably not configured. The Phase 1 "no Hook operation in flight" condition is unchanged.
  5. Replay: the continuation already holds each call's effective input after its Hooks (`request.call`). A restored call whose PreToolUse and PermissionRequest occurrences completed skips `decideHookInputs` and uses that input. Today `decideHookInputs` runs for every request whenever `this.hooks` is set, restored requests included (`hosted-workspace-tool-turn.ts:5890`). Deciding again would compare the Hook-modified input with the original Hook plan and raise `HostedHookInputConflictError` (`:4053`).
- **Confirmed: startup Hooks do not refire.** The model driver fires SessionStart and UserPromptSubmit only when neither `resumeFromToolResults` nor `resumeModel` is set (`hosted-harness-model.ts:842`), and a resumed native batch sets `resumeFromToolResults`. The model test "resumes tool results without refiring startup Hooks or reapplying their rewrite" pins this. Neither Hook fires on resume, even when SessionStart has no completed occurrence, so G3's "without reapplying startup Hooks" holds.
- **Confirmed, contrary to the expectation: resumed rounds see the accepted Prompt, not the Hook rewrite.**
  - The Harness commits the accepted Prompt parts as the Turn's user record before the driver runs (`hosted-harness-session.ts:4335-4355`).
  - The driver applies UserPromptSubmit's `updatedPrompt` and the startup Hooks' additional context to the live request only. For the first Prompt it commits neither; only queued messages are committed with their rewrite (`hosted-harness-model.ts:1166`).
  - The same model test shows that the live request carries the rewrite while the resumed history holds only the accepted text. The Harness test below shows that the resumed history's user record is the accepted Prompt.
  - A crash-recovered Turn behaves the same way, so park and crash stay equivalent. A resumed round still differs from the live one whenever these Hooks changed the Prompt. S5 accepts this (decision 7).
- **Confirmed on a config-scoped owner: the mount handback and the resumed owner.** The Harness test "hands back a config-scoped Hook owner mount at park and resumes its Hooks on the same owner" parks an extension command step on a Session with PreToolUse and PostToolUse Hooks.
  - At the park, the owner close hands back that owner's mount once and releases no row under its id.
  - After the Allow, the resumed batch reacquires the plan's binding and generation on the same owner.
  - The two PreToolUse occurrences completed before the wait, for the `skill` call and for its command step, are read back without rerunning. The approved step's PostToolUse runs once on that owner.
- **Still to verify in S5's own tests.**
  - The plan parked above is a command step, so its batch had no dispatched native-file work. S5 must still show that the Phase 1 "unsettled Runtime work" term excludes every native batch whose mount handback R14-2 would refuse.
  - The resumed run fired no PostToolUse for the outer `skill` call. No comparison with an unparked run has been made yet.
- **Surface.** Harness only, but it touches the G3 producer and recovery arms, so the G3 A3/A6 fault gates need Hook variants.

### 4.6 S6: MCP

- **Dependency.** Phase 2's `qwen.managed-agent.runtime-broker.mcp-parking.enabled`. Only when connections and the catalog are retained across the suspension, and the new writer reacquires them by durable owner identity, can the MCP tool definitions seen after a cold load be guaranteed to deep-equal those saved in the continuation. Otherwise do not park: discovering after a park that recovery fails is worse than staying resident.
- **Change.** The producer admits MCP tools into the allowlist, and the continuation records the MCP configuration's durable revision and catalog pin. Eligibility requires MCP parking to be enabled, the current grant to reacquire the same owner, and every earlier MCP call in the batch to have a committed result. If any call is still in flight, the Phase 1 "unsettled Runtime work" condition already refuses. The waiting MCP call has not been dispatched, so an Allow dispatches it exactly once.
- **Continuation and catalog.** The continuation parser's tool allowlist (`hosted-approval-continuation.ts:55-63`) and the restored requests, which hard-code `mcp: false` (`hosted-workspace-tool-turn.ts:4433-4448`), learn MCP calls and their MCP request identity. `ParkedMcpReclamationJob` must skip an owner whose Session holds an Action park certificate: `JdbcParkedMcpOwners.sealedFor` currently checks only `state = 'SEALED'`, so S6 adds the parked-certificate predicate and a reclamation test. That keeps the catalog the continuation pins the one the Session reacquires; a reclaimed owner would turn every pin check into a decline.
- **Invariant.** MCP calls have no prepare/receipt protocol like native files, so a dispatched call is never replayed, and any call with an uncertain dispatch state declines.
- **Surface.** The Harness producer and recovery arm, the Broker's MCP owner reacquisition, and `JdbcParkedMcpOwners.sealedFor` / `ParkedMcpReclamationJob`, with a test that an Action-parked owner is not reclaimed.

### 4.7 S7: extension command-step approvals

- **Change.** The command-step wait registers a real freeze. Park eligibility accepts `plan.commandStep` under the Session-shape terms the takeover arm requires for it: extensions are enabled and the Session has a tool owner. These terms become one shared function that both call, beside the native one. The Hooks relaxation applies only to command-step plans, consistent with `extensionsCommandStepTakeover`, and does not depend on S5. A command step on an MCP Session stays resident until S6, although recovery admits it. Eligibility needs no configuration-revision term; see below.
- **Confirmed.** The load during decision delivery carries the takeover flags for a Workspace Session and takes the parked Turn over. The connector test `resolvesActionsThroughAuthorizedColdAndCachedWorkspaceAttachments` asserts the passive recovery flag on the cold loads decision delivery sends, and the Harness test "resumes a parked approval through the passive load decision delivery sends" shows that a load with only that flag resumes a parked approval through the takeover recovery arm.
- **Confirmed.** A bare load of a parked command step answers 409 `turn_unsettled` and writes nothing to the journal, so the R9-1 guard holds. The extension configuration cannot change while the Turn is unsettled: every route that changes the extension configuration refuses while a Turn is active, and a parked Session attaches only through a takeover load, which makes the Turn active again. The revision mismatch `resumeSavedNativeBatch` (`hosted-workspace-tool-turn.ts:4328`) refuses therefore cannot arise during a park; if it did, it would surface as a retriable 503, not a typed decline. The Harness test "parks a command-step approval that a bare load leaves unanswered and the decision-delivery load resumes" in #18166 pins both.
- **Surface.** Harness only.

### 4.8 S8: `uncaptured` batches

- **Shell before dispatch (S8a).** This item has the highest value: most approvals on a Shell profile are `run_shell_command`. G3 requires Shell before dispatch to build its own positive continuation and ownership evidence. The pre-start checks are confirmed by tests, checked against `main` at `7862c3eef3`:
  - **The Broker needs no new semantics (confirmed).** A Tool v3 Shell reservation is prepared with `dispatch = false` (`RuntimeBrokerService.java:995`). Preparing again under the same key and reference returns the original reservation without dispatching it. A changed `publicationId` or payload digest under that key is refused as `runtime_idempotency_conflict` (`:1654`). After the execution settles, the same key answers with its original record.
  - **Public-children Sessions are already covered (confirmed).** Since #15171, a Session with `publicChildAgentsVersion = 1` captures Shell before dispatch. The producer skips the `shell_profile` refusal for it (`hosted-workspace-tool-turn.ts:4532`) and records each Shell call's `publicationId` (`:4620`). `resumeSavedNativeBatch` checks that identity and re-prepares the saved `runtimeCallId`, digests and `publicationId` through `prepareV3` (`:4435`, `:6081`). Park eligibility has no Shell term, so such a wait already parks. A test parks one, cold-loads it and allows it, and sees one `prepareV3` with the saved identity and one execution.
  - **That path parks before its own G3 review (decision 8).** #15171 built it for crash recovery and #18115 made it parkable, but no design has checked it against G3's cases. S8a's G3 extension design treats it as existing evidence to validate, not as new work. Its §7 cases must pass before any deployment turns on `action-parking.enabled`, and they do not wait for the rest of S8a.
  - **The gate's unit cases pass (confirmed).** All four outcomes complete as §7 requires, both after a park and after a Harness death. A background Shell approval also parks and resumes: after the Allow, every `child_run` record belongs to the one reserved execution, so no second process starts. The real-process MySQL 8.4 case of §7 is still owed before the switch is turned on.
  - **What S8a still covers.** Shell-profile Sessions without public children still refuse as `shell_profile`. The reader treats a saved plan as a Shell plan only when it carries `publicChildModel` (`hosted-approval-continuation.ts:248`, `:288`), which only public children record (`hosted-workspace-tool-turn.ts:4627`). These plans therefore need another way to be recognized. Still to verify: which Sessions fall here in practice.
  - The slice still extends the G3 contract, so write a separate G3 extension design before implementing; it extends existing evidence rather than adding Broker semantics. Dispatched Shell keeps its refusal.
- **Plans over 64 KiB.** Not supported yet. The P0 refusal counts show how often they occur; consider storing plans as non-inline resources only if the rate is significant.
- **Still excluded.** `todo` batches, batches with no Runtime, unsupported tools and undigested calls keep their refusals; S8 covers only Shell before dispatch and oversize plans.
- **v1/v2.** Not supported. They exist only in waits written before the upgrade, G3 already states that legacy reconstruction needs its own validation, and the benefit shrinks to zero over time.

## 5. Decisions and rationale

1. **Cold recovery first, parking second, delivered in the same slice.** A park is a controlled crash, so no shape may become parkable ahead of its crash recovery.
2. **P0 first.** Every later slice relaxes eligibility; with two copies of the conditions, every relaxation is another chance for parking and recovery to disagree.
3. **Wake-owned parks are woken by the scan, without new `ma_turn` rows.** Creating dispatch rows for wake Turns would change their ownership model and every relay and pump invariant built on it. Reusing the wake-recovery scan costs one column and one query term.
4. **MCP parking is tied to Phase 2 MCP parking.** Without a retained catalog, an MCP park cannot prove its definitions are unchanged at recovery.
5. **The child slice does not include parent-waits-on-child.** The latter is another kind of wait (no Action, no approval continuation); bundling it would widen what G3 must prove.
6. **S5 parks only on a config-scoped Hook owner.** Park teardown releases an activation-scoped owner's Runtime session, and on lifecycle v1 the next load cannot recompute that owner's id. Keeping such an owner would change the earlier-owner release invariants. S5 instead counts it as `hooks_activation_owner` until measurement shows it is worth doing.
7. **A resumed Hooks Turn continues on the accepted Prompt (S5).** UserPromptSubmit's rewrite and the startup Hooks' additional context reach only the live request, so a resumed round sees the accepted Prompt (§4.5, confirmed). S5 accepts this and adds no refusal for it.
   - The same already holds wherever a Hooks Session's history is rebuilt from the journal, from reading the code at `f2c689c812`. A later Turn reads the accepted Prompts of earlier Turns. When today's Hooks crash recovery resumes a Turn's model rounds, it starts from the accepted Prompt (`hosted-harness-session.ts:9156-9182`).
   - Personal-memory recall context already behaves this way in the parks that ship today: it reaches only the live request and is not recalled again on resume.
   - Refusing such Turns would keep most context-injecting Hooks Sessions resident, while protecting nothing that those paths do not already expose.
   - Committing the rewritten first Prompt, as queued messages already are, would change every later Turn's history. It is follow-up work outside this design.
8. **Public-children Shell waits keep parking, with no temporary refusal (S8a).** They already park (§4.8, confirmed), although no design has checked that path against G3.
   - Parking adds no recovery path. The same cold recovery already serves a Harness that dies in the wait, so decision 1 holds.
   - Parking does make that path run for every idle Shell approval instead of only after a crash. So its S8a cases in §7 gate `action-parking.enabled` (§8), ahead of the rest of S8a.
   - A park-only refusal would hold the same line, but as temporary code in a default-off feature, which those cases would remove anyway. Add it only if the switch has to be turned on before they pass.

## 7. Verification plan

Each slice inherits every case of parent §11 and adds:

- **Agreement.** For the same journal state, park eligibility and the cold-recovery arm give the same answer. Cover the shape the slice opens and the neighbouring shapes that stay excluded.
- **Crash equivalence.** First run "SIGKILL during the wait → another Harness generation takes over → decide" for the slice's shape and confirm cold recovery is correct; then run "park → cold load → decide". Both must yield the same journal outcome.
- **P0**: a Session with no Workspace opens no Action, even for a memory write, so it never registers a wait to park.
- **S1**: after an image-only Prompt parks, is cold-loaded and is allowed, and also after its Harness dies in the wait and a fresh Harness takes it over, the tool runs once and the first model call after resume restarts from empty text with the original image in its history.
- **S2**: a background terminal arriving during the park unparks and resumes the Turn, and the notification is delivered after the Turn settles; the tool and the notification each happen exactly once. Cover staging before the seal, between the seal and the CAS, and after the CAS.
- **S3**: a child Session's approval parks with no approval revision and, after a cold load, the allowed tool runs once; after its Harness dies in the wait, a fresh Harness completes it the same way. A parked child Turn that outlives the relay's message-turn wait is still waited on; a single-question child batch hands its mount back after cold recovery (`questionChild`); a session-message step that meets a closing or cold-open-busy Session spends no attempt.
- **S4**: Turns started by a monitor notification, a loop fire, an automation run and a child result each park and complete through decision, mode change and expiry, and through cancellation where their source has one, without the coordinator; a writer that clears the certificate and then crashes leaves the head to the scan; the pump no longer settles a wake input at `await_action` as a crash. A wake-parked Turn's owed cleanup neither reaches the cleanup-debt scan nor turns the recovery view to `operator_required`. S4b: a channel Turn and a `pr_event` Turn each complete through a decision after a park and after their Harness dies in the wait, and a completed channel Turn plans exactly one reply.
- **S5**: completed PreToolUse/PermissionRequest occurrences are not rerun after resume (asserted by occurrence counts); an occurrence with a record and no result declines; SessionStart and UserPromptSubmit do not refire; separate cases cover a PreToolUse `updatedInput`, a PermissionRequest `decision.updatedInput`, and a sibling batch whose Hooks ran for siblings before the first approval. An extension-bundle Hook catalog (config-scoped owner) parks and resumes. A Session-definition Hook catalog (activation-scoped owner) refuses `hooks_activation_owner` at capture, at eligibility and at each of the three recovery entry points. A Turn whose startup Hooks changed the Prompt parks and resumes on the accepted Prompt. For a native batch, the park's mount handback succeeds, and a PostToolUse after an Allow runs once on the resumed Runtime session.
- **S6**: with MCP parking on and off, the Session parks only when it is on; after resume the tool definitions are equal and no dispatched MCP call is replayed. An Action-parked owner survives the reclamation job's idle sweep with its catalog intact.
- **S8a** (public-children Shell, which already parks; decision 8): a Shell approval completes through Allow, Deny, expiry and a mode change that allows on the user's behalf, each both after a park and after its Harness dies in the wait. Allow and the mode change re-prepare the saved reservation and execute once; Deny and expiry execute zero times. A background Shell (`is_background`) approval either parks and resumes without starting a second process, or refuses with a typed reason at capture and at eligibility.
- **Real process and MySQL 8.4**: each slice puts at least one "park → new Harness generation → decide" case into the required CI tier; H2 results cannot replace it.

## 8. Acceptance criteria

- After each slice ships, a wait outside that slice's conditions behaves exactly as before, and existing test results are unchanged.
- A newly opened shape parks cleanly after one idle period. For each of decision, cancellation, mode change (where applicable) and expiry, one cold recovery completes the original Turn with unchanged Action, Prompt and batch identities; Allow executes exactly once and Deny zero times.
- The same shape, when the Harness crashes during the wait, also continues through cold recovery instead of being settled as failed.
- The real-process, MySQL and fault cases of §7 pass in CI, and the parent §7 measurements are complete, before any deployment turns on `action-parking.enabled`.

## 9. Open questions

None of these blocks development. Each of questions 1–3 is implemented with the default below first and revisited after measurement, and none of the later adjustments needs a protocol or schema change. Question 4 lies outside this design.

1. **Latency of changing the approval mode of a parked wake-started Turn (S4).** Once that path sets `wake_retry_at` to now, its latency is bounded by the wake-recovery scan interval (2s by default); a cancellation brings its own load.
   - Default: rely on the scan alone. Ordinary parked Turns are already redispatched by the dispatch sweep (1s), and the parent design treats an immediate kick after commit as a latency optimization, not a correctness requirement (parent §4.6).
   - Revisit if the measured latency is unacceptable: add a direct load kick after the commit, which is a single extra call.
2. **Minimum park duration for combined parks (S2).** A Session with frequent background terminals may lose more than it gains from repeated parks and reloads.
   - Default: none. This is tuning, not correctness, and the feature is default-off.
   - Revisit if measurements show repeated park-and-reload churn: add a Harness eligibility constant. The certificate and the control plane are unaffected.
3. **Share of plans over 64 KiB and of Shell before dispatch in real load.** This affects only whether S8 is worth doing, and when; P0 through S6 are unaffected. It is answered by the P0 refusal counts once `suspensionStats` is exposed to operators (see P0).
4. **Parking a parent Session that waits on a child result** (a non-goal in §2). There is no Action, so it needs its own wait proof and wake source (the child Turn's terminal). It is required for zero residency across a child-Session tree and needs its own proposal.
