# 面向 Qwen Code 之外程序的对等端点

[English](2026-09-10-peer-endpoint-sdk.md) | [简体中文](2026-09-10-peer-endpoint-sdk.zh-CN.md)

状态：与本文档一同实现。新增 `@qwen-code/sdk/peer`：为不是 Qwen Code 会话的程序提供一份独立的跨会话协议实现。

## 问题

[Cross-Session Protocol](../users/features/cross-session-protocol.md) 描述了 Qwen Code 之外的程序要被发现、被联系、能收到回应所需做的一切：写注册记录、绑定 inbox、出示正确的令牌、按格式组帧、把回执当作状态迁移来读。但还缺两件事。

### 没有人实现过这一页

协议的每个读写方都是 Qwen Code 自己，这一页也是照着那份代码写的。没有任何东西证明它完整、没有歧义。只存在于代码里的规则——记录文件名如何与 PID 对应、回执出示哪个令牌、inbox 何时改用兄弟 socket 名——可能在文档里缺失，而直到某个外部程序在真实会话上失败之前都不会有人发现。

### 每个使用方都得手写协议

第一个外部使用方是一个指挥用户所有会话的语音前端（#10118），它需要的正是这些：出现在目录里、以受信 controller 身份发指令、收到回应。没有现成的库，它就得在自己的仓库里重新实现：从 `/proc` 读启动令牌、原子写记录、socket 放置、auth 行、消息 id 语法、回执状态机——每一处都是和对端会话产生分歧的机会。

## 设计

**第二份实现，而不是包装。** 该模块依据协议文档、只用 Node 自带模块编写。Qwen Code 的 core 不是 SDK 的运行时依赖，包装它也验证不了这一页。构建会拒绝任何含运行时依赖或 Qwen Code 源码的产物。

**与 Qwen Code 双向对测。** 一组一致性测试在同一进程里让端点和 Qwen Code 自己的注册表、inbox、目录与发送路径互相运行：双方都能列出并联系到对方；两个方向发送的帧都被解析并得到应答；一条合并的 dropped 回执能结算一批消息；按用户铸造方式得到的 controller 令牌会被认出，伪造的不会。同一组测试把恶意构造的帧、记录文件和名字喂给两份实现并要求判定一致，并把文档公布的每个上限钉到 Qwen Code 的常量上。这里出现分歧，意味着两份实现之一或文档本身有错。

**独立子路径，仅限 Node。** `@qwen-code/sdk/peer` 是单独的入口，形态与 transports 入口相同。默认入口和 daemon 入口会被打包进浏览器，必须不含 Node 内建模块；本模块需要 socket 与文件系统。

**共享记录名空闲时就用它。** 端点写 `<pid>.json`，这是所有带注册表的 Qwen Code 版本都读得懂的名字。该名字被占用时——被同进程的另一个端点、被另一个命名空间或机器上 PID 撞号的记录、被更新 schema 的记录——端点改写一个新铸的 `<pid>-<8 hex>.json`，而不去覆盖可能仍然存活的记录。只有能证明是同 PID 的更早进程遗留的记录才会被替换。

**只做发现、接收、发送与跟踪。** inbox 只接受一个令牌，即端点自己的。它不带 Qwen Code 会话为保护自己而设的审阅机制：没有限流、没有 hold、没有 controller 授权。加入目录的程序自己决定如何处理收到的消息。它会记住已应答过的消息 id，这样发送方重试同一 id 时得到同样的答复，而不是让程序把消息处理两遍。

**从不删除别人写的东西。** 列举时读目录并应用文档里的存活规则，但从不删除任何记录或 socket 文件。清理已死会话的记录是 Qwen Code 会话的事；一个只是加入目录的程序无权删除其他进程的文件。

**信任只来自 controller 令牌。** 程序没有能如实声明的审阅类别，所以它发出的消息默认会被 hold 等待审阅。用户通过铸造 controller 令牌授权投递，端点用它代替接收方自己的令牌出示。记录里的 `kind` 和 `name` 换不来任何东西，文档也明确这么写。

**生命周期跟随程序。** 打开的 inbox 会让进程保持运行，就像一个服务器。关闭时删除记录和 socket，退出钩子在 `process.exit` 时做同样的事。端点不安装信号处理器，因为那会改变程序的退出方式；未关闭就被杀掉的进程会留下记录，Qwen Code 会话在其启动令牌证明进程已不在时将其清除。

**在 Linux 上，没有身份就不写记录。** 读不到启动令牌或 PID 命名空间时，`start()` 直接失败，而不是发布一条读者既无法信任、也永远清理不掉的记录。

## 对协议文档的修改

照文档文本实现时发现有两条规则文档没有明说，现已写进 "Writing your own record"：

- 在 Linux 上，`procStart` 与 `pidNs` 是必需的。每个读者都会拿记录的 `pidNs` 和自己的比较，缺少它的记录永远不会被列出，也永远不会被清扫。
- `<pid>.json` 已被占用时，写入方只有在能证明该文件是同 PID 的更早进程遗留的——`pidNs` 相同、boot id 相同、start ticks 不同——才替换它，否则改写 `<pid>-<8 hex>.json`。读者两种名字都接受，而挡路的那条记录可能属于另一命名空间或另一台机器上的活进程。

在一致性测试覆盖到的其余方面，文档、Qwen Code 与端点之间没有发现分歧。

## 不做的事

- 多个端点共用一个 inbox。同一进程里的两个端点各自绑定 socket、各自发布记录。
- Windows：目前没有对应的 socket 放置方案，`start()` 以 `unsupported-platform` 失败。
- 为程序自己的 inbox 提供限流、hold 等保护。
- Python 与 Java SDK 中的对应实现。

## 验证

- 帧、标签、注册表读写、目录、客户端、inbox 与端点的单元测试。
- 上文描述的一致性测试。
- 钉住该子路径导出与 `package.json` 条目的公共面测试。
- 构建时检查产物不超预算、不含任何运行时依赖，且类型声明不引用任何内部包。
