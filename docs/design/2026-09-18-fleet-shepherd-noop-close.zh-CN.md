# Fleet Shepherd：关闭合入后不会改变任何内容的 bot PR

[English](2026-09-18-fleet-shepherd-noop-close.md) | [简体中文](2026-09-18-fleet-shepherd-noop-close.zh-CN.md)

日期：2026-09-18（2026-09-19 在第 1–2 轮评审后修订）
状态：提议中 —— 由 [#12150](https://github.com/QwenLM/qwen-code/pull/12150) 实现；等待评审

## 问题

autofix 机器人为每个它认领的 issue 开一个 PR。当另一个 PR 先把同样的修复合入
`main`，这个 bot PR 就变成了空壳：合入它不会改变任何一个字节。GitHub 仍把它显示为
普通的 open PR，于是评审机器人继续评审它，autofix 循环继续在上面发「无需改动」的
轮次，直到某位维护者注意到并手工关闭。

自 7 月以来未合并即关闭的 54 个 bot PR 中，有 45 个是人工关掉的。triage 的前置阶段已
经会在开 PR 的那一刻关闭整份差异已被其关联 issue 的已合入修复覆盖的 bot PR（#10788、
#11018），但之后才变成 —— 或之后才被识别为 —— 空壳的 PR 没有任何环节去关。9 月的三个
这样的空壳展示了代价：

| PR     | 可被判定为空壳的时刻 | 人工关闭的时刻    | 以空壳状态滞留 | 此后 autofix 机器人发的评论 |
| ------ | -------------------- | ----------------- | -------------- | --------------------------- |
| #11379 | 2026-09-08 11:19Z    | 2026-09-08 22:56Z | 11 h           | 8                           |
| #11376 | 2026-09-09 14:47Z    | 2026-09-17 11:26Z | 188 h          | 5                           |
| #12109 | 2026-09-17 16:09Z    | 2026-09-18 02:47Z | 10 h           | 2                           |

「可被判定」指第一个 tree 与某个 `main` 的 tree 相同的 head 提交 —— 也就是下文的判定
能看见它的那一刻（见「哪个 `main`」）。

triage 跑完之后，现有自动化中没有任何环节会关闭这样的 PR。autofix 的 agent 车道没有 GitHub 写凭据
（它在 #11376 上自己就是这么说的），循环的推送与报告步骤持有 bot PAT 但没有关闭
路径，`stale.yml` 要等 60 + 30 天才动手。Fleet Shepherd 每 15 分钟用 bot PAT 走一遍
bot 车队，并且已经拥有车队的其它杠杆（冲突派发、陈旧 base 同步、liveness、接管
自动释放），所以它是再加一个杠杆的自然位置。

## 判定：GitHub 自己的试合并

对每个可合并的 PR，GitHub 都会构建一个试合并提交，在 GraphQL 中以
`potentialMergeCommit` 暴露。它的第一个父提交是 base 一侧；第二个父提交是 head 一
侧，探针要求它等于车队快照的 head —— 否则读作 `head-moved` —— 因此「tree 相等」的
结论在结构上绑定于通知将要引用的那个 head，不受 GitHub 重建时机影响。若试合并的
tree 与其 base 父提交的 tree 相同，合入这个 PR 就不会增加任何内容 —— 那个 `main` 已
经包含分支提出的每一个 hunk。每个可合并的 `autofix/*` PR 一次 GraphQL 读取，无需检
出。

这条配方在自动化之前先对照历史记录做了核验：

- 上面三个空壳全部读出 tree 相等（它们同时也显示 `changed_files = 0`）。
- 当时 open 车队中的每一个可合并 PR 都读出有变化，与本地
  `git merge-tree --write-tree origin/main <head>` 的结果一致。
- #10452 是一个作为另一个 open PR 的*重复*而被关闭的 bot PR，它读出有变化。与仍然
  开着的东西重复不是空壳；它仍然是人工裁决，本杠杆不得碰它。

**哪个 `main`。** 是构建试合并时所对照的那个 `main`，不一定是今天的。GitHub 在 PR 的
head 移动时构建试合并，而只在部分时候才对着更新的 `main` 重建它：在 open 的 PR 中观察
到它会在某些 `main` 推送之后、head 没有移动的情况下成批重建（有一个 head 自 7 月起就
没动过的 PR，带的是 9 月构建的试合并），但并不可靠：2026-09-19 那天，15 个 bot PR 里
有 6 个在一次 `main` 推送后两分钟内被重建，另外 9 个则完全没有；而前一天 16 个里有 15
个落后于 `main`，最多落后 21 个提交、约 60 个 shepherd tick 的读取。重建由什么触发没
有文档说明，也没有找到。因此判定结论是「相对构建试合并时的那个 `main` 是空壳」，探针
会读出那个 base 提交，让通知和关闭评论可以引用它。由此有两个推论：

- *出生即*空壳的 PR（#11379：PR 打开时 `main` 已经有了这个修复）在下一个 tick 就能被
  看见。
- 因为另一个 PR 之后才合入而*变成*空壳的 PR，要等 GitHub 下一次重建它的试合并才能被
  看见 —— 正常情况下不晚于它的 head 下一次移动之后的第一个 tick（如果 GitHub 还在构
  建试合并，则再晚一个 tick）：循环自己合并 `main`、一次冲突解决、或 shepherd 的陈旧
  base 同步。#11376 和 #12109 就是这样变得可见的：#11376 的修复在表中那个合并提交之前 2 小
  时 36 分就已合入 `main`；#12109 是通过它自己的冲突解决变成空壳的。之后它们分别滞留
  了 188 小时和 10 小时，这一段正是本杠杆消除的部分。

PR 对象上的 `changed_files == 0` 是更便宜但更弱的信号：它需要 `main` 已被合进分支，
所以会漏掉分支早于修复的「出生即空壳」，而 tree 比较能看见。

任何达不到「已证明 tree 相等」的答案，绝不会被当作空壳来报告或处理，也绝不会被报告
为「有差异」。它喂养的杠杆会关闭 PR，所以读取失败时 fail closed：推迟该杠杆，不关闭
任何 PR。该 PR 的其它杠杆不依赖探针，照常按普通 PR 处理，所以失效的探针不会把同步
杠杆一起拖垮。探针会说明它拿到的是哪一种「无答案」，因为失效的探针不能看起来和良性
等待一样：

| `NOOP_STATE`    | 含义                                                                                                                                               | 报告方式                                        |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `no-test-merge` | GitHub 还没有构建试合并（每次 head 移动都会重置它）                                                                                                | 仅行内备注 —— 良性                              |
| `head-moved`    | PR 的 head 自车队快照以来移动过，或试合并是用更早的 head 构建的（其 head 侧父提交不是快照 head）—— 无论哪种，结论都不是针对通知将要引用的那个 head | 仅行内备注 —— 良性；下一个 tick 会看到新的 head |
| `api-failure`   | `gh` 非零退出：PAT 权限丢失、限流、字段改名                                                                                                        | 行内备注、计数、带 `gh` 自己的错误发警告        |
| `unparsable`    | 响应不是 JSON、没有 `pullRequest` 节点、没有 head 或没有关闭事件计数，或试合并没有 tree / 没有 base 父提交（结构漂移）                             | 行内备注、计数、发警告                          |

失败按 tick 计数（仪表盘表头中的 `no-op probe failures`，tick 汇总中的
`noop_probe_failures`），并且每个 tick 发一条 `::warning::`、点名第一个原因，这样对
整个车队都失效的探针无法在逐行备注后面藏上几个星期。

## 杠杆

空壳关闭分两步、落在不同的 tick 上，两步都以机器人身份发出：

1. **通知。** 当探针证明空壳，且 PR 上没有机器人针对当前 head 的可用通知时，发一条
   双语通知：检测到了什么、对照的是哪个 `main` 提交；若 head 不再变动，PR 会在之后的
   某个 tick 关闭 —— 最早在通知发出 10 分钟之后，通常在约 20 分钟内；什么会让它顺延
   （本 PR 有在飞的 autofix 运行、状态不可读、每 tick 关闭上限）；`autofix/needs-human`
   会把它交由人工处理；以及 `autofix/skip` 可以保留它。`autofix/skip` 是车队级的
   退出开关，不只是本杠杆的：标签存续期间，该 PR 完全离开 shepherd 的快照 —— 没有仪
   表盘行、没有冲突派发、没有陈旧 base 同步 —— 直到标签被移除。标记：
   `<!-- fleet-shepherd noop-notice sha=<head> -->`，在 `NOOP_NOTICE_MAX_AGE_SEC` 之
   内按 head SHA 去重。
2. **关闭。** 在之后的某个 tick，若针对该 head 的最新通知处于其年龄窗口内、探针仍证明
   空壳、并且实时读取显示 PR 仍然开着且 head 未变，则关闭它，然后作为另一次写入发一
   条双语关闭评论。标记：`<!-- fleet-shepherd noop-close sha=<head> -->`。

两步之间的一次推送会移动 head，从而使通知失效并让这一对重新开始。重新获得差异的
head 则根本不会再进入这个杠杆。

**通知的年龄窗口。** tick 间隔不是契约：在连续 400 个定时 tick 之间的 399 个间隔里，
中位数约为 950 秒、最小 427 秒，而且评审实测到某个延迟 tick 结束 75 秒后其排队后继就被
放行 —— 从通知到关闭大约 2 分钟。所以通知承诺的反应窗口是按通知自身的时间戳强制执
行的，而不是从调度假定出来的。关闭要等到通知至少有 `NOOP_NOTICE_GRACE_SEC`（600）
秒。取 600 而不是一个调度间隔的 900，是因为真实间隔里 44% 小于 900 秒、只有 7.5% 小
于 600 秒 —— 取 900 会把将近一半的关闭推迟到第三个 tick，而对人没有任何好处，取 600
则大约每十次关闭有一次如此。早于 `NOOP_NOTICE_MAX_AGE_SEC`（86400）秒的通知已经用掉
了它的警示作用 —— 它经历了长时间的顺延，或经历了一次在通知发出一天多之后才被移除的
`autofix/skip` —— 因此视同不存在，先重新发一条通知，代价是多一个 tick。在这一天之
内，已有的通知仍然有效。存在但无法确定时间的通知会推迟该杠杆。

**每个 PR 至多一次。** 本仓库没有任何自动化会重新打开 PR，所以一个曾被关闭、如今又开
着的 PR，就是被人重新打开的 —— 无论当初是谁关的：本杠杆、triage 的前置阶段、还是某位
维护者（7 月以来的 214 个 bot PR 里恰好只有一次重新打开，是人做的）。此后该杠杆把这
个 PR 交还给人，无论是同一个 head 还是之后的任何 head —— 关闭评论里写明了这一点。证
据是 PR 自己的关闭事件，由探针在同一次 GraphQL 调用中计数（`CLOSED_EVENT` 的
`filteredCount`；`totalCount` 会无视过滤条件，把每个 PR 都读成曾被关闭）；它不依赖关
闭评论是否发出成功。这正是让「重新打开」成为下文陈旧结论风险的可用恢复手段的原因，
它也覆盖了有人恰好在本杠杆关闭之前的瞬间关掉 PR 的情形。关闭与其评论仍然是两次写
入、先关闭：捆绑的 `gh pr close --comment` 会先发评论再关闭，而为一次随后失败的关闭
发出的「已作为空壳关闭」评论是不实文字，并且每个 tick 都会重发一次。

**只作用于 autofix 分支。** 该杠杆只处理 `autofix/*` 分支。机器人账号下还有由人或其
它 agent 驱动的 PR —— 超过它 7 月以来 PR 的三分之一 —— 而这里没有任何手段能像看见
`review-address` 运行那样看见那些进行中的工作，所以一个暂时与 `main` 相同的分支（占
位、第一次推送）不该由本杠杆来关。三个作为动机的空壳都是 `autofix/issue-*` 分支。

**被搁置的 PR 豁免。** 带有 `autofix/needs-human` 的 PR 是循环停下来并交给人（合并 /
关闭 / 拆分 / 重新接管）的 PR。本杠杆既不通知也不关闭它：关闭会让它从只列 open 的
「等待人工」表中消失，并替它正在等待的那个人做了决定。仪表盘行仍显示
`no-op vs main`，所以人的决定只需一次点击。该标签在车队快照上检查一次（不再花任何
读取），并在任一次写入之前对实时标签再检查一次。

杠杆位于车队遍历中冲突杠杆之后、陈旧 base 同步之前，只在 `MERGEABLE` 快照上触发：
`CONFLICTING` 没有试合并，`UNKNOWN` 意味着 GitHub 仍在计算。已被证明完全包含在
`main` 里的分支应当关闭而不是同步 —— 同步只会换来在空差异上跑一遍 CI 和评审。它也有
意不等待 checks 结束：刚同步完启动的评审运行会把数小时花在空差异上，而关闭 PR 正是
取消它的方式。

护栏与冲突杠杆同类：

- 只有机器人自己的通知算数；人工粘贴标记不能把关闭提前。
- 评论历史跨所有分页读取并合并。GitHub 按从旧到新返回评论，所以只读第一页就永远看不
  到长线程里机器人自己的通知，会每个 tick 重发一次而永远不关闭。
- 本 PR 有在飞的 `review-address` 作业时，两次写入都会推迟 —— 它的推送会落到一个已关
  闭的 PR 上。杠杆通过列出*确实在跑*的 autofix 运行（按状态过滤：in progress、
  queued、pending、waiting、requested —— 通过 Runs API，其状态过滤在每个 gh 版
  本上都是服务端生效；`gh run list --status` 在 2.65.0 之前会被 gh 客户端的允许值列
  表拒绝 `pending`）并读取它们的 jobs 来发现它，每个 tick 只做一次，且只在某个被标
  记的 PR 即将写入时才做。找到的运行集合会回显到 tick 日志，使持续多天的顺延能指名
  它在等什么。各个状态的列表先去程、再回程各列一遍，
  全部列完之后才读取 jobs，所以在扫描期间只换了一次状态的运行 —— 排队的作业拿到了
  runner、或运行在两个作业之间重新排队 —— 会被两遍中的某一遍抓到。这条护栏看不见的有：
  几秒之内连换两次状态；以及尚不存在的 address 矩阵作业 —— 它是矩阵展开出的一个作
  业，要等所在运行的 `build-cli` 作业结束才会被创建，那已是运行选定目标几分钟之后；而
  且它的答案每 tick 只取一次，和车队遍历一样旧。address 作业会在完成环境准备之后、动
  到该 PR 之前，复查一次 PR 是否仍然开着，所以在关闭*之后*才走到这次复查的作业会自行
  停下。已经过了那次复查的作业则不在覆盖范围内：此时关闭会落在一个正在工作的 agent 头
  上，它的推送会落到一个已关闭的空壳 PR 上。这一点被接受 —— 窗口每个 tick 至多约一分
  钟，该 PR 不改变任何内容，PR 的 head 分支也仍然保留。
  任何读取失败或无法解析、运行 id 去重失败、以及任何满 100
  条的分页（截断会丢掉最老的运行 —— 也就是长时间的 address 作业），都视为忙碌状态未
  知：推迟，并且每个 tick 发一条指名 gh 首个错误行的警告。它有意不复用 shepherd 共享的 busy-set —— 那个集合取自最新的 50 个 autofix
  运行，而该 workflow 每小时启动约 60 个运行，所以承载 1–3 小时 address 作业的运行会
  在作业仍在工作时滑出窗口（2026-09-18 实际观察到：#11989 的作业运行于
  14:25–15:57Z，却在 14:36Z 那个 tick 之后就从 busy 行里消失了）。评论历史不可读同样
  会推迟该杠杆。
- 每 tick 关闭预算（`MAX_NOOP_CLOSES_PER_TICK`，3）只限制关闭 —— 通知不设上限 —— 并
  在实时读取之前检查。实时 `autofix/skip` 复查在两次写入之前都会执行，标签状态不可读
  或响应里没有标签列表时同样 fail closed（不写入）。
- 通知借助实时标签读取的响应载荷做写入前的状态与 head 复查：自车队快照以来被人关
  闭或推送过的 PR 不会收到通知（到被标记的 PR 走到写入时，快照可能已有半分钟之
  久）。
- 关闭前会重新读取实时 head；PR 已关闭或 head 已移动都意味着不关闭。
- 每次写入都经过 `act()`：dry-run 不执行任何操作，失败的写入绝不推进计数器或标记。
- 仪表盘行显示 `no-op vs main` 及杠杆结果。表头与 tick 汇总报告通知数、关闭数与探针
  失败数。

## 不在范围内

- **孤儿 PR。** 2026-09-18 当天 17 个 open 的 autofix PR 中有 10 个的关联 issue 已被
  人工关闭（多为已恢复的 CI 事故），但仍带有真实差异；#10455 的 issue 甚至是被另一个
  已合入的 PR 关掉的。它们不是空壳。剩余差异是否仍然需要是人工决定，本杠杆不碰它们。
- **与 open PR 重复**（#10452 的形态）—— 同样的原因。
- **关联 issue。** 空壳关闭不触碰 issue 及其 `autofix/in-progress` 标签；关闭评论请人
  工在 issue 仍开着时确认 `main` 已解决它。这不是回归 —— 今天人工关闭空壳时同样会留下
  这种搁浅 —— 把 issue 交还自动化是一项包含两半的后续工作（见下）。
- **更早看见之后才合入的重复修复。** 要在重复修复合入的那一刻就判定空壳，需要对着当前
  `main` 计算合并。GitHub 按它自己的节奏重建试合并，shepherd 又不做检出、不会自己计
  算。
- **阻止空壳的诞生。** 在 agent 写补丁之前，于新拉取的 base 上重新确认目标仍能复现，
  本可以彻底避免 #11379。那属于 `qwen-autofix.yml` 的 issue 阶段，是另一处改动。

## 约束与风险

- **结论的年龄等于 GitHub 最近一次构建试合并的年龄。** 杠杆自己控制的任何东西都约束不
  了这个年龄 —— 最坏情况是自最近一次 head 推送以来的时间 —— 所以被在飞运行顺延了数小
  时的关闭、或 24 小时后的重新通知路径，都可能依据一个旧结论行事。它只有在 `main` 此
  后*回滚*了恰好是分支所带的那些内容时才会出错，那时被关闭的 PR 本应重新有差异。恢复
  方式是重新打开 PR —— 被重新打开的 PR 不会再被本杠杆关闭 —— 而且每条评论都引用了它自
  己那次结论所对照的 `main` 提交（如果 GitHub 在两者之间重建过，通知和关闭评论引用的
  提交可以不同）。通知的年龄窗口与实时 head 读取约束的是与推送的竞态；这一点有意不加
  约束。
- **同一个 head 上的结论可能翻回去。** 如果 GitHub 对着一个已不再包含分支内容的 `main`
  重建了试合并，该 PR 会重新读出有变化并离开这个杠杆。已经为该 head 发出的通知会留在
  PR 上、不会被撤回；它在一天之内仍然有效，所以如果结论在
  `NOOP_NOTICE_MAX_AGE_SEC` 之内又翻回来，关闭会依据它继续进行，超过之后则先发一条
  新通知。
- **被搁置或被重新打开的空壳不再被同步。** 读出空壳的 PR 会走进遍历中本杠杆的分支，
  即使杠杆随后把它交还给人也是如此，所以在结论成立期间，它下方的陈旧 base 同步不会
  对这个 PR 运行。对真正的空壳这无害；对错误的结论则意味着，重新打开 PR 的人还需要
  移动它的 head（或等 GitHub 重建试合并），该行才会变化。
- **`autofix/skip` 会把 PR 从整个 shepherd 隐藏，不只是本杠杆。** 通知里给出的这个标
  签会把 PR 从车队快照中移除：没有仪表盘行、没有冲突派发、没有陈旧 base 同步、没有
  CI 红牌报告。如果之后有真实改动落到分支上，PR 会带着有效差异不可见地滞留，直到有
  人打开 PR 页面并移除标签。可见的搁置方式是 `autofix/needs-human`：它的行仍留在仪
  表盘上。
- **无答案不会暂停其它杠杆。** 在探针对一个已带通知的 PR 给不出答案的 tick 上，陈旧
  base 同步仍然可能触发并移动 head，从而使通知失效：多一条通知、多一个 tick，以及在
  一个空壳分支上花掉的一次同步。反过来，若在探针失败时暂停同步，失效的探针就会让整
  个车队的同步都停掉，那是更糟的取舍。
- **不是我们做的关闭。** 如果有人恰好在实时读取与调用之间的瞬间关闭了 PR，
  `gh pr close` 会静默成功，于是该 tick 会把一次它没有执行的关闭计入。这个窗口只是两
  次连续 API 调用之间的间隙，且终态完全相同（PR 已关闭、评论已发出），所以选择接受
  而不是为它做工程。
- **成本。** 每个可合并的 `autofix/*` PR 每 tick 一次 GraphQL 调用（约 15 个 PR，每 15 分钟一次），
  叠加在遍历已经发出的 compare 调用之上；只对探针标记的 PR 读取评论历史，时间戳转换
  只对已带通知的被标记 PR 运行，而在跑运行的列表（九次按状态过滤的 Runs API 读
  取，外加每个在跑运行一次 `gh run view`，走的是 workflow token 而不是 PAT）每个 tick
  至多花一次，且只在某个被标记的 PR 即将写入时。
- **workflow 体积。** 该杠杆让 `qwen-fleet-shepherd.yml` 超过其记录基线；基线在同一
  PR 中更新，远低于 470 KB 门槛。

## 验收标准

- 位于 `autofix/*` 分支上、试合并 tree 与其 base 父提交 tree 相同的 bot PR 收到一条机器人通知，并在之后的
  tick 中 —— 不早于宽限期 —— head 未变动时被关闭，两个标记都存在，仪表盘如实反映。
- 任何带有真实差异、合并状态为冲突或仍在计算、探针失败、有*本 tick 实时运行列举能
  看到的* address 运行（在列举之后才创建的 leg、或已越过自身 open 复查的 leg，是已
  接受的窗口 —— 见「护栏」）、带 skip 标签或 needs-human 标签、或分支不在 `autofix/*`
  之下的 PR 都不会被关闭，也没有任何 PR 会被按空壳关闭两次。
- 探针失败以计数和警告的形式可见，且与等待试合并的良性状态区分开。
- 读作空壳的 PR 在结论成立期间绝不会被做陈旧 base 同步 —— 无论杠杆随后是关闭它、
  顺延它、还是把它交还给人（见「约束与风险」）。
- 对不读作空壳的 PR，shepherd 的既有行为（冲突派发、同步、liveness、接管池、等待人
  工表）保持不变；读作空壳的 PR 走遍历中本杠杆的分支，而不是陈旧 base 同步。脚本测
  试套件全绿。
