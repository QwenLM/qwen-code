## Problem statement

The merged managed `/loop` slices carry review findings that were recorded as deferred under the convergence posture — acknowledged, not fixed in their rounds. Six of them are confirmed still valid on current main and are small, self-contained hardening fixes. This PR closes exactly those six; the rest of the deferred backlog (design-doc stale claims, dead Java branches, child-catalog code gaps, other probes) is left for separate follow-up.

## The six fixes

1. **Fake-model minted-id extraction pin (#17470).** Re-pointing the clear-leg pin to the assertion-side `createdScheduleId` left the fake model's own id extraction (the delete fixture's id source) unpinned. The extraction is now the top-level pure `mintedScheduleId(messages, createCallId)` — it filters tool results by structured `tool_call_id` and returns `undefined` rather than an invented id — used by both fakes and executed in the meta-test against hostile histories, with pins on both call sites and on the loud-failure `?? 'missing-schedule-id'` fallback, so a fabricated id, a dropped call-id filter or a substring match reddens the fast suite. (Round 2 consolidated the original inline regex plus filter into this helper; see Round-2.)
2. **Classifier narrowing executable witness (#17470).** The block-schema narrowing was pinned only as text (`'shouldBlock' in blockProperties`); an additive fallback that answers `shouldBlock:false` for any `respond_in_schema` query re-created the mis-answer of unrelated side queries (title, tool-use summary, next speaker) while staying green. Extracted the decision into a top-level pure `classifierBlockAnswer(blockProperties)` (returns the stage-exact answer for a block schema, `undefined` otherwise), used by both the skill and fire fakes, and executed it in the meta-test against block (stage 1/2) and non-block schemas. The additive-fallback mutation reddens the non-block directions.
3. **Sentinel allow-list (#17272).** The union/wakeup sentinel guard was a deny-list of the two known non-expanding forms (`<<loop.md>>`, `<<autonomous-loop>>`), so a newly added sentinel would ship undetected. Inverted to an allow-list: a body may carry only the wakeup-expanded `<<loop.md-dynamic>>` / `<<autonomous-loop-dynamic>>` forms (cron: none). Extracted as the pure `assertSentinelsExpanded(body, profile)` and executed against a hostile body with a brand-new sentinel.
4. **`Nd` cron semantics (#17272).** The interval table claimed `0 0 */N * *` means "every N days"; it is a day-of-month step (days 1, 1+N, … resetting at each month start), not a rolling N-day cadence. Corrected the bundled SKILL.md table row and added a caveat naming the month-boundary reset; updated the generator's managed substitution to the accurate UTC wording; regenerated the sidecars.
5. **Parsing rule inventory pin (#17272).** The drift guard checks source→body coverage, so a rule deleted from the bundled source is invisible to it. Added a parity test pinning the exact Parsing rule inventory (`Empty input`, `Leading interval token`, `Trailing "every" clause`, `Prompt-only input`), so a deletion reddens.
6. **Single-source profile set (#17272).** The profile list `['union', 'cron', 'wakeup']` was hand-kept in six test loops. Exported `MANAGED_LOOP_PROFILES` as the single source, derived `ManagedLoopProfile` from it, and replaced the hand-kept full lists; the `Record<ManagedLoopProfile, …>` asset map and the parity `it.each` now force coverage of every profile, so an added or removed profile cannot drift.

## Design decisions

- **Executable guards over text pins.** Fixes 2 and 3 follow the established pattern (assertCallerImportReplaced, assertScheduledFireWitness): a top-level pure declaration the meta-test loads and executes, so severing or drifting the guard reddens an assertion rather than merely failing a text match.
- **Allow-list, not deny-list.** Fix 3 fails closed on any unknown sentinel; the two expanding forms are the closed set a Managed body may teach.
- **Content fix flows through the generator.** Fix 4 edits the bundled source and the generator's substitution together and regenerates the committed sidecars, so the byte-for-byte parity test stays the oracle; no hand-edited sidecar.
- **No runtime code change; model-facing skill content does change.** No runtime module imports managed-loop-skill.ts — its only consumers are the regenerator and its own test — and the classifier helper lives in the E2E runner's fake model, not in shipped code. But the `Nd` fix edits the bundled `SKILL.md`, which ships with the build and is read at runtime by `readBundledReference`, so the local `/loop` guidance a model sees does change (that is the intended correctness fix), as does the Managed sidecar JSON the Java classpath copies at build. The two imports this PR adds to managed-loop-skill.ts (`LOOP_SENTINEL_DYNAMIC`, `AUTONOMOUS_SENTINEL_DYNAMIC`) are the sentinel constants the allow-list sources; they do not make the generator a runtime module.

## Round-1 review refinements

The first review round hardened the six fixes against second-order drift (each witnessed by a mutation that reddens the new assertion and restores green):

- **Caveat accuracy + pin (R1-1).** The month-boundary gap is _at most_ N days (exactly N when the month length is a multiple of N), not strictly shorter; the caveat now says "at most N days and often shorter" and states the N ≤ 30 bound (a step of 31 already collects only day 1, since 1+31 is past the day-of-month field maximum). A parity pin requires the corrected phrases in the cron and union bodies, so deleting or rewording the caveat reddens.
- **Producer single-source (R1-2).** The regenerator now derives its targets from `MANAGED_LOOP_PROFILES` (filename `managed-loop-skill-<profile>.json`), and a parity assertion requires the committed sidecar set (excluding `bundled-body`) to equal the declared profile set — a stray or orphaned sidecar reddens.
- **Guard sources the runtime constants (R1-3).** `EXPANDING_SENTINELS` is built from `LOOP_SENTINEL_DYNAMIC` / `AUTONOMOUS_SENTINEL_DYNAMIC` (the constants the wakeup fire actually expands), so a runtime rename reddens the parity build instead of silently whitelisting a token nothing expands. The body templates and SKILL.md prose keep the literals; the guard fail-closes on any drift from the constants.
- **Call-site pin (R1-4).** A build-level test injects a brand-new sentinel into the Input section (carried verbatim into every profile) and requires `buildManagedLoopSkill` to reject it, so inlining a deny-list back into the build while keeping the export reddens.
- **Statement-anchored count pins (R1-5, R1-6).** The classifier and fake-createdId call-site pins count both arms (`toHaveLength(2)`), anchored to the full statement (trailing `;` / `?.[0];`) so an additive `?? { shouldBlock: false }` fallback or a fabricated id in either arm breaks the match; each arm's own create-call filter (`loop-cron-create` / `loop-fire-create`) is pinned separately.

## Round-2 review refinements

The second round caught a fix-induced critical and four second-order gaps (each witnessed):

- **N ≤ 30, not N ≤ 31 (round-2 critical).** `0 0 */31 * *` already matches only day 1 (the step starts at day 1 and 1+31 is past the field maximum), so N = 31 is the degeneration itself, not the last safe value; the last step matching more than one day is `*/30` (`{1,31}`). The caveat, the parity pin and both design docs now state N ≤ 30; reverting to N ≤ 31 reddens the pin.
- **Java served-set pin (R2-1).** The profile single-source now crosses the TypeScript boundary: a parity assertion reads `ManagedLoopSkill.java`'s `sidecars()` keys and requires them (minus the provenance-only `bundled` key) to equal `MANAGED_LOOP_PROFILES`. That map only _supplies_ bodies; whether a workspace profile reaches one is decided by `forProfile()`'s hand-kept routing chain, which round 3 pins as well — the original rationale named the wrong mechanism (see Round-3).
- **Executable minted-id helper (R2-2).** The fake-side extraction is consolidated into a top-level pure `mintedScheduleId(messages, createCallId)` (returns `undefined`, never an invented id), used by both arms and executed in the meta-test against hostile histories; a source-spelling count alone missed a forged `?? 'asch_' + '0'.repeat(32)` fallback and blocked the consolidation. The call sites and the loud-failure `?? 'missing-schedule-id'` fallback are pinned.
- **Classifier gate pin (R2-3).** A count pin on `if (blockAnswer !== undefined) {` (both arms) closes the gate-widening spelling (`if (blockProperties !== undefined)` + `blockAnswer ?? {…}`) that restored the mis-answer with the assignment count still two.
- **Substituted-cell pin (R2-4).** The managed Nd fix's `sub()` replacement is pinned (`midnight UTC on days 1, 1+N, … of each month`, `not.toContain('every N days')`) plus the worked-example gaps, so reverting the replacement string and regenerating cannot teach "every N days" again with every gate green.

The scanner is executed against a hostile fake, so it cannot be vacuous: a second-binding sibling is detected and prose naming the binding and the tool name changes no count. Witnesses: the reported sibling reddens the answer-site set while the old counts stay 1 and 6; a sibling under a different call id reddens the same set; a hand-built tool call reddens the literal inventory; a comment naming `blockAnswer`, `shouldBlock: false` and `respond_in_schema` stays green; the previously covered usage-line `?? { shouldBlock: false }` fallback still reddens, now naming the offending expression instead of a count. Round-4 extends the same scanner with the allow's construction site, reassignments of the decision, and the schema-properties provenance.
- **The caveat's arithmetic derived from a parser (R3-1).** The bound and the worked examples were hand-written prose pins — which is how `Keep N ≤ 31` survived two rounds. - **The Java pin covers routing, not just supply (R3-2).** `sidecars()` only supplies bodies; `forProfile()`'s hand-kept chain decides which workspace profile reaches one, so a profile appended to the tuple passed every gate this PR adds while no profile routed to its body. ## Round-4 review refinements

Round 4 posted three suggestions, two of them fix-induced by round 3's own replacement. All three repair guards this PR adds rather than widening its scope, so they land here; the boundary stated in the round-3 summary stands — a further round regenerating siblings in these two test files goes to a follow-up issue.

- **Construction site and reassignment (R2-3, fix-induced).** Replacing the ingredient counts dropped the only assertion about _where_ the allow is built, and the AST inventory inspected neither object literals nor reassignments: `let blockAnswer = …; if (blockAnswer === undefined) blockAnswer = { shouldBlock: false };` kept every round-3 assertion green while non-block side queries were answered with an invalid allow again. The scanner now collects every `{ shouldBlock: false }` construction site with its enclosing function (exactly one, inside `classifierBlockAnswer`) and every reassignment of the decision or its input under any assignment operator (none — `??=` and `||=` reassign exactly when the decision is undefined, which is the non-block case, so checking only `=` would miss them). Structural, so the restored guarantee stays comment-insensitive instead of depending on a raw-text count. Witnesses: the reported `let` + reassignment mutation reddens the construction-site set; a `??=` reassignment to a helper-derived allow (no new literal, no new answer site) reddens the reassignment set; the round-3 second-binding sibling still reddens the answer-site set (continuity).
- **Provenance of the schema properties (R4-1).** The declarations inventory recorded only the argument token `blockProperties`, so a fabricated initializer (`schemaTool ? { shouldBlock: { type: 'boolean' } } : undefined`) passed while making every side query look like the block schema. The scanner now records each `blockProperties` initializer text and requires both arms to read `schemaTool?.function?.parameters?.properties`. Witness: fabricating either arm's initializer reddens the provenance set while the other inventories stay green.
- **The right oracle for the Managed caveat (R3-1, fix-induced).** Round 3 derived the bound and gaps from `utils/cronParser`, which serves the local CLI scheduler; Managed bodies are fired by the Java `CronSlots` scanner whose TypeScript twin is `managed-automation-slots.ts`'s `compileCron`. Deriving from the wrong parser would let a Managed slot-semantics change leave the caveat teaching a bound the Managed scheduler no longer honours. The test now derives from `compileCron` (the same `[1, 31]` day-of-month field as `CronSlots.java`). Witness: lowering the Managed compiler's day-of-month upper bound to 30 reddens the derived assertion (`Keep N ≤ 29`) — a mutation the previous oracle was blind to; the module restored byte-equal returns 32/32.

The executed scanner control covers all of these shapes at once (fabricated provenance, `let` reassignment to an inline allow, a `??=` rewrite of the input, second-binding sibling), while prose naming the binding, the allow literal and the tool name moves no inventory.

## Round-5 verification and round-6 review refinements

The second independent verification round measured four survivors of the round-4 scanner, and the sixth review round posted no inline findings but recorded eleven deferred items. Ten of the eleven and all four survivors are closed here; one is deferred to #17673 with a reason.

- **In-place writes to the decision input (H22, and the `Object.assign` sibling).** The reassignment inventory only recorded an `Identifier` left-hand side, so `blockProperties['shouldBlock'] = {…}` before the helper call re-created the mis-answer with all inventories green. The scanner now records any write to either binding: every assignment operator, a member write (`blockProperties.x` / `blockProperties['x']`), a `delete`, and an in-place `Object.assign` / `Object.defineProperty`.
- **Template-literal tool names (H23).** `answers` and the tool-name inventory matched only `StringLiteral`, so a sibling answering through ``fakeToolCall(`respond_in_schema`, …)`` escaped both. Tool names now accept a no-substitution template literal as well, every helper call is inventoried with its argument (a fabricated schema is a third call), and a `fakeToolCall` whose tool name is computed at all is recorded separately and must be absent.
- **Per-callback scoping.** The tool-name inventories were file-wide exact counts, so a legitimate non-loop `respond_in_schema` arm would redden a loop pin. Each site now carries its `startFakeOpenAIServer` callback, and `loopClassifierScope` confines the assertions to the callbacks that answer a loop classifier call id: one answer site and two tool-name sites each, while an unrelated arm moves nothing.
- **Clause-level caveat pairing (H21).** The four derived values were asserted separately, so swapping the 30-day and 31-day gaps kept every `toContain` satisfied. Each worked example is now asserted as one composed clause (derived day, derived ordinal, derived gap), so a swap reddens.
- **Two evaluators bound.** The caveat reaches both schedulers, so the test now also requires `parseCron` (which the local `CronCreate` validates with) and `compileCron` to expand every step 1..31 to the same day-of-month set.
- **Java routing as a mapping (H19), scraped from code.** Comparing the target set could not see two profile families swapping bodies. The test now parses each `forProfile` branch into profile→key pairs and asserts the mapping (`SHELL_V4→union`, `FILES_V4`/`INTERNAL_TEAM_LEAD_V2→cron`, `SHELL_V3→wakeup`), plus the reachable-key set. - **Per-shell Parsing inventories.** The bundled inventory could not see the managed-only rules the cron and wakeup shells write themselves. A `Record<ManagedLoopProfile, …>` pin now asserts each shell's rule names, so deleting cron's `No interval` or renaming wakeup's `Interval requested` reddens.
- **Record corrections.** The design record and the PR Risk section claimed "no production runtime change / no runtime import". Verified against the code: no runtime module imports the generator, but the bundled `SKILL.md` ships with the build and is read at runtime by `readBundledReference`, so model-facing content does change. Both documents and the PR body now say "no runtime code change; shipped skill content changes". Fix #1's description still named the pre-round-2 inline regex and filter; it now describes `mintedScheduleId`.
- **Deferred to #17673: binding the caveat's oracle to `CronSlots.java`.** The shared `managed-automation-slots-v1` fixtures (30 cases) contain no day-of-month step case, so the Java evaluator is not bound to the TS twin for `*/N`. The two-evaluator agreement above covers the JavaScript side only.
