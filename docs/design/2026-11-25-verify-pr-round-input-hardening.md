## 1. Motivation

The NIC-less microVM channel implements `verify-pr-input-v1` in `scripts/verify-pr-vm-runner.mjs`, `scripts/verify-pr-vm-channel.mjs`, and `scripts/verify-pr-vm-guest-vsock.py`. A host preflight probe established two concrete wiring gaps:

- The JavaScript API accepts a caller-supplied `roundInput.entropyHex`, but the JSON `run --config` adapter drops it. A caller that supplies a matching fixed `trustedInputDigest` therefore always receives `trustedInputDigest does not match generated roundInput manifest digest` instead of a reproducible input handoff.
- Manifest generation advertises the guest model-proxy port, defaulting to 54, independently of where the model proxy actually listens. Host TCP, an alternate UDS, or a plan without `modelVsockPath` can therefore produce a manifest the guest cannot use.

The probe also confirmed that the Python guest client already rejects truncated payloads, oversized declarations, malformed headers, trailing bytes, and an incorrect bundle digest through a real UDS peer. These protections need execution witnesses in the repository, not additional duplicate checks. Two small hygiene items accompany the change: clean up the temporary bare repository when output-parent creation fails, and remove a `socket.gaierror` assertion that cannot observe the health fixture's construction.

## 2. Goals and non-goals

- Preserve deterministic input pinning through the public runner CLI as well as the direct JavaScript API.
- Fail closed before creating listener credentials or launching a worker when a guest input manifest would promise an unusable model endpoint.
- Pin the existing guest rejection behavior using real UDS sockets and the actual Python fetch client.
- Remove the temporary-repository leak without changing the two-OID export contract.

This change does not add a provider, create cloud resources, expand CLI configuration surfaces, extract shared socket helpers, or change `packages/`, `.github/`, `.qwen/skills/`, or `/review`. It does not alter legacy `container`, manually operated `vm`, or `waived` verification workflows. No PR commit, push, or publication is implied by this design.

## 3. Design decisions

### 3.1 Forward the existing entropy field

Add `entropyHex: rawRoundInput.entropyHex` to the existing `resolvedRoundInput` whitelist. Do not add another digest input or bypass canonical-manifest construction. `buildInputManifest` remains responsible for validating exactly 64 lowercase hexadecimal characters and for retaining its random 32-byte default when no entropy was supplied. The runner performs the same validation before reading, generating or copying a prebuilt input, so malformed caller entropy cannot produce a private artifact; the later canonical-manifest guard is unchanged.

A caller-provided `trustedInputDigest` is still compared with the digest of the generated canonical manifest; the canonicalization and comparison are not weakened. A stale digest remains an error. Temporary proxy token/nonce values remain independently random and are still part of the canonical manifest, so the reproducible CLI pinning fixture uses `modelProxy: null`. This change does not expose credential fields, derive credentials from caller-selected entropy, or let callers predict a manifest containing newly generated credentials. A matching fixed digest over reproducible inputs passes this comparison regardless of whether `run --config` or the JavaScript API constructed the input.

### 3.2 Make the endpoint promise match the actual binding

Whenever `roundInput` is present and `modelProxy` is enabled, preflight requires a non-empty `plan.modelVsockPath` and exact equality between that path and the effective proxy binding. The effective binding retains the current order: explicit `socketPath`, then the planned VSOCK UDS when `listenHost` is absent, otherwise host TCP.

The rejected configurations are therefore an explicit host-TCP listener, an alternate UDS, or a missing planned model VSOCK path. Valid Firecracker/vfkit VSOCK plans keep their existing behavior. Host TCP and explicit alternate UDS configurations **without** `roundInput` remain supported because they do not create this guest-endpoint promise; this change does not claim that those routes work in a NIC-less guest.

The guard is ordinary input validation, before the temporary proxy token/nonce are generated, before token-file writes and listener creation, and before `launchBackend`. It does not create an implicit TCP-to-guest mapping, change a provider planner, or suppress the mismatch. The manifest's base path, temporary token, nonce, and the host-only upstream API key rules remain unchanged.

### 3.3 Pin fail-closed guest fetch behavior

A test-only UDS server returns a valid manifest followed by one malicious bundle response. Drive the real `python3 scripts/verify-pr-vm-guest-vsock.py fetch-inputs --unix ... --out ...` client for these cases:

1. A declared payload that is truncated before its length is reached.
2. A declared length greater than `MAX_BUNDLE_BYTES` (128 MiB).
3. A malformed `OK` header.
4. Bytes after the declared payload.
5. Payload bytes whose SHA-256 or length differs from the valid manifest.

Every case must exit nonzero, emit the specific protocol/integrity error, and leave neither `round.bundle` nor another input-file promotion in the output directory. No test hook, mock fetcher, real model service, or real upstream key is needed. Removing a guard must make the corresponding test fail.

### 3.4 Scope cleanup to the full scratch lifetime

Move creation of the `qc-round-bundle-*` scratch bare repository inside its guarded lifetime. Output-parent creation and bundle construction share `try`/`catch`/`finally` ownership: failed bundle output still removes its partial file, and the scratch directory is removed if it was created. If scratch creation itself fails there is nothing to remove.

The test uses an existing searchable but non-writable output parent (mode 0500) under an isolated temporary root. A nested `outPath` returns `ENOENT` at the initial `lstat`, scratch creation then succeeds, and the real `mkdirSync(..., {recursive: true})` fails with `EACCES`/`EPERM`. An ordinary-file obstruction is a control: its initial `ENOTDIR` rejection occurs before scratch creation and must not be mistaken for the leak. The permission fixture uses the existing `arePermissionBitsEnforced()` kernel probe instead of assuming a uid of 0 cannot be tested. It runs only when `chmod` actually denies reads and writes. Ordinary root bypass is a skip, while the real `EACCES` case for capability-stripped root must execute; an inconclusive probe is not a passing permission check. The test restores directory permissions before removing the fixture and does not mock Git or the filesystem. Existing checks for explicit base/head OIDs, read-only alternates, no copied `.git/config`, no private branch or secret-file export, and atomic output replacement remain unchanged.

Delete only the test assertion that expects the fixed HTTP health response not to contain `socket.gaierror`. Keep the actual response checks and the separate IPv6 runtime capability probe.

## 4. Security and compatibility boundaries

| Case                                                    | Required result                                                             |
| ------------------------------------------------------- | --------------------------------------------------------------------------- |
| Valid fixed entropy through `run --config`              | Reaches the normal post-manifest lifecycle without a digest mismatch        |
| Stale `trustedInputDigest`                              | Fails before token/listener/worker creation                                 |
| `roundInput` plus a non-VSOCK or missing model binding  | Fails before token/listener/worker creation                                 |
| No `roundInput`; legacy host TCP or alternate UDS proxy | Existing behavior                                                           |
| Guest receives malformed or inconsistent bytes          | Nonzero exit and no promoted temporary bundle                               |
| Output-parent creation fails during bundle export       | Original error propagates; owned scratch and output temporaries are removed |

This is a transport/configuration consistency control, not a new hypervisor or a claim of end-to-end verification inside a newly launched kernel. Existing socket identity, single-link regular-file, authentication, budget, revocation, and teardown mechanisms retain their responsibilities. The upstream key never enters the manifest.

## 5. Risks and limitations

- An endpoint-equality assertion does not prove a real VM can communicate with the guest. It prevents the known misconfiguration; actual transport evidence remains a separate integration test.
- Python UDS tests do not establish Linux AF_VSOCK or Apple Virtualization.framework behavior.
- A deliberately early-exiting launcher used by the CLI wiring test is not a successful VM round or merge approval. Later failure must be distinguished from a manifest-digest rejection.
- Old PR verification, successful CI on unrelated code, and green tests from another head cannot establish the result for this change.

There are no unresolved product-direction questions in this slice. Provider-VM and Agent Sandbox data planes remain separate future work, with their existing explicit authorization and cloud-resource boundaries.

## 8. Follow-up reviews: environment, semantic validation, and resource limits (2026-11-26)

The CI and independent reviews added concrete boundaries, not additional protocol options or providers. Sections 8.1–8.4 record the resulting invariants; section 8.5 separately records the subsequent Linux and real-KVM evidence and its environment boundaries. No broader cloud validation is claimed.

### 8.1 Keep host credentials out of the VMM/helper environment

The default Firecracker `spawn` now supplies only `PATH`, with a platform-neutral fallback when `PATH` is absent. That preserves custom tool locations while revoking inherited `REVIEW_OPENAI_API_KEY`, `GH_TOKEN`, and other host credentials. The key remains in the host model-proxy process, never in a manifest or in the VMM/helper environment. vfkit's existing enforcing `env -i` wrapper and hardware/trust-class selection are unchanged. A launcher canary captures the actual child environment without printing real upstream keys. It is not evidence of a real VM boot, and the known helper's expected identity/early-exit errors remain separately visible.

### 8.2 Require semantic manifests before downloading bundles

The Python guest and the Node fetch client now enforce the existing canonical manifest shape before the bundle connection: the schema, accepted top-level/model fields, run ID/repository/PR types, 40-hex OIDs, 64-hex SHA/entropy values, positive bundle sizes, and non-empty proxy tokens/nonces with a positive safe port. `modelProxy: null`, optional PR nullability, and the usual path/token defaults remain valid. Unknown fields and object/array mistakes fail closed instead of being ignored. Canonical generation preserves positive safe-integer PR values and continues normalizing unsupported values, including unsafe integers, to `null`, so the generator does not produce a PR field which both clients then reject. This does not expose an upstream key, add alternate proxy-auth mechanisms, or reinterpret missing entropy as the string `undefined`.

Because the field check precedes bundle fetching, missing entropy produces one manifest request, not a second bundle request followed by `KeyError` and three accepted files. For the byte-integrity stage, the manifest, bundle, and entropy each use a pid-suffixed temporary file, mode 0600, followed by per-path promotion. A promotion only counts as completed after its `rename` succeeds. A validation error, framing error, size/hash mismatch, or staging error removes only temporary files and files promoted by this attempt. Existing outputs which were not replaced are not blindly removed. Fresh per-round output directories are the verified case; stages are not a directory-wide ACID transaction for mixed-Round reuse or concurrent readers.

Node additionally requires actual strings whose entire value matches the grammar, rather than coercing arrays or accepting a trailing line terminator through JavaScript's `$` behavior. Both clients reject invalid UTF-8/JSON instead of accepting replacement characters that disagree with the preserved manifest bytes. Node's bundle writer waits for `close` on both success and failure: a late filesystem error may follow `end()`'s callback, and cleanup cannot safely unlink before an asynchronous open completes. Normal successful transfers retain their full-byte and SHA checks plus three-file promotion.

Generation and both fetch clients use the same definition of a whitespace-only credential. JavaScript trims its own whitespace and additionally accounts for Python `str.isspace()` characters. Python treats `str.isspace()` characters and `U+FEFF` as blank. This includes `U+001C`–`U+001F`, `U+0085`, `U+FEFF`, and their mixtures. A credential containing a meaningful non-whitespace character is preserved byte-for-byte; the new rule only closes the Node/Python acceptance divergence for wholly blank values, rather than restricting tokens to ASCII.

Positive-safe integer fields use the Node client's numeric-value semantics, not Python's textual or runtime type alone. JSON numeric spellings such as `4.0` and `4e0` represent permitted integer values; finite integral floats are normalized to `int` internally for PR number, bundle bytes, and proxy port. Booleans, zero, negatives, fractions, non-finite values and unsafe values remain invalid. The raw manifest bytes and their digest are preserved, while downloaded payload sizes and socket-facing integers remain exact. This preserves the Python client's compatibility with integral numeric values instead of letting Node accept a manifest that the guest would reject solely because JSON produced a float object.

Before initializing either Git worktree, the two materialize targets are created as needed, canonicalized, and required to have distinct, non-nested identities. Directory dev/ino identities and both ancestor chains supplement canonical string-prefix checks, so case-only aliases on case-insensitive filesystems cannot disguise the same directory or a parent directory. Paths are not lowercased, because they may name distinct directories on a case-sensitive filesystem. Identical paths, symlink aliases, and parent/child targets are rejected, so the head cannot silently replace the base's checked-out code. Sibling directory names that share a prefix remain valid. This does not add a blanket prohibition on existing directories or forbid unrelated, separate symlink targets; it only closes the aliasing/nesting isolation hole.

### 8.3 Bound byte-stream and bridge resources while preserving legacy behavior

Bundle generation uses `git bundle create -`, verified to stream a valid Git bundle over stdout. Both prebuilt and repoDir inputs use `min(caller maxBundleBytes, DEFAULT_MAX_BUNDLE_BYTES)` as their effective payload cap; an oversized caller budget is not passed through to the Git generator. The total Git `maxBuffer` is that payload cap plus a bounded 64 KiB stderr allowance. The allowance covers diagnostics, not guest payload bytes: native `ENOBUFS` and the subsequent exact-length hash check both fail closed, and a post-copy size rejection still removes this attempt's temporary output. Error messages label the payload limit, not the combined stderr-inclusive buffer. That error retains the `allowed range` diagnostic and the underlying `ENOBUFS` cause. The stdout stream is still hashed using 256 KiB chunks before the existing mode-check and rename. This gives a hard bound on payload bytes buffered by Git and written by this creator, not a claim about total Node RSS, kernel page-cache cost, or all repository/object-store resources. A real attempt to export qwen-code's two OIDs and their complete base history exceeded 128 MiB and stopped with the preserved `ENOBUFS` cause, without producing the output bundle. A separately constructed small, real two-OID Git repository must therefore be used for a transport fixture; it does not certify this entire repository's handoff. The slice does not enlarge the budget, send a truncated bundle, silently switch to a host-only/kernel route, or claim a successful full-repository VM round.

The fetch client validates `maxBundleBytes` and `maxManifestBytes` as positive safe integers before creating an output directory or connecting a socket. Non-finite limits therefore cannot disable comparisons while input is being buffered, and invalid limits cause no request or output directory.

For prebuilt bundle paths, `maxBundleBytes` is checked against both the path metadata and the opened descriptor. The hash loop also rejects if its actual read count exceeds the effective budget, and returns that count with the descriptor's dev/ino/nlink. Rejection occurs after a chunk crosses that budget; this is not a claim that an underlying read syscall can never return more than `maxBytes`. A later path stat must agree on dev/ino and the hashed byte count rather than combining the hash of one file state with the size or identity of another. Actual `bundleBytes` remains bounded by the guest's existing 128 MiB transport limit, even if a caller configures a larger host budget for headroom. A larger budget alone does not change that guest limit: a small actual bundle remains usable, while a bundle over 128 MiB is rejected before token-file writes, listener startup, or backend allocation. A zero-size or over-budget payload rejects before token creation, model listener startup, or a launcher. The actual file contents are hashed incrementally with `O_NOFOLLOW|O_NONBLOCK` and `fstat`. Hashing does not discard shared-inode information: it reports the descriptor’s dev/ino/nlink so the existing single-link and shared-storage rejection remains intact.

A prebuilt source is then reopened with no-follow flags and its descriptor identity and size are compared with the initial validation. A private staging file is exclusively created and set to mode 0600 through its fd. Copying uses 256 KiB chunks: cumulative reads must remain within the caller's budget and the fixed guest cap before a chunk is written, and EOF requires both the original byte count and SHA-256 to match. As with the hash reader, an individual read can cross the budget before rejection; that chunk is not written after the violation is detected. A checked, single-link regular private bundle can be replaced by a private staging file with `rename`, allowing a launcher or its own private bundle to be reused. Directory, symlink and multi-link existing targets are refused without unlinking them. Staging remains exclusive and its cleanup is limited to the inode actually created by this attempt. `EEXIST` before ownership is acquired leaves a caller's input untouched; later identity mismatch blocks unlink rather than deleting a replacement object. Cleanup errors are reported outside the cleanup block, so they cannot mask the original budget or copy error. The injected backend and input server both receive the verified private copy, not the caller's mutable source path. The bundle is not buffered whole in memory, and the guarantees do not claim that a trusted host operator cannot modify its own private files.

When a Node file writer cannot accept another slice, the fetch client pauses that socket and resumes it after the writer's `drain` event, unless the operation has already failed or completed. This bounds the writer queue instead of admitting almost the whole bundle into it, while preserving full-byte/SHA validation and writer-close promotion. It does not claim a bound on every socket chunk, total Node RSS, kernel page cache, or wall-clock duration.

The guest bridge now admits at most 64 concurrently active client connections. Once full, it closes a new socket before creating its upstream connection or relay threads. The first overflow emits one fixed stderr diagnostic per bridge process, including the limit but no token or payload; this does not change the raw TCP rejection protocol. Completion releases its slot only after both directions close, so the counter does not claim finished clients are still active. A shared `threading.Lock` protects accept-side check/reservation and completion-side decrement; it is never held while connecting upstream or waiting for relay threads, so correct accounting does not serialize live streams. The connection cap is a raw TCP backpressure policy, not an HTTP 429 or a new authorization policy. It does not introduce a user-configurable callback, change upstream authentication, or eliminate benign slow streams. `maxRequests` remains a count of accepted requests, not a global duration, per-request byte quota, or total billing cap. Idle-time backpressure semantics are preserved; idle clients still occupy their bounded slots until they finish or fail.

### 8.6 Earlier private-copy and Unicode replay evidence (2026-11-27)

Two further independent audits identified a post-validation prebuilt replacement window and inconsistent Unicode blank-credential handling. The bounded fixes are described in §8.2–8.3. The new real child-process driver replaces a same-size, single-link source after the validated manifest has been prepared and then exercises both the backend handoff and a real input-server UDS. Before the fix, the consumers received the replacement bytes while the manifest retained the original digest. After the fix, both receive the original verified bytes and matching digest through the private mode-0600 snapshot. The provider callback is only a sentinel for this data flow, not a cloud allocation or a claimed VM report; cloud lifecycle errors from that deliberately failing sentinel are not reported as successful teardown.

The next adversarial fixtures grow the source after its first copy loop has read a chunk. With a 1024-byte budget, only 64 bytes are written before the next chunk is rejected, the caller-owned expanded source remains intact, and no allocation or token file is created. These fail the old full-copy and unlink behaviors, respectively, and are now executable regressions. ### 8.9 Review-driven witness strengthening

The new review asked for observable witnesses rather than another coverage assertion. These test-only changes keep the original budgets and socket contracts, while making the requested startup and budget guards individually observable.

- **Slot accounting is proved at saturation.** After an injected startup failure, 63 held connections establish 63 real upstream sockets. Two subsequent healthy echo clients reuse the remaining capacity normally. Before each next client, the test also waits for the preceding relay pair to reach completion, because a peer close alone does not prove that the slot has been returned. Destroying those held sockets requires all 65 relay pairs to finish, with two startup-failure variants preserving expected counts. Removing only outer `finish_client()` makes the next healthy client fail with `ECONNRESET`, while the bridge's only saturation diagnostic reports that the connection limit of 64 was reached. The probe therefore distinguishes one leaked slot from correct slot return without increasing connection count or enlarging the cap.
- **The native budget error is distinguished from the post-stream budget check.** A real Git export including 2 MiB of random file data, with `maxBundleBytes=1048576`, triggers native `spawnSync` ENOBUFS.
