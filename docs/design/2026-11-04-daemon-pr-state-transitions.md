# PR state transitions from the daemon PR refresh

[English](2026-11-04-daemon-pr-state-transitions.md) | [简体中文](2026-11-04-daemon-pr-state-transitions.zh-CN.md)

Status: proposed (2026-11-04). Once implemented, this supersedes the "PR state watch" part of [GitHub Channel Events to PR-Bound Sessions](2026-11-02-github-channel-bound-session-events.md); the comment-delivery part of that design is unchanged.

## Problem

The daemon tracks the state of every PR a session is bound to twice, with two credentials, two schedules and two definitions of "CI failed":

1. `packages/cli/src/serve/server/session-pr-refresh.ts` already sweeps every trusted workspace's PR sidecars every 5 minutes (`QWEN_SESSION_PR_REFRESH_MINUTES`), runs `gh pr list` with the daemon host's `gh` credential, and rewrites each sidecar's `state` (open / merged / closed) and closing issues. The Web Shell sidebar reads the result. Nothing is delivered to the session.
2. The GitHub channel's PR state watch (`runPrStateWatch` in `packages/channels/github/src/GithubAdapter.ts`) polls every bound PR once per channel poll (60 s by default) with the channel's own token through Octokit: `pulls.get` per PR, plus `checks.listForRef` and the combined status on a conditional schedule, capped at 30 PRs, with its own `github-pr-watch.json` state file, pending queue, fired ring, dead-letter and reconciliation rules. It detects `ci_failure`, `merge_conflict`, `head_change` and `state_change`, and delivers them into the bound session through the daemon's prompt route.

The second poller exists only where an operator configured a GitHub channel with `deliverToBoundSessions` and `prWatchEvents`. A session that follows a PR without such a channel never hears that its CI went red. Where both run, the same PR is fetched by both, the channel's CI aggregate excludes `cancelled` / `stale` while core's rollup (`aggregateChecks` in `packages/core/src/utils/github-prs.ts`) counts them, and the channel's API budget at the cap is roughly 1,800 `pulls.get` calls per hour plus bounded re-checks, against 12 `gh pr list` calls per hour per workspace for the refresh.

## Current state

- Sidecar schema (`packages/core/src/services/session-pr-service.ts`, `SessionPr`): `number`, `url`, `createdAt`, `state?`, `source?`, `role?`, `issues?`. No head SHA, CI rollup or mergeability is persisted, so a refresh cannot see a transition.
- The refresh's GitHub path fetches `gh pr list --state all --limit 500` in **slim** mode (`number,url,headRefName,state`) because the CI rollup field makes large `--state all` queries hit GitHub GraphQL server timeouts (504). `GH_PR_LIST_FIELDS` (non-slim) already carries `statusCheckRollup`, `isDraft`, `reviewDecision`, `updatedAt`, but not `headRefOid` or `mergeable`; the rollup reducer, `aggregateChecks`, is module-private.
- The daemon already injects prompts into sessions it does not own the keyboard of: the channel bound relay (`POST /session/:id/prompt` with the `qwen.channel.prompt` / `qwen.daemon.channelBoundRelay` markers and an `idempotencyKey`), and it restores dormant sessions through the `/session/:id/resume` path. Neither is an in-process call today: the relay runs in the channel worker process and reaches the daemon over HTTP, and the prompt admission — the idempotency ring (`promptIdempotencyBySession`), the worker-credential classification, the bound-relay and display-text markers, and the skip of the PR-binding backfill for channel prompts — lives in the module the route handler calls (`packages/cli/src/serve/routes/session-prompt-admission.ts`). `qwen.channel.prompt` is honoured only along a trusted chain: the route accepts it only from a caller holding the channel worker credential, the bridge (`packages/acp-bridge/src/session-control-plane.ts`) re-arms it only from trusted context (`context.channelPrompt`), and the session child (`packages/cli/src/acp-integration/acpAgent.ts`) re-arms it only for a trusted private parent; `Session.ts` reads it to exempt the turn from the loop-detected rejection. The bridge keeps a display text for a turn only in channel-owned sessions (`getChannelPromptDisplayText`), and the bound relay sends none, so a relayed event appears in the bound session's transcript as sent.
- The channel watch's user-facing semantics are documented in `docs/users/features/channels/github.md` and were merged on 2026-11-03 (#16117) and shipped in v0.26.7 (2026-11-04), whose release notes name the feature; `prWatchEvents` is therefore a released, operator-configurable setting. Since #16258 (merged 2026-11-04 and shipped in v0.26.8 on 2026-11-05, whose release notes name the templates and the channel editor that edits them), a channel with `boundSessionActions` routes watch events by binding role — `review`, `verify`, `fix` or untyped, one winner per role, each with an operator instruction template selected by `watch:<type>` keys; without the map it keeps the single most-recent winner.

## Goals

- One source of PR state: the daemon refresh. It observes head, CI and mergeability alongside the state it already refreshes, and delivers the four transitions into the session that follows the PR.
- No GitHub channel needed to receive PR state events; the channel keeps delivering GitHub _conversation_ events (comments, review requests, assignments).
- No new polling loop. The only new state is one small daemon-owned watch file per bound PR, which is both the snapshot and the durable queue (key decision 4); the session sidecars are unchanged.
- Remove the adapter's PR state watch and its configuration.

## Non-goals

- Webhook push ingestion (unchanged future work).
- Aone merge requests: the refresh's Aone path keeps refreshing `state` only; transitions for Aone can follow the same shape later.
- Comment events: they stay in the GitHub channel's notification lane and its bound-session delivery.
- New event types (`review_decision` is fetched already and is an open question below, not part of this change).

## Design

### 1. Observation

The refresh keeps its slim `--state all` listing for `state` and adds one `gh pr view <url> --json url,title,headRefOid,mergeable,state,statusCheckRollup` per bound PR of the workspace's sessions as the bindings scan enumerates them, except merged PRs and closed PRs the sweep's slim listing returned; hidden-catalog sessions and sidecars whose transcript is archived are therefore not viewed for, and a binding that exists only in the bridge's memory is viewed once its sidecar is written. Merged is terminal by the PR's newest observation (its watch file's `state`, §2, or the top-level `state` when no file exists yet). Closed is not, because a closed PR can be reopened: the listing observes a closed PR it returns, and a closed PR it does not return — every PR of the untrusted primary, which has no listing; a binding to another repository, which is never in this repository's listing; a PR beyond the listing's 500-PR limit — stays in the view rotation behind the open PRs, so a reopen is always seen.

Views go by the binding's URL, never by number inside the checkout: `gh` resolves a bare number against the workspace's own repository, and a binding can name another one — the sweep already treats such bindings as foreign: `updateSessionPrStates` writes a listed state only to an entry whose canonical URL matches, and `isForeign` keeps them out of the closing-issue lookup and lets a merged one converge without it. A view is used only when the PR it returns has the binding's host and number, both URLs normalised as the refresh's `pullRequestKey` normalises them (host lowercased with `www.` stripped and any port dropped; any path after the number, such as `/files`, and a `.diff` or `.patch` suffix ignored), so the bind paths' tolerated spellings match the canonical URL `gh` returns; unlike `pullRequestKey`'s own `host/owner/repo` key, `owner/repo` is deliberately not compared. A different `owner/repo` with the same host and number means the repository was renamed or transferred, which GitHub resolves from the old name: the view is accepted, with a log line once per PR. A different host or number is logged and discarded. The watch file stays keyed by the binding's own identity — `pullRequestKey` of the bound URL — so a rename changes nothing for an existing binding: its file, binders, `lastBoundAt` and recipients are found exactly as before. A PR bound under both its old and its new repository name is watched once per name, and each of its transitions is delivered once per name; that is a stated boundary. Views go only to GitHub hosts: `github.com`, the hosts the daemon's `gh` configuration already lists, and the web host of each GitHub channel this daemon hosts, compared lowercased with `www.` stripped as `pullRequestKey` does. A binding on any other host is skipped with a log line before any `gh` call, so a binding URL — or a workspace whose `origin` is not GitHub at all — cannot make `gh` present the daemon's enterprise credential (`GH_ENTERPRISE_TOKEN`) to an arbitrary host. Views run with the swept workspace's environment (`runtime.env.effectiveEnv`), as its listing does, so a workspace's own `GH_TOKEN` or `GH_CONFIG_DIR` applies to its PRs; the untrusted primary's views run with the daemon's own environment. Their working directory is the daemon-private watch directory (§2, mode 0700), never a shared one such as `os.tmpdir()`, because `gh` resolution (`resolveGhBinary`) resolves relative or empty `PATH` entries against the child's working directory.

Views are capped at 30 per workspace sweep with a rotating window of the same shape as the Aone path's `sweepStart`; the GitHub path reports its own consumed count and the timer advances a GitHub offset per workspace (today only the Aone path reports one). The window wraps inside a sweep exactly as the Aone one does: two consecutive sweeps over 40 open bound PRs observe all 40 — the second window starts at the 31st PR, wraps to the head of the set and repeats 20 of the first sweep's views — and a workspace with more than 30 observes every one within ⌈n/30⌉ sweeps when no deadline truncates a window and the set does not change in between. The repeated views stay inside the cap and keep those PRs fresher, which is why the window is not made non-wrapping.

The views run under one tick-level deadline rather than the Aone loop's per-workspace `AONE_SWEEP_VIEW_BUDGET_MS`. The timer walks workspaces sequentially behind one `running` guard, so W workspaces each spending a 60-second budget plus one in-flight 10-second view would stretch a tick to 70·W seconds — past the 5-minute interval from W = 5 — and the guard would then skip the next tick for every workspace. The timer therefore computes one deadline when a tick starts, half the refresh interval later, and hands it to every workspace sweep of that tick. Past it, a sweep starts no further views (one in flight may still run out its `GH_TIMEOUT_MS`); dormant-session restores never run on the tick at all (§4); the rotation advances by the views actually started; and the order in which a tick walks workspaces rotates per tick, so a persistent overrun starves no workspace. A failed view or delivery for one PR is isolated, so the rest of the sweep continues. The deadline bounds only the work this design adds: the slim listing and closing-issue lookups keep their own per-call timeouts and the Aone loop keeps its per-workspace budget, so several slow workspaces at a short interval can still overrun a tick, as they can today.

A PR bound in several workspaces is viewed once per tick: a later sweep in the same tick skips the view when the PR's watch file was observed at or after the tick's start; the next tick views it again, and a skipped view does not count against the cap. A single-PR view does not hit the bulk-rollup timeout. Where the slim listing observes a merged or closed PR, that observation updates the watch file (its `state` and `observedAt`) exactly as a view does; a view that returns `merged` or `closed` counts the same way.

The timer sweeps trusted workspaces, as today, plus the primary workspace when it is untrusted: the bindings scan covers the primary without the trust gate, and the channel delivers to its sessions today. Because views run outside the checkout, no `gh` call runs inside the untrusted checkout; its slim listing, closing-issue lookups, origin resolution and Aone path are skipped, so no `git`, `gh` or `a1` process runs inside that checkout and its PRs are observed through views alone. With no event set in effect (`sessionPrWatch.events` unset and no alias, §7), no `gh pr view` runs at all and the refresh is unchanged (acceptance criterion 4).

`mergeable` is mapped `MERGEABLE → mergeable`, `CONFLICTING → conflicting`, `UNKNOWN → undefined` (GitHub still computing; never overwrites the last known value). The no-overwrite rule is a merge rule in the file write, not in the mapper: an `UNKNOWN` observation leaves the stored `mergeable` in place and emits no transition. CI uses core's existing `aggregateChecks` rollup (`passing` / `failing` / `pending` / `none`), exported for this: one definition for the sidebar and for events.

### 2. Watch state per PR

The watch state belongs to the PR, not to any session that follows it, so it lives once per PR in a daemon-owned watch file — `<global qwen dir>/serve/pr-watch/<first 40 hex of sha256 of host/owner/repo#number>.json`, the binding's own identity (§1) — rather than in the session sidecars, which keep their `state` and `issues` for the sidebar unchanged. One file per PR, not one copy per binder, means there is exactly one baseline, one queue and one delivered record for each PR, however many sessions bind it and whichever of their workspaces is reachable, trusted or retired this tick: no replica can lag behind, so nothing ever has to be adopted, merged or re-detected from a stale copy. One daemon owns the watch directory, created with mode 0700, because several daemons may share one global qwen dir and even one workspace (`docs/design/2026-09-02-relaxed-standalone-daemon-ownership.md`). Ownership is an owner record, `pr-watch/owner.pid`, written and checked exactly as the channel service pidfile is (`packages/cli/src/commands/channel/pidfile.ts`, generalised to a caller-chosen path): an exclusive create (`wx`) under the module's lock, carrying the owner's pid, process start token and PID namespace. A record whose process is provably gone on this boot and in this PID namespace is swept and replaced; a record this machine cannot verify — written before a reboot, by another machine or by another PID namespace sharing the home — is kept and blocks the claim until it is deleted by hand, with a log line naming the file at every attempt, as the channel service does today; and on a platform without a process start token (macOS) a record whose pid was reused counts as live, as it does for the channel service. A daemon whose effective event set (§7) is non-empty and whose refresh timer runs attempts the claim when the timer starts and on every tick, so ownership passes to a surviving daemon once the owner exits; a daemon with an empty set or no refresh timer (an interval of `0`, or the `hosted-harness` profile, which starts none) never claims, and when several configured daemons run, the first to claim governs and the others log that its set applies. A daemon that does not hold the record runs no PR watch — it views, writes, drains and deletes nothing, the slim listing's `state` write to a watch file included — while its state refresh stays as today, so a session bound only in workspaces the owner does not register gets no PR-state events. Daemons share sessions when they resolve the same runtime base, which `QWEN_RUNTIME_DIR` or a workspace's `advanced.runtimeOutputDir` can place outside the global qwen dir (`resolveSessionRuntimeBaseDir` in `packages/cli/src/serve/run-qwen-serve.ts`); two daemons with different global qwen dirs over one runtime base would each own a watch and each deliver, so that configuration is not supported for the PR watch, and at most one such daemon sets `sessionPrWatch`. On shutdown the owner stops its PR watch — the timer, the drains, and every restore and admission in flight — before it removes its record, so a successor never overlaps it; PR A reorders the serve lifecycle's close (`packages/cli/src/serve/serve-app-lifecycle.ts`) to do so. With one writer, the owner's in-process locks are authoritative for every file. Every change to a watch file — detection, the slim listing's `state` write, the `lastBoundAt` refresh, the deletion and each drain step (§5) — reads the file and writes or deletes it within one hold of the owner's in-process lock for that PR, a `PathMutexRegistry` (`packages/cli/src/serve/fs/path-mutex-registry.ts`) keyed by the file, so no write can put back content read before another write; the store's read and write functions take no lock of their own, because `runExclusive` is not re-entrant. On POSIX a daemon claims the watch only when its effective uid owns the watch directory and every watch file in it; one running as another user, root included, or finding a watch file another uid owns logs that, naming the directory or file, and does not claim, as for a record it cannot verify. Since a non-owner writes nothing, every watch file is then created and replaced by the owner's uid, which keeps unreachable the in-place path core's `atomicWriteFile` (`packages/core/src/utils/atomicFileWrite.ts`) takes for a file another uid owns, where a write would fail or tear the file; a watch file another uid places there after the claim, which only a process outside the PR watch can do, is treated as a read error (below): its PR is skipped with a log line naming the file. Each write is therefore a temp file beside the target renamed over it, so an interrupted or failed write leaves the previous file intact:

```ts
interface PrWatchState {
  /** The binding's identity: host and `owner/repo` split from `pullRequestKey`'s `host/owner/repo` key, and the number. */
  pr: { host: string; repo: string; number: number };
  /** When a scan last listed a binder of the PR or a retained row last named it (§4): the deletion clock, kept across restarts. */
  lastBoundAt?: string;
  /** Observation version: the time of the observation that last updated the file — a `gh pr view`, or the slim listing for a merged or closed PR. */
  observedAt?: string;
  state?: 'open' | 'merged' | 'closed';
  /** Title at the last view, for the prompt's identity line. */
  title?: string;
  headSha?: string;
  checks?: 'passing' | 'failing' | 'pending' | 'none';
  mergeable?: 'mergeable' | 'conflicting';
  /** Heads for which ci_failure already fired, oldest first (cap 16). */
  ciFired?: string[];
  /** Keys already admitted — group-suffixed with role-aware actions — oldest first (cap 64). */
  delivered?: string[];
  /** Detected but not yet delivered transitions, oldest first (cap 16); `served` lists the role groups already admitted. */
  pending?: Array<{
    type: PrTransitionType;
    key: string;
    summary: string;
    detectedAt: string;
    served?: Array<'review' | 'verify' | 'fix' | 'untyped'>;
  }>;
}
```

A PR without a file — its first observation, every bound PR right after this change ships, or a PR bound again after its file was deleted — is initialised silently from the next observation: nothing fires, even if its CI is already failing. A file created by the slim listing holds only `state` and `observedAt`; it is initialised the same way, so the first view after a reopen fills `headSha`, `checks` and `mergeable` without firing `head_change`, `ci_failure` or `merge_conflict`. Once a file has a `headSha`, a `mergeable` it has never known counts as non-conflicting, so a first `conflicting` after the first views returned `UNKNOWN` fires `merge_conflict`, as the channel's `undefined → dirty` does. A file that does not exist, or whose content does not parse or validate, is treated as absent — the PR initialises silently, with a log line for an invalid one — and is never a reason to touch a sidecar. Any other read error (`EACCES`, `EMFILE`, `EIO`) fails closed, as the adapter's `loadPrWatchState` does today: the PR is skipped for that tick — no detection, no drain step, no deletion and no recording write, an admitted key keeping its in-memory mark — and retried on the next one, so an intact file is never overwritten after a failed read.

The owner deletes a file when a complete scan (no `partial`, §4) finds no binder of the PR, and otherwise once 7 days have passed since its `lastBoundAt` — the horizon of the pending age limit (§5), so this drops no entry the age limit would keep; its undelivered entries are dropped with a log line, since no session follows the PR any more. A PR bound again after that initialises silently, as the channel re-baselines a PR it stopped watching. A PR bound again before its file is deleted resumes from its last observation, so a transition in the gap reaches the new binder once. A temp file left by a crash mid-write is removed when a daemon next takes ownership, so the number of files is bounded by the PRs bound in the last 7 days.

### 3. Transition rules

The channel watch's transition rules, so operators who move over see the same transitions, with one deliberate CI-predicate difference (key decision 5, open question 2: core's rollup counts `cancelled` / `stale` runs as failing where the channel's aggregate excluded them):

| Event            | Fires when                                                                                                                                                                                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `head_change`    | `headSha` differs from the previous observation (a force-push back to a recent SHA is a new transition).                                                                                                                                                                                  |
| `ci_failure`     | `checks` is `failing`, the previous observation of the same head was not (a head change resets the comparison, as the channel's per-head reset does), and `headSha` is not in `ciFired`; appends it, so it fires once per head even if CI flaps or a force-push revisits an earlier head. |
| `merge_conflict` | `mergeable` becomes `conflicting` from a non-conflicting or not yet known value (edge-triggered; `conflicting → mergeable → conflicting` fires again).                                                                                                                                    |
| `state_change`   | `state` leaves `open` (merged or closed). A reopen returns `state` to `open`, so a later close fires again.                                                                                                                                                                               |

Each transition's key is `pr-state:<owner/repo>#<number>:<type>:<headSha or previous→next>:<detectedAt>`; `detectedAt` keeps instances detected after a file deletion distinct while `ci_failure` stays once-per-head through `ciFired`. `ciFired` is the daemon's equivalent of the channel's durable `fired` ring: bounded per-head history, so `A failing → B failing → A failing` after a force-push back to `A` does not fire a second time for `A`. The bound differs deliberately: the channel keeps 64 keys shared by all four event types per PR and pins only the current head once they are evicted, while the daemon keeps the last 16 failing heads of each PR; a head revisited after more than 16 other failing heads fires again, as it does in the channel after eviction. With role-aware actions (§4) each role group's admission uses the key suffixed with `:<group>`. A key longer than the prompt route's 200-character `idempotencyKey` cap is hashed deterministically into `pr-state:h:<first 40 hex of sha256>`, the channel's shape, so retries still dedupe (a long `owner/repo` with the two-SHA `previous→next` form reaches 275 characters before any suffix).

### 4. Delivery

- **Detection.** A sweep compares a fresh view — or the slim listing's state for a merged or closed PR — with the PR's watch file and writes the new observation, the updated `ciFired` and any detected transition to it in one atomic write under the PR's lock. An observation is stamped with the time it started, and one that started before the file's `observedAt` is discarded — neither compared nor written — so a slow view can never roll the baseline back. Because the file is the only baseline, observation can stay per workspace while detection and delivery are PR-scoped: a binder whose workspace is unreachable, untrusted or retired this tick holds no copy that could lag behind or detect a transition a second time, and when it becomes reachable again it simply becomes a recipient candidate.
- **Target.** One recipient per PR across the whole daemon — one per role group with role-aware actions, below — never one per workspace. The recipient is resolved lazily, at delivery time, and only for keys not yet admitted (§5): among the eligible sessions bound to the PR in the workspaces the bindings scan covers (trusted workspaces and the primary), the most recently active one (transcript mtime, refined by the bridge's live activity), the channel's legacy rule, dispatched through that session's owning runtime. On a partial scan the drain keeps, for each session the scan does not list, its row from the last scan that did list it — complete or partial, as the adapter rebuilds its retained bindings from every snapshot — bounded as the adapter's retention is (`MAX_PARTIAL_RETAINED`, oldest dropped first), and drops a retained row once a complete scan omits the session, so a newer binder that is briefly unreachable still competes by recency — the adapter retains unlisted sessions for the same reason, so that a partial answer listing only an older session cannot displace the newer one — and when such a retained session wins, the entry stays pending until it can be reached. This applies within each role group with role-aware actions. A recipient archived or outranked between detection and drain loses nothing: the drain resolves the next one. Archived sessions, channel-owned sessions (`sourceType: 'channel'`) and machine-owned hidden-catalog sessions (`isHiddenCatalogSource`: `agent-host`, `agent`) are never targets, and a workspace that is no longer registered, no longer covered by the scan (untrusted and not primary), or whose runtime generation is retired (`assertGenerationOpen()`) is skipped with a log line, re-resolved immediately before dispatch. Two registered workspaces for one repository, each with a session following the same PR, therefore produce one delivery, not two, with or without a crash in between.
- **Self-pushed heads.** `head_change` is detected from the head SHA alone: GitHub's PR object does not name the pusher, and an account-level "own push" test cannot distinguish two sessions pushing under one git identity — it would suppress every push, not only the recipient's own. Suppression is therefore per recipient and only for `head_change`: a candidate whose own pushed-head ledger contains the new head is excluded for that transition, and the drain re-resolves the next binder — within its role group with role-aware actions, the single winner without them — while the existing no-candidate rules decide between dropping with a log line on a complete scan and waiting on a partial one. `ci_failure`, `merge_conflict` and `state_change` are never suppressed by authorship: a self-pushed head whose CI turns red is exactly the signal a fix session needs. The ledger is `pushedShas` in the autofix-pr watch state for that PR (`.qwen/tmp/autofix-pr-<n>-state.json`), under the root the helper resolves for an existing watch rather than the registered workspace root the binding's `workspaceCwd` names: `push` writes through `resolveWatchRoot()` = `findWatchRoot() ?? watchRoot()` (`packages/cli/src/commands/autofix-pr/state.ts`, `push.ts`), so the ledger sits in the linked worktree the watch was prepared in and stays there when the session's cwd later moves. The drain resolves it the same way instead of guessing from a coordinate: one `git worktree list --porcelain -z` per clone, run from the candidate's clone (the bridge live summary's `worktree.path`, else the binding's `workspaceCwd`), then the helper's file-only `vouchedScanRoots` filter and regular-file check select the worktree holding this PR's state, a live watch worktree winning over a stale file. That is the helper's own single-git-call discovery, not a new scan. The untrusted primary is the exception this design already makes: no git command runs in that checkout, so the coordinate alone is used there and no discovery runs. A candidate whose coordinate is unavailable, or whose discovery finds no state, has no ledger and is delivered to. The file is read through the helper's guarded regular-file reader (`readRegularFile`: `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`, then `fstat` must confirm a regular file), never a bare read — a FIFO planted at that path would otherwise block the drain on the refresh thread and stall every PR's detection. Every refusal — absent, non-regular, unreadable, or a `sessionId` and host/owner/repo/number that do not match the candidate and the binding — means no ledger, and the transition delivers as before. `lastKnownHeadSha` is deliberately not part of the ledger: `sync` adopts heads other people pushed into it. The helper's own gate suppresses on `knownHeads`, which is that field plus `pushedShas` (`packages/cli/src/commands/autofix-pr/snapshot.ts`), so the two paths deliberately diverge on a head the watch merely adopted: the gate stays quiet because the watch already holds that head as its own, while the daemon still delivers because someone else pushed it. Two boundaries: a head SHA is not a pusher identity, so a force-push back to a head the session pushed earlier is attributed to that session and its `head_change` dropped, while the other three transitions still fire; and only pushes made through that helper are recorded, so a manual `git push` still wakes the session that made it (open question 5). The ledger is session-writable, so this is a cost optimisation, not a trust boundary: a forged entry can suppress `head_change` deliveries for that PR to the session it names and, because the drain then re-resolves, redirect that head change to the next binder rather than silence it — bounded to that PR, that role group or the single winner, and `head_change` alone. It publishes nothing and cannot touch the other three transitions, and `vouchedScanRoots` already rejects a watch worktree nested in another root's `.qwen/tmp`, so the forgery surface is narrower than a bare file write suggests.
- **Role-aware actions.** With `sessionPrWatch.actions` set, delivery follows the channel's role-aware mode (#16258) restricted to the four transitions. Keys are `<type>`, `<role>:<type>`, `<role>:default` and `default`, with `<role>` one of `review`, `verify`, `fix`; values are instruction templates, non-empty, trimmed and at most 2,000 code points as in the channel, with the channel's variables (`%repo%`, `%pr%`, `%url%`, `%title%`, `%event%`, `%sender%`, `%role%`): `%repo%` is `owner/repo` as the group winner's bound URL spells it at delivery time, keeping its case as the channel's does, `%pr%` is its number, `%url%` is that URL's origin with `www.` stripped and its port kept, followed by `/<owner/repo>/pull/<number>` (the watch file's key, lowercased and without a port, is not used for display), `%title%` comes from the last view, and `%sender%` is `GitHub`, as for the channel's watch events; every value is sanitised, and `%title%` and `%sender%` are also capped at 200 code points with a visible marker, as in the channel. Each role group — review, verify, fix and untyped, by the binding's `role` in the sidecar — resolves `<role>:<type>` → `<role>:default` → `<type>` → `default`, untyped bindings resolve only the bare chain, and no match skips that group for the transition. A group is matched when its chain resolves a template; a matched group with no eligible binder on a complete scan is skipped for the transition, and on a partial scan it waits (Scan completeness). Each matched group has its own winner (the most recently active binder with that role), its own admission under the group-suffixed key, and a prompt carrying the rendered instruction in the channel's labelled trusted-instruction block, under the channel's untrusted-data notice that extends to the GitHub-derived values substituted into it; at most four deliveries per transition. Each group's admission records the group in the entry's `served` list and the group-suffixed key in `delivered`, in one write, and a drain skips a served group, so a group is never served twice while another group's winner is still dormant; the entry leaves `pending` once every matched group is served. Without `actions`, delivery is the single winner and the generic prompt. The key and template validation, the chain resolution and the rendering are not reimplemented: PR A moves the channel's own code for them out of `GithubAdapter.ts` into `@qwen-code/channel-base`, with the event vocabulary and the comment-lane class as parameters and the renderer taking the variable values instead of a channel envelope — the channel passes `watch:<type>`, its notification reasons and, for comment events, the `comment` lane (so `<role>:comment` and `comment` still catch them), and derives the values from its envelope as today; the daemon passes the four bare transition types, no lane and the values above, so `fix:ci_failure` is a valid key here and a notification reason such as `mention` is not — and the adapter keeps using it for comment events and, until PR B, for watch events, so `%%` renders a literal `%` and an unknown `%foo%` stays literal exactly as in the channel. The move fixes two quirks of the channel's renderer: a `%name%` naming an `Object.prototype` member, such as `%constructor%`, rendered that member instead of staying literal, and only `%title%` and `%sender%` were sanitised. `%event%` renders the bare transition type (`ci_failure`); under the alias (§7) a template written for the channel, where it rendered `watch:ci_failure`, therefore renders the bare type.
- **Scan completeness.** The sweep calls the scan in-process for its view set and its recipients. On this tree `partial` means something could not be read — a registered workspace with no runtime, a chats directory that cannot be listed, an unreadable sidecar or transcript, a live session list that cannot be fetched — never a page boundary: the scan is one directory listing per workspace (#16241). A workspace the scan cannot enumerate contributes no views and no newly listed recipients this tick — its sessions' retained rows still compete (Target) — and nothing else depends on it, because no watch state lives in its sidecars; `partial` defers every negative decision: deleting a watch file (§2; under partial scans only the 7-day `lastBoundAt` rule applies), skipping a role group for lack of an eligible binder, and dropping a transition because no candidate remains (below) are decided only on a complete scan; on a partial one the entry stays in `pending` for a later drain, within the 16-entry cap and the 7-day age limit (§5). The slim-listing `state` refresh is unaffected.
- **Archive and restore.** Archiving a session changes nothing in the PR's watch file: the session only leaves the recipient candidates, and its sidecar keeps its top-level `state`, still refreshed. A session restored from the archive rejoins them. If another binder kept the PR watched, the file is current and the restored session receives transitions from then on; if nobody followed the PR, its file was deleted (§2) and the PR initialises silently, so what changed while the session was archived is not replayed into it — the restore is a user action, and the refreshed top-level `state` already shows it in the sidebar. A restore within 7 days of the last binder leaving, while scans stay partial, resumes from the last observation and delivers a transition in the gap once.
- **Mechanism.** PR A extracts the prompt admission from the route handler into a function the route and the refresh both call — the idempotency ring, the classification and the backfill skip move with it, the skip honouring the trusted classification as well as the request's own marker (an in-process caller has no request marker; a request's own marker, even without the worker credential, still keeps relayed text out of the backfill and opts only its sender out) — and the refresh calls it in-process, together with the code behind the resume route. The refresh rides the channel bound relay's classification end to end instead of adding a grant: it passes `context.channelPrompt`, which the bridge turns into `qwen.channel.prompt` only from trusted context and the session child honours only from a trusted private parent, and no PR-binding backfill runs on the injected text. The turn carries every effect that classification has for the bound relay in the same sessions today (`Session.ts`), and accepts them: it skips the loop-detected rejection, records no branch checkpoint (it is not a rewind point), runs with the repeated-tool-failure guard off, does not count as a user submission turn, cannot have its model response cut short by queued or send-now user input, its Stop hook is not interruptible, and it schedules no managed auto-memory extraction or Dream and gets no follow-up suggestion. The transition key (group-suffixed with role-aware actions) is the `idempotencyKey`, so a retry to the same session within the daemon's lifetime deduplicates into the original admission. No display text is set: like the channel's bound relay today, the injected prompt appears in the session's transcript as sent, untrusted-data notice included, so the session's user sees exactly what the model received (the bridge keeps display texts only for channel-owned sessions). No new marker is introduced, so no strip list changes; a route test pins that a client body carrying `qwen.channel.prompt` without the worker credential gets no classification.
- **Dormant sessions.** A bound session that is not live is restored through the resume path the channel accessor uses — PR A extracts the restore from the route's `restoreSessionHandler` into a function the route and the refresh share — then delivered to, and the refresh releases the client registration the restore mints once the delivered prompt settles, as the channel accessor does, so a woken session can still close when idle. Restores never run on the tick: the drain starts a dormant recipient's restore and admission without waiting for them (at most four at once; the rest wait for a later drain), the key stays in flight until they settle (§5), and a restore timeout therefore never stretches a tick. `wakeDormant` is on by default so a daemon restart does not strand events in `pending`; with `wakeDormant: false` the transition stays in `pending` and is delivered on the session's next live turn (the drain also runs on resume, through a hook PR A adds to that shared restore), and the 16-per-PR cap and the 7-day age limit (§5) apply with a log line, so nothing vanishes silently. Restore failures are split as the channel splits `BoundSessionGoneError` from `BoundSessionUnavailableError`. Only a permanent outcome — the channel's Gone set: the session record is gone (404), or a 409 `session_archived`, `worktree_session_superseded`, `worktree_marker_missing` or `worktree_reset_interrupted` — excludes the session; the drain then re-resolves the recipient among the remaining binders, within its role group with role-aware actions, and drops the transition with a log line only when a complete scan leaves no candidate. A temporary outcome — the restore timeout, a 503 (session limit, draining), a 429, a 409 `restore_in_progress` or `session_busy`, or `session_writer_conflict` — leaves the entry pending for the same recipient at the next drain. A restore returns `session_writer_conflict` while another daemon holds the session only when the session writer lease is on (`experimental.sessionWriterLease`, off by default for ordinary workspace sessions), and the lease covers daemon and ACP writers only: interactive and headless `qwen` CLI sessions stay outside it. A session another process writes live — a CLI session in a terminal, or a session another daemon over the same runtime base holds without the lease — can therefore be restored by the owner as a second writer, and the event lands in a copy nobody is using; with the lease on, the owner's copy can also fail after admission (`session_transcript_changed`, `session_writer_lost`), which counts as delivery. This is the exposure the channel's bound delivery has today, since it wakes sessions through the same restore path. Fencing interactive writers is out of scope, and operators who run several daemons over one runtime base turn the lease on. An excluded session rejoins the candidates when the owner's own unarchive, restore or re-bind path names it, and in any case after one hour. Nothing is ever published anywhere.
- **Prompt text.** The channel's bound prompt shape and its hygiene: an event header, the untrusted-event-data notice, PR identity (repo, number, the title from the last view, URL), an `Event:` line and the summary (`ci_failure` names up to five failed checks from the rollup). Every line built from GitHub data — title, check names, branch names, the summary — passes through `sanitizePromptText` from `@qwen-code/channel-base` exactly as `buildBoundSessionPrompt` does (it folds CR/LF/TAB and the other C0/DEL controls and peels start-of-line tags, so a check-run `name:` taken from the PR branch's own workflow YAML cannot open a prompt line outside the `Event:` attribution), and the assembled body keeps the channel's 6,000-code-point cap with its visible truncation marker. The envelope is not reimplemented either: the header line, the untrusted-data and not-published notices in both variants, the labelled trusted-instruction block, the sanitised data lines, the `Role:` line and the capped body move with the template contract into `@qwen-code/channel-base` (`buildBoundEventPrompt`), which the adapter's `buildBoundSessionPrompt` now calls and the daemon calls with its own provenance line, so a later change to any of them reaches both. The move also gives the trusted block a fixed label, `[Operator instruction — trusted]`, with the source on a `Source:` line under it: the content of the channel's old label, `[Operator instruction — trusted, from this channel's configuration]`, was 65 characters, one over the 64 that `sanitizePromptText` peels from a start-of-line tag, so an event body that began with a copy of it kept the brackets. The reply stays in the session.

### 5. Durability

Detection and the new observation are persisted by one atomic write of the PR's watch file, the transition appended to its `pending`. Delivery drains `pending` oldest-first, and every drain step for a PR runs under that PR's in-process lock, re-reading the watch file after acquiring it: checking `delivered` and the in-memory in-flight mark, resolving the recipient, setting the mark, admitting, and the write that adds the key to `delivered` and removes the entry from `pending` (with role-aware actions, records the group in `served` and removes the entry once every matched group is served); the mark is cleared after that write, or when the admission is rejected outright, leaving the entry for the next drain. If the recording write itself fails, the mark is kept — as admitted, to that session — and later drains only retry the write, never re-resolving or re-admitting the key, until it succeeds; only a restart loses such a mark, within the restart allowance below. Only a dormant recipient's restore runs outside the lock, with its key marked in flight; its admission re-acquires the lock, re-reads the file and skips the key if it is already in `delivered`. Two drains of one PR — a sweep's and a resume's — therefore never interleave between a check and the admission it guards: neither can admit a key the other admitted, to the same session or another, nor drop the entry of a key whose admission then fails. Admission counts as delivery, as it does for the channel's bound relay: a prompt admitted behind a running turn waits in the bridge's in-memory queue, so a daemon restart before that turn ends loses it — the admission's own note says the queue is in-memory and 'a daemon restart loses both together' (`packages/cli/src/serve/routes/session-prompt-admission.ts`) — and the watch file, which already records the key, does not re-inject it. The prompt route's admission ring is keyed by session and key, so it cannot stop the same key from being admitted to a different session; `delivered` does, because a key in it is never admitted again, whoever the most recently active binder is now. A pending entry older than 7 days is dropped with a log line instead of delivered.

**Crash windows.** Before the write, the transition is re-detected on the next sweep (no loss, nothing delivered). After the write and before admission, the next sweep drains `pending`. After admission and before the write that records it succeeds, the key is admitted again after the restart, once: at-least-once, the same trade the channel made, and the only way a transition is delivered twice. An admitted prompt still queued behind a running turn at the restart is lost with the queue (above). `pending` is capped at 16 per PR; overflow drops the oldest with a log line.

### 6. Configuration

A daemon-level setting in the daemon's settings, read at startup from PR B on (§7): `sessionPrWatch: { events: ['ci_failure', 'merge_conflict', 'head_change', 'state_change'], wakeDormant?: boolean, actions?: Record<string, string> }`, with `QWEN_SESSION_PR_WATCH_EVENTS` and `QWEN_SESSION_PR_WATCH_WAKE_DORMANT` as environment overrides (`actions` is settings-only). Default: no events (off); `wakeDormant` defaults to true, and `false` keeps transitions for dormant sessions in `pending` until their next live turn (§4); without `actions`, delivery is the single winner and the generic prompt, and a key outside the vocabulary, an empty template or one over 2,000 code points is a validation error, as in the channel. The refresh timer is started in `packages/cli/src/serve/run-qwen-serve.ts` before the app exists, so it reaches the shared admission and restore through late-bound getters, as it already reaches the archive coordinator (`getArchiveCoordinator`). Detection latency is nominally one refresh interval (5 minutes by default; values below one minute fall back to the default and `0` disables the sweep) when the workspace's view set — its open bound PRs plus the closed ones the listing does not return (§1) — has at most 30 entries, and ⌈n/30⌉ intervals for n entries while the set does not change. Neither figure is a bound: a PR's observation moves within the tick as the workspace order rotates (§1) and other workspaces' listings and views run before it, and detection takes longer still when the deadline truncates a window, the `running` guard skips a tick (§1), a change in the set shifts the window, a view fails, the scan cannot enumerate the workspace or read the PR's sidecar, a watch-file read error skips the PR (§2), or ownership passes to another daemon (§2); delivery waits further drains when a retained recipient cannot be reached or a role group waits on a partial scan (§4), when dormant recipients wait for one of the four restore slots the daemon runs at once, each held until its restore settles, so that the last of k such recipients waits ⌈k/4⌉ − 1 further drains or more, and when a restore fails temporarily; with `wakeDormant: false` it waits for the session's next live turn. During the deprecation window PR B opens (§7), the GitHub channels' `prWatchEvents` and `watch:*` actions are read as aliases when `sessionPrWatch` is unset.

### 7. Channel migration

The GitHub channel's `deliverToBoundSessions` and its comment delivery stay in the channel, unchanged apart from the fixes of §4. Two PRs, and no window in which both pollers run.

**PR A** adds the daemon observation and delivery with their tests — the watch store and its owner record, the drain, the shared admission and restore, the prompt construction — behind an internal switch that stays off: the refresh runs no view and delivers nothing, and the `sessionPrWatch` setting is not read yet. The adapter watch keeps its behaviour apart from the fixes of §4 — its only code change is that it imports the template and prompt-envelope code PR A moves into `@qwen-code/channel-base` (§4) — so no build, nightly included, ever runs both pollers, and the two never need to split or hand over event types.

**PR B** turns the switch on and adds the `sessionPrWatch` setting (§6), and in the same change removes the adapter watch — the watch pass, its task-store branches, the 30-PR cap and the CI re-check intervals — opening a one-minor-release deprecation window. B no longer watches from the watch state file: at the first connect after the upgrade it reads the file once to log how many undelivered entries it still held, then renames it with a `.retired` suffix so the line is logged once, and it retires every persisted `watch:` inbound task privately with a log line, never through the comment lane's public fallback. `connect()` keeps accepting `prWatchEvents` and the `watch:*` keys of `boundSessionActions`, logs exactly one warning naming `sessionPrWatch`, runs no watch pass, and the Web Shell descriptor marks them deprecated. With `sessionPrWatch` unset, the daemon reads them as aliases, per host: each GitHub channel this daemon hosts — loaded with the trust gating channel hosting already applies, so an untrusted workspace's settings never contribute (`packages/cli/src/serve/channel-workspace-grouping.ts` refuses to host its channels) — contributes its `prWatchEvents` as the event set and its `watch:*` actions (`watch:<type>` → `<type>`, `<role>:watch:<type>` → `<role>:<type>`, with `default` and `<role>:default` kept) for PRs on its web host. A channel whose `boundSessionActions` is non-empty stays role-aware under the alias even when none of its keys applies to PR-state events, so a channel that subscribed no role to watch events keeps receiving none. The alias counts as the effective set of the daemon that hosts the channel — one daemon per global qwen dir, the channel service reservation — for the owner claim (§2); if another daemon already owns the watch with an explicit set, that set governs. PRs on other hosts get nothing from the alias, an explicit `sessionPrWatch` wins, and two channels on one host take the union of their events, each type taking its actions — the role-aware mode and keys — from the first channel by name whose `prWatchEvents` includes that type and whose configuration delivers it (no actions, or a chain that resolves a template for it), with a logged conflict; the alias logs once when it takes effect. The alias views use the daemon's `gh`, not the channel's token, so a PR the channel could read but the daemon's `gh` cannot gets nothing from the alias: the daemon logs a warning naming the PR and the error class after two consecutive failed views of it, once per failure streak, and also warns once at startup when an alias is in effect while the refresh timer is not running. An operator whose channel connected with its own token makes the host's `gh` able to read those repositories before upgrading. An operator who turned the watch on in v0.26.7 therefore keeps receiving its transitions across the release that ships B for every PR the daemon's `gh` can view while the daemon that hosts the channel holds the watch (§2) and runs its refresh timer, at the latency of §6 instead of the channel's 60 seconds, with one boundary: before B the daemon kept no watch file, so its first sweep after the upgrade initialises every bound PR silently (§2), and a transition between the channel's last poll and that sweep, or one the channel had not delivered when the upgrade landed — before its next poll, still deferred by backpressure, or dead-lettered — is not delivered; B's one-time log line counts such entries.

The first minor release after B rejects `prWatchEvents` and the `watch:*` keys at `connect()` with the same message and drops the alias. The setting shipped in v0.26.7, and a shipped, release-noted option is not rejected on sight even though it is opt-in behind `deliverToBoundSessions` and adoption is plausibly near zero; the `watch:*` keys (#16258) shipped in v0.26.8 and follow the same window for the same reason. B updates the channel docs and lands after A.

## Key decisions

1. **The daemon owns PR state.** It already polls it for the sidebar with the host credential; adding three fields and a delivery step is cheaper than a second poller, and it serves every bound session, not only those behind a configured channel.
2. **Per-PR `gh pr view` by URL, not the bulk rollup.** The refresh's slim bulk listing exists because the rollup field times out on large `--state all` queries; single-PR views avoid that, go by URL so a binding to another repository is fetched correctly, and are bounded by the view set — the open bound PRs plus the closed ones the listing does not return (§1) — at 30 per sweep, rotating, under one tick deadline.
3. **Same selection and transition rules as the channel watch**, role-aware actions included, so operators moving over see the same events, with one deliberate CI-predicate difference (decision 5, open question 2).
4. **One watch file per PR is the snapshot and the queue.** PR state is per PR, so the baseline, the pending transitions and the delivered record live once per PR in a small daemon-owned file instead of in every binder's sidecar. No copy can lag behind, so the design needs no rule for adopting, merging or re-detecting from stale replicas, and the sidecars keep only what the sidebar reads.
5. **One CI definition** (core's rollup), accepting that `cancelled` and `stale` count as failing until the open question below is settled.
6. **One-release deprecation window with aliases** for `prWatchEvents` and the `watch:*` actions: v0.26.7 shipped the setting (#16117, released 2026-11-04) and v0.26.8 the `watch:*` actions (#16258, released 2026-11-05), each named in its release notes, so neither is rejected on sight; adoption is plausibly near zero (days old, opt-in behind `deliverToBoundSessions`), so one minor release in which the old fields warn and are read as aliases — no configured operator loses events past the first sweep for a PR the daemon's `gh` can view while the daemon hosting the channel holds the watch and runs its refresh timer, and the daemon warns for one it cannot — is enough before `connect()` rejects them.
7. **Off by default** in this change; turning it on by default is a product decision for later.
8. **Self-push suppression is per recipient, from a push ledger, not from the GitHub account** (§4). An account cannot distinguish two sessions of one operator, and suppressing the transition itself would starve the review and verify roles that a fix session's push is meant to wake. Only `head_change` is suppressed, only for the session whose ledger records that head, and only where a ledger exists; the helper that performs the push already keeps one, so the daemon reads it instead of parsing shell commands or installing a hook.

## Constraints and risks

- **Latency** is nominally one refresh interval (5 minutes by default), instead of the channel's 60-second poll; for a view set of n entries it is nominally ⌈n/30⌉ intervals. Neither figure is a bound: §6 lists what makes it longer. Operators who need faster signal lower `QWEN_SESSION_PR_REFRESH_MINUTES` (values below 1 fall back to the default; `0` disables the sweep) and pay for it in views: each halving of the interval doubles the view volume, so at the one-minute floor one workspace spends up to 1,800 `gh pr view` calls per hour — the channel watch's figure at its cap — and five workspaces 9,000. The tick deadline (§1) shrinks with the interval (30 s at one minute), so the added views cannot stretch a tick past it by more than one view timeout, and restores run off the tick (§4); the listing calls the refresh already makes are unchanged.
- **Credential.** Requires `gh` authenticated on the daemon host, which the refresh and the PR sidebar already require. Workspaces without it keep today's behaviour (no state refresh, no events); from PR B on, a PR the daemon's `gh` cannot read receives no PR-state events, with a warning (§7).
- **State files.** One small JSON file per PR bound in the last 7 days, in a private directory owned by one daemon per global qwen dir (§2); the sidecars are unchanged. A daemon that does not hold the owner record delivers no PR-state events, and a record this machine cannot verify blocks the watch until it is deleted by hand, as for the channel service, and a daemon running as a user other than the owner of the watch directory or of a watch file in it never claims it (§2).
- **API budget.** At most 30 `gh pr view` calls per workspace per sweep: 360·W per hour for W swept workspaces at the default interval (1,800 per hour at W = 5, the channel watch's figure for one channel at its cap), on top of the existing listing, under the tick-level view deadline of half the refresh interval (§1). Views are deduplicated per tick by PR across workspaces (§1), so a PR bound in several workspaces is fetched once per tick.
- **Untrusted content into an interactive session.** The event prompt carries the PR title and check names as data, marked untrusted and passed through `sanitizePromptText` under the channel's 6,000-code-point cap (§4), the same contract as the channel's bound prompt; the session's approval mode governs its actions. A binding in the untrusted primary is viewed with the daemon's own credential (§1) — on every allowed host with `sessionPrWatch`, on the channel's web host under the alias (§7) — so the title and check names of a PR it names in any repository that credential can read reach that session as untrusted data. That is wider than the channel's watch today, which reads such bindings only on its own web host and with the token the operator gave the channel (`parsePrBindingUrl` in `GithubAdapter.ts`), and under the alias it arrives with the upgrade rather than by opting in. The design accepts it; an operator who does not want it leaves `sessionPrWatch` unset and removes the deprecated `prWatchEvents`, which ends the alias.
- **Admission classification.** A daemon-origin turn that is not an interactive prompt must stay unforgeable from clients. The design adds no new grant and no new marker: it rides the channel prompt's trusted chain — the route's worker credential, the bridge's trusted context, the child's trusted-parent check (§4).

## Validation plan

- Unit: view mapping (`url`, `title`, `headRefOid`, `mergeable` states, rollup) and the identity check (a view that returns another host or number is discarded; a binding spelled with `www.` or `/files` matches; a view of a renamed or transferred repository is accepted and keeps updating the binding's own file); the allowed hosts (a binding on another host, or a workspace whose `origin` is not GitHub, causes no `gh` call; `www.github.com` and `github.com` compare equal; `github.com` is allowed with no channel configured); the view environment (a workspace's own `GH_TOKEN` applies to its PRs) and working directory (the daemon-private watch directory); ## Acceptance criteria

1. With `sessionPrWatch.events` set, a bound session receives one prompt per transition instance for CI failure, merge conflict, head change and merge/close — one per matched role group with `actions` — with the same recurrence semantics as the channel watch, without any GitHub channel configured, except where this design states otherwise: a first observation and a re-bind before the watch file's deletion (§2), the 16-entry cap and the 7-day age limit (§5), no remaining candidate (§4), a head in the recipient's own pushed-head ledger (§4), a PR the daemon's `gh` cannot read (§7), a PR bound under both an old and a new repository name, delivered once per name (§1), a session another process writes live — a CLI session, or another daemon without the session writer lease (§4), a session served only by a daemon that does not hold the owner record, or while a record this machine cannot verify, or a watch directory or watch file another user owns, blocks the claim, and daemons with different global qwen dirs over one runtime base, which the PR watch does not support (§2), an admitted prompt still queued when the daemon restarts (§5), and the restart allowance of criterion 2.
2. Without a restart, a transition is detected at most once and each of its keys admitted at most once, whatever happens to the binders' sessions and workspaces in between — archived, outranked, unreadable, untrusted, retired — and even when two drains run concurrently. Across a restart a transition is delivered at most twice — only a crash between an admission and the write that records it repeats one — and at least once unless the PR's watch file is lost or no longer validates (§2), or its prompt was admitted and still queued behind a running turn when the daemon restarted (§5).
3. The GitHub channel no longer issues any PR-state API call; a configuration with `prWatchEvents` or `watch:*` actions still connects, logs exactly one deprecation warning naming `sessionPrWatch`, runs no watch pass, and — with `sessionPrWatch` unset — receives each transition through the daemon that hosts the channel from the first sweep after the upgrade for every PR that daemon's `gh` can view, routed by its `watch:*` actions, with a warning for one it cannot — unless another daemon with an explicit `sessionPrWatch` owns the watch, whose set then governs, or the hosting daemon otherwise does not hold the watch (§2) or runs no refresh timer, which it warns about at startup (§7); from the first minor release after PR B it is rejected at `connect()` with the same message.
4. With `sessionPrWatch` unset and no alias in effect, the refresh's behaviour and API call volume are unchanged.
5. Two trusted workspaces for one repository, each with a session bound to the same PR, receive one delivery per transition, to the most recently active of those sessions, also when the recipient is archived or outranked between detection and drain or either workspace is unreachable for a while; and a force-push back to a head whose CI failure already fired does not fire `ci_failure` again while that head is within the PR's 16-head history.
6. With `wakeDormant: false`, a transition for a dormant session is retained in `pending` and delivered on its next live turn; no build runs both pollers: before PR B the adapter delivers every PR-state event and the daemon none, and from PR B on the daemon delivers all of them.
7. A `head_change` whose new head is in a candidate's own pushed-head ledger — the one under the root the helper resolves for an existing watch, read through its guarded regular-file reader — is not delivered to that candidate: the drain re-resolves the next binder (within the same role group with role-aware actions), the other matched groups still receive it, and with no remaining candidate the transition is dropped with a log line on a complete scan and kept pending on a partial one. An absent, unreadable or mismatched ledger delivers as before, and authorship never suppresses `ci_failure`, `merge_conflict` or `state_change` (§4).

## Open questions

1. Should `sessionPrWatch` be on by default for the four events?
2. Should `cancelled` / `stale` check runs count as `ci_failure`? Core's rollup counts them (a concurrency-cancelled superseded run would fire); the channel watch excluded them.
3. `reviewDecision` is already fetched: add a `review_decision` transition (approved / changes requested) in the same mechanism?
4. Aone parity: expose the same transitions for Aone MRs once the Aone backend returns head and pipeline state.
5. Manual pushes have no ledger: only the autofix-pr helper records the heads it pushed (§4). Should a session-side record — a push ledger written by the tool that pushes, or a `pre-push` hook installed with the operator's consent — cover a manual `git push` too, or is the helper-only boundary acceptable?
