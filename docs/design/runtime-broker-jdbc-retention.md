# Runtime Broker JDBC Retention

[English](runtime-broker-jdbc-retention.md) | [简体中文](runtime-broker-jdbc-retention.zh-CN.md)

Status: Implemented for [#13203](https://github.com/QwenLM/qwen-code/issues/13203)

## Problem and scope

Terminal Broker bindings, sessions and executions accumulate indefinitely. New placement also maps and decrypts historical bindings to decide whether an earlier writer still blocks admission. Retention must bound cleanup work without discarding physical recovery, publication or migration evidence.

This change removes eligible JDBC records under retired bindings. It does not retire workers, delete physical storage, collect publication metadata or clean historical children under active bindings. Slots, generation counters, placement guards, harness heads and storage fences remain durable. Both embeddings use the single canonical 32-table baseline introduced in #14069; retention creates no second schema.

## Eligibility and references

Use the database clock. A binding must be older than the configured maximum age and have no live operation lease. RELEASED bindings are eligible; managed bindings additionally require a valid drain receipt or both loss and stopped-writer evidence. FAILED bindings are eligible only for unmanaged legacy/static placements with all three provision-seed columns absent. Other states and incomplete evidence remain retained.

Any nonterminal child retains the whole binding. SETTLED and ABANDONED executions must have completion timestamps older than the retention cutoff and no live dispatch lease. RELEASED and FAILED sessions must have last_active_at older than the cutoff and no remaining execution. Delete the binding only after every child is gone.

Operator recovery, Workspace holders and CSI retirement retain the whole binding, including completed recovery records. Publication and CSI worker ACK records retain their execution and, through it, the session and binding; unrelated siblings may be removed. COLLECTED publication records still retain their original evidence. Publication and ACK hashes use SHA-256 over raw UTF-8, unlike the Broker's length-prefixed execution hash; compute reference keys from bounded candidate IDs rather than joining unlike hashes.

A child Session's lineage retains its binding while the canonical parent child_run projection is missing or has no settled_at. Cascade and relay repair can need the original binding identity after the child has stopped, even without a tool execution or Workspace holder. Read lineage and the parent projection by primary key on the sweep connection, with exact raw identity checks. Lineage commits before child warm, and a terminal run cannot reopen; its committed settled_at ends this protection. Keep Session lineage, parent records and the permanent relay ledger intact.

A binding with a `<call>:process` execution is also retained while that execution's owning Session has an unsettled background Shell child_run projection. This includes top-level Sessions and both Session and Workspace isolation. Session-open reconciliation treats absence of that row as never-started proof, so cleanup must preserve the whole family until the owning Session's background Shell records settle. The guard first deduplicates owning Sessions using both the raw value and its binary identity, then performs the indexed existence lookup on the sweep connection with exact tenant, Workspace, Session and generation checks. This is conservative Session-level protection, not a one-to-one Shell/execution match.

## Components and concurrency

JdbcRuntimeRetention is a framework-neutral JDBC sweep with a same-connection reference guard supplied by the embedding. It returns continuation and scanned, skipped and per-table deletion counts. Its two-level keyset cursor tracks the binding and child phase; checked protected rows advance the cursor. Binding cursor comparisons use UTC literals with six fractional digits so Connector/J's MariaDB compatibility handshake cannot truncate timestamp parameters and stall traversal. A complete sweep wraps to the beginning, and a restart may safely repeat work.

For batch size B, one tick selects at most B binding candidates and B deletion-candidate child rows and deletes at most B rows across all three tables. Reference lookups can examine additional indexed rows; the batch counters do not cap database rows read. Large families span ticks. Each transaction locks tenant placement domain, slot, binding and then children; it rechecks eligibility and references using current committed state before deleting execution, session and finally binding. No transaction performs an unbounded cascade. Database errors roll back and propagate. Local publication mutations acquire the tenant placement guard and original JDBC binding and execution locks in their existing transaction, before publication locks, closing the reference-creation race and preserving the session lifecycle lock order. CSI retains its existing lock order.

Managed-server owns a separate single-thread scheduler gated by both Broker and retention enablement. Settings under qwen.managed-agent.runtime-broker.retention are enabled=false, max-age=30d, batch-size=100 (1–1000) and scan-delay=1m. Age and delay must be at least 1ms. A unit-less max-age is interpreted as days; explicit units, including sub-day windows of at least 1ms, are preserved. Successful ticks log counts; failed ticks log the error and retry on the next scheduled run. A failure rolls back the current binding transaction; earlier commits in that tick remain committed and are not included in a partial-count report. Recovery scheduling remains independent. Existing HTTP and business repository interfaces remain unchanged.

Use `ma_runtime_binding`, `ma_runtime_session` and `ma_tool_execution` for the three cleanup families. The one active `V1__managed_schema.sql` supplies binding state/time/ID and tenant/state indexes, an `ma_output_capture.execution_key` index and a `(work_kind, target_key, operation_key)` index on `ma_operation_work`. Reuse the existing `ma_storage_owner` binding/generation index and typed `ma_operation` target index. Operator recovery and CSI retirement must have their corresponding operation kind and `RUNTIME_BINDING` target; CSI ACK protection requires both `CSI_WORKER_ACK` work and a `CSI_RETIREMENT` parent operation. Parent and Shell projections must be `DOMAIN` records in `ma_session_record`, so another shared-table variant cannot falsely protect or authorize cleanup. The retired V69 SQL and legacy upgrade witness remain outside active classpaths under `docs/archive/managed-agent-schema/`; they are historical evidence, not deployment prerequisites. Placement uses SELECT 1 with LIMIT 1 and scalar state/identity predicates equivalent to blocksPlacement for valid records, preserving exact identity comparisons and conservatively treating incomplete seed/lease columns as present. It does not decrypt historical secrets and works independently of retention enablement.

## Retention contract and rollout

Enabling retention allows eligible, unreferenced historical records to be deleted once they age past max-age; it does not guarantee deletion by that age. Publication and CSI worker ACK references retain executions and their parent sessions and bindings regardless of age, including COLLECTED publications. Unreferenced siblings may be removed. After deletion, existing missing-record behavior applies; callers must not reuse expired runtime-session IDs or idempotency keys. No permanent execution tombstones are added.

Initialize a fresh database with the canonical 32-table V1 baseline and keep retention disabled. Validate exact Managed Server/Broker catalog parity and repeated initialization preserving existing terminal receipts. Legacy, partial or foreign catalogs are rejected before initialization writes; this change does not migrate old data or support an in-place upgrade. Preserve the old environment for historical reads, stop its new admissions and settle in-flight work before cutover; create new Sessions only in the new environment. Rollback after new data exists must preserve and serve the new database records. Keep retention disabled until the exact-identity Hosted cleanup release-proof contract in [#13992](https://github.com/QwenLM/qwen-code/issues/13992) is delivered and verified, and every publication writer uses the new locking protocol. An owed cleanup descriptor can outlive its RELEASED binding; collection then changes original release to a conflict and blocks the Hosted Session. This PR does not implement that release-proof contract. Observe scan/deletion/skip counts, duration and failures. Disable retention before reverting to older writers. Disabling stops future cleanup but cannot restore deleted records.

## Validation and acceptance

Cover age boundaries, database time, lifecycle states, physical evidence, live leases, nonterminal children, generation continuity and expired lookup behavior. Cover every external reference, completed recovery, COLLECTED publication and the distinct hash algorithms. Prove bounded progress with large families and protected rows, including subsecond timestamps, equal-time ID ordering and single-row batches, concurrent sweepers, rollback and reference creation races. Compare placement decisions to the in-memory implementation and assert zero historical decrypts. Check canonical schema/Flyway agreement, exact 32-table catalogs, old-schema refusal without writes, immutable rows on reinitialization, typed shared-table variants, scheduling isolation and configuration gates. Exercise locking and collation on MySQL/MariaDB, not H2 alone.

Reproduce a stopped child whose parent still owes dispatch/attach journal repair: cleanup must preserve its original binding until that repair can complete. Verify missing projections fail closed, raw identity mismatches do not end protection, the guard sees the sweep transaction's own writes, and a canonical terminal projection allows cleanup without collecting lineage or relay classifications.

Verify that an unsettled top-level background Shell keeps its original process-status evidence under both isolation modes, while a settled projection permits cleanup. Check raw identity and generation mismatches and replacement-generation admission. Include thousands of settled Shells with other-Session noise and permissive-collation owners; verify the guard finishes and the real sweep reaches the following family.

The legacy-schema verification remains historical evidence. The 32-table port is accepted only after rerunning the same integration witness, scoped regression tests and native MySQL/MariaDB retention, reference-race and catalog contracts. Query plans are not latency guarantees, and these checks do not qualify production cutover, physical worker recovery or the separate cleanup release-proof contract.

Implementation artifacts are the Broker sweep and placement guard, managed-server reference guard, scheduler/configuration, the single canonical baseline, repository tests and README updates. Retention remains disabled pending the separate cleanup release-proof contract in #13992.
