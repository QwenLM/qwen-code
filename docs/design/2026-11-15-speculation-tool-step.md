## The question

#17045 asks speculation's PR 6b to put "the tool step and the run on the shared loop, or a recorded decision to keep its own". PR 6a (#17029) already moved speculation's model round onto `runModelRound`. This decision covers the tool step and the surrounding speculative loop.

## What the code actually requires (verified)

Speculation runs ahead of the user in the background with read-only tools and copy-on-write overlay writes, and its tool step is built around that. The [speculation engine design](prompt-suggestion/speculation-design.md) specifies the tool gate, path rewrite and boundary handling restated below; the line citations are verified against the code.

1. **Direct execution, bypassing the scheduler.** Each call is run through `tool.build(args)` and `invocation.execute(signal)` directly (`speculation.ts:458-519`), not through `CoreToolScheduler`. Permission-deferred calls bail to the normal flow instead (`:412-416`).
2. **Overlay writes, not the real filesystem.** A `redirect` gate rewrites path arguments into the overlay (`rewritePathArgs`, `:448-456`); the overlay is copied to the real filesystem only on accept, and discarded on reject.
3. **A boundary gate that bails mid-batch.** `evaluateToolCall` returns `boundary` / `redirect` / `allow`; a boundary (or a failed rewrite, or a guard denial) stops the speculative run at that call and hands back to the normal loop (`:435-456`, `:499-511`). The hand-back is a **partial batch**: the already-executed responses are kept and the unexecuted calls are stripped, keeping the first N `functionCall` parts by order to match the responses (`:611-659`).
4. **No committed recording.** Speculation finalizes responses (`finalizeToolResponses`, `:607`) but never records them as committed tool calls; its results are speculative and must not enter the committed tool-call history.
5. **Sequential with early bail.** Calls are processed one at a time and the run stops at the first boundary.

### What the shared batch interface already allows

The execution and recording mechanics above are **not** structural blockers of the shared interface, and neither are partial results. `runToolBatch` takes a caller-provided `executor` (`agent-loop.ts:476`), so a speculative executor could run calls directly and sequentially; `client` is optional (`:467`), and `client?.recordCompletedToolCall(...)` (`:673`) updates session bookkeeping — the tool-call count, the recent-completed-tool names used for memory, and the skills-modified flag — so omitting `client` skips that bookkeeping; the committed tool-result write is the separate `record()` closure calling `recordToolResult` (`:741`, `:746`), which `deferRecording` (`:490`) returns as a callback instead of invoking (`:761-765`), so a surface records only what it sends — avoiding committed recording means deferring those callbacks, not merely omitting `client`. Three further seams bear on the boundary/partial-batch behavior (this list is not exhaustive): `keepCancelledResults` (`:485`) finishes and returns a cancelled batch's results for a surface that keeps them; `ToolBatchResult.responses` (`:500`) returns the parts by call "for a surface that drops some calls' results", which a live surface already uses to send only a subset (`use-llm-stream.ts:6710-6714`); and the per-call launch gate `host.beforeToolLaunch` (`:221`, wired at `:632`) refuses a call in request order and leaves it unexecuted. Direct execution, sequential execution, avoiding committed recording, partial results and per-call refusal are all expressible through this interface; they do not, by themselves, justify keeping a separate tool step.

## Decision

**Keep speculation's own tool step and speculative loop — because the adapter that composes the shared seams into speculation's hand-back is not worthwhile for a background optimization, not because the shared interface cannot express the mechanics.** The seams above express direct, sequential, unrecorded execution and partial results. The mechanical difference is in the default output: the batch answers every executable call it did not run with a `skipped` response in `parts` (`agent-loop.ts:692`), whereas speculation's hand-back strips the unexecuted `functionCall` parts out of the model message itself (`speculation.ts:611-659`). A surface reconciles this by building its next round from `responses` rather than `parts` — `use-llm-stream.ts:6710-6714` already drops a subset that way — so the strip is a composition the surface writes, not a capability the batch lacks. On top of that composition speculation still needs its overlay accept/reject (on accept the overlay is applied to the real filesystem best-effort per file; on reject it is discarded) and its surrounding speculative loop. Composing and maintaining that speculative adapter against a working, tested tool step is the cost this decision declines for a background optimization. This is the same shape as the Hosted Harness decision: the model round is shared, the specialized tool step stays.

The model round stays on the shared loop as PR 6a landed it (`runSpeculationModelRound`, gated by `isUnifiedAgentLoopEnabled('speculation')`); the tool gate, direct execution, overlay writes and boundary handling are unchanged.

**End-state note.** Keeping speculation's own loop and finalizer permanently means the parent design's original end-state targets of 1 agent loop implementation and 1 `finalizeToolResponses` caller are not literally reachable: speculation's call (`speculation.ts:607`) remains alongside the shared batch's (`agent-loop.ts:715`). Those two targets count the shared implementation plus the copies the keep-its-own decisions retain, as the End state table in [unified agent loop](2026-10-23-unified-agent-loop.md) now notes — its Target cells count those copies.

## Integration gate decision

No integration test runs speculation today. **Recorded decision: speculation's unit parity suite is its gate.** The suite already compares the shared round off and on (`speculation.test.ts`, "speculation model round on the shared agent loop" and "speculation shared-round event semantics"), including a branch marker pinning that the shared round runs only with the setting on. A deterministic end-to-end speculative round is not a practical integration gate: speculation is a background, timing-dependent optimization whose accept/boundary outcome depends on user input arriving mid-run. The unit parity suite, not an integration scenario, gates the shared-round migration. The off/on comparison covers the shared model round. The boundary hand-back is speculation's own unchanged tool step: the boundary tests exercise its zero-executed bail on the raw-chunk arm, and the partial-batch hand-back (item 3) — including its composition with the shared round's parts — is now tested on both arms (#17399), which also pins absolute execute counts in the multi-call parity scenarios. That partial-batch coverage is closed (#17399); it was a pre-existing gap, not one this decision introduced.

This gates the shared-round migration (PR 6a), not PR 6c's default flip. The parent design's integration entry ("that run is added when its default flip is prepared") and its default-change criteria — the five-step model's step 2, whose full condition list is in [unified agent loop](2026-10-23-unified-agent-loop.md) and is not restated here — still stand for 6c. Since a deterministic end-to-end speculative round is impractical for the timing reasons above, the 6c author must reconcile that requirement: name a nightly integration signal that satisfies it, or record in the follow-up #17284 that the unit parity suite suffices for the default flip too. This record leaves that question to 6c rather than preempting it.
