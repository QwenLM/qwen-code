# Deliver background (async) hook output to the model

[English](2026-11-16-async-hook-output-delivery.md) | [简体中文](2026-11-16-async-hook-output-delivery.zh-CN.md)

- **Status**: implemented in this change for the `LlmClient` request path. Moves capability ledger row L11 from `missing` to `differs`: the output reaches the model on surfaces whose model round sends through `LlmClient.sendMessageStream`; the ACP default legacy round sends through the session's own chat and does not drain yet, so that surface's delivery is a follow-up carried by #17284.
- **Date**: 2026-11-16, against `main` `27681123f719`.
- **Related**: [agent loop capability ledger](2026-11-15-loop-capability-ledger.md) (L11); [unified agent loop](2026-10-23-unified-agent-loop.md); follow-up #17284; the synchronous counterpart `hooks/user-prompt-submit-context.ts`.

## The defect

Background (async) hooks run between turns. When one completes, `AsyncHookRegistry.complete` parses its stdout and accumulates model-facing context (`hookSpecificOutput.additionalContext`) and notification messages (`systemMessage`, plain stdout, stderr) into `completedContexts` / `completedOutputs`. `HookSystem.getPendingAsyncOutput()` drains both (get-and-clear), and its doc comment says the output is "for delivery to the next turn" — but **nothing called it**: on `main` the only occurrence of `getPendingAsyncOutput` outside tests is its own definition (`hooks/hookSystem.ts:996`). The output was collected and then silently dropped; it never reached the model. The 1.0 loop drains the equivalent pending async context in its request preparation (`event-bus/llm/request-preparation.ts:748-760`) and injects it as a meta user message before compression.

## The decision

Drain the pending async output when the outgoing request is assembled, and append it as a tagged context part, so it reaches the model on the next request.

- **Delivery point**: `LlmClient.sendMessageStream`, at the `requestToSend` assembly — after the UserPromptSubmit hook-context receipt and before the IDE-context merge and the system-reminders prepend. This is downstream of the Goal-admission and hook-window settlement blocks (it touches none of their contracts) and upstream of the send and its in-chat auto-compaction, so the compression threshold sees the same tail the provider will — matching the 1.0 "drain before compression" intent. It covers every turn type that reaches the assembly. Surfaces whose model round is the main session's `LlmClient` reach it — headless and Ink (including their unified-loop defaults, where the shared round's source is the `LlmClient`), and ACP with the unified loop opted in; the ACP default legacy round sends through the session's own chat (`Session.ts` → `chat.sendMessageStream`) and never enters this method, so its async output is still dropped there — a follow-up, not a regression against base, which delivered nothing on any surface. `getHookSystem` is read defensively (`getHookSystem?.()`, and the helper calls `getPendingAsyncOutput?.()`), so a config or hook-system double without the method degrades to "nothing to deliver" rather than throwing.
- **Placement keeps the sync receipt trailing**: when a UserPromptSubmit context receipt is the trailing part, the async part is spliced in _before_ it (`appendAsyncHookContextPart`), not appended after it. The resume half of the receipt contract (`restoreUserPromptSubmitContextReceipt`), the legacy transcript-projection strip and the session-title strip all recognize the sync block only in last position; an async part trailing it would silently defeat them on a co-occurrence turn (sync context + async output in one request), losing the sync block's resume provenance and re-injecting its context after resume. With no trailing sync receipt the async part is simply appended.
- **Wire order keeps the instruction last**: the async envelope is registered with the injected-context classifier — `isAsyncHookContextPartText` (beside the tag constants in `hooks/async-hook-context.ts`) is OR'd into `isInjectedPromptContext` (`core/prompt-context-order.ts`), so `movePromptContextAheadOfUserText` hoists the block ahead of the user's instruction on the wire copy, like the other injected blocks. Without this the bare tag would count as the caller's own text and the wire entry would end in hook output. Only wire copies are reordered; the stored-history placement the splice depends on is untouched.
- **Ownership gates the drain**: a concurrent `/btw` side query runs through the same client and must not consume the running turn's pending block. Its first send carries `isConcurrentSideQuery`, but its tool-result continuation arrives **unflagged**, so a flag-only guard would still admit the continuation as a consumer. The client therefore records the prompt id of each flagged side-query first send (`concurrentSideQueryPromptIds`), and the drain skips when `isConcurrentSideQuery === true` OR the send is a `ToolResult` whose prompt id is a recorded side-query id. Every other `ToolResult` drains: the owning turn's continuation, and a continue-interrupted turn (`continue_last_turn`) that sends `ToolResult` first under a fresh prompt id. The exploration-budget prompt id (`ownsExplorationBudget`) is deliberately **not** the discriminator: it is claimed only on `startsInteraction`, so a `ToolResult`-first turn — whether the budget id is unclaimed (fresh client) or stale from an interrupted turn — would be refused and silently lose the block, re-introducing the very silent-loss class this change fixes. A recorded side-query id is the only signal that separates a side continuation from a legitimate `ToolResult`-first turn. The record is cleared when a new main turn claims a different prompt id (a same-id retry keeps it). This is deliberately narrow: it is not a general hook/epoch authority model for Cron, ACP, background sessions or rebindings, which remain follow-ups.
- **What is delivered**: both `contexts` (verbatim additional context) and `messages` (labeled `[type] hookName: message`), joined into one block. `<`/`>` are escaped so hook output cannot forge the closing tag, mirroring the synchronous UserPromptSubmit context.
- **Reserved tag**: `<qwen:async-hook-context>…</qwen:async-hook-context>`, defined in the new self-contained `hooks/async-hook-context.ts`.
- **Get-and-clear, no dedup**: the drain clears the registry, so a block is _selected for delivery_ once. Unlike the synchronous UserPromptSubmit context — which persists in history and therefore needs the receipt symbol, history dedup and resume re-stamping — the async block needs none of that machinery. Two boundaries are deliberate: (1) "selected once" is not "admitted by a model turn" — a send that fails after the drain (loop detection, goal interruption, a 429/retry) consumes the block without delivering it, the consume-but-not-sent window; locating the drain immediately before the send minimizes it without changing the evidence class. (2) The block is appended to the **in-memory request history only**: the transcript record is built from the pre-append `request`, so the block is not persisted, and a resumed session (`--continue`) does not carry it. Resume provenance for the async tag is a documented follow-up, not a regression against base, which delivered nothing at all.

## Scope

- **In**: model-facing delivery of pending async hook output (L11) on the `LlmClient` request path: the drain, the formatting/wrapping helper, the single call site in the request assembly, the wire-order classifier registration, and unit tests with mutation witnesses.
- **Out (follow-up)**: (1) the ACP default legacy round's own assembly — it sends through the session's chat, not `LlmClient`, so it needs the same drain/append pair (reusing the helper) to deliver there; (2) display projection and resume provenance for the async tag. The synchronous context is hidden from the user-facing transcript projection and re-stamped on resume via its receipt; the async block is delivered as a tagged part but is not yet wired into `projectUserTranscriptForDisplay`, so it currently projects as model-facing text. Hiding it and giving it resume provenance is a separate concern from "the output reaches the model" and is left to a follow-up.

## Verification

`hooks/async-hook-context.test.ts` drives a real `AsyncHookRegistry`: a completed hook's `additionalContext` and `systemMessage` are delivered in the tagged part, a second drain delivers nothing (get-and-clear), blank context and whitespace-only messages yield no part, a hook-system double without the drain method degrades to null, and hook output cannot forge the closing tag. `appendAsyncHookContextPart` is tested for the splice-before-trailing-receipt placement, and a co-occurrence test resumes a cloned entry (symbols dropped) and asserts `restoreUserPromptSubmitContextReceipt` re-stamps the sync block when the async part is spliced ahead of it — and fails to when the async part trails it (the bug the placement avoids). `client.test.ts` adds call-site witnesses: a real `sendMessageStream` turn with a registry-backed `getHookSystem` delivers the block into the outgoing request, drains it once across two turns, and delivers nothing when no output is pending; a co-occurrence UserQuery turn carrying `promptContext` asserts the sync receipt stays the last part `turn.run` receives with the async block immediately before it; and a ToolResult turn asserts the block is appended after the `functionResponse` parts, which are carried through unchanged. Further call-site cases pin the remaining boundaries: the persisted user record carries no async block while the wire request does (in-memory only); a `/btw` side query — both its flagged first send and its unflagged non-owner `ToolResult` continuation — leaves the block for the owning turn, which receives it once; and a continue-interrupted `ToolResult`-first turn delivers the block both when its prompt id was never claimed (fresh client) and when a prior turn left a stale claimed budget id. These call-site checks match the envelope with `isAsyncHookContextPartText`, the same predicate the code uses. `prompt-context-order.test.ts` asserts the wire reorder hoists a trailing async block (and an async + sync run) ahead of the caller text, and `isAsyncHookContextPartText` is unit-tested for envelope recognition, whitespace tolerance and internal-tag rejection. Mutation witnesses (each restored byte-identical): making the drain deliver nothing turns the delivery tests red; removing the escaping turns the escaping tests red; removing the message blank-guard turns the whitespace test red; collapsing the splice to a plain append turns the placement and co-occurrence tests red; deleting the `client.ts` call site turns the call-site delivery tests red; dropping the async matcher from `isInjectedPromptContext` turns the two wire-order hoist tests red; forcing `syncReceiptTrailing` to `false` turns the co-occurrence call-site test red; skipping the drain on a ToolResult turn turns the ToolResult test red; dropping the recorded-side-query-id check (a flag-only gate) turns the `/btw` side-query test red; reverting the gate to the exploration-budget ownership refusal turns the two continue-turn delivery tests red; draining into the recorded `request` turns the persisted-record test red. A real-environment run — the headless CLI from source against a mock OpenAI server, with an `async: true` PostToolUse hook configured in settings — confirmed the full pipeline: the hook's `additionalContext` was drained and appeared in the outgoing provider request body as a `<qwen:async-hook-context>` block on the turns after the hook completed. `prettier`/`eslint` clean on the changed files; the changed files typecheck (CI's frozen-lockfile build is authoritative).
