# Deliver background (async) hook output to the model

[English](2026-11-16-async-hook-output-delivery.md) | [简体中文](2026-11-16-async-hook-output-delivery.zh-CN.md)

- **Status**: implemented in this change. Closes capability ledger row L11, carried as a defect by the follow-up #17284.
- **Date**: 2026-11-16, against `main` `27681123f719`.
- **Related**: [agent loop capability ledger](2026-11-15-loop-capability-ledger.md) (L11); [unified agent loop](2026-10-23-unified-agent-loop.md); follow-up #17284; the synchronous counterpart `hooks/user-prompt-submit-context.ts`.

## The defect

Background (async) hooks run between turns. When one completes, `AsyncHookRegistry.complete` parses its stdout and accumulates model-facing context (`hookSpecificOutput.additionalContext`) and notification messages (`systemMessage`, plain stdout, stderr) into `completedContexts` / `completedOutputs`. `HookSystem.getPendingAsyncOutput()` drains both (get-and-clear), and its doc comment says the output is "for delivery to the next turn" — but **nothing called it**: on `main` the only occurrence of `getPendingAsyncOutput` outside tests is its own definition (`hooks/hookSystem.ts:996`). The output was collected and then silently dropped; it never reached the model. The 1.0 loop drains the equivalent pending async context in its request preparation (`event-bus/llm/request-preparation.ts:748-760`) and injects it as a meta user message before compression.

## The decision

Drain the pending async output when the outgoing request is assembled, and append it as a tagged context part, so it reaches the model on the next request.

- **Delivery point**: `LlmClient.sendMessageStream`, at the `requestToSend` assembly — after the UserPromptSubmit hook-context receipt and before the IDE-context merge and the system-reminders prepend. This is downstream of the Goal-admission and hook-window settlement blocks (it touches none of their contracts) and upstream of the send and its in-chat auto-compaction, so the compression threshold sees the same tail the provider will — matching the 1.0 "drain before compression" intent. It covers every turn type that reaches the assembly. `getHookSystem` is read defensively (`getHookSystem?.()`, and the helper calls `getPendingAsyncOutput?.()`), so a config or hook-system double without the method degrades to "nothing to deliver" rather than throwing.
- **Placement keeps the sync receipt trailing**: when a UserPromptSubmit context receipt is the trailing part, the async part is spliced in _before_ it (`appendAsyncHookContextPart`), not appended after it. The resume half of the receipt contract (`restoreUserPromptSubmitContextReceipt`), the legacy transcript-projection strip and the session-title strip all recognize the sync block only in last position; an async part trailing it would silently defeat them on a co-occurrence turn (sync context + async output in one request), losing the sync block's resume provenance and re-injecting its context after resume. With no trailing sync receipt the async part is simply appended.
- **What is delivered**: both `contexts` (verbatim additional context) and `messages` (labeled `[type] hookName: message`), joined into one block. `<`/`>` are escaped so hook output cannot forge the closing tag, mirroring the synchronous UserPromptSubmit context.
- **Reserved tag**: `<qwen:async-hook-context>…</qwen:async-hook-context>`, defined in the new self-contained `hooks/async-hook-context.ts`.
- **Get-and-clear, no dedup**: the drain clears the registry, so a block is _selected for delivery_ once. Unlike the synchronous UserPromptSubmit context — which persists in history and therefore needs the receipt symbol, history dedup and resume re-stamping — the async block needs none of that machinery. Two boundaries are deliberate: (1) "selected once" is not "admitted by a model turn" — a send that fails after the drain (loop detection, goal interruption, a 429/retry) consumes the block without delivering it, the consume-but-not-sent window; locating the drain immediately before the send minimizes it without changing the evidence class. (2) The block is appended to the **in-memory request history only**: the transcript record is built from the pre-append `request`, so the block is not persisted, and a resumed session (`--continue`) does not carry it. Resume provenance for the async tag is a documented follow-up, not a regression against base, which delivered nothing at all.

## Scope

- **In**: model-facing delivery of pending async hook output (L11): the drain, the formatting/wrapping helper, the single call site in the request assembly, and unit tests with mutation witnesses.
- **Out (follow-up)**: display projection and resume provenance for the async tag. The synchronous context is hidden from the user-facing transcript projection and re-stamped on resume via its receipt; the async block is delivered as a tagged part but is not yet wired into `projectUserTranscriptForDisplay`, so it currently projects as model-facing text. Hiding it and giving it resume provenance is a separate concern from "the output reaches the model" and is left to a follow-up.

## Verification

`hooks/async-hook-context.test.ts` drives a real `AsyncHookRegistry`: a completed hook's `additionalContext` and `systemMessage` are delivered in the tagged part, a second drain delivers nothing (get-and-clear), blank context and whitespace-only messages yield no part, a hook-system double without the drain method degrades to null, and hook output cannot forge the closing tag. `appendAsyncHookContextPart` is tested for the splice-before-trailing-receipt placement, and a co-occurrence test resumes a cloned entry (symbols dropped) and asserts `restoreUserPromptSubmitContextReceipt` re-stamps the sync block when the async part is spliced ahead of it — and fails to when the async part trails it (the bug the placement avoids). `client.test.ts` adds a call-site witness: a real `sendMessageStream` turn with a registry-backed `getHookSystem` delivers the block into the outgoing request, drains it once across two turns, and delivers nothing when no output is pending. Mutation witnesses (each restored byte-identical): making the drain deliver nothing turns the delivery tests red; removing the escaping turns the escaping tests red; removing the message blank-guard turns the whitespace test red; collapsing the splice to a plain append turns the placement and co-occurrence tests red; deleting the `client.ts` call site turns the call-site delivery tests red. `prettier`/`eslint` clean on the changed files; the changed files typecheck (CI's frozen-lockfile build is authoritative).
