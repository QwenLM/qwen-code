# Deliver background (async) hook output to the model

[English](2026-11-16-async-hook-output-delivery.md) | [简体中文](2026-11-16-async-hook-output-delivery.zh-CN.md)

- **Status**: implemented in this change for the `LlmClient` request path. Moves capability ledger row L11 from `missing` to `differs`: the output reaches the model on surfaces whose model round sends through `LlmClient.sendMessageStream`; the ACP default legacy round sends through the session's own chat and does not drain yet, so that surface's delivery is a follow-up carried by #17284.
- **Date**: 2026-11-16, against `main` `27681123f719`.
- **Related**: [agent loop capability ledger](2026-11-15-loop-capability-ledger.md) (L11); [unified agent loop](2026-10-23-unified-agent-loop.md); follow-up #17284; the synchronous counterpart `hooks/user-prompt-submit-context.ts`.

## The defect

Background (async) hooks run between turns. When one completes, `AsyncHookRegistry.complete` parses its stdout and accumulates model-facing context (`hookSpecificOutput.additionalContext`) and notification messages (`systemMessage`, plain stdout, stderr) into `completedContexts` / `completedOutputs`. `HookSystem.getPendingAsyncOutput()` drains both (get-and-clear), and its doc comment says the output is "for delivery to the next turn" — but **nothing called it**: on `main` the only occurrence of `getPendingAsyncOutput` outside tests is its own definition (`hooks/hookSystem.ts:996`). The output was collected and then silently dropped; it never reached the model. The 1.0 loop drains the equivalent pending async context in its request preparation (`event-bus/llm/request-preparation.ts:748-760`) and injects it as a meta user message before compression.

## The decision

Drain the pending async output when the outgoing request is assembled, and append it as a tagged context part, so it reaches the model on the next request.

- **Delivery point**: `LlmClient.sendMessageStream`, at the `requestToSend` assembly — after the UserPromptSubmit hook-context receipt and before the IDE-context merge and the system-reminders prepend. This is downstream of the Goal-admission and hook-window settlement blocks (it touches none of their contracts) and upstream of the send and its in-chat auto-compaction, so the compression threshold sees the same tail the provider will — matching the 1.0 "drain before compression" intent. It covers every turn type that reaches the assembly. Surfaces whose model round is the main session's `LlmClient` reach it — headless and Ink (including their unified-loop defaults, where the shared round's source is the `LlmClient`), and ACP with the unified loop opted in; the ACP default legacy round sends through the session's own chat (`Session.ts` → `chat.sendMessageStream`) and never enters this method, so its async output is still dropped there — a follow-up, not a regression against base, which delivered nothing on any surface. `getHookSystem` is read defensively (`getHookSystem?.()`, and the helper calls `getPendingAsyncOutput?.()`), so a config or hook-system double without the method degrades to "nothing to deliver" rather than throwing.
- **Placement keeps the sync receipt trailing**: when a UserPromptSubmit context receipt is the trailing part, the async part is spliced in _before_ it (`appendAsyncHookContextPart`), not appended after it. The resume half of the receipt contract (`restoreUserPromptSubmitContextReceipt`), the legacy transcript-projection strip and the session-title strip all recognize the sync block only in last position; an async part trailing it would silently defeat them on a co-occurrence turn (sync context + async output in one request), losing the sync block's resume provenance and re-injecting its context after resume. With no trailing sync receipt the async part is simply appended.
- **Wire order keeps the instruction last**: the async envelope is registered with the injected-context classifier — `isAsyncHookContextPartText` (beside the tag constants in `hooks/async-hook-context.ts`) is OR'd into `isInjectedPromptContext` (`core/prompt-context-order.ts`), so `movePromptContextAheadOfUserText` hoists the block ahead of the user's instruction on the wire copy, like the other injected blocks. Without this the bare tag would count as the caller's own text and the wire entry would end in hook output. Only wire copies are reordered; the stored-history placement the splice depends on is untouched.
- **Ownership gates the drain**: a concurrent `/btw` side query runs through the same client and must not consume the running turn's pending block. Its first send carries `isConcurrentSideQuery`, but its tool-result continuation arrives **unflagged**, so a flag-only guard would still admit the continuation as a consumer. The client therefore records the prompt id of each flagged side-query first send (`concurrentSideQueryPromptIds`), and the drain skips when `isConcurrentSideQuery === true` OR the send is a `ToolResult` whose prompt id is a recorded side-query id. Every other `ToolResult` drains: the owning turn's continuation, and a continue-interrupted turn (`continue_last_turn`) that sends `ToolResult` first under a fresh prompt id. The side query's client-initiated continuations — the blocking Stop-hook and stop-policy sends, which are `Hook`-type and rebuild their options via `hostContinuationOptions` — carry the flag forward, so they are refused as well; the owning turn's own such continuations carry no flag and keep draining. The exploration-budget prompt id (`ownsExplorationBudget`) is deliberately **not** the discriminator: it is claimed only on `startsInteraction`, so a `ToolResult`-first turn — whether the budget id is unclaimed (fresh client) or stale from an interrupted turn — would be refused and silently lose the block, re-introducing the very silent-loss class this change fixes. A recorded side-query id is the only signal that separates a side continuation from a legitimate `ToolResult`-first turn. The record is kept for the client's lifetime: a side query still awaiting its continuation must stay refused even after a new main turn starts (clearing it there would let the late continuation drain the new turn's block), and prompt ids are per-turn unique, so a recorded id is never legitimately reused. This is deliberately narrow: it is not a general hook/epoch authority model for Cron, ACP, background sessions or rebindings, which remain follow-ups.
- **What is delivered**: both `contexts` (verbatim additional context) and `messages` (labeled `[type] hookName: message`), joined into one block. `<`/`>` are escaped so hook output cannot forge the closing tag, mirroring the synchronous UserPromptSubmit context.
- **Bounded block**: the registry accumulates every completion with no total limit, so the joined block is capped at `MAX_ASYNC_HOOK_CONTEXT_LENGTH` — aliased to the user-prompt-expansion additional-context cap so the two stay in lockstep — before wrapping; a verbose hook or many completions cannot append megabytes to the request or to the side query that reuses it. Notification messages are reserved first (the get-and-clear drain would otherwise lose a notice displaced by a verbose context tail), and the context half is truncated to the remaining budget with a `[async hook context truncated]` notice reserved inside the bound, mirroring `boundToolHookContext`. A message-only block past the cap is bounded too (non-JSON stdout/stderr become single messages with no per-message cap), and a cut message half carries a distinct `[async hook message truncated]` notice — so a message-only block does not announce a context truncation that never happened, and a squeezed message cut is not left unmarked. When a large message half squeezes the context budget below the notice's length — including a message that fills the cap and displaces the context entirely — the notice's room is reserved from the message side so the cut or displaced context stays marked, rather than reading as complete or as "no context"; this diverges from `boundToolHookContext`, whose budget is caller-chosen rather than squeezed by a sibling half. The cut strips a trailing partial escape entity first and then backs off an orphaned high surrogate (as `safePrefix` does): the strip shortens the prefix and can re-expose a surrogate, so the back-off must run after it.
- **Reserved tag**: `<qwen:async-hook-context>…</qwen:async-hook-context>`, defined in the new self-contained `hooks/async-hook-context.ts`.
- **Get-and-clear, no dedup**: the drain clears the registry, so a block is _selected for delivery_ once. Unlike the synchronous UserPromptSubmit context — which persists in history and therefore needs the receipt symbol, history dedup and resume re-stamping — the async block needs none of that machinery. Two boundaries are deliberate: (1) "selected once" is not "admitted by a model turn" — a send that fails after the drain (loop detection, goal interruption, a 429/retry) consumes the block without delivering it, the consume-but-not-sent window; locating the drain immediately before the send minimizes it without changing the evidence class. (2) The block is appended to the **in-memory request history only**: the transcript record is built from the pre-append `request`, so the block is not persisted, and a resumed session (`--continue`) does not carry it. Resume provenance for the async tag is a documented follow-up, not a regression against base, which delivered nothing at all.

## Scope

- **In**: model-facing delivery of pending async hook output (L11) on the `LlmClient` request path: the drain, the formatting/wrapping helper, the single call site in the request assembly, the wire-order classifier registration, and unit tests with mutation witnesses.
- **Out (follow-up)**: (1) the ACP default legacy round's own assembly — it sends through the session's chat, not `LlmClient`, so it needs the same drain/append pair (reusing the helper) to deliver there; (2) display projection and resume provenance for the async tag. The synchronous context is hidden from the user-facing transcript projection and re-stamped on resume via its receipt; the async block is delivered as a tagged part but is not yet wired into `projectUserTranscriptForDisplay`, so it currently projects as model-facing text. Hiding it and giving it resume provenance is a separate concern from "the output reaches the model" and is left to a follow-up.

## Verification

`hooks/async-hook-context.test.ts` drives a real `AsyncHookRegistry`: a completed hook's `additionalContext` and `systemMessage` are delivered in the tagged part, a second drain delivers nothing (get-and-clear), blank context and whitespace-only messages yield no part, a hook-system double without the drain method degrades to null, and hook output cannot forge the closing tag; the joined block is bounded (a verbose context and many completions are capped to exactly the bound, a notification message survives a verbose context that fills the cap, a cut straddling an escape entity is stripped clean and a cut straddling an astral character backs off, a cut that re-exposes a surrogate after the entity strip backs off in the correct order, a cut context stays marked when the message half squeezes its budget below the notice, a message-dominated block with no context is bounded, a context displaced by a cap-filling message stays marked, the message-half cut strips a straddling escape entity and backs off a straddling astral character at both the message-only and squeeze sites, a message-only block carries the message notice rather than the context notice, a squeezed message half is marked, a truncation notice marks a cut context, and an under-cap block is untouched). `appendAsyncHookContextPart` is tested for the splice-before-trailing-receipt placement, and a co-occurrence test resumes a cloned entry (symbols dropped) and asserts `restoreUserPromptSubmitContextReceipt` re-stamps the sync block when the async part is spliced ahead of it — and fails to when the async part trails it (the bug the placement avoids). `client.test.ts` adds call-site witnesses: a real `sendMessageStream` turn with a registry-backed `getHookSystem` delivers the block into the outgoing request, drains it once across two turns, and delivers nothing when no output is pending; a co-occurrence UserQuery turn carrying `promptContext` asserts the sync receipt stays the last part `turn.run` receives with the async block immediately before it; and a ToolResult turn asserts the block is appended after the `functionResponse` parts, which are carried through unchanged. Further call-site cases pin the remaining boundaries: the persisted user record carries no async block while the wire request does (in-memory only); a `/btw` side query — both its flagged first send and its unflagged non-owner `ToolResult` continuation — leaves the block for the owning turn, which receives it once; and a continue-interrupted `ToolResult`-first turn delivers the block both when its prompt id was never claimed (fresh client) and when a prior turn left a stale claimed budget id; and a side continuation that arrives after a new main turn starts — or after a same-id retry of the main turn — is still refused, while the new turn's own continuation receives the block; and a side query whose blocking Stop hook ends the answer in a `Hook` continuation leaves the block for the owning turn's `ToolResult` continuation. These call-site checks match the envelope with `isAsyncHookContextPartText`, the same predicate the code uses. `prompt-context-order.test.ts` asserts the wire reorder hoists a trailing async block (and an async + sync run) ahead of the caller text, and `isAsyncHookContextPartText` is unit-tested for envelope recognition, whitespace tolerance and internal-tag rejection.
