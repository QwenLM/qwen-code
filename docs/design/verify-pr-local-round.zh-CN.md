# /verify-pr 的本地轮次辅助脚本

[English](verify-pr-local-round.md) | [简体中文](verify-pr-local-round.zh-CN.md)

状态：已实现；本次补充下方的计数、守卫、覆盖与署名页脚规则。

## 问题

`/verify-pr` 有两条入口。沙箱 lane 会提供 PR 元数据快照、同时含有两个 OID 的克隆，以及一个会拒绝「判定与自身断言计数矛盾」的发布步骤。维护者在自己机器上跑的轮次三者皆无，而 skill 给出的答案是散文式的：手写的 `gh pr view` 字段列表、「不要假设 `HEAD^1`/`HEAD^2`」、收集步骤用 glob 匹配的目录名，以及「自己把计数数清楚」。这些都是确定性的规则，却没有任何可执行形态，于是每一轮都要重新推导，出错时又是静默的：快照来自错误的仓库、把父提交当成基线、目录名不被发布步骤识别、计数与判定互相矛盾。

## 现状

- 本地路径要求 agent 抓取快照并挂成 `$QWEN_VERIFY_CONTEXT`、解析 `baseRefOid`/`headRefOid`、在开始任何验证工作前建好 `tmp/pr<n>-verify-<ts>/`。
- 隔离要求（「无凭据的容器或 VM」）及其退路（「触发沙箱 lane」）都是散文。没有任何东西告诉 agent 当前进程处于哪种情形。
- 发布 job 会拒绝「`merge-ready` 且 `fail` 非零」，也会拒绝内部不一致的 `assertions.json`，因此 CI 路径端到端由机器校验。本地轮次没有对应物，可以发布与自己判定矛盾的计数。

后续某一轮又暴露出三处同类缺口——规则只写在散文里、没有可执行形态，于是静默出错：

- **计数规则只教了一半。** 一段讲怎么证明红项是环境问题（两臂都启动、展示同样的失败），另一段讲预期红算通过、harness 自身故障算 `inconclusive`。两者之间没有接线，于是宿主环境红项无处归类。那一轮把同一条仓库测试的红记了两次——head 一次、base 对照一次——发布出 `fail: 2` 加 `findings`，却在自己的判定行里写着两个原因都不是本 PR 的缺陷。base 那一格本就是「断言 base 会红」，它如期红了，所以它是通过的。
- **发布前守卫是 fail-open 的。** 它问的是「有没有新东西」，而抓取失败会返回 0 条，于是答案是「没有」。实测：轮次开始时 324 条 review comment，重新抓取时 0 条，原因是调用失败而不是 PR 安静了。这恰好是本地路径上唯一一条背后没有脚本的安全规则。
- **覆盖声明是断言出来的，不是枚举出来的。** 「上一轮之后每个生产提交都单独做了变异」这句话发布时，有两个提交根本没有对应行。矩阵是按守卫组织的，比 prose 声称的更弱，只有自审发现了这个差别。

## 方案

新增三个独立脚本，并让 skill 在流程需要的位置指向它们，而不是放在文末。

- `scripts/verify-pr-prepare.mjs <pr> --repo <owner>/<repo>` 负责解析坐标：用 lane 相同的字段列表抓取快照、校验两个 OID 在本克隆中存在、拒绝不是 PR head 干净检出的树、创建带 `evidence/` 子目录的产物目录，并报告当前进程能观测到的隔离信号。它不据此设闸：解析元数据需要 `gh`，而 `gh` 与边界互斥，因此这条路径总是在宿主上运行。闸门是 `--require-isolation`，用于在边界内、轮次执行任何东西之前运行。
- `scripts/verify-pr-check.mjs <dir>` 把发布侧的规则套到本地产物目录：必需文件、四个判定词、为正且自洽的断言三元组、以及不允许带失败断言的 `merge-ready`。报告形态与证据命名只作为警告，因为纯文档轮次没有截图，检查器也无法知道是否跑过 harness。
- `scripts/verify-pr-guard.mjs` 接管发布前守卫的两个半程。`--pr <n> --repo <owner>/<repo> --snapshot <file>` 抓取 head、PR 状态以及三个评论列表（带 `--paginate`），只有每次调用都成功才写文件。`--compare --start <a> --now <b>` 列出本轮 dirty 的全部原因并退出 1。

检查器在产物契约要求轮次写出的产物上新增两条规则。产物契约里两者都要点名：产物清单没要求的文件，轮次就不会产出，而对一个不存在的文件做检查是静默的。

- `assertions.json` 在 `fail` 非零时带 `failures: [{ id, attribution }]`，每条失败断言一项，归因为 `pr`、`harness` 或 `environment`。若 `findings`/`blocked` 的账本里没有任何一条归因为 `pr`，报错；账本长度与 `fail` 不一致，同样报错。有失败但没有账本只报警告，因此旧产物仍能通过。
- `mutations.json` 可以声明 `coverageClaim: "per-commit"`，并给出来自 `git log --no-merges <previous>..<head> --not <target>` 的 `productionCommits` 与 `rows[].commit`。列出的提交没有对应行时报错，并点名这些提交；列表为空同样报错——对空集合做的声明恒真。

每个已准备的产物目录保存带完整坐标的 `context.json`——`repo`、`pr`、`baseRefOid` 与 `headRefOid`——本地轮次因此从一个文件读出两个 OID，而不是从 `HEAD` 推导。prepare 只在当前树是 `headRefOid` 的干净检出时才写它：轮次复用这棵树作为 A/B 的 head 侧，所以 HEAD 不对会退出 3 并点名要跑的 `git checkout`，树脏会退出 3 并要求维护者自己提交或 stash——脚本绝不代为 stash，且拒绝时不创建任何产物目录。检查器优先使用该轮快照，并注明实际使用的来源。旧目录回退到按 PR 共享的快照；该轮快照不可读或无效时只报警告，不会改用后续轮次的共享提交号。

## 署名页脚

发布出去的验证评论以与 `/review` 相同的署名形状收尾：

`_— <model> via Qwen Code /verify-pr (v<cli-version>; skill <skill-hash>)_`

- model 是本轮运行所用的身份，CLI 版本取 `qwen --version`，skill 版本取 `git hash-object --no-filters .qwen/skills/verify-pr/SKILL.md` 的前 12 个字符。用内容哈希而不是提交号：lane 的树只有 depth-2，`.qwen` 又是 `git archive` 来的，没有任何历史可达；而内容哈希恰好指名本轮实际加载的那份指令——在工作站上还包括未提交的修改。`--no-filters` 是因为 prepare 把 `.git` 留给了 node 所有，否则一个被种下的 clean filter 就能决定被哈希的内容——甚至以 root 身份执行。
- 在 lane 里，三个值都是 run step 的 workflow 自有输出——配置的模型、runner 上的 CLI、重新钉住的 skill 文件——绝不从 agent 可写的产物树里读。它们在基线重新钉住之后、agent 启动之前采集：工作区父目录始终归 node 所有，因此 agent 运行期间 PR 代码可以整个替换 `.qwen` 目录（mv + mkdir）而不必碰里面 root 所有的文件，agent 之后再取哈希就可能指名本轮根本没加载过的指令。一条元测试钉住这个顺序，而不只是字符串。发布侧只在正文确实带有报告、且三个值都到达时才盖页脚；否则评论保留通用的 `— _Qwen Code · sandboxed verification_` 签名，各类弱通知（取消 / 基础设施故障 / 跳过 / 结果不可用 / 产物下载成功但没有报告）同样保留它：它们报告的是 lane，不是某一轮。
- 本地轮次从 `$QWEN_CODE_MODEL_IDENTITY`（为空则 `$QWEN_CODE_MODEL`）解析模型，两者都取不到时省略页脚——空身份比没有更糟，而且工作站轮次绝不冒用 lane 的 `sandboxed verification` 签名。
- `report.md` 本身不带页脚：两条发布路径都在发评论时追加，写进报告里的页脚会出现两次。
- 一条 workflow 元测试把同一模板钉在两个表面（发布侧与 skill）上，因此改了一处的措辞不会让另一处发出不同的形状。

## 设计决策

1. **`--repo` 必填。** 脚本无法区分维护者克隆与贡献者 fork，而在 fork 上 `origin` 会把同一个 PR 号解析成另一个无关 PR。fail closed 的代价是一个参数，消掉的正是 skill 已经警告的那种失败。
2. **脚本不碰轮次本身，坐标路径也不对隔离设闸。** prepare 只抓元数据、建目录；它不建 worktree、不构建、不执行 PR 代码。但它对树设闸，因为轮次在当前树里跑 A/B 的 head 侧：HEAD 不是 PR head、或有任何未提交改动，测到的就是报告没有点名的代码，所以两者都在写出任何东西之前被拒绝。它也无法判断本进程是否有资格执行那些代码：解析元数据必须访问 `gh`，而边界按设计排除 `gh`，所以它总是在宿主上运行。在那里设闸会让每一轮都触发，并让覆盖开关变成常规路径，因此检查被拆成独立模式，用于在边界内运行。
3. **本地检查器镜像发布侧，而不是替换它。** 把发布 job 里的断言抽成共享代码会动到 workflow 及其 meta 测试；规则只有四条、稳定，且集中在一处。代价是可能漂移，记录在下方。
4. **报告形态只报警告。** 发布侧同样不强制报告结构。比发布侧更严格的检查器会拒绝 lane 本来接受的产物，结果只会教会维护者忽略它。
5. **归因是一份账本，不是第五个判定词。** 面对环境红项，最诱人的修法是加一个 `merge-ready-with-caveats` 之类的判定，但那要同时改发布侧、它的 case 标签和对应 pin。判定词仍是四个：红项被改写成它本来就是的那条断言——两臂都因原因 R 失败——账本则记录谁造成了什么。检查器于是读归因，而不是从 prose 里猜。
6. **守卫接管抓取，而不只是比对。** 只比对两个文件的脚本会把手写抓取留在原地，而调用失败后写出的空文件比对起来是干净的。因此调用失败即致命且不写任何文件，比对侧又独立地把「列表变短」判为 dirty。两个半程缺任何一个，洞都还开着。不设重试参数：让维护者重跑一次拒绝是诚实的，而静默的重试预算会掩盖一台连不上 API 的机器。
7. **检查器校验的是覆盖声明与轮次自己给出的枚举是否一致。** 它没有仓库，无法推导提交集合；`productionCommits` 列得不全是 skill 规则的责任，文档里也这么写明。可机器校验的是「声明 vs 所给列表」，而这正是实测那一轮的缺口所在——外加唯一一种原本能通过全部检查的不完整列表：空列表。拒绝它对纯文档轮次没有代价：它该做的是不提出这个声明，而不是对空集合提出声明。

## 约束与风险

- 隔离检测只把容器类信号计为边界。内置 macOS 沙箱设置 `SANDBOX=sandbox-exec`，但其默认 profile 仍能读取宿主文件，因此只作为注意事项报告，不算边界。仅有标记也不等于无凭据就绪：CLI 自带的 Docker/Podman 启动器会挂载 gcloud 配置与 ADC 文件并复制模型 key，因此闸门还要求显式声明，并在看到已知信号时拒绝。
- 树闸门只证明源码身份。`dist/` 与 `node_modules/` 都被 gitignore，head 的干净检出仍可能带着更早提交的构建——评审中已复现：prepare 退出 0，而被忽略的构建以新 head 的名义跑旧代码。因此 install/build 的复用是有条件的：轮次必须先确立产物确为本 head 所建（否则按本地安装策略重建），prepare 的成功行也相应写成「先校验或刷新其 install/build」，而不是宣传无条件复用构建。
- 发布规则存在两份实现，可能漂移。一条 workflow 元测试把检查器的判定词表钉到发布侧的 case 标签上，任一侧新增第五个词都会让套件失败。CI 发布侧仍是权威。
- PR 标题是不可信输入且会到达维护者终端，因此在打印前剥离控制字符。
- 这些是本地辅助脚本：lane 从基线分支钉住 `.qwen`，因此引用它们的 skill 文本要在本改动合入后才生效。
- 守卫把每个条目归一为 `id`、一个取值 `updated_at ?? submitted_at` 的时间戳、`body`，以及仅 review 才有的 `state`。只看时间戳回答不了「有没有东西变过」：对本仓库 API 实测，review 对象只有 `submitted_at`、没有 `updated_at`，而编辑正文或 dismiss 这条 review 都不会改动这个时间戳。PR 15388 上的 review 5673309455 报告的 `submitted_at` 是 2026-10-27T19:47:16Z，而它在五小时三十六分钟后的 2026-10-28T01:22:57Z 被 dismiss。时间戳仍是更早的那个值，说明 dismiss 没有动它，并且这条 review 仍报告 4838 字的正文：除了 `state`，没有任何字段记录它被 dismiss 过。正文是否也被改过则无法观测——这正是要点——而正是这次 dismiss 解开了合并闸门。三个列表都返回字符串 `body`、review 还返回字符串 `state`，因此两者都与时间戳一起参与比对；当某个条目没有 body、或某条 review 没有 state 时，整次抓取直接拒绝，而不是当作「什么都没变」去比。代价是快照文件更大——正文按原样保存，这也让轮次无需再抓一次就能读到究竟来了什么。
- 参与比对的字段，是那些会改变「评审者说了什么、判了什么」的字段。reaction 计数与其他元数据被有意排除：整条对象比对会让一个点赞就把轮次判成 dirty，把维护者推进毫无意义的重新抓取循环。把这条边界写下来，正是为了不让字段清单每审计一轮就长一截。
- 列表变短时只报它自己的原因加一个丢失条数，不逐条点名。实测于一个真实 PR：被截断的重新抓取先打出「列表变短」的原因，接着打出 321 行 `disappeared`，把唯一可操作的那一行埋在自己的回声里。这些 id 是截断的后果，不是独立的原因。长度相等时缺失的 id 就是全部信号，因此仍然逐条点名——另有一条 pin 专门防止这个抑制把真实删除也吞掉。
- `environment` 归因的可信度完全取决于背后的 A/A 对照。检查器看不到那个对照，因此 skill 仍要求报告里给出两臂与共同原因；账本挡的是错记计数，不是编造的归因。
- 枚举命令是 `git log --no-merges <previous>..<head> --not <target>`，因为两种显而易见的写法朝相反方向出错。`--no-merges` 只丢掉合并提交本身，却保留那次合并带进来的每一个提交：在提出错误覆盖声明的那条分支上、按它上一轮的区间实测，85 个生产提交里有 24 个才是分支自己的，多出的 61 个全部来自一次 `Merge branch 'main'`。`--first-parent` 用丢掉每个第二父提交的办法消掉这个多算，代价是当本 PR 合入自己的功能子分支时，把那些真由 PR 写的提交也一起丢掉：用一个含一次功能分支合并、一次 `main` 合并的四提交图实测，`--no-merges` 列出 5 个、其中 2 个属于 `main`；`--first-parent --no-merges` 只列出 1 个，丢掉了 PR 自己写的 2 个功能提交；`--not <target>` 列出正确的 3 个。两者之中少算是更危险的那个，因为检查器看到的是一个看起来完整的枚举，于是在被漏掉的提交没有对应行时仍然接受声明。检查器两种都抓不到——它没有仓库——所以命令本身和钉住它的 pin 是唯一防线：本改动的初稿给的是光秃秃的 `--no-merges`，第二稿给的是 `--first-parent`。
- `--not <target>` 是**live 轮次**的配方，这条限制是真的：它减掉的是目标分支已经包含的内容，因此分支一旦合入，枚举就是空的。在本改动自己那一轮的区间 `36b6d9c77f..5a86a0e352` 上实测（该分支此后已被合入）：`--no-merges` 85 个、`--first-parent --no-merges` 24 个、`--not origin/main` 0 个。在 live 区间上三者一致——本 PR 的 `f08535976c..HEAD` 三者都是 15。因此 skill 把前提写进规则，而「空枚举拒绝」正是用来接住跑晚了的轮次。

## 验证计划

- 纯函数的单元测试：仓库 slug、产物目录名、隔离信号、快照形状、参数解析；以及检查器的规则集。
- 驱动两个 CLI 的端到端测试：临时克隆加 `gh` 替身，断言退出码、写出的快照与产物目录；以及覆盖检查器每种结果的产物夹具。
- 在维护者克隆上对真实 PR 干跑一次 `prepare`，并对真实产物目录跑一次 `check`。
- 守卫方面，用 `PATH` 上的 `gh` 替身驱动真实 CLI 走完两条路径，因此「调用失败时不写文件」是被观测到的，而不是从纯函数推断的。
- 发布步骤分别在带与不带三个署名输出的情况下真实执行，逐字断言两种情形下所发评论的最后一行——包括产物下载成功但没有报告的情形；另有结构 pin 钉住采集顺序（重新钉住 → 采集 → agent 启动），以及 skill 的页脚模板与发布侧模板一致。
- 对本改动新增的每一个守卫做 vacuity 矩阵：就地反掉一个子句、跑应当抓住它的套件、再还原。只有被点名的那条断言变红才算击杀，不是「随便某条红了」。实测：35 行，35 杀，其中包含一行针对既有 `merge-ready`/`fail` 守卫的对照，因此其余击杀不是「harness 根本没跑到这段代码」。每一行还带上引入该子句的提交，而且是推导出来的、不是指派的：分支上第一个文件内容里含有该锚点的提交，并读父提交的内容确认它确实没有。对照行是例外——它的子句在 `main` 上，这一点同样做了校验。把这套枚举用到本改动自己身上时，它点名了没有对应行的纯文档提交，因此矩阵按守卫报告、不提出按提交的声明；同一份数据若声明为按提交则会被拒绝，并点名这些提交。规则抓住了自己的作者，而正确的回应是把声明收窄，不是给它编一行。
- 其中十九行之所以存在，是因为自审在本改动自身里发现了缺陷。第一遍五行：抑制警告的分支会让畸形账本走到对 null 的读取；拒绝信息把畸形的列表条目说成 head 缺失；`--compare` 在两侧是同一个文件时读作 clean；以及列表变短的报告把 321 个丢失 id 全部点名、埋掉了自己唯一可操作的那一行——最后一项是一对行，一行证明抑制确实发生，另一行证明它不会在长度相等时把真实删除也吞掉。第二遍四行：枚举命令漏了 `--first-parent`；产物契约从未要求 `mutations.json`、也没要求账本（两行，检查器读的两个文件各一行，而当时没有任何东西会产出它们）；以及对空提交列表的覆盖声明被放行。后续一遍一行：prose 无条件叫每一轮都声明按提交覆盖，这与契约犯的是同一个过头——声明要靠枚举挣来，有缺口的轮次应当改为按守卫报告。第七遍三行，其实是同一个缺陷：守卫只看时间戳，因此一条被编辑过、时间戳却没动的 review 会被比成 clean——一行针对比对本身，一行针对「完全没有 body 的列表也照收」，还有一行针对那段声称时间戳就够用的规则文本。第八遍三行，问的是「还有什么会变、却不动时间戳」：被 dismiss 的 review，实测于 PR 15388——一行针对 state 比对，一行针对「没有 state 的 review 列表也照收」，还有一行针对只提了正文、没提 state 的规则文本。这一遍还把边界写死，免得下一遍再把它翻出来。另有三处发现——指向一个不存在的报告条目的交叉引用、一个任何调用方都观测不到的返回值，以及契约无条件要求矩阵而检查器按设计视其为可选——都修掉了但没有对应行，因为都不是守卫。此外还有一批发现同样不是守卫、因此没有对应行，这里逐条列出而不是报一个数字——对一个会增长的集合报数字，正是本改动要治的病。它们是：指向不存在的报告条目的交叉引用、任何调用方都观测不到的返回值、没有任何模块 import 的导出、契约无条件要求矩阵而检查器视其为可选、把被 dismiss 的 review 正文写成「原封不动」而记录里只有时间戳、一句「缺任一个字段就拒绝」的规则文本对 comment 条目并无 state 可缺、一处被向下取整了六分钟的时长，以及最后两处只改进设计文档却没有同步到已发布评论的修正。

## 验收标准

- 在同时含有两个 OID 的克隆上，`prepare` 写出的快照其 `baseRefOid`/`headRefOid` 与 PR 一致，创建符合 glob 的目录，其中 `context.json` 带 `repo`、`pr`、`baseRefOid` 与 `headRefOid`，且在宿主上退出 0。`--require-isolation` 只有在容器标记存在、`QWEN_VERIFY_CREDENTIAL_FREE=1` 声明边界干净、且看不到已知凭据信号时才通过；否则退出 4。
- HEAD 不是 PR head（点名要跑的 `git checkout`）、树带有未提交改动（无论已跟踪还是未跟踪，消息点名条目并给出能清掉未跟踪文件的 stash 形式）、或索引标志隐藏了已跟踪状态（skip-worktree / assume-unchanged，sparse checkout 会批量设置）时，`prepare` 退出 3，任何拒绝都不写产物目录；它绝不代维护者 stash。detached 于 PR head 的 HEAD 会通过：身份是 OID 而非分支，且有测试钉住消息里打印的 checkout 补救确实能走到退出 0。
- OID 缺失时失败，并给出用 `--repo` 指定仓库（而非 `origin`）的 fetch 命令。
- `check` 拒绝带失败断言的 `merge-ready`、不一致的三元组、未知判定词；对相同计数下的 `findings` 予以通过。
- 当失败账本里没有任何一条归因为 PR 时，`check` 拒绝 `findings` 与 `blocked`；账本长度与 `fail` 不一致时拒绝；对带 `harness` 失败的 `inconclusive` 予以通过；旧产物没有账本时只报警告。
- `check` 拒绝所列提交未被行全覆盖的 `per-commit` 声明，缩写与完整 OID 双向匹配；对空提交列表上的声明同样拒绝，而没有提出声明时保持静默。
- skill 的产物契约会要求这两条规则读取的两个文件；其枚举命令用 `--not <target>` 减去目标分支，而不是在第一个父提交处截断；任一处被改掉都有 pin 变红。
- 任一调用失败时 `guard --snapshot` 不写文件并退出 1；`guard --compare` 在快照畸形、列表变短、条目新增/被编辑/消失、head 移动、状态变化时退出 1，两侧是同一个文件时退出 2，只有一切未动才退出 0。列表变短时报它自己的原因加一个丢失条数；长度相等时仍逐条点名消失的 id。
- 条目正文变了而时间戳没变、或 review 的 state 变了时，`guard --compare` 报 dirty；条目不带 body、或 review 不带 state 的列表，`guard --snapshot` 直接拒绝。
- 模型、CLI 版本、skill 哈希三者都解析成功时，发布的报告评论以署名页脚收尾；否则以通用签名收尾；弱通知——包括产物下载成功但没有报告——一律保留通用签名。lane 在基线重新钉住之后、agent 启动之前采集三个值，该顺序有元测试钉住。skill 与发布侧携带同一页脚模板并有元测试钉住，`report.md` 本身不带页脚。
- 所有脚本都不执行 PR 代码。
- 对于自带轮次快照的报告，在不同产物目录中准备后续轮次不会改变检查所用的提交号。可发布的轮次快照不包含 PR 标题或正文。
