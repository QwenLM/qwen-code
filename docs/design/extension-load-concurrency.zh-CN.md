# 有界扩展加载

[English](extension-load-concurrency.md) | [简体中文](extension-load-concurrency.zh-CN.md)

## 问题与范围

完整扩展刷新在启动下一个扩展前，会等待前一个扩展加载完成。安装了许多 skills 的
扩展集合因此会累积各扩展的文件系统延迟。本次仅解决当前 main 上的这层串行循环。

目录与详情读取已避免了不必要的资源加载。保留这些路径、激活策略、缓存发布、启动
行为，以及每个资源加载器原有的校验和错误处理。不引入重试策略、恢复状态、拒绝
记录表或嵌套资源并发。

## 设计

在 `ExtensionManager.loadExtensionsFromExtensionsDir` 中，每批最多加载四个目录
条目。等待该批全部结果后，按原目录顺序处理：追加非 null 的扩展；如有加载拒绝，
按目录顺序重新抛出第一个错误，不再启动下一批。

四是单次扫描中同时加载扩展数的固定保守上限，并非进程级文件描述符上限。各资源
加载器保留现有调度。批次屏障使实现保持简单，并确保失败扫描退出 store 读取事务
前，已启动的同批加载全部结束。慢条目可能延迟下一批，这是相对于引入队列或新的
并发抽象所作的明确取舍。

结果顺序必须保持稳定：运行时缓存插入采用同名后者覆盖语义，详情选择采用最后一个
匹配条目。null 仍表示原加载器跳过了条目。原循环会向外传播的拒绝（包括最初的目录
stat 错误）仍须使扫描失败。失败批次可能启动串行扫描原本不会到达的条目，警告输出
也可能交错；失败扫描的任何结果均不会进入缓存发布。

## 影响路径

生产行为仅修改 `packages/core/src/extension/extensionManager.ts` 的外层循环。
其消费者为完整刷新、目录快照、详情快照和 `loadExtensionsFromDir`。按名称过滤的
刷新和直接按名称加载保留原行为。回归覆盖放在扩展管理器测试旁。

## 验证与验收

- 受控的待完成加载证明同时启动的条目数大于一且最多四个，完成顺序不会改变结果顺序。
- 加载拒绝时等待已启动的同批任务，保留原错误，且不启动后续批次。
- 真实文件系统夹具保留有效资源内容、跳过非法 manifest，并通过现有目录、详情、
  激活及缓存测试。
- 使用相同隔离夹具、多次运行，将完整刷新耗时与未改动的 main 实现对比。记录夹具
  规模、中位数和环境；合成夹具的热缓存测量不是生产 SLA。
- 构建、类型检查、打包、定向测试及隔离 CLI 冒烟验证通过。

## 待定问题

无。进一步并发或修改现有错误策略需要独立证据和独立变更。
