# 程序驱动的会话收下被接受的跨会话消息

[English](2026-09-21-acp-accepted-peer-delivery.md) | [简体中文](2026-09-21-acp-accepted-peer-delivery.zh-CN.md)

状态：与本文档一同实现。

## 问题

由程序通过 ACP 驱动的会话——编辑器起的，或 daemon 托管的——会在会话
目录里登记，可被寻址，也能发消息。但发给它的一切，它都回 `refused`。

这是这些会话刚进目录时定下的，对其中一部分流量，理由至今成立：挂起
是向人提出的问题，而没有人替这样的会话盯着挂起列表。消息停在那里只
会等到过期，而它的发送方收到的是 `held`——那句回执承诺会有人来看。

但到达这类会话的消息，大多本来就不会被挂起。daemon 托管的会话所处的
审批模式，会接受同一类别的另一个会话发来的消息。受信控制器——用户亲
手、在带外铸出授权的程序——无论什么模式都会被接受，那正是授权的意义。
会话自己启动的进程同样会被接受。今天这些全被拒绝，因为答案是对所有
消息一次性定下的，而不是逐条判定的。

通过 SDK 对端端点接入的语音前端正是这种情况：用户铸出的授权，向
daemon 驱动的会话说话，被挡在门外。

## 设计

**由闸门判定，只拒绝本该停留的那些。**闸门新增一个选项
`presentsHolds`。对它答 false 的宿主没有地方安放停留的消息，于是每一
次挂起都变成 `refused` 回执，任何消息都不会停留。接受不受影响。

这个转换必须发生在闸门里。宿主也可以改为让策略读取器返回 `refuse`，
但那个读取器分不清"本该挂起的"和"本该接受的"：显式设置的优先级高于
受信控制器与会话自己的进程，在那里拒绝，恰好会把这次改动要放行的消
息挡掉。

这样转换出来的拒绝不写墓碑。消息被挂起的一些原因是一时的——会话正在
收尾时读不到审批模式，会被记为未知——把 id 结算掉会让这一条消息永远
被拒。只有策略自身判定的拒绝才是终局。

**收件人只解析一次，在进闸门之前。**一个会话对两种拼写应答：它登记
时用的 id，那个永不改变；以及它的 Config 当下持有的 id，`/clear` 和
恢复会把它换掉。发送方读到的记录跟随后者，所以两种拼写实际都会出现。

宿主只被问一次，由传输层在它本来就判定 misaddressed 的地方发问——它
给出的名字会替换掉帧上发送方的拼写。此后的每一步都从帧上读收件人：
闸门的设置读取、它的挂起记账、宿主端的队列查找。它们都不再发问，也
就无从彼此矛盾。

另一种做法是在闸门内部、每个按收件人比较或分组的地方各自解析，试过
并放弃了：每一处都是两个答案产生分歧的机会，而宿主的答案在这些时刻
之间本来就可能变。

**消息成为它自己的一轮。**先写入 transcript，再作为一种新的后台通知
（kind 为 `peer`）入队，等会话空闲时处理——与终端前的人得到的"下一轮"
相同，而不是打断正在运行的事情。消息 id 就是任务 id，所以同一条消息
到达两次会被认出来，而不是处理两次。

**消息在那个队列里有自己的额度。**它既不挤掉结果，也不被结果挤掉。
本会话自己的工作产出的结果可以再产一次，别人的消息不能，而且它的发
送方已被告知消息已到。额度在回答发送方之前检查，并计入正在写入
transcript 的那些，所以额度满了会用一条发送方能据以行动的回执把它挡
回去。

**宿主负责更正会话未读消息的回执。**进入队列的消息回执是 `delivered`。
若会话带着未读的它关闭，那条回执就是错的，而只有宿主说得清：它的各
个会话的队列各自消费，消息交付的先后顺序说明不了哪些还在等。至于根
本没到达任何会话的那些，仍由传输层结算。

## 尚未解决的部分

挂起的消息。程序驱动的会话仍然无法呈现挂起，因此
`agents.crossSessionInbound: hold` 会把消息挡回去。挂起该怎样浮现给
这些会话——经 ACP 客户端，还是 daemon 自己的 API——是下一项工作，随之
而来的问题已集中记录。

去重窗口。30 秒同文检查只按发送方分桶，因此同一段内容在窗口内发给同
一进程的两个会话，第一个收到，第二个被丢弃。按收件人分桶必须两侧同
时改，因为发送方在花掉一次连接之前，会在本地预测接收方的答案。
