# 程序驱动的会话收下被接受的跨会话消息

[English](2026-09-21-acp-accepted-peer-delivery.md) | [简体中文](2026-09-21-acp-accepted-peer-delivery.zh-CN.md)

状态：与本文档一同实现。

## 问题

由程序通过 ACP 驱动的会话——编辑器起的，或 daemon 托管的——会在会话
目录里登记，可被寻址，也能发消息。但发给它的一切，它都回 `refused`。

这是这些会话刚进目录时定下的，对其中一部分流量，理由至今成立：挂起
是向人提出的问题，而没有人替这样的会话盯着挂起列表。消息停在那里只
会等到过期，而它的发送方收到的是 `held`——那句回执承诺会有人来看。

但到达这类会话的消息，大多本来就不会被挂起。daemon 托管的会话所处的
审批模式，会接受同一类别的另一个会话发来的消息。受信控制器——用户亲
手、在带外铸出授权的程序——无论什么模式都会被接受，那正是授权的意义。
会话自己启动的进程同样会被接受。今天这些全被拒绝，因为答案是对所有
消息一次性定下的，而不是逐条判定的。

通过 SDK 对端端点接入的语音前端正是这种情况：用户铸出的授权，向
daemon 驱动的会话说话，被挡在门外。

## 设计

**由闸门判定，只拒绝本该停留的那些。**闸门新增一个选项
`presentsHolds`。对它答 false 的宿主没有地方安放停留的消息，于是每一
次挂起都变成 `refused` 回执，任何消息都不会停留。接受不受影响。

这个转换必须发生在闸门里。宿主也可以改为让策略读取器返回 `refuse`，
但那个读取器分不清"本该挂起的"和"本该接受的"：显式设置的优先级高于
受信控制器与会话自己的进程，在那里拒绝，恰好会把这次改动要放行的消
息挡掉。

这样转换出来的拒绝不写墓碑，而发送方被告知什么，取决于它本该为何被
挂起。其中三种原因是会话自己的常驻答案——它的设置、发送方属于另一审
阅类别、发送方没有声明类别——用 `refused` 告诉发送方停下。另两种是一
时的：会话正在收尾时读不到审批模式，会被记为未知；设置读取器出于同
样的原因可能抛错。这两种回 `expired`，既不要求发送方做什么，也不叫它
停下，因为同样的内容在之后的一次尝试里就会落地。只有策略自身判定的
拒绝才是终局，也只有它结算 id。

会话正在关停时这个转换根本不跑：那时闸门已经对每条消息都回
`expired`，在那里回 `refused` 会让发送方以为这个会话拒收它的消息，而
它只是要离开了。

**收件人只解析一次，在进闸门之前。**一个会话对两种拼写应答：它登记
时用的 id，那个永不改变；以及它的 Config 当下持有的 id，`/clear` 和
恢复会把它换掉。发送方读到的记录跟随后者，所以两种拼写实际都会出现。

每条到达的消息，宿主只被问一次，由传输层在它本来就判定 misaddressed
的地方发问——它给出的名字会替换掉帧上发送方的拼写。此后判定这条消息
的每一步都从帧上读收件人：闸门的设置读取、它的挂起记账、宿主端的队
列查找。它们都不再解析，也就无从彼此矛盾。

有一个问题只能稍后再问：宿主是否仍持有**已停留**的那条消息所指的会
话。一条消息可能停留到一个人愿意回答为止，所以那是关于当下的问题，
不是关于它到达那一刻的。闸门在那里会再次询问宿主的解析器，而且这次
故意不捕获异常——解析器在收尾中抛错，会让消息继续停留；同样的抛错发
生在到达路径上则意味着 misaddressed。在那里结算，会把一个审阅者正要
放行的消息写成墓碑，而一次重新评估会把其余所有停留的消息一并结算掉。

另一种做法是在闸门内部、每个按收件人比较或分组的地方各自解析，试过
并放弃了：每一处都是两个答案产生分歧的机会，而宿主的答案在这些时刻
之间本来就可能变。

**消息成为它自己的一轮。**先写入 transcript，再作为一种新的后台通知
（kind 为 `peer`）入队，等会话空闲时处理——与终端前的人得到的"下一轮"
相同，而不是打断正在运行的事情。消息 id 就是任务 id，所以同一条消息
到达两次会被认出来，而不是处理两次；会话处理完这条消息后就把这个 id
忘掉，因为对端可以无限量地铸出 id，而在线上阻止同一条消息二次到达的
是传输层自己的记录。

等待被读的消息会把会话钉住：一次条件关闭若把它读成空闲，就会把整个
队列丢掉，而别人的消息——回执已经是 `delivered`——不可能比已经能拒掉
这种关闭的队列中结果或 shell 输出更不值钱。

发送方的名字随消息一起走，并按它到底是谁加上限定（`controller:`、
`own process:`、`peer:`），且与其他通知标签一样截断。展示标签的界面
是单独展示它的，否则一个把自己命名成用户所铸授权的对端，就会被读成
那个授权。

写不下消息的会话就收不了消息，所以由闸门替它回绝，而不是到投递时把
发送方挡回去：关掉聊天记录后，"没有空间"会被读成"现在不行"，于是对
着一个永不改变的条件反复重试。

**消息在那个队列里有自己的额度。**它既不挤掉结果，也不被结果挤掉。
本会话自己的工作产出的结果可以再产一次，别人的消息不能，而且它的发
送方已被告知消息已到。额度在回答发送方之前检查，并计入正在写入
transcript 的那些，所以额度满了会用一条发送方能据以行动的回执把它挡
回去。

**宿主负责更正会话未读消息的回执。**进入队列的消息回执是 `delivered`。
若会话带着未读的它关闭，那条回执就是错的，而只有宿主说得清：它的各
个会话的队列各自消费，消息交付的先后顺序说明不了哪些还在等。至于根
本没到达任何会话的那些，仍由传输层结算。

离开队列不等于被读到。drain 在轮次开跑之前就把条目取出队列，而一轮
可能没跑它就结束了——开跑前被取消、被宿主拒绝准入、或撞上会话的
token 上限，那条路径会把它本要发送的部分丢掉。这样的消息改为进入一份
在途清单，等模型拿到它、或等下一轮会发送的历史里有它之后才离开；会
话把两份清单一起交还，因此一条消息只在其中一处等待，它的发送方也只
被告知一次。在途的消息同样计入额度，否则一个不断丢消息的会话会不断
继续接受消息。

这些更正按批发送，每批都在传输层并发发送上限之下，而收件箱会等它们
发完：突发超过那个上限会被拒，而被拒的更正就等于把错的回执留在了原
处。

## 尚未解决的部分

挂起的消息。程序驱动的会话仍然无法呈现挂起，因此每一条本该被挂起的
消息都会被挡回去——无论是 `agents.crossSessionInbound: hold`，还是未
设置时默认会挂起的那些原因。挂起该怎样浮现给
这些会话——经 ACP 客户端，还是 daemon 自己的 API——是下一项工作，随之
而来的问题已集中记录。

去重窗口。30 秒同文检查只按发送方分桶，因此同一段内容在窗口内发给同
一进程的两个会话，第一个收到，第二个被丢弃。按收件人分桶必须两侧同
时改，因为发送方在花掉一次连接之前，会在本地预测接收方的答案。

更正之后复用同一个消息 id。`reportExpired` 会退掉去重窗口保留的同文
记录，因此把未被读到的内容如实重发可以落地。但它无法撤回闸门里的
`delivered` 墓碑，所以发送方在收到 `expired` 更正后仍复用同一个消息
id 时，会再次被告知 `delivered`，而它指向的会话已经不在了。换一个新
id 重发不受影响，SDK 的端点正是这么做的。
