# 程序驱动的会话接收跨会话消息

[English](2026-09-18-acp-inbound-peer-messages.md) | [简体中文](2026-09-18-acp-inbound-peer-messages.zh-CN.md)

状态：与本文档一同实现。由 `qwen --acp` 进程托管的会话，无论是 daemon 拉起的还是编辑器直接驱动的，现在都按与终端会话相同的审阅规则接收其他会话发来的消息。

## 问题

[目录中的 daemon 会话](2026-09-09-daemon-sessions-in-directory.zh-CN.md) 让 `qwen --acp` 托管的每个会话都有注册记录和收件箱，因此这些会话能被列出，也能发送。但发给它们的任何消息都被回以 `refused`。还缺两件事。

### 挂起没人能回答

挂起的消息是向人提出的问题：投递，还是丢弃。终端会话通过 `/peers` 来问。被驱动的会话没有地方可问，挂起只会让每个发送方白等到过期。在这个问题有去处之前，拒绝才是诚实的回答。

### 一个进程，多个工作区

一个 `qwen --acp` 进程可以托管在不同目录打开的会话，每个会话有自己的设置和审批模式。闸门以前每个进程只读一份审批模式和一份入站设置。用一个会话的策略去判断发给另一个会话的消息，两个方向都会出错：一个把所有消息都挂起的仓库，可能因为兄弟会话接受消息而被直接投递。

## 设计

**每个问题都按被寻址的会话回答。**闸门读取审批模式、`agents.crossSessionInbound`、挂起时长和策略作用域的读取器，现在都接收帧所寻址的会话 id。只托管一个会话的进程忽略它。托管多个会话的进程从该会话自己的配置和设置作答，对不属于自己的 id 视为 `refuse`。过期读取每条挂起消息所属会话的时长，因此一个工作区里一分钟的挂起会按时过期，旁边十分钟的挂起继续等待。闸门的计时器按最早到期的那条设置。

**被接受的消息是一条后台通知。**被驱动的会话已经有一条"没人输入时有东西到了"的路径：后台任务完成后写入对话记录、排队，会话空闲时在后台轮次里交给模型。这条路径已经会等待进行中的 prompt、向 daemon 申请开轮许可、在实时状态里报告该轮次，并限制队列长度。跨会话消息只是它上面多出的一个种类 `peer`，但有自己的额度：每个会话最多 20 条，与 20 条后台结果分开计。已告诉发送方 `delivered` 的消息不能在之后被一批结果挤掉，消息也不能挤掉模型还没看到的结果。额度在告诉发送方之前就预留好，并计入仍在写入的消息；额度满时回以 `queue-full`。没有对话记录器的会话在同一处就拒收，因为入队从写记录开始。消息写入期间会话开始关闭的，报告为未入队，发送方的回执随之更正。已接受却没能入队的消息（会话已关闭，或对话记录写入失败），会用 `expired` 收回之前的 `delivered` 回执；从 `delivered` 到 `expired` 是合法的状态迁移。

**挂起的消息是一次权限请求。**ACP 已经有一种向驱动会话的一方提问的方式：`session/request_permission`，每个客户端都会渲染它。编辑器弹出对话框；daemon 把它发布为 `permission_request` 事件，列入会话的待处理交互，并把投票路由回来。所以挂起也这样问，给出两个选项 `peer_deliver` 与 `peer_drop`。请求带 `_meta.qwenInteractionKind: "peer_message"` 标记，并携带发送方、来源和挂起原因，供想把它显示成消息而非工具调用的客户端使用。客户端不需要新增任何东西，功能就能工作。

**审阅不排在工具审批的队伍里。**会话的工具审批是串行的。挂起可能要等好几分钟才有答复，期间的工具调用不能排在它后面。审阅请求直接发给客户端。

**每个挂起一次审阅。**宿主监视挂起集合。新的挂起发起一次审阅。挂起消失时（过期、因模式变化被放行、或在别处被决定），宿主不再等待那次审阅。会话离开时，它的审阅全部停止。既不是两个选项之一的答复，包括取消和超时，都让消息保持挂起，宿主会在一段延迟后再问一次，延迟每次翻倍，最长一分钟。请求可能因与消息无关的原因被取消：取消一个 prompt 会取消该会话所有待处理的请求。如果不再问，消息会一直挂着，却没有人能决定它。延迟让一个取消所有请求的客户端不会被循环追问。如果答复是投递但会话暂时收不下，闸门会把消息原样放回挂起；宿主随后按同样的节奏重试投递，不再询问那个人。

**审阅不属于任何轮次。**消息可能在一个无关的 prompt 或后台轮次运行时被挂起。daemon 会把权限请求绑到正在运行的轮次上，并在轮次结束时取消它。对挂起消息的审阅不做这种绑定，所以审阅等待的是消息的过期，而不是轮次。

**请求自带期限。**ACP 不允许 agent 撤回已发出的请求。所以审阅在 `_meta.expiresAt` 里写明它何时失去意义，daemon 在那一刻结束请求；若配置的权限超时更早，则以超时为准。没有期限的请求维持原有配置行为。daemon 的待处理列表不会显示已经过期的消息。

**判断依据一变就重新判断积压。**被寻址的会话换了审阅类别后，对等规则可能放行挂起的消息；入站策略或挂起时长变了，结论也会变。宿主为每个托管会话订阅它的 Config 审批模式和它的设置，而不是在已知的路径上逐个调用：客户端调用、工具进入或退出计划模式、设置重载，都汇到这两处。每条消息按它自己的会话重新判断。

**关闭的会话会结算它的挂起。**会话可以在进程继续运行时关闭。从它被 dispose 的那一刻起就算作已离开：即使移除还在等清理完成，也不会再向它投递、不会再向它的客户端提问。它的审阅按会话对象撤回，因为 /clear 可能已经换了它的 id；仍为它挂起的消息结算为 `expired`。为已不在的会话挂起的消息不会按另一个会话的策略判断：重新判断时回以 `misaddressed`。仍在它队列里等待的已接受消息也更正为 `expired`：队列在会话 dispose 之前读取，已更正过的消息不会再更正一次。

**找不到会话的挂起消息会再看一次。**消息可能在会话开始应答某个 id 之前的一瞬被挂起，比如发布途中或 /clear 时。宿主按与审阅相同的退避再看一次，而不是等挂起集合发生无关变化。

**挂起上限按会话计。**50 条挂起消息的上限对每个托管会话分别生效，一个工作区的积压不会让发给另一个工作区的消息全被拒收。

**退出时按 id 结算。**退出时，已接受却从未处理的消息要更正回执。单个会话的队列按先进先出消费，数个数就够了。一个进程里的多个会话各自按自己的节奏消费，所以宿主现在报告确切还在等待的消息 id。据以更正的已接受消息列表也按同样的 id 修剪，而不是截到固定长度：一条消息在一个会话里等待、另一个会话处理了很多条时，它仍在，仍能被更正。

## 不做的事

- 不新增 daemon 接口。挂起使用现有的待处理交互列表和投票路由。
- 挂起不持久化。与终端会话一样，挂起的消息不会比进程活得更久。
- 被驱动的会话没有 `/peers`。审阅是在那里决定挂起的唯一方式。
- 不读 `_meta.expiresAt` 的编辑器可能在挂起消失后仍保留对话框。那时作答不会改变任何事情。
- 同一收件箱后的会话对每个对端仍是同一个发送方，共享速率额度和去重窗口。这一点没有变化，协议页面仍将其列为未定事项。

## 验证

- 闸门：一个闸门上两个策略不同的托管会话，发给各自的消息按各自的设置判断，挂起按各自会话的时间表过期；挂起上限按会话计；会话离开时结算它的挂起；为已不在的会话挂起的消息回以 `misaddressed`。
- 会话：被接受的消息以 `peer` 种类记录并在后台轮次中运行；消息与后台结果互不驱逐；报告剩余空间和等待中的 id；审阅映射三种答复，并在中止时停止。
- 宿主：读取器按会话作答，未知 id 被拒绝；投递路由到被寻址的会话；每个挂起只发起一次审阅，答复映射为决定，挂起或会话消失时审阅停止；没有答复的审阅会再问一次；已批准但会话暂时收不下的消息会重试投递；关闭的会话其审阅停止、挂起被结算；两条模式切换路径都会重新判断。
- 桥接：`_meta.expiresAt` 缩短请求超时，对等消息详情投影进待处理交互，prompt 运行期间发出的审阅不绑定到该 prompt。
- 针对 `qwen serve` 的端到端：SDK 对端发给 daemon 会话的消息被投递；被挂起的消息作为待处理权限请求出现，并在过期时离开列表。
