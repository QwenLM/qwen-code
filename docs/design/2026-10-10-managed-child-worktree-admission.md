# Managed child worktree admission (isolation slice, I2)

[English](2026-10-10-managed-child-worktree-admission.md) | [简体中文](2026-10-10-managed-child-worktree-admission.zh-CN.md)

Status: implemented in this change. Landed: a hosted child agent may run in its own child Workspace (`isolation: "worktree"`). The relay prepares that Workspace before creating the child, merges it back when the child completes and before the result is committed, and discards it when the child fails or is cancelled; the close cascade discards it too; the receipt reports the merge outcome to the parent's model. Still design: I3 (`snapshot`, and the serialization decision). This is I2 of [#13753](https://github.com/QwenLM/qwen-code/issues/13753), built on I1 ([child Workspace capability](2026-10-09-managed-child-workspace.md), #13781), H4b ([child Session runtime](2026-10-07-managed-child-session-runtime.md)) and H4c ([workflow child kind](2026-10-09-managed-workflow-child-kind.md)).

## Problem and scope

Issue #13753 asks of I2: "The relay creates a `worktree` child in its own Workspace; the close and settle paths run the merge policy; `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` admits `worktree`." Its exit check: "A worktree child's writes do not appear in the parent's tree until its merge policy runs, and a cancelled child's worktree is discarded."

I1 delivered the capability with no caller. This change wires the one producer, the hosted Agent tool, through the child agent pipeline H4b built. `workflow` stays disabled (H4c decisions 5 and 6): the relay and the cascade still act on `child_agent` runs only, so admitting `worktree` changes nothing for workflows until their runtime slice widens both.

## Current state

The facts below are from `main` at `1136a51a68`.

- **Admission.** `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` is `['shared']`. `childLaunchBody` writes `workspaceMode: 'shared'`, and the hosted tool turn passes `shared` to `childLaunchAdmission`. The managed `agent` tool takes `description`, `prompt` and `run_in_background` and refuses `isolation` as a legacy-only argument (H4b decision 11).
- **Relay.** `ChildResultRelay.create` reads the launch envelope and calls the non-isolated `createChildSession`; the record's `workspaceMode` is never read. A completed child is committed (`commit_result`, `accept`) and closed afterwards (`deliver`). The fail, quota and give-up arms admit the child's close before their `fail` commit. The receipt is `{childSessionId, turnId, status, completedAt}`, stored by the parent as an opaque resource; no validator in either language parses it.
- **Cascade.** `SessionLifecycleCoordinator.cascadeChildScopes` requests a stop for every unsettled `child_agent` run, closes each child Session through its own lifecycle, and only then commits `close_scope`. Any owed step re-arms the parent's close.
- **Child Workspaces (I1).** `ChildWorkspaceService.prepare`/`finish` admit the row and drive Git synchronously; the scan drives what is left. `requestFinish` refuses while a bound child Session is not closed (I1 decision 8), and a different finish is refused except a discard after a merge that ended `conflicted` or `blocked`.
- **Foreground wait (#13769).** A foreground child's wait is restart-recoverable: a recovered Turn re-enters it from its checkpoint, and the recovery gap fill answers an admitted orphan call. Both fold the accepted result through `fitChildResultInline`.
- **Hosted session creation.** Java creates or loads the hosted Session with `toolProfile`, the store connection and, for a child, `lineage`. Nothing tells `qwen serve` whether the control plane can serve child Workspaces.

## Decisions

1. **The model opts in, per launch.** The managed `agent` tool gains an optional `isolation` argument whose only value is `"worktree"`, the legacy Agent tool's name and value. Without it the child is `shared`, exactly as today; any other value is an argument error. The launch records `workspaceMode: "worktree"`, a fixed key, so every later revision and every replay carries it, and a replayed launch that names another mode conflicts. `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` becomes `['shared', 'worktree']`; `snapshot` stays refused (I3). The declaration the model sees shows `isolation` only on a host that serves child Workspaces (decision 2); elsewhere it stays exactly as it was. The team variant of the Agent tool (H4e-b1, `name`) gains `isolation` the same way, and a team member may run isolated like any child.
2. **The capability is known at admission.** Java adds `childWorkspaces: true` to every hosted create and load request (attach, recovery, lifecycle settle) when child Workspaces are enabled. Startup now also requires the durable local-process Broker for them, the only one that closes Workspace Sessions: a merge needs the child closed, so a host that cannot close cannot merge. `qwen serve` keeps the flag on the resident Session, refreshed by every create or load whose owner it has proven (only an exact `true` counts; a lifecycle re-answer, which only the files profile without the Agent tool takes, leaves it as it was) and never persisted, because it describes the host and not the Session. Without it `admitChildLaunch` refuses a `worktree` launch with the existing `workspace_mode` reason, before anything commits and without spending the launch budget, and the tool result tells the model to launch without isolation. A replayed launch is never re-admitted, so a host that lost the capability still answers a launch it already committed.
3. **The relay prepares before it creates.** For a `worktree` run the relay first requests the child Workspace: the row is admitted and the child Workspace scan runs its Git, never the relay's single thread. While the row is `preparing` the relay looks again on its heartbeat without spending an attempt. A `ready` row creates the child with `createChildSession(..., isolated = true)`, so the child's directory joins the creation digest (I1 decision 13) and a replay from the committed body names the same binding. A refused layout (`failed`), a preparation that ended `blocked`, a `ready` row whose finish was already asked, a creation the row refuses because it left the parent's binding after it read `ready`, or a host or parent that cannot admit the row settles the run `failed`/`creation_failed`, never started, and the row (if an earlier attempt admitted one) is asked to discard. A child the lineage already names (a creation whose answer was lost) is not judged that way: the ordinary retries and the give-up chain settle it as started.
4. **Finish requests are durable and run once the child is closed (amends I1 decision 8).** `requestFinish` no longer refuses while a bound child Session is open. It records the request; the row leaves `ready` only once every child Session bound to the run is `CLOSED`, `ARCHIVED` or `DELETED`, and looks again every 5 seconds without spending an attempt until then. The safety I1 wanted is kept: no finish removes a directory under a running Session, and a creation still refuses once a finish is requested. A discard may replace a merge request that has not started (the row is still `ready`), and the step that leaves `ready` compares the request it read, so a merge a discard replaced never runs; once the row is `merging` the merge runs to its end.
5. **A completed worktree child merges before its result is committed.** When the child's Turn completes, the relay requests the merge, admits the child's close, and waits on its heartbeat until the row records an outcome: `merged`, `conflicted`, or the code of a blocked merge. Only then does it commit the result with the outcome in the receipt, accept, mark delivered, and replay the close. Waits never spend the attempt budget; faults while waiting still do, as for any run. A run that gives up keeps a child's completed work: a merge already asked keeps its place, and a give-up after a completed Turn asks for it. The work lands, as a `shared` child's writes would have, and the run settles `failed` like a `shared` run that gave up. A host that lost its close capability waits at the close-debt cadence (5 minutes) instead of committing a result whose merge cannot run. A discard asked first (the parent closing) keeps its place, and the receipt then reports `discarded`.
6. **The receipt carries the outcome.** A `worktree` run's receipt adds `workspace`: `{ mode: "worktree", childWorkspaceId, outcome, code, conflictPaths?, resultRef? }` (table below). It is built from the row's `outcome_code`, `conflict_paths` and `result_commit`, which a later discard leaves alone, so a replayed `commit_result` is byte-equal. The paths are names the child chose, so the receipt keeps them within 16 KiB of JSON and counts the rest in `omittedConflictPaths`: the receipt always fits the parent's 64 KiB inline resource. To keep that true, a merge that already ended now keeps its outcome when a later discard ends `blocked`, as I1 already did for `merged`; the discard's failure stays the last error. A `shared` run's receipt is unchanged. The record contract does not change: the receipt is the parent's opaque resource.
7. **The parent's model sees the outcome.** The foreground tool result ends with one line after the child's result, and the line survives the fold of an oversized result:
   - `[child workspace] merged into this Workspace as uncommitted changes.`
   - `[child workspace] merge conflicted at "src/a.ts", "b.md"; the child's changes did not land; the child's work is kept at refs/qwen/child-workspaces/<id>/result.`
   - `[child workspace] merge blocked (<code>); the child's changes did not land; the child's work is kept at <ref>.` (the ref only when a result was pinned)
   - `[child workspace] discarded; the child's changes did not land.`
   - `[child workspace] the merge outcome is unavailable; inspect this Workspace before relying on the child's changes.` when a `worktree` run's receipt is off shape.

   The recovered wait and the recovery gap fill end their answers with the same line: the fold keeps it whole after the result.

   Conflict paths are names the child chose: each is quoted as JSON, so a newline stays an escape, then stripped of display controls, the line and paragraph separators JSON leaves raw are escaped too, and the list stops at 4 KiB with `and N more` (counting the paths the receipt omitted). The background notification carries the same sentence in a `<workspace>` element beside `<status>`. Both read the receipt the acceptance names; a `shared` run adds nothing.

8. **A failed or cancelled worktree child is discarded.** The relay's fail arms (a failed or cancelled Turn, a give-up with no completed Turn, decision 5) request the discard before their `fail` commit; a merge already asked keeps its place, so a later Turn of the child that fails never replaces it. A completed child's work is never discarded unpinned: an over-bound answer settles `quota_exceeded` and asks for the merge. the record settles on time and the discard runs when the child is closed (decision 4). The relay's own path for a parent that is no longer active asks for it too, so a row admitted while the parent began closing, after the cascade looked, is not left behind. A refusal meaning the row already settled is not owed, and a run without a row (every `shared` run) is only looked up. The relay never waits for a discard to finish.
9. **The close cascade discards, never waits.** After its stop request the cascade requests the discard of a `worktree` run. A refusal that means the row is already settled (`merged`, `discarded`, a merge already running) is not a failure: a running merge lands. Any other failure of the request re-arms the parent's close like the cascade's other owed steps, and keeps that run's scope open (no `close_scope`), so the re-armed close finds the run again and asks again. The parent's close never waits for the discard to run, so a discard that cannot finish never wedges the close; the row's own retries and `blocked` end (I1) hold it.
10. **Siblings merge in completion order.** Each child's merge runs when that child completes, under the storage's maintenance hold (I1 decision 10), and is computed against the parent's tree as it is then, including earlier siblings' merges. A later sibling that edited the same lines ends `conflicted` with its paths and its work pinned; nothing orders siblings beyond that.
11. **The lease rules stay as H4b set them.** A child Workspace lives in the parent's storage, so the existing guards apply unchanged: a foreground child is refused while the Turn holds the mount, and an agent-only batch takes no mount. Preparation and merge meet a held storage as `workspace_busy` and look again without spending an attempt.

## Receipt

| Field                            | Meaning                                                                                                                                                                                                                                                          |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workspace.mode`                 | `"worktree"`.                                                                                                                                                                                                                                                    |
| `workspace.childWorkspaceId`     | The 32-hex id of the child Workspace (I1).                                                                                                                                                                                                                       |
| `workspace.outcome`              | `merged`, `conflicted`, `blocked` or `discarded`.                                                                                                                                                                                                                |
| `workspace.code`                 | The row's `outcome_code`: `merged`, `conflicted`, `discarded`, or the code that ended the merge `blocked` (a `child_workspace_*` refusal or a Broker code). A code outside `[a-z][a-z0-9_]{0,63}` makes the model-facing text report the outcome as unavailable. |
| `workspace.conflictPaths`        | For `conflicted`: the conflicting paths in merge order, at most 100 and at most 16 KiB of JSON.                                                                                                                                                                  |
| `workspace.omittedConflictPaths` | When the byte bound left recorded paths out: how many.                                                                                                                                                                                                           |
| `workspace.resultRef`            | When the work did not land and a result exists: the pin ref that keeps the child's result commit.                                                                                                                                                                |

## Non-goals

- `snapshot`, and the serialization decision (I3).
- `workflow` children: the kind stays disabled; its runtime slice widens the relay and the cascade.
- A hosted producer of continuations (H4d). A continuation keeps its predecessor's mode, so a continued `worktree` run would prepare a Workspace of its own from the parent's tree as it then is.
- Choosing a merge strategy per launch, resolving conflicts automatically, or committing the merged changes for the parent.
- Concurrency between parent and child: one storage lease still serializes their tool turns (I1 decision 1).
- Any public contract change: the OpenAPI contract, routes, record bodies and migrations stay as they are.

## Acceptance criteria

- A `worktree` child's writes do not appear in the parent's tree until its merge runs; a completed child's merge lands as uncommitted changes before the parent sees the result, and a conflict reaches the parent's model with its paths and the ref that keeps the child's work.
- A failed or cancelled `worktree` child's worktree is discarded, and a parent's close never waits for that discard.
- A host without child Workspaces refuses `isolation: "worktree"` before anything commits.
- `shared` children behave exactly as before, and `workflow` stays disabled.

## Open questions

1. **Retention of a conflicted child's result pin** stays I1's open question 2. A merge that ends `blocked` keeps its worktree, and its result pin when one was made, for an operator: once its run settled, nothing discards it (a parent that closes while the run is still unsettled discards it, decision 9).
2. **Whether the merge should commit** the child's changes for the parent, instead of leaving them uncommitted, is left to a later request.
3. **A bound on the merge wait.** The merge waits for the child's close, and the result waits for the merge. A close that never completes holds the result: a foreground parent Turn waits until it is cancelled, which leaves the committed child running as H4b documents. Giving up on the wait would either discard the unpinned work or report an outcome the row may still change, so no bound is set yet.
