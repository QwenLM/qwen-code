# Managed child worktree admission (isolation slice, I2)

[English](2026-10-10-managed-child-worktree-admission.md) | [简体中文](2026-10-10-managed-child-worktree-admission.zh-CN.md)

Status: implemented in this change, with the follow-up to its review deferrals (see "Follow-up to the review deferrals"). Landed: a hosted child agent may run in its own child Workspace (`isolation: "worktree"`). The relay prepares that Workspace before creating the child, merges it back when the child completes and before the result is committed, and discards it when the child fails or is cancelled; the close cascade discards it too; the receipt reports the merge outcome to the parent's model. I3 (`snapshot`, and the serialization decision) is implemented by its own [design](2026-10-11-managed-child-snapshot.md). This is I2 of [#13753](https://github.com/QwenLM/qwen-code/issues/13753), built on I1 ([child Workspace capability](2026-10-09-managed-child-workspace.md), #13781), H4b ([child Session runtime](2026-10-07-managed-child-session-runtime.md)) and H4c ([workflow child kind](2026-10-09-managed-workflow-child-kind.md)).

## Problem and scope

Issue #13753 asks of I2: "The relay creates a `worktree` child in its own Workspace; the close and settle paths run the merge policy; `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` admits `worktree`." Its exit check: "A worktree child's writes do not appear in the parent's tree until its merge policy runs, and a cancelled child's worktree is discarded."

I1 delivered the capability with no caller. This change wires the one producer, the hosted Agent tool, through the child agent pipeline H4b built. `workflow` stays disabled (H4c decisions 5 and 6): the relay and the cascade still act on `child_agent` runs only, so admitting `worktree` changes nothing for workflows until their runtime slice widens both. _(Superseded by the [workflow runtime slice](2026-10-10-managed-workflow-child-runtime.md), which enables `workflow` and widens the relay and the cascade to it; a workflow launch is still admitted with `workspaceMode: shared` only, so `worktree` stays a child agent capability.)_

## Current state

The facts below are from `main` at `1136a51a68`.

- **Admission.** `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` is `['shared']`. `childLaunchBody` writes `workspaceMode: 'shared'`, and the hosted tool turn passes `shared` to `childLaunchAdmission`. The managed `agent` tool takes `description`, `prompt` and `run_in_background` and refuses `isolation` as a legacy-only argument (H4b decision 11).
- **Relay.** `ChildResultRelay.create` reads the launch envelope and calls the non-isolated `createChildSession`; the record's `workspaceMode` is never read. A completed child is committed (`commit_result`, `accept`) and closed afterwards (`deliver`). The fail, quota and give-up arms admit the child's close before their `fail` commit. The receipt is `{childSessionId, turnId, status, completedAt}`, stored by the parent as an opaque resource; no validator in either language parses it.
- **Cascade.** `SessionLifecycleCoordinator.cascadeChildScopes` requests a stop for every unsettled `child_agent` run, closes each child Session through its own lifecycle, and only then commits `close_scope`. Any owed step re-arms the parent's close.
- **Child Workspaces (I1).** `ChildWorkspaceService.prepare`/`finish` admit the row and drive Git synchronously; the scan drives what is left. `requestFinish` refuses while a bound child Session is not closed (I1 decision 8), and a different finish is refused except a discard after a merge that ended `conflicted` or `blocked`.
- **Foreground wait (#13769).** A foreground child's wait is restart-recoverable: a recovered Turn re-enters it from its checkpoint, and the recovery gap fill answers an admitted orphan call. Both fold the accepted result through `fitChildResultInline`.
- **Hosted session creation.** Java creates or loads the hosted Session with `toolProfile`, the store connection and, for a child, `lineage`. Nothing tells `qwen serve` whether the control plane can serve child Workspaces.

## Decisions

1. **The model opts in, per launch.** The managed `agent` tool gains an optional `isolation` argument whose only value is `"worktree"`, the legacy Agent tool's name and value. Without it the child is `shared`, exactly as today; any other value is an argument error. The launch records `workspaceMode: "worktree"`, a fixed key, so every later revision and every replay carries it, and a replayed launch that names another mode conflicts. `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` becomes `['shared', 'worktree']`; `snapshot` stays refused here (I3 admits it on a host that serves snapshots; see its [design](2026-10-11-managed-child-snapshot.md)). The declaration the model sees shows `isolation` only on a host that serves child Workspaces (decision 2); elsewhere it stays exactly as it was. The team variant of the Agent tool (H4e-b1, `name`) gains `isolation` the same way, and a team member may run isolated like any child.
2. **The capability is known at admission.** Java adds `childWorkspaces: true` to every hosted create and load request (attach, recovery, lifecycle settle) when child Workspaces are enabled. Startup now also requires the durable local-process Broker for them, the only one that closes Workspace Sessions: a merge needs the child closed, so a host that cannot close cannot merge. `qwen serve` keeps the flag on the resident Session, refreshed by every create or load whose owner it has proven (only an exact `true` counts; a lifecycle re-answer, which only the files profile without the Agent tool takes, leaves it as it was) and never persisted, because it describes the host and not the Session. Without it `admitChildLaunch` refuses a `worktree` launch with the existing `workspace_mode` reason, before anything commits and without spending the launch budget, and the tool result tells the model to launch without isolation. A replayed launch is never re-admitted, so a host that lost the capability still answers a launch it already committed.
   - **Every control-plane replica sets `qwen.managed-agent.runtime-broker.child-workspaces-enabled` alike.** Each replica reads only its own setting, and nothing compares it across replicas, but the relay's scan claims pending child runs on every replica. A replica with child Workspaces off therefore settles a `worktree` run it claims before the child exists as `creation_failed` (decision 3), and waits at the close-debt cadence on a run whose merge was asked (decision 5): a capable replica still runs the merge, but committing the result, or telling a failure or a stop, can lag the merge's outcome by up to 5 minutes. A replica from before this slice cannot join such a cluster: #14069 replaced the database with a fresh baseline that takes no in-place upgrade, and every binary that can use it includes this slice.
3. **The relay prepares before it creates.** For a `worktree` run the relay first requests the child Workspace: the row is admitted and the child Workspace scan runs its Git, never the relay's single thread. While the row is `preparing` the relay looks again on its heartbeat without spending an attempt. A `ready` row creates the child with `createChildSession(..., isolated = true)`, so the child's directory joins the creation digest (I1 decision 13) and a replay from the committed body names the same binding. A refused layout (`failed`), a preparation that ended `blocked`, a `ready` row whose finish was already asked, a creation the row refuses because it left the parent's binding after it read `ready`, or a host or parent that cannot admit the row settles the run `failed`/`creation_failed`, never started, and the row (if an earlier attempt admitted one) is asked to discard. A child the lineage already names (a creation whose answer was lost) is not judged that way: the ordinary retries and the give-up chain settle it as started.
4. **Finish requests are durable and run once the child is closed (amends I1 decision 8).** `requestFinish` no longer refuses while a bound child Session is open. It records the request; the row leaves `ready` only once every child Session bound to the run is `CLOSED`, `ARCHIVED` or `DELETED`, and looks again every 5 seconds without spending an attempt until then. The safety I1 wanted is kept: no finish removes a directory under a running Session, and a creation still refuses once a finish is requested. A discard may replace a merge request that has not started (the row is still `ready`), and the step that leaves `ready` compares the request it read, so a merge a discard replaced never runs; once the row is `merging` the merge runs to its end.
5. **A completed worktree child merges before its result is committed.** When the child's Turn completes, the relay requests the merge, admits the child's close, and waits on its heartbeat until the row records an outcome: `merged`, `conflicted`, or the code of a blocked merge. Only then does it commit the result with the outcome in the receipt, accept, mark delivered, and replay the close. Waits never spend the attempt budget; faults while waiting still do, as for any run. A run that gives up keeps a child's completed work: a merge already asked keeps its place, and a give-up after a completed Turn asks for it once the child is bound to the run. A give-up on a row whose child was never bound (a lost creation answer) discards instead: its merge would hold a `creating` row that the next scan walks into the same give-up again. The work lands, as a `shared` child's writes would have, and the run settles `failed` like a `shared` run that gave up. A merge the relay asked holds every settlement of the run, not only its result: a failure (a later failed Turn, an over-bound answer, a give-up) or a stop is told only once the row records the merge's outcome, so the work never lands after the parent was told the run ended. A host that lost its close capability, or runs no child Workspace steps (child Workspaces turned off), waits at the close-debt cadence (5 minutes) instead: the merge cannot run there, and a host that can run it records the outcome. The merge is asked all the same, so a parent's close meanwhile pins the work (decision 9). This is the one place where a host without the close capability holds a settlement: the merge needs the child closed. A discard asked first (the parent closing) keeps its place, and the receipt then reports `discarded`.
6. **The receipt carries the outcome.** A `worktree` run's receipt adds `workspace`: `{ mode: "worktree", childWorkspaceId, outcome, code, conflictPaths?, resultRef? }` (table below). It is built from the row's `outcome_code`, `conflict_paths` and `result_commit`, which a later discard leaves alone, so a replayed `commit_result` is byte-equal. The paths are names the child chose, so the receipt keeps them within 16 KiB of JSON and counts the rest in `omittedConflictPaths`: the receipt always fits the parent's 64 KiB inline resource. To keep that true, a merge that already ended now keeps its outcome when a later discard ends `blocked`, as I1 already did for `merged`; the discard's failure stays the last error. A `shared` run's receipt is unchanged. The record contract does not change: the receipt is the parent's opaque resource.
7. **The parent's model sees the outcome.** The foreground tool result ends with one line after the child's result, and the line survives the fold of an oversized result:
   - `[child workspace] merged into this Workspace as uncommitted changes.`
   - `[child workspace] merge conflicted at "src/a.ts", "b.md"; the child's changes did not land; the child's work is kept at refs/qwen/child-workspaces/<id>/result.`
   - `[child workspace] merge blocked (<code>); the child's changes did not land; the child's work is kept at <ref>.` (the ref only when a result was pinned)
   - `[child workspace] discarded; the child's changes did not land.`
   - `[child workspace] the merge outcome is unavailable; inspect this Workspace before relying on the child's changes.` when a `worktree` run's receipt is off shape.

   The recovered wait and the recovery gap fill end their answers with the same line: the fold keeps it whole after the result.

   A `worktree` run that started and then failed or was cancelled has no receipt (the record sets `terminalReceiptRef` only with a result), so its answer cannot name the outcome. It ends instead with `[child workspace] the child's changes did not land, unless the child had finished its work before this end and its merge landed them here. Inspect this Workspace before relying on the child's changes; work that did not land may be kept under refs/qwen/child-workspaces/.` The line claims an order, never a landing: decision 5 holds the run's end until a merge the relay asked has its outcome, so what landed is already in this Workspace when the answer is read, and an outcome that did not land — a conflict, a blocked merge, or a discard that pinned first — kept the work at the result ref. A run that never started, and a `shared` run, add nothing.

   Conflict paths are names the child chose: each is quoted as JSON, so a newline stays an escape, then stripped of display controls, the line and paragraph separators JSON leaves raw are escaped too, and the list stops at 4 KiB with `and N more` (counting the paths the receipt omitted). The background notification carries the same sentence in a `<workspace>` element beside `<status>`. Both read the receipt the acceptance names; a `shared` run adds nothing.

8. **A failed or cancelled worktree child is discarded.** The relay's fail arms (a failed or cancelled Turn, a give-up with no completed Turn, decision 5) request the discard before their `fail` commit, and the stop arm (H4f, a public task cancel) before its `close_scope`; the record settles on time and the discard runs when the child is closed (decision 4). A merge already asked keeps its place, so a later Turn of the child that fails, or a stop, never replaces it. A child whose task Turn completed before a message turn failed, before a message it never answered ran out (H4d-b), or before a stop cancelled such a message turn, has its work merged like a give-up after a completed Turn. The relay records that merge as soon as it sees the task Turn of a child bound to the run completed, even while message turns still run, so a parent's close in that window pins the work. (Before the child is bound, for instance after a lost creation answer, nothing is recorded: the creation's replay must not meet a finish request. A stop first binds the child the lineage names, then finishes.) The relay itself never discards a completed child's work unpinned, except on a give-up whose child was never bound (decision 5); decision 9 names the cases where a parent's close still can: an over-bound answer asks for the merge and settles `quota_exceeded` once it has its outcome. A parent that closes before that merge starts still discards it, pinning the child's result first (decision 9). The relay's own path for a parent that is no longer active asks for it too, so a row admitted while the parent began closing, after the cascade looked, is not left behind. A refusal meaning the row already settled is not owed, and a run without a row (every `shared` run) is only looked up. The relay never waits for a discard to finish.
9. **The close cascade discards, never waits.** After its stop request the cascade requests the discard of a `worktree` run. A refusal that means the row is already settled (`merged`, `discarded`, a merge already running) is not a failure: a running merge lands. Any other failure of the request re-arms the parent's close like the cascade's other owed steps, and keeps that run's scope open (no `close_scope`), so the re-armed close finds the run again and asks again. The parent's close never waits for the discard to run, so a discard that cannot finish never wedges the close; the row's own retries and `blocked` end (I1) hold it. A discard that replaces a merge whose result is not pinned yet (one that has not started, or one that ended `blocked` before its pin) is recorded as `discard_pinned`: it first takes and pins the child's result, as a conflict does, so a completed child's work is kept at its result ref although it does not land. The pin never holds the discard back: when no result can be taken (a worktree or repository that is gone, broken or unsafe, or a failure that outlasts the row's retries, such as a nested repository the child left without a commit), the discard goes on as an ordinary one, as it did before the pin. A parent that closes in the few seconds between a child's task Turn completing and the relay's next look still discards the work unpinned: nothing has recorded the merge yet.
10. **Siblings merge in completion order.** Each child's merge runs when that child completes, under the storage's maintenance hold (I1 decision 10), and is computed against the parent's tree as it is then, including earlier siblings' merges. A later sibling that edited the same lines ends `conflicted` with its paths and its work pinned; nothing orders siblings beyond that.
11. **The lease rules stay as H4b set them.** A child Workspace lives in the parent's storage, so the existing guards apply unchanged: a foreground child is refused while the Turn holds the mount, and an agent-only batch takes no mount. Preparation and merge meet a held storage as `workspace_busy` and look again without spending an attempt.

## Receipt

| Field                            | Meaning                                                                                                                                                                                                                                                          |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workspace.mode`                 | `"worktree"`.                                                                                                                                                                                                                                                    |
| `workspace.childWorkspaceId`     | The 32-hex id of the child Workspace (I1).                                                                                                                                                                                                                       |
| `workspace.outcome`              | `merged`, `conflicted`, `blocked` or `discarded`.                                                                                                                                                                                                                |
| `workspace.code`                 | The row's `outcome_code`: `merged`, `conflicted`, `discarded`, or the code that ended the merge `blocked` (a `child_workspace_*` refusal or a Broker code). A code outside `[a-z][a-z0-9_]{0,63}` makes the model-facing text report the outcome as unavailable. |
| `workspace.conflictPaths`        | For `conflicted`: the conflicting paths in merge order, at most 100 and at most 16 KiB of JSON.                                                                                                                                                                  |
| `workspace.omittedConflictPaths` | When the byte bound left recorded paths out: how many.                                                                                                                                                                                                           |
| `workspace.resultRef`            | When the work did not land and a result exists: the pin ref that keeps the child's result commit.                                                                                                                                                                |

## Non-goals

- `snapshot`, and the serialization decision (I3).
- `workflow` children: the kind stays disabled; its runtime slice widens the relay and the cascade. _(Superseded: the runtime slice enables the kind and widens both; workflow launches are `shared` only.)_
- A hosted producer of continuations (H4d). A continuation keeps its predecessor's mode, so a continued `worktree` run would prepare a Workspace of its own from the parent's tree as it then is.
- Choosing a merge strategy per launch, resolving conflicts automatically, or committing the merged changes for the parent.
- Concurrency between parent and child: one storage lease still serializes their tool turns (I1 decision 1).
- Any public contract change: the OpenAPI contract, routes, record bodies and migrations stay as they are.

## Acceptance criteria

- A `worktree` child's writes do not appear in the parent's tree until its merge runs; a completed child's merge lands as uncommitted changes before the parent sees the result, and a conflict reaches the parent's model with its paths and the ref that keeps the child's work.
- A failed or cancelled `worktree` child's worktree is discarded, and a parent's close never waits for that discard.
- A host without child Workspaces refuses `isolation: "worktree"` before anything commits.
- `shared` children behave exactly as before, and `workflow` stays disabled _(superseded: the workflow runtime slice enables it, `shared` only)_.

## Follow-up to the review deferrals

The review of #13841 deferred these findings; the follow-up settles them without a contract change or a migration:

- **A stopped worktree run kept its child Workspace.** The stop arm (H4f, merged before I2) settled the run `cancelled` without a finish request, so its row stayed `ready` with the worktree on disk. It now asks for the discard (decision 8).
- **A failure was told before the merge landed.** The over-bound, give-up and later-failed-Turn arms settled `failed` while the merge they asked for ran afterwards, and the parent's model saw no workspace line. The merge now holds those settlements (decision 5), and the answer ends with a workspace line (decision 7).
- **A merge waited on every heartbeat on a host without child Workspace steps.** It now waits at the close-debt cadence there (decision 5). The wait itself stays unbounded (open question 3).
- **A parent's close discarded a completed child's work unpinned** when it replaced a merge that had not started, or one that ended `blocked` before its pin. That discard now pins the result first (decision 9).

Its validation:

- **Relay** (`ChildResultRelayTest`): a stopped worktree run discards, with nothing minted and with a cancelled child; a stop waits for a merge its child asked for, and a stop after a completed task merges that work first; the merge is recorded once the task completes, while a message still waits; an already failed run still asks for its discard; a failed later Turn, an over-bound answer and a give-up each wait for the merge they hold and settle after its outcome; a completed task whose message ran out merges before it fails; a host without child Workspace steps asks for the merge, admits the close and waits the idle interval, and one without the close capability still asks for the merge.
- **Child Workspace state machine** (`ChildWorkspaceServiceTest`, on H2 with real repositories): a discard replacing an unstarted merge is recorded as `discard_pinned`, a repeated discard is the same request, and it pins the child's result and leaves the parent's tree alone, while a plain discard pins nothing; a merge blocked before its pin is pinned by the discard; a worktree that is gone, one whose `.git` is gone and a repository that is gone each let the discard go on without a pin; a pin that cannot be written is retried, and after the last retry the discard goes on without it.
- **TypeScript** (`hosted-workspace-tool-turn.child-agent.test.ts`, `hosted-child-wait-recovery.test.ts`): the foreground answer and the recovery gap fill of a started `worktree` run that failed or was cancelled end with the workspace line; a run that never started and a `shared` run do not.

## Open questions

1. **Retention of a conflicted child's result pin** stays I1's open question 2; it covers the pins a discard takes when it replaces a merge (decision 9) too. A merge that ends `blocked` keeps its worktree, and its result pin when one was made, for an operator: once its run settled, nothing discards it (a parent that closes while the run is still unsettled discards it after pinning its result, decision 9).
2. **Whether the merge should commit** the child's changes for the parent, instead of leaving them uncommitted, is left to a later request.
3. **A bound on the merge wait.** The merge waits for the child's close, and the result waits for the merge. A close that never completes holds the result: a foreground parent Turn waits until it is cancelled, which leaves the committed child running as H4b documents. Giving up on the wait would either discard the unpinned work or report an outcome the row may still change, so no bound is set yet. The wait also holds a failure, a stop or a give-up of a run whose merge was asked (decision 5). With child Workspaces turned off on every host, such a run waits until they are turned on again, or until its parent closes: the cascade then settles the run and asks the discard, which pins the result.
