## Problem and decisions

The two Stores mix transaction entry points with SQL, mutable business state and several unrelated operation state machines. Moving methods by name would conceal side effects and can disable the existing single-file lock-order audit. Stable facades and explicit component ownership keep transaction behavior and callers reviewable throughout the extraction.

Keep public business interfaces, DTOs, exception mapping and package-visible compatibility bridges. New collaborators are package-private `final` classes in the same package, constructed once by the facade. Add no Spring beans, Maven modules, public business interfaces, mutable dependency setup or generic Context/Support container. Existing worktree, definition and skills components retain their responsibilities.

Dependencies use concrete types in one direction. Do not introduce facade callbacks or bundles of constructor functions to escape a cycle. Existing lazy Spring cycles, per-call fencing callbacks and compatibility value types keep their current meaning. If an extraction needs a shared rule, move its actual dependency closure with the first consumer; do not build unused helper frameworks.

`AgentStoreRows` owns shared Session/Turn row mapping and locked row reads. Commands owns shared receipts/settlement, EventJournal owns event identity and notification, and MessageProjection owns projection repair. Higher-level admission, lifecycle and execution workflows depend on these concrete lower-level collaborators. Move operation scans with their state machines.

Queries must not become a facade-shaped dependency of every writer. Writers use Rows for shared row access. `contextCompressionState(s)` performs projection backfill and belongs to ExecutionOperations. `deliverableRenames` changes delivery state and belongs to Commands. Preserve unannotated writes such as `markRenameSubmitted` as unannotated entries.

The worktree presentation entries `findSessionWorktree(s)` and `listSessions` can persist BLOCKED through the existing `SessionWorktreeStore` verification and its `REQUIRES_NEW` quarantine transaction. Exclude these three names from A1's pure-query slice; keep their complete implementation until A6 moves the worktree collaboration into the intended Queries presentation path. Keep that path explicitly side-effecting, reuse the existing worktree component and add no duplicate wrapper or new transaction. A1's boundary is smaller than the final Queries responsibility.

## Transactions, locks and atomicity

Every facade entry retains its original transaction manager, propagation, isolation, read-only flag and absence of an annotation. This includes `MANDATORY`, `NOT_SUPPORTED` and `READ_COMMITTED`. Ordinary collaborator objects create no transaction proxy and introduce no `REQUIRES_NEW`. Existing programmatic transactions keep their original placement and timeout.

For paths locking both Session and Turn, Session remains first. Placement, retention, root and head locks retain each path's existing order. CSI continuation exceptions and bounded lock-wait/deadlock mapping remain explicit; do not impose a new universal order.

Commit resource changes, extension/action/message projections, journal transaction and head update atomically. Preserve duplicate-return positions, writer/CSI rechecks, configuration read timing and notification timing. Rollback and replay must not add notifications; standalone behavior without synchronization remains unchanged.

Resource reads are not plain queries. Ordinary and snapshot reads retain their distinct verification/quarantine behavior and retention lease handling. Owner reads continue to reject an ambient transaction and use short admission transaction, object read, short recheck/receipt/cleanup transaction. Compression projection backfill keeps its programmatic transaction.

Existing external `REQUIRES_NEW` boundaries remain: worktree quarantine and the snapshot caller's isolated `READ_COMMITTED` template. The ban is on introducing new transaction boundaries, not deleting those already required by callers.

Do not change SQL, digests, JSON or protocol bytes, schema, HTTP/OpenAPI contracts or algorithms while extracting.

## Lock-audit implementation

Keep the JDK parse-tree audit and its bounded resolution model. Load the facade with the same-package `Agent*.java` or `Journal*.java` collaborator family, rather than depending on a manually updated per-class allowlist. Other persistence files retain their existing boundary scan. New SQL-bearing files must still change the exactly pinned sibling populations visibly.

Harvest members across the selected files using owner, name and parameter types. Keep source-specific imports and constant environments separate; qualify shared constants so one file cannot overwrite another file's SQL spelling. Cross-check parsed members against compiled classes for every selected source, including collaborators and nested types.

Follow a field receiver only when the reference is final and its declared class is a parsed concrete final type. Resolve each field type in its declaring class. Support bare fields and explicit `this.field`; parameters/locals shadow bare fields without shadowing explicit field access. An external imported type must not borrow members or SQL constants from a same-named parsed collaborator. Keep unresolved, polymorphic, overload-ambiguous, generic/local-class and deferred-body cases fail-closed when a candidate reaches a Session lock or Turn row. Do not broaden ambiguity exemptions or delete population assertions to make moved code pass.

Retain current facade entry sets, transaction checks, sibling boundary sets and ambiguity/deferred-body assertions. Collect entry populations under their facade owner so a same-named collaborator cannot satisfy them; order, ambiguity and compiled-member checks still cover the whole source family. Regression examples must cover a multi-file transitive delegate, moving the Session lock after Turn access, removing the lock entirely (caught by the pinned locker population), hiding it behind an unresolved receiver, shadowing, ambiguous overloads and file-specific constants/imports.

The audit establishes source-level ordering, not transaction runtime semantics or database deadlock freedom. Each implemented stage still needs its relevant runtime and MySQL evidence.

## Risks and open decisions

The accepted architectural direction has no outstanding product decision. The main implementation risks are hidden query side effects, shared receipt/resource validation, lazy construction cycles, moved transaction boundaries and source-audit blind spots. Resolve an unexpected dependency in the smallest affected slice and update both language versions before changing the design. Do not silently absorb an algorithm, SQL, storage or protocol redesign into a movement PR.

## Implemented dependency boundaries

The facade evaluates the same settings and catalog validation once, in the original order, then supplies the same values and dependency instances to final collaborator fields. Agent construction is Rows → Queries/EventJournal → Policies/Projection → Commands → Admissions/Lifecycle/TurnExecution → ExecutionOperations. Journal construction is Rows → Fencing → WriterLifecycle/HistoryQueries/LifecycleAuthorization/ResourceWrites/ResourceReads → Commit. No collaborator receives a facade or a constructor callback bundle.

Shared Session/Turn point reads live in Rows; Queries forwards its three compatible point-read entries to those implementations. Policies owns shared admission predicates, while Rows owns their existing key encoders and database-time reads. The nine-argument default Session admission remains the original interface-default forwarding entry on the facade, preserving virtual dispatch and its transaction boundary. Resource row verification remains separate from object IO, leases and quarantine. Commit calls the extracted lifecycle-dispatch authorization block at its original location, with the existing call-local resource reader.

Session construction now resolves all nine former setter references. The required Spring dependencies remain required; standalone constructors retain their original null/in-process/unbound defaults. Either missing lifecycle dependency disables both. Only a same-data-source JDBC runtime binding repository enables CSI. Maintenance entry points and fixtures supply dependencies before constructing downstream consumers; actual Spring factory construction is covered separately.

The lock audit keeps its facade populations and pins the 23 remaining migrated private-helper overloads by owner/name/arity after deleting the unused `beginLifecycle/9`. Companion sources are analyzed with their complete family and retain separate, explicit SQL-owner boundary populations. Compiled-member coverage, fail-closed receiver resolution and the original negative regressions remain required. The original-line inventories below refer to the recorded baseline, not the new source locations.

### Worktree display decision and side effects

The worktree display entries are NOT pure reads. `findSessionWorktree` / `findSessionWorktrees` call `SessionWorktreeStore.descriptor(s)` (107-145), and `listSessions` calls `descriptors` after its batched page SQL (4645). `verifiedDescriptor` (112-120) verifies filesystem identity and reads the current branch; on `ManagedAgentException` it calls `blockIdentity` (368-378), which opens an EXISTING `TransactionTemplate` with `PROPAGATION_REQUIRES_NEW`, changes READY to BLOCKED and increments revision. The separate transaction deliberately survives a caller's failed admission rollback. Final decision: exclude these three entry names from the first A1 pure-query slice and retain their original facade implementation until A6. In A6 they move to the existing AgentSessionQueries component as explicitly side-effecting compatibility display paths, reusing SessionWorktreeStore validation/quarantine and its existing transaction. Do not add readOnly, omit verification, copy quarantine code, remove the existing transaction, or add another worktree wrapper.

The same existing worktree verification path appears in policy/execution admission through `requireCwdChangeRegistryFacts` (3894): `SessionWorktreeStore.requireReady` then `hasExecutionRegistryFacts`. Preserve worktree verification before the creator/binding facts check, including its persisted quarantine semantics.

### Transaction and bridge exceptions

- `findWorkspaceCreateReplay` (555) has no declaration; `replayWorkspaceSessionCommand` (570) has plain `@Transactional`. Both re-check replay digest, internal-team-lead identity, workspace binding and current read permission. Do not normalize the two transaction modes.
- `insertCsiSessionCommand` (582) is package-private, has no transaction annotation, explicitly requires an active transaction, and rejects journal event transport. `requireCsiRequest` (633) preserves the same transport isolation, locks Session plus runtime-request key and validates the CSI profile/request identity. The caller `WorkspaceCsiSessionCommands.create` (19-47) rejects an ambient transaction, starts a fresh 10-second TransactionTemplate, checks its original physical transaction connection, locks placement then retention, verifies registration, then calls both Store bridges on that connection. This caller uses the standalone `var sessions = new ManagedAgentStore(...)` construction path.
- `requireCsiRequest` is also called by `WorkspaceCsiRuntimeAccess.request` (183-190); preserve all pre-existing continuation/retention lock behavior in that caller. Keep its facade method/package visibility and the seven-argument standalone constructor available.
- `readBinding` (7569) is public static and directly used by `WorkspaceMigrationMain`, `WorkspaceMigrationStore` and `WorkspaceFileStore`; keep a facade forwarding entry even after moving actual mapping into rows.
- `requireMcpSettingsCommit` (1215) and `requireConfigurationCommit` (1266) are MANDATORY. `requireContextCompressionCommit` (3200) has NO annotation; it is called from `ManagedExtensionRecordStore` in an existing commit flow, and must not acquire an invented MANDATORY/REQUIRES_NEW wrapper.
- `findMessagePage` overloads (5234/5242) explicitly use managedAgentTransactionManager, readOnly true and REPEATABLE_READ. Ordinary Query entries are unannotated and must remain so.
- `deliverableRenames` (1933) is a transactionally mutating scan: it parks expired SUBMITTED claims and resets expired PREPARING ones before selecting work. `markRenameSubmitted` (1979) is a guarded write with no declarative transaction. Keep both in Commands and preserve the difference.
- `contextCompressionState` (3005) calls `ensureCompactionProjection` (3066); a missing projection opens a default TransactionTemplate with a DataSourceTransactionManager and replays journal rows. Batch `contextCompressionStates` (3020) may fall back to this write path and marks unavailable states. Both belong in A8, with the same programmatic transaction, rather than A1.
- `publishAfterCommit` (7489) publishes only after synchronization commit; if no synchronization exists it publishes immediately. Empty events do nothing. The EventJournal extraction must retain the standalone fallback and avoid replay/rollback notifications.

### Actual lock families (do not replace them with one global order)

- Row helper `requireSessionForUpdate` (7061/7066) locks the PUBLIC Session row first and reads/locks its event-stream counters only AFTER that lock. The list mapper and the strict single-session mapper have different missing-stream behavior. `requireTurnForUpdate` (7106) then locks a Turn where that path needs both; its NOT_FOUND mapping must survive extraction.
- Many admission/mutation/policy entrypoints begin `WorkspaceMigrationAdmission.lockTenant`, then Session/stream, then Turn/receipt/operation as required. MCP/extension idle rechecks (1340) specifically use fresh locking reads in this order: Session plan -> active Turn -> unsettled child-run record -> requested action records -> active operation/rename/receipt. Existing journal snapshots are the reason these may not become ordinary consistent reads.
- Lifecycle admission `beginLifecycle` (2695) locks migration tenant, conditionally retention tenant, then Session/stream; it preserves failed-operation replay/resume, authorizes state, checks idle journal, writes operation/fence/head and event in original order. `completeOperation` (4143) first applies the legacy CSI guard, then conditionally placement and bounded retention, then deletion lock either before or after Session according to lifecycle protocol, then operation claim. Do not normalize its branches.
- `ManagedLegacySessionGuard.requireLegacyMutation` itself performs the indexed CSI root locking read through `ManagedSessionStore.namedRootDeadlock`, with a 10-second query timeout. Some Turn lease paths use this guard plus a guarded UPDATE, while admission/terminal paths take a full Session/stream lock and then Turn. Retain that distinction; a generic row-helper transaction/lock would change semantics.
- Materialization and replay-floor advancement lock Session/stream before inspecting Turn evidence or updating coverage. Retraction repair `rebuildTurnText` (6172) locks stream coverage and message rows only after the enclosing Turn workflow has acquired its existing owner/epoch locks.

### 6. Actual resource-read effects and transactions

#### Ordinary and snapshot reads

The shared implementation at M:1930 first validates scope, credential, resource identity, head and read grant. The read grant itself reads retention state and database time. `outputRetention.read` (ToolPublicationRetentionStore:379) uses its existing TransactionTemplate, with default REQUIRED/DEFAULT/readOnly=false, to execute Tg→R→H through lockGenericSession and insert a 120-second `ma_read_lease`. It joins an existing ambient transaction. The outer resource method has no NOT_SUPPORTED annotation; do not add one.

Ordinary reads use findResource with lock=true, verify the row, update last_verified_at (M:1953), and read an object stream for TOOL_PUBLICATION. Length/digest failures quarantine capture/resource state. Snapshot reads use lock=false, do not update verification time and do not quarantine, but still insert, conditionally renew, check and close retention leases. Neither belongs in a pure-query component. `verifyStoredResource` itself does not perform those effects; see section 8.

The snapshot caller's existing isolated template at `ManagedNativeJournalSnapshots:56–61` uses REQUIRES_NEW + READ_COMMITTED. Its admission/basis (:89), build (:92), lease close (:94) and resource read (:520) retain that template. **Preserve this existing REQUIRES_NEW behavior.** The prohibition on introducing REQUIRES_NEW forbids additional boundaries; it does not authorize deleting this one or copying it into the new components.

#### Owner reads

M:1978 rejects both `isActualTransactionActive()` and an already-bound jdbc DataSource resource. Non-CSI traffic at M:1995 still falls back to the ordinary reader. The CSI path remains:

1. The ownerReads template at M:197–200 uses the same-DataSource manager, REQUIRED/DEFAULT/readOnly=false and a ten-second timeout. Admission runs lockCsiContinuation→original admission or DRAINING checkpoint-continuation check→R/H→read grant→resource metadata FOR UPDATE. Require inline storage, construct identity evidence, recheck CSI/read lease, insert the OPEN CSI_RESOURCE_READ receipt, recheck again, insert ma_read_lease with generation=0, and retain the receipt.
2. After leaving that transaction, fetchNativeResource at M:2172 obtains a separate DataSource connection to SELECT the complete inline bytes with a ten-second statement timeout. This independent reading stage must not hold the admission transaction or reuse its physical connection.
3. finishNativeRead at M:2199 opens another short ownerReads transaction. Relock continuation/original→R/H→read receipt FOR UPDATE; changed identity/receipt is rejected. Unknown fetch failure records UNKNOWN / jdbc_fetch_unknown and retains the lease under the existing path. On a returned fetch, lock/check the read lease, lock resource metadata, compare row identity/bytes/hash, recheck CSI/read grant, update verification time, record RETURNED with verified or the refusal code, and delete the lease only after the final recheck. Existing early fencing failures roll back rather than forcing settlement; do not replace this with unconditional finally cleanup.
4. A RuntimeException/Error during fetch attempts completion and attaches completion failure as suppressed before rethrowing the original error. Do not wrap owner IO in a large transaction or collapse repeated current-time/read-grant checks.
