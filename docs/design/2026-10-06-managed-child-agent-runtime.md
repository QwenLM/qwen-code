## Problem and scope

Issue #12380 states H4 plainly: "Independent child Sessions, parent acceptance/consumption, durable messages and close cascades. Shared record names alone are not executable domains." The reference design §13 sets the H4 gate: independent child Sessions, worktree isolation, parent accept/consume, and recoverable message and close cascades. The reference design §8 fixes the semantics:

- A parent Session commits a `child_run` launch plus outbox; the control plane creates the child Session idempotently; the child Harness commits one terminal result; the result travels the child result outbox; the parent commits `acceptChildResult` (accepted) together with the tool result or a notification input and its wake; the parent model then consumes it (consumed).
- Child terminal, parent accepted and parent consumed are three independent facts. A relay redelivers the original result only until accepted; a result that arrives at a closed parent is kept orphaned, never reviving the parent model.
- A foreground child (`completion: "tool"`) returns only through the original tool result; a background child (`completion: "sent"`) returns only through a durable notification input. Never both.
- Parent close cascade-cancels every child that has not been explicitly detached; detached children migrate to an independent durable owner.

Nothing on main carries these semantics for a child agent or workflow. The `child_run` and `child_acceptance` names sit in the closed v1 domain index with no body beyond H3's `kind: "shell"`, and the automation design's field-level contracts (`startChildRun`, `commitChildResult`, `acceptChildResult`, `cancelChildRun`) have no implementing record shape.

## Decisions

1. **One domain, one body version, per-kind closed shapes.** `child_run` keeps recordRef `managed-child_run` schema version 1, and the body's own `kind` field dispatches closed key sets: `shell` (H3) and, from this change, `child_agent`. Section 3.1 of the storage design pins `recordRef.schemaVersion = 1` for the v1 index, and `domain.committed` enforces it (`managed-session-records.ts:30`, 1146-1157), so a new kind is a new body shape, not a new envelope version; H3's "its own body version" therefore reads as each kind's own body shape inside the v1 envelope. An older reader refuses a `child_agent` body — a writer lacks the body and never commits it, a reader lacking it fails to reopen — which is the fail-stop stance H3 established for new record shapes. Because no Session on any deployed profile holds a `child_run` record yet (the domain is disabled everywhere), there is no mixed-version window, and enabling `child_run` and `child_acceptance` stays an explicit, server-first-deployed step for H4b, identical in kind to the H1/H2 ordering and to what H3 documented for its own pending enablement.
2. **Chain identity is per kind.** A `shell` chain is keyed by `shellId`; a `child_agent` chain by `childRunId`. The H0c keying rule (decision 3: domain plus the body's own identity) is unchanged, and the task ID derivation is unchanged.
3. **The launch identity is the opening command.** The automation design's `launchId` is the operation that opens the `child_run` record: H0c already enforces one record per opening command, the authority replays a retried command to its committed record, and the Java store keeps the opening command's hash. H4b derives the cross-Session creation idempotency key from the record key, so the body carries no field duplicating the envelope — "creation and the first input use the original `launchId`" is satisfied by derivation, and an ambiguous creation never mints a second record.
4. **The child agent's delivery rides the run block; the acceptance is its own record.** A `child_agent` run carries a `session`-target delivery line (`planned → accepting → accepted → consumed`, plus `unknown`, `rejected`, `cancelled`), which is what the outbox projection and any dispatcher scan read. It does not carry the acceptance evidence: dedupe, content binding and consumption tracking live in `managed-child_acceptance`, the separate domain section 3.1 names for it, because the three facts — child terminal, parent accepted, parent consumed — must be independently committed and independently killable (automation §8 A06). One `commitExtensionRecord` transaction carries one record revision, so the acceptance act is the acceptance record plus its input and wake in one transaction; advancing the `child_run` delivery line is a separate, relay-driven commit that a crash may delay but never corrupts (the acceptance record already stops redelivery).
5. **No orphaned field.** An orphaned result — a result arriving at a parent that is closing or closed — is not an acceptance: no input is admitted and no wake fires, so no `child_acceptance` record exists for it. The relay keeps the orphan classification on its own side (H4b), per automation §5: the receipt inbox preserves the original outcome, never presents it as consumed, and never revives the parent model. The body therefore has nothing to say about orphans.
6. **Cross-Session references are always parent-held copies.** The acceptance's `contentRef` and `terminalReceiptRef`, and the child run's `resultRef` and `terminalReceiptRef`, name resources in the parent Session's own store. The parent's authority copies the child's published result and receipt before accepting; the digests in `contentDigest` and the refs bind those copies to the child's originals, and a redelivery naming the same record with different content is a conflict, not a second acceptance. No reference ever crosses Sessions, matching the storage design's rule that a resource named by a commit must be held by that Session.
7. **`resultVersion` is fixed at 1 in v1.** A child has exactly one logical terminal result; continuing a completed child creates a new `childRunId` with `predecessorChildRunId` set (automation §5). A late physical receipt is a settlement update of the original operation, not a revision of the result.
8. **Depth and the tree root are explicit, the budget allocation is not (yet).** The body carries `depth` and `rootSessionId` so a nested tree is auditable where it lives (each child's record lives in its direct parent's journal), and the depth-1 commit-time rule binds that tree to this journal: a first-level child's `rootSessionId` must be this Session on both sides. Automation §5's `budgetRef` is left out of v1: budget accounting lands with its runtime slice (reference design §12's child row), and the contract cap on depth does not wait for it. The cap at 8 is the managed contract's own choice, independent of the legacy `--max-subagent-depth` user setting (limit 100, default 5), which sizes legacy subagent nesting only; H4b's dispatcher must visibly refuse a managed launch the record cannot carry — clamping would write a `depth` the launch did not have.
9. **The acceptance opens settled, already accepted.** The generic H0c opening rule has a first revision open `reserved`/`admitted` with a delivery at most `planned`. `managed-child_acceptance` cannot follow that: the shared run parser refuses a `session` delivery beyond `planned` on a non-terminal run, because accepting a result before the run ends is exactly the confusion H0b forbids. The record is not a run with a lifecycle, though — it is the receipt of an act that has just happened, so its first revision opens with the run already `settled` and the delivery `accepted`, the only ended state that describes a successfully completed acceptance. Its only later transition advances the delivery to `consumed` in one step while the run stays settled, which the shared successor rules admit as the one change an ended run may take. `accepted` can therefore never masquerade as `consumed`, and no extra commit can rewind a consumption.
10. **Workflow is a kind, not a second domain — later.** H4c adds the `workflow` body kind under the same per-kind dispatch, with its definition pin naming the workflow definition revision. Deferring it keeps this change to exactly the two bodies the child runtime consumes; adding a kind later is the same additive, fail-stop-for-old-readers operation as adding `child_agent` is here.
11. **The Java control plane gains both bodies with Java-side replay, ahead of any writer.** This is the server-first half of decision 1: `managed-agent-server` validates `child_agent` and `child_acceptance` the day this lands, so when H4b enables submission, any store already deployed refuses nothing a new writer may commit. `child_acceptance` projects no task — its rows carry null task columns, as MCP's do (V23) — while `child_agent` maps the existing `TaskKind.child_agent` and needs no contract change.

## Records

### `managed-child_run`, kind `child_agent`

Schema version 1. The chain is keyed by `childRunId`. All keys are required; a nullable key holds `null`.

| Key                     | Rule                                                                                                                                                                                                                                                                          |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind`                  | `"child_agent"`                                                                                                                                                                                                                                                               |
| `childRunId`            | id                                                                                                                                                                                                                                                                            |
| `ownerScopeId`          | id: the parent activation scope that owns the child and receives its result (automation §5's `parentScopeId`)                                                                                                                                                                 |
| `rootSessionId`         | id: the root of the nesting tree; for a first-level child it is the Session that owns this journal                                                                                                                                                                            |
| `depth`                 | count from 1 to 8                                                                                                                                                                                                                                                             |
| `completion`            | `"tool"` or `"sent"` (decision: foreground returns only through the original tool result, background only through a durable notification input)                                                                                                                               |
| `inputRef`              | durable ref: the launch input — the child's first prompt — held by the parent Session                                                                                                                                                                                         |
| `workspaceMode`         | `"shared"`, `"snapshot"` or `"worktree"`: the isolation policy fixed at launch (reference design §8); v1 runtimes admit only what they can prove (H4b)                                                                                                                        |
| `workingDirectory`      | id-safe relative directory text within the bound Workspace, `.` for the root: normalized NFC, no leading or trailing `/`, no backslash, no empty, `.` or `..` segment, no drive spec, at most 512 UTF-8 bytes                                                                 |
| `childSessionId`        | null or id: set once, with the dispatch that the control plane admitted the creation; idempotent creation names the same Session. Null while the execution is null, an intent, a dispatch in flight or proven unstarted — a Session exists only once the dispatch is attached |
| `predecessorChildRunId` | null or id: set at launch for a continuation, never changed                                                                                                                                                                                                                   |
| `resultVersion`         | count, exactly 1 in v1 (decision 7)                                                                                                                                                                                                                                           |
| `resultRef`             | null or durable ref: the parent-held copy of the terminal result content                                                                                                                                                                                                      |
| `terminalReceiptRef`    | null or durable ref: the parent-held copy of the child's terminal receipt                                                                                                                                                                                                     |
| `stopReason`            | null, or the closed reason fitting the run's end state, below                                                                                                                                                                                                                 |
| `stopRequested`         | boolean: set once, never cleared — the cancel request, including the close cascade's                                                                                                                                                                                          |
| `run`                   | the run block                                                                                                                                                                                                                                                                 |

- **Run.** The run names the start call's `executionCallId` in v1 (children are launched by a tool call; automation-triggered children are H6 with `effectId`). `dispatchId` is set with the cross-Session creation dispatch, never changed. `deliveryId` is null: a `session` delivery needs none. `definition` pins the launched definition (`definitionId`, `definitionRevision`, `definitionDigest` — the subagent or AgentBundle revision actually used), no later than dispatch. `runtime` records the child Session's Runtime binding at dispatch and follows the shared re-attach rules. `delivery` is a `session`-target line, present from the first revision as `planned`.
- **Delivery states.** `planned` at open; `accepting` when the relay claims the terminal result; `accepted` the moment the parent commits the `child_acceptance` record; `consumed` when the parent's consumption commits; `unknown` when the acceptance outcome is unproven after the relay claimed the result — a run whose _dispatch_ outcome is unproven keeps `planned` until it ends, and an end without a result carries `cancelled`; `cancelled` exactly when the run ends without a result (`failed`, or `cancelled` before a result exists); `rejected` when the parent definitively refuses acceptance. A run that ended changes only its delivery, per the shared rule.
- **Result refs.** `resultRef` and `terminalReceiptRef` change only together, and appear only in the revision that settles the run with a result: a settled run carries both, and a run at any other state carries neither — a half-result can never be committed early, wedging the chain's delivery forever.
- **Stop reasons.** `settled` by `completed`; `failed` by `creation_failed`, `child_failed` or `quota_exceeded`; `cancelled` by `stop_requested`. A `stop_requested` end requires `stopRequested`. `creation_failed` requires an execution that never produced a child Session (`childSessionId` null). `quota_exceeded` is the reason exactly when the run carries a quota reason (mirroring the Shell rule). `completed` requires `resultRef` and `terminalReceiptRef`.
- **Revisions.** A later revision keeps `kind`, `childRunId`, `ownerScopeId`, `rootSessionId`, `depth`, `completion`, `inputRef`, `workspaceMode`, `workingDirectory` and `predecessorChildRunId`; `childSessionId`, `dispatchId` and `definition` are set-once, and `childSessionId` is required — not merely allowed — once the execution is `running_attached` or `settled`, since creation is then proven; the Session the child runs in is hosted by a Runtime binding, required with the `childSessionId`, and the `definition` pin is required no later than the dispatch; `resultVersion` never changes; `resultRef` and `terminalReceiptRef` may only appear, never change or disappear — a settled child never restates its result; `stopRequested` is set but never cleared. Once the run is terminal, nothing outside the run changes at all and the run itself may move only its delivery — so a stop request can never be added to terminal evidence, and the result refs are frozen by construction.
- **Resource closure.** `inputRef`, `resultRef` and `terminalReceiptRef` close over the parent Session's resources at commit time on both sides, as H3 pinned for `commandRef`/`startReceiptRef`/`outputRef`. At the same time both sides bind the tree to this journal: a first-level child's `rootSessionId` must equal this Session, per decision 8.

### `managed-child_acceptance`

Schema version 1. The chain is keyed by `childRunId` — one acceptance chain per child run. This record lives in the parent Session's journal; it projects no task.

| Key                     | Rule                                                                                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `childRunId`            | id: must name a `child_agent` `child_run` record of the same Session whose run ended with a result and whose `resultVersion` equals this record's             |
| `parentScopeId`         | id: must equal that child run's `ownerScopeId` — the dedupe key is Session plus scope plus run plus result version (automation §5)                            |
| `parentExecutionCallId` | null, or the parent tool call the result attaches to: required for `completion: "tool"`, null for `"sent"` — exactly the child run's `run.executionCallId`    |
| `resultVersion`         | count, exactly 1 in v1                                                                                                                                        |
| `contentRef`            | durable ref: the parent-held copy of the accepted result content                                                                                              |
| `contentDigest`         | digest: must equal `contentRef.digest`; binds the copy to the child's committed result; a redelivery naming the same record with a different digest conflicts |
| `terminalReceiptRef`    | durable ref: the parent-held copy of the child's terminal receipt                                                                                             |
| `run`                   | the run block                                                                                                                                                 |

- **Run.** The acceptance is purely logical (the recovery design: a parent acceptance creates no physical phase), so `executionCallId`, `effectId`, `dispatchId`, `deliveryId`, `runtime` and `execution` are permanently null. `delivery` is a `session`-target line.
- **Open settled, at accepted** (decision 9). The first revision opens `run.state = "settled"` with `delivery = "accepted"`; a later revision may only advance the delivery to `consumed` while the run stays settled, and the record then freezes. A first revision that shows `consumed`, and any later revision that touches anything but the delivery, is refused.
- **Consistency.** The commit-time checks on both sides enforce the cross-record rules above against the journal's rebuilt records: the referenced child run must exist as this Session's record, ended with a result, with matching scope and result version, and — for a `"tool"` completion — the same start call. A redelivery with the same identity but different content, or an acceptance of a run that ended `failed` or `cancelled` with no result, is refused with `409 managed_session_extension_record_rejected` on the Java side and the equivalent conflict on the authority side. The child run's delivery line is advanced by the separate commit of decision 4; the acceptance never waits for it.
- **Resource closure.** `contentRef` and `terminalReceiptRef` close over the parent Session's resources at commit time, as decision 6 requires.

### Task projection

`child_agent` produces a task of kind `child_agent` (an enum value the public contract already ships as `partial`, so H4a needs no OpenAPI change); its Runtime state mapping is the shared one, with `draining` applying as it did for Shell (a stop request with an unsettled execution). The body registry's task kind therefore stops being a constant of the `child_run` domain and becomes a function of the body's own `kind`: `shell → background_shell`, `child_agent → child_agent`. `child_acceptance` projects no task; its Java rows carry null task columns, as MCP records do since V23.

## Non-goals

- **Enablement.** Both domains stay disabled for submission; enabling them is H4b's server-first-ordered step.
- **Runtime paths.** No Harness loop, dispatcher, Broker, worker, route, OpenAPI or Flyway change. The task-list routes already enumerate `child_agent`; no `planned` route is mapped.
- **Child Session creation and lineage storage.** H4b designs the Java lineage columns (V48+), the internal creation route and the relay.
- **The completion mechanics.** How a `"tool"` acceptance settles the original tool call, and which completion mode ships first, are H4b's decisions; the bodies are neutral between the modes.
- **Close cascade and detach.** The cascade is a `stopRequested` plus the shared close order (H4b); detach to an independent durable owner stays follow-up work, as it did for H3's processes.
- **Workflow, peer messages, teams, public cancel.** Their slices are named under Slicing; their bodies do not exist yet.
- **Legacy migration.** Importing legacy subagent/team state as evidence is H4e's and the automation design §7's concern; nothing here migrates anything.

## Acceptance criteria

- In both languages, every malformed shape and every illegal transition in the fixtures is refused, and every valid case is accepted.
- The H3 shell fixtures replay unchanged except `kind-unknown`, repointed from `kind: "child_agent"` to `kind: "workflow"` so it stays an unknown-kind witness.
- The authority and the Java store commit and rebuild a `child_agent` chain and an acceptance chain ahead of enablement, and a `child_acceptance` row projects no task.
- Cross-tenant and missing-resource commits keep the store's existing answers; the consistency violations answer `409 managed_session_extension_record_rejected`.
- `child_run` and `child_acceptance` remain refused for submission; outside the new validators, the only behavior change is the workspace restore's detached-lineage enumeration skipping child agents with their own records instead of refusing the Session.
- Existing behavior is otherwise unchanged, including every H1/H2/H3 contract test and the zero-gap `contract-known-gaps.txt`.

## Open questions

1. **Which completion mode ships first in H4b.** `"sent"` rides the existing input-plus-wake bundling; `"tool"` needs an atomic acceptance-and-settlement path against the original call. The bodies are decided; the order is H4b's.
2. **Where the relay's delivery ledger lives once orphan retention lands** — a table of its own in V48+, or a reuse of an existing ledger; H4b, and it must not take the reserved `qwen_managed_session_task_event` name.
3. **The admitted `workspaceMode` values of the first runtime slice** — `shared` only, or `snapshot` with evidence; `worktree` needs a Runtime capability the Workspace stages have not delivered.
4. **Whether `depth` beyond 1 is admitted in the first runtime slice**; the contract cap is 8, and nested children (automation §8 A06) can land behind the same gate as the runtime's nesting support.
5. **The `unknown` delivery's operator story** — a delivery that never resolves is `recovery_blocked`-adjacent without being a run block; the cancel slice (H4f) decides how an operator closes one, with #12847 A7.
