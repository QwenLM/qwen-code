## 0. 目标

- 在普通会话里 @ Agent，它就在这个会话里流式回答；不建 thread，也不跳页面。
- 每个 Agent 是独立进程，跑在本机或远端；程序可以是 Qwen Code、Claude Code 或 Codex。
- Agent 之间能在会话里互相 @，文字和工具（`session_send`）两种方式都支持。
- 远端 Agent 的能力和本机一致：
  - 流式输出；
  - 工具审批；
  - 同样的状态：排队、进行中、等审批、超时、离线、失败。
- 已经在跑的 `qwen serve` 不用重启、不用多起进程，就能作为 runtime 加入另一个实例。
- 同一会话里多次 @ 同一个 Agent，会续接它的原生会话；不同会话之间互相独立。

## 1. 背景

旧设计把一次 @ 转到单独的协作 thread 里。这个 thread 是工单式的：有状态、优先级、验收和预算。系统会把最近几条消息拷贝过去当上下文，然后把用户带到 thread 页面。

远端 Host 当时也有很多限制：只能跑 Qwen，只读，所有审批一律拒绝，进度只回传折叠后的快照。

这和产品意图不符：协作就应该发生在用户正在进行的这个对话里。所以本设计改用会话原生的记录，加上一个按（会话, Agent）运作的编排器。

## 2. 不做什么

- 不做项目看板、工单或工作项状态机。
- 不把上下文拷到别处。Agent 通过已读位置直接读这个会话（§9.1）。
- 不自动审批。Agent 需要的每一次审批都交给用户（§3.3）。

## 3. 目标形态

### 3.1 分层

```
WebShell ──HTTP/SSE──▶ 协调端 qwen serve ◀──主动外连 HTTP── 远端 qwen serve（runtime / Host）
                         │ 编排器（按 会话×Agent）               │
                         │ 会话事件流、审批                      │
                     本机适配器                               本机适配器
               qwen（ACP）· claude（stdio）· codex（stdio）   qwen（ACP）· claude（stdio）· codex（stdio）
```

- **会话**：普通会话。参与者是用户、会话自带的 Qwen，以及被 @ 的 Agent。
- **绑定**：每个（会话, Agent）一条，记录原生会话 ID、这个原生会话所在的 runtime 和程序、已读位置、运行状态。
- **编排器**（在 daemon 里）：负责排队与合并、启动 run、发布实时事件和状态、转发审批、重启后恢复。
- **会话的 ACP 子进程**：会话记录的唯一写入者。它持久化 `agent_mention` 和 `agent_message` 记录，并把它们写进 Qwen 的模型历史。
- **投影器**（`transcript-replay`）：刷新、`/resume` 和导出时，把记录还原成带作者的 Agent 消息。

### 3.2 一次 @ 的完整链路

1. 用户发送 `@claude-b 看下这个 bug`。这条消息记为 `agent_mention`。如果只 @ 了 Agent，Qwen 这一轮不回答。
2. 对每个被 @ 的 Agent：空闲就起一个 run；忙就把这次 @ 合并进它唯一的那个排队 run。
3. 输入是这个 Agent 已读位置之后的会话内容（有预算上限），再加上触发它的那条消息。如果有原生会话 ID，就续接这个会话。
4. 本机 Agent 直接通过适配器执行。远端 Agent 的这一轮以租约形式交给它所在的 Host，由 Host 上的适配器执行，事件通过 HTTP 回传。
5. 编排器把事件发布到这个会话的事件流，内容包括作者、状态、步骤和 token 用量。前端把它显示为一条正在进行中、带作者的消息。
6. 结束时，编排器通过扩展方法 `qwen/control/session/external_record`，让会话的 ACP 子进程写入一条 `agent_message` 记录。这条记录会持久化，也会进入 Qwen 的历史，但不会触发 Qwen 回答。如果 Qwen 正在回答，就等它这一轮结束再写。
7. 如果回复里 @ 了别的 Agent，或者调用 `session_send` 时点了名，就回到第 2 步。是否继续受链路预算约束（§8-7）。

### 3.3 审批

Agent 发起的权限请求，会在会话里那条 Agent 消息上显示为审批卡片。它归属于这个 Agent 的 run，不挂在 Qwen 的回合上。用户的决定会回给本机适配器；如果是远端 run，就下发给 Host。

| 程序   | 怎么发起审批                                                                                                                                                                                 | 给用户的选项                                                                     |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Qwen   | ACP 权限请求。多个请求同时到达时，逐个交给用户。                                                                                                                                             | 允许、拒绝。不提供"一直允许"：隐藏会话固定在默认审批模式，这种授权不会生效。     |
| Claude | `--permission-prompt-tool stdio`。每个 `control_request` 的 `can_use_tool` 都会等用户决定。                                                                                                  | 允许、拒绝。预览显示的是实际会执行的输入：后台运行的标记在展示之前就已改为前台。 |
| Codex  | `codex app-server`，设置 `approvalPolicy: on-request` 和 `sandbox: read-only`，每次 `thread/resume` 都重新发送。写操作、需要离开只读 sandbox 的命令都会审批；只读命令在 sandbox 内直接执行。 | 允许、本对话内一直允许、拒绝。                                                   |

- 等待审批期间，暂停无响应超时。
- 停止时，未处理的请求和停止后才到的请求，都按"已取消"回复。
- daemon 重启导致挂起的审批丢失时，这个 run 标为失败，可以重试。

### 3.4 状态

每条 Agent 消息上显示它的状态：

- 排队（第几个）
- 进行中（实时步骤）
- 等待审批
- 超时
- 完成
- 失败（附原因）
- 离线（Host 租约过期）

实时状态不写进会话记录。刷新后，前端从编排器拉取当前快照。以下几种 run 可以重试或忽略：

- 失败的；
- 离线的；
- 回复没能写进会话记录的。

### 3.5 加入

| 场景         | 方式                                                                                                        |
| ------------ | ----------------------------------------------------------------------------------------------------------- |
| 远端已经在跑 | 在远端的 WebShell 点"加入协调端"，或运行 `qwen agents join <链接>`。两者都调用远端自己的 `/hosts/connect`。 |
| 远端还没跑   | 运行 `qwen serve --join <链接>`。                                                                           |

- runtime 相关的路由不依赖启动时的协作开关，只要求鉴权（§8-5）。
- 建立的连接会持久化，重启后自动重连。
- 加入后，Host 探测本机装了哪些 CLI。协调端为每个可用程序自动建一个 Agent，名字形如 `claude-机器名`（§8-4）。
- Host 协议 v2 的流程：
  - enroll、心跳、领取任务；
  - 按顺序回传事件批次；
  - 回传结果；
  - 长轮询拿审批决定。
- 租约 60 秒，以租约 ID 和尝试次数作为键。
- v1 Host 在心跳时就被拒绝，并提示升级。

## 4. 各层改动

### 4.1 core

- **会话记录**：新增子类型 `agent_mention` 和 `agent_message`，带作者、显示文本、状态、步骤、token 用量，以及相关的小队字段。这两种子类型不参与回合计数、标题生成、恢复裁剪和孤儿清理。
- **模型可见外壳**：给模型看的 Agent 消息外层包装。作用是：
  - 标明消息来源；
  - 转义标签；
  - 声明权限边界；
  - 截断过长内容。

  这部分文字上线前需要评测（§10）。

- **会话 Agent 存储**：每个会话一个绑定文件，另有一份"哪些会话有活跃 run"的索引。
- **`session_send` 工具**：Qwen 内置；Claude 和 Codex 以 stdio MCP 服务的形式注入。
- **Persona**：Qwen 会话 Agent 执行定义中的工具限制，写操作走审批（§8-1）。原生 Claude/Codex 无法执行 Qwen 的工具允许列表或禁止列表，因此关联了工具受限定义的 Agent 会在启动回合前被拒绝；这类定义应使用 Qwen。省略或留空 `tools`，以及没有禁止列表的 `tools: ['*']`，沿用原生 runtime 的工具。

### 4.2 acp-bridge 与 ACP 子进程

- **写记录**：扩展方法 `external_record` 写入记录但不起回合。Qwen 回合进行中时，写入会延后。
- **投影**：`transcript-replay` 把 Agent 记录投影成带作者的消息。它和实时流共用同一套段 ID（`agent:<runId>`、`mention:<recordUuid>`），所以刷新后不会出现重复消息。

### 4.3 daemon（`packages/cli/src/serve`）

- **编排器**：
  - 每个（会话, Agent）最多一个活跃 run，后续的 @ 合并；
  - 已读位置；
  - 只有 runtime 和程序都一致时，才续用原生会话；
  - 链路预算；
  - 重启恢复。
- **适配器**：`qwen-acp`、`claude-cli`、`codex-app-server`。远端 Host 上用的是同一套适配器。
- **路由**：
  - @；
  - 运行快照；
  - 停止和重试；
  - 小队；
  - Host v2；
  - 加入。

### 4.4 SDK

`qwenAgentMessage` 元数据和会话 Agent 相关视图的类型定义。

### 4.5 WebShell

- @ 之后直接在当前会话里发起，不跳转，也不拷贝上下文。
- Agent 消息显示作者、状态、步骤、token 用量和审批卡片。
- 会话级的"停止所有 Agent"按钮。
- 智能体页面分为 Agent、小队、Runtime 三个视图。

## 5. 风险

- **写所有权**：只有会话的 ACP 子进程能写记录。给没加载的会话写记录，得先把这个会话加载起来。
- **回合结构**：在 Qwen 回合进行中往历史里写，会破坏回合结构，所以这时的写入要延后。
- **Agent 输出进入 Qwen 历史**：会占用上下文预算，也带来提示注入的风险。这正是需要外壳、并且外壳需要评测的原因。
- **共用工作目录**：有写权限的本机 Agent 和会话共用同一个工作目录。审批能缓解这个问题，但不能消除。

## 6. 发布节奏

- **本 PR**：会话原生的协作。thread 后端保留但没有界面入口；A2A 仍走 thread。
- **过渡期限制**：Host v1 已被 v2 取代，所以派给远端 Agent 的 thread run，在 A2A 改为基于会话之前跑不了。这类请求 A2A 会返回 `unsupported`。
- **后续 PR**：删除 thread 后端，并把 A2A 改为基于会话：一个 A2A 任务对应会话里的一轮 Agent 回复，`contextId` 就是这个会话。

## 7. 验收

在两台真实机器上验证：

1. runtime 不重启就能加入，它上面的程序自动出现为 Agent。
2. 多个 Agent 在同一个会话里直接回答，Qwen 不插话。
3. Agent 之间能交接，文字 @ 和 `session_send` 两种方式都行。
4. 远端的写操作会弹出审批，用户的决定会被执行。
5. 刷新、`/resume`、导出之后 Agent 消息都还在；再次 @ 时，Agent 记得之前的内容。
6. 不同会话互相独立。
7. 停止和重试正常。
8. 离线后能恢复，重启后能恢复。

## 8. 决定（2026-10-05）

1. **工具权限**：会话 Agent 可以用全部工具，写入和执行类操作走会话内审批。
2. **接入方式**：Claude 和 Codex 走各自 CLI 的原生接口（§3.3）。
3. **一轮一个进程**：每一轮起一个新进程，靠原生会话 ID 续接。同一个原生会话绝不会同时有两个进程：每个（会话, Agent）最多一个正在执行的 run 加一个排队的 run，之后的 @ 都合并进排队的那个。
4. **自动建 Agent**：runtime 加入后，为每个可用程序自动建一个 Agent。
5. **加入不依赖启动开关**：作为 runtime 被加入，不依赖启动时的协作开关。
6. **附件**：@ 时附带附件，暂时拒绝。
7. **链路上限与预算**：
   - 链长上限是设置项 `experimental.agentChainLimit`，默认 0，即不限。
   - 防止失控循环靠的是会话 token 预算 `experimental.agentTokenBudget`：默认 1,000,000，设为 0 表示不限。用户发言后预算清零重计。
   - 没有上报 token 的回合，按 10,000 计入预算，所以拿不到用量数据的循环也会停下。
   - 每条 Agent 消息都显示 token 用量。
   - 只要有 Agent 在运行，"停止所有 Agent"按钮就可见。

## 9. 设计时补上的缺口

### 9.1 已读位置

已读位置锚定在会话记录的 ID 上。聊天压缩只改模型历史，不改记录，所以这个锚点是稳定的。

发给 Agent 的内容：

- 包括：用户文本、Qwen 的回复文本、其他 Agent 的消息；
- 不包括：工具调用的输入和输出；
- 超出预算时截断，保留开头和最近的部分。

原生会话无法续用时，已读位置会重置。例如换了 Host 或程序，或者续接被拒绝。

### 9.2 只 @ Agent 的消息

只 @ 了 Agent 的消息会被记录，但不会触发 Qwen 回合。只有同时也 @ 了 Qwen 时，Qwen 才回答。

### 9.3 远端 Claude / Codex 怎么用 `session_send`

MCP 服务跑在 Host 上，经本机回环地址上的中继转给 Host 的 daemon，再由 daemon 转发到协调端。超出记录写入上限的文本会直接在中继这一步被拒绝，这样模型就不会被告知"已发送"、而消息实际被丢弃。

### 9.4 审批协议探测

验收时已用真实 CLI 验证：

- Claude：会收到 `can_use_tool`，允许和拒绝都能生效。
- Codex：`on-request` 配合只读 sandbox 时，写操作会请求审批，用户的选择会被执行。

### 9.5 共用工作目录

见 §5。

## 11. 小队（2026-10-06）

小队由一个 leader Agent 和若干成员 Agent 组成，成员可以带一个角色。

- `@小队` 只唤醒 leader。
- leader 负责协调，自己不干活：用 @ 把工作分给成员，然后结束本轮。
- 每个成员回复后，leader 都会被再次唤醒，决定下一步或向用户汇报。

### 11.1 数据

- **存储**：`squads.json`，和 Agent 名册放在同一目录，用同一把锁。字段：`{id, name, description?, instructions?, leaderAgentId, members: [{agentId, role?}], createdAt, retiredAt?}`。
- **命名**：小队名和 Agent 名共用一个命名空间，规则相同。
- **成员**：只能是 Agent，本机或远端都可以，程序不限。

### 11.2 一次协作（engagement）

- **开始**：@ 小队会在这个会话里开启一次协作，并给 leader 排一轮，这一轮的输入带上小队简报。
- **成员 run**：被 leader @ 的成员，其 run 记为待完成。成员的 run 记录所属小队，所以它的回复会显示小队标记。
- **唤醒 leader**：每个成员回复都会唤醒 leader。
  - 同时到达的多次唤醒，合并成 leader 的一轮。
  - daemon 重启时还没发出的唤醒，会持久化，重启后恢复。
  - 重试某个成员时，它欠 leader 的那次唤醒会转给新的 run。
- **结束**：leader 结束一轮时没有再分派，并且没有待完成的成员 run，这次协作就结束。
- **并发**：一个会话可以同时有多次协作。
- **预算**：每次唤醒 leader 都算一跳，计入会话 token 预算。

### 11.3 leader 简报

简报放在 leader 每轮输入的开头，对所有程序都一样。内容包括：

- 小队名和指令；
- 成员名单，含角色、程序和机器，都做了转义；
- 协作守则：
  - 用 `@成员名` 分派；
  - 措辞简短；
  - 分派后结束本轮；
  - 无需动作时回复空内容。

这属于模型可见文本，需要评测。

### 11.4 无需动作

leader 的回复为空（只有空白或不可见字符）时，记录为 `squadOutcome: 'no_action'`，显示成一行灰色小字，而不是一个气泡。

### 11.5 界面

- 智能体页的"小队"视图：每个小队一张卡片，画出指挥链。leader 在上，成员挂在一条线上，角色在同一列对齐。支持新建、编辑和退役。
- @ 选择器里会列出小队。
- 对话里：
  - leader 和成员的回复都带小队标记；
  - 进行中的协作有一个状态条，每个参与者各一个状态。

### 11.6 与"任务验收"的关系

leader 本来就承担"确认目标是否达成、向用户汇报"的角色，所以不另外引入状态机。

### 11.7 A2A 与远端

- A2A 不暴露小队。
- leader 和成员都可以是远端 Agent，不需要改协议。

### 11.8 决定

1. 成员只能是 Agent。
2. 每个成员回复都唤醒 leader。
3. 无需动作时，leader 不发言，只显示那行灰字。
4. 一个会话里可以同时进行多次协作。
