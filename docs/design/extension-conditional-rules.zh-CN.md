# Extension 条件规则

[English](extension-conditional-rules.md) | [简体中文](extension-conditional-rules.zh-CN.md)

## 状态与问题

这是 #12030 的实现草案，属于 #12028。规则发现、迁移文档及按 extension
展示成本已经实现；完整运行验收仍未完成。
信任边界和仅允许条件规则的提案仍须维护者评审后才能合入。

已启用 extension 的上下文文件会拼接到常驻上下文中。将场景指引移出这些文件，
应复用现有路径触发规则，而不是另造记忆文件匹配器或截断指令。
现有上下文文件保持兼容；仅安装此改动不会自动缩小它们。

## 范围与决策

- 从每个已启用 extension 的实际根目录发现 `rules/**/*.md`，包括没有上下文文件
  的 extension。根目录取自 extension 元数据，不能从上下文文件的父目录推断。
- 沿用工作区 folder-trust 门控。不可信工作区不加载项目及 extension 规则；
  全局用户规则保持现有行为。
- 只接受非空 `paths:` 规则。无条件 extension 规则跳过，并在 debug 日志中点名。
  必须常驻的事实仍放在 extension 上下文文件中。
- 复用现有解析器、排除规则、glob 匹配、项目根目录语义、符号链接感知匹配及
  会话内单次消费机制。模式匹配工作区文件，不匹配 extension 安装目录。
- 保持当前跳过规则发现的 safe 与 bare 模式。启动和记忆刷新走同一发现路径。
  刷新后已禁用 extension 不得贡献新规则；已经注入的历史对话文本不追溯删除。
- 同步提供项目 rules 文档和 extension 迁移文档。#12119 之后，在
  `/context detail` 按 extension 汇总记忆成本；不要只为附加展示元数据而改动提示词。

绝对告警阈值属于 #12029，预存 workflow 仍由 #11631 跟进。
本改动不能把这两项默认为已经完成。

## 实现路径

生产 core 调用方是 `Config.refreshHierarchicalMemory`，它调用
`loadServerHierarchicalMemory`。AppContainer 手动刷新另行调用 CLI 包装器；
添加目录后的刷新直接调用 core 加载器。三个入口都填入已启用 extension 根目录
及 bare 模式选项，CLI 包装器转发同一组 options。
通过记忆加载 options 将已启用 extension 根目录传给 `loadRules`。
不能只新增参数却不在生产调用方赋值。完成实现前检查 extension 启用、禁用和刷新
的消费者。激活逻辑复用 `ConditionalRulesRegistry`。

## 验证与验收

### 归因实现

在现有记忆组装步骤中保留来源元数据，与实际附加的准确文本配对，不为报表重新读取磁盘。使用 extension 顶层上下文文件身份确定归属，不使用显示路径。导入内容归属于内联它的顶层贡献者；重复内联确实产生重复内容，不能按源路径去重。

元数据须与对应记忆快照同步。通用记忆替换必须使旧归因失效；启动、手动刷新和目录添加后的刷新须填入相同元数据。SDK 直接传入且没有来源的记忆保持未知。不从嵌套或伪造的 prompt 标记推断归属。

按确认的 extension 聚合现有 memory 明细行，替换原行，而不是新增内容分类。文本、Ink、OpenTUI、ACP 与 Web Shell 复用 `{path, tokens}`，保持 memory 小计不变。已激活条件规则仍属于历史内容，不重复计入常驻记忆。聚合告警触发时，从同一快照指出最大的已确认 extension 贡献者。告警估算与明细包含的包装不同，不能声称数值严格相等或等于 provider 账单。

测试已覆盖 imports、重复内联、链接根目录、元数据失效、未知内容和小计守恒。整个工作项仍须完成运行验收。

#### 具体归因数据流

加载器在 `memoryContent` 之外返回来源记录：每个实际附加的顶层文件保留绝对路径、处理导入并 trim 后的正文，以及可选的已确认 extension 名称。导入保留在该正文内。常驻 rules 使用独立的无归属记录；条件规则不进入此列表。保持实际 prompt 的包装、分隔符及内容逐字节不变。

文件来源的正文包含结束包装之前已有的换行，沿用旧明细估算口径。独立 rules 记录不伪造文件路径，正文就是实际组装的常驻规则块。

三个调用入口通过现有 options 传入启用 extension 的名称和声明的上下文文件路径。归属按 canonical 文件身份匹配，与显示路径格式化分开。同一文件被多个 extension 声明，或无法解析真实身份时，保持无归属。output-language 文件不能因为与 extension 路径共用一个输入列表就被归给 extension，也不能用目录包含关系推断归属。

`setUserMemory` 接收配对的可选来源；未传来源时清除旧记录。保存防御性快照，避免加载结果后续被修改而改变归属。SDK 构造时直接提供的正文仍无归属。不新增序列化或会话记录格式：恢复会话沿用既有上下文发现路径。

已知来源的 `/context` 明细直接使用记录的正文，不解析嵌套标记；未知正文保守显示为无归属内容。沿用统计算法先缩放各行，再聚合同一已确认 extension，保证聚合前后明细之和严格不变，包括取整影响。显示名称须清理控制字符；不能把同名的普通文件行和 extension 标签行混为一组。

小计守恒指同一来源快照聚合前后的对比，不是保留旧 parser 的漏算：存在 context-file 标记时，旧 parser 会遗漏常驻 rules；嵌套标记也可能提前截断正文。测试必须区分补齐统计覆盖与聚合展示，两者都不是输入 token 节省。

当前工作树早于 #12119。已在独立 worktree 针对其准确的 `7e7b0bd0` head 做组合验证：在该 PR 现有明细缩放之后聚合，41 项 context command 测试全部通过，其中包含缩放后聚合／未聚合小计一致的对照。合并分支时不能另造归一化算法。该组合 worktree 的整仓 build 不能算通过证据：0.24.0 源码复用了当前 checkout 的 0.24.1 依赖，browser-use declaration 在到达本改动前即因版本不匹配失败。绝对告警阈值仍归 #12029；这里只添加贡献者名称，不改变阈值或截断记忆。

### 已有规则发现的验收

1. 改动前基线：已发布版本不会发现 extension 内的规则，以可匹配的项目规则作为正向对照。
2. 已启用且可信的 extension：匹配文件操作后只注入一次；不相关路径不触发。
   初始提示词中没有规则正文。
3. 禁用 extension、不可信工作区、safe 模式及 bare 模式均不加载 extension 规则。
   刷新遵循当前启用集合。
4. 缺失或空 `paths:`、格式错误的 frontmatter、空文件、排除项、嵌套规则目录和
   符号链接路径边界遵循已记录的解析与信任行为。无条件 extension 规则不能变成
   常驻规则。
5. 没有上下文文件的 extension 也可工作；全局和项目规则的顺序与行为保持不变。
   Extension 发现顺序确定。
6. 迁移示例保留始终需要的事实，仅迁移场景指引。在固定配置下，对比迁移前后
   实际组装的请求内容，覆盖激活前与激活后。
7. 完成之前通过构建、类型检查、定向测试、运行或脚本验证及两轮无新增问题的
   完整 diff 自审。Provider token 收益和任务质量须另行控制变量验证；字符差值
   不是 token 数。

## 风险与待确认项

条件指令只有匹配文件操作后才到达，不能替代操作前就需要的规则。
加载的文本可能留在对话历史中，后续仍有输入 token 成本。
刷新可能按现有 registry 生命周期重置消费状态，须显式测试，不能承诺更强的去重。
确认支持的 manifest 格式和链接安装的实际根目录处理。
未检查这些消费者前，不引入新的 manifest 功能。

现有工具调度器在配置了 execution environment 时会跳过本地路径激活。
保持该边界：本改动不承诺远程文件系统规则激活，迁移文档必须说明此限制。
