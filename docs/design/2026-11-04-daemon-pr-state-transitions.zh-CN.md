# 由 daemon PR 刷新产生 PR 状态转换事件

[English](2026-11-04-daemon-pr-state-transitions.md) | [简体中文](2026-11-04-daemon-pr-state-transitions.zh-CN.md)

状态：提案（2026-11-04）。实现后取代 [GitHub Channel 事件投递到 PR 绑定会话](2026-11-02-github-channel-bound-session-events.zh-CN.md) 中"PR 状态监视"的部分；该设计的评论投递部分不变。

## 问题

daemon 对每个会话绑定的 PR 状态跟踪了两遍，用两套凭据、两套调度，以及两种"CI 失败"的定义：

1. `packages/cli/src/serve/server/session-pr-refresh.ts` 已经每 5 分钟（`QWEN_SESSION_PR_REFRESH_MINUTES`）扫一遍每个受信 workspace 的 PR sidecar，用 daemon 宿主的 `gh` 凭据跑 `gh pr list`，重写每个 sidecar 的 `state`（open / merged / closed）和关闭的 issue。Web Shell 侧栏读取结果。不会向会话投递任何东西。
2. GitHub channel 的 PR 状态监视（`packages/channels/github/src/GithubAdapter.ts` 里的 `runPrStateWatch`）每次 channel 轮询（默认 60 秒）用 channel 自己的 token 经 Octokit 轮询每个绑定 PR：每个 PR 一次 `pulls.get`，加上按条件调度的 `checks.listForRef` 与合并状态，上限 30 个 PR，带自己的 `github-pr-watch.json` 状态文件、pending 队列、fired 环、死信和 reconcile 规则。它检测 `ci_failure`、`merge_conflict`、`head_change`、`state_change`，并通过 daemon 的 prompt 路由投递到绑定会话。

第二个轮询器只在运维者配置了带 `deliverToBoundSessions` 与 `prWatchEvents` 的 GitHub channel 时才存在。没有这样的 channel 的会话永远听不到自己的 PR CI 变红。两者同时运行时，同一个 PR 被抓取两次；channel 的 CI 聚合排除 `cancelled` / `stale`，而 core 的 rollup（`packages/core/src/utils/github-prs.ts` 的 `aggregateChecks`）把它们算进去；channel 在上限处的 API 预算约为每小时 1,800 次 `pulls.get` 加有界复查，而刷新是每 workspace 每小时 12 次 `gh pr list`。

## 现状

- sidecar 结构（`packages/core/src/services/session-pr-service.ts` 的 `SessionPr`）：`number`、`url`、`createdAt`、`state?`、`source?`、`role?`、`issues?`。不持久化 head SHA、CI rollup 或可合并性，所以刷新看不到任何转换。
- 刷新的 GitHub 路径以 **slim** 模式（`number,url,headRefName,state`）跑 `gh pr list --state all --limit 500`，因为 CI rollup 字段会让大的 `--state all` 查询撞上 GitHub GraphQL 服务端超时（504）。非 slim 的 `GH_PR_LIST_FIELDS` 已含 `statusCheckRollup`、`isDraft`、`reviewDecision`、`updatedAt`，但没有 `headRefOid` 或 `mergeable`；rollup 归约函数 `aggregateChecks` 是模块私有的。
- daemon 已经会向自己不握键盘的会话注入 prompt：channel 的绑定中继（带 `qwen.channel.prompt` / `qwen.daemon.channelBoundRelay` 标记与 `idempotencyKey` 的 `POST /session/:id/prompt`），并经 `/session/:id/resume` 路径恢复休眠会话。今天两者都不是进程内调用：中继运行在 channel worker 进程中，经 HTTP 访问 daemon；prompt 准入——幂等环（`promptIdempotencyBySession`）、worker 凭据分类、绑定中继与显示文本标记、以及对 channel prompt 跳过 PR 绑定回填——都内联在路由处理函数里（`packages/cli/src/serve/routes/session.ts`）。`qwen.channel.prompt` 只沿一条受信链生效：路由只接受持有 channel worker 凭据的调用方带上它，bridge（`packages/acp-bridge/src/session-control-plane.ts`）只从受信 context（`context.channelPrompt`）重新装配它，会话子进程（`packages/cli/src/acp-integration/acpAgent.ts`）只为受信的私有父进程重新装配它；`Session.ts` 读它来让该回合免于循环检测拒绝。bridge 只在 channel 自有会话中为回合保留显示文本（`getChannelPromptDisplayText`），绑定中继也不发送显示文本，因此中继的事件在绑定会话的 transcript 中按原样显示。
- channel 监视面向用户的语义记录在 `docs/users/features/channels/github.md`，于 2026-11-03 合入（#16117）并随 v0.26.7（2026-11-04）发布，发布说明点名了该功能；`prWatchEvents` 因此是已发布、运维者可配置的设置。自 #16258（2026-11-04 合入，随 v0.26.8 于 2026-11-05 发布，发布说明点名了这些模板以及编辑它们的 channel 编辑器）起，配置了 `boundSessionActions` 的 channel 按绑定角色路由监视事件——`review`、`verify`、`fix` 或无类型，每个角色一个赢家，各自带一条由 `watch:<type>` 键选出的运维者指令模板；没有该映射时仍是单一的最近赢家。

## 目标

- PR 状态只有一个来源：daemon 刷新。它在已刷新的 state 之外同时观察 head、CI 与可合并性，并把四种转换投递到跟随该 PR 的会话。
- 接收 PR 状态事件不需要 GitHub channel；channel 继续投递 GitHub 的*会话类*事件（评论、评审请求、指派）。
- 不新增轮询循环。唯一新增的状态是每个绑定 PR 一个由 daemon 持有的小监视文件，它既是快照也是持久队列（关键决策 4）；会话 sidecar 不变。
- 移除适配器的 PR 状态监视及其配置。

## 非目标

- webhook 推送接入（仍是未来工作）。
- Aone 合并请求：刷新的 Aone 路径继续只刷新 `state`；Aone 的转换可以之后按同样形状补上。
- 评论事件：仍留在 GitHub channel 的通知车道及其绑定会话投递中。
- 新事件类型（`review_decision` 已经在抓取，列为下面的开放问题，不属于本次改动）。

## 设计

### 1. 观察

刷新保留用于 `state` 的 slim `--state all` 列表，并对绑定扫描所枚举的该 workspace 会话中的每个绑定 PR 增加一次 `gh pr view <url> --json url,title,headRefOid,mergeable,state,statusCheckRollup`，merged 的 PR 以及本次扫描 slim 列表返回了的 closed PR 除外；因此不会为隐藏目录会话、以及 transcript 已归档的 sidecar 做 view，而只存在于 bridge 内存中的绑定在其 sidecar 写入后才被 view。merged 按该 PR 的最新观察判定为终态（其监视文件的 `state`，§2；尚无文件时看顶层 `state`）。closed 不是终态，因为 closed 的 PR 可以重新打开：列表返回的 closed PR 由列表观察；列表没有返回的 closed PR——不受信 primary 的全部 PR（它没有列表）、指向别的仓库的绑定（永远不在本仓库的列表里）、超出列表 500 个上限的 PR——排在 open PR 之后留在 view 旋转中，因此重新打开总能被看到。

view 按绑定的 URL 执行，绝不在 checkout 内按编号执行：`gh` 会把裸编号解析到该 workspace 自己的仓库，而绑定可以指向别的仓库——扫描已经把这类绑定当作外来绑定处理：`updateSessionPrStates` 只把列表中的状态写进规范 URL 一致的条目，`isForeign` 让它们不参与关闭 issue 查询，并让 merged 的外来绑定不经该查询直接收敛。只有 view 返回的 PR 与绑定的 host 和编号相同时才被采用，两个 URL 都按刷新的 `pullRequestKey` 的方式规范化（host 转小写、去掉 `www.` 并舍弃端口；忽略编号之后的任何路径（如 `/files`）以及 `.diff` 或 `.patch` 后缀），因此绑定路径容许的写法与 `gh` 返回的规范 URL 匹配；与 `pullRequestKey` 自身的 `host/owner/repo` 键不同，这里刻意不比较 `owner/repo`。host 与编号相同而 `owner/repo` 不同，表示仓库被改名或转移、GitHub 从旧名解析过去：该 view 被采用，每个 PR 记一次日志。host 或编号不同则记日志并丢弃。监视文件始终以绑定自身的身份——绑定 URL 的 `pullRequestKey`——为键，因此改名对已有绑定没有任何影响：其文件、绑定者、`lastBoundAt` 与收件者都与之前一样找到。同时以仓库旧名与新名被绑定的 PR 按每个名字各监视一次，其每个转换按每个名字各投递一次；这是明确的边界。view 只发往 GitHub host：`github.com`、daemon 的 `gh` 配置中已列出的 host，以及本 daemon 承载的每个 GitHub channel 的 web host，像 `pullRequestKey` 那样转小写并去掉 `www.` 后比较。其它 host 上的绑定在任何 `gh` 调用之前就记一行日志跳过，因此绑定 URL——或 `origin` 根本不是 GitHub 的 workspace——无法让 `gh` 把 daemon 的企业版凭据（`GH_ENTERPRISE_TOKEN`）出示给任意 host。view 使用被扫描 workspace 的环境（`runtime.env.effectiveEnv`），与其列表相同，因此 workspace 自己的 `GH_TOKEN` 或 `GH_CONFIG_DIR` 作用于它的 PR；不受信 primary 的 view 使用 daemon 自己的环境。view 的工作目录是 daemon 私有的监视目录（§2，权限 0700），绝不是 `os.tmpdir()` 这类共享目录，因为 `gh` 的解析（`resolveGhBinary`）会把 `PATH` 中相对或空的条目按子进程的工作目录解析。

每次 workspace 扫描的 view 上限 30 个，使用与 Aone 路径 `sweepStart` 同形的旋转窗口；GitHub 路径报告自己消费的数量，定时器为它按 workspace 推进一个 GitHub 偏移（今天只有 Aone 路径报告）。窗口在一次扫描内与 Aone 的一样会回绕：对 40 个 open 绑定 PR 的两次连续扫描观察到全部 40 个——第二个窗口从第 31 个 PR 开始，回绕到集合头部，重复了第一次扫描的 20 次 view——超过 30 个的 workspace 在没有截止时间截断窗口、且集合期间不变时，于 ⌈n/30⌉ 次扫描内观察到每一个。重复的 view 仍在上限之内，并让这些 PR 更新鲜，这就是不把窗口改成不回绕的原因。

view 受一个 tick 级截止时间约束，而不是 Aone 循环按 workspace 的 `AONE_SWEEP_VIEW_BUDGET_MS`。定时器在一个 `running` 保护后面顺序遍历 workspace，W 个 workspace 各花满 60 秒预算再加一次在飞的 10 秒 view，会把一个 tick 拉长到 70·W 秒——W = 5 起就超过 5 分钟间隔——保护随即让所有 workspace 跳过下一个 tick。因此定时器在 tick 开始时算出一个截止时间（半个刷新间隔之后），交给该 tick 的每个 workspace 扫描。过了截止时间，扫描不再发起新的 view（在飞的一次仍可能跑满自己的 `GH_TIMEOUT_MS`）；休眠会话的恢复根本不在 tick 上运行（§4）；旋转按实际发起的 view 数推进；tick 遍历 workspace 的顺序逐 tick 轮转，持续超时不会饿死任何 workspace。单个 PR 的 view 或投递失败被隔离，扫描其余部分照常进行。截止时间只约束本设计新增的工作：slim 列表与关闭 issue 的查询保留各自的单次调用超时，Aone 循环保留其按 workspace 的预算，因此间隔很短时多个慢 workspace 仍可能让 tick 超时，与今天一样。

绑定在多个 workspace 的 PR 每个 tick 只 view 一次：同一 tick 内后来的扫描在该 PR 监视文件的观察时间不早于本 tick 开始时刻时跳过 view；下一个 tick 再次 view，被跳过的 view 不计入上限。单个 PR 的 view 不会撞上批量 rollup 的超时。slim 列表观察到 merged 或 closed 的 PR 时，这次观察同样更新监视文件（其 `state` 与 `observedAt`），与一次 view 完全一样；返回 `merged` 或 `closed` 的 view 也同样计。

定时器像今天一样扫描受信 workspace，另外在 primary workspace 不受信时也扫描它：绑定扫描不经信任门控就覆盖 primary，channel 今天也向其会话投递。由于 view 在 checkout 之外执行，不会有 `gh` 调用在不受信的 checkout 内运行；它的 slim 列表、关闭 issue 查询、origin 解析与 Aone 路径都被跳过，因此不会有 `git`、`gh` 或 `a1` 进程在该 checkout 内运行，其 PR 只经 view 观察。没有生效的事件集合时（`sessionPrWatch.events` 未设置且无别名，§7），完全不跑 `gh pr view`，刷新不变（验收标准 4）。

`mergeable` 映射为 `MERGEABLE → mergeable`、`CONFLICTING → conflicting`、`UNKNOWN → undefined`（GitHub 仍在计算；绝不覆盖上次已知值）。不覆盖是文件写入时的合并规则而非映射器的规则：一次 `UNKNOWN` 观察保留已存的 `mergeable` 且不产生转换。CI 使用 core 已有的 `aggregateChecks` rollup（`passing` / `failing` / `pending` / `none`），为此将其导出：侧栏与事件共用一个定义。

### 2. 按 PR 的监视状态

监视状态属于 PR，而不属于跟随它的某个会话，因此它在每个 PR 一个、由 daemon 持有的监视文件中只存一份——`<global qwen dir>/serve/pr-watch/<first 40 hex of sha256 of host/owner/repo#number>.json`（即绑定自身的身份，§1）——而不放在会话 sidecar 中；sidecar 照旧保留供侧栏使用的 `state` 与 `issues`。每个 PR 一个文件、而不是每个绑定者一份副本，意味着每个 PR 恰好只有一个基线、一个队列和一份已投递记录，无论有多少会话绑定它、本 tick 它们的哪些 workspace 可达、受信或已退役：没有副本会落后，因此永远不需要从陈旧副本采用、合并或重新检测任何东西。监视目录由一个 daemon 持有，以 0700 权限创建，因为多个 daemon 可以共用一个 global qwen dir，甚至同一个 workspace（`docs/design/2026-09-02-relaxed-standalone-daemon-ownership.md`）。所有权是一条 owner 记录 `pr-watch/owner.pid`，其写入与检查方式与 channel 服务 pidfile 完全相同（`packages/cli/src/commands/channel/pidfile.ts`，推广为由调用方指定路径）：在该模块的锁下以独占创建（`wx`）写入，携带 owner 的 pid、进程启动令牌与 PID 命名空间。能证明其进程在本次启动、本 PID 命名空间内已不存在的记录会被清扫并替换；本机无法核验的记录——写于重启机器之前、由另一台机器或共用该 home 的另一个 PID 命名空间写入——会被保留，并在被手动删除之前阻止认领，每次尝试都记一行点名该文件的日志，与 channel 服务今天的行为相同；在没有进程启动令牌的平台（macOS）上，pid 被复用的记录视为存活，channel 服务亦然。生效事件集合（§7）非空且刷新定时器在运行的 daemon 在定时器启动时以及每个 tick 尝试认领，因此 owner 退出后所有权会转给仍在运行的 daemon；事件集合为空或没有刷新定时器（间隔为 `0`，或不启动定时器的 `hosted-harness` profile）的 daemon 从不认领；运行多个已配置的 daemon 时，先认领者生效，其余记录一条日志说明采用它的集合。没有持有该记录的 daemon 不运行 PR 监视——不 view、不写入、不排空、不删除任何东西，包括 slim 列表对监视文件的 `state` 写入——其状态刷新与今天相同，因此只绑定在 owner 未注册的 workspace 中的会话收不到 PR 状态事件。daemon 在解析到同一个运行时根目录时共享会话，而 `QWEN_RUNTIME_DIR` 或 workspace 的 `advanced.runtimeOutputDir` 可以把它放到 global qwen dir 之外（`packages/cli/src/serve/run-qwen-serve.ts` 中的 `resolveSessionRuntimeBaseDir`）；global qwen dir 不同、却共用一个运行时根目录的两个 daemon 会各自持有一个监视、各自投递，因此 PR 监视不支持这种配置，这样的 daemon 至多一个设置 `sessionPrWatch`。关闭时 owner 先停止其 PR 监视——定时器、排空，以及每个进行中的恢复与准入——再删除其记录，因此后继者绝不会与它重叠；PR A 为此调整 serve 生命周期的关闭顺序（`packages/cli/src/serve/serve-app-lifecycle.ts`）。由于只有一个写入方，owner 的进程内锁对每个文件都是权威的。对监视文件的每一次改动——检测、slim 列表的 `state` 写入、`lastBoundAt` 刷新、删除以及每个排空步骤（§5）——都在 owner 对该 PR 的进程内锁的同一次持有之内读取文件并写入或删除它，该锁即以文件为键的 `PathMutexRegistry`（`packages/cli/src/serve/fs/path-mutex-registry.ts`），因此任何写入都不会写回在另一次写入之前读到的内容；存储的读写函数自身不取锁，因为 `runExclusive` 不可重入。在 POSIX 上，daemon 只有在其有效 uid 拥有监视目录及其中每个监视文件时才认领监视；以其他用户（包括 root）运行、或发现某个监视文件属于另一个 uid 的 daemon 记一行点名该目录或文件的日志且不认领，与无法核验的记录相同。由于非 owner 不写入任何东西，每个监视文件都由 owner 的 uid 创建和替换，这使 core 的 `atomicWriteFile`（`packages/core/src/utils/atomicFileWrite.ts`）对属于另一个 uid 的文件所走的原地写入路径无法到达——在那条路径上写入会失败或写坏文件；认领之后由另一个 uid 放入的监视文件（只有 PR 监视之外的进程才能做到）按读取错误处理（见下）：跳过其 PR，并记一行点名该文件的日志。因此每次写入都是在目标旁写临时文件再改名覆盖，被中断或失败的写入会保留原文件不变：

```ts
interface PrWatchState {
  /** 绑定的身份：从 `pullRequestKey` 的 `host/owner/repo` 键拆出的 host 与 `owner/repo`，以及编号。 */
  pr: { host: string; repo: string; number: number };
  /** 扫描最后一次列出该 PR 的绑定者、或保留行最后一次提到它的时间（§4）：删除所用的时钟，跨重启保留。 */
  lastBoundAt?: string;
  /** 观察版本：最后一次更新该文件的那次观察的时间——一次 `gh pr view`，或 merged / closed PR 的 slim 列表。 */
  observedAt?: string;
  state?: 'open' | 'merged' | 'closed';
  /** 最后一次 view 时的标题，用于 prompt 的身份行。 */
  title?: string;
  headSha?: string;
  checks?: 'passing' | 'failing' | 'pending' | 'none';
  mergeable?: 'mergeable' | 'conflicting';
  /** 已触发过 ci_failure 的 head，最旧在前（上限 16）。 */
  ciFired?: string[];
  /** 已准入的 key——启用角色化动作时为加组后缀的 key——最旧在前（上限 64）。 */
  delivered?: string[];
  /** 已检测但尚未投递的转换，最旧在前（上限 16）；`served` 列出已准入的角色组。 */
  pending?: Array<{
    type: PrTransitionType;
    key: string;
    summary: string;
    detectedAt: string;
    served?: Array<'review' | 'verify' | 'fix' | 'untyped'>;
  }>;
}
```

没有文件的 PR——其首次观察、本次改动发布后的每个绑定 PR，或文件被删除后再次被绑定的 PR——由下一次观察静默初始化：即使其 CI 已经失败，也不触发任何东西。由 slim 列表创建的文件只有 `state` 与 `observedAt`；它同样静默初始化，因此重新打开后的第一次 view 填入 `headSha`、`checks` 与 `mergeable`，不触发 `head_change`、`ci_failure` 或 `merge_conflict`。文件一旦有了 `headSha`，其从未知晓的 `mergeable` 视为非冲突，因此在最初几次 view 返回 `UNKNOWN` 之后首次出现的 `conflicting` 会触发 `merge_conflict`，与 channel 的 `undefined → dirty` 相同。不存在的文件、或内容无法解析或校验不通过的文件，视为不存在——该 PR 静默初始化，无效文件记一行日志——绝不会因此去动任何 sidecar。其它读取错误（`EACCES`、`EMFILE`、`EIO`）一律拒绝继续，与适配器今天的 `loadPrWatchState` 相同：该 PR 本 tick 被跳过——不检测、不执行排空步骤、不删除、不做记录写入，已准入的 key 保留其内存标记——下个 tick 重试，因此完好的文件绝不会在一次读取失败后被覆盖。

owner 在一次完整扫描（无 `partial`，§4）发现某 PR 没有任何绑定者时删除其文件，否则在距其 `lastBoundAt` 满 7 天时删除——与 pending 年龄上限（§5）的期限相同，因此不会丢掉年龄上限本会保留的条目；其中未投递的条目丢弃并记日志，因为已没有会话跟随该 PR。此后再被绑定的 PR 静默初始化，与 channel 对停止监视过的 PR 重新建立基线相同。在文件删除之前再被绑定的 PR 从其最后一次观察继续，因此间隔期内的转换会投递给新的绑定者一次。写入中途崩溃遗留的临时文件在下一个 daemon 取得所有权时被删除，因此文件数量以最近 7 天内被绑定过的 PR 为界。

### 3. 转换规则

沿用 channel 监视的转换规则，迁移过来的运维者看到相同的转换，只有一处刻意的 CI 判定差异（关键决策 5、开放问题 2：core 的 rollup 把 `cancelled` / `stale` 算作失败，channel 的聚合排除了它们）：

| 事件             | 触发条件                                                                                                                                                                                                                         |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `head_change`    | `headSha` 与上次观察不同（force-push 回到最近的 SHA 是新的转换）。                                                                                                                                                               |
| `ci_failure`     | `checks` 为 `failing`、同一 head 的上一次观察不是（head 变化会重置比较，与 channel 的逐 head 重置相同），且 `headSha` 不在 `ciFired` 中；随后追加进去，因此即使 CI 反复、或 force-push 回到更早的 head，每个 head 也只触发一次。 |
| `merge_conflict` | `mergeable` 从非冲突或尚未知晓的值变为 `conflicting`（边沿触发；`conflicting → mergeable → conflicting` 会再次触发）。                                                                                                           |
| `state_change`   | `state` 离开 `open`（merged 或 closed）。重新打开会让 `state` 回到 `open`，之后再关闭会再次触发。                                                                                                                                |

每个转换的 key 为 `pr-state:<owner/repo>#<number>:<type>:<headSha or previous→next>:<detectedAt>`；`detectedAt` 让文件删除后检测到的实例彼此不同，而 `ci_failure` 通过 `ciFired` 保持每个 head 一次。`ciFired` 是 daemon 侧与 channel 持久化 `fired` 环等价的东西：有界的逐 head 历史，因此 force-push 回到 `A` 之后的 `A failing → B failing → A failing` 不会为 `A` 再触发一次。上限刻意不同：channel 每个 PR 保留 4 类事件共用的 64 个 key，被挤出后只钉住当前 head；daemon 每个 PR 保留最近 16 个失败过的 head，一个 head 在超过 16 个其它失败 head 之后再被回访会再次触发，与 channel 被挤出后的行为一致。启用角色化动作时（§4），每个角色组的准入使用加了 `:<group>` 后缀的 key。超过 prompt 路由 200 字符 `idempotencyKey` 上限的 key 确定性地哈希为 `pr-state:h:<first 40 hex of sha256>`（channel 的形状），重试仍能去重（很长的 `owner/repo` 配上双 SHA 的 `previous→next` 形式在加后缀之前就可达 275 字符）。

### 4. 投递

- **检测。** 扫描把新鲜 view——或 merged / closed PR 的 slim 列表状态——与该 PR 的监视文件比较，并在该 PR 的锁下以一次原子写入写入新观察、更新后的 `ciFired` 与检测到的转换。每次观察都带有其开始时间，开始时间早于文件 `observedAt` 的观察直接丢弃——既不比较也不写入——因此慢的 view 绝不会让基线倒退。由于该文件是唯一的基线，观察可以仍按 workspace 进行，而检测与投递以 PR 为范围：本 tick 所在 workspace 不可达、不受信或已退役的绑定者不持有任何可能落后、或会把一个转换检测第二次的副本；它重新可达时只是重新成为收件者候选。
- **目标。** 整个 daemon 范围内每个 PR 只有一个收件会话——启用下文的角色化动作时每个角色组一个——绝不是每个 workspace 一个。收件者在投递时才惰性决定，且只针对尚未准入的 key（§5）：在绑定扫描覆盖的 workspace（受信 workspace 与 primary）中绑定该 PR 的合格会话里取最近活跃的那个（transcript mtime，再以 bridge 的 live 活动修正），即 channel 的传统规则，经该会话所属的 runtime 派发。扫描不完整时，排空为本次扫描未列出的每个会话保留最近一次列出它的扫描中的行——无论那次扫描完整与否，与适配器从每次快照重建其保留绑定相同——规模与适配器的保留上限相同（`MAX_PARTIAL_RETAINED`，最旧的先丢弃），一次完整扫描不再列出该会话时丢弃其保留行，因此暂时不可达的较新绑定者仍按最近活跃程度参与竞争——适配器出于同样的原因保留未列出的会话，使只列出较旧会话的不完整答案无法取代较新的那个——这样保留下来的会话胜出时，条目留在 pending 直到它可达。启用角色化动作时，这一规则在每个角色组内适用。检测与排空之间被归档或被别的会话超过的收件者不会丢任何东西：排空解析出下一个。归档会话、channel 自有会话（`sourceType: 'channel'`）与机器自有的隐藏目录会话（`isHiddenCatalogSource`：`agent-host`、`agent`）永远不是目标；不再注册、不再被扫描覆盖（不受信且非 primary）或 runtime 代际已退役（`assertGenerationOpen()`）的 workspace 记一行日志跳过，并在派发前立即重新解析。因此同一仓库注册了两个 workspace、各有一个会话跟随同一个 PR 时，无论中间是否崩溃，都只投递一次而非两次。
- **自推的 head。** `head_change` 只凭 head SHA 检测：GitHub 的 PR 对象不给出推送者，而按账号判「自己的 push」无法区分用同一个 git 身份推送的两个会话——那会抑制所有 push，而不只是收件者自己的。因此抑制按收件者进行，且只针对 `head_change`：自己的已推 head 账本里含有新 head 的候选，在这次转换中被排除，排空重新解析下一个绑定者——启用角色化动作时在其角色组内，未启用时替代那个单一赢家——而「没有剩余候选」的既有规则决定是在完整扫描时记一行日志丢弃，还是在不完整扫描时等待。`ci_failure`、`merge_conflict` 与 `state_change` 绝不因作者身份被抑制：自推的 head 上 CI 变红正是 fix 会话需要的信号。账本是这个 PR 的 autofix-pr 监视状态（`.qwen/tmp/autofix-pr-<n>-state.json`）里的 `pushedShas`，落在 helper 为既有 watch 解析出的根下，而不是绑定的 `workspaceCwd` 所指的已注册 workspace 根：`push` 经 `resolveWatchRoot()` = `findWatchRoot() ?? watchRoot()` 写入（`packages/cli/src/commands/autofix-pr/state.ts`、`push.ts`），因此账本位于准备该 watch 的那个链接 worktree，会话 cwd 之后移动它也留在那里。排空以同样方式解析，而不是凭坐标猜：每个 clone 一次 `git worktree list --porcelain -z`，从候选的 clone（bridge live 摘要的 `worktree.path`，否则绑定的 `workspaceCwd`）执行，再用 helper 纯文件的 `vouchedScanRoots` 过滤与常规文件检查选出持有该 PR 状态的 worktree，活的 watch worktree 胜过陈旧文件。这就是 helper 自己的单次 git 调用发现机制，不是新增扫描。不受信 primary 是本设计已有的例外：该检出内不跑任何 git 命令，因此那里只用坐标、不做发现。坐标拿不到、或发现找不到状态的候选，视为没有账本并照常投递。文件经 helper 带守卫的常规文件读取器读取（`readRegularFile`：`O_RDONLY|O_NOFOLLOW|O_NONBLOCK`，再由 `fstat` 确认是常规文件），绝不是裸读——否则在该路径放一个 FIFO 就会把排空阻塞在刷新线程上，让每个 PR 的检测都停摆。任何拒绝——缺失、非常规、读不了，或 `sessionId` 与 host/owner/repo/number 同候选及绑定不匹配——都视为没有账本，转换照常投递。`lastKnownHeadSha` 刻意不算在账本内：`sync` 会把别人推的 head 采用进它。helper 自己的闸门按 `knownHeads` 抑制，那是该字段加上 `pushedShas`（`packages/cli/src/commands/autofix-pr/snapshot.ts`），因此两条路径在「监视只是采用过来的 head」上刻意分叉：闸门保持沉默，因为监视已把该 head 当作自己的；daemon 仍投递，因为那是别人推的。两条边界：head SHA 不是推送者身份，因此 force-push 回到该会话早先推过的 head 会被归给该会话并丢掉它的 `head_change`，另外三种转换照常触发；以及只有经该 helper 完成的 push 才被记录，因此手工 `git push` 仍会唤醒推它的会话（开放问题 5）。账本由会话可写，所以这是成本优化而非信任边界：伪造的条目能抑制该 PR 投给它所点名会话的 `head_change`。它不发布任何东西，也无法抑制另外三种转换。
- **角色化动作。** 设置 `sessionPrWatch.actions` 后，投递遵循 channel 的角色化模式（#16258），限于四种转换。键为 `<type>`、`<role>:<type>`、`<role>:default` 与 `default`，`<role>` 取 `review`、`verify`、`fix` 之一；值为指令模板，与 channel 一样须非空、经裁剪且不超过 2,000 码点，变量与 channel 相同（`%repo%`、`%pr%`、`%url%`、`%title%`、`%event%`、`%sender%`、`%role%`）：`%repo%` 为投递时该组赢家的绑定 URL 中原样拼写的 `owner/repo`，与 channel 一样保留大小写，`%pr%` 为其编号，`%url%` 为该 URL 的 origin（去掉 `www.`、保留端口）后接 `/<owner/repo>/pull/<number>`（监视文件的键已转小写且不含端口，不用于显示），`%title%` 取自最近一次 view，`%sender%` 为 `GitHub`，与 channel 的监视事件相同；每个值都经过清洗，`%title%` 与 `%sender%` 还与 channel 一样以 200 码点为上限、带可见标记。每个角色组——review、verify、fix 与无类型，按 sidecar 中绑定的 `role`——依次解析 `<role>:<type>` → `<role>:default` → `<type>` → `default`，无类型绑定只解析裸链，无匹配则该组跳过这次转换。一个组的链解析出模板时，该组为匹配；匹配的组在完整扫描中没有合格绑定者时跳过这次转换，在不完整的扫描中则等待（扫描完整性）。每个匹配的组有自己的赢家（该角色最近活跃的绑定者）、以加组后缀的 key 单独准入，prompt 在 channel 带标签的受信指令块中携带渲染后的指令，并沿用 channel 的不可信数据提示——该提示同样覆盖代入指令中的 GitHub 派生值；每个转换最多四次投递。每个组准入后，都以一次写入把该组记进条目的 `served`、把加组后缀的 key 记进 `delivered`；排空跳过已服务的组，因此另一组的赢家仍休眠时，已服务的组不会被服务第二次；每个匹配组都已服务后，条目才离开 `pending`。没有 `actions` 时，投递为单一赢家与通用 prompt。键与模板校验、链解析与渲染都不重新实现：PR A 把 channel 自己的这部分代码从 `GithubAdapter.ts` 移到 `@qwen-code/channel-base`，以事件词表与评论 lane 类别为参数，渲染函数接收变量值而不是 channel 的 envelope——channel 传入 `watch:<type>`、它的通知原因，以及评论事件的 `comment` lane（因此 `<role>:comment` 与 `comment` 仍能匹配它们），并照旧从 envelope 推出变量值；daemon 传入四种裸转换类型、不传 lane，并传入上述变量值，因此这里 `fix:ci_failure` 是合法的键、`mention` 这类通知原因则不是——适配器继续用它处理评论事件，并在 PR B 之前处理监视事件，因此 `%%` 渲染为字面的 `%`、未知的 `%foo%` 原样保留，与 channel 完全一致。迁移顺带修正 channel 渲染函数的两处问题：指向 `Object.prototype` 成员的 `%name%`（如 `%constructor%`）此前会渲染出该成员而不是原样保留，且此前只有 `%title%` 与 `%sender%` 经过清洗。`%event%` 渲染为裸转换类型（`ci_failure`）；因此在别名下（§7），为 channel 编写、原本渲染为 `watch:ci_failure` 的模板会渲染为裸类型。
- **扫描完整性。** 扫描在进程内被调用，为刷新提供 view 集合与收件者。在当前代码中 `partial` 表示有东西读不到——已注册但没有 runtime 的 workspace、列不出来的 chats 目录、读不了的 sidecar 或 transcript、拿不到的 live 会话列表——绝不是分页边界：扫描是每个 workspace 一次目录列表（#16241）。无法枚举的 workspace 本 tick 不提供 view，也不提供新列出的收件者——其会话的保留行仍参与竞争（目标）——此外再无任何东西依赖它，因为没有监视状态存放在它的 sidecar 中；`partial` 推迟所有否定性的决定：删除监视文件（§2；扫描不完整时只适用 7 天的 `lastBoundAt` 规则）、因没有合格绑定者而跳过某个角色组、因没有剩余候选而丢弃转换（下文）都只在完整扫描时判定；不完整的扫描中条目留在 `pending` 等待之后的排空，受 16 条上限与 7 天年龄上限约束（§5）。slim 列表的 `state` 刷新不受影响。
- **归档与恢复。** 归档会话不改动该 PR 监视文件中的任何东西：该会话只是离开收件者候选，其 sidecar 保留顶层 `state` 并照常被刷新。从归档恢复的会话重新加入候选。若另有绑定者一直在跟随该 PR，文件是新的，恢复的会话此后收到转换；若无人跟随该 PR，其文件已被删除（§2），该 PR 静默初始化，因此会话归档期间发生的变化不会补投给它——恢复是用户操作，刷新过的顶层 `state` 已经在侧栏显示了这些变化。在最后一个绑定者离开后 7 天内、且扫描一直不完整时的恢复，会从最后一次观察继续，把间隔期内的转换投递一次。
- **机制。** PR A 把 prompt 准入从路由处理函数中抽成一个路由与刷新共用的函数——幂等环、分类与回填跳过随之迁移，回填跳过改按受信分类判断，而不是按请求自带的标记——刷新在进程内调用它，以及恢复路由背后的代码。刷新全程沿用 channel 绑定中继的分类，而不是新增一种授权：它传入 `context.channelPrompt`，bridge 只从受信 context 把它变成 `qwen.channel.prompt`，会话子进程只在受信的私有父进程下认可它，注入文本也不做 PR 绑定回填。该回合带有这一分类今天在同样的会话中对绑定中继所具有的全部效果（`Session.ts`），并接受它们：跳过循环检测拒绝，不记录分支检查点（它不是 rewind 点），关闭重复工具失败防护，不计为用户提交回合，排队或立即发送的用户输入无法打断其模型响应，其 Stop hook 不可中断，也不调度托管记忆的提取或 Dream，不生成后续建议。以转换 key（启用角色化动作时加组后缀）作为 `idempotencyKey`，因此 daemon 生命周期内对同一会话的重试会去重到原始准入。不设置显示文本：与 channel 今天的绑定中继一样，注入的 prompt 在会话 transcript 中按原样显示，包括不可信数据提示，因此会话的用户看到的正是模型收到的内容（bridge 只为 channel 自有会话保留显示文本）。不新增任何标记，因此剥离清单无需改动；一个路由测试钉住：不带 worker 凭据、携带 `qwen.channel.prompt` 的客户端请求体得不到分类。
- **休眠会话。** 已绑定但不在线的会话通过 channel 访问器所用的恢复路径恢复——PR A 把恢复从路由的 `restoreSessionHandler` 中抽成路由与刷新共用的函数——后再投递，并像 channel 访问器那样在投递的 prompt 结束后释放恢复所创建的客户端注册，使被唤醒的会话空闲时仍能关闭。恢复绝不在 tick 上运行：排空启动休眠收件者的恢复与准入后不等待它们（同时最多四个，其余等之后的排空），key 在它们结束前保持在飞（§5），因此恢复超时绝不会拉长 tick。`wakeDormant` 默认开启，这样 daemon 重启不会让事件滞留在 `pending` 中；`wakeDormant: false` 时转换留在 `pending`，在该会话下一次 live 回合投递（排空在恢复时也会运行，经 PR A 在该共用恢复中加入的钩子），每个 PR 16 条的上限与 7 天年龄上限（§5）照常适用并记日志，不会静默消失。恢复失败按 channel 区分 `BoundSessionGoneError` 与 `BoundSessionUnavailableError` 的方式划分。只有永久性结果——即 channel 的 Gone 集合：会话记录已不存在（404），或 409 `session_archived`、`worktree_session_superseded`、`worktree_marker_missing`、`worktree_reset_interrupted`——才排除该会话；排空随即在其余绑定者中重新解析收件者（启用角色化动作时在其角色组内），只有当完整扫描没有留下任何候选时才丢弃该转换并记一行日志。临时性结果——恢复超时、503（会话数上限、draining）、429、409 `restore_in_progress` 或 `session_busy`，或 `session_writer_conflict`——让条目留在 pending，在下一次排空时投给同一收件者。只有在会话写锁开启时（`experimental.sessionWriterLease`，普通 workspace 会话默认关闭），另一个 daemon 持有该会话时恢复才会返回 `session_writer_conflict`，而且该写锁只覆盖 daemon 与 ACP 写入者：交互式与 headless 的 `qwen` CLI 会话不在其内。因此另一个进程正在写入的会话——终端里的 CLI 会话，或共用运行时根目录的另一个 daemon 在未开启写锁时持有的会话——可能被 owner 作为第二个写入者再恢复一份，事件投进一个无人使用的副本；开启写锁时，owner 的副本也可能在准入之后失败（`session_transcript_changed`、`session_writer_lost`），而准入即视为投递。channel 的绑定投递今天也有同样的风险，因为它经同一恢复路径唤醒会话。为交互式写入者加防护不在本设计范围内，在一个运行时根目录上运行多个 daemon 的运维者应开启该写锁。被排除的会话在 owner 自己的取消归档、恢复或重绑路径提到它时重新成为候选，无论如何一小时后也会恢复。任何地方都不会公开发布。
- **prompt 文本。** 沿用 channel 绑定 prompt 的形状及其卫生措施：事件头、不可信事件数据提示、PR 身份（仓库、编号、最后一次 view 的标题、URL）、一行 `Event:` 与摘要（`ci_failure` 从 rollup 中列出最多五个失败的 check）。每一行由 GitHub 数据构成的内容——标题、check 名称、分支名、摘要——都像 `buildBoundSessionPrompt` 那样经过 `@qwen-code/channel-base` 的 `sanitizePromptText`（折叠 CR/LF/TAB 及其它 C0/DEL 控制字符、剥掉行首标签，因此取自 PR 分支自己 workflow YAML 的 check-run `name:` 无法在 `Event:` 归属之外另起一行 prompt），拼好的正文保留 channel 的 6,000 码点上限与可见的截断标记。外层包装同样不重写：事件头、两种变体下的不可信数据提示与不发布提示、带标签的受信指令块、经过清洗的数据行、`Role:` 行与有上限的正文随模板契约一起移入 `@qwen-code/channel-base`（`buildBoundEventPrompt`），适配器的 `buildBoundSessionPrompt` 现在调用它，daemon 以自己的来源行调用它，因此日后对其中任何一项的修改都会同时作用于两者。迁移同时给受信块换成固定标签 `[Operator instruction — trusted]`，配置出处写在其下的 `Source:` 行：channel 原来的标签 `[Operator instruction — trusted, from this channel's configuration]` 内容为 65 个字符，比 `sanitizePromptText` 剥除行首标签时的 64 个字符上限多一个，所以此前以其副本开头的事件正文会保留方括号。回复留在会话内。

### 5. 持久性

检测结果与新观察以该 PR 监视文件的一次原子写入持久化，转换追加到其 `pending`。投递按最旧优先排空 `pending`，一个 PR 的每个排空步骤都在该 PR 的进程内锁下进行，获取锁后重新读取监视文件：检查 `delivered` 与内存中的在飞标记、解析收件者、设置标记、准入，以及把该 key 加进 `delivered` 并把条目移出 `pending` 的那次写入（启用角色化动作时，把该组记进 `served`，每个匹配组都已服务后再移出条目）；标记在那次写入之后清除，或在准入被直接拒绝时清除，条目留给下一次排空。若记录写入本身失败，标记保留——视为已准入、投给了那个会话——之后的排空只重试该写入，绝不重新解析或再次准入该 key，直到写入成功；只有重启会丢掉这样的标记，这在下文的重启余量之内。只有休眠收件者的恢复在锁外运行，其 key 标为在飞；它的准入重新获取锁、重新读取文件，若该 key 已在 `delivered` 中则跳过。因此一个 PR 的两次排空——扫描的与恢复的——绝不会在检查与它所守护的准入之间交错：哪一方都不能准入另一方已准入的 key（无论投给同一会话还是另一会话），也不能丢掉一个随后准入失败的 key 的条目。准入即视为投递，与 channel 绑定中继相同：排在运行中回合之后被准入的 prompt 在 bridge 的内存队列中等待，因此在该回合结束前重启 daemon 会丢失它——路由自己的注释写明该队列在内存中、"daemon 重启会让两者一起丢失"（`packages/cli/src/serve/routes/session.ts`）——而已经记录了该 key 的监视文件不会重新注入它。prompt 路由的准入环按会话加 key 键控，挡不住同一 key 对另一会话的准入；挡住它的是 `delivered`，因为其中的 key 绝不会再次准入，无论此刻最近活跃的绑定者是谁。超过 7 天的 pending 条目丢弃并记日志，而不是投递。

**崩溃窗口。** 写入前崩溃，下次扫描重新检测（无丢失，也没投递过任何东西）。写入后、准入前崩溃，下次扫描排空 `pending`。准入后、记录它的写入成功之前崩溃，该 key 在重启后再准入一次：at-least-once，与 channel 的取舍相同，也是一个转换被投递两次的唯一途径。重启时仍排在运行中回合之后的已准入 prompt 随队列一起丢失（上文）。`pending` 每个 PR 上限 16 条；溢出时丢弃最旧的并记日志。

### 6. 配置

daemon 设置中的一个 daemon 级设置，自 PR B 起在启动时读取（§7）：`sessionPrWatch: { events: ['ci_failure', 'merge_conflict', 'head_change', 'state_change'], wakeDormant?: boolean, actions?: Record<string, string> }`，环境变量 `QWEN_SESSION_PR_WATCH_EVENTS` 与 `QWEN_SESSION_PR_WATCH_WAKE_DORMANT` 可覆盖（`actions` 只能在 settings 中设置）。默认：无事件（关闭）；`wakeDormant` 默认为 true，`false` 让休眠会话的转换留在 `pending` 直到其下一次 live 回合（§4）；没有 `actions` 时投递为单一赢家与通用 prompt，词表之外的键、空模板或超过 2,000 码点的模板与 channel 一样是校验错误。刷新定时器在 app 创建之前就于 `packages/cli/src/serve/run-qwen-serve.ts` 中启动，因此它经延迟绑定的 getter 访问共用的准入与恢复，与它今天访问归档协调器（`getArchiveCoordinator`）的方式相同。当 workspace 的 view 集合——其 open 绑定 PR 加上列表没有返回的 closed PR（§1）——不超过 30 项时，检测延迟名义上为一个刷新间隔（默认 5 分钟；小于 1 分钟回退到默认值，`0` 关闭扫描）；集合为 n 项且不变时，名义上为 ⌈n/30⌉ 个间隔。两个数字都不是上界：workspace 顺序每个 tick 轮换（§1），其它 workspace 的列表与 view 先于它运行，一个 PR 在 tick 内被观察的时刻因此会移动；截止时间截断窗口、`running` 守卫跳过一个 tick（§1）、集合变化使窗口移位、view 失败、扫描无法枚举该 workspace 或读不到该 PR 的 sidecar、监视文件读取错误跳过该 PR（§2），或所有权转给另一个 daemon（§2）时，检测还会更晚；保留的收件者无法到达或角色组等待不完整的扫描时（§4），休眠收件者等待 daemon 同时运行的四个恢复名额之一时（每个名额在其恢复结束前一直被占用，因此 k 个这样的收件者中最后一个要再等 ⌈k/4⌉ − 1 次或更多次排空），以及恢复临时失败时，投递都要再等后续的排空；`wakeDormant: false` 时则等到会话的下一次 live 回合。在 PR B 开启的弃用窗口内（§7），`sessionPrWatch` 未设置时，GitHub channel 的 `prWatchEvents` 与 `watch:*` 动作被读作别名。

### 7. channel 迁移

GitHub channel 的 `deliverToBoundSessions` 及其评论投递留在 channel 中，除 §4 所述的修正外不变。两个 PR，且不存在两个轮询器同时运行的窗口期。

**PR A** 增加 daemon 的观察与投递及其测试——监视存储及其 owner 记录、排空、共用的准入与恢复、prompt 构造——但置于一个保持关闭的内部开关之后：刷新不运行任何 view，也不投递任何东西，`sessionPrWatch` 设置也尚未被读取。适配器监视的行为除 §4 所述的修正外保持不变——唯一的代码改动是改为导入 PR A 移入 `@qwen-code/channel-base` 的模板与 prompt 外层包装代码（§4）——因此任何构建（包括 nightly）都不会同时运行两个轮询器，两者也无需分工或交接任何事件类型。

**PR B** 打开该开关并加入 `sessionPrWatch` 设置（§6），并在同一个改动中移除适配器监视——监视通道、任务存储中的监视分支、30 个 PR 的上限与 CI 复查间隔——开启一个 minor 版本的弃用窗口。B 不再依据监视状态文件做监视：升级后首次连接时读一次该文件，记录其中仍有多少未投递条目，然后给它加上 `.retired` 后缀改名，使这行日志只记一次；并把每个持久化的 `watch:` 入站任务私下退役并记日志，绝不经评论车道的公开回退。`connect()` 继续接受 `prWatchEvents` 与 `boundSessionActions` 的 `watch:*` 键，只记一条点名 `sessionPrWatch` 的告警，不跑监视通道，Web Shell 描述符将其标为已弃用。`sessionPrWatch` 未设置时，daemon 按 host 把它们读作别名：本 daemon 承载的每个 GitHub channel——按 channel 承载已有的信任门控加载，因此不受信 workspace 的设置绝不会参与（`packages/cli/src/serve/channel-workspace-grouping.ts` 拒绝承载其 channel）——为其 web host 上的 PR 提供自己的 `prWatchEvents` 作为事件集合，以及自己的 `watch:*` 动作（`watch:<type>` → `<type>`，`<role>:watch:<type>` → `<role>:<type>`，`default` 与 `<role>:default` 保留）。`boundSessionActions` 非空的 channel 在别名下仍是角色化的，即使它没有任何键适用于 PR 状态事件，因此没有为任何角色订阅监视事件的 channel 仍然收不到它们。在 owner 认领中（§2），别名算作承载该 channel 的 daemon 的生效集合——每个 global qwen dir 只有一个这样的 daemon，即 channel 服务的预留；若另一个带显式集合的 daemon 已持有监视，则以那个集合为准。其它 host 上的 PR 从别名得不到任何东西，显式的 `sessionPrWatch` 优先；同一 host 上的两个 channel 取事件的并集，每种类型的动作——角色化模式与键——取自 `prWatchEvents` 包含该类型、且其配置会投递该类型（没有动作，或有能为它解析出模板的链）的按名字排第一的 channel，并记录冲突；别名生效时记一次日志。别名的 view 使用 daemon 的 `gh`，而不是 channel 的 token，因此 channel 读得到而 daemon 的 `gh` 读不到的 PR 从别名得不到任何东西：daemon 在对它连续两次 view 失败后记一条点名该 PR 与错误类别的告警，每个失败周期一次；别名生效而刷新定时器未运行时，也在启动时告警一次。channel 用自己 token 连接的运维者应在升级前让宿主的 `gh` 能读到这些仓库。因此在 v0.26.7 上开启了监视的运维者跨过 B 所在的版本，在承载该 channel 的 daemon 持有监视（§2）且运行其刷新定时器期间，对 daemon 的 `gh` 能 view 的每个 PR 仍收到这些转换，只是延迟从 channel 的 60 秒变为 §6 所述的延迟；有一个边界：B 之前 daemon 不保存任何监视文件，因此升级后的第一次扫描静默初始化每个绑定 PR（§2），channel 最后一次轮询与这次扫描之间的转换、以及升级落地时 channel 尚未投递的转换——还没到下一次轮询、仍因背压被推迟、或已进死信——都不会投递；B 的那一次日志会统计这类条目。

B 之后的第一个 minor 版本在 `connect()` 以同一条信息拒绝 `prWatchEvents` 与 `watch:*` 键，并去掉别名。该设置已随 v0.26.7 发布，已发布且写进发布说明的选项不能见到就拒绝，即便它需在 `deliverToBoundSessions` 之后可选开启、实际采用量大概率接近于零；`watch:*` 键（#16258）已随 v0.26.8 发布，出于同样的原因遵循同一个窗口。B 同时更新 channel 文档，在 A 之后合入。

## 关键决策

1. **daemon 拥有 PR 状态。** 它已经为侧栏用宿主凭据轮询这些状态；多加三个字段和一个投递步骤比第二个轮询器便宜，而且服务所有绑定会话，而不只是配置了 channel 的那些。
2. **按 URL 的逐 PR `gh pr view`，而非批量 rollup。** 刷新的 slim 批量列表之所以存在，是因为 rollup 字段在大的 `--state all` 查询上超时；单个 PR 的 view 避开了这一点，按 URL 执行使指向别的仓库的绑定也能抓对，且受 view 集合——open 绑定 PR 加上列表没有返回的 closed PR（§1）——约束：每次扫描上限 30，旋转，受一个 tick 截止时间约束。
3. **与 channel 监视相同的选择与转换规则**，包括角色化动作，迁移过来的运维者看到的事件相同，只有一处刻意的 CI 判定差异（决策 5、开放问题 2）。
4. **每个 PR 一个监视文件，既是快照也是队列。** PR 状态按 PR 存在，因此基线、待投递转换与已投递记录在一个由 daemon 持有的小文件中每个 PR 只存一份，而不是存在每个绑定者的 sidecar 中。没有副本会落后，因此设计不需要任何从陈旧副本采用、合并或重新检测的规则，sidecar 也只保留侧栏读取的内容。
5. **单一 CI 定义**（core 的 rollup），在下面的开放问题定案前接受 `cancelled` 与 `stale` 算作失败。
6. **带别名的一个版本弃用窗口**，针对 `prWatchEvents` 与 `watch:*` 动作：v0.26.7 已发布该设置（#16117，2026-11-04 发布），v0.26.8 已发布 `watch:*` 动作（#16258，2026-11-05 发布），两者都在发布说明中点名，因此都不能见到就拒绝；采用量大概率接近于零（只有几天、需在 `deliverToBoundSessions` 之后可选开启），所以一个 minor 版本内旧字段告警并被读作别名——在承载 channel 的 daemon 持有监视且运行其刷新定时器期间，对 daemon 的 `gh` 能 view 的 PR，已配置的运维者在第一次扫描之后不会断事件，不能 view 的 PR 由 daemon 告警——就足够，之后再由 `connect()` 拒绝。
7. **本次改动默认关闭**；默认开启是之后的产品决策。
8. **自推抑制按收件者、依据推送账本，而不是依据 GitHub 账号**（§4）。账号无法区分同一运维者的两个会话，而抑制转换本身会饿死 fix 会话的 push 本该唤醒的 review 与 verify 角色。只抑制 `head_change`、只抑制账本记录了该 head 的那个会话、且只在账本存在时抑制；执行 push 的 helper 已经记了一本账，因此 daemon 读它，而不是解析 shell 命令或安装钩子。

## 约束与风险

- **延迟**名义上为一个刷新间隔（默认 5 分钟），而非 channel 的 60 秒轮询；view 集合为 n 项时名义上为 ⌈n/30⌉ 个间隔。两个数字都不是上界：§6 列出使它更长的情形。需要更快信号的运维者调低 `QWEN_SESSION_PR_REFRESH_MINUTES`（小于 1 回退到默认值；`0` 关闭扫描），代价是 view 次数：间隔每减半 view 量翻倍，在 1 分钟的下限一个 workspace 每小时最多 1,800 次 `gh pr view`——即 channel 监视在上限时的数字——五个 workspace 则是 9,000 次。tick 截止时间（§1）随间隔缩短（1 分钟时为 30 秒），因此新增的 view 至多让 tick 越过它一次 view 超时，恢复也不在 tick 上运行（§4）；刷新已有的列表调用不变。
- **凭据。** 需要 daemon 宿主上已认证的 `gh`，这是刷新与 PR 侧栏已有的要求。没有它的 workspace 保持今天的行为（不刷新状态，也无事件）；自 PR B 起，daemon 的 `gh` 读不了的 PR 收不到 PR 状态事件，并会告警（§7）。
- **状态文件。** 最近 7 天内被绑定过的每个 PR 一个小 JSON 文件，位于每个 global qwen dir 由一个 daemon 持有的私有目录中（§2）；sidecar 不变。未持有 owner 记录的 daemon 不投递 PR 状态事件，本机无法核验的记录在被手动删除之前会阻止监视，与 channel 服务相同；以监视目录或其中某个监视文件的所有者之外的用户运行的 daemon 从不认领它（§2）。
- **API 预算。** 每 workspace 每次扫描最多 30 次 `gh pr view`：W 个被扫描的 workspace 在默认间隔下每小时 360·W 次（W = 5 时 1,800 次，即 channel 监视单个 channel 在上限时的数字），叠加在现有列表之上，受半个刷新间隔的 tick 级 view 截止时间约束（§1）。view 每个 tick 按 PR 跨 workspace 去重（§1），绑定在多个 workspace 的 PR 每个 tick 只抓取一次。
- **不可信内容进入交互式会话。** 事件 prompt 把 PR 标题与 check 名称作为数据携带、标记为不可信并经 `sanitizePromptText` 处理、受 channel 的 6,000 码点上限约束（§4），与 channel 绑定 prompt 的契约相同；会话自身的审批模式决定其行为。不受信 primary 中的绑定以 daemon 自己的凭据 view（§1）——设置 `sessionPrWatch` 时在每个允许的 host 上，别名下在 channel 的 web host 上（§7）——因此它指向的、该凭据能读的任意仓库中的 PR，其标题与 check 名称会作为不可信数据进入该会话。这比 channel 监视今天的范围更宽：后者只在自己的 web host 上、以运维者交给 channel 的 token 读取这类绑定（`GithubAdapter.ts` 中的 `parsePrBindingUrl`），而在别名下，这一变化随升级到来，而不是由运维者选择开启。本设计接受这一点；不希望如此的运维者不设置 `sessionPrWatch`，并删除已弃用的 `prWatchEvents`，从而结束别名。
- **准入分类。** 非交互式 prompt 的 daemon 来源回合必须对客户端不可伪造。本设计不新增授权，也不新增标记：它沿用 channel prompt 的受信链——路由的 worker 凭据、bridge 的受信 context、子进程的受信父进程检查（§4）。

## 验收标准

1. 设置 `sessionPrWatch.events` 后，绑定会话对 CI 失败、合并冲突、head 变更、合并/关闭的每个转换实例收到一条 prompt——设置 `actions` 时每个匹配的角色组一条——重复触发语义与 channel 监视相同，且无需配置任何 GitHub channel；本设计另有说明之处除外：首次观察与监视文件删除前的重绑（§2）、16 条上限与 7 天年龄上限（§5）、没有剩余候选（§4）、收件者自己的已推 head 账本里的 head（§4）、daemon 的 `gh` 读不了的 PR（§7）、同时以旧仓库名与新仓库名被绑定的 PR（按每个名字各投递一次，§1）、另一个进程正在写入的会话——CLI 会话，或未开启会话写锁的另一个 daemon（§4）、只由未持有 owner 记录的 daemon 服务的会话、本机无法核验的记录或属于其他用户的监视目录或监视文件阻止认领期间，以及 PR 监视不支持的、global qwen dir 不同却共用一个运行时根目录的多个 daemon（§2）、daemon 重启时仍在排队的已准入 prompt（§5），以及标准 2 的重启余量。
2. 不重启时，一个转换至多被检测一次、其每个 key 至多准入一次，无论绑定者的会话与 workspace 在此期间发生什么——归档、被超过、读不了、不受信、已退役——两次排空并发运行时亦然。跨重启时一个转换至多投递两次——只有准入与记录它的写入之间的崩溃会让它重复——且至少投递一次，除非该 PR 的监视文件丢失或不再通过校验（§2），或其 prompt 已被准入、在 daemon 重启时仍排在运行中回合之后（§5）。
3. GitHub channel 不再发出任何 PR 状态 API 调用；带 `prWatchEvents` 或 `watch:*` 动作的配置仍能连接，只记一条点名 `sessionPrWatch` 的弃用告警、不跑监视通道，且在 `sessionPrWatch` 未设置时，对承载该 channel 的 daemon 的 `gh` 能 view 的每个 PR 从升级后的第一次扫描起经该 daemon 收到每个转换，按其 `watch:*` 动作路由，不能 view 的 PR 会告警——除非另一个带显式 `sessionPrWatch` 的 daemon 持有监视（此时以其集合为准），或承载该 channel 的 daemon 因其他原因未持有监视（§2），或未运行刷新定时器——对此它在启动时告警（§7）；PR B 之后的第一个 minor 版本起在 `connect()` 以同一条信息拒绝。
4. 未设置 `sessionPrWatch`、也没有生效的别名时，刷新的行为与 API 调用量不变。
5. 同一仓库的两个受信 workspace 各有一个会话绑定同一个 PR 时，每个转换只投递一次，给其中最近活跃的会话，收件者在检测与排空之间被归档或被超过、或任一 workspace 一段时间不可达时亦然；force-push 回到一个 CI 失败已触发过的 head 时，只要该 head 仍在该 PR 的 16 个 head 历史内，`ci_failure` 不再触发。
6. `wakeDormant: false` 时，休眠会话的转换保留在 `pending` 并在其下一次 live 回合投递；任何构建都不会同时运行两个轮询器：PR B 之前由适配器投递所有 PR 状态事件、daemon 一个也不投递，自 PR B 起全部由 daemon 投递。
7. 新 head 在某候选自己的已推 head 账本里时——账本位于 helper 为既有 watch 解析出的根下、经其带守卫的常规文件读取器读取——该 `head_change` 不投给该候选：排空重新解析下一个绑定者（启用角色化动作时在同一角色组内），其它匹配组仍收到它，没有剩余候选时完整扫描记一行日志丢弃、不完整扫描保留在 pending。账本缺失、读不了或不匹配时照常投递，作者身份绝不抑制 `ci_failure`、`merge_conflict` 或 `state_change`（§4）。

## 开放问题

1. `sessionPrWatch` 是否应对四种事件默认开启？
2. `cancelled` / `stale` 的 check run 是否算作 `ci_failure`？core 的 rollup 算（并发取消的被取代 run 会触发）；channel 监视排除了它们。
3. `reviewDecision` 已在抓取：是否在同一机制下增加 `review_decision` 转换（approved / changes requested）？
4. Aone 对齐：Aone 后端返回 head 与流水线状态后，为 Aone MR 暴露相同的转换。
5. 手工 push 没有账本：只有 autofix-pr helper 记录它推过的 head（§4）。是否应由会话侧的记录——执行 push 的工具写入的推送账本，或经运维者同意安装的 `pre-push` 钩子——也覆盖手工 `git push`，还是只有 helper 的边界就可以接受？
