# 随上下文压力调整工具输出

[English](pressure-aware-tool-output.md) | [简体中文](pressure-aware-tool-output.zh-CN.md)

## 问题

#2566：长会话中上下文逐渐填满时，工具结果仍使用同一个静态预算，几次大结果就可能比必要更快地把会话推过压缩触发线。token 数归属于具体聊天及其 provider 路由，共享的 Config getter 无法选出动态预算，这个决定必须在聊天发送请求的地方做出。

## 变更

在聊天发送边界，聊天可以只依据自己上一次成功的用量报告，缩小即将发送的请求中的工具结果。只有当该报告来自同一 provider 路由、之后计数和历史都未被替换、并且它覆盖的历史仍是当前历史的原样前缀时，才能作为依据。计数是恢复或估算得来的、历史被替换、路由不同、属于另一个聊天，或报告之后又已经发出过请求，都视为没有依据，静态预算照常生效。显式设置的 `truncateToolOutputThreshold` 始终优先。

余量以自动压缩触发线而不是硬上限为基准：剩余 token =（auto − 报告中的 prompt+output token − 保守估算的、该预算无法缩减的新增输入）/ 现有的新增内容安全系数。在默认的 1M 窗口上，auto（850k）与 hard（977k）之间相差约 127k token，以硬上限为基准时，只有在压缩已经触发之后才会缩小结果。字符预算为剩余 token × 4，按批内每条结果下限 4,000 字符，并且只在低于该批的静态容量（单工具门限 × 该预算可缩减的结果数）时才生效。达到或超过 auto 触发线时已没有余量可分，由压缩接管，因此不做任何缩小。

该预算由请求中的所有工具结果共享，并与现有的 200k 聚合发送保护取较紧的那个。应用候选结果之前，发送边界会检查压缩准入使用的实际估算值。如果候选结果仍达到 auto，则改用仅按聚合预算处理的候选结果，前提是它低于 hard，避免在压缩仍会发生时丢弃结果文本。小窗口中，如果仅按聚合预算处理的请求会达到 hard，则保留压力裁剪，即便它仍触发压缩。两个候选结果都从原始结果生成，因此同一条结果不会被裁剪两次。

聚合预算配置为 `<= 0` 时保留其非有限的「已禁用」哨兵值，并关掉整个发送保护——与该设置在其他所有消费者上的行为一致。同一消息中的用户文本永远不会被缩短。与现有发送保护一样，最终选定的候选结果保留每个结果的头尾，不会新写落盘文件；已经由单工具层落盘的结果保留其恢复指针。

## 范围与限制

静态默认值保持 25,000 字符 / 1,000 行，本改动不上调它们。只有字符预算会动态调整，行数上限不变。由于调整区间起点贴近 auto 触发线，预算只在自动压缩前最后几千 token 左右起作用：在此之前它大于该批的静态容量，在此之后由压缩接管。这是对压缩的补充而不是替代，也不保证精确的 token 准入。

结果大小统计（#11536）是另一项改动。

## 验收

聚焦测试覆盖：1M 窗口上接近 auto 触发线时缩小；每条结果的下限仍会进入真实压缩准入时保留八条完整结果；同一区间内保留媒体及其附带文本；小窗口中仅按聚合预算处理会达到 hard 时保留下限；远离或越过 auto 时不变；并行结果共享同一预算且用户文本保留；显式、估算、恢复、外部路由和其他聊天的归属下保持静态输出；以及报告之后又发出过请求时不再复用该报告。真实准入回归测试在受控的 PreCompact hook 处停止，不生成摘要；实际 CLI 请求和完成路径另以受控 provider 与 tmux capture 验证。
