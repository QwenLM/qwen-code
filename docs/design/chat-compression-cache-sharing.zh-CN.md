# 聊天压缩缓存共享

[English](chat-compression-cache-sharing.md) | [简体中文](chat-compression-cache-sharing.zh-CN.md)

## 背景

聊天压缩目前发送一条冷侧查询：专用的系统指令、不含主会话的工具声明，
以及一份经过媒体精简的对话副本。若提供商的提示缓存键以工具和系统指令
开头，则无法复用主会话已缓存的prefix。

## 设计

当以下条件全部成立时，压缩会先尝试一次特殊的单回合请求：

- 压缩请求路由到主模型——解析后的模型、认证类型和端点与主生成器一致，
  因此命名主模型的提供商限定选择器与端点 pin 选择器同样符合资格；
- 当前提供商为 Anthropic 或 OpenAI 兼容端点且启用了缓存控制，或提供商为
  Gemini / Vertex AI（隐式提供商托管缓存；`enableCacheControl` 不适用）；
- 会话拥有提供商上报的提示 token 数，用于锚定估算；
- 有效提示 token 数加上有界的压缩输出预留，能放进模型的上下文窗口。

该请求使用当前回合的有效生成配置（包括子代理使用的每请求工具覆盖），
以及完整的历史（包括媒体）。发送时按常规做模型模态过滤，因此受支持的
媒体保持不变，不支持的媒体使用与其他模型请求相同的占位符。现有的压缩
指令作为最后一条用户消息追加。Gemini 与 Vertex AI 依赖其提供商托管的
隐式前缀缓存。本请求中的函数调用不会被消费或执行。包含函数调用、空
响应、畸形状态快照或请求错误的响应会被丢弃，并通过现有的冷侧查询重试
一次；其媒体精简输入只在真正需要回退时才惰性构建。取消不会触发回退。

使用当前 `GeminiChat` 使请求保持在活跃会话作用域内。进程级的全局 fork
缓存被有意排除：它只保留很短的历史尾部，且可能属于另一个并发会话。

压缩选择器路由离开主模型的会话（不同的模型、认证类型或端点）保持原有
路径，因为它们的缓存身份与主会话不同。携带媒体的历史优先走共享路径，
使面向提供商的前缀保持不变，从而复用主会话的缓存。

OpenAI 兼容端点即使缓存控制能力未知，也使用相同的前缀保持请求形状，
允许 vLLM 等服务端自动前缀缓存进行匹配。Qwen Code 不会向这些端点发送
提供商专用的缓存字段。对于官方 OpenAI API，各请求共享稳定的会话缓存
键；每个并发运行的非 fork 子代理追加自己稳定的代理身份，避免无关前缀
在父键下互相竞争；fork 则保留会话键，因为其继承的前缀与父级一致。这
遵循 OpenAI 的建议：同一键下所有前缀的总流量保持在每分钟约 15 次请求，
更高流量的场景使用
[稳定映射](https://developers.openai.com/api/docs/guides/prompt-caching#improve-cache-hit-rates-with-a-prompt-cache-key)
做分区。GPT-5.6 及之后的压缩请求还会标记最后一个可复用的用户/工具边界
并选择 explicit-only 缓存模式，使新的压缩指令不会移动有效缓存断点。

## 验证

单元测试断言精确的系统指令、工具、完整历史与尾随指令的构造；提供商/
模型门控；共享路径上的媒体保留；窗口预检；回退后的媒体精简；函数调用
与畸形响应的回退；以及取消行为。提供商侧验证应对比主回合与压缩请求的
序列化请求前缀和缓存 token 用量。

文中引用的真实提供商缓存数字是一次性验证证据，不是入库的基准。要复现：
将一个交互式 CLI 进程经透明 OpenAI 兼容代理路由，发送一条带随机数的
主回合，然后执行 `/compress` 和一条回溯该随机数的后续消息。只记录消息
角色、长度与哈希、工具哈希、缓存字段存在性和提供商用量（绝不记录提示
内容或授权）。验证主请求与压缩请求共享相同的系统指令、初始用户消息和
工具哈希，并将命中率计算为 `cached_tokens / prompt_tokens`。验证使用了
DashScope `qwen3.7-max`：主回合上报 18,944 / 19,627 缓存 token
（96.52%），压缩上报 18,944 / 20,409（92.82%）。一次确定性的精确前缀
mock 对比匹配了最长的字节相同序列化前缀：干净基线的 `main` 走冷摘要
路径且零缓存 token，而本设计匹配 28,032 / 29,034 提示 token（96.55%）。
凭据、抓取的提示内容和私有代理夹具有意不入库；单元测试是持久的请求
形状验证。
