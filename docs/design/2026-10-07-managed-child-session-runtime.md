# Managed child Session runtime (H4b)

[English](2026-10-07-managed-child-session-runtime.md) | [简体中文](2026-10-07-managed-child-session-runtime.zh-CN.md)

Status: proposed; this document pins the decisions before implementation begins. Nothing it describes is implemented yet. This is slice **H4b** of [#12827](https://github.com/QwenLM/qwen-code/issues/12827), stage H of the Managed Agent proposal [#12380](https://github.com/QwenLM/qwen-code/issues/12380): the child Session runtime. It follows H4a ([record contract](2026-10-06-managed-child-agent-runtime.md), PR #13505), which delivered the `managed-child_run` body kind `child_agent` and the `managed-child_acceptance` body with the six-slice H4 delivery map, and it extends the obligations of H0b ([record contract](2026-09-27-managed-extension-record-contract.md)), H0c ([authority](2026-09-27-managed-extension-authority.md)) and H3 ([background Shell and Monitor](2026-10-03-managed-shell-monitor-runtime.md)). Below, "the reference design" is sections 3, 8, 12, 13 and 14 of the [extension runtime design](https://github.com/doudouOUC/code_agent/blob/689121646cc25ca08a34508a5f5555ae15308833/qwen-code/feature/managed-agents/managed-agent-extension-runtime.md), "the automation design" is section 5 of the [automation, Channels and child delivery design](https://github.com/doudouOUC/code_agent/blob/689121646cc25ca08a34508a5f5555ae15308833/qwen-code/feature/managed-agents/managed-agent-automation.md), and "the recovery design" is the [recovery operations design](https://github.com/doudouOUC/code_agent/commit/689121646cc25ca08a34508a5f5555ae15308833) at the commit that #12827 pins (whose `child_run` phase names — `launch`, `attach`, `cancel`, `drain` — this document uses). The earlier [H4 problem framing](2026-10-04-managed-child-agents.md) remains this slice's background; wherever it and the H4a contract disagree, the H4a contract governs (its "Decisions" section records the supersessions).

## Problem and scope

H4a pinned _what may be committed_: the `child_agent` run body and the acceptance body, their transitions, their cross-record commit checks, replayed identically in TypeScript and Java. Nothing _produces_ them: no Session may submit either domain, no caller constructs a body, and the reference design's pipeline — parent commits launch → control plane creates the child Session idempotently → child Harness commits a terminal result → result crosses → parent accepts (and later consumes) — has no implementing component. Issue #12380's H4 line is the exit this slice works toward: "Independent child Sessions, parent acceptance/consumption, durable messages and close cascades. Shared record names alone are not executable domains."

H4b delivers the child-agent part of that pipeline:

- The **child operations** as parent-authority commands: `startChildRun` (admitted from the Agent tool in the hosted tool turn), `queryChildRun` (read-only, control plane), `commitChildResult`, `acceptChildResult`, `cancelChildRun` and `closeChildScope` (control plane, relay- and cascade-driven). `continueChildRun` is _not_ produced in this slice (decision 12).
- **Java lineage storage and idempotent child creation** (V54): lineage columns on `managed_agent_session`, plus a service-level creation entry whose idempotency key derives from the parent's committed launch (H4a decision 3), so an ambiguous creation answer never mints a second Session.
- **The first cross-Session dispatcher — the child result relay**: a `managed-agent-server` worker that discovers `child_agent` runs needing creation or delivery, drives creation, watches the child Session to its terminal state, copies the published result and receipt into the parent Session, and submits the acceptance; it classifies results that arrive at a closed parent as orphaned instead of reviving it.
- **Both completion paths.** A foreground child (`completion: "tool"`) answers the original tool call with the child result, folding the `accepted` delivery step into the tool-result commit; a background child (`completion: "sent"`) delivers the result as a durable notification input with its generated wake, in the acceptance transaction. Never both (reference design section 8).
- **The close cascade**: closing a parent cancels every non-terminal child (recovery-design `cancel`/`drain` phases), recursively, with the close order of reference design section 12; late results become orphaned.
- **Quotas**: depth, concurrency and input bounds, refused at admission with the shared H0b vocabulary.
- **Enablement with the server-first deployment order**, kind-selective so H3's shell stays disabled (decision 10).

Still deferred (not this slice): the `workflow` kind (H4c), durable peer messages (H4d), teams (H4e), public task cancel (H4f), detach to an independent durable owner, `snapshot`/`worktree` workspace modes, depth beyond 1, custom subagent definitions distinct from the parent's, and any production AgentBundle enablement — exactly as the H4a delivery map assigns them.

## Current state

The facts below are from this slice's base (the H4a branch head `3261e4d452`, whose merge-base with `main` is `ac81c07dc8`).

- **Records.** `managed-child-run-record.ts` defines the closed `child_agent` body (17 keys, chain keyed by `childRunId`, delivery target `session`, `resultVersion` exactly 1, result and receipt refs appearing only together with the settling revision); `managed-child-acceptance-record.ts` the acceptance body (opens `settled` at delivery `accepted`, one allowed successor step to `consumed`, no task projection). The authority's commit path checks the acceptance against the committed child run (`managed-session-authority.ts`, the `child_acceptance` branch of `assertExtensionRevision`), and `verifyExtensionResources` closes both bodies' refs over the Session's own store. `MANAGED_EXTENSION_RECORD_BODIES` holds both bodies; `child_run` projects `child_agent` tasks by the body's kind, `child_acceptance` none.
- **Enablement.** `MANAGED_SESSION_ENABLED_DOMAINS` enables the four envelope domains plus H1/H2. `child_run` and `child_acceptance` are named but disabled; H3 deliberately keeps `child_run` (its `shell` kind) and `monitor_run` disabled pending its own enablement gates, and the enablement list is the only domain gate — there is no runtime admission switch beneath it (H3 design, "Reader compatibility"). The hosted tool turn's background-shell admission reads the same gate (`childRunAdmissionsEnabled()`), so enabling the domain as-is would also wake H3's shell producers.
- **Authority machinery.** `LocalManagedSessionAuthority.commitExtensionRecord` commits exactly one record revision per transaction, optionally bundled with one notification input whose wake the authority generates in the same transaction; a retried command returns its committed receipt. `assertDomainAdmittable` consults the enabled list. `close()` only seals the journal — lifecycle close, including any cascade, lives in the Java control plane. Actor classes include `trusted_entry`, the class control-plane operations (H3's maintenance and runtime-outcome paths) already commit with.
- **Receipt of a cross-Session result.** The relay pattern exists in legacy: the daemon `create_sub_session` (`completion: 'sent' | 'first-turn'`, depth cap 1, per-caller and total caps) retries result notification until the parent durably accepts; `agents/workspace-agents/` keeps a JSON outbox reconciled transactionally (`reconcileThreadOutbox`, `deliverParentReports`). Neither is managed-aware; their recovery credentials (callbacks, PIDs, best-effort files) are exactly what the reference design forbids on the Managed path.
- **Hosted turn and tools.** The private Hosted profile admits file/Shell(/glob) tool sets plus MCP tools; `agent`, `workflow`, `create_sub_session` and `send_message` are not in the declaration set and are refused at admission (`prepareRequests`). A tool call runs `prepare → execute → tool_result commit → Broker acknowledge`; harness commits are journaled before acknowledgement. `run_shell_command`'s `is_background` and the `monitor` tool admit only behind their domain gates — the pattern H4b's Agent tool admission follows.
- **Notification and wake.** A notification input commits with `input.accepted` (+ generated `wake.requested`); the embedded harness scheduler runs it as an ordinary text turn while idle and queues it while busy; consumption is derived journal-side as "an input is consumed exactly when a turn with its turnId settles" (`pendingSessionInputs`). The Monitor slice uses this for `monitor_run` notifications; nothing yet maps an input to a _child_ acceptance's consumption.
- **Java control plane.** `ManagedAgentService.createSession`/`createWorkspaceSession` admit creation with an `Idempotency-Key` and a semantic request digest (replay returns the original admission); `SessionLifecycleCoordinator.settle` runs close as claim → workspace close → Harness close (original holder only) → live-writer check → Runtime drain, with operation retry and blocked classifications, and `@Scheduled recoverOperations` resumes in-flight operations. `SessionEventHub` bridges committed store events to SSE. There is no lineage anywhere: `parentSessionId`/`rootSessionId`/`child_session` do not occur in `packages/sdk-java`, and `managed_agent_session` carries no hierarchy columns. `qwen_managed_session_extension_record` (V18; task columns nullable since V23) materializes `domain`, `delivery_target` and `delivery_state` per latest revision, with no delivery-pending index. Flyway stands at V47 (`V45__managed_session_task_journal` reserves the name `qwen_managed_session_task_event` for the later task-view outbox; H4b must not take it). The public OpenAPI contract is at 1.33.0 with `TaskKind.child_agent` already `partial`; H4b needs no public contract change.
- **Profiles.** The private Hosted Workspace profiles (`hosted-workspace-files|shell/1..2`) live in the `tool_profile` column; production AgentBundle enablement remains separate, as in H1–H3.

## Decisions

1. **One producer surface, two caller paths.** All six child operations are methods on the Session authority layer (TypeScript), the only writer of the parent journal, and every one commits with actor `trusted_entry` — the only actor class `domain.committed` admits, and the class H3's in-process result/maintenance commits already use. The Agent tool's admission calls `startChildRun` in-process; the Java control plane reaches the remaining operations through the embedded session-command surface. No second write path to the journal exists (H0c invariant), and the relay never touches the parent store except through those operations.
2. **The launch commit is complete before any effect.** `startChildRun` publishes the launch-input resource (the envelope of decision 11) and commits revision 1: run `admitted`, execution `intent`, delivery `planned`, the launch identities (`childRunId`, `ownerScopeId`, `rootSessionId`, `depth`, `completion`, `workspaceMode`, `workingDirectory`, `predecessorChildRunId`, `resultVersion = 1`), the definition pin and the start call's `executionCallId`. As in H4a decision 3, the cross-Session creation idempotency key derives from the committed record key (`sha256(parent session key | child_run | childRunId)`), so the body's launch identity and the creation command cannot diverge, and an ambiguous creation answer reconciles by replay, never by re-firing.
3. **`workspaceMode`: `shared` only, admitted.** The reference design's default (an independent worktree for a writing child) needs a Runtime capability the Workspace stages have not delivered — worktree lifecycle, quota and close-time merge all remain undelivered — and a read-only snapshot needs a frozen view no provider implements. `shared` needs nothing new: the child binds the parent's Workspace exactly as a second creator Session does and inherits the existing Workspace lease/settlement discipline (sessions sharing a Workspace already serialize through it). Launches naming `snapshot` or `worktree` are refused at admission with a tool error naming the unsupported mode; the contract vocabulary stays intact for their slices. This makes the earlier H4 framing's "read-only snapshot first" narrower still, deliberately: the first runtime slice proves Sessions, relay and cascades, not isolation.
4. **Depth and concurrency are launch-time refusals, not records.** A launch deeper than depth 1 (the contract cap is 8; nested runtime support lands with its own evidence) or beyond the per-scope active-children cap (4, on top of the serve's existing tenant inflight bounds) is refused by the Agent tool's admission as a tool error naming the H0b quota reason (`depth_limit` / `count_limit`); nothing commits, mirroring how the legacy spawn guards refuse before any registry entry. A control-plane refusal that reaches the _relay_ (e.g. a tenant Session cap at creation) is instead settled as a failed run (`quota_exceeded`, execution `not_started_proven`, `childSessionId` null) — evidence the parent model can consume — never silently retried into a breach.
5. **Foreground and background share one pipeline until the acceptance.** Creation, lineage, relay watching and result copy are identical. The arms differ only in the accept transaction grouping (reference design section 8, automation design section 5):
   - `"tool"` — the Agent tool call stays pending across as many model rounds and restarts as the child needs. When the relay submits the result, the parent commits, in order: (a) `commitChildResult` — the child-run settling revision with the parent-held result and receipt copies and delivery `accepting`; (b) `acceptChildResult` — the acceptance record alone (no input, no wake, ever); (c) the original tool call's result commit, immediately followed by the `accepting → accepted` successor. The model-visible answer and the delivered fact are ordered commits, not one folded transaction — the message sink is not an authority-commit surface — and the waiter's answer is always re-derivable: after any crash it re-reads its own journal (settled run + acceptance) and issues the tool result from the committed copies, so a crash between (b) and (c) answers from evidence, never from relay memory, and the pair can never durably half-answer without a committed path back to the answer. A turn cancelled mid-wait abandons only its answer: the child keeps running to its settled result and `accepted`, and consumption stays uncommitted — visible as accepted-not-consumed, never widened.
   - `"sent"` — the launch returns a task handle immediately. The accept transaction bundles the acceptance record with the notification input and the authority-generated wake in one transaction (the existing `commitExtensionRecord` input bundling); the notification carries the accepted result's **bounded** summary — escape-then-bounded far below the inline cap of both the bundled input and the wake turn's later message envelope, with an explicit truncation marker pointing at the acceptance record's `contentRef` — the full bytes ride the acceptance. The child-run delivery advance to `accepted` is the separate relay-driven commit H4a decision 4 allows to lag — never corrupt, since the acceptance record already stops redelivery.
6. **Consumption is progress evidence, separate from acceptance, on both arms.** When the parent Turn that consumed the result — the wake turn started by the notification input (`"sent"`), or the turn that received the folded tool result (`"tool"`) — commits its `turn.settled`, the Harness commits the two consumed revisions (`child_acceptance` delivery `accepted → consumed`, then the `child_run` delivery `accepted → consumed`). The acceptance successor rule (one step, no rewind, H4a decision 9) makes an over-eager consumer uncommittable, and a crash before the consumption commit leaves `accepted` alone — re-readable as accepted-not-consumed, never widened (reference design section 14 item 7).
7. **The acceptance record is authoritative (the owed delivery-direction decision).** H4a's follow-up note requires H4b to resolve that a `child_run` delivery may today advance to `consumed` with no acceptance record, or back off to `unknown`/`rejected` after one exists. This slice adds the reverse commit-time check in the authority and the Java store alike: a `child_run` revision whose delivery enters `accepted` or `consumed` must name a `childRunId` whose acceptance chain exists in the same Session (at `accepted` or beyond), and a `child_run` revision whose delivery enters `unknown` or `rejected` is refused once any acceptance revision exists for the chain. `planned → accepting` and `accepting → unknown` remain legal while no acceptance exists (relay retry vocabulary).
8. **The relay lives in `managed-agent-server`, leashed by a ledger it owns.** A scheduled worker scans `qwen_managed_session_extension_record` for `delivery_state IN ('planned','accepting','unknown')` among `child_run` rows (V54 adds the supporting index) and reconciles each against the child Session's committed state — creation answers, session status, settled turns. Its own table `qwen_managed_child_result_relay` (V54; _not_ the reserved task-event name) holds one row per claimed child run: claim lease and heartbeat, the idempotent creation key, the child Session id once known, attempt/backoff counters, and the durable classifications — `orphaned` (parent closing/closed) and `unknown` (an outcome that cannot be proven either way) — which survive the worker and must never be presented as consumed or trigger re-execution. Rows are minted at creation-claim time, so a relay restart resumes from its own committed claims and re-queries original occurrences, exactly the recover-operations pattern of the lifecycle coordinator. The relay is idempotent end to end: a second claim (or a second worker under a stale lease) replays creation, re-reads settlement and re-submits acceptance; every authority operation answers a retry with the original receipt. An answered acceptance short-circuits no owed step: a `watching` row whose `accept` committed but whose `delivering` advance was lost reconciles through the same idempotent walk — replaying the result, the acceptance, then the advance — so the ledger's mark_accepted step and completion are never stranded behind a non-delivery early-out. The child Session's durable close is a debt the row owes before it retires: on a host capable of Workspace close, the admission lands before the settle/fail commit (a transient falter parks, never drops); on a host without the capability at all, settlement still commits on time — quota and the parent's next Turn never wait on a capability — and the row parks as `close_debt` (claimed, named by the child id, due on the heartbeat, surfaced by the same discovery page) until a capable scan discharges it, and only then retires. The same retention fills the settlement-committed / debt-unwritten interruption window: before a non-ACTIVE parent can classify a row `orphaned`, a settled delivery whose child Session still stands reconciles into the debt; unsettled rows orphan as before (that side was the close cascade's to stop).
9. **The child's terminal result and receipt are the parent's copies, digest-bound** (H4a decision 6). The relay reads the child Session's own publication (its settled final turn content and turn-settlement evidence), submits the bytes with `commitChildResult`, and the parent side stores them as _its_ resources before the settling revision names them; the acceptance's `contentDigest` and both refs bind copies to originals, so a redelivery naming the same record with different content is a conflict — refused with `409 managed_session_extension_record_rejected` — not a second acceptance. The receipt is a bounded structured summary (turn id, settle sequence, terminal classification), not the child's journal.
10. **Enablement is kind-selective, because one domain now holds two capabilities with independent gates.** Enabling `child_run` as a domain would wake H3's background-shell producers — whose enablement explicitly waits on the H3 gates — through the same single gate (`childRunAdmissionsEnabled()` reads the domain list). This slice therefore leaves `MANAGED_SESSION_ENABLED_DOMAINS` without `child_run` and introduces a per-kind gate beside it: `MANAGED_SESSION_ENABLED_CHILD_RUN_KINDS`, initialized to `['child_agent']`, checked by the authority's admission for that domain and by the tool-turn admission (`agent` admits on the kind gate; `is_background`'s shell admission keeps reading the domain list and stays off). `child_acceptance` has a single shape and joins the plain enabled list. When H3's gates clear, `shell` joins the kind gate (or the domain list with the kind gate retired) — H3's call, not this slice's. The server-first order is preserved exactly as H4a arranged it: the Java store has validated both bodies since the H4a release, so the release carrying these writers deploys the server before any writer can submit, with the reader-compatibility argument of H3 unchanged (the bodies parse on every managed-session/1 reader; new shapes fail-stop old writers, and no Session holds these records yet).
11. **The child is a plain bound Session with a lineage stamp — v1 clones the parent's definition.** `createChildSession` (service-level sibling of `createWorkspaceSession`, called only by the relay) creates the Session in the parent's tenant and Workspace binding with the parent's tool profile, records ancestry in the V54 columns (`parent_session_id`, `root_session_id`, `parent_child_run_id`, `child_depth`), and drives its first turn with the launch input. The launch input envelope (the `inputRef` content, bounded JSON) carries `{ description, prompt }` and the definition pin. In v1 the pin names the _parent's own_ agent definition (id, revision, digest at launch): custom `subagent_type` values — whose prompt/tool composition is the D8b/D8c "apply definition fields to execution" scope — are refused at admission with a tool error naming that scope, so this slice never half-applies a definition. The Agent tool's managed parameters are `description`, `prompt` and `run_in_background` (v1 has no `name`: teammate routing is H4e's, and an inert name would be a dead switch); `fork_*`, `working_dir`, `isolation`, profile and type selectors stay legacy-only. The child shares neither model context nor permission view with the parent (reference design section 8): its initial context is composed from the shared agent definition plus the envelope, by the ordinary Hosted Session admission path.
12. **`continueChildRun` and `queryChildRun` have no v1 commit surface and are not built as operations.** The continuation slot (`predecessorChildRunId`) is already in the body; its real producers are the peer-message and revive paths (automation design section 5.1, "paused/completed continue along continueChildRun's new run identity"), which are H4d's, and after a _failed_ child the honest recovery is a new independent run, never a replay of unknown work (reference design section 14 item 10). A `query` needs no journal write: the relay reconciles over the SQL projection (`qwen_managed_session_extension_record` latest rows plus session lineage), and TypeScript-side consumers (the cascade, the tool-turn waiter) read the rebuilt records in the authority — no operation is built for what a projection already answers. `cancelChildRun`/`closeChildScope` are built with the cascade as their only v1 caller (public cancel is H4f's).
13. **Close cascade: cancel before Harness close; physical safety first when the parent side is unreachable; unproven never rewritten.** In `SessionLifecycleCoordinator.settle`, after admission barriers (existing) and before the Harness close, the coordinator asks the parent side to `cancelChildRun` every non-terminal `child_agent` run (stop request committed: `stopRequested` set, run unchanged — a request is not an end state), then closes each child Session through **its own Session lifecycle** — the cascade admits the child's idempotent close operation (the run's stable key, the child actor cloned from the parent-owned binding), dispatches it, and waits on the child's terminal Session status, recursively cascading; a child Session whose Turn is still active refuses the admission, and the whole close re-arms until the Turn ends by its own machinery — then submits each child's terminal revision (`cancelled` by `stop_requested`; execution `settled` when the child's Session status is terminal-proven, `not_started_proven` when no child Session ever admitted; delivery `cancelled`). A run whose launch body never learned the child Session id (the create→attach window) resolves the child through the relay ledger **and then the committed lineage row** — the creation pipeline stamps the child's own lineage at insert, so a window where both the body and the ledger lack the id still identifies the child, and a missing ledger id is never evidence for `not_started_proven`. Such a child's `dispatch_started`/`attach` are replayed through the record's valid transitions from its proven evidence (its own committed dispatch facts, or the physical Runtime binding it warms with) before the settling revision — the body parsers accept `settled` only over a chain whose attach committed, and a reply lost before the relay's own attach no longer wedges the parent close into retrying a revision no parser reads. If the parent's writer is unreachable (a crashed Harness with no live `qwen serve` writer), the stop-request and terminal revisions stay owed: the close operation retries them in the coordinator's ordinary retry/blocked classification, and it never rewrites a run as cancelled on suspicion (section 12: the observation timeout only bounds API waiting, and never releases a physical owner). Late results from such children are the orphaned classification of decision 8. Detach is not built: a request to detach an unmanaged child is refused, as H3 refused its unmanaged processes.
14. **No public contract surface moves; v1 admits only Shell-laned profiles.** The OpenAPI stays at 1.33.0 (`TaskKind.child_agent` is already `partial`; the task list shows the `child_agent` tasks the projection already knows how to map); no route, Flyway-independent schema, or WebShell type changes. V54 is the only migration, carrying the lineage columns, the relay ledger and the scan index. The zero-gap `contract-known-gaps.txt` stays byte-identical. The Agent tool advertises exactly where the Session owns its child orchestrator over the proven Shell lanes (`hosted-workspace-shell/1..2`); `hosted-workspace-files/*` — including the public files/1 conversation flow — keeps its exact current tool vocabulary and behavior. Child admission on files profiles and on the public flow is its own separate gate, the same way the public foreground Shell admission is (#13271), not a consequence of this slice.

## The pipeline, revision by revision

Parent Session (journal authority on `qwen serve`; all commits single-writer):

| Step | Commit              | Contents                                                                                                                                                                                                                              |
| ---- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | launch (rev 1)      | run `admitted`, execution `intent`, delivery `planned`, pin, identities (§D2) — `startChildRun`                                                                                                                                       |
| 2    | dispatch (rev 2)    | execution `dispatch_started`, `dispatchId`, `run.runtime` (the binding the admitted creation assigns; the run contract records the binding by the time a run dispatches, never later) — after the control plane has admitted creation |
| 3    | attach (rev 3)      | `childSessionId`, execution `running_attached`, once the child Session's Harness is confirmed live (the body pins the Session to no earlier execution state)                                                                          |
| 4a   | settle (rev)        | execution `settled`, run `settled`/`completed`, `resultRef`+`terminalReceiptRef` (copies), delivery `accepting` — `commitChildResult`                                                                                                 |
| 4b   | failure ends        | run `failed`/`creation_failed`·`child_failed`·`quota_exceeded` or `cancelled`/`stop_requested`, execution `settled` or `not_started_proven`, delivery `cancelled`                                                                     |
| 5    | accept              | acceptance record rev 1 (`settled`,`accepted`) (+ notification input + wake on the `"sent"` arm) — `acceptChildResult`                                                                                                                |
| 6    | accepted (rev)      | child-run delivery `accepting → accepted` — folded into the tool-result commit (`"tool"`) or separate relay commit (`"sent"`)                                                                                                         |
| 7    | consumed (two revs) | acceptance `accepted → consumed`, then child-run delivery `accepted → consumed`, on the consuming turn's settle                                                                                                                       |

Each commit moves every state line at most one allowed step (the H0b successor rule), so a crash between any two rows reconciles from the last committed row. Java relay (control plane): claims the launch, drives creation until admitted (rev 2), confirms the child's physical Runtime binding live (rev 3 — the binding exists from the child's first Hosted tool turn's warm, so a child that answers end-to-end in text is provable the same way), watches the child to terminal, copies result/receipt, submits steps 4–6; a parent `close` walks step 4b via `cancelChildRun`/`closeChildScope`; a result finding its parent closed is ledger-marked `orphaned`. A relay crash between creation admitted (session physically exists) and rev 3 replays creation by its derived key — the lineage columns and the idempotency key name the same Session — and then attaches; the parent journal learns of the Session at attach, never by inference.

## Quotas

| Bound                           | Value                                                                                                                                                                                                                  | Refusal                                   |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| Depth                           | 1 (contract cap 8)                                                                                                                                                                                                     | launch tool error, `depth_limit`          |
| Active children per owner scope | 4                                                                                                                                                                                                                      | launch tool error, `count_limit`          |
| Launch envelope                 | ≤ 32 KiB UTF-8 (description ≤ 512 bytes)                                                                                                                                                                               | launch tool error, `byte_limit`           |
| Relay attempts per child run    | bounded backoff, then `unknown`                                                                                                                                                                                        | ledger classification, never rerun        |
| Result copy                     | ≤ 64 KiB, pinned to the parent Session's durable inline bound (larger results: refused with `byte_limit`, run `failed/quota_exceeded` — Artifact staging of larger outputs is follow-up O-slice work, not inline here) | `commitChildResult` refusal before settle |
| Notification inline copy        | ≤ 64 KiB (escape-then-truncate with a marker; the full bytes stay on the acceptance record)                                                                                                                            | truncation, never refusal                 |

## Non-goals

- **`snapshot` / `worktree` workspace modes**, **depth > 1**, **custom subagent definitions** — refused at admission (decisions 3, 4, 11).
- **`continueChildRun`, detach, public cancel, workflow/peer/team kinds, orphan GC policy** — H4c–H4f and follow-ups, per the delivery map.
- **Production enablement**: the private Hosted profile only; AgentBundle capability lists and the §13 H4-gate real-stack acceptance (including §14 items 2, 7) stay the recorded follow-up gates — this slice provides the implementation and store/authority evidence they verify.
- **Any Legacy path change**: the in-process Agent tool, `create_sub_session`, `send_message`, workflows and teams keep current behavior; the reference design forbids switching engines on a running Session.

## Acceptance criteria

- The three facts are separately observable: child terminal (the child-run settle), parent accepted (acceptance revision + child-run delivery `accepted`), parent consumed (both deliveries `consumed`) — on both completion arms.
- A restarted relay re-sends only an un-`accepted` original result and never creates a second child for a committed launch; a relay crash between creation and acceptance reconciles from the committed occurrence; an identical re-acceptance answers its recorded revision.
- A closing parent refuses new launches, cancels its non-terminal children through the ordinary pipeline, and is never revived by an orphaned result; an unproven child leaves the close retrying/blocked, not rewritten.
- Kind-selective enablement: `shell` bodies stay refused while `child_agent` commits; the reverse acceptance check refuses the H4a-identified contradictions in both languages; `child_run` stays off the plain enabled list.

## Amendments (2026-10-09, R22 review round)

1. **Never-started verdicts name the minted Session (contract revision).** A `creation_failed` or `stop_requested` settlement whose execution lands on `not_started_proven` may carry `childSessionId` and no Runtime binding — the mint is exactly what survives the create→attach window, and an unnamed mint would orphan the child: nothing else would ever discover it. Both record validators relax three clauses (session requires an admitted dispatch, session requires a hosting binding, `creation_failed` requires a null session), each bounded to `not_started_proven` — the one terminal with no dispatch to host from. The `fail`/`close_scope` wire operations accept an optional `childSessionId`; the builders restate the same id replay-safely and refuse a rename with `child_operation_record`; the shared fixtures pin the newly-lawful shapes.
2. **The terminal verdict and the mint share one commit seam.** Ingestion of any `not_started_proven` terminal revision locks the run's own extension row `FOR UPDATE` — the same row the creation fence reads in `insertChildSessionCommand` — and then reads `managed_agent_session.parent_child_run_id` under that lock: the revision's `childSessionId` must equal the lineage's mint (null exactly when no lineage exists), or the commit is refused and the writer retries with fresh evidence. A give-up verdict whose evaluation saw an empty lineage is refused when the mint landed first, and the deferred retry re-reads the lineage and names the child — the inverse ordering of R21's creation-versus-verdict race is closed at commit time, not by preventative chance.
3. **The give-up's start proof reads the record body, never the `runtime_state` projection.** The projection column holds Runtime states (`unbound`, `provisioning`, `ready`), so the execution-enum comparisons never matched and the chain resent refused started pairings forever (R22's give-up wedge). `executionState` now reads the committed body through its inline resource; an unreadable body owes a bounded retry rather than a guessed verdict, and a self-proven `not_started_proven` execution pairs the unstarted verdict directly.
4. **The cascade's started call binds any-state evidence.** A start is proven by the body's committed dispatch facts, by a binding row in ANY state (`findLatestBindingByHarnessSessionAnyState` — a retired RELEASED/LOST row still proves its dispatch and names the repair's identity; the repair-for-warmth read stays READY-only), or by the child Session's own durable Turn. A creation key is an attempt id, never a start. With none of the three, the never-started pairing settles `started: false` — named when the lineage minted a Session; with any, the repair rebuilds dispatch and attach from that evidence and the settlement commits `started: true`.

## Amendments (2026-10-09, R23 review round)

1. **The gate's lineage read is a locking read.** Under REPEATABLE READ the committing transaction's snapshot is established by its ordinary reads long before the verdict's row lock, so a plain lineage SELECT misses a mint committed after that snapshot even while the lock serializes against the mint's fence — R23 reproduced exactly that on MySQL 8.0.46 (READ COMMITTED and H2 both reject and recover, so only the production topology showed it). The lineage read now runs `FOR UPDATE`, which always reads the latest committed data on either InnoDB default and takes the same extension-then-session lock order the mint uses. A two-live-connection IT on MariaDB REPEATABLE READ witnesses both directions (plain read misses → RED; locking read rejects → green).
2. **The give-up replays its repair chain from historical binding evidence.** Terminal reconciliation needs the dispatch identity, not warmth, so `reconcileAttach`'s physical-child repair also reads `findLatestBindingByHarnessSessionAnyState` — a RELEASED binding still names what the dispatch committed, and an executed child whose binding retired before the record recovered now settles instead of wedging the budget behind a READY answer that can never come.
3. **A Turn proves a start only through its G3 dispatch pair.** `TurnLine` carries `submission_attempted` and `harness_event_epoch`, and both the relay's physical-ran probe and the cascade's started call read `dispatched()` (either set). A Turn the coordinator failed before warm-up, create/load or submission is a pre-admission failure and proves nothing — it settles the named never-started pairing instead of hunting a binding that never existed (the exact wedge R23 left the parent CLOSING behind).

## Amendments (2026-10-09, R24 review round)

1. **A runnable Turn fences the never-started verdict (relay).** `!dispatched()` describes a live `ACCEPTED` Turn waiting for its coordinator as exactly as it describes the terminal pre-admission failure, and a verdict minted ahead of the coordinator's outcome is the same false pairing with better timing — on a close-incapable host the give-up committed `creation_failed` over a Turn the coordinator later claimed, submitted and completed. The relay now defers (bounded) on any Turn that is neither `dispatched()` nor `preAdmissionTerminal()` (`FAILED`/`CANCELLED` with neither pair). The cascade needed no sibling branch: the active-Turn close admission already guards the same window there (it `continue`s on the refusal, and the terminal truth settles on the next walk).
2. **The gate's refusal is a rollbackable non-commit over the wire.** The verdict/mint gate rejects with a dedicated `child_run_lineage_minted` code instead of the generic record rejection, and the HTTP client maps it (409) to `ManagedSessionCommitRejectedError` — the authority rethrows that class without latching `writeFailure`, so the relay's corrected named retry commits on the resident parent authority instead of finding its Session log stopped after the first refusal. A word-level invariant rides the Thread-line: the code is pinned in the H2 decision table, the MySQL IT, and the TS client suite (one-shot 409 → typed rejection, `writesStopped` false, corrected retry commits).

## Amendments (2026-10-09, R25 review round)

1. **The G3 reset mark is evidence-neutral, never evidence-negative.** `withdrawSubmissionAttempted` after a lost reply leaves the Turn `CANCELLED` with neither dispatch mark nor epoch — the identical field shape as the genuine pre-admission failure — while the historical binding remains, so the terminal shape `FAILED|CANCELLED && !dispatched()` still cannot prove never-started alone. The intent reconciliation now orders its evidence: an outstanding Turn outcome (live, neither dispatched nor terminal pre-admission) always owes the bounded defer; the proven pair or the historical binding row takes the dispatch replay with the same identity; only their joint absence plus a terminal pre-admission failure settles the named never-started pairing. Terminal status never upgrades a reset to a proof.
