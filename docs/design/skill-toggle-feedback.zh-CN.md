# Skill 开关反馈与工作区控制

[English](skill-toggle-feedback.md) | [简体中文](skill-toggle-feedback.zh-CN.md)

## 问题

本次修改处理 [#10152](https://github.com/QwenLM/qwen-code/issues/10152)。
成功写入设置后，所选 Skill 可能从刷新的目录中消失。页面随后返回列表，
但操作结果通知没有显示。受上层设置禁用的 Skill 也缺少一个入口，
让用户在它仍被禁用时移除旧的工作区启用声明。

## 行为

在详情和列表中复用现有可关闭的管理通知。如果刷新的目录没有目标 Skill，
只报告工作区设置已更新，另行区分实际可用状态。写入失败时显示错误并解除忙碌状态。
在另一个工作区或客户端发起的操作，其结果不能更新当前页面。

对于受上层设置锁定的已禁用 Skill，增加 **在此工作区禁用** 操作。
它使用现有设置开关，传入 `enabled: false`，移除工作区 `skills.enabled`
中的条目并添加 `skills.disabled`。它不会解除上层限制，也不会让 Skill
变为可运行。这是明确的工作区禁用操作，不是恢复继承设置。不增加 daemon 或 SDK
API。目前 daemon 已拒绝在上层锁定时新增启用声明；反向操作也能处理之前保存的声明。

App 已能在只改变声明的变更后释放已加载 Skill 列表的暂存。本次只补测试，
不修改这部分产品逻辑。修正 TUI 注释，说明锁定 Skill 未被操作的工作区声明会被保留；
不改变 TUI 保存行为。

## 验证

- 刷新后缺少目标 Skill：列表显示设置结果，通知可以关闭。
- 写入被拒绝：显示错误，控件恢复可用，不显示成功通知。
- 上层锁定：新操作向所选工作区写入 `false`，移除已有启用声明，实际状态仍为禁用。
  不支持该功能的 daemon 保持操作不可用。
- 写入或刷新期间切换工作区：丢弃旧通知，不让新工作区的控件一直处于忙碌状态。
- 只改变声明的变更：释放暂存，显示之后更新的 session Skill，并且下一次已应用的变更
  不会再次读取状态。

使用组件测试、聚焦的 App 回归测试以及使用临时设置的隔离 daemon 验证。
实际验证结果记录在 PR 测试报告中。
