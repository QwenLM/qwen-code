# UserPromptSubmit 上下文去重

[English](user-prompt-submit-context-dedup.md) | [简体中文](user-prompt-submit-context-dedup.zh-CN.md)

**Status:** Implemented

**Date:** 2026-10-13

## 问题

返回 `additionalContext` 的 `UserPromptSubmit` hook，会在每一轮把这段文本追加到用户消息后面。当 hook 是确定性的——同样的查询、同样的结果集——第 2、3……N 轮都会追加完全相同的块。由于每次追加的块都会成为会话历史中永久的一部分，这段载荷每轮都会被重新发给模型，累计请求 token 呈平方级增长。

本仓库自带的检索扩展很容易触发这一点：`integrations/external-context` 与
`integrations/external-context-mem0` 的自动召回 hook 都基于一个有界、最新优先的结果窗口构造载荷，因此只有配置的 dialect 省略每次查询的分数时，上游结果集稳定才会让渲染出的字节逐轮完全相同。若 dialect 复制相似度分数（仓库自带示例即 `"scoreField": "score"`），分数是针对当前提示计算的，载荷每轮都会重新渲染。

## 现状

- `packages/core/src/core/client.ts` 在交互式 `UserPromptSubmit` 注入点把 hook 上下文作为独立 part 追加，并用保留标签包裹。
- `packages/cli/src/acp-integration/session/Session.ts` 在 ACP/IDE 路径上追加同样的被包裹 part。两个注入点都是每轮针对共享的会话历史执行，因此以同样的方式让记录增长。
- `packages/core/src/utils/transcript-records.ts` 拥有保留标签，以及识别带标签 part 的匹配器。
- `packages/core/src/hooks/user-prompt-submit-context.ts` 拥有围绕该标签的共享边界逻辑；目前它只导出一个被会话标题使用的剥离辅助函数。
- 记忆子系统中其他所有去重路径，比较的都是 core 在两侧都能识别的条目（本地记忆文件用 body 引用加修改时间，core 自己投递过的外部结果用记忆标识）。没有任何地方会把 hook 载荷文本与 core 此前注入过的文本相比较。

## 目标

不要重新注入已经存在于会话历史中的 hook 上下文块。模型仍然能看到这个块——它就在更早的那一轮里——所以这里消除的是重复，而不是信息。

## 非目标

- 将 hook 上下文与 core 并未注入的内容去重，例如某个托管记忆文件的措辞与检索结果在语义上相似。core 对不透明的外部载荷不持有任何标识，因此这种比较在投递时刻是无法表达的。
- 改变载荷格式、体积，或扩展所执行的有界渲染。
- 给 `getAdditionalContext()` 加上长度上限。这是另一个独立问题。
- 任何新的配置开关、协议字段或扩展 manifest 特性。该行为是无条件的。

## 方案

在既有标签辅助函数旁边新增一个导出的谓词，并用它守护两个注入点。

该谓词在会话历史中扫描是否存在某个 part，其文本恰好等于即将追加的那个被包裹的块，比较的是完整包裹后的字符串，而不是解析并重新切片内层正文。这里精确相等是正确的，因为 core 是这些 part 的唯一生产者，且存储的就是它自己构造出的字符串、未做修改。它还绕开了两个陷阱：包裹函数在正文两侧各插入一个换行，因此基于偏移的内层切片很容易写错；而注入的字符串是 HTML 转义后的形式，若与原始 hook 输出比较，则含尖括号的载荷永远匹配不上。

仅字节相符不足以证明来源，形状也不足以：调用方自写的消息可以逐字节地以被包裹的块结尾（ACP 客户端可以提交两个文本块，落盘后恰好就是注入的形状）。因此注入器在它追加的 part 上打一个模块私有的 symbol 回执（`createUserPromptSubmitContextPart`），谓词除了要求相同文本之外，还要求这个回执：该 part 位于 user 条目的索引 1 或之后（此后追加的任何 part，包括记忆目录快照或普通上下文，都不会使这份已投递证据失效），或者它是该条目唯一的 part（反应式压缩可能以这种方式保留块）。缺少来源证明的单 part 标签文本仍视为用户自撰内容，并在会话中保留展示。symbol 无法穿过 JSON 会话记录、ACP 提示块或模型输出，因此只有注入器构造的 part——或恢复会话时依据逐轮记录的 `hookContext` 来源信息重新盖章的 part——才算作已投递。仅仅「出现过」的带标签文本，无论以何种条目形状出现，都不会抑制一次新的投递；来源无法证明时，按原行为注入。

该谓词回答的是关于单条历史条目的问题——该条目是否在首个 part 之后保留了这个被包裹的块及其回执——调用方则从最新到最旧逐条喂给它，并在第一个匹配处停止。把谓词做成按条目而不是按历史数组，使同一个辅助函数可以服务两个注入点，而每个注入点各自保留对历史的访问方式。

交互式注入点与 ACP/IDE 注入点都会在追加前查阅会话历史，因此由任一路径投递的块都会抑制另一路径的重复投递。

回执能在基于展开的容器复制中存活（这类复制保留 symbol 键），但在 `structuredClone` 与序列化中都不存活——两者都会丢弃 symbol 键属性。恢复会话时，会话记录被重建为 API 历史，symbol 不在其中；重建过程会依据逐轮记录的 `hookContext` 来源信息重新盖章，而该信息只有注入器会写入。恢复回执仍只检查原始用户记录的末尾 part；随后重放独立的记忆目录快照记录，才会追加快照 part。ACP/IDE 注入点不为它的轮次记录这份来源信息，因此在 ACP 投递之后恢复的会话，会保守地重新注入，而不是在来源无法证明时抑制。prepared-request 重放用 `structuredClone` 安装历史（`llm-chat.ts`），回执同样会丢失，因此会重新注入一次，随后重新武装抑制。

记录压缩检查点时，会复制捕获时的每个 `Content` 容器及其 parts 数组。展开复制保留用于提取提示标识和上下文标记的 symbol 元数据，但不会递归冻结 part 数据。随后发生的救援不会把块加入该检查点。从不含该块的检查点恢复时，可以新注入一份。若检查点已经含有该块、但缺少可恢复的来源信息，恢复时仍可能保守地重新注入；快照拥有独立容器不代表私有回执能穿过序列化。

匹配成功时，本轮不再追加该 part，也不再记录本轮的 hook 上下文来源信息，从而让展示出来的会话记录与模型实际收到的一致。

历史查找走 chat 上只读的「最新优先」检索，它返回活动条目且不做克隆。注入点在每次续跑时都会到达，包括工具往返，因此在这条路径上不能使用深拷贝的历史访问器。

## 设计决策与理由

**与历史比较，而非与其他 hook 输出比较。** 一个 `UserPromptSubmit` 块可能已经存在的地方只有一处，就是会话历史。

**丢弃，而非标记。** 标记（例如「已在当前上下文」占位符）仍然每轮都要付出占位符的 token 代价，并且要求模型去推理一个它无法解析的记号。丢弃重复项后，原始块仍能在更早的那一轮里取到。

**变化时自愈。** 载荷的任何变化——新结果、分数变化、顺序变化——都会使相等判断失败，块会被正常注入。不存在会过期的抑制状态。

**无条件、无开关。** 今天，一个刻意希望每轮都重复某个固定块的 hook 无法表达这一意图；而给 hook 输出 schema 增加字段将是一个远大于本修复的协议变更。这一点被接受，并作为局限记录下来，而不是在这里解决。

## 约束

- hook 运行器将 hook stdout 限制在 1 MiB，这为载荷大小提供了上界。
- 该检查必须避开深拷贝的历史访问器。
- 包之间不得使用相对导入；该辅助函数应紧邻它所推理的标签语义。

## 风险

- **固定/常驻块从第 2 轮起被丢弃。** 一个有意每轮重复某条指令的 hook 会失去这种重复。该文本仍然会在首次投递它的那一轮中可见一次。
- **载荷内嵌每次查询的分数时收益有限。** 若扩展的 dialect 复制了相似度分数，则只要分数变化载荷就会变化，因此抑制只会在分数也重复时触发。省略分数的 dialect 能获得全部收益。
- **压缩在同一次发送内被救援；其它历史重建可能重新注入。** 抑制以回执为门槛，而回执只在存在逐轮 `hookContext` 来源信息的地方被重新盖上，即交互式恢复路径。丢弃回执的重建会让该块恰好在丢失上下文最多的那一轮消失，因此压缩带有救援：每次发送恰好一个所有者重新追加一次——当 ACP 发送助手自己运行的压缩消费了副本时由它负责，否则由 `LlmChat` 在其硬阈值或反应式救援点中先触发的那个负责。令牌经 `LlmChatSendOptions.suppressedHookContext` 与对应的 `Turn` 构造参数传递，且 `LlmChat` 的硬阈值救援点会跳过请求中已存在的块，因此助手侧追加之后再转发也不会产生重复。每个救援点都会由新的末尾回执立即重新武装抑制，包括反应式兜底分支推入的单 part 用户条目。没有救援的重建——客户端驱动的 ACP 回滚、`structuredClone` 安装历史（例如 prepared-request 重放）、恢复一个 ACP/IDE 轮次（该路径不记录来源信息）——在无法恢复回执时可能保守地重新注入。新的末尾 part 会在活动历史中重新武装抑制，但不保证回执在后续重建中持久保留。

## 验证方案

1. 针对该谓词的单元测试，覆盖不存在、存在与结构异常等条目，另加来源相关用例：用户条目中的真实单 part 应抑制重复投递；缺少来源证明的单 part 标签文本仍视为用户自撰内容并保留展示。索引零之后带真实回执的相同 part，即使后面追加了记忆目录或普通上下文，仍应抑制重复投递。带标签的块出现在 model 条目里，或带真实回执但位于索引零的多 part 条目中，应注入而非抑制。仅涉及形状的变体（前后多余空白、缺少换行分隔符）由 `isUserPromptSubmitContextPartText` 覆盖，它识别任意带标签块；该谓词比较的是一个精确载荷，刻意不做 trim。
2. 每个注入点各一个回归测试：当带标签的块已在历史中时，交互式路径上追加的 part 与记录的 hook 上下文来源信息都不存在，ACP/IDE 路径上只发送提示词文本；当历史为空时，既有行为不变。
3. 端到端检查：使用载荷恒定的 `UserPromptSubmit` hook，在同一会话中跑多轮，逐条用户记录统计带标签的块与来源信息是否存在。只统计用户记录，因为同一份记录里不相关的条目（遥测、自动记忆抽取器）也会把载荷原样引用回来，使得对整个文件做子串计数失去意义。
4. 使用真实记录器做回归验证：捕获压缩检查点后，在排队写入完成前重新赋值活动条目的 parts。序列化检查点仍应保留捕获时的 parts 和提示标识，而活动历史包含救援块。移除记录器的容器复制必须使该断言失败；在调用时复制 mock 载荷不能替代这项验证。从该检查点恢复后不含救援块，因此下一次相同 hook 恰好新注入一份。反应式救援产生真实单 part 后，下一次相同 hook 应在活动历史中抑制第二份副本。
5. `npm run build && npm run typecheck`，以及断言保留标签的 core 单元测试套件。

ACP/IDE 注入点复用同一个谓词，并有自己的配套回归测试：当被包裹的块已在历史中时，只把提示词文本发给模型。

## 验收标准

- 逐字节相同的 hook 上下文块，只要带回执的 part 仍位于所在用户条目的索引 1 或之后，或作为该条目唯一的 part，无论来自哪个注入点，都至多一次到达模型，这一点在面向模型的请求和会话记录中都能观察到。之后追加的任何内容（记忆目录快照、手动退出 plan 模式的提示、中途消息合并）都保留抑制能力。若历史重建时缺少逐轮 `hookContext` 来源信息，回执就会丢失。
- 同一次发送内的压缩恰好重新追加一次被抑制的块——每次发送一个所有者：当 ACP 发送助手自己的压缩消费了副本时由它负责，否则由 `LlmChat` 负责——且在助手已追加过时绝不追加第二次。新的末尾回执会立即重新武装抑制，包括反应式兜底分支的单 part 条目。缺少可恢复来源信息的重建可能保守地重新注入。
- 压缩检查点拥有捕获时独立的 `Content` 容器和 parts 数组，保留元数据，但不包含随后追加的救援块。从不含该块的检查点恢复时允许新注入一份；已经含有该块但缺少来源信息的检查点仍可能导致保守的重新注入。

- 载荷发生变化时总是会被追加。
- 除这一个导出的谓词外，不新增任何配置、schema 或公共 API 表面。
