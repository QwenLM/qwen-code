# DAC Chat Plan toggle

[English](dac-plan-toggle.md) | [简体中文](dac-plan-toggle.zh-CN.md)

## Problem and scope

Web Shell uses one approval-mode value for both planning and execution permission. Plan appears in the permission menu, and confirming a plan may choose a different execution policy. DAC Chat needs a Plan toggle that is separate from the permission control. The existing single-row responsive toolbar remains: narrow widths collapse labels to icons. No other toolbar control moves, and no CLI/TUI semantics change is included.

Generating a plan leaves Plan enabled until the user approves it. Approval exits planning and executes under the policy selected when the user confirms. Rejection leaves planning enabled. Changing permission while planning updates only the policy for execution and never auto-confirms the plan. Manual toggle-off exits planning under the selected permission; it does not submit the pending plan approval. Existing running-turn switch timing is preserved; this feature does not add cancellation or model steering.

## Runtime and transport

Retain runtime ApprovalMode.PLAN and its existing tool restrictions. Add an optional DAC-only selected execution policy to Config, populated exclusively by an explicit planMode boolean on the existing session approval-mode control. Legacy requests omit the flag and retain their behavior. Validate the flag and reject PLAN as an execution policy. Core applies the existing derived-config and folder-trust constraints before changing state. Updating execution policy while already planning does not end or restart the planning lifecycle.

For DAC selections, RestorePrevious captures the selected execution policy in the confirmation callback. Legacy confirmations still restore their original snapshot. Execution retains cancellation and approval-mode-revision checks. Policies chosen after confirmation must not silently alter that already-approved decision.

The existing route remains live-session-owner scoped through withOwnerMutableSession. Use its resolved runtime, bridge and Config throughout, with existing unknown/removed/draining failure behavior. No primary-runtime fallback, new workspace route or permission persistence is introduced. Transport the selected policy in approval responses, mode notifications and session-mode metadata; preserve it through bridge reconciliation, snapshots and client hydration. The effective runtime mode remains authoritative for whether the Plan toggle is on.

## Web Shell

Plan is chosen rarely, so its entry is a checkbox item at the end of the composer add menu (`+`) rather than a permanent toolbar control. While Plan is on, a dismissible Plan chip sits after approvalMode so the state stays visible; clicking it exits planning, and its description names the execution policy that applies after approval. While Plan is off the toolbar carries no Plan control. The host must explicitly include `plan` in `composerToolbarActions` or `composerToolbarAdditionalActions`; omitted configuration hides it in main and split panes. The standalone browser host explicitly opts in, and split panes always carry the add menu. The rule is per composer: one whose host lists `plan` without `addMenu` has no menu to hold the entry and keeps the earlier Plan Switch after approvalMode, using the shared Switch primitive. Such a host therefore shows the switch in its main composer and the menu entry in its split panes; listing `addMenu` makes them match. Plan never falls back into the permission menu. Wide layouts show the Plan label; narrow layouts drop it, leaving the chip as its icon and the switch as icon plus switch. The chip carries no close mark at rest: the mark shares the icon slot and takes it over on hover or keyboard focus, so revealing it never changes the width of the chip. Where the primary pointer cannot hover the mark stays shown instead, but only beside the label. There, a chip too narrow for its label keeps the Plan icon at rest rather than becoming a bare close mark that names nothing: it shows no mark unless it takes keyboard focus, and works as the pressed button it is, which a tap releases. Under forced colours the masked icon is repainted with a system colour so that it survives. The chip is the one Plan control that unmounts when Plan turns off, and it can do so while it holds keyboard focus: its click cannot move focus into an input that is disabled, and the host can end Plan with no click at all. Rather than let focus fall to the body, the chip hands it on: to the input; or, when the input is disabled, to a toolbar control beside where the chip was — the permission control, or the model control while the permission control is still disabled by the mode change in flight. Focus the user has since moved elsewhere is left alone, and a host that shows neither control gets no handoff. Where the primary pointer is coarse the handoff skips the input and goes to a toolbar control: focusing an editable outside a gesture claims the active element without opening the keyboard, after which a tap may raise none, which is why the Composer gates its own focus restoration the same way. Preserve the single row, tooltip, accessible name and checked/pressed state, and keep `data-web-shell-plan-control` and `data-web-shell-plan-button` on the chip as well as on the switch, with `data-web-shell-plan-chip` marking the chip. A host that selects the Plan control by those hooks finds a `button` with `aria-pressed` rather than a `role="switch"` with `aria-checked`, and finds nothing while Plan is off, because the chip exists only then. Toggling from the add menu or the chip leaves focus in the editor when the input can take it, so unlike the switch, which reported its own state while focused, nothing announces the change to a screen reader; the chip still carries the state for a user who moves to it. Closing that gap needs a signal for which Plan changes the user initiated, which this change does not add; see the deferred note in [Composer add menu](web-shell/web-shell-composer-add-menu.md). The add menu is disabled together with the Composer input, so with the input disabled Plan cannot be entered. The chip is not disabled with the input, but it only does anything where the host accepts a mode change: both composers decline one while the session is write-blocked or its transcript is loading, and there the chip is a silent no-op, exactly as the switch it replaces was. A host reading these hooks should also note that the chip reports a busy handoff through `aria-disabled`, where the switch put `data-disabled` on its label. It is not natively disabled, because both hosts go busy inside the chip's own click and a focused button that becomes disabled loses focus to the body on the spot. A press while busy therefore reaches the composer surface, as a press on the bare toolbar does, but does not toggle Plan. While mode controls are busy the menu entry is disabled and says so, and the fallback switch is disabled and the chip inert; like every toolbar button the chip keeps its appearance, and being focusable rather than disabled it still shows its tooltip and can still be reached by Tab. Hide the entire Composer and its status area while a plan awaits approval, matching ordinary permission and AskUserQuestion overlays. Restore them when the overlay resolves. Floating plan cards scroll only their plan content, keeping the heading and approval buttons visible, including text-only plans. Execution permission remains adjustable during planning before the approval overlay appears. Remove Plan only from Web Shell permission menus/cycling. Keep Auto alongside Default, Auto Edit and YOLO. Do not change the shared SDK approval enum or the agent-definition editor.

Main and split panes use the same daemon action contract. Plan confirmations expose one approval action labelled with the chosen execution policy and a rejection action. A permission change during Plan cannot auto-submit pending approval. Briefly disable plan confirmation while a mode update is pending, and prevent new mode updates during plan-approval handoff until the runtime exits Plan or the handoff fails; neither request may overtake the other. Buttons reflect only successful state changes; failures keep the previous state. Session-owner guards prevent late responses updating replacement sessions.

/plan toggles, /plan on enables, /plan off disables through the same action. Preserve `/plan <prompt>` as enter-and-send and /plan exit as a compatibility alias for off. A new session is created with its execution policy, then Plan is applied before submitting the first prompt; preparation failure prevents that prompt.

## Open questions

None for the requested behavior. Cross-process restoration beyond existing session-mode persistence and new mid-turn steering guarantees are out of scope.

## Review corrections

Metadata reads that omit modes, fail, or are skipped during event-stream restart preserve the existing mode and execution policy together. An authoritative non-Plan mode clears the policy. Plan approval receives only the daemon-reported execution policy; a Composer display fallback must never label the approval as executing under a permission the daemon did not report.

For explicit DAC `planMode` controls, `persist: true` saves only the execution policy as the workspace default for future sessions. The requesting session publishes its actual Plan state and selected policy. Existing peer sessions receive neither a mode event nor a cache update. Requests without `planMode` retain the previous workspace-default broadcast behavior.

Regression checks cover metadata reuse after prompt restart, missing-mode context responses followed by a real Plan exit, approval with/without reported execution policy in main and split panes, DAC persistence with Plan/non-Plan peers, and the existing legacy persistence tests.

## Confirmation policy precondition

DAC RestorePrevious responses include the execution policy displayed by the approving client. The bridge preserves this permission-response extension and Session forwards it to the tool. Core reads the current DAC policy once, rejects a missing or different expected policy, and otherwise freezes that value until execution. Legacy Plan without a DAC policy keeps its pre-plan snapshot behavior. Policy equality is sufficient: a change away and back to the same policy does not change the permission the user approved. The lifecycle revision remains separate.

A rejected precondition consumes the old permission request and returns a tool error while retaining Plan. The model must request plan approval again; HTTP acknowledgement does not imply that Plan exited. No client-side retry of the consumed approval is attempted.

The Plan chip and the fallback Plan Switch retain their accessible name and pressed/checked state and directly reference a persistent, dynamic execution-policy description. Mode controls becoming busy close the open permission menu. Slash completion includes the existing exit alias. Unused Plan & Review mode labels are removed; agent-editor Plan labels and workflow review translations remain.
