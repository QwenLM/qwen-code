# Web Shell worktree manager

[English](2026-09-18-web-shell-git-worktree-manager.md) | [简体中文](2026-09-18-web-shell-git-worktree-manager.zh-CN.md)

Status: implemented. Part of [#11941](https://github.com/QwenLM/qwen-code/issues/11941); the commit history lane graph and search from the same issue are described in [2026-09-18-web-shell-git-history-graph.md](2026-09-18-web-shell-git-history-graph.md).

## Problem

A Web Shell user can start a session in a worktree, but nothing in the Web Shell lists the repository's worktrees, shows which of them are dirty or stale, or shows which sessions run inside each. Stale worktrees accumulate unnoticed and cleaning them up means a terminal.

## Current state

- `GitWorktreeService` in `packages/core/src/services/gitWorktreeService.ts` creates and removes the managed worktrees under `<workspace>/.qwen/worktrees/<slug>` for sessions, and the daemon's `POST /session` creates one when the request asks for a worktree. No daemon route lists worktrees.
- Session summaries carry `worktree: { slug, path, branch }` for sessions that live in a managed worktree, both live and persisted.
- `GitDialog` in `packages/web-shell/client/components/dialogs/GitDialog.tsx` hosts the Changes, History, and Pull requests tabs; the Pull requests tab is gated on a daemon capability feature.
- `exit_worktree` refuses to remove a worktree with uncommitted changes unless the caller opts into discarding them.

## Goals

- List every worktree of the workspace's repository with its path, branch, HEAD, lock and stale state, working-tree counters, and the sessions that run inside it.
- Remove a worktree from the list, refusing destructive cases unless the user explicitly confirms them.
- Resume a session that lives in a worktree, and start a new worktree session, from the same surface.
- Reach the surface from the branch chip.

## Non-goals

- No new worktree-creation plumbing: "New worktree session" arms the existing worktree intent of the composer, which creates the worktree through the existing session route.
- No branch deletion on removal; the branch stays and the branch picker remains the place to delete it.
- No listing of worktrees from other repositories or other workspaces.

## Design

### Core

`packages/core/src/utils/git-worktrees.ts` wraps `git worktree list --porcelain -z` into `GitWorktreeEntry` records (path, head, branch, detached, bare, locked, prunable, isMain; the main worktree is the first entry), `git worktree remove [--force --force] -- <path>`, which removes the named registration and only that one, and `git worktree prune` for the shapes remove refuses that git marks prunable, plus `git worktree lock` / `unlock` to shield the rest from it and a reachability check for a detached worktree's HEAD. It shares `runGit` with the branch helpers, and passes the program-valued config keys git would otherwise take from the repository being removed.

### Daemon routes

Three workspace-qualified routes, all **selected-runtime scoped**: they resolve the trusted runtime for `:workspace`, assert its generation is open, and act on that runtime's `workspaceCwd` only. None falls back to the primary runtime. The one deliberate exception is the removal refusal's session count, described below.

- `GET /workspaces/:workspace/git/worktrees` lists the entries plus two derived marks: `isWorkspace` (the runtime's own checkout, compared by real path) and `slug` (the directory name for entries under the runtime's `.qwen/worktrees/`). A non-repository answers `available: false`.
- `GET /workspaces/:workspace/git/worktrees/status?path=` returns the working-tree counters of one listed worktree. The path must match a listed entry exactly; anything else is 404, so a client cannot aim the probe. The listing itself is the bound, and a repository can shape it: `git worktree list` is built from this repository's own `.git/worktrees/*/gitdir` files, so anyone who can write there can make a path outside the workspace appear. The readability gate narrows what that discloses to paths whose `.git` is a gitfile; anything else answers `available: false`. It costs write access to the repository's admin directory, and what it discloses is that path's branch, detached state, change counters, and ahead/behind.
- `POST /workspaces/:workspace/git/worktrees/remove` with `{ path, force? }` runs behind the strict mutation gate. It refuses the main worktree and any registered workspace (409 `worktree_is_main` / `worktree_is_workspace`) regardless of `force`. Without `force` it also refuses when live sessions run in the worktree (409 `worktree_in_use` with `sessions`), when the working tree has staged, unstaged, untracked, or conflicted entries (409 `worktree_dirty` with `changes`, asked with `status.showUntrackedFiles` overridden, because a repository that hides untracked files hides them from git's own safety check too), when a rebase, merge, cherry-pick, revert or bisect is unfinished (409 `worktree_operation_in_progress`, which leaves every counter at zero), when a detached worktree is the last thing pointing at its own commits (409 `worktree_unmerged_commits` with `unmergedHead`), when the worktree is locked (409 `worktree_locked` with git's `reason` when it recorded one, redacted and bounded like any other git prose, since anyone who can run git in the repository writes it), or when the working tree cannot be read (409 `worktree_status_unknown`). Every refusal leaves through one place, which attaches the rest of what the second click would take — the counters, an unfinished operation, commits no ref keeps, a nested repository, or the fact that none of it could be counted: the second click overrides all of them at once, and uncommitted work is the part that does not come back. A lock is read from the listing, so git is never asked to refuse it — but only where `--force --force` could clear it, meaning a checkout git can still reach, or a path holding nothing at all. A dangling symlink is not nothing: git finds the link and fails on it, so that shape and a directory that outlived its gitfile are both left to git, because a second click there has nowhere to land; every other refusal git makes on its own comes back as 409 `worktree_remove_refused` with git's redacted sentence in `detail`, provided nothing changed and git can still reach the checkout — and every refusal carries `submodules` when the checkout holds an initialised one, since forcing deletes its repository along with everything else and no counter sees it. An entry git cannot reach skips the working-tree probe, and the status route answers `available: false` for it. The test is whether `<path>/.git` is a gitfile, which is how git reaches a linked worktree and is also the first step of the walk that would otherwise go wrong: `getGitWorkingTreeStatus` resolves the repository by walking _up_ from the path it is given, so for a managed worktree it sails past the broken entry and answers with the **main** worktree's branch and counters, attributed to the worktree that was asked about. A `.git` directory there is some other repository created in place, and answering with its branch misattributes just as badly, so only the main worktree's counts. git's own prunable mark is not the test either, because a _locked_ worktree never gets it even once its gitfile is gone. Removal is per-path — `git worktree remove` drops one registration and leaves the repository's other stale ones alone. git deletes the directory first and drops the registration second, and a deletion it could not finish (a read-only subtree, a file another process holds open) does not stop the drop, so a rejection is re-checked against the listing: the registration is what this route removes, and if it is gone the request is done rather than a failure whose retry would 404. The fallback runs for any registration git has already marked prunable, which is the only mark that says prune would clear it. Two shapes reach it: a directory that outlived its gitfile, and a path that is no longer a directory at all, a dangling symlink being the reachable case. git refuses both per-path at every force level and clears both with prune. The shapes it refuses _without_ marking prunable are in Constraints, and the fallback does not run for those. Prune is repository-wide (git has no per-path form), so the route locks every other stale registration for the duration — git skips locked worktrees, and stops marking a locked one prunable — then releases them. The listing is not the same set as what prune drops, though: a registration whose gitdir file is missing or empty is absent from it, cannot be locked, and is dropped all the same. So the shield is proven against `git worktree prune -n -v`, which names every admin directory prune would take; unless that comes back naming exactly one, the route reports git's refusal instead of pruning: a failed removal is retryable and a bystander's commits are not. A lock left behind by a removal that died in between names this route, and the next removal of that entry releases it, since git refuses a locked worktree at every force level and prune skips it. Prune deletes no files in the working tree, and because a lock taken after this request read the listing would make prune skip the entry silently, the route re-lists afterwards and surfaces git's own refusal rather than reporting a removal that did not happen. A success carries `directoryRemains` when anything is still at the path — asked with `lstat`, so a symlink left behind counts, and answered `true` whenever the daemon cannot see the path at all, since a removal it could not watch is exactly the one that leaves a whole checkout behind. That is what the prune fallback and an unfinished deletion leave. git failures pass through the shared redacted git error path.

The session count is the single place a route reads outside the runtime it resolved. It enumerates every registered workspace's current runtime — `listManaged`, not `listAll`, because a workspace that is draining, blocked, or mid-replacement still holds a live bridge with live sessions — and counts those whose worktree path matches, keyed by session id so the number the user sees counts each session once. A worktree of this repository can host a session belonging to a _different_ registered workspace, and `worktree_is_workspace` fires only when the worktree _is_ a workspace root — counting only the selected runtime would let that session lose its checkout without even asking for `force`, which is exactly the harm the refusal exists to prevent.

Removing a worktree that belongs to another repository is not a case the routes have to defend against: git validates that the target's `.git` is a gitfile _and_ that it points back at the admin directory git resolved, and `--force --force` bypasses neither check, so a planted registration fails closed on git's own validation.

The capability feature `workspace_git_worktrees` advertises the routes; older daemons keep the tab and the chip entry hidden.

### SDK

`WorkspaceDaemonClient` gains `workspaceGitWorktrees()`, `workspaceGitWorktreeStatus(path)`, and `workspaceGitRemoveWorktree(path, { force })` with the matching `DaemonGitWorktree*` types.

### Web Shell

`GitWorktreesContent` in `packages/web-shell/client/components/dialogs/GitWorktreesDialog.tsx` is the fourth `GitDialog` tab, "Worktrees", shown when the daemon advertises the feature. On open it fetches the worktree list and the workspace's session list together, joins sessions to worktrees by `worktree.path`, and renders one row per worktree: slug or directory name, badges (main, this workspace, locked, stale), branch or detached HEAD, short HEAD, working-tree state, the sessions inside it as chips, and a remove button for removable entries. Working-tree state is fetched lazily after the list renders, three requests at a time, so a repository with hundreds of worktrees lists instantly. A filter box narrows by path, branch, or slug.

Removal is a two-step inline confirmation, and the first step says what it will actually do: a stale entry is described as bookkeeping git already lost rather than a directory about to be deleted. The first request never forces. A 409 from the daemon turns the confirmation into an explanation of what would be lost (uncommitted change count, running session count, or the lock's reason) with a "Remove anyway" button that repeats the request with `force: true`. For a refusal git made itself, the explanation is git's own sentence. Other failures show the daemon's message and only offer Cancel. A successful removal re-fetches the list, and when the daemon reports the directory outlived the registration the tab says so above the list — the row it concerns is the one that just disappeared, and a row disappearing reads on its own as the directory having gone.

Clicking a session chip closes the dialog and switches to that session; "New worktree session…" closes the dialog and starts a draft with the worktree intent armed, the same path as the sidebar's entry. `BranchPickerPopover` gains a "Worktrees…" action after "Manage Remotes…"; `ChatEditor` and `EnvironmentPanel` thread it from `App`, which passes it only when the daemon advertises the feature.

## Constraints

- Removing a worktree runs git with the repository's program-valued config keys stripped, the way every other git helper in core does. A worktree's own `.git/config` chooses `core.fsmonitor`, and git runs it on the index refresh the non-forced removal's status check triggers.
- The worktree list is repository-wide, so it includes worktrees created outside Qwen Code. They can be removed like any other, subject to the same refusals.
- A worktree that is another registered workspace's root still shows a remove button, because the row's `isWorkspace` mark answers about the selected workspace while the refusal spans every registered one. The daemon refuses it at every force level, so the button cannot destroy anything; it simply cannot succeed either. Marking it on the wire is follow-up work.
- Some broken shapes cannot be cleared from the tab at all, because git refuses them at every force level and prune either skips them or does not apply: one that is locked with its gitfile gone, one whose `.git` is a directory (a repository created in its place), and one whose `.git` is a regular file that is not a valid gitfile — holding bytes git does not understand, naming a directory that is not there, or pointing back at another repository. git marks none of them prunable, so the fallback does not run. The lock arm asks whether forcing could work before it offers a second click, but it asks by the _shape_ of `.git` and not its contents, so one of that last group which is also locked is offered a force that fails. A hand at a terminal is the way out. A lock on an otherwise healthy worktree is _not_ in this group: `--force --force` clears it, which is why the lock refusal is forceable.
- Not every refusal is one the route can anticipate. git declines to remove a worktree holding initialised submodules and calls that worktree clean, so no counter and no listing mark can see it coming; it clears under `--force --force`. Rather than name git's refusals one by one, a non-forced removal that fails while leaving the registration in place comes back as `worktree_remove_refused` carrying git's own sentence, and the tab offers the same second click a dirty worktree gets. A refusal after `force` is not offered again, and neither is one for a checkout git can no longer reach.
- Both removal refusals compare paths for equality, not containment. A workspace registered at a path _inside_ a worktree, or a session rooted there without worktree metadata, is therefore not what `worktree_is_workspace` or `worktree_in_use` protect; the dirty check covers uncommitted work anywhere in the worktree's tree, but an ignored nested checkout does not count as a change, so it does not cover that. Equality is inherited from the surfaces this builds on and is left deliberate rather than widened here.
- Clearing a registration whose directory outlived its gitfile prunes every _other_ stale registration too, because git offers no per-path prune. That holds even when the removal then reports failure — the fallback prunes before it can discover the entry it was asked about survived a lock taken mid-request — so the tab re-reads its list after a failed removal as well as a successful one. Nothing on disk is deleted, and every other removal is per-path. Such an entry is also dropped on the first click without a `worktree_dirty` refusal: git has stopped treating its contents as a checkout, so there is no working tree to call dirty, and nothing in it is deleted.
- Every refusal names everything the second click would discard, not only the one the daemon refused on: the uncommitted count, an unfinished operation, commits no ref keeps, a nested repository, and the fact that none of it could be counted. Sessions come first, because forcing past them strands a checkout while forcing past a lock destroys nothing — the lock is bookkeeping, and the row carries its badge either way. When the working tree cannot even be looked at, that is said too: not being able to count the work is not the same as there being none. Otherwise a lock or a live session reported by itself sends the user past uncommitted work that was never mentioned, since `force` overrides all of them together.
- Removal usually deletes the directory, and says when it did not: a registration git has already lost is cleared by a prune that deletes no files, and a deletion git could not finish still drops the registration. Both report `directoryRemains`. Force removal discards uncommitted work and leaves live sessions with a missing cwd; the confirmation says so before the second click, says the other thing for a stale entry, and for a detached worktree promises no branch, because there is none to keep.
- Sessions are joined on the client from one page of the session list (100 entries); a worktree whose sessions fall outside that page shows none. The join is also by exact path while the daemon's count resolves symlinks first, so where a session's recorded path and git's listing spell one directory differently, a row can show no chips and still be refused as in use. Both bound what the tab _displays_, not what the daemon refuses: the removal check counts sessions server-side, unpaged, across every registered runtime. The join predates this change.
- Working-tree state is read once per worktree per refresh, never polled. A refresh re-reads every worktree rather than only the new ones, which is one git process per worktree at concurrency three — the price of not showing a cached “clean”. A worktree another session dirties while the tab sits open keeps its badge until the next refresh; the daemon re-reads the working tree on every non-forced removal, so a stale badge can mislead a reader but cannot let a removal through.
- Files the repository ignores are deleted with the directory and are not counted, because `git status` excludes them and counting them would refuse every worktree with a build directory. The ordinary confirmation says the directory goes, which is what happens to them.
- A lock reason is free-form text, so the shared git-output redaction is a weaker guarantee for it than for git's own prose. The workspace's own path always goes, and so does any path the sweep can see — it recognises one after whitespace, a quote or a bracket, which is where git always puts them. A reason that writes `owner=/elsewhere/secret` keeps that path. Whoever wrote the reason had local git access to this repository and already knew it, so this is defence in depth rather than a boundary.
- The status route's reach is bounded by git's own worktree listing rather than by the workspace root — see the route description above.

## Acceptance criteria

- The Worktrees tab lists every worktree of the repository with path, branch, state, and sessions, and loads instantly even with hundreds of entries.
- A clean, idle linked worktree can be removed after one confirmation; a dirty, locked, session-hosting one, or one git refuses for a reason of its own, needs a second, explicit "Remove anyway" and is never a dead end where the daemon could have done it.
- The main worktree and registered workspaces can never be removed from the tab, and a worktree hosting a live session is refused whichever workspace that session belongs to.
- A session listed under a worktree opens on click; "New worktree session…" starts a worktree draft.
