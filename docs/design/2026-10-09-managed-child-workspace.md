# Managed child Workspace capability (isolation slice, I1)

[English](2026-10-09-managed-child-workspace.md) | [简体中文](2026-10-09-managed-child-workspace.zh-CN.md)

Status: I1 is implemented in this change. Landed: the child Workspace (a Git linked worktree inside the parent's storage), its durable command with fencing and recovery, its merge and discard finishes, the storage-lease maintenance hold, and the binding of a child Session to a prepared child Workspace. Still design: I2 (`worktree` admission, relay and cascade wiring) and I3 (`snapshot`, and the serialization decision), each with its own later slice (Follow-up work). This is the isolation slice of [#12827](https://github.com/QwenLM/qwen-code/issues/12827), stage H of the Managed Agent proposal [#12380](https://github.com/QwenLM/qwen-code/issues/12380), tracked by [#13753](https://github.com/QwenLM/qwen-code/issues/13753). It was split from H4c ([#13743](https://github.com/QwenLM/qwen-code/issues/13743), PR #13754), whose [design](2026-10-09-managed-workflow-child-kind.md) settles the vocabulary in its decision 11. It follows H4a ([record contract](2026-10-06-managed-child-agent-runtime.md)) and H4b ([child Session runtime](2026-10-07-managed-child-session-runtime.md)).

## Problem and scope

Issue #13753 asks for three items:

- **I1, a Workspace capability.** A provider operation that creates a child worktree from the parent's bound Workspace at a recorded revision, binds a child Session to it, and later merges it back or discards it. It needs its own durable command, fencing and recovery.
- **I2, `worktree` admission.** The relay creates a `worktree` child in its own Workspace, the settle and close paths run the merge policy, and the launch admission admits `worktree`.
- **I3, `snapshot` and serialized sharing.** A read-only frozen view, and a decision on whether a per-child generation or barrier is needed beyond the Workspace lease.

This change delivers I1 and records the direction of I2 and I3. Nothing in it is reachable from a model: `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` still admits `shared` only, the relay never prepares a child Workspace, and the capability is off unless an operator enables it. This is the same order H4a used: the capability lands, proven by its own suites, before any producer.

## Current state

The facts below are from `main` at `9e9d1c037d`, after H4c (#13754) landed the `workflow` child kind.

- **Child binding.** `ManagedAgentStore.insertChildSessionCommand` copies the parent's whole binding into the child row with one `INSERT ... SELECT`: Workspace, generation, storage, `cwd_relative`, context and policy refs. The record's `workspaceMode` and `workingDirectory` are validated in both languages, but no runtime reads them.
- **Storage and mounts.** A storage's root is an administrator mount (`runtime-broker.workspace-mounts`: tenant, storage, root). Mounts are static, canonical and must not overlap or nest. W1 §5.1 asks operators to keep the storage root outside every Git worktree and to place Session working directories in its children.
- **The storage lease.** `managed_workspace_execution_lease` holds one row per storage and one holder at a time. The holder is a Runtime Session (`binding_id`, `runtime_generation`, `runtime_session_id`). A tool turn that meets another holder receives the retryable `workspace_busy` and polls. W1a fence and registration require an idle lease; W0e `releaseLost` clears the holder of a lost binding and treats any other holder shape as corrupt.
- **Worker containment.** The worker resolves a binding as the mount root joined with `cwd_relative`. Tools may reach anywhere inside the mount except the directory of another installed Session. W1 §5.1 states that this layout reduces accidents and does not confine host-permitted tool access.
- **Git.** No Java code runs Git. TypeScript has worktree primitives for the daemon and the legacy Agent tool (`createUserWorktree`, `removeUserWorktree`). Its only merge back is Arena's `applyWorktreeChanges`, which applies a patch and reports a conflict as Git's error text. This capability does not build on them: they run in the daemon rather than the control plane that owns the storage lease, keep no durable record bound to a child run, and surface a conflict only as error text.

## Decisions

1. **A child Workspace is a Git linked worktree inside the parent's storage.** Its directory is `<storage root>/.qwen-child-workspaces/<childWorkspaceId>`, where `childWorkspaceId` is the first 32 hex digits of `sha256(tenant NUL parentSessionId NUL childRunId)`. The child binding keeps the parent's tenant, Workspace, generation, storage, context and policy refs; only `cwd_relative` changes, to the worktree directory plus the parent's offset inside its repository. This was chosen over a storage of its own because mounts are static and cannot nest, so a new storage would need dynamic mount registration, a new W1a guard and, under Kubernetes, a new CSI registration. One storage keeps the mount guard, the marker, the lease and, later, the same PVC.
   - Consequence: a child's tool turns still serialize with the parent's through the one storage lease, exactly as `shared` children do. Isolation here is isolation of working trees. It is neither concurrency nor a security boundary (W1 §5.1).
   - The worktree shares the parent's object store and refs, as every linked worktree does. Commits the child makes in its detached worktree are not merged as commits: the merge reads the worktree's content.
2. **The layout is checked, never assumed.** The parent's working directory must lie in a Git repository whose top level is strictly inside the storage root, and whose Git directory and common directory are inside it too. A storage root that is itself inside a repository (the layout W1 §5.1 rules out), a directory outside any repository, a bare repository, a repository inside the reserved directory, a Git directory that points outside the root, a link where these commands make Git write or delete (`refs`, `logs` and `worktrees` at any depth, `objects` and its entries, and `packed-refs`, whose lock file Git places beside the file a link names), which would carry a write or a deletion out of the storage, a parent directory the snapshot does not carry (an empty or ignored one), or a child directory that would break the rule every Session directory meets (at most 1024 code points), is refused as `child_workspace_layout`. The reserved `.qwen-child-workspaces` directory must be a real directory, never a symbolic link.
3. **The base revision is a snapshot commit of the parent's working tree.** At preparation the control plane reads `HEAD` into a private index file, runs `git add -A` against it, and commits the resulting tree on top of `HEAD`. The private index starts from `HEAD` rather than from a copy of the parent's index, because a copy would carry `assume-unchanged` and `skip-worktree` bits that hide changes from `git add`. The commit therefore holds what the parent's working tree holds: committed, modified and untracked non-ignored files, with the working-tree version of a path even when a different one is staged. The parent's own index, `HEAD` and working tree are never touched. Ignored files (build output, `node_modules`) are not carried. The commit uses a fixed identity and fixed dates, so recomputing it over unchanged content names the same commit; its message names the child Workspace, so two children prepared from the same parent state still get bases of their own. Its id is recorded before the worktree is created, and the worktree is checked out detached at it.
4. **Commits are pinned while the row needs them.** The base is pinned as `refs/qwen/child-workspaces/<id>/base`, and a computed result as `.../result`, so `git gc` never collects them. A merge deletes both pins. Every other finish keeps the result pin when a result exists, so a discard never deletes work the child produced unless that work was merged.
5. **The merge policy is a three-way merge into the parent's working tree, computed off-tree.**
   - The child's result `C` is a snapshot of the worktree (the same private-index technique) on top of the base `S`.
   - The parent's current state `P` is a snapshot of the parent's working tree.
   - `git merge-tree --write-tree --merge-base=S P C` computes the merged tree `M` without touching any working tree or index.
   - On a conflict the row ends `conflicted` with the conflicting paths (at most 100 recorded), and nothing is written into the parent. A merge conflict is a durable outcome and never a silent overwrite. The worktree and the base pin are removed at once, while the child's result stays pinned (decision 4); a discard then retires the row.
   - On a clean merge, only the paths that differ between `P` and `M` are written, as uncommitted changes in the parent's working tree. The parent's index and `HEAD` stay as they were, so the child's work arrives exactly like edits the parent made itself.
   - Two kinds of path in a clean merge cannot be written, and end the row `conflicted` like a conflict: a submodule pointer the merge moves, because a patch cannot move one, and a path the merge adds where the parent holds an ignored file or directory, or an ignored file where one of the path's directories must go, because the write would overwrite content `P` does not carry. A path whose name is not UTF-8 is reported the same way, because the write could not spell it byte for byte.
6. **The write is resumable and checked path by path.** `P` and `M` are recorded before anything is written. Each write attempt snapshots the current working tree `W` and requires every changed path to hold either its `P` or its `M` version; the paths still at `P` are written to `M` with one `git apply` of a tree-to-tree patch. Each changed path is judged by what is on disk, ignored or not, so a merged path the parent ignores (it started ignoring the directory while the child ran, or the child force-added the path) is neither refused by the verification nor written twice. A crash between two files therefore resumes where it stopped. Any other content means something outside the lease changed the tree; the row ends `blocked` and nothing is overwritten. The patch's shape is pinned (no colour, three lines of context), because the repository's config could otherwise make it unappliable. After the write, the tree is verified against `M`. The merge and its write run under one maintenance hold (decision 10), so no tool turn can change the parent's tree between computing `M` and writing it.
   - Under the same hold the row then moves to `applied`, before the worktree and the pins are removed. A resumed `applied` row only removes them and never judges the parent's tree again: the storage was free since, and an edit there is the parent's own. The one window left is a failure between the write landing and that record; the resumed `applying` row checks the tree again and ends `blocked` if a tool turn edited a merged path meanwhile.
7. **Discard removes the worktree and keeps the produced work.** Discard removes the registered worktree with `git worktree remove`, then removes whatever is still at the reserved path without following any symbolic link in it, removes the worktree's own administrative directory (the entry under `<commonDir>/worktrees` whose `gitdir` names it, never through `git worktree prune`, which would judge the parent's worktrees too), removes the refs the child created, and deletes the base pin. The reserved path belongs to the control plane, so a directory the model replaced or emptied there goes too, and a symbolic link left there is removed as a link and never followed. When the recorded repository is gone (no Git directory at its top level), only the directory is removed. Any other refusal, such as an unsafe config (decision 11), a changed layout or a momentary fault, fails the discard like any other step, so the registration and the pins are never skipped. Discard is the finish for failed and cancelled children, and the way out of `conflicted` and `blocked`.
   - A branch or tag the child creates lands in the repository's shared refs, where removing the worktree does not reach it. Before the worktree exists, the repository's ref names are recorded beside it (`.qwen-child-workspaces/<id>.refs`). When a result exists, the discard that removes the worktree reads the child's `HEAD` first and deletes every ref absent from that record that contains this child's base (decision 3) and lies on that `HEAD`'s line, whose final content the result holds; a symbolic ref is deleted itself, never its target. A side branch off that line is left alone, so no commit that only a ref holds is lost; without a result, or when the worktree is already gone or unreadable, nothing is deleted. Nothing at all is deleted once the base has reached anyone else's history: when the parent's `HEAD`, a ref the parent had (even one the child moved), a ref a worktree has checked out, or another child's pin contains it, as after the parent merges a child's branch. `refs/stash`, whose one reflog holds the parent's stashes too, is never deleted, so a child's stash stays in the stash list. A record that is not a regular file of at most 16 MiB is not read, and then nothing is deleted; whatever stands at the record's name is removed with the worktree. A branch the parent itself pointed at the child's line while the child ran, without taking it into a ref it had or its `HEAD`, still meets the rule and is deleted with the child's own; its commits stay in the result.
8. **One durable row per child run.** `qwen_managed_child_workspace` (V60) holds one row per (tenant, parent Session, child run). Its states are:
   - `preparing` → `ready`, or `failed` when the layout is refused (no worktree, pin or recorded base; at most an unreachable snapshot object that `git gc` collects).
   - `ready` → `merging` → `applying` → `applied` → `merged`, or `merging` → `conflicted`.
   - `preparing`, `ready`, `conflicted`, `blocked` or `failed` → `discarding` → `discarded`.
   - Any active state → `blocked` when the evidence cannot be reconciled. An `applied` row that ends `blocked` keeps `merged` as its outcome, with the cleanup's failure as its last error, also through a later discard that fails; its discard removes both pins.

   A discard that cannot finish ends `blocked` with its request cleared, so the row never loops back into the discard that just failed; a new discard request retries it. The finish request (`merge` or `discard`) is recorded once. A repeated request answers the row; a different one is refused, except that `discard` may follow a `merge` that ended `conflicted` or `blocked`. A merge is admitted only from `ready`, and no finish is admitted while the bound child Session is not closed, because a finish would remove the directory under a running Session.

9. **Claims fence the writers; a scan resumes the work.** The row carries `claimed_by`, `claimed_until` and `claim_generation`. Every transition is a compare-and-set on the state and the claim generation, so a worker whose claim expired cannot commit a step. A scheduled scan (`qwen.managed-agent.child-workspace.scan-delay`, 2 s) drives every row in an active state or with an owed finish, and the operations called from a service drive the same steps synchronously. Every physical step is idempotent and reconciles from what is on disk and in the row, never from memory. A claim lasts 2 minutes and is renewed every third of that while its step runs, so a slow Git command never lets a second worker into a step that is still going; it is released when the step ends. A live claim is never taken twice, not even by its own worker, so a synchronous call and the scan never run one row at once. A step whose claim moved on, or could not be renewed for most of its life, stops: no further Git command starts, and the running one is killed, so a worker that lost its claim never writes beside the one that took the row over. A step that cannot get the storage lease waits 1 s without spending an attempt. A scan drives at most 20 rows and starts none after 60 s, leaving the rest to the next scan. Other failures retry with a backoff that doubles from 1 s to 60 s, and after 16 attempts the row ends `blocked` with the last error.
10. **Physical steps run under a maintenance hold on the storage lease.** Before each step the worker takes the storage's `managed_workspace_execution_lease` row as a maintenance holder: `holder_key = sha256("child-workspace" NUL id NUL claimGeneration)`, the Runtime holder columns null, and the new `maintenance_id` column set to the row id. It releases the hold when the step ends.
    - A tool turn meeting the hold receives the existing retryable `workspace_busy` and polls, so a merge never races a turn that writes the parent's tree.
    - W1a fence and registration need an idle lease, so they refuse, non-retryably, while a hold exists; an operator retries them once the step ends.
    - W0e `releaseLost` recognizes the maintenance shape as not belonging to the lost binding and leaves it alone, instead of refusing as corrupt.
    - Taking the hold requires the row's current claim generation, read under a lock in the same transaction: a worker whose claim another worker took over is refused, and the new claimant may replace a hold carrying its own `maintenance_id`. A stale worker's release names its old claim generation, so it can never release the new hold. An expired claim that is still the current generation may take the hold; the scan frees it once nothing renews that claim.
    - The hold takes the same W1a storage guard check as a Runtime claim.
    - A hold outlives its step only until the next scan, which first releases every hold whose child Workspace no live claim owns: a worker that died, or failed to release, after its last step. It does so on every host, with the capability on or off, because it needs no Git and nothing else frees that storage. Where the capability is on, a hold whose child Workspace is still in a step's state is kept instead: the scan resumes that row, and its new claimant takes the hold over, so no tool turn slips in between. A host with the capability off frees such a hold only 4 minutes (twice the claim) after its claim expired, leaving it to a host that runs steps first. A host judges claim expiry by its own clock, so hosts must keep their clocks within the claim's renewal margin (about 80 s).
    - W1c storage migration counts a child Workspace that is not `merged`, `discarded`, `failed` or `conflicted` as unsettled work, because its worktree records absolute paths of the storage root.
    - Like a `shared` child's tool turns, a step waits while the parent's Hook catalog or MCP owner holds the storage for the whole Session. The Agent tool already refuses a child launch in that state (H4b), and I2 keeps that refusal.
11. **Git runs hardened, because the model can write the repository.** Each command runs with:
    - A cleared environment: only `PATH` survives. `HOME` and `XDG_CONFIG_HOME` point to an empty private directory, system and global config are disabled, and prompts, optional locks and replace objects are off. Child Workspaces are not supported on Windows, and need a JVM whose file names are UTF-8 (`sun.jnu.encoding`, set by the locale); enabling them otherwise fails startup.
    - Discovery bounded by `GIT_CEILING_DIRECTORIES` at the storage root, so Git never finds a repository above it.
    - Hooks disabled (`core.hooksPath` overridden to an empty private directory, which covers the default hooks directory and `reference-transaction` too), `core.fsmonitor` overridden empty, `core.safecrlf` off (a line-ending check would otherwise refuse or flood every snapshot), `log.showSignature` off, automatic `gc` and maintenance off, `--no-gpg-sign` on every commit, and `--no-ext-diff --no-textconv` on every diff.
    - A configuration check: before each step the repository's own config files (the common `config` and, when `extensions.worktreeConfig` is on, `config.worktree`) are read as data with includes off. The step is refused as `child_workspace_unsafe_config` if a key that these commands can reach names a program or redirects Git: `filter.*`, `merge.*.driver`, `diff.external`, `diff.*.command`, `diff.*.textconv`, `core.worktree`, or any `include.*` or `includeif.*`, whose included keys the check cannot see. A `.gitattributes` file reaches a program only through such a key, so this also closes clean and smudge filters and merge drivers. A promisor remote (`extensions.partialClone`, `remote.*.promisor`) is refused as well: any command that meets a missing object would fetch it lazily and run the remote's transport programs. Keys these commands never reach are not refused, so ordinary repositories pass: no command opens an editor or a terminal or signs, and the two hook keys are overridden rather than read. A boolean key (`extensions.worktreeConfig`, `core.sparseCheckout`, `core.bare`) counts as on whenever Git reads it so: a valueless key, any non-zero integer, or `true`, `yes`, `on`; a value Git cannot read counts as on, the side that refuses.
    - Defense in depth behind the promisor refusal: lazy fetches are disabled (`GIT_NO_LAZY_FETCH`, Git 2.45 and later) and every transport protocol is disallowed (`GIT_ALLOW_PROTOCOL`), so no command talks to a remote.
    - A sparse checkout is refused as `child_workspace_layout`, because the private-index snapshot would read every file outside the sparse cone as deleted.
    - A time bound per command (`qwen.managed-agent.runtime-broker.child-workspace-git-timeout`, 120 s, refused at startup outside 1 s to 1 h) and a bound on each output stream (256 MiB) checked while the command runs; only the first 512 characters of the error output are read. A command stopped for its bounds or a lost claim is killed with every process it started, such as the checkout `worktree add` runs. The executable is `child-workspace-git` (`git` on the `PATH` by default).
    - Pins are written and deleted with `--no-deref`, and a symbolic ref at a pin's name is no pin, so a planted symbolic ref never redirects a pin to a branch.

    The check runs under the maintenance hold, so no tool turn can change the config between the check and the command. A process the model left running outside any turn is not covered; that is the residual W1 §5.1 already names.

12. **The capability belongs to the Workspace provider and is off by default.** `RuntimeWarmer.childWorkspaces()` answers the provider, or null. `EmbeddedRuntimeBroker` answers one only when `qwen.managed-agent.runtime-broker.child-workspaces-enabled` is true, the deployment has Workspace mounts, and a startup probe finds Git 2.40 or later (the first release with `merge-tree --merge-base`; every other option the steps pass is older, and both suites pass against Git 2.40.0). Enabling it without Workspace mounts, or with an older Git, fails startup. Without the provider, `prepare` refuses with `child_workspace_unsupported` and commits nothing.
13. **Binding a child Session to its Workspace.** `createChildSession` gains an `isolated` argument. When set, the store locks the row of the same parent and run in the creating transaction, requires it to be `ready` with no finish requested, prepared from the parent's current Workspace, generation and storage, and naming the requested directory, and inserts the child with that directory instead of the parent's. A finish request locks the same row, so a creation and a finish never pass each other. The child directory is part of the request digest, so a replay that names a different binding is an idempotency conflict. A row that is not `ready` refuses the creation with `child_workspace_not_ready`.
14. **I2 direction.** The relay prepares the child Workspace of a `worktree` run before `createChildSession`, then creates the child bound to it. On `completed` it finishes `merge` before `commit_result`, so the terminal receipt can report `merged` or `conflicted` with the paths. Decision 8 refuses a finish while the child Session is open, and today the relay closes a finished child only after its result is committed, so I2 moves that close ahead of the merge for `worktree` runs. On failure, cancellation, quota or give-up it finishes `discard`, and the close cascade discards the Workspaces of the children it cancels. `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` then admits `worktree`, for `child_agent` and `workflow` alike. Whether the merge outcome needs a record key or travels in the terminal receipt is I2's decision. I2 builds on H4c (#13754, merged), whose files it shares.
15. **I3 direction.**
    - Serialized sharing needs no value of its own. The storage lease admits one holder at a time, and every writer of a storage, parent, `shared` child, `worktree` child or child Workspace maintenance, takes it before writing. So no two of them can hold the storage at once, and the lease is already the generation barrier the 2026-10-04 framing asked for.
    - `snapshot` can reuse this capability: a child Workspace that is always discarded, bound to a child whose tool profile refuses every write. I3 decides whether a profile-level refusal is enough evidence of "cannot write".

### `qwen_managed_child_workspace` (V60)

| Column                                                                    | Meaning                                                                                                                                   |

| `attempts`, `next_retry_at`, `created_at`, `updated_at`                   | Retry bookkeeping.                                                                                                                        |

Rows are never deleted, so every read keys on what it filters: the scan on `(state, finish_request, next_retry_at)`, where each arm of its predicate is a range, and the migration gate on `(tenant_id, storage_id, state)`.

### `managed_workspace_execution_lease.maintenance_id` (V60)

A nullable column naming the child Workspace that holds the storage as a maintenance holder (decision 10). It is null for every Runtime holder and for an idle lease, and indexed so the stale-hold release reads only held rows.

## Non-goals

- I2 and I3, beyond the direction recorded in decisions 14 and 15.
- A provider other than the local process one. The Kubernetes and CSI providers answer no child Workspace provider, and their own slices decide whether the Git steps run in the control plane or in the Pod.
- Concurrent writing by parent and child. The lease still serializes them.
- Merging commits or branches. The child's work lands as uncommitted changes, and the parent decides what to commit.
- Submodule contents. A submodule's gitlink is carried as an entry and its working tree is not materialized in the child; a merge that moves a gitlink ends `conflicted` (decision 5).
- Any public contract change. The OpenAPI contract, routes and record bodies stay as they are.

## Validation

- **Git steps** (`ChildWorktreeGitTest`, 48 cases against real repositories in temporary directories):
  - Snapshot: carries the working tree, not ignored files, whatever the parent's index says (`skip-worktree`, `assume-unchanged`, a staged version that differs), leaves the parent's index, `HEAD` and status untouched, and is deterministic; a `core.safecrlf` repository neither refuses nor floods it.
  - Layout: the offset, and every refusal of decision 2, including a storage root inside a repository and a sparse checkout spelled `true`, `2` or with no value (an empty value passes).
  - Configuration: an unsafe config refused with its filter program never run; an include refused; a `config.worktree` switched on by `2` or by a valueless key read too; the same check on the child's own `config.worktree`; the boolean matrix; the refused-key matrix; a promisor remote refused as `child_workspace_unsafe_config` with its transport program never run.
  - Overrides: a repository `core.hooksPath` hook, the default hooks directory's `post-checkout` and `reference-transaction`, and a repository `core.fsmonitor` never run; every command sees only the runner's own environment.
  - Merge and write: a clean merge landing as uncommitted changes with `HEAD` and the index untouched, a child commit merged as content, the worktree, both pins and the child's branch and tag removed while the parent's refs stay; the sweep deleting symbolic refs themselves and keeping the result pin and the parent's stashes; the sweep taking only the child's checked-out line, and nothing without a result or once the worktree is gone; a discard with a file at the container's name; the sweep standing down once the base reaches another history (a branch the parent had, a checked-out branch, the parent's branch or detached `HEAD`, a sibling's base); siblings from one parent state getting bases and sweeps of their own; a ref record too large to read sweeping nothing, and whatever stands at its name removed; a symbolic ref at a pin's name replaced, never followed; names beyond ASCII merging, and a name that is not UTF-8 a conflict; a merged path the parent ignores landing and resuming; a tracked file the merge turns into a directory landing; a merge that would overwrite an ignored file, or put a directory where an ignored file stands, and a moved submodule pointer, ending as conflicts, the write refusing a recorded gitlink change too; colour and zero-context diff config not spoiling the write; a conflict naming its path and writing nothing; the apply resuming from a half-written tree and refusing to overwrite a path changed outside the lease.

## Acceptance criteria

- A child Workspace can be created, bound, merged and discarded idempotently across a control-plane restart.
- A merge conflict surfaces as a durable `conflicted` outcome and never as a silent overwrite.
- A child Workspace's writes do not appear in the parent's tree until its merge runs, and a discarded child's worktree is removed.
- No model-reachable behavior changes: `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` is `['shared']`, and the capability is off by default.

## Open questions

1. **Where the Git steps run for containerized providers**: in the control plane against the mounted volume, or inside the Pod through a worker operation.
2. **Retention of result pins** after a `conflicted` or `blocked` row is discarded: kept until an operator removes them, or bounded by the Session archive.
3. **The merge outcome's contract**: a record key, or the terminal receipt (I2).
