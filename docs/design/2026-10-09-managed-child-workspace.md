# Managed child Workspace capability (isolation slice, I1)

[English](2026-10-09-managed-child-workspace.md) | [简体中文](2026-10-09-managed-child-workspace.zh-CN.md)

Status: I1 is implemented in this change. Landed: the child Workspace (a Git linked worktree inside the parent's storage), its durable command with fencing and recovery, its merge and discard finishes, the storage-lease maintenance hold, and the binding of a child Session to a prepared child Workspace. Still design: I2 (`worktree` admission, relay and cascade wiring) and I3 (`snapshot`, and the serialization decision), each with its own later slice (Follow-up work). This is the isolation slice of [#12827](https://github.com/QwenLM/qwen-code/issues/12827), stage H of the Managed Agent proposal [#12380](https://github.com/QwenLM/qwen-code/issues/12380), tracked by [#13753](https://github.com/QwenLM/qwen-code/issues/13753). It was split from H4c ([#13743](https://github.com/QwenLM/qwen-code/issues/13743), PR #13754), whose [design](2026-10-09-managed-workflow-child-kind.md) settles the vocabulary in its decision 11. It follows H4a ([record contract](2026-10-06-managed-child-agent-runtime.md)) and H4b ([child Session runtime](2026-10-07-managed-child-session-runtime.md)).

## Problem and scope

Issue #13753 asks for three items:

- **I1, a Workspace capability.** A provider operation that creates a child worktree from the parent's bound Workspace at a recorded revision, binds a child Session to it, and later merges it back or discards it. It needs its own durable command, fencing and recovery.
- **I2, `worktree` admission.** The relay creates a `worktree` child in its own Workspace, the settle and close paths run the merge policy, and the launch admission admits `worktree`.
- **I3, `snapshot` and serialized sharing.** A read-only frozen view, and a decision on whether a per-child generation or barrier is needed beyond the Workspace lease.

This change delivers I1 and records the direction of I2 and I3. Nothing in it is reachable from a model: `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` still admits `shared` only, the relay never prepares a child Workspace, and the capability is off unless an operator enables it. This is the same order H4a used: the capability lands, proven by its own suites, before any producer.

## Current state

The facts below are from `main` at `f20ed558e3`, after H4c (#13754) landed the `workflow` child kind.

- **Child binding.** `ManagedAgentStore.insertChildSessionCommand` copies the parent's whole binding into the child row with one `INSERT ... SELECT`: Workspace, generation, storage, `cwd_relative`, context and policy refs. The record's `workspaceMode` and `workingDirectory` are validated in both languages, but no runtime reads them.
- **Storage and mounts.** A storage's root is an administrator mount (`runtime-broker.workspace-mounts`: tenant, storage, root). Mounts are static, canonical and must not overlap or nest. W1 §5.1 asks operators to keep the storage root outside every Git worktree and to place Session working directories in its children.
- **The storage lease.** `managed_workspace_execution_lease` holds one row per storage and one holder at a time. The holder is a Runtime Session (`binding_id`, `runtime_generation`, `runtime_session_id`). A tool turn that meets another holder receives the retryable `workspace_busy` and polls. W1a fence and registration require an idle lease; W0e `releaseLost` clears the holder of a lost binding and treats any other holder shape as corrupt.
- **Worker containment.** The worker resolves a binding as the mount root joined with `cwd_relative`. Tools may reach anywhere inside the mount except the directory of another installed Session. W1 §5.1 states that this layout reduces accidents and does not confine host-permitted tool access.
- **Git.** No Java code runs Git. TypeScript has worktree primitives for the daemon and the legacy Agent tool (`createUserWorktree`, `removeUserWorktree`). Its only merge back is Arena's `applyWorktreeChanges`, which applies a patch and reports a conflict as Git's error text.

## Decisions

1. **A child Workspace is a Git linked worktree inside the parent's storage.** Its directory is `<storage root>/.qwen-child-workspaces/<childWorkspaceId>`, where `childWorkspaceId` is the first 32 hex digits of `sha256(tenant NUL parentSessionId NUL childRunId)`. The child binding keeps the parent's tenant, Workspace, generation, storage, context and policy refs; only `cwd_relative` changes, to the worktree directory plus the parent's offset inside its repository. This was chosen over a storage of its own because mounts are static and cannot nest, so a new storage would need dynamic mount registration, a new W1a guard and, under Kubernetes, a new CSI registration. One storage keeps the mount guard, the marker, the lease and, later, the same PVC.
   - Consequence: a child's tool turns still serialize with the parent's through the one storage lease, exactly as `shared` children do. Isolation here is isolation of working trees. It is neither concurrency nor a security boundary (W1 §5.1).
   - The worktree shares the parent's object store and refs, as every linked worktree does. Commits the child makes in its detached worktree are not merged as commits: the merge reads the worktree's content.
2. **The layout is checked, never assumed.** The parent's working directory must lie in a Git repository whose top level is strictly inside the storage root, and whose Git directory and common directory are inside it too. A storage root that is itself inside a repository (the layout W1 §5.1 rules out), a directory outside any repository, a bare repository, a repository inside the reserved directory, a Git directory that points outside the root, a parent directory the snapshot does not carry (an empty or ignored one), or a child directory that would break the rule every Session directory meets (at most 1024 code points), is refused as `child_workspace_layout`. The reserved `.qwen-child-workspaces` directory must be a real directory, never a symbolic link.
3. **The base revision is a snapshot commit of the parent's working tree.** At preparation the control plane reads `HEAD` into a private index file, runs `git add -A` against it, and commits the resulting tree on top of `HEAD`. The private index starts from `HEAD` rather than from a copy of the parent's index, because a copy would carry `assume-unchanged` and `skip-worktree` bits that hide changes from `git add`. The commit therefore holds the parent's committed, staged, modified and untracked non-ignored files, while the parent's own index, `HEAD` and working tree are never touched. Ignored files (build output, `node_modules`) are not carried. The commit uses a fixed identity and fixed dates, so recomputing it over unchanged content names the same commit. Its id is recorded before the worktree is created, and the worktree is checked out detached at it.
4. **Commits are pinned while the row needs them.** The base is pinned as `refs/qwen/child-workspaces/<id>/base`, and a computed result as `.../result`, so `git gc` never collects them. A merge deletes both pins. Every other finish keeps the result pin when a result exists, so a discard never deletes work the child produced unless that work was merged.
5. **The merge policy is a three-way merge into the parent's working tree, computed off-tree.**
   - The child's result `C` is a snapshot of the worktree (the same private-index technique) on top of the base `S`.
   - The parent's current state `P` is a snapshot of the parent's working tree.
   - `git merge-tree --write-tree --merge-base=S P C` computes the merged tree `M` without touching any working tree or index.
   - On a conflict the row ends `conflicted` with the conflicting paths (at most 100 recorded), and nothing is written into the parent. A merge conflict is a durable outcome and never a silent overwrite. The worktree and the base pin are removed at once, while the child's result stays pinned (decision 4); a discard then retires the row.
   - On a clean merge, only the paths that differ between `P` and `M` are written, as uncommitted changes in the parent's working tree. The parent's index and `HEAD` stay as they were, so the child's work arrives exactly like edits the parent made itself.
6. **The write is resumable and checked path by path.** `P` and `M` are recorded before anything is written. Each write attempt snapshots the current working tree `W` and requires every changed path to hold either its `P` or its `M` version; the paths still at `P` are written to `M` with one `git apply` of a tree-to-tree patch. A crash between two files therefore resumes where it stopped. Any other content means something outside the lease changed the tree; the row ends `blocked` and nothing is overwritten. After the write, the tree is verified against `M` before the row is `merged`. The merge and its write run under one maintenance hold (decision 10), so no tool turn can change the parent's tree between computing `M` and writing it.
7. **Discard removes the worktree and keeps the produced work.** Discard removes the registered worktree with `git worktree remove`, then removes whatever is still at the reserved path without following any symbolic link in it, prunes, and deletes the base pin. The reserved path belongs to the control plane, so a directory the model replaced or emptied there goes too, and a symbolic link left there is removed as a link and never followed. When the recorded repository is gone (no Git directory at its top level), only the directory is removed. Any other refusal, such as an unsafe config (decision 11), a changed layout or a momentary fault, fails the discard like any other step, so the prune and the pins are never skipped. Discard is the finish for failed and cancelled children, and the way out of `conflicted` and `blocked`.
8. **One durable row per child run.** `qwen_managed_child_workspace` (V58) holds one row per (tenant, parent Session, child run). Its states are:
   - `preparing` → `ready`, or `failed` when the layout is refused (nothing was created).
   - `ready` → `merging` → `applying` → `merged`, or `merging` → `conflicted`.
   - `preparing`, `ready`, `conflicted`, `blocked` or `failed` → `discarding` → `discarded`.
   - Any active state → `blocked` when the evidence cannot be reconciled.

   A discard that cannot finish ends `blocked` with its request cleared, so the row never loops back into the discard that just failed; a new discard request retries it. The finish request (`merge` or `discard`) is recorded once. A repeated request answers the row; a different one is refused, except that `discard` may follow a `merge` that ended `conflicted` or `blocked`. A merge is admitted only from `ready`, and no finish is admitted while the bound child Session is not closed, because a finish would remove the directory under a running Session.

9. **Claims fence the writers; a scan resumes the work.** The row carries `claimed_by`, `claimed_until` and `claim_generation`. Every transition is a compare-and-set on the state and the claim generation, so a worker whose claim expired cannot commit a step. A scheduled scan (`qwen.managed-agent.child-workspace.scan-delay`, 2 s) drives every row in an active state or with an owed finish, and the operations called from a service drive the same steps synchronously. Every physical step is idempotent and reconciles from what is on disk and in the row, never from memory. A claim lasts 2 minutes and is renewed every third of that while its step runs, so a slow Git command never lets a second worker into a step that is still going; it is released when the step ends. A live claim is never taken twice, not even by its own worker, so a synchronous call and the scan never run one row at once. A step whose claim moved on, or could not be renewed for most of its life, stops: no further Git command starts, and the running one is killed, so a worker that lost its claim never writes beside the one that took the row over. A step that cannot get the storage lease waits 1 s without spending an attempt. Other failures retry with a backoff that doubles from 1 s to 60 s, and after 16 attempts the row ends `blocked` with the last error.
10. **Physical steps run under a maintenance hold on the storage lease.** Before each step the worker takes the storage's `managed_workspace_execution_lease` row as a maintenance holder: `holder_key = sha256("child-workspace" NUL id NUL claimGeneration)`, the Runtime holder columns null, and the new `maintenance_id` column set to the row id. It releases the hold when the step ends.
    - A tool turn meeting the hold receives the existing retryable `workspace_busy` and polls, so a merge never races a turn that writes the parent's tree.
    - W1a fence and registration already require an idle lease, so they wait too.
    - W0e `releaseLost` recognizes the maintenance shape as not belonging to the lost binding and leaves it alone, instead of refusing as corrupt.
    - Taking the hold requires the row's current claim generation, read under a lock in the same transaction, so a worker whose claim expired can neither take nor keep the storage. The claimant that took the row over may replace a hold carrying its own `maintenance_id`, and a stale worker's release names its old claim generation, so it can never release the new hold.
    - The hold takes the same W1a storage guard check as a Runtime claim.
    - A hold outlives its step only until the next scan. The scan first resumes the due rows, whose new claimants take a crashed step's hold over, so no tool turn writes between the crash and the resumed step. It then releases every hold whose child Workspace no step claims: a worker that died, or failed to release, after its last commit.
    - W1c storage migration counts a child Workspace that is not `merged`, `discarded`, `failed` or `conflicted` as unsettled work, because its worktree records absolute paths of the storage root.
    - Like a `shared` child's tool turns, a step waits while the parent's Hook catalog or MCP owner holds the storage for the whole Session. The Agent tool already refuses a child launch in that state (H4b), and I2 keeps that refusal.
11. **Git runs hardened, because the model can write the repository.** Each command runs with:
    - A cleared environment: only `PATH` (and `SystemRoot` on Windows) survives. `HOME` and `XDG_CONFIG_HOME` point to an empty private directory, system and global config are disabled, and prompts, optional locks and replace objects are off.
    - Discovery bounded by `GIT_CEILING_DIRECTORIES` at the storage root, so Git never finds a repository above it.
    - Hooks disabled (`core.hooksPath` overridden to an empty private directory), `core.fsmonitor` overridden empty, `log.showSignature` off, automatic `gc` and maintenance off, `--no-gpg-sign` on every commit, and `--no-ext-diff --no-textconv` on every diff.
    - A configuration check: before each step the repository's own config files (the common `config` and, when `extensions.worktreeConfig` is on, `config.worktree`) are read as data with includes off. The step is refused as `child_workspace_unsafe_config` if a key that these commands can reach names a program or redirects Git: `filter.*`, `merge.*.driver`, `diff.external`, `diff.*.command`, `diff.*.textconv`, `core.worktree`, or any `include.*` or `includeif.*`, whose included keys the check cannot see. A `.gitattributes` file reaches a program only through such a key, so this also closes clean and smudge filters and merge drivers. A promisor remote (`extensions.partialClone`, `remote.*.promisor`) is refused as well: any command that meets a missing object would fetch it lazily and run the remote's transport programs. Keys these commands never reach are not refused, so ordinary repositories pass: no command opens an editor or a terminal or signs, and the two hook keys are overridden rather than read.
    - Defense in depth behind the promisor refusal: lazy fetches are disabled (`GIT_NO_LAZY_FETCH`, Git 2.45 and later) and every transport protocol is disallowed (`GIT_ALLOW_PROTOCOL`), so no command talks to a remote.
    - A sparse checkout is refused as `child_workspace_layout`, because the private-index snapshot would read every file outside the sparse cone as deleted.
    - A time bound per command (`qwen.managed-agent.runtime-broker.child-workspace-git-timeout`, 120 s); the executable is `child-workspace-git` (`git` on the `PATH` by default).

    The check runs under the maintenance hold, so no tool turn can change the config between the check and the command. A process the model left running outside any turn is not covered; that is the residual W1 §5.1 already names.

12. **The capability belongs to the Workspace provider and is off by default.** `RuntimeWarmer.childWorkspaces()` answers the provider, or null. `EmbeddedRuntimeBroker` answers one only when `qwen.managed-agent.runtime-broker.child-workspaces-enabled` is true, the deployment has Workspace mounts, and a startup probe finds Git 2.40 or later (the first release with `merge-tree --merge-base`). Enabling it without Workspace mounts, or with an older Git, fails startup. Without the provider, `prepare` refuses with `child_workspace_unsupported` and commits nothing.
13. **Binding a child Session to its Workspace.** `createChildSession` gains an `isolated` argument. When set, the store locks the row of the same parent and run in the creating transaction, requires it to be `ready` with no finish requested, prepared from the parent's current Workspace, generation and storage, and naming the requested directory, and inserts the child with that directory instead of the parent's. A finish request locks the same row, so a creation and a finish never pass each other. The child directory is part of the request digest, so a replay that names a different binding is an idempotency conflict. A row that is not `ready` refuses the creation with `child_workspace_not_ready`.
14. **I2 direction.** The relay prepares the child Workspace of a `worktree` run before `createChildSession`, then creates the child bound to it. On `completed` it finishes `merge` before `commit_result`, so the terminal receipt can report `merged` or `conflicted` with the paths. Decision 8 refuses a finish while the child Session is open, and today the relay closes a finished child only after its result is committed, so I2 moves that close ahead of the merge for `worktree` runs. On failure, cancellation, quota or give-up it finishes `discard`, and the close cascade discards the Workspaces of the children it cancels. `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` then admits `worktree`, for `child_agent` and `workflow` alike. Whether the merge outcome needs a record key or travels in the terminal receipt is I2's decision. I2 builds on H4c (#13754, merged), whose files it shares.
15. **I3 direction.**
    - Serialized sharing needs no value of its own. The storage lease admits one holder at a time, and every writer of a storage, parent, `shared` child, `worktree` child or child Workspace maintenance, takes it before writing. So no two of them can hold the storage at once, and the lease is already the generation barrier the 2026-10-04 framing asked for.
    - `snapshot` can reuse this capability: a child Workspace that is always discarded, bound to a child whose tool profile refuses every write. I3 decides whether a profile-level refusal is enough evidence of "cannot write".

### `managed_workspace_execution_lease.maintenance_id` (V58)

A nullable column naming the child Workspace that holds the storage as a maintenance holder (decision 10). It is null for every Runtime holder and for an idle lease.

## Non-goals

- I2 and I3, beyond the direction recorded in decisions 14 and 15.
- A provider other than the local process one. The Kubernetes and CSI providers answer no child Workspace provider, and their own slices decide whether the Git steps run in the control plane or in the Pod.
- Concurrent writing by parent and child. The lease still serializes them.
- Merging commits or branches. The child's work lands as uncommitted changes, and the parent decides what to commit.
- Submodule contents. A submodule's gitlink is carried and merged as an entry; its working tree is not materialized in the child.
- Any public contract change. The OpenAPI contract, routes and record bodies stay as they are.

## Validation

- **Git steps** (`ChildWorktreeGitTest`, 21 cases against real repositories in temporary directories): the snapshot carries modified, staged and untracked content but not ignored files, leaves the parent's index, `HEAD` and status untouched, and is deterministic; the layout and offset; every layout refusal of decision 2, including a storage root inside a repository and a sparse checkout; an unsafe config refused with its filter program never run, an include refused, and the same check on the child's own `config.worktree`; a promisor remote whose transport program never runs although a missing tree would be fetched; the refused-key matrix; a repository `core.hooksPath` hook never running; a clean merge landing as uncommitted changes with `HEAD` and the index untouched, a child commit merged as content, the worktree and both pins removed; a conflict naming its path and writing nothing; the apply resuming from a half-written tree and refusing to overwrite a path changed outside the lease; an interrupted checkout rebuilt and an unregistered directory refused; a link at the reserved path removed without being followed, and a linked container refused; a discard keeping the result pin, surviving a removed repository, and keeping the worktree when Git cannot run; a gone repository told apart from a changed one; a step that lost its claim starting no Git and killing the running one.
- **State machine** (`ChildWorkspaceServiceTest`, 20 cases on H2 in MySQL mode with real repositories): prepare, bind and merge end to end, refusing the finish while the bound child Session is open; conflict, then a discard keeping the child's work; a refused layout ending `failed` with nothing created; no capability admitting nothing; the finish rules; the isolated binding's refusals; a busy storage parking without spending an attempt; the maintenance hold owned by one claim; an expired claim yielding to another worker and unable to commit or hold, also when the state is unchanged; a live claim never taken twice, even by its own worker; a running step renewing its claim, and a step whose claim moved on stopping its Git; the merge and its write under one hold; crash resumption between recording the base and creating the worktree, and after the write landed; a discard that cannot finish ending `blocked` until asked again; the scan releasing a hold no step owns; a child directory past the Session rule refused; bounded retries ending `blocked`; an unforeseen fault spending an attempt.
- **Lease and migration** (`WorkspaceRuntimeTest`; `WorkspaceRecoveryContract`, also replayed on MariaDB by `ManagedAgentMySqlIT`; `WorkspaceMigrationStoreTest`): Runtime claims and the maintenance hold exclude each other, `releaseLost` leaves a maintenance hold alone, and a storage with an open child Workspace refuses migration.
- **Binding and configuration** (`ManagedAgentServiceChildWorkspaceTest`, `ManagedAgentPropertiesTest`, `EmbeddedRuntimeBrokerTest`): the isolated child's directory joins its digest and a run without a child Workspace refuses; the capability is off by default, needs the mounting Broker and Workspace mounts, resolves the verified mount root, and fails startup without Git.
- **Mutation checks**: 39 mutants, each disabling one guard of decisions 2 to 13: the divergence refusal, the resume set, the private-index `add -A`, the conflict branch, the refused keys including promisor remotes, the hooks override, the child's config check, the Git-directory, sparse and Session-directory refusals, a gone repository told apart from a changed one, the kept result pin, the unregistered-directory refusal, the four finish rules, the blocked discard clearing its request, the claim generation in transitions and holds, the single live claim, the claim renewal, the step stopping when its claim is lost, the busy wait, `failed` against `blocked`, the retry bound, the busy hold, the hold release, the stale-hold release, `releaseLost`, the migration refusal, the binding checks, the digest, the single hold for merge and write, and the discard's Git failure. All 39 went red. The two environment variables that disable lazy fetches and transports are defense in depth behind the promisor refusal: with the refusal in place, removing them changes nothing a test can observe.

## Acceptance criteria

- A child Workspace can be created, bound, merged and discarded idempotently across a control-plane restart.
- A merge conflict surfaces as a durable `conflicted` outcome and never as a silent overwrite.
- A child Workspace's writes do not appear in the parent's tree until its merge runs, and a discarded child's worktree is removed.
- No model-reachable behavior changes: `MANAGED_CHILD_ADMITTED_WORKSPACE_MODES` is `['shared']`, and the capability is off by default.

## Open questions

1. **Where the Git steps run for containerized providers**: in the control plane against the mounted volume, or inside the Pod through a worker operation.
2. **Retention of result pins** after a `conflicted` or `blocked` row is discarded: kept until an operator removes them, or bounded by the Session archive.
3. **The merge outcome's contract**: a record key, or the terminal receipt (I2).
