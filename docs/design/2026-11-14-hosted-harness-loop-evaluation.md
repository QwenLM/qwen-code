## The behavior difference

The shared agent loop (`packages/core/src/core/agent-loop.ts`) runs `runModelRound` (`:401`) then `runToolBatch` (`:512`): one model round whose events are forwarded to the surface, then the whole batch on one `CoreToolScheduler` (`createSchedulerExecutor`, `:807`), then `finalizeToolResponses` (`:709`) and recording (`:671`), then the next round. Every surface decision is an optional callback on `AgentLoopHost` (`:173`).

The Hosted Harness runs its own cycle in `runPreparedHostedHarnessTextTurn` (`hosted-harness-model.ts:524`, entered through `runHostedHarnessTextTurn` `:380`). Its round loop (`:1174-1178`) sends a model request, collects the calls, fires its own Stop and MessageDisplay hooks at the stop point, and hands the calls to `input.toolTurn.execute` (`:1564`). That tool turn is `HostedWorkspaceToolTurn` (`hosted-workspace-tool-turn.ts:2138`): a **durable, journaled, exactly-once, sequential** dispatch, not an in-memory scheduler batch. The difference is not "a different loop shape"; it is that the Hosted Harness's tool execution is a recovery system, and the shared loop's tool batch is not.

## What the code actually requires (verified)

Five facts from the current tree shape the work. Each is a contract a migration must preserve, not a detail it can drop.

1. **The model round is `LlmClient.sendMessageStream` with a durable-feed retraction, plus a prepared-recovery `Turn`.** The round calls `client.sendMessageStream` (`hosted-harness-model.ts:1345`) with `retractDeliveredOutputOnRetry: true` (`:1353`); on a non-continuation `Retry` (`:1381`) or a `ModelFallback` (`:1390`) it retracts the orphaned prefix from the durable feed (`textDeltas.retract()`) and clears the text. This is the #13319 contract: published deltas cannot be un-glued, so a cut that already delivered content replays the request and retracts the prefix. A `preparedRecovery` resumes a prepared request through `new Turn(client.getChat(), …).run(…)` (`:1331`) instead. The shared `runModelRound` forwards the same events and discards collected calls on `Retry`/`ModelFallback`, but it has no notion of the durable feed or of a prepared recovery; both would have to live in the surface's `onModelEvent` and in a wrapper around the round.

2. **The tool batch is a durable journaled exactly-once sequential dispatch.** `execute` (`hosted-workspace-tool-turn.ts:3439`) runs `executeNative` (`:4590`) then `completeHookResults` (`:3450`). `executeNative` prepares the requests (allowlist, plan-mode, truncation refusal) and then dispatches them one at a time in a sequential loop (`:6425`): shell through the broker (`execute` `:6952`, `executeV3` `:6889`), memory (`:6550`), child agents, team tools, session commands, questions and plan exit, each committing its `tool_result` to the journal. Exactly-once rides the journaled set, never the process: `journaledToolResultIds` (`:1903`) reads the durable `tool_result` records keyed on the `functionResponse` id, and a replay skips only the commit (`if (!journaled?.has(callId)) await this.commit('tool_result', …)`, `:8922`) while the replay-safe acceptance still runs. Recovery arms such as `resumeAgentWaitRuns` re-enter the wait for every run the checkpoint still owes. The shared `runToolBatch` schedules the whole batch on one `CoreToolScheduler`, in parallel for concurrency-safe calls. It suppresses duplicates and replays in memory (`agent-loop.ts:536-571`), but that state does not survive a restart: there is no durable journal and no restart recovery. It cannot replace this dispatch without losing the durability that is the Hosted Harness's core value.

3. **The turn cap is a third formula, and it throws.** The Hosted Harness stops at `maxRounds > 0 && round >= maxRounds` (`hosted-harness-model.ts:1187-1188`, `maxRounds = config.getMaxSessionTurns()` `:1173`) and throws `HostedModelRoundLimitError`. `round` is zero-indexed and resumes from `input.resumeModel?.round ?? input.initialRound ?? 0` (`:1175`). This differs from `LlmClient`'s `max > 0 && sessionTurnCount > max` (`client.ts:4995-4996`, which yields a `MaxSessionTurns` event) and from the shared loop's `options.maxRounds !== undefined && rounds >= options.maxRounds` (`agent-loop.ts:337`, which returns a `next_round` stop reason). Three boundaries, three outcomes: a thrown typed error, a terminal event, and a typed stop reason. A migration must reconcile the boundary and preserve the error type the Hosted callers catch, or change every caller.

4. **Fourteen self-fired hooks, journaled with exactly-once occurrence ids, and a Stop continuation sent as `ToolResult`.** `HOSTED_EXPLICIT_HOOK_EVENTS` (`hosted-harness-model.ts:74-88`) lists thirteen events — SessionStart, SessionEnd, SessionDelete, UserPromptSubmit, UserPromptExpansion, Stop, StopFailure, MessageDisplay, PreToolUse, PostToolUse, PostToolUseFailure, PostToolBatch, PermissionRequest — and the harness also fires InstructionsLoaded (`:849`, `:872`). It fires them itself with occurrence-id dedup (`hasCompletedOccurrence`, e.g. SessionStart `:837-842`), not through the client's hook chain. At the stop point it fires Stop (`:1495`) and, if blocked, continues with the hook's reason; the continuation goes out as `SendMessageType.ToolResult` on the next round (`:1346-1349`), where `LlmClient` sends a Stop continuation as `Hook`. The tool hooks (PermissionRequest, PreToolUse, PostToolUse, PostToolUseFailure, PostToolBatch) are fired by `completeHookResults` from journaled `hook_execution` records. The shared loop relies on the client's Stop/steering/next-speaker chain; moving the Hosted round onto it would double-fire these hooks unless new send options disable the client's firing, and those options would be transition steps in the unified design's "Send options a host owns" table.

5. **Resume and recovery are first-class.** The round resumes from `resumeModel.round` / `initialRound` (`:1175`), refuses to start when hooks have pending operations (`HostedHookRecoveryRequiredError`, `:1181`) or a hook stop reason is set (`:1183`), and wraps a failure with pending tool results as `HostedToolRecoveryRequiredError` (`:1577-1579`). A client-initiated skill call is executed before the round loop (`:1113`). The shared loop has no resume or recovery concept; these would remain a Hosted-specific wrapper around any shared round.

## Migration shapes considered

**Full migration (model round and tool batch).** Blocked. The shared `runToolBatch` cannot own the journaled exactly-once dispatch without either re-implementing the journal inside the shared batch (which would put Hosted-specific durability into `packages/core` for every surface) or dropping durability (which the Hosted profile cannot accept — it commits to a remote Workspace with no undo backup, `hosted-workspace-tool-turn.ts:4641-4644`). Neither is acceptable.

**Model-round-only migration (as speculation did in #17029).** Conceivable but still heavyweight. Speculation moved its round onto `runModelRound(turnModelRound(chat, model, …))` because it owns an `LlmChat` and parses chunks itself. The Hosted round already uses the main-session `LlmClient`, which is the shared loop's main-session round source, so the round itself could run through `runModelRound(client, …)`. But it would still require all of:

- a durable-executor adapter that supplies the journaled dispatch at the batch boundary and bypasses the shared batch's `finalizeToolResponses`/recording, so the journal stays the single recording authority;
- new send options to disable the client's hook firing while the harness keeps firing its 14 journaled hooks, plus reconciliation of the Stop-continuation send type;
- turn-cap reconciliation that preserves `HostedModelRoundLimitError` and the zero-indexed resume boundary;
- preservation of the durable-feed retraction (#13319) in `onModelEvent`, and of the prepared-recovery and hook/tool recovery paths as a Hosted wrapper.

That is a larger surface-policy surface than any prior surface migration, and it touches the durability guarantees that are the Hosted Harness's reason for existing. The benefit — one loop implementation — does not outweigh that risk today.

## Recommendation

**Do not migrate the Hosted Harness in this program round. Land this evaluation, and revisit the migration only after the other surfaces have converged and a durable-executor adapter exists.** Reasoning, grounded in the code above:

- The unified-loop program's value is one shared loop for the surfaces whose tool execution is an in-memory scheduler batch. The Hosted Harness's tool execution is a journaled exactly-once recovery system; it is the one surface whose tool execution is durable rather than an in-memory executor, and forcing it would either pollute `packages/core` with Hosted-specific durability or weaken the Hosted profile's guarantees.
- The other surfaces (headless, ACP, Ink, OpenTUI, AgentCore, speculation) are migrated or in review, and their default flips wait on the nightly unified-loop E2E gate. The Hosted Harness is explicitly out of that gate's scope until it is evaluated; this document is that evaluation.
- A model-round-only migration is the only viable shape, and it is blocked on a durable-executor adapter, new hook-ownership send options, turn-cap reconciliation and the retraction/recovery contracts. Each needs its own parity evidence before the Hosted default could change.

The evaluation keeps the recommendation of the unified design: the Hosted Harness is evaluated separately, and this is the record of that evaluation. It does not add a setting, change a default, or move any code.

## Decision points for the follow-up

When the migration is revisited, these are the decisions it must take, in order:

1. **Executor seam.** Can `AgentLoopToolExecutor` (`agent-loop.ts:244`) wrap the journaled dispatch so the shared batch supplies the calls and takes the results, while the journal stays the single recording authority and the shared `finalizeToolResponses`/`recordCompletedToolCall` are bypassed? If not, the model-round-only shape is not viable either.
2. **Hook ownership.** Which send options disable the client's hook firing for the Hosted round, and how is the Stop-continuation send type (`ToolResult` vs `Hook`) reconciled without changing the durable feed? Each option is a transition row in the unified design's table.
3. **Turn cap.** Reconcile `max > 0 && round >= max` (thrown `HostedModelRoundLimitError`) with the shared `next_round`/`max_session_turns` stop reasons, preserving the zero-indexed resume boundary and the error type callers catch.
4. **Retraction and recovery.** Preserve the #13319 durable-feed retraction in `onModelEvent`, and the prepared-recovery, hook-recovery and tool-recovery paths as a Hosted wrapper around the shared round.
5. **Parity evidence.** A Hosted parity suite must show, with the setting on, that the requests, the durable feed, the journal commits, the hook occurrence counts and the recovery outcomes match the current loop, apart from listed differences — including a restart mid-batch and a retry that retracts a delivered prefix.
