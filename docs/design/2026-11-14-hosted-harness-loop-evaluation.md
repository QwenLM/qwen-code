## The behavior difference

The shared agent loop (`packages/core/src/core/agent-loop.ts`) exposes two seams. `runModelRound` (`:401`) runs one model round: it forwards the model's events to the surface, collects the tool calls, and returns a stop reason. `runAgentLoop` (`:301`) drives the whole cycle — rounds plus `runToolBatch` (`:512`) on one `CoreToolScheduler` (`createSchedulerExecutor`, `:807`), then `finalizeToolResponses` (`:709`) and recording (`:671`). A surface can take either: the whole cycle through `runAgentLoop`, or the model round alone through `runModelRound` while it keeps its own tool step.

The Hosted Harness runs its own cycle in `runPreparedHostedHarnessTextTurn` (`hosted-harness-model.ts:524`, entered through `runHostedHarnessTextTurn` `:380`). Its round loop (`:1174-1178`) sends a model request, collects the calls, fires its own Stop and MessageDisplay hooks at the stop point, and hands the calls to `input.toolTurn.execute` (`:1564`). That tool turn is `HostedWorkspaceToolTurn` (`hosted-workspace-tool-turn.ts:2138`): a **durable, journaled, exactly-once, sequential** dispatch, not an in-memory scheduler batch. The difference that matters is split: the Hosted **tool execution** is a recovery system that the shared tool batch is not, but the Hosted **model round** is already the same `LlmClient.sendMessageStream` the shared round uses.

## What the code actually requires (verified)

Six facts from the current tree shape the work. Each is a contract a migration must preserve, not a detail it can drop.

1. **The shared round seam is model-round-only.** `runModelRound` (`agent-loop.ts:401`) calls the model source, forwards every event to `host.onModelEvent`, collects `ToolCallRequest` calls (dropping the ones a `Retry`/`ModelFallback` replaced), and returns `{ turn, calls, stop }`. Its doc comment says "A surface that still runs its own tool step calls it directly" (`:396-400`). It does not run `runToolBatch`, `finalizeToolResponses`, recording, or the `maxRounds` check — those belong to `runAgentLoop` (`:301`) and `runToolBatch` (`:512`). ACP already uses it this way (`Session.ts:8992-9013`: `runModelRound` when the round is not on the shared tool batch), and speculation moved its round onto it (`speculation.ts:300-305`). A surface can therefore adopt the shared model round without adopting the shared tool batch.

2. **The Hosted model round is `LlmClient.sendMessageStream` with a durable-feed retraction, plus a prepared-recovery `Turn`.** The round calls `client.sendMessageStream` (`hosted-harness-model.ts:1345`) with `retractDeliveredOutputOnRetry: true` (`:1353`); on a non-continuation `Retry` (`:1381`) or a `ModelFallback` (`:1390`) it retracts the orphaned prefix from the durable feed (`textDeltas.retract()`) and clears the text. This is the #13319 contract: published deltas cannot be un-glued, so a cut that already delivered content replays the request and retracts the prefix. A `preparedRecovery` resumes a prepared request through `new Turn(client.getChat(), …).run(…)` (`:1331`) instead. The shared `runModelRound` forwards the same events and discards collected calls on `Retry`/`ModelFallback`, but it has no notion of the durable feed or of a prepared recovery; both would have to live in the surface's `onModelEvent` and in a wrapper around the round. These are model-round dependencies; the migration shapes below give the full list.

3. **The Hosted tool batch is a durable journaled exactly-once sequential dispatch.** `execute` (`hosted-workspace-tool-turn.ts:3439`) runs `executeNative` (`:4590`) then `completeHookResults` (`:3450`). `executeNative` prepares the requests (allowlist, plan-mode, truncation refusal) and then dispatches them one at a time in a sequential loop (`:6425`): shell through the broker (`execute` `:6952`, `executeV3` `:6889`), memory (`:6550`), child agents, team tools, session commands, questions and plan exit, each committing its `tool_result` to the journal. Exactly-once rides the journaled set, never the process: `journaledToolResultIds` (`:1903`) reads the durable `tool_result` records keyed on the `functionResponse` id, and a replay skips only the commit (`if (!journaled?.has(callId)) await this.commit('tool_result', …)`, `:8922`) while the replay-safe acceptance still runs. Recovery arms such as `resumeAgentWaitRuns` re-enter the wait for every run the checkpoint still owes. The shared `runToolBatch` schedules the whole batch on one `CoreToolScheduler`, in parallel for concurrency-safe calls. It suppresses duplicates and replays in memory (`agent-loop.ts:536-571`), but that state does not survive a restart: there is no durable journal and no restart recovery. It cannot replace this dispatch without losing the durability that is the Hosted Harness's core value. This is the tool-batch blocker, independent of the model round.

4. **The fourteen self-fired hooks are already isolated from the client.** `HOSTED_EXPLICIT_HOOK_EVENTS` (`hosted-harness-model.ts:74-88`) lists thirteen events — SessionStart, SessionEnd, SessionDelete, UserPromptSubmit, UserPromptExpansion, Stop, StopFailure, MessageDisplay, PreToolUse, PostToolUse, PostToolUseFailure, PostToolBatch, PermissionRequest — and the harness also fires InstructionsLoaded (`:849`, `:872`). It fires them itself with occurrence-id dedup (`hasCompletedOccurrence`, e.g. SessionStart `:837-842`). The isolation is already in place: the managed dispatcher the harness passes to `config.initialize` (`:668`) returns `false` from `hasHooksForEvent` for every event in `HOSTED_EXPLICIT_HOOK_EVENTS` (`:598-604`); `HookSystem.hasHooksForEvent` delegates to that dispatcher (`hookSystem.ts:338-340`); `config.hasHooksForEvent` delegates to `HookSystem` (`config.ts:11882`); and the client's Stop branch fires only when `config.hasHooksForEvent('Stop')` is true (`client.ts:6048`). So the client already sees no Stop hook and does not fire the fourteen hooks — a Hosted test asserts exactly this (`hosted-harness-model.test.ts:2058`). The Stop continuation is sent as `SendMessageType.ToolResult` by the Hosted outer loop (`:1346-1349`). Because `runModelRound` passes `round.options` through unchanged and does not replace the dispatcher, moving the model round onto it does not double-fire these hooks and needs no new send option.

5. **The turn cap is a third formula, and it throws.** The Hosted Harness stops at `maxRounds > 0 && round >= maxRounds` (`hosted-harness-model.ts:1187-1188`, `maxRounds = config.getMaxSessionTurns()` `:1173`) and throws `HostedModelRoundLimitError`. `round` is zero-indexed and resumes from `input.resumeModel?.round ?? input.initialRound ?? 0` (`:1175`). This differs from `LlmClient`'s `max > 0 && sessionTurnCount > max` (`client.ts:4995-4996`, which yields a `MaxSessionTurns` event) and from `runAgentLoop`'s `options.maxRounds !== undefined && rounds >= options.maxRounds` (`agent-loop.ts:337`, which returns a `next_round` stop reason). Three boundaries, three outcomes. For migration: `runModelRound` has no cap, so a model-round-only migration keeps the Hosted outer loop's cap unchanged; only a full migration onto `runAgentLoop` would reconcile the three formulas and the error type callers catch.

6. **Resume and recovery are first-class.** The round resumes from `resumeModel.round` / `initialRound` (`:1175`), refuses to start when hooks have pending operations (`HostedHookRecoveryRequiredError`, `:1181`) or a hook stop reason is set (`:1183`), and wraps a failure with pending tool results as `HostedToolRecoveryRequiredError` (`:1577-1579`). A client-initiated skill call is executed before the round loop (`:1113`). The shared loop has no resume or recovery concept; these remain a Hosted-specific wrapper around any shared round. The prepared-recovery `Turn` path (fact 2) is the part a model-round migration must adapt.

## Parity differences and where they land

| Concern                                  | Hosted Harness (today)                                                                                                                           | Shared loop                                                                                                   | Where it lands                                                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Tool execution                           | durable journaled exactly-once sequential dispatch with broker execution and restart recovery (`hosted-workspace-tool-turn.ts:6425`, `:1903`)    | one in-memory `CoreToolScheduler` batch, parallel for concurrency-safe calls (`agent-loop.ts:807`)            | **blocks the tool-batch migration**: the shared dedup is in-memory, not a durable journal; the tool turn stays                 |
| Recording / finalization                 | each arm commits its own `tool_result` to the journal; `completeHookResults` reads journaled hook records                                        | `runToolBatch` runs `finalizeToolResponses` (`:709`) and `recordCompletedToolCall` (`:671`) once per batch    | **blocks the tool-batch migration**: the journal stays the recording authority; the shared finalize/record would double-record |
| Retry / fallback retraction              | retracts the orphaned prefix from the durable feed and clears text (`:1353`, `:1381`, `:1390`)                                                   | discards collected calls, no durable-feed side effect (`agent-loop.ts:441-444`)                               | **model-round dependency**: preserve the #13319 retraction in `onModelEvent`                                                   |
| Prepared recovery                        | resumes a prepared request through a `Turn` (`:1331`)                                                                                            | `runModelRound` sends through the source's `sendMessageStream`                                                | **model-round dependency**: adapt via `turnModelRound` or a wrapper                                                            |
| Hooks                                    | 14 self-fired, journaled exactly-once; Stop continuation sent as `ToolResult` (`:74-88`, `:1495`, `:1346`)                                       | client hook chain, but the managed dispatcher hides the 14 events from it (`:598-604`)                        | **already isolated**: no new send option; the Stop continuation stays `ToolResult` because the outer loop owns it              |

| Resume / recovery, per-round preparation | resume, hook/tool recovery, drain user messages, re-declare tools, refresh the system instruction (`:1175`, `:1181`, `:1189-1226`, `:1577-1579`) | no such concept                                                                                               | **stays in the Hosted outer loop** for model-round-only                                                                        |

The first two rows are the load-bearing tool-batch blockers: the Hosted tool execution is a durability system, and the shared batch is not. Rows three and four are the model-round dependencies. The last three rows stay with the Hosted outer loop and tool turn in a model-round-only migration, so they are not prerequisites for it.

## Migration shapes considered

**Full migration (onto `runAgentLoop`, model round and tool batch).** Blocked. The shared `runToolBatch` cannot own the journaled exactly-once dispatch without either re-implementing the journal inside the shared batch (which would put Hosted-specific durability into `packages/core` for every surface) or dropping durability (which the Hosted profile cannot accept — it commits to a remote Workspace with no undo backup, `hosted-workspace-tool-turn.ts:4641-4644`). Neither is acceptable.

**Model-round-only migration (onto `runModelRound`, keeping the Hosted outer loop and tool turn).** Viable — this is the ACP and speculation pattern. The Hosted round already uses the main-session `LlmClient`, which is the shared round's main-session source, so it can run through `runModelRound(client, …)` while the outer loop keeps the turn cap, the per-round preparation, the Stop/MessageDisplay hooks, the resume/recovery paths, and `input.toolTurn.execute`. Its real dependencies are:

- preserve the durable-feed retraction (#13319) in `onModelEvent` (fact 2);
- adapt the prepared-recovery `Turn` path, via `turnModelRound` or a wrapper (facts 2 and 6);
- map `runModelRound`'s returned calls and stop reason back into the outer loop, including the usage and model-scope handling currently done on `Finished`/`ModelFallback`;
- parity evidence for the above.

It does **not** depend on a durable-executor adapter (the tool batch stays), on new hook send options (the dispatcher already isolates the hooks, fact 4), or on turn-cap reconciliation (the outer loop keeps its cap, fact 5). Those belong to the full migration or are already handled. An earlier draft of this evaluation listed them as model-round blockers; the 2026-11-14 review corrected that, and the separation above is the result.

## Recommendation

**Keep the journaled tool batch; migrate the model round only, as a separate opt-in slice.** Reasoning, grounded in the code above:

- The Hosted tool execution is a journaled exactly-once recovery system; the shared in-memory batch cannot replace it without polluting `packages/core` with Hosted-specific durability or weakening the Hosted profile's guarantees. The Hosted Harness therefore does not fully converge onto `runAgentLoop`, and the tool-batch migration stays deferred.
- The Hosted model round is already the shared `LlmClient` round. Moving it onto `runModelRound` while keeping the outer loop and tool turn is the same shape ACP and speculation already use. It is viable, and it is not gated on an executor adapter or on hook send options. Its real work is the retraction, prepared-recovery and stop-mapping adaptations, plus parity evidence.
- This PR is the evaluation: it adds no setting, changes no default, and moves no code. The model-round-only implementation and its parity suite are the follow-up slice; the tool-batch migration remains deferred.

## Decision points for the follow-up

1. **Model-round dependencies (the real work).** Preserve the #13319 durable-feed retraction in `onModelEvent`; adapt the prepared-recovery `Turn` path; map the returned calls and stop reason, and the usage/model-scope handling, back into the Hosted outer loop.
2. **Hook ownership.** Already isolated via the managed dispatcher filter; no send option is needed to adopt the shared model round. Only if a migration wants to move hook ownership to the client is that a separate choice to argue, and it would change the durable-feed and occurrence-id semantics.
3. **Tool-batch seam (only if the tool batch ever moves).** Can `AgentLoopToolExecutor` (`agent-loop.ts:244`) wrap the journaled dispatch so the journal stays the single recording authority and the shared `finalizeToolResponses`/`recordCompletedToolCall` are bypassed? This is not a prerequisite for the model-round-only path.
4. **Turn cap (only for a full migration onto `runAgentLoop`).** Reconcile `max > 0 && round >= max` (thrown `HostedModelRoundLimitError`) with the shared `next_round`/`max_session_turns` stop reasons, preserving the zero-indexed resume boundary and the error type callers catch. The model-round-only path keeps the Hosted cap.
5. **Parity evidence.** A Hosted parity suite must show, with the setting on, that the requests, the durable feed, the journal commits, the hook occurrence counts and the recovery outcomes match the current loop, apart from listed differences — including a retry that retracts a delivered prefix and a prepared-recovery resume. A restart mid-batch is a tool-batch concern and is unchanged, because the tool turn stays.
