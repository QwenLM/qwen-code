# 重复 YAML frontmatter 解析

[English](yaml-frontmatter-parse-cache.md) | [简体中文](yaml-frontmatter-parse-cache.zh-CN.md)

## 问题与目标

资源发现会在 ACP 初始化及后续刷新中多次解析相同的 frontmatter。优化前，共享 YAML 包装器每次都会重新解析和转换文本。目标是减少这部分重复工作，同时保留独立返回值、诊断和完整资源校验。下文分别报告组件和整合时延证据，不将它们归为同一队列。

## 建议改动

在 `packages/core/src/utils/yaml-parser.ts` 中维护私有的进程内 FIFO 缓存，以完整原始文本为键。最多缓存 256 个成功的原始对象结果，单个输入不超过 16,384 个 UTF-16 代码单元。这些固定限制约束保留规模，不代表精确堆内存上限，也不引入设置项。不持久化缓存，不跨进程共享。

256 条限制避免长期运行进程无界积累，16,384 代码单元限制排除大型一次性文档。二者均为保守工程限制，不是通过实验优化出的容量。条目数和输入长度约束的是逻辑保留规模，不能换算为堆内存或 RSS 字节上限：字符串底层存储、原始对象图及分配器开销各不相同。超长输入绕过缓存查询、document 预检和准入，沿用原解析器及诊断。

保持现有 schema 和 tag 选项。普通未命中先解析 document；仅在没有错误或警告，且所有映射键均为 null 或值为基本类型的 scalar 时准入。集合键、alias 键和对象值 scalar 键继续走原解析器，保留转换阶段的警告。转换与现有清洗都成功后才准入。错误、非对象、超长输入及回退结果均不缓存。

每次返回，包括命中，都对私有原始结果运行现有递归清洗。嵌套对象和数组必须相互独立，继续移除 null 属性、保留显式类型值的现有转换，并保持映射的空原型。不得返回缓存的原始对象或上一次清洗结果。

`LOG_TOKENS` 或 `LOG_STREAM` 为 truthy 时，在缓存查询和 document 预检前直接运行一次原解析器，保留库的调试输出，包括字符串 `"0"`。其他警告和错误输入每次均保留原解析器与回退行为。不符合准入条件的未命中可能同时产生一次预检和一次重新解析；必须测量这部分成本。

## 范围与消费者

就此缓存组件而言，仅修改共享 `parse` 实现及其同目录测试。`stringify`、直接 AST 读取者及资源发现不变。仓库内十个读取文件覆盖 Skill、子代理、命令、规则、输出样式、结构化记忆和扩展转换。Core 的公开重导出也将该契约提供给外部调用者，优化不能假定特定资源类型或调用者所有权。

文件读取、编辑、删除、激活、工作区作用域、校验、Hook、鉴权、取消、工具和 readiness 继续正常执行。缓存仅保存已解析文本，不保存资源决策或会话对象。它会将可能敏感的 frontmatter 有界保留到淘汰或进程退出。

## 验证与验收

先使用全局 CLI dry-run 基线，再使用本地打包 CLI 验证。在不请求模型的条件下检查资源加载、编辑/删除和隔离。对于 CLI 无法可靠暴露的内部对象所有权和 YAML 诊断，使用直接测试脚本回退。

聚焦测试必须验证嵌套结果独立性、空原型、alias 和显式类型值；重复调用时解析警告、错误与回退不变；缓存已有条目后切换调试变量；精确文本键、淘汰和超长绕过。构建、类型检查及受影响消费者测试必须通过。升级 YAML 库时重新检查转换警告路径。

针对其他条件一致的真实发布制品运行新的交错完整 SDK 基准。保持全新进程、运行时和会话状态与完整资源，保留全部样本，分别报告首会话和总启动耗时。解析微基准不能证明 500 ms 目标。只有实测收益足以支撑准入逻辑和保留成本时才交付该缓存。

## 状态与待确认事项

本地缓存实现及目标测试已完成。实际安装库为 YAML 2.9.0，已检查其警告/转换路径和调试环境变量读取。全局 CLI 基线、直接解析器检查、重复值/原型/警告/调试对照，以及整合构建、类型检查和消费者测试验证了所覆盖的语义。公开 Core 导出与外部调用方契约仍需正常 maintainer 评审。

一组其他条件一致的独立四条件组件队列在较早源码上分离 YAML：空缓存首 SDK 中位数为 773.850 到 730.584 ms，已安装缓存/resolver 条件为 560.817 到 521.601 ms。后者候选在两对中更慢，总耗时均值为 941.971 ms，对照为 941.672 ms。四对全部保留，不能证明稳定 500 ms 或尾延迟边界。

提交 maintainer 评审的建议是纳入缓存，并对符合准入条件的调用启用，依据是已覆盖的语义检查及这些有限的同条件首 SDK 改善。小样本、部分对次变慢及已安装条件下略差的总耗时均值限制了证据强度；provider profile 或组合启动结果均不能证明 YAML 单项归因，也不能验证容量选择。“尚未发布”指发布状态，不表示运行时功能被关闭；是否纳入仍须正常 Core maintainer 接受。

最终同 main 源码组合还包括初始化及 CLI 按需改动，八对中位数为 815.994 到 706.277 ms，均值为 833.257 到 719.861 ms，不能将其归为 YAML 单项收益。最终整合 E2E 两侧各通过 59 项，但保留普通旧快照的时序差异。缓存尚未发布，完整 500 ms 目标仍未完成，详见[评估](../performance/acp-initialization-evaluation.zh-CN.md)。实际语料有依据时可降低固定限制，新增配置不在范围内。
