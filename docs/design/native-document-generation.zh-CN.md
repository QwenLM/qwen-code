# 文档生成：DOCX MCP 提案

[English](native-document-generation.md) | [简体中文](native-document-generation.zh-CN.md)

状态：提案，尚未实现。关联 issue：[#14616](https://github.com/QwenLM/qwen-code/issues/14616)。

## 问题说明

用户要求生成 Word 合同时，需要的是可以下载并打开的文件。
Qwen Code 可以运行生成文档的脚本，但用户仍需自行组合文档库、操作说明和产物发布步骤。

本提案建议先交付一个本地 DOCX 生成器，将其封装为带有配套 skill 的 MCP 扩展。
skill 通过现有产物工具协调生成和发布。本设计 PR 只提出这一工作流，
不交付服务器、skill、依赖或运行时改动。

## 当前状态

以下源码引用说明了现有行为：

- [工具结果契约](../../packages/core/src/tools/tools.ts)支持文档产物和结果路径。
- [write_file](../../packages/core/src/tools/write-file.ts)会识别 Office 扩展名并生成产物元数据。
  它的公开内容参数是字符串，不提供二进制缓冲区输入或 base64 解码选项。
- [MCP 结果适配器](../../packages/core/src/tools/mcp-tool.ts)在普通结果转换中返回模型内容和显示信息，
  不填充 `ToolResult.artifacts`。仅返回文件名不会通过这条转换路径发布工作区产物。
- [record_artifact](../../packages/core/src/tools/record-artifact.ts)验证工作区文件位置并返回产物元数据。
  这可以确认发布，但不能确认 Word 是否能够打开文件。
- [扩展指南](../users/extension/getting-started-extensions.md)说明了如何一起封装 MCP 服务器和 skill。
- [exceljs 已经是 Web Shell 的生产依赖](../../packages/web-shell/package.json)。
  [预览解析器](../../packages/web-shell/client/components/artifacts/excel-preview-parser.ts)用它加载已有电子表格。
  这既没有提供本提案中的 DOCX 生成器，也没有决定未来服务端 XLSX 生成器的依赖方案。

这些结论来自源码阅读，不能证明真实会话中的生成、下载或 Office 应用兼容性已经通过验证。

## 目标与范围

- 生成一个包含标题和纯文本段落的 DOCX。
- 通过现有产物工作流发布生成文件。
- 封装生成器及其文档库，使用户无需为生成文档单独安装转换器。
- 在本地生成文件，并将输出限定在配置的工作区内。
- 在实现前为评审者提供具体契约和验证计划。

首版不包含 XLSX、PPTX、PDF、模板、格式转换、图片、表格或已有文档编辑。
它不新增原生 core 工具，也不新增会话记录导出格式。
可用的扩展本身就能满足此请求，无需以后必须将生成能力迁入 core。

## 交付方案

| 方案                                | 优点                                     | 成本或限制                           | 决定                 |
| ----------------------------------- | ---------------------------------------- | ------------------------------------ | -------------------- |
| 调用 Pandoc 或 LibreOffice 的 skill | 复用已有本地转换器                       | 需要额外安装系统工具并组织转换工作流 | 作为临时解决办法记录 |
| 本地 MCP 扩展及 skill               | 无需修改 core 即可封装一种生成器         | 需要安装扩展并单独调用产物发布工具   | 推荐首版采用         |
| 原生 core 工具                      | 可以在一次调用中生成文件并返回产物元数据 | 需要维护者决策、依赖评审和 core 集成 | 等待证据充分后再评估 |

选择 DOCX 是为了对应 issue 中的合同示例。这是范围选择，不代表 DOCX 的需求最高。
现有产物代码能够减少集成工作，但不足以据此估算实现时间。

## 拟议工具契约

以下类型描述拟议的 MCP 工具 `generate_docx`，不是现有 Qwen API。

```ts
type GenerateDocxInput = {
  outputPath: string;
  title: string;
  paragraphs: string[];
};

type GenerateDocxResult = {
  resolvedPath: string;
  mimeType: 'application/vnd.openxmlformats-officedocument.wordprocessingml.document';
  sizeBytes: number;
};
```

`outputPath` 相对于配置的工作区，且必须以 `.docx` 结尾。
拒绝绝对路径、父目录穿越和已经存在的目标。
工作区根目录来自可信的启动配置，不接受工具输入指定的根目录。
要求标题非空，且至少包含一个段落。标题渲染为文档标题，每个段落按文本处理，
不执行 HTML 或 Markdown。

首先评估 `docx` 库。选定版本前，确认其许可证、依赖体积、支持的 Node 版本和打包后的运行时。
在服务器内部渲染字节，不通过模型或 `write_file` 传递二进制数据。

完成写入后，返回实际的绝对路径 `resolvedPath`、固定 MIME 类型和文件大小。
在 MCP `structuredContent` 和文本内容中返回同一份简短结果。
失败时返回 MCP 工具错误，不附带成功元数据。发布前明确记录并测试输入大小上限。

## 扩展打包与工作区绑定

拟议扩展包含构建后的服务器、运行时依赖和 `skills/generate-document/SKILL.md`。
使用现有扩展机制；最终发行位置由维护者决定。

以下是未来扩展的说明性清单：

```json
{
  "name": "document-generation",
  "version": "0.1.0",
  "mcpServers": {
    "documents": {
      "command": "node",
      "args": [
        "${extensionPath}${/}dist${/}server.js",
        "--workspace",
        "${workspacePath}"
      ],
      "cwd": "${workspacePath}"
    }
  }
}
```

`${extensionPath}` 和 `${workspacePath}` 是现有的
[扩展变量](../../packages/core/src/extension/variableSchema.ts)。
`--workspace` 是拟议服务器需要实现的参数。
启动时解析并验证该根目录。不要从扩展安装目录推断工作区，
也不要接受模型生成的调用指定另一个根目录。

初始目标是本地 stdio 服务器，它与 Qwen 绑定的工作区共享同一文件系统视图。
远程服务器和不同的容器文件系统映射需要单独设计。
声称支持 worktree 或多个工作区前，先在 worktree 和两个独立工作区会话中验证绑定。

## 生成与发布工作流

1. skill 收集标题、段落和请求的目标路径。
2. 它调用发现的 `generate_docx` MCP 工具。使用实际注册的工具名，不假设特定的 MCP 命名前缀。
3. 服务器验证输入、渲染文档并完成写入。
4. 生成成功后，skill 使用返回的绝对路径、显式的 `kind: "document"`、MIME 类型和大小调用 `record_artifact`。
5. 只有登记成功后，助手才报告产物可下载。如果登记失败，应说明生成成功但发布失败，
   并保留文件以便重试发布。

以挂载于 `/workspace` 的工作区为例，发布参数如下：

```json
{
  "title": "nda.docx",
  "kind": "document",
  "workspacePath": "/workspace/reports/nda.docx",
  "mimeType": "application/vnd.openxmlformats-officedocument.wordprocessingml.document"
}
```

实际路径必须来自服务器结果。skill 不得为了重试发布而重新生成文件，
也不得重复登记同一次成功输出。发布工具不可用或被禁用时，必须明确报告。

这仍然是由模型协调的工作流。skill 指令不能保证每次都会执行后续调用。
会话测试必须检查这一步衔接；将 MCP 输出自动转换为 Qwen 产物不属于本提案范围。

## 写入安全与失败语义

外部服务器负责自身的文件系统写入。后续产物验证不能保护已经发生的写入。
现有 Qwen 路径和原子写入辅助函数可以作为参考，但不会自动为服务器提供安全保证。

实现必须满足以下要求：

- 在规范化后的启动工作区内解析输出，拒绝通过符号链接或 junction 重定向到工作区外。
  字符串前缀检查并不足够。必须在实际写入操作中评审竞态条件。
- 在目标目录内写入临时文件，通过禁止覆盖的操作仅发布完整文件。
  先单独检查存在性，再执行可能覆盖目标的重命名，不能保证禁止覆盖。
- 失败时保留已有文件，只清理本次调用创建的临时文件，并在发布完成后才返回成功。
- 平台或文件系统无法满足这些写入要求时，明确失败。
  不得静默退回到部分写入或覆盖式写入。
- 不记录文档正文，生成文档期间不发起网络请求，并遵循宿主的 MCP 审批和工作区信任决定。

具体写入原语需要在原型阶段接受评审和平台测试。
本提案不声称已经为外部 Node 进程实现无竞态的路径限制或沙箱强制执行。
如果无法建立要求的边界，原型就不能发布。

## 分阶段实现计划

1. **构建独立生成器。** 在选定的扩展项目中加入单个工具、文档渲染、经过验证的工作区绑定，
   以及禁止覆盖的文件输出。先直接测试服务器，再引入模型。
2. **封装工作流。** 加入扩展清单和配套 skill。
   验证安装后的发行包无需全局文档库或转换器即可启动。
   将文档操作说明放在 skill 中，不添加到每次会话的上下文里。
3. **验证完整会话。** 先用全局 `qwen` CLI 试跑，再检查 Web Shell 中的产物发布和下载。
   记录确切的包版本、平台、提示词、失败情况和输出证据。
4. **评审发行方式与范围。** 请维护者决定扩展的发行位置，并判断证据是否足以支持发布。
   根据已经证明的需求，单独评估其他格式或 core 集成。

## 验证计划

| 层级       | 检查                                                               | 预期证据                                         |
| ---------- | ------------------------------------------------------------------ | ------------------------------------------------ |
| 生成器     | 生成标题和 Unicode 段落，再用独立 DOCX 读取器解析输出              | 预期文本和段落结构得到保留                       |
| 写入       | 测试目录穿越、绝对路径、父目录重定向、已有目标、并发写入和中断写入 | 不越出工作区、不覆盖目标、不将部分文件报告为成功 |
| 打包       | 在没有开发依赖或系统转换器的环境中安装构建后的发行包               | 服务器使用打包的运行时启动并生成 DOCX            |
| 会话       | 请求 NDA，发布返回的路径，并下载产物                               | 下载字节与服务器文件一致                         |
| 应用       | 在 Word 或 LibreOffice 中打开下载文件                              | 没有修复警告，且包含预期标题和段落               |
| 失败       | 拒绝生成或产物登记，禁用发布工具                                   | 明确报告失败状态，不声称存在可下载产物           |
| 工作区绑定 | 在 worktree 和两个独立工作区会话中生成文档                         | 每份输出都留在各自配置的工作区内                 |

声称跨平台支持前，先在 Linux、macOS 和 Windows 上执行写入和打包检查。
仅有 ZIP 签名或产物记录不能证明 DOCX 有效。
应用打开检查与自动解析是两项独立验证。

本设计文档 PR 需要格式、引用和双语一致性检查，不提供运行时测试结果。
后续会话测试计划和证据应放在 `.qwen/e2e-tests/` 及实现 PR 的测试报告中。

## 验收标准

- 安装后的扩展能够根据标题和段落生成有效 DOCX。
- 生成不依赖全局文档库或已安装的转换器，也不发起网络请求。
- 输出始终留在配置的工作区内，即使并发调用也不能覆盖已有目标。
- 成功会话只发布一次实际生成的文件，下载保留原始字节，且文件可在 Office 应用中打开。
- 生成或发布失败时，提供准确的失败报告。
- 声称支持的平台和工作区模式都有已记录的运行时证据。
- 两种语言版本描述相同的范围、约束和决定。
