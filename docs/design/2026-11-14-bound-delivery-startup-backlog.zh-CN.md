# 绑定投递启动积压：评论摘要

[English](2026-11-14-bound-delivery-startup-backlog.md) | [简体中文](2026-11-14-bound-delivery-startup-backlog.zh-CN.md)

状态：已实现（#17199；2026-11-14 提案）。下文按该增量当时的设计描述。扩展[绑定 PR 评论监视](2026-11-08-bound-pr-comment-watch.zh-CN.md)；摘要路径之外，评论 lane 的逐条投递契约不变。PR **状态** watch 自[operator 拥有的 watch 迁移](2026-11-14-daemon-pr-watch-config-migration.zh-CN.md)起归 daemon 所有，不在本设计范围内。

## 问题陈述

channel 停摆一段时间（重启、发布或持续 API 故障）后，停机期间绑定 PR 上新增的每条同账号评论在轮询恢复时同时变得可投递。评论 watch 把每条评论作为独立持久任务与 prompt 投递，于是绑定的 `fix` 会话被每条评论一个模型回合的洪泛淹没——其中多数已被后续讨论取代。游标跨重启存活，积压是真实的、必须投递，但应以紧凑摘要而非洪泛到达。

## 现状

- 评论 watch（`watchPrComments`）轮询每个绑定 PR 的会话评论 + 行内评审评论，把每条新同账号评论投递给每个没有发过它的绑定 follower，受跨被监视 PR 共享的每轮突发预算（`MAX_WATCH_COMMENTS_PER_PASS`，20）约束。
- 停机后整个缺口窗口同时可投递；突发预算封顶单轮，但尾部在后续轮次仍按每条评论一条 prompt 排出——仍是洪泛。
- PR 状态 watch（head/CI/冲突/状态迁移）已移到 daemon、归 operator 所有；channel 不再检测或投递状态迁移。因此本设计只涉及评论 lane。

## 目标

1. 检测到停机缺口后（或可投递窗口大于逐条评论 pass 上限），把每个绑定 PR 的同账号评论积压以私有摘要 prompt 投递——每个正文预算窗口一条，绝不每条评论一条；角色路由、归属排除方向、游标崩溃安全性均不变。
2. 不新增配置键；不改通知 lane、公开发布契约、摘要之外的逐条投递路径。

## 范围边界

- **仅评论 lane。** 状态 watch 归 daemon 所有；本设计不触碰状态迁移。
- **通知 lane 不变。** 异账号评论保持现状。
- **上限内逐条投递不变。** 无缺口、无持久摘要装载、且可投递窗口在 pass 上限内时，投递与今天逐字节一致。
- **首次观测保持静默。** 无持久条目的 PR 即使在缺口下也静默基线化（首次观测不投递积压）。

## 提议改动

### 1. 停机缺口检测

- `GithubCursor` 新增 `lastPollAt?: string`，**仅在成功 poll 后**盖章（基类在 `pollOnce` resolve 后保存游标）。`validateCursor` 接受缺失（遗留游标）并丢弃畸形值。
- 每个 poll 比较 `now - lastPollAt > max(10 分钟, 5 × pollInterval)`；缺口超阈值时置内存标志 `startupDigestPending`（每边缘一次 stderr）。健康 poll 重新盖章心跳，故稳态不会触发。进程重启与进程内故障都算缺口：失败 poll 跳过游标保存，心跳保持陈旧直至 poll 恢复。阈值随配置 poll 间隔缩放，长间隔 channel 不会每轮都摘要。缺口检测以绑定投递且评论监视开启为门：评论监视禁用时的缺口不装载摘要，故禁用期间累积的评论在重新启用后按逐条投递——以逐条评论上限为限；超上限窗口仍经大小触发摘要，那是独立于缺口的洪泛防护。在禁用**之前**已持久化的装载，会在 poll 循环的 watch 门处清除（可观测到禁用状态的位置——禁用时根本不会调用 watch pass），故禁用重启不会把装载带入之后的重新启用、摘要那些从未属于缺口积压的评论。瞬态跳过（绑定刷新失败、预算保留）保留装载：积压是真实的。

### 2. 评论积压摘要（按 PR，由缺口或窗口大小装载）

全局标志为**每个**持久 watch 条目装载持久化的按条目 `digestPending` 标志——不仅是当前快照的活跃 key，故降级（空/部分）首轮仍为磁盘条目装载，完整快照前的重启能找到装载。装载也在缺口检测时立即持久化，故 watch pass 被跳过（绑定刷新失败）的 poll 不会丢失它。watch 上限切片之外的条目保留装载直至被监视。全局标志是**真正的一次性**：一旦装载了持久条目即清除，而非等到可信 pass——让它在中止的 pass 间存活会重新装载早先 pass 已排空的条目，使之后一条普通新评论以虚构的停机 lead 摘要。按条目标志（由该 pass 的 save 持久化）跨越逐 PR 错误、上限排除、不可信快照、中止 pass 与重启为单个 PR 承载摘要。条目积压被消费（摘要结清且无省略，或无可投递）或静默首次观测时清除其装载。停留的游标（省略尾部、被拒 dispatch、gate 宽限）**保留**装载。完整但空的绑定快照是权威缺席：条目按既有契约剪枝，之后出现的绑定是静默首次观测。

摘要模式也由**积压大小**装载：可投递窗口大于 `MAX_WATCH_COMMENTS_PER_PASS` 时无论心跳如何都摘要，因为持续逐 PR 拉取失败后恢复的端点保持心跳新鲜而游标停留在数小时前——仅缺口永远不会装载它。该上限是 **pass 级**逐条评论预算，被刻意复用为**按 PR** 的洪泛阈值：单个 PR 的窗口若独自超过整个 pass 预算，本会跨多轮每条评论一条 prompt 排出，故改为摘要。大小装载的摘要用中性 lead（不得声称并未发生的停机），并在省略成员时持久化自身装载，使余量以更多摘要补投。按条目记住大小触发的来源（`digestSizeArmed`），故经持久装载重新进入的后续摘要也保持中性 lead；只有真实停机缺口才用离线积压措辞。检测到的缺口会**重置**大小来源，故打断大小臂排空的停机重新报告离线 lead，而非继承陈旧的中性措辞。

在 `watchPrComments` 中，摘要模式取代逐条 dispatch 循环：

- **正文预算，最新优先**：共享绑定 prompt 上限（`BOUND_PROMPT_BODY_MAX_CODE_POINTS`，6,000）保留前缀，故摘要最新优先分配：完整成员行（作者 lead、按 `MAX_AGGREGATE_COMMENT_CHARS` 封顶并带截断提示的摘录、评论 URL）从最新往回接受，直到超出「上限减 lead 与前置省略提示」。最新成员因此总是幸存；共享上限绝不截断摘要尾部。
- **基于已渲染片段与 follower 集的作者排除**：仅当 follower 写了**每个**已渲染成员才排除（它已持有全部正文）；population 与逐条路径所用的绑定 follower 集相同，故投递时 Gone 回退无法把摘要投回给写了每个已渲染成员的会话。部分作者仍收到摘要——互相署名情形（两角色各写一条）绝不能以零 prompt 消费整包。全目标排除不可达（每个可投递成员都有某个没写过它的目标），故没有摘要无目标分支。
- **省略无损且保留装载**：装不下的成员（超出最新 20 窗口或被预算丢弃）计入**前置**的 `offlineOmittedNotice`（「……将以更多摘要补投」），其去重键**不**记录，游标停在积压头部之前且**保留**装载，故下一轮重列并**摘要**余量（已渲染后缀去重）。此处清除装载会让余量按每条评论一条 prompt 排出——正是本功能消除的洪泛。无任何未投递即消费。已渲染后缀同时对按条目持久化前沿（`digestRendered`）与共享 `dispatchedComments` 环去重：环淘汰早于**通知**游标的键，而健康 poll 会把通知游标推进到停留摘要的积压之后，故已渲染键可能在排空中途被淘汰；前沿使其保持去重，后续摘要既不重投也不多数「新增评论」。前沿在游标停留期间累积，积压消费时清除。
- 信封：`messageId` 为 `comment-digest:<n>:<排序后已渲染成员 key 的 sha256-40>`（对实际投递内容的哈希身份，镜像聚合 lane 的超集语义）；metadata 保持 `Trigger: comment.`，故 `boundEventClass` 解析为 `comment`，角色路由与逐条评论 watch 投递逐字节一致。`dispatchedComments` 恰好记录已渲染成员 key。信封携带 **channel 账号**身份（`senderId = botUsername`），与本同账号车道的逐条信封完全一致：合成 sender 会在群组发送者白名单 preflight 被拒（豁免匹配 channel 登录），从而退役 digest 而游标却推进过整段积压。
- **退役不等于消费**：retired 判定（如 preflight 拒绝）消费任务并返回 settled 但**不**记录投递。摘要路径在 dispatch 后要求「已知为正」的投递证据——持久投递环，且**不**可读环（那是未知而非证明）——若事件未投递，则撤销认领时的成员记账、停留 `since`、保留装载，故游标绝不推进过从未投递的成员，下一轮重列它们。若不撤销，认领时的 key 会把每个成员从重试中隐藏，下一轮的空候选集将以零 prompt 消费积压。成功投递会重写投递环并**单独闩锁**一个修复标志，故启动时不可读的环被首个接受的摘要修复，积压一次排出而非每轮重复投递。修复只在摘要的 delivered 判定处生效：不可读判定本身永不清除，因为随文件丢失的键仍是未知，公开重复抑制调用方必须对它们保持 fail-closed——全局清除会把每个损坏前事件从「已投递」翻成「未投递」，打开不可逆的公开回复窗口。「未投递」保持对**瞬时**原因 fail-closed（推迟返回 unsettled，下一轮重列），但**永久**退休（preflight 拒绝摘要：settled 且无投递）由按条目连续退休计数（`digestRetiredCount`，`MAX_DIGEST_RETIREMENT_RETRIES`）设上界：达到上界后带可见 journal 痕迹（`comment_digest_retired`）消费积压，而非让游标保持、每轮耗费 pass 级 watch 预算直到进程结束。瞬时推迟或成功投递会重置计数。
- 游标：dispatch 已投递且无省略时提交 `nowIso`（清除装载）；有省略时停在积压头部之前（保留装载）；无投递时停留 `since`（保留装载）。gate 宽限停留保持其既有的一轮语义（批粒度）并保留装载。若连一个成员都装不下（病态长 URL），摘要退回逐条路径并消费其装载。
- 摘要路径从不递减 pass 级评论突发预算（每 PR 一个任务而非每条评论），故摘要 pass 总是看到预算完好；预算继续约束逐条扇出。
- 跨实例说明：逐条评论 watch 投递经稳定 GitHub id 跨 channel 实例去重；摘要的哈希身份是实例本地的（每实例有自己的游标），匹配每订阅至少一次语义。两个实例经同一缺口监视同一 PR 时各自投递自己的摘要。

`BOUND_DELIVERY_COPY` 新增文案（en + zh）：离线积压 lead（缺口臂）、中性评论积压 lead（大小臂）、离线省略提示。离线 lead 的措辞对**两种**缺口触发都为真——重启与进程内 API 故障都使心跳陈旧而进程可能仍在运行——故说「自上次成功轮询以来」，而非声称 channel 未运行。省略提示前置，因为共享正文上限从尾部截断。结构性标记与平台值遵循既有语言契约（`en` 逐字节英文）。

## 设计决策与理由

1. **仅摘要评论 lane。** 它是 channel 仍投递的唯一无界积压源；状态 watch 归 daemon。捆绑状态事件需要新事件类别与有路由回归风险的模板扩展。
2. **缺口检测是纯本地心跳比较**，仅在成功时盖章，故重启与进程内故障都能被检测，无需额外 API 调用。
3. **按条目持久装载，为每个持久条目装载。** 仅全局一次性标志会在降级首轮或逐 PR 错误时丢失摘要；按条目标志跨越它们与重启存活。
4. **大小臂与缺口臂并存。** 持续逐 PR 拉取失败后恢复的端点保持心跳新鲜，仅缺口永远不会装载摘要；超上限窗口直接装载。
5. **最新优先正文预算。** 共享上限保留前缀，故最旧优先分配会恰好吞掉最新、最可操作的成员。
6. **基于已渲染片段与 follower 集排除。** 基于整个可投递集排除会把整包自身评论投给写了整个已渲染片段的会话；仅排除解析出的目标会让 Gone 回退把它投回给非目标作者。
7. **基于已渲染成员的内容哈希身份。** 游标保存前崩溃会重列窗口；已渲染成员去重，长大的窗口只派发新增余量（聚合 lane 超集语义）。
8. **channel 账号身份 + 退役不等于消费。** 任一 alone 即可闭环静默消费路径；两者都保留作为纵深防御。不可读环的门仅设在摘要处，因为环的 fail-open 方向对抑制调用方承重。
9. **省略保留装载并以更多摘要补投。** 在省略尾部清除装载会让余量按每条评论一条 prompt 排出——正是本功能消除的洪泛。

## 约束

- 逐条投递（无缺口、窗口在上限内、无持久装载）与今天逐字节一致；摘要是增量路径。
- 无任何静默消费：停留的游标绝不推进过未投递成员，**瞬时** retired/推迟判定绝不推进游标。**永久**退休（preflight 持续拒绝摘要）是唯一有上界的例外：连续 `MAX_DIGEST_RETIREMENT_RETRIES` 次退休后**带可见 journal 痕迹**消费积压，绝不静默。
- 角色路由、归属排除方向、通知 lane 不变。
- 摘要从不递减 pass 级突发预算。

## 风险

- 摘要概括而非逐条重放评论；需要特定较早评论的会话仍可列出 PR 评论（省略提示点名数量）。最新成员总在正文预算内幸存。
- 两个 channel 实例经同一缺口监视同一 PR 时各自投递自己的摘要（实例本地哈希身份），匹配每订阅至少一次语义。
- 永久退休上界会消费一份从未投递的积压（preflight 持续拒绝）。这是刻意的——替代方案是每轮耗费 watch 预算的无界保持——且绝不静默：`comment_digest_retired` journal 行点名被消费的摘要与消费数。成员键保留记录，故评论不再重列：一旦达到上界，该积压就此游标被消费，之后修好路由/发送者门**不会**重新投递——恢复是操作者动作，而非自动重试。
- 启动时不可读的投递环会让公开回退抑制在进程生命周期内保持 fail-closed，即使一次成功写入已修复环：随文件丢失的键仍是未知，故一个从未投递的全新 `pr:` 事件与丢失键无法区分，也被抑制公开回退直到重启。这是以可恢复的代价（损坏环后未绑定 PR 的公开回复暂停至重启）换取关闭不可逆的重复方向；摘要自身的接受判定以修复后的环加新写入的键为门，故摘要车道本身正常排出。

## 验收标准

1. 缺口超阈值后（或窗口大于逐条评论 pass 上限），每个绑定 PR 的同账号评论积压以类别为 `comment` 的私有摘要 prompt 到达——每个正文预算窗口一条，最新成员在预算内，恰好记录已渲染成员去重键，基于已渲染片段与 follower 集排除全上下文作者，channel 账号身份被发送者白名单接纳，瞬时 retired/推迟判定绝不推进游标（永久退休仅在重试上界处带可见痕迹消费），省略成员以更多摘要补投（游标停留、装载保留、无丢失）。
2. 无缺口（或首次观测）、无持久摘要装载、且可投递窗口在逐条评论 pass 上限内时，评论投递与今天逐字节一致：逐条 prompt、静默基线、无摘要。窗口超上限时即使无缺口也摘要（大小臂）；早先缺口留下的持久装载仍会把上限内窗口摘要。
3. 角色感知路由、归属排除方向、通知 lane、公开发布契约不变。
