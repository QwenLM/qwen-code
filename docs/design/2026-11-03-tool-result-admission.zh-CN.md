# 恢复会话时工具结果的放行规则

[English](2026-11-03-tool-result-admission.md)

## 行为约定

工具执行完成后，用户可以在本地会话记录里看到结果。新版写入的会话只有在记录了放行决定后，才会把结果加入模型历史。[#15595](https://github.com/QwenLM/qwen-code/issues/15595) 报告了恢复会话时把已被 `UserPromptSubmit` 拦截的工具输出发送给模型的问题。

## 写入和恢复

- 通过普通工具结果记录器写入的外层结果带有 `requiresToolResultAdmission` 标记。完成记录先于下一轮 hook 写入，工具结束后会话仍可动态安装 hook。
- 模型请求通过提示词 hook 后，会写入 `tool_result_admission` 系统记录，其中列出本轮获准结果的完成记录 UUID。发送方核对提交的工具响应及其附带内容。该记录证明输入已获准发送。模型服务端的应答情况由实际请求决定。宿主显式以工具结果结束当前回合时，例如 Goal 检查点，也在该处记录决定。
- 恢复时，工具输出在原来的位置等待对应决定。放行记录缺失或无效时，原文不会进入模型历史。只含工具结果的发送若在放行前取消，会保持历史原样，并在调用方读取流时返回取消错误。发送方在混入独立输入前标出准确的工具内容；取消时按对象身份移除这些内容，包括附带文字和图片。独立输入保留正常的历史写入和中断提示词续接行为，即使它的文字与工具附带文字相同。普通提示词和已准备请求的重放保留修改前的取消行为。若 ACP 明确拦截，或在工具完成后取消请求，模型可收到与实时会话相同的合成错误。如果进程在决定写盘前退出，沿用现有机制补齐未结束的工具调用。单独排队的用户输入保留原顺序。
- ACP 用户提示、定时任务及后台通知将已完成批次的结果传入共享模型轮次。工具结果轮次被拦截或取消时，统一记录扣留决定，并移除工具附带内容，保留单独排队的用户输入。每个完成结果保留首个有效决定。放行后若请求准备失败，包括压缩期间失败，实时历史与恢复历史都保留已放行的结果。发送守卫裁剪后更新保留快照，包括来源信息及独立输入；之后才添加单独领取的手动退出计划模式通知。此前已扣留的结果保留原有原因。最初的 Cron 和 Notification 请求沿用既有 hook 策略。
- 不再发送下一轮模型请求、而是直接保留已完成批次的终止路径，也遵循放行约定。没有适用的提示词 hook 时，先确认允许凭据已写入，再保留结果。有尚未完成的适用 hook 时，记录扣留决定，只保留合成工具响应和独立输入。这会收紧取消、配额换模型和后台容量耗尽路径；取消本身不代表允许。ACP 旧循环的结果轮保留既有的不运行提示词 hook 的策略。Goal 显式终止保留既有许可策略。先前有效的决定不可反转。
- 正常发送、终止路径和 Goal 终止都等待记录器确认写入后，再将结果加入模型历史。写入器不可用、拒绝记录或写入失败会向调用方报错，不能放行原文；若历史结构变化使本轮凭据无效，则拒绝该操作。这是写入确认和进程恢复保证，不新增整机断电或文件系统 `fsync` 保证。
- ACP 共享轮次已经失败或取消时，工具结果结算错误会单独记录，轮次保留原有结果。未经确认的工具输出不会进入历史。旧版定时循环在准备下一条消息时取消，仍按既有 hook 策略结算已完成的批次。
- 迟到结果只有在该调用的首个响应仍是孤立调用修复占位符，且调用后的连续用户历史片段尚未被新的模型回复截断时，才能替换它。跨过该边界的迟到结果在记录或发出前直接丢弃，因为现有恢复格式无法表达对更早位置的更新。会话先保护该历史位置，再记录结果、确认放行，最后完成替换。Ink 在这一保护范围内复用共享批已整理的结果及延迟记录回调，保留附件信息，并在放行前只记录一次。发送等待此操作；竞争中的同步历史修改在改变历史前报错。拒绝替换时不写完成记录或凭据；写入失败时释放保护并保留占位符。确认期间切换会话，不会把记录或替换转移到新会话。在允许替换的连续用户历史片段内，现有恢复机制只前移工具响应，不会同时移动其附带内容。因此，若中间已有独立用户输入，实时请求和恢复请求中附带内容的顺序仍可能不同。本次保证放行边界、工具配对和内容保留，不承诺迟到结果请求逐字一致。
- Restore 重新执行有意写入不带标记的完成记录，并在既有恢复授权下将同样的响应直接加入实时历史。这条写入路径不属于新增的普通工具结果放行门禁。
- 全量读取和索引读取使用同一套恢复逻辑。Code Mode 内部调用的结果仍不进入模型历史。压缩检查点已经保存模型历史，并取代之前的决定。
- Ink 保留共享循环等待模型流空闲、按序排空工具批及发送时检查容量的策略。Goal 之外的共享工具显式终止，遵循 ACP 既有显式终止政策，即使有提示词 hook 也须确认放行后保留结果。额度切换及容量停止时，未执行的适用 hook 仍使结果扣留。终止保留不取走单独排队的输入。
- ACP 消息成功写入历史后清除该消息的工具片段归属，后续独立 steer 消息不沿用旧批次。OpenTUI 在 steer 前或刷新上下文期间取消时也结算成功/取消混合批次；终止历史发布在凭据确认前后都核对捕获的会话及轮次。放行确认后若模型准备失败，保留的历史仍携带下一轮派发计量所需的工具输出来源信息。
- 用户拒绝全部工具后，Ink 会停止排队的 Mod 提示。若凭据写入失败，Ink 仍完成取消清理，包括暂停关联 Goal 并释放轮次许可。写入错误继续向上报告，历史仍须在写入确认后发布。重试补发的日期提醒和独立输入仍不属于工具片段。

## 兼容性与验证

旧版工具完成记录没有放行信息，沿用原来的恢复行为，旧会话中曾被拦截的输出也受此限制。使用新版写入时，若工具完成后、放行前发生崩溃，完整结果可能只能在本地会话记录中查看。

用本地假模型检查首轮请求和恢复后的请求。分别执行拦截、放行、取消等待中的 hook，以及在完成记录落盘后强杀进程。核对每个工具调用 ID、整份请求正文和追加用户输入的位置。ACP 旧循环在工具结果轮不运行提示词 hook，可用它验证普通工具结果仍能正常放行。
