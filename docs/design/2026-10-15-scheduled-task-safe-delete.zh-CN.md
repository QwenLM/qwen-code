# 定时任务会话的安全删除

[English](2026-10-15-scheduled-task-safe-delete.md) | [简体中文](2026-10-15-scheduled-task-safe-delete.zh-CN.md)

## 问题

删除定时任务时，系统会先移除调度定义，再关闭任务自有会话。当前关闭采用强制语义。如果该任务轮次启动了后台 agent、shell、workflow、待发送通知或其他活动轮次，删除任务会中止这些工作，并可能在没有通知的情况下丢失结果。

禁用任务不会关闭会话。后续自动清理会询问持有该会话的 ACP 子进程是否仍有活动工作，并在子进程拒绝或结果不确定时保留会话。删除操作应使用同一安全边界。

## 目标

- 立即删除定时任务，同时保留其自有会话中的活动工作。
- 只有在守护进程安全检查通过，并且支持该能力的持有方子进程以原子方式确认没有活动工作后才关闭会话。
- 保留会话的持有工作结束后，复用现有 idle reaper 完成清理。
- 保持用户显式关闭、kill、shutdown 以及同请求回滚的现有语义不变。

## 方案

在 `CloseSessionOpts` 中增加 `closeIfUnheld`。设置该选项后，bridge 会将请求交给现有的两阶段 `closeIfChildUnheld` 路径，而不是直接进入强制关闭。

在联系子进程前，如果会话仍有守护进程已接纳的工作、正在恢复、已协商的持有类别覆盖不完整，或持有方 channel 已被判定不可用，bridge 会保留会话。否则，第一阶段在子进程的会话关闭门控内发送 `onlyIfUnheld: true`，请持有会话的子进程执行关闭。子进程报告持有、请求超时、传输结果不确定或会话条目已变化时，守护进程都会保留会话。子进程确认会话已关闭后，bridge 再次校验条目身份，并执行现有的本地清理。这样既沿用 idle reaper 已使用的并发与未知结果处理语义，也将不可用 channel 的内部排空能力限制在已经完成安全筛选的自动清理路径中。

定时任务 DELETE 路由使用该选项，并将关闭原因设为 `scheduled_task_deleted`。同请求回滚仍使用强制关闭，因为这些会话尚未完成任务轮次。

## 生命周期与所有权

即使会话被保留，定时任务仍会从持久化存储中删除。该任务的 channel delivery 授权会被撤销。活动工作结束前，保留的会话继续以现有名称显示。本次不增加孤儿会话标记，也不重命名。子进程不再报告持有后，现有 idle reaper 会关闭这个未附着会话。

守护进程对自己已经接纳、但子进程可能尚不可见的工作负责；持有会话的 ACP 子进程对子进程侧的持有负责。守护进程快照可以指导何时重试清理，但不能作为销毁授权。

## 兼容性

显式关闭调用方不设置 `closeIfUnheld`，继续保持强制语义。已协商 active-work 能力的 ACP 子进程会收到条件关闭探测。旧版子进程沿用 bridge 对自动清理已有的兼容行为。

HTTP 结构、持久化任务 schema、transcript schema 和 Java 控制面契约均不变化。

## 风险

- 保留的会话可能暂时显示一个已删除任务的名称。该状态由活动工作界定；持有清除后，还需等到最后一个事件订阅者断开，现有 idle reaper 才会回收这个未附着会话。
- DELETE 响应不区分会话立即关闭和安全保留。两种结果都完成了定时任务删除；会话清理仍属于内部生命周期行为。

## 验证计划

- 验证 DELETE 路由只对任务自有会话请求 `closeIfUnheld`。
- 验证 bridge 向子进程发送 `onlyIfUnheld: true`，并在子进程报告后台持有时保留守护进程状态。
- 验证守护进程已接纳的工作、持有类别覆盖不完整、恢复中和持有方不可用状态都会在不探测子进程的情况下保留会话。
- 验证显式关闭和回滚路径继续使用强制语义。
- 执行守护进程的定时任务删除流程，保存删除任务且持有工作继续存活的前后证据。
- 执行聚焦单测、build、typecheck、lint、格式检查、正确性 review 和简化审查。

## 验收标准

- 删除任务不能静默中止由 active-work hold 表示的工作。
- 条件关闭被拒绝或结果不确定时，会话保持可用并等待后续清理。
- 直接条件关闭不能绕过守护进程已接纳的工作或不安全的持有方生命周期状态。
- 没有持有的会话通过现有 bridge 清理路径移除。
- 任务自身已删除，不能再次触发。
- 不增加新的 reaper、生命周期状态、持久化字段或公开 HTTP 响应字段。
