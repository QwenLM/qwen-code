# 压缩请求准入

[English](2026-10-19-compression-request-admission.md) | [简体中文](2026-10-19-compression-request-admission.zh-CN.md)

状态：已为 [#9455](https://github.com/QwenLM/qwen-code/issues/9455) 实现。

## 问题

压缩要把整段历史发给摘要模型。会话越长越需要压缩，这个请求也就越大，最终连它自己都放不进模型的窗口。于是自动、响应式和手动 `/compress` 压缩，会和主请求以同样的方式失败，已经超大的会话无法恢复。

冷路径会按估算剩余的空间夹紧输出预算（#7960），但下限是 1。估算的输入一旦占满窗口，它仍会把请求发出去，此时 `max_tokens: 1`：provider 要么拒绝，要么只返回 1 个 token 的片段。原有的大小检查只覆盖单独配置的压缩模型；主模型同时负责压缩时，没有任何检查拦住请求。

## 改动前的现状

- 冷路径请求由精简后的历史（去掉媒体）、压缩提示词和指令组成，大小用 char/4 估算。
- `computeCompactionOutputBudget` 返回 `min(20K, window − estimate − 1K)`，下限为 1。
- side-query 失败时返回 `COMPRESSION_FAILED_API_ERROR`，只尝试一次（`maxAttempts: 1`）。
- 本地估算对 thought part 只计 `text`，忽略同一 part 上的 `thoughtSignature`。

## 目标

- 绝不发送无法给摘要留出可用输出预算的压缩请求。
- 历史放不下时，分阶段、有界地缩减，并保留完整的工具交互、用户最初的请求和最新的上下文。
- 怎么缩减都放不下时，在本地以清楚的 input-too-large 状态停止。
- 本来就放得下的对话仍走原来的一次压完路径。

## 非目标

- 更准的估算器。固定的按语言倍率会把高密度中文高估约 2 倍（#9541 中实测），导致本可压缩的会话被拒绝，所以不改估算器。
- 共享缓存请求。它失败后会回退到冷路径，而本次改动覆盖冷路径。
- 切换模型后先用旧模型压缩。

## 设计

### 准入

冷路径请求的输出预算不低于 `MIN_COMPACTION_OUTPUT_TOKENS`（4,096）时，照常发送；低于时先缩减。

### 缩减阶段

每个阶段在估算达到目标时立即停止。目标是给摘要留出窗口的四分之一，并限制在 4,096 到 20,000 token 之间。

1. **截短工具内容。** 工具结果、工具调用参数和模型文本截到 4,000 字，复用载荷过大时的上限（#10380）。开启 `preserveUserText` 后，用户自己的文本保持完整。
2. **把较早的轮次压成用户原话。** `condenseToUserMessages` 原样保留最新的若干轮。保留部分从 model 消息开始，这样不会把 function call 和它的 response 拆开，角色也保持交替。更早的部分合并为一条 user 消息，逐字引用用户的消息：
   - 第一条消息总是保留；之前压缩过时它就是那次的摘要，所以最多可占 32,000 字，在后面的消息需要剩余空间时至少占引用预算的一半；
   - 其余按从新到旧的顺序填入；
   - 其余每条引用不超过 8,000 字，全部引用合计不超过 64,000 字；
   - 和工具结果同在一个 user 轮次里的用户文字（工具运行期间插入的输入）会被引用，工具输出不会；
   - 注入的 `<system-reminder>` 块不是用户的话，不会被引用，以免它们在有上限的引用里挤掉真正的需求；
   - 用一句说明写明省略了多少条助手和工具消息，以及中间省略了多少条用户消息。

   先丢弃助手回复和工具输出，因为文件可以重读、命令可以重跑，而用户说过的话没有别处可以找回。摘要提示词本来就要求写 `primary_request_and_intent` 和 `all_user_messages`，这些引用正好为二者提供输入。

缩减后仍无法留出 4,096 token 时，压缩返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`，不发送任何请求。它和其他失败一样计入熔断次数。

### 因上下文长度被拒后重试一次

估算仍可能偏低，尤其是高密度中文。provider 以上下文长度为由拒绝冷路径请求时（`getContextLengthExceededInfo`），压缩会用一个更小的请求重试一次：

- 报错里给出请求实际大小时，用"实际大小 ÷ 该请求的估算"这个比例来确定重试的大小，保证重试仍能留出完整的输出预算。这个比例来自刚被拒绝的请求本身，而不是之前的轮次。
- 报错里没有数字时，重试目标为被拒请求估算值的 60%。

第二次失败，或任何其他错误，仍像以前一样返回 `COMPRESSION_FAILED_API_ERROR`。

### token 计数

缩减后的请求已不能代表它要替换的历史，所以不再用它返回的 usage 推算压缩后的 token 数，而是改走"可见历史估算"的路径。载荷过大压缩本来就走这条路径。

### Thought signature

`estimatePartChars` 现在会把 `thoughtSignature` 和 thought 文本一起计入。所有使用这个共享估算器的地方，得到的数都会略大、更保守。

## 决策与理由

| 决策                             | 理由                                                                                                                      |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 保留 char/4 估算器               | 它偏低，所以基于它的拒绝只会发生在请求确实放不下时。#9541 把它换成按字节加权的估算，结果中文会话从窗口约 50% 起就被拒绝。 |
| 先丢助手和工具内容，再动用户消息 | 文件可以重读、命令可以重跑，用户说过的话没有别处可以找回（Codex 出于同样理由逐字保留用户消息）。                          |
| 在 model 消息处切分              | 不用解析轮次结构，就能让 function call 和 response 保持成对，并让引用块之后的角色保持交替。                               |
| 只重试一次                       | 压缩仍是尽力而为，不阻塞用户。报错自带的数字让一次大小合适的重试在常见情况下就够用。                                      |
| 新增失败状态                     | 让用户和遥测能区分"太大无法压缩"和 API 错误。                                                                             |

## 风险

- 基于压缩后输入写出的摘要，对被压缩部分中助手做过的工作了解得比全量历史摘要少。
- 被引用的用户消息里可能夹带随 user 轮次注入的提醒，每条引用都有上限。
- 报错里没有数字时，60% 的重试对密度极高的文本仍可能过大。此时压缩像以前一样失败，不会发出第三次请求。

## 验证

- `compactionInputSlimming.test.ts` 中的单元测试：thought signature 计数、`preserveUserText`，以及 `condenseToUserMessages`（固定第一条、顺序、上限（含第一条消息的更大上限）、与工具结果同轮的用户文字、model 切分点、超大尾部、不修改输入）。
- `chatCompressionService.test.ts` 中的单元测试（`issue #9455`），使用一个强制 `prompt + max_tokens <= window`、并可按高于本地估算计数的后端：
  - 放得下的请求原样发送；
  - 只截短就够；
  - 压成用户原话；
  - 本地拒绝；
  - 压缩后的 token 计数；
  - 中文会话原样准入；
  - 带数字重试、无数字重试、重试一次后放弃、其他错误不重试，以及在请求被拒时恰好中止；
  - 载荷过大（413）压缩基于已截短的输入完成压缩。
- 新状态文案的 CLI 测试。
- 对新逻辑做了 18 个变异的变异测试（准入阈值、本地拒绝、重试次数、重试大小与"必须更小"的检查、中止处理、token 计数条件、413 输入、输出预留、保留用户原话、去掉系统提醒、签名计数、model 切分点、第一条消息的固定与上限、插话文字）：每个变异都至少让一个测试失败。

## 验收标准

- 不发送输出预算低于 4,096 token 的冷路径压缩请求。
- 放得下的请求原样发送。
- 缩减后的请求逐字保留第一条和最新的用户消息，保留部分从 model 消息开始，并且每个 function response 都在它的 call 之后。
- 无法缩减的请求返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`，不发送任何请求，CLI 为它显示非空提示。
- 因上下文长度被拒后，最多重试一次更小的请求。
