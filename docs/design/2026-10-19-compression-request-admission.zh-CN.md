# 压缩请求准入

[English](2026-10-19-compression-request-admission.md) | [简体中文](2026-10-19-compression-request-admission.zh-CN.md)

状态：已为 [#9455](https://github.com/QwenLM/qwen-code/issues/9455) 实现。

## 问题

压缩要把整段历史发给摘要模型。会话越长越需要压缩，这个请求也就越大，最终连它自己都放不进模型的窗口。于是自动、响应式和手动 `/compress` 压缩，会和主请求以同样的方式失败，已经超大的会话无法恢复。

冷路径会按估算剩余的空间夹紧输出预算（#7960），但下限是 1。估算的输入一旦占满窗口，它仍会把请求发出去，此时 `max_tokens: 1`：provider 要么拒绝，要么只返回 1 个 token 的片段。原有的大小检查只覆盖单独配置的压缩模型；主模型同时负责压缩时，没有任何检查拦住请求。

## 改动前的现状

- 冷路径请求由精简后的历史（去掉媒体）、压缩提示词和指令组成，大小用 char/4 估算。
- `computeCompactionOutputBudget` 返回 `min(20K, window − estimate − 1K)`，下限为 1。
- side-query 失败时返回 `COMPRESSION_FAILED_API_ERROR`，只尝试一次（`maxAttempts: 1`）。
- 本地估算对 thought part 只计 `text`，忽略同一 part 上的 `thoughtSignature`。

## 目标

- 绝不发送无法给摘要留出可用输出预算的压缩请求。
- 历史放不下时，分阶段、有界地缩减，并保留完整的工具交互、用户最初的请求和最新的上下文。
- 怎么缩减都放不下时，在本地以清楚的 input-too-large 状态停止。
- 本来就放得下的对话仍走原来的一次压完路径。

## 非目标

- 更准的估算器。固定的按语言倍率会把高密度中文高估约 2 倍（#9541 中实测），导致本可压缩的会话被拒绝，所以不改估算器。
- 共享缓存请求。它失败后会回退到冷路径，而本次改动覆盖冷路径。
- 切换模型后先用旧模型压缩。

## 设计

### 准入

冷路径请求的输出预算不低于下限时照常发送。下限是 `MIN_COMPACTION_OUTPUT_TOKENS`（4,096）；窗口的四分之一比它小时，取窗口的四分之一。固定的 4,096 会占掉 8K 窗口的一半、4K 窗口的全部，而自建部署确实会用这么小的窗口。低于下限时先缩减。

### 缩减阶段

每个阶段在估算达到目标时立即停止。目标是给摘要留出窗口的四分之一，最多 20,000 token，且永远不低于下限。

1. **截短工具内容。** 工具结果、工具调用参数和模型文本截到 4,000 字，复用载荷过大时的上限（#10380）。开启 `preserveUserText` 后，用户输入的文字最多保留 32,000 字（`PRESERVED_USER_TEXT_MAX_CHARS`）；再长的话，一条粘贴的消息就可能比整个窗口还大，怎么缩减都放不下。qwen-code 代用户附加到 user 轮次上的内容（@ 引用的文件、MCP 资源、引用的历史会话）按工具输出截短。装着请求的片段，由构造它、并且知道是哪一段的代码打上标记，即设置 `partMetadata['qwen-code:typed-prompt']`（`markTypedPrompt`）：以纯字符串发送的 prompt 及其重试由 `LlmClient` 标记；用户的 prompt 由 CLI 的 @ 命令处理标记；命令展开后的 prompt 在所有前端（Ink、OpenTUI、无界面模式、ACP）都标记，`@{path}` 注入的文件内容不标记；工具执行期间插进来的输入（Ink、OpenTUI、ACP）标记；ACP 会话的 prompt 标记，没有文字时也标记，此时它的 `@uri` 指针代表附件；只有和命令展开后的 prompt 放在一起的指针不标记，因为那时请求是展开内容；托管服务（hosted serve）的 prompt 标记。定时任务的 prompt 和通知批次发送时不标记：`/loop` 每次触发都以同一种消息类型发送程序生成的文字。之后有两步仍会给它们打上标记：失败后的重试，prompt 是纯字符串时 `LlmClient` 像其他重试一样标记；它运行的命令的展开内容，像其他命令一样标记（Ink 中只有展开结果是片段数组时才标记，纯字符串的展开以定时任务的消息类型发送）。这段文字通常是该轮唯一的文字，按位置读也算用户输入。有标记的轮次里只有带标记的片段算用户输入，不管排列顺序如何；其余片段都算附加内容，包括没有可识别标题行的内容，而提醒、hook 上下文和记忆快照两者都不算。`partMetadata` 只在客户端使用：原生生成器会去掉它，其他转换器从不写出它，会话文件会保存它，ACP 会话记录的 prompt 也一样。没有标记的轮次（标记出现之前记录的、subagent 的任务、定时任务的 prompt、上一次的摘要）沿用按位置的规则，所以文字不会丢：第一个片段是用户输入，即使它以标题行开头也不会被当成附加内容；从第一个以附加内容标题行开头的片段起到该轮结束都算附加内容；hook 上下文和记忆快照各有自己的标识，永远不算用户输入。这些标题行由写出它们的代码和压缩代码共用（`utils/attached-content.ts`）。结束行不可信，因为 `--- End of content ---` 不带随机数，文件内容里也能出现它。超过上限的 `<system-reminder>` 片段会被整段替换成一个保留首尾标签的短提醒，不会因为截断后缺了结束标签，而把后面的文字也包进去。
2. **把较早的轮次压成用户原话。** `condenseToUserMessages` 保留最新的若干轮。保留部分从 model 消息开始，这样不会把 function call 和它的 response 拆开，角色也保持交替。更早的部分在保留部分剩下的空间里合并为一条 user 消息，引用用户的消息。保留部分先按"给引用留出 `maxChars` 的四分之一（最多 64,000 字）"来选，引用再用保留部分实际剩下的空间：
   - 第一条和最新一条消息总是被引用。之前压缩过时第一条就是那次的摘要，所以最多可占 32,000 字，在中间的消息需要剩余空间时至少占最新一条剩下空间的一半；最新一条最多占 8,000 字；
   - 中间的消息按从新到旧的顺序填入，放不下的一条会被跳过，后面更短的仍能填入；
   - 其余每条引用不超过 8,000 字，整个引用块（含说明）不超过 64,000 字。被截短的引用保留开头和结尾，因为长请求常常在结尾才提出问题；
   - 和工具结果同在一个 user 轮次里的用户文字（工具运行期间插入的输入）会被引用，工具输出不会；
   - 引用的消息里出现的 `<user_message>` 和 `<system-reminder>` 标签会被转义（包括带属性或变形的写法），引用无法提前结束自己的包装、伪造另一条引用，也不会带上原样剥离漏掉的提醒；
   - 整段的 `<system-reminder>` 片段不是用户的话，整段不引用，以免它们在有上限的引用里挤掉真正的需求；prompt 片段开头的完整提醒块（CLI 在这里拼入 IDE 上下文）会被去掉，出现在其他位置的提醒标签是用户自己写的，保留并转义；
   - ACP 执行中途的消息在附件解析失败时附带的提示，会保留在引用旁边；
   - 代用户附加的内容只写名字，不引用内容：`[Attached, not quoted: src/app.ts]`。最多列 8 个名字、每个最多 120 字，每个名字压成一行、去掉尖括号，截断时不会切开代理对，因为这些名字来自用户无法控制的标签和路径；
   - 用一句说明写明省略了多少条助手和工具消息，以及中间省略了多少条用户消息；只有没有任何引用被截短时，才说引用是逐字的。说明、引用标签和分隔符都计入长度，所以引用块和保留部分不会超出目标；
   - 剩下的空间放不下第一条和最新一条各 2,000 字（`CONDENSED_MESSAGE_MIN_CHARS`，较短时取全文）时，先把保留部分的文字截到 500 字；这些轮次碰过的文件和图片压缩后本来就会恢复。仍然放不下时（一次并行的大量工具调用就可能这样），不再保留任何轮次，改为引用全部用户消息；只有这样也放不下下限时，才不返回任何结果，因此不会发出丢了用户原话的请求。

   先丢弃助手回复和工具输出，因为文件可以重读、命令可以重跑，而用户说过的话没有别处可以找回。摘要提示词本来就要求写 `primary_request_and_intent` 和 `all_user_messages`，这些引用正好为二者提供输入。

缩减后仍无法留出下限时，压缩返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`，不发送任何请求。它和其他失败一样计入熔断次数。

### 因上下文长度被拒后重试一次

估算仍可能偏低，尤其是高密度中文。provider 以上下文长度为由拒绝冷路径请求时（`getContextLengthExceededInfo`），压缩会用一个更小的请求重试一次，大小由这次拒绝本身决定：

- **窗口。** 报错给出的是整个上下文窗口（`limitKind: 'total'`）且比配置的窗口小时，重试按它来算。报错没说明上限类型时（"prompt is too long: N tokens > M maximum"），只要报错给出的输入大小已经超过这个上限，也同样按它来算；按 1M 推断、实际只提供 200K 的模型，正是在这里第一次暴露真实窗口。自建服务的窗口可能比模型本身的小，而拒绝信息是它第一次出现的地方。
- **输入大小。** 重试从拒绝信息里读出被拒请求输入部分本身的大小。"you requested N tokens" 没有分项时，这个总数还包含请求的输出预算，重试把它当作输入大小的上界：发送途中 `max_tokens` 可能被配置或模型的输出上限压得比压缩要求的更小，减去要求的预算可能把输入算小。数字远低于该请求的估算，或者按同一条信息给出的上限、该请求本来放得下时，它描述的是别的请求，会被忽略。
- **只是输出超了。** 输入给摘要留下了预留空间（窗口的四分之一，最多 20,000 token）时，原样重发同一个请求，只把 `max_tokens` 降到这个数字留下的空间，且不会低于预留空间。如果这个空间并不比发出去的预算小，说明按这个数字请求本该放得下，服务端的窗口比这个窗口小、但报错没说小多少，这时改为固定缩小到 60%。
- **删掉超出的部分。** 否则重试从估算里删掉超出量（输入大小 + 预留 + 1,024 − 窗口；报错写明了输入上限、并且下式更大时，取输入大小 + 1,024 − 输入上限），先删工具输出，并按预留空间要输出。char/4 通常偏低，所以每删掉一个估算 token，真实至少减少一个 token，无论剩下的内容疏密如何，输入都放得下。用"数字 ÷ 估算"的比例则做不到：缩减保留的用户文字往往比删掉的工具输出更密（中文对英文），比例会低估剩下的部分。如果数字比估算还小（比较稀疏的英文），删掉一个估算 token 减少不到一个真实 token，所以按这个比例多删一些。
- **删不出超出量。** 怎么缩减都删不掉"每个估算 token 按一个真实 token 计"的超出量时，如果删掉的内容和其余部分一样密，删得少一些就够了。这时不直接拒绝，而是按被拒请求的平均密度（数字 ÷ 估算）来定重试大小，并且至少缩小到 60%。只有留下的内容比删掉的更密时它才会超长，然后像任何第二次被拒一样失败。
- **没有数字。** 重试目标为被拒请求估算值的 60%，如果要留出预留空间需要更小，就取更小的值。
- **放不下。** 在这个窗口里怎么缩减都留不出下限，或者缩减后根本没有变小时，不发送重试，压缩返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`。重试再次因为上下文长度被拒时也返回这个状态，而不是 API 错误。

第二次失败，或任何其他错误，仍像以前一样返回 `COMPRESSION_FAILED_API_ERROR`。

`getContextLengthExceededInfo` 只从把输入和输出预算分开写的报错里报告输入本身的大小（`promptTokens`）：OpenAI 的 "resulted in N tokens"、从 "you requested N tokens (… in the completion)" 里减去输出部分（OpenAI、DeepSeek、旧版 vLLM、OpenRouter）、Anthropic 的 "prompt is too long"、vLLM 的 "your prompt contains N input tokens" 和 "your request has N input tokens"、Gemini 的旧写法、llama.cpp 和 SGLang。没有分项的 "you requested N tokens" 总数报告为 `requestedTokens`；只说输出的写法（"you requested N tokens in the completion"）不给数字。每种写法都只在报错的单个片段内匹配，所以不会把别的字段里的数字配到这句话上。`actualTokens` 仍是被动压缩路径一直读取的那个数。vLLM 的 "contains at least N" 写法表示分词在哪里停下，不是请求的实际大小，因此仍只取窗口。

### 被截断的摘要

摘要打开了 `<state_snapshot>` 却没有闭合时，不管报告的输出数是多少，都按 `COMPRESSION_FAILED_OUTPUT_TRUNCATED` 丢弃。vLLM 遇到 `prompt + max_tokens > window` 时不拒绝请求，而是把 `max_tokens` 降到 prompt 剩下的空间，于是报告的输出数低于请求的预算，原有的阈值检查看不出被截断。不带标签的摘要不受影响。检查前只去掉已闭合的 `<analysis>` 块：真实模型经常在 snapshot 里引用压缩指令，连同其中的 `<analysis>` 标签；如果从这个引用一直去到结尾，snapshot 的闭合标签也会被一起去掉。检查的是第一个出现在行首的开始标签：句子中间提到这个标签（不论在 snapshot 之前还是之后）都不会打开 snapshot。代价是反过来的情况：摘要先引用了一个完整的示例 snapshot、后面真正的 snapshot 却被截断，这样的摘要能通过检查。改动之前基于输出数的检查也漏掉这种情况。

### token 计数

缩减后的请求已不能代表它要替换的历史，所以不再用它返回的 usage 推算压缩后的 token 数，而是改走"可见历史估算"的路径。载荷过大压缩本来就走这条路径。

### Thought signature

`estimatePartChars` 现在会把 `thoughtSignature` 和 thought 文本一起计入。所有使用这个共享估算器的地方，得到的数都会略大、更保守。

## 决策与理由

| 决策                                 | 理由                                                                                                                                                                                                                                               |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 保留 char/4 估算器                   | 它偏低，所以基于它的拒绝只会发生在请求确实放不下时。#9541 把它换成按字节加权的估算，结果中文会话从窗口约 50% 起就被拒绝。                                                                                                                          |
| 先丢助手和工具内容，再动用户消息     | 文件可以重读、命令可以重跑，用户说过的话没有别处可以找回（Codex 出于同样理由逐字保留用户消息）。                                                                                                                                                   |
| 在 model 消息处切分                  | 不用解析轮次结构，就能让 function call 和 response 保持成对，并让引用块之后的角色保持交替。                                                                                                                                                        |
| 只重试一次                           | 压缩仍是尽力而为，不阻塞用户。报错自带的数字让一次大小合适的重试在常见情况下就够用。                                                                                                                                                               |
| 新增失败状态                         | 让用户和遥测能区分"太大无法压缩"和 API 错误。                                                                                                                                                                                                      |
| 16K 以下用窗口的四分之一作下限       | 固定的 4,096 只给 8K 窗口的历史留很少空间，4K 窗口则完全没有。较小预算放不下的摘要会按截断丢弃，历史保持不变。                                                                                                                                     |
| 删掉超出的部分，而不是按比例缩放     | 比例假设请求的每个部分一样密。重试保留用户文字、删掉工具输出，比例会低估剩下的部分。按"每个估算 token 至少一个真实 token"删掉超出量，剩下的内容一定放得下，重试的 `max_tokens` 也来自数字而不是估算。                                              |
| 在构造请求的地方打标记               | 排列顺序不同：CLI 把 prompt 放在最前，ACP 会话放在最后。附加内容的来源很多而且还在增加；请求只在少数几个知道它是哪一段的地方构造（见"验证"）。没有标记的轮次按位置判断，不打标记的路径不会丢失原来就有的内容。结束行不可信，因为文件里也能出现它。 |
| 未闭合的 snapshot 不看输出数直接丢弃 | 悄悄降低 `max_tokens` 的服务报告的输出数低于预算，未闭合的标签是唯一的截断信号。不带标签的摘要不受影响，因为较弱的模型可能不按格式输出。                                                                                                           |

## 风险

- 基于压缩后输入写出的摘要，对被压缩部分中助手做过的工作了解得比全量历史摘要少。
- 没有标记的轮次里，附加内容靠 qwen-code 写出的标题行识别；用别的方式附加的文字（比如 URL 媒体的转写文本）会被当成用户输入，最多保留 32,000 字。直接拼进 prompt 片段里的文字（比如 CLI 的 IDE 上下文）在截短阶段算用户输入；它是片段开头的 system reminder，引用时会被去掉。
- 历史整理时如果把两条相邻的 user 轮次合并（丢弃了无效的模型回复，或者失败的 prompt 留在历史里），而其中一条来自不打标记的路径，同一轮里就会同时有带标记的片段和不带标记的请求文字。不带标记的文字只会被列为附加内容，不会被引用。
- `/loop` 每次触发的说明会像用户消息一样被引用：没有标记时按位置判断，被重试或命令展开打上标记时直接算用户输入。
- 报错里没有数字时，60% 的重试对密度极高的文本仍可能过大。此时压缩像以前一样失败，不会发出第三次请求。
- 删掉超出部分的做法假设每删掉一个估算 token，减少的真实 token 不少于整个请求的平均值（平均值大于一时按一计）。删掉的内容本身也很密时（比如中文的工具输出），会删得比需要的多。完整的删减做不到时，重试改按平均密度来定，留下的内容比删掉的更密时仍可能超长；压缩在那一次重试后失败。
- 窗口小于约 16K 时，缩减后的请求只给摘要留窗口的四分之一，较长的摘要可能放不下，此时按截断丢弃，历史保持不变。在 4K 窗口下，压缩后的输入基本只剩第一条请求。

## 验证

## 验收标准

- 不发送输出预算低于 4,096 token（窗口的四分之一更小时取四分之一）的冷路径压缩请求。
- 放得下的请求原样发送。
- 缩减后的请求引用第一条和最新的用户消息（全文，或保留开头和结尾、各至少 2,000 字），保留部分从 model 消息开始，并且每个 function response 都在它的 call 之后。它不会把附加内容当成用户原话引用。
- 历史里有用户消息时，不发送不含用户原话的压缩请求。
- 无法缩减的请求返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`，不发送该请求；或者在拒绝信息表明任何重试都放不下时不发送重试，或者重试也因为上下文长度被拒；CLI 为它显示非空提示。
- 因上下文长度被拒后，最多重试一次更小的请求。拒绝信息给出窗口时，重试放得进这个窗口。给出输入大小时，重试要么原样重发并减少输出空间（不低于预留），要么删掉超出量并按预留空间要输出。
- 在 `<state_snapshot>` 中间被截断的摘要不会被保存。

## 后续

- 共享缓存路径对来自其他路由的 token 锚点做准入。
- 切换到更小窗口前，先用旧模型压缩。
- vLLM 的 "`max_tokens` cannot be greater than" 拒绝不会被识别为上下文超长。识别它也会改变主对话路径的行为。
- 超长时从最前面丢消息而不是拒绝的服务（Ollama 的默认行为）不会给出可供重试的拒绝，而压缩后的引用块正是它最先丢掉的消息。
- 用考虑中文的偏高估算来确定第一次请求的输出预算，让高密度会话不必先被拒绝、再靠重试修正。
- 按片段估算密度下限（比如英文每 4 个字符 1 个 token、中文每 2 个字符 1 个 token），删掉的内容很密时，删超出量就能删得少一些。
- Anthropic 的 "input length and `max_tokens` exceed context limit: P + C > L" 不会被识别为上下文超长。识别它也会改变主对话路径的行为；对重试来说，它直接给出了输入大小。
- 没有标记的轮次里，用别的方式附加的文字（比如 URL 媒体的转写文本）没有可识别的标题行，会被当成用户输入。标记出现之前记录的会话没有标记。
