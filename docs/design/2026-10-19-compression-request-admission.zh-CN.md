# 压缩请求准入

[English](2026-10-19-compression-request-admission.md) | [简体中文](2026-10-19-compression-request-admission.zh-CN.md)

状态：已为 [#9455](https://github.com/QwenLM/qwen-code/issues/9455) 实现。在缩减后的请求里完整保留用户消息，留给后续改动（[#14953](https://github.com/QwenLM/qwen-code/pull/14953)）。

## 问题

压缩要把整段历史发给摘要模型。会话越长越需要压缩，这个请求也就越大，最终连它自己都放不进模型的窗口。于是自动、响应式和手动 `/compress` 压缩，会和主请求以同样的方式失败，已经超大的会话无法恢复。

冷路径会按估算剩余的空间夹紧输出预算（#7960），但下限是 1。估算的输入一旦占满窗口，它仍会把请求发出去，此时 `max_tokens: 1`：provider 要么拒绝，要么只返回 1 个 token 的片段。原有的大小检查只覆盖单独配置的压缩模型；主模型同时负责压缩时，没有任何检查拦住请求。

## 改动前的现状

- 冷路径请求由精简后的历史（去掉媒体）、压缩提示词和指令组成，大小用 char/4 估算。思考 part 的签名和文字一起计入：签名会和文字一起原样发回服务端，而 #9455 要求准入守卫不要继承估算器漏算签名的问题。
- `computeCompactionOutputBudget` 返回 `min(20K, window − estimate − 1K)`，下限为 1。
- side-query 失败时返回 `COMPRESSION_FAILED_API_ERROR`，只尝试一次（`maxAttempts: 1`）。

## 目标

- 绝不发送输入本身就给摘要留不出任何输出空间的压缩请求；留不出可用的输出预算时先缩减。
- 历史放不下时，在不丢掉任何轮次的前提下缩减，让每个工具调用都保留它的结果。
- 缩减后仍放不下时，在本地以清楚的 input-too-large 状态停止。
- 本来就放得下的对话仍走原来的一次压完路径。

## 非目标

- 更准的估算器。固定的按语言倍率会把高密度中文高估约 2 倍（#9541 中实测），导致本可压缩的会话被拒绝，所以不改估算器。
- 在缩减后的请求里完整保留用户消息，或丢掉较早的轮次来腾出空间。二者都需要知道哪段文字是用户输入的，留给后续改动（#14953）。
- 共享缓存请求。它失败后会回退到冷路径，而本次改动覆盖冷路径。
- 切换模型后先用旧模型压缩。

## 设计

### 准入

冷路径请求的输出预算不低于下限时照常发送。下限是 `MIN_COMPACTION_OUTPUT_TOKENS`（4,096）；窗口的四分之一比它小时，取窗口的四分之一。固定的 4,096 会占掉 8K 窗口的一半、4K 窗口的全部，而自建部署确实会用这么小的窗口。低于下限时先缩减。

### 缩减

缩减后的请求把每个文本片段（工具结果、工具调用参数、模型文本和用户消息）截到 4,000 字，复用载荷过大时的上限（#10380）。被截短的片段保留开头。不丢掉任何轮次，所以每个 function call 都保留它的 response，角色也保持交替。以 `<system-reminder>`、钩子上下文块或 `<task-notification>` 开头的片段，以及以这类块结尾的文字（比如调度器在输出之后追加了提醒的工具结果），如果截断落在这个块里面，会在截断处之后补回块的结束标签：如果像普通文字一样截断，它会缺了结束标签，把后面的文字也包进去。IDE 上下文被前置到用户提示所在的片段里，虽然片段以用户提示结尾，它也算这样的块。只有结束标签越过上限的块保留到结束标签为止，之后的内容截掉。文字开头或结尾处的块按写入方自己的块来读，包括在那里只隔着空白叠放的几个：CLI 会把一个提醒叠在另一个之上，工具结果末尾也可能跟着不止一个，截断落在其中第二个里时，闭合的就是第二个（#15936 R3-3）。写入方会转义块正文里的标签，但工具读到的文件和用户输入的文字不转义，可以在任何位置引用一个块。截断落在这样一个被引用的块里面时（在整段文字里配成一对的开始标签和结束标签之间），也会在截断处之后把这个块闭合；有嵌套时先闭合里面的（#15936 R7-1）。单独被引用的一个标签配不成对，按原样保留。

缩减后仍留不出下限的请求，和这次改动之前一样，按剩下的空间发送。摘要放不下这点空间时，由下面的截断检查丢弃，历史保持不变。如果改为拒绝，一个放得下的请求就变成了必然的失败：没有超过 4,000 字的片段时缩减什么也截不掉，由短消息组成的会话就完全无法压缩（#15936 R3-7）。只有输入本身留不出任何输出空间（估算加 1,024 的余量达到或超过窗口）的请求才不发送：压缩返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`，不发送任何请求。它和其他失败一样计入熔断次数。载荷过大时的压缩（#10380）在计算大小之前就截短了每个片段，缩减已经没有可截的内容；留不出任何空间的请求同样在本地拒绝，而不是带着压到 1 的预算发出去。413 恢复以这个状态结束时，给出开新会话的提示：它不同于临时的侧查询失败，之后的发送只会让历史更长。

### 因上下文长度被拒后重试一次

估算仍可能偏低，尤其是高密度中文。provider 以上下文长度为由拒绝冷路径请求时，压缩会重试一次，大小按本地估算来定：

- **窗口。** 重试按配置的窗口和拒绝文字本身写明的每个窗口（`statedContextWindows`）中最小的那个来算。自建服务的窗口可能比配置的小，而拒绝信息是它第一次露面的地方。写明的窗口只会让重试变小。不带类型的 "N tokens > M" 不当作窗口，因为限额类文字也是这个形状；输入上限也不当作窗口，因为它允许 `prompt + max_tokens` 超过它，按它定窗口会把摘要预算压到最低（#13876）。
- **请求。** 缩减后的请求；缩减什么也没截掉时，就是被拒的那个请求。
- **输出预算。** 它的估算在这个窗口里留下的空间，最多到预留空间：窗口的四分之一，最多 20,000 token。这次拒绝刚说明估算偏低，所以估算声称的、超出预留空间的那部分不去用。按完整输出预算来定时，在输入实际是估算 1.5 倍的会话里，实测 25 种情况有 15 种重试再次超长；限制在预留空间以内时只有 3 种。
- **什么时候发。** 它在输入或输出预算上比被拒的请求小，并且按估算在窗口里还有空间时就发。这和第一次发送用的是同一条规则，所以剩余空间低于下限的重试照样按留下的空间发送（#15936 R5-3），输入缩不下来的重试也会带着更小的输出预算发出（R5-4）。
- **放不下。** 否则不发送重试，压缩返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`。重试再次因为上下文长度被拒时也返回这个状态，而不是 API 错误。

第二次失败，或任何其他错误，仍像以前一样返回 `COMPRESSION_FAILED_API_ERROR`。

拒绝信息里只读窗口。`statedContextWindows` 从报错里每段本身就是上下文超长拒绝的文字中，在措辞写明窗口时取一个数："maximum context length is N"（OpenAI、vLLM、DeepSeek）、SGLang 的 "maximum context length of N"、llama.cpp 的 available context size，以及 TGI 的总量上限。服务商给出的被拒请求输入大小不读。第 3 到第 5 轮审查一直在找出读错的情况：放在别的字段或同一段文字里的更早一次尝试的数字、被当成计数的上限、被算进输入的输出预算（"resulted in N tokens (X in the messages, Y in the completion)"）。每次修复只覆盖一种写法，下一轮又找到另一种。调研的几家 agent 里，只有 Claude Code 读这种数字，而且只读它自家 API 写的那一种格式，读出来也只当参考，读不到就固定删一部分。多服务商的 Codex、opencode、pi、grok-build、Cline 都不读；唯一尝试去读的 fantasy，把包含输出的总数记成了已用量。主对话被动压缩路径的读法，除了 SGLang 的 "of" 写法以外没有变化。

### 被截断的摘要

摘要打开了 `<state_snapshot>` 却没有闭合时，只有服务端自己报告的输入数和输出数表明请求在它所按的窗口里还有余量（两者加起来比该窗口少 1,024 token 以上），才保留它：这时没有东西截断它，模型可能只是结束时漏写了闭合标签，把这类摘要都丢掉会触发失败熔断。其他情况按 `COMPRESSION_FAILED_OUTPUT_TRUNCATED` 丢弃。服务端遇到 `prompt + max_tokens > window` 时可能不拒绝请求，而是在窗口用完处停止输出（llama.cpp 的服务端就是这样），于是报告的输出数低于请求的预算，原有的阈值检查看不出被截断。服务端不报告输出数、或只报告输入数（输出数只能本地估算）时，没有任何东西能说明窗口没被撑满，摘要不会在这种不确定下被保留（#15936 R4-8）。重试按拒绝信息给出的更小窗口来算时，检查的就是那个窗口。这项检查不管不带标签的摘要。但一条更早的规则（#7960）原样保留，它确实会丢弃摘要：输出预算被压到完整摘要预算以下、且输出数是本地估算时，估算值到不了截断阈值，所以没有闭合 snapshot 的摘要（不论带不带标签）会按截断丢弃，并计入熔断。检查前只去掉已闭合的 `<analysis>` 块：真实模型经常在 snapshot 里引用压缩指令，连同其中的 `<analysis>` 标签；如果从这个引用一直去到结尾，snapshot 的闭合标签也会被一起去掉。检查的是第一个出现在行首的开始标签：句子中间提到这个标签（不论在 snapshot 之前还是之后）都不会打开 snapshot。代价是反过来的情况：摘要先引用了一个完整的示例 snapshot、后面真正的 snapshot 却被截断，这样的摘要能通过检查。改动之前基于输出数的检查也漏掉这种情况。

摘要结尾停在开始标签中间（`<state_snap`，短到只剩一个 `<`）或刚写完开始标签时，不论 usage 怎么说都会被丢弃：模型不会自己停在那里，只有截断才会。检查只看最后一行最后一个 `<` 起的部分，所以标签前面有文字（`Summary: <state_snap`）也藏不住它，而标签后面还跟着任何字符的提及（`<state_snapshot>.`）不算截断（#15936 R5-9）。

### token 计数

缩减后的请求已不能代表它要替换的历史，所以不再用它返回的 usage 推算压缩后的 token 数，而是改走"可见历史估算"的路径。载荷过大压缩本来就走这条路径。缩减什么也没截掉时，请求和原来一样，所以照常用它的 usage，和从未缩减过一样。

## 决策与理由

| 决策                                         | 理由                                                                                                                                                                                                                                                                                                       |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 保留 char/4 估算器                           | 它偏低，所以基于它的拒绝只会发生在请求确实放不下时。#9541 把它换成按字节加权的估算，结果中文会话从窗口约 50% 起就被拒绝。                                                                                                                                                                                  |
| 截短每个文本片段，保留每个轮次               | 复用载荷过大时的截短（#10380），不用解析轮次结构就能让 function call 和 response 保持成对。完整保留用户消息需要知道哪段文字是用户输入的，由后续改动加入。                                                                                                                                                  |
| 只重试一次                                   | 压缩仍是尽力而为，不阻塞用户。限制在预留空间以内的重试在大多数实测情况下都放得下；放不下的和任何第二次被拒一样失败。                                                                                                                                                                                       |
| 新增失败状态                                 | 让用户能从提示文字区分"太大无法压缩"和 API 错误。                                                                                                                                                                                                                                                          |
| 16K 以下用窗口的四分之一作下限               | 固定的 4,096 只给 8K 窗口的历史留很少空间，4K 窗口则完全没有。较小预算放不下的摘要会按截断丢弃，历史保持不变。                                                                                                                                                                                             |
| 低于下限但放得下时照常发送                   | 下限决定什么时候缩减，而不是要不要发送。拒绝一个放得下的请求，会把一份可能放得下的摘要变成必然的失败；放不下的摘要无论哪种做法都按截断丢弃。调研过的 agent（Claude Code、Codex、grok-build、opencode、pi、crush）都不会在发送前拒绝摘要请求。                                                              |
| 不从拒绝信息里读请求大小                     | 各家写请求大小的方式不同，同样一个数可能是输入、输入加输出预算、一个下限，或者一个上限；一个报错里可能装着好几次尝试，文字里没有任何东西能说明哪个是这一次的。五轮审查每轮都找到新的读错。窗口只用来让重试变小，所以读到旧的或错的窗口，最多是摘要变小或这次重试被拒。                                     |
| 每次重试只用一条规则                         | 重试和第一次发送一样定大小、一样准入：按估算，限制在预留空间以内，比被拒的请求小并且有空间就发。按读出的数分支，结果就取决于命中了哪种写法。                                                                                                                                                               |
| 只在 usage 表明有余量时保留未闭合的 snapshot | 在窗口用完处停止输出的服务报告的输出数低于预算。报告的输入数和输出数表明窗口还有余量时，没有东西截断摘要，未闭合的标签只可能是模型漏写，丢掉这类摘要会触发失败熔断。缺少其中任何一个数时，分不出是被截断还是漏写，写了一半的摘要会替换掉历史。这项检查不管不带标签的摘要，因为较弱的模型可能不按格式输出。 |

## 风险

- 缩减后的请求像工具输出一样把用户消息截到 4,000 字、只保留开头，摘要可能看不到长请求的结尾。后续改动会完整保留它们。
- 缩减只截短超过 4,000 字的片段。由许多较短消息组成的会话不会变小，会按剩下的空间发送，较长的摘要可能放不下；那份摘要按截断丢弃，并计入熔断次数。只有输入本身留不出任何空间时，才以 `COMPRESSION_FAILED_INPUT_TOO_LARGE` 拒绝。
- 重试按本地估算来定，而这次拒绝刚说明估算偏低。文本密度很高时，限制在预留空间以内的缩减请求仍可能超长：在输入实际是估算 1.5 倍的会话里，实测 25 种情况有 3 种。此时压缩在那一次重试后失败，不会发出第三次请求。从拒绝信息读出的数字能把这些情况定得更准，代价是上面那些读错；用服务商的 usage 校准估算是后续工作。
- 窗口小于约 16K 时，缩减后的请求最多给摘要留窗口的四分之一，无法缩减的请求可能留得更少。较长的摘要可能放不下，此时按截断丢弃，历史保持不变。
- 只用不带类型的 "N tokens > M"（Anthropic 的写法）或输入上限来说明窗口的情况不会被读取。真实窗口比配置小、又只这样写的服务端，重试会按配置的窗口来算，可能再次被拒。
- 第一次请求只是输出预算超了时，重试仍会截短输入里的长片段，摘要看到的工具输出会比本来可以看到的短。
- 服务端在比请求所按窗口更小的窗口处停止输出，或传输层把输出上限压到预算以下时，摘要可能在 snapshot 中间被截断，而 usage 并没有达到那个窗口。这样的摘要会被保留，和改动之前一样。
- 输出预算被压低、且服务端只报告输入数时，#7960 的规则会丢弃没有闭合 snapshot 的摘要（不论带不带标签），并计入失败熔断。在这样的服务端上，不按格式输出的较弱模型会失去这些压缩。本次改动原样保留这条规则。
- 服务端不报告输出数时，打开了 `<state_snapshot>` 却没有闭合的摘要即使在完整的输出预算下也会被丢弃，并计入失败熔断。在这样的服务端上，漏写闭合标签的模型会失去这些压缩。停止原因能分清是被截断还是漏写，但压缩目前还拿不到它。
- 在 80,000 token 及以上的窗口上，预留空间等于 20,000 token 的输出上限。缩减什么也截不掉、拒绝信息也没写明更小的窗口时，重试没法比用满预算被拒的请求要更少的输出，所以不发重试，压缩返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`。低于这个大小时，只降输出的重发照常进行。这是第 6 轮延后的 R5-4。
- 思考签名现在和文字一样按 char/4 计入，而且是在所有调用方共用的估算函数里。服务端按低于这个的量计费、或某条请求路径不发送签名时，估算偏高：压缩会更早地压低输出预算或缩减输入；其他对带签名思考的历史做的估算（首次拿到服务端计数之前的自动压缩判断、旁路请求的输出上限）也会偏高。`tokenEstimation.ts` 记载偏高是安全的方向。

## 验证

- `compactionInputSlimming.test.ts` 中的单元测试：在 500 字和 4,000 字两种上限下，过长的提醒被截短并重新闭合；截断落在合并到用户提示前面的 IDE 上下文里、或落在钩子上下文块里时，同样重新闭合；在上限之前已闭合的提醒不会被闭合两次；只有闭合标签越过上限时，提醒保持完整；被截断的任务通知重新闭合；追加在工具输出或错误信息之后的提醒被截断时重新闭合，只有这个提醒的闭合标签越过上限时工具输出保持完整，工具自身输出里引用的标签和被截掉的提醒都不补闭合标签；在片段开头叠放的两个提醒、追加在工具输出后的两个提醒，截断落在哪个里就重新闭合哪个；工具结果只在末尾引用了一个闭合标签、任何地方都没有开始标签时，不补闭合标签；截断落在工具输出里或文本片段中间被引用的块里时，重新闭合这个块，有嵌套时每一层都闭合。

## 验收标准

- 冷路径压缩请求给摘要留下的空间不到 4,096 token（窗口的四分之一更小时取四分之一）时，先缩减。缩减后输入仍留不出任何输出空间的不发送；放得下的按它留下的空间发送。
- 重试只从拒绝信息里读它自己写明的窗口，而且只用来让重试变小；不读请求大小。
- 放得下的请求原样发送。
- 缩减后的请求保留每个轮次，所以每个 function response 都在它的 call 之后。
- 无法缩减的请求返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`，不发送该请求；或者在拒绝信息表明任何重试都放不下时不发送重试，或者重试也因为上下文长度被拒；CLI 为它显示非空提示。
- 因上下文长度被拒后，最多重试一次。拒绝信息写明窗口时，重试按估算放得进这个窗口。重试在输入或输出预算上比被拒的请求小。
- 在 `<state_snapshot>` 中间被截断的摘要不会被保存，除非服务端自己报告的输入数和输出数表明请求在它所按的窗口里还有余量；结尾停在开始标签中间或刚写完开始标签的摘要一律不保存。

## 后续

- 在缩减后的请求里完整保留用户消息，并在截短不够时把较早的轮次压成用户原话（#14953）。
- 用服务商的 usage 校准压缩估算：上一次请求报告的输入数除以本地对它的估算，大于 1 时乘上去。它和 #9541 的固定系数不同，是每个会话实测的，不应系统性高估。它能像读出的数字那样把高密度的重试定准。
- 从服务端本身获取自建服务的窗口，而不是从拒绝文字里读：llama.cpp 的 `/v1/models` 会报告 `n_ctx`，crush 就是这么读的。
- 把服务商的停止原因传给压缩调用，因长度停止的摘要直接丢弃。pi、Claude Code 和 Codex 只看这一项；`GenerateTextResult` 目前不带它。缺少停止原因不等于正常停止：非流式的 OpenAI 转换代码会补成 `stop`。
- 共享缓存路径对来自其他路由的 token 锚点做准入。
- 切换到更小窗口前，先用旧模型压缩。
- vLLM 的 "`max_tokens` cannot be greater than" 拒绝不会被识别为上下文超长。识别它也会改变主对话路径的行为。
- 超长时从最前面丢消息而不是拒绝的服务（Ollama 的默认行为）不会给出可供重试的拒绝。
- 用考虑中文的偏高估算来确定第一次请求的输出预算，让高密度会话不必先被拒绝、再靠重试修正。
- 压缩遥测只在压缩走完全程时记录，所以这个状态和 API 失败都不会出现在遥测里。在失败返回处带上状态记录遥测，就能在看板上比较两者。
- Anthropic 的 "input length and `max_tokens` exceed context limit: P + C > L" 不会被识别为上下文超长。识别它也会改变主对话路径的行为。
- 另有一些超长报错同样不会被识别为上下文超长：xAI、Together 的 "The input (N tokens) is longer than"、SiliconFlow、Bedrock Titan、vLLM 引擎层的 "decoder prompt"、llama.cpp 无法拆分的输入、Kimi 的旧写法、MiniMax、智谱的 "Prompt exceeds max length"、LM Studio 和 Ollama 的 llama-server。它们的压缩请求被拒时仍像以前一样失败。识别它们也会改变主对话何时压缩，所以应当单独改动，就像 #16245 为 TGI 做的那样。
