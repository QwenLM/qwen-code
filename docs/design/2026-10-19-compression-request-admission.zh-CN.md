# 压缩请求准入

[English](2026-10-19-compression-request-admission.md) | [简体中文](2026-10-19-compression-request-admission.zh-CN.md)

状态：已为 [#9455](https://github.com/QwenLM/qwen-code/issues/9455) 实现。在缩减后的请求里完整保留用户消息，留给后续改动（[#14953](https://github.com/QwenLM/qwen-code/pull/14953)）。

## 问题

压缩要把整段历史发给摘要模型。会话越长越需要压缩，这个请求也就越大，最终连它自己都放不进模型的窗口。于是自动、响应式和手动 `/compress` 压缩，会和主请求以同样的方式失败，已经超大的会话无法恢复。

冷路径会按估算剩余的空间夹紧输出预算（#7960），但下限是 1。估算的输入一旦占满窗口，它仍会把请求发出去，此时 `max_tokens: 1`：provider 要么拒绝，要么只返回 1 个 token 的片段。原有的大小检查只覆盖单独配置的压缩模型；主模型同时负责压缩时，没有任何检查拦住请求。

## 改动前的现状

- 冷路径请求由精简后的历史（去掉媒体）、压缩提示词和指令组成，大小用 char/4 估算。
- `computeCompactionOutputBudget` 返回 `min(20K, window − estimate − 1K)`，下限为 1。
- side-query 失败时返回 `COMPRESSION_FAILED_API_ERROR`，只尝试一次（`maxAttempts: 1`）。

## 目标

- 绝不发送无法给摘要留出可用输出预算的压缩请求。
- 历史放不下时，在不丢掉任何轮次的前提下缩减，让每个工具调用都保留它的结果。
- 缩减后仍放不下时，在本地以清楚的 input-too-large 状态停止。
- 本来就放得下的对话仍走原来的一次压完路径。

## 非目标

- 更准的估算器。固定的按语言倍率会把高密度中文高估约 2 倍（#9541 中实测），导致本可压缩的会话被拒绝，所以不改估算器。
- 在缩减后的请求里完整保留用户消息，或丢掉较早的轮次来腾出空间。二者都需要知道哪段文字是用户输入的，留给后续改动（#14953）。
- 共享缓存请求。它失败后会回退到冷路径，而本次改动覆盖冷路径。
- 切换模型后先用旧模型压缩。

## 设计

### 准入

冷路径请求的输出预算不低于下限时照常发送。下限是 `MIN_COMPACTION_OUTPUT_TOKENS`（4,096）；窗口的四分之一比它小时，取窗口的四分之一。固定的 4,096 会占掉 8K 窗口的一半、4K 窗口的全部，而自建部署确实会用这么小的窗口。低于下限时先缩减。

### 缩减

缩减后的请求把每个文本片段（工具结果、工具调用参数、模型文本和用户消息）截到 4,000 字，复用载荷过大时的上限（#10380）。被截短的片段保留开头。不丢掉任何轮次，所以每个 function call 都保留它的 response，角色也保持交替。超过上限的整段 `<system-reminder>` 片段同样截短正文，再补回结束标签：如果像普通文字一样截断，它会缺了结束标签，把后面的文字也包进去。

缩减后仍无法留出下限时，压缩返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`，不发送任何请求。它和其他失败一样计入熔断次数。

### 因上下文长度被拒后重试一次

估算仍可能偏低，尤其是高密度中文。provider 以上下文长度为由拒绝冷路径请求时（`getContextLengthExceededInfo`），压缩会重试一次，大小由这次拒绝本身决定：

- **窗口。** 报错给出的是整个上下文窗口（`limitKind: 'total'`）且比配置的窗口小时，重试按它来算。报错没说明上限类型时（"prompt is too long: N tokens > M maximum"），只要报错给出的输入大小已经超过这个上限，也同样按它来算；按 1M 推断、实际只提供 200K 的模型，正是在这里第一次暴露真实窗口。自建服务的窗口可能比模型本身的小，而拒绝信息是它第一次出现的地方。
- **输入大小。** 重试从拒绝信息里读出被拒请求输入部分本身的大小。"you requested N tokens" 没有分项时，这个总数还包含请求的输出预算，重试把它当作输入大小的上界：发送途中 `max_tokens` 可能被配置或模型的输出上限压得比压缩要求的更小，减去要求的预算可能把输入算小。数字远低于该请求的估算，或者按同一条信息给出的上限、该请求本来放得下时，它描述的是别的请求，会被忽略。
- **只是输出超了。** 输入给摘要留下了预留空间（窗口的四分之一，最多 20,000 token）时，原样重发同一个请求，只把 `max_tokens` 降到这个数字留下的空间，且不会低于预留空间。如果这个空间并不比发出去的预算小，说明按这个数字请求本该放得下，服务端的窗口比这个窗口小、但报错没说小多少，这时改为发送缩减后的请求，和报错里没有数字时一样。
- **删掉了超出量。** 否则重试需要估算减少一个超出量：输入大小 + 预留 + 1,024 − 窗口；报错写明了输入上限、并且下式更大时，取输入大小 + 1,024 − 输入上限。缩减后的请求减少了这么多时，就以预留空间作为输出预算发送。char/4 通常偏低，所以每删掉一个估算 token，真实至少减少一个 token，无论剩下的内容疏密如何，输入都放得下。用"数字 ÷ 估算"的比例则做不到：缩减保留的文字（比如没超过上限的中文消息）可能比截掉的工具输出更密，比例会低估剩下的部分。如果数字比估算还小（比较稀疏的英文），删掉一个估算 token 减少不到一个真实 token，所以需要减少的量按这个比例放大。
- **没删掉超出量。** 缩减后的请求减少得不够时，如果删掉的内容和其余部分一样密，删得少一些就够了。这时不直接拒绝，而是按被拒请求的平均密度（数字 ÷ 估算）来定重试的输出预算。只有留下的内容比删掉的更密时它才会超长，然后像任何第二次被拒一样失败。
- **没有数字。** 发送缩减后的请求，输出预算按它自己的估算来定。
- **放不下。** 缩减后的请求在这个窗口里留不出下限，或者并不比被拒的请求小时，不发送重试，压缩返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`。重试再次因为上下文长度被拒时也返回这个状态，而不是 API 错误。

第二次失败，或任何其他错误，仍像以前一样返回 `COMPRESSION_FAILED_API_ERROR`。

`getContextLengthExceededInfo` 只从把输入和输出预算分开写的报错里报告输入本身的大小（`promptTokens`）：OpenAI 的 "resulted in N tokens"、从 "you requested N tokens (… in the completion)" 里减去输出部分（OpenAI、DeepSeek、旧版 vLLM、OpenRouter）、Anthropic 的 "prompt is too long"、vLLM 的 "your prompt contains N input tokens" 和 "your request has N input tokens"、Gemini 的旧写法、llama.cpp 和 SGLang。没有分项的 "you requested N tokens" 总数报告为 `requestedTokens`；只说输出的写法（"you requested N tokens in the completion"）不给数字。每种写法都只在报错的单个片段内匹配，所以不会把别的字段里的数字配到这句话上。`actualTokens` 仍是被动压缩路径一直读取的那个数。vLLM 的 "contains at least N" 写法表示分词在哪里停下，不是请求的实际大小，因此仍只取窗口。

### 被截断的摘要

摘要打开了 `<state_snapshot>` 却没有闭合，且报告的 usage 显示请求撑满了它所按的窗口（输入加输出与该窗口相差不到 1,024 token）时，按 `COMPRESSION_FAILED_OUTPUT_TRUNCATED` 丢弃。服务端遇到 `prompt + max_tokens > window` 时可能不拒绝请求，而是在窗口用完处停止输出（llama.cpp 的服务端就是这样），于是报告的输出数低于请求的预算，原有的阈值检查看不出被截断；但输入和输出的数加起来正好是窗口。没有这个迹象时，摘要和改动之前一样保留：模型可能结束时漏写闭合标签，把这类摘要都丢掉会触发失败熔断。重试按拒绝信息给出的更小窗口来算时，检查的就是那个窗口。不带标签的摘要不受影响。检查前只去掉已闭合的 `<analysis>` 块：真实模型经常在 snapshot 里引用压缩指令，连同其中的 `<analysis>` 标签；如果从这个引用一直去到结尾，snapshot 的闭合标签也会被一起去掉。检查的是第一个出现在行首的开始标签：句子中间提到这个标签（不论在 snapshot 之前还是之后）都不会打开 snapshot。代价是反过来的情况：摘要先引用了一个完整的示例 snapshot、后面真正的 snapshot 却被截断，这样的摘要能通过检查。改动之前基于输出数的检查也漏掉这种情况。

### token 计数

缩减后的请求已不能代表它要替换的历史，所以不再用它返回的 usage 推算压缩后的 token 数，而是改走"可见历史估算"的路径。载荷过大压缩本来就走这条路径。

## 决策与理由

| 决策                                | 理由                                                                                                                                                                                                              |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 保留 char/4 估算器                  | 它偏低，所以基于它的拒绝只会发生在请求确实放不下时。#9541 把它换成按字节加权的估算，结果中文会话从窗口约 50% 起就被拒绝。                                                                                         |
| 截短每个文本片段，保留每个轮次      | 复用载荷过大时的截短（#10380），不用解析轮次结构就能让 function call 和 response 保持成对。完整保留用户消息需要知道哪段文字是用户输入的，由后续改动加入。                                                         |
| 只重试一次                          | 压缩仍是尽力而为，不阻塞用户。报错自带的数字让一次大小合适的重试在常见情况下就够用。                                                                                                                              |
| 新增失败状态                        | 让用户和遥测能区分"太大无法压缩"和 API 错误。                                                                                                                                                                     |
| 16K 以下用窗口的四分之一作下限      | 固定的 4,096 只给 8K 窗口的历史留很少空间，4K 窗口则完全没有。较小预算放不下的摘要会按截断丢弃，历史保持不变。                                                                                                    |
| 删掉超出的部分，而不是按比例缩放    | 比例假设请求的每个部分一样密。缩减保留的文字可能比截掉的工具输出更密，比例会低估剩下的部分。要求按"每个估算 token 至少一个真实 token"减少超出量，剩下的内容一定放得下，重试的 `max_tokens` 也来自数字而不是估算。 |
| 只在撑满窗口时丢弃未闭合的 snapshot | 在窗口用完处停止输出的服务报告的输出数低于预算，撑满的窗口才是截断的信号。没有这个信号时，未闭合的标签可能只是模型漏写，丢掉这类摘要会触发失败熔断。不带标签的摘要不受影响，因为较弱的模型可能不按格式输出。      |

## 风险

- 缩减后的请求像工具输出一样把用户消息截到 4,000 字、只保留开头，摘要可能看不到长请求的结尾。后续改动会完整保留它们。
- 缩减只截短超过 4,000 字的片段。由许多较短消息组成的会话不会变小，会以 `COMPRESSION_FAILED_INPUT_TOO_LARGE` 被拒绝，而不是完成压缩。
- 报错里没有数字时，缩减后的请求对密度极高的文本仍可能过大。此时压缩在那一次重试后失败，不会发出第三次请求。
- 缩减后的请求没删掉全部超出量时，输出预算按平均密度来定，留下的内容比删掉的更密时仍可能超长；压缩在那一次重试后失败。
- 窗口小于约 16K 时，缩减后的请求只给摘要留窗口的四分之一，较长的摘要可能放不下，此时按截断丢弃，历史保持不变。
- 服务端在比请求所按窗口更小的窗口处停止输出，或传输层把输出上限压到预算以下时，摘要可能在 snapshot 中间被截断，而 usage 并没有达到那个窗口。这样的摘要会被保留，和改动之前一样。

- `compactionInputSlimming.test.ts` 中的单元测试：在 500 字和 4,000 字两种上限下，过长的提醒被截短并重新闭合。

- `chatCompressionService.test.ts` 中的单元测试（`issue #9455`），使用一个强制 `prompt + max_tokens <= window`（测试设置时还强制输入上限）、并可按高于本地估算计数的后端：
  - 放得下的请求原样发送；
  - 只截短就够时发送缩减后的请求；
  - 本地拒绝；
  - 缩减后的请求和缩减后的重试的压缩后 token 计数；
  - 中文会话原样准入；
  - 带数字重试、无数字重试、重试一次后放弃、其他错误不重试，以及在请求被拒时恰好中止；
  - 8K 窗口按四分之一窗口的预算完成压缩，2K 窗口在本地拒绝；
  - 重试按拒绝信息给出的更小窗口来算，该窗口放不下任何重试时在本地拒绝，以及服务端在该窗口用完处截断的重试会被丢弃；
  - 只是输出超了时，原样重发同一个请求并减少输出空间，分别针对分出输出部分的报错、只给总数的报错，以及比主模型窗口更小的压缩模型；
  - 保留的文字（没超过上限、按高密度计费的中文消息）比截掉的工具输出更密时，重试仍放得下；
  - 报错写明的输入上限之上的超出量；
  - 数字远低于估算或与同一信息里的上限矛盾时被忽略；
  - 没有分项的总数被当作上界，分别针对发送途中输出被压低和没有被压低的情况；
  - 服务端窗口小于配置窗口时，单纯 "N tokens > M" 写法的拒绝；
  - 数字表明请求本该放得下时发送缩减后的请求（SGLang 的写法，没有解析出上限）；
  - 服务商算出的数比估算少时，重试仍放得下，以及这个数表明缩减后的请求放不下时不发送重试；
  - 单条用户消息比整个窗口还大的会话能完成压缩，而不是被拒绝。
- `chatCompressionService.test.ts` 中的单元测试（`issue #7960`）：占满窗口的轮次被缩减，而不是以下限为 1 的预算发送；服务端在窗口用完处停止输出、在 snapshot 中间被截断的摘要会被丢弃；usage 没有撑满窗口时，未闭合的 snapshot 会被保留；不带标签的完整摘要会被保留；闭合后又提到标签的完整摘要也会被保留。

## 验收标准

- 不发送输出预算低于 4,096 token（窗口的四分之一更小时取四分之一）的冷路径压缩请求。
- 放得下的请求原样发送。
- 缩减后的请求保留每个轮次，所以每个 function response 都在它的 call 之后。
- 无法缩减的请求返回 `COMPRESSION_FAILED_INPUT_TOO_LARGE`，不发送该请求；或者在拒绝信息表明任何重试都放不下时不发送重试，或者重试也因为上下文长度被拒；CLI 为它显示非空提示。
- 因上下文长度被拒后，最多重试一次。拒绝信息给出窗口时，重试放得进这个窗口。给出输入大小时，重试要么原样重发并减少输出空间（不低于预留），要么发送缩减后的输入。
- 在 `<state_snapshot>` 中间被截断、且报告的 usage 达到请求所按窗口的摘要不会被保存。

## 后续

- 在缩减后的请求里完整保留用户消息，并在截短不够时把较早的轮次压成用户原话（#14953）。
- 共享缓存路径对来自其他路由的 token 锚点做准入。
- 切换到更小窗口前，先用旧模型压缩。
- vLLM 的 "`max_tokens` cannot be greater than" 拒绝不会被识别为上下文超长。识别它也会改变主对话路径的行为。
- 超长时从最前面丢消息而不是拒绝的服务（Ollama 的默认行为）不会给出可供重试的拒绝。
- 用考虑中文的偏高估算来确定第一次请求的输出预算，让高密度会话不必先被拒绝、再靠重试修正。
- 按片段估算密度下限（比如英文每 4 个字符 1 个 token、中文每 2 个字符 1 个 token），删掉的内容很密时，超出量检查就能接受缩减后的请求。
- Anthropic 的 "input length and `max_tokens` exceed context limit: P + C > L" 不会被识别为上下文超长。识别它也会改变主对话路径的行为；对重试来说，它直接给出了输入大小。
