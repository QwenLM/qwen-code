# GitHub Channel 发布契约

[English](2026-07-29-github-channel-publication-contract.md) | [简体中文](2026-07-29-github-channel-publication-contract.zh-CN.md)

## 目标

让 GitHub channel 的回复可以安全地自动发布，并在事后可追溯。channel 只通过适配器发布 agent 的最终回复；中间推理、工具输出和流式分块永远不会变成 GitHub 评论。

## 契约

- GitHub 适配器关闭块流式输出，因此每个被接受的入站事件至多产生一个待投递的最终回复。
- 最终投递使用当前 prompt 所在的 issue/PR 线程，而不是可能已过期的共享会话目标。
- channel 指令要求 agent 不得用 `gh` 或 GitHub API 创建评论或 review，公开投递由适配器负责。
- 去除首尾空白后只剩 `<no-reply/>` 哨兵的最终回复会被有意抑制。空白、大小写、`/>` 前的空格以及单层包裹的代码围栏会被规范化；其它内容原样发布。
- 抑制和发布都记录在本地只追加的 JSONL 审计文件 `~/.qwen/channels/<workspace-scope>/<channel>-<name-hash>-github-audit.jsonl` 中。记录包含时间、channel、会话、来源消息、线程、结果、存在时的 GitHub 评论标识/URL，以及回复的 SHA-256 和字符数。记录中绝不包含回复正文、凭据或 GitHub token。
- 审计写入是尽力而为的。审计失败只记日志，不改变发布结果。歧义的 GitHub API 失败仍算投递失败，不会重试。确定未写入的响应——GitHub 的限流器以 403 或 429 拒绝评论，响应带有数值形式的 `x-ratelimit-remaining`，并且配额已耗尽、带有 `retry-after`，或报错文案写明是二级限流——会先在进程内重试；如果 GitHub 仍然拒绝，就写入私有的待发投递文件，之后在 channel 运行期间和下次启动时重试。缺少该头的限流答复按歧义处理。

## 流程

1. GitHub 适配器把被接受的事件派发进 `ChannelBase`。
2. 当前 prompt 在最终投递结束前一直保留入站消息和 issue/PR 线程。
3. agent 返回一个最终回复。
4. 适配器要么抑制精确匹配的哨兵，要么创建一条 issue 评论。
5. 适配器追加一条发布审计记录。任务的终态生命周期仍由 `ChannelBase` 负责。
6. 如果最终投递遇到确定未写入的响应，适配器会再尝试两次：`retry-after` 是正的秒数时按它等待；否则在配额耗尽时等到配额重置；再否则先等一分钟、再等两分钟（重置时间看起来已经过去时也是如此）。其中某次尝试拿到歧义答复时，按普通歧义失败处理，结束尝试且不留待发记录。如果 GitHub 仍然拒绝，或 channel 在等待期间停止，适配器会把最终文本以私有文件权限存入 `~/.qwen/channels/<workspace-scope>/<channel>-<name-hash>-github-pending-deliveries.json`，并重试投递，不重新运行 agent：channel 运行期间在后台重试，下次启动时也会重试。运行期间，等待结束后第一次成功列出通知的轮询会启动一轮重试；投递到绑定会话的 channel 在拿到完整或含有绑定的绑定快照之前不列通知；拿到的是空的 partial 快照时，要再过 30 次绑定扫描才列。等待时间按拒绝的 `retry-after`（或让上一轮停下的那个答复的 `retry-after`），或配额耗尽时按配额重置时间，但距拒绝或上一轮至少五分钟（每有一轮结束后仍留有回复就加倍，待发文件读不出来也算；某一轮结束后不再留有回复，就回到五分钟）、至多一小时。这样的一轮对每条回复只尝试一次；启动时那一轮仍按上面的方式等待。运行中的 channel 已发出、或发出后得到歧义答复的回复，即使审计和待发文件都写不进去，也不会再发。每一轮（包括启动时那一轮）遇到会让后面的回复同样被拒的第一个答复即停止发送，后面的回复留到下一轮：确定未写入或 401 时，这一条也一并保留；其他限流答复、服务端或网络失败时，这一条按歧义丢弃；审计中已记录为 posted 的回复会被丢弃。

## 非目标

- 不重试歧义的发布失败，不创建状态评论，也不启用流式回复。这些属于 issue #8012 的其它部分。
- 禁止 agent 直接用 `gh`/API 发布的指令只是对 agent 的操作边界，不是沙箱强制。工具级 GitHub 写入限制的强制执行属于运行时权限模型。
- 待发投递的保留策略，包括最大尝试次数、最长保留时间、大小上限、过期回复处理和遗留临时文件清理，另由 #8142 跟踪。

## 验证

GitHub 适配器的针对性测试覆盖哨兵抑制、正常的最终评论投递、不含回复正文的审计字段，以及不阻塞的审计写入失败。已有的路由和投递测试保持不变。另有适配器测试覆盖哪些拒绝算作确定未写入、进程内等待及等待期间的停止，以及启动时和运行期间对待发投递的重试及其时间安排。
