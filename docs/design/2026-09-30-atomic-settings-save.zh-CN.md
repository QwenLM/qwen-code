## 问题与证据

基线实现在保存已有设置文件时，先把目标改名为备份，再把临时文件改名为目标。
两步之间目标不存在。操作者设置读取路径把这种缺失当作空设置，因此一次与
沙箱无关的设置保存，也可能让并发启动暂时丢失执行沙箱策略。

独立的受控复现使用了真实基线 writer 和 reader，并调用 macOS arm64、
Node.js 22.14.0 上的全局 qwen 0.24.6。保存前后，qwen sandbox 读到配置的
策略，因为所选执行沙箱需要 Linux 而以退出码 1 拒绝运行。在备份 rename
完成后立即暂停 writer，目标文件消失，源码 reader 返回无策略；第二个
qwen sandbox 以退出码 0 输出 "Tool execution sandbox: none"。随后恢复
writer，并清理隔离的测试目录。

这证明了可观测的中间状态，没有测量自然竞态频率，没有执行 Linux 上逃逸
限制的工具，也没有验证 Windows。issue 中历史的 100 次出现 2 次记录
未在本次重跑。复现材料保存在 .qwen/issues/issue-12417.md 和
.qwen/e2e-tests/issue-12417-settings-gap-repro.json。

## 目标与边界

替换已有设置文件时，仓库自身的保存操作必须发布完整文件，不能使目标缺失。
保存期间每次成功打开目标，都应读到之前或刚刚提交的完整文件。替换失败时，
不能改动当前目标，必须报告保存失败。

首个实现只覆盖 #12417 的原子保存部分。保留 scope 优先级、JSONC 编辑、
环境变量展开、文件缺失行为与沙箱选择语义。不增加设置锁服务、运行时策略
热更新、设置合并冲突检测、启动重试，也不自动恢复外部删除的文件。

首次创建在发布前仍然没有文件；本方案不能让尚未存在的策略提前生效。
并发保存仍以最后一次成功的整文件发布为准。两个读后修改再写入的操作仍
可能丢失无关编辑；消除这种独立冲突不属于本次范围。

## 建议保存流程

保留同步 API，在 helper 中实现以下流程。通过 fs.mkdtempSync，在目标旁
创建独占、名称唯一的工作目录，前缀为 settings.json.write-。其中暂存文件
为 settings.json.tmp，备份文件为 settings.json 加 backupSuffix，默认
为 .orig。同一个父目录所属的文件系统支持同文件系统 rename，也让每次
调用独占自己的辅助文件。

1. 保留对目录型目标的现有拒绝。创建工作目录，在其中以排他创建和
   flush: true 写入完整新字节。保留 helper 的现有编码与新建文件权限语义。
2. 如果目标存在，通过 COPYFILE_EXCL 将它复制到本次调用的备份路径。
   复制不得移动或截断目标；备份失败就终止发布，不能静默继续。
3. 只通过一次 fs.renameSync 将暂存文件发布到目标。这是唯一替换目标的
   步骤；此前不得 rename 或 unlink 目标。
4. 发布成功后，尽力清理本次调用的工作目录。清理失败不能撤回成功的保存。
5. 发布前失败时，逐字节比较完整备份与当前目标。若相同，尽力删除本次
   调用的目录，避免在单文件 bind mount 等持续拒绝替换的环境中不断积累
   相同副本。若不同或任一读取失败，保留备份，在错误中指出其路径，并
   尽力只删除暂存文件。没有完整备份时，清理私有目录。绝不把备份自动
   恢复并覆盖当前目标。

私有目录避免共享 .tmp 冲突以及共享 .orig 的归属混乱。直接复制到固定
备份路径还可能覆盖预先存在的符号链接所指向的文件；在新建私有目录中排他
创建备份，可以避免引入这种行为。不删除或使用其他调用的辅助文件，包括
历史 .tmp/.orig，也不把它们当作已提交设置。不增加新的清扫器。

备份是供诊断或人工恢复使用的某个完整旧文件副本，不是权威事务快照；它可能
早于另一 writer 的成功发布。移除旧的自动恢复分支是必要的：writer A 在
writer B 发布后失败，不能用 A 的旧备份覆盖 B。Provider 适配器显式执行的
事务恢复属于独立逻辑。

## 失败与崩溃行为

| 时点                                      | 目标行为                                                 | 辅助文件与结果                                                       |
| ----------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------- |
| 工作目录或暂存文件创建、写入、flush 失败  | 已有目标不变                                             | 保存失败；只清理本次拥有的辅助文件。                                 |
| 备份复制失败                              | 已有目标不变                                             | 保存失败；不能宣称不完整备份可用于恢复。                             |
| 最终 rename 失败，包括 EPERM/EACCES/EBUSY | 本次调用不改动当前目标，包括其他 writer 已成功提交的内容 | 保存失败；删除相同备份，保留不同或不可读备份；不回滚、不用复制兜底。 |
| 发布成功但清理失败                        | 已提交的完整新文件保留                                   | 保存成功；可能留下私有辅助文件。                                     |
| 进程在发布前停止                          | 目标仍是已有提交的文件                                   | 可能留下私有辅助文件，读取路径忽略它们。                             |
| 进程在发布后停止                          | 目标仍是完整已提交文件                                   | 备份或暂存清理可能未完成；不自动重放。                               |

以上是受支持的本地文件系统上的进程崩溃与发布可见性要求。保留现有文件
flush，但不增加目录 fsync，也不新增断电持久性保证。外部删除、权限修改、
网络文件系统语义，以及其他主体替换父目录，都不在保证范围内。

清理成功时，重复失败的保存不会累积相同备份。不同或不可读的恢复副本、
清理失败及进程崩溃仍可能留下多个私有目录。比较不是锁，也不保证后续
外部删除时仍可恢复；它绝不修改当前目标。恢复副本绝不自动加载；
人工恢复错误中给出的备份前，需要先检查当前目标，因为备份可能早于其他
writer 的提交。检查后只删除指定调用的目录；本方案不增加清扫历史调用
辅助文件的机制。

## Windows 与其他方案

所有平台使用同一条单次 rename 发布路径。Node.js 文档说明会替换已有目标；
本地 Node.js 使用的 Windows libuv 实现调用 MoveFileExW，并使用
MOVEFILE_REPLACE_EXISTING。这些来源支持机制选择，但不是 Windows 运行
测试证据。参见 [Node.js rename](https://nodejs.org/docs/latest-v22.x/api/fs.html#fsrenameoldpath-newpath-callback)、
[libuv v1.49.2](https://github.com/libuv/libuv/blob/v1.49.2/src/win/fs.c#L2077) 和
[Microsoft 替换标志](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)。

如果 Windows 共享或访问规则拒绝替换，传播失败并保留目标。不能降级为
复制到正在使用的目标，也不能先 unlink 再 rename。Node.js 明确不保证
复制的原子性，这些兜底会暴露部分内容或文件缺失。参见
[Node.js copyFileSync](https://nodejs.org/docs/latest-v22.x/api/fs.html#fscopyfilesyncsrc-dest-mode)。

必须在真实 Windows NTFS、受支持的 Node 版本上，验证普通替换和存在
禁止替换句柄时的行为。模拟 EPERM 只能验证本方控制流。本机没有真实
Windows 验证，因此该验收要求仍然待完成。

已评估现有 core `atomicWriteFileSync` 作为替代方案。它提供唯一暂存文件、
文件 flush、权限保留、符号链接处理和 EPERM/EACCES rename 重试。这些
共享能力有用，但其失败契约与本次设置变更不同：EXDEV 时降级为直接写入
正在使用的目标；`noFollow: true` 时先 unlink 目标再重新创建。因此，兜底
失败可能留下不完整字节或目标缺失。目前没有受支持的选项可拒绝该兜底。
保留 uid 的原地写入分支属于异步 `atomicWriteFile`，不属于建议用于这些
设置调用方的同步版本。

直接把这些调用方改为共享 helper 会削弱“发布被拒绝时已提交设置不变”的
要求，也会移除既有人工恢复副本，并把默认符号链接行为从替换链接改为
写入链接目标。因此，本次仍保留较小的 CLI writer，采用严格的替换失败
语义和私有恢复文件。修改 core 的兜底策略或新增严格模式会涉及其他调用方，
超出本次修复范围。该选择不继承 core 的权限保留或重试行为；继续沿用
现有设置权限语义，真实 Windows 验证仍然必需。单凭 rename 重试不能证明
Windows 上的替换与拒绝行为。如果共享 helper 以后能提供等价的严格发布
契约且不改动这些调用方，可以重新考虑复用。

完全移除备份可以简化发布，但会丢掉 helper 已有的人工恢复契约。保留共享
暂存路径则让两个 writer 进程可以消费彼此的临时文件。给 reader 增加重试
只会掩盖 writer 制造的文件缺失，其他 reader 仍然暴露。本方案不需要平台
兜底，也不增加依赖包。

## 实现与验证计划

生产逻辑变更集中在 writer。旧命名 writer 与同目录测试已改名为
write-with-backup.ts、write-with-backup.test.ts，两处生产导入已更新，
过时的文件名 allowlist 条目已删除。helper、JSONC 编辑器、settings 与
适配器的说明已同步恢复契约。现有 reader 与沙箱校验没有生产逻辑变更；
settings 测试的文件系统 mock 已适配私有暂存路径。

测试应验证结果，而不是文件系统调用次数或顺序：

- 在暂存、备份和发布前加入确定性检查点：真实操作者 reader 始终保留合法
  的已配置策略。重新引入 rename-away 必须使测试失败。另行覆盖 scope 重载。
- 真实 writer/reader 子进程：交替保存两份都保留策略的完整 JSONC 文档。
  每次采样目标都完整，启动从不丢失策略。增加两个 writer 验证辅助文件
  隔离；不能据此声称读后修改写入具有串行化保证。
- 注入备份和最终 rename 失败，确认精确已提交字节不变。让 writer B 在
  A 备份完成后、A 被注入失败前发布，验证 B 的结果保留，并报告不同的恢复
  副本。目标字节不变时，重复 EBUSY 失败经清理后不得留下本次辅助文件；
  比较读取失败时必须保留完整副本和原始写入错误。覆盖自定义后缀、
  编码、首次创建、目录拒绝及尽力清理。
- 在发布前后终止 writer，reader 忽略私有残留。保留既有 JSONC、迁移、
  适配器恢复和 watcher 行为。
- 运行真实 Linux、macOS、Windows 文件系统用例。Linux 上先跑全局 qwen
  基线，再使用构建后的 CLI，在重复保存期间验证沙箱与普通受限工具调用。

实现后从根目录运行 build、typecheck，从 packages/cli 运行 writer、
JSONC 编辑器、操作者设置、settings、适配器与 watcher 的定向测试。
CLI 验证前构建 bundle。详细计划位于
.qwen/e2e-tests/issue-12417-atomic-settings-save.md。

验收标准：仓库自身的替换不删除目标；reader 读到完整提交的字节；helper 的
失败路径不能回滚其他 writer（调用方显式请求的快照恢复属于独立逻辑）；
辅助文件归本次调用独占；真实 Windows 替换与拒绝行为
已验证；Linux 在保存期间保持工具限制。本地实现证据见下文，真实平台的
