# Java CI 失败上报

Java CI 失败后，作者应能直接收到摘要，或在 issue 队列看到跟踪单，而不必自行翻找 Actions job。main 手动全量 39042781121 失败，对应上报流程 39047669819 的所有 job 却被跳过。审批触发的 Managed Agent 全量也被上报流程的 main 分支过滤排除，即使它在 PR 合并后才结束。

扩展现有失败上报流程，复用其解析、去重与自动修复派单能力：

- 保留现有 main push 和定时失败上报，并接入 main 或 PR 分支上手动触发的 SDK Java 全量失败。
- 接入失败的 Managed Agent PR 和审批运行。按源仓库、分支和精确 head SHA 查找对应 PR，因为事件的 `pull_requests` 数组可能为空。忽略已被新提交替代的运行。
- 每个失败 run 在 PR 中发布或更新一条评论，列出失败 job 的直达链接、失败步骤和已识别的测试。PR 已合并时，同时进入既有 issue 去重和自动修复派单流程；未合并时仅回贴 PR，不创建 main 回归单。
- 保留现有的基础设施失败单次重试和按失败测试去重的行为。

只读分析 job 仅检出默认分支，不检出触发运行的 PR。评论和 issue 发布 job 不检出仓库，不执行仓库代码；摘要通过环境变量和正文文件传递。关联 PR 时必须匹配源仓库、目标仓库、目标分支和当前 head SHA。不可信 PR 代码不会获得 bot PAT，也不能在合并前创建已批准自动修复的 issue。

验证使用真实失败运行的元数据，重放事件过滤逻辑，通过替代 GitHub CLI 边界验证 PR 关联和评论更新，并覆盖原有日志解析、issue 去重及基础设施重试行为。本地验证与线上触发、发布分开记录。
