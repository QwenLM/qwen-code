# 降低 `qwen serve` 启动延迟

[English](serve-startup-latency.md) | [简体中文](serve-startup-latency.zh-CN.md)

## 当前行为

打包后的 CLI 在分发 `serve` 前加载通用命令入口。快速路径先监听，再等到已鉴权的健康检查响应后 50 ms、已鉴权的运行时请求，或 1,000 ms 兜底定时器，才加载运行时。托管启动器分别轮询端口和工作区就绪状态。TCP 监听、应用路由可响应、工作区就绪是不同的启动节点。

## 设计

- 工作区 CLI 与打包产物都将首参数为 `serve` 的命令交给现有轻量解析器。帮助、版本、不支持的参数和托管更新继续交给通用 CLI。复用入口生命周期，保留错误处理及环境初始化。
- 沿用现有运行时启动触发条件。在预发热编译缓存、初期每 50 ms 探活的条件下，监听后立即启动运行时相对默认路径让工作区就绪提前 49 ms，首次浅探活延后 163 ms。这里比较的是配对差值的中位数。
- 在托管镜像构建时预热 Node 编译缓存。使用隔离的 home 和工作区启动已安装的守护进程，深度健康检查确认运行时已加载后将其停止。托管启动器启动 Node 时传入同一个 `NODE_COMPILE_CACHE` 目录。缓存复用依赖 Node 版本和安装模块路径。冷缓存或存储不可用时仍可正常启动。
- 在首次收到需要鉴权的 webhook 请求时加载 webhook 配置。由请求触发运行时初始化前仍先执行 webhook 鉴权。
- 必需的 Channel 启动完成后，将排队中的 `/brand`、`/workspace/voice` 和 `/workspaces/:workspace/stat` 的 `GET` 和 `HEAD` 请求交给已挂载的应用，无需等待 Live Host 发现记录发布。沿用原有鉴权和工作区解析。`/capabilities` 在支持的单工作区启动中继续使用引导响应，需要完整工作区信息时由运行时提供快照。
- 并行执行遥测初始化和剩余子会话及相关路由模块的加载。SDK 初始化 Provider 后再注册守护进程指标。ACP 预热继续异步运行。

## 托管启动器

opencode `release/FY27B22` 的配套变更传入由启动器管理的编译缓存目录，并分别在浅探活与深探活的前 2 秒每 50 ms 轮询，之后恢复为每 250 ms 轮询。就绪仍通过 HTTP 健康检查与目标工作区的作用域状态确认，保留旧版本回退逻辑。

## 验收

- 用打包入口和工作区入口检查 `serve --help`、`serve --version`、非法参数以及优雅关闭。
- 确认引导阶段可以返回浅探活响应，健康检查、已鉴权的运行时请求和兜底定时器均可触发运行时启动。验证鉴权及运行时启动失败的响应。
- 用相同的构建条件测量进程到监听、首次健康响应、首次作用域状态成功的时间。分别报告冷、热编译缓存。在目标部署环境复测后，再判断本次变更覆盖了多少线上实测耗时。
