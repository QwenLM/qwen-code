# GitHub Channel Events to PR-Bound Sessions

[English](2026-11-02-github-channel-bound-session-events.md) | [简体中文](2026-11-02-github-channel-bound-session-events.zh-CN.md)

Status: proposed (decisions confirmed by the maintainer on 2026-11-02: prompt-injection delivery, in-channel state watch, event scope = CI failure + merge conflict + new comments + head change / merged / closed).

## Problem

A user who follows a PR in a Qwen Code session (a Web Shell or CLI session that created, reviewed, or verified the PR) gets no help from the GitHub channel when that PR changes:

1. **Two disconnected session systems.** The GitHub channel routes every event to a channel-owned session keyed by `github:<owner>/<repo>:pr:<N>` (`SessionRouter`, `chat_thread` scope). The session that actually follows the PR — the one with the worktree, the context, and the PR binding in its `prs` sidecar — never sees the event.
2. **Event coverage gaps.** The adapter polls the Notifications API and enumerates comments. A pure CI failure (reason `ci_activity`, no new comment) dispatches nothing. A merge conflict produces no GitHub notification at all. New pushes and merge/close transitions are likewise invisible unless someone comments.

The building blocks for closing both gaps already exist:

- **PR bindings**: `packages/core/src/services/session-pr-service.ts` persists `<chatsDir>/<sessionId>.pr.json`; the daemon refresh timer (`packages/cli/src/serve/server/session-pr-refresh.ts`) already scans every trusted workspace's sidecars on a cycle. There is no reverse lookup (PR → sessions) yet.
- **Delivery into an existing session**: `POST /session/:id/prompt` accepts prompts for any live session, resolves the owner runtime by session id (cross-workspace capable), and FIFO-queues while the session is busy (`DEFAULT_MAX_PENDING_PROMPTS_PER_SESSION = 5` in `packages/acp-bridge/src/session-control-plane.ts`; queue full → HTTP 503 `prompt_queue_full` + `Retry-After`).
- **Session creation**: the channel's existing `SessionRouter` path already creates a channel session when no route exists.

## Goals

- When a GitHub event concerns a PR that is bound to a live session, deliver the event into that session as a prompt turn, so the session can handle it with its existing context.
- Sense the events the Notifications API cannot deliver: CI failure on the PR head, merge-conflict appearance, head advancement, and PR merged/closed transitions — for the set of PRs bound to sessions.
- When no bound session exists, keep today's behavior: the event flows through the normal channel path and creates (or reuses) a channel session.

## Non-goals

- No webhook push ingestion. The daemon's `POST /channels/:channelName/webhooks/:source` route stays as it is (static targets); true push delivery is future work.
- No channel takeover of bound sessions (`SessionRouter.activateManagedSession` is not used): a bound session's replies must NOT be auto-published as GitHub comments under the channel publication contract.
- No cross-session peer messaging for this path (review-class gating and external-peer registration add complexity without benefit here).
- No automatic PR binding of channel-created sessions. Channel sessions keep their existing routing and public-reply behavior.
- No support for standalone `qwen channel start` (non-daemon ACP mode): the reverse lookup is a daemon route. The feature degrades to today's behavior there.
- Inline PR review comments remain out of scope (existing adapter limitation).

## Design

### Layer 1 — daemon reverse-lookup route

New process-global, read-only route:

```
GET /sessions/pr-bindings
→ { "bindings": [ { sessionId, workspaceCwd, sourceType, updatedAt, prs: [{number, url, state?}] } ], "partial": false }
```

- Ownership class: **process-global** (same class as `POST /sessions/backfill-prs`). It iterates the registry's workspace entries (`listAllEntries()`) and enumerates active sessions of each active trusted runtime through the live-merged session-list path (`listWorkspaceSessionsForResponse`, which enriches summaries from the PR sidecars), paginating up to a bounded page cap. Untrusted non-primary workspaces are skipped (they cannot create or restore sessions, so their absence is legitimate); an untrusted PRIMARY is skipped with `partial` set, because session creation/restore exempts primary from the trust gate and it still serves bound sessions.
- Archived sessions are excluded. `sourceType` is included so callers can exclude channel-owned sessions. `prs` entries are projected to `{number, url, state?}`.
- **`partial`** is true when the answer is incomplete: a workspace failed to list, a trusted workspace is not active (draining / transitioning / blocked — it still serves sessions but cannot be enumerated), an untrusted primary workspace (still serves bound sessions, skipped), a live-merge degraded success (`liveMergeFailed`), a page reported truncation, the page cap was exhausted, or the scan needed more than one page. The last source matters because activity-ordered pagination is not snapshot-isolated: a live session whose activity advances between page fetches can be skipped on every page while the scan still finishes clean, so any multi-page answer is non-authoritative. Consumers must not treat a missing entry in a partial answer as an authoritative absence (the adapter merges partial answers into its known bindings and skips watch-state pruning). A per-workspace scan failure is logged to stderr (workspace + cause) so a persistent partial has a diagnostic surface.
- Authenticated like the other session routes (bearer when `--require-auth`). No new write surface.
- The route is a scan, not an index: at the scale of the sidecar system (tens of sessions per workspace) a per-poll scan is acceptable; the adapter caches the result for one poll cycle.

### Layer 2 — worker-provided delivery accessor

`ChannelBaseOptions` (in `packages/channels/base/src/ChannelBase.ts`) gains one optional field; the `ChannelAgentBridge` contract is unchanged:

```ts
boundSessions?: {
  listPrBindings(): Promise<{ bindings: PrBindingSummary[]; partial: boolean }>;
  deliverPrompt(sessionId: string, prompt: string): Promise<void>;
};
```

- The daemon channel worker (`packages/cli/src/commands/channel/daemon-worker.ts`) implements it with the SDK client it already holds: `listPrBindings` calls the new route and rebuilds its session→cwd cache from each complete answer (sessions that left the bindings drop out); a malformed HTTP-200 body (non-array `bindings`) throws instead of returning an authoritative empty snapshot, routing the failure into the adapter's fail-closed refresh handling. `deliverPrompt` posts the prompt as a text content block and treats acceptance into the FIFO queue as delivery — the worker does not wait for the target session's turn to finish. The POST rides the same channel-turn classification as the bridge (`_meta` channel-prompt marker plus the worker authorization, which admission verifies together), so the relay is not treated as an interactive user prompt (loop-detected rejection, live PR-binding backfill on relayed text). The worker authorization is a **process-level relay credential**: admission accepts a registered worker token for any workspace the daemon serves bindings for (primary or trusted), not just the worker's home workspace, because bound delivery is cross-workspace (Key decision 3); a forged or unregistered token is still dropped at the route and again at the bridge admission strip. Every response body is consumed or cancelled and every body read is bounded by an abort signal: an unread undici body holds its connection until GC, and a stalled mid-body read would otherwise hang the poll loop.
- **Dormant wake**: the bindings route lists persisted active sessions, but the prompt route only serves live ones; after a daemon restart a bound session is dormant and answers 404. On 404 the accessor restores the session through the same resume path the channel bridge uses for its own dormant sessions (workspace cwd taken from the cached bindings, refreshed once if unknown), then retries the prompt once. The restore mints a client registration; the accessor releases it (detach) once the retried prompt settles — a non-empty registration blocks the daemon's prompt-settled idle close, so discarding it without detaching would pin the session live until the TTL reaper. When the cwd is unknown and the refresh returns a partial snapshot that omits the session, the accessor defers with a backpressure error (`BoundSessionUnavailableError`) instead of classifying the 404 as gone or consuming the failure budget: absence from an incomplete enumeration is not evidence of deletion.
- **Wake error classification**: a 404 restore (session record gone, or the workspace itself unregistered — the restore route answers a distinguishable `workspace_not_found` 404 for permanent absence, while reversible draining/transitioning states keep `workspace_mismatch` / `workspace_runtime_unavailable`), an archived session (409 `session_archived`, excluded from the candidate set by contract), and a superseded session (409 `worktree_session_superseded` — a worktree reset severs it permanently, never restored again) become `BoundSessionGoneError`, so the adapter re-resolves or falls back rather than deferring a permanent state toward a dead-letter. Queue-full, temporarily-unavailable workspaces/sessions (503, restore conflicts, session limits, an armed worktree-reset prompt barrier 409 `worktree_reset_active` — the reset flow tells channel-worker callers to retry) and bindings-refresh failures are backpressure or transient errors so the adapter defers or retries instead of degrading into public channel delivery. The direct prompt path classifies these 409 codes the same way as wake (archived/superseded → gone; reset barrier/restore-in-progress/busy → backpressure).
- `deliverPrompt` surfaces gone, queue-full (`BoundSessionQueueFullError`) and temporarily-unavailable (`BoundSessionUnavailableError`) as distinct errors so the adapter can fall back, defer, or retry.
- When the option is absent (standalone mode, tests), adapters behave exactly as today.

### Layer 3 — GitHub adapter changes

All in `packages/channels/github/src/GithubAdapter.ts` plus the plugin descriptor in `index.ts`.

#### Configuration

Two new management fields:

| Field                    | Kind        | Default    | Meaning                                                                                                  |
| ------------------------ | ----------- | ---------- | -------------------------------------------------------------------------------------------------------- |
| `deliverToBoundSessions` | boolean     | `false`    | Route events for PRs bound to a live session into that session instead of the channel session.           |
| `prWatchEvents`          | string-list | `[]` (off) | State transitions to watch for bound PRs: `ci_failure`, `merge_conflict`, `head_change`, `state_change`. |

`validateConfig` rejects a non-empty `prWatchEvents` when `deliverToBoundSessions` is off (the watch set is defined by bindings; watching without delivery has no MVP meaning). The descriptor delegates to the adapter's shared validator (`validateBoundSessionConfig`), so the management UI and `connect()` enforce one vocabulary and cannot drift. Both fields are opt-in; existing deployments are unaffected.

#### Bound-session selection

At the start of each poll, when `deliverToBoundSessions` is on, the adapter fetches `GET /sessions/pr-bindings` and builds a map `owner/repo#number → session`. The key lowercases the repo path on both sides: GitHub URLs are case-insensitive (core's `canonicalSessionPrUrl` lowercases them), binding URLs may carry any case while notification subject URLs carry the canonical case. A leading `www.` is stripped on both sides of the host comparison (users paste `www.github.com` links; core's `repoKeyFromWebUrl` normalizes the same alias). Binding URL parsing tolerates trailing tab segments (`/files`, `/commits`, `/checks`) because the binding routes accept any http(s) URL naming the PR.

- Keep only bindings whose PR URL host matches the channel's GitHub host (Aone and other-provider bindings are ignored).
- Keep only entries with recorded `state` not `merged`/`closed` for the active watch set, unless the terminal transition has not been observed yet (see PR state watch); delivery candidates for comment events accept any recorded state (a comment on a just-merged PR still deserves delivery while the binding refresh catches up).
- Exclude sessions with `sourceType === 'channel'` — channel sessions are reached through the normal channel path, which preserves their public-reply contract.
- Multiple candidates: pick the most recently updated session (`updatedAt` desc; the route falls back to `createdAt` for live summaries that lack `updatedAt`, so a fresh live session is never outranked by a stale persisted one). Deterministic, no broadcast.
- A failed refresh keeps the previous map (stale candidates fail at delivery time and fall back); the watch pass is skipped for that poll so a transient failure cannot prune the persisted baseline. A `partial` snapshot is merged into the previous map and binding list — known bindings the incomplete answer failed to list are retained, so private delivery never degrades to the public path on a scan failure — and watch-state pruning is disabled. Retention is per session, not per PR key: a LISTED session's PR set is authoritative (the route returns each listed session's complete sidecar projection), so retention never revives a PR that session just unbound; and a retained candidate competes by recency, so a partial answer listing only an older session cannot displace the newer known one. The accessor likewise keeps its session→cwd wake cache on partial answers.
- **Cold start**: until the first snapshot succeeds (complete OR partial — the map is populated from partial answers too), the comment lane is deferred (the cursor does not advance). Claiming delivery against a cold empty map would permanently freeze events onto the public channel path even after the scan recovers; persisted tasks still recover while the lane is deferred. The gate opens on any successful snapshot (`boundSnapshotSeen`), not complete-only: a permanent partial (a multi-page scan or a long-lived non-active workspace) would otherwise stall the lane forever. Re-validation and watch pruning still require a complete snapshot (`boundSnapshotTrusted`).

#### Comment delivery intercept

`dispatchEnvelope` is the single funnel for accepted comment/body/review/assign events. Before claiming the inbound task it consults the bound-session map:

- **Bound session found** → the persisted `InboundTaskRecord` gains `delivery: { kind: 'bound-session', sessionId }`. `runInboundTask` delivers the event prompt through `boundSessions.deliverPrompt` instead of `handleInbound`. Because this bypasses `handleInbound`, the bound path runs the same `preflightInbound` (group policy, sender gate, pairing — side effects included) before delivering; watch events are exempt (no human sender, operator opt-in). The frozen target is re-validated against the latest complete snapshot at delivery time, so a live rebind retargets the event instead of misdelivering to the old session; on a partial/failed scan the persisted target stands (fail-closed). Dedupe keys and the recoverable-task machinery are unchanged — only the terminal delivery differs.
- **No bound session** → today's path for comment events (`handleInbound` → channel session). **Watch events are private-only**: they are operator-facing machine state with no pre-existing public path, and a channel session's reply would publish the internal prompt text on the PR (and re-gate it through the sender allowlist). A watch event with no bound target — at delivery, after a gone re-resolution, or at drain time — is logged and retired, never fallen back publicly.
- **Delivery fails**: 404 → the accessor first tries the dormant wake (Layer 2); only a session that cannot be restored surfaces as gone, and the adapter then re-resolves once from a fresh binding fetch; a different candidate is re-delivered, no candidate left → comment events fall back to `handleInbound`, watch events retire with a log. Queue-full and temporarily-unavailable sessions/workspaces are backpressure, not failure: they do not consume the retry budget, so a busy or draining session defers the event instead of losing it after `MAX_INBOUND_TASK_ATTEMPTS = 3`. Backpressure is bounded (`MAX_BOUND_DEFERRALS = 240`, ~4 hours at the default poll): beyond the horizon the event is retired to a private dead-letter log (`github-bound-deadletter.jsonl`) with a stderr alert — surfaced, never silently consumed. Pure bound backpressure does not hold the shared notification cursor (one stuck session must not freeze mark-as-read for every unrelated PR); other recoverable tasks still hold it. Non-backpressure bound failures exhaust the 3-attempt cap and likewise retire to the dead-letter log (the private path's exhaustion surface — it posts no public error comment). Acceptance is persisted (`deliveredAt`) before the task is removed, so a crash in that window retires the task on recovery without replaying the injection; a crash-loop charges one attempt per recovery pickup so it terminates. Recovery after restart honors the persisted `delivery` field.

The injected prompt reuses the webhook-task prompt shape (`buildChannelWebhookPrompt` style): event header, explicit "untrusted event data" warning, PR identity (repo, number, title, URL), the lane's `Trigger:`/`Event:` lines plus the direct lane's factual `Author:` details, the comment author/body or event details, and guidance that the reply stays in this session (the session is not under the channel publication contract; it acts on GitHub through its own normal tools if needed). Channel-facing publication wording never reaches the bound session: the metadata's publication instructions are dropped, and the aggregate lane's "output exactly `<no-reply/>`" prefix is replaced with a plain "New comments on the PR" header.

#### PR state watch

When `prWatchEvents` is non-empty, `pollOnce` reconciles durable pending events, then runs a watch detection pass after the binding refresh and before generic inbound recovery and notification processing:

1. **Watch set**: bound PRs from the same binding fetch, filtered to the channel's GitHub host, capped at 30 (most recently updated bindings first) for active polling. When more than 30 PRs are bound, the overflow is logged to stderr (count + excluded keys) so the oldest bindings being deterministically unwatched is surfaced, never silent. A binding recorded `merged`/`closed` by the independent refresh stays polled until the poll itself observes the terminal transition (`prState: 'closed'`), so `state_change` is never skipped by the refresh winning the race. Once observed, the terminal MARKER is retained without polling for as long as the binding lists the PR — pruning it would re-add the closed PR as a first observation on the next poll (query oscillation). Binding retention and active polling are separate concerns. No bound PRs → zero API calls. Persisted entries are pruned against the full candidate set (not the capped watch set, so PRs rotating out of the cap keep their baseline), only when the snapshot is complete — a partial snapshot never prunes — and never while the entry still holds undelivered pending events.
2. **Per PR**: `pulls.get` every poll (head SHA, `mergeable`, `mergeable_state`, `state`, `updated_at`). Check runs (`checks.listForRef`) and combined commit status (`repos.getCombinedStatusForRef`) are fetched only when `ci_failure` is subscribed AND: the head SHA changed since the last poll, the last observed CI aggregate was pending/in_progress, no CI observation exists yet, the PR's `updated_at` advanced, the aggregate is `none` within a 10-minute grace window after the head was first observed (checks register asynchronously), or the last CI fetch is older than the 10-minute re-check interval. The periodic re-check is load-bearing: GitHub does NOT bump a PR's `updated_at` on check activity (verified against the live API), so a settled head whose check re-run turns red — or CI that appears late on a manual `workflow_dispatch` — would otherwise be missed forever. Steady-state cost is one call per PR per poll plus the bounded periodic re-check. Watch API calls fail fast on rate limiting — both primary (remaining exhausted) and secondary/abuse limits (a `retry-after` header) — with no blocking cooldown sleep, so a rate-limited watch pass cannot pin the notification lane that runs after it (the fail-fast predicate is watch-local; the publication lane keeps its own retry semantics).
3. **Transition detection** against persisted watch state (`channelFilePath('github-pr-watch.json')`, pruned against the full candidate set on complete snapshots — see item 1):
   - `ci_failure`: aggregate turns to failure (any completed check run with `failure`/`timed_out`/`action_required`/`startup_failure` conclusion, or a nonempty combined status reporting `failure`/`error`). An empty combined status (`total_count: 0`, which GitHub returns as `state: "pending"` for SHAs without legacy statuses) never counts as active CI. Fires once per head SHA via the durable `fired` ring, even if the aggregate flaps back to success and fails again; a new head that fails fires again. A per-entry `ciFiredSha` pin backs the ring: the capped ring can evict the `ci_failure:<sha>` key after 64 non-ci episodes on a long-lived head, and the pin preserves the once-per-head guarantee even after that eviction (it resets when the head changes). The event summary names the failed checks (up to 5) so the session can act without re-querying.
   - `merge_conflict`: `mergeable_state` enters `dirty`. Edge-triggered; `dirty → clean → dirty` fires again. `mergeable === null` (GitHub still computing) never overwrites the last known state.
   - `head_change`: head SHA differs from the last observed SHA (first observation initializes silently). A force-push revisit of a recent SHA is a new transition and fires again.
   - `state_change`: PR `state` leaves `open` (merged or closed). First observation initializes silently; close → reopen → close fires again.
   - **Dedupe key identity**: `ci_failure` keys on the head SHA (once per head). The other three key on a per-entry monotonic episode counter (`watch:<type>:<seq>`) — a transition INSTANCE, not a state value — so the legitimate recurrences above are never suppressed by the fired ring. The counter is persisted with the baseline.
4. **Durable event queue**: detected events are appended to a `pending` queue persisted in the same write as the new baseline, so a crash between detection and claim loses nothing. A reconciliation pass drains ALL pending entries (no GitHub calls) BEFORE generic recovery and independently of the live watch pass: a failing or rate-limited API pass cannot starve already-detected events, and recovery cannot deliver-and-remove a task that a later drain would re-claim (a crash between the claim and the pending→fired save leaves both records on disk). Draining then, per event: re-validate the recipient against the latest complete snapshot, claim the inbound task (durable — a terminal failed/cancelled record for a recurring WATCH key is replaced, never silently reused; comment/event/issue-body keys are stable identifiers that never re-fire, so their terminal records stay a permanent dedupe barrier — replacing them would revive a cancelled comment after a crash leaves the cursor behind the cancel), move the key from `pending` to a capped `fired` ring (durable), then run the task. A crash at any point leaves either a pending event or a claimed task; the `fired` ring is the durable once-per-transition record (task-level dedupe alone would let a flapping aggregate re-fire the same head after the completed task is removed). A failed claim leaves the event queued for the next poll. A failed pending→fired save AFTER a successful claim rolls the claim back (removes the task, restores the pending event) and retries next poll, so a watch-file-unwritable / task-file-writable divergence cannot deliver the same transition twice across a restart. Event tasks use `source.messageId = watch:<eventType>:<headSha|seq>` and are delivered privately like comments — but with no public fallback (see Comment delivery intercept).
5. **Binding state upkeep** stays with the existing 5-minute refresh timer; the adapter does not PATCH metadata. Once the timer records `merged`/`closed` AND the watch has observed the terminal transition, the PR leaves active polling; its terminal marker is retained until the binding itself disappears.
6. **Persistence failure semantics**: a transient read error (EACCES/EMFILE/EIO) fails CLOSED — the watch pass is skipped and nothing is saved until the state loads again, so a degraded in-memory state can never overwrite the intact file. Only ENOENT (first start) and persistent JSON corruption start fresh. Failed atomic writes clean up their UUID-named tmp file so sustained disk pressure cannot accumulate orphans. The state file and directory are mode 0600/0700 (they persist private comment envelopes).

#### API budget

Default 60 s poll, cap 30 watched PRs: steady state ≤ 1 800 calls/hour, plus the periodic settled-head re-check (≤ 2 calls per PR per 10-minute interval → ≤ 360/hour). CI-active bursts add 1 combined-status call plus `ceil(checkRuns/100)` check-list pages per affected PR per poll — a 300-check monorepo head costs 4 calls, so 30 such PRs in a CI-active hour reach ~7 200 calls and can exceed the 5 000 calls/hour token budget; the watch fails fast on rate limiting and retries next poll rather than blocking. Notification polling overhead is unchanged. The adapter logs and skips the watch pass when the binding fetch fails (notifications still flow).

## Key decisions

1. **Prompt injection, not channel attach.** `activateManagedSession` would bind the followed session's outbound target to the GitHub thread, so every final reply of an interactive session would be published as a public PR comment (publication contract). Injection keeps replies in the session and leaves GitHub actions to the session's own judgment and tools.
2. **In-channel state watch, not webhooks.** The watch reuses the channel's existing poll loop and credentials; detection happens at the API layer and costs zero model tokens until a real transition. Webhook push would need a public tunnel plus repository webhook creation (operator consent) and a rework of the static webhook targets. The watch is polling, but it is the gate-probe shape the maintainer accepts: cheap detection outside the model, model only on change.
3. **Reverse lookup lives in the daemon.** Bindings span workspaces; the worker is workspace-scoped and already talks to the daemon over authenticated HTTP. A read-only process-global route reuses the refresh timer's scan pattern instead of duplicating sidecar access in the worker.
4. **One candidate, most recently updated.** Broadcasting to every bound session multiplies model cost and produces duplicate GitHub actions; the freshest non-archived, non-channel session is the one most likely to hold the working context.
5. **Channel sessions excluded from candidates.** A channel-created session bound via `/review` backfill must keep its public-reply contract; the normal channel path already serves it.
6. **Opt-in defaults.** Public-repository events driving an interactive session is a new trust surface; operators enable it explicitly, and comment sender gates still apply before delivery.
7. **Wake dormant sessions instead of falling back.** E2E showed that after a daemon restart the bound session is dormant and the prompt route 404s; treating that as "gone" silently diverted every post-restart event into public channel delivery — breaking the feature's core private-delivery promise. The accessor therefore restores the session (the same resume path the channel bridge already uses) and retries once; only an unrestorable session falls back. The restore mints a client registration that the accessor explicitly detaches once the retried prompt settles: a non-empty registration blocks the daemon's prompt-settled idle close, so without the detach the woken session would stay pinned live until the TTL reaper (or forever with the reaper disabled).
8. **Watch events are private-only.** A comment has a pre-existing public path to fall back to; a watch event does not. Falling a watch event back to a channel session would publish operator-facing machine state ("CI failed on head X. Inspect the failed checks…") as a public PR comment and re-gate it through the sender allowlist. Maintainer decision (2026-11-02, resolving the triage/verification escalation): a watch event with no bound target is logged and retired, never published. The retirement is surfaced (stderr + task removal), not a silent drop.
9. **Bounded backpressure with a dead-letter surface.** Queue-full and unavailable conditions defer without consuming the failure budget, but the deferral horizon is bounded (~4 hours) and pure bound backpressure does not hold the shared notification cursor — one stuck session must not freeze mark-as-read for every unrelated PR, and a permanently stuck session must not wedge a task forever. Events that exhaust the horizon or the failure budget retire to a private dead-letter log: the private path posts no public error comment, so the dead-letter is its exhaustion surface.

## Constraints and risks

- **Untrusted content into an interactive session.** Event payloads are marked untrusted in the injected prompt (same contract as webhook tasks). Comment sender gates apply unchanged. State events have no human sender; they exist only because the operator opted in, and they are private-only (no public fallback). The target session's own approval mode governs its actions.
- **Queue pressure.** A burst of events can fill the target's 5-slot prompt queue; queue-full and temporarily-unavailable conditions are backpressure (they do not consume the retry budget) and delivery retries on later polls. The deferral horizon is bounded (`MAX_BOUND_DEFERRALS`, ~4 hours); beyond it — or when non-backpressure failures exhaust the 3-attempt cap — the event retires to the private dead-letter log with a stderr alert. Pure bound backpressure does not hold the shared notification cursor; other recoverable tasks still hold it. No bound event is silently consumed: it is delivered, deferred, or dead-lettered.
- **Rate limits.** The watch caps, conditional check fetches and the bounded periodic re-check keep the steady state under the 5 000 calls/hour token budget (large-CI bursts can exceed it; see API budget). Watch API calls fail fast on rate limiting — the watch pass is skipped with a log and notifications are unaffected, rather than sleeping out the reset window ahead of the notification lane.
- **Stale bindings.** A dormant bound session is woken by the accessor (Layer 2), so daemon restarts do not divert events into public channel delivery; the cold-start gate defers the comment lane until the first successful snapshot (complete or partial) populates the binding map. A binding whose session was truly deleted fails the wake → comment events fall back to the channel path, watch events retire with a log; the next poll's binding fetch heals the map.
- **Closed sessions.** `DELETE /session/:id` closes a session without deleting its record; the record stays resumable and bound, so such sessions are still woken for delivery (verified in E2E). Only record deletion (`POST /sessions/delete`) or archiving removes a session from the candidate set (an archived session's restore answers 409 `session_archived`, classified as gone for delivery). Closing is a resource action, not an unsubscribe; the binding expresses the follow intent.
- **Scan cost.** The route scans sidecars per call; at current scale this is milliseconds. Multi-page scans are flagged partial (activity-ordered pagination is not snapshot-isolated), which makes consumers retain known bindings rather than prune — a deliberate conservative trade. If scale grows, a snapshot-consistent enumeration or an in-memory index invalidated by `session_metadata_updated` is the follow-up, not part of this change.

## Validation plan

- **Unit**: route scan (trusted/untrusted, archived exclusion, sidecar corruption tolerance); adapter selection (host filter, state filter, channel-source exclusion, recency tie-break); delivery intercept (bound → inject, unbound → channel path, 404 fallback, queue-full retry, recovery honors persisted delivery); watch transitions (each event type, dedupe per head, null-mergeable guard, first-observation silence, state-before-dispatch ordering); config validation.
- **E2E** (daemon + local build): bind a PR to a session via PATCH metadata; simulate events with a stubbed GitHub API layer; assert the bound session receives exactly one injected prompt per transition, replies stay in-session, and an unbound PR still creates a channel session. Plan details in `.qwen/e2e-tests/github-channel-bound-session-events.md`.

## Acceptance criteria

1. With both fields enabled, a new comment on a bound PR arrives as a prompt in the bound session (not the channel session), and the session's reply is not auto-posted to GitHub.
2. A CI failure on the bound PR's head, a transition to `mergeable_state: dirty`, a head advance, and a merge/close each produce exactly one injected prompt per transition instance, surviving daemon restarts without re-firing; legitimate recurrences (dirty → clean → dirty, close → reopen → close, a SHA revisit, a new head failing) fire again, and a settled head whose check re-run turns red is caught by the periodic re-check.
3. With no bound session, comment events behave exactly as today (channel session created/reused, public reply contract intact); watch events are logged and retired, never published.
4. With the fields disabled (default), behavior and API call volume are unchanged.
5. Queue-full and unavailable paths defer without losing events and without freezing the shared cursor; session-gone comment paths fall back without loss; watch paths retire privately; exhausted events are dead-lettered, and no crash window replays an accepted injection or silently consumes a transition.
