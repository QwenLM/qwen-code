# GitHub Channel Events to PR-Bound Sessions

[English](2026-11-02-github-channel-bound-session-events.md) | [简体中文](2026-11-02-github-channel-bound-session-events.zh-CN.md)

Status: proposed (decisions confirmed by the maintainer on 2026-11-02: prompt-injection delivery, in-channel state watch, event scope = CI failure + merge conflict + new comments + head change / merged / closed).

## Problem

A user who follows a PR in a Qwen Code session (a Web Shell or CLI session that created, reviewed, or verified the PR) gets no help from the GitHub channel when that PR changes:

1. **Two disconnected session systems.** The GitHub channel routes every event to a channel-owned session keyed by `github:<owner>/<repo>:pr:<N>` (`SessionRouter`, `chat_thread` scope). The session that actually follows the PR — the one with the worktree, the context, and the PR binding in its `prs` sidecar — never sees the event.
2. **Event coverage gaps.** The adapter polls the Notifications API and enumerates comments. A pure CI failure (reason `ci_activity`, no new comment) dispatches nothing. A merge conflict produces no GitHub notification at all. New pushes and merge/close transitions are likewise invisible unless someone comments.

The building blocks for closing both gaps already exist:

- **PR bindings**: `packages/core/src/services/session-pr-service.ts` persists `<chatsDir>/<sessionId>.pr.json`; the daemon refresh timer (`packages/cli/src/serve/server/session-pr-refresh.ts`) already scans every trusted workspace's sidecars on a cycle. There is no reverse lookup (PR → sessions) yet.
- **Delivery into an existing session**: `POST /session/:id/prompt` accepts prompts for any live session, resolves the owner runtime by session id (cross-workspace capable), and FIFO-queues while the session is busy (`DEFAULT_MAX_PENDING_PROMPTS_PER_SESSION = 5` in `packages/acp-bridge/src/session-control-plane.ts`; queue full → HTTP 503 `prompt_queue_full` + `Retry-After`).
- **Session creation**: the channel's existing `SessionRouter` path already creates a channel session when no route exists.

## Goals

- When a GitHub event concerns a PR that is bound to a live session, deliver the event into that session as a prompt turn, so the session can handle it with its existing context.
- Sense the events the Notifications API cannot deliver: CI failure on the PR head, merge-conflict appearance, head advancement, and PR merged/closed transitions — for the set of PRs bound to sessions.
- When no bound session exists, keep today's behavior: the event flows through the normal channel path and creates (or reuses) a channel session.

## Non-goals

- No webhook push ingestion. The daemon's `POST /channels/:channelName/webhooks/:source` route stays as it is (static targets); true push delivery is future work.
- No channel takeover of bound sessions (`SessionRouter.activateManagedSession` is not used): a bound session's replies must NOT be auto-published as GitHub comments under the channel publication contract.
- No cross-session peer messaging for this path (review-class gating and external-peer registration add complexity without benefit here).
- No automatic PR binding of channel-created sessions. Channel sessions keep their existing routing and public-reply behavior.
- No support for standalone `qwen channel start` (non-daemon ACP mode): the reverse lookup is a daemon route. The feature degrades to today's behavior there.
- Inline PR review comments remain out of scope (existing adapter limitation).

## Design

### Layer 1 — daemon reverse-lookup route

New process-global, read-only route:

```
GET /sessions/pr-bindings
→ { "bindings": [ { sessionId, workspaceCwd, sourceType, updatedAt, prs: [{number, url, state?}] } ], "partial": false }
```

- Ownership class: **process-global** (same class as `POST /sessions/backfill-prs`). It iterates the registry's workspace entries (`listAllEntries()`) and enumerates active sessions of each active trusted runtime through the live-merged session-list path (`listWorkspaceSessionsForResponse`, which enriches summaries from the PR sidecars), paginating up to a bounded page cap. Untrusted non-primary workspaces are skipped (they cannot create or restore sessions, so their absence is legitimate); an untrusted PRIMARY is skipped with `partial` set, because session creation/restore exempts primary from the trust gate and it still serves bound sessions.
- Archived sessions are excluded. `sourceType` is included so callers can exclude channel-owned sessions. `prs` entries are projected to `{number, url, state?}`. **Every successfully scanned session gets a row, including an empty one**: a `prs: []` row is a tombstone meaning "scanned, no bindings" (an observed unbind), which callers must be able to distinguish from "this answer did not enumerate the session" — otherwise any partial answer would revive a stale binding after an explicit unbind. A session whose sidecar EXISTS but could not be read (I/O error, invalid JSON, failed shape check — the projection's `prsReadFailed` flag, backed by core's `readSessionPrsDetailed` absent/invalid distinction) is omitted with `partial` set: its bindings are unknown, not empty.
- **`partial`** is true when the answer is incomplete: a workspace failed to list, a trusted workspace is not active (draining / transitioning / blocked — it still serves sessions but cannot be enumerated), an untrusted primary workspace (still serves bound sessions, skipped), a live-merge degraded success (`liveMergeFailed`), a page reported truncation, the page cap was exhausted, or the scan needed more than one page. The last source matters because activity-ordered pagination is not snapshot-isolated: a live session whose activity advances between page fetches can be skipped on every page while the scan still finishes clean, so any multi-page answer is non-authoritative. Consumers must not treat a missing entry in a partial answer as an authoritative absence (the adapter merges partial answers into its known bindings and skips watch-state pruning). A per-workspace scan failure is logged to stderr (workspace + cause) so a persistent partial has a diagnostic surface.
- Authenticated like the other session routes (bearer when `--require-auth`). No new write surface.
- The route is a scan, not an index: at the scale of the sidecar system (tens of sessions per workspace) a per-poll scan is acceptable; the adapter caches the result for one poll cycle.

### Layer 2 — worker-provided delivery accessor

`ChannelBaseOptions` (in `packages/channels/base/src/ChannelBase.ts`) gains one optional field; the `ChannelAgentBridge` contract is unchanged:

```ts
boundSessions?: {
  listPrBindings(): Promise<{ bindings: PrBindingSummary[]; partial: boolean }>;
  deliverPrompt(
    sessionId: string,
    prompt: string,
    idempotencyKey?: string,
  ): Promise<void>;
};
```

- The daemon channel worker (`packages/cli/src/commands/channel/daemon-worker.ts`) implements it with the SDK client it already holds: `listPrBindings` calls the new route and rebuilds its session→cwd cache from each complete answer (sessions that left the bindings drop out); a malformed HTTP-200 body (non-array `bindings`) throws instead of returning an authoritative empty snapshot, routing the failure into the adapter's fail-closed refresh handling. Empty-prs tombstone rows pass through to the adapter (they are the observed-unbind signal); ANY malformed PR entry — or a dropped session row — flags the answer partial, and a listed session whose PR entries ALL fail shape validation is additionally skipped instead of projecting an authoritative empty set. `deliverPrompt` posts the prompt as a text content block and treats acceptance into the FIFO queue as delivery — the worker does not wait for the target session's turn to finish. Every POST carries the caller's `idempotencyKey` (a stable event identity derived from the source chat and message id): the prompt route remembers admitted keys per session and returns the original admission on a repeat, so a retry after a lost acceptance mark or a lost 202 re-injects nothing (Key decision 10). Every reachable pre-enqueue admission check throws SYNCHRONOUSLY — including the reserved standalone working-directory guard, which answers a retryable `409 working_directory_missing` while the session's managed conversation binding has not released — so the route never returns a phantom 202 that the relay would consume as durable acceptance; the route's key-forget on a deferred non-admission remains defense-in-depth. The POST rides the same channel-turn classification as the bridge (`_meta` channel-prompt marker plus the worker authorization, which admission verifies together), so the relay is not treated as an interactive user prompt (loop-detected rejection, live PR-binding backfill on relayed text). The worker authorization is a **process-level relay credential scoped to its reason**: home-workspace turns ride the per-workspace registration; CROSS-workspace classification additionally requires the explicit `qwen.daemon.channelBoundRelay` marker and a primary/trusted target, because bound delivery is cross-workspace (Key decision 3) but a plain prompt carrying a foreign worker token must stay an ordinary interactive prompt. A forged or unregistered token is still dropped at the route and again at the bridge admission strip. Every response body is consumed or cancelled and every body read is bounded by an abort signal: an unread undici body holds its connection until GC, and a stalled mid-body read would otherwise hang the poll loop.
- **Dormant wake**: the bindings route lists persisted active sessions, but the prompt route only serves live ones; after a daemon restart a bound session is dormant and answers 404. On 404 the accessor restores the session through the same resume path the channel bridge uses for its own dormant sessions (workspace cwd taken from the cached bindings, refreshed once if unknown), then retries the prompt once. The restore mints a client registration; the accessor releases it (detach) once the retried prompt settles — a non-empty registration blocks the daemon's prompt-settled idle close, so discarding it without detaching would pin the session live until the TTL reaper. When the cwd is unknown and the refresh returns a partial snapshot that omits the session, the accessor defers with a backpressure error (`BoundSessionUnavailableError`) instead of classifying the 404 as gone or consuming the failure budget: absence from an incomplete enumeration is not evidence of deletion.
- **Wake error classification**: a 404 restore (session record gone, or the workspace itself unregistered — the restore route answers a distinguishable `workspace_not_found` 404 for permanent absence, while reversible draining/transitioning states keep `workspace_mismatch` / `workspace_runtime_unavailable`), an archived session (409 `session_archived`, excluded from the candidate set by contract), a superseded session (409 `worktree_session_superseded` — a worktree reset severs it permanently, never restored again), and the interrupted-worktree shapes (409 `worktree_marker_missing` / `worktree_reset_interrupted`, whose repair is a worktree-reset retry rather than a resume retry, so deferring them would dead-letter without ever falling back) become `BoundSessionGoneError`. Queue-full, temporarily-unavailable workspaces/sessions (503, the daemon's own prompt-tier rate limit 429 and other 5xx, restore conflicts, session limits, an armed worktree-reset prompt barrier 409 `worktree_reset_active` — the reset flow tells channel-worker callers to retry), bindings-refresh failures, and a **404 on the retry AFTER a successful wake** (the owner may have begun draining between the resume and the retry, and the prompt route answers the same reversible 404 for a non-active owner) are backpressure or transient errors so the adapter defers or retries instead of degrading into public channel delivery — the next wake's resume reports a permanent 404/409 if the session is truly gone. The direct prompt path classifies these 409 codes the same way as wake (archived/superseded → gone; reset barrier/restore-in-progress/busy → backpressure), plus the unreleased standalone working-directory binding (`working_directory_missing`, which the daemon marks retryable with `Retry-After`) as backpressure: the bind/release window around a conversation restore is transient, so the event defers instead of burning the failure budget. An authoritative Gone also evicts the session's cached wake cwd, so a permanent partial snapshot cannot make every later delivery pay a doomed resume round-trip.
- `deliverPrompt` surfaces gone, queue-full (`BoundSessionQueueFullError`) and temporarily-unavailable (`BoundSessionUnavailableError`) as distinct errors so the adapter can fall back, defer, or retry.
- When the option is absent (standalone mode, tests), adapters behave exactly as today.

### Layer 3 — GitHub adapter changes

All in `packages/channels/github/src/GithubAdapter.ts` plus the plugin descriptor in `index.ts`.

#### Configuration

Two new management fields:

| Field                    | Kind        | Default    | Meaning                                                                                                  |
| ------------------------ | ----------- | ---------- | -------------------------------------------------------------------------------------------------------- |
| `deliverToBoundSessions` | boolean     | `false`    | Route events for PRs bound to a live session into that session instead of the channel session.           |
| `prWatchEvents`          | string-list | `[]` (off) | State transitions to watch for bound PRs: `ci_failure`, `merge_conflict`, `head_change`, `state_change`. |

`validateConfig` rejects a non-empty `prWatchEvents` when `deliverToBoundSessions` is off (the watch set is defined by bindings; watching without delivery has no MVP meaning). The descriptor delegates to the adapter's shared validator (`validateBoundSessionConfig`), so the management UI and `connect()` enforce one vocabulary and cannot drift. Both fields are opt-in; existing deployments are unaffected.

#### Bound-session selection

At the start of each poll, when `deliverToBoundSessions` is on, the adapter fetches `GET /sessions/pr-bindings` and builds a map `owner/repo#number → session`. The key lowercases the repo path on both sides: GitHub URLs are case-insensitive (core's `canonicalSessionPrUrl` lowercases them), binding URLs may carry any case while notification subject URLs carry the canonical case. A leading `www.` is stripped on both sides of the host comparison (users paste `www.github.com` links; core's `repoKeyFromWebUrl` normalizes the same alias). Binding URL parsing tolerates trailing tab segments (`/files`, `/commits`, `/checks`) because the binding routes accept any http(s) URL naming the PR.

- Keep only bindings whose PR URL host matches the channel's GitHub host (Aone and other-provider bindings are ignored).
- Keep only entries with recorded `state` not `merged`/`closed` for the active watch set, unless the terminal transition has not been observed yet (see PR state watch); delivery candidates for comment events accept any recorded state (a comment on a just-merged PR still deserves delivery while the binding refresh catches up).
- Exclude sessions with `sourceType === 'channel'` — channel sessions are reached through the normal channel path, which preserves their public-reply contract.
- Multiple candidates: pick the most recently updated session (`updatedAt` desc; the route falls back to `createdAt` for live summaries that lack `updatedAt`, so a fresh live session is never outranked by a stale persisted one). Deterministic, no broadcast.
- A failed refresh keeps the previous map (stale candidates fail at delivery time and fall back); the watch pass is skipped for that poll so a transient failure cannot prune the persisted baseline. A `partial` snapshot is merged into the previous map and binding list — known bindings the incomplete answer failed to list are retained, so private delivery never degrades to the public path on a scan failure — and watch-state pruning is disabled. Retention is per session, not per PR key: a LISTED session's PR set is authoritative (the route returns each listed session's complete sidecar projection), so retention never revives a PR that session just unbound; and a retained candidate competes by recency, so a partial answer listing only an older session cannot displace the newer known one. The accessor likewise keeps its session→cwd wake cache on partial answers.
- **Cold start**: until the first snapshot succeeds (complete OR partial — the map is populated from partial answers too), the comment lane is deferred (the cursor does not advance). Claiming delivery against a cold empty map would permanently freeze events onto the public channel path even after the scan recovers; persisted tasks still recover while the lane is deferred. The gate opens on any successful snapshot (`boundSnapshotSeen`), not complete-only: a permanent partial (a multi-page scan or a long-lived non-active workspace) would otherwise stall the lane forever. **An EMPTY partial answer is additionally bounded**: while no complete snapshot has ever succeeded and the map is empty, consecutive empty-partial answers keep the lane closed for up to `MAX_COLD_EMPTY_PARTIAL_POLLS = 30` polls (throttled stderr) — a draining/unreadable workspace answering `{bindings: [], partial: true}` on the first poll after a restart must not route every event publicly and commit the cursor before the real snapshot arrives. At the cap the lane opens anyway (a permanently empty partial must not freeze the channel), and unmatched events then take the per-event bounded deferral below instead of the public path. Re-validation and watch pruning still require a complete snapshot (`boundSnapshotTrusted`). Because a binding refresh that has NEVER succeeded (an old daemon without the route, rotated credentials) would otherwise freeze every notification behind a misleading "keeping previous map" line, the deferral logs a distinct, throttled, actionable message naming the stalled lane and the route to check — the gate itself stays fail-closed.
- **Absence is never established by an incomplete scan**: while `boundSnapshotTrusted` is false, an event whose PR has no candidate in the map is NOT routed publicly. It is claimed and deferred as backpressure (no delivery yet, same durable retry and `MAX_BOUND_DEFERRALS` horizon as every other deferral, dead-letter at the horizon); recovery re-resolves such deferred events against the current map, so a complete snapshot that lands later routes them privately. Known targets are unaffected and proceed immediately. Public routing of an unmatched event requires a complete snapshot to have established the absence at least once.

#### Comment delivery intercept

`dispatchEnvelope` is the single funnel for accepted comment/body/review/assign events. Before claiming the inbound task it consults the bound-session map:

- **Bound session found** → the persisted `InboundTaskRecord` gains `delivery: { kind: 'bound-session', sessionId }`. `runInboundTask` delivers the event prompt through `boundSessions.deliverPrompt` instead of `handleInbound`. Because this bypasses `handleInbound`, the bound path runs the same `preflightInbound` (group policy, sender gate, pairing — side effects included) before delivering; watch events are exempt (no human sender, operator opt-in). The frozen target is re-validated against the latest complete snapshot at delivery time, so a live rebind retargets the event instead of misdelivering to the old session; on a partial/failed scan the persisted target stands (fail-closed). Dedupe keys and the recoverable-task machinery are unchanged — only the terminal delivery differs.
- **No bound session** → today's path for comment events (`handleInbound` → channel session). **Watch events are private-only**: they are operator-facing machine state with no pre-existing public path, and a channel session's reply would publish the internal prompt text on the PR (and re-gate it through the sender allowlist). A watch event with no bound target — at delivery, after a gone re-resolution, or at drain time — is logged and retired, never fallen back publicly.
- **Delivery fails**: 404 → the accessor first tries the dormant wake (Layer 2); only a session that cannot be restored surfaces as gone, and the adapter then evicts the dead session from its binding maps (so a partial snapshot cannot retain it by recency and shadow a live follower) and re-resolves once from a fresh binding fetch; a different candidate is re-delivered (a Gone from that re-delivery hop falls through to the same fallback instead of consuming the failure budget), no candidate left on a COMPLETE snapshot → comment events fall back to `handleInbound`, watch events retire with a log; under a partial/failed refresh the comment fallback defers as backpressure until a complete snapshot establishes absence (Key decision 11). Queue-full and temporarily-unavailable sessions/workspaces are backpressure, not failure: they do not consume the retry budget, so a busy or draining session defers the event instead of losing it after `MAX_INBOUND_TASK_ATTEMPTS = 3`. Backpressure is bounded (`MAX_BOUND_DEFERRALS = 240`, ~4 hours at the default poll): beyond the horizon the event is retired to a private dead-letter log (`github-bound-deadletter.jsonl`) with a stderr alert — surfaced, never silently consumed. If the dead-letter append itself fails, the task is KEPT (the payload is dumped to stderr and the durable record survives for the next poll's retry or operator recovery) — a removal there would leave one log line as the event's only trace. Pure bound backpressure — including the targetless deferrals an incomplete snapshot produces — does not hold the shared notification cursor (one stuck session must not freeze mark-as-read for every unrelated PR); other recoverable tasks still hold it, except watch tasks while reconciliation is blocked (they cannot make progress and do not ride the notification cursor). Non-backpressure bound failures exhaust the 3-attempt cap and likewise retire to the dead-letter log (the private path's exhaustion surface — it posts no public error comment). Acceptance is persisted (`deliveredAt`) before the task is removed; the mark is an optimization, not the replay guard: every injection carries a stable event identity (source chat + message id) as an admission-side `idempotencyKey`, so a crash or write failure in the acceptance window (or a lost 202) replays the POST with the SAME key — even when recovery re-creates the task with a new id — and the daemon deduplicates it into the original admission (Key decision 10). A crash-loop charges one attempt per recovery pickup so it terminates. Recovery after restart honors the persisted `delivery` field and re-resolves targetless backpressure deferrals against the current map.

The injected prompt reuses the webhook-task prompt shape (`buildChannelWebhookPrompt` style): event header, explicit "untrusted event data" warning, PR identity (repo, number, title, URL), the lane's `Trigger:`/`Event:` lines plus the direct lane's factual `Author:` details, the comment author/body or event details, and guidance that the reply stays in this session (the session is not under the channel publication contract; it acts on GitHub through its own normal tools if needed). The mention and first-contact lanes supply no `Author:` metadata line, so the prompt falls back to the envelope's sender name — the session must be able to tell a maintainer's instruction from a drive-by commenter's. Channel-facing publication wording never reaches the bound session: the metadata's publication instructions are dropped, and the aggregate lane's "output exactly `<no-reply/>`" prefix is replaced with a plain "New comments on the PR" header. **No tail is silently consumed**: comment content is capped at 6,000 code points with an explicit `[prompt truncated: N more characters omitted]` notice appended outside the slice; an aggregate batch that drops older comments at the 20-comment cap prepends an omission notice (at the FRONT, so the code-point cap cannot truncate the notice itself); and each aggregated comment's 400-character display cap carries its own `[comment truncated: N more characters]` marker — every such comment is already recorded in `dispatchedComments`, so a silent cut at any level would lose it from every surface while the prompt reads complete.

#### PR state watch

When `prWatchEvents` is non-empty, `pollOnce` reconciles durable pending events, then runs a watch detection pass after the binding refresh and before generic inbound recovery and notification processing:

1. **Watch set**: bound PRs from the same binding fetch, filtered to the channel's GitHub host, capped at 30 (most recently updated bindings first) for active polling. When more than 30 PRs are bound, the overflow is logged to stderr (count + excluded keys) so the oldest bindings being deterministically unwatched is surfaced, never silent. A binding recorded `merged`/`closed` by the independent refresh stays polled until the poll itself observes the terminal transition (`prState: 'closed'`), so `state_change` is never skipped by the refresh winning the race. Once observed, the terminal MARKER is retained without polling for as long as the binding lists the PR — pruning it would re-add the closed PR as a first observation on the next poll (query oscillation). Binding retention and active polling are separate concerns. No bound PRs → zero API calls. Persisted entries are pruned against the full candidate set (not the capped watch set, so PRs rotating out of the cap keep their baseline), only when the snapshot is complete — a partial snapshot never prunes — and never while the entry still holds undelivered pending events. Because a permanent partial never prunes, retention is bounded separately: at most 1024 unlisted sessions and 1024 idle watch entries are kept (oldest-first eviction, surfaced on stderr for both caps), so a permanently unscannable workspace cannot grow adapter state without bound. Watch-entry eviction additionally skips entries a retained binding still claims or an in-flight watch task still owns; an evicted entry's PR has no delivery target, and a later rebind re-baselines silently like any first observation, so eviction bounds memory without losing a deliverable event. A dropped session's unmatched events defer (an evicted binder is unlisted, so absence is not authoritative) and surface in the dead-letter at the horizon.
2. **Per PR**: `pulls.get` every poll (head SHA, `mergeable`, `mergeable_state`, `state`, `updated_at`). Check runs (`checks.listForRef`) and combined commit status (`repos.getCombinedStatusForRef`) are fetched only when `ci_failure` is subscribed AND: the head SHA changed since the last poll, no CI observation exists yet, the last observed CI aggregate was pending AND the 5-minute pending re-check interval (`CI_PENDING_RECHECK_INTERVAL_MS`) has elapsed, the PR's `updated_at` advanced, the aggregate is `none` within a 10-minute grace window after the head was first observed (checks register asynchronously), or the last CI fetch is older than the 10-minute settled-head re-check interval. The pending interval is load-bearing in the other direction: a workflow queued for environment approval or an offline runner can stay pending for hours, and an unbounded per-poll re-fetch would turn the settled-head cost model into ~3,600 CI calls/hour at the watch cap — over budget once `pulls.get` is counted. The periodic re-check is load-bearing too: GitHub does NOT bump a PR's `updated_at` on check activity (verified against the live API), so a settled head whose check re-run turns red — or CI that appears late on a manual `workflow_dispatch` — would otherwise be missed forever. Steady-state cost is one call per PR per poll plus the bounded periodic re-checks. A failed CI fetch is isolated in its own try/catch: CI is a conditional refinement of the `pulls.get` baseline, so a persistent Checks-endpoint failure (a classic PAT without Checks permission, an enterprise policy) logs and continues WITHOUT writing a CI state — `merge_conflict`/`state_change` still fire from the data that already arrived, and the last known aggregate stands (writing `none` would re-fire `ci_failure` when the endpoint heals). Watch API calls fail fast on conditions a retry cannot fix — credential failure (401), any rate limit (403/429; GitHub does not always send a `retry-after` header on a secondary/abuse limit) and permanent per-PR statuses (404/410/451 — the PR was deleted, transferred, or the repo became unavailable) — with no blocking cooldown sleep. The shared conditions (401/403/429) abort the WHOLE pass at the failing PR: walking the rest of the set would issue one doomed request per watched PR per poll for the whole reset window; per-PR permanent statuses stay isolated so one deleted PR does not stop the others. The fail-fast predicate is watch-local so the publication lane keeps its own retry semantics, and the notification lane still runs in the same poll.
3. **Transition detection** against persisted watch state (`channelFilePath('github-pr-watch.json')`, pruned against the full candidate set on complete snapshots — see item 1):
   - `ci_failure`: aggregate turns to failure (any completed check run with `failure`/`timed_out`/`action_required`/`startup_failure` conclusion, or a nonempty combined status reporting `failure`/`error`). An empty combined status (`total_count: 0`, which GitHub returns as `state: "pending"` for SHAs without legacy statuses) never counts as active CI. Fires once per head SHA via the durable `fired` ring, even if the aggregate flaps back to success and fails again; a new head that fails fires again. A per-entry `ciFiredSha` pin backs the ring: the capped ring can evict the per-head `ci_failure` key after 64 non-ci episodes on a long-lived head, and the pin preserves the once-per-head guarantee even after that eviction (it resets when the head changes). The event summary names the failed checks (up to 5) so the session can act without re-querying.
   - `merge_conflict`: `mergeable_state` enters `dirty`. Edge-triggered; `dirty → clean → dirty` fires again. `mergeable === null` (GitHub still computing) never overwrites the last known state.
   - `head_change`: head SHA differs from the last observed SHA (first observation initializes silently). A force-push revisit of a recent SHA is a new transition and fires again.
   - `state_change`: PR `state` leaves `open` (merged or closed). First observation initializes silently; close → reopen → close fires again.
   - **Dedupe key identity**: every watch key bakes in the PR number and the detection timestamp (`watch:<type>:<pr>:<seq>:<detectedAt>`; `watch:ci_failure:<pr>:<sha>:<detectedAt>`). The PR number scopes the key because the delivery idempotency key carries only chat + message id, and two PRs of one repo bound to the same session issue parallel episode counters. The timestamp keeps instances unique across episode-counter resets (prune, corruption recovery): the daemon's idempotency ring outlives the worker, so a re-issued bare counter key would dedupe into the old admission and silently swallow the new transition. `ci_failure` still fires once per head SHA — the fired ring and pending queue match its keys by PR+SHA prefix — while the other three key on the episode counter, a transition INSTANCE rather than a state value, so the legitimate recurrences above are never suppressed by the fired ring. The counter is persisted with the baseline. An event key that would exceed the prompt route's 200-character cap is replaced by a deterministic hash of the same identity (`github:h:<sha256-40>`), so retries still dedupe instead of burning the failure budget on 400s. Watch identities are instance-local by design: two channel configurations watching the same repository each deliver their own watch notifications (at-least-once per subscription) — the daemon ring dedupes retries of ONE delivery, not independent subscriptions; comment events still dedupe across instances via their stable GitHub ids.
4. **Durable event queue**: detected events are appended to a `pending` queue persisted in the same write as the new baseline, so a crash between detection and claim loses nothing. A reconciliation pass drains ALL pending entries (no GitHub calls) BEFORE generic recovery and independently of the live watch pass: a failing or rate-limited API pass cannot starve already-detected events, and recovery cannot deliver-and-remove a task that a later drain would re-claim (a crash between the claim and the pending→fired save leaves both records on disk). **When reconciliation ITSELF fails** (e.g. the watch file is unreadable), generic recovery skips watch tasks entirely until a reconciliation succeeds — delivering and removing an accepted watch task with its pending record still unreconciled on disk would let a later drain claim and deliver the same transition a second time; unrelated comment recovery keeps running. Blocked watch tasks also stop holding the shared notification cursor: they cannot make progress while reconciliation fails, and watch events are detected from PR state rather than notifications, so freezing mark-as-read for them would stall every unrelated PR until the sidecar recovers; once reconciliation succeeds they hold the cursor again until their bounded retries settle them. Draining then, per event: re-validate the recipient against the latest complete snapshot, claim the inbound task (durable — a terminal failed/cancelled record for a recurring WATCH key is replaced, never silently reused; comment/event/issue-body keys are stable identifiers that never re-fire, so their terminal records stay a permanent dedupe barrier — replacing them would revive a cancelled comment after a crash leaves the cursor behind the cancel), move the key from `pending` to a capped `fired` ring (durable), then run the task. A crash at any point leaves either a pending event or a claimed task; the `fired` ring is the durable once-per-transition record (task-level dedupe alone would let a flapping aggregate re-fire the same head after the completed task is removed). A failed claim leaves the event queued for the next poll. The drain stops at the first failed delivery so a later event cannot jump ahead of an earlier retrying one (per-PR ordering); pending and fired are already persisted, so stopping loses nothing. The ordering holds across passes too: while an earlier watch transition of the same PR still has an unsettled task, the whole entry's drain is skipped (the watch pass re-drains after reconcile, and the next poll's reconcile runs before recovery) — a task whose key equals the pending head is that event's own crash-window claim and drains normally. A claim persistence failure propagates out of the drain so reconcile fails and the recovery guard holds. The per-entry pending queue is capped at 64: a persistently failing claim cannot grow it without bound; overflow retires the OLDEST queued event to the dead-letter, and a failed dead-letter write keeps it queued for the next detection. A failed pending→fired save AFTER a successful claim rolls the claim back (removes the task, restores the pending event) and retries next poll, so a watch-file-unwritable / task-file-writable divergence cannot deliver the same transition twice across a restart. Event tasks use `source.messageId = watch:<eventType>:<pr>:<headSha|seq>:<detectedAt>` and are delivered privately like comments — but with no public fallback (see Comment delivery intercept).
5. **Binding state upkeep** stays with the existing 5-minute refresh timer; the adapter does not PATCH metadata. Once the timer records `merged`/`closed` AND the watch has observed the terminal transition, the PR leaves active polling; its terminal marker is retained until the binding itself disappears.
6. **Persistence failure semantics**: a transient read error (EACCES/EMFILE/EIO) fails CLOSED — the watch pass is skipped and nothing is saved until the state loads again, so a degraded in-memory state can never overwrite the intact file. Only ENOENT (first start) and persistent JSON corruption start fresh; a syntactically valid file whose individual entries are malformed is repaired in place — each bad entry is dropped (with a stderr line) and the healthy entries survive, so one corrupt value cannot starve the API-independent drain of the entries after it. The per-entry shape check validates pending events with the SAME envelope and delivery validators the task store applies at claim time: a shape-valid envelope missing `chatId` would otherwise throw in the binding-key lookup and abort the whole reconcile loop, and a partial envelope would be claimed verbatim, rejected on the next task-file read, and wedge the store until an operator deletes the file. Failed atomic writes clean up their UUID-named tmp file so sustained disk pressure cannot accumulate orphans. The state file and directory are mode 0600/0700 (they persist private comment envelopes).

#### API budget

Default 60 s poll, cap 30 watched PRs: steady state ≤ 1 800 calls/hour, plus the periodic settled-head re-check (≤ 2 calls per PR per 10-minute interval → ≤ 360/hour) and the bounded pending re-check (≤ 2 calls per PR per 5-minute interval → ≤ 720/hour worst case with every watched PR pending). CI-active bursts add 1 combined-status call plus `ceil(checkRuns/100)` check-list pages per affected PR per re-check — a 300-check monorepo head costs 4 calls, so large-CI bursts can still exceed the 5 000 calls/hour token budget; the watch then aborts the pass on the shared rate-limit/credential failure (one doomed call, not one per PR) and retries next poll rather than blocking. Notification polling overhead is unchanged. The adapter logs and skips the watch pass when the binding fetch fails (notifications still flow).

## Key decisions

1. **Prompt injection, not channel attach.** `activateManagedSession` would bind the followed session's outbound target to the GitHub thread, so every final reply of an interactive session would be published as a public PR comment (publication contract). Injection keeps replies in the session and leaves GitHub actions to the session's own judgment and tools.
2. **In-channel state watch, not webhooks.** The watch reuses the channel's existing poll loop and credentials; detection happens at the API layer and costs zero model tokens until a real transition. Webhook push would need a public tunnel plus repository webhook creation (operator consent) and a rework of the static webhook targets. The watch is polling, but it is the gate-probe shape the maintainer accepts: cheap detection outside the model, model only on change.
3. **Reverse lookup lives in the daemon.** Bindings span workspaces; the worker is workspace-scoped and already talks to the daemon over authenticated HTTP. A read-only process-global route reuses the refresh timer's scan pattern instead of duplicating sidecar access in the worker.
4. **One candidate, most recently updated.** Broadcasting to every bound session multiplies model cost and produces duplicate GitHub actions; the freshest non-archived, non-channel session is the one most likely to hold the working context.
5. **Channel sessions excluded from candidates.** A channel-created session bound via `/review` backfill must keep its public-reply contract; the normal channel path already serves it.
6. **Opt-in defaults.** Public-repository events driving an interactive session is a new trust surface; operators enable it explicitly, and comment sender gates still apply before delivery.
7. **Wake dormant sessions instead of falling back.** E2E showed that after a daemon restart the bound session is dormant and the prompt route 404s; treating that as "gone" silently diverted every post-restart event into public channel delivery — breaking the feature's core private-delivery promise. The accessor therefore restores the session (the same resume path the channel bridge already uses) and retries once; only an unrestorable session falls back. The restore mints a client registration that the accessor explicitly detaches once the retried prompt settles: a non-empty registration blocks the daemon's prompt-settled idle close, so without the detach the woken session would stay pinned live until the TTL reaper (or forever with the reaper disabled).
8. **Watch events are private-only.** A comment has a pre-existing public path to fall back to; a watch event does not. Falling a watch event back to a channel session would publish operator-facing machine state ("CI failed on head X. Inspect the failed checks…") as a public PR comment and re-gate it through the sender allowlist. Maintainer decision (2026-11-02, resolving the triage/verification escalation): a watch event with no bound target is logged and retired, never published. The retirement is surfaced (stderr + task removal), not a silent drop.
9. **Bounded backpressure with a dead-letter surface.** Queue-full and unavailable conditions defer without consuming the failure budget, but the deferral horizon is bounded (~4 hours) and pure backpressure — bound deliveries AND the targetless deferrals an incomplete snapshot produces — does not hold the shared notification cursor: one stuck session must not freeze mark-as-read for every unrelated PR, and a permanently stuck session must not wedge a task forever. Events that exhaust the horizon or the failure budget retire to a private dead-letter log: the private path posts no public error comment, so the dead-letter is its exhaustion surface. A failed dead-letter write keeps the task instead of removing it.
10. **Admission-side idempotency, not a bigger acceptance window.** The durable `deliveredAt` mark can only protect crashes AFTER it lands; the acceptance write itself can fail (EIO) or the 202 can be lost, and the daemon mints a fresh prompt id per request, so a retry used to re-inject the same event. Moving the mark before the POST would trade a duplicate for a silent loss. Instead the POST carries a stable event identity (source chat + message id) as an `idempotencyKey` — stable across task re-creation, which a task-scoped key would not be — and the prompt route deduplicates admitted keys per session (bounded in-memory ring, 128 keys per session, 1024 sessions, FIFO): a retry returns the original admission without enqueueing. The ring's lifetime equals the in-memory prompt queue's — a daemon restart loses both together, making re-injection the correct recovery there. The session cap is the one exception: a key can be evicted while its queue is still live if more than 1024 sessions hold keys, and a retry after such an eviction re-injects. The mark remains as a fast path that retires the task without a round-trip. For aggregate comment batches the message id is a content hash of the sorted member ids (`agg:<sha256-40>`), not the first comment: a crash before the cursor save can re-list a SUPERSET batch, and a first-comment key would let the daemon ring dedupe the grown batch into the original admission, silently dropping the new members; identical batches still dedupe across the acceptance crash window. The publication audit's consumption verdict is the LAST outcome per source key: a terminal `failed` (a provable no-write) after `posting` leaves the event retryable, while an ambiguous failure (`failed_ambiguous` — the write may have landed) and a `posting` with no terminal record (crash mid-post) consume at-most-once, since a second public reply would be irreversible; an unreadable audit freezes the poll's cursor rather than skipping events past a mark-read, and every dispatch lane honors the refusal before recording its dedupe key. The freeze is enforced at DISPATCH time: a recovery pass holding only watch tasks reads neither public store (watch events are never published, so they can match neither a pending delivery nor an audit key), and a private watch retire completes even while the audit is unreadable — the next public dispatch still refuses and freezes.
11. **An incomplete scan never establishes absence.** A partial bindings answer — especially an EMPTY one after a restart — is not evidence that a PR is unbound, and public routing is irreversible (the cursor commits in the same poll). So the cold gate defers empty-partial answers for a bounded number of polls, and unmatched events defer per-event (recoverable, dead-letter at the horizon) instead of taking the public path whenever absence is not authoritative — before the first complete snapshot, and, for PR events, during ANY partial answer or failing refresh. A partial answer cannot prove absence even when every OBSERVED binder is listed and excludes the PR: an unscannable workspace may hold a never-observed follower, and a listed tombstone proves only that the listed session unbound (it still stops private delivery and watching immediately). Known targets proceed immediately. Issue events are exempt from the partial/failed-refresh clauses: bindings are PR-only, so once the cold-start gate opens an issue's absence is provable. The bounds keep a permanently degraded deployment from freezing: the lane opens at the cap and events surface in the dead-letter rather than vanishing.

## Constraints and risks

- **Untrusted content into an interactive session.** Event payloads are marked untrusted in the injected prompt (same contract as webhook tasks). Comment sender gates apply unchanged. State events have no human sender; they exist only because the operator opted in, and they are private-only (no public fallback). The target session's own approval mode governs its actions.
- **Process-level relay credential (widened worker authorization).** Bound delivery is cross-workspace, so the prompt route cannot keep the old home===target equality for the worker token. The widening is scoped to its reason: cross-workspace channel classification requires the explicit `qwen.daemon.channelBoundRelay` marker IN ADDITION to a registered worker token and a primary/trusted target, and a plain prompt carrying a foreign worker token gets no channel classification and no caller-supplied display projection. Residual risk, stated plainly: the marker is intent, not authentication — a holder of workspace B's worker token can set it and relay into a trusted workspace A, opting that turn out of loop-detected rejection and supplying its display text. The security boundary remains token possession plus the target's trust (the same trust model the bindings route enumerates); a daemon serving an internal interactive workspace alongside a workspace whose channel ingests attacker-controlled text extends that channel's reach into the trusted workspace's sessions. Operators who cannot accept that should not register channel workers on the same daemon, or should keep the ingestion workspace untrusted (untrusted non-primary workspaces are already excluded from both the bindings scan and the relay gate).
- **Queue pressure.** A burst of events can fill the target's 5-slot prompt queue; queue-full and temporarily-unavailable conditions are backpressure (they do not consume the retry budget) and delivery retries on later polls. The deferral horizon is bounded (`MAX_BOUND_DEFERRALS`, ~4 hours); beyond it — or when non-backpressure failures exhaust the 3-attempt cap — the event retires to the private dead-letter log with a stderr alert. Pure bound backpressure does not hold the shared notification cursor; other recoverable tasks still hold it, except watch tasks while reconciliation is blocked (they cannot make progress and do not ride the notification cursor). No bound event is silently consumed: it is delivered, deferred, or dead-lettered.
- **Rate limits.** The watch caps, conditional check fetches and the bounded periodic/pending re-checks keep the steady state under the 5 000 calls/hour token budget (large-CI bursts can exceed it; see API budget). A shared credential/rate-limit failure (401/403/429) aborts the whole watch pass with a log — one doomed call, not one per watched PR — and notifications are unaffected, rather than sleeping out the reset window ahead of the notification lane. The daemon's own prompt-tier 429 is backpressure for delivery (defer, never burn the failure budget).
- **Stale bindings.** A dormant bound session is woken by the accessor (Layer 2), so daemon restarts do not divert events into public channel delivery; the cold-start gate defers the comment lane until the first successful snapshot populates the binding map, and empty-partial answers keep it closed for a bounded number of polls (Key decision 11). Unmatched events defer recoverably instead of routing publicly whenever absence is not authoritative (no complete snapshot yet, or — for PR events — any partial answer or failing refresh). A binding whose session was truly deleted fails the wake → comment events fall back to the channel path, watch events retire with a log; the next poll's binding fetch heals the map. Under a partial/failed scan the comment fallback defers as backpressure until a complete snapshot establishes absence — an unscannable workspace may still hold a never-observed follower, and the public reply would be irreversible. An observed unbind (a scanned session listed with an empty PR set) stops private delivery and watching even on a partial answer — the tombstone row makes "scanned, no bindings" distinguishable from "not enumerated" — while public routing for the PR still waits for a complete snapshot.
- **Closed sessions.** `DELETE /session/:id` closes a session without deleting its record; the record stays resumable and bound, so such sessions are still woken for delivery (verified in E2E). Only record deletion (`POST /sessions/delete`) or archiving removes a session from the candidate set (an archived session's restore answers 409 `session_archived`, classified as gone for delivery). Closing is a resource action, not an unsubscribe; the binding expresses the follow intent.
- **Scan cost.** The route scans sidecars per call; at current scale this is milliseconds. Multi-page scans are flagged partial (activity-ordered pagination is not snapshot-isolated), which makes consumers retain known bindings rather than prune — a deliberate conservative trade. If scale grows, a snapshot-consistent enumeration or an in-memory index invalidated by `session_metadata_updated` is the follow-up, not part of this change.

## Validation plan

- **Unit**: route scan (trusted/untrusted, archived exclusion, sidecar corruption tolerance); adapter selection (host filter, state filter, channel-source exclusion, recency tie-break); delivery intercept (bound → inject, unbound → channel path, 404 fallback, queue-full retry, recovery honors persisted delivery); watch transitions (each event type, dedupe per head, null-mergeable guard, first-observation silence, state-before-dispatch ordering); config validation.
- **E2E** (daemon + local build): bind a PR to a session via PATCH metadata; simulate events with a stubbed GitHub API layer; assert the bound session receives exactly one injected prompt per transition, replies stay in-session, and an unbound PR still creates a channel session. Plan details in `.qwen/e2e-tests/github-channel-bound-session-events.md`.

## Acceptance criteria

1. With both fields enabled, a new comment on a bound PR arrives as a prompt in the bound session (not the channel session), and the session's reply is not auto-posted to GitHub.
2. A CI failure on the bound PR's head, a transition to `mergeable_state: dirty`, a head advance, and a merge/close each produce exactly one injected prompt per transition instance, surviving daemon restarts without re-firing; legitimate recurrences (dirty → clean → dirty, close → reopen → close, a `head_change` SHA revisit, a new head failing) fire again, and a settled head whose check re-run turns red is caught by the periodic re-check. `ci_failure` is once per head SHA within the fired-ring window — a revisited SHA's CI failure is suppressed while that head's key remains in the ring, and `head_change` carries the revisit itself.
3. With no bound session, comment events behave exactly as today (channel session created/reused, public reply contract intact); watch events are logged and retired, never published.
4. With the fields disabled (default), behavior and API call volume are unchanged.
5. Queue-full, rate-limited (429), and unavailable paths defer without losing events and without freezing the shared cursor; session-gone comment paths fall back without loss; watch paths retire privately; exhausted events are dead-lettered (and a failed dead-letter write keeps the task); no crash window replays an accepted injection — a retry after a lost acceptance mark or a lost 202 carries the same idempotency key and deduplicates into the original admission — and none silently consumes a transition; an empty partial cold snapshot never routes events publicly, and an observed unbind stops private delivery even on a partial answer.
