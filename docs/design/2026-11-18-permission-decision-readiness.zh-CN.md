# 权限决策的可审查性

[English](2026-11-18-permission-decision-readiness.md) | [简体中文](2026-11-18-permission-decision-readiness.zh-CN.md)

状态：提案，尚未实现。作为 issue #17715 立项跟踪，是 PR #17132 的后续跟进；该 PR
已实现的行为记录在
[确认界面正文高度预算](2026-11-14-confirmation-body-height-budget.zh-CN.md)。

## 问题

一次确认可以在「可以作答」的同时，它所要询问的东西却不可审查。命令、拟做的
编辑、目标主机、MCP 的服务器加工具这一对——也就是决策的实质主体——都可能被
视口压力压缩到屏幕上一个像素都不剩，而肯定选项依然可用且高亮。PR #17132 里的
每一个修复都只回应了这样一个画面；评审者指出的是这一类问题在修复之后依然存在，
因为「屏幕上有一个选项」和「它的主体被显示过」是两个独立事实，现有设计里没有任何
东西把二者关联起来。

后果是：用户可能授予一个他根本没有机会读过内容的权限，而这次授予的记录——一个
被选中的选项 id——与一次知情的授予看起来完全相同。

## 当前状态

有两条互相独立的路径回答权限请求，两条路径都没有「可审查性」的概念：

- 终端路径：`packages/core/src/core/coreToolScheduler.ts` 构造确认详情，并应用
  在 Ink 确认界面（`packages/cli/src/ui/components/messages/ToolConfirmationMessage.tsx`）
  中做出的选择。
- ACP 路径：`packages/cli/src/acp-integration/session/Session.ts` 收到请求，并
  通过 `packages/cli/src/acp-integration/session/permissionUtils.ts` 中的
  `resolvePermissionOutcome` 解析回答。这一侧的解析函数是真正的收口处——会话本身、
  `acp-tool-batch.ts` 里的工具批次，以及 `SubAgentTracker.ts` 里的子代理跟踪器，
  都要经它取回答——但它只看得见客户端送来的东西。

同一个请求随后由若干客户端各自按自己的视口计算布局来渲染——
`packages/vscode-ide-companion/src/services/acpConnection.ts`、
`packages/web-shell/client/components/messages/ToolApproval.tsx`、
`packages/cli/src/ui/opentui/dialogs-confirm.tsx`、`packages/live-host`，以及
`packages/channels/base` 里的通道桥——因此没有任何渲染器的布局知识能到达回答。

请求里带着这次工具调用和选项列表，但完全没有关于「屏幕上显示过什么」的信息。
这些形状并不都属于我们：ACP 侧的 `PermissionOption`、`RequestPermissionRequest`
与 `RequestPermissionResponse` 来自上游的 `@agentclientprotocol/sdk`；daemon 侧
则在 `packages/sdk-typescript/src/daemon/types.ts` 里有自己的 `PermissionOutcome`
——取值为 `…Selected` / `…Cancelled`。

daemon 确实协调的事情是「谁」可以回答，而不是他们看到了什么。serve 能力注册表
（`packages/cli/src/serve/capabilities.ts`）广播 `permission_mediation`，模式为
`first-responder`、`designated`、`consensus` 和 `local-only`；`/capabilities`
信封在运行时上报当前生效的策略，而 `permission_partial_vote` 与
`permission_forbidden` 就是现成的拒绝信号。决策的*形状*由中心而非按客户端决定的
地方只有两处有限的先例：`coreToolScheduler.ts` 里的 `hideAlwaysAllow`，以及
`packages/core/src/core/plan-mode-shell-policy.ts`。

## 目标

- 在代码和协议里区分权限决策的必备主体与可选的说明性文字。
- 让「这个待决决策的主体是可审查的」成为一个被明确陈述的值，而不是只有某一个
  客户端能观察到的布局算术的副产品。
- 把肯定结果与该值绑定，使一次无法被审查的决策不再与一次可以被审查的决策
  悄悄等同。

## 范围

- 本文只提出形状。这里没有任何东西被实现；PR #17132 交付的是布局不变量，而该
  不变量是这里任何内容的前提，不是它的替代品。
- 不含肯定动作的被动信息输出不在范围内；主体完整可见的批准也不应多出一额步骤。

## 方案

1. **先有语义主体，再谈布局。** 每种确认类型把自己的实质主体作为一个值命名出来：
   确切的操作、这次权限覆盖什么（exec 命令、拟做的编辑、每一个具体目标地址、
   MCP 的服务器*与*工具）、请求的权限范围，以及影响决策的告警。说明性文字不属于
   其中。PR #17132 已经把这一排序编码成一条行规则——行数不够时主体优先于说明——
   所以这个概念已经存在；要做的变化是让它变成别的代码能读到的东西。
2. **每个请求一个可审查性状态。** `inspectable`：主体就画在取走回答的那个画面里。
   `escapable`：主体不在那个画面里，但存在一条完整细节路径，且已知它确实可用。
   `unavailable`：两者都没有。渲染出来的提示、省略号或溢出 id 都不满足
   `escapable`；今天的 `ctrl-s` 调出也不满足，因为输入缓冲区里有草稿时它会被压制。
3. **把肯定结果绑定到该状态。** 批准需要 `inspectable` 或 `escapable`。处于
   `unavailable` 时，拒绝与取消保持可用；批准需要先打开一个有保证的审查界面。
   被选中选项背后的动作与权限范围永不改变——改变的只是它此刻能否被选中。

## 设计决策与理由

- **不放在布局层。** 在 `ToolConfirmationMessage` 内部算出的可审查性标记描述的
  是一个 Ink 画面。VS Code 伴生扩展、web-shell、OpenTUI、live host 和各通道桥
  会为同一个请求做自己的布局决定，因此一个它们从不设置的标记对它们发回的回答
  毫无意义。
- **回答必须携带它。** 要让可审查性约束一次决策，它就得随结果一起传递，也就是说
  ACP 权限响应上要有一个字段，daemon SDK 类型上要有对应字段，并由两条回答应用处
  共同消费。这是一次带兼容窗口的协议变更，不是组件变更。
- **按其他 daemon 特性的方式广播它。** 能力注册表已经为权限行为处理过「字段缺失」
  这个问题：SDK 告诉客户端，在依赖调停事件之前先预检 `permission_mediation` 标签，
  因为较旧的 daemon 不会发出这些事件。可审查性字段可以沿用这一约定，于是 daemon
  路径上的情况是可判定的——没有该标签就是今天的行为，有该标签就该期待该字段。
- **ACP 那一半不是我们能改的。** 权限选项与结果形状属于
  `@agentclientprotocol/sdk`，因此本仓库里的任何改动都无法让 ACP 原生客户端携带
  可审查性取值。所以闸门首先对第一方客户端成立；这种分裂的保证是设计的真实状态，
  不是可以含糊过去的实现细节。
- **失败关闭需要下限。** 在无法确立可审查性时就阻断批准，等于把可审查性计算里的
  任何缺陷变成一种把用户自己的请求困住的手段。任何 `unavailable` 处理都需要一条
  用户总能到达的出口——而这恰恰是没有调出 affordance 的无头通道所缺的东西。

## 约束

- 权限请求及其回答跨越 ACP、`packages/acp-bridge`、daemon SDK 类型和各通道桥；
  新增字段是一次有外部消费者的公开协议变更。
- 两条回答应用处都必须遵守该状态，否则闸门只是一个建议。
- 可审查性必须由实际画出的内容或由一条被证实的路径确立，绝不能由预算数字得出——
  这与 PR #17132 的测试断言渲染画面而非算术是同一个理由。
- 每种确认类型的一套主体模型必须同时服务一个六行终端、一个网页面板和一个由通知
  驱动的通道，而不是为每个客户端发明一套「足够」的定义。
- 在 `first-responder` 调停策略下，只存在于某一个客户端里的闸门根本不是闸门：任何
  忽略可审查性的客户端都能抢先回答。强制点必须落在回答应用处，而四种调停模式——
  包括远程投票者被直接拒绝的 `local-only`——都要在其下得到自洽的结果。
- 有保证的完整细节路径今天只对某些确认类型存在：在编辑器中打开完整计划，以及在配置了
  外部编辑器时用外部编辑器修改一处拟做的编辑。因此某处出现了提示，并不能据此假定
  `escapable` 可用。

## 风险与取舍

- 如果 `inspectable` 算得过于保守，本来已经可读的批准会多出一额步骤。
- 实现了该字段的客户端与未实现的客户端会对同一个请求给出不同的保证，在铺开完成
  之前，这对用户比一个统一（但较弱）的保证更糟。
- 闸门制造了一种阻断正当工作的新方式；这一领域的每个修复都需要一条可达的出口。

## 验证方案

- 在两条回答应用处做协议往返测试：分别以每种可审查性取值选中一个选项，再加上
  字段缺失的情况，断言的是调度器由此产生的行为，而不只是类型本身。
- 每个客户端一个契约测试：渲染一个已知放不下的主体，断言该客户端上报的状态——
  与 `ToolConfirmationMessage.test.tsx` 使用的同一种「以画面为证」的风格，因为
  一个由算术算出的值完全可以在画面不可读时仍然是绿的。
- 同一个请求的跨客户端用例：终端、web-shell 与 VS Code 伴生扩展，检查它们在相同
  尺寸下对相同内容上报相同状态。

## 验收标准

- 每种确认类型只有一个被命名的实质主体概念，由渲染器和回答路径共同读取，而不是
  在各自内部重新推导。
- 状态为 `unavailable` 时不能肯定地授予权限决策，而拒绝与取消结果保持可用。
- `escapable` 只能由一条在请求出现在屏幕上那一刻被证实可用的路径设置。
- 现存客户端继续工作，且闸门的铺开状态是可见的，而不是隐含的。

## 待决问题

1. 能力标签在 daemon 路径上能解决「字段缺失」的情况，在 ACP 路径上不能。只覆盖
   第一方客户端的闸门，值不值得用这种分裂的保证去换——还是这个想法必须先走上游？
2. 客户端能否不测量自己的布局就声明 `inspectable`，还是每个渲染器都必须把一次
   测量接进回答？
3. 对没有调出 affordance 的通道，有保证的审查界面是什么——如果根本不存在，这样的
   通道是否被允许提供肯定选项？
4. 可审查性是否应随决策一起被记录下来，以便日后审计能区分知情的授予与不知情的
   授予？
5. `unavailable` 的拒绝是复用现有的 `permission_forbidden` 界面，还是需要自己的
   结果，好让「你不能回答这个」和「你看到的还不够回答这个」在记录里保持可区分？
