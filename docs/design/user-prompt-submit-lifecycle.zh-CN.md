# UserPromptSubmit 生命周期

[English](user-prompt-submit-lifecycle.md) | [简体中文](user-prompt-submit-lifecycle.zh-CN.md)

## 问题

共享模型客户端会在工具结果和 Stop 触发的续跑上执行 `UserPromptSubmit`。旧版 ACP 也可能在重试时再次执行。包含两次工具调用的用户消息在给出最终回答前，可以三次执行同一组钩子。工具结果轮次可能花时间生成已交付的上下文，钩子也可能阻止已经完成的工具结果进入模型。

## 设计

- 共享模型客户端对一条新用户消息执行一次检查。在展开前完成检查的调用方把该结果传给第一次发送。工具结果、Stop 续跑、重试和历史恢复走各自的入口，无需再次检查。
- ACP 的两种模型循环采用同一规则。直接 ACP 请求和 daemon 侧用户提交即使没有原始文本元数据，也会执行。daemon 在接收时标记消息来源，ACP 子进程只接受已认证父进程写入的标记。转入普通队列的用户消息符合条件。内部发起的任务和仅供协调的消息走各自的来源。渠道请求的可信来源标为由用户发起时会执行。
- 终端沿用现有的草稿恢复和消息准入逻辑。终端把未发送的消息放回队列时，已完成的检查结果随队列项保留。终端队列将多份未经检查的草稿合成一条新请求时，仍按合成后的请求检查一次。
- Hosted Harness 根据已接收输入的来源判定新用户消息。运行中逐条检查和持久恢复继续使用现有的执行标识。

`submitted_prompt` 仍表示可选的原始文本来源，是否触发钩子独立于该字段。仅在本地执行的命令、Mod 生成的消息、定时任务和内部续跑不触发这一事件。工具执行和其他钩子事件沿用各自的规则。

公开的消息接口默认按用户提交处理收到的请求，已认证的元数据可以表明其来源。独立 Qwen Live 进程等外部中转方通过同一接口提交生成文本时，遵循这一接口规则。

## ACP 中途追问

桥接层接管已接收的追问，直到消息正式提交、被策略拒绝、被撤回，或转入草稿恢复。ACP 子进程以租约申领一批追问，在轮次的取消信号下解析附件，并对每条用户消息执行一次 `UserPromptSubmit`。子进程逐项回报放行、明确策略拒绝、执行异常或释放租约。内部协调消息沿用专用路径。

| 桥接层状态             | 裁决                       | 结果                                                                   |
| ---------------------- | -------------------------- | ---------------------------------------------------------------------- |
| 排队、持有租约或已顺延 | 取消、执行异常或子进程中断 | 撤销提交资格，将原文与有效附件追加到指定客户端的恢复队列。             |
| 排队、持有租约或已顺延 | 撤回或删除                 | 撤销提交资格并移除队列项。                                             |
| 持有租约或已顺延       | 钩子明确拒绝               | 移除队列项并报告策略原因。                                             |
| 持有租约或已顺延       | 租约仍有效且钩子放行       | 先持久化消息、钩子上下文与附件引用，再广播送达并返回已提交的消息标识。 |
| 排队                   | 当前轮次自然结束           | 按相同的租约和准入规则发起后续轮次。                                   |
| 已提交                 | 取消或子进程退出           | 保留消息并补齐未完成的历史写入。                                       |

宿主串行裁决定案、取消和撤回。租约被撤销后，晚到结果无法放行或拦截该消息。未定案的租约归还宿主，按轮次结束原因结算。用户停止当前轮次时，一并取消未提交的追问，独立排队的普通消息继续遵循原有契约。附件解析和钩子响应取消信号，取消收尾阶段无需执行消息检查。

宿主持久化提交是进入聊天流、模型请求和对话历史的共同边界。子进程收到宿主确认后按消息标识写入历史。替代子进程在接收下一条请求之前，将已提交内容补齐到历史中。确认历史已持久化后，宿主即可清理用于补齐的数据。顺延后的首条消息也遵循同一规则。

客户端在上传或入队前生成消息标识，并绑定目标轮次与取消代次。确认完成交接后，宿主取得草稿归属。客户端在本地保全尚未接管的输入。请求结果不确定时，客户端保留副本，核对同一消息标识后再恢复。取消后的目标轮次不能自动改用普通消息接口重新发送。宿主为每条恢复记录指定唯一客户端。指定客户端按顺序将追问合并至已有草稿，以消息标识去重，保存后确认消费。

## 验证

- 含两次工具调用的一轮中，第一次请求前执行一次 `UserPromptSubmit`，执行两次 `PostToolUse`，两份工具结果都进入对应的模型请求。覆盖 headless 和两种 ACP 模型循环。
- 在同一个会话提交另一条用户消息，观察它独立的钩子结果。覆盖无元数据的提交、附加上下文的追问，以及工具成功但追问被阻止的场景。
- 验证重试、Stop 续跑和自动输入无需执行 `UserPromptSubmit`。验证初始钩子阻止消息或收到取消时，模型收不到该请求。
- 在追问入队前、排队中、附件解析或钩子执行中、钩子放行但尚未提交、以及提交后立即停止。分别检查聊天流、模型请求、历史、钩子执行次数和草稿恢复。
- 在排队、持有租约或已顺延时撤回，验证晚到结果无法重新送达。覆盖自然结束顺延、策略拒绝、钩子超时或输出格式错误、提交前后子进程退出，以及重复补齐历史。
- 丢弃入队响应并刷新发送端。使用第二个客户端及两批尚未消费的恢复记录，验证只有指定端回填、每条消息与附件只恢复一次，以及草稿持久化后再确认消费。
