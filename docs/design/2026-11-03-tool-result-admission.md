# Tool result admission on session recovery

[简体中文](2026-11-03-tool-result-admission.zh-CN.md)

## Contract

A completed tool result remains available to the local transcript. A new session recording includes that result in model history only when its admission is recorded. This addresses [#15595](https://github.com/QwenLM/qwen-code/issues/15595), where resuming a session exposed output a `UserPromptSubmit` hook had withheld.

## Recording and recovery

- Each outer completion written by the ordinary tool-result recorder is marked `requiresToolResultAdmission`. The completion is recorded before the next hook can run. A session can install a hook after the tool finishes.
- A model send past the prompt hook appends a `tool_result_admission` system record referencing the completion UUIDs of the current round. The sender matches the submitted function responses and their companion parts. The receipt records permission for this input independently of whether the provider responds. A host that explicitly ends a tool batch in live history, such as a Goal checkpoint, makes the same decision at that boundary.
- Recovery holds the tool parts in their original positions until the corresponding decision arrives. A missing or invalid receipt exposes no result bytes. A tool-only send cancelled before admission leaves history untouched and reports its error when the caller reads the stream. Senders identify the exact tool-owned parts before adding independent input; cancellation removes those parts, including companion text and images, by object identity. Separately supplied input retains the normal history-push and interrupted-prompt behavior even when its text equals a tool companion. Ordinary prompts and prepared-request replay retain their pre-change cancellation behavior. An explicit ACP block or cancellation after tools finish can close the calls with the same synthetic error as the live session. A process that dies before the decision leaves the calls for existing orphan repair. Separately queued user input keeps its position.
- ACP prompt, cron and background-notification turns pass the completed batch parts into the shared model round. Blocked or cancelled tool-result rounds record the same withholding decision and remove tool-owned companion content while retaining separately queued user input. Each completed result keeps its first valid decision. If setup fails after admission, including during compression, live history retains that admitted result just as recovery does. Previously withheld results retain their original reason. The initial Cron and Notification requests retain their existing hook policy.
- A terminal path that keeps a completed batch without another model send follows the same admission contract. With no applicable prompt hook it confirms an allow receipt before keeping the results. With an unfinished applicable hook it records withholding and keeps only synthetic closures and independent input. This tightens cancelled, quota-switch and exhausted-capacity paths; cancellation does not itself grant permission. Legacy ACP result rounds retain their existing no-prompt-hook policy. Explicit Goal termination retains its existing permission policy. A prior valid decision cannot be reversed.
- Admission awaits the recorder’s confirmed write before publishing model history, including normal sends and Goal termination. Writer unavailability, rejected records and write errors propagate instead of allowing the raw result; a topology change that prevents a valid current-round receipt is rejected. This is a confirmed-write/process-recovery guarantee, not a new power-loss or filesystem `fsync` guarantee.
- Late results may replace an orphan-repair placeholder only when the first response for that call is still that placeholder and the call’s consecutive user-history segment has not been followed by another model turn. A result beyond that boundary is dropped before recording or emitting it; the existing recovery format cannot express an update to that earlier slot. The chat reserves that history slot before recording the result, confirms admission, and then replaces it. Ink reuses the shared batch’s finalized result and deferred recording callback inside that reservation, preserving its attachments and recording it once before admission. Sends wait for this operation; competing synchronous history mutations fail before changing history. A rejected replacement writes no completion or receipt. A failed write releases the reservation and retains the placeholder. Switching sessions during confirmation does not redirect the record or replacement to the new chat. Within the permitted user-history segment, existing recovery hoists the function response but does not move its companion parts with it. If independent user input intervenes, live and recovered requests can therefore order those companions differently. This change preserves admission, tool pairing and content; it does not promise byte-identical late-result requests.
- Restore re-execution writes an intentionally unmarked completion and inserts the same response directly into live history under its existing restore authorization. That writer is outside the new ordinary-result admission gate.
- The full and indexed history readers use the same projection. Internal Code Mode results remain outside model history. A compression checkpoint already contains model history and supersedes earlier decisions.
- Ink retains the shared loop’s stream-idle waiting, ordered batch drain and send-time capacity checks. Shared tool-requested termination outside Goal confirms admission before retaining results, following ACP’s explicit termination policy even with a prompt hook. Quota-switch and capacity stops continue to withhold when an applicable hook has not run. Terminal retention does not drain separately queued input.
- A sent ACP message releases its tool-part ownership before a later independent steering message is prepared. OpenTUI settles mixed successful/cancelled batches even when cancellation arrives before steering or during context refresh. Its terminal history publication checks the captured session and turn both before and after receipt acknowledgement. If model setup fails after confirmed admission, retained history keeps the tool-output provenance used for later dispatch accounting.

## Compatibility and verification

Pre-change completions lack admission evidence. They keep their prior recovery behavior, including for output withheld in old sessions. Starting with the new writer, a crash between completion and admission can leave the full output available only in the transcript.

Use a local recording model to inspect the first and resumed requests. Block, allow, cancel a pending hook, and kill the process after completion is on disk. Check each call ID, the whole request body, and the relative position of additional user input. The legacy ACP loop also provides a control: it permits ordinary tool results without running the prompt hook on that round.
