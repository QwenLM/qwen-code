# npm 安装验收改为夜间运行

[English](2026-10-27-installed-acceptance-nightly.md) | [简体中文](2026-10-27-installed-acceptance-nightly.zh-CN.md)

## 问题与范围

目前 npm 安装产物生成任务及其四个原生平台分发任务在每次匹配的 PR 更新时都会运行，绕过了源码 TUI 影响分类器，甚至纯 Java 改动也会启动安装套件。2026-10-27 采样的五次成功运行中，产物生成任务排队中位数为 67.3 分钟、执行中位数为 8.8 分钟，每轮五个安装任务累计消耗 90.7–108.5 runner 分钟。这些样本说明调整调度的原因，不构成未来提速保证。

只修改现有 `tui-parity` 工作流的调度。保留全部安装断言、唯一产物依赖、原生平台覆盖、工具链版本、runner 路由和失败行为。不修改产品代码或发布自动化。

## 调度决策

- 增加每天一次的 `17 19 * * *` UTC 定时触发，对应下一个自然日的北京时间 03:17。GitHub 定时任务使用默认分支，可能因平台排队延迟，不保证准点启动。
- `installed-npm` 仅在 `schedule` 或 `workflow_dispatch` 时执行。PR 更新无论修改哪些路径都跳过。
- `installed-distribution` 继续依赖成功的 `installed-npm` 产物生成任务。上游跳过或失败时，禁止在缺少唯一产物的情况下启动消费者。
- 定时运行跳过影响分类器和两个源码 TUI 任务。保留它们现有的 PR 影响规则、分类失败仍执行的行为以及手动执行能力。
- 保留 PR 更新取消旧运行的策略及独立的手动运行。夜间任务沿用基于 run ID 的并发分组，PR 更新不会取消夜间验收证据。
- 沿用现有工作流和手动触发入口，不在另一个工作流中复制产物流转链路。手动触发会对所选 ref 同时执行源码 TUI 和安装验收。

## 取舍与运维方式

普通改动造成的安装回归可能延迟到下一次夜间运行才被发现，而非在合并前发现。夜间通过只覆盖当次测试的提交和产物，不覆盖后续变更。打包、依赖、启动器及私有 Bun、原生资源和启动兼容性均可能影响这些测试，即使测试代码本身没有变化。

对于高风险安装或运行时改动，维护者应在合并前对候选 ref 手动运行此工作流；发布前也应验证具体的发布候选。本次不自动化或强制新增发布门禁，不调整必需检查、不取消现有排队任务，也不声称覆盖公开已发布版本的升级。定时配置只有在工作流变更进入默认分支后才生效。

## 验证与验收

- 工作流元测试固定每日时间和安装任务事件白名单，保留 PR 及手动触发的源码门禁行为，排除夜间源码门禁，并保留分发任务仅在产物生成成功后执行的依赖。
- 确认更新后的回归测试针对旧工作流失败、针对调度变更通过。
- 运行现有工作流合约及 runner 路由测试、YAML 校验、格式检查、CI 预算和体积检查。产品构建及类型检查单独记录；不为验证调度而触发未修改的四平台产品验收。
- 审阅最终差异，确保没有改变测试命令、原生平台矩阵、唯一产物或工具链版本。产品行为不变，无需 UI 验证。
