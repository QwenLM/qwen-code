# 超大粘贴文本折叠为附件

[English](web-shell-paste-as-attachment.md) | [简体中文](web-shell-paste-as-attachment.zh-CN.md)

## 问题

Web Shell 的输入框会拦截粘贴进来的图片和文件，但从不拦截文本。带 `text/plain`
的粘贴会直接落到编辑器里，多长都原样插入，于是一段长粘贴就变成输入框里的一堵墙：
用户既看不清也改不动，自己敲的字还被顶出视野。

超长内联文本还会在后面的三个环节失败，而粘贴当下不会有任何提示。daemon 拒绝超过
10 MB 的请求体，所以发送会直接失败。回合中插入最多 16,384 个字符，所以一条长的排队
消息无法插进正在跑的回合。会话草稿只存文本、且写失败被静默吞掉，所以超大粘贴会在刷新
后悄悄失去可恢复性。

折叠并不减少模型看到的内容。上传的附件在建轮次之前会被还原成 prompt 正文，
所以两条路径最终都把内容交给了模型。收益在书写与传输，不在上下文。

## 行为

当被粘贴的那一段内容达到 200 行、或达到 8,000 个字符，且其 UTF-8 大小在附件上传上限
之内时，粘贴会折叠成一张附件卡片。更短的粘贴和今天一样内联插入。两个条件都以
**被粘贴的那一段**为度量对象，而不是粘贴之后的整份草稿：字符按字符串长度计，
行按换行数加一计。

有两种状态无论多长都保持内联：输入框被禁用时，以及正在编写 shell 命令时。
两者都没有可挂附件的 prompt——尤其是 shell 模式，折叠会静默丢掉 `!` 前缀，
把脚本当成聊天消息发给模型而不是执行它——所以两者完全保持今天的行为。
关闭了附件能力的主机是第三种豁免，理由相同：没有卡片可折叠。

8,000 字符这一条是刻意选的，不是随手取的。留在输入框里的单段内容压在
中途插入的 16,384 字符上限之下，因此仍然可以插进正在跑的回合。
那条上限约束的是**一条排队消息**，而不是整份草稿——几段各自低于阈值的粘贴，
或者一段粘贴加打字，依然可能超过它——所以这里的保证只针对单段内容，措辞不多说一分。
行数条件让规则对用户可读（“两百行太长了”），字符条件则是保住这条规则诚实性的兜底，
因为压缩成一行的内容可以有几个 MB。

超过附件上传上限的粘贴不折叠：那么大的附件根本发不出去，折叠等于把一个今天还能发出的
载荷变成发送时才失败的载荷。这条上限与拖入文件那条路径用的是同一个，于是同样大小的
粘贴和文件从此以同一种方式失败——留在输入框里，而不是变成一张传不上去的卡片。

卡片是现有附件芯片的加宽形态，和粘贴的图片、文件一起排在输入框上方。
它的标题取自**正文开头本身**——先把换行与连续空白折叠成单个空格，文件名承载不了的
字符也折成空格，再截短——因为这条标题同时就是附件的名字；这样首行只有一个词时，
标题依然是能读的一段话。第二行以卡片唯一的动作开头，大小紧随其后：**显示到输入框**。
选择该动作会移除卡片，并把全文以一次可撤销的编辑插入到光标处（仅限 CodeMirror
编辑器后端），卡片不再回来。
不选择它直接发送，则按附件发送。卡片同时保留既有的附件预览（点标题）与移除。

内容始终在用户手里：卡片是默认值，不是替用户做的决定；提交前后两个方向都只差一次点击。

粘贴替换选中文字时保持内联，以保留选区替换与撤销行为。命令判断同时检查原草稿与粘贴后的完整草稿：shell（`!`）和斜杠（`/`）命令无论是整段粘贴、粘贴参数，还是在已有命令前粘贴正文，都保持内联，避免折叠改变命令路由或丢弃参数。折叠的卡片也优先于待确认的跟进建议：折叠后草稿为空，而空草稿正是建议被提交的状态，所以提交发出的是粘贴内容。展开卡片的 CodeMirror 撤销步骤与前后编辑隔离。

## 设计

折叠产出的就是一个普通的粘贴文件：名字、媒体类型、正文，放进粘贴图片和文件已经在用的
同一个附件列表。芯片渲染、移除、预览、提交时上传、失败回滚、以及乐观消息回显都是既有行为，
原样复用；协议格式不动。

折叠粘贴的名字就是它自己的标题加 `.txt` 后缀，声明 `text/plain`，因此发出去的消息与卡片
显示的是同一条串。这个后缀是承重的，不是观感问题：桥接层按存储时的文件名反查类型，
没有它正文就会被解析成不透明二进制。标题同样被构造成能过附件名清洗器——文件名承载不了
的字符一律折成空格，而标题窗口恰好把一个星形字符切成两半时，那半个会被丢弃，因为附件
令牌要带着这个名字过 `encodeURIComponent`。

刻意不覆盖纯文本拖拽。从输入框内部拖出的文本和从别的窗口拖进来的文本，
在同一条路径上无法区分；折叠前者会把原文留在输入框里，同时为它的一份副本再建一张卡片。
本次增量承诺的手势是粘贴。

只有指向编辑器本身的粘贴才会被折叠。承载这条规则的处理器挂在输入框 surface 上，
而这个 surface 里还有自己接收文本的控件——今天的搜索框，以及将来宿主注入的页脚——
它们必须继续拿到属于自己的粘贴。

剪贴板同时带文本和图片时，保持今天的“文本优先”：文本被折叠（或内联），图片不被摄取。
折叠绝不改变哪种表示胜出。

这里的阈值刻意大于终端 UI 自己的大段粘贴阈值（后者把粘贴折叠成单行输入框里的
文本占位符）。两个界面优化的是不同的东西，而且彼此都无法 import 对方的模块，
所以各自持有自己的数值；把这条分歧写在这里，是为了让将来调参的人不会把它读成漂移。

不做 daemon 能力门控。今天 Web Shell 会连接的所有 daemon 都提供附件上传，
加门控只会引入一个任何受支持部署都走不到的分支。这个取舍的后果记在“风险”一节。

### 保留与草稿

折叠内容之后会怎样，取决于用户走到了哪一步，只有中间那一种情况需要写代码。

一旦 prompt 已提交，附件就已经上传并由 daemon 保存，所以刷新或重进会话都能从
daemon 侧取回。

如果发送失败或被拒，现有的回填路径会把 prompt 内容放回输入框，并把附件留在失败的
消息行上供重试。折叠出来的卡片是同一类对象，自动继承这两种行为。

在发送之前，卡片和今天的粘贴图片、粘贴文件一样，只活在输入框的内存里。
本次增量不为正文增加持久化：会话草稿只存文本，而持久化的附件存储已经在 daemon 侧存在。

未提交的卡片没有任何防刷新保护；而同等大小的内联粘贴过去能靠输入框草稿活过一次刷新，
所以对草稿配额以内的粘贴而言，这是一次真实的可恢复性下降，而不只是超大输入的边角情况。
`beforeunload` 确认提示是**考虑过并否决**的：它会对任何未提交附件都触发，
而不是只对折叠的粘贴；而且 Web Shell 自身有程序化的刷新路径，这种弹窗会打断它们。
丢失依然是有界的——内容来自粘贴，通常还在剪贴板上；而且刷新只会丢掉未发送的草稿，
绝不会丢掉 daemon 已经保存的内容。

把卡片的正文放回编辑器时，不得重新编码或重新上传：卡片与展开后的文本共用同一份内存副本。

## 范围与非目标

做：折叠判定与两个阈值、卡片的标题与大小显示、以及把内容移入编辑器的那个动作。

不做：纯文本拖拽的折叠；未提交折叠正文的持久化存储；刷新护栏；重复粘贴的内容哈希去重；
后缀嗅探；其它对话框内的粘贴文本折叠（定时任务的 prompt 有自己的编辑器和自己的限制）；
以及中途插入路由的任何改动。

中途插入入口保持原样。带附件的排队消息本来就不会显示 Insert，所以折叠后的粘贴
只是让这个入口消失，而不是在用户按下时失败。让插入也能携带附件是独立的增量，
且必须同时处理子进程侧那条 10 万字符的资源上限——它会把超大的插入内容静默丢弃。

## 风险

- **没有能力门控。** 在不支持附件上传的 daemon 上，发送折叠后的粘贴会失败而不是降级。
  这是刻意的接受：没有任何受支持的部署处在这个状态，而一个走不到的分支比一个有记录的
  取舍更糟。
- **折叠内容是会话级的。** 附件随会话生命周期存在与释放，所以恢复旧会话看到的是附件
  令牌而不是正文。内联文本没有这个性质，这也是“移入编辑器”这条单向出口必须显眼、
  必须便宜的原因。
- **不省上下文。** 两种形态最终都会进模型。期待折叠能保护上下文窗口的用户会失望。
- **阈值观感。** 一段紧凑的 150 行内容虽然没到行数条件，也会被字符条件折叠。
  卡片用内容本身作标题并显示大小——标题说明折进去的是什么，大小说明有多少。
- **未提交的卡片过不了刷新。** 输入框把它放在内存里，和粘贴的图片、文件一样，
  刷新丢弃它之前不会有任何提示。
- **展开后按撤销会丢掉这段内容。** 文本插入时卡片已经移除，所以撤销那一次编辑之后，
  内容两边都不在了。替代方案——跟踪这次插入、让撤销把卡片放回来——是本次增量不愿付的
  复杂度；内容来自剪贴板，重贴一次只需一个动作。
- **“一次可撤销”只对编辑器后端成立。** 移动端 textarea 上的插入是普通的受控值写入，
  没有应用级撤销步骤，原生撤销栈在那里的行为也未经验证。卡片同样已经移除，所以内容
  可能两边都不在。
- **提交 shell 命令会丢掉卡片。** 聊天模式折出的卡片能带进 shell 模式，而 shell 路径
  不携带附件，所以提交命令会把卡片清掉——既没发出去，也没有任何提示。粘贴图片和拖入
  文件今天就是这个行为，本次增量既没有引入也没有修掉它；记在这里，是因为折叠内容正是
  用户最不希望被无声丢掉的东西。

## 受影响组件与验证

- `packages/web-shell/client/hooks/useComposerCore.ts`：粘贴判定、折叠卡片状态、
  以及把正文移入编辑器的编辑事务。
- 一个新的输入框侧小模块：阈值、折叠判定、附件上限、卡片构造（名字、媒体类型、正文）。
- `packages/web-shell/client/components/ChatEditor.tsx`：卡片的标题、大小与它的动作，
  与既有芯片并列。
- `packages/web-shell/client/utils/imageIngestion.ts`：复用既有的附件名清洗、去重与大小上限。
- `packages/web-shell/client/i18n.tsx`：新增的卡片动作文案，双语。
- 每个被改动的文件旁配单元测试，另有一份带 PR 门禁标签的浏览器用例。

验证：单元测试覆盖判定边界（199/200 行、7,999/8,000 字符、单个超长行、结尾无换行的
文本、恰好达到与超过附件上限）、卡片构造与命名（含第二次折叠的去重）、指向 surface 上
其它控件的粘贴、选区替换与 `!`/`/` 命令判断、shell 模式、输入框禁用与关闭附件的豁免、
折叠卡片优先于待确认的跟进建议、"移入编辑器"是否是一次可撤销的编辑、
卡片的 size 文案（无 size 的卡片不显示）、触摸端 textarea 上的折叠与移入、
以及折叠卡片是否以附件形式进入提交载荷。
浏览器验证覆盖粘贴到卡片、短粘贴仍内联、以及移入编辑器；发送链路在 actions 层验证，
因为浏览器侧的 mock daemon 没有附件存储。
命令与结果见 `.qwen/e2e-tests/web-shell-paste-as-attachment.md`。

没有待定的设计问题。上面记录的后续项（插入也携带附件）是刻意排除的范围，不是未决的决策。
