# Mobile follow-up suggestion acceptance

[English](web-shell-mobile-followup-acceptance.md) | [简体中文](web-shell-mobile-followup-acceptance.zh-CN.md)

Status: implemented on `feat/web-shell-mobile-followup-acceptance` (PR #17918), revised through successive review rounds on 2026-11-20 (Tab key → action-word key → single chip bar → caret/slash key row → 240px wrap fix → grapheme/visual-line caret with held column and scroll reveal → bounded mirror measurement, wrap-end grapheme clamp, vertical-only column write, expanded-dialog surface, dismiss without focus).

## Problem

The touch composer (plain `<textarea>` backend, `(hover: none) and (pointer: coarse)`) renders a follow-up suggestion only as placeholder text. Desktop CodeMirror accepts it with Tab / Enter / Right Arrow, which fill the input without submitting; the touch backend has no equivalent gesture. Tapping Send with an empty input submits the suggestion directly, and typing a prefix then sending completes it, but neither lets the user edit the suggestion before sending.

Two earlier decisions shape this change. The mobile-composer-actions redesign removed the legacy simulated Tab/Esc/left/right keys because Tab did nothing on the textarea backend. #14220 removed the editing row's up/down history stepping because the history search panel is the touch recall path and a plain textarea restore cannot rebuild inline tag chips. History stepping is therefore not revived here.

## Design

One touch point, one accept path:

- **Suggestion chip bar** above the input row, in every composer variant: a chip-styled tappable button whose label is the suggestion text itself, preceded by an insert icon, plus a dismiss button. The editing row carries no follow-up-specific control; its → caret key doubles as the same accept (desktop ArrowRight parity).

The single chip emerged from three review rounds; later rounds added the caret/slash key row and the narrow-width wrap described below. The first revision added the bar plus an editing-row key labelled `Tab`; review noted touch users have no Tab key or Tab-accept habit. The second revision relabelled that key with the localized action word (`Fill in` / 填入 / Вставить); review noted a bare transitive verb still lacks its object and sits spatially detached from the suggestion content. The final revision removes the editing-row key entirely and gives the bar a chip container (subtle background, border, insert icon) so it reads as tappable without hover: the content is the label, the most understandable form, matching mobile suggestion chips elsewhere. The `composerMobile.fillFollowup` catalog keys were removed with the key.

A fourth review round added always-live editing keys to the editing row's trailing side (default variant, touch): ↑/↓ move the caret between the _displayed_ lines — soft-wrapped visual lines measured only around the caret with a cached mirror of the textarea's wrapping styles (one live mirror per textarea, removed on replacement and discarded on draft clear and composer unmount; binary-searched line tops instead of any per-grapheme rect loop over the draft; a grapheme step does not enumerate visual lines for the move itself, while viewport reveal may consult the cached mirror because programmatic selection alone can leave a far caret clipped (as the Chromium control demonstrates); a 20k/50k draft still avoids per-grapheme measurement of the whole document on a key press), falling back to logical `\n` lines when layout is unavailable — stepping and clamping at grapheme boundaries so a caret never lands inside a surrogate pair, with the wrapped line's content end taken at the wrap boundary itself (an explicit newline alone is skipped) and an empty next line keeping its zero-length boundary via the next-next line start sentinel, holding the preferred grapheme column across a consecutive vertical run (written only on vertical moves; cleared by →, /, draft edits and user selection jumps, with our own programmatic selection changes exempt from the jump reset), clamping to shorter lines and to the document edges at the first/last line, and scrolling the caret's line back into the height-capped scrollport; the last vertical move's landed displayed line anchors the next press, so repeated Up crosses a wrap boundary instead of re-selecting the same offset. → steps one grapheme right and doubles as the desktop ArrowRight follow-up accept only when the completion has an actual remainder over the draft — an exact-match draft falls through to the caret move, and the key's aria-label uses the same predicate — replacing the draft with the completion (telemetry method `right`); / inserts a literal slash, a character convenience because the textarea backend has no slash menu — command browsing stays in the add drawer. The keys ignore taps during IME composition, and caret-only moves never touch the draft or its persistence. They are absent in the simple variant and during voice capture, where the editing row does not render. History recall stays with the search panel: no stepping callback is revived, so the inline-tag-chip limitation that removed stepping in #14220 does not apply.

Adversarial review refinement: the mirror cache and the vertical anchor share a layout fingerprint (client width, the copied font/spacing metrics, padding, border widths and font readiness), so a width or font/border change cannot reuse stale visual rows. Ordinary and expanded callback refs preserve a `.current` view for existing focus/blur callers, but discard their own mirror and strong host reference on replacement or detach. A right grapheme step still skips visual-row enumeration; its bounded viewport reveal may use a measured mirror because native `setSelectionRange` alone was proven not to reveal a far caret in Chromium. Horizontal borders are added only to the mirror's outer border-box width, and reveal includes top padding so the last line enters the scrollport. The no-`Intl.Segmenter` fallback pairs a high surrogate only with an actual low surrogate.

Visibility: touch backend mounted, suggestion visible, draft empty, composer enabled. The chip hides as soon as the user types, matching the desktop ghost's prefix rule in spirit while keeping the touch surface draft-free. While the chip is visible the touch textarea keeps its ordinary placeholder, so the suggestion text appears on exactly one surface; an earlier revision also left it in the placeholder, which duplicated the text on screen. The expanded full-screen dialog is the one exception to the chip-only rule: the chip bar lives in the inline composer, so while the dialog is open with an empty draft the dialog's textarea carries the suggestion as its placeholder and aria-label (restoring the ordinary placeholder once the draft is non-empty), keeping the suggestion on exactly one surface in every layout. Desktop keeps rendering the suggestion as placeholder (empty input) and ghost completion (typed prefix).

Accept calls `onAcceptFollowup('tab')` without `skipOnAccept`, so the host's existing `onAccept → insertText` wiring fills the textarea and requests focus. Focus timing: the composer's outer click handler focuses the textarea synchronously inside the tap gesture first; the host's accept then defers the insert by a microtask (`queueMicrotask`) and re-requests focus after inserting. On real iOS the deferred insert's focus request may fall outside the tap gesture and the keyboard may not open — real-iOS keyboard behavior is unverified and out of scope. Dismiss calls `onDismissFollowup` and stops click propagation so the outer focus handler does not run: dismissing from an unfocused composer leaves the textarea unfocused and the hide-keyboard control absent, keeping the existing ignored-outcome telemetry. No new data path: the daemon sidechannel, controller, and insertText touch branch are reused unchanged.

Preserved fast paths: Send with an empty input still submits the visible suggestion; typing a prefix and sending still completes and submits it. The bar makes the first path discoverable without changing its semantics.

## Constraints

- 44px touch targets; the chip row occupies one 44px row only while a suggestion is visible, so idle layout is unchanged.
- The textarea keeps its 16px font (iOS focus auto-zoom rule); the chip is a button with 14px text, an insert icon and single-line ellipsis.
- The chip prevents mousedown default like the other composer controls, so focus is not lost before the gesture-driven insert; its aria-label combines the localized action with the suggestion text so screen readers get both.
- The old "no simulated keyboard keys" acceptance stays true: no follow-up control names a keyboard key or a bare verb; the editing-row keys are caret/character keys with live native meaning, not simulated accept/history keys.
- Editing keys pause during IME composition (compositionstart/end gate); caret-only moves do not modify the draft, so draft persistence and history-browse state are untouched.
