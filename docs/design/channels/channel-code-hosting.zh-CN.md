# 代码托管 Channel 适配器 — 设计

[English](channel-code-hosting.md) | [简体中文](channel-code-hosting.zh-CN.md)

## 概述

GitHub 轮询适配器让 AI agent 通过轮询通知 API 在 GitHub 上领取任务，并把 agent 的回复发成 issue/PR 评论。与 IM 适配器（实时 webhook/长轮询）不同，这个适配器按固定间隔轮询。

## 架构：通知只作唤醒信号

核心观察：平台通知是**线程级**且**可变**的 —— 任何活动（评论、推送、改标签）都会刷新 `updated_at`。通知不能当作可靠的逐条评论事件流。

因此通知只用作**唤醒信号**（"这个线程有动静"）。适配器随后通过平台的评论 API 枚举实际评论，用逐线程的水位线判断哪些评论是新的。

## GitHub：基于游标的评论窗口

### 通知与评论时间戳脱钩

一个关键的时序问题：**通知的 `updated_at` 与评论的 `updated_at` 是脱钩的**。

- `notification.updated_at` 会被线程上的*任何*活动（评论、推送、改标签）刷新，而且会有投递延迟
- `comment.updated_at` 反映评论实际创建或编辑的时间

这两个时间戳之间没有因果关系。通知可能比触发它的评论晚 16 秒才到，也可能被无关活动再次刷新。用通知时间戳来限定评论枚举会产生两种失败：

1. **重复回复** —— `PUT /notifications` 是异步的（202 Accepted），带 `last_read_at` 截止时间。服务端处理标记之前，bot 的回复已把 `updated_at` 刷到截止时间之后，于是该通知永远不会被标为已读。下次轮询会再次拉到它，并重复处理同样的评论。
2. **漏掉回复** —— 游标前进到 `max(notification.updated_at)`，可能越过晚到通知上的评论。这些通知最终到达时，它们的评论已落在游标窗口之下，被静默排除。

### 设计

正确性来自**基于游标的评论窗口**，而不是通知的已读状态：

轮询周期：

1. `GET /notifications?since={cursor-1s}` —— 发现未读线程
2. 保存 `windowSince = cursor.lastProcessedAt`（本次轮询推进游标**之前**的值）
3. `markNotificationsAsRead(maxUpdatedAt)` —— 尽力而为的全局标记（清理非 issue 通知）
4. 把全局游标推进到 `max(notification.updated_at)`
5. 逐线程：`listComments(since=windowSince)` —— 枚举评论（窗口要读游标所在那一秒时，从早一秒开始列，见下文）
6. 排除：bot 自己的评论；`created_at > maxUpdatedAt` 的评论（窗口之上）；`created_at < windowSince` 的评论，以及上一个窗口已读过的 `windowSince` 那一秒的评论，游标没有那一秒的记录时则是那一秒的全部评论（窗口之下）
7. 处理：检测提及 → 信封 → `handleInbound`

实际的评论窗口是 `(windowSince, maxUpdatedAt]`，游标记有那一秒时，外加上一个窗口没读过的 `windowSince` 那一秒的评论（见下文）。之前窗口处理过的评论满足 `created_at <= windowSince`（那个窗口的 `maxUpdatedAt`），都会被排除：更早几秒的由下界排除，`windowSince` 那一秒的由随游标保存的、上一个窗口读过的评论列表排除。同一窗口较早几轮（窗口被保持了多轮）接走的评论，由已接评论的去重环防止二次派发。无论 `PUT /notifications` 是否成功，这都能防止重复。编辑评论不会重新触发处理 —— 窗口归属只看 `created_at`。上一个窗口没读过的 `windowSince` 那一秒的评论，在游标前进之前每次读取都会重新判断，所以这段时间里编辑加上的提及会得到回复。

全局标记（第 3 步）仍会调用，用来清理非 issue/PR 通知、缩短未读列表，但去重并不依赖它。

### 游标所在的那一秒

GitHub 的评论和通知时间戳都精确到秒，而游标是推进它的那个窗口里最新通知的 `updated_at`。一条通知可能在那个窗口标为已读之后才到，却仍带着游标那一秒的时间戳，指向窗口没列出的线程上、同一秒的一条评论。如果下一个窗口从游标那一秒之后开始，这条评论在之后每次读取时都会被排除。

所以窗口标为已读时，游标会保存 `boundaryComments`：窗口读过的、创建于新游标那一秒的评论的键（node ID），以及窗口列出过且未被过滤的、通知属于那一秒的线程，各最多 500 个。下一个窗口会再读一遍那一秒，在处理通道处理之前只排除这些评论：那一秒里还没读过的评论会被处理一次，读过的不会再被接走。评论和通知一样从游标早一秒开始列，所以无论 GitHub 的 `since` 在边界上怎么取舍，那一秒都包含在内。带游标那一秒时间戳、而窗口没列出过其线程的通知是晚到的，可能指向这样的评论，所以有更新的窗口在等待标为已读时，它不当作陈旧的重复列出：读它时遇到 5xx 会保持那个窗口，直到窗口把这个线程读过一次；此后它又按陈旧处理，所以读该线程时 GitHub 还没列出的那一秒的评论，只有之后再读成功才会读到。线程已被列出过的那种，按标已读没生效的重复列出处理，仍像以前一样算陈旧；如果它带着窗口读过该线程之后、同一秒里新发的评论，读到该线程时这条评论仍会被读到，但遇到 5xx 时不会为它保持窗口。没有更新的窗口在等待时，本轮不会标记任何已读，所以在窗口读过这个线程之前，读它时遇到 5xx 不消耗窗口的重试预算，并记为 `failed`：这个线程会被再读一遍。

游标没有对应的记录时（由不含该记录的版本保存的游标，或这样的评论超过 500 条），窗口仍像以前一样从游标那一秒之后开始，带那一秒时间戳的通知按陈旧的重复列出处理；第一个游标是带毫秒的启动时间，不会与任何 GitHub 时间戳相等。去重环会保留创建于游标那一秒的评论的键，所以窗口一直被保持时，再次读到已被接走的那一秒的评论，也不会再接一次。这个列表只在游标前进时写入，并且只包含当前进程读过的评论，所以那一秒里有两类评论交给去重环处理，它们不会被再接一次（逐条接收评论的处理通道每个窗口记一行 `duplicate` 跳过；关注线程的批次则静默排除）：一是列表写好之后才接走的晚到评论，它的通知在游标前进之前一直保持未读，每轮都会被重读；二是在窗口被保持期间重启时，重启前接走的评论。

### 已知限制：通知晚到

因为游标是全局的（而非逐线程），在比评论 `created_at` 更晚的轮询中才到的通知，其评论可能被游标窗口排除。这需要通知投递延迟跨过一次轮询边界，**并且**期间另一个线程的评论把游标推过了它们。游标记有那一秒时，游标所在那一秒的评论会被再读一遍（见上文）；更早几秒的不会。实际中这个窗口很窄（通知通常在一个轮询间隔内送达）；用户可以重新提及来重试。

### 已知限制：PR 审查评论

`issues.listComments` 只返回普通的对话评论，不返回 PR 审查评论（针对 diff 某一行的评论）。PR 审查评论里的 @ 提及会被静默丢弃。请改在 PR 上发一条普通对话评论。

### 场景行为

| 场景                         | 行为                                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------- |
| 新线程（评论里 @bot）        | 出现（未读）→ 从游标起枚举 → 处理                                                     |
| 已有线程，新评论             | 再次出现（未读）→ 从游标起枚举 → 旧评论被排除在窗口之下 → 只处理新的                  |
| 晚到通知，游标那一秒         | 出现（未读）→ 从游标早一秒起枚举 → 上一个窗口没读过的评论 → 处理                      |
| 非评论活动（推送/改标签）    | 出现 → 窗口内没有新评论 → 跳过                                                        |
| 用户在 github.com 上标为已读 | 从 API 中消失 → 不处理                                                                |
| markNotificationsAsRead 失败 | 游标窗口仍能防止重复 → 不影响正确性                                                   |
| 标记已读后、处理完成前崩溃   | 游标未保存 → 下次启动重新拉取同一批通知 → 崩溃的那批会重新处理，不会丢                |
| Bot 回复了一个线程           | `updated_at` 被刷新 → 通知可能保持未读 → 下次轮询拉到它 → 评论被游标窗口排除 → 不重复 |
| 新 issue 正文里有 @bot       | 没有评论 → 正文包含提及 → 把正文作为触发（通过 `dispatchedBodies` 去重）              |

## PollingChannelBase

`PollingChannelBase<Cursor>`（位于 `packages/channels/base/`）继承 `ChannelBase`，提供轮询循环的基础设施：

- **轮询循环**：通过 `startPollLoop()`/`stopPollLoop()` 启停，由 `connect()`/`disconnect()` 调用
- **轮询间隔**：读取 channel 配置 `pollInterval`（毫秒），校验为有限正数，上限钳制为 86400000（一天），默认 60000。之所以要钳制，是因为 Node 会把超出 32 位范围的超时钳成 1ms，让循环变成忙循环；一天到该上限之间的值会被钳制而不是替换，以免之前生效的间隔被悄悄放大
- **游标持久化**：每次 `pollOnce()` 成功后原子地保存 JSON 游标；构造时加载（损坏或日期无法解析 → 回退到 `createInitialCursor()`）
- **游标校验**：`validateCursor()` 虚钩子 —— 基类拒绝非对象和数组；子类追加结构检查（例如 GitHub 拒绝缺失或无效的 `lastProcessedAt` 日期）
- **退避**：轮询出错时指数退避 2s → 30s，成功后重置
- **可中断睡眠**：以受保护方法 `abortableSleep(ms)` 暴露 —— 轮询间隔和错误退避都可被 `disconnect()` 打断

子类只需实现：

- `pollOnce()` —— 完成工作，修改 `this.cursor`
- `createInitialCursor()` —— 首次运行的默认值

`Cursor` 泛型可以是任何可 JSON 序列化的对象。GitHub 的游标包含 `lastProcessedAt` 和若干去重记录，例如 `dispatchedBodies`（首次接触正文的去重，限制为最近 500 条）和 `boundaryComments`（见[游标所在的那一秒](#游标所在的那一秒)）。

## 提及检测

基于正文、不区分大小写的正则。检测（`testBotMention`）和剥离（`stripBotMention`）是两个独立函数：

- 检测：显式的正则匹配，返回布尔值 —— 从不通过比较剥离前后的文本来推断（空白差异会造成误报）
- 剥离：只移除 `@bot`，保留其他所有格式（不合并空白）

## 会话范围

轮询适配器使用 `chat_thread` 范围：路由键 = `channel:chatId:threadId`。这能避免跨仓库的会话冲突（`repo-a/issue:42` 与 `repo-b/issue:42`）。

## 错误处理

投递是**尽力而为**的。`handleInbound` 失败时，每个线程每个轮询周期只发一条错误评论（随后 `break` 退出评论循环 —— 避免 N 条相同的错误评论）；用户重新提及即可重试。单条通知的 API 错误用 `continue` —— 一条失败的通知不会阻塞整批其余通知。没有 `subject.url` 的通知（Discussion、SecurityAlert 类型）会被静默跳过。

如果进程在处理中途崩溃，游标不会保存（只在 `pollOnce()` 完成后持久化），所以下次启动会重新拉取同一批通知 —— 但基于游标的评论窗口会排除已处理的评论，防止重复。

去重**不**依赖 `PUT /notifications` 成功。全局标记只是尽力而为的清理；游标窗口才是承担去重的机制。
