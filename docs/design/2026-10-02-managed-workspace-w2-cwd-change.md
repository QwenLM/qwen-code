# Managed Workspace W2: Controlled Same-Workspace cwd Change

[English](2026-10-02-managed-workspace-w2-cwd-change.md) | [简体中文](2026-10-02-managed-workspace-w2-cwd-change.zh-CN.md)

Research baseline: main `d5c22d336b` (2026-10-02); integrated onto the later merges #13138 (W1b, V31), #13135 + #13223 (bound close, V32), #13142 (D8a, contract v1.29.0, V33), #13194 (bound archive/delete) and #13112 (bound later turns) — the PR merges origin/main past all of them, and the migration renumbered to V46 after #13090 took V34, the tool profile took V35, the session-journal chain took V36–V39 (`V36` activation, `V37` event-type index, `V38` deferral marker, `V39` sequence index), the session-creator record plus the CSI chain took V40–V44, and the task journal took V45 meanwhile.
The target contract is [Workspace v1.12, section 4](https://github.com/doudouOUC/code_agent/blob/689121646cc25ca08a34508a5f5555ae15308833/qwen-code/feature/managed-agents/managed-agent-workspace-context.en.md) and the in-repo reviewed OpenAPI contract v1.27.0, which already pins the two `planned` routes and their schemas.

## Problem

A Workspace-bound Managed Session pins `cwdRelative` and `contextRevision=1` at creation (W0b). Nothing can change the directory afterwards: the W1 contract forbids it, and every legacy mutation route throws `workspace_unavailable` to a bound Session. The only escape today is to abandon the Session and create a new one, losing the conversation. W2 adds controlled, durable directory changes inside the same authorized Workspace: the operator's actor asks for a new relative directory, the control plane serializes that request against turns and lifecycle operations, verifies the target, and commits one atomic revision bump that later tool turns execute against.

Notes on the order and semantics:

- Rows 2–4 run in the admission service before the store transaction opens (the G0 parse-then-digest precedent): a lexical check consults no Session fact, so its error cannot leak one, and the digest it feeds already pins the replay semantics of row 8.
- The request digest covers `sessionId`, the fixed operation name, the **normalized** target directory and the expected revision (`RequestDigests` canonical SHA-256). A retry after the commit therefore replays the completed operation even though row 13 would now fail.
- Rows 5 onward run under the Session row lock; replay stays ahead of the revision and busy checks with the V17 binary-safe key comparison, exactly as the contract text demands; rows 6–9 mirror `beginLifecycle`'s invisible-caller and replay-first discipline.
- Creator-only matches the policy #13112 announced for later turns and the execution layer's own creator-grant recheck (`authorizePassiveAttachment` joins on the creation actor). Widening to non-creator Workspace writers is a separate admission decision. The refusal vocabulary for readable non-creators is `403 session_operation_forbidden` — the exact pairing the merged bound lifecycle (#13135's close, #13194's archive/delete) already ships; the first version of this design answered 404 everywhere and aligned with the sibling semantics at integration time. The settlement re-verifies the full grant set (`can_read` + `can_create` of the creation actor) at commit via `hasCwdChangeRegistryFacts`, so a grant revoked after admission still blocks the change.
- A target equal to the current directory is admitted and completes, raising the revision. It is a legal re-validation transition; rejecting it would add a branch that protects nothing.
- No event is appended at admission. The contract's only cwd event is completion's `session.context.changed`; the 202 body and the operation query carry the pending state.

The `admission_stage` is `JAVA_DURABLE` and `delivery_state` starts `PENDING` with `available_at = now`, so the existing claim and recovery scans pick the operation up. `session_status_before` records `ACTIVE` but is not consulted by the settlement.

## Settlement

`SessionLifecycleCoordinator.deliver` gains a `CWD_CHANGE` branch:

1. **Claim** through the existing generic `claimOperation` (RUNNING, LEASED, claim generation). A contended claim returns silently, exactly as lifecycle operations do.
2. **Deterministic settlement probe.** A new `WorkspaceRuntimeResolver.verifyInstallable(binding, targetCwdRelative)`:
   - mounts the binding's `(tenant, storageId)` through the administrator mount table, rejecting a missing mapping;
   - re-checks the mount's canonical path and `fileKey`, and runs the storage guard's mount verification of the **candidate** binding (target directory) when verified recovery is enabled, exactly as `resolve()` would for a real acquisition of that target;
   - runs the direct-question shape of the directory rule `acquire()` enforces: the acquire path keeps its long-standing boolean-predicate `requireDirectory` (every I/O anomaly terminal — an ENOTDIR-shaped cwd fails the Turn immediately with the accurate code, never a retryable mis-attribution), while the probe twin `requireDirectoryForProbe` probes with throwing calls — `readAttributes` with `NOFOLLOW_LINKS`, `toRealPath` identity, `checkAccess(READ, EXECUTE)` in place of the false-on-error `Files.is*` predicates — so the catch arms classify by the verdict: vanished target, permission denial and ENOTDIR/ELOOP structural shapes terminal (the last two reach some JDKs as bare `FileSystemException`, so the residual arm walks the ancestor chain — a plain-file or dangling/looping symlink ancestor is structural), only opaque blips (`ESTALE`/`EIO`, `ENAMETOOLONG`) retrying through the budget.
   - A structural failure is terminal for the operation: `failCwdChangeOperation` records `failure_code=workspace_unavailable` and the Session stays at its prior revision. Run against the **same host and mount snapshot the worker uses**, this probe has the same verdict the worker's installation verification would return — its guard runs against the _candidate_ binding through a probe-only guard entry (the shared acquire path keeps the terminal classification it always had), so a change away from a destroyed current directory stays reachable (the escape this feature exists for), and the shared directory rule carries the worker's own `access(R_OK|X_OK)` checks, so nothing passes here that the worker would later refuse as an untyped wedge. Structural probe refusals fold into the typed terminal verdict (re-issuable by the caller), and the refusal log carries the broker code, class, message and the preserved cause; a momentary I/O failure keeps its cause and retries through the delivery machine instead of certifying a verification that never happened — **bounded at 8 attempts** under the capped dispatch backoff, after which the change settles with the typed terminal failure: an accepted operation always terminates typed, the row leaves the deliverable set, and both admission barriers re-open with the Session unchanged and executable.
3. **Commit** in one transaction: lock the Session row; re-verify `ACTIVE` status, expected revision, no active Turn, no other open operation, and the binding-matching Registry facts plus the creation actor's surviving grants (`hasCwdChangeRegistryFacts` — the same passive-attachment subset; the full execution-time set including frozen profile refs remains the next turn's acquire-time gate); then update `cwd_relative` and `context_revision = expected + 1` with the usual `version` bump, mark the operation COMPLETED with `result_context_revision = expected + 1` and `receipt_id`, and append `session.context.changed` (`data: {sessionId, operationId, workspaceId, cwdRelative, contextRevision}`, camelCase per the store's event-data convention, source `operation:<id>:completed`). The committed-event publisher pushes it after commit through the existing SSE hub.
   - If the re-verified facts no longer hold — `context_revision_conflict` when the revision moved, `session_context_busy` when a Turn or another operation appeared, `workspace_unavailable` when the grant/registry facts changed — the operation ends as `failed` with that `failure_code`; the Session row provably keeps its prior context because nothing ran before this transaction.
   - Any other `RuntimeException` (transport, SQL, clock) retries through the existing `retryOperation` backoff, unbounded, matching the lifecycle contract that an accepted operation never silently dies.
4. **Reclaim** of a LEASED operation whose owner died re-enters the same branch: the probe is read-only and its verdict deterministic, so rerunning it is idempotent. Double-settlement is fenced not by that CAS but by the delivery machine itself: a settled row is `CONFIRMED` and unclaimable, and a stale owner's completion or failure write is refused by the lease/owner/generation/live-lease predicate — a contested completion returns `null`, a contested failure write is skipped (`failCwdChangeOperation` reports `false`). The probe leaves no ownership or worker footprint (it claims nothing and talks to no worker), so a crash can strand nothing — unlike the turn path, which by design may retain the storage lease pending W0e recovery.

`recovery_blocked` is dropped from the implemented `CwdOperationStatus` enum: nothing in this slice can emit it — every terminal state proves the prior context intact by construction, and the slice introduces no path that can observe a half-installed Session. Advertising an unreachable state to generated clients would promise recovery handling that cannot fire; the first slice that gains a producer re-adds the value then (the enum has never shipped `implemented` before this slice).

### Deterministic settlement probe

The reference design asks for Runtime and Harness installation receipts before commit. This slice deliberately scopes that down, and the deviation is safe to take because of verified properties of the merged architecture:

- Every tool turn acquires a **fresh** Runtime Session and installs the then-current binding before any tool runs (`installations` are keyed by Runtime Session ID; a same-Session re-install with a different digest is refused). The production receipt for the new context therefore exists before the first post-change tool executes, and its absence blocks that turn with `managed_context_unavailable` — typed, never silently in the wrong directory.
- The worker is same-host, same-UID, same mount snapshot as the control plane (enforced by `validateWorkspaceFiles` and the resolver's construction-time mount checks), and the shared `requireDirectory` carries the worker's own `access(R_OK|X_OK)` checks, so the Java probe verdict and the worker's install verdict coincide on the same snapshot; a later divergence can only come from the filesystem changing after commit, where it still surfaces typed at the first turn, never misdirected.
- Committing only after a Java-side deterministic check keeps the settled operation honest without inventing ownership-free access to the worker's installation route (which today exists only inside `acquire()`'s claim→install→activate chain, whose ownership claim may by design strand storage on an ambiguous crash — an unacceptable risk for a probe).

When deployments gain cross-host or containerized runtimes, the probe must become a real closed-gate install (own transport sequence, no storage claim) and this design's [boundaries](#boundaries-and-follow-ups) revisit it.

## Contract and DTO surface

`PublicCwdOperation` / `WebShellCwdOperation` differ from `PublicCommandOperation` (no `admission_stage`/`delivery_state`/`receipt_id`; adds the revision/target/failure fields), so the new DTO records land next to the existing ones rather than stretching the lifecycle record. Operation read-backs (`GET /{sessionId}/operations/{operationId}`, `POST /api/agent/web-shell/v1/operations/query`) branch on kind — the `ACTION_RESPONSE` precedent — and return the cwd shape for `CWD_CHANGE`; the store's `CWD_CHANGE` lowercases to the contract's `cwd_change` type constant. The store RUNNING state maps to the public `installing`; `PENDING→pending`, `COMPLETED→completed`, terminal refusal→`failed`.

WebShell requests carry `sessionId`, `idempotencyKey`, `cwdRelative`, `expectedContextRevision` in the body (camelCase, matching the controller's existing DTO conventions); the public route takes the Idempotency-Key header with a snake_case body, as the contract pins.

## Concurrency and races

- **Admission vs admission** (two cwd changes, or cwd vs close): serialized by the Session row lock; a losing cwd admission hits row 8's replay or row 14's `session_context_busy`, and a losing lifecycle admission hits `requireNoOpenOperation`'s `session_operation_active`.
- **Admission vs Turn**: row 14's `hasActiveTurn` covers an active Turn, and the op side sees pending mutation commands as busy. In the reverse direction, this slice itself adds the handshake the merged #13112 needs: bound later-turn admission (`insertTurnCommand`) counts open **context-changing** operations (operation rows, excluding `ACTION_RESPONSE`) under the same Session row lock and refuses `session_context_busy`, so a Turn can never slide in underneath one — while a stuck display mutation (a killed rename) or an in-flight permission Action can never wedge Turn admission, the Session's only re-acquire path. The cwd admission and the settlement re-check keep the wider `hasOpenOperation` barrier on purpose: an unsettled mutation or a requested permission Action disputes which context is current until it resolves, and committing under that dispute would certify a certainty that does not exist. The price is documented honestly: a stuck PENDING rename row is never cleared by any scheduled scan (its only owners are the same-key replay and `abandonSessionMutation`), so it holds the barrier forever — a deliberate trade the Turn barrier does not make, because Turn admission is the Session's only re-acquire path.
- **Admission vs cancel**: a cancel is real work only while a Turn is active (`commandEffect` false otherwise), and an open operation gates any Turn, so a cancel admitted while a cwd operation is open is a completed no-op insertion — it cannot disturb the commit, which re-runs its fact checks afterwards anyway. The earlier version of this bullet promised a typed refusal such a cancel would produce; the shipped and pinned mechanism is the benign one.
- **Probe vs commit**: the probe is read-only and needs no storage lease; the commit transaction re-checks every fact under the row lock, so a grant revoked or a Turn admitted between probe and commit fails the operation cleanly instead of committing.
- **Crash windows**: admission-insert is one transaction; probe+commit has no footprint to strand; the commit is atomic with its event; reclaim re-runs the branch idempotently.
- **Post-commit execution**: the next turn's `acquire` re-resolves the binding, claims storage, installs and activates the new context on a new Runtime Session, asserting ownership afterwards. A leaked pre-commit Runtime Session cannot execute — execution requires the ACQUIRING/READY record state that release closes, and an unsettled one keeps the Turn that owns it `RUNNING`, which blocks admission at row 14.

## Acceptance criteria

- 202 acceptance is durable: Java restart at any window resolves through the original operation — completion is observed at most once, and a lost response retries to the same operation identity.
- A change that names a missing/aliased target directory fails the operation with `failure_code=workspace_unavailable` and leaves the Session's binding and revision unchanged and executable.
- The commit is atomic: reads before it observe the old `(cwd_relative, context_revision)` pair, reads after observe the new pair, and post-commit tool-turn acquisition installs exactly the new binding on a fresh Runtime Session (proved at store/transport level and end-to-end in the hosted IT: a bound later Turn after the change writes files only into the committed directory).
- Input/cwd races admit exactly one side (row-lock serialization), pinned in every reachable direction: cwd-vs-cwd admits one, the op admission refuses while an input Turn is active (`session_context_busy`), the settlement's commit-time re-check refuses one that appeared in flight, and a bound later Turn is refused while an operation is open (the #13112 handshake).
- The contract's planned routes and schemas become implemented with no drift-test or pin regressions, and existing lifecycle/permission operations are byte-identical in behavior.
