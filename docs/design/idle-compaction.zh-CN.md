# 空闲期自动压缩

[English](idle-compaction.md) | [简体中文](idle-compaction.zh-CN.md)

状态：提案（issue #16508）。尚无实现；本文固定设计，使实现 PR 拥有可评审的契约。

## 为什么

当前自动压缩在 `chat.sendMessageStream` 内部触发（`llm-chat.ts:3537`、`:6531`，
有效提示估算越过 `autoCompactThreshold` 时）。摘要往返落在**回合中**——用户刚
发出请求，却要为一件与该请求无关的工作等 30–60 秒；且阈值触发偏晚，会话长期
贴近上限运行，压缩输入在其最大时刻才被处理。

在用户空闲时压缩，把这段延迟移到无人经历它的时刻，下一个提示到达时面对的
是已压缩的会话。提供商对话缓存寿命约一小时级；下一次缓存重建以压缩后的
前缀——而不是近上限的前缀——计价。

## 设计

### 触发

两个条件均可配置，**同时满足**才触发：

- 空闲 ≥ `context.idleCompactionMinutes`（默认 `5`）；缺省或 `0` 即禁用；
- 有效提示估算 ≥ 软水位 = `context.idleCompactionWatermark`（默认 `0.7`）×
  生效的 `autoCompactThreshold`。

估算复用回合内检查的同一套记账，两个触发器对"满"的判定不会分歧。水位低于
`1.0` 留出余量：空闲压缩若被打断，回合内路径仍是不变的兜底。

空闲检测站在客户端现有空闲状态（`use-program-status`）之上；core 只收到显式
的"空闲心跳"调用，core 自身不携带定时器。

### 动作

空闲心跳以新的 `PreCompactTrigger` 种类 `idle` 调用现有
`ChatCompressionService.compress`。下游一切——缓存共享门、历史处理、通知、
遥测——都是现有手动通道的机器；新增的只有触发种类（及以其为键的通知文案）。

### 并发提示

压缩进行中到达的提示**不被取消**、也不与摘要竞争：新回合等待该压缩
promise，与今天回合内变体的调用方同语义。压缩本身走侧查询路径，从不阻塞
提示的准入。

### 范围排除

Headless/SDK 运行（`runNonInteractive`）与 hosted/managed 会话整体禁用——
它们的"空闲"没有可返回的操作者，其回合内的记忆排空由 #13885 单独负责。
本提案只覆盖 CLI 交互会话。

### 通知

用户下一次交互时，标准自动压缩通知以 `idle` 原因渲染。无新界面；按触发
种类为键的现有通知路径直接承载。

## 非目标

- 不改微压缩、记忆提取或压缩算法。
- 不做提供商专属的缓存固定或预热调用。
- 本切片不含 hosted/web-shell 等价物（issue 待定问题 3）。

## 验收标准

- 空闲 ≥ 阈值且用量 ≥ 水位：每个空闲周期恰好压缩一次；同一空闲周期内的
  第二次心跳为空操作。
- 空闲时用量低于水位 → 不压缩、无通知。
- 空闲压缩进行中提交提示：等待其完成并观察到已压缩历史；不重复压缩。
- 配置禁用 → 行为与今天完全一致。
- Headless 与 hosted 会话永不触发。
