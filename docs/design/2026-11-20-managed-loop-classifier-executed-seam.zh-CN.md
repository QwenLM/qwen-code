## 问题陈述

managed-agent E2E runner 在每个 fake 模型回调内部回答 `cron_create` 的准入侧查询。接缝画在 `blockProperties`：schema 查找、收窄、门与 answer 站点全部内联在 fake 里，故快速测试唯一能断言的是它们的**形态**。一个手写 AST 扫描器为该形态做库存，而 #17594 的十四轮评审大部分花在「新实测出一个兄弟形状绕过扫描器之后再扩展扫描器」上。

该 evasion 面按构造就是无界的。任何「写同一个值、或发同一个答案，但不按扫描器寻找的拼写来写」的方式都能击败它。第 13、14 轮实测出八个这样的兄弟并逐个关闭——shorthand 的 `toolCalls` 键、shorthand 的 allow 键、值为「曾初始化为 `false` 的绑定」的 allow、rest 解构写入、带括号与带类型转换的赋值目标、for-of / for-in 初始化器——而每次关闭都是又一份以另一种拼写为键的库存。残留已有记录：以 `!true` 或 `Boolean(false)` 算出的 allow 不拼写 `false`，任何拼写库存都看不见它。

同一根因还带来两项代价。两条臂携带**除 call id 外逐字节相同的判定块**，故对一条臂的修复可能静默漏掉另一条。而扫描器自身的「非空转」必须靠一个敌意控制来证明，该控制在 `8dd9567685^` 上占 259 行，其中含 10 处 `fakeToolCall(` 构造与 14 处 `respond_in_schema`——这份夹具的唯一用途就是显示扫描器没有闲着。

## 拟议改动

### Runner：一个被执行的判定，两条委托的臂

在 `classifierBlockAnswer` 旁新增顶层纯函数：

`loopClassifierResponse(body, callId)` 对 block-schema 侧查询返回整个 fake 响应，请求不是该查询时返回 `undefined`。它执行 tools 提取、`respond_in_schema` 查找、properties 读取、经 `classifierBlockAnswer` 的收窄与门，并用 `fakeToolCall` 构造响应。两个 fake 把各自的内联块替换为委托：函数结果有定义就返回它，否则完全按今天的方式继续往下。

该函数为顶层，故既有 `extracted`/`load` 机制无需改动即可触达；`fakeToolCall` 作为依赖注入，与 `waitUntil` 注入 `inspect` 的方式相同。

### 元测试：执行判定，退役形态库存

新增一个被执行的测试，用敌意 body 驱动 `loopClassifierResponse`，断言**整个响应**——工具名、call id 与 arguments 载荷一起——或 `undefined`。敌意方向：阶段 1 与阶段 2 的 block schema；三种非 block 侧查询（title、tool-use summary、next speaker）；缺失、非数组与畸形的 `tools`；名字不是 `respond_in_schema` 的 schema 工具；多个 schema 工具而非 block schema 排在 block schema 之前，故首匹配胜出、后面的 block schema 不会补救；畸形的 `tools` 元素与非对象的 `properties`，必须落穿而非抛错；以及两个 call id，断言响应携带的就是传给函数的那个 id。每条臂各传哪个 id **不判**——见下文钉的范围。

退役 `loopClassifierWiring`、`loopClassifierScope`、写入者名集与目标包装集、钉测试里的十条分类器断言、敌意控制与隔离 allow 站点用例。保留钉测试中一切与分类器判定无关的内容，并保留独立的 minted-id 面（`mintedIdWiring`、`mintedScheduleId`、fake-createdId 钉）不动。

以一条**有界**钉取代被退役的库存，由一个逐子句命名的判据裁定，并由一个敌意源控制逐子句执行见证。它只问两次委托坐在哪里——四条子句，且不枚举「什么东西可以围在调用旁边」：

- 恰好**两处** `loopClassifierResponse(` 调用；
- 各传一个**可解析为字面量**的 call id——内联、折叠、带标注、常量绑定皆然——且两个 id **互异**；
- 委托的**最近外层函数就是该回调本身**——回调是传给 `startFakeOpenAIServer` 的那一个，按解析而非匹配认定：内联箭头、提升的 `const`、具名 `function` 声明皆然。回调只是「声明」出来的闭包不算回调本身，无论承载它的是哪种成员或绑定；
- 两者位于**互异**回调，故一个 fake 不能同时服务两条臂。

每条子句都有一条实测能通过了它所取代的更弱形态的敌意用例。正向对照携带等价改写——臂顺序、id 互换、各种门的拼写、提升或按引用传入的回调、额外包装 flag、折叠或带类型标注的 id——**以及本轮采样到的那些被退役库存的形状**，它们在这里按决定为绿——该清单是采样，不是对已退役子句所能判定的一切的枚举。传的是**哪两个** id 不判：全仓实测 runner、CLI 与 Java 侧都没有按它们筛选的逻辑，故一致地改名两个 id 是保行为改写，必须保持绿。

### 该钉有意不覆盖的部分

十一轮评审量出了「让快速结构钉去判超出落位的东西」会发生什么。每轮关闭一个缺口就生出下一轮的发现，两个方向都是，直到钉达到 **518 非注释行——超过本改动退役的 309 行扫描器**——却仍放行不工作的接线、拒绝输出相同字节的改写。第 11 轮实测五种假绿（`calls['push'](<手搭>)`、`[calls] = [[…]]`、`for (calls of …)`、名为 `toolCalls` 的 getter、成员别名 push）与六种假红（无关 `...extra`、`calls.sort(cmp)`、`splice(0, 1)`、计算字面成员键、可归属的成员赋值、无关的计算键写入）。十一种在做决定前全部复现。

因此应答库存与写入归属**已退役**，以下明确不由快速钉覆盖。判定的值由被执行的判定测试承担；接线行为由打包 `/loop` 臂承担。

| ----------------------------------- | ---------------------------------------------------------------------------- |

| 构造之后才建的应答                  | `calls.push(<手搭>)`、`Object.assign`、`Reflect.set`、任何键拼写下的变异方法 |

| 名为 `toolCalls` 的 getter 或类字段 | `{ get toolCalls() { return [<手搭>] } }`                                    |

| 门的存在、拼写与极性                | `if (classified === undefined) return classified;`                           |
| 门之后的 fall-through               | `return classified;`、直接返回调用                                           |

**这些里只有三行有打包臂实测结论，其余各行没有裁决。** 只改 skill 臂的委托实测：「丢弃判定结果」与「吞掉 fall-through」各自让打包 skill 臂**失败**；「委托前写入请求 body 的 schema」**通过**，故该行两条通道都不覆盖。durable-failover fake 里的应答根本不被 skill 臂行使。表中其余每一行都**未经臂验证**——快速钉不判它，也没有为它跑过臂。它们按「不覆盖」列出，不并入「由臂承担」的说法。

别名链的环守卫是**终止**条件而非判定子句：删掉它会让解析不终止，而不是改变裁决，故没有隔离夹具；链式遍历本身由两跳正向对照见证。被别名的 `startFakeOpenAIServer` 被调名按拼写匹配，读 `in-fake-callback`——又一条被接受的误红，因为导入绑定不在本文件的声明表里。

解析保持 fail-closed：解析器无法归约到唯一函数的回调实参——`flag ? a : b`、有歧义的名字——不登记任何东西，故这类接线读作 `in-fake-callback`，而不是猜。

id 解析继承与回调解析相同的作用域盲区：调用后被重新赋值的 `let`、或另一块中的同名绑定，都会解析到被计数的那个声明，而不是作用域内的那个。

另有两条**误红**被接受并点名，都来自解析而非包含：声明计数是全文件的，故两条臂各自在块内提升同名回调（两处 `const cb`）读 `in-fake-callback` 与 `distinct-callbacks`；被调方按名字匹配，故经别名调用判定（`const alias = loopClassifierResponse; alias(body, …)`）读 `call-count`。作用域感知解析与被调方解析正是退役移除的那套 machinery。

包含规则带来一条**误红**，在此点名而不是留待日后发现：把委托抽进「回调会调用的 helper」（`const g = () => { … }; return g();`）读作 `in-fake-callback`。该规则问的是委托落在哪里，而不是回调调用了什么；追调用正是已退役的数据流家族。此前的规则——向外遍历、在四类类成员处停下——实测会放行同一闭包的另外四种写法（对象字面量箭头属性、带括号的类字段、普通嵌套箭头、嵌套函数声明），却判红它们的方法与字段兄弟。一个包含问题用更少代码闭合全部四种，且没有种类需要枚举；helper 抽取就是它的代价。

快速钉是对落位的廉价冒烟检查；它不是判定的第二份副本，也不是打包臂的替代品。

## 关键设计决策

- **一个按 call id 参数化的函数，而非两份副本。** 两个块除 id 外已经相同；复制它们正是「修复到达一条臂而漏掉另一条」的成因。参数化还让「一条臂在另一条的 id 下作答」成为被执行测试可断言的方向。
- **返回整个响应，而非只返回 answer。** 只断言 answer 会让工具名与 call id 无钉，而分别钉它们又会重演分散断言此前暴露过的映射弱点。对响应做一次深比较即钉住映射。
- **保留落位钉，去掉判定库存与数据流子句。** 快速套件跑不了打包臂，故「fake 确实从正确的位置委托了」需要一条廉价断言。无界家族住在判定**内部**，执行判定把这一家族直接消除。随后三轮评审表明：用 AST 去判接线的**数据流**，等于把同一家族上移一层重新踏入，故该钉止步于落位，行为归打包臂。
- **退役扫描器，而非留作「第二意见」。** 一个行为两套守卫会互相漂移，而扫描器的维护成本正是本次要移除的东西。其历史记录留在 #17594 设计文档里。
- **`undefined` 保持其确切含义。** 它表示「不是 block 侧查询，继续走 fake 的其余部分」。委托不得把它转成响应，也不得吞掉继续往下的路径。该不变式由被执行的判定测试与打包臂承担；快速钉不再声称检查它。

## 三轮评审，以及它们指向哪里

下面每个形状都在动手之前，用当时已提交的判据在真实 runner 文本上实测过。已提交的 runner 始终读作 `[]`。

**第 1 轮**（PR 上的 bot 评审）在第一版替换钉里找出六条：漏判手搭与计算名应答、伪造 body 实参、重写写入、类成员内的 return、停在别条臂 fake 里的委托、被吞掉的 fall-through；同时把六种保行为改写判红——臂块顺序、id 互换、nullish 兜底返回、倒置的 undefined 门、箭头常量判定、以及合法第三个 fake 应答 title 查询。

**第 2 轮**（17 agent 本地评审）在修正后的钉里又找出六条：十一种非裸写入拼写、被别的绑定的门豁免的 return、被重写或遮蔽的 `body`、被判成缺陷的五种等价门拼写、别名，以及——按打包臂证据推翻的——第 1 轮对直接返回的接受，该形式无论裸写还是加 `??` 兜底都让 skill 臂失败。

**第 3 轮**（17 agent 本地评审）在**那些**子句里再找出十一条：`delete` 与原地 API 写入、返回别的绑定的第二个门、被嵌套 `if` 借走的臂 flag、绑定名的块级遮蔽、交换律的 `undefined === classified`、被判成缺陷的非包围 `body` 遮蔽、从错误分支返回、以及在下一层闭包里构造的应答。零 Critical；无方向审计直接点破了成因——接线钉已变成对无界改写空间的手写语义分析。

第 3 轮里有两种形状属于落位缺陷而非数据流，缩小后的钉又保留了它们八轮：被借走的臂 flag，与下一层闭包里的应答。第 12 轮把两者连同它们所属的库存一并退役——臂 flag 已完全不读，调用旁边也不再枚举任何东西。其余即上面列出的已退役数据流检查。

第 3 轮之后由维护者拍板：停止让钉继续长大，把它缩到落位。两项实测支撑该决定：缩减前的钉按当时口径约 370 行 AST 分析，守的却是两行委托；且每一轮的修复都生出了下一轮的发现。下一句里的 **370** 是另一个对象：被退役的扫描器按 AST 口径在 `8dd9567685^` 上实测为 **370 行 / 309 非注释**（`loopClassifierWiring` 345/284 加 `loopClassifierScope` 25/25）。两个数字不是同一次测量；缩减后的第 3 轮钉按下文 AST 口径为 161/141。**行数按版本分别标注，因为第 4 轮又把它撑回去了。** 口径：`classifierDelegation` 与 `delegationViolations` 各自**整条 `const` 变量语句**之和，边界取自 TypeScript AST 的语句范围；「非注释」指非空且不以 `//` 起头的行。第 14 轮把 `unwrap` 提到模块作用域以便 `literalText` 共用，这把 14 行（14 非注释）移出该跨度但没删除任何逻辑；下文把它加回，使数字仍可比。按此口径，第 3 轮提交 `d1ebe200b2` 上是 161 行（141 非注释），`59857272fc` 上 297 行（254），`6fef090d01` 上 312 行（267），第 5 轮提交 `dd77c9387e` 上 390 行（356），第 6 轮回归修复后 403 行（363），第 11 轮后 609 行（518），第 12 至 15 轮退役库存、统一包含规则、移除期望 id 子句并解析 call id 后**交付版 149 行（128 非注释）**——两个 helper 135/114 加共用的 `unwrap` 14/14。第 4 至 11 轮的增长都花在消除误红与闭合绕过上，而每轮的闭合都生出下一轮的发现；到 518 非注释行时，钉已超过它替换掉的 309 行扫描器，却仍在两个方向上判错，这正是逼出第 12 轮决定的事实。128 非注释行不到该扫描器的一半，故缩减的成本论据重新成立——按交付版，而不是按第 3 轮那版。扫描耗时**不承重**：单独跑 `classifierDelegation` 七次，本机中位 92.7 ms、区间 81.6–174.5 ms，离散过大，故只把行数当作成本引用。

此前有一条变异存活，已归因而非掩盖：要求门分支内每条 return「读取该绑定且不得读别的」没有隔离夹具，因为它会误红 `return classified ?? other`——门内的死兜底。它被移除，而不是用硬造的夹具去佐证一条会把正确改写判成缺陷的规则。那正是第 3 轮在更大尺度上确认的同一信号。

## 评审第 4 轮：落位也犯了同样的拼写毛病

以下第 4 至 11 轮是**历史**。它们描述的子句已被第 12 轮退役，夹具随之一并移除，只有解析 helper 留存。保留这段序列，是因为它本身就是退役决定的证据，而不是因为其中任何子句仍在交付。各轮的现在时态指该轮当时的状态。

对缩小后的钉再做一次评审，返回 0 Critical、6 条 Suggestion。其中两条针对记录本身而非判据：一条正向对照列了记录判定为破坏行为的形状；一处拼接产生的收尾花括号吞掉了下一个测试的起始注释。一条针对被执行测试：把 payload 当预序列化 JSON 字符串比较，钉住的是答案的**键插入顺序**，故把 `classifierBlockAnswer` 的三个键换个顺序就会让保行为改写变红；现在 payload 解析后再比较。

另外三条量出落位子句里的绕过与误红，全部先复现；各轮总数不在此复述，因为它们从未按同一口径重测。五种误红——臂 flag 改名、请求绑定改名、提升的 cron 数组、闭包包裹的委托、按引用传入的回调——**已全部消除**，因为落位改为解析而非匹配。绕过闭合了六种：计算式 `toolCalls` 键、三种构造后成员写入、同一臂 flag 下两个 fake、fire 块嵌在 skill 臂内。其余两种已补进上面的「不覆盖」表。body 写入那条随后跑了打包 skill 臂，结果**通过**，故记为两条通道都不覆盖，而非「臂兜底」；要闭合它需要别名追踪，属已退役的数据流家族。

有一处早先的归因是错的，在此更正：第 3 轮把 fake 臂多重集当作「arm-scoping 的第二份副本」删掉了。第 4 轮「同一 flag 下两个 fake」的形状表明它不是——两次委托的臂可以看着正确，而两个 fake 的臂并不正确。该检查已恢复，并以该形状作为其隔离夹具。

## 评审第 5 轮：统一「臂」的定义

第 5 轮返回 0 Critical、5 条 Suggestion。其中三条针对记录与诊断而非判据：一处注释仍在论证删掉记录已恢复的 fake 臂集合检查；行数与耗时口径描述的是第 3 轮的钉而非交付版；变红只报子句名、没有文件/行号/源文本，相对本改动删除的扫描器是退步。现在每次命中都带行号与文本，钉把它们作为断言消息传入——并按与判定相同的臂集合过滤，故消息不会点名钉并不判定的 fake。

另外两条延续的是第 2 轮开的那两个线程——**R2-1**「钉接受了它自己的子句声称禁止的接线」与 **R2-2**「保持行为的改写把钉判红」——共七种绕过与七种误红。十四种全部先复现，而它们有**同一个根因**：钉保留了两套臂定义——委托取最近 flag、fake 取最外层——且在遍历过程中就过滤库存，那时臂集合还不存在。把臂统一到 fake 的调用点、并把过滤移到第二遍，一次消除了全部七种误红；其余绕过由上面列出的解析逐项闭合。十四种都成了提交夹具（七敌意、七正控制），已提交 runner 仍读 `[]`。

第 6 轮评审找出**一条 Critical，且是第 5 轮引入的回归**：统一臂查找时，把应答库存也一并放到了委托探针的成员边界之后，于是「建在 fake 自己声明的类成员或对象成员里的应答」不再被清点。同一份 runner 文本实测：对象字面量方法、类方法、对象 getter、类构造器四种在 `dd77c9387e` 上都读 `[]`，而在 `59857272fc` 上同样四种都报 `no-loop-answer-site`；箭头闭包与内联两个对照在两版上都报红。现在两个问题用两次独立查找——库存问「最近的 fake」不带边界，委托探针保留边界——且两个方向都有见证：把边界还给库存会让四条新成员用例变红，把边界从委托探针拿掉会让既有的「委托停在死成员」用例变红。

第 8 轮对保留的落位子句给出一条 Critical：七种实测「接线不成立」的形态读 `[]`，三种保行为改写被判红，而记录对其中几条声称相反。这十条里，五条属有界的解析不足并已修复，三条在下文披露，另两条在该 head 实测不成立（见第 9 轮段落记录的更正）。五条修复各配一条提交夹具与只删除它的变异：

- **声明之后被写入**的提升数组（`calls.push(<手搭 allow>)`）在声明处被枚举而放行——相对本改动删除的扫描器是回归，因为同一写入经成员就会被判红；
- 键以**名字**传入的原地写入器（`const KEY = 'toolCalls'; Reflect.set(answer, KEY, …)`）未被解析；
- 以 `X === false` 测试的臂 flag 被记功，于是永不运行的臂算作已接线；
- `ids.map((id) => fakeToolCall('cron_list', {}, id))` 被判红，尽管它与内联数组产出相同字节；
- `loopClassifierResponse(body!, …)` 被判红，尽管断言不改变实参。

另有三条**披露而非追逐**，因为闭合它们要追踪身份或位置、而不是解析名字：臂集合由委托自身的 flag 推出、委托在回调内的位置不被判定、名为 `body` 的 rest 绑定被记功。三条在该轮都带实测 `[]` 进了不覆盖表；第 12 轮退役把臂 flag 与来源子句整条删除，故今天的表里只剩「位置」那一行。记录里 fail-closed 与解析相关的句子已收窄到代码现在的行为，任何声明都不宽于其背后的实测。

第 9 轮验证量出第 8 轮修复里的五处缺口，以及本记录中一处错误声明。全部先复现再修，各配提交夹具与只删除它的变异：

- **解构声明**（`{ const { toolCalls } = makeCalls(); … }`）不绑定任何被计数的名字，shorthand 仍解析到提升数组；现在绑定模式所绑的每个名字都计数；
- **一个绑定 hop 之外**的不可归属写入（`const alias = calls; alias.push(<手搭>)`）被接受；不安全标记现在沿别名链回传；
- 以**字面量拼接**拼出的原地键（`Reflect.set(answer, 'tool' + 'Calls', …)`）被接受；`literalText` 现在折叠字面量拼接，该键指向同一成员；
- **合法的 push 构造** cron 应答（`const calls = []; calls.push(fakeToolCall('cron_list', …))`）被拒；写入规则现在区分「不可归属的写入」与「只添加字面名调用的写入」，后者继续被接受；
- **带引号的** `body` 键（`({ 'body': body })`）被判 `argument-provenance`，尽管它绑定同一属性；现在键按标识符或字面量读取。本记录此前声称它读 `[]` 且不记功——该声明是错的，第 8 轮回复对评审的「更正」也一并错了；
- **以箭头初始化的类字段**被记功，而同位置的类方法不被记功；类字段现在也是成员边界。

歧义路径也改为保留首个初始化式而非置空，因此拒绝第二次声明的是声明**计数**这一子句，而不是丢弃初始化式的副作用；删掉计数检查现在会让套件变红。

第 10 轮验证又量出三项，均先复现：别名污染只从别名传向其源，因此「写入数组、返回其**别名**」被接受；**计算字面量** `body` 键（`({ ['body']: body })`）被判红，尽管绑定同一属性；写入归属规则里有三个判定没有提交夹具，删掉任一套件仍全绿。现在污染双向传播至不动点、计算键被读取，而那三个判定——新增数组元素的字面名要求、映射数组的接受、标量元素的同一要求——各有提交夹具与只删除它的变异。

第 11 轮处理的是第 9、10 轮写在**评审正文**而非行内线程里的延后清单。四项可测量并已闭环：经**读不出的元素键**触达的变异方法（`answer[KEY].push(<手搭>)`）此前被接受，现在 fail-closed；变异与原地集合里五个成员（`unshift`、`splice`、`fill`、`copyWithin`、`defineProperties`）没有提交夹具，删任一套件仍全绿——现在各有一条；五条**落位**子句任一判红时断言消息为空，因为只有库存命中记站点，现在委托调用点也暴露并拼进消息；记录里「经 body 链本身的写入会判红」过宽——实测判红条件是链中带**元素下标**（点号或括号皆然），无下标的链不会。

两条被延后的说法经实测不成立，按更正处理而非修复：`distinct-callbacks` 被报为无法单独触发，但删掉它会经其隔离夹具让套件变红；被退役扫描器的「约 370 行」被报为从未重测——在 `8dd9567685^` 上实测恰为 370 行 / 309 非注释，现已连同口径写下。

第 12 轮采纳了第 11 轮 Critical 主张、并由维护者拍板的方案：**退役库存，只保留有界性质**。实测依据是体量倒挂——518 非注释行对上被退役扫描器的 309——以及同一轮里复现的五种假绿与六种假红。补解析已连续十一次生出下一轮的发现；有界的问题不需要它们。

钉现为 **149 行（128 非注释）**，不到它替换掉的扫描器的一半，六种假红读 `[]`。五种假绿仍读 `[]`——这正是退役让渡的覆盖，列在上表而非隐藏，并点名打包臂为其承担者。前几轮的库存夹具随其子句一并移除；它们见证过的解析 helper（`resolve` 的歧义规则、按引用与具名声明的回调）保留且仍有夹具。

有一条保留子句是**被简化而非被扩展**。一条延后项报告成员边界只看直接父节点；实测确认属实，并发现该规则在另外四种写法上自相不一致。把向外遍历换成一个包含问题——最近外层函数必须是登记过的回调——用少十二行的代码闭合全部四种，且其自身的变异（恢复向外遍历）会让套件变红。它的代价，即「委托被抽进回调会调用的 helper」，已在上文披露。

## 验证

本改动只涉及测试基础设施，故承重证据是：被执行的判定测试在变异下对每个敌意方向打红（additive fallback、伪造 schema、错误 call id、去掉门）；委托钉的每条子句在「单独删掉它」或「把它收窄回去」时打红，接受等价改写的那些子句也一样；退役那些库存不削弱任何存活钉子；以及整栈重建后跑打包臂，其结果按归因认定而非假定。

落位钉的子句逐条见证，而非整块见证：整条删除可能被兄弟子句杀掉，而对它做一处记号的收窄却仍能全绿。

在合并后的 head `5df9a05f0f` 实测，并在交付树上复跑 scripts 元套件（仍 `186 passed (186)`）：scripts 元套件 `186 passed (186)`、core parity `35 passed (35)`、core `tsc --build` 净、eslint 与 prettier 净、build 与 bundle rc=0 且 core/cli dist 与 bundle 按构建起点时间戳断言已刷新、Java SDK 与 server jar 重建（没有任何 Java 源码或 pom 比 jar 更新）、四份嵌套契约 sidecar 字节相等、`ManagedLoopSkillTest` 22/22。对交付版判据的二十四条子句级变异——每条子句各一，另加注册解析、包含规则、歧义计数、绑定模式计数、调用点位置、id 解析、字面量拼接折叠及其操作数解包、模板字面量分支、被调名解包、非空、`satisfies` 与 `<T>expr` 三支、fake 服务器被调名解包，以及 `isFn` 七类可调用中的五类各一（另两类由基线用例承载）——全部被敌意接线用例击杀，每条字节还原。

**两条打包臂在本 head 均红，且红属 main。** 只把 runner 文件换成 `origin/main` 的版本重跑各臂，复现完全相同的失败——skill `Cron tool loop-cron-list was never called`、fire `No model round ran the /loop create input`——跑完 runner 字节还原。本 PR 的 runner diff 是三处 hunk，均不在这些路径上，故未夹带无关修复。上文「由臂承担」的结论是在臂为绿时实测的，今天不把它们重述为一次绿跑。
