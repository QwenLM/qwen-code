# 按需加载 ACP 工作流历史

[English](acp-on-demand-workflow-history.md) | [简体中文](acp-on-demand-workflow-history.zh-CN.md)

## 问题与目标

ACP 在构造会话前，要等待中断工作流恢复并读取所有保留的工作流快照。普通 `qwen serve` 会话创建也会经过这一步，包括关闭工作流控制的工作区。纯文本提问无需恢复扫描和快照列表。将两者移出会话创建路径，同时保留中断工作流的发现和操作能力。

## 设计

- 每个会话首次通过鉴权请求包含工作流的任务列表时，执行批量恢复。同一 ACP Agent 内，同一个工作流存储目录的并发首次读取，共享正在执行的恢复。新的 ACP Agent 从空状态开始。恢复调用返回后标记会话。恢复抛出异常时记录日志，下次请求重试。
- 恢复结束后沿用现有的会话级快照读取和合并。每次读取独立记录删除顺序，包括兄弟会话通知的删除。这样既保留运行中和收尾中的任务，也避免共用旧快照列表导致已删除的记录重新出现。
- 重试和重跑继续沿用已有的单次运行恢复机制。删除请求在获取现有变更锁前恢复目标运行记录，以支持首次查询历史之前删除仅有检查点的记录。已有的运行状态检查和快照成员检查继续决定是否允许删除。
- 包含工作流的任务请求沿用工作流可用性和工作区信任检查。任务面板、工作流运行页以及后台任务产生后的轮询均可发起该请求。普通任务查询和纯文本首问无需读取工作流历史。

生产改动限定在 `packages/cli/src/acp-integration/acpAgent.ts`。Daemon 路由、请求和响应结构、快照格式和 TUI 启动沿用当前约定。

## 取舍与验收

首次包含工作流的请求承担恢复耗时。该查询可以触发现有维护写入，包括将中断任务记为失败、移除检查点和执行快照保留策略。会话始终未请求工作流历史时，中断检查点会保留在磁盘，直到包含工作流的请求、按 ID 操作或其他已有恢复入口处理。若进程在较早会话扫描后退出，后续会话的首次工作流历史请求仍可发现这些检查点。恢复状态保存在每个 ACP Agent 的内存中。

验证普通 ACP 会话创建和普通任务查询都不扫描中断记录、不读快照。验证并发工作流请求、首次列表前直接按 ID 重试和删除、活跃写入进程保护以及工作区隔离。在同一源码基线下，交替启动全新的 daemon 进程，对比 1 个与 7 个工作区、0 与 30 条快照。测量建会话、首问受理及本地模拟模型服务收到首问的耗时，并记录首次工作流历史请求成本、主机和文件系统条件。
