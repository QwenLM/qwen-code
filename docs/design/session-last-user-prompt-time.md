# Last human prompt time in session summaries

[简体中文](session-last-user-prompt-time.zh-CN.md)

## Product requirement

Clients need the recorded time of the latest genuine human question to show “asked 5 minutes ago” and to support a view ordered by the user's questions. Session creation time is unrelated; activity `updatedAt` also advances on assistant output and background work.

For example, the user asks A at 10:00 and B at 10:05, then A continues output at 10:10. Activity ordering puts A first; question-time ordering must keep B first. Both are valid product views and require distinct facts.

This PR supplies optional `lastUserPromptAt` consistently on workspace session-list pages, batch catalog rows, standalone SDK summaries and loaded-session status. It also includes the optional server and WebShell [question-time sort](session-question-time-sort.md), which processes the complete eligible candidate set before pagination. Default ordering remains compatible.

## Timestamp semantics

Use the recorded timestamp of the last qualifying input on the effective main transcript branch, normalized to UTC ISO milliseconds. Include attachment-only, voice and persisted human mid-turn messages and human agent mentions. Exclude assistant/tool/system activity, notifications, cron/Goal, external agents, inherited fork history and inactive branches. Missing means unknown or no qualifying input, never creation/activity/current time. Do not advance for input rejected, cancelled before recording, or failed persistence.

## Performance problem in the first implementation

The original scalar cache used JSONL identity, size and mtime. Assistant appends changed its key and could rebuild the full transcript index on the next list/catalog/status request. A synthetic reproduction at `16435cd` measured full index-build counts of 1 cold, 1 unchanged, 2 after one assistant append and 3 after another, with the human timestamp unchanged. Existing catalog enumeration reads bounded metadata; this does not make an additional effective-transcript scan free.

## Cold recovery and hot updates

- On a cold metadata miss, reconstruct the effective persisted transcript using the canonical reader. Enrich returned rows for default reads, or the complete eligible set before question sorting, at most two concurrently; concurrent reads share the same initialization. The scalar cache retains complete scopes within 100,000 entries and 64 scopes and survives the separate catalog TTL and dense-index eviction.
- For warm default metadata reads, inspect file identity/size/mtime without reading transcript content. Ordinary append growth retains the scalar. Replacement, truncation or same-size rewrite is an explicit recovery condition. On filesystems reporting no verifiable inode, a changed warm snapshot omits the optional value without rescanning until a human notification or cold recovery re-establishes it. A cold miss above the canonical 256 MiB index ceiling omits metadata without scanning.
- After a qualifying human record is successfully persisted, the recorder sends its actual recorded timestamp through the existing owner-scoped ACP notification transport. The daemon installs that scalar in the same runtime/workspace cache used by list, catalog and status, then advances the catalog version. No full transcript scan is required for this update. A hot known timestamp can still be served for a transcript above the cold-scan ceiling.
- Assistant/tool/automatic activity does not send a prompt-time update and append growth does not invalidate hot metadata. No new HTTP endpoint, client request, polling loop or background timer is added.
- Persisted rewind and message-group deletion invalidate the scalar; the next read recovers the effective branch once. A newly registered owner also invalidates older process-local metadata, so a restore/replacement recovers any changes made while no live owner was present. Restart naturally starts cold.

This metadata is authoritative for this daemon's observed writer. Unobserved external append-only writes to an otherwise warm, unloaded session become visible on a cold recovery/owner registration/cache eviction; they do not trigger a full scan on every catalog request. This is the deliberate hot-memory contract.

## Cold-path acceleration, sidecar persistence, and concurrency/cancellation bounds

Production profiling on multi-workspace daemons (`#17889`) showed that cold starts, scope evictions, and owner re-registrations across dozens of workspaces could still fan out into many concurrent full dense-index builds on default session-list requests. To eliminate that rebuild storm while preserving the exact `lastUserPromptAt` contract:

- **Persisted `.prompt-time.json` sidecar**: `chats/<sessionId>.prompt-time.json` (and `chats/archive/<sessionId>.prompt-time.json` when archived) stores the verified `{ version: 1, fileIdentity, snapshotSize, lastUpdated, lastUserPromptAt, leafUuid, anchorLeafUuid?, firstRecordOwner, prefixSha256?, prefixUuidBloom?, managed? }` checkpoint. `prefixSha256` is the full-prefix SHA-256 digest of `[0 .. snapshotSize)`, and `prefixUuidBloom` is an adaptive power-of-two Bloom filter (256 B to 128 KiB, `k = 7`, canonical base64) recording every physical record UUID in `[0 .. snapshotSize)` with zero false negatives. Up to 120,000 records, saturating past ~8 bits/item resizes up to 128 KiB; above 120,000 records `prefixUuidBloom` is intentionally omitted to cap sidecar disk size at 128 KiB, so `sidecar_exact` still serves unchanged files in O(1) while append growth falls back to `lightweight_scan`. The recorder updates the sidecar on persisted human prompt writes (carrying forward a matching same-identity sidecar's verified bloom and prefix hash on resume, advancing `prefixSha256` asynchronously over 256 KiB streams rather than blocking the event loop with synchronous reads, doubling the target record capacity and resizing the bloom up to 128 KiB on saturation, preserving or streamingly catching up from a verified reader-healed sidecar carrying valid prefix state when the writer lacks prefix state on `ino !== 0` filesystems, and keeping the bloom and hash across `rewind` appends), removes the sidecar on rewind or message-group deletion, and logs write failures via `debugLogger.debug` without poisoning transcript recording. Session registration/restore (`setLastUserPromptAt(id, undefined)`) clears only in-memory metadata without unlinking a healthy persisted sidecar. Trusted cold reads (and subsequent trusted warm/cached hits after an untrusted cold read populated `pendingSidecar`) self-heal the sidecar once ownership passes `validateFirstRecord` (covering project-owned worktree sessions under the same repository while still rejecting foreign worktrees; direct reader calls without `validateFirstRecord` retain strict `cwd === workspaceCwd`) without regressing a strictly newer on-disk checkpoint. Archive, unarchive, conflict resolution, working-directory relocation (`/cd`), and session deletion move or clean up the sidecar alongside existing session sidecars. All daemon listing callers explicitly pass `allowSidecarWrite` from workspace trust state so untrusted / read-only workspace inspections (`allowSidecarWrite: false`) and foreign-project transcripts never write the sidecar.
- **Exact hit and linear tail extension**: On a process-local cache miss, the reader first checks for an exact warm dense-index hit, then inspects the sidecar. An exact `(dev, ino, snapshotSize, lastUpdated)` match returns in O(1) without reading the JSONL transcript (even if `prefixSha256` or `prefixUuidBloom` is omitted). When `ino !== 0` and the same file grew (`stats.size > sidecar.snapshotSize`) on a non-Managed transcript carrying both a valid `prefixSha256` and `prefixUuidBloom` with `\n` at `sidecar.snapshotSize - 1`, the reader streams `[sidecar.snapshotSize .. stats.size)` first (bounded to 10,000 appended conversation records). Because legacy `recordCustomTitle`/`recordSessionSource` writes chain onto the active tail while periodic 32 KiB re-anchors append as siblings, both cold scans and `index_cache` hits resolve trailing metadata re-anchors to `{ leafUuid, anchorLeafUuid? }` (where `leafUuid` walks back to the non-anchor conversation tail and `anchorLeafUuid` records the trailing metadata UUID), and tail extension accepts either parent in `allowedParents` before clearing `anchorLeafUuid` on the next regular conversation record. Every valid appended record is tested against `prefixUuidBloom` (and added to a working copy) before advancing `leafUuid` and `lastUserPromptAt`; non-conversation records and metadata re-anchor records (`custom_title`, `session_source` anchored on an allowed parent) add their UUID to the bloom without advancing `leafUuid` or counting toward the 10,000-record cap. The moment any invalidating record (rewind, branch jump, Bloom hit, Managed header, or record limit) is encountered, the line callback returns `false` and destroys the tail `ReadStream` immediately instead of reading to EOF. Only after the tail passes linearity does the reader cooperatively verify `prefixSha256` over `[0 .. sidecar.snapshotSize)` (catching any equal-length or arbitrary in-place prefix rewrite) and extend the digest across the tail bytes. Any mismatch or non-linear append falls back cleanly to a cold scan from byte 0.
- **Lightweight cold scan**: `lastUserPromptAt` is active-branch-sensitive rather than file-order positional — a persisted `rewind` abandons newer user prompts on inactive branches and must surface the latest human prompt still on the active branch. When a cold scan is required, `getLastUserPromptAt` uses a dedicated minimal-envelope scanner that walks backward along the active `leafUuid` parent chain instead of constructing a full `TranscriptIndex`. It skips `validateTranscriptRecord` object cloning, branch-point part projection, `resolveBranchPoints`, navigation turn assembly, execution-engine tracking, and dense-index cache admission, while preserving identical session-id validation, cycle/gap traversal, Managed projection handling (bounded by `maxBodyBytes = getMaxAllReplayBytes()` without duplicating projection record validation), line-size caps, and heap-growth ceilings.
- **Process-wide build gate and `AbortSignal` propagation**: Cold transcript scans, dense index builds, and incremental extensions share a process-wide concurrency semaphore (default 2) so concurrent workspace listings and transcript page reads cannot launch dozens of simultaneous parses on the main thread. `AbortSignal` propagates from `session-list` enrichment and daemon HTTP transcript, turn-index, turn-hooks, and tool-calls routes (`readPage`, `readTurnIndexPage`, `readTurnHooksPage`, `readSessionToolCalls`) — including early pre-abort guards before workspace resolution and flush barriers, as well as Managed projections (`readManagedSessionRecordsAndTitle`) — through shared refcounted in-flight tasks, semaphore queues, and `forEachLineInSnapshot` streams: an individual aborted waiter detaches immediately without harming surviving sharers, while aborting the last active waiter cancels the underlying stream immediately and cleans up its in-flight slot. Non-HTTP `readRestoreProjection` remains outside `AbortSignal` cancellation scope and is left as follow-up work.

## Ownership and consumers

The persisted metadata is workspace/runtime scoped. Resolve the runtime first, use its storage root and canonical workspace, and validate cold snapshot ownership. The cache key includes both the resolved transcript path and workspace. Default reads detect file replacement; warm question sorting uses the observed writer cache until explicit recovery. ACP notifications are accepted only for the session owned by the sending channel; unknown/foreign owners do not update memory. Do not fall back to the primary runtime.

Workspace session-list and batch catalog share one enrichment producer. Status resolves its live owner and uses the same cache. SDK list/catalog/standalone/status preserve the optional wire value. Memory-only live-state keeps its existing shape and performs no transcript enrichment. Native CLI columns/JSON and ACP listing are unchanged.
