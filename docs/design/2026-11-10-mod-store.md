# Mod store

[English](2026-11-10-mod-store.md) | [简体中文](2026-11-10-mod-store.zh-CN.md)

Status: proposed. Tracked in #13749. The method names and shapes are those of the `$.store` methods in the Mod authoring API.

## Problem and current behavior

A Mod has nowhere to keep a value past its session. A module variable lasts until the session ends, and the Mod environment has no file system. A Mod that counts its runs, remembers a choice the person made, or caches a slow answer starts from nothing every time.

`$.store` is the authoring API's place for this, but in Qwen Code every call rejects with `Mod API not supported: $.store.get`, and hooks on `store.*` load without ever running.

## Goals and non-goals

Goals:

- `$.store.get`, `set`, `delete` and `keys` in every host that runs Mods: headless runs and the Ink and OpenTUI terminals.
- Values kept between sessions and shared by the sessions of one plugin, including two that run at once.
- The calls run as API events, so other plugins' hooks hear them, as with the other `$` methods.

Non-goals:

- `$.state`, the session's named values that drawings subscribe to. It needs a render subscription and a runtime module of its own, and comes later.
- Removing a plugin's store when the plugin is uninstalled.
- Stores in ACP sessions, which load no Mods yet.

## Proposed changes

### 1. Where the store is kept

Each plugin has one JSON file, `<global Qwen dir>/mods/store/<plugin name>.json`, where the global Qwen dir is `~/.qwen` or `$QWEN_HOME`. The file holds `{ version: 1, entries: [[key, value], ...] }`.

### 2. Who touches the file

The session's main thread, not the Mod worker. The worker forwards each call as a `store` request and waits for the `store-result` answer, as it does for `$.turn.abort` and `$.prompt.submit`. The runtime takes a `ModStore` when it is created; a host that passes none keeps no store, and the worker then lists no `store.*` methods and rejects every call.

### 3. Reads and writes

- `get` and `keys` read the file each time, with no lock and no cache.
- `set` and `delete` take an in-process mutex and a process-owned directory lock, re-read the file under the lock, apply the change and replace the file through a temporary file and a rename.
- A `delete` of a key that is not set writes nothing.

### 4. Limits and failures

- A plugin's store holds at most 4 MiB of JSON. A write that would go over rejects, and the file keeps what it had.
- One value is also bound by the existing 256 KiB limit on what a Mod passes to Qwen Code, and by the 512-level nesting limit.
- A new key also has to fit in the serialized key list within the 256 KiB Mod reply budget. A plugin can still delete existing keys from a store above this limit.
- A file that does not parse as a store fails every call on that store, and nothing overwrites it.
- A symlink at the store file path causes store calls to reject. The write replaces its own directory entry atomically.
- `set` rejects `undefined` and anything that does not serialize as JSON (a function, a cycle).

### 5. Middleware

`store.get`, `store.delete` and `store.keys` are pinned. A `store.set` hook may pass on another `value`; the key is pinned, so a hook that moves a write to another key fails and is skipped. A hook may answer any call with `{ value }` or refuse it with `{ deny }`.

## Design decisions

- **The file is the host's.** The worker can be terminated while a dispatch runs, when the dispatch is cancelled or times out. A lock or a rename cut short there would leave the lock behind or the file half-written. On the main thread a write is not cut short by a worker that ends, and the runtime waits for the writes it is answering before it closes. A process that is killed mid-write leaves the old file or the new one, never half of either, since the file is replaced by a rename.
- **Keyed by plugin name.** An extension's id is a hash of its install source, so for a local install it changes when the install path does. The name stays the same across reinstalls. Extension names allow only letters, digits, `-`, `_` and `.`, match without case, and a name of dots alone is refused, so the file cannot leave its directory.
- **Entries as pairs.** A plain object would list keys such as `"10"` and `"2"` in numeric order rather than insertion order, and `__proto__` would not be an own key.
- **No cache.** Another session may write at any time, and a read is a single small file. Reading each time means a value another session wrote shows up at the next `get`.
- **A write whose dispatch ended may still land.** When the dispatch that made a call ends first, the host still finishes the write but the answer goes nowhere, so the caller's promise rejects. Undoing the write would need a second write, which could itself be cut off.

## Validation and acceptance

- Unit tests for `ModStore` cover live and dead lock owners, concurrent writes, the 4 MiB limit, deleting keys from a previously oversized list, plugin names, symlink refusal, and file mode 0600.
- Real-worker tests cover key ordering, JSON round trips, persistence and ownership, the key-list limit, draining writes at close, unreadable files, middleware, and capability gating before middleware.
- A headless run that sets a value and a second run that reads it, on the built CLI, and two runs writing at once.

## Risks and open questions

- Store files are never removed. A cleanup command or removal on uninstall can follow.
- A paused writer keeps its lock. Acquiring the lock across processes times out after eight seconds. A later writer can recover a lock left by a dead process on the same host. On Linux, recovery also requires the same boot and PID namespace. A lock whose owner cannot be verified stays in place.
