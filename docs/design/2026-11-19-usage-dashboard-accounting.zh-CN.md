# 用量面板的计量口径

[English](2026-11-19-usage-dashboard-accounting.md) | [简体中文](2026-11-19-usage-dashboard-accounting.zh-CN.md)

状态：选项 A 已实现，缺陷 2 的持久化侧也已修复。缺陷 1 已彻底修复；缺陷 3 在逐请求台账覆盖到的那些天上已修复。缺陷 4 与 5 仍未解决。本次改动之前写入的记录保持原样——不做迁移。

## 问题

Web Shell 的 Daemon 状态「用量」页高估了 token 消耗。以逐请求台账
`~/.qwen/usage/token-usage-YYYY-MM.jsonl` 为准绳，在一份真实的重量级历史上于
2026-11-18（本地日）实测：

| 窗口  | 面板            | 逐请求台账     | 倍数    |
| ----- | --------------- | -------------- | ------- |
| 今日  | 1,690,741,563   | 851,107,656    | 约 2.0x |
| 7 天  | 67,264,675,464  | 13,030,723,769 | 约 5.2x |
| 30 天 | 301,992,859,495 | 43,099,928,198 | 约 7.0x |

两列读数在一台仍在活动的机器上相隔数分钟采集，因此倍数是近似值；下文的逐会话对账是精确的。历史规模：2,060 条持久记录、3,877 条合并记录、76,849 个 project 目录、约 12 GB transcript、770,906 行台账（约 291 MB）。

差额由五个互相独立的缺陷造成。

1. **推理被计费两次（已修复）。** 输出 tile 渲染的是
   `summary.outputTokens + summary.thoughtsTokens`，但 chat-completions 类 provider
   的 output 计数本身已含推理。今日该 tile 显示 7,208,898，而 provider 上报的 output
   为 4,952,378（虚高 45.6%），且输入 + 输出之和不等于 hero 总量。

2. **resume 的历史被当作新用量落盘（已修复）。** `persistSessionUsage` 原先写入的是
   `uiTelemetryService.getMetrics()`，而 session-swap 重放已把被恢复会话的整段历史灌入其中。会话
   `4669c795-e9bc-4ae7-9a1e-1c75795cf446` 只覆盖 7 分钟窗口
   （01:04:23 -> 01:11:54），却带有 506 个请求、45,679,298 token，其逐模型总量与 transcript
   `df2ad8ce-e86d-49f5-80c7-6012e8736660` 的全量历史 telemetry 完全相同
   （`qwen3.8-max-preview` / `gpt-6-astra` / `glm-5.3` 分别为 6,682,231 / 5,209,415 / 30,559,974）。
   该会话每被 resume 一次，就再追加一份完整副本。这是差额的主要来源。两侧现在都已修复：
   台账覆盖到的那一天，面板不再读取这些 token；而一次运行也不会再把自己没花过的历史落盘。

3. **窗口按会话结束时刻归属（台账覆盖处已修复）。** `aggregateUsage` 以 `r.timestamp`（会话最后一条记录）过滤，
   日粒度图与热力图也按同一值分桶，于是一个会话的全部消耗都落在它最后活动的那天。会话
   `864fc39f-956e-48ce-810d-231d9e2f82aa` 向「今日」贡献了 335,062,436，而其事件实际分桶为
   126,738,776（11-15）、207,250,267（11-16）、1,073,393（11-18）。今日 42 个会话中有 7 个始于往日，
   带入 818,260,710 token（占显示总量的 48.4%）。

4. **同一次运行在两个 sessionId 下各计一次（未解决）。** transcript 的文件名取自
   `chatRecordingService` 的 `binding?.sessionId ?? pinnedSessionId ?? config.getSessionId()`，
   而 `persistSessionUsage` 以 `config.getSessionId()` 为键。近两天被触碰的 189 个 transcript 中，
   只有 1 个的 id 出现在持久集合里，因此 `skipSessionIds` 与 `dedupBySessionId` 双双失效。
   以「持久记录的结束时刻与 transcript 最后一条记录相差 2 秒内、同项目、重放量 <= 持久量」为判据：
   今日 2 对（51,636,168 token）、7 天 13 对（2,249,442,081）、30 天 120 对（5,302,870,324）。
   例：transcript `8159416a` 重放出 23 个请求 / 816,135 token，而持久记录 `d8111ad4` 对同一次运行
   记了 34 个请求 / 1,117,620 token，两者结束时刻相差 83 ms，却曾被同时计入。现在它只影响
   会话粒度的 tile 以及台账未覆盖的那些天。

5. **last-wins 去重丢弃不相交的时间段（未解决）。** `dedupBySessionId` 每个 sessionId 只保留一条，
   但被恢复的会话会合法地在同一 id 下持久化多个互不重叠的时间段。11 个 id 持有多条记录，其中 9 个
   的时间段不相交；去重丢弃 22 条记录 / 120,082,542 token。`df2ad8ce` 持有 6 段（07-30 -> 10-15），
   只有最后一段（43,386,166）存活，而其 transcript 又因 id 命中持久集合被跳过重放。
   实测影响仅限 30 天以前的窗口（今日 / 7 天 / 30 天内被丢弃的 token 为 0），因此它扭曲的是热力图与更长区间。

## 现状

`GET /usage/dashboard`（`packages/cli/src/serve/routes/usage-stats.ts`）把加载好的数据源缓存 60 秒，
并按区间重跑 `buildUsageDashboard`。本次改动之前，数据源只有会话历史：持久的 `usage_record.jsonl`
与有界的 transcript 重放取并集，按 sessionId 去重（后者胜、持久优先）。为 #4479 引入的逐请求台账
（`packages/core/src/services/tokenUsageService.ts`）当时已按每次 API 响应存储 `localDate`、
`localMonth` 与 `authType`，但面板并不读取它。

重放缓存与扫描边界由
[Usage Dashboard Replay Cache](2026-11-14-usage-dashboard-replay-cache.md) 负责，
该设计明确把本地「今日」窗口语义列为不在范围内。

## 目标

- hero、明细、日粒度图与热力图反映所选窗口内**实际消耗**的 token。
- 一次运行只贡献一次，与 resume / clear / branch 无关。
- 保持面板只读，且热加载维持亚秒级。
- 会话数 / 请求数 / 工具调用 / 变更行数 / 技能这几个 tile 不受损。

## 范围边界

- 范围内：`usage-dashboard-service.ts`、`tokenUsageService.ts`（仅读取路径）、
  `usage-stats` 路由、Web Shell 用量页的输出 tile，以及持久化侧
  （`UiTelemetryService`、两处重放点、两处落盘调用方）。
- 范围外：`/stats` 的会话视图（其「累计含恢复历史」的语义是有意为之）、台账与用量记录的 schema、
  迁移已落盘的存量记录、费用计费、重放缓存的扫描边界。

## 已实现方案（选项 A）

**一张按日 × 模型的计数表，一条代码路径。** `buildUsageDashboard` 先用会话记录建出
`localDate -> model -> counters` 表（即原有的「按结束日归属」），随后对台账覆盖到的每一天，
用台账的条目**替换**该天。所有与 token 有关的输出——summary 的各 token 字段、请求数、
逐模型占比、日粒度 token、热力图格——都由这张表派生。会话数、工具调用、变更行数与技能仍取自
`aggregateUsage`，因为台账有意不携带这些。

- `loadTokenUsageDailyByModel(sinceLocalDate)` 流式读取起始月及之后的每个按月文件，用既有的
  `isTokenUsageRecord` 校验每条记录，并在不物化整份历史的前提下累加计数。usage 目录不存在时返回空表；
  其它读取错误一律向上抛出，避免某个月只读了一半却静默少算窗口。
- `loadUsageDashboardSources()` 以 `LEDGER_WINDOW_DAYS = 366` 同时加载会话历史与台账，
  与路由的 `heatmapDays` 上限一致，因此一次缓存加载即可覆盖调用方可能请求的任何窗口。
- 路由现在只有一个可注入依赖 `loadSources`，同时返回两者，这样注入了会话记录的测试不会
  意外读到操作者真实的台账。
- 输出 tile 渲染 `summary.outputTokens`，由 core 通过 `outputTokenCount` 逐模型归一化（缺陷 1）。

## 已实现方案（持久化侧）

**第二个只由真实事件喂养的计数器。** `UiTelemetryService` 在展示聚合之外维护 `#liveMetrics`。
`addEvent` 同时喂两者；`addReplayedEvent`——由两处重放点使用，即
`replayUiTelemetryFromConversation` 与 `LlmClient.initialize()` 的 restore-runtime 分支——
只喂展示聚合与会话桶。两处落盘调用方（`/clear` 与进程退出清理）现在写入 `getLiveMetrics()`。

- 不做减法、不改 schema：live 计数器由同一个累加器构建，因此没有重放时它与展示聚合逐字段相同，
  既有记录形状完全不变。
- `reset()` 会清空它，因此每个 `/clear` 分段只为自己计费。
- `UiTelemetryReplaySnapshot` 携带它，因此被放弃的 swap 在回滚时也会还原它，
  不会让一次废弃的重放把 live 计数器留在虚高状态。
- 一次「只 resume、没发请求」的运行现在过不了调用方的 `hasActivity` 检查，因而根本不写记录，
  而不是写一条全是历史的记录。

**未做：给 `UsageSummaryRecord` 增加按本地日的明细。** 它是最初选项 B 草案的另一半。
既然日归属已由台账提供，它就只对台账未覆盖的天有帮助，代价却是在 telemetry 中增加按日分桶、
扩展记录 schema，并为存量记录定义降级规则。因此推迟，而不是投机地先建起来。

## 设计决策与理由

- **台账本就是按日用量的既定数据源。** #4479 选择「每次响应一条 JSONL、带本地日期与 auth type」
  正是为了回答按日 / 按月消耗；面板早于这次对齐，读的是会话摘要。
- **按天替换，绝不相加。** 同一批请求同时存在于两个数据源，因此被覆盖那天的会话记录副本是丢弃而非叠加。
  相加会重现原本的虚增。
- **未覆盖的天沿用会话记录归属。** 这既保住了台账出现之前的热力图历史，也保住了关闭用量统计的用户
  的行为（台账为空 -> 沿用原有数字）。
- **按日历日取窗口。** 日桶无法按小时切分，因此 `today`、`week`、`month` 现在都取整个本地日
  （`today` 不变；`week` 与 `month` 纳入完整的边界日，而不是滚动 `now - N*24h` 之后的那几个小时）。
  这让 summary 与按日分桶的图表口径一致。在回退路径上该影响可测量且只限那一天：参考历史的 `week`
  窗口里，2026-11-12 从 4,110,008,866 变为 17,376,555,073 token，因为一个在该日凌晨结束的会话
  带着被重放虚增的历史。有台账覆盖时那天本来就会被替换。
- **归属无法事后修补。** 会话级总量不含日期信息，仅改过滤条件无法修复缺陷 3。
- **会话记录必须保留。** 台账有意不存 project 路径、工具计数、变更行数与技能调用（#4479 的隐私边界），
  因此无法替代非 token 的 tile。
- **载荷形状不变。** 面板 JSON 未变，因此 SDK 类型与 Web Shell 客户端都不需要新增字段。

## 约束

- 面板路径不得写入 `~/.qwen`。
- 台账写入受 `config.getUsageStatisticsEnabled()` 门控，且跳过 internal prompt id
  （见 `loggers.ts`），因此台账覆盖并不保证。
- 不得向台账记录加入 project 路径或内容。
- 不得就地重写或迁移既有的 `usage_record.jsonl`。
- 保持重放缓存的热加载延迟与去重顺序保证。

## 风险

- **部分覆盖。** 若某天只有部分进程写了台账，该天会被整体替换，未写入进程的 token 就在该天丢失。
  早于台账功能的历史属于同一类缺口。
- **台账读取代价。** 实测流式解析 771,906 条记录（约 304 MB、5 个按月文件）耗时 862 ms；
  两个数据源合并加载实测 29.4 s，仍由 transcript 重放主导，路由缓存 60 秒。
- **目录作用域。** 台账位于 `Storage.getRuntimeBaseDir()` 之下（与其写入方同一个基目录），
  而会话历史读自 `Storage.getGlobalQwenDir()`。默认二者重合；若部署为每个工作空间钉住独立的运行时目录，
  就会把该运行时的台账与全局会话历史放在一起聚合。
- 缺陷 4 与 5 仍会扭曲会话粒度的 tile 与未覆盖的天。
- 本次改动之前写入的记录仍然虚增，因此 `loadUsageHistory` 的其它消费方（尤其是 TUI 跨会话视图）
  对那段历史看到的仍是旧数字。只有新写入的记录是正确的。
- live 计数器与它所镜像的展示聚合一样是进程级的，因此长驻进程若不经 `/clear` 就切换会话，
  仍会把总量归到最后那个 session id 上。这是既有行为，本次未改动。

## 验证计划

- 单元测试：台账覆盖的天是替换而非叠加；token 落在每次响应实际发生的那天；未覆盖的天沿用会话记录 token；
  loader 按日 / 模型聚合、跳过更早的日与月、无台账时返回空表、丢弃非法与未来 schema 的记录；
  两种 provider 口径下的输出 tile。
- 路由集成：两个数据源都真实落盘，走真实 loader。
- 以独立台账扫描为准绳的真实数据 A/B，跑在台账的**冻结副本**上，使两臂读到完全相同的字节。
- 持久化侧：live 计数器的单元测试（排除重放、无重放时与展示聚合平价、reset、废弃 swap 的还原）；
  真实 `/resume` + `/branch` 夹具断言展示保留历史而 live 不保留；`/clear` 断言纯 resume 不写记录。
  另有一个两臂探针，分别驱动两个检出里真实的重放函数与落盘函数。
- 对每个新增守卫做变异见证，并写明实际跑过哪些套件。

## 验收标准

- 台账覆盖时，今日 / 7 天 / 30 天的 token 总量、请求数、输入、缓存与推理都等于同一窗口的独立台账聚合值，
  且每个被覆盖天的热力图 token 与缓存率一致。**已验证**：在参考历史的冻结副本上三个区间全部精确相等
  （`ALL_RANGES_EXACT=true`，0 个日不符）。
- 每个区间都满足 `inputTokens + outputTokens == totalTokens`。**已验证。**
- 会话粒度的 tile（会话数、工具调用、变更行数、技能）不受台账影响。**已验证**：与同一批记录在空台账下逐项相同。
- 跨三天的会话向三个日桶都贡献。**已验证**：单元测试与逐日热力图比对各一次。
- 热加载维持亚秒级，且面板路径不写任何文件。
- 相对改动前的 builder，在参考历史上的实测效果：今日 -59.4%、7 天 -75.8%、30 天 -85.9%
  （活动历史，故为近似值）。
- resume 长会话的那次运行只落盘自己的请求。**已验证**：用真实重放函数与落盘函数的两臂探针——
  400 条历史响应加一次真实请求，改动前落盘 401 个请求 / 400,000,005 输入 token，
  改动后落盘 1 个请求 / 5 输入 token，而两臂的展示聚合都保持 401 / 400,000,005。

## 待定问题

- 台账只部分覆盖的那天，是否应按模型逐个回退，而不是整体替换？
- 存量的虚增记录是否应被修复或标记，从而让 TUI 跨会话视图与回退路径不再展示它们？
- daemon 会话是否应在会话结束时持久化用量（承接重放缓存设计的待定问题），从而缩小重放路径？
- TUI 的跨会话视图（`statsDataService.ts`）是否应采用同一口径——它共用 `loadUsageHistory` 与同一去重。
- 缺陷 4 与 5 需要一个会话身份决策：让持久记录以 transcript 的身份为键（或同时记录两者），
  并把去重键改为 `sessionId` 加时间段窗口，使不相交的时间段被求和。删除前抢救与持久化迁移共用该键，
  三个调用方必须一起改。
