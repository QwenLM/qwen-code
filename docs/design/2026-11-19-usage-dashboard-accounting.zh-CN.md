# 用量面板的计量口径

[English](2026-11-19-usage-dashboard-accounting.md) | [简体中文](2026-11-19-usage-dashboard-accounting.zh-CN.md)

状态：已实现。缺陷 1 已彻底修复；缺陷 2 的读取侧与持久化侧都已修复；缺陷 3 在逐请求台账覆盖到的那些天上已修复，覆盖范围包括 daemon 面板**与** TUI 跨会话视图。发现 4 已**撤回**——台账证伪了它。发现 5 已**更正**：last-wins 对存量记录本来是对的，真正需要修的是修复缺陷 2 之后引入的「运行增量被丢弃」回归。这些改动之前写入的记录保持原样——不做迁移。

## 问题

Web Shell 的 Daemon 状态「用量」页高估了 token 消耗。以逐请求台账
`~/.qwen/usage/token-usage-YYYY-MM.jsonl` 为准绳，在一份真实的重量级历史上于
2026-11-18（本地日）实测：

| 窗口  | 面板            | 逐请求台账     | 倍数    |
| ----- | --------------- | -------------- | ------- |
| 今日  | 1,690,741,563   | 851,107,656    | 约 2.0x |
| 7 天  | 67,264,675,464  | 13,030,723,769 | 约 5.2x |
| 30 天 | 301,992,859,495 | 43,099,928,198 | 约 7.0x |

两列读数在一台仍在活动的机器上相隔数分钟采集，因此倍数是近似值；下文的逐会话对账是精确的。历史规模：2,060 条持久记录、3,877 条合并记录、76,849 个 project 目录、约 12 GB transcript、770,906 行台账（约 291 MB）。

差额由三个缺陷造成。首轮另有两项发现，下面连同更正一并记录——它们都曾作为「实测缺陷」报告过，但都没有通过独立复核。

1. **推理被计费两次（已修复）。** 输出 tile 渲染的是
   `summary.outputTokens + summary.thoughtsTokens`，但 chat-completions 类 provider
   的 output 计数本身已含推理。今日该 tile 显示 7,208,898，而 provider 上报的 output
   为 4,952,378（虚高 45.6%），且输入 + 输出之和不等于 hero 总量。

2. **resume 的历史被当作新用量落盘（已修复）。** `persistSessionUsage` 原先写入的是
   `uiTelemetryService.getMetrics()`，而 session-swap 重放已把被恢复会话的整段历史灌入其中。会话
   `4669c795-e9bc-4ae7-9a1e-1c75795cf446` 只覆盖 7 分钟窗口
   （01:04:23 -> 01:11:54），却带有 506 个请求、45,679,298 token，其逐模型总量与 transcript
   `df2ad8ce-e86d-49f5-80c7-6012e8736660` 的全量历史 telemetry 完全相同
   （`qwen3.8-max-preview` / `gpt-6-astra` / `glm-5.3` 分别为 6,682,231 / 5,209,415 / 30,559,974）。
   该会话每被 resume 一次，就再追加一份完整副本。这是差额的主要来源。两侧现在都已修复：
   台账覆盖到的那一天，面板不再读取这些 token；而一次运行也不会再把自己没花过的历史落盘。

3. **窗口按会话结束时刻归属（台账覆盖处已修复）。** `aggregateUsage` 以 `r.timestamp`（会话最后一条记录）过滤，
   日粒度图与热力图也按同一值分桶，于是一个会话的全部消耗都落在它最后活动的那天。会话
   `864fc39f-956e-48ce-810d-231d9e2f82aa` 向「今日」贡献了 335,062,436，而其事件实际分桶为
   126,738,776（11-15）、207,250,267（11-16）、1,073,393（11-18）。今日 42 个会话中有 7 个始于往日，
   带入 818,260,710 token（占显示总量的 48.4%）。

4. **「同一次运行在两个 sessionId 下各计一次」—— 已撤回。** 首轮把 transcript 与持久记录之间的 id
   不匹配读成了身份分叉（`chatRecordingService` 的 `binding ?? pinnedSessionId ?? config.getSessionId()`
   对 `config.getSessionId()`），并报告今日 2 对（51,636,168 token）、7 天 13 对、30 天 120 对。
   台账在响应时刻以 `config.getSessionId()` 为键，它证伪了这个判断：那些配对里的四个持久 id
   （`d8111ad4`、`d7a62020`、`15c11db0`、`4669c795`）**台账请求数为零、且没有 transcript 文件**；
   而与它们配对的 transcript id（`8159416a`、`7f6dc04d`）分别有 31 与 257 个台账请求、有自己的
   transcript、且**没有任何持久记录**。不存在第二个身份——那些持久记录来自「自己没发过请求」的运行，
   写入的只有被重放的历史。它是缺陷 2 的症状，并随缺陷 2 一起消失：这样的运行现在过不了
   `hasRunActivity`，什么都不写。189 个里有 188 个不匹配，只是那些运行从未持久化而已。

5. **last-wins 去重 —— 已更正，以及它现在需要避免的回归。** 首轮报告 last-wins 在 11 个多记录 id 上
   丢弃了 22 条记录 / 120,082,542 token 的真实用量。按*窗口*把分段判为「不相交」是误导：它们的*内容*
   是累计副本。`6eed223d` 的 5 段每条都恰好 35,036 token，而它的台账真值就是 35,036。在有台账存在的
   7 个多记录 id 上，last-wins 保留 52,500,008，台账真值 54,780,252（低 4%）；而把分段求和会得到
   172,089,989 —— **真值的 3.1 倍**。所以对存量记录而言 last-wins 本来是对的，用「求和」去「修」它
   反而会是一次倒退。

   真实存在的问题是修复缺陷 2 带来的后果：一旦每条记录都是运行增量，last-wins 就会静默丢掉除最后
   一次以外的所有运行。已用真实的持久化与读取函数复现——同一会话两次运行（1,000 + 2,000 token）
   读回只剩 1 条 / 2,000 token。本次修复的就是它。

## 现状

`GET /usage/dashboard`（`packages/cli/src/serve/routes/usage-stats.ts`）把加载好的数据源缓存 60 秒，
并按区间重跑 `buildUsageDashboard`。本次改动之前，数据源只有会话历史：持久的 `usage_record.jsonl`
与有界的 transcript 重放取并集，按 sessionId 去重；去重时优先采用已有的持久记录或经验证的重建快照，避免转录副本与已知运行被重复计入。为 #4479 引入的逐请求台账
（`packages/core/src/services/tokenUsageService.ts`）当时已按每次 API 响应存储 `localDate`、
`localMonth` 与 `authType`，但面板并不读取它。

重放缓存与扫描边界由
[Usage Dashboard Replay Cache](2026-11-14-usage-dashboard-replay-cache.zh-CN.md) 负责，
该设计明确把本地「今日」窗口语义列为不在范围内。

## 目标

- hero、明细、日粒度图与热力图反映所选窗口内**实际消耗**的 token。
- 一次运行只贡献一次，与 resume / clear / branch 无关。
- 保持面板只读，且热加载维持亚秒级。
- 会话数 / 工具调用 / 变更行数 / 技能这几个 tile 不受损；请求数与延迟则有意随其它 token 计数一并改由台账提供。

## 范围边界

- 范围内：`usage-dashboard-service.ts`、`tokenUsageService.ts` 中将真实响应写入可选
  `executionId` 的路径，以及该字段的读取与已结束月份 copy/merge、`usage-stats` 路由、
  Web Shell 用量页的输出 tile、持久化侧（`UiTelemetryService`、两处重放点、各运行落盘调用方）、
  `usageHistoryService` 的记录标记与归约，以及 TUI 跨会话视图（`statsDataService.loadStatsData`）。
- 范围外：`/stats` 的会话视图（其「累计含恢复历史」的语义是有意为之）、台账或用量记录的
  版本升级或迁移、改写已落盘的存量记录、费用计费、重放缓存的扫描边界。
  新写入响应行的可选 `executionId` 不需要版本变更；两个可选、纯增量的来源标记
  （`runScoped` 和 `transcriptRebuild`）也不构成 schema 版本变更。
  按 root 配对台账 / 历史及其重放缓存生命周期是 root 隔离修正，不改变单独设计中的重放扫描边界。

## 已实现方案（选项 A）

**一张按日 × 模型的计数表，一条代码路径。** `buildUsageDashboard` 先用会话记录建出
`localDate -> model -> counters` 表（即原有的「按结束日归属」），随后只**替换**实际被台账覆盖的
模型 / session 条目，并加上台账计数。所有与 token 有关的输出——summary 的各 token 字段、请求数、
逐模型占比、日粒度 token、热力图格——都由这张表派生。会话数、已结束运行时长、工具调用、变更行数与技能
仍取自 `aggregateUsage`，因为台账有意不携带这些。两个表面都按与 token 切片相同的本地日闭区间过滤这些记录，
而不是使用滚动毫秒截止点。按日的 `sessions` 特指**在该日结束的运行**；跨午夜运行的请求和它的结束记录
因此可以出现在不同日期。

- `loadTokenUsageDailyByModel(sinceLocalDate)` 流式读取起始月及之后的每个按月文件，用既有的
  `isTokenUsageRecord` 校验每条记录，并在不物化整份历史的前提下累加计数。usage 目录不存在时返回空表；
  其它读取错误一律向上抛出，避免某个月只读了一半却静默少算窗口。两个表面随后都经由 `loadLedgerOrEmpty`
  调用它：任何这类错误都会降级为空表，恢复可能带有历史虚增的记录口径，只在 debug 日志中留下警告，
  而不是让整个表面失败。
- `loadUsageDashboardSources()` 以 `LEDGER_WINDOW_DAYS = 366` 同时加载会话历史与台账，
  与路由的 `heatmapDays` 上限一致，因此一次缓存加载即可覆盖调用方可能请求的任何窗口。
- 测试可通过 `loadSources` 注入整个数据源集合。真实加载器还接受 `getLedgerRuntimeBaseDirs`，
  用于提供已注册 workspace 的 runtime roots；不替换整个加载器的调用方需要这一依赖来聚合这些根目录。
- 输出 tile 渲染 `summary.outputTokens`，由 core 通过 `outputTokenCount` 逐模型归一化（缺陷 1）。

## 已实现方案（持久化侧）

**第二个只由真实事件喂养的计数器。** `UiTelemetryService` 在展示聚合之外维护 `#liveMetrics`。
`addEvent` 同时喂两者；`addReplayedEvent`——由两处重放点使用，即
`replayUiTelemetryFromConversation` 与 `LlmClient.initialize()` 的 restore-runtime 分支——
只喂展示聚合与会话桶。`/clear`、成功的会话切换与进程退出清理所写的记录都取自 `getLiveMetrics()`。

- 不做减法、也不做 schema 版本升级或迁移：live 计数器由同一个累加器构建，因此没有重放时它与展示聚合逐字段相同。
  可选 `runScoped` 标记与下节的 transcript 重建来源标记，对不认识它们的既有读取方保持兼容。
- 会话时钟与运行时钟由不同生命周期决定。`resetLiveMetrics()` 只重置 live 计数与
  `getRunStartTime()`，不重启所展示会话的时钟。成功初始化不同 session id 时，客户端将
  `getSessionStartTime()` 绑定至传入会话自身的 `conversation.startTime`；该时间缺失或无效时回退到当前时间。
  selective restore 在外层投影被消费后，仍在运行时状态里保留 `SessionRestoreProjection.startTime`，不依赖完整 resumed-session 数据，也不回拨当前 run 的时钟。
  不会把前一会话的时钟继续套用到新会话。初始化或重放失败时，快照还原此前的会话与运行时钟。
  `SessionStatsProvider` 在初始化后读取该时钟，而非每次显示切换都用 `new Date()` 重建起点。
  会话切换持久化辅助函数和 `/clear` 都以 `getRunStartTime()` 记录当前运行起点；
  `/clear` 再为新会话完整重置两种时钟。
- `reset()` 会清空它，因此每个 `/clear` 分段只为自己计费。成功的 `/resume` 或 `/branch`
  也会先按切换前捕获的 session id 落盘旧运行，再在 UI 提交点调用 `resetLiveMetrics()`。
  它只重置待持久化计数和运行起始时间，不清除已重放的传入会话展示历史，
  从而避免退出时把旧运行写在被恢复会话的 id 下。
- `UiTelemetryReplaySnapshot` 携带它，因此被放弃的 swap 在回滚时也会还原它，
  不会让一次废弃的重放把 live 计数器留在虚高状态。落盘只在成功时发生，回滚路径不会落盘。
- 一次「既无 API 响应、也无技能调用」的 resume 过不了调用方的 `hasRunActivity` 检查，
  因而根本不写记录，而不是写一条全是历史的记录。只有 skill 调用、没有模型请求的 branch
  也会落盘这段实际发生的技能用量。

**未做：给 `UsageSummaryRecord` 增加按本地日的明细。** 它是最初选项 B 草案的另一半。
既然日归属已由台账提供，它就只对台账未覆盖的天有帮助，代价却是在 telemetry 中增加按日分桶、
扩展记录 schema，并为存量记录定义降级规则。因此推迟，而不是投机地先建起来。

## 已实现方案（运行增量归约）

`persistSessionUsage` 给它写入的记录打上 `runScoped: true`，因为调用方传入的是该次运行的 live 指标。
从整份 transcript 重建的记录仍不带 run 标记，是累计值；而真正按事件时间重建的
（`summarizeTranscriptFile`、持久化迁移、删除前抢救）另写 `transcriptRebuild: true`，
从而把已测量的历史与来源不可知的旧累计记录分开。

`dedupBySessionId` 先按 sessionId 和 project 分组，然后：

- **组内没有 run-scoped 记录** -> 普通累计副本继续 last-wins；但更新时间更晚的真实 transcript 重建可以按实际事件时间替代较旧重建快照，防止旧快照隐藏之后出现的 daemon 原生用量。
  Replay 也可能在同一事件时间返回完整重建及其有界尾部补充。两侧的 execution IDs 必须都是非空数组，每个 ID 都是非空字符串且不重复；完整重建还须包含全部尾部 ID，且模型、工具和文件计数能够覆盖它时，才优先采用完整重建。畸形、重复、新的或有冲突的身份仍保守保留，不能仅凭时间或 token 总量把它吸收掉。
- **组内有 run-scoped 记录** -> 保留各次不相交运行。运行窗口是半开区间：
  新运行的起点恰好等于前一运行的终点时保留。完全相同的 `[startTime, endTime)` 窗口以及部分重叠窗口，
  属于重复或有歧义的记录，收敛到最后一条。因此同一毫秒内相邻的各次运行也全部存活。
- **同时依据来源与窗口形状。** 普通未标记累计记录让位于运行增量，因为它可能又是重放虚增的副本。
  按事件重建的历史可与不相交运行并存；完全相同的窗口视为副本，不算两次消耗。
  新摘要携带成功响应和失败事件的本地 `execution_id` 集合。两边都有身份时，重建集合必须包含 run 的全部 id，且工具和文件证据必须覆盖它，才能替代该 run；
  不相交且非空的 id 集合表示独立活动，不是副本，也不能因窗口相同折叠。部分交集仍有歧义，保留已知 run，
  不把可能重复的重建再加一次。没有执行身份的旧摘要继续采用有界的旧覆盖规则：起点与模型、工具、文件证据必须覆盖 run，
  工具名称及成功/失败结果也必须一致；但相同的累计数字仍不能证明跨存储逐事件身份。
  transcript 重放没有技能调用通道，因此覆盖 run 已知的实际技能计数会保留在重建摘要中。
  按技能名称合并的计数器使用 null-prototype map，所以 `__proto__` 等名称仍是可枚举的自有键。
  有 run 与无 run 两条归约路径都按实际事件时间选择最新重建。
  重放指标不进入 live 身份集合；集合存放在指标对象之外的内部结构中，不改变 headless JSON 形状。
- **两类不同的时钟。** run 的时间戳是退出、`/clear` 或会话切换的墙钟，
  而重建结束于最后一个 transcript 事件。用户阅读回答后停留片刻再退出是正常的，即相差数分钟也不能等同为不同调用。
  绝不能直接比较这两类时间就声称发生了不同消费；覆盖由请求身份或有界的旧证据判定。
  重建证据不完整或存在歧义时，仍采用保守的已知 run 口径。

**精确的逐响应台账身份。** 真实 API 响应提供 `execution_id` 时，成功响应的台账行将其保存为可选 `executionId`，与台账行自己的随机 `id` 不同。
当前月读取以及已结束月份的 copy/merge 都保留这一证据。对 run-scoped 记录，符合条件的日 / 模型 / session 台账桶必须共同证明其非空 `successfulRequestExecutionIds` 的全部 ID；证明可以在一个本地日内完成，也可以跨多个本地日收集。
每个 ID 必须来自属于该记录的 session 的同一条响应行，不能把一行中的 session 与另一行中的 ID 拼成证明。
先收集每个目标 ID 在所有相关日 / 模型桶中的响应指纹，再决定是否可证：即使另一个日期或只有 API 耗时不同，该 ID 仍未证明。
按台账与日 / 模型惰性建索引保留候选，避免为每条 run 重扫整个桶。
执行 ID 是可选的：某次响应没有 ID，就使成功 ID 列表不完整，已知的匹配 ID 不能代替其余响应的连接证据。
owner-aware 读取保留 run 和台账，不用日期 / 模型 / 计数代替缺失证明，接受与其它未解决证据边界相同的已披露潜在重复。
各模型成功响应数也必须与被证明的 ID 数相符。消费计数比较必须承认 provider 已定义的等价口径，而不是无条件做算术相等：除下述 cache-only 归一化外，input 必须精确相等，不能把 cached 数之内的任意 input 差异视为同一 API 响应；output、cached、reasoning 计数、成功请求数与 grand total 仍严格检查。仅当原始 session input 为零、cached 为正时，允许台账以 exact cached 值作为代理 input，且台账总额等于记录的自洽总额，或恰好多出完整的 cached 部分。这兼容缺 input / total 的旧数据，但不能覆盖另一条独立消费；100-token 响应不能仅凭相同 execution ID 替代独立观察的 200-token 记录。缺 total 时逐 row 按自己的 `authType` 汇总 `inputTokens + outputTokens + (outputIncludesThoughts(authType) ? 0 : thoughtsTokens)`，不能把混合 OpenAI / Gemini 汇成任一 provider 的单一 flag；该合计只有在 session 的完整 input / output / reasoning 分项总额一致时才能匹配。缺少、空、不同或不完整的身份都不能通过精确 ID 路径删除另一条独立真实消费。
有界的 transcript / 所有权回退继续用于兼容旧数据，但缺失或冲突的 owning-root path 不能授权一次碰巧的连接。
具备归属信息的读取方不能把新的冲突身份降级成 session / 日 / 模型模糊覆盖；没有这类元数据的原始 legacy 日表保留兼容回退。
不完整的元数据宁可保留已披露的 legacy 潜在重复，也不由计数去猜事件同一性。旧记录缺 `project` 时，不能只因 session、时间窗与 token 相符便归入当前 project；没有真实归属证据，就得保守保留它与重建记录之间可能存在的重复，不把目录名或 sanitized 拼写当作项目归属证明。双方明确属于不同 project 的同 ID 记录仍分别保留。
这把成功响应与没有成功响应台账行的失败尝试分开，避免单桶覆盖误判。
可选 `executionId` 存在但不是字符串时，该台账行对聚合无效。

有 owning scope 的台账可以对本地真实 `transcriptRebuild` 使用同样的证明；显式 runtime-scoped 构建也可以跨 root 建立该证明。
普通累计记录并不因此变成运行增量证明。
调用方明确给出的当前 live 记录是另一个 owner 边界，而不是同 session 无条件豁免。
只有这条确切记录的请求 ID 完整、唯一、非空且没有记录的模型错误时，才允许这些 request ID 代替旧快照缺失的成功 ID 列表；
每个 ID 仍必须通过同一响应行指纹和模型成功数证明，不能给失败请求、未知连接或其它项目的同 ID 记录授权。
没有这类 ID 时保留该 live 记录与台账，不走旧的模糊回退去抹掉另一笔独立响应；活动请求 ID 尚未能在完整执行证据表中找到时，也不能被更早的台账覆盖。若活动记录只有部分响应已落盘，只扣减同模型、唯一响应指纹且与调用方活动计数相容的台账行，保留未落盘残量，不把整条记录再加到台账旁边。归并后的活动副本按 session / project 与完整 ID 集合确认归属，不比较数组顺序；任一预期响应指纹冲突都禁止部分扣减。
全局同 session、跨 project 的歧义不撤销另一 root 自己完整且归属相容的精确证明；该证明必须在这个 root 的 transcript / project 归属内独立成立，不能使用合并 token 总数代替。

跨 root 的内存证据表只提供日 / 模型、session 与执行 ID 元数据，token 计数为零。
只有精确 ID 证明使用证据日期与本地 root 日期的并集，并包含实际查询 root 的日期；空的全局台账不能隐藏另一完整 root 的日桶。正常跨日的响应可以使用完整本地证明；拒绝的是同一 execution ID 的响应指纹冲突，而不是日期数量。旧的 legacy fallback 仍只看本地 root 的日期及 owning transcript scope。

跨 root 的重复台账行必须有完整一致的响应指纹：原始 localDate、session、模型、执行 ID、认证类型、来源、响应时间戳以及全部响应计数（含 API 耗时）。
随机台账行 `id` 不参与同一性判断。只从内存聚合中扣减后续完全相同的行，不改磁盘台账；不同证据仍全部保留。
加与扣共用同一 provider 计数归一化，包含只有总量的行。台账自己的 session / 执行 ID 索引及 owning scope 随该 ledger map 一起复制；
不能错误地从 records 数组借 scope，否则归属证明会被清空。每份台账表按日 / 模型在私有 WeakMap 中保存 session→executionId→未加工响应行及其指纹集，只在证据完整时用于候选查找；合并执行证据会使派生索引失效，预算释放或证据不完整只能得到空证明，不复用旧索引冒充更完整证据。这些都是只读内存元数据，不向台账 / dashboard JSON 加字段，也不写盘。已有覆盖快照的 future 对账读取不能每次重复追加同一快照；迟到事件仍可被发现，真正新项目的首次迁移只在必要时写入一次，不让已知覆盖行无限增长。

**有界身份证明。** 月度 JSONL 仍然流式读取，但每份逻辑台账表（含 completed-month 与合并派生表）最多为身份证明保留 `MAX_LEDGER_EXECUTION_EVIDENCE_RECORDS`（10,000）条完整响应行。
流式读取或合并超过预算时，释放私有执行证据并标记不完整，不再保存完整响应行或第二套永久执行 ID 索引；每个有效范围内行的 session / 模型 / 日计数仍完整累加。
没有 execution ID 的行在私有内存中只保留日 / 模型 / session 存在性作为歧义证据，并计入上述同一预算，不另开容量；合并时同样保留这些元数据。即使达到预算后释放了完整响应行或指纹证据，仍保留这层用于否决误归属的歧义信息，而不是把它当作精确证明。它们不能被当成没有台账，也不能由 legacy fallback 用来抹掉具有已知执行 ID 的响应。
已结束月份聚合另行保存受同一预算限制的末日完整身份快照。只有窄窗口恰好从该日开始且文件签名未变时才复用快照；其他窄窗口重新流式读取以取得窗口内证据。此时计数与身份证据均来自同一次扫描，不与旧快照混用，因此窗口重扫期间的追加不会造成计数与身份证明版本错位。该月份内较早的行不会耗尽窄窗口预算，也不会因整月证明不完整而替换其末日精确身份。

超过上限后，`isCompleteLedgerExecutionEvidence` 为 false，不能把有限样本伪装成全量证据，不能使用该受限证据做新的精确 ID 证明或跨 root 台账扣减。各 root 的完整表与此受限合并证据独立查询，丢弃超限合并不会撤销本地仍然完整的响应证明。
run-scoped 的旧日/session 回退仍需唯一预期 transcript 路径；scoped 归属有歧义时保留潜在重复。
没有逐响应执行证据时，缺失的旧路径、未知项目或有限身份预算都不能变成新的精确 ID 证明。
无作用域 legacy 累计记录保留既有的有限日/session 兼容回退，但现代冲突身份证据仍否决 session / 模型捷径。
证据完整时，冲突或不完整身份仍是禁止模糊覆盖的否决，而不是 session / 模型捷径。
这只释放可重建内存证据，不改写 transcript、持久运行记录或台账行，也不宣称受限预算下能完成全部精确去重。

**独立迟到证据。** 公开 transcript 只与含内部 helper 调用的 run 共享部分身份时，主重建自身可能有歧义，不能再次相加；
但一个新 API 响应或错误只要带已知 run 没有的 `execution_id`，且可用时间严格晚于该 run 的落盘时钟，就作为临时 `transcriptSupplement` 保留。
它不是新 run，也绝不持久化为整段历史的权威记录。工具和文件计数没有执行 id 连接键，晚到的工具或文件记录不能用来证明先前 run 的覆盖；
保留已知 run 自身的工具耗时与文件变更，不让更晚的 edit 借计数覆盖关系冒充它。
补充按执行 id 分别构建，当前 live 调用与其它 daemon 调用共享尾部时，不会因为部分重合就删掉另一个独立调用。
这些补充只贡献模型 / API 计数及耗时，不增加 session、run 时长、工具 / 文件计数或 ended-run 次数。
若任何存活记录（含正常通过身份与非模型覆盖检查的全量重建）已有此 API 身份，则不重复加入补充。
无身份的旧 run 继续使用最早运行起点恢复不相交历史，同时仍可保留这类有明确身份的迟到调用；超出这条规则的未知身份或不可用时间仍是有界且公开的连接歧义，
不能用来证明一次新请求。缓存签名至少包含文件 `(mtimeMs, size)`、精确 `beforeMs`、`afterMs` 与排序后的已知执行 id 集合；
新 run 落盘改变归属时，不能错误复用旧归属下的补充。内存缓存不会让边界补充变成持久化副本。
无法解析的会话级起止时钟使整会话累计重建无效，但不能连带丢弃已经识别的边界后补充；
即使返回 `record: null`，这些补充也必须保留，而不是随无效会话时钟一起丢失。

来源标记、可选 `requestExecutionIds` 与 `successfulRequestExecutionIds` 数组及可选失败次数/耗时元数据都是增量补充；所有按 `version === 1` 过滤的读取方继续可用，无需 schema 迁移或就地改写历史。

定向查找仅当每个 id 都定位到唯一且验证过的 transcript 路径时，才直接读取已知文件而不枚举目录。
路径由匹配的持久项目元数据或调用方明确提供的当前工作区确定，可以跨越多个不同的项目目录。
在工作区由调用方明确提供时，同一项目中另一个已知 run 的 transcript 缺失只跳过该文件，
不再因此遍历所有项目目录；同一 session id 有多个候选目录、无法定位到 transcript 映射或文件已失效时，

先分别保留它与重放结果，再交给严格的消费身份归并；即使只留下一个真实 transcript 候选，
ID 或模型消费字段不一致时也保留两份真实记录。仅有完整一致的副本证据才允许合并。
在已确定的 root 内，彼此兼容的重建仍沿用原来的归约规则，更完整的后续快照覆盖旧快照，而不是重复相加。
部分身份，或同一请求集合却有冲突模型消费字段的记录，必须绕开这条普通归并路径，交给严格身份比较。
这样既允许正常的 transcript 追加，也不会把 100-token 与 200-token 的冲突当成同一份证据。

副本归并与台账覆盖是两件事：候选必须具备相同的 project/session 和同一非空、唯一、完整的执行 ID 集合，且 ID 数量等于记录的模型请求数。
模型名称按字典序对齐后，其请求、错误、input、output、cache-read、reasoning 与 total-token 计数也必须一致；
相同 ID 但 token 证据冲突的记录仍各自保留。API 与失败耗时是需要保留或归并的观测信息，不是为了对齐身份而丢弃的消费字段。
补充记录以及未识别或部分识别的记录从不参与。优先保留全局来源，使模糊的归属仍与其台账配对。
沿用的运行 / 重建身份、工具 / 文件与技能证据决定归并，能保留更真实的 API 延迟与观测信息，而不是为了对齐计数删除这些数据。
只有非重建快照在比较时临时视为 run-scoped；重建记录保留自身覆盖规则，并在对外提供或持久化前恢复原来源。对消费身份完全相同的持久非重建副本，即便写入窗口不相交，也允许折叠，避免把窗口差异伪造成第二笔 API 消费；不同 ID、不同消费计数或不完整出处从不因此合并。
被选中的旧 run 若缺少成功 ID，只能当组内所有已定义候选数组具有相同唯一排序内容时，继承对应数组。
冲突集合不能把全部 request ID 伪造成成功集合，也不能覆盖被选记录自己的成功 ID；缺失仍保守处理。
若不能唯一归约为一条，整组原记录全部保留。
这里不向另一个 root 借用聚合台账计数作覆盖，也不从日期、模型或聚合计数推导事件同一性；只有上述完整的执行 ID 证明可以跨 root。

**session id 不能跨 project 作为归并命名空间。** transcript 回放与持久运行归约分别保留 project/session 对，
即使同一个 runtime 根目录中出现相同 id 或相同时间窗。同一 project 内仍保留目录首项选择，
以及既有的同窗口计数与身份规则。project 仍是独立输入，不能从日期、模型或聚合总数伪造事件连接。
transcript 无法给出有效 project 时钟时，按文件保留已识别的补充，不让同 session 的首项规则吞掉它们。

已知 root 的台账检查使用私有内存索引，记录既有项目枚举中实际出现的 transcript 路径，
不增加内容读取，也不向台账添加 project 字段。同一 id 存在多个真实路径时，
不能让某个 project 的台账替换另一个 project 的运行。run-scoped 记录或真实重建在 owner-aware legacy 回退中需要其目标 transcript 实际路径才能替换；transcript 缺失本身不否决另一个 root 已精确证明的逐响应身份，存在冲突或来自多个 project 的 transcript 也不能授权该证明。
归属缺失或歧义时，保留独立记录与台账，不删除消费；可能保留的重复与无法溯源的旧重放一样，
是明确接受的边界，不是宣称完美去重。已被覆盖的普通文件利用目录项信息，避免额外 `stat`。
没有该索引时保留有界的旧判定作为兼容回退，不把它宣称为通用事件身份连接。

持久历史的快路径也必须保留这些归属信息。它只检查符合条件的记录的标准 project/transcript 路径，文件仍存在时才采用，不枚举所有项目。
scope 查找沿用重放使用的裸 session id 键，每条路径则按记录的真实 project 与 runtime root 构造。
不同项目中同 ID 的路径不能合并成一次授权；缺失或有歧义的证据继续保守处理。
`sinceMs` 补充豁免还同时绑定预期路径与实际解析 header 的 project/session 键：裸 session id 不能使另一 project 的同 ID 旧文件越界接受补建。
两个不同 project 键对应同一个 sanitized 预期路径时，双方都不获得豁免，不能选择最后一条记录；预期路径上的实际 header 不匹配时，该文件也不能成为补充。
项目元数据缺失时不授予路径豁免。显式 `sinceMs: 0` 仍允许正常发现，但不能把不匹配的 header 变成 future run 归属。
这些私有 path/key 映射不会向台账行或 dashboard 返回新增任何 project/path 字段。

台账按日 / 模型建立身份索引，并在每份表上缓存；raw-row 合并在初次创建时复制数组，之后仅按源数组原长度追加，避免逐次展开已累积的完整数组。
同一身份跨 root、但各根 transcript 的观测完整度不同时，工具、文件与技能分别选择该领域观测最丰富的完整 payload，不把重复副本相加；当工具 / 技能总计数相等时，则比较 `byName` 的 count、success、fail 完整度，工具还比较各项耗时，文件按新增 + 删除总行数选取完整载荷，不能把逐字段拼合或枚举顺序当成 richer。各模型保留最大的成功/失败时延，记录总时延取这些模型值之和，与指标序列化口径一致，权威运行时钟也继续保留。
不虚构工具身份：未知 legacy 与部分身份观测仍保留明确的保守去重边界。

**project 边界来自记录内容，而不是目录拼写。** replay 读取器从实际解析到的 transcript header 中
取得 sessionId 与 cwd，选择本 project 的 before/after/request-id 过滤；不通过项目目录名反推归属，
目录可能采用旧别名。replay 缓存按 owning root 分区：某个根目录只清理自身过期或已删除文件，
不抹掉另一根目录的暖缓存。只有文件 mtime/size、项目边界与时间边界都匹配时才复用。
仅发生变化的文件需要再次读取内容。没有边界约束的瞬态 transcript 不会仅因存在 cwd 就被标成 scoped project。
已有唯一 project/session 覆盖的 transcript 只有在缓存 `(mtimeMs, size)` 与当前文件一致时才可使用快路径；已覆盖文件追加后必须重新扫描。相反的 cache 身份必须重读 header。此例外不绑定新发现的冷 transcript：实际 header 才选择匹配的 project 过滤，普通缓存复用也要求先前观察到的 project/session 键。
另一个项目的持久候选只提供该项目的窗口过滤，不删除缓存中已观察到的实际 project 键；
若 transcript 的实际项目没有已知窗口，仍可命中暖缓存，而不会借用已记录项目的边界。
调用方裸 session 的 `beforeMs` 只用于声明的当前 project root；未提供该选项时保留旧调用方窗口行为。
删除前抢救的两次覆盖检查同样按 project/session 身份判断，不因为另一 project 的记录而放弃真实 transcript 的持久化。
按访问顺序保留 64 个最近使用的 root；淘汰只涉及可从真实文件重建的内存摘要，不删除持久记录、台账行或真实文件。
future ownership 不全局关闭缓存。私有签名包含已拥有的执行 ID 及其有界 future 时间窗；拥有快照被修改或删除后必须重新验证，即使旧摘要为 `record: null` 也不能复用。无关 project 的条目仍按普通暖缓存路径命中；未观察到 project 键的条目不提供 future 归属证明。

**会话钟与已结束运行的时间截止各有作用。** 恢复的会话钟可能在 UI 初次订阅之后才绑定；
通知携带目标 session id。另一个 session id 仍处于活动状态时，provider 忽略该更新；
只有 `startNewSession(targetId)` 提交目标 id 与对应指标时，才一并应用恢复时钟。
不带 owner 的旧时钟通知保持既有行为。只有显式的 `clockSessionId` 标记（包括没有 owner 的值）才读取 telemetry store 的时钟作为时钟更新。
普通指标通知保留 provider 当前时钟，不把另一个会话恢复出的值混入其快照。`resetLiveMetrics` 与持久化运行起点仍属于当前 run。

跨 root 归并组中存在时钟有效的权威 run-scoped 记录时，即使重建提供更完整的响应观测信息，也恢复该运行的 `timestamp`、`startTime`、`durationMs` 和 provenance。
损坏的权威时钟不得覆盖有效重建时钟；若已选记录的时钟同样损坏，可采用有效的原生候选时钟；没有有效替代时钟时，不虚构零时长证据。
若存在权威 run，其 provenance 继续优先，即使缺失重建标记也是有意这样恢复，而不是错误回退成原生标记。run / session 的日期归属仍取真实退出日，token / API 请求的日期归属仍取真实响应发生日。跨午夜验证必须分别检查这两个日期，不能把昨天的台账强行放进今天的 token 桶。

live 与普通 history 读取都使用完整持久历史决定 replay ownership 和“历史是否存在”，仅在返回 / 归约视图中应用读取时刻的 ended-run 截止。
不能用这项截止选择首次迁移或挖出无关旧 transcript。每次读取只捕获一次 `readAt`，replay ownership、outer/inner root 暂存及 ended/future 分区共用它。非有限的持久 timestamp 既不提供 future ownership，也不用于把普通 replay 截断到更早 run 起点，不能据此抹掉有效 transcript 证据。timestamp 恰好等于该时刻时归 ended，不会两个分区都不进，也不会因各 root 的时钟不同而重复归属。非有限 timestamp 即便没有可恢复的 transcript，也保留在保守持久化侧，不因两项时间比较都为 false 而消失，也不虚构响应日期。
明确属于 future run 的 API response/error ID 即使其事件早于 `readAt`，也从 replay 中排除。按 project/session 分别保存有限 future-owned 时间窗，不压成一个最早开始至最晚结束的区间；介于两次 owned run 之间的独立 API / 工具事件仍纳主重建，并推进实测时钟。落在拥有区间内也不能仅据此删除另一个独立 response ID（包括其它 model），只有已拥有的响应才可抑制；位于所有拥有区间外的 tool，或者 outer / inner 时钟冲突的 tool，不因更早乱序的 owned 响应而随 tool-only replay 被整体删除。只有响应本来会进入主重建或迟到补充时，才应用 API-owned 抑制；被时间边界排除的 future 行不能标记更早的独立工具史供删除。早于已知 future window 最早起点的工具证据独立于 API-owned 清除继续保留；只有没有这类独立证据的纯 owned tool-only 副本才被清理，时间窗或时钟缺失时保守保留。私有标记不写入持久字段；未知关系宁可保留潜在重复，也不能虚构逐工具身份。临时文件 header 损坏或乱序时，重建把恢复出的起点钳制到有效终点，使时长为零而非负数。尾行 timestamp 无效时，回退到最近一个有效纳入行，再回退到 header，不能因此丢弃已测得的工具 / 文件活动。
future run 已确有真实响应 ID、终点有限但起点无效时，只有有限且非负的 duration 才可推导 `[0, end]` 内的起点；同一有界起点必须同时约束普通 replay 纳入和 future 工具归属。无法建立有限有界起点的 identified future 记录不能把 supplement 截止往后延长，因而不能让另一个有实际日期的迟到响应消失在两个截止时间之间；但它仍会把自身的 `requestExecutionIds` 加入 `knownRequestIdsBySession`，防止已归属的 future 响应被再次产出为迟到补充。`dedupBySessionId` 处理 run 覆盖 run 时以 `candidateRun` 跨全部已保留项双向归并后再决定插入，避免被覆盖的桥接 run 残留在完整覆盖快照旁。精确 execution ID 匹配（`identifiedLedgerModels` 与活跃会话部分扣减）不再按读取端本地时区 `[startDay, endDay]` 截断，按原始 output/thoughts 与 cached-only 规则精确扣减并在旧历史超出 10,000 行预算时为当前活跃会话补读窄范围证据。已完成月份缓存合入同 `(day, model)` 时累加而非覆盖；已覆盖 transcript 的缓存快路径保留缓存项且不丢弃更新快照；目录 sanitize 碰撞下的 `supplementalTranscriptPaths` 校验只作用于窗口外豁免文件且不缓存被拒 `null`；`beforeMs` 缓存复用按扫描最大观测时间戳校验；daemon 台账根目录枚举仅纳入受信任的受管运行时（`listManaged().filter(r => r.trusted)`）。行时间不可读不能证明其属于 future window，不能由该边界截掉；时间窗无效时，匹配的工具计数也不能证明逐工具同一性，宁可保留不确定的一份观测，也不能删掉另一 run 真正较早的工作。
header 无法解析不得丢弃已测得的用量：只用实际纳入重建的 api_response、api_error 与 tool_call 的最早 / 最晚有效事件时间恢复时钟，不替无证据事件编造日期。没有有效权威 run 提供时钟时，选择最新且时钟完整的 native；纯 durable 副本归并使用实际入选 durable 的时钟，不能由 root 枚举顺序决定日期。无界 `all` 聚合保留非有限 timestamp 对应的真实消费，受限日期范围不把这些记录臆造为那一天的活动。
只有 `runScoped === true` 才将 future 行作为独立延后的 delta，与更早 ended run 隔离，并在精确跨 root 消费归并前回到实际所属 root。其它快照仍与 ended 记录一起归约。同一 project/session 的普通 future 累计快照若遇到明确的 future delta，旧副本让位于 delta；较新的普通累计快照在自身具有完整消费键，并由 `rebuildCoversRun` 证明其起点、请求 ID 超集、逐模型请求 / error / token 计数及工具 / 文件覆盖包含旧 delta 时，不得仅因旧 delta 存在而丢掉新增 ID 和相容消费。仅 ID 是超集但总消耗更低的快照不能删除旧 delta，未解决的普通累计冲突要与旧 delta 一起保守保留。这不是通用 last-wins：ID 不相交、证据不足 / 冲突或没有完整身份的记录仍须分开保留；其它 future 累计组不变。原生重建则另按覆盖证明处理，不能仅因存在 delta 就删除它。ID 的存在不是 run-delta 出处。replay-only 选项不返回这些持久 future 快照，但它们仍参与 replay 边界。绝不根据日/模型总量臆造会话归属。
非法 ID 条目逐项忽略，同数组的有效项仍可建立归属；非数组形状只不建立归属，不使整个历史读取抛出 TypeError。持久 JSONL 中不可作为身份的畸形 owner 对象在加载时隔离，不强制转成 session / project 键，也不影响同文件的合法记录。
transcript 补充仍保留明确的豁免，读取不会改写历史。
同一天中结束时刻晚于本次读取的运行，其已结束 session、工具与 session-record token 均被排除。
这一字段级截止**不会**删除成功响应的台账行：该行已经证明真实 API 消耗，并不是 ended-run 归属。
所以，带一条真实 100-token 台账响应的 future-ended run，仍向汇总 / 每日 token 贡献 100 token 和 1 次请求，
但它的 sessions/tools 为零。transcript 补充同样贡献实际 API token，但不伪造一个已结束运行。
若该持久记录本身是响应的直接证据，即使台账缺失，其未覆盖 token/request 回退也保留；在 `readAt` 之前仍不会因此生成 ended session 或工具计数。
既有日历日窗口不变；不能借用时钟不一致来删除真实消耗，只为让所有 tile 都显示零。

## 已实现方案（TUI 跨会话视图）

`/stats` 的历史区间读的是 `loadUsageHistory` + `aggregateUsage`，完全没有台账参与，因此带着同样的虚增：
实测 7 天为台账真值的 2.06 倍、30 天为 6.25 倍；平均延迟也虚高（某日为 24,057 ms 对真值 8,621 ms），
因为请求数这个分母被灌大了。

计数表的构建与窗口求和现在是 `usage-dashboard-service` 的**共享导出**——
`buildUsageDayTable(records, ledgerDaily)` 与 `sumUsageWindowByModel(table, startKey, endKey)`——
两个表面共用，因此不可能漂移。`recordTouchesLedgerDays` 同时向日表与环比提供唯一运行跨度覆盖判定，
不能各自另造口径。`TokenUsageDayModelTotals` 增加了 `apiDurationMs`，成功响应耗时来自逐请求台账。
失败次数与耗时使用 run 中可选的 `errors`、`errorLatencyMs`，共享表按模型只给被成功台账覆盖的模型补入这些数值，相邻模型未覆盖时也不能丢弃这些错误。
它不生成虚假的零 token 台账日，因此失败不能授权丢弃更早的真实成功会话；失败归属日沿用 session 记录，两个表面采用同一套算术。
补入前逐日 / 模型克隆台账合计，避免从缓存源反复构建面板时重复累加失败次数或耗时。

`loadStatsData` 每次读取台账时，从最早记录的起始日与环比前一窗口首日中较早者开始读，
使替换判定不依赖所选显示范围：即使今天还没有台账行，也不会因选择 Today 而把昨天的实际消耗错归到今天。
只有窗口求和受显示范围限制，覆盖发现不受其限制。随后以共享表替换当前 report 的
`models`、`totalRequests` 与 `totalLatencyMs`。只有某一侧所有活跃模型都有台账覆盖时，
该侧才采用台账口径；平常的周末即使既没有请求也没有台账键，仍不必退回记录口径。
只要存在真正未覆盖的活跃模型，两侧就都保留会话记录口径，不混合两种计量依据。
连续的空闲日不会人为生成零 token 台账行。相同起始日的并发打开共享一次未完成读取；
已结束月份聚合仅在文件 mtime 与大小未变时复用；读取前采样签名，迟到追加会使缓存失效并重新读取，
当前月及未来月份文件始终重新流式读取。
一份排序后的台账日期数组同时供日表与环比两侧复用，避免每条记录重复排序。
每次加载再基于这个月聚合重建日 / 模型表与新的 report 形状。连续活跃日只数 token 为正的天；
技能调用、文件与其它非 token 字段仍取自会话记录，不伪造模型 token 替身。

当前仍在运行的记录取自 `getLiveMetrics()` 与 `getRunStartTime()`，而非展示聚合；
活动判据和记录构造也与持久化写入方共用。会话 id 单独传入，因此只有重放历史、没有本轮活动时，
也能补回该会话尚未持久化的 transcript，而不伪造空的运行记录或把重放历史计费成新运行。
确有当前活动时，live 记录由同一个共享构造函数生成。历史已经归约，只取其当前会话的连续记录段
再做局部归并，不再对所有旧窗口做第二次全量比较。先前不相交运行及兼容的真实 transcript 重建，
各自保留 token 与会话粒度字段。原有 transcript root/path scope 仍附着于持久化数组；
只有合并 live 记录后才重建 project/session 键，否则其它项目的同名历史会被活动请求的台账错误删除。
它们仍是私有 WeakMap metadata，不向台账或 dashboard JSON 增加 project 字段。
原始 live 记录也传入 `buildUsageDayTable`，仅允许它自身在没有已持久化成功 ID 时以完整请求身份精确覆盖。

仍取自会话记录的：`sessionCount`、`totalDurationMs`、工具、变更行、技能，以及**项目**；
它们都按与 token 相同的本地日闭区间筛选。台账没有项目维度（#4479 的隐私边界），
所以按项目的 token 列无法由它修正，仍是记录口径——
这是一处被明确承认的、与已修正总量的不一致，而不是编造一个归属。

## 设计决策与理由

- **台账本就是按日用量的既定数据源。** #4479 选择「每次响应一条 JSONL、带本地日期与 auth type」
  正是为了回答按日 / 按月消耗；面板早于这次对齐，读的是会话摘要。
- **替换实际覆盖的模型 / session 条目，绝不把已覆盖请求重复相加。** 同一批请求同时存在于两个数据源。
  一条记录的 `[startTime, timestamp]` 跨度及其 session / 模型身份与台账覆盖匹配时，才剔除该模型条目。
  其它模型与独立 session 记录仍然累加。
- **与台账完全不重叠的运行沿用会话记录归属。** 这既保住了台账出现之前的热力图历史，也让关闭用量统计的用户
  那些天仍由记录提供数字。保守取舍必须明确：若某个已覆盖的模型同时跨过覆盖日与未覆盖日，该模型在记录中的
  整个条目会被剔除，因而无法按响应日拆分的未覆盖日部分也会少算。例如，一条 1,100 token 的记录跨两个日期，
  覆盖日台账有 500 token、另一日无台账时，总量显示 500 而非 1,100；会话级总量无法安全地把剩余 600
  按日拆开。未匹配的模型与 session 仍会保留。对这段有歧义的部分宁可少算，也不重复计算。
- **按日历日取窗口。** 日桶无法按小时切分，因此 `today`、`week`、`month` 现在都取整个本地日
  （`today` 不变；`week` 与 `month` 纳入完整的边界日，而不是滚动 `now - N*24h` 之后的那几个小时）。
  这让 summary 与按日分桶的图表口径一致。起始日期按当前本地日历日期减 7/30 天，定位到当日午夜，
  而不是将固定的毫秒数跨越 DST 变化后得到的本地日期；完整纳入边界日是有意保留的语义。
  在回退路径上该影响可测量且只限那一天：参考历史的 `week`
  窗口里，2026-11-12 从 4,110,008,866 变为 17,376,555,073 token，因为一个在该日凌晨结束的会话
  带着被重放虚增的历史。有台账覆盖时那天本来就会被替换。
- **归属无法事后修补。** 会话级总量不含日期信息，仅改过滤条件无法修复缺陷 3。
- **会话记录必须保留。** 台账有意不存 project 路径、工具计数、变更行数与技能调用（#4479 的隐私边界），
  因此无法替代非 token 的 tile。
- **载荷形状不变。** 面板 JSON 未变，因此 SDK 类型与 Web Shell 客户端都不需要新增字段。
- **一张表，两个表面。** 把建表与窗口求和提取出来，而不是为 TUI 再实现一遍，保持单一计量真相；
  提取之后重新核过面板在冻结台账上的精确性。
- **只比较已完成的本地日。** token 与会话记录的日桶没有日内分解，所以未过完的今天不能与完整的昨天公平比较。
  环比因此比较当前窗口的已完成前段与该前段之前、互不相交且同样天数的完整日。天数以本地正午按日历日计算，
  不依赖 `N * 24h`。显示的总量仍包括未过完的今天，但百分比专属于这个已完成日比较。
  Today 没有已完成日，直接不返回环比，而不是把当天假装成零。每日恒定 100 token 时，week 和 month 都为 0%，
  包括 00:30 和 DST 切换时；不编造日内分布，也不从不存在的数值构造乘数。

## 约束

- 面板路径不得写入 `~/.qwen`。
- **台账计量真实 API token 消耗，包括内部 helper 调用。** 开启用量统计后，`logApiResponse`
  记录它收到的每个真实响应的 token，包括 `prompt_suggestion`、`forked_query`、`speculation` 与 `side-query:*`。
  内部 prompt 内容仍不写入 transcript。若仅记录普通响应却在汇总时剔除整段 run，会漏掉同时发生的侧查询真实消费。
  旧行缺失的内部响应没有事件身份可重建，不得用日期、模型、计数或聚合大小猜测补齐。
  进入 `logApiResponse` 前已被过滤的调用、关闭用量统计以及 best-effort 写入失败，不在这项保证内。
- **provider 不报 total 时遵循 auth 语义。** 缺少 `total_token_count` 时，
  `apiResponseEventToTokenUsageRecord` 改用共享的 `outputIncludesThoughts`，而不是无条件加推理。
  OpenAI chat completions、OpenAI Responses、Qwen OAuth 与 Qwen subscription 的 output 已含推理；
  Gemini 类 provider 的推理另计。未识别 provider 的通用回退保持不变。
- **逐条读取时归一化旧合计。** 升级前的写入方可能在 `outputTokens` 已含推理时又把推理计入 `totalTokens`。
  台账读取在逐条聚合时依据 `authType` 采用只计一次推理的 output，并将 input 与该 output 之和带入按日 / 模型及查询合计。
  API 与导出摘要保留 provider 原样报告的 `outputTokens`；`totalTokens` 则使用只计一次推理的计费 output。
  这只改变读取视图，不写回或迁移旧行。provider 有正的总数、而 input / output 规范化分项之和为 0 时，
  读取方保留原总数，不把只有总数的响应误判为零消耗。
- **旧版托管用量保持封闭的 api 形状。** 失败耗时仍可供用量统计使用，但非 diagnostics 的托管序列化会移除
  model 与 source 的 `api` 对象里的这个新增计数，不扩展消费方恰好三个键的既有契约。
- **覆盖须对齐模型与共享会话身份。** 台账读取把持久化的 `sessionId` 索引保存在私有 WeakMap 中，
  在已完成月份缓存和已知 root 合流时保留。日表仅剔除实际覆盖的模型 / 运行条目，再与未匹配的真实历史求和，
  而不是覆盖整日。日期与模型相同本身不证明另一个 session 的活动可以替代记录。缺少该元数据的输入保留旧的有界行为，
  不宣称全局事件连接；ledger 的 `id` 与 telemetry 的 `execution_id` 仍是不同身份。
  没有 `runScoped` 标记并不证明一条记录就是重放副本；有 session 元数据时，某个 session 不在台账中，
  也不能仅因日期和模型相同，就将其重新归类为另一 session 的消费。
- 台账写入受 `config.getUsageStatisticsEnabled()` 门控。internal prompt id 禁止的是 chat transcript 记录，
  不是 token 计量；best-effort 存储仍不能保证每个响应都实际写入磁盘。
- 不得向台账记录加入 project 路径或内容。
- 不得就地重写或迁移既有的 `usage_record.jsonl`。
- 保持重放缓存的热加载延迟与去重顺序保证。

## 风险

- **记录跨日范围的部分覆盖。** 如果某个模型 / session 只在其跨日运行的部分本地日中有台账证据，
  就不能凭空补齐时间戳来按天精确分配该模型的全部花费。已覆盖的请求不重复计入，未覆盖部分仍没有精确逐日归属。
  未匹配的模型与 session 则保留保守的 record-day 归属，不再被无关台账整日覆盖。
- **台账读取代价。** 实测流式解析 771,906 条记录（约 304 MB、5 个按月文件）耗时 862 ms；
  两个数据源合并加载实测 29.4 s，仍由 transcript 重放主导，路由缓存 60 秒。
- **目录作用域。** 路由把每个已知 runtime 的 transcript 根目录与台账根目录组为一份来源，
  另加默认全局 CLI 来源。尽可能 canonicalize 根目录，消除尾分隔符差异；
  文件系统提供目录 dev/inode 身份时，还据此去除符号链接和大小写别名，
  不把大小写敏感卷上的不同目录合并；无法验证物理身份时不按字母大小写强行合并。
  不同 realpath 共享同一个 dev/inode 身份时，本次读取固定首个已确认的 canonical root 为代表，
  后续别名不会再拆出独立作用域。覆盖仅在每份配对来源内进行，不跨 root 混合并再猜归属。共享持久历史只读取一次；
  精确的 session/project 记录只与实际唯一 transcript 文件所属 root 配对，缺失或歧义归属留在全局保守来源。
  不以无关 ambient runtime 台账替代已知工作空间，也不丢弃全局或未映射记录。
  即使 transcript 根目录是相对路径、且对应 runtime 停用自身 token 台账，
  其 transcript 仍可提供 session、工具与文件变更；无法 canonicalize 的 root 沿既有逐 root 降级读取，
  不改映射到 ambient root，也不拖垮其他来源。
  这不改变保守归属无法精确到逐请求事实的边界。
- **存量历史大部分是重放。** 2,065 条持久记录中有 1,482 条（72%）所属 id 的台账请求数为零，
  合计 376,868,201,294 token。台账只从 2026-07-30 开始，且关闭用量统计的运行同样不写台账，
  所以这是重放规模的**上界**，并不能证明这些记录每一条都虚增。
- **跨升级时点的会话。** 已有运行增量时，来源不明的普通累计副本会被丢弃，因此有歧义的升级前活动可能被少算。
  真实 transcript 重建仍与后续不相交运行并存（见上文「有意的取舍」）。
- **按项目的 token 仍然虚高。** TUI 的项目表无法由台账修正，因此与它上方已修正的总量不一致。
- **按日历日取窗口现在适用于每个记录派生 tile。** token、会话数、时长、工具、变更行与技能都包括完整的
  边界日；TUI 上一环比窗口与当前窗口互不相交且已完成天数相同。daemon 按日的 `sessions` 仍表示结束运行序列，
  并不声称当日全部 token 都由当天结束的那些运行产生。Today 的展示仍包括未过完的今天，
  而环比若没有至少一个已完成的本地日就不显示。
- 本次改动之前写入的记录仍然虚增，因此本 PR 未转换的 `loadUsageHistory` 消费方
  （例如按项目的 token 列与修复前的回退窗口）对那段历史看到的仍是旧数字。只有新写入的记录是正确的。
- **缓存仅限已结束月份。** TUI 只复用文件签名未变的旧月份聚合，避免每次打开都重读数百 MB 台账，并合并并发未完成读取。
  迟到追加会使对应月份缓存失效并重新读取；当前月始终重新流式读取，因此下一次打开也能看到新 token。
  `_resetStatsLedgerCacheForTest` 除未完成读取外也会清除调用方的已结束月份缓存。daemon 仍保持独立的 60 秒数据源缓存。

## 验证计划

- 单元测试：台账覆盖的天是替换而非叠加；token 落在每次响应实际发生的那天；触及任一覆盖日的运行被丢弃，
  而完全不重叠的运行沿用记录 token；loader 按日 / 模型聚合、跳过更早的日与月、无台账时返回空表、丢弃非法与未来 schema 的记录；
  两种 provider 口径下的输出 tile。
- 路由集成：两个数据源都真实落盘，走真实 loader。
- 以独立台账扫描为准绳的真实数据 A/B，跑在台账的**冻结副本**上，使两臂读到完全相同的字节。
- 持久化侧：live 计数器的单元测试（排除重放、无重放时与展示聚合平价、reset、废弃 swap 的还原）；
  真实 `/resume` + `/branch` 夹具断言展示保留历史而 live 不保留；`/clear` 断言纯 resume 不写记录。
  另有一个两臂探针，分别驱动两个检出里真实的重放函数与落盘函数。
- 归约：单元测试覆盖运行标记与 transcript 来源标记、不相交运行全部存活、部分重叠与相同窗口收敛、
  旧累计记录沿用 last-wins、有歧义副本让位于运行增量，以及真实事件时间 transcript 重建与后续
  不相交运行并存。另覆盖混合重叠 / 不相交的组、完整覆盖替代、零长度跨源副本，
  以及含后续 API 活动的旧无标记迁移：只计入 run 起点之前的真实事件，不重复计算后续 run；
  按时间截断的补建不得另落为整会话权威快照。隔离真实文件 oracle 覆盖迁移加 live 的同类场景。
  同一文件按两个不同边界连续读取时给出不同的有界摘要；超过 mtime 窗口的已知旧 run transcript 被纳入，
  无关旧文件不被打开；相同 id 在缓存冷热时都选择目录首项对应项目。真实 fork 后追加无标记的 daemon 遥测，
  新活动恰计一次，时长只由原生事件推出；嵌套或字符串内同名标记不得导致整份大型工具载荷被解析。
- TUI：单元测试覆盖按天替换、按日归属、完全不重叠的运行、环比前一窗口走台账、平坦用量的等长环比、
  记录派生字段同样按日筛选，以及两次打开之间的新鲜读取。另覆盖纯重放不生成当前记录、
  live run 与旧的不相交运行合并、任一侧台账日覆盖不全时环比两侧都退回记录口径；
  并分别钉住完整 reset、live reset 与重放快照还原中的会话时钟与运行时钟。
  同时覆盖空记录的稀疏台账环比、零 token 技能活动不延长 token 连续使用天数，
  以及真实 context 形状下挂载组件时传入 live 指标和 run 起点。只归并当前会话的记录段，
  断言归并器输入不包含其它会话；成功初始化后绑定目标会话自身的时钟，
  live reset 不改变所显示会话的时钟，回滚再还原两种时钟。
  还通过真实文件验证 A 已持久化、B 未持久化时，有无新活动都恰各计历史一次，且 B 不被提前落盘。
  多个被覆盖记录在环比两个窗口中共享一次台账键枚举。
- 对每个新增守卫做变异见证，并写明实际跑过哪些套件。

## 验收标准

- 台账覆盖时，今日 / 7 天 / 30 天的 token 总量、请求数、输入、缓存与推理都等于同一窗口的独立台账聚合值，
  且每个被覆盖天的热力图 token 与缓存率一致。**已验证**：在参考历史的冻结副本上三个区间全部精确相等
  （`ALL_RANGES_EXACT=true`，0 个日不符）。
- 每个区间都满足 `inputTokens + outputTokens == totalTokens`。**已验证。**
- 会话粒度的 tile（会话数、工具调用、变更行数、技能）不受台账影响。**已验证**：与同一批记录在空台账下逐项相同。
- 跨三天的会话向三个日桶都贡献。**已验证**：单元测试与逐日热力图比对各一次。
- 热加载维持亚秒级，且面板路径不写任何文件。
- 相对改动前的 builder，在参考历史上的实测效果：今日 -59.4%、7 天 -75.8%、30 天 -85.9%
  （活动历史，故为近似值）。
- resume 长会话的那次运行只落盘自己的请求。**已验证**：用真实重放函数与落盘函数的两臂探针——
  400 条历史响应加一次真实请求，改动前落盘 401 个请求 / 400,000,005 输入 token，
  改动后落盘 1 个请求 / 5 输入 token，而两臂的展示聚合都保持 401 / 400,000,005。
- 同一会话的两次运行都能在读侧存活。**已验证**：同一探针在归约改动前读回 1 条 / 2,000 token，
  改动后读回 2 条 / 3,000 token。
- 真实 transcript 迁移与后续不相交 live run 并存。**已验证**：单元测试与隔离运行时上的真实 JSONL
  均为 1,000 + 200 = 1,200；`loadStatsData` 的 all-time 读数也相同，保留两条运行记录。
- 当前统计不把重放历史写成 live 记录；live reset 不改变会话时钟；环比两侧始终同口径。**已验证**：
  针对性套件与真实文件 oracle 中，纯重放不生成记录，显示时钟来自被恢复会话而运行起点独立前移；
  台账部分覆盖时为同记录口径的 -100%，两侧完整覆盖时为 +100%；当前 token 表的独立台账合计为 7,007。
  `SessionStatsProvider` 在 Ink 的 `startNewSession()` 后仍保留伪造时间设置的原始会话时钟；
  修复前，该测试真的让 Wall Time 前进到模拟的一分钟后。
- 存量历史的归约结果与之前完全一致。**已验证**：真实 `usage_record.jsonl` 2,065 条原始记录、
