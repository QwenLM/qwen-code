# Mount release for recovery-blocked Hosted Workspace turns

[English](workspace-execution-mount-recovery-block-release.md) | [简体中文](workspace-execution-mount-recovery-block-release.zh-CN.md)

## Status and scope

Implemented. This slice ends the cross-Session wedge of [#13800](https://github.com/QwenLM/qwen-code/issues/13800): a Hosted Workspace tool turn that goes recovery-blocked hands its Workspace execution mount back, so later tool turns of unrelated Sessions on the same storage proceed instead of parking forever on `409 workspace_busy`. It covers the plain tool lane, the Hook lane's Session-scoped owner and the MCP lane's Session-scoped owner, at every door where a turn holding the mount parks its Session blocked: the prompt route's recovery block, a turn owing its release to the cleanup debt whose cleanup failed or never ran because its terminal record did not land, and every parking arm of the recovery fleet's `POST /session/:id/managed-runtime/continue`. Out of scope: A1 itself ([#13533](https://github.com/QwenLM/qwen-code/issues/13533), fixed by [#13789](https://github.com/QwenLM/qwen-code/pull/13789)), daemon-death residue (the LOST family's existing sweep, `#12670` family), the `POST /session/:id/files/rewind` lane's per-request mount (a failed rewind parks the Session blocked without handing its mount back — a pre-existing leak tracked as a follow-up), and enabling `monitor_run` or the `child_run` `shell` kind.

## Problem and the named mechanism

A `recovery_blocked` Session wedged later turns of other Sessions on the same daemon: the journal stopped after `hostedModelAttempt` and before `commitMessage`, the model was never called again, no error, no terminal event. Runtime witnesses in the issue isolated the mechanism:

1. Every Workspace tool turn's Broker acquire passes `WorkspaceRuntimeTransport.acquire` → `WorkspaceExecutionStore.claim`, which keeps one `ma_storage_owner` row per local storage (`storage_key`, `storage_kind = 'LOCAL'`); its holder columns (`holder_key`, `binding_id`, `runtime_generation`, `runtime_session_id`) name the holding Runtime Session.
2. Only `finish()`'s full `release()` on the settled path frees the row. A turn that goes recovery-blocked (an uncertain outcome under the block-and-never-replay contract) throws `HostedToolRecoveryRequiredError` before any release, so a turn that parks alive by contract holds the mount forever. The Hook and MCP lanes hold a Session-scoped mount whose own releasers are vetoed by the same unproven work, so a blocked Session of those profiles holds it just as long.
3. Every later tool turn on the same storage spins on `409 workspace_busy` (`retryable: true`) with no error and no terminal event. Clearing only the holder of that row live-unwedged a parked turn in under a second while the blocked Session stayed blocked — the coupling is exactly the mount.

## Fix

The blocked turn hands back the mount — never the Runtime Session.

**Broker endpoint.** New broker-internal `POST /tool-sessions/{runtimeSessionId}:release-mount`, body `{harnessSessionId, mountClaimId}`. `RuntimeBrokerService.releaseMount` resolves only the resident Session Context (a dead Daemon's residue belongs to the LOST family's sweep and answers `503 runtime_reconciliation_required`), checks the Harness identity, and applies the sibling `:release`'s lifecycle fence: during a close, archive or delete the handback answers `409 runtime_admission_closed`, and that operation's own drain frees the mount. Under the Session Context lock it then requires:

- **The claim that owes the handback.** Every acquire carries a `mountClaimId` the Broker records under the same lock, so a later acquire of the same identity — a recovery re-drive, a load, a lane's next run — supersedes it, and an old handback answers `409 runtime_session_conflict` instead of freeing a live turn's mount. The holder and the binding generation cannot serve as this fence: a re-drive of the same Runtime Session gets exactly the same ones.
- **No unsettled work.** An in-flight control or any unsettled execution (background processes included — this path runs no sweep, so unlike the drain it excludes nothing) answers the retryable `409 runtime_session_busy`.
- **No writer that never proved it stopped.** A settled execution whose stored capture is neither `complete` (both streams sealed) nor `detached` (its live process is its own `:process` row) — `partial` or `unavailable` — may leave an escaped writer in the Workspace; the operator-recovery family fences exactly that Workspace. Settled rows never change, so this answers the final `409 workspace_writer_unproven`. The stored `deliveryStatus` cannot serve here: it stays `pending` forever for every Shell capture, and the commit lives only in the publication's admission outcome.

The check and the clear run under that one lock, so no acquire recorded between them can lose its mount. `RuntimeTransport.releaseMount` defaults fail-closed (`501 workspace_mount_release_unsupported`); `WorkspaceRuntimeTransport` clears the holder columns. The Runtime Session row stays `READY`, never `RELEASED`, so the recovery fleet keeps its adoptable identity.

**Claiming it again.** Before this slice a READY Runtime Session claimed its mount once, at its first acquire. Now every acquire of an existing identity — resident, stored `READY`, or a Hook owner's recovery acquire — calls `RuntimeTransport.reclaimMount`, which claims the mount again when the Session no longer holds it. The claim is holder-conditioned: a mount still held is left alone, and one a rival took answers the retryable `workspace_busy`, which the turn's acquire queue already waits on.

**Worker detach.** The worker keeps the handed-back Session's installation, since a re-drive reuses it. `WorkspaceRuntimeTransport` records the detach as owed when it clears the holder of a `READY` Session, or of a `RELEASING` one that still holds the mount because its cleanup release failed at the worker, so that Session's later full release still dispatches the provider release and the Workspace deactivation instead of taking the absent-holder shortcut. The shortcut keeps serving a Session that never installed anything, which holds no mount to hand back. The debt is in memory; after a Broker restart it falls back to the worker's own lifetime.

**Daemon.** `HostedWorkspaceBroker.acquire` records a fresh claim before the request leaves, so a reply lost after the grant still names it, and `releaseMount(claim)` sends it. A turn that parks blocked calls `releaseForRecoveryBlock()` at every door: `executeHostedTurn` on the four recovery-required errors (`monitorWakeNeedsRecovery`), when a settled turn's owed cleanup release fails, and when a turn owing that cleanup exits before running it because its terminal record did not land (the durable cleanup debt keeps retrying its full release; the mount does not wait for it), and the continue route's single exit for every arm that leaves the re-drive blocked. The lane picks the owner:

- The plain lane hands back its broker's latest claim, or the takeover branch's original identity; a turn that never sent an acquire holds nothing and sends nothing.
- The Hook lane's owner (`HostedHookSession.mountHandback`) and the MCP lane's owner (`HostedMcpSession.mountHandback`) hand back their Session-scoped mount only when their own work is proven. The Broker cannot see a Hook run or an MCP operation, so a Hook execution that neither has a result nor provably never dispatched, a pending occurrence, an MCP operation in recovery, a configuration in flight, or a Hook run sharing the MCP owner keeps the mount. Each owner stays booked as acquired, so its close still runs the full release, and its next acquire claims the mount again.

A failed attempt is logged, never thrown — the block verdict must reach the Session, and it waits for the first attempt only up to a short bound. A lost reply, the busy refusal and the Broker's internal error retry on a widening backoff with a steady one-minute tail; a lane's unproven work retries the same way, so the mount goes back once that work settles. Every other answer is final. The Session's close does not stop the chain, because it never frees a parked turn's mount; the daemon owns the chain and stops it at shutdown, and the log names each distinct failure once.

## Alternatives considered

- Full `broker.release()` on the block transition: rejected — it persists `RELEASED` forever, and the recovery fleet re-adopts the same READY identity.
- Fencing the handback by binding id and generation, as the cleanup release does: insufficient — a re-drive of the same Runtime Session has the same binding and generation, so only a per-acquire claim tells a stale handback from a live one.
- Dispatching the worker detach on every absent-holder release: rejected — a Session whose acquire never installed anything would fail its activation release forever and stay `RELEASING`.
- Server-side lease TTL with heartbeat and steal-on-expiry: rejected for this issue — schema, renewal and steal protocol machinery disproportionate to the named mechanism; the live Daemon can and should act at the transition it owns.
- Claim-time eviction keyed on journal `recovery_status`: insufficient — the recovery block settles Daemon-locally without persisting to the journal, so such an eviction would not fire.
- Bounding the Daemon's `workspace_busy` queue: converts the wedge into a named failure but never lets a fresh turn complete against a leaked mount, and fails turns queued behind a genuinely long-lived holder; the prompt deadline already bounds the wait.

## Validation and acceptance

- Broker unit and contract tests: a resident handback keeps `READY` and counts zero full releases; a crossed Harness answers `runtime_session_conflict`, and so does a claim a later acquire superseded, while the later claim lands; a lifecycle authority answers `runtime_admission_closed`; a non-resident Session answers `runtime_reconciliation_required`; an unsettled execution, an in-flight control and a settled execution whose background process still runs each answer `runtime_session_busy`; a `complete` capture whose stored delivery stays `pending` hands back; `partial`/`producer_lost` and `unavailable`/`storage_failed` answer `workspace_writer_unproven`; a re-acquire after a handback claims the mount again. The repository probe runs the same contract on the in-memory store and on H2 through the JDBC store.
- Transport tests (`WorkspaceRuntimeTest`): the handback dispatches no detach, and the later full release dispatches the provider release and the deactivation once while a rival keeps its claim; a handback after a cleanup release failed at the worker leaves the retried release reaching the worker and the deactivation, while a never-installed Session's handback still owes nothing; a re-claim is refused while a rival holds the mount and lands once it is free.
- Daemon unit tests: the handback sends the claim of the acquire that owes it, including after a lost acquire reply; a turn that never acquired sends nothing; the busy refusal keeps the handback owed on the cadence and logs once; a lost reply earns a re-send; each final refusal stops after one attempt; the block verdict does not wait out a hung handback; the daemon's shutdown stops the chain; the Hook and MCP lanes hand back through their owner. The Hook lane hands back once its work is proven and keeps the mount while an outcome is unknown; the MCP lane does the same for an unknown operation and for a shared Hook run, and both claim the mount again on their next acquire.
- Route tests: a prompt-driven turn that goes recovery-blocked through each of the four recovery-required error families hands the mount back exactly once and never sees the full release; a settled turn whose owed cleanup release fails, a turn owing that cleanup whose terminal record cannot be written, and a continued Turn that goes recovery-blocked again, do the same.
- Real-stack IT (`HostedWorkspaceConcurrencyIT#mountReleaseFreesHeldStorageAndKeepsTheSessionReady`): a rival acquire answers `workspace_busy` while held; the handback refuses `runtime_session_busy` with an unsettled execution and `runtime_session_conflict` for a foreign claim, then lands after settlement; the holder columns clear; the Runtime Session stays `READY`; the rival acquires; a re-drive of the holder answers `workspace_busy` while the rival holds and claims the mount again once it is free; the holder's full release then settles `RELEASED`.
- Fault-gate ITs (`HostedWorkspaceToolTurnIT`): the families whose work settled hand the mount back with the Runtime Session `READY` — including a lost release that parks the Session through its owed cleanup — and `prepare-twice`, whose execution never settles, keeps it; an earlier case's owed handback may still retry while the next case runs, and the drivers forward it outside that case's ledger.

Restore the mechanism — drop the handback at the block transition — and the route witnesses see no handback, the IT sees the holder pinned, and the rival wedges.
