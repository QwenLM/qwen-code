# Compression request admission

[English](2026-10-19-compression-request-admission.md) | [简体中文](2026-10-19-compression-request-admission.zh-CN.md)

Status: implemented for [#9455](https://github.com/QwenLM/qwen-code/issues/9455).

## Problem

Compression sends the whole history to a summarizer. The longer a session gets, the more it needs compressing, and the larger that request becomes, until the request no longer fits the model's own window. Automatic, reactive, and manual `/compress` compaction then fail the same way the main request did, and an oversized session cannot recover.

The cold path clamps its output budget to the room the estimate leaves (#7960), but floors it at 1. Once the estimated input fills the window it still sends the request, now with `max_tokens: 1`, which the provider rejects or answers with a one-token fragment. The only size check covered a distinct compaction model. When the main model also compresses, nothing stopped the request.

## Current state before this change

- The cold request is the slimmed history (media stripped) plus the compression prompt and directive. Its size is a char/4 estimate.
- `computeCompactionOutputBudget` returns `min(20K, window − estimate − 1K)`, floored at 1.
- A failed side-query returns `COMPRESSION_FAILED_API_ERROR`. It is tried once (`maxAttempts: 1`).

## Goals

- Never send a compression request that cannot leave the summary a usable output budget.
- When the history does not fit, reduce it in bounded stages that keep complete tool interactions, the user's original request, and the newest context.
- Stop locally with a clear input-too-large status when no reduction fits.
- Keep conversations that already fit on the same single-pass path.

## Non-goals

- A more accurate estimator. A fixed per-language multiplier over-counts dense CJK text by roughly 2× (measured in #9541) and refuses sessions that would compress, so the estimator is unchanged.
- The cache-sharing request. If it fails, compression falls back to the cold path, which this change covers.
- Compacting with the previous model after a model switch.

## Design

### Admission

A cold request is sent as today when its output budget is at least the minimum: `MIN_COMPACTION_OUTPUT_TOKENS` (4,096), or a quarter of the window when that is smaller. A fixed 4,096 would take half of an 8K window and all of a 4K one, which self-hosted deployments do run. Below the minimum, the request is reduced first.

### Reduction stages

Each stage stops as soon as the estimate fits the target. The target leaves the summary a quarter of the window, up to 20,000 tokens. That is never below the minimum.

1. **Truncate tool payloads.** Tool results, tool-call arguments, and model text are cut to 4,000 characters, reusing the payload-overflow cap (#10380). With `preserveUserText`, the text the user typed stays whole up to 32,000 characters (`PRESERVED_USER_TEXT_MAX_CHARS`); past that, one pasted message could outgrow the window and no reduction would bring the request under it. Content qwen-code attaches to the user turn on the user's behalf (@-mentioned files, MCP resources, referenced sessions, the note written for an MCP resource that returned nothing, and the context added for an @-mentioned MCP server or extension, and a file attached to hosted input) is truncated like tool output. The part that holds the request is marked with `partMetadata['qwen-code:typed-prompt']` (`markTypedPrompt`) by the code that builds it and knows which part that is: `LlmClient` for a prompt or its retry sent as a plain string; the CLI's @-command processor for a user's prompt; a command's expanded prompt in every front end (Ink, OpenTUI, headless, ACP), with file content an `@{path}` injection added left unmarked; input steered in while tools run (Ink, OpenTUI, ACP); the ACP session's prompt, including one with no text, whose `@uri` pointers stand for its attachments, but not the pointers beside a command's expansion, which is the request there; and hosted serve's prompt. Scheduled prompts and notification batches are not marked when they are sent: a `/loop` tick sends text the harness wrote under the same message type. Two later steps mark them anyway: a retry after a failure, which `LlmClient` marks like any retry when the prompt is a plain string, and the expansion of a command the prompt runs, marked like any command's (in Ink only when it is built as parts, since a plain-string expansion is sent under the scheduled type). That text is usually the turn's only text, which the positional rule reads as typed too. In a marked turn only marked parts are typed, whatever the layout; every other part is attached, including content no header names, while reminders, hook context and the memory snapshot are neither. `partMetadata` stays client-side: the native generator strips it, the other converters never serialize it, and the session file keeps it, the ACP session's record of the prompt included. A turn with no mark (recorded before the mark existed, a subagent task, a scheduled prompt, the previous summary) keeps the positional rule, so its text is never dropped: its first part is typed and never taken for attached content, even when it starts like a header; everything from the first part that opens attached content to the end of the turn is attached; and hook context and the memory snapshot, which carry their own markers, are never typed. The headers are shared with the code that writes them (`utils/attached-content.ts`). Closing markers are not trusted, since `--- End of content ---` carries no nonce and a file can contain it. A wrapped `<system-reminder>` part longer than the cap has its body cut the same way and its closing tag added back: cut like other text, it would lose that tag and read as open over the text after it.
2. **Condense older turns to the user's messages.** `condenseToUserMessages` keeps the newest turns. They start on a model turn, so no function call is separated from its response and roles keep alternating. Everything older becomes one user message, within the room the kept turns leave, that quotes the user's messages. The kept turns are first chosen to leave the quotes a quarter of `maxChars` (up to 64,000 characters); the quotes then take whatever the kept turns actually leave:
   - the first message and the newest are always quoted. After an earlier compaction the first holds that summary, so it may take up to 32,000 characters, at least half of what the newest leaves when the middle messages need the rest; the newest takes up to 8,000;
   - the middle messages fill newest-first, skipping one that does not fit so that shorter ones behind it still can;
   - every other quote is capped at 8,000 characters, and the whole block, note included, at 64,000. A quote that is cut keeps its start and its end, since a long request often ends with the question;
   - user text that rides a tool-result turn (input steered in while tools ran) is quoted, the tool output is not;
   - `<user_message>` and `<system-reminder>` tags inside a quoted message are escaped, attributed and otherwise disguised ones included, so a quote cannot close its envelope or forge another, nor carry a live reminder the literal strip missed;
   - wrapped `<system-reminder>` parts are not the user's words and are left out whole, so they cannot fill a capped quote ahead of the prompt. The IDE context the CLI prepends to the prompt's own part is stripped: a complete reminder block at the start of that part whose first line is one of the two IDE context openers (`IDE_CONTEXT_OPENER`, `IDE_CONTEXT_CHANGES_OPENER`, shared with the code that writes it). Any other reminder block, including one the user wrote at the start of their message, and a tag anywhere else are the user's, kept and escaped. A marked part is never taken for an injected reminder, even when the IDE context opens it and the user's text closes it with a reminder tag;
   - the notice an ACP mid-turn message gets when its attachment cannot be resolved is kept beside the quote;
   - content attached on the user's behalf is named, not quoted: `[Attached, not quoted: src/app.ts]`. At most 8 names of up to 120 characters are listed, each flattened to one line without angle brackets and never cut inside a surrogate pair, since names come from labels and paths the user does not control;
   - a note says how many assistant and tool messages, and how many middle user messages, were left out, and calls the quotes verbatim only when none was shortened. The note, the quote tags and the separators are all counted, so the block and the kept turns stay within the target;
   - when that room cannot hold the first and the newest message at 2,000 characters each (`CONDENSED_MESSAGE_MIN_CHARS`), or whole when shorter, the kept turns' text is first cut to 500 characters; the files and images they touched are restored after compaction anyway. If the room is still too small, as a wide parallel tool batch can make it, no turn is kept and every user message is quoted instead. Only when even that cannot hold the minimum does it return nothing, so no request goes out that has lost the user's words.

   Assistant replies and tool output are dropped first because files can be re-read and commands re-run, while the user's words exist nowhere else. The summary prompt already asks for `primary_request_and_intent` and `all_user_messages`, and the quotes feed both.

If the reduced request still cannot leave the minimum, compression returns `COMPRESSION_FAILED_INPUT_TOO_LARGE` without sending anything. It counts toward the failure breaker like other failures.

### One retry after a context-length rejection

The estimate can still run low, notably for dense CJK text. When the provider rejects the cold request for context length (`getContextLengthExceededInfo`), compression retries once with a smaller request, sized from the rejection itself:

- **Window.** When the rejection names the whole context window (`limitKind: 'total'`) and it is smaller than the configured one, the retry uses it. A limit whose wording leaves its kind open ("prompt is too long: N tokens > M maximum") is used the same way once the rejection's own prompt count is past it; a model inferred at 1M and served at 200K first shows its real window there. A self-hosted server can run a smaller window than the model's own, and the rejection is the first place it shows.
- **Prompt count.** The retry takes the rejected prompt's own size from the rejection. "You requested N tokens" with no breakdown counts the requested output too; that total is taken as an upper bound on the prompt, since the transport can lower `max_tokens` below the budget compression asked for (a configured or model output cap), and subtracting that budget could undercount the prompt. A count far below the request's estimate, or one under which the request would have fit the limit the same message states, describes some other request and is ignored.
- **Only the output overran.** When the prompt leaves the summary its reserve (a quarter of the window, up to 20,000 tokens), the same request is sent again with `max_tokens` lowered to the room the count leaves, which is never below the reserve. When that room is no smaller than the budget sent, the count says the request fit this window, so the server's window is smaller by an amount the message does not state, and the retry takes the 60% step instead.
- **Cut the overflow.** Otherwise the retry removes the overflow (prompt count + reserve + 1,024 − window, or prompt count + 1,024 − the input limit when the rejection states one and that is larger) from the estimate, tool output first, and asks for the reserve. char/4 usually under-counts, so an estimated token removed takes at least one real token with it, and the prompt fits whatever mix of dense and sparse text remains. A ratio of the count to the estimate would not: the user text the reduction keeps is often denser (CJK) than the tool output it removes (ASCII), so the ratio underrates what is left. When the count runs below the estimate (sparse ASCII), an estimated token removed takes less than one real token with it, so the cut grows by that ratio.
- **Overflow cannot be cut.** When no reduction removes the whole overflow at one real token per estimated token, less suffices if the removed text is as dense as the rest. Rather than refuse, the retry is then sized by the rejected prompt's average density, its count over its estimate, and is at least the 60% step smaller. It overruns only when the text kept is denser than the text removed, and then fails like any second rejection.
- **No counts.** The retry aims at 60% of the rejected request's estimate, or less when that is what leaves the reserve.
- **No fit.** When no reduction leaves the minimum in that window, or none gets any smaller, the retry is not sent and compression returns `COMPRESSION_FAILED_INPUT_TOO_LARGE`. A retry rejected for context length again returns the same status, not an API error.

A second failure, or any other error, returns `COMPRESSION_FAILED_API_ERROR` as before.

`getContextLengthExceededInfo` reports the prompt's own size (`promptTokens`) only from wording that states it apart from the output budget: OpenAI's "resulted in N tokens", the completion broken out of "you requested N tokens (… in the completion)" (OpenAI, DeepSeek, older vLLM, OpenRouter), Anthropic's "prompt is too long", vLLM's "your prompt contains N input tokens" and "your request has N input tokens", Gemini's older wording, llama.cpp and SGLang. A "you requested N tokens" total with no breakdown is reported as `requestedTokens`; one that names only the output ("you requested N tokens in the completion") gives no count. Each wording is matched within a single fragment of the error, so a number from a sibling field is never paired with it. `actualTokens` keeps the figure the reactive path has always read. vLLM's "contains at least N" is where tokenization stopped, not the prompt's size, and stays limit-only.

### Truncated summaries

A summary that opens `<state_snapshot>` and never closes it is dropped as `COMPRESSION_FAILED_OUTPUT_TRUNCATED` when the reported usage shows its request filled the window it was sized for: prompt plus output count within 1,024 tokens of that window. A server can stop the output where its window ends instead of rejecting `prompt + max_tokens > window` (llama.cpp's server does), so the reported output count stays below the budget requested and the existing threshold check cannot see the cut; the prompt and output counts still add up to the window. Without that sign the summary is kept, as before this change: a model can end without closing the tag, and dropping every such summary would trip the failure breaker. An output count estimated locally, when the server reports only the prompt, is not that sign. After a retry sized for a smaller window the rejection reported, that window is the one checked. A summary without the tags is unaffected. Only closed `<analysis>` blocks are set aside before the check: real models often quote the compression directive, `<analysis>` tag included, inside the snapshot, and stripping from that quote to the end would take the closing tag too. The first opening tag that starts a line is the one checked: a tag named mid-sentence, before the snapshot or after it, opens nothing. The cost is the opposite shape: a summary that first quotes a complete example snapshot and is then cut inside its real one passes. The usage-based guard missed that shape before this change too.

### Accounting

A reduced request no longer describes the history it replaces. Its reported usage is therefore not used to derive the post-compression count. The visible-history estimate path is used instead, as it already is for payload-overflow compactions.

## Decisions and rationale

| Decision                                              | Rationale                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Keep the char/4 estimator                             | It under-counts, so a refusal based on it only happens when the request cannot fit. #9541 replaced it with a byte-weighted estimate and refused Chinese sessions from about 50% of the window.                                                                                                                                                                                               |
| Drop assistant and tool content before user messages  | Files can be re-read and commands re-run. The user's words exist nowhere else (Codex keeps them verbatim for the same reason).                                                                                                                                                                                                                                                               |
| Cut at a model turn                                   | Keeps function calls and responses paired, and keeps roles alternating after the quote block, without parsing turn structure.                                                                                                                                                                                                                                                                |
| A single retry                                        | Compression stays best-effort and does not block the user. The rejection's own numbers make one well-sized retry enough in the common case.                                                                                                                                                                                                                                                  |
| New failure status                                    | Users and telemetry can tell "too large to compress" apart from an API error.                                                                                                                                                                                                                                                                                                                |
| A quarter of the window as the minimum below 16K      | A fixed 4,096 leaves an 8K window little room for history and a 4K one none. A summary that does not fit the smaller budget is dropped as truncated, and the history is kept.                                                                                                                                                                                                                |
| Cut the overflow rather than scale by a ratio         | A ratio assumes every part of the request is equally dense. The retry keeps user text and removes tool output, so a ratio underrates what is left. Removing the overflow at one real token per estimated token fits whatever remains, and the retry's `max_tokens` comes from the count, not the estimate.                                                                                   |
| Mark the typed prompt where it is built               | The layout differs: the CLI writes the prompt first, the ACP session writes it last. Attached content has many producers and gains more; the request is built in a few places that know which part it is (see Validation). A turn with no mark is read by position, so a path that does not mark loses nothing it had before. A closing marker is not trusted, since a file can contain one. |
| Drop an unclosed snapshot only when the window filled | A server that stops the output at the end of its window reports a count below the budget, so the filled window is the sign of the cut. Without it, an unclosed tag may only mean the model skipped it, and dropping those summaries would trip the failure breaker. Summaries without tags are left alone, since weaker models may skip the format.                                          |

## Risks

- A summary written from condensed input knows less about assistant work in the condensed part than a full-history summary would.
- In a turn with no mark, attached content is recognized by the headers qwen-code writes; text attached some other way, such as a URL media transcript, is treated as typed and kept whole up to 32,000 characters. Text spliced into the prompt part itself, such as the CLI's IDE context, is kept as typed in the truncation stage; quotes leave it out by its opening line. If that line ever changes without the shared constant, the IDE context is quoted, escaped, rather than any of the user's text dropped.
- One turn can mix a marked part with unmarked request text when the curated history merges two adjacent user turns (after an invalid model reply is dropped, or a failed prompt is left in history) and one came from a path that does not mark. The unmarked text is then named as attached, not quoted.
- A `/loop` tick's instructions are quoted like a user message: read by position when unmarked, and as typed when a retry or a command's expansion marks them.
- Without counts in the rejection, a 60% retry may still be too large for very dense text. Compression then fails as before, without sending a third request.
- Cutting the overflow assumes each estimated token removed costs at least as many real tokens as the whole request averages, or one when the average is above one. When the text removed is dense too, such as CJK tool output, the cut removes more than needed. When the full cut cannot be built, the retry falls back to the average density, which can overrun if the text kept is denser than the text removed; compression then fails after the one retry.
- On windows below about 16K a reduced request leaves the summary a quarter of the window, which a long summary may not fit. It is then dropped as truncated, and the history is kept. At 4K the condensed input is little more than the first request.
- A server that stops the output at a window smaller than the one the request was sized for, or a transport output cap below the budget, can cut a summary mid-snapshot without the usage reaching that window. Such a summary is kept, as it was before this change.

## Acceptance criteria

- No cold compression request is sent with an output budget below 4,096 tokens, or a quarter of the window when that is smaller.
- A request that fits is sent unchanged.
- A reduced request quotes the first and newest user messages, whole or with their start and end and at least 2,000 characters each, starts its kept turns on a model turn, and keeps every function response after its call. It never quotes attached content as the user's words.
- No compression request is sent without the user's words when the history has any.
- An irreducible request returns `COMPRESSION_FAILED_INPUT_TOO_LARGE` without sending it, or without its retry when a rejection showed that no retry fits, or after its retry was rejected for context length too, and the CLI shows a non-empty message for it.
- A context-length rejection leads to at most one smaller retry. When the rejection reports a window, the retry fits it. When it reports the prompt's size, the retry either resends the same input with less output room, never below the reserve, or removes the overflow and asks for the reserve.
- A summary cut off inside its `<state_snapshot>` is not persisted when its reported usage reaches the window its request was sized for.

## Follow-ups

- Cache-sharing admission against an anchor from another route.
- Compacting with the previous model before switching to a smaller window.
- vLLM's "`max_tokens` cannot be greater than" rejection is not recognized as a context overflow. Classifying it would change the main chat path too.
- A server that drops messages from the front instead of rejecting (Ollama's default) sends nothing to retry from, and the condensed quote block is the first message it drops.
- A CJK-aware upper-bound estimate to size the first request's output budget, so dense sessions are not rejected before the retry corrects them.
- A per-part density floor (for example, ASCII at one token per four characters and CJK at one per two) would let the overflow cut remove less when the text it removes is dense.
- Anthropic's "input length and `max_tokens` exceed context limit: P + C > L" is not recognized as a context overflow. Recognizing it would change the main chat path too; for a retry it states the prompt's size directly.
- In a turn with no mark, text attached by other means, such as URL media transcripts or the attachment context an ACP client sends (its text comes from the client, with no header qwen-code writes), carries no recognized header and is treated as typed. Sessions recorded before the mark existed have no marks.
