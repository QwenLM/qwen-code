# Compression request admission

[English](2026-10-19-compression-request-admission.md) | [简体中文](2026-10-19-compression-request-admission.zh-CN.md)

Status: implemented for [#9455](https://github.com/QwenLM/qwen-code/issues/9455). Keeping the user's messages whole in a reduced request is a follow-up ([#14953](https://github.com/QwenLM/qwen-code/pull/14953)).

## Problem

Compression sends the whole history to a summarizer. The longer a session gets, the more it needs compressing, and the larger that request becomes, until the request no longer fits the model's own window. Automatic, reactive, and manual `/compress` compaction then fail the same way the main request did, and an oversized session cannot recover.

The cold path clamps its output budget to the room the estimate leaves (#7960), but floors it at 1. Once the estimated input fills the window it still sends the request, now with `max_tokens: 1`, which the provider rejects or answers with a one-token fragment. The only size check covered a distinct compaction model. When the main model also compresses, nothing stopped the request.

## Current state before this change

- The cold request is the slimmed history (media stripped) plus the compression prompt and directive. Its size is a char/4 estimate.
- `computeCompactionOutputBudget` returns `min(20K, window − estimate − 1K)`, floored at 1.
- A failed side-query returns `COMPRESSION_FAILED_API_ERROR`. It is tried once (`maxAttempts: 1`).

## Goals

- Never send a compression request whose input leaves the summary no output room; below a usable budget, reduce it first.
- When the history does not fit, reduce it without dropping a turn, so every tool call keeps its response.
- Stop locally with a clear input-too-large status when the reduced request does not fit either.
- Keep conversations that already fit on the same single-pass path.

## Non-goals

- A more accurate estimator. A fixed per-language multiplier over-counts dense CJK text by roughly 2× (measured in #9541) and refuses sessions that would compress, so the estimator is unchanged.
- Keeping the user's messages whole in a reduced request, or dropping older turns to make room. Both need to know which text the user typed, and are left to a follow-up (#14953).
- The cache-sharing request. If it fails, compression falls back to the cold path, which this change covers.
- Compacting with the previous model after a model switch.

## Design

### Admission

A cold request is sent as today when its output budget is at least the minimum: `MIN_COMPACTION_OUTPUT_TOKENS` (4,096), or a quarter of the window when that is smaller. A fixed 4,096 would take half of an 8K window and all of a 4K one, which self-hosted deployments do run. Below the minimum, the request is reduced first.

### Reduction

The reduced request cuts every text part (tool results, tool-call arguments, model text and the user's messages) to 4,000 characters, reusing the payload-overflow cap (#10380). A cut part keeps its start. No turn is dropped, so every function call keeps its response and roles keep alternating. A part that opens with a `<system-reminder>`, a hook-context block or a `<task-notification>`, and text that ends with one, as a tool result does with the reminder the scheduler appends after its output, get the block's closing tag added back when the cut lands inside the block: cut like other text, it would lose that tag and read as open over the text after it. The IDE context, prepended to the prompt's own part, is such a block even though the part ends with the prompt. A block that runs past the cap only by its closing tag is kept through that tag, and anything after it is cut. Only blocks at the start or the end of the text count, including several stacked there apart only by whitespace: the CLI prepends one reminder over another, and a tool result can end with more than one, so a cut inside the second of them closes that one (#15936 R3-3). The writers escape tags inside a block's body, but a file a tool read and what the user typed are not escaped, so a tag inside them is left as written.

A reduced request that still cannot leave the minimum is sent with the room it has, as before this change. A summary that does not fit that room is dropped by the truncation checks below, and the history is kept. Refusing it instead turned a request that fits into a certain failure: with no part longer than 4,000 characters the reduction cuts nothing, so a session of short messages could not compact at all (#15936 R3-7). Only a request whose input leaves no output room at all, its estimate plus the 1,024-token margin at or past the window, is not sent: compression returns `COMPRESSION_FAILED_INPUT_TOO_LARGE` without sending anything. It counts toward the failure breaker like other failures. A payload-overflow compaction (#10380) cuts every part before sizing, so its reduction has nothing left to cut, and a request that leaves no room is refused the same way rather than sent with a budget floored at 1. A 413 recovery that ends with this status gives the new-session advice: unlike a transient side-query failure, a later send only adds to the history.

### One retry after a context-length rejection

The estimate can still run low, notably for dense CJK text. When the provider rejects the cold request for context length (`getContextLengthExceededInfo`), compression retries once, sized from the rejection itself:

- **Window.** When the rejection names the whole context window (`limitKind: 'total'`) and it is smaller than the configured one, the retry uses it. A limit whose wording leaves its kind open ("prompt is too long: N tokens > M maximum") is used the same way once the rejection's own prompt count is past it; a model inferred at 1M and served at 200K first shows its real window there. A self-hosted server can run a smaller window than the model's own, and the rejection is the first place it shows.
- **Prompt count.** The retry takes the rejected prompt's own size from the rejection. "You requested N tokens" with no breakdown counts the requested output too; that total is taken as an upper bound on the prompt, since the transport can lower `max_tokens` below the budget compression asked for (a configured or model output cap), and subtracting that budget could undercount the prompt. A count far below the request's estimate, or one under which the request would have fit the limit the same message states, describes some other request and is ignored.
- **Only the output overran.** When the prompt leaves the summary its reserve (a quarter of the window, up to 20,000 tokens), the same request is sent again with `max_tokens` lowered to the room the count leaves, which is never below the reserve. When that room is no smaller than the budget sent, the count says the request fit this window, so the server's window is smaller by an amount the message does not state, and the reduced request is sent instead, as when the rejection has no counts.
- **The overflow is cut.** Otherwise the retry needs the estimate to drop by the overflow: prompt count + reserve + 1,024 − window, or prompt count + 1,024 − the input limit when the rejection states one and that is larger. When the reduced request drops that much, it is sent with the reserve as its output budget. char/4 usually under-counts, so an estimated token removed takes at least one real token with it, and the prompt fits whatever mix of dense and sparse text remains. A ratio of the count to the estimate would not: the text the reduction keeps, such as CJK messages under the cap, can be denser than the tool output it cuts, so the ratio underrates what is left. When the count runs below the estimate (sparse ASCII), an estimated token removed takes less than one real token with it, so the drop needed grows by that ratio.
- **The overflow is not cut.** When the reduced request drops less than that, less suffices if the removed text is as dense as the rest. Rather than refuse, the retry's output budget is then sized by the rejected prompt's average density, its count over its estimate, up to the reserve. It overruns only when the text kept is denser than the text removed, and then fails like any second rejection.
- **No counts.** The reduced request is sent with the room its own estimate leaves, up to the reserve. The rejection has just shown that estimate runs low, so the room it claims past the reserve is not taken: sized to the full output budget, a retry after a rejection that names only the window overran again in 15 of 25 measured session shapes where the prompt counted half again its estimate, against 3 with the reserve.
- **No fit.** When the reduced request cannot leave the minimum in that window, or is no smaller than the rejected one, the retry is not sent and compression returns `COMPRESSION_FAILED_INPUT_TOO_LARGE`. A retry rejected for context length again returns the same status, not an API error.

A second failure, or any other error, returns `COMPRESSION_FAILED_API_ERROR` as before.

`getContextLengthExceededInfo` reports the prompt's own size (`promptTokens`) only from wording that states it apart from the output budget: OpenAI's "resulted in N tokens", the completion broken out of "you requested N tokens (… in the completion)" (OpenAI, DeepSeek, older vLLM, OpenRouter), Anthropic's "prompt is too long", vLLM's "your prompt contains N input tokens" and "your request has N input tokens", Gemini's older wording, llama.cpp, SGLang, TGI's `inputs` count in both its wordings, vLLM's "Input length (N)" and Bedrock's "prompt tokens (N)". A "you requested N tokens" total with no breakdown is reported as `requestedTokens`; one whose clause names only the output ("in the completion", "in your completion") gives no count. A count wording that a limit word just before it qualifies ("maximum prompt tokens (N)", "the maximum input token count (N)", "max input length (N)") names what the server takes, not what the request held, and gives no count whatever the verb's tense. All figures come from one fragment of the error, the first that is itself a context-length rejection and states the prompt's size, so a count and a limit are never paired across fragments. Collection order puts the error's own message before the fields and causes it carries, so an earlier attempt's rejection riding along in a sibling field, a cause or the same JSON body does not size this retry. An embedded JSON body is read field by field for this, and a field that reports no overflow supplies no figure (#15936 R3-2). A fragment whose statements of the request's size disagree (two prompt counts, or a prompt count and a requested total) carries more than one attempt, and nothing in provider prose says which one is this request's. It gives no size, and the search ends there: the fields after it are likelier still to be earlier attempts. Its other figures are kept, as for a rejection that states no size; a window read from it only bounds the retry from above, since the retry takes the smaller of it and the configured one. The retry is then sized as without counts (#15936 R3-2, round 4). The bound vLLM's "Input length (N) exceeds model's maximum context length (M)" and Bedrock's "prompt tokens (N) exceed model maximum (M)" state after the count is read as the limit, `limitKind: 'total'` when it names the context length. `actualTokens` keeps the figure the reactive path has always read, from that same fragment. vLLM's "contains at least N" is where tokenization stopped, not the prompt's size, and stays limit-only. The window is read from "maximum context length is N" and from SGLang's "maximum context length of N", both as `limitKind: 'total'`, so the retry after an SGLang rejection is sized for the window SGLang states.

### Truncated summaries

A summary that opens `<state_snapshot>` and never closes it is kept only when the server's own prompt and output counts show its request left room in the window it was sized for: together more than 1,024 tokens below that window. Then nothing cut it: a model can end without closing the tag, and dropping every such summary would trip the failure breaker. Otherwise it is dropped as `COMPRESSION_FAILED_OUTPUT_TRUNCATED`. A server can stop the output where its window ends instead of rejecting `prompt + max_tokens > window` (llama.cpp's server does), so the reported output count stays below the budget requested and the existing threshold check cannot see the cut. When the server reports no output count, or only the prompt so that the output count is a local estimate, nothing shows the window was not filled, and the summary is not kept on that doubt (#15936 R4-8). After a retry sized for a smaller window the rejection reported, that window is the one checked. This check leaves a summary without the tags alone. An older rule (#7960) is kept as it was and does drop one: when the output budget was clamped below the full summary budget and the output count is a local estimate, the estimate cannot reach the truncation threshold, so a summary without a closed snapshot, tagged or not, is dropped as truncated and counts toward the breaker. Only closed `<analysis>` blocks are set aside before the check: real models often quote the compression directive, `<analysis>` tag included, inside the snapshot, and stripping from that quote to the end would take the closing tag too. The first opening tag that starts a line is the one checked: a tag named mid-sentence, before the snapshot or after it, opens nothing. The cost is the opposite shape: a summary that first quotes a complete example snapshot and is then cut inside its real one passes. The usage-based guard missed that shape before this change too.

### Accounting

A reduced request no longer describes the history it replaces. Its reported usage is therefore not used to derive the post-compression count. The visible-history estimate path is used instead, as it already is for payload-overflow compactions. A reduction that cuts nothing leaves the request as it was, so its usage is used as for one that was never reduced.

## Decisions and rationale

| Decision                                                 | Rationale                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Keep the char/4 estimator                                | It under-counts, so a refusal based on it only happens when the request cannot fit. #9541 replaced it with a byte-weighted estimate and refused Chinese sessions from about 50% of the window.                                                                                                                                                                                                                                                                                                      |
| Cut every text part, keep every turn                     | It reuses the payload-overflow cut (#10380) and keeps function calls paired without parsing turn structure. Keeping the user's messages whole needs to know which text the user typed, which the follow-up adds.                                                                                                                                                                                                                                                                                    |
| A single retry                                           | Compression stays best-effort and does not block the user. The rejection's own numbers make one well-sized retry enough in the common case.                                                                                                                                                                                                                                                                                                                                                         |
| New failure status                                       | Users can tell "too large to compress" apart from an API error by its message.                                                                                                                                                                                                                                                                                                                                                                                                                      |
| A quarter of the window as the minimum below 16K         | A fixed 4,096 leaves an 8K window little room for history and a 4K one none. A summary that does not fit the smaller budget is dropped as truncated, and the history is kept.                                                                                                                                                                                                                                                                                                                       |
| Below the minimum, send a request that fits              | The minimum decides when to reduce, not whether to send. Refusing a request that fits turns a summary that may fit its room into a certain failure; one that does not fit is dropped as truncated either way. None of the agents surveyed (Claude Code, Codex, grok-build, opencode, pi, crush) refuses a summary request before sending it.                                                                                                                                                        |
| Take every figure from one rejection fragment            | Figures read from different fragments, or a limit read as a count, size the one retry wrongly. A wording outside the list then gives no count, and the retry is sized as without counts, rather than from a number that may be another request's or a limit. A fragment that states two different sizes gives none: taking the first or the last is right only for the order a provider happens to write.                                                                                           |
| Cut the overflow rather than scale by a ratio            | A ratio assumes every part of the request is equally dense. The text the reduction keeps can be denser than the tool output it cuts, so a ratio underrates what is left. Requiring the overflow's drop at one real token per estimated token fits whatever remains, and the retry's `max_tokens` comes from the count, not the estimate.                                                                                                                                                            |
| Keep an unclosed snapshot only when the usage shows room | A server that stops the output at the end of its window reports a count below the budget. Reported prompt and output counts that leave the window room show nothing cut the summary, so an unclosed tag there only means the model skipped it, and dropping those would trip the failure breaker. Without both counts nothing tells a cut from a skipped tag, and a half-written summary would replace the history. Summaries without tags pass the check, since weaker models may skip the format. |

## Risks

- A reduced request cuts the user's messages to 4,000 characters like tool output, keeping their start, so the summary can miss the end of a long request. The follow-up keeps them whole.
- The reduction only cuts parts longer than 4,000 characters. A session made of many shorter messages does not get smaller. It is sent with the room it has, which a long summary may not fit; that summary is dropped as truncated and counts toward the failure breaker. Only when its input leaves no room at all is it refused with `COMPRESSION_FAILED_INPUT_TOO_LARGE`.
- Without counts in the rejection, the reduced request may still be too large for very dense text. Its output budget comes from its own estimate, held to the reserve; when the prompt counts far above that estimate it can still overrun. Compression then fails after the one retry, without sending a third request.
- When the reduced request does not drop the whole overflow, its output budget comes from the average density, which can overrun if the text kept is denser than the text removed; compression then fails after the one retry.
- On windows below about 16K a reduced request leaves the summary at most a quarter of the window, and a request that cannot be reduced can leave less. A long summary may not fit; it is then dropped as truncated, and the history is kept.
- A provider wording outside the ones listed reads no count, and the retry is sized as without counts. Such a wording is never read as a count; MiniMax's "you requested ~N tokens", the Vercel gateway's "Input too long: N input tokens, limit is M" and kronk's "input tokens [N] exceed context window [M]" are among them.
- A server that stops the output at a window smaller than the one the request was sized for, or a transport output cap below the budget, can cut a summary mid-snapshot without the usage reaching that window. Such a summary is kept, as it was before this change.
- When the output budget was clamped and the server reports only the prompt count, #7960's rule drops a summary without a closed snapshot, with or without tags, and the drop counts toward the failure breaker. A weaker model that skips the format on such a server loses those compressions. This change keeps that rule as it was.
- When the server reports no output count, a summary that opens `<state_snapshot>` and never closes it is dropped even under the full output budget, and the drop counts toward the failure breaker. A model that skips the closing tag on such a server loses those compressions. The stop reason would tell a cut from a skipped tag, but compression does not receive it yet.

## Acceptance criteria

- A cold compression request that leaves its summary less than 4,096 tokens, or a quarter of the window when that is smaller, is reduced first. One whose input then leaves no output room is not sent; one that fits is sent with the room it leaves.
- The retry's figures come from the rejection itself: never from another fragment of the error, never a number its wording names as a limit, and no size from a text that states two different ones.
- A request that fits is sent unchanged.
- A reduced request keeps every turn, so every function response stays after its call.
- An irreducible request returns `COMPRESSION_FAILED_INPUT_TOO_LARGE` without sending it, or without its retry when a rejection showed that no retry fits, or after its retry was rejected for context length too, and the CLI shows a non-empty message for it.
- A context-length rejection leads to at most one retry. When the rejection reports a window, the retry fits it. When it reports the prompt's size, the retry either resends the same input with less output room, never below the reserve, or sends the reduced input.
- A summary cut off inside its `<state_snapshot>` is not persisted unless the server's own prompt and output counts show its request left room in the window it was sized for.

## Follow-ups

- Keep the user's messages whole in a reduced request, and condense older turns to them when truncation is not enough (#14953).
- Carry the provider's stop reason to the compression call and drop a summary that stopped on length. pi, Claude Code and Codex decide on it alone; `GenerateTextResult` does not carry it yet. A missing stop reason is not a clean stop: the non-streaming OpenAI converter fills in `stop`.
- Cache-sharing admission against an anchor from another route.
- Compacting with the previous model before switching to a smaller window.
- vLLM's "`max_tokens` cannot be greater than" rejection is not recognized as a context overflow. Classifying it would change the main chat path too.
- A server that drops messages from the front instead of rejecting (Ollama's default) sends nothing to retry from.
- A CJK-aware upper-bound estimate to size the first request's output budget, so dense sessions are not rejected before the retry corrects them.
- A per-part density floor (for example, ASCII at one token per four characters and CJK at one per two) would let the overflow check accept a reduced request whose removed text is dense.
- Compression telemetry is logged only for a compression that runs to the end, so neither this status nor an API failure reaches it. Logging the failure returns with their status would let a dashboard compare the two.
- Anthropic's "input length and `max_tokens` exceed context limit: P + C > L" is not recognized as a context overflow. Recognizing it would change the main chat path too; for a retry it states the prompt's size directly.
- Other overflow wordings are not recognized as context overflows either: xAI, Together's "The input (N tokens) is longer than", SiliconFlow, Bedrock Titan, vLLM's engine-level "decoder prompt", llama.cpp's non-splittable input, Kimi's older wording, MiniMax, Zhipu's "Prompt exceeds max length", LM Studio and Ollama's llama-server. Their compression rejections fail as before. Recognizing them changes when the main chat compacts too, so it belongs in its own change, as #16245 did for TGI.
