# Managed channel runtime (H5b/H5c)

[English](2026-10-07-managed-channel-runtime.md) | [简体中文](2026-10-07-managed-channel-runtime.zh-CN.md)

Status: implemented in this change for the email reference adapter; the production AgentBundle enablement and the real-environment gates listed under "Acceptance criteria" stay separate. This is the runtime part of slice H5 of [#12827](https://github.com/QwenLM/qwen-code/issues/12827), stage H of the Managed Agent proposal [#12380](https://github.com/QwenLM/qwen-code/issues/12380): slices **H5b** (inbound) and **H5c** (outbound) of the [H5 design](2026-10-04-managed-channels.md). It follows H5a (the `managed-channel_route` and `managed-channel_delivery` record contract, PR #13548) and slice C (the planned public channel routes and the V47 serving tables, PR #13497), and extends the obligations of H0b ([record contract](2026-09-27-managed-extension-record-contract.md)), H0c ([authority](2026-09-27-managed-extension-authority.md)) and H3 ([background Shell and Monitor](2026-10-03-managed-shell-monitor-runtime.md), whose embedded wake scheduler this slice reuses). Below, "the reference design" is sections 1, 3, 6, 11, 12 and 14 of the [extension runtime design](https://github.com/doudouOUC/code_agent/blob/689121646cc25ca08a34508a5f5555ae15308833/qwen-code/feature/managed-agents/managed-agent-extension-runtime.md), and "the automation design" is section 3 (C10) of the [automation, Channels and child delivery design](https://github.com/doudouOUC/code_agent/blob/689121646cc25ca08a34508a5f5555ae15308833/qwen-code/feature/managed-agents/managed-agent-automation.md), at the commit that #12827 pins. Wherever this document and the H5 design disagree, this document records the supersession in "Decisions".

## Problem and scope

H5a pinned _what may be committed_: a route binding chain keyed by `routeId` whose revisions carry the account generation, and a delivery chain keyed by `deliveryId` whose revisions carry a stable segment plan with one receipt per segment. Slice C froze the three public read routes as `planned` and shipped two serving tables. Nothing _produces_ or _serves_ any of it: no Session may submit either domain, no adapter routes an inbound event onto the managed path, no dispatcher reads the delivery outbox, and the three routes answer nothing. Issue #12380's H5 line is the exit this slice works toward: "Durable inbound routing/attachments, result outbox dispatch, receipts and partial/unknown delivery recovery."

This slice delivers both verticals for the email adapter:

- **Inbound (H5b).** A trusted channel adapter submits an authenticated platform event to the control plane; the control plane dedupes it on the four-part ingress identity, resolves or creates the route's Session, and commits — through one Harness operation — the route binding revision (when one is owed), the staged attachment resources, the input and its wake in one journal transaction. The Session's embedded wake scheduler runs the input as an ordinary text turn.
- **Outbound (H5c).** When a channel turn settles, the Harness commits the reply as a `channel_delivery` record with a segment plan (`planned`). The adapter pulls its outbox from the control plane: a claim moves the record to `sending` and the V47 ledger with it; per-segment receipts commit as record revisions (`partial` → `delivered`); a disconnect after a send commits `unknown` and is never resent automatically; a definitive provider refusal commits `rejected`; an explicit resend opens a new `deliveryId` carrying only the segments proven unsent and warns about possible duplication.
- **Public reads.** `GET /v1/agent-channels`, `GET /v1/agent-channels/{channelId}/deliveries` and `GET /v1/agent-channels/{channelId}/deliveries/{deliveryId}` move from `planned` to `partial`, served read-only over the registered connections, the V47 ingress rows and the V47 delivery ledger.
- **Enablement.** Both domains become submittable, gated per adapter: the route's committed policy names its adapter, and only `email` is admitted.

Still deferred (not this slice): a second adapter; card-style segmented surfaces; attachment kinds beyond inline staging; the Legacy control commands (`/help`, `/status`, `/cancel`, `/clear`, pairing) on the managed path; proactive (non-reply) sends and H6 automation deliveries; a public resend mutation and WebShell mirror routes; production AgentBundle enablement.

## Current state

The facts below are from this slice's base (the H5a branch head `8b283d1c3f`, whose merge-base with `main` is `ac497aeed9`).

- **Records.** `managed-channel-record.ts` defines both closed bodies; the authority's `verifyExtensionResources` closes the route's `policyRef` and the delivery's `contentRef`, segment `contentRef`s and receipt `proofRef`s over the Session's own store; `MANAGED_EXTENSION_RECORD_BODIES` holds both with `taskKind: null`. Java's `ManagedChannelRecords` replays the same corpus. Neither domain is in `MANAGED_SESSION_ENABLED_DOMAINS`, and no cross-record check ties a delivery to its route.
- **Serving tables (V47).** `qwen_managed_channel_route` holds one row per four-part ingress identity (`route_key = sha256(tenant|channel|generation|event|revision)`, NUL-joined) with the scope, the target `session_id`, `state staged|admitted`, the admitted `input_id` and `staged_attachment_refs_json`; `qwen_managed_channel_delivery` holds one row per `delivery_id` carrying one `segment_id`/`segment_ordinal`, a state drawn from the shared channel delivery line and a `provider_receipt`. Both have JDBC repositories (`findOrCreate`, `admit`, `transition`, newest-first listing) that nothing calls. The public shapes (`PublicChannel`, `PublicChannelRoute`, `PublicChannelDelivery` and their lists) are frozen `planned` at contract 1.33.0; `PlannedChannelContractTest` pins them planned and the API contract test requires every non-planned operation to be exercised.
- **Harness side.** `hosted-harness-session.ts` already hosts per-capability funnels (`HostedChildAgentSession`, `HostedMonitorSession`) and one control-plane operation route per capability (`POST /session/:id/children/operations`), and the H3 embedded wake scheduler runs pending notification inputs (`source` `monitor`, H4b adds `child_agent`) as text turns, deriving the pending set from the journal (`pendingSessionInputs`). The hosted prompt accepts text blocks only. The HTTP Session store publishes inline resources up to 64 KiB each.
- **Control plane.** `HarnessConnector`/`HostedHarnessClient` carry one operation verb per capability (`runChildOperation`); `ManagedAgentService.createWorkspaceSession` admits an empty bound Session idempotently under the actor's Workspace grant; `TenantContextFilter` names the internal prefixes it resolves a tenant for; `@Scheduled` workers (`ChildResultRelay`, `SessionLifecycleCoordinator.recoverOperations`) reconcile from committed rows, never from memory. Flyway stands at V47 on `main`; open branches reach V50 (W1c) and V51 (H4b).
- **Legacy email adapter.** `packages/channels/email` keeps, in one locked JSON file, `uidValidity`, `lastUid`, in-flight `pending` UIDs, `outboundPending` Message-IDs, a 1,024-entry dedupe window and reply routes; it refuses to start over uncertain in-flight state; it parses with `mailparser`, polls with `imapflow` and sends with `nodemailer`. Its behavioral suite runs against fakes of those three modules.

## Decisions

1. **Three ledgers, one authority.** The Session journal's `channel_route` and `channel_delivery` chains are the only business facts. The control plane keeps three rebuildable indexes beside them, as the automation design's "route/task catalog" allows: the V47 `qwen_managed_channel_route` row is the ingress occurrence — the dedupe index of decision 2 plus the admission outcome; the V47 `qwen_managed_channel_delivery` row is the dispatcher's claim ledger for one delivery; and V52 adds `qwen_managed_channel_instance` (the registered connection: platform, account, generation, state, Workspace selection, owning actor, policy) and `qwen_managed_channel_binding` (scope key → `routeId` → `sessionId`, the lookup a new event needs). None of them holds a second copy of a journal fact; each is derived from or settled by a journal commit.
2. **The ingress identity is the V47 route key.** `inputId = chin-<routeKey>` where `routeKey = sha256(tenant NUL channelId NUL accountGeneration NUL platformEventId NUL semanticRevision)` — one derivation in Java and TypeScript. A provider redelivery hits the same row and the same `inputId`; the Harness answers the committed admission by `inputId` (the journal's command idempotency) without a second input or turn. Two real messages with identical text have different platform event IDs (email: `uidValidity:uid`) and stay two inputs. For email the semantic revision is fixed at 1.
3. **The route chain is keyed by scope, not by generation.** `routeId = chrt-<sha256(channelId NUL accountId NUL scope.kind NUL senderId NUL chatId NUL threadId)>`. The first event on a scope opens the chain (revision 1, `admitted`, `effectId = routeId`) in the same transaction as its input; a later event whose account generation is newer than the committed one opens a rollover revision (routeRevision + 1, the new generation) in the same transaction as _its_ input; an event whose generation is older than the committed one is refused (`channel_generation_stale`) — the old generation admits nothing new (H5 design decision 6). An event on a committed route at the same generation commits the input alone (`submitInput`), pinning the route and its revision in the input envelope.
4. **One Session per route; creation is idempotent and actor-granted.** The control plane creates the route's Session through the existing `createWorkspaceSession` path as the connection's registered owning actor, with `Idempotency-Key = chcr-<sha256(tenant NUL channelId NUL routeId)>`, the instance's Workspace selection and no input; the binding row is inserted after admission. A lost creation answer replays by that key — never a second Session. The root Session of a route is the route's own Session in v1 (`rootSessionId = sessionId`).
5. **One Harness operation admits inbound; it is complete before any effect and replay-safe.** `POST /session/:id/channels/operations` with `kind: submit_input` publishes the attachment resources and the input envelope, then commits route revision + input + wake in one authority transaction (or the input alone). The control plane marks the V47 row `admitted` with the returned `inputId` only after the operation answers; a crash anywhere before that leaves the row `staged`, and the adapter's retry re-drives the same operation, which answers the original admission. Staged bytes are retained where they already are durable: the adapter's immutable platform copy (IMAP) until it records the admission, and the Session's resource store once published; the V47 row records the attachment content digests (`sha256:<hex>`) as its staged references.
6. **Attachments stage as Session resources, inline-bounded.** Each attachment ≤ 64 KiB (the inline resource bound of the hosted store) is published as a `managed-channel-attachment` resource before admission and referenced from the envelope with its name, MIME type, size and digest; a larger one is listed in the envelope as `omitted` with its digest and size — visible to the model and the record, never silently dropped (reference design section 6: "unsupported 可见"). Promotion of larger bytes to O2/O3 Artifacts is follow-up work recorded under "Open questions".
7. **The channel turn is the H3 wake path.** The input's `source` is `channel`; the embedded wake scheduler admits it beside `monitor` and `child_agent`, so it runs as an ordinary text turn while the Session idles, queues in the journal while a turn runs, and stays accurately pending while the Session is blocked. The turn text is the envelope rendered as a `<channel-message>` block: sender, platform identity, untrusted subject metadata, the attachment listing and the message text. Channel inputs are excluded from parked-turn arithmetic exactly like monitor inputs, and the close path settles pending channel inputs model-free with no reply.
8. **The reply is planned on settle, idempotently, and reconciled on open.** After a channel wake turn settles `completed` with non-empty assistant text, the funnel publishes the reply resource (`managed-channel-reply`: the text and the adapter-opaque reply context the input carried) and one `managed-channel-segment` resource per segment, then commits `channel_delivery` revision 1 (`planned`) with `deliveryId = <inputId>:reply`, `sourceTurnId = turnId` and the route pin from the envelope. The email plan is one segment: the reply text bounded to 48 KiB with a truncation notice. A turn that settled `error` or `cancelled`, or model-free on close, plans nothing. `reconcileReplies()` runs when the Session opens and plans any settled channel turn that has no delivery yet, so a crash between settle and plan loses nothing and duplicates nothing.
9. **The outbox is adapter-pulled through the control plane, and every step is a record revision.** The adapter calls `deliveries:claim`; the control plane finds `planned` deliveries of the channel's Sessions (through the binding index and the extension-record projection), inserts the V47 ledger row (`planned`), asks the Harness to commit `sending` (`kind: claim_delivery`) and moves the ledger to `sending`, then returns the segments' content and the reply context. A per-segment `receipt` commits the segment's receipt (`partial` while segments remain, `delivered` with the last) and moves the ledger with the provider receipt. `unknown` (the adapter cannot prove the provider does not hold the message) commits `waiting`/`unknown`; `rejected` (a definitive provider refusal) commits `failed`/`rejected`; both are terminal for automatic work. The Harness answer is the authority: the ledger moves only after the record committed, and a ledger step that finds the record already there is the idempotent replay.
10. **Unknown is reconciled by lease, never by resend.** A ledger row left `sending` longer than the claim lease (default 10 minutes) with no receipt is settled `unknown` by the control plane's scheduled reconciler (Harness `settle_delivery` with `outcome: unknown`): the adapter may have died after sending. Nothing resends on that path (reference design section 14, item 5). A `planned` delivery whose Session is no longer `ACTIVE` has no writer left to revise it: the claim skips non-active Sessions, and the record stays visibly `planned`.
11. **Resend is a new chain, explicit, and warns.** `deliveries/{deliveryId}:resend` is admitted only for `unknown`, `rejected` or `partial`-then-`unknown` deliveries; the Harness opens `<deliveryId>:r<n>` (`planned`) with the same route pin, `sourceTurnId` and `contentRef`, carrying only the segments that hold no receipt (ordinals renumbered densely, segment identities kept). The original record is untouched. The answer carries `possibleDuplicate: true`. v1 exposes it on the trusted adapter surface only; a public mutation needs its own contract work.
12. **Enablement is adapter-scoped.** `channel_route` and `channel_delivery` join `MANAGED_SESSION_ENABLED_DOMAINS`, and a new gate beside it — `MANAGED_SESSION_ENABLED_CHANNEL_ADAPTERS = ['email']` — is checked by the authority on every first route revision: it reads the committed `policyRef` resource (`managed-channel-policy`: `{ adapter, senderPolicy, allowedSenders, dispatchMode }`) and refuses an adapter not in the list. A delivery is admitted only against a committed, non-terminal route at the pinned `routeRevision` (the cross-record check both languages add), so deliveries are gated transitively. The server-first order holds: the Java store has validated both bodies since H5a and gains the cross-record check here.
13. **The trusted adapter surface is internal.** `/internal/managed-channels/v1/channels/{channelId}` (register/connect, `disconnect`), `.../inbound`, `.../deliveries:claim`, `.../deliveries/{deliveryId}:receipt` and `.../deliveries/{deliveryId}:resend` are mounted on the internal listener like the Session store, resolve the tenant from `X-Qwen-Tenant-Id` (the filter gains the prefix), and are reachable only by the deployment's trusted channel workers. Registration supplies the owning actor, platform, account identity and generation, Workspace selection and policy; a re-key reports a higher generation.
14. **The email adapter's managed mode is a separate loop over the Legacy parsing helpers, and the Legacy path does not change.** `ManagedEmailAdapter` reuses `message.ts` (sender acceptance, bounded text, reply routes) and the IMAP/SMTP modules, keeps its own locked state (`uidValidity`, generation, `lastUid`, in-flight `pending` events with their admitted `inputId`, in-flight `outbound` segments), and drives the pipeline: poll → ingress event → control plane → persist admission; claim → SMTP send → receipt (`accepted` with the generated Message-ID, `rejected` on a 5xx SMTP response, `unknown` on anything ambiguous). A `uidValidity` change advances the generation and resets the cursor. The CLI exposes it as `qwen channel managed-email`, an experimental subcommand that the Legacy `qwen channel start` never selects.

## The pipeline, revision by revision

| Step | Where                       | Commit                                                                                                                                                   |
| ---- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | adapter                     | poll, parse, gate the sender, persist `pending` with the four-part identity                                                                              |
| 2    | control plane               | V47 row `findOrCreate` (`staged`); binding lookup or idempotent Session creation (decision 4)                                                            |
| 3    | Harness `submit_input`      | route rev 1 or rollover rev + `input.accepted` + `wake.requested` in one transaction (or input alone); replay answers the committed `inputId`            |
| 4    | control plane               | V47 row `admitted` with `inputId`; adapter clears `pending`, advances `lastUid`                                                                          |
| 5    | Harness (wake)              | the channel turn runs; `turn.settled`                                                                                                                    |
| 6    | Harness (settle / open)     | `channel_delivery` rev 1 `planned` (decision 8)                                                                                                          |
| 7    | control plane `claim`       | ledger `planned`; Harness `claim_delivery` → rev `running`/`sending`; ledger `sending`                                                                   |
| 8    | adapter                     | SMTP send per segment, `outbound` persisted before the send                                                                                              |
| 9    | control plane `receipt`     | Harness `segment_receipt` → `partial`/`delivered` (run `settled`), or `settle_delivery` → `unknown`/`rejected`; ledger follows with the provider receipt |
| 10   | control plane reconciler    | lease-expired `sending` → `unknown`; a non-active Session's `planned` deliveries are skipped by the claim and stay visible                               |
| 11   | adapter / operator `resend` | new chain `<deliveryId>:r<n>` `planned` with the unsent segments; warning returned                                                                       |

Each commit moves every state line at most one allowed step (the H0b successor rule), so a crash between any two rows reconciles from the last committed row; every control-plane verb re-reads the committed record before acting and treats "already there" as its own replay.

## Quotas

| Bound                         | Value                                                                      | Refusal                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Inbound text                  | ≤ 32,000 characters (the email `maxTextLength` default), envelope ≤ 64 KiB | adapter bounds the text; the envelope beyond the bound is refused `channel_input_too_large` |
| Attachments                   | ≤ 16 per event; each staged inline ≤ 64 KiB, larger ones listed `omitted`  | none (visible omission)                                                                     |
| Reply segment                 | ≤ 48 KiB, one segment for email                                            | truncated with a notice                                                                     |
| Segments per delivery         | 1–64 (contract)                                                            | plan refusal                                                                                |
| Claim lease                   | 10 minutes (`qwen.managed-agent.channels.claim-lease`)                     | reconciler settles `unknown`                                                                |
| Claim batch                   | ≤ 16 deliveries per call                                                   | —                                                                                           |
| In-flight inbound per channel | ≤ 32 pending events (adapter)                                              | adapter stops admitting until one settles                                                   |

## Non-goals

- **Proactive sends, control commands, pairing, memory and loops** on the managed path; the reply is the only delivery source in v1 (automation design 3.2, `source: reply`).
- **Multi-segment plans and card surfaces**: the contract supports them; the email plan is one segment and the V47 ledger keys one segment per `deliveryId`.
- **Attachment bytes beyond the inline bound**, reading staged attachments from a tool, and O3 public Artifact promotion.
- **A public resend mutation, WebShell mirror routes, and any OpenAPI change beyond flipping the three frozen routes and their schemas to `partial`.**
- **Any Legacy change**: `EmailChannel`, `ChannelBase`, the daemon channel worker and routes keep their behavior.

## Validation plan

- **TypeScript**: body-builder and identity suites (every builder yields a body the H5a parser accepts and the successor rule admits; every refusal names its reason); authority suites for the adapter gate, the cross-record check, rollover-in-one-transaction, stale-generation refusal, replay by `inputId`, delivery claim/receipt/unknown/rejected/cancel/resend, and reopen rebuild; funnel suites in `packages/cli` for `submit_input` replay, attachment staging and omission, reply planning on settle and reconciliation on open, and the wake admission of `channel` inputs; email adapter suites replaying the Legacy behavioral cases (dedupe window, redelivery, generation rollover, uncertain SMTP, capacity) against a fake control plane.
- **Java**: store suites for V52, the binding index and the pending-delivery query; service suites for ingress dedupe (one platform event → one V47 row and one `inputId`; identical text under two events → two), creation replay, claim/receipt/unknown/rejected/resend transitions against a recording Harness, and the reconciler's lease and closed-Session rules; the cross-record check answering a refusal; the contract test exercising the three routes (200, 400 `invalid_cursor`/`invalid_limit`, 403, 404) with schema validation.
- **Fault injection (store/authority level)**: crash before the V47 row; between the row and the Harness answer; between the answer and `admitted`; between settle and plan; between claim and send; after send before receipt; between receipt and ledger — each ends in one input per event and at most one provider send per segment, or in a visible `unknown`.
- **Mutation checks**: the dedupe derivation, the generation comparison, the adapter gate, the cross-record check, each delivery transition and the resend filter, disabled in turn, fail a test in both languages.

## Acceptance criteria

- Reference design section 14, item 5: a channel redelivery forms exactly one input; two genuine identical-text messages stay two; a lost outbound acknowledgement never causes an automatic second send.
- Section 14, item 10: every delivery resolves to `delivered`, `partial`, `rejected`, `cancelled` or `unknown`; `unknown` never masquerades as delivered and is never auto-resent; an explicit resend is a new chain with a warning.
- Section 11: the three channel resources are served read-only over committed rows; no Runtime identity, credential, absolute path or PID appears in them.
- Both domains are submittable only for the `email` adapter; the contract test proves the gate is explicit and adapter-scoped, and `shell`/other producers stay unaffected.
- All existing suites stay green — every H1–H4a/H5a contract replay, authority, store, tool-turn and lifecycle test, `npm run typecheck && npm run lint && npm run build`, and the `managed-agent-server` surefire suite.
- Still separate: real IMAP/SMTP providers, multi-instance control planes, second-host recovery and the §13 product-stack acceptance recorded in #12380.

## Open questions

1. **Larger attachments.** Inline staging stops at 64 KiB; whether `omitted` attachments gain O2/O3 Artifact staging in a later revision of the envelope is decided with the media follow-up, not here.
2. **Dedupe index retention.** V47 rows and the binding index are not pruned in v1; retention rides the Session archive/delete work.
3. **Claim lease versus provider latency.** Ten minutes is the SMTP default; a provider with slower acceptance needs a per-platform lease, which the instance registration can carry later.
4. **Public resend.** Whether the public contract gains `POST .../deliveries/{deliveryId}:resend` (with the possible-duplicate warning in its response) is an API-contract decision for the WebShell slice.
