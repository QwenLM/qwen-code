# Managed Agent operation dispatch and retention

[English](2026-11-28-managed-operation-dispatch-retention.md) | [简体中文](2026-11-28-managed-operation-dispatch-retention.zh-CN.md)

Proposal based on `main` at `cc652838c4`, 2026-11-28.

## Goals and current behavior

Move frequent operation discovery from every control-plane replica to MQ wakeups and a small recovery worker deployment. Reduce the contents of settled `ma_operation` rows while preserving operation IDs, authorization, replay behavior, and evidence used by downstream readers. Pilot with SQL-only Session resource collection. Full Session data erasure, external publication collection, and backup expiry each have their own completion conditions.

The control plane already dispatches lifecycle operations locally after admission and scans periodically for due work and expired leases. Session retirement writes `SESSION_RESOURCE_GC` in the same transaction as its retirement marker. The collector also backfills missing rows and verifies read leases, original writers, and recovery activity. The optional RocketMQ event transport already sends Journal and public event notifications. Its best-effort delivery is backed by SQL reconciliation. Keep task wakeups on a separate topic and consumer group with independent backpressure.

## Dispatch rollout order

1. **Pilot `SESSION_RESOURCE_GC` on MySQL-only deployments.** Reuse its operation ID, lease, blocker checks, and bounded collector. Enable SQL collection independently of tool publication on a dedicated worker. Extract claim-by-reference from `SessionResourceCollectionCollector` so MQ and polling share the same claim and page logic. Keep projection collection, capture collection, and publication verification on their existing schedules. The pilot covers task discovery for the current SQL collector.
2. **Move lifecycle and other typed worker discovery.** Add `CLOSE`, `DELETE`, and `CWD_CHANGE` individually once the pilot proves retry and takeover. Retain post-admission local dispatch during validation. Then evaluate `CONTEXT_COMPRESSION`, `ACTION_RESPONSE`, and `TASK_CANCEL` using their own claims and completion rules. A `RECOVERY_BLOCKED` operation waiting for original evidence wakes its reconciler and settles against that evidence.
3. **Move work that depends on other records or external evidence separately.** Start `CHILD_SESSION_START` discovery from the durable `child_run` transition and preserve `CHILD_SESSION_CLOSE` compensation. For `TOOL_RESULT_PROJECTION`, `OUTPUT_VERIFY`, `CAPTURE_GC`, `WORKSPACE_CREATE`, and `WORKSPACE_UPLOAD`, first map the prerequisite, timeout, and original-target confirmation to a durable wake condition. Preserve each current owner and retry policy.

`SUBMIT_INPUT` and `CANCEL` remain under the Turn dispatcher. If its discovery moves later, wake the original Turn and keep result reconciliation on its Journal evidence. `ARCHIVE`, `RENAME`, and `UNARCHIVE` keep their synchronous paths. `CHANNEL_INGRESS` and `PR_WATCH_INJECT` keep their inbound event triggers. Keep `OBJECT_PUT` and operator-driven recovery and migration under their current owners. In the SQL-only pilot, use a separate completion record for future full SQL erasure when the schema can support it. The existing `SESSION_RESOURCE_GC` success stays available to Workspace recovery.

## MQ wakeups and failure handling

The pilot keeps the existing V1 schema and the durable operation row as the source of work. A committed DELETE sends a wakeup that identifies the tenant and Session so the consumer can find the GC operation. Polling handles due rows, expired leases, and missing historical collection rows directly. GC checks the grace period and `available_at` using database time. Verify the scan plan against the existing due index and measure query cost on a representative catalog.

The consumer verifies the original row's scope and kind before using the existing transactional claim. Every mutation still checks owner, generation, lease, and any cursor or resource preconditions. It commits page progress or a blocker before acknowledging. SQL polling drives further pages and retries, and a worker crash makes the original operation eligible again when its lease expires. Later operation kinds can use wakeups keyed by operation reference after an admission, retry, or continuation commits. For a side effect with an uncertain outcome, continue the original protocol and confirm its evidence before re-executing it.

This pilot relies on SQL polling for a crash between commit and publish, lost messages, and expired leases. For a later requirement to durably register every wakeup in the business transaction, use a transactional outbox after a supported schema upgrade. Keep wakeup delivery state separate from the execution lease. Publish outside the SQL transaction, confirm the outbox entry after broker acknowledgement, and reconcile expired publisher claims. Duplicate sends remain valid if the publisher crashes before recording the acknowledgement. Lease expiry and eligibility changes still need a timer or reconciliation even with an outbox.

## Minimal execution state, receipts, and evidence

- **In flight or unresolved.** Keep `operation_ref`, public `operation_id`, kind, tenant and scope, target and revision, authorized actor scope, idempotency key and digests. Keep the exact request and protocol version, typed `state`/`phase`, admission and delivery state, `available_at`, `claim_owner`, `claim_generation`, `claim_until`, retry/deadline fields, cursor, and outstanding evidence references as required by the kind. Keep per-target work in `ma_operation_work`. Settlement and recovery use these values with or without MQ.
- **Terminal receipts.** `ARCHIVE`, `CWD_CHANGE`, `CONTEXT_COMPRESSION`, `ACTION_RESPONSE`, `TASK_CANCEL`, `SUBMIT_INPUT`, `CANCEL`, `OUTPUT_UPLOAD`, `OUTPUT_VERIFY`, `OUTPUT_FINISH`, `CHANNEL_INGRESS`, `PR_WATCH_INJECT`, `WORKSPACE_CREATE`, and `WORKSPACE_UPLOAD` can be reduced to the original identity and authorized de-duplication scope, request digest, final status, receipt/failure fields, timestamps, and the result fields their callers actually read. Examples include a CWD target and its revisions, an approval decision receipt, a compression outcome and revision, an ingress input ID, and a publication's terminal resource reference. An output verifier's predecessor state stays until its consumer settles. Keep `ma_request_receipt.result_operation_ref` resolvable, and keep create-session de-duplication even after the Session is deleted. Existing readers compare the original idempotency key text as well as its digest.
- **Terminal business evidence.** Keep `CLOSE`, `DELETE`, `SESSION_RESOURCE_GC`, `CHILD_SESSION_START`, `CHILD_SESSION_CLOSE`, `CHILD_WORKSPACE`, `SESSION_WORKTREE`, `TOOL_RESULT_PROJECTION`, `WORKSPACE_OPERATOR_RECOVERY`, `WORKSPACE_RECOVERY`, and `STORAGE_MIGRATION` for as long as their operational readers require them. Keep `DELETE` and the fixed `session-resources-<sessionId>` proof for recovery, the close receipt for lifecycle admission, and the child close marker for duplicate suppression. Keep the READY result and source for artifact readers. Before removing a completed migration row, move its `history_identity_json` to the storage authority and switch the reader. Before removing operator recovery, migrate the Runtime retention guard keyed by binding and generation. Apply the same pattern to child and worktree joins.
- **Audit after all operational obligations end.** `CAPTURE_GC` can be considered after the capture/resources durably say `COLLECTED`, deletion intent references are handled, and no claimant remains. `OBJECT_PUT` can be considered after the publication has been collected and original write reconciliation and replay have ended. Keep only identifiers, authorized actor or service scope, timestamps, outcome, and counts in the audit record. Verify historical `WORKSPACE_RETIREMENT` rows against Runtime retention before cleanup. New rename and unarchive keep their existing command receipts and can emit structured audit events.

First compact in place, with kind-specific terminal projections using the existing columns and a distinguishable receipt version where needed. Preserve the existing NOT NULL constraints and return shape. Introduce a narrow terminal reader before changing any payload that an old mapper still parses. In particular, `CONTEXT_COMPRESSION` currently reads `expectedCompactionRevision` from the request, `ACTION_RESPONSE` re-parses the request to build its response, and `WORKSPACE_UPLOAD` still decodes the original target. Start later compaction with eligible individual rows. New tables and physical column removal require a schema upgrade.

## Existing readers, historical rows, and rollback

1. **Inventory and deploy compatible readers first.** Measure row counts by kind and state, the oldest due age, and queries from API, workers, Broker, and maintenance tools. Test legacy payloads and compact receipts against identical read and replay contracts. Keep the original operation IDs and row references. Treat unknown payloads or state combinations as ineligible for compaction and report their IDs or counts.
2. **Run dual triggers on the same database.** Install the MQ consumers and exercise them with the existing scanner active for the pilot kind. Both use the same claim. Once the pilot passes failure injection, make MQ primary for that kind and move its fallback scan to the dedicated worker. Keep normal polling for other kinds. Roll back dispatch by restoring the original scanner before stopping the consumer. Outstanding messages can finish or be redelivered through the same claim protocol.
3. **Backfill dispatch and compact receipts independently.** On an existing compatible V1 catalog, use bounded primary-key pages. Capture a high-water ID per pass, recheck due or terminal eligibility under lock, and commit progress per page. Re-enqueue old due operations and expired claims by their original ID. Reuse the existing missing-GC-row repair. Never reset a completed `SESSION_RESOURCE_GC` to pending. A future full SQL-erasure job needs its own identity and completion evidence. Start terminal compaction with new `ARCHIVE` receipts, then backfill allowlisted terminal rows after comparing live readers. Leave unresolved rows intact. For rows with live business consumers, migrate or expire those references before compaction.
4. **Separate dispatch rollback from compact-format rollback.** Keep legacy readers compatible until every process that reads targeted kinds has the new terminal reader. Delay irreversible trimming until the compatibility rollback window closes. A dispatch rollback can still use polling with the compatible binary. Keep the current retention behavior for legacy receipts until a per-kind expiry policy is published and verified. The lifecycle design specifies at least 24 hours for its retry window. It is not a global TTL, especially for restore and authorization evidence.

The repository currently validates one shared V1 baseline and does not maintain pre-release in-place upgrades. Keep the first rollout schema-compatible so existing V1 history stays in place. A later change that requires an outbox table, a new operation kind, or a new proof column has a separate schema and deployment gate. Follow the current baseline rules for new development catalogs. For a deployed catalog without a supported upgrade, keep the schema-compatible path and retain the historical database. Plan an explicit data migration or a qualified supported upgrade before changing that catalog's shape.

## Verification and rollout gates

- On real MySQL 8.4 with two eligible consumers, use the same data and conditions in poll and MQ modes. Exercise duplicate, late, lost, and out-of-order wakeups, publisher outage, crash after admission, crash after claim, and crash after a page commits. Assert one valid claim commits each page, durable progress continues, and no eligible operation disappears. Include a pre-expiry wakeup and a blocked recovery or reader. For the pilot, verify that SQL collection works with tool publication disabled.
- Run compatibility fixtures for each compacted kind. Compare the operation lookup and same-key responses for legacy and compact rows, including a different actor and a conflicting digest. Verify operation references, output predecessors, Worktree/artifact joins, CLOSE evidence, and Workspace recovery. Validate that schema-compatible rollback starts on the existing catalog and can resume the original lease and cursor.
- Observe operation scans and queried rows per instance, oldest due age by kind, MQ lag and redelivery, lease conflicts and takeovers, recovery backlog, and compaction mismatches. Move the next kind only after the pilot shows reduced API-replica scanning and passes fault recovery within the agreed latency budget. Define the per-kind replay retention and the dedicated worker's capacity before enabling payload trimming or queue-only discovery on its normal path.

The broker deployment and delay support, the per-kind latency and receipt retention targets, and historical database volumes remain to be confirmed on the intended environment. Capacity and failure-injection acceptance are still required in the target environment.

## Phase-one implementation scope

Enable `qwen.managed-agent.session-resource-gc.enabled` for MySQL-only collection. Supply the RocketMQ proxy endpoints, a dedicated DELAY topic, and an ordinary consumer group to add MQ delivery. A successful DELETE signals a best-effort wakeup after commit. The message identifies the tenant and Session, from which the worker derives the existing `SESSION_RESOURCE_GC` operation reference. MySQL still checks the grace period, blockers, lease and cursor.

Each wakeup attempts one page through the same claim and page transactions as SQL polling. The one-second polling worker drives further pages, deferred work, historical backfill, and recovery from missing messages or expired claims. API replicas can set `worker-enabled=false` and still publish. Keep at least one worker enabled. Clearing all three MQ settings reverts to polling only. Sessions with external resources, captures, or journal packs are deferred. The implementation uses the existing V1 schema and the existing legacy tool-publication schedule.
