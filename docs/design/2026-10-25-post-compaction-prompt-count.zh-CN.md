# 压缩后的 prompt 计数

[English](2026-10-25-post-compaction-prompt-count.md) | [简体中文](2026-10-25-post-compaction-prompt-count.zh-CN.md)

状态：已为 [#15486](https://github.com/QwenLM/qwen-code/issues/15486) 实现。

## 问题

自动压缩可能在一条消息尚未发出时运行。这发生在 hard 档兜底，或工具循环中途的自动压缩里：工具结果已经拿到，但还没发出去。压缩本身成功了，下一次请求的估算却偏大，原因有两个：

1. **待处理消息被算了两遍。** 它留在了压缩后的计数里，下一次估算时又被加了一次。
2. **余量吃掉了输出保底。** 每次压缩后得到的都是估算计数，而估算计数会被加上 20,000 token 的余量。给回复保留空间的保底，上限是“窗口 − 带余量的估算”。窗口比余量还小时，这个上限是负数，保底就降成了 1。

具体看哪个检查读到这个估算，回合会以下面两种方式之一失败：

- hard 档检查拦下回合（“Context is too large to send safely after automatic compression … compression status: COMPRESSED”）；
- 或者请求以 `max_tokens: 1` 发出，最后报 “Model stream ended after a tool result without visible progress”。

实测情况：

- **已发布的 0.24.6，64K 窗口，mock provider。** hard 档压缩成功，压缩后计数为 25,225，其中已经包含待处理的结果。检查用的估算是 45,241，超过 41,000 的 hard 阈值，回合被拦下。
- **真实 provider，262,144 token 窗口。** 一次 47.6 万字符的 `read_file` 之后，下一次请求约 126K token，连续 5 次以 `max_tokens: 1` 发出。
- **16K 窗口。** `/compress` 之后计数为 4,805，输出上限计算用的估算是 24,903，于是 `max_tokens` 为 1，而实际还空着约 8K token。

## 本次修改之前的现状

- 自动压缩和 hard 档兜底时，调用方把它的有效估算当作压缩的原始计数传入。这个有效估算 = 上一轮计数 + 上一轮输出 + 待处理消息，如果本次发送时记忆目录有变化，还要再加一份记忆快照。
- 压缩服务的说明里，这个计数是“待处理消息**之前**”的 prompt。它用摘要替换原始计数里历史所占的部分，得出压缩后的计数。所以调用方额外加进去的内容，都会留在压缩后的计数里。
- 压缩之后，聊天对象把这个计数存为估算值。hard 档检查和输出上限计算都会在它上面再加上待处理内容，输出上限计算还会乘以 1.5。
- 输出上限计算会给估算计数加 20,000 token 的余量。恢复重试时，对历史的遍历估算也加同样的余量。
- 输出保底是 `min(4,000, window − prompt)`，其中 `prompt` 是带余量的估算（#13252）。
- 压缩记录存的是“压缩后的历史 + 追加的待处理消息”，好让恢复后保留压缩发生时的那一轮。记录里还存了压缩后的计数，它现在之所以包含待处理消息，只是因为上面那个重复计数。

## 目标

- 压缩之后，待处理内容只计算一次。
- 只要估算本身已经包含固定开销，放得下的 prompt 至少能拿到保底；剩余空间比保底小时，拿到全部剩余空间。
- 新会话的输出上限，以及所有达到或高于保底的输出上限，都保持不变。
- 压缩记录的计数与它存的内容一致：压缩后的历史，加上请求实际携带的待处理消息。

## 非目标

- 去掉余量或调整余量大小。新会话的历史遍历会漏掉系统指令和工具定义：现有的一次 dry run 中，真实 prompt 是 18,359 token，估算只有 1。
- 压缩后恢复文件的预算（#15487）。
- 压缩请求本身的大小（#14953、#9455）。
- 回复被截断后提升 `max_tokens`。

## 设计

### 传给压缩的基线

发送路径把同一个估算算两次：一次包含本次发送的待处理内容（有效计数），一次不包含（基线），两者都传入。压缩用基线作为原始计数，这正是压缩服务说明里写的含义。这样，压缩后的计数 = 压缩后的历史 + 基线里带的固定开销；hard 档检查和输出上限计算各自只加一次待处理内容。

后备情况：

- 调用方如果只传了有效计数，就从中减去待处理消息的估算。
- 没有预先算好的计数时，本地估算只遍历不含待处理消息的历史。

变的只有原始计数。压缩的触发门仍然读取包含待处理内容的有效计数（`precomputedEffectiveTokens`），缓存共享请求的大小检查也读它。基线低于 auto 阈值、但加上待处理消息后超过阈值的发送，照样会触发压缩。

冷路径用 side query 的输入计数推出压缩后的计数。自 #17141 起，这个公式有两个分支：

- **没有保留尾部。** side query 带着待处理的工具结果，服务从输入计数里减掉这个结果。
- **有保留尾部。** side query 在保留的操作之前截止，不带待处理结果，所以什么也不减。

两个分支下，压缩后的计数都是：原始计数 − 被摘要的历史 + 摘要（有尾部时，再加上引出尾部的那段说明）。所以只要基线不含待处理消息，两个分支下压缩后的计数都不含它。

### 压缩记录

记录的快照里仍然存着待处理消息；如果之后没有回复带回用量，恢复时就用这条记录里的计数作为起始值。所以记录会把待处理消息加回到它的两个计数里，两处写记录的地方都这样做：自动压缩，以及延后写入的 hard 档记录。加回的是压缩后那次请求实际携带的这条消息，也就是恢复时回放的内容。压缩后的历史里没有记忆快照，所以有记忆目录时，发送会附上当前目录的快照；没有记忆目录时，请求会去掉重放消息里带的旧快照，这份快照就不计数，但记录仍按原样保存这条重放消息。压缩前算出的有效计数不能代替这个值：记忆目录已经在历史里时，它不会附快照，而压缩又把那份快照删掉了，于是压缩后的发送会再附一次。不涉及记忆快照时，持久化的数值和现在完全一样；涉及时，记录会计入恢复后历史里确实存在的那份快照，不计入不存在的那份。

加回时新建一份记录内容，不改压缩结果本身。压缩后聊天对象采用的计数和 `COMPRESSED` 事件，都保持不含待处理消息的压缩后计数。如果改成把消息加进压缩结果，重复计数就会回来，因为聊天对象是在写完记录之后才采用结果里的计数。

### 余量与输出保底

`clampOutputTokensToWindow` 新增一个可选参数，指定给保底封顶用的 prompt 大小，默认就是它正在计算的那个 prompt：

```
room      = window − paddedPrompt − margin
floor     = max(1, min(4,000, window − floorPrompt))
maxTokens = min(ceiling, max(floor, room))
```

- **首次发送。** 只有估算计数会加余量。这个计数为正时（压缩后的计数，或用估算值恢复的会话），给保底封顶的是不带余量的估算。计数为 0 时，估算来自新会话的历史遍历，保底仍按带余量的估算封顶。provider 计数不加余量，它的保底也就不变。所以这项放宽只作用于 `count > 0 && isEstimated`。
- **恢复重试。** 每次恢复重试都会给历史遍历加余量，不管计数从哪里来。基于计数的估算（来自 provider 计数或压缩后的计数）覆盖了遍历结果时，用它给保底封顶；否则（包括计数为 0 时）用带余量的遍历结果。
  - 这也覆盖了 #15486 上报告的小窗口下 `MAX_TOKENS` 之后的续写。在 32,768 token 的窗口上，基于用量的估算约 22.8K，遍历结果约 14.5K，带余量的遍历结果约 34.5K，续写请求以 `max_tokens: 1` 发出。现在它拿到 4,000。基于用量的估算本身就占满窗口时，仍然是 1。
- **恢复重试的上限。** 恢复重试的上限，是这次尝试在按窗口夹之前的那个上限：发生过提升时用提升的上限，否则用请求自己的上限。每次重试都会用自己的估算按窗口重新夹一遍。以前它沿用第一次发送夹过之后的值，而那个值是在任何用量返回之前算的：新会话上，带余量的历史遍历可能把它压到只有几百 token，即使新鲜用量显示还有空间，恢复重试也一直停在那里。一次 32,768 token 窗口的端到端运行中，每次续写都只有 320。
- **剩余空间。** room 始终用带余量的估算计算，所以余量照样会缩小保底以上的每一个输出上限。

### 窗口不变量（#5950）

输出上限计算的设计目标是：只要估算的 prompt 放得进窗口，每个主回合请求都满足 `prompt + max_tokens ≤ window`（#5950）。之后 #13252 又用 `window − prompt` 给 4,000 token 的保底封顶，让小窗口也守住这个不变量。

本次修改有意对基于计数的估算放宽了这个不变量。它们的保底按“窗口 − 不带余量的估算”封顶，所以带余量的估算加上 `max_tokens` 最多可以比窗口多出一个余量。不变量现在针对的是不带余量的、基于计数的估算，而不是带余量的估算。计数为 0 的新会话遍历仍按带余量的估算封顶；首次发送时 provider 计数本来就不加余量。

不放宽的话，小窗口在压缩之后就没有输出空间。在 32,768 token 的窗口上，窗口减去余量只剩 12,768 token，即使修掉了重复计数，任何超过这个数的压缩后估算都会拿到 `max_tokens: 1`。

输出上限计算在 `docs/design/` 下没有单独的设计文档。本节记录这项修改，`tokenLimits.ts` 中 `MIN_CLAMPED_OUTPUT_TOKENS` 和 `clampOutputTokensToWindow` 的注释写明了同样的范围。

## 决策与理由

| 决策                               | 理由                                                                                                                                                                                                                                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 改调用方，而不是压缩服务           | 压缩服务遵守了它写明的约定，是一个调用方传入的计数违反了约定。手动 `/compress`、被动压缩、`/compress-fast` 和 hosted 压缩都不传待处理消息，保持不变。                                                                                                                                                  |
| 传入基线，而不是减去待处理消息     | 有效计数里可能还有随这条消息一起发送的记忆快照。用同一个估算、只去掉待处理内容，无论里面有什么都能精确抵消。                                                                                                                                                                                           |
| 记录按实际发送的样子计入待处理消息 | 记录的快照里存着这条消息，恢复时又用记录里的计数作为起始值。记录如果不计入它，恢复后的会话就会少算一条消息。按压缩后那次请求实际携带的样子计数，恢复后历史里有的记忆快照会被计入，请求去掉的不会。                                                                                                     |
| 限制保底的上限，保留余量           | 新会话的历史遍历确实漏掉了约 18K token 的固定开销。输出上限高于保底时，超出窗口的量正好是余量和安全边距没覆盖到的那部分开销。窗口的 1/4 作为余量，加上 10K 的安全边距，要到约 33K 的窗口才能覆盖 dry run 里的 18,359 token，所以更小窗口的新会话会超窗。限制保底的上限，只改变那些低于保底的输出上限。 |
| 只针对基于计数的估算               | 在新会话的历史遍历上，余量代表真实存在的开销。在那里改用不带余量的估算来封顶，会出现一个区间：现在约 2K 的输出上限放得下，4K 却放不下。按 dry run 里 18,359 token 的开销算，这个区间是“窗口 − 估算”在 20K 到约 22.4K 之间。                                                                            |
| 恢复重试要求计数覆盖遍历结果       | 遍历结果超出计数时，多出来的部分可能是计数漏掉的真实增长，比如某次回复没有带回用量。这时保留带余量的封顶。                                                                                                                                                                                             |
| 对基于计数的估算放宽 #5950 不变量  | 基于计数的估算已经带着余量所代表的那部分开销；再按带余量的估算给它的保底封顶，小窗口在压缩之后就没有空间了。代价是可能出现一次 400：首次发送时由既有的被动溢出恢复处理，恢复重试时回复停在已经写出的内容（见“风险”）；不放宽的话，则是一个结束回合的 `max_tokens: 1` 回复。                            |
| 触发门继续读有效计数               | 变的只是用来推算压缩后计数的那个计数。压缩仍按本次发送真正要带的 prompt 触发，不会比以前触发得晚。                                                                                                                                                                                                     |

## 风险

- 基于计数的估算漏掉固定开销时，放宽后的保底（见“窗口不变量”）可能超过实际剩余的空间，比如压缩后的计数，其基线本身就来自新会话的历史遍历；或者恢复时用的是估算值。受影响的只有真实 prompt 超过 `window − 4,000` 的情况，在一个最宽 4,000 token 的区间内。这时 provider 会以上下文溢出拒绝请求，由既有的被动溢出恢复压缩后重试。修改之前，同样的情况会以 `max_tokens: 1` 发出，回合没有任何输出就结束，所以现在的失败方式严格更好。
  - 在 16K 窗口上实测：恢复后的会话会重新加入约 3K token 的启动上下文，而从压缩记录取得的计数里没有这部分。`/compress` 之后的追问超出窗口 639，溢出恢复做了压缩，回合随后完成。同样的流程在 20K 窗口上放得下。
  - 回复被截断后的恢复重试，只有基于计数的估算覆盖了历史遍历结果时才放宽保底，这排除了漏掉的内容比计数所含开销还多的计数。漏得更少的过期计数（循环里某次回复没有带回用量）仍会通过，这次发送最多超出窗口 `min(4,000, 计数漏掉的内容)`。恢复循环不走被动溢出恢复：被拒绝的那次发送会被撤销，回复停在已经写出的内容。修改之前，这次发送拿到的是按带余量估算的保底，更小，在小窗口上常常是 1。
- 带待处理消息的自动压缩之后，“Context compressed (A -> B)” 提示和压缩遥测里的两个数都不再含待处理消息；在下一次回复带回用量之前，ACP 的会话计数也不含它。
- 保底抬高输出上限时，回复截断后的提升仍然不会触发，和现在一样。
- 在 16K 窗口上，请求无论如何都有一部分无法满足，因为真实的固定开销可能接近整个窗口。

## 验证

- `tokenLimits.test.ts` 中的单元测试：
  - 保底按不带余量的估算封顶；
  - 带余量的剩余空间达到保底时保持不变；
  - #13252 的封顶对不带余量的估算依然成立；
  - 低于保底的显式上限被保留。
- `llm-chat.test.ts` 中的单元测试（`#15486`）：
  - **基线：**
    - 不含待处理消息，保留上一轮输出；
    - 同样不含随消息发送的记忆快照；
    - 没有预先算好的计数时，同样不含待处理消息。
  - **通过真实压缩服务的端到端测试：**
    - C1 场景，待处理消息分工具结果和纯文本，分别走缓存共享和冷路径两条计数分支。请求都能发出，压缩后的计数小于待处理消息；
    - 冷路径公式的两个分支，有和没有保留尾部。压缩后的计数精确等于：基线 − 被摘要的历史 + 摘要（有尾部时再加上尾部前的说明）；只有没有尾部时，side query 才带着待处理结果；
    - 触发门：基线 165K，低于 170K 的 auto 阈值，10K 的待处理消息让有效计数达到 175K。压缩经由真实的触发门运行，传入的 `precomputedEffectiveTokens` 是完整计数。
  - **记录：** hard 档和自动压缩的记录都计入了待处理消息，而聊天对象采用的计数和 `COMPRESSED` 事件保持压缩后的计数。两条记录路径上，记录加回的都恰好是请求实际携带的消息：带新的记忆快照；压缩从历史里删掉快照、发送时再次附上；以及请求去掉重放快照，而记录仍保存它。
  - **首次发送：** 16K 窗口压缩后得到 4,000 而不是 1；新会话保留带余量的封顶（32K 窗口上为 1,999）。
  - **恢复重试：**
    - 有 provider 计数的 16K 窗口得到 4,000；
    - 在 32,768 token 的窗口上，留有空间的新鲜用量得到 4,000，占满窗口的新鲜用量得到 1；
    - 计数没有覆盖遍历结果时，保留带余量的封顶，计数为正但小于遍历结果时也是如此；
    - 基于计数的估算恰好等于遍历结果时，用它给保底封顶：这个判断包含相等；
    - 新会话的第一次发送被余量压到约 500 token 时，用量显示还有空间后，恢复重试得到 4,000；调用方设的 2,000 上限仍然有效。
- 更新的现有测试：两个原始计数的期望值改为不含待处理消息，一个记录计数的期望值改为包含它。
- 变异检查：14 个手写变异，每个撤销上面的一项决定（记录加回、采用的计数、触发门的输入、首次发送和恢复重试时保底的适用范围、冷路径的任一分支、基线本身），每个都至少让上面的一个测试失败。第一轮评审后的修复另有 5 个变异，同样都会失败：任一条记录路径改回加原始消息；自动压缩的记录改用压缩前的有效计数减基线（会漏掉压缩删掉的快照）；恢复重试的判断写成 `>` 或 `> 0`。恢复重试的上限另有 3 个变异（改回第一次发送的值、一律用请求自己的上限、一律用提升的上限），也都会让某个测试失败。
- 针对 mock provider 和真实 provider 的端到端运行，在 PR 中报告。

## 验收标准

- 带待处理消息的压缩之后，hard 档检查和输出上限计算只计算一次待处理内容。
- 放得下的、基于计数的估算，不会因为余量而拿到低于 `min(4,000, window − 不带余量的估算)` 的 `max_tokens`。
- 新会话的输出上限，以及所有达到或高于保底的输出上限，保持不变。
- 压缩记录的计数恰好等于：压缩后的历史，加上压缩后那次请求实际携带的待处理消息。
