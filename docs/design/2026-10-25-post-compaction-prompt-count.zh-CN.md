# 压缩后的 prompt 计数

[English](2026-10-25-post-compaction-prompt-count.md) | [简体中文](2026-10-25-post-compaction-prompt-count.zh-CN.md)

状态：已为 [#15486](https://github.com/QwenLM/qwen-code/issues/15486) 实现。

## 问题

自动压缩可能在一条消息尚未发出时运行。这发生在 hard 档兜底，或工具循环中途的自动压缩里：工具结果已经拿到，但还没发出去。压缩本身成功了，下一次请求的估算却偏大，原因有两个：

1. **待处理消息被算了两遍。** 它留在了压缩后的计数里，下一次估算时又被加了一次。
2. **余量吃掉了输出保底。** 每次压缩后得到的都是估算计数，而估算计数会被加上 20,000 token 的余量。给回复保留空间的保底，上限是“窗口 − 带余量的估算”。窗口比余量还小时，这个上限是负数，保底就降成了 1。

具体看哪个检查读到这个估算，回合会以下面两种方式之一失败：

- hard 档检查拦下回合（“Context is too large to send safely after automatic compression … compression status: COMPRESSED”）；
- 或者请求以 `max_tokens: 1` 发出，最后报 “Model stream ended after a tool result without visible progress”。

实测情况：

- **已发布的 0.24.6，64K 窗口，mock provider。** hard 档压缩成功，压缩后计数为 25,225，其中已经包含待处理的结果。检查用的估算是 45,241，超过 41,000 的 hard 阈值，回合被拦下。
- **真实 provider，262,144 token 窗口。** 一次 47.6 万字符的 `read_file` 之后，下一次请求约 126K token，连续 5 次以 `max_tokens: 1` 发出。
- **16K 窗口。** `/compress` 之后计数为 4,805，输出上限计算用的估算是 24,903，于是 `max_tokens` 为 1，而实际还空着约 8K token。

## 本次修改之前的现状

- 自动压缩和 hard 档兜底时，调用方把它的有效估算当作压缩的原始计数传入。这个有效估算 = 上一轮计数 + 上一轮输出 + 待处理消息，如果本次发送时记忆目录有变化，还要再加一份记忆快照。
- 压缩服务的说明里，这个计数是“待处理消息**之前**”的 prompt。它用摘要替换原始计数里历史所占的部分，得出压缩后的计数。所以调用方额外加进去的内容，都会留在压缩后的计数里。
- 压缩之后，聊天对象把这个计数存为估算值。hard 档检查和输出上限计算都会在它上面再加上待处理内容，输出上限计算还会乘以 1.5。
- 输出上限计算会给估算计数加 20,000 token 的余量。恢复重试时，对历史的遍历估算也加同样的余量。
- 输出保底是 `min(4,000, window − prompt)`，其中 `prompt` 是带余量的估算（#13252）。
- 压缩记录存的是“压缩后的历史 + 追加的待处理消息”，好让恢复后保留压缩发生时的那一轮。记录里还存了压缩后的计数，它现在之所以包含待处理消息，只是因为上面那个重复计数。

## 目标

- 压缩之后，待处理内容只计算一次。
- 只要估算本身已经包含固定开销，放得下的 prompt 至少能拿到保底；剩余空间比保底小时，拿到全部剩余空间。
- 新会话的输出上限，以及所有达到或高于保底的输出上限，都保持不变。
- 压缩记录里持久化的计数保持不变。

## 非目标

- 去掉余量或调整余量大小。新会话的历史遍历会漏掉系统指令和工具定义：现有的一次 dry run 中，真实 prompt 是 18,359 token，估算只有 1。
- 压缩后恢复文件的预算（#15487）。
- 压缩请求本身的大小（#14953、#9455）。
- 回复被截断后提升 `max_tokens`。

## 设计

### 传给压缩的基线

发送路径把同一个估算算两次：一次包含本次发送的待处理内容（有效计数），一次不包含（基线），两者都传入。压缩用基线作为原始计数，这正是压缩服务说明里写的含义。这样，压缩后的计数 = 压缩后的历史 + 基线里带的固定开销；hard 档检查和输出上限计算各自只加一次待处理内容。

后备情况：

- 调用方如果只传了有效计数，就从中减去待处理消息的估算。
- 没有预先算好的计数时，本地估算只遍历不含待处理消息的历史。

### 压缩记录

记录的快照里仍然存着待处理消息；如果之后没有回复带回用量，恢复时就用这条记录里的计数作为起始值。所以记录会把待处理消息的估算加回到它的两个计数里，持久化的数值和现在完全一样，只有运行中的计数变了。

### 余量与输出保底

`clampOutputTokensToWindow` 新增一个可选参数，指定给保底封顶用的 prompt 大小，默认就是它正在计算的那个 prompt：

```
room      = window − paddedPrompt − margin
floor     = max(1, min(4,000, window − floorPrompt))
maxTokens = min(ceiling, max(floor, room))
```

- **首次发送。** 估算基于计数时（从 provider 计数或压缩后的计数出发），给保底封顶的是不带余量的估算。新会话的历史遍历仍用带余量的估算。
- **恢复重试。** 基于计数的估算覆盖了历史遍历结果时，用它给保底封顶；否则用带余量的遍历结果。
- **剩余空间。** room 始终用带余量的估算计算，所以余量照样会缩小保底以上的每一个输出上限。

## 决策与理由

| 决策                           | 理由                                                                                                                                                                                                                                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 改调用方，而不是压缩服务       | 压缩服务遵守了它写明的约定，是一个调用方传入的计数违反了约定。手动 `/compress`、被动压缩、`/compress-fast` 和 hosted 压缩都不传待处理消息，保持不变。                                                                                                                                                  |
| 传入基线，而不是减去待处理消息 | 有效计数里可能还有随这条消息一起发送的记忆快照。用同一个估算、只去掉待处理内容，无论里面有什么都能精确抵消。                                                                                                                                                                                           |
| 记录继续计入待处理消息         | 记录的快照里存着这条消息，恢复时又用记录里的计数作为起始值。记录如果不计入它，恢复后的会话就会少算一条消息。                                                                                                                                                                                           |
| 限制保底的上限，保留余量       | 新会话的历史遍历确实漏掉了约 18K token 的固定开销。输出上限高于保底时，超出窗口的量正好是余量和安全边距没覆盖到的那部分开销。窗口的 1/4 作为余量，加上 10K 的安全边距，要到约 33K 的窗口才能覆盖 dry run 里的 18,359 token，所以更小窗口的新会话会超窗。限制保底的上限，只改变那些低于保底的输出上限。 |
| 只针对基于计数的估算           | 在新会话的历史遍历上，余量代表真实存在的开销。在那里改用不带余量的估算来封顶，会出现一个区间：现在约 2K 的输出上限放得下，4K 却放不下。按 dry run 里 18,359 token 的开销算，这个区间是“窗口 − 估算”在 20K 到约 22.4K 之间。                                                                            |
| 恢复重试要求计数覆盖遍历结果   | 遍历结果超出计数时，多出来的部分可能是计数漏掉的真实增长，比如某次回复没有带回用量。这时保留带余量的封顶。                                                                                                                                                                                             |

## 风险

- 基于计数的估算仍可能漏掉固定开销，比如压缩后的计数，其基线本身就来自新会话的历史遍历；或者恢复时用的是估算值。在一个最宽 4K 的区间内，保底可能超过实际剩余的空间。这时 provider 会拒绝请求，由被动溢出恢复处理。而在同样的情况下，现在会以 `max_tokens: 1` 发出，回合直接结束。
  - 在 16K 窗口上实测：恢复后的会话会重新加入约 3K token 的启动上下文，而从压缩记录取得的计数里没有这部分。`/compress` 之后的追问超出窗口 639，溢出恢复做了压缩，回合随后完成。同样的流程在 20K 窗口上放得下。
- 带待处理消息的自动压缩之后，“Context compressed (A -> B)” 提示和压缩遥测里的两个数都不再含待处理消息；在下一次回复带回用量之前，ACP 的会话计数也不含它。
- 保底抬高输出上限时，回复截断后的提升仍然不会触发，和现在一样。
- 在 16K 窗口上，请求无论如何都有一部分无法满足，因为真实的固定开销可能接近整个窗口。

## 验证

- `tokenLimits.test.ts` 中的单元测试：
  - 保底按不带余量的估算封顶；
  - 带余量的剩余空间达到保底时保持不变；
  - #13252 的封顶对不带余量的估算依然成立；
  - 低于保底的显式上限被保留。
- `llm-chat.test.ts` 中的单元测试（`#15486`）：
  - **基线：**
    - 不含待处理消息，保留上一轮输出；
    - 同样不含随消息发送的记忆快照；
    - 没有预先算好的计数时，同样不含待处理消息。
  - **通过真实压缩服务的端到端测试：** C1 场景，待处理消息分工具结果和纯文本，分别走缓存共享和冷路径两条计数分支。请求都能发出，压缩后的计数小于待处理消息。
  - **记录：** hard 档和自动压缩的记录都计入了待处理消息。
  - **首次发送：** 16K 窗口压缩后得到 4,000 而不是 1；新会话保留带余量的封顶（32K 窗口上为 1,999）。
  - **恢复重试：** 有 provider 计数的 16K 窗口得到 4,000；计数没有覆盖遍历结果时，保留带余量的封顶。
- 更新的现有测试：两个原始计数的期望值改为不含待处理消息，一个记录计数的期望值改为包含它。
- 11 个变异全部被测试抓到。它们覆盖：传入的基线、带待处理内容的基线、减法后备、遍历后备、输出上限的保底参数、首次发送“基于计数”条件的正反两面、恢复重试“计数覆盖遍历”条件的正反两面，以及两处写记录的地方。
- 针对 mock provider 和真实 provider 的端到端运行，在 PR 中报告。

## 验收标准

- 带待处理消息的压缩之后，hard 档检查和输出上限计算只计算一次待处理内容。
- 放得下的、基于计数的估算，不会因为余量而拿到低于 `min(4,000, window − 不带余量的估算)` 的 `max_tokens`。
- 新会话的输出上限，以及所有达到或高于保底的输出上限，保持不变。
- 压缩记录里持久化的计数保持不变。
