# Web Shell 输入框任务解释

[English](web-shell-composer-task-explain.md) | [简体中文](web-shell-composer-task-explain.zh-CN.md)

状态：已实现并于 2026-11-16 在本地完成验证（单测、E2E、visuals、真实模型运行）；点击与焦点契约于 2026-11-23 更新。

## 问题

输入框上方的 chip 只说明哪类后台工作尚未结束（`1 shell`、`2 local agents`），点击后打开的是原始详情：shell 输出、subagent 转录、workflow 图。只想知道“这个任务到底在做什么、为什么在跑”的用户，必须打开界面自行解读。缺少一键获得的通俗解释。

## 现状

- chip 行为在 [Background agent status and details](background-agent-status-and-details.md) 中规定：每类未结束工作一个 chip，单任务 chip 直接打开任务，多任务 chip 在 chip 行上方列出任务供选择。
- daemon 已有侧问通道（`POST /session/:id/btw/stream`，能力 `session_btw_stream`）：fork 一个共享完整主对话上下文、无工具、流式回答且不中断主回合的轻量 agent。Web Shell 通过 `/btw` 与输入框添加菜单暴露它，回答渲染在输入框上方的面板里。
- `POST /session/:id/recap` 是“不产生提示词回合的尽力而为模型摘要”的第二个先例。

## 目标与非目标

目标：

- 每个后台任务一个“?”入口，请模型用 2-4 句话解释该任务，同时利用任务快照与对话上下文。
- 解释不得中断主回合或任务本身，也不得向转录添加提示词回合。

非目标：

- 不新增 daemon 路由、SDK 表面或 capability 标签。
- 不改变任务生命周期、chip 成员规则或轮询。
- 不做解释历史持久化、不做自动解释、不在服务端聚合更丰富的上下文（输出尾部、转录）——见后续工作。

## 设计

UI（全部在 Web Shell 客户端）：

- 单任务 chip 旁增加一个“?”按钮，样式为配套的圆角小按钮。chip 本身仍然打开任务；“?”只负责提问。无论是否渲染“?”，每个 chip 都位于稳定的 wrapper 中，因此组跨越 1↔2 任务边界时 chip 节点被复用而不是重建，键盘焦点不会落到另一个 chip 上。“?”本身会在组增长时卸载；焦点回收效果随后落在所属组的 chip 上（按 kind 标记），而不是排序最前的组，也不受另一分组展开的列表影响。
- 多任务 chip 本身不带“?”；其列表每行在打开按钮之后各带一个。每行 Tab 序为：打开，然后解释。行的每一个着色点都属于两个按钮之一——打开按钮承担行内边距与其 hover 填充，“?”拉伸到整行高度，行间距为零——因此没有无处理器的条带被点亮，行只作为祖先焦点提示保留强调色。行内“?”按 Escape 与行打开按钮一致：关闭列表并把焦点交回 chip。应用层的 btw 关闭快捷键向拥有键盘的表面让路，复用应用层处理器信任的同一组集中标记：展开的模态框（dialog/alertdialog/drawer，含移植进 shell 根的组件级确认框）、等待小游戏、键盘作用域子树。这些表面只拥有它们实际消费的按键，守卫信任集中标记而非手工归类的表面名称。drawer——以及任何未把自己标记为键盘作用域的 dialog——只拥有 Escape：其主体上的 Enter/Space 仍能关闭落定解释，控件上的 Enter/Space 仍能激活该控件。等待小游戏（Space 暂停、Enter 重开）、键盘作用域状态卡片（Enter/Space 开关详情、执行服务端动作），以及基于共享 DialogShell 构建的 dialog（它把内容标记为键盘作用域，使其表单与列表保留 Enter/Space）都除 Escape 外还消费 Enter/Space，故守卫也向它们让出这些键。取消组合键从不被这些表面拥有——Ctrl+C/Ctrl+D 即使在模态框/drawer 打开时仍能中止在途侧问（1001px 以下抽屉承载的详情面板会让展开的模态表面恒存在）。唯一例外是守卫下真实文本表面（input/textarea/select、非 `false` 的任意 contenteditable、CodeMirror 编辑器）上 Ctrl+C 的复制语义；Ctrl+D 永不复制，键盘作用域子树本身也不是文本表面，故状态卡片内的按钮仍能取消。可激活控件（按钮、链接、字段、菜单项、tab、grid/tree 行等）上的 Enter/Space 激活该控件；chip 行内或展开的菜单/listbox 内的 Escape 归该控件。grid 与 tree 用 Enter/Space 打开行，但并不普遍拥有 Escape（轨迹网格只在有行选区时才消费），故不是 Escape 持有者——豁免它们的 Escape 会让按键无人消费、在面板背后预备一次意外的回合取消。应用层 Escape 处理器同样在判定意图前向键盘作用域子树让路，因此不会在自身延迟处理器拥有 Escape 的状态卡片背后预备两次按键的回合取消。其余位置的 Escape——包括点击后持有焦点的面板头部“?”——按面板快捷键提示关闭或取消，Ctrl+C/Ctrl+D 可取消在途侧问（守卫下真实文本表面上 Ctrl+C 让位复制）。输入框编辑器从不豁免。chip 旁的“?”沿用 chip 键盘处理（方向键在 chip 间移动，Down/Escape/可打印字符回到输入框），但 ArrowLeft 回到它所属的 chip 而不是越过它。两种“?”都绘制与 chip 一致的键盘焦点环；仅靠填充在浅色主题下与 hover 无法区分。
- 该入口是组件的可选 prop；未接线的宿主不渲染任何“?”（无 header 嵌入与宿主自带 footer 不受影响）。
- 同样的解释也可从任务的详情面板发起：当右侧面板的活动 tab 展示 shell、monitor 或 subagent 任务时，共享面板头部在动作区旁提供一个“?”。shell 与 monitor tab 自带任务快照；subagent tab 按打开路径注册的同一 id 域（`toolUseId ?? id`）在注册表中解析任务，因此已被注册表驱逐的 agent 不提供“?”。workflow tab 不指向具体运行，仅保留 chip 列表入口。

### chip 直接激活与列表选行

直接激活单任务 chip 时，会传递任务和明确的切换意图（`onSelectTask(task, true)`）。任务的当前详情面板已经展开时，再次激活会关闭它。列表选行只传递任务（`onSelectTask(task)`），用于选择或切换详情，不会折叠已经选中的面板。重新打开已隐藏或未激活的任务时，应用按任务身份复用现有详情页签及 id，不会在后台或 pending 页签旁再复制一个标准页签。复用沿用普通页签激活路径，失败或仍在加载的 pending 详情会恢复或重试 hydration。再次激活检查当前激活且匹配任务的别名，而不是第一个匹配页签，标准与后台别名共存时也不能让折叠判定漏掉已展开面板。

找不到可用 transcript 行的 Workflow 会打开 Tasks 弹窗。从请求发起前就按任务 id 与工具调用身份记录这个由 chip 触发的目标，因此快速再次激活同一目标能在弹窗尚未出现前取消打开。后来的激活带有不同工具调用身份时，仍可继续导航，而不会被误判为旧弹窗目标。已经显示的模态弹窗仍通过自身控件关闭，不假定被遮挡的 chip 仍可点击。由其他入口打开的 plan/tasks 弹窗不会给该 Workflow chip 赋予展开状态。transcript 中已有对应行的 Workflow 保留既有定位导航行为，不把内联图的局部展开与右侧面板或模态弹窗混为一谈。

多任务列表中，鼠标按下其按钮会保留现有焦点，避免浏览器的按钮聚焦行为在点击前卸载该行。失焦目标未确定时，指针手势会保留到指针释放，不会直接导致列表消失。焦点移动到组件外的明确 DOM 目标、外部指针按下或窗口失焦时，列表立即关闭。释放时，通过已有的 shadow-aware 焦点工具判断焦点是否仍在内部；若已移出，列表关闭，手势状态清除。轮询替换任务对象不会破坏手势保护，因为生命周期跟随真实的展开布尔值，而不是任务对象身份。

问题构造（纯客户端函数）：

- 事实来自 chip 已读取的任务快照：类型、标签、状态、已运行时长；按类型附加命令与工作目录（shell）、命令与事件计数（monitor）、agent 类型、prompt 摘录与最近五条活动（agent）、当前阶段、agent 进度、待审批数与最近五条日志（workflow）。
- daemon 用命令合成 shell 的 label 与 description，用 description 合成 monitor 的 label。因此构造器在 shell 的 `Label:` 与命令相同时省略该行（由 `Command:` 行承载），并在 `Description:` 与该类型的显示标签重复时省略它，同一段文本不会花费两份预算，也不会挤掉按类型的事实。
- 事实标签保持英文——它们是模型输入，不是 UI 文案。指令跟随 UI 语言（EN/ZH 目录；其他语言回退 EN），与会话的输出语言偏好一起引导回答语言。
- 逐字段摘录上限（label 400、description 400、command 500、prompt 1200、activity 160、log 200）防止单个字段淹没整个问题；最终守卫把整个问题控制在 4096 字符内，与 core 的 `BTW_MAX_INPUT_LENGTH` 一致（daemon 拒绝更长的侧问）。两处截断都丢弃末尾的高代理项，保证 JSON 载荷不出现孤立代理对。

回答路径：

- 点击“?”构造问题，并带一个独立的展示串交给现有的可见 btw 流程：模型收到完整的构造 prompt，面板只回显一条本地化短句（“解释这个任务在做什么：<label>”）。展示标签与“?”的 aria 标签都按 120 字符摘录，因此 label 是多 KB 命令的 shell 也不会把面板绘满。事实转储是模型输入，绝不绘制到面板上。手输 `/btw` 仍回显用户原话——展示覆盖默认回落到原问题。回答流式进入输入框上方现有的 btw 面板。接着问另一个任务会中止上一个侧问，与连续问两个 `/btw` 的语义一致。任务列表保持打开。任务解释带任务 id 标记，因此只要该任务的 tab 处于活动状态，回答还会就地镜像到详情面板主体上方——无论从哪个入口发起。镜像以 btw 消息 id 为 key，新提问会重挂载并恢复答案自动跟随。两份都不渲染 `/btw ` 斜杠命令前缀：按钮触发不是手输命令。镜像也不渲染输入框面板的快捷键页脚——它没有自己的可聚焦表面，页脚宣传的键会落在持有焦点的控件上（在头部“?”上按 Enter 会重新提问）。手输 `/btw` 不带标记、保留前缀，绝不镜像。

## 决策与理由

- **复用 btw 通道，而非专用 explain 路由。** fork 的 agent 已共享完整对话历史，因此知道任务为什么被启动——这是客户端快照携带不了的上下文。专用路由需要跨包改动（daemon、SDK、capability 基线、协议表），换来的却是严格更小的上下文。复用把 diff 留在 Web Shell 内，并继承已验证的不中断语义。
- **按任务粒度，而非整行一个“?”。** 解释保持有针对性；整行提问得到的是泛泛的摘要，且同样花费一次模型调用。
- **现有答案面板，而非新 popover。** 零新增浮层 UI，与 `/btw` 一致，且面板就在 chip 所在的输入框上方。

## 约束与风险

- 事实仅来自快照：不拉取 shell 输出尾部或 agent 转录。已运行时长取快照的 runtime，可能滞后于运行中的任务。任务快照来自 daemon 序列化器，label/description/command/cwd 无条件写入；构造器信任该契约，不为没有任何生产者会产生的形态设防。
- 解释质量依赖启动过程存在于对话上下文中；在本会话历史之外启动的任务只能依据事实解释。
- 每次点击花费一次 btw 通道模型策略下的侧问（配置了 fast model 时用 fast model，否则用会话模型），重试沿用该通道通常的流式重试行为。回答长度由 2-4 句的指令引导，而非特殊的 token 预算；fork 继承主 chat 的生成配置。写受阻会话静默无操作，与 `/btw` 一致。
- 信任边界不变：任务事实是模型撰写的文本，回答经由与任何 `/btw` 回答相同的 btw 表面渲染。

## 验证

- 单测：问题构造器（按类型事实、label 上限与重复事实省略、摘录上限、EN/ZH 的 4096 预算、两处截断的代理对安全、UI 语言指令）；组件（位置、点击、键盘含 chip“?”的 ArrowLeft、焦点归还、1↔2 边界下 chip 节点恒等、单任务与多任务可选退出）；App 到 btw 流的接线并钉住展示/问题分离。
- E2E：既有 composer-task-chips spec 更新为双动作行契约（定位器与 Tab 序），并新增“?”侧问用例（展示短句、无事实转储）、Escape 用例（列表关闭而解释面板保留），以及行命中盒（高亮左缘的 elementFromPoint 落在打开按钮上）与“?”焦点环（计算样式与 chip 自身环一致）的门禁断言；visuals 场景在明暗两主题下截取 chip、键盘聚焦的“?”、列表与流式回答，截图前均有锚定断言。
- 语言渲染：zh 的 aria 标签、tooltip 与面板展示短句都有测试真实渲染（组件与 App），删除 zh 键不会静默回退英文。
- 详情面板：ArtifactPanel 单测（头部“?”点击、按任务 id 匹配的就地镜像、另一任务或无任务时不镜像、摘录 aria）；App 用例经面板 props 钉住 chip→面板→解释 的接线；E2E 用例从 chip 打开 shell 面板并断言就地回答。
- 本机 daemon 真实模型确认：真实会话启动真实后台 shell 任务；点击“?”发出构造的问题（拦截所得，354 字符），模型以对话语言回答，点名命令、cwd、用户的后台启动要求以及更早结束的任务——期间任务持续运行。

## 验收标准

- 单任务 chip 显示一个相邻“?”；多任务列表每行一个；宿主未接线时不出现“?”。
- 点击“?”把解释流式送入 btw 面板，不打开任务、不产生转录提示词回合、不停止任务。面板显示展示短句，而非构造的 prompt。
- 构造的问题在任何已发布 UI 语言下都不超过 daemon 的侧问上限，且超长的 label 或命令不会挤掉按类型的事实。
- chip 行的键盘与焦点行为保持既有契约，并按文档扩展每行 Tab 停靠点：聚焦的 chip 节点在组大小变化时存活，chip 内的 Escape 不被面板快捷键吞掉，两种“?”都显示 chip 的焦点环。
- shell、monitor 或经注册表解析的 subagent 任务的详情面板在头部提供同样的“?”，并就地镜像解释；手输 `/btw` 的回答绝不镜像。

## 后续工作（有意延后）

- 若仅快照的解释被证明太单薄，再做服务端 explain 路由聚合更丰富上下文（输出尾部、最近转录）。
- 若用户希望解释钉在任务旁，再做 chip 相邻 popover 替代共享答案面板。
- 解释的持久化或刷新；今天每次点击都重新提问。
