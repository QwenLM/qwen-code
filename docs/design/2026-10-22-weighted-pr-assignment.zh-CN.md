# PR 负责人的加权随机分配

[English](2026-10-22-weighted-pr-assignment.md) | [简体中文](2026-10-22-weighted-pr-assignment.zh-CN.md)

## 问题

PR 分配目前会选择所属领域中未关闭且已分配的 Issue 数最少的候选人。
负载查询只统计 Issue，因此多分配一个 PR 不会增加该计数。如果某人有 17 个
Issue，而其他人都有 18 个或更多，所有进入这个候选池的新 PR 都可能分给同一个人。

## 设计

对 PR 分配，为每个符合条件的负责人设置 `1 / (openIssues + 1)` 的权重，
通过 `Math.random()` 按归一化后的权重抽取一次。加一使零 Issue 的情况也能正常
计算。每个候选人的概率均大于零；在同一候选池中，取得的 Issue 计数越低，概率越高。

例如，Issue 数为 0、1、3 时，权重分别为 1、1/2、1/4，概率分别为
4/7、2/7、1/7。负载相同则概率相同。只有一个符合条件的负责人时仍选择该人。

PR 选择函数放在 `.github/scripts/assign-pr-owner.mjs` 中。现有 Issue 选择函数
保留在 `.github/scripts/assign-issue-owner.mjs` 中，Issue 分配继续使用当前的
最小负载和并列轮转规则。两条路径继续共用配置加载和 Issue 计数查询。

按文件路径选择领域、退回更宽泛的领域、排除作者、实时写权限校验，以及写入前的
覆盖状态和 head 检查继续生效。已有候选池负责人被分配或参与评审后，后续运行
不会再次抽取。Dry run 会抽取候选人但不写入；由于它不预留结果，后续运行可以
抽到不同的人。

分配和 dry-run 摘要记录未经舍入的原始随机数、按有效候选人选择顺序排列的
实际参与计算的 Issue 负载，以及重试后仍无法取得负载的负责人。GitHub 静默拒绝
所选负责人时也保留相同证据。选择函数显式接收随机数，选择和摘要共用这一次抽样。
查询不可用时仍按零负载计算权重，但该负责人会列在不可用列表中，以区别于实际
查询得到的零负载。

## 范围与取舍

本次只修改 PR 选择规则，不增加设置、依赖、持久化轮转状态或工作流权限。
现有负载计数仍以 100 个未关闭 Issue 为上限，不计 PR。查询失败时仍保留现有的
重试和按零负载处理的回退，因此权重反映的是可取得的估计，而非完整工作量。

随机抽取仍可能连续选中同一个人。它分散的是分配机会，不保证严格轮转或工作量
均等。PR 编号不再决定被选中的负责人。

## 验证与验收标准

- 使用确定的随机数验证区间边界、零负载、相同负载、单人候选池，以及较忙者仍有
  非零概率被选中。
- 使用固定间距的抽样点验证独立计算的 4:2:1 比例，避免针对实际随机源执行不稳定的
  统计测试。
- 完整脚本测试只通过测试进程的 preload 控制随机数，验证较低和较高负载的候选人
  都能进入实际分配请求。恢复为最小负载选择后，这些检查必须失败。
- Preload 拒绝第二次随机抽样。分配、dry-run 和静默拒绝分配的摘要都应展示原始
  随机数、按顺序排列的有效负载及查询不可用的负责人，并区分查询失败与实际零负载。
- Preload 路径使用文件 URL，确保 POSIX 系统上包含 `#` 或 `?` 的临时目录可用。
- 现有测试继续覆盖作者排除、领域回退、权限过滤、dry run、负载查询失败、head
  变化、已有负责人和分配 API 失败。Issue 分配测试应保持不变并通过。
- 基线与新脚本通过模拟 GitHub CLI 验证，不在测试中重新分配真实 PR。这个工作流
  独立于 Qwen 交互式 CLI 运行。

## 待定事项

本次没有待定事项。如果基于 Issue 的概率仍不足以满足需要，可以另行考虑统计
已分配 PR 或细化领域负责人。
