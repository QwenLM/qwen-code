# 终端流式输出节奏

[English](tui-streaming-cadence.md) | [简体中文](tui-streaming-cadence.zh-CN.md)

## 问题与证据

用户在 Warp 中看到流式文字成批出现。主聊天会先缓存正文和思考 60 毫秒，
然后才更新 React；Ink 另外将虚拟视口限制为每秒最多 60 帧。因此，第一层等待
已经将持续到达的小分片合并成批，之后才进入渲染。

受控 PTY 复现约每 10 毫秒发送一个分片，已安装 CLI 的可见正文约每 67 毫秒
推进一次。另一组绕过聊天缓冲的 React 和 Ink 实验表明，普通 Markdown 的
渲染足以支持更短的更新间隔。代码高亮开销更大，单独测量。这些观察将应用
批处理与服务端分片节奏、终端绘制区分开来。

40×16 的另一组复现中，文字持续接收超过两秒，但可见段落不再推进，直到完成。
流式 Markdown 预览按照视口高度预算只保留开头，甚至可能丢弃整条很长的源代码行，
而虚拟列表本身已经能够测量和滚动较高的内容行。

CI 还发现输入补全关闭后的视口预算过期。Composer 在局部状态中恢复底部栏，
使控件从五行变为六行，但父组件仅在预先枚举的状态变化时重测。列表仍按
45 行滚动，Ink 实际只裁出 44 行，导致 `/restore` 的最后一行隐藏，直到另一次
交互触发测量。

## 拟议修改

将主聊天正文和思考的缓冲窗口从 60 毫秒缩短到 17 毫秒，约为一个 60 Hz 帧。
保留已有的有序事件缓冲和边界刷新。相邻文字分片仍合并成一次更新；思考转
回答、图片、工具、完成、取消和错误保留原有顺序。重试替换和模型回退继续
丢弃被替换尝试的内容。

让虚拟列表中的流式 LLM 消息使用与完成消息相同的已有大内容高度预算。
虚拟列表负责测量内容、裁剪视口并跟随不断增长的尾部。工具和审批内容继续
使用实际视口高度。LLM 图片也使用已有的完成消息预算，仍受内容宽度限制。

通过 Ink 已有的 `useBoxMetrics` 布局订阅读取主控件高度。它能够观察子组件
局部的底部栏、快捷键、建议、面板和弹窗变化，不再维护父组件依赖清单。
直接使用实测高度计算聊天区预算和 shell 尺寸。保留原生滚动历史的预留空间、
标签栏预留空间和高度不低于零的限制。

旧流处理器和共享 agent 循环使用同一个事件处理器，因此都适用缩短后的缓冲。
主聊天的虚拟视口、原生滚动历史和屏幕阅读器展示路径也都适用。Arena agent
标签页目前展示已提交的轮次消息，并不展示实时文字；为其增加流式展示属于
独立工作。

## 决策与范围

- 复用已有缓冲，不引入另一套调度器或配置项。Ink 继续负责限制屏幕刷新频率。
- 原样保留收到的文字。不延迟分片来模拟打字，也不将服务端的大分片人为拆成
  逐字更新。
- 保留已有 Markdown 块边界、源码复制、选择、视口锚定和输入区几何布局。
  原生滚动历史的预览保留高度安全限制，其高内容块裁剪与虚拟列表修复分开处理。
- 本次不启用增量终端写入，也不引入 Markdown 或高亮缓存。这些修改需要分别
  由测量支持；输出字节减少本身不能说明文字节奏变好。

## 涉及的实现

实现修改 `packages/cli/src/ui/hooks/use-llm-stream.ts` 的缓冲间隔，以及
`packages/cli/src/ui/components/MainContent.tsx` 的流式虚拟 LLM 高度覆盖，
并在同目录加入回归测试。
`packages/cli/src/ui/AppContainer.tsx` 将手动控件测量替换为已有布局 hook，
其测试覆盖输入和终端尺寸未变时的纯布局通知。不需要修改 provider、协议、
权限或传输层。

## 验证与验收

用虚拟时钟回归测试确认正文和思考在一个缓冲窗口内可见、相邻分片顺序不变，
并且连续多个窗口都能更新。保留已有的完成、取消、错误、重试、图片顺序和
共享循环覆盖。

用同一确定性 PTY 场景比较未修改的本地 bundle 和重新构建的 bundle。分别记录
普通正文、中文、Markdown/代码和工具转回答的服务端分片间隔、可见文字推进。
检查最终文字、视口与输入区位置，以及窄终端行为。运行仓库构建、类型检查和
受影响的单元测试。对窄窗口长段落，确认最新收到的文字在完成前就能看见，
且能够滚动查看。检查流式图片与工具确认分别遵守内容和视口预算。
反复执行 `/restore` 和 `/about` 直到历史溢出，确认最后的检查点名称无需滚动或
缩放补救就能显示。运行已有的检查点编辑、热恢复和冷启动恢复集成测试。
检查建议和快捷键开关、面板变化和窄窗口缩放后，底部栏与聊天区预算仍一致。

验收要求持续小分片正文的可见更新间隔明显缩短、窄虚拟列表的文字在完成前
持续推进、最终内容完整准确，且边界刷新和布局无回归。
17 毫秒缓冲不代表保证每秒可见 60 帧：服务端批次、渲染
开销和终端调度仍会影响结果。原生 Warp 与 Grok 的帧率对等需要单独测量。

## 待定问题

单独测量的后续机会。
