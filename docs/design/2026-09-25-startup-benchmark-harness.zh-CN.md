# 启动基准工具

[English](2026-09-25-startup-benchmark-harness.md) | [简体中文](2026-09-25-startup-benchmark-harness.zh-CN.md)

状态：已实现。

## 1. 问题

[#12622](https://github.com/QwenLM/qwen-code/pull/12622)（设计文档 `2026-09-24-fresh-startup-performance.zh-CN.md`）中的全新启动优化，是用一个从未提交进仓库的基准工具度量的。其第 9 节（决定 7）把它留给了本后续工作：任何人都应能按相同的定义复现这些度量，而不必重新搭建工具。同一决定还提议对确定性计数增加 CI 棘轮；第 3.5 节说明了本设计为何不加入它。

为独立验证那个 PR 而重新搭建基准工具时，发现了一些会悄悄扭曲数据的陷阱。基准工具应当把它们固化下来，免得别人再踩一遍。

## 2. 目标与范围

**目标：**

- 提交一个基准工具，按全新启动设计中的定义度量其指标（J1、J2、J3、M1、S1、D1、D2）。

**范围外：**

- CI 门禁或定时任务；基准工具由人手动运行（第 3.5 节）。
- D3（Valgrind 下的 CPU 指令数）；它很慢，而且需要一个基准钩子。
- macOS 与 Windows；基准工具读取 `/proc` 并使用 strace。

## 3. 设计

### 3.1 组成

| 部分                                      | 作用                                                                                               |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `scripts/startup-benchmark/lib.mjs`       | 公共部分：每次启动的干净环境、本地回环的 OpenAI 兼容 stub、真实终端，以及 `/proc` 与 strace 的读取 |
| `scripts/startup-benchmark/benchmark.mjs` | 对两个构建做交错 A/B 的墙钟基准测试，手动运行                                                      |
| `scripts/startup-benchmark/proxies.mjs`   | 在 strace 下度量单个构建的 D1 与 D2，输出结果供手动比较                                            |

### 3.2 干净环境

每次启动都会得到新的 `HOME`、`QWEN_HOME`、`QWEN_RUNTIME_DIR`、`XDG_*` 目录和工作区，工作区是一个空的 git 仓库。设置文件选择 OpenAI 认证并指向本地回环 stub，环境变量只保留终端会传递的那些：`PATH`、`LANG`、`TERM`，以及 stub 的密钥与地址。`--credentials settings` 或 `--credentials dotenv` 会把密钥与地址从 shell 移到设置文件的 `env` 块（`/auth` 存放它们的位置）或 `~/.qwen/.env`（文档推荐的位置），以便度量 env 文件触发的重启规则。CLI 通过真实的 bin 入口 `cli-entry.js` 启动，运行在 120×40 的 node-pty 终端中，屏幕由 `@xterm/headless` 重建。

### 3.3 指标

定义与全新启动设计一致。

| ID  | 度量方式                                                                  |
| --- | ------------------------------------------------------------------------- |
| J1  | 从启动到 "Type your message" 可见、已输入一个按键、且该按键出现在输入框中 |
| J3  | 从启动到第一个可见字符                                                    |
| J2  | 从启动 `qwen -p` 到它的第一个请求到达 stub                                |
| M1  | J1 时进程树的 RSS 之和；`-p` 取退出前的峰值 RSS                           |
| S1  | J1 之后屏幕上已有的文字是否被替换或清除                                   |
| D1  | J1 之前（`-p` 为退出之前）启动的 Node 进程映像数，按 `execve` 计数        |
| D2  | 这些映像打开的 JavaScript 字节数，每个文件在每个映像中只计一次            |

### 3.4 基准工具固化的陷阱

| 陷阱                                           | 忽略的后果                                             | 基准工具的做法                                               |
| ---------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------ |
| Node 只在正常退出时写入编译缓存                | 强行结束会话的基准测试，每次"热缓存"运行实际都是冷缓存 | 每个交互式会话都以 `/quit` 结束；每个构建使用各自的缓存目录  |
| xterm 会应答 DA1，但不应答背景色查询           | CLI 要等查询超时，而真实终端从不会让它等               | 基准工具会应答该查询；`--silent-terminal` 用于度量等待的情形 |
| `npm` 会修改自己的进程名（`process.title`）    | 轮询进程名会漏掉更新检查的 `npm view`                  | D1 改为在 strace 下统计 `execve` 调用，而不是轮询            |
| fork 出的子进程在运行其程序之前看起来像 `node` | 轮询会把 `git` 和 `rg` 算作 Node 进程                  | 同上：只有执行 `node` 可执行文件的 `execve` 才计数           |
| 同一帧的各行可能分几次读取到达                 | 仍在绘制的帧看起来像 J1 之后的变化                     | S1 只统计被替换或清除的已有文字                              |
| 不同批次运行之间的时间会漂移                   | 跨批次比较会看到并非由改动引起的偏移                   | 基准测试让两个构建成对交替运行，报告配对中位差与胜出对数     |

### 3.5 不设 CI 门禁

CI 步骤可以在 D1 或 D2 超出仓库中记录的预算时让 PR 失败，从而在引入回退的那个 PR 上就发现它。本设计没有这样做：

- **runner 速度会渗入结果。**D1 与 D2 统计的是事件而不是时间，但交互式计数截止于 J1，而 J1 之前有些工作由定时器驱动：更新检查的 `npm view` 以及懒加载的模块。较慢或负载较高的 runner 会让它们发生偏移，因此门禁要么让无关的 PR 失败，要么需要宽松到会漏掉真实回退的容差。
- **维护成本。**每一次有意的增加都需要修改预算；提示符文字或退出流程一旦变化，基准工具也会明确失败。

取而代之的做法是：涉及启动的 PR 手动运行基准工具并报告其结果，就像全新启动 PR 所做的那样。

## 4. 风险

1. **仅手动运行。**只有在有人运行基准工具时，启动回退才会被发现。
2. **仅限 Linux。**macOS 与 Windows 的启动不在度量范围内。
3. **与 UI 耦合。**基准工具会等待 "Type your message" 并以 `/quit` 退出。任一项变化时，它会输出最后一屏内容并失败，而不是报告错误的数据。

## 5. 验证

- 单元测试覆盖 strace 解析。
- 用 `proxies.mjs` 连续三次度量 `main`：D1 每次都是交互式 4、`-p` 2，D2 为 44.9–45.0 MB 与 21.7 MB。全新启动 PR 的度量结果为各 1 个进程，17.1 MB 与 14.2 MB。
- `benchmark.mjs` 以 8 对运行对比全新启动 PR 之前的 `main` 与该 PR：J1 1755 → 852 毫秒，J3 1231 → 527 毫秒，J2 1366 → 636 毫秒，M1 574 → 232 MB，S1 8/8 → 0/8。该 PR 在每一对中都胜出。

## 6. 验收标准

- 除了 `pnpm install`、构建与打包之外，无需任何额外准备即可在仓库中运行基准工具。
- 本文档的两个语言版本内容一致。
