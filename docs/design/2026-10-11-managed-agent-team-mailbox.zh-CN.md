# Managed agent team:基于 Session 消息的 lead mailbox(H4e-b2)

[English](2026-10-11-managed-agent-team-mailbox.md) | [简体中文](2026-10-11-managed-agent-team-mailbox.zh-CN.md)

状态:已实现,但在真实 Hosted 环境上的实机验收(决策 10)尚待进行,将在本变更合入前完成。这是 [#12827](https://github.com/QwenLM/qwen-code/issues/12827) 的 **H4e** 中第二个运行时切片,即 Managed Agent 提案 [#12380](https://github.com/QwenLM/qwen-code/issues/12380) 的 H 阶段,由 [#13745](https://github.com/QwenLM/qwen-code/issues/13745) 跟踪。它建立在 H4e-a([团队记录契约](2026-10-10-managed-agent-teams.zh-CN.md),#13811)、H4e-b1([lead 一侧的团队运行时](2026-10-10-managed-agent-team-lead-runtime.zh-CN.md),#13824,由 #13846 启用)与 H4d-b([Session 消息运行时](2026-10-10-managed-session-message-runtime.zh-CN.md),#13822)之上。它回答 H4e-a 的开放问题 1、2 与 4,以及 H4e-b1 的开放问题 3。它还调整了 H4e-b1 设计中 H4e-b2 与 H4e-b3 的范围:见下文决策 1、7 与 8。

## 问题与范围

H4e-b1 给了 lead 一个团队:具名成员的名册、任务板、带标签的汇报,以及有保护的删除。它的成员是一次性的 H4b child。成员基于 launch 提示词运行,汇报,然后被关闭。H4d-b 之后,父可以给运行中的 child 发消息,也可以续跑已完成的 child;成员就是 lead 的 child。所以成员运行时,lead 可以用它的 task id 给它发消息。但续跑会产生一个没有任何名册指向的新 run,因此 #13846 在本切片之前拒绝续跑开启中团队的成员。结果是已完成的成员无法再接收工作。成员不能按名字寻址,也不能被一次全部触达,成员也不知道自己在团队中。

H4e-b1 设计把 H4e-b2 规划为五个部分,并启用 `team_message`:

- 带成员一侧投递与回执的 `team_message` 中继;
- `send_message` 的团队路由;
- 成员一侧的任务板工具;
- 任务分配的投递;
- 成员续跑。

本设计保留其中 lead 的那一半,改变它的传输方式,并替换任务分配的投递:

- **lead 的 mailbox:**
  - lead 按成员名以及向全体成员发送的 `send_message`;
  - 成员发给 lead 的消息,带它的名字标签。
- **成员续跑:** 成员就是它的续跑链,因此已完成的成员可以接收更多工作,并且仍是成员。
- **成员身份:** 成员链上每个 run 的指令都以"它是谁、它的结果如何到达 lead、如何联系 lead"开头。
- **工作随指令传递,而不是随任务板写入传递:** lead 用 `send_message` 把工作交给成员,`task_update` 仍只是任务板记录(决策 7)。
- **不在此处:** 成员要请 lead 代为完成的一切:
  - 任务板的读写;
  - 发给其他成员的消息;
  - 计划请求与 shutdown 回复,它们本来就归 H4e-b3。

  这些需要一条从成员到其 lead、在 lead journal 上提交且不经模型回合的通道。这样的通道并不存在,H4e-b3 会为它们一次建好(决策 8)。

## 现状

以下事实来自 `main` 的 `66ddb151cb`,其中包含 #13846(以其 head `9909df4523` 合入,启用了 H4e-b1 团队 domain)。

- **成员。**
  - **加入。** 具名的 Agent launch 先提交一个 H4b `child_run`,再加入名册:`team_state.members` 增加 `{ name, childRunId, planModeRequired: false }`。名册只追加,并永远指向第一个 run。
  - **谁是成员。** `hostedTeamMembership` 只按精确的 `childRunId` 匹配 run。成员的状态就是那一个 run 的状态(`memberRunState`):已结算的 run 读作 `completed`,仍在进行的 run 即使已请求停止也读作 `running`。
  - **删除。** 该 run 尚未结束时,`team_delete` 拒绝。
  - **名册视图。** `task_list` 显示每个成员的状态与失败或取消的 run 的停止原因;该 run 运行期间,还显示它的 task id。
  - **owner**(`assertOwner`,#13846 在实机验收后定下的规则):
    - 运行中的成员可以被设为 owner。
    - 已完成的成员只能被设到本次调用结束时为 `completed` 的任务上,以便任务板记录是谁做了这项工作。
    - 保留下来的 owner 若其 run 已结束,在本次调用把任务移到另一个开放状态时会被再次检查,因此已结束的成员不会落到开放工作上。
  - **任务板答复。** owner 在运行时,`task_update` 的答复说该成员没有收到通知,并指向按 task id 的 `send_message`。
- **续跑成员。** `sendToChild` 拒绝续跑开启中团队里已完成的成员(`hostedOpenTeamMembership`):"a member of an open team cannot be continued yet"。团队删除后,前成员作为普通 child 续跑,结果不带标签。lead 的 `send_message` 只接收 `task_id`。在团队工具旁边,它被声明为 `HOSTED_TEAM_SEND_MESSAGE_TO_CHILD_TOOL`,使用 H4d-b 的 schema,描述中写明成员运行期间按 `task_list` 显示的 task id 寻址,以及已结束的成员要等团队删除后才能续跑。`to` 被拒绝;在声明了团队工具的地方,拒绝信息指向 `task_list` 显示的 task id。
- **成员内部。** 成员 Session 不持有任何团队记录。它的 launch 信封是 `{ description, prompt, definition }`,首条输入是 `[description]` 加上提示词。只有 lead 的模型把名字写进提示词时,成员才知道自己的名字。
- **消息(H4d-b)。**
  - **路由。** `session_message` 已启用。lead 的 `send_message` 在 child funnel 的写入链上路由:
    - 任务的链头在运行:一条发往该 run 的 outbound `session_message`;
    - 已完成且未请求停止:一个以该消息为指令的续跑 `child_run`,上面那种开启中团队的成员除外;
    - 其他情况:具名拒绝。
  - **链头**是最新的、未被证明从未启动(`not_started_proven`)的续跑。创建失败的续跑,或启动前被取消的续跑,不会移动链头。
  - **id。** 消息 id 为 `msg_` 加上 `sha256(sender | turn | call)` 的 32 个十六进制字符。续跑的 run id 就是调用键 `${promptKey}:${callId}`。
  - **投递。** relay 把每条消息交给该 run 挂接的 child,由 child 把 `session_message` 回执连同 input 与 wake 一起提交。child 的结算、任务取消与关闭都会等待、停止或归类 child 持有的消息。失败或被取消的 child 不发送通知。
  - **结果。** child 的结果是它最新已结算的 API 或消息回合(H4d-b 决策 8)。续跑的首条输入是 `[description]`,然后是整条链的历史,再是 `Your next instruction:` 与新指令。
  - **child 到父。** child 用 `to: "parent"` 给父发消息。此时 lead 的输入写作 `<from>child agent {taskId}</from>`,没有名字。
  - **共用的键。** Java relay、child result relay 的 journal 判定、wake pump 与关闭流程都以 `session_message` domain 及其输入来源为键。
- **`team_message` domain。**
  - 它有记录体与 H4e-a 的规则,处于关闭状态。没有任何东西产出它,重开白名单也不接纳它。
  - 它的目标规则把成员绑定到其名册条目所指 run 的 Session。
  - 只有发给 `leader` 的消息才能在同一事务中携带其 input,因为成员的 journal 不持有团队记录。
  - H4e-a 决策 5 把任务分配称为 `task_assignment` 类型的 `team_message`。
- **跨 Session 调用。** Harness 只为自己 Session 的 store、工具发布与 Runtime Broker 调用 Java。每个跨 Session 的效果都是一条持久记录,由 Java relay 拾取,再经私有 Harness 路由驱动。没有任何路由能让一个 Session 的工具调用使另一个 Session 提交。
- **Legacy。**
  - **`send_message`。** 它接收 `to`(队友名、`leader`、表示广播的 `*`,或 peer)或 `task_id`,加上 `message` 与可选的 `summary`。leader→成员与成员→成员的文本只存在于内存,队友终止时会丢失。
  - **队友。** 队友是长生命周期的,每次转为空闲时取一条排队的消息。它每个回合的最后一段文本都会转发给 leader。队友拥有 `send_message`、`task_list`、`task_update` 与 `task_create`。
  - **任务分配。** 它是一条携带任务主题与描述的直接提示词。当任务处于 `in_progress`,且其 owner 是本次调用改过的、或任务刚由本次调用移入 `in_progress` 时,`task_update` 发送它。被阻塞的任务不能分配。
  - **未使用的类型。** `task_assignment` 与两种 `plan_approval_*` mailbox 类型已声明,但从未被写入。

## 决策

1. **lead 与成员之间的消息是 Session 消息(回答 H4e-a 开放问题 1 与 2)。** 成员是 lead 的 child run。因此 lead 发给成员的每条消息都走 H4d-b 已在中继的血缘边,成员发给 lead 的每条消息都是成员自己的 `to_parent` 条目。
   - lead 把每条消息提交为一条 outbound `session_message`;成员已完成时,提交为一个续跑 `child_run`。
   - 成员的回执就是 H4d-b 的 inbound `session_message`,连同其 input 与 wake 一起提交。这回答了开放问题 1:成员不需要自成一类的回执。
   - 成员发给 lead 的消息是它自己的 outbox 条目。lead 的回执按 H4d-a 决策 6 携带其 input。这回答了开放问题 2:不需要 `team_message` 绑定。

   因此投递、持有消息的 child 的结算保持、H4f 对消息回合的停止以及关闭时的取消全部原样适用,Java 代码不做任何改动。

   `team_message` 中继要为同一种投递把这些全部重做一遍。它需要:
   - 在 relay 的查询与账本中加入第二个 domain;
   - 在 child result relay 的 journal 与边读取中加入 `team_message` 分支;
   - 父方 `child_messages_pending` 否决与停止分支的团队孪生版本;
   - 第二条续跑路径。

   本切片中 `team_message` 保持关闭且无人产出。团队在 H4d-b 之上增加的是路由与呈现:名字、广播、标签与身份。这些都由 lead journal 中的名册推导。成员撰写的消息、任务分配或协议类型是否需要 `team_message`,是 H4e-b3 的问题(开放问题 1)。

2. **成员就是它的续跑链(回答 H4e-a 开放问题 4 与 H4e-b1 开放问题 3)。**
   - **链。** 名册条目指向链上的第一个 run。若一个 run 的链根在开启中团队的名册上,它就属于该团队的一个成员。链根沿 lead 的 `child_run` 记录回溯 `predecessorChildRunId` 找到。launch 本身从来不是续跑,所以每个链根都是一次 launch。每次 funnel 调用按前驱为 lead 的 `child_run` 记录建一次索引,并在路由与作答间复用。名册视图与恢复中的广播都为全部成员只建一次;实时广播至多调用十次 funnel。
   - **成员的状态**就是其链头的状态,链头按 H4d-b 路由的定义。它读作:
     - `running`,请求停止后读作 `running (stopping)`;
     - `completed`;请求停止后才结算的链头读作 `completed (stop requested)`,路由拒绝续跑它;
     - `failed` 或 `cancelled`,附停止原因。
   - **名册视图。** `task_list` 显示该状态;只要成员还能接收工作(运行中或可续跑),就同时显示链头的 task id。若链头最新的续跑(即最后提交的那个)从未启动,该行还会写出原因,以及发给它的消息中有多少条从未到达(H4d-b 会取消发往交接前就已结束的 run 的消息)。例如:`alpha: completed — task_r1 (its latest continuation never started (creation_failed), so the work it carried did not arrive, nor did 1 message sent to it)`。启动前因用户请求而被取消的续跑,则写作 `was cancelled before it started (stop_requested)`。该行不显示那个续跑的 task id,因为它不指向任何存活的 run。对每个 child,无论成员还是普通 child,按这个 id 发送仍能到达这条链:路由都会从从未启动的续跑回溯到它的前驱,而 H4d-b 原先会把这样的发送当作发给已结束的 run 而拒绝。失败或被取消的 child 不发送通知,所以 lead 正是通过这一行得知新工作没有到达成员,这与 H4e-b1 决策 6 让名册视图承担失败可见性的用意一致。
   - **读取状态的地方。**
     - 任一链头仍在运行时,`team_delete` 拒绝。
     - owner 规则也读取链头(决策 7)。在那里,正在停止的链头算作已结束且未完成;请求停止后才完成的链头算作已完成但不可续跑。
     - 在挂接 child Session 之前被停止的续跑仍可能未启动就结束,这会把成员交还给它的前驱。在它结算之前,发给该成员的消息和 owner 变更都以"正在停止"被拒绝,拒绝文本会说明这一点,并让 lead 在它结算后查看 `task_list`,而不是指向启动新成员。
   - **现在允许续跑。** #13846 在本切片之前加入的 `sendToChild` 拒绝续跑开启中团队成员的规则,对 `active` 团队撤销。已完成的成员像任何已完成的 child 一样被续跑,续跑加入它的链。处于 `closing` 的团队仍然拒绝,因为它在收尾期间不接收新工作(H4e-a 决策 8),而 `team_delete` 只在没有成员运行时才提交 `closing`。
   - **worktree 成员。** worktree 成员的续跑保留其 `workspaceMode`,与每个 H4d-b 续跑一样,因此需要支持 child Workspace 的主机。
   - **记录不变。** 续跑从不加入名册,因为它由 `send_message` 启动,而不是由具名 Agent 调用启动。H4e-a 的加入规则只接纳存活且未被其他团队列出的 run,它仍然守护每一次加入。
   - **已结束的成员。** 链头在启动后失败或被取消的成员保持结束状态:H4d-a 决策 9 从不续跑这样的 run。请求停止后才完成的链头也一样。lead 改为启动新成员,新成员占用另一个名册名额(开放问题 4)。
   - **从未启动的续跑**让它的成员保持原样,因为 H4d-a 决策 9 会释放其前驱。这包括创建失败,以及启动前被 H4f 取消。下一条消息会再次续跑同一个链头。对每个 child,无论成员还是普通 child,其答复都会说明上一次续跑从未启动、发给它的消息丢了多少条。除非新消息已经包含那份工作,否则答复要求再次发送工作。对每条丢失消息,只有它自己的 `send_message` 答复尚未要求重发时,这里才要求重发一次:这样既不会遗漏先前在线答复只写“已排队”的消息,也不会重复恢复或重放答复已经要求的重发。用户在启动前取消的续跑会单独说明,只有那份工作仍然需要时才要求再次发送,因为用户可能是有意取消的。
   - **取消成员的工作。** 用户的 H4f 任务取消只停止其 task id 所指的那个 run。要停止被续跑成员的工作,用户要指定链头的任务,即公开任务列表中该成员最新的未结束 child 任务。第一个 run 的任务会答复该任务已经结算。
   - **`team_delete` 之后。** 按名路由、广播、前言与续跑标签(决策 3–6)只涉及开启中团队的名册。团队删除后,前成员的链只能通过 `task_id` 接收消息,并作为普通 child 续跑,不带前言也不带标签,与 #13846 的决定一致(开放问题 7)。

3. **lead 按名字寻址成员。**
   - **在哪里声明。** `send_message` 的团队形式取代 #13846 在团队工具旁边放的声明(`HOSTED_TEAM_SEND_MESSAGE_TO_CHILD_TOOL`):即声明团队工具的地方(H4e-b1 决策 1),且 `session_message` 已启用。它的 schema 增加 `to`,描述中去掉对续跑已结束成员的拒绝。
   - **参数。** `to` 或 `task_id`(恰好一个),加上 `message`。
   - **名字解析。** `to` 在调用运行时解析,而不是在批次准入时解析,因此同一批次中先前启动的成员也可以被寻址。
     - 去掉首尾空白后为 `*` 的是广播(决策 4)。
     - 其他 `to` 按 Legacy 的名字规则清洗,之后必须是开启中团队的成员名。
   - **拒绝:**
     - `leader` 被拒绝,因为 lead 就是发送方。
     - 未知名字被拒绝,答复列出名册。
     - 没有开启中的团队时,`to` 被拒绝,答复指向 `team_create` 或 `task_id`。
   - **路由。** 名字的路由与该成员第一个 run 的 task id 完全相同:
     - 运行中的链头收到消息,正在停止的除外;
     - 可续跑的链头(已完成且未请求停止)被续跑;
     - 其他链头被拒绝,答复写明成员名及其状态。已结束成员的拒绝信息指向以新名字启动新成员,因为普通 launch 不会加入团队。
   - **id。** 消息 id 与续跑 run id 就是 `task_id` 形式在同一次调用中会生成的那些。因此 H4d-b 的重放与上限原样适用:
     - 信封上限;
     - 在途 8 条与每个 run 64 条;
     - 续跑的 launch 准入(正在关闭、H4b 的活跃上限、H4c 的 launch 预算、worktree 对 child Workspace 的需要)。
   - **重放顺序。** 重放先查找该调用已提交的消息或续跑,再解析 `to`,因此即使团队已经变化,它也会答复已提交的发送。
   - **答复。** 答复写明成员:`Message queued for delivery to member "<name>" (task <id>)…`,或 `Member "<name>" had completed; continued it as task <id>…`。若本次发送所启动的续跑之前的那个续跑从未启动,答复会说明这一点(决策 2),但不写那个续跑的 task id。按 `task_id` 发给开启中团队的成员,得到相同的答复,因为 lead 的回复提示写的是 task id(决策 6)。
   - **Legacy 的 `summary`** 作为不支持的参数被拒绝。一个没有意义的参数,正是 H4b 决策 11 拒绝的那种失效开关。

4. **`to: "*"` 触达全体成员。** 广播按名册顺序发给开启中团队的每个成员。每个成员按决策 3 单独路由、单独提交。广播进行中 Turn 被取消时,不再发给后续成员,因为每次发送都可能启动一个续跑;重放会先报告已经提交的位置,再遵守这次取消。广播没有送达全部成员时,答复只让 lead 按名发给收件行明确写着未收到、仍能接收消息且仍需要这份工作的成员。
   - **id。** 无论 provider 给出什么调用 id,收件方的 id 都位于任何单次发送或 launch 都到达不了的命名空间中。只对调用 id 取摘要是不够的:provider 给出的 id 恰好等于该摘要的普通调用会生成相同的 id。
     - **续跑的 run id** 为 `bcast_` 加上 `sha256(promptKey \0 callId \0 position)` 的前 32 个十六进制字符,其中 `position` 是成员在名册中从 1 开始的位置。每个单次发送或 launch 的 run id 都是 `${promptKey}:${callId}`,因此都含冒号;广播的 run id 不含冒号,两个集合永不相交。
     - **消息 id** 为 `msgb_` 加上 `sha256(senderSessionId \0 turnId \0 callId \0 position)` 的前 32 个十六进制字符。每个单次发送的消息 id 都以 `msg_` 开头,两个集合永不相交。在广播之间,摘要区分不同的调用与位置。
     - 两者长度固定,最多 38 个字符,因此收件方的 id 不会随调用 id 增长,并保持在 128 字符的 `parentChildRunId` 上限之内。
     - 只追加的名册上位置永不改变。
     - 收件方的续跑或消息以广播调用的键 `${promptKey}:${callId}` 作为其 `executionCallId`,与单次发送相同,因此决策 7 的 owner 规则会把它算作本 Turn 已交付的工作。
   - **批次规则。** 发起广播的批次不得同时启动成员、创建团队或删除团队。这样广播读到的名册就是其批次留下的名册,被重新驱动的批次会触达相同的成员。
   - **部分结果。** 被拒绝的收件方不会阻止其他收件方。收件方在链头已结束或正在停止时、被消息上限拒绝时(`count_limit` 或 `budget_exhausted`),或其续跑被 launch 准入拒绝时(决策 3)被拒绝。
   - **答复。** 与 Legacy 一致:
     - 全部送达;
     - `sent to <n> of <m>`,并列出每个被拒绝的成员及原因;
     - 或者一个都未送达时,返回工具错误。
   - **重放。** 重放的广播会找到每个收件方已提交的消息或续跑,不会重复添加。
   - **范围。** lead 从不是收件方。广播从不离开团队。
   - **审批。** 对 `to: "*"` 的一次审批覆盖所有收件方,最多 10 次续跑。审批卡片预览输入的前 8 KiB,因此团队形式把 `to` 或 `task_id` 编码在 `message` 之前,收件方总会显示出来。

5. **成员链上每个 run 的指令都以"它是谁"开头。** 该指令以一段固定前言开头。前言:
   - 写明成员及其团队;
   - 说明启动它的 agent 就是 leader;
   - 说明它的结果如何到达 leader:只有它对收到的最后一条指令的答复;
   - 说明如何询问 leader;
   - 说明它既不能给其他成员发消息,也不能编辑任务板。

   ```text
   <team-member name="{name}" team="{team}">
   You are a member of this team. Your parent, the agent that launched you, is the team leader. Your result is your answer to the last instruction you receive: if another message from the leader arrives after you have answered, your answer to it becomes your whole result, so answer it in full and repeat anything from your earlier answers the leader still needs. To ask the leader something, use send_message with to "parent"; its reply reaches you after you have answered, as your next instruction. You cannot message other members or edit the team's task board.
   </team-member>
   ```
   - **前言为何要解释结果。** H4d-b 以最新已结算的回合结算 run(其决策 8)。消息只在运行中成员的当前回合结束后才到达它(H4d-b 决策 6)。所以成员作答之后又收到 lead 的消息,就只会交付它对这条消息的答复。没有被提醒的成员会丢掉它先前工作的汇报。
   - **放在哪里。**
     - **具名 launch。** 前言放在 launch 信封中模型提示词的前面,所以成员的首条输入是 `[description]`、前言,然后是提示词。launch 准入在成员名被接纳后,连同前言一起编码信封。超长的提示词因此与没有团队时一样,得到 `byte_limit` 拒绝。
     - **每次续跑。** 成员链的续跑把前言放在新指令之前,位于整条链的历史之后、`Your next instruction:` 之下。无论续跑来自名字、广播还是 `task_id` 都是如此。较早的前言留在历史中,与历史其余内容一样经过 XML 转义。
   - **为何每次续跑都加。** 续跑的历史(H4d-b 决策 9)超出上限时会省去最旧的 run,所以身份不能只依赖第一条指令。
   - **上限。** 前言是信封的一部分,因此计入信封上限。H4d-b 的单一发送上限因此仍是单一的:无论链头在运行还是已完成,大小检查都构造同一个信封。前言只随开启中的团队出现,因此在上限附近,`team_delete` 之前被拒的消息在之后可能放得下。
   - **运行中的成员。** 发给运行中成员的消息不带前言。该成员当前的 run 开头已经有一段,除非它是在本切片之前启动的。
   - **重放证据。**
     - 名字被清洗为 `[a-z0-9-]`,因此前言无需转义。
     - 重放从不重建前言。前言是否存在取决于团队,而团队在重放前可能已变化;重放的具名 launch 也可能尚未加入:H4e-b1 被重新驱动的 launch 会补完首次运行丢失的加入。
     - 因此当该调用的续跑或 launch 已提交时,若其已提交的指令等于所发送的文本,或是一段格式正确的 `<team-member name="…" team="…">` 块加上所发送的文本,就接受它。重放随后原样使用已提交的信封。
     - 检查读的是块的格式而不是措辞,所以在改写了前言措辞的版本之间也成立。
   - **从未完成加入的 launch。** H4e-b1 有两种这样的情况:加入被拒绝,以及崩溃窗口。该 run 仍带着前言,其中的名字名册上并没有。它作为普通后台 child 运行和汇报。它的父仍是 lead,所以只有声称的名字是错的(开放问题 5)。

6. **lead 能看到是谁写的。** 在 lead 一侧,成员发给父的消息的回执会成为一条输入,内容为:
   - `<from>child agent {taskId}</from>`,与以前相同;
   - 随后是 `<teammate>{name}</teammate>`;
   - 再随后是 H4d-b 的回复提示,保持不变:`<reply>To answer, use send_message with task_id "{taskId}".</reply>`。提示一旦提交就是固定文本,可能在 lead 的上下文中停留许多回合。后来的团队可能同时复用团队名与成员名,所以按名的提示可能送到另一个成员。task id 总能到达写这条消息的成员的链;在其团队开启期间,按 task id 发送与按名发送得到相同的路由、前言与标签(决策 3、5 与 6)。

   `team_delete` 之后,前成员的消息保持 H4d-b 的输入:不带标签,按 `task_id` 回复。

   续跑的结果通知在其链根位于开启中团队的名册上时,带有该成员的 `<teammate>` 标签。这把 H4e-b1 决策 4 扩展到续跑。两种情况保持原有规则:
   - 名册指向的 run 保持 H4e-b1 的标签查找不变,它读取每个团队,包括已删除的团队;
   - 前成员的续跑保持不带标签,与 #13846 的决定一致。

   这留下一处不对称。成员的某个 run 在 `team_delete` 之前结算、之后才被接受时,若它是成员的第一个 run 就保留标签,若它是续跑就失去标签。若后来的团队复用了这个名字,H4e-b1 的查找可能给迟到的第一个 run 打上一个开启中团队也在用的名字。

7. **工作随指令传递;`task_update` 仍只是任务板记录(取代 H4e-b1 的"尚无任务分配投递")。** 本切片通过 launch 提示词或 `send_message` 把工作交给成员,成员已完成时 `send_message` 会续跑它。`task_update` 不发送任何东西。像 Legacy 那样从 `task_update` 投递,在任务板允许的每种情况下都会出错:
   - **成员已完成。** #13846 的实机验收发现,一次性成员通常在 lead 的 `task_update` 到达前就已完成。把任务投递给已完成的 owner,会续跑它去重做已经做完的工作。#13846 的规则只允许已完成的成员拥有本次调用结束时为 `completed` 的任务,以便任务板记录是谁做了这项工作;该规则保持不变。
   - **成员在运行。** 运行中的成员通常正在做 lead 所记录的那个任务,这个任务由它的 launch 提示词带来,所以投递的任务分配会重复这项工作。若任务是新工作,它的回合会成为成员最新的回合及其结果(决策 5),成员当时所做工作的汇报就会丢失。
   - **重放时。** 重放的 `task_update` 无法判断这次调用是否欠一次投递。它的第一个修订已经覆盖了条件所比较的 owner 与状态。

   因此已完成的成员在同一个 Turn 中(最好在同一批次中)分两步接收新工作:
   1. 按名字 `send_message` 续跑它,它的链头开始运行。
   2. 随后 `task_update` 让它成为该开放任务的 owner,因为该成员在本 Turn 已被交付工作(见下文)。

   同一批次按顺序运行其调用,所以 `task_update` 运行前发送已经提交,但没有任何东西让成员一直运行到那时。relay 会在 lead 的 Turn 运行期间提交并结算 child 的结果,两个 funnel 也没有覆盖整个批次的共同锁。因此被这次发送续跑的成员,或正在运行并读到这条消息的成员,可能在两次调用之间就已完成。owner 规则用一个概念覆盖这种情况,即本 Turn 已交付的工作:
   - **Turn** 就是一个 prompt id。它覆盖其所有模型回合,中断后恢复的 Turn 也是同一个 Turn。
   - **本 Turn 已交付的工作。** 若同一 Turn 中更早的调用为某成员的链提交了一个未被证明从未启动的续跑,或一条发往该链上已启动的某个 run、未被取消也未被拒绝的 outbound 消息(发往从未启动的续跑的消息会被取消,永远不会到达),该成员就在本 Turn 被交付了工作。两者都以发送调用的键作为 `executionCallId`,它是本 Turn 的某个调用键,所以 lead 的记录就能判定。
   - **接受。** 无论这样的成员的链头仍在运行还是已经完成,它都可以被设为开放任务的 owner。发送已经交付了工作,所以任务板记录谁拥有它;汇报到达时,lead 把状态设为 `completed`。
   - **仍被拒绝。** 链头失败、启动后被取消、正在停止,或请求停止后才完成的成员被拒绝,因为决策 2 把它算作已结束。
   - **已完成的工作。** 对于把任务保持为 completed 的调用,只要成员链上有任一 run 已完成,即使其链头此后已结束,也会被接受:那个 run 可能做了这项工作,而 #13846 记录的正是谁做了它。链上从未有 run 完成的成员被拒绝,拒绝文本指向做了这项工作的成员或 `leader`,而不是新成员。

   这些文本引导模型这样做。它们都不断言过去某次发送承载的是哪个任务,因为没有记录把一次发送与一个任务关联起来;也都不会为从未到达的工作提供跳过发送的选项:
   - **`task_update` 的答复。** owner 是成员时,答复说明它没有通知任何人,并说明若该成员还没有这份工作,按成员名 `send_message` 就能交给它。答复不要求模型发送:本 Turn 更早的发送,或 launch 提示词,可能已经交付了这份工作,再发一次会让它重复。若本 Turn 更早的发送已给该成员交付了工作,答复会说明这一点,并且只在那次发送没有承载这个任务时才要求发送。重述任务原有 owner 与状态的调用不会再次检查,所以答复直接读取该成员:若其最新的续跑从未启动,答复会说明这一点并要求再次发送那份工作;每条丢失消息仅在其自身答复尚未要求重发时才要求重发;对已结束的成员,答复说明它不再接收工作。
   - **本 Turn 未被交付工作、已完成且可续跑的成员。** 它在开放工作上以一段条件文本被拒绝:若它已经做了这个任务的工作(来自 launch 提示词或 lead 发给它的消息),就在汇报到达后以该 owner 把状态设为 `completed`;否则先按成员名 `send_message` 交付工作(这会续跑它),再指定它。第一个分支就是 #13846 保留下来的出路。
   - **链头最新的续跑从未启动。** 拒绝信息说明这次续跑从未启动及其原因,以及它承载的工作和发给它的消息都没有到达;它指向按名再次发送这份工作,仅在丢失消息自己的答复尚未要求重发时各重发一次,然后指定任务。对于用户在启动前取消的续跑,只有那份工作仍然需要时才要求再次发送。
   - **无法续跑的成员。** 失败、被取消、正在停止,或请求停止后才完成的成员,以已结束被拒绝。拒绝信息指向启动新成员;对已完成的成员,若它做了这项工作,还指向以它为 owner 完成任务。
   - **描述。** `task_update`、`task_create` 与 `task_list` 的描述,以及团队形式 `send_message` 的描述,也这样说明。`task_list` 不再把 task id 说成联系成员的方式。

   若 `task_update` 接受 owner 之后续跑从未启动,任务板仍把 owner 留在开放任务上。`task_list` 显示那个从未启动的续跑(决策 2);任务下次移到另一个开放状态时,保留 owner 的检查会拒绝继续保留该成员。

   `task_assignment` 仍无人产出,Legacy 的任务分配提示词没有对应物。lead 自己的消息就是任务分配。

8. **成员一侧的工作移到 H4e-b3,连同成员到 lead 的命令通道。**
   - **成员保留什么。** H4d-b 发往 `"parent"` 的 `send_message`,没有团队工具。
   - **其余为何要等。** 成员读写任务板,或给另一个成员发消息,都是请 lead 的 journal 代它提交。H4e-b3 的计划请求与 shutdown 回复也一样。目前没有任何东西能承载这样的命令:
     - 没有任何路由能让一个 Session 的工具调用在另一个 Session 中提交;
     - H4d-b 的 `to_parent` 条目不是合适的载体,因为它的回执必须提交一条唤醒 lead 模型的 input,而不是由 lead funnel 执行的命令。
   - **计划。** H4e-b3 一次建好这条通道,并把四种用途都放在上面。[H4e-b3 设计](2026-10-11-managed-agent-team-member-commands.zh-CN.md)将它建为 `session_command` domain,并在其上承载其中三种:任务板读写、成员消息与计划递交。shutdown 回复不再需要,因为 lead 直接停止成员而不征询它;计划的决定也不需要命令,因为 lead 对自己的 child 作出它。
   - **拒绝保持原样。** 成员发往 `"parent"` 以外任何对象的 `send_message` 以 H4d-b 的文本被拒绝。child Session 不持有团队记录,所以它的拒绝无法区分成员与其他 child。告诉成员它不能联系其他成员的是前言。

9. **被中断的回合按已提交的内容作答(扩展 H4d-b 决策 16)。**
   - **查找哪些 id。** 无论 journal 中记录的参数是什么,恢复与 PostToolUse 派发证据都会在 `send_message` 调用的基础 id 与十个广播位置的 id 下查找它。PreToolUse 或权限 hook 可能改写调用实际执行的输入,所以 journal 中的 `to` 未必就是实际运行的那个。
   - **单次发送。** 在基础 id 下找到的,按决策 3 对实时发送的方式作答:团队开启期间写明成员名,否则用 H4d-b 的 task id 文本。对已经到达的发送,它绝不引导重试。若发送到达的 run 此后被证明从未启动,答复会说明消息没有到达以及如何再次发送:失败的 child 不发送通知,没有别的途径会告诉 lead。恢复或重放答复只要求重发它自己的消息;之后“上一次续跑从未启动”的说明仅在该丢失消息自己的答复尚未要求重发时才提出重发,因此先前只写“已排队”的在线答复不会掩盖丢失,两个答复也不会重复要求同一次重发。对从未启动的 launch,答复说明该成员或 child 已结束。消息自身的投递若已失败,即使其 run 并未被证明从未启动,也同样没有到达:交接前被取消、被目标拒绝,或仍在等待交接、而 relay 会因其 run 已结束或正在停止而取消它(H4d-b)。答复会说明这一点:链仍接收消息时指向重发;启动前被停止的续跑尚在结算时,指向等它结算;已经挂接的 run 正在停止时,指向结束后启动替代者;链已结束时,指向启动新成员(普通 child 则为新 agent)。记录为 `unknown` 的投递既不呈现为已到达,也不呈现为失败:答复说明它无法确认,并要求 lead 在重发前先向成员核实。若一条已经交接、处于 `accepting` 的消息在 relay 记录之后的拒绝之前遇到 run 停止,较早的答复仍可能写作已排队,因为回执可能已经存在;这个窗口无法从记录中作进一步推断。
   - **广播。**
     - 在位置 id 下找到的,逐个收件方作答,依据每个位置已提交的消息或续跑。
     - 答复分别列出哪些已送达、哪些没有、哪些投递无法确认。所到达的 run 从未启动,或其消息的投递如上失败的收件方,算作未送达。正在结算从未启动续跑的成员、挂接后正在停止的成员与已结束成员分别列出,并使用和单次发送一致的状态提示;实时重放则在该成员的那一行注明。无法确认的收件方在 lead 核实之前不进入重发提示。若团队此后已被删除或替换,答复只列出已发送到的收件方,与实时重放相同。
     - 会恢复 Turn 的路由,把一个什么也没提交的调用作答为从未运行。
   - **派发证据。** 已提交的广播在重启后仍算已派发。

10. **没有门禁、没有契约变更、没有 Java 变更。**
    - **门禁。** `send_message` 的团队形式、前言、标签与成员续跑都依附于已经打开的门禁:
      - 团队工具的门禁(`team_state` 与 `team_task`,由 #13846 启用);
      - H4d-b 的 `session_message` 门禁;
      - H4d-b 的续跑门禁。

## 一条消息的路径

lead 发给成员 `alpha` 的消息,`alpha` 的第一个 run `r1` 已完成:

| 步骤 | Journal | 提交                                             | 执行者                        |
| ---- | ------- | ------------------------------------------------ | ----------------------------- |
| 1    | lead    | `r1` 的续跑 `child_run` `r2`;指令 = 前言 + 消息  | `send_message`(`to: "alpha"`) |
| 2–6  | 两边    | H4b 的派发、挂接、结算与接受;结果带 `alpha` 标签 | H4b relay,与任何 child 相同   |
| 7    | lead    | `alpha` 的下一条消息路由到链头 `r2`              | 下一次 `send_message`         |

发给运行中的成员时,第 1 步是一条发往链头的 outbound `session_message`,随后从 H4d-b 管线的第 2 步开始运行。成员发给 lead 的消息走 H4d-b 的 `to_parent` 管线,lead 的输入带标签。若 `r2` 从未启动,`r1` 仍是链头,`task_list` 会写出 `r2` 及原因。

## 验收标准

- **lead 到成员的投递。**
  - lead 能按名字触达一个成员,并能用 `*` 一次触达全体成员。
  - 运行中的成员把消息作为下一条输入收到。
  - 已完成的成员被续跑且仍是成员:它带标签、可以拥有开放工作,并被 `team_delete` 计入。

  - `task_update` 不发送任何东西。
  - 没有记录、规则、路由、迁移或 Java 变更。

## 开放问题

1. **`team_message` 是否会被产出。** lead 与成员之间的消息是 Session 消息(决策 1),任务分配就是 lead 自己的消息(决策 7)。这样 `team_message` 只剩下成员撰写的消息,以及计划审批与 shutdown 的协议类型。H4e-b3 要决定两件事:
   - 成员到 lead 的通道是把它们提交为 `team_message` 记录,还是作为 lead 的 Session 消息路由给收件方;
   - 该 domain 及其 `task_assignment` 类型随后是否退役。

   若产出 `team_message`,其目标规则必须在两种语言中改为跟随链头。它目前把成员绑定到其第一个 run 的 Session,因此任何发给被续跑成员的消息都会被拒绝。

   [H4e-b3 设计](2026-10-11-managed-agent-team-member-commands.zh-CN.md)回答了这一问题:`team_message` 与 `task_assignment` 保持不产出,作为保留项(其决策 11)。

2. **成员占用的上限与预算份额。** H4e-b1 把活跃上限留作开放问题(其开放问题 2)。
   - 续跑一个已完成的成员会计入 H4b 的 4 个活跃 child。当其他成员仍在运行时,向多个已完成成员的广播可能因上限被拒绝。
   - 每次续跑还会用掉 H4c 每个 Session 64 次 launch 中的一次,用掉的 launch 永不恢复,即使续跑从未启动。不断续跑成员的团队,会比一次性成员更快耗尽 Session 的 launch。
3. **结果只是最后一次答复。** H4d-b 的结果规则让运行中成员对 lead 消息的答复成为它的全部结果。前言要求成员重述 lead 仍需要的内容(决策 5),但不这样做的成员会丢掉先前的汇报。
   - 保留每个回合的答复需要改变 H4d-b 的结果规则,而那在 Java 中。
   - 另一种做法是,成员在接下一项工作前,先用 `send_message` 发给 `"parent"` 汇报每一项工作。
4. **失败的成员就此结束。** 在启动后失败或被取消的链头会永久结束它的成员(H4d-a 决策 9),即使是暂时性失败。替代者是另一个名字下的新成员,它占用名册 10 个名额中的一个,而名额永不释放。
5. **没有名册条目的前言。** 从未完成加入的 launch 会保留一段声称名册中并不存在的成员身份的前言(决策 5)。若要在加入之后才写入前言,就需要在第一个回合之前加入第二条输入,而 H4b 的 launch 没有这一步。
6. **长历史中的前言。** 续跑历史中的每条较早指令都保留前言,转义并编码后,每个 run 约占 600 到 750 字节。48 KiB 上限覆盖整条首条输入,其最后的指令本身也带一段前言。要从较早的 run 中去掉它,就得让 Java 的历史拼装感知团队,而本切片不改 Java。
7. **前成员的身份。** `team_delete` 之后被续跑的前成员不带前言,但它的历史中仍保留着较早的前言,所以它可能仍以已删除团队成员的身份作答。加一行告诉它团队已删除可以纠正这一点,但这也会改变 #13846 定下的普通 child 续跑方式,因此留作开放问题。
