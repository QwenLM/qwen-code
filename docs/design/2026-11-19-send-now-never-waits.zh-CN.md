# 立即发送不再等待工具

[English](2026-11-19-send-now-never-waits.md) | [简体中文](2026-11-19-send-now-never-waits.zh-CN.md)

状态：已定，分两个 PR 实现（PR 1：#17825）。

本文修改 [立即发送回合中排队的消息](2026-10-08-send-mid-turn-messages-now.zh-CN.md)
中「工具调用开始后不打断」的决策和「正在运行的工具永远不被打断」的保证。
本文也落地该文「风险」一节留待以后的「把运行中的 shell 转到后台」。其余行为（Enter 排队、
工具边界送达、会话级、请求绑定回合、先取队列再截断）保持不变。

## 问题

用户在 Web Shell 点「立即发送」时，如果模型的回复已经开始调用工具（参数还在流式
生成，或工具正在执行），守护进程返回 `{ requested: true }`，agent 却什么都不做：
排队行仍是「排队中...」，按钮还在，消息要等这批工具结束才送达。真实案例：模型用
`write_file` 写一份大文件，参数生成了 13 分钟，用户想纠正的恰恰是这次写入。

实测（`qwen serve` + Web Shell + 脚本化 provider，2026-11-19）：

| 点击时的状态                     | 现在                          |
| -------------------------------- | ----------------------------- |
| 模型在输出正文                   | 约 50 ms 送达，同一轮回应     |
| 模型在生成 `write_file` 参数     | 等参数和工具都结束（约 16 s） |
| shell 命令运行中（旧文实测 8 s） | 等命令结束（6.1 s）           |

按钮的名字承诺「立即」，行为却取决于用户看不到的内部阶段，用户只能理解为点了没反应。

## 现状

- 回合中排队的消息存在守护进程的 `midTurnMessageQueue`。agent 每批工具结束后
  （`#buildNextMessageAfterToolRun`）取一次队列。回合结束时，守护进程根据 prompt
  FIFO 的状态，通过 `settleUndrainedMidTurnMessages` 提升未取走的消息。自主 Goal
  回合使用 `settleMidTurnQueueAfterAutomaticTurn`。
- 立即发送：`Session.sendMidTurnInputNow()` 记下请求，`#openResponseInterrupt` 的
  `pull` 只在回复还没出现工具调用（`hasFunctionCalls()` 为假）时先取队列再截断。
- ACP 旧循环通过 `Session.runTool` 执行工具，调用
  `invocation.execute(signal, onProgress, shellConfig)`。shared round 通过
  `runAcpToolBatch` 和 `CoreToolScheduler` 执行工具。调度器已为 shell 调用传入
  `setPromoteAbortControllerCallback`，并把转后台控制器保存在执行中的工具调用状态上。
  TUI 的 Ctrl+B 使用该状态。ACP 的立即发送处理仍需接入这些控制器。
- 停止（`cancelPendingPrompt`）除了中止当前回合，还会停掉 cron 调度器并清空 cron
  队列、暂停后台通知、以用户中断为由暂停 Goal（`#settleGoalTurn` 把
  `USER_CANCEL_ABORT_REASON` 记为用户中断）。被新 prompt 抢占的 Goal 回合
  （`NEW_PROMPT_ABORT_REASON`）则按交接处理，Goal 不暂停。
- 实测：生成工具参数时或 shell 运行时按停止，排队消息都会在下一轮送达，请求的角色
  顺序合法；没写完的工具调用被丢弃，被取消的 shell 记为已取消的工具结果。

## 参考

Claude Code 的发送键分两种：Enter 排队，在工具边界送达；Ctrl+Enter 立即发送，能
转到后台的工作（shell、子代理）转后台继续运行、同一轮读消息，其余情况打断当前回合、
接着发送消息。转后台的 shell 在工具结果里写明是为送达消息而转、命令没有中断。
Codex 默认打断。本设计的分工与前者相同（Enter 不变，「立即发送」从不等待），理由见
「决策与理由」。

## 目标与范围

- 更早排队的 prompt、在途取队列或工具取消没有延迟投递时，「立即发送」的目标是在
  一次往返内把用户消息交给模型。
- 已经在跑、可以转后台的 shell 命令不被杀掉。
- 打断只结束当前这一轮，不停 cron、不暂停后台通知、不暂停 Goal。

不在范围内：子代理转后台（qwen-code 目前只有 shell 支持中途转后台）；cron 和后台
通知回合中的立即发送（这类回合没有 `pendingPrompt`，保持现状：在工具边界送达）；
TUI 的立即发送快捷键；工具行区分「正在准备」和「正在执行」。

## 方案

agent 收到立即发送请求时，按当前回合在做什么分三种情况。下表假定消息前面没有已排队
的普通 prompt。

| 当前回合在做什么                                     | 处理                                                                                | 消息在哪一轮被回应 |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------ |
| 模型在输出正文或思考，还没有工具调用                 | 现有逻辑：先取队列，再截断回复                                                      | 同一轮             |
| 工具批次只剩前台 shell 在运行                        | 把这些 shell 转到后台（PR 2），批次随即结束，工具边界取队列                         | 同一轮             |
| 其他情况：回复已开始调用工具、工具在执行或等授权等等 | 以 `MID_TURN_SEND_NOW_ABORT_REASON` 中止当前回合；守护进程把队列提升为下一轮 prompt | 下一轮（立即开始） |

批次里既有前台 shell 又有其他工具时：PR 1 整批打断（shell 也被取消）；PR 2 起先把
shell 转到后台，再打断其余工具。

### 打断（PR 1）

1. `sendMidTurnInputNow()` 先照旧让开放的回复取队列并截断。回合处在工具阶段（回复
   已有工具调用，或它调用的这批工具还没结束，包括执行中和等授权），且此时没有取队列
   的请求在途时，就以 `MID_TURN_SEND_NOW_ABORT_REASON` 中止当前回合的
   `pendingPrompt`。这批工具一结束，工具阶段就结束：之后的请求等工具边界取队列或
   下一次回复截断，不会打断一个已经在收尾的回合。
2. 这个原因和停止一样算受控取消，回合以 `cancelled` 结束。cron 调度器继续运行并
   保留已排队的触发。守护进程结算 prompt FIFO 期间（含解析附件或撤回消息），agent
   暂缓自主 Goal、cron 和独立后台通知。等待结果的 `per_task` 渠道 prompt 仍可处理
   自身工作链上的通知并结算。
3. Goal：被打断的 Goal 回合（含 Goal 激活时的用户回合）按交接处理，和被新 prompt
   抢占相同：结束这一轮，Goal 保持活跃。如果 FIFO 允许在结算时提升消息，该 prompt
   作为下一个 Goal 回合运行。更早排队的普通 prompt 保持原顺序，可以在工具边界取走
   消息。被打断的回合仍计入用量，但不累加无进展次数，因为守护进程要等回合结算后
   才能提交排队消息。
4. 打断分支把消息留在守护进程，按 FIFO 顺序取出或提升，避免消息被取走后无人回应。
5. 竞态：守护进程只在队列里有用户消息时才发请求；某次取队列已经取走消息、还在读
   附件没回答时，守护进程先扣住请求，等回答发出后队列里仍有用户消息才转给 agent。
   请求和取队列的回答走同一条有序通道。agent 处理请求时如果有取队列的请求在途，
   那次取队列会把消息带进同一轮，就不打断；没有在途请求时，消息一定还在守护进程，
   可以安全打断。超时的取队列事后交回的消息要等工具边界送达，这时也不打断，新消息
   跟着一起在工具边界送达，保持顺序。回合被打断后不再向守护进程取队列。请求仍按现有
   规则绑定回合。
6. 回复里已说出口的正文保留；没写完的工具调用丢弃；正在执行的工具按停止路径记为已
   取消，但工具结果不用停止时的「用户取消，等待进一步指示，不要重试」，而是说明用户
   为了发消息打断了这次调用、消息紧随其后，读完再决定是否重跑；等待授权的请求随回合
   中止而取消，不执行，也不记成「用户拒绝」。

### shell 转后台（PR 2）

1. 将运行中的前台 shell 的转后台控制器交给会话。旧循环里，`runTool` 为顶层 shell
   调用传入 `setPromoteAbortControllerCallback`。shared round 里，`runAcpToolBatch`
   从调度器的工具状态更新读取已有控制器交给会话，并报告每个结算的调用。还没启动进程
   的 shell、嵌套在 `exec` 里的调用、模拟执行的 `sed` 编辑和 Managed runtime 的调用
   不交出控制器，按 PR 1 打断。
2. 立即发送请求到达时，对每个句柄
   `abort({ kind: 'background', shellId, forUserMessage: true })`，`bg_` id 由会话
   选定，之后才能停掉它。批次里只剩这些 shell 时（批次里每个还没结算的调用都是转后台
   的 shell；旧循环按顺序执行，还没开始的调用也算剩下的），批次随即结束，工具边界取
   队列，同一轮回应。还有其他工具时，等转后台的 shell 的工具调用结算后再按 PR 1 打断：
   提前打断会把它们的结果换成打断说明，模型就丢了后台 id，可能把命令再跑一遍。PR 1 的
   取队列在途、超时晚到消息两项检查只约束这次打断，打断触发时重新检查。shell 正在转
   后台时再来一次请求，不会再转，也不会提前打断。
3. 工具结果带后台 id、输出位置和状态行，并写明原因：为了让用户消息送达模型，命令
   在没有被中断的情况下转到后台，消息紧随其后（区别于用户手动转后台）。
4. 后台 shell 之后结束时走 ACP 现有的后台 shell 通知。
5. 用户在同一轮里接着按停止时，这些为送达消息而转后台的 shell 一并停掉，时机在它们的
   工具调用结算、后台条目已经存在之后；下一轮开始后不再特殊处理。停止既可能以会话
   取消的形式到达，也可能是守护进程的取消 prompt 请求，所以会话监听回合信号上的用户
   取消。

### Web Shell

只改提示文字：「立即发送排队的消息。模型正在回复或调用工具时会打断它」，PR 2 加上
「正在运行的命令转到后台继续运行」。不新增行状态：打断后消息很快作为下一轮出现，
排队行随之消失。等待授权时 Web Shell 用授权面板替换输入区和排队行，这个阶段只有其他
客户端（例如 SDK）能请求立即发送。

## 决策与理由

- **「立即」就是立即。** 用户点这个按钮时已经判断消息比当前工作更重要。让行为随用户
  看不到的阶段变化，比打断代价更大：用户会重复点、或者干等。
- **能转后台的不杀。** 长命令跑到一半被杀，重跑代价高，还可能留下半完成的副作用；
  转后台既不丢工作，也让消息马上送达。
- **其余情况打断回合、走下一轮，而不是在同一轮里取消工具。** 停止路径已经能正确处理：
  丢弃没写完的工具调用、给被取消的工具记结果、回合结束后提升队列，实测请求合法。
  同一轮继续需要新的批次级中止、给未执行的调用合成结果、处理授权弹窗，并且要在两条
  循环里各做一遍，复杂度高很多，收益只是少开一轮。
- **正文阶段保留同一轮截断。** 这条路径已经实现并测过；模型看到的内容和走下一轮几乎
  相同，而同一轮不会多出一个 `cancelled` 回合，SDK 调用方和 Goal 都更简单。
- **专门的中止原因。** 停止会停掉 cron、暂停通知、暂停 Goal，这些都不是用户点
  「立即发送」时想要的。
- **Goal 自动继续。** 用户插话是在纠正方向，不是叫停目标；按交接处理和「新 prompt
  抢占 Goal 回合」一致。
- **打断前不取队列。** 取走后回合又结束，消息会被记录但不被回应；留在守护进程由回合
  结束时提升，路径更短、已验证。
- **分两个 PR。** 打断独立可用，先解决「点了没反应」。shell 转后台需要分别接入两条
  工具执行路径，单独评审。

## 约束

- 两条 ACP 路径共用 `Session` 中的立即发送打断、中止原因分类和 Goal 结算逻辑。
  中止原因 `USER_MESSAGE_INTERRUPT_ABORT_REASON` 和对应的工具结果文字定义在 core，
  供 `Session.runTool` 和 `CoreToolScheduler` 使用。PR 2 将两条工具执行路径接入会话，
  测试覆盖两条路径。不等待 #17744。
- `sendMidTurnMessagesNow` 的路由和能力位不变，但 SDK 调用方会看到新行为，发布说明
  需写一行。

## 风险

- 打断会丢弃模型已生成的工具参数，重新生成要再花 token。这是用户显式点击的结果。
- 被打断的工具可能只做了一半（例如命令执行到中途）。和停止相同；提示文字写明会打断。
- 部分工具完成当前操作后才会结算取消。比如 `record_artifact` 的目录扫描或已经开始的
  worktree 修改都可能延迟下一轮 prompt。
- 打断依赖「没有在途取队列请求时消息一定还在守护进程」，即请求和取队列回答在同一条
  通道上有序到达；需要专门测试。点击后用户又删光了排队消息时，这一轮会被打断但没有
  后续消息，概率很低，可以接受。
- 守护进程只在回合结束、且 FIFO 里只有这一轮时提升队列。用户已经另外排了普通 prompt
  时，点击会结束当前回合，但消息要等下一个 prompt 到工具边界才送达。
- 等待授权时被打断，agent 放弃这次授权请求。守护进程在结算时取消属于当前 prompt
  或自主 Goal 回合的授权。自主 Goal 的授权按 Goal 回合 ID 关联，守护进程开始向 agent
  写入接替的 prompt 时清除旧授权卡片。接替的 prompt 如果在写入前被拒绝，仍在执行的
  Goal 保留其授权。被扣住的立即发送请求在转发前可撤销。即使取队列的回调已经安排
  转发，所属回合结束时也会丢弃该请求。

## 验证计划

- 单测（`Session.test.ts`）在两条循环路径上覆盖三种送达情况。已排队的 cron 触发在
  交接后执行，调度器持续运行。相关通知会让 `per_task` 渠道 prompt 结算，独立通知
  继续排队。被打断的 Goal 保持 active，不记为用户中断。请求绑定
  回合，没有回合时无操作，有取队列请求在途时不打断。等待授权时被打断不记为用户
  拒绝。PR 2 的测试覆盖 shell 转后台后同一轮送达、工具结果说明原因，以及之后停止
  这些 shell 的行为。
- 守护进程：打断后提升的消息顺序和来源客户端不变。
- E2E（`qwen serve` + Web Shell + 脚本化 provider）：复用旧文的延迟表，新增「生成
  `write_file` 参数」「shell 运行中」「混合批次」「Goal 回合」四行。

## 验收标准

- 在没有更早排队的普通 prompt、且没有在途取队列决定投递时，下表各场景从点击到
  携带消息的模型请求不超过 1 s：

| 点击时的状态             | 现在       | 目标                                   |
| ------------------------ | ---------- | -------------------------------------- |
| 模型在输出正文           | 约 50 ms   | 不变                                   |
| 模型在生成工具参数       | 等工具结束 | 下一轮，< 1 s（PR 1）                  |
| 前台 shell 运行中        | 6.1 s      | PR 1：下一轮；PR 2：同一轮，命令仍在跑 |
| 可以及时取消的工具运行中 | 等工具结束 | 下一轮，< 1 s（PR 1）                  |

- 打断后 Goal 仍为 active。已排队的自动回合在交接后恢复执行。
- 旧文中被本文保留的保证仍有测试覆盖。

## 待定问题

无。2026-11-19 已定：打断走下一轮；正文阶段保留同一轮截断；混合批次先转后台再打断
（PR 2）；Goal 自动继续；分两个 PR，不等 #17744。
