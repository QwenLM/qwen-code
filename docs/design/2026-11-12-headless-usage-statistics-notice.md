# Headless usage statistics notice

[English](2026-11-12-headless-usage-statistics-notice.md) | [简体中文](2026-11-12-headless-usage-statistics-notice.zh-CN.md)

## Problem

Usage statistics are on by default. Interactive sessions disclose them through the privacy notice linked from the auth dialog, but a headless `qwen -p` run renders no dialog, so it uploads usage statistics without any disclosure. No CLI output names the collection host. This gap was confirmed in #17052.

## Decision

On the headless entry path, before `config.initialize()` sends the first usage statistics event (`session_start` is flushed immediately during initialization), decide whether a one-time notice is due. The notice names the usage statistics host (`USAGE_STATS_HOSTNAME`, now shared from the core telemetry constants), states that events carry a random per-install ID (the stable pseudonym derived from the local installation ID) while prompts, code, and file contents are not collected, gives the environment-variable and settings opt-outs, notes that opting out also stops the models.dev catalog refresh, and links to the privacy notice.

Follow the existing headless notice convention: in text mode, write the notice to stderr immediately, before initialization, so stdout stays clean for scripts. In JSON and stream-JSON modes, keep it pending and emit a system message with subtype `usage_statistics_notice` and `data.notice` right after the session initialization message; if the run fails before that message (for example, at the auth check), emit it before the error result; if the process exits before either, write it to stderr from an exit handler. Deciding early is what makes runs that stop before the prompt, such as the unauthenticated run captured in #17052, still disclose. Skipping JSON modes would hide the disclosure in exactly the automated runs that need it, and consumers that ignore unknown system subtypes are unaffected.

Show it only to users relying on the default: skip it when usage statistics are disabled, or when the operator has explicitly opted in — `QWEN_USAGE_STATISTICS_ENABLED` set to any value, or `privacy.usageStatisticsEnabled` set to `true` — because an explicit opt-in is already an informed choice. An operator `false` suppresses nothing on its own: either it is in effect and collection is off, or a trusted workspace overrode it and collection is on, which still needs the disclosure. Only operator-authored values count: the environment variable must come from the launch environment (a value written by a `.env` file or a settings `env` block, which a cloned repository can provide, is ignored for this check via `isFileSourcedEnvKey`), and the setting is read from the user, system, and system-defaults scopes only, never the workspace scope. A repository can therefore still turn collection off, but it cannot hide the notice while collection stays on. Once the notice has been written to the output (immediately for text and stream-JSON, when the document is written for buffered JSON), record it as `usage-statistics-notice-shown` in the global Qwen directory (`$QWEN_HOME`, normally `~/.qwen`), next to the installation ID. A run that exits before writing it prints it to stderr at exit and only then records it, and a marker that cannot be written never suppresses the notice; in both cases it is shown again next run. Within one process it is shown at most once, so persistent stream-JSON sessions that run several turns do not repeat it.

## Scope and risks

The notice discloses; it does not ask for consent and does not change what is collected. The decision, and in text mode the output, happen before config initialization, which is where the `session_start` event is flushed and the models.dev refresh starts. In JSON modes the system message follows `init`, so it appears in the output after those requests have started; the decision itself was made before them. Interactive mode is unchanged. Ephemeral environments with an empty home directory see the notice on every run, which is intended, because each is a fresh installation. The text is English-only, like other headless stderr notices.

## Verification

Unit tests cover showing once and writing the marker only on delivery, once-per-process behavior, skipping when disabled or explicitly configured through the launch environment or an operator setting, still showing when the variable is file-sourced or the setting is workspace-only, the default environment and marker location, showing again when the marker cannot be written, immediate stderr output in text mode, and the exit-time stderr fallback in JSON modes. An entry test checks that the notice is decided before `config.initialize()` even when the auth check then fails; the auth validator tests check that a pending notice precedes the error result in JSON and stream-JSON; a headless test checks that it also precedes the error result when Mod startup fails after `init`; adapter tests check that buffered JSON records the marker only after the document is written; an operator `false` overridden by the workspace still shows the notice; headless tests cover a `usage_statistics_notice` system message after `init` in JSON and stream-JSON modes.
