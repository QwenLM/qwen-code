# Mod 提示提交

[English](2026-10-30-mod-prompt-submit.md) | [简体中文](2026-10-30-mod-prompt-submit.zh-CN.md)

状态：提议中。本阶段接在 #15443 的回合事件之后，由 #13749 跟踪。依据是 Claude Code 2.1.310 插件 API 对 `prompt.submit` 和 `$.prompt.submit` 的声明。

## 问题与现状

为 Claude Code 写的 Mod 会处理用户发出的提示：

- 守卫用 `{ drop: reason }` 拦下含有凭据的提示。
- Mod 用 `next({ ...e, text })` 改写提示，例如展开缩写。
- Mod 用 `next({ ...e, context: [...] })` 附上模型能读到、用户看不到的上下文。
- Mod 用 `$.prompt.submit` 在会话空闲后发出自己的提示。

Qwen Code 在加载时跳过 `prompt.submit` hook，并提示 `Hooks for unsupported events will not run: prompt.submit`。写在这里的守卫不会运行。

## 目标与非目标

目标，分六个 PR：

1. core 和 headless：事件本身、规则和上下文。本文随它合入。
2. Ink 终端。
3. OpenTUI 终端。
4. core 和 headless 中的 `$.prompt.submit`，见第 9 节。
5. Ink 终端中的 `$.prompt.submit`。
6. OpenTUI 终端中的 `$.prompt.submit`。

非目标：

- 斜杠命令。Claude Code 对它们带 `command` 触发，留到后续处理命令行的步骤。
- 宿主自己发起的提示：后台通知、定时提示、队友消息、goal 续跑、中断回合的续跑。Claude Code 对其中一部分标 `isMeta`。Mod 用 `$.prompt.submit` 提交的提示虽然也不是用户输入的，但属于范围之内，见第 9 节。
- 回合进行中输入、在模型边界插入当前回合的提示。
- `attachments` 和 `$.prompt.media`。

## 方案

### 1. 触发时机

用户每提交一个提示（从第 4 步起还包括 Mod 提交的每个提示，见第 9 节），在宿主拿到文本之后、任何地方读取它之前触发 `prompt.submit`：在 UserPromptSubmit 之前，在读取 `@` 引用之前，在记录或显示用户消息之前。只有会触发该事件的宿主才加载它的 hook；其他宿主在启动时照常跳过并给出提示，守卫不会被悄悄绕过。第 1 步在 headless 运行中触发：`-p` 的提示和 stream-json 的每条用户消息。第 2 步在 Ink 终端触发，见第 7 节；第 3 步在 OpenTUI 终端触发，见第 8 节。

### 2. 输入

| 字段      | 值                                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------ |
| `text`    | 提交的提示，粘贴内容已展开；stream-json 消息只取其文本块                                                           |
| `context` | 宿主触发时不带                                                                                                     |
| `wait`    | `false`                                                                                                            |
| `origin`  | headless 为 `{ kind: 'sdk' }`；终端为 `{ kind: 'composer' }`；Mod 提交的提示为 `{ kind: 'plugin', name, asUser? }` |
| `turnId`  | 不带，直到终端为回合进行中输入的提示触发该事件                                                                     |

hook 可以把改过的 `text` 和 `context` 传给 `next`；`origin`、`wait`、`turnId` 不可改。`context` 是文本列表。

### 3. 最终提交什么

和 Claude Code 一样，提交的是穿过所有 hook 到达链底的提示：worker 记录到达链底的 `text` 和 `context`。`next(e)` 解析为它们，外加 origin。hook 在 `next` 返回之后再给出的答复不起作用，这时只检查它是不是 drop。

链的结果有三种：

- 提示到达链底：带着它的文本和上下文提交；
- 某个 hook 答复 `{ drop: reason }`：提示被 hook 丢弃；
- 链没有到达链底就结束了，因为某个 hook 没调 `next` 就答复了 `{ text }`：提示没有提交，对应 Claude Code 的 `a hook answered without passing the prompt on`。

和 Claude Code 一样，调过 `next` 之后再答复 drop 的 hook 算失败：先问它的 `.catch`，否则跳过它，保留它最后一次 `next` 的结果。失败或超时的 hook 被跳过；worker 出错时提示原样通过。坏掉的插件不会拦住提示。

### 4. 改写与上下文

改写后的文本在宿主保存提示的每一处都替换掉原文：发给模型的文本、`@` 处理读取的文本、`turn.start` 的文本、transcript 记录及其显示文本。stream-json 消息若还带有非文本块，这些块会序列化后随文本发给模型；hook 只听到其中的文本块，改写替换的也是文本块，其他块接在改写后的文本之后；发给模型的文本和 transcript 都是这样，与没有改写时一致。

上下文并入 core 已有的隐藏块，即追加在提示之后、存放 UserPromptSubmit `additionalContext` 的那一块，排在后者之前，转义方式相同。client 通过新的发送选项 `promptContext` 接收它，只有该提示自己的 UserQuery 会用掉它。transcript 把这一块记作 hook 上下文，因此恢复会话时它仍然隐藏，压缩时也和 UserPromptSubmit 的上下文一样保留。

### 5. 丢弃

drop 在 UserPromptSubmit 和任何模型请求之前拦下提示，不开始回合。原因只保留一行，最多 4,096 个字符，超出部分以省略号结尾，与 Claude Code 相同。headless 运行以错误结果 `Prompt dropped by a hook: <reason>`（或 `Prompt not submitted: a hook answered without passing the prompt on`）结束，退出码为 1。stream-json 会话继续处理下一条消息。

### 6. 限制

超过 Mod 负载一半（JSON 128 KiB）的提示不经过任何 hook，并在 transcript 日志出现的位置给出 `prompt.submit hook skipped: the prompt is too long for a Mod payload`。Claude Code 会完整传递。改写或上下文让 hook 的答复超过 Mod 负载时，该 hook 算失败。

### 7. Ink 终端

Ink 终端在 `prepareQueryForLlm` 中为用户输入的提示触发该事件：在输入历史记录它之前，在添加它的消息行之前，在读取 `@` 引用之前。它触发事件时才加载这些 hook：`InteractiveModSession.initialize` 接收 `{ prompts: true }`，终端宿主再把它传给加载请求。以第一次 `initialize()` 调用为准，因为正是这次调用加载 Mod：`{ prompts: true }` 必须随这次调用传入，之后的调用无法再开启提示 hook。需要绘制提示上方区域的宿主只初始化一次，两者一起传。

- **哪些提示触发。** 用户输入的提示，包括回合进行中排队的提示，后者在真正发送时触发。斜杠命令、shell 模式命令、定时提示、通知、队友消息和重试都不触发。
- **排队的提示等回合结束。** 终端通常会在下一个工具边界把回合进行中输入的提示送进该回合。有 Mod 挂了 `prompt.submit` 时，工具边界不再取走它们，每个排队的提示在回合结束后发送，届时 hook 会听到它。
- **hook 听到什么。** 用户输入的文本，粘贴内容已展开。附件引用和终端为模型放在提示前面的一次性提醒（例如恢复的 worktree）不在其中。
- **改写。** 它替换模型收到的提示中用户输入的部分，附件引用和提醒仍在前面；同时替换消息行、输入历史、取消后的恢复、工作流关键字和 `turn.start` 中的文本。终端按输入框的方式包裹粘贴内容，从而在模型提示的末尾找到用户输入的部分。改写中完整交还的每段粘贴内容会重新折叠并包裹；没有完整交还全部粘贴内容的改写会被拒绝，见下文。答复与提示只差首尾空白时不算改写。
- **丢弃。** 原因显示为一行错误。该提示没有消息行，也不写入输入历史。它会带着折叠的粘贴内容回到输入框，放在之后输入的内容前面，方便修改后重新发送。
- **hook 运行时按 Esc。** 提示被取消，并以同样方式回到输入框。

### 8. OpenTUI 终端

OpenTUI 终端在两处触发该事件。实时回合（`useOpenTuiLiveTurn`）为用户输入的提示触发：在添加它的消息行之前，在输入历史记录它之前，在读取 `@` 引用之前。命令分发器（`OpenTuiSlashDispatcher`）为 `?` 形式的输入触发：在输入历史记录它之前，在命令运行之前。它以同样方式声明：在加载 Mod 的那一次调用中传 `initialize(['AbovePrompt'], { prompts: true })`。

- **哪些提示触发。** 与 Ink 相同：用户输入的提示，包括回合进行中排队的提示，后者在成为回合时触发。斜杠形式的文本、shell 模式命令、斜杠命令生成的提示和重试都不触发。例外是附带图片的斜杠形式文本：shell 把它作为提示发给模型，所以它和其他用户输入的提示一样触发该事件。`?btw` 这类 `?` 形式的输入在 OpenTUI 中作为命令运行，在 Ink 中作为提示发送，它同样是用户输入的文本：hook 在它被记录或运行之前听到它，粘贴内容已展开；丢弃时拒绝它并放回输入框，改写时运行改写后的文本。改写必须保留用户输入的命令：解析成别的命令或不再是 `?` 形式的改写会被拒绝，显示一行错误，什么都不运行。hook 附加的上下文随命令开启的回合（例如技能开启的回合）的首次发送一起发出；`?btw` 不开启回合，其上下文不使用。
- **排队的提示等回合结束。** 与 Ink 相同：有 Mod 挂了 `prompt.submit` 时，工具边界不取走排队的提示。
- **hook 听到什么。** 用户输入的文本，粘贴内容已展开。输入框把附加的图片作为单独的部分放在文本旁边，OpenTUI 也不在提示里加提醒，所以 hook 听到的就是提示的全部文本。
- **消息行等 hook 答复。** 没有提示 hook 时，消息行在提交时添加。有提示 hook 时，等 hook 放行后才添加，有改写就显示改写；在此之前回合显示为进行中。
- **Mod 加载期间提交的提示等 Mod 加载完。** 与 Ink 相同，会话的第一条提示不会在 hook 加载前漏过去。Mod 加载失败时，该提示被拒绝，显示与 Ink 相同的那行提示，并回到输入框。与 Ink 相同，斜杠形式的文本既不等待也不被拒绝，除非它附带图片、因而作为提示发给模型。会话在加载 Mod 之前就启动失败不算 Mod 失败：它的提示照常进入发送，由发送报告会话自己的错误。
- **改写。** 它替换发给模型的提示文本、消息行及按上键调出的文本、输入历史、取消后的恢复、`UserPromptSubmit` 的来源记录和 `turn.start`。附加的图片仍在它后面。改写中完整交还的每段粘贴内容会重新折叠并包裹；没有完整交还全部粘贴内容的改写会被拒绝，见下文。只差首尾空白不算改写。
- **丢弃。** 原因显示为一行错误，该提示没有消息行，也不进入输入历史；它带着折叠的粘贴内容回到输入框，放在之后输入的内容前面。
- **hook 运行时按 Esc。** 提示回到输入框，放在排在它后面的提示和之后输入的内容前面。对话框关着输入框时，该提示等输入框重新出现，排队的提示仍留在队列里。

### 9. Mod 自己的提示：`$.prompt.submit`

`$.prompt.submit({ text, asUser? })` 提交一条 Mod 自己写的提示，等会话空闲后作为独立的回合运行。

- **调用。** 它和其他 `$` 方法一样是 API 事件：worker 以输入 `{ text, wait: false, origin: { kind: 'plugin', name, asUser? } }` 触发 `prompt.submit`，`name` 是调用者的名字。它经过的 hook 是除调用者自身以及调用者所处的外层 hook 之外的全部 hook，这些由 `$` 调用已有的 frames 排除；调用者所在插件的其他 hook 会听到它。形状不对的调用会被拒绝，`attachments` 有单独的拒绝提示。文本为空或只有空白、或超过 Mod 负载一半（JSON 128 KiB）的调用直接返回 drop，不触发事件；对任何 Mod 调用都过大的输入会被拒绝（reject）。
- **链底。** 所有 hook 答复之后，最后到达链底的内容以 `{ plugin, text, context?, asUser? }` 交给宿主，因此调用两次 `next` 的 hook 只排队一条提示。宿主将其排队，或说明不排队的原因，调用随之返回 `{ text, context?, origin }` 或 `{ drop }`。hook 的 drop、不调用 `next` 就答复的 hook，或传下空文本、超过负载一半的文本的 hook，都不会排队任何内容。限制在负载一半以内，调用的返回值总能放进 Mod 负载，所以已排队的提示不会被报告为失败。
- **何时返回。** 在这条链结束时返回，仍处于发起调用的 hook 所在的分发之内。worker 一次只运行一个分发，并在分发结束前等待其中的调用；如果调用要等到回合开始才返回，它就会拖住正让会话无法空闲的那个分发。这条链上的 hook 不在发起调用的 hook 之下运行，所以 hook 没有 await 的调用在 hook 返回之后仍会排队。出于同样的原因，这个调用不像其他调用那样暂停调用者的预算：否则调用未完成期间仍在运行的 hook 就不受预算约束。await 它的 hook 会为其他 Mod 的 `prompt.submit` hook 所花的时间计费。
- **宿主从哪里接手。** 能运行这类提示的宿主在加载时传入一个队列，加载请求会注明这一点。只有这时 `$.session.version()` 才列出该方法；其他宿主上调用直接返回 drop，不触发事件。这一步只在 headless 中传入队列。
- **回合。** 运行空闲时，该提示排在队列中先到的项目之后，作为独立的回合运行：类型为 `UserQuery`，以 Mod 的文本作为提交的提示，并带上 hook 附加的上下文，因此 UserPromptSubmit 会听到它，它也计入会话回合上限。文本中的 `@` 引用不会被读取。该回合会触发 `turn.start` 和 `turn.complete`。以消息作答的斜杠命令（Mod 命令就是这样）自身不开始回合：如果它留下了排队的 Mod 提示，运行会先显示它的回复，再接着运行该提示，最后只给出一个结果。文本输出只打印运行的最后一个回答，因此回复在出现时直接写出。原本要交给该命令的 worktree 提示，随运行发出的第一个请求一起发送。
- **模型读到什么。** 除非 Mod 传了 `asUser`，文本会放进 `<qwen:mod-prompt mod="<name>">` 块中，块后有一行说明：这条消息是该 Mod 发来的、一直等到会话空闲，用户没有输入它，应把它当作代表用户、在用户要求和允许范围内的请求。文本里的每个 `<` 和 `>` 都会被转义（与 hook 附加的上下文相同），因此闭合标记无论怎么写都无法提前结束这个块。带 `asUser` 时模型读到的是原文。
- **记录。** transcript 把这条提示存为用户消息，来源为 `mod_prompt`，带上 Mod 的名字，并以它的文本作为显示文本。Goal 证据和会话代理视图只读取用户本人的话，因此都不会把它当成用户说的。在生成会话标题所用的文本里，它保留自己回合的位置，但不提供任何内容，也不会单凭自己让标题只读这些文本，所以提示都没有记录显示文本的会话仍从对话生成标题，并剔除模型读到的那条 Mod 消息；用 `asUser` 发送的不剔除，因为它的原文读起来就是用户的话，也会与用户输入的同样文字相匹配。它不计入提交署名的提示数。记忆召回检索的是 Mod 的文本，而不是框文。stream-json 客户端没有发送这条提示，因此会在该回合的输出之前收到它的文本（user 消息），随后是一条注明 Mod 的 `mod_prompt` 系统消息。
- **回合上限。** 在用户再次发送提示之前，Mod 的提示最多启动 8 个回合，排队中的也计算在内。超过之后，调用返回 drop，并在 transcript 日志出现的位置显示 `$.prompt.submit refused: …`。headless 运行时，运行收到的提示算作用户的；stream-json 会话中，客户端发送的每条消息都算，斜杠命令也算。通过 `/clear` 或 `/resume` 切换到另一个会话时，新会话没有排队的提示，计数从 0 开始；旧会话结束期间提交的提示会以 `the session is ending` 被拒绝。
- **不会运行的情况。** 为已被 `/clear` 或 `/resume` 替换的会话排队的提示、会话关闭过程中排队的提示，以及运行因中断、结构化结果、检测到循环或斜杠命令失败而提前结束时仍在队列里的提示。

## 设计决策

- **由宿主触发事件。** 每个宿主在展开或记录提示之前就已拿到提交的文本。在这里触发，改写就能先于文本的每一次使用，且不必改 core 的发送流程。
- **UserPromptSubmit 在 Mod hook 之后、在 core 里运行。** Claude Code 把两者放在同一次准入里，下层设置 hook 的拦截会让 `next(e)` 变成 `{ drop }`。这里链底不等 UserPromptSubmit：它在发送流程更靠后的位置运行，耗时取决于它的命令。需要知道 UserPromptSubmit 是否拦下提示的 Mod 可以看 `turn.start`，只有获准的提示才会触发它。
- **宿主自行声明。** 加载请求说明宿主是否触发 `prompt.submit`，就像它为 `ui.render` 列出绘制的位置一样。每一步只为它新增的宿主开启。
- **上下文共用 hook 上下文块。** 它到达模型、进入 transcript、在恢复时的处理都和 UserPromptSubmit 的上下文一致，不需要新的记录类型。会话里已有一字不差的同一上下文时不再发送，与 UserPromptSubmit 相同。每条 Mod 上下文和 UserPromptSubmit 的上下文分别判断，所以每轮都变的 Mod 上下文不会让没变的 UserPromptSubmit 上下文重复发送。

- **被丢弃的提示不进入输入历史。** 输入历史会写入磁盘，并在之后的会话中恢复，而守卫丢弃提示通常正是因为其中的内容，例如凭据。不写入历史才能守住守卫的目的。把它放回输入框，用户仍可直接修改，不必重新输入；之后输入的内容保留在它后面。
- **加载了提示 hook 时暂停中途插话。** 中途插话把排队的文本附在运行中回合的工具结果后面，没有可以拦下或改写的独立提示。让排队的提示等到回合结束，用户输入的每个提示都会经过 hook，代价是挂了这类 hook 的会话不能在回合中途插话。
- **OpenTUI 中消息行等 hook 答复。** 守卫丢弃提示通常正是因为其中的内容，先显示消息行就会把守卫想挡住的内容显示出来；改写也会替换一条用户已经看到的消息行。在有 Mod 挂了 `prompt.submit` 时，以及 Mod 加载完成之前，消息行都会等待，所以 transcript 不会在可能丢弃提示的 hook 答复之前显示它；Mod 没有挂任何 hook 的会话只多等加载这一段。回合进行中输入的提示在发送前仍显示在排队消息栏里，与输入框显示它的方式相同：那里是用户自己待发的输入，不会被记录，hook 听到它时它就离开该栏。
- **改写必须完整交还每段粘贴内容，否则被拒绝。** 模型会被告知哪些文本是粘贴的，从而把它当作材料，而不是用户的指令。hook 听到的是展开后的粘贴内容，终端按文本在改写中找到每段粘贴内容。粘贴内容被改动了内部、被删掉或重复出现时就找不到它，此时发出改写，模型会把粘贴的文本当成用户亲手输入的。终端会拒绝这样的改写，显示一行错误并把提示交还；Ink、OpenTUI 和 `?` 形式输入都是如此。需要挡住某段粘贴内容的守卫应丢弃提示。同一段文本粘贴两次时，只要它在改写中出现两次就能找到。
- **`$.prompt.submit` 在提示排队时返回。** worker 的单一分发正是 hook 的调用不会活得比它更久的原因；如果调用在回合开始时才返回，就需要一种能跨过分发结束的调用，而 await 它的 hook 会让会话一直忙碌，回合永远不会开始。在 hook 答复之后返回，与 `next(e)` 对用户输入的提示已有的行为一致，因此 Mod 无论哪种情况都在同一时刻读到同样的形状。
- **模型会被告知 Mod 的提示是谁发的。** 不是用户输入的提示不应读起来像用户说的：模型对用户的话比对工具的话更看重，而 Mod 运行的代码用户可能从未看过。这个块写明 Mod 的名字，块后的说明让这条提示具有代表用户提出的请求的地位。`asUser` 是 Mod 按 API 的允许、把文本作为用户的话发出的选择。
- **Mod 的提示有自己的来源。** transcript 把用户的提示标为用户本人的，Goal 的验证器把这些当作用户提出的要求来读。如果 Mod 写的提示也挂在用户的来源下，Mod 就能在那里替用户说话；单独的来源能让所有寻找用户本人话语的读取方都找不到它。会话标题和提交署名的提示数用别的方式读取用户的提示，所以各自单独跳过 Mod 的提示。
- **限制 Mod 启动的回合数。** 每次 `turn.complete` 都提交提示的 hook 会让会话永远忙碌，在 headless 中则永远无法退出。8 个回合足以覆盖 Mod 跟进几次的情况；用户的下一条提示会重新计数，所以交互会话在用户继续使用时可以一直进行。
- **UserPromptSubmit 会听到 Mod 的提示。** 它是进入会话的提示，守护提示的设置 hook 不应因为提示是 Mod 写的就被绕过。
- **hook 听到用户输入的文本，而不是只给模型的提醒。** 用户输入的文本是用户写的；那些提醒属于终端，随会话变化。改写只替换用户输入的部分，守卫不会误删终端的提醒。

## 与 Claude Code 的差异

以下内容写进用户指南：

- 斜杠命令和不是用户输入的提示不触发它，所以不会出现 `command` 和 `isMeta`。
- 不会出现 `attachments`，也没有 `$.prompt.media`。
- UserPromptSubmit 的拦截不会让 `next(e)` 变成 `{ drop }`；`next(e)` 在回合开始之前就返回。
- 会话里已有一字不差的同一上下文时不再发送，每条 Mod 上下文和 UserPromptSubmit 的上下文分别判断。
- 超过 JSON 128 KiB 的提示不经过任何 hook。
- headless 的 drop 是错误结果，退出码为 1。
- `$.prompt.submit` 在提示排队时返回，而不是在回合开始时返回；它不接受 `attachments`。

## 风险与待定问题

- 慢 hook 会让提示延迟，最多为它的预算，每个 hook 10 秒。
- 目前遮蔽斜杠命令的参数要靠 `command.run`；带 `command` 的 `prompt.submit` 留到以后。
- 恢复的会话把 Mod 的提示显示为它提交的文本；终端如何显示这类提示及其 transcript 记录，留到 Ink 那一步。
