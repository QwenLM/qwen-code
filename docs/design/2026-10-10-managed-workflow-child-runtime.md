# Managed workflow child runtime (H4 workflow slice)

[English](2026-10-10-managed-workflow-child-runtime.md) | [简体中文](2026-10-10-managed-workflow-child-runtime.zh-CN.md)

Status: implemented in this change. Landed: the managed workflow admission (inline script source only), the workflow launch envelope, the workflow first-Turn execution with digest re-verification, the kind-parametric relay/cascade/funnel, and the kind gate listing both child Session kinds. Still design: saved or extension workflow references, script-level resume, nested managed grandchildren, a workflow definition catalog, and the other Follow-up items. This is the **workflow child runtime** slice of [#12827](https://github.com/QwenLM/qwen-code/issues/12827), stage H of the Managed Agent proposal [#12380](https://github.com/QwenLM/qwen-code/issues/12380), tracked by [#13803](https://github.com/QwenLM/qwen-code/issues/13803). It follows H4a ([record contract](2026-10-06-managed-child-agent-runtime.md), #13505), H4b ([child Session runtime](2026-10-07-managed-child-session-runtime.md), #13550) and H4c ([workflow kind and launch budget](2026-10-09-managed-workflow-child-kind.md), #13754), whose "Workflow runtime" follow-up row this slice is. Where the earlier documents disagree with this one, this document governs for this slice.

## Problem and scope

H4c landed the `workflow` body kind of `managed-child_run` as a **disabled record contract** and named what enablement actually takes: the Workflow tool's managed admission, the launch envelope, a child Session that executes a workflow, the relay and cascade widened to `workflow` rows, then — and only then — the kind gate entry. Issue #13803 files exactly that slice as K1–K4:

| Item                                            | Deliverable                                                                                                                                                                                                                     | Exit check                                                                                                                                    |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| K1 — workflow-driven child creation             | The relay discovers a pending `workflow` launch and creates the child Session from a workflow reference rather than a prompt, idempotently under the parent's exact Workspace binding, lineage stamped in the same transaction. | One child Session per launch under retry (same `dispatchId`); the child's launch input names the workflow and its pinned definition revision. |
| K2 — relay and cascade include `workflow` rows  | The discovery page and the live-scope query stop selecting `child_agent` only; the cascade cancels a `workflow` child through a funnel that can act on it.                                                                      | Closing a parent cancels its non-terminal `workflow` children; no row is invisible to the relay or unreachable by the cascade.                |
| K3 — definition pinning from the first revision | A `workflow` run pins its definition from the opening revision.                                                                                                                                                                 | A first revision without the pin is refused; a child agent chain is not.                                                                      |
| K4 — lift the kind gate                         | Add `workflow` to `MANAGED_SESSION_ENABLED_CHILD_RUN_KINDS`, after K1–K3 and a physical acceptance pass of the same shape as [#13532](https://github.com/QwenLM/qwen-code/issues/13532).                                        | A `workflow` launch runs end to end on a real host; the unlisted-kind refusal witnesses are flipped deliberately, not silently.               |

What this slice does **not** deliver: saved or extension workflow references (only inline source), script-level resume of an interrupted child, nested managed grandchildren, a tenant-scoped workflow definition catalog, detach, durable peer messages, teams, public cancel — each named under Follow-up work.

## Current state

The facts below are from `main` at `ba8615f4c4` (Flyway V60, contract v1.38.0), and re-check every verification note #13803 carries.

- **The record contract is complete for both kinds.** `parseChildRun` dispatches `shell`, `child_agent` and `workflow`; the two child Session kinds share one closed key set, one successor rule set and one classifier (`isChildSessionRun`). A `workflow` run must pin `run.definition` from its opening revision — K3's refusal exists today (`managed-child-run-record.ts:519-523`, mirrored by `ManagedExtensionRecords.requireChildSession`). The task projection maps `child_run.workflow` to the `workflow` task kind in both languages; the OpenAPI already ships `TaskKind.workflow` as `partial`.
- **The kind gate and its sites.** `MANAGED_SESSION_ENABLED_CHILD_RUN_KINDS` is `['child_agent']` (`managed-session-records.ts:182`). The authority's commit path checks it on **every** `child_run` revision, not only the opening one (`managed-session-authority.ts:1515-1523`), so a relay or cascade verb (`dispatch_started`, `attach`, `commit_result`, `accept`, `mark_accepted`, `fail`, `cancel`, `close_scope`) on a `workflow` row answers 409 `child_operation_record` today. The hosted tool turn checks the gate through `childAgentAdmissionsEnabled()`, a reader hard-coded to `child_agent`.
- **The relay and cascade narrow deliberately.** `ChildResultRelayStore.PENDING_SQL` (`:97`) and `findLiveScopes` (`:220`) carry `task_kind = 'child_agent'` with comments naming this slice. Neither #13753/I1 (#13781) nor H4d-a (#13786) widened them.
- **The child-agent runtime extends cleanly.** The launch envelope `{description, prompt, definition}` is encoded in TS (`managed-child-operations.ts:55-121`) and decoded by the Java relay (`ChildResultRelay.create`, `ChildResultRelay.java:239-258`), which creates the child through `ManagedAgentService.createChildSession` — one transaction copying the parent's Workspace binding and tool profile, stamping the V54 lineage columns, inserting the first Turn, idempotent by the record-key-derived creation key. The funnel (`HostedChildAgentSession`) is kind-specific in four named places: the `record()` kind filter, the `parseAgent` refusal, the notification `<kind>` tag and `source`, and the tool-turn admission literal. Quotas (`launchedChildRunsOf`/`activeChildRunsOf`), the restore skip and the cross-record checks are already kind-generic.
- **The ordinary-path workflow engine exists and is headless-capable.** `WorkflowRunner.start` (`packages/core/src/agents/runtime/workflow-runner.ts`) executes a deterministic JS script in a `node:vm` sandbox with `agent()`/`parallel()`/`pipeline()` dispatching to in-process `AgentHeadless` subagents (per-run caps: 1000 agents, 30-minute wall clock, 50 turns/10 minutes per subagent, token budget), settling with `{runId, result, phases, logs, meta}`. The Workflow tool admits inline `script`, saved `name`/`scriptPath`, `args`, `resumeFromRunId` and `sourceRef {id: string, revision: string}`; scripts compute a 16-hex content digest for permission grants. The Hosted profiles declare no `workflow` tool and `prepareRequests` refuses one.
- **The pin has no ordinary-path source.** `DefinitionPin.definitionRevision` is a number and its digest a full lowercase SHA-256 hex (`assertManagedSessionDigest`); the legacy workflow vocabulary has neither a numeric revision nor a definition store, and a saved-workflow name resolves per host and mutates between calls ("edits take effect on the next call").

## Decisions

1. **v1 admits inline script source only.** The managed workflow admission takes `script` (the same deterministic JS body the ordinary path's inline mode runs), bounded `args`, and `run_in_background`. `name`, `scriptPath`, `resumeFromRunId` and `sourceRef` are refused at admission with a tool error naming the follow-up scope — the same honesty stance H4b took for `snapshot`/`worktree` modes and custom `subagent_type`. Reasons: an inline source is the only reference whose content the parent can bind at launch with zero lookup; a saved name resolves per host and may change between launch and dispatch, so a digest pinned at launch would need a dispatch-time re-verification and a new honest refusal path; a tenant-scoped definition catalog is real work the record contract deliberately never required (H4a decision 10). Inline is also the canonical authoring flow of the ordinary path (the model writes the script it launches), so the restriction loses no primary use case.
2. **The pin derives from the script itself.** With decision 1, `DefinitionPin` is computed at admission from the exact bytes that will run: `definitionDigest` = SHA-256 of the script source (full lowercase hex, satisfying `assertManagedSessionDigest`); `definitionRevision` = `1` by convention for inline sources — a content-bound identity needs no counter, and the H4b precedent (`hosted-agent/<profile>`, revision 1) already uses revision 1 the same way; `definitionId` = `workflow/<meta name>` when the script's statically parsed `meta.name` matches the ordinary `WORKFLOW_NAME_PATTERN`, else `workflow/unnamed`. The id+revision classify, the digest binds. The child turn re-verifies `sha256(script) = pin.digest` before executing and fails the turn honestly on mismatch (decision 4), so a mangled copy can never execute. K3's exit check stays with the H4c contract fixtures; this slice's obligation is that every produced launch carries these values, which the admission suite pins.
3. **The workflow launch envelope is a sibling closed shape.** The `inputRef` resource of a `workflow` launch carries `{ definition, script, args }` with closed keys (`encodeWorkflowLaunchEnvelope`/`decodeWorkflowLaunchEnvelope` beside the child agent's pair), bounded by the same 32 KiB `maxEnvelopeBytes` — the envelope holds source plus structured arguments, and a launch beyond budget is refused with `byte_limit`. The `child_agent` envelope `{description, prompt, definition}` is untouched; consumers branch on the **record kind**, never on envelope shape sniffing. The envelope repeats the record's `run.definition` pin by construction (one computation site in TS feeds both), exactly as the `child_agent` envelope carries its pin today; Java builds the child's launch from the envelope alone.
4. **The child Session executes the workflow as its first Turn — deterministically, never through a model mediator.** Creation of a `workflow` child (a `createChildSession` sibling arm) inserts the first Turn with a structured `workflow_launch` input block `{ definition, script, args }` instead of the `"[description]\n\nprompt"` text block, and the hosted turn runner, on reading that block, drives `WorkflowRunner.start` in-process: the Turn's settled content is the bounded serialization of the run outcome (`{ runId, result, phases, logs, meta }`, with the same escape-then-truncate discipline as other bounded contents), and its receipt names the outcome classification, the `wf_` run id and the script digest. Everything downstream is then **unchanged H4b machinery**: the relay watches the Turn line to terminal, copies the published result and receipt, submits settle/accept; the cascade closes the child through its own lifecycle; the two completion arms (`"tool"` waiter, `"sent"` notification) are kind-blind below the funnel. The turn wires the Session's ordinary abort signal to `runner.abort()`, so a cancelled or harness-closed child settles the turn promptly through the existing terminal classifications rather than running out the script's wall clock. A daemon death mid-script leaves an interrupted Turn the ordinary turn-recovery settles failed; the relay then settles the run `child_failed` — honest, and script-level resume is the follow-up named below.
5. **The script's `agent()` calls run inside the workflow child.** They dispatch to in-process `AgentHeadless` subagents under the ordinary per-run caps (1000 agents, 30-minute wall clock, per-subagent turn/time caps, token budget), exactly as on the ordinary path — they are **not** managed grandchild Sessions. The managed durable boundary of this slice is the child Session: a reclaimed Runtime mid-script fails the run visibly (decision 4) instead of silently relocating fan-out. Nested managed grandchildren require depth 2, the cascade's (already recursive) semantics applied below depth 1 and a per-subtree budget — that is the "depth beyond 1" follow-up every H4 document names, not this slice. The child Session's tool turn keeps suppressing the `agent` tool (`childDepth`), and suppresses the new `workflow` tool the same way, so no nested launch can even be admitted. This settles H4c open question 2 in the direction the stage-H shape demands: migrate the existing capability, invent none.
6. **The managed workflow admission mirrors the Agent tool's.** A `HOSTED_WORKFLOW_TOOL` declaration (`{ script, args?, run_in_background? }`) is advertised exactly where the Agent tool is: Sessions owning their child orchestrator on the proven Shell lanes, at `childDepth === 0`, behind its own gate reader `childWorkflowAdmissionsEnabled()` (which reads the kind gate for `workflow`, as `childAgentAdmissionsEnabled()` reads it for `child_agent`). Invalid arguments answer the same model-visible validation-error vocabulary; the launch admission runs the unchanged `admitChildLaunch` (closing → workspace_mode → definition_scope → depth_limit → budget → count → byte), whose quota counts already include `workflow` runs, so enabling workflows cannot double a scope's allowance (H4c decision 10). The launch body comes from a `workflowLaunchBody` sibling of `childLaunchBody` (kind `workflow`, depth 1, `workspaceMode: shared`, the decision-2 pin), committing revision 1 through the same `HostedChildAgentSession.admit` funnel with the same replay discipline. Approval: in the private Hosted profile the admitted launch **is** the grant, mirroring the Agent tool — no dialog exists on this path, and the child inherits the parent's tool profile and approval mode, which bound everything the script's subagents may do.
7. **K2 and K4 land in the same change, by construction.** The kind gate fires on every `child_run` revision commitment, so a widened relay or cascade would 409 on its first verb against a `workflow` row while the gate is down, and a lifted gate without the widened queries is exactly the quarantine failure the issue forbids. The single change therefore flips `MANAGED_SESSION_ENABLED_CHILD_RUN_KINDS` to `['child_agent', 'workflow']`, widens `PENDING_SQL` and `findLiveScopes` to `task_kind IN ('child_agent', 'workflow')`, retires the H4c narrowing comments, and makes the funnel kind-parametric end to end: `record()` admits both kinds, the `parseAgent` refusal vanishes (the shared `ChildSessionRun` parse serves both), the notification's `<kind>` tag carries the record's own kind, the notification `source` names the record kind (`child_agent` / `workflow`) with `isWakeInputSource`, `isWakeOwnedInput`, the close-time pending-input drain and the consumption predicate widened to match, and the `/children/operations` error mapping is unchanged. Every pre-existing witness of the unlisted refusal — the gate constant test, the H4c authority witnesses of "registered but not enabled", the tool-turn/funnel stubs of the gate reader — is rewritten in that commit to assert the admitted behavior, so no refusal witness dies silently.
8. **No schema and no public contract movement.** The widening needs no columns (the relay ledger, the discovery index and the lineage columns are kind-blind), so no Flyway migration follows V60. `TaskKind.workflow` already ships as `partial`; the OpenAPI and `contract-known-gaps.txt` are byte-identical. The enablement posture matches H4b exactly: the private Hosted profiles only; production AgentBundle enablement stays the separately gated follow-up.
9. **K4's physical acceptance runs before merge, in #13532's shape.** A behaviors table executed against the packaged stack (managed-agent-server plus its database plus the bundled daemon) at the PR head commit on a real host, each row recording command and output, blocked-with-reason never passed-as-skipped. Behaviors: (1) a foreground workflow launch completes end to end with exactly one child Session under retry; (2) a background launch delivers its notification and consumes it; (3) closing a parent mid-script cancels the workflow child through the full record line (`stopRequested`, cancelled, child Session closed); (4) a pin-tampered turn refuses to execute (decision 2's re-verification); (5) the flipped witnesses hold on the packaged stack — a workflow commit succeeds with the gate as shipped, and the unlisted refusal is reproducible on the base build; (6) a relay interruption mid-run re-claims without minting a second child and delivers the result at most once. The pass file lives under `.qwen/e2e-tests/` with this plan. Production enablement, once proposed later, owes the Linux re-run exactly as #13532 records for H3.

## The pipeline, revision by revision (workflow arm)

Identical to H4b's table with two substitutions: revision 1 carries `kind: "workflow"` and the decision-2 pin on its opening revision, and the "creation" the relay drives composes a `workflow_launch` first Turn instead of a prompt Turn. Every relay/cascade verb, every quota, every successor rule, both completion arms and the close cascade are the shared mechanisms the H4b table names; the exit check "exactly one child Session under retry" rides the same record-key-derived creation key.

| Step                             | Commit                                                                        | Workflow-arm specifics                                                              |
| -------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 1 launch (rev 1)                 | `admitted` / `intent` / `planned` + decision-2 pin                            | `workflowLaunchBody`; envelope `{definition, script, args}` published as `inputRef` |
| 2 dispatch (rev 2)               | `dispatch_started`, `dispatchId`, runtime binding                             | unchanged                                                                           |
| 3 attach (rev 3)                 | `childSessionId`, `running_attached`                                          | unchanged                                                                           |
| 4 settle (rev)                   | `settled`/`completed`, `resultRef`+`terminalReceiptRef`, delivery `accepting` | result = bounded serialized run outcome from the workflow Turn                      |
| 4b failure ends                  | `creation_failed` / `child_failed` / `quota_exceeded` / `stop_requested`      | adds: script refused (determinism gate), digest mismatch, runner abort              |
| 5–7 accept → accepted → consumed | acceptance record, delivery advances                                          | unchanged, both arms                                                                |

## Non-goals

- **Saved or extension workflow references, `sourceRef`, resume** (decision 1) — a definition catalog or a verified-reference slice, later.
- **Nested managed grandchildren and depth 2** (decision 5).
- **Script-level resume across a reclaimed Runtime** — the runner's journal stays host-local in v1; the record line is the durable story.
- **Workflow definition catalog with numeric revisions** — obsoleted for inline source by decision 2's digest binding; reconsidered only with saved references.
- **Production AgentBundle enablement, detach, peer messages, teams, public cancel, isolation modes** — their own named slices, unchanged.
- **Any legacy path change** — the ordinary Workflow tool, its trust gates and its approval dialogs are untouched; the managed admission is a separate declaration.

## Validation plan

- **TypeScript**: envelope round-trip and closed-key refusal fixtures; the admission matrix (each refusal reason, both kinds, the shared quota counts); gate flip witnesses asserted in the same commit; funnel suites replaying every verb over a `workflow` chain; tool-turn suites for declaration, admission, the foreground waiter and the consumed-commit over a workflow child; the workflow Turn runner's unit suite (determinism gate, digest re-verification, abort wiring, bounded serialization) with an injected dispatch, mirroring `workflow-runner.test.ts`.
- **Java**: relay discovery returns both kinds and drives each through creation; the workflow creation arm's idempotent replay (same key, same digest → same Session; same key, different digest → conflict); cascade live-scope and cancel over a `workflow` row; contract replays unchanged.
- **Dual-language**: the envelope shapes and the flipped gate are witnessed in both languages where both sides read them (record contracts already replay; the envelope is encoded TS-side, decoded Java-side — the hand-typed replay pin in `ChildResultRelayTest` carries the same envelope JSON the encoder produces and the relay test asserts the created block's pin fields from it).
- **Fault injection (authority/relay level)**: crash before launch commit; between launch and creation; between creation and first-Turn dispatch; mid-script daemon death; between settle and accept; each run ends in exactly one child Session and at most one delivered result, or a visible `unknown` classification.
- **Mutation checks**: every new guard — the envelope closed keys, the pin computation, the digest re-verification, the widened queries, the kind-parametric funnel reads, the gate reader — disabled in turn fails its named witness, in both languages, per the H0b discipline.
- **Physical acceptance**: decision 9's behaviors table, on the packaged stack at the PR head, appended to the E2E plan file with outputs.

## Acceptance criteria

- **K1**: a `workflow` launch produces exactly one child Session under retry (same creation key, same `dispatchId`), and the child's first Turn names the workflow and its pinned revision — evidenced store-side and physically.
- **K2**: closing a parent cancels its non-terminal `workflow` children through the same funnel as `child_agent`; the relay discovery page and the cascade live-scope query return both kinds; a `workflow` row is never invisible nor cancelled through a refusal.
- **K3**: every produced launch carries the decision-2 pin from revision 1; the H4c refusal fixtures replay unchanged; the child turn's digest re-verification refuses a tampered copy.
- **K4**: `MANAGED_SESSION_ENABLED_CHILD_RUN_KINDS` lists both kinds; every previously unlisted-refusal witness is rewritten deliberately in the same commit; the physical acceptance table records every behavior observed, blocked-or-evidenced.
- All existing suites stay green — every H1–H4e contract replay, authority, store, tool-turn, funnel, relay and lifecycle suite in both languages; `npm run build && npm run typecheck`, `npm run bundle`, and the full `managed-agent-server` surefire suite; the zero-gap contract file is byte-identical.

## Open questions

1. **The workflow child's `workingDirectory` and Workspace mode at launch.** v1 fixes them as the Agent tool does (`.`, `shared`); whether a workflow may name a subdirectory rides the launch-admission vocabulary conversation, not this slice.
2. **Script-level resume wired into child Turn recovery** — the runner's journal resume (`resumeFromRunId`) is the honest mechanism, but mapping `wf_` run identity across a replaced harness is its own design point.
3. **Result size staging.** The 64 KiB result-copy bound applies unchanged; larger workflow results wait for the Artifact-staging follow-up the H4b open question already names.
