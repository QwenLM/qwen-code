# TUI parity CI 效率优化

[English](2026-10-24-tui-parity-ci-efficiency.md) | [简体中文](2026-10-24-tui-parity-ci-efficiency.zh-CN.md)

## 问题与范围

TUI parity 工作流会为所有 package 变更运行，包括只改 Java 服务的 PR，而且不会取消同一 PR 的过期运行。两个检查都会构建全部工作区。在运行 [39975710372](https://github.com/QwenLM/qwen-code/actions/runs/39975710372) 中，parity job 耗时 22 分 33 秒，其中构建 6 分 21 秒，串行产品验收 13 分 02 秒。这些是基线观测，不是对优化收益的承诺。

本次修改优化调度与构建范围，不改变断言、runner 路由、产物名称或三种运行时/渲染器组合。

## 设计决策

- 按工作流、事件和 PR 编号划分并发组。取消同一 PR 的过期运行，包括两个重型 job。手动触发使用独立 run ID，不会被其他手动触发或 PR 更新取消。
- 保留全部 package 的触发覆盖。补充 integrations、补丁、脚本、工作区配置、Node 配置、本地 CI actions/scripts 等共享构建输入，避免缩小构建范围后漏掉输入变化。
- 轻量 hosted job 通过分页 PR-files API 判定，不检出 PR 代码。仅当所有变更路径都在 `packages/managed-agent-server/`、`packages/vscode-ide-companion/src/` 或 `docs/` 下时，跳过原有名称的 parity 和 no-flicker job。重命名也检查原路径。其他路径均要求运行两项检查；手动触发始终运行。
- 文件数量不完整、缺失数量或达到 API 的 3,000 个文件上限时，必须运行测试。判定 job 失败也不会跳过检查：除工作流已取消外，下游条件明确允许失败的依赖。判定失败仍然会使整个工作流失败。
- 两项检查均使用已有的 `npm run build -- --cli-only`，构建 CLI 依赖闭包以及构建脚本已列出的运行时附加包。依赖安装、打包、组件检查与全部产品测试保持完整。

## 约束与后续工作

本次不并行三组产品验收。集成测试的全局初始化共用按时间戳命名的目录及清理逻辑，调用方还提供了同一个 `QWEN_HOME`。ECS 主机承载多个 runner，目前集成配置有意限制 worker，编辑器测试也包含亚秒级时间断言。并行前需要独立的初始化、缓存和 home 生命周期，并在真实 runner 负载下取得证据。

Java 排除范围保持精确：其他 package（包括未来新增的 CLI 依赖）仍运行。混合 PR 若包含这三个排除目录之外的无关路径，可能保守地运行。Companion 的排除止于 `src/`：其 package 清单、打包配置和 `scripts/` 既是 Companion 构建的输入，也是 `bundlePaths.ts` 记录的 bundled-CLI 拷贝输入，因此仍要求运行两项检查。现有工作流级路径过滤仍允许纯文档修改不启动工作流；纯服务端修改会启动工作流并生成 skipped 的原名检查。新增轻量 job 会增加 hosted 调度和 API 依赖。跨 job 共享构建产物暂缓，因为平台及原生依赖兼容性需要更大范围的修改。

## 验证与验收

- 工作流元测试执行实际内嵌判定脚本：Java 加文档跳过；Companion 源码-only 变更跳过，而其清单、打包配置和 `scripts/` 运行；CLI、core、channels、新 package、构建输入、重命名和第一页之后的相关变更运行；不完整 diff 与手动触发运行。每个排除目录各有独立的重命名用例，避免只收窄重命名分支仍保持绿色。
- 固定仅取消 PR、手动运行独立分组、稳定 job 名称、判定失败时的执行条件及 CLI-only 构建命令。保留已有超时、严格未处理异常和产物检查。
- 执行工作流语法校验、格式检查及相关脚本测试。
- 从全新依赖安装开始构建 CLI 依赖闭包及 bundle，然后在本机前置条件允许时执行组件一致性、离线防闪烁及原有串行产品验收。明确记录无法执行的检查。
- 发布 PR 后比较 CI 耗时。完成 CI 之前不承诺固定提速；本地耗时无法预测共享 runner 的排队时间。

UI 验收不适用：此次修改仅涉及 CI 调度和构建选择，不修改产品源码或交互。已有 TUI 测试验证所选构建的实际消费者。
