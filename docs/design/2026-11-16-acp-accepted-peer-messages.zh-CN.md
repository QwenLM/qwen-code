# 程序驱动的会话接收已被接受的跨会话消息

[English](2026-11-16-acp-accepted-peer-messages.md) | [简体中文](2026-11-16-acp-accepted-peer-messages.zh-CN.md)

状态：随本文档一起实现。

## 问题

程序通过 ACP 驱动的会话（daemon 为 Web Shell 运行的会话，或编辑器直接驱动的会话）会登记到会话目录，能被 `list_agents` 列出，也能用 `send_message` 发消息。但发给它的任何消息都会收到 `refused`。托管它的 `qwen --acp` 进程绑定 inbox 时，策略读取函数对每条消息都回答 `refuse`，所以没有一条消息真正经过审查。

当初的理由是：hold 是要人来回答的问题，而没有人替这类会话看 hold 列表。这条理由对会被 hold 的消息仍然成立，对其余消息不成立。来自同一审查类别的会话、受信控制器或会话自己启动的进程的消息，本来无需审查就会被接受，现在却和其它消息一样被拒收。结果是两个 Web Shell 会话之间没法互相说一句"构建完成了"，终端会话也没法对 Web Shell 会话说。

之前的两次尝试（#12162、#12403）一次性引入了完整的消息生命周期：从接受到一个可能根本不会运行的 turn，每条消息都要记账，每一步都要更正回执。每轮评审都在状态迁移里发现新的缺陷。这次只做本身就有用的最小一块：接受网关会接受的消息，提供和交互式终端会话目前相同的保证，并列出留待后续的部分。

## 设计

**网关把会 hold 的消息改为拒收。** `InboundGate` 新增一个选项 `presentsHolds`，默认为 true。设为 false 的主机没有地方展示被 hold 的消息，所以网关把 hold 判定当作拒收：发送方收到 `refused`，这个 id 记为已结算，不会停放任何消息。接受的路径不变，显式的 `refuse` 设置也不变。

这个转换必须在网关里做。主机不能靠在策略读取函数里回答 `refuse` 得到同样的效果。那个读取函数只反映显式设置，而显式设置的优先级高于受信控制器和会话自己的进程。主机现在正是这样回答 `refuse` 的，这也是那些消息被拒收的原因。

在这里，所有会导致 hold 的原因都应该回答 `refused`。显式的 `hold`、另一审查类别的发送方、没有声明类别的发送方、无法识别的设置值，都取决于这个会话的常设配置。用户不改，配置就不会变，所以发送方应该停下，而不是重试。审批模式未知的情况，对本主机持有的会话不会出现，因为下面的读取函数从活着的 `Config` 读取它。

**每个读取函数都针对消息指向的会话。** 主机已经认得一个会话的两个名字：它发布时的 id，和它的 `Config` 当前持有的 id（`/clear` 和 resume 会替换后者）。创建会话时会检查这两个 id 是否已被占用。任一 id 只匹配一个已登记的会话时才能路由，匹配多个时返回 `misaddressed`。所有读取函数都使用同一次查找规则：

- 主机是否持有该会话（`ownsSessionId`）。只有为消息登记过的会话才算。设置里关闭了消息的会话没有记录，不可寻址；即使发送方知道它的 id，也会得到 `misaddressed`。现在这样的发送方会被按另一个会话的模式审查。
- 审批模式取自该会话的 `Config`。
- 策略是该会话自己的 `agents.crossSessionInbound`。
- 投递进入该会话的队列。正在关闭或因 Stop 暂停的会话返回 `queue-full`。新一轮用户输入会解除暂停。会话消失后再重试会收到 `misaddressed`。

**子进程凭据只用于单会话 inbox。** 进程级凭据只能证明子进程来自同一个宿主。共享的 ACP inbox 接受 peer 凭据和控制器凭据。终端会话保留自己的子进程凭据。

**投递函数在 socket 绑定之前接上。** `PeerMessaging.start` 接受投递函数作为选项，并在 inbox 开始监听之前装好，和它对网关的处理一样。一开始就有投递函数的主机永远不会缓冲。如果缓冲中的某条消息的会话已经消失，它无法投递，还会挡住后面的所有消息。

**被接受的消息是一条 `peer` 类型的后台通知。** 主机把消息交给它指向的会话，会话把它放进承载已完成 agent 和 shell 结果的通知队列。会话空闲后，消息在单独的一轮中写入对话记录、展示给客户端并交给模型。排队阶段过期的消息不会在重放中显示为等待处理。这和终端会话得到的"下一轮"相同，不会打断正在运行的工作。`peer` 类型已经被会话和客户端之间的所有解析器识别（#12342）。消息等待期间，会话算作忙碌，所以条件关闭不会丢掉它。这一轮的 label 是接收方自己对消息来源的标注（"Message from another session (name): ..."），截断到 label 长度上限。Web Shell 把 label 显示在跨会话消息标记旁边。

peer 消息在通知队列内独享 20 个槽位，后台结果保留原有的 20 个槽位。peer 额度用完时，新消息得到 `queue-full`，发送方可以重试。等待中的工作链仍有空间接收它所需的完成通知。

**会话没有读到的消息会被更正为 `expired`。** 主机移除会话时，先取出仍在等待的 peer 消息，再发送 `expired`。`/clear` 切换对话时，按入队时记录的会话 ID 找出旧消息并做同样的结算。进程退出时，先停止入队并取出未读消息，再等待 socket 关闭以及会话清理期间重新入队的消息回执。各批回执独立发送，使用进程共享的出站槽位（上限 64）。槽位已满时等待可用容量。

## 留待后续

- **被 hold 的消息。** 程序驱动的会话仍然无法展示它，所以网关会 hold 的消息一律拒收。通过客户端的权限请求来展示它、它在 Web Shell 里呈现为什么交互，以及 #12303 中的问题（离开的会话的 hold、整个主机的上限），是下一步的工作。
- **被一个没有运行的 turn 取走的消息。** 队列在 turn 开始前就把消息取走。turn 在模型看到消息前被取消，或在 token 上限处被截断时，发送方拿到的 `delivered` 不会被更正。（会话拒绝启动的 turn 会把消息放回队列，上面的更正仍能找到它。）交互式终端会话也有同样的缺口。要补上它需要跟踪正在处理中的消息，也就是让 #12403 停下来的那个状态机。
- **重复检查窗口按发送方计算。** 同一发送方在 30 秒内把同样的内容发给同一主机的两个会话，第一个会话收到，第二个会以 `duplicate` 丢弃。要按收件会话区分，接收方和发送方本地的限速器必须一起改。
- **更正之后复用同一个 id。** 网关对该 id 的结算记录仍是 `delivered`，所以发送方在收到 `expired` 更正后用同一个 id 重发，会再次被告知 `delivered`。用新 id 重发不受影响，Qwen Code 会话和 SDK 端点都是这样做的。

## 验证

- 单元测试：`presentsHolds: false` 时，网关拒收会被 hold 的消息，并保留默认的控制器规则和单会话子进程规则。共享 inbox 通过会话目录发布地址。主机按已登记会话的任一名字路由。peer 消息和任务结果各用独立额度，等待中的消息在对话切换和关闭时过期，开始处理时写入对话记录。
- 端到端：同一审查类别的终端会话和 Web Shell 会话互发消息。Web Shell 会话展示收到的消息，并在单独的一轮里回应。来自另一审查类别的会话的消息被拒收，发送方的对话记录会说明这一点。
