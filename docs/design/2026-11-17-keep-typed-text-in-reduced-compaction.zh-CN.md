# 在缩减后的压缩请求中保留用户输入的文字

[English](2026-11-17-keep-typed-text-in-reduced-compaction.md) | [简体中文](2026-11-17-keep-typed-text-in-reduced-compaction.zh-CN.md)

## 问题

压缩请求放不进窗口时，会按[压缩请求准入](2026-10-19-compression-request-admission.zh-CN.md)设计所述被缩减：每个超过 4,000 字的文本片段都被截到前 4,000 字，用户输入的文字也一样。摘要提示词要求模型在涉及意图时引用用户的原话，并列出全部用户消息；于是一条长请求（例如粘贴的需求文档，或者在一段日志之后才写出的指令）到达摘要时，前 4,000 字之后的内容都没有了。

## 改动前的现状

- 缩减分不清哪些是人输入的，哪些是随同一条用户消息附带的内容。不同前端的排列方式不同：CLI 把提问放在前面、附件放在后面，ACP 把附件放在前面、提问放在最后。用户消息里还会带上其他文字：召回的记忆、IDE 上下文、CLI 的通知、任务通知、上一次的摘要和恢复的文件。
- #14953 尝试过按位置判断的规则（第一个附件标题之前的片段算用户输入）。上面列出的大多数情况它都判断错了。
- CLI 各前端在提交一个人的提问时，已经会传入 `humanInput`，即这个人提交的文字，用于工作流关键词检测。Ink 和 OpenTUI 只在人的提问时设置它：斜杠命令、Mod 的提问、shell 模式和 `/btw` 提问都不设置。无界面模式只给以 stream-json 输入发送、来源是人的用户消息设置它；普通的 `-p` 提问不带它。

## 目标

- 在缩减后的请求里保留一个人输入的文字，以摘要额度允许为限：目前单条消息最多约 14,000 字。
- 普通缩减会发送的请求，本地一律不拒绝；在每个字符不超过一个 token 的任何密度下，普通缩减会被接受的请求，不会因为保留的文字而被拒绝。
- 没有标记为用户输入的文字，截法与改动前完全相同。

## 非目标

- 覆盖一个人的文字进入用户消息的所有途径。普通的 `-p` 提问、斜杠命令展开的内容、定时提示、运行中插入的消息、托管模式在一轮运行期间排队的输入，以及托管模式中被钩子改写或追加内容的提问，都不打标记，照旧截断。
- 保留长消息的结尾。额度无法保留的消息，和其他文字一样被截断，保留开头。
- 把较早的轮次压缩成只剩用户消息（#14953）。
- 被拒后的重试和请求体过大的路径，它们仍发送普通缩减。

## 设计

### 标记

保存一个人输入文字的片段带有 `partMetadata['qwen-code:typed-prompt'] = true`，在构造请求的地方设置。`partMetadata` 只在客户端使用：原生通道在 SDK 看到之前删除它（Vertex AI 会拒绝这个字段），OpenAI、Anthropic 和 Responses 转换器从不序列化它。会话文件会保存它，所以恢复后的会话仍带有标记。

有两处检查只在片段只有一个 `text` 键时，才把已完成的本地命令输入从恢复的历史中去掉：历史累加器，以及托管提示账本里的镜像判断。两处都接受元数据只有这一个标记的片段（`isBareTextPart`）。

### 在哪里设置

- **core，用于 CLI 各前端。** `sendMessageStream` 收到带有人的提问的 `humanInput`，且提问不是 Mod 的时，标记请求里的第一个文本片段。这些前端都把人的文字放在最前面。普通的 `-p` 提问不带 `humanInput`，所以不标记。粘贴的文字发送时包在 `<clipboard-paste>` 里，后面再跟一行说明粘贴来源的文字，这个片段整体被标记。
- **ACP。** 在由人写的提问中，由其文本块生成的片段被标记，把这些文字与附件指针拼在一起的指令片段也被标记。只发给模型的提问、运行时的目标续跑、运行中插入的消息、斜杠命令（包括以斜杠开头但不是命令的文字），以及只包含附件的提问，都不标记。
- **托管模式。** 会话用户发送的提问（也就是记忆召回读取的那个输入）原样到达模型时被标记。被钩子改写或追加了内容的提问，或者拼入了召回记忆的提问，不标记。

之后被拼进已标记片段的文字会继承标记：CLI 把 IDE 上下文加在提问片段的开头，并把它的通知拼在提问之前。因此压缩时，把已标记片段开头连续的标签块视为不是用户输入。

### 在缩减后的请求中保留

`slimCompactionInput(history, modalities, { maxTextChars, keepTypedText: true })` 把用户消息中已标记的片段最多保留 `TYPED_TEXT_MAX_CHARS`（32,000 字）。片段开头连续的标签块和其他文字一样截到 `maxTextChars`，截断落在哪个标签块里，就重新补上它的结束标签。用户文字超过 32,000 字时在该处截断，规则与其他被截断的文字相同。其余片段照旧截断。下文的额度规则让保留的文字目前远低于这个上限，最多约 14,000 字，所以只有额度变大时这个上限才会起作用。

### 何时发送保留版请求

只在第一次发送、并且普通缩减已让请求变小之后。保留版申请的总量不超过普通缩减：输入多出它保留的字数，每个字符按一个完整 token 计算，输出预算相应减少同样的数量。只有当这个预算仍不少于普通请求预算的一半、并且不低于摘要的最低空间时，才用它替换普通缩减。服务端拒绝它时，唯一的一次重试发送普通缩减。请求体过大的路径永远不会发送它：那条路径的输入一开始就是普通截法。

## 决策与理由

- **在源头打标记，只保留有标记的文字。** 没有标记的文字退回普通截法，所以漏掉某个来源只会失去改进，不会出错。按位置判断的规则错在相反的方向：它保留了不是用户输入的文字。
- **在 core 中用 `humanInput` 作为判断条件。** 前端已经判断过哪些发送是人的提问，而且一处就能覆盖三个前端。
- **标记第一个文本片段，而不是要求与 `humanInput` 完全相同。** CLI 在发送前会给粘贴内容加框，并把通知拼进提问，完全相同的要求在最主要的情况，即带粘贴内容的请求上会失败。
- **每个字符按一个 token 计算，并且不超过普通请求的总量。** 估算按四个字符一个 token 计算，而中日韩文字实际密得多。把每个保留的字符算作一个 token，并从输出预算中扣除，就能保证：服务端会接受普通形式的请求时，在每个字符不超过一个 token 的任何密度下，也会接受保留了文字的请求。代价是保留文字较多时，输出预算变小。
- **最多占用摘要预算的一半。** 保留的文字从输出预算里拿走的每个 token，都是长摘要可能需要的空间；摘要超过保留版的预算时会被当作截断而丢弃，而普通请求本来放得下，并且这次丢弃会计入失败熔断。保证至少留下普通预算的一半，就给这个代价设了上限。
- **只保留开头。** 超过上限、或额度无法保留的消息，都只保留开头。从中间省略会产生新的截断形态，而被截断文字的补闭合规则从未在这些形态上验证过。

## 风险

- 有些字符（例如生僻的中日韩文字和表情符号）占用不止一个 token。超过每字符一个 token 时这个保证不成立；服务端拒绝保留版请求时，会用普通缩减重试。
- 摘要的输出预算会减少保留的字数，最多减少一半。超过这个预算、而普通请求本来放得下的摘要，会被当作截断而丢弃。
- 普通请求的预算是 20,000 token 上限时，比普通截法多保留 10,000 字以上就会占用超过一半，所以长于约 14,000 字的请求照旧截断。窗口更紧时这个界限更低。
- 服务端拒绝保留版时，会用普通截法重试。如果普通请求本来也会被拒绝，两条流程在这里会不同：普通流程用更小的预算重试或放弃，保留版流程则发送一次普通截法。
- 已标记片段中开头标签块之后的文字，会被整体当作用户输入保留。在 CLI 中这包括粘贴说明文字，以及被 `UserPromptSubmit` 钩子改写过的提问，因为 `humanInput` 会随改写而变。
- 本次改动之前记录的会话没有标记，照旧截断。
- 本次改动没有衡量保留这些文字是否改善任务结果。

## 验证

- 标记的单元测试：它的形状；它不出现在原生、OpenAI 兼容、Anthropic 和 Responses 通道的请求中；它能经过会话文件保存下来；以及两处本地命令检查。
- 每个设置位置的单元测试，包括所有排除情况：没有 `humanInput`、内部发送类型、Mod 的提问、并发辅助请求、第一个文本片段为空；ACP 中只发给模型的提问、运行时的目标续跑和只含附件的提问；托管模式中不是新用户输入、被改写或追加、拼入记忆的提问。
- `keepTypedText` 的单元测试：开头的标签块、连续的多个标签块、用户自己输入的孤立开始标签、32,000 字上限，以及上限截断落在块内部的情况。
- 服务测试：输出预算恰好减少保留的字数；恰好留下普通预算一半时使用保留版，多一个字就不用；保留版会让摘要低于最低空间时、被拒后的重试和请求体过大的路径都发送普通截法；按估算 2.4 倍计费的中文文字能被保留且不被拒绝；以及一组扫描，覆盖 5 种会话形态、6 种请求长度、英文或中文文字：凡是普通请求一次就被接受的，保留版也一次就被接受。
- 每个判断条件都有一个变异，并确认它会让对应测试失败，共 20 个。
- 在模拟后端上做了请求层面的对比：5 种会话形态，请求长度 3,000 到 40,000 字，每条请求中均匀放入 5 句话。在 6,000、9,000 和 12,000 字时，到达摘要请求的句子数从 25 句中的 15、10、10 句，提高到 23、19、16 句，英文和中文结果相同。3,000 字时不会截断；从 18,000 字起不使用保留版。

## 验收标准

- 只要按上述规则摘要仍能保有一半额度和最低输出空间，缩减后的请求就把已标记的请求整条保留：额度为 20,000 token 上限时，单条消息最多约 14,000 字。否则照旧截断。
- 没有标记的轮次，截法与改动前完全相同。
- 没有新增的本地拒绝；在每个字符不超过一个 token 的密度下，没有因保留文字导致的拒绝。

## 后续工作

- 为其余来源打标记：普通的 `-p` 提问；斜杠命令展开的内容（其中注入的文件和 shell 输出保持不标记）、运行中插入的消息、托管模式在一轮运行期间排队的输入。
- 对长消息在预算允许的范围内尽量多保留，而不是全保留或全不保留。
- 除了开头，也保留长消息的结尾。
- 截断不够时，把较早的轮次压缩成只剩用户消息（#14953）。
