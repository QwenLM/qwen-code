# 按轮固定 Skill 与扩展修订

[English](turn-scoped-resource-revisions.md) | [简体中文](turn-scoped-resource-revisions.zh-CN.md)

**设计与实现评审草案。** 本文描述目标契约。同一 PR 已实现可选的 Skill 文件快照、受管套件安装目录的读保护、按套件制品区分 MCP 连接，以及原生会话空闲退役。[Serve 协议](../developers/qwen-serve-protocol.md)和[可执行回归](../../integration-tests/cli/qwen-serve-turn-resources.test.ts)说明当前覆盖范围。受管 Skill 自身声明的会话级授权或 Hook 仍需单独支持。两个不兼容的完整套件并行执行时需要独立安装目录。

讨论见 [#18178](https://github.com/QwenLM/qwen-code/issues/18178)。

## 问题与范围

一个长轮次发现 Skill 或扩展后，可能在读取脚本或调用工具前等待审批。如果后续发布在等待期间覆盖了安装目录，旧轮次可能执行来自不同修订的指令或可执行资源。事件流关闭时，审批或工具调用可能仍在进行。运营方也需要在旧轮次等待期间启动使用新版的新轮次。

拟保护的范围是每轮使用的 Qwen 托管 Skill 和扩展资源，包括 Skill 正文和配套脚本、指令片段、工具与命令定义、Hook、子 Agent，以及能够隔离的 MCP 客户端或进程。用户工作区文件、模型和远端服务状态沿用现有语义。固定修订不会固定授权或凭据。审批和工具派发仍按当时的信任、权限和凭据规则执行。

## 当前行为

[扩展存储](../../packages/core/src/extension/extension-store.ts)与[存储路径](../../packages/core/src/extension/storage.ts)在用户存储下维护已安装扩展。工作区启用状态与[扩展刷新](../../packages/cli/src/serve/routes/workspace-extensions-controller.ts)管理资源发现并更新会话状态。工作区边界和等待已有操作完成的机制能协助协调，但同一安装的两个修订仍共用存储。

[Skill 刷新](../../packages/core/src/tools/skill.ts)已支持在发现变更后使过期正文失效，并保留历史用量统计，参见 [#12182](https://github.com/QwenLM/qwen-code/pull/12182)。[#12147](https://github.com/QwenLM/qwen-code/issues/12147) 讨论由部署系统管理的扩展目录，也是互补能力。把完整资源视图绑定到已准入轮次、让新旧修订在同一执行域并行，仍需单独设计。

## 拟议生命周期

1. **准备不可变修订。** 在调用方有权访问的执行域内解析清单。每个托管条目记录来源、稳定身份、实际修订和内容摘要，并包含生效的启用和工具配置。在实时发现路径之外暂存已验证的制品，构建对应的资源视图。内容摘要用于核对资源身份。访问仍取决于工作区、归属的运行时和可信调用方。准备失败或中断时，当前修订可以继续使用。
2. **发布活动指针。** 在执行域内，将准备并验证完成的修订原子发布为后续准入的默认值。更新时检查预期的旧指针与运行时代次，避免迟到的发布者在新版生效后重新激活旧候选。已在发布前领取引用的请求继续使用原修订。发布保留已有历史和审批。
3. **由原生准入领取引用并返回回执。** 准入成功时，轮次先持有资源引用，再进入队列。需要指定修订的认证调用方可以携带内部的预期修订，仍须经过独立的能力和授权检查。其他请求在准入时读取原生默认指针。队列插入和引用领取必须与取消、发布和回收有统一顺序。准入失败时释放引用。引用随队列记录经桥接层传给执行者。轮次真正开始时仍使用该引用，即使默认指针已经更新。
4. **执行并释放。** 执行者通过已固定的视图解析托管资源，包括稍后读文件以及审批恢复后的回调。仍归当前轮次的中途消息沿用该视图。提升为独立轮次的消息需要经准入领取引用。当前上下文中的 Skill 去重按实际资源身份进行，历史中已出现的正文继续计入用量。修订变化时重建生效的托管指令。轮次结果明确，且已跟踪的原生任务、工具回调和取消转发均收尾后，才释放引用。事件流关闭、客户端超时或发出终态事件本身都不足以证明可以释放。
5. **安全回收。** 保留默认指针、已授权的暂存引用、排队和执行中的轮次、未结束的审批及工具，以及受支持的恢复引用。只回收没有可达引用的代次，回收与发布、准入遵循同一顺序。限制磁盘用量、保留修订数和子进程数。达到上限时先回收无引用资源，其次以可重试的容量结果拒绝新的准备任务。已有轮次继续使用原资源。暂存或保留修订不会授予使用权限。

[Serve 准入辅助模块](../../packages/cli/src/serve/routes/session-prompt-admission.ts)与 [ACP 桥接控制面](../../packages/acp-bridge/src/session-control-plane.ts)分别负责准入和执行的不同环节。保留桥接层的有序队列及拒绝语义。在原生队列入口携带资源引用，避免工作线程开始时重新发现可变资源。核对 HTTP、进程内入口、渠道投递、提升的消息和旁路任务生命周期。[运行时活动门禁](../../packages/cli/src/serve/conversations/conversation-runtime-activity.ts)可以协调排空。轮次引用的生命周期须与实际原生任务一致。

## 回执、兼容与恢复

当前准入辅助模块在内存里维护从幂等键到 Prompt 的映射，其保护的队列也在内存里。进程重启或映射淘汰后，不能从该映射推断已有持久回执。

对于需要在进程崩溃后对账的调用方，后续协议可以关联已授权的操作 ID、请求身份、会话和运行时代次、资源修订及结果。完全匹配的重试可读取原回执。同一 ID 绑定不同请求或预期修订时应报告冲突。明确区分确认未准入与结果未知。进程崩溃后查不到回执，并不足以证明可重发有工具调用的轮次。跨重启自动重放需要持久化、具备代次保护的准入与恢复契约。第一阶段在进程内实现隔离即可保留结果未知状态，且不跨重启重放。

保留现有请求和返回协议的兼容性。预期修订和回执查询等扩展能力由运行时能力协商启用。不支持隔离的 Hook、进程环境、共享端口或 MCP 传输不能当作已隔离。只有资源能独立使用时才并行运行两个修订。其他情况下保留旧视图并等待安全排空，要求独立运行时，或返回能力错误。用户文件和任意 Shell 命令仍可在本契约之外发生变化。复制资源本身不构成宿主机文件系统隔离。扩展归档也不会固定 PATH 上的 CLI、Python 环境或其他进程级依赖。要将这些依赖纳入轮内保证，需要不可变的可执行路径或独立环境。可选工具在首次使用时检查能力，能力缺失仅影响该工具调用。

## 交付与验收

1. 增加显式启用的不可变资源视图，先覆盖独立 Skill 和它的托管配套文件。原生准入和执行者持有同一视图。保留存量客户端行为、权限、事件格式和历史用量统计。用确定性夹具覆盖正常执行、队列拒绝、执行前取消、延后审批和回收竞争。
2. 扩展到套件提供的组件。逐类验证发现、脚本读取、注册、子进程和断连行为都使用已固定的视图，再启用该类别。可跨重启恢复执行的能力等持久回执与恢复模型评审后再扩展。
3. 执行端到端夹具。轮次 A 选择修订 1，在即将打开托管脚本时进入待审批状态。发布修订 2，另起一个会话，在同一 serve 运行时上让轮次 B 使用修订 2 跑通。随后批准 A，核对实际脚本输出仍来自修订 1。A 会话的下一轮应使用修订 2。另测排队中的旧轮次、准入被拒或被取消、回执丢失、发布失败和回收与准入竞争。以内容摘要和工具实际输出验收。对包含 MCP 的扩展，用能报告自身修订的夹具服务，断言 A 和 B 分别访问各自的服务。仅看版本标签不足以确认。
