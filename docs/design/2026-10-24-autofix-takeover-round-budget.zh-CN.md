# Autofix 托管的轮次预算

[English](2026-10-24-autofix-takeover-round-budget.md) | [简体中文](2026-10-24-autofix-takeover-round-budget.zh-CN.md)

状态：本次改动中实现，2026-10-24。

## 问题陈述

`autofix/takeover` 标签才是把人工提交的 PR 交给 autofix 循环的入口 —— 既可由 `@qwen-code /takeover` 打上，也可手工贴；手工贴标签时扫描同样会发首次接管的 ack。它刻意是常驻的：把轮次上限从 10 抬到 100，之后每十分钟一次的扫描持续管理该 PR，直到标签被移除或熔断器触发。

维护者经常要的其实是更窄的一件事 —— "看一遍这批反馈，修掉，然后别再动这个 PR" —— 而现在只能用常驻机制去表达：

- `@qwen-code /takeover from 99` 把整个上限在一轮**产出改动**的轮次里花掉，下一次扫描就把 PR 暂停。此时计数早已越过 `CRITICAL_ONLY_AFTER_ROUND`，那一轮是 Critical-only、Suggestions 只记录不修；暂停还会打上 `autofix/needs-human` 并发"已达到轮次上限"的通知，读起来像故障，而不是一次正常结束的有界托管。而 no-op 轮次不会推进计数，所以在"每轮都没发现要改"的 PR 上，这个绕法根本约束不住任何东西。
- 裸 `/takeover` 再加 `/takeover stop` 可以得到完整范围的一轮，但需要人盯着运行并记得收手。忘了就要付最多 100 轮的代价。

两种绕法都说不出真实意图，而且都只能约束"一轮"。

## 拟议改动

在现有命令上增加一种参数化形式：

```
@qwen-code /takeover for N
```

`N` 是一位或两位十进制整数且 `>= 1`。它的接管语义与裸命令完全一致，只是在 engage / re-arm 的 ack 上额外记录一个**按"托管代"作用域的轮次预算 N**：

```
<!-- takeover-ack engaged -->
<!-- autofix-round-budget 3 -->
```

该窗口的有效轮次上限变为 `min(接管上限, N)`，于是循环最多跑 N 轮，之后不再触碰该 PR。预算与已耗尝试都按**托管代**读取 —— 维护者命令开启一代，自动的增长审计 re-arm 不开启 —— 因此审计照常换基其轮次窗口，而剩余额度继续生效。手工贴标签同样开启一代，且它不带预算：这是 `for N` 无法约束的唯一入口。

## 关键设计决策

1. **预算计的是"尝试次数"，而尝试次数数的是 eval 标记。** no-op 轮次也必须消耗一次，否则"每轮都没发现要改"的 PR 会在只给一轮预算时被永远托管下去。no-op 写的是 `<!-- autofix-eval … round=ROUND -->`，轮次号不变，所以只看 `ROUND` 会漏计；数标记则恰好计一次。同一个选择也修掉了相反方向的错误：熔断器在真实尝试远少于上限时，用 `round=MAX_ROUNDS` 写下终止标记，而哨兵跳变不产生新标记 —— 二十轮预算里的五次失败因此读作五次尝试，熔断器要求的升级得以保留，不会被误判为预算耗尽。

2. **预算按"托管代"作用域，并寄存在 ack 上。** 它作为独立标记挂在锚定这一代的评论上，并从该锚点及其之后的每一条 ack / re-arm 读回 —— 即扫描侧的 `BUDGET_FLOOR` 谓词：一条 `takeover-ack engaged`、一条 `takeover-ack released`（它关闭托管代，因此显式 `stop` 会结束预算），或一条**不带** `autofix-eval ` 标记的 `autofix-rearm`。那个排除正是全部要点：它把维护者的命令与自动的增长审计 re-arm（其评论带该轮的 eval 标记）区分开。轮次记账（`autofix-round-start`）仍是窗口级的 —— 与 ack 评论的 `created_at` 相等 —— 所以两种读取刻意不是同一形状；把预算读取合流成窗口键相等，会在每次自动 re-arm 时静默丢掉预算与消耗计数。

3. **耗尽时释放，而不是升级。** `autofix/needs-human` 的语义是"循环停了，必须由人解锁"；预算正常用完没有留下任何卡点，标签与暂停通知都会是假话。释放就是一次标签 DELETE，PR 自己离开托管池。强制 dispatch 同样不能释放：它必须出声回应本次调度，因此先暂停，由下一趟非强制扫描释放。所以那次释放也要删掉升级标签 —— 通知否认有任何事情在等人，它自己推迟时打上的标签就不能活过这条通知 —— 而被推迟那一趟的通知引用尝试数，而不是 no-op 永不推进的轮次计数。

4. **bot 提交的 PR 保留暂停路径。** 它们有没有标签都受管，移除标签等于交回标准十轮管理，预算就变成了谎话。只有这一类 PR 上，"暂停待人工"才是准确的结论。

5. **`for` 与 `from` 互斥。** 两者都是单一参数化形式但含义不同（Suggestions 预算 vs 轮次预算）；同时携带、`for 0`、三位数、任何尾随文本都保持"不是精确命令"并什么都不做。

6. **有预算的新窗口连排队中的 conflict 轮次也作废。** conflict 通常豁免于"窗口被取代"的丢弃，因为它始终可处理。预算不同：排队的作业带着旧上限，会越过新的托管上限继续跑，因此"带预算的当前窗口"也会丢弃它，下一次扫描按新窗口重新选中该 conflict。

7. **自动 re-arm 照常换基增长窗口，预算随之延续。** growth audit 追加 `<!-- autofix-rearm -->` 为自身记账开新窗口；抑制它会恰好在第一次超预算的轮次之后把增长基线钉死，之后每轮都变成 Critical-only —— 所以它保持无条件。但它并不是唯一会重锚增长基线的东西：base 分支更新（`autofix-base-updated`，它把更早的 `autofix-growth-base` 标记从基线读取中滤掉）以及扫描侧的首次接管补发 ack 同样会移动它。让预算保持诚实的不是 re-arm 的排他性，而是它的键：预算与花费按"托管代"读取，而非按窗口 —— 维护者命令开启一代，自动 re-arm（其评论同时带该轮的 eval 标记）不开启，于是审计照常换基，而剩余额度与此前已耗次数继续生效。

8. **prepare 复刻扫描的尝试计数。** 排队中的轮次可能比"花掉本窗口最后一次尝试"的兄弟活得更久：no-op 让 `ROUND` 停在 0、窗口键也没变，所以"窗口被取代"检查与轮次上限都拦不住它。`review-address` 因此自己重数本窗口的 eval 标记，预算已耗尽就丢弃。

## 范围边界

- 不改轮次上限、失败/收敛熔断器、Critical-only 刹车或增长预算。fleet shepherd 只动一处——其恢复探测认识两种参数化命令——释放策略不变。
- 不新增标签。人工 PR 上预算耗尽刻意不**留下** `autofix/needs-human`：被推迟的释放会清掉它自己那次暂停打上的标签。
- 不改准入：同样的作者/write+ 门禁、fork 规则与 `autofix/skip` 优先级都适用于 `for N`。

## 风险与限制

- 被取消或在 setup 阶段就失败的运行**仍会**消耗一次尝试：报告步骤挂在 `always()` 上，因此它会走到"既非成功也非失败"的分支，写下一个带哨兵时间戳、轮次 +1 的 eval 标记。只有在那一步收尾之前就被杀掉的运行才是免费的。所以误差方向是**提前**释放而非延后，替代方案（只由收尾步骤递增的专用计数器）也改不了这一点。
- "预算已用完"通知先于 DELETE 发布，并按窗口去重：DELETE 失败时，下一次扫描只重试 DELETE。
- 释放通知必须先落地、标签才能消失：通知失败就保留标签，下一次扫描两者都重试 —— 因为标签一旦消失，该 PR 不在任何选择池中，再也不会有谁去重发那条通知。
- 预算低于 `CRITICAL_ONLY_AFTER_ROUND` 时，每一轮都保留 Suggestions 通道。这是有意的：预算要缩短的是托管时长，不是范围。
- 预算在 `autofix/takeover` 存在时生效；对**已耗尽**预算的 bot 作者 PR，它还一直生效到一条 `takeover-ack released` 标记把托管代下限推后为止。所以显式 `stop` 能结束它；而 shepherd 的静默自动释放（以及同样不留标记的手工摘除）不会——该 PR 就停在 N/N 并挂着 `autofix/needs-human`，直到新的命令推后下限。未耗尽的预算则随标签一起结束，这正是 `stop` 能把预算中途被暂停的 bot PR 解出来的原因。
- 预算寄存在 engage ack 上，ack 发不出去就等于丢了预算、退化成无上限托管。这不是新增的失败模式，而是 seed 标记本来就有暴露：命令 job 会重试一次并大声告警。扫描侧的补发 ack 有两种触发 —— 完全没有 ack，或出现晚于上一条 ack 的标签事件 —— 两者都不带预算，因此手工重新贴标签会重锚窗口并静默丢掉剩余额度。手工贴标签本来就不带预算：真正让 PR 进入托管的是标签，而不是命令。要在别处持久化这个数字，就得为"标签本身已经可见"的情形再加一个写入方。

## 验证

- 对每一种接受与拒绝的评论体做解析回放。
- ack 回放，钉住全新 engage 与 re-arm 两条路径上的标记。
- 上限读取回放，证明预算会压低有效上限、跨自动 re-arm 携带它的是托管代下限（而不是窗口键），且计数会排除 `win=none` 的标记。
- cap 分支回放，证明释放路径只发一条通知、删除标签，且从不**打上** `autofix/needs-human` —— 同时覆盖被推迟（强制 dispatch）的那一趟：它暂停、通知里引用尝试数，并由随后的释放清掉升级标签，404 也算通过。
- 无法在本地端到端验证：该命令只在上游仓库用 bot PAT 运行时才真正生效。测试是逐字回放 workflow 里的 shell 片段，因此一旦漂移就会失败。
