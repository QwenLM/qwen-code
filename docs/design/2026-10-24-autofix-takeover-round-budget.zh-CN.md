# Autofix 托管的轮次预算

[English](2026-10-24-autofix-takeover-round-budget.md) | [简体中文](2026-10-24-autofix-takeover-round-budget.zh-CN.md)

状态：本次改动中实现，2026-10-24。

## 问题陈述

`@qwen-code /takeover` 是把人工提交的 PR 交给 autofix 循环的唯一入口，而它刻意是常驻的：打上 `autofix/takeover` 标签、把轮次上限从 10 抬到 100，之后每十分钟一次的扫描持续管理该 PR，直到标签被移除或熔断器触发。

维护者经常要的其实是更窄的一件事 —— "看一遍这批反馈，修掉，然后别再动这个 PR" —— 而现在只能用常驻机制去表达：

- `@qwen-code /takeover from 99` 把整个上限在一轮里花掉，下一次扫描就把 PR 暂停。此时计数早已越过 `CRITICAL_ONLY_AFTER_ROUND`，那一轮是 Critical-only、Suggestions 只记录不修；暂停还会打上 `autofix/needs-human` 并发"已达到轮次上限"的通知，读起来像故障，而不是一次正常结束的有界托管。
- 裸 `/takeover` 再加 `/takeover stop` 可以得到完整范围的一轮，但需要人盯着运行并记得收手。忘了就要付最多 100 轮的代价。

两种绕法都说不出真实意图，而且都只能约束"一轮"。

## 拟议改动

在现有命令上增加一种参数化形式：

```
@qwen-code /takeover for N
```

`N` 是一位或两位十进制整数且 `>= 1`。它的接管语义与裸命令完全一致，只是在 engage / re-arm 的 ack 上额外记录一个**窗口级轮次预算 N**：

```
<!-- takeover-ack engaged -->
<!-- autofix-round-budget 3 -->
```

该窗口的有效轮次上限变为 `min(接管上限, N)`，于是循环最多跑 N 轮，之后不再触碰该 PR。

## 边界处的行为

| 状态                                         | 结果                                                                                                                 |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 人工提交的 PR 预算耗尽                       | 发一条中英双语"预算已用完 —— 已释放"通知，随后移除 `autofix/takeover`。不打 `autofix/needs-human`，也不发暂停通知。  |
| bot 提交的 PR 预算耗尽                       | 不移除标签（bot PR 无标签也受管），因此走既有的暂停路径：暂停通知 + `autofix/needs-human`。预算同样把它限制在 N 轮。 |
| 预算窗口结束后执行 `/retry` 或裸 `/takeover` | 开启无预算的新窗口 —— 即今天的无上限托管。                                                                           |
| 窗口被取代时仍有排队中的轮次                 | 既有的窗口键检查会丢弃排队作业；新窗口的预算生效。                                                                   |

## 关键设计决策

1. **预算计的是"发起的轮次"，不是"产出改动的轮次"。** 报错、超时、崩溃的轮次必须消耗预算，否则一个持续失败的 PR 会被一路重试到失败子上限触发 —— 与"只处理一次"正相反。失败轮本来就会写 `<!-- autofix-eval … round=ROUND+1 -->`（ts 用哨兵值），所以既有的 `ROUND` 已经是"发起次数"，不需要新的计数器写入方。

2. **预算通过 ack 做窗口级作用域。** 它作为独立标记挂在"`created_at` 即窗口键"的评论上，与 `autofix-round-start` 完全同一套读写。被取代窗口的预算不会泄漏到下一个窗口，重新武装天然重置。

3. **耗尽时释放，而不是升级。** `autofix/needs-human` 的语义是"循环停了，必须由人解锁"；预算正常用完没有留下任何卡点，标签与暂停通知都会是假话。释放就是一次标签 DELETE，PR 自己离开托管池。

4. **bot 提交的 PR 保留暂停路径。** 它们有没有标签都受管，移除标签等于交回标准十轮管理，预算就变成了谎话。只有这一类 PR 上，"暂停待人工"才是准确的结论。

5. **`for` 与 `from` 互斥。** 两者都是单一参数化形式但含义不同（Suggestions 预算 vs 轮次预算）；同时携带、`for 0`、三位数、任何尾随文本都保持"不是精确命令"并什么都不做。

## 范围边界

- 不改轮次上限、失败/收敛熔断器、Critical-only 刹车、增长预算或 fleet shepherd。
- 不新增标签。人工 PR 上预算耗尽刻意不使用 `autofix/needs-human`。
- 不改准入：同样的作者/write+ 门禁、fork 规则与 `autofix/skip` 优先级都适用于 `for N`。

## 风险与限制

- 在 prepare 之前就被取消的运行不会写标记，那一轮因此免费。误差方向是"释放延后"，从不提前；替代方案（在 always() 收尾里写专用计数器）为一个边界情况换来大得多的改动面。
- "预算已用完"通知先于 DELETE 发布，并按窗口去重：DELETE 失败时，下一次扫描只重试 DELETE。
- 预算低于 `CRITICAL_ONLY_AFTER_ROUND` 时，每一轮都保留 Suggestions 通道。这是有意的：预算要缩短的是托管时长，不是范围。
- 预算寄存在 engage ack 上，ack 发不出去就等于丢了预算、退化成无上限托管。这不是新增的失败模式，而是 seed 标记本来就有暴露：命令 job 会重试一次并大声告警，扫描侧的补发 ack（仅在没有任何 ack 时发）不带预算，因此维护者看到的 ack 里不会有那句预算说明。要在别处持久化这个数字，就得为"标签本身已经可见"的情形再加一个写入方。

## 验证

- 对每一种接受与拒绝的评论体做解析回放。
- ack 回放，钉住全新 engage 与 re-arm 两条路径上的标记。
- 上限读取回放，证明预算会压低有效上限，且被取代窗口的预算被忽略。
- cap 分支回放，证明释放路径只发一条通知、删除标签，且从不打 `autofix/needs-human`。
- 无法在本地端到端验证：该命令只在上游仓库用 bot PAT 运行时才真正生效。测试是逐字回放 workflow 里的 shell 片段，因此一旦漂移就会失败。
