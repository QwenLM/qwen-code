# K2 physical completion and retained release receipts

Status: private progress implementation candidate. Same-Connection DRAINED validation, immutable plans, stop intent, persisted normal DELETE attempts and observed source prefixes are implemented. The sealed `1169bfd7` candidate passed independent real Hosted/application-to-physical SQL acceptance, complete coordinator windows and narrow private Main plan/status/replay. Its node source and Kubernetes services were explicit protocol/API fixtures. That acceptance applies only to its exact candidate and cannot qualify later Pod-construction changes or ACK deployment. ## Problem and supported boundary

Application DRAINED closes the original file handles and releases the logical Runtime Session. The container may still exist and kubelet may still hold the original CSI publication. Reusing the physical volume requires the continuous original task/cgroup and publication/unpublication evidence, followed by one atomic ownership change. API acceptance, NotFound, a successful empty-target retry and a holder phase alone cannot establish that result.

Support the reviewed single isolated node and fresh Session/request/slot/binding for each owner. Keep the original immutable DRAINING intent, application DRAINED receipt and PUBLISHED association. Runtime generation 1 and native epoch 1 remain distinct from the shared holder revision. Do not enable normal Spring or public selection before the complete qualification and reuse acceptance.

## Original DRAINED authority

The physical store obtains a package-private validated result from the application store on the same transaction-bound Connection. The result is privately constructed only after the original lock prefix, Session credential, binding/boot, typed application inventory, saved freeze/cut/finalize bytes and actual finalize response all match. A bare broker application Authority or a DRAINED column is insufficient.

The operation owns a ten-second transaction and rejects ambient composition. Preserve placement → retention → sorted original slots/bindings → private Session/pin/context → alias/physical holder → immutable retirement/progress → native head/history/resources/refs → original Runtime Session/sorted executions → explicit secondary/source/physical catalog. Recheck database time after lock waits. Source, Kubernetes, worker and protection RPCs remain outside SQL locks. Physical and historical reads do not renew the original writer or reuse the five-minute application settlement deadline.

## Immutable plan and explicit physical catalog

V74 adds a dedicated six-column physical record: retirement_id, binding_id, physical_key, record_version, record_bytes and record_sha256. Its current closed JSON format is `qwen-csi-physical-progress/1`, with exactly format, retirementId, bindingId, physicalKey, stage, planBase64, planSha256, intent, attempts and observations. Stages are PLANNED, INTENT, STOPPED and UNPUBLISHED. There is no qualification or RELEASED field in this version. Each payload pair is either wholly absent or wholly present. Every original field and every earlier attempt remains immutable, apart from filling one previously unknown reply once.

The record is bounded to 16 MiB, its plan to 64 KiB, each journal prefix and HTTP reply to 1 MiB, attempts to eight and observations to two. A checked version starts at one and counts each saved intent, attempt, actual reply and stage observation. Repeating the same Pod resourceVersion returns the saved attempt without resending, including when its outcome is unknown or rejected. An actual STOPPED source may still require normal Pod deletion before CSI unpublication.

The plan derives from the verified original request, binding, registration/reservation, saved handle/boot, application baseline/freeze/cut/finalizer and exact nineteen-column PUBLISHED source association. It pins source identity/incarnation, node, ARM/BOUND/publication prefixes, Pod UID, original image/container, target and all dependency cursors. Revisions are decimal strings. The exact serialized source configuration is Base64, preserving unsigned kernel start values without conversion through floating point or signed long; the original strict configuration decoder validates the recovered bytes.

The current nested plan is `qwen-csi-physical-plan/3`. Its `ownershipReleaseInventorySha256` pins the exact expected application inventory after the three ownership-row changes below. The projection starts from the privately validated DRAINED inventory, checks the original binding/slot/holder correlation and checked counters, and preserves all other rows, fields, keys and membership. It performs no SQL writes and grants no physical permission. The fourth row, the physical progress record and final receipt, requires qualified evidence and has no precomputed outcome. Saved version-one and version-two plans are refused by this candidate; finish them with their original binary rather than changing their bytes, hash or stop-intent dependency.

The plan also pins `historicalReleaseInventorySha256`, a deterministic declared original read-set image derived from that projected ownership result. It preserves complete ORIGINAL rows except the shared physical holder and excludes OTHER rows and unrelated context. Required original tenant placement/retention identities and original workspace generation/storage/config/policy/state remain pinned; workspace display name is outside this read set. Context column masks are fixed in code, represented canonically and cannot be chosen by a caller. The projection retains catalog schemas, typed keys and every original cell, including the empty original request slot and released binding. This is the expected-image prerequisite for the historical reader, not a SQL reader, release receipt or physical capability.

Readback requires the saved plan bytes to equal the exact encoding of the verified expected plan, in addition to matching their saved hash. Equivalent JSON values with changed whitespace, field order or escaping refuse; they must not establish a new plan hash or stop-intent dependency on retry.

The physical table has a separate explicit typed catalog and validator, read on the same Connection after the application closure. The application catalog remains 62 tables and 847 columns. Before DRAINED, the companion must have its exact six-column schema and no matching retirement, binding or physical-key row. After the complete DRAINED image is verified, any companion row must match the original plan and exact stored bytes/hash/version; foreign or duplicate rows and schema drift refuse progress. Its current expected image permits only the declared insert, append or one pending-outcome replacement. No positive state is backfilled into a deployed database. The old worker-ACK table is unsupported in this lane and does not supply physical qualification. Qualified release requires a separately implemented format and validator.

## Stop intent and exact normal DELETE

Commit the immutable plan before requesting STOP_INTENT from the fixed authenticated original source. After the RPC, reacquire the common prefix and save the exact prefix/head extending the original publication, with original retirement ID and plan hash. A lost reply can reconcile only that unchanged original stream. Changing ARM, source incarnation or plan cannot repair an unknown result.

Outside SQL, read the exact original Pod and corroborate node/protection/source pins. Persist each DELETE attempt before sending it: ordinal, namespace/name, canonical original UID, the newly observed opaque resourceVersion and exact request bytes/hash. Only gracePeriodSeconds=30, propagationPolicy=Background and both UID/RV preconditions are supported. A replacement UID or missing Pod retains ownership.

The Kubernetes client must expose the prepared immutable request and preserve the actual bounded HTTP status and raw response bytes. Sending must use the same prepared bytes saved by the coordinator. HTTP 200/202 mean request acceptance only. Preserve 404, 409, redirects and other rejection outcomes without treating them as completion. Transport loss, timeout, truncated/oversized body or a crash between send and outcome persistence leaves an ambiguous attempt. A later RV creates another attempt; it never replaces the old request or manufactures its reply. Generic GET/CREATE/PATCH error behavior stays unchanged.

The private command is `physical <status|plan|intent|delete|observe> <reviewed-runtime-json> <reviewed-node-json> <retirement>`. It selects the original tenant/Session/request/binding, uses the retained original writer credential and fixed source configuration, and closes owned HTTP clients. Status and plan access only SQL and return before loading Kubernetes/source client credentials. Plan matches the reviewed node with the original stored association inside its transaction, before inserting or changing any physical record. Before external intent, DELETE or observation operations, the coordinator corroborates the original node UID/boot/Ready condition and protected volume outside SQL. There is no release action, Spring route or Hosted public selector. An already saved intent or final UNPUBLISHED state can return its durable progress without another mutating source or DELETE request.

## Atomic release and monotonic counters

The final same-Connection transaction validates the complete original application/physical image and qualification, then changes exactly four rows:

| Row                            | Sole permitted change                                                       |
| ------------------------------ | --------------------------------------------------------------------------- |
| Original physical record       | RELEASED, checked version+1, immutable final receipt bytes/hash             |
| Original runtime binding       | binding_state=RELEASED and checked record_version+1                         |
| Original request-specific slot | active_binding_id=NULL; preserve last_generation                            |
| Original physical holder       | csi_phase=RELEASED, checked csi_revision+1; clear only six CSI owner fields |

The six fields are csi_reservation_id, csi_registration_key, csi_registration_revision, binding_id, runtime_generation and csi_provision_request_id. Preserve all other bytes, including original seed/handle/lease, binding timestamps and stop/loss/drain evidence, slot identity, holder maintenance/protection and immutable intent/application/source rows. Runtime Session was already released by application completion and is not a fifth write. Every CAS must affect one row; overflow, timeout, unexpected image or any zero-row CAS rolls back all four changes. Do not loosen generic sealed-binding CAS. A narrow private physical capability must be minted only by the full actual validator before the terminal binding/slot write.

Shared holder transitions use RELEASED%3=0, RESERVED%3=1, DRAINING%3=2 and MAX=9007199254740990. Use the actual stored revision and checked increments throughout subsequent cycles.

The current candidate admits only the initial ownership cycle, revisions 0 through 2. An independent store-only H2 fault test reproduced the previous gap: a manually injected RELEASED revision 3, with all retirement/physical proof tables empty, became RESERVED revision 4. Later-cycle holder reads now refuse before reservation, replay or alias registration can write. Counter arithmetic remains generalized, but a nonzero released counter cannot stand in for a qualified historical outcome. Replace this temporary gate only together with the complete historical validator and qualified release writer; it does not implement successful reuse.

## Historical receipt and the next owner

The first historical SQL component reuses the production native journal
grammar on an explicitly read-only REPEATABLE_READ connection. It obtains
the original binding facts from real SQL rows, including their actual
DRAINING or RELEASED state, and reads the original genesis-to-terminal chain,
resources, refs and SEALED head without locking or checking expired writer

reference and original installed context. These use the same production
semantic checks as the live path. Historical seal reading excludes the shared
holder; live reading preserves that holder check and its existing locks and
authority. The returned terminal proof is only a native semantic result;

write authority and does not open a historical or public selector by itself.

The companion application component rechecks the saved baseline's typed associations and native membership, the closed frozen envelope and commit encoding, the complete pre-cut worker observation, the exact cut and finalizer, and the reconstructed released history image.
