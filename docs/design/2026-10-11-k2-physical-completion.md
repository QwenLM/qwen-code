# K2 physical completion and retained release receipts

[English](2026-10-11-k2-physical-completion.md) | [简体中文](2026-10-11-k2-physical-completion.zh-CN.md)

Status: private progress implementation candidate. Same-Connection DRAINED validation, immutable plans, stop intent, persisted normal DELETE attempts and observed source prefixes are implemented. The sealed `1169bfd7` candidate passed independent real Hosted/application-to-physical SQL acceptance, complete coordinator windows and narrow private Main plan/status/replay. Its node source and Kubernetes services were explicit protocol/API fixtures. That acceptance applies only to its exact candidate and cannot qualify later Pod-construction changes or ACK deployment. The exact revised host units passed owned Linux functional tests with explicit runtime/CSI protocol fixtures. No qualified release writer, historical release reader or public selector exists. This design continues #13395 and Draft PR #13526; it does not authorize installation in ACK.

## Problem and supported boundary

Application DRAINED closes the original file handles and releases the logical Runtime Session. The container may still exist and kubelet may still hold the original CSI publication. Reusing the physical volume requires the continuous original task/cgroup and publication/unpublication evidence, followed by one atomic ownership change. API acceptance, NotFound, a successful empty-target retry and a holder phase alone cannot establish that result.

Support the reviewed single isolated node and fresh Session/request/slot/binding for each owner. Keep the original immutable DRAINING intent, application DRAINED receipt and PUBLISHED association. Runtime generation 1 and native epoch 1 remain distinct from the shared holder revision. Do not enable normal Spring or public selection before the complete qualification and reuse acceptance.

## Original DRAINED authority

The physical store obtains a package-private validated result from the application store on the same transaction-bound Connection. The result is privately constructed only after the original lock prefix, Session credential, binding/boot, typed application inventory, saved freeze/cut/finalize bytes and actual finalize response all match. A bare broker application Authority or a DRAINED column is insufficient.

The operation owns a ten-second transaction and rejects ambient composition. Preserve placement → retention → sorted original slots/bindings → private Session/pin/context → alias/physical holder → immutable retirement/progress → native head/history/resources/refs → original Runtime Session/sorted executions → explicit secondary/source/physical catalog. Recheck database time after lock waits. Source, Kubernetes, worker and protection RPCs remain outside SQL locks. Physical and historical reads do not renew the original writer or reuse the five-minute application settlement deadline.

## Immutable plan and explicit physical catalog

V69 adds a dedicated six-column physical record: retirement_id, binding_id, physical_key, record_version, record_bytes and record_sha256. Its current closed JSON format is `qwen-csi-physical-progress/1`, with exactly format, retirementId, bindingId, physicalKey, stage, planBase64, planSha256, intent, attempts and observations. Stages are PLANNED, INTENT, STOPPED and UNPUBLISHED. There is no qualification or RELEASED field in this version. Each payload pair is either wholly absent or wholly present. Every original field and every earlier attempt remains immutable, apart from filling one previously unknown reply once.

The record is bounded to 16 MiB, its plan to 64 KiB, each journal prefix and HTTP reply to 1 MiB, attempts to eight and observations to two. A checked version starts at one and counts each saved intent, attempt, actual reply and stage observation. Repeating the same Pod resourceVersion returns the saved attempt without resending, including when its outcome is unknown or rejected. An actual STOPPED source may still require normal Pod deletion before CSI unpublication.

The plan derives from the verified original request, binding, registration/reservation, saved handle/boot, application baseline/freeze/cut/finalizer and exact nineteen-column PUBLISHED source association. It pins source identity/incarnation, node, ARM/BOUND/publication prefixes, Pod UID, original image/container, target and all dependency cursors. Revisions are decimal strings. The exact serialized source configuration is Base64, preserving unsigned kernel start values without conversion through floating point or signed long; the original strict configuration decoder validates the recovered bytes.

The current nested plan is `qwen-csi-physical-plan/3`. Its `ownershipReleaseInventorySha256` pins the exact expected application inventory after the three ownership-row changes below. The projection starts from the privately validated DRAINED inventory, checks the original binding/slot/holder correlation and checked counters, and preserves all other rows, fields, keys and membership. It performs no SQL writes and grants no physical permission. The fourth row, the physical progress record and final receipt, requires qualified evidence and has no precomputed outcome. Saved version-one and version-two plans are refused by this candidate; finish them with their original binary rather than changing their bytes, hash or stop-intent dependency.

The plan also pins `historicalReleaseInventorySha256`, a deterministic declared original read-set image derived from that projected ownership result. It preserves complete ORIGINAL rows except the shared physical holder and excludes OTHER rows and unrelated context. Required original tenant placement/retention identities and original workspace generation/storage/config/policy/state remain pinned; workspace display name is outside this read set. Context column masks are fixed in code, represented canonically and cannot be chosen by a caller. The projection retains catalog schemas, typed keys and every original cell, including the empty original request slot and released binding. This is the expected-image prerequisite for the historical reader, not a SQL reader, release receipt or physical capability.

Readback requires the saved plan bytes to equal the exact encoding of the verified expected plan, in addition to matching their saved hash. Equivalent JSON values with changed whitespace, field order or escaping refuse; they must not establish a new plan hash or stop-intent dependency on retry.

The physical table has a separate explicit typed catalog and validator, read on the same Connection after the application closure. The application catalog remains 62 tables and 847 columns. Before DRAINED, the companion must have its exact six-column schema and no matching retirement, binding or physical-key row. After the complete DRAINED image is verified, any companion row must match the original plan and exact stored bytes/hash/version; foreign or duplicate rows and schema drift refuse progress. Its current expected image permits only the declared insert, append or one pending-outcome replacement. No positive state is backfilled into a deployed database. The old worker-ACK table is unsupported in this lane and does not supply physical qualification. Qualified release requires a separately implemented format and validator.

## Stop intent and exact normal DELETE

Commit the immutable plan before requesting STOP_INTENT from the fixed authenticated original source. After the RPC, reacquire the common prefix and save the exact prefix/head extending the original publication, with original retirement ID and plan hash. A lost reply can reconcile only that unchanged original stream. Changing ARM, source incarnation or plan cannot repair an unknown result.

Outside SQL, read the exact original Pod and corroborate node/protection/source pins. Persist each DELETE attempt before sending it: ordinal, namespace/name, canonical original UID, the newly observed opaque resourceVersion and exact request bytes/hash. Only gracePeriodSeconds=30, propagationPolicy=Background and both UID/RV preconditions are supported. A replacement UID or missing Pod retains ownership.

The Kubernetes client must expose the prepared immutable request and preserve the actual bounded HTTP status and raw response bytes. Sending must use the same prepared bytes saved by the coordinator. HTTP 200/202 mean request acceptance only. Preserve 404, 409, redirects and other rejection outcomes without treating them as completion. Transport loss, timeout, truncated/oversized body or a crash between send and outcome persistence leaves an ambiguous attempt. A later RV creates another attempt; it never replaces the old request or manufactures its reply. Generic GET/CREATE/PATCH error behavior stays unchanged.

The private command is `physical <status|plan|intent|delete|observe> <reviewed-runtime-json> <reviewed-node-json> <retirement>`. It selects the original tenant/Session/request/binding, uses the retained original writer credential and fixed source configuration, and closes owned HTTP clients. Status and plan access only SQL and return before loading Kubernetes/source client credentials. Plan matches the reviewed node with the original stored association inside its transaction, before inserting or changing any physical record. Before external intent, DELETE or observation operations, the coordinator corroborates the original node UID/boot/Ready condition and protected volume outside SQL. There is no release action, Spring route or Hosted public selector. An already saved intent or final UNPUBLISHED state can return its durable progress without another mutating source or DELETE request.

## Source evidence and deployment qualification

The physical verifier requires an exact raw-prefix extension of the saved publication, unchanged source identity/incarnation, original scope and all original ARM/BOUND/custody/publication records. The current journal/3 reader requires explicit retained Pod-parent coverage, distinct parent inode and unchanged same-filesystem identities alongside the original leaf/PID/start tuple. The synthetic v3 fixture and cross build do not qualify a native parent lifetime or first execution. STOP_INTENT must bind the plan. ORIGINAL_STOPPED must bind the retained original task, pidfd/cgroup identities, custody, publication and intent. UNPUBLISH_BEGIN/OK must explicitly depend on that durable stop and original publication, with the same pinned caller/backend chain. A late intent without custody/publication, BLOCKED scope, gap, replacement process or altered dependency refuses completion.

Protocol decoding, authenticated transport and ResourceGuard corroboration are separate from deployment qualification. Qualification must consume reviewed actual executable/configuration/namespace/LSM facts, nondelegated confinement from birth, Pod CREATE/gate/binding/exec/ephemeral/DELETE actor restrictions, exclusive frontend/registrar/backend wiring and unchanged runtime/plugin/boot. There is currently no production consumer for this complete installation contract. An operator boolean, self-signed statement, test fixture or journal hash cannot mint permission. Until the actual consumer and installation are qualified, recording progress must preserve the DRAINING holder and release remains closed.

The [original ACK deployment candidate](../../deploy/k2-evidence/ack-existing-cluster/README.md) supplies a local renderer and cold-installation/undo sequence for a new isolated Node's known CSI addon exclusion. It leaves the original DaemonSet and shared nodes intact. Local expression evaluation passed 20 request-map cases; actual API schema/defaulting, enforcement, policy modification privileges and complete Pod/host confinement remain pending. This component cannot mint the physical capability.

The same directory renders five worker access guards for a dedicated namespace: exact original gated CREATE, coordinator-only gate removal, explicit additional-process/eviction denials, scheduler-only binding to the isolated Node, and coordinator-only normal UID/RV deletion. CREATE/gate rules enumerate the pinned API schema, but actual typechecking, admission enforcement and actors remain unqualified. The rules do not cover direct kubelet/runtime/static-Pod access or admission-configuration writers, and do not themselves prove runtime confinement from birth. Those boundaries must be established before the installation consumer can grant release.

## Atomic release and monotonic counters

The final same-Connection transaction validates the complete original application/physical image and qualification, then changes exactly four rows:

| Row                            | Sole permitted change                                                       |
| ------------------------------ | --------------------------------------------------------------------------- |
| Original physical record       | RELEASED, checked version+1, immutable final receipt bytes/hash             |
| Original runtime binding       | binding_state=RELEASED and checked record_version+1                         |
| Original request-specific slot | active_binding_id=NULL; preserve last_generation                            |
| Original physical holder       | csi_phase=RELEASED, checked csi_revision+1; clear only six CSI owner fields |

The six fields are csi_reservation_id, csi_registration_key, csi_registration_revision, binding_id, runtime_generation and csi_provision_request_id. Preserve all other bytes, including original seed/handle/lease, binding timestamps and stop/loss/drain evidence, slot identity, holder maintenance/protection and immutable intent/application/source rows. Runtime Session was already released by application completion and is not a fifth write. Every CAS must affect one row; overflow, timeout, unexpected image or any zero-row CAS rolls back all four changes. Do not loosen generic sealed-binding CAS. A narrow private physical capability must be minted only by the full actual validator before the terminal binding/slot write.

Shared holder transitions use RELEASED%3=0, RESERVED%3=1, DRAINING%3=2 and MAX=9007199254740990. Use the actual stored revision and checked increments throughout subsequent cycles.

The current candidate admits only the initial ownership cycle, revisions 0 through 2. An independent store-only H2 fault test reproduced the previous gap: a manually injected RELEASED revision 3, with all retirement/physical proof tables empty, became RESERVED revision 4. Later-cycle holder reads now refuse before reservation, replay or alias registration can write. Counter arithmetic remains generalized, but a nonzero released counter cannot stand in for a qualified historical outcome. Replace this temporary gate only together with the complete historical validator and qualified release writer; it does not implement successful reuse.

## Historical receipt and the next owner

After release, the live application guard cannot read the old receipt: the original slot is empty and the shared holder may belong to the next owner. Add a persisted-workspace/original-retirement read route with the original Session/tenant credential and retained writer-token hash. It validates only the declared immutable original historical read set and original released delta in a bounded snapshot. It returns exactly the committed original receipt without source/API/worker RPC, acquire/renew, new evidence or writes to either owner.

Historical validation must retain original intent/freeze/cut/finalizer, PUBLISHED association, physical plan/attempts/proofs/qualification, original released binding/slot, terminal native rows and original Runtime Session/executions. It validates required placement/retention/context identity but does not compare current shared holder, unrelated context or new-owner bytes with the old global snapshot. A corrupt or unsupported retained receipt refuses replay; it is never rebuilt from a current volume observation.

Use a fresh ten-second read-only REPEATABLE_READ transaction on one Connection, without FOR UPDATE or context initialization. Do not weaken the live application authority to accept RELEASED: it requires the still-active original slot, and its physical catalog intentionally includes all matching physical-key rows. The historical companion query instead identifies the original retirement/binding; a later owner's companion row must not become an original historical row. Reuse the fixed typed catalog and decoder, check schemas even for expected-empty tables, and read complete original keys plus their strong reference closure. The expected keys alone cannot detect added executions, native tails or orphan references. Shared physical key, volume markers, tenant/storage and scope without the original Session are insufficient roots for this closure; anchored unknown or contradictory references still refuse.

The retained writer hash must agree in the frozen baseline head, frozen envelope, terminal transaction and final SEALED head, then match the presented original token through the same credential policy and constant-time hash comparison. Reconstruct the complete original application/native/finalizer semantics before comparing the fixed history image; image arithmetic alone cannot validate a receipt. Public replay and internal old-lineage classification share that structural validator but have distinct credential layers. Internal classification never asks the new owner for the old writer token or returns the old receipt or secrets.

The next owner's live inventory must classify the old lineage before generic physical-key/JSON mention expansion. Only a completely verified immutable qualified RELEASED outcome can establish historical/OTHER membership. Keep the old proof rows in the explicit catalog; do not ignore them or accept a phase flag. Cover original retirement/source/binding/slot/execution/native rows and cross-tenant aliases. A missing/corrupt proof blocks reuse. The new owner gets a fresh reservation, ARM, Pod and custody and cannot borrow any original proof.

Reuse must also validate that the current holder exactly matches the latest qualified released outcome, including its checked counter and six empty ownership fields. Discover the candidate historical tenants before taking write locks, acquire their placement and retention roots in deterministic tenant order, then lock slots/bindings/aliases/holder/proofs in the declared order and recheck the complete candidate set. Do not acquire an old tenant's placement lock after holding the new tenant's physical holder. The public historical snapshot remains independent of these write locks. Keep the initial-cycle gate until this complete consumer and four-row writer exist.

## Implementation and verification order

The ownership projection was independently compiled and verified over a previously sealed real application DRAINED tuple. Its reconstructed digest exactly matched the original production plan before projection. Across 62 tables, 847 columns and 236 rows, exactly three rows and eleven cells changed; all remaining cells, keys, membership and the already released Runtime Session were preserved. Independent Java covered 64 distinct image cases, with a separate binary-codec comparison. A separate four-case codec probe reproduced acceptance of whitespace-changed plan bytes despite equivalent JSON values and matching recomputed hashes, then verified refusal after the exact-byte fix while the original control remained valid. Focused Java verification at that ownership-projection revision passed 82 tests and static checks. These results cover image math and the specific plan-byte fix; they do not qualify plan/2 through a live Store transaction or any physical release, historical replay, reuse or public selection.

Independent acceptance of the sealed `1169bfd7` candidate covered 21 real MySQL Store windows, 11 complete coordinator windows using the actual authenticated TLS source client and actual Kubernetes HTTP client, and three original Main plan/status/replay processes. The actual Hosted file tools and original application retirement produced DRAINED before physical progress. Full typed comparisons kept the other 63 tables unchanged; a real zero-row physical CAS rolled back the whole transaction. Unknown DELETE retained the attempt, a same-RV coordinator retry sent zero additional DELETEs, replacement identity refused, and later source observations persisted STOPPED/UNPUBLISHED without releasing ownership. Status and plan replay were SQL no-ops with zero new RPC. Original observer failures were retained and corrected in separate attempts. Source identities/publication and API services remained fixtures; no actual ACK stop/unpublish, qualified release, reuse or public-selection result follows from these checks.
