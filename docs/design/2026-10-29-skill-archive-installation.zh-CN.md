## 状态与基线

方案于 2026-10-29 批准实施，扩容仅限新的 raw/文件来源。实施从 main `06fbfc9951c0a0833e57eb84a9b3625bb84f2853` 开始，其中已包含 [PR #15030](https://github.com/QwenLM/qwen-code/pull/15030) 的提交 `2415b12329b1bb0ef1b5beb6bfc0bd0535b9ee7b`。

## 现状与剩余需求

| 维度             | 当前 main                                    | 剩余需求                                        |
| ---------------- | -------------------------------------------- | ----------------------------------------------- |
| ZIP 传输         | Base64 JSON，压缩内容最多 7,864,071 字节     | 不增大全局 JSON 上限，也能传输真实 20 MiB 归档  |
| HTTP JSON 请求体 | 10 MiB                                       | 保持现有 JSON 路由的限制                        |
| 解压后的包       | 总量 64 MiB、单文件 32 MiB、2000 个文件      | 仅扩容新的 raw/文件归档来源，保持所有旧来源政策 |
| 解压             | 压缩包完整 Buffer，随后逐条目流式写入并计数  | 直接打开磁盘 ZIP，避免整个归档进入内存          |
| 来源             | GitHub URL、本地目录、base64 ZIP             | 增加 daemon 主机上的 ZIP 文件引用               |
| 发布             | 暂存、验证、备份/重命名/回滚，现有路由互斥锁 | 新传输复用既有路径                              |
| 身份             | 现有名称/路径契约，manifest 名称必须匹配     | 首次交付保持不变                                |

两种调用场景需要不同入口：浏览器只有需要上传的 File；集成方可能已经把 ZIP 上传到了 daemon 所在主机。要求后者再读取并编码为 base64，会重复传输工作。

要解决的是内存有界的大文件传输。最大可接受包规模、与外部安装器的完整兼容是另外两个需求。首次交付不声称其他系统接受的所有包都能由 Qwen 安装。

## 范围

本功能包含基于磁盘文件的 ZIP 安装、raw HTTP 上传、SDK 与 Web Shell 接入、自有输入、可取消等待、有界尝试回执，以及局部发布/恢复保护。新归档采用 200 MiB / 4096 条目；旧来源限额、名称规则、GitHub 获取、目录复制与发布结构保持不变。

将新政策扩展到旧来源、重新设计身份或发布器、跨进程锁、持久化事务、自动重试和断点续传不在本次范围内。

## 安装契约

### 已上传的 ZIP

扩展现有 JSON 来源联合类型：

```json
{
  "name": "example-skill",
  "scope": "global",
  "attemptId": "c72732d3-7e2e-4b91-8c39-ec0f5ed45176",
  "source": { "type": "zip-file", "path": "/absolute/path/example.zip" }
}
```

路径属于 daemon 主机，不是浏览器本地路径。沿用现有认证、信任、运行时归属和名称验证。要求绝对路径的普通文件，拒绝作为来源的符号链接及特殊文件，验证打开的句柄，并限制压缩输入字节数。Qwen 借用该来源，不删除或重命名它。

在等待变更锁之前，将借用的 ZIP 复制到安装器自己的磁盘文件，解压只读取该副本。调用方需要在获取期间保持来源稳定，不再需要贯穿等待锁和解压全过程。下方生命周期决策说明复制的保证边界，以及可选的 `source.sha256` 验证。

### 浏览器 ZIP

使用一次 raw 请求，`Content-Type: application/octet-stream`：

| 路由                                                                               | 归属与激活                                         |
| ---------------------------------------------------------------------------------- | -------------------------------------------------- |
| `POST /workspace/config/skills/install-archive?name=...&attemptId=...`             | 全局配置；保留现有全局所有者/信任解析和协调更新    |
| `POST /workspaces/:workspace/config/skills/install-archive?name=...&attemptId=...` | 选中的可信运行时，workspace 范围；协调更新该运行时 |

路由固定 scope。在接收正文前完成认证、名称、运行时、信任、内容类型和并发准入检查。流式写入私有临时文件，无论有无 Content-Length 都按实际字节计数。拒绝 HTTP 内容编码。未知、不可信、启动中、排空中或已移除的运行时沿用原失败语义，绝不回退到 primary。

接收完成后进入现有安装请求使用的同一互斥锁、同一 key 和安装流程。沿用现有变更结果与激活行为。正常操作仍是一次同步 POST，不需要上传会话、第二次提交请求、断点续传或后台任务服务。只读尝试查询用于在响应丢失后确认操作结果。

请求持有临时文件，并在操作确实结束后的所有结果下清理它。不借用通用 workspace 文件上传的目标目录：该接口发布的是用户文件，归属和重名处理不同。复用 SDK 的传输逻辑不等于复用会缓冲整个请求体的 HTTP 解析器。

### SDK 与 Web Shell

为全局和 workspace 安装增加薄封装方法。发送新归档请求前生成 `attemptId`，在客户端错误中保留它，并提供尝试查询。复用已有二进制上传的认证、错误处理、AbortSignal 和可选进度约定，保持原文件上传行为不变。

仅在支持的服务端暴露 `skill_archive_install`、`skill_zip_file_source` 和 `maxSkillArchiveBytes`。Web Shell 在支持 raw 能力时直接发送 File/Blob，否则保留 7,864,071 字节的 base64 路径，超限时在上传前提示升级。保持现有配置/运行时划分及激活处理。

初版 UI 可以继续使用现有忙碌状态。上传进度达到 100% 只代表接收完成，不代表安装成功。丢失响应或超时后，结果仍待确认，直到尝试查询提供证据。不自动换传输方式重试，也不把已有同名目录/路径当作本次版本已安装的证明。列表刷新用于了解当前清单，与历史尝试结果分别处理。

### 已批准的来源政策与 API 边界

只有现代 config 安装路由接受 `zip-file`；旧 runtime 路由返回要求使用 config 路由的错误。SDK 旧 runtime 来源类型保持不变。两种新归档来源采用 50 MiB 压缩 / 200 MiB 实际保留展开字节 / 4096 ZIP 记录。普通资源只受剩余展开总量约束。新来源条目在过滤前验证路径/类型，保留文件使用独占创建；在现有单层 wrapper 归一化后、读取文本前，对有效根 SKILL.md 应用 32 MiB 限额。嵌套资源 manifest 仍是普通资源。不引入全量元数据规划框架。

SDK 归档调用默认 130 秒；timeoutMs=0 仅禁用客户端计时器。结果不确定时，Web Shell 用 5 秒超时独立查询一次，仍在进行/未知则提供手动检查，绝不自动重传。激活失败不改变已提交内容的成功结果，另附激活警告。历史回执查询遵循配置读取的授权和 workspace 身份，不进入变更 coordinator，也不要求旧 generation 仍活跃。已移除或不可访问的所有者不回退 primary。

## 资源与生命周期政策

| 限制                         | 固定政策                                             |
| ---------------------------- | ---------------------------------------------------- |
| 新 raw/文件 ZIP 的压缩字节数 | 50 MiB                                               |
| 旧 base64 的压缩字节数       | 7,864,071 字节，不变                                 |
| 展开后的包总量               | 新 raw/文件归档为 200 MiB                            |
| 有效根 SKILL.md              | 32 MiB，不变                                         |
| ZIP 条目数                   | 新来源过滤前计数 4096 ZIP 记录；旧来源仍为 2000 文件 |
| 路径                         | 现有长度 512 / 深度 16 规则                          |
| 新本地归档操作               | 每个 daemon 最多同时准入两个；超额在接收前拒绝       |

50 MiB 是固定传输上限，不保证所有 50 MiB ZIP 都能安装。归档仍必须满足展开总量、单文件、路径和 manifest 规则。目录与 GitHub 政策保持不变。

采用统一的发布前 120 秒预算，涵盖接收/复制、等待锁和解压，各阶段不重新计时。进入发布时再次检查单调时钟的已用时间。SDK 默认等待时间为 130 秒，但它是客户端等待预算，不能证明服务端已回滚。发布、回滚及尚未结束的文件系统清理可能超过这些预算；下方取消与回执契约明确该边界。

一个自有归档及候选目录最多新增 250 MiB 临时磁盘，两个操作最多 500 MiB。raw 上传不再复制一遍。已有安装、备份、文件系统元数据和崩溃遗留另计。优先让已由请求持有的 raw 临时文件直接进入相同的内部文件解压流程，避免再次复制，也不暴露公共所有权转移开关。借用文件复制一次；调用方持有的原文件不计入安装器临时磁盘预算。

## 生命周期决策

### 借用文件被修改

**推荐：自有磁盘副本、常规变化检测，以及可选的预期内容校验。** 只读文件描述符绑定的是已打开文件的身份，其他进程仍能修改或截断同一个文件。硬链接也有同样问题。等到拿锁之后才读取借用 ZIP，会无谓延长暴露时间。

不跟随最终符号链接，打开并验证普通文件句柄，确认句柄与已验证输入一致。记录身份、大小和修改/变更元数据，经压缩字节计数及 SHA-256 哈希流式复制到私有、独占创建的文件，再次比较来源元数据。发现变化、读取字节数不匹配或超限时失败。关闭写句柄，此后 ZIP 解析和解压只使用自有副本。获取完成后，原路径被替换或删除不应影响本次尝试；Qwen 绝不能清理该原路径。调用方不能从经过的时间或上传进度推断获取已完成：通常应等请求结束再清理原文件，除非服务端报告的阶段已确认获取完成。

复制不等于对并发写入来源做原子快照。前后元数据检查能识别普通竞争，不能识别所有恶意或不可见修改。如果生产者已知完整上传的摘要，可以提供可选的 `source.sha256`；获取摘要不一致时，在解压前拒绝。这能把接受的字节绑定到生产者预期内容，但不能证明作者可信或对应某个文件系统瞬间。没有预期摘要时，支持契约仍要求复制期间来源稳定。Qwen 自己计算的哈希只能标识实际获取的字节，不能证明生产者原本想安装什么。

| 选项                         | 保证与代价                                   | 决策                               |
| ---------------------------- | -------------------------------------------- | ---------------------------------- |
| 直接只读句柄                 | 无复制；整个解压期间都可能受原地修改影响     | 不作为默认                         |
| 硬链接或协作式锁             | 硬链接共享写入；锁要求所有写入者配合         | 不能建立所需隔离                   |
| 自有副本加检查               | 获取完成后解压输入稳定；增加一次有界磁盘复制 | 推荐                               |
| 自有副本加生产者摘要         | 额外验证归档符合预期字节                     | 对已有上传摘要的集成方提供可选能力 |
| 文件系统快照或不可变上传服务 | 更强来源所有权，但引入平台/协议依赖          | 独立的后续需求                     |

复制增加最多一份 50 MiB 本地读写和临时文件。复制时同时算哈希，不再整包读取一遍。raw HTTP 输入完成后，私有上传文件本身已经是自有输入。这样消除了漫长等待锁期间对原文件生命周期的依赖。

Codex 的远程包路径先持有已下载字节，再解压进自有 TempDir；其存储层复制到暂存目录，并在发布前比较 manifest 字节。这些所有权方式值得参考，但不能证明借用本地 ZIP 或可变来源目录中所有文件具有某一时刻的一致性。[远程获取](https://github.com/openai/codex/blob/a29c7b97e88367044ae84c28c85451ec3e72af9f/codex-rs/core-plugins/src/remote_bundle.rs#L257-L301)、[存储暂存](https://github.com/openai/codex/blob/a29c7b97e88367044ae84c28c85451ec3e72af9f/codex-rs/core-plugins/src/store.rs#L555-L638)。

### 等待锁时取消

**推荐：为现有互斥锁等待增加可选取消能力，保持串行顺序，并设立一次发布准入边界。** 沿用新旧安装/删除共享的 registry/key。本次不另设归档专用锁，也不搬动现有临界区。不传 signal 的调用方保持原行为；共用该类的文件系统操作需要回归覆盖。直接返回忙碌可以省去排队取消，但会改变现有等待行为；让已取消请求继续排队则占用文件/准入名额，并可能意外执行。推荐付出小幅等待逻辑改动，保留既有行为。

在准入前被取消的等待者应及时退出等待，绝不调用安装回调，移除 abort 监听，并在真实 I/O 结束后释放自有输入。对当前 Promise-tail 实现，被取消等待者的顺序连接必须留在前驱之后，直到前驱结束；安装回调和包内容不必继续挂在链上。不能因为被取消的调用已经返回，就删除对应 key。A 持锁、B 等待时取消 B，不得让 C 与 A 并发。只有顺序链真正结束且仍是当前 tail，才能清理 map 中的 tail。

入队前和获准执行后都检查 signal。接收/解压期间，取消应停止实际流并阻止后续工作；在实际工作结束前继续持有锁和并发准入名额。只对等待锁做竞速，并正确撤销落败等待者，可以成立；对整个安装 Promise 与计时器做竞速不够，因为客户端被告知取消后，安装可能仍继续。

第一次修改目标目录的 rename 之前，同步检查取消、截止时间和运行时资格，中间不经过 await 就进入发布阶段。先处理取消则不得发布；先获准发布则完成提交或回滚，不受 HTTP abort 或客户端截止时间打断。运行时 generation 检查和文件系统失败仍走既有一致性/回滚路径；保护发布阶段不等于允许向已移除运行时发布。

| 阶段                | 取消语义                                           |
| ------------------- | -------------------------------------------------- |
| 接收 / 自有副本准备 | 停止 I/O，等待关闭，清理自有文件；不发布           |
| 等待变更锁          | 撤销本等待者，绝不调用其回调，保持其他等待者的顺序 |
| 持锁解压 / 验证     | 停止实际工作、清理暂存，再释放锁                   |
| 发布 / 恢复备份     | 完成一致的结果；取消不再能承诺没有安装             |

客户端 AbortSignal 表达的是取消请求。只有服务端观察到的断连/取消或自己的截止时间，才能阻止发布；代理可能延迟传播断连。客户端 AbortError 本身不是取消确认。首版不增加独立取消接口，通过尝试查询报告是否已发布。

Codex 插件同步 gate 对获取锁设置了独立的 120 秒超时。它的企业登录流程明确对获取 gate 与取消做竞速，并共享取消/提交准入状态。它的目标写入器即使 RPC 消失，也继续持锁完成后台 I/O。后两者属于不同子系统，仅作为生命周期设计参考，不代表插件 API 的保证。[插件 gate](https://github.com/openai/codex/blob/a29c7b97e88367044ae84c28c85451ec3e72af9f/codex-rs/core-plugins/src/manager.rs#L1723-L1735)、[可取消等待](https://github.com/openai/codex/blob/a29c7b97e88367044ae84c28c85451ec3e72af9f/codex-rs/app-server/src/request_processors/account_processor/enterprise_login.rs#L161-L174)、[提交准入](https://github.com/openai/codex/blob/a29c7b97e88367044ae84c28c85451ec3e72af9f/codex-rs/app-server/src/request_processors/account_processor/enterprise_login.rs#L262-L293)、[I/O 所有权](https://github.com/openai/codex/blob/a29c7b97e88367044ae84c28c85451ec3e72af9f/codex-rs/app-server/src/request_processors/thread_goal_user_context.rs#L24-L50)。

### 超时后确认结果

**推荐：客户端生成尝试 ID，每次尝试保留一份有界内存回执。** 这确实增加协议范围，但普通 Skill 清单无法区分旧安装、本次尝试和后续覆盖。正常 API 仍是同步 POST；回执用于响应不确定后的核对，不是任务调度系统。

新 raw/文件调用在传输前生成 UUID `attemptId`：文件来源放在 JSON 字段中，raw 上传放在 query 参数中。SDK 即使没收到响应也保留它。认证和准入后，在接收正文之前预留回执。回执绑定已解析的全局/workspace 所有者、适用时的运行时 generation、目标名称，以及获取后才有的归档 SHA-256。持有 ID 不增加任何访问权限。

只读查询路由为 `GET /workspace/config/skills/install-attempts/:attemptId` 和 `GET /workspaces/:workspace/config/skills/install-attempts/:attemptId`，遵守相同归属、认证与可见性边界。运行时不可用或已移除时，不得回退到其他所有者。查询使用新的、有超时限制的只读请求，不复用已经 abort 的安装 signal。

| 回执结果              | 客户端可以得出的结论                                                 |
| --------------------- | -------------------------------------------------------------------- |
| `running`             | 本次尝试仍活跃；包含阶段，不要重新提交                               |
| `committed`           | 本次尝试已完成所记录归档字节的发布；运行时激活和当前清单另行判断     |
| `not_committed`       | 本次从未发布，或已确认恢复此前状态；附失败/取消原因                  |
| `recovery_required`   | 发布/回滚未能确认恢复状态；不能声称已取消，也不自动重试              |
| 未知 / 没有可访问记录 | 无法判断成败；请求可能未到达、记录可能过期，或 daemon/运行时发生变化 |

在安装器最终提交边界、最后一个可能导致 generation 回滚的决策之后、返回 service/HTTP 层之前记录 `committed`，不能仅从 HTTP 200 推导。后续运行时、激活或刷新失败不得把已提交内容标成不存在，应保留提交结果并附相应错误。尽力执行的备份清理可以继续，同时保留对尚未结束工作的所有权。回执表达历史事实：后来的安装、删除或外部编辑仍可能改变当前目录。归档摘要标识输入，不是当前展开目录的已验证哈希。读取当前清单回答的是另一个问题。

活跃回执保留到工作结束；终态保留 10 分钟，总容量 256 份。变更前预留容量，满时拒绝新尝试，不驱逐已承诺保留且尚未过期的记录。这些是固定默认值，不是公开配置开关。同一所有者/保留窗口内的重复 ID 绝不再次执行，即使提交了不同内容，也返回冲突并引导查询。这是有界的重复抑制，不是持久化的恰好执行一次或自动重放契约。新 raw/文件调用要求 ID；原有来源请求保持原契约。

daemon 重启会丢失这些回执。未知必须保持未知，不能变成“失败，可以安全重试”。首版不做自动重试、跨重启去重或持久化。rename 后另写回执文件存在崩溃窗口；在候选目录中放标记会改变包元数据，也覆盖不了后续旧路径/外部写入；持久化事务日志是独立设计。如果必须支持重启后的结果恢复，这个有界回执方案不够，需要先设计更强保证再作承诺。

局部回滚改动区分已确认恢复与 `recovery_required`，并确保后续安装仍保留可恢复备份。未发布候选目录的清理失败不能阻止恢复旧安装。测试覆盖响应丢失、提交中的迟到 abort、恢复失败、后续覆盖、重复 ID、回执容量/过期，以及重启/所有者消失。

Codex 把 `installAttemptId` 定义为客户端生成的关联标识，并将其转交远端安装请求，同时检查返回的插件身份和启用状态。已检查的客户端代码不能证明存在按尝试查询接口、服务端幂等或跨崩溃持久化结果。上述 Qwen 回执是我们的新增建议，不是对 Codex 功能的宣称。[协议定义](https://github.com/openai/codex/blob/a29c7b97e88367044ae84c28c85451ec3e72af9f/codex-rs/app-server-protocol/src/protocol/v2/plugin.rs#L956-L975)、[远端请求](https://github.com/openai/codex/blob/a29c7b97e88367044ae84c28c85451ec3e72af9f/codex-rs/core-plugins/src/remote.rs#L1641-L1683)。

## 复用与正确性边界

当前 ZIP 打开函数是依赖 Buffer 的边界；其余解压逻辑消费 ZIP reader。因此文件打开分支复用惰性条目遍历、路径检查、声明尺寸检查、实际字节计数、包装目录展开、manifest 检查和发布流程。保留自有 PassThrough 的流关闭处理及现有 inflater。

实施验证发现，yauzl 2.10 的 fd-slicer 依赖在当前 Node 版本下会提前把文件流标记为已销毁，阻止缓冲中的压缩字节继续流出。一个有效的 70 MiB 条目在输出 60,071,690 字节后挂起，尚有 58,163 压缩字节滞留；同一归档通过 2.10 的 Buffer 入口和 yauzl 3.4 的文件入口均完整结束。因此 CLI 升级到仓库其他位置已使用的 yauzl 3.4，并保留旧安装测试作为回归覆盖。不引入自定义文件 reader 或 inflater。

不要仅为新增输入就迁移锁位置、引入跨进程锁、重写目录复制或搭建归档框架。新路由必须参加既有互斥，本方案不宣称跨 daemon 串行化。

回滚失败返回 `recovery_required` 及保留路径。后续安装必须保留遗留备份；成功安装仍清理自己创建的备份。故障注入测试覆盖恢复失败后再次安装的序列。不引入自动恢复程序或发布器重写。

## 验证与验收

已完成的基线使用全局 `qwen 0.22.0`，不是合入后的 main bundle。小 ZIP 与目录请求成功且字节一致；真实 20 MiB ZIP 编成 27,962,121 字节 JSON 后返回 413；zip-file 返回 400，raw 上传返回 404。该版本没有现代配置路由，因此这些结果不能验证当前 main 的相应行为。临时输入得到保留，测试 daemon 已清理。

上述固定基线的未修改 main bundle 也已验证：现代 config 路由成功安装小 ZIP 和目录，内容逐字节一致；真实 20 MiB base64 请求返回 413，`zip-file` 返回 400，raw 上传返回 404。以下实施验收以此为基线：

- 真实 20 MiB 归档分别通过 raw 和文件来源安装，逐字节对比；新路径不读取整个归档为 Buffer。
- 新来源 50 MiB 压缩 / 200 MiB 展开 / 4096 条目及有效根 manifest 32 MiB 边界；旧来源保持 64 MiB / 32 MiB / 2000 文件边界。
- 新旧路径对穿越、符号链接、重复路径、包装目录、manifest、GitHub 回退和 base64 兼容的共同表现。
- 接收中断、伪造声明尺寸、暂存写入失败、等待锁时超时、运行时 generation 关闭、替换失败；实际工作结束、临时文件关闭并清理，未提交时保留旧安装。
- 全局与选中运行时的激活归属正确；拒绝 workspace 状态时没有 primary 回退。
- SDK fetch/XHR 行为、旧 daemon 回退、通用文件上传不变。
- 两个大操作期间的内存和临时磁盘实测，以及第三个操作被拒绝。

新 4096 限额统计所有显式 ZIP 记录，包括目录和忽略元数据；隐式父目录不重复计数。展开字节只统计保留文件。将新政策仅用于新来源，可以避免收紧旧目录布局。名称兼容和受管理内容归属也需要独立验收，不能从上传成功推导。

## 验证边界

采用上方固定政策，不增加配置开关。测量内存与临时磁盘，验证取消和恢复故障，并使用构建后的 bundle 执行独立真实 HTTP 与浏览器验收。记录实际操作系统与浏览器；源码检查和单元测试不代表跨平台或浏览器验收通过。执行证据单独记录在 E2E 报告中。
