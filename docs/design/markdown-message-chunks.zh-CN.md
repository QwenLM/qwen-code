# Markdown 消息分段

[English](markdown-message-chunks.md) | [简体中文](markdown-message-chunks.zh-CN.md)

## 问题和范围

钉钉和企业微信当前会在链接、表格行和代码围栏内部截断长 Markdown。保留现有普通消息发送路径，加入共享的结构感知分段。交互卡片、附件、通用发送/重试行为和无关重构不在本次范围内。

## 行为约定

常规目标仍为 3800；完整表格、代码块或行内元素可以超过目标，但不得超过 20,000。钉钉按 UTF-16 单位计量，企业微信按 UTF-8 字节计量。前缀、提及、重复表头、引用定义和生成的围栏均占用预算。优先选择块、段落、列表项和句子边界；预算允许时将标题与后续首个片段放在一起。保留 URL 原始拼写和完整 Unicode 字符。

超过硬上限的表格仅在行间拆分，并重复原始两行表头。超长代码块关闭并重新打开围栏，保留语言和元数据，优先按行拆分。超过硬上限的不可分元素使用明确标注的纯文本围栏片段，保留完整原文；超长 URL 此时无法在消息间保持可点击。

普通消息每批都在发送第一条之前完成分片计划，使用该批已经拿到的文本，不等待整轮任务未来的输出。候选分片必须逐片符合硬预算；数量不得超过 `ceil((原文大小 + reservedLength) / (targetLength + reservedLength))` 的四倍（至少允许一片）；总大小不得超过 `(原文大小 + reservedLength)` 的四倍加一个完整硬预算余量。`reservedLength` 是调用端已经从正文预算扣除的前缀/头部长度；检查总输出时为每片计入此开销（仅首片使用的提及/头部也保守计入）。这些相对边界为结构边界和原文围栏留出余量，不是固定发送条数上限，也不得靠截断满足。候选不合格时从原文重新规划，将硬上限作为目标；仍不合格则将该批完整原文降级为明确标注的纯文本片段，不再重复 Markdown 容器上下文。嵌套预算 `RangeError` 和候选输出超量只中止当前保结构尝试，随后从原文尝试下一完整方案；最终纯文本尝试的错误仍明确抛出。若纯文本片段仍无法满足边界，则在发送任何片段前报错。

围栏包装占用一半目标预算时改用硬预算。包装或表头较大本身不构成纯文本降级的理由：只要完整候选满足整批边界，就保留代码语言/metadata 和表格结构。只有实际硬预算无法容纳包装加正文字符，或表头加表格行时，才局部降级。生成过程中用整批输出余量限制中间候选数组，超量即放弃该候选并从原文重新规划，避免先生成数千个重复包装。中间片段可能随后合并，因此不将其中间数量当成最终消息数。纯文本片段使用硬预算，避免深层列表前缀在软目标下仅留下几个正文字符。

## 实现及理由

共享的 `channel-base/markdown-chunks` 子路径使用 CommonMark 源码位置，不重新序列化 Markdown。GFM 表格候选只用两行表头验证，避免解析完整大表格；非表格段落另行解析行内边界。普通正文片段若在新边界处变成代码围栏，则使用明确标注、保留原文的降级方式，确保文字可见。重新打开的代码围栏保留原始 info 字符串拼写，包括实体和转义。列表按项、引用按块拆分，保留容器标记并计入预算。不支持的超长结构采用相同的明确标注、保留原文的降级方式。拆分后的消息重复顶层引用定义；嵌套多行引用解析不在本次范围内。

钉钉和企业微信先扣除现有来源/提及前缀再分段。若前缀使正文剩余目标不足常规目标的一半，则以剩余硬预算作为正文目标，避免为极短正文反复发送长标签。钉钉主动消息还将实际序列化的 `{title,text}` JSON 与 15,000 UTF-8 字节上限比较，包括续篇标题。降低 JSON 载荷预算时，从原文重新规划整批候选，而不是再次拆分已经包装的片段。发送计划保存已经完成预处理的原文。尚未发送任何正文分片时，后台标题/头部重组后对整批原文重新规划；一旦开始发送，则保留现有仅重试未发送片段的行为。流式状态卡使用独立更新路径；卡片回退和单个后台 response 使用此普通消息批次规划，不等待整轮任务完成。重新分段不得重复附件准备，也不得改变发送/重试循环。

涉及文件为新增共享分段器及测试、channel-base 清单及锁文件、钉钉 Markdown 工具和适配器/测试、企业微信适配器/测试。解析器不经由 channel-base 通用聚合入口导入。不增加公开配置。

## 验证和验收

仅使用示例域名的合成 URL。定向测试需保留完整链接、所有表格行及表头，保留代码内容及闭合围栏，验证两种计量和前缀预算，并捕获后台重组后的主动消息序列化载荷。覆盖采用有界表头检测的大文档、3789 和 19985 长度的围栏信息、预算临界点邻居、预算允许时必须保留结构的 10.5k–15k 代码 info 和 10.5k–11k 表头、提前放弃超量候选、重复表头、深层有序列表前缀、中文/emoji、来源标签预算及 header/title 重组。同时断言完整原文/正文恢复、分片数量、总输出及单片载荷有界。执行包内单元测试、build、bundle、typecheck 和 lint；完成独立只读 test-engineer 验证、两轮干净自审和代码评审。

基线尝试全局 CLI，修复后尝试构建后的 CLI。如果没有真实平台账户就无法从 CLI 到达通道发送路径，则使用捕获适配器载荷及独立 Markdown 渲染器的测试脚本替代，并记录原因。

## 待完成的平台验收

3800/20,000 是应用预算，不证明端点接受能力。真实钉钉会话回复、主动消息及企业微信 Markdown 发送仍需接收方实测容量和渲染。本地序列化和渲染器测试不能证明真实平台行为。明确保留这一缺口，不因此改变已接受设计。
