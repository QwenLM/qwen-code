# Markdown 消息分段

[English](markdown-message-chunks.md) | [简体中文](markdown-message-chunks.zh-CN.md)

## 问题与范围

钉钉当前按 3800 个 UTF-16 单元切分回复，可能切进 Markdown 链接内部。
企业微信按 3800 个 UTF-8 字节切分，续条可能缺少表头。
合成的知识检索回归样本含有很长的百分号编码引用 URL，覆盖这两种问题。

本次覆盖钉钉普通回复、主动推送、普通消息回退，以及企业微信 Markdown 发送。
不修改交互状态卡片、个人微信、媒体发送、用户配置或附件能力。

## 分段约定

常规目标为 3800，单段上限为 20,000。这是应用层预算，并不表示所有平台端点
都接受 20,000。钉钉按 UTF-16 单元计量，企业微信按 UTF-8 字节计量。
转义后的来源标签、首条 @ 前缀、重复表头和补齐的代码围栏均计入预算。

全文不足 20,000 时仍在目标长度附近分段。优先选择章节、段落、列表项、表格和
代码块边界；加入下一个完整块会超过目标时，先结束当前消息。标题与后面的
第一块内容片段保持在一起，长章节继续拆内部内容块。超过目标但未超过上限的
完整表格、代码块或行内元素保持完整。

超过上限的表格按完整数据行拆分，每条重复原表头和分隔行。单行仍超限时，
连同表头降为带明确提示的纯文本代码片段。超限代码块按行拆分，闭合并重开围栏，
保留语言和元信息；单行过长时采用 Unicode 安全切点。长段落保护完整行内元素，
在普通文本中优先选句末或空白。两种计量方式都不切断代理对。

单个不可拆元素超过上限时，明确提示并以纯文本代码块分条发送。保留全部原始
内容，包括完整 URL 和 `__dac_citation` 数据。该回退无法让超长链接跨消息保持
可点击，因此需要让用户看到这一限制。不缩短 URL，不删除元数据，不上传文件。

## 实现

`channel-base/markdown-chunks` 导出 `splitMarkdown(text, { targetLength, maxLength, unit })`。
通过 `unified`、`remark-parse` 和 `remark-gfm` 识别块级与行内边界。
使用源码位置保留原始语法，不通过序列化重写 URL。引用式链接的定义（包括
嵌套定义）会重复，保证各条消息均能解析引用，定义长度也计入预算。调用者提供
非法预算时抛出 `RangeError`，不发送超限消息或陷入无限循环。

适配器先扣除前缀预算再分段，并按原逻辑添加前缀。钉钉在所有内容片段中保守
预留首条 @ 前缀空间，但只在第一条实际添加。保留发送循环、顺序、媒体提取、
错误传播和从首条未发送消息继续的逻辑。依赖直接声明在 channel-base 中，
同步更新 pnpm 锁文件。

常规 barrel 只导出选项类型，避免 daemon 启动时加载 Markdown 解析器。
短且完整的消息保持原文，未闭合围栏仍会补齐。保留块间分隔与句末相邻空白；
列表在目标附近拆分并保留嵌套，引用块把每行标记计入预算。递归容器最多处理
16 层，再深的剩余原文降为带提示的纯文本代码。大引用定义最多占用一半常规
目标；衍生硬预算不足以安全渲染时，对原始文档降级，避免抛异常或逐字发送。
来源前缀耗尽常规预算时直接报错，保留原有保护。

钉钉主动发送还检查实际 JSON `msgParam` 的 UTF-8 长度，包括标题、续条标题、
转义文本和来源前缀。仅当载荷超过 15,000 字节时，采用更小的结构预算重新分段，
直到每个载荷均符合限制。该保守限制也用于主动单聊。

## 验证与验收

提交的 fixture 仅含合成内容（无末尾换行）：8704 个 UTF-16 单元、
9438 个 UTF-8 字节、12 个引用链接、2 张表格、6 行数据。所有 URL 均使用
`docs.example.com`、虚构区域及文档标识，引用元数据也由测试生成；不包含真实
服务地址或业务记录。回归断言检查允许使用的合成 URL 结构。两种计量方式下都
必须发送多条消息，每个 URL 原样保留，全部数据行仍处于表格中。重点检查第六
和第十个引用 URL 完整，以及第五个数据行所在消息有表头。

单元测试覆盖目标和上限边界、重复原文超过 20,000、中文与 emoji、前缀、长表格、
代码语言和超长单行、引用式链接、行内格式，以及超长链接回退。逐条解析，检查
结构、数量、顺序、内容及载荷长度。适配器回归覆盖普通发送、@ 和已有重试、回退
行为。test-engineer 使用独立 Markdown 渲染器检查捕获的适配器载荷。
执行相关测试、build、bundle、typecheck、lint，再完成两轮干净自审和代码评审。
E2E 计划与本地报告位于 `.qwen/e2e-tests/markdown-message-chunks.md`。

## 平台验证与剩余风险

官方[企业微信智能机器人 WebSocket 协议](https://developer.work.weixin.qq.com/document/path/101463)
允许 `aibot_send_msg` Markdown 内容最多 20,480 个 UTF-8 字节；旧群机器人
Webhook 的 4,096 字节限制属于另一套接口。官方[钉钉主动群聊接口](https://open.dingtalk.com/document/orgapp/the-robot-sends-a-group-message)
限制序列化 `msgParam` 为 15,000 字节，适配器在 UTF-16 应用预算之外单独检查。
本次未确认会话 Webhook 回复和主动单聊的具体容量数值。

需要真实接收会话验证接受与渲染：钉钉会话回复超过 3800 并接近 20,000 单元
应用上限、企业微信内容接近 20,000 字节，以及钉钉主动 JSON 载荷接近
15,000 字节。本地载荷捕获和 Markdown 解析不能证明这两项平台
结果。完成前，应分别说明实现、本地验证和真实平台验收状态。平台 Markdown
方言差异及端点长度限制仍是风险；发送错误继续进入现有错误处理路径。
