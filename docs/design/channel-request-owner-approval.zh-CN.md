# Channel 请求发起者审批

[English](channel-request-owner-approval.md) | [简体中文](channel-request-owner-approval.zh-CN.md)

## 问题

文字权限命令目前在查找请求前就要求共享会话操作员权限。因此，通过准入的用户可以
发起轮次并收到工具确认，却无法回答，使用 `sessionScope: "single"` 的私聊也会
遇到此问题。群聊中的请求发起者同样受影响。

## 决策

允许通过准入的发送者对自己当前交互轮次的待审批请求使用 `/approve`（仅允许
本次）和 `/deny`。该规则覆盖私聊和群聊，不依赖 `operators` 名单，空名单也适用。
拥有某个请求的审批权，不代表获得共享会话管理权。

`/approve-always`、代答其他发送者的文字请求、`/cancel`、`/clear`、`/who`、
`/status`、`/loop`、`/btw`、loop 工具及 steer 保留现有操作员权限要求。
现有原生卡片的发起者校验保持不变，不扩大卡片代审或持久授权权限。

## 实现及边界

保持会话路由和共享会话操作员判定不变。在待审批请求中记录当前 run ID。
对于没有共享会话操作员权限的调用者，查找时仅保留发送者、当前交互轮次、聊天及
线程均匹配的请求。缺失、已取消、无人值守或已被替换的轮次不能提供发起者权限。
在生成歧义列表或显示请求标题之前应用筛选，显式请求 ID 也遵循此规则。

操作员保留现有查找规则，并仍需通过正常会话准入。命名任务选择、原生卡片归属、
权限选项和请求结算复用已有路径。不从 pairing 推导操作员，也不自动改写配置。

## 验证与验收

- 在 `single`、`chat_thread` 和群聊 `thread` 会话中，当前请求的发起者无需
  操作员身份即可仅批准本次或拒绝。
- 真实通过私聊配对的发送者能够回答自己在私聊中触发的请求。
- 其他普通成员不能回答或列出别人的请求；拒绝代答后，请求仍可由发起者回答。
- 拒绝跨聊天或线程的显式 ID、没有交互发起者的请求、已取消轮次和旧轮次请求。
- 共享会话中的非操作员发起者不能通过 `/approve-always` 获取持久权限，也不能
  清空共享对话。
- 现有操作员代审和原生卡片请求结算继续正常工作。
- 运行定向及完整 ChannelBase 测试、构建、类型检查和打包；区分本地测试与需要
  部署新构建后才能进行的真实 IM 验收。

## 风险

本次有意区分请求审批权和会话管理权：空 `operators` 继续禁用共享会话管理和
代审，但不再阻止当前交互请求的发起者仅批准本次或拒绝。请求必须使用当前轮次的
发送者快照，不能使用跨发送者共享的 `single` 会话最初记录的归属。
