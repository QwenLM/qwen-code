# 从聊天标题栏打开工作区文件

[English](2026-10-16-header-workspace-files.md) | [简体中文](2026-10-16-header-workspace-files.zh-CN.md)

## 问题与当前行为

聊天标题旁的文件夹通过悬停提示展示当前工作区，但不能点击。打开现有文件树
需要先展开右侧面板，再选择“文件”。

## 预期行为

点击标题前的文件夹，打开右侧面板并选中当前工作区的“文件”标签。重复点击保持
该标签打开，不创建重复标签。悬停继续展示工作区名称与完整路径。

## 实现与决策

`ChatContextHeader` 接收可选的 `onOpenFiles` 回调。提供回调时，现有文件夹成为
原生按钮，支持键盘激活并显示焦点样式；没有回调时，仍为信息图标。无障碍名称
组合现有的本地化文件浏览操作说明与工作区标签。

`App` 仅在聊天视图且 `filesAvailable` 为真时传入现有 `openFilesPanel` 回调。
该路径已经负责解析面板所属工作区、检查信任和配置、去重标签、选中“文件”、
调整面板大小并打开面板。复用此路径可以保留所选工作区的归属，不增加文件系统
或 daemon 行为。

浮动文件抽屉通过“引用”操作关闭时，焦点必须返回输入区，而非标题栏入口。
记录此次关闭意图，并在抽屉的关闭自动聚焦回调中处理；普通关闭仍恢复入口焦点。

## 范围与约束

新增入口仅位于内置标题栏，同时在文件抽屉关闭路径中保留引用文件后的输入区
焦点。自定义标题栏、输入区工作区标识、后端路由、文件操作以及公开宿主 API
均不在本次范围内。空白任务页面仍遵守现有规则：输入区已显示
工作区时隐藏文件夹。禁用“文件”、工作区未解析或未受信任时，保留信息提示，
不提供点击操作。

受影响的实现为 `ChatContextHeader.tsx`、其 CSS 模块和 `App.tsx`。验证覆盖
相邻单元测试以及现有文件浏览器 E2E 测试。不新增依赖。

## 风险与验证

主要风险是打开错误工作区、重复点击导致面板关闭、丢失提示或键盘访问能力。
针对性测试覆盖操作可用性、正确归属、从其他标签切换至“文件”、重复激活和
提示保留。浏览器 E2E 使用现有模拟 daemon，检查实际文件树和带工作区限定的
内容请求；不将其作为真实文件系统或 Git 后端验证。执行仓库构建、类型检查、
bundle，以及针对性的 Web Shell 测试和浏览器检查。

## 验收标准

- 点击标题栏文件夹后，右侧打开对应工作区的文件树。
- 再次点击保持唯一的“文件”标签打开并选中。
- 其他标签处于激活状态时，点击文件夹切换至“文件”。
- 键盘用户可聚焦并激活按钮，名称和路径提示仍可访问。
- 不可用工作区及禁用“文件”的配置不提供打开文件操作。
- 从抽屉引用文件后，焦点返回输入区，可继续输入。
- 保留现有文件夹隐藏规则与自定义标题栏行为。
