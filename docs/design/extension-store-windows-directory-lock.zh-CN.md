# 扩展仓库 Windows 目录占用问题设计

[English](extension-store-windows-directory-lock.md) | [简体中文](extension-store-windows-directory-lock.zh-CN.md)

状态：已实现。日期：2026-09-14。

## 背景

在 Windows 上更新或卸载用户级扩展时，会抛出一条原始的文件系统错误，没有任何解释：

```text
EPERM: operation not permitted, rename
'C:\Users\<user>\.qwen\extensions\i-have-adhd' ->
'C:\Users\<user>\.qwen\extension-store\rollback\b101694b-c6a6-4a54-9cf1-4f3e8dd7f7c0'
```

这段文字会原样出现在终端里，因为更新命令用 `writeStderrLine(getErrorMessage(error))` 报告
变更失败。事务被干净地回滚了，扩展停留在旧版本，没有损坏任何东西——但这个操作永远不可能
成功，而且提示信息没有给用户任何可执行的下一步。全新安装扩展不受影响。

## 根因

`ExtensionStore.commitArtifact()` 通过把整个已安装目录改名挪进回滚区，来为新版本腾位置：

```ts
await renameWithRetry(destinationDirectory, backupDirectory, 3, 50);
```

在 Windows 上，如果被改名目录的**任意后代目录**上存在一个打开的句柄，`MoveFileEx` 就会失败。
而这个句柄正是 Qwen Code 自己打开的：`ExtensionFileWatcher` 用 chokidar 以无限深度监视
`~/.qwen/extensions`，而 chokidar 会为它发现的**每一个子目录**各挂一个原生
`ReadDirectoryChangesW` 句柄。于是每个交互会话都会锁住每个已安装扩展的每个目录。

重试救不了。`renameWithRetry` 针对 EPERM/EACCES 在约 350 ms 内做 4 次尝试，而这个锁不是瞬时
的：它由另一个正在运行的会话持有，会一直持续到那个会话退出。

周边代码有三个性质塑造了这个修法。
`ExtensionFileWatcher.subscribeExtensionManagerMutations()` 对变更事件的响应是调用
`ExtensionRefreshState.beginSuppression()`，它只是隐藏由此产生的刷新通知，从不释放 chokidar
句柄——所以在活动会话内发起的变更会锁住自己的目标目录。`renameWithRetry` 与
`atomicWriteFile`、原生 LSP 服务、后台 shell 注册表共用，所以它的可重试错误码不是加 store
专用分类的地方。`EBUSY` 也不在重试集合里；它是子进程的工作目录**就是**被改名目录时上报的码，
而这需要清单把 `cwd` 指到扩展内部——hook 用 `process.cwd()`，stdio server 的 `cwd` 取自自己
那条清单配置——所以它进分类是因为失败形态相同，不是因为常见。上游 issue #10187 为托管 Skill
修了同类问题，采用的正是这套备份改名模式，它消除了数据丢失，但没有处理 Windows 占用。

谁持有句柄取决于入口：CLI 子命令在解析参数阶段就退出、根本不启动 watcher，所以那条路径上的锁
属于**其他**会话。这正是修法必须与持有者无关的原因，也是"关掉其他 Qwen Code 会话"不可靠的原因
——UI 路径是被发起会话自己锁住的。

### 实测证据

在 Windows 上的探针（Node 24 + chokidar 4，与本仓库依赖版本一致），被改名目录内含一层子目录：

| 句柄持有者                                        | 祖先目录改名结果          |
| ------------------------------------------------- | ------------------------- |
| 无                                                | OK                        |
| `fs.watch` 在该目录本身                           | OK                        |
| `fs.watchFile`（stat 轮询）                       | OK                        |
| chokidar 递归，仓库同款配置                       | **EPERM**，4 次尝试全失败 |
| chokidar 递归，改名前先 close                     | OK                        |
| chokidar `depth: 1` / `depth: 0`                  | OK                        |
| 目录树内某个文件被打开（授予删除共享，Node 默认） | OK                        |
| 目录树内某个文件被打开（不授予删除共享）          | **EPERM**                 |
| 子进程 cwd 在其子目录                             | **EPERM**                 |
| 子进程 cwd 就是该目录                             | **EBUSY**                 |
| 后代句柄存在时执行 `rm -rf`                       | OK                        |
| 后代句柄存在时执行 `cp -r` 覆盖                   | OK                        |

并已在真实机器上确认：在真实的 `~/.qwen/extensions` 下创建一次性目录，在其他 Qwen Code 会话
运行期间同样无法改名；探针目录随后已清除。最后两行正是这个修法可行的原因：这些句柄只阻塞目录
改名，不阻塞目录删除、删除内容与复制，所以交换可以绕开占用，而不需要任何跨进程协议。

关于句柄的行按**共享模式**拆开（原先一行把两种情况混在一起）：授予删除共享的持有者（`libuv` 就是
这样打开的，所以每个 Qwen Code 子进程都算）既不阻塞改名也不阻塞复制；而不授予删除共享的持有者
（扫描器、独占打开某个文件的编辑器）会以 `EPERM` 拒绝改名，并让对该文件的复制以 `EBUSY` 失败。
后者正是占用分类器在复制路径上会看到的码，也是复制要重试的原因。

## 范围

在范围内：

- 在其他 Qwen Code 会话正在运行时，Windows 上的 `qwen extensions update <name>` 与
  `uninstall <name>` 能够成功；并且即使发起更新的那个活动会话本身就是持有者之一，来自
  `/extensions` UI 的更新也能完成。
- 当交换确实无法完成时，用用户能据此采取行动的语言说明，并保留原已安装版本。
- 让新交换方式的日志恢复语义保持明确。基于复制的回退只限 Windows；日志标记以及由它们推出的规则
  ——已了结的事务不阻塞下一次变更、无法重试出可加载产物的回滚会中止调用方、被卡住的回滚按延后的
  重试窗口再试——在所有平台生效。

范围之外：

- 不引入会话之间的跨进程协调协议，也不改动 watcher 挂到扩展目录树的方式。
- 不修改 `renameWithRetry` 对其其他调用方的语义。
- 不试图让基于复制的交换具备原子性。它做不到；本设计是把这种情况纳入处理，而不是假装它不存在。

## 方案

两部分。第一部分让交换能容忍别的进程持有着的目录；第二部分让仍然换不动的情况可读可行动。

**A — 可容忍占用的交换。** 当备份改名在 Windows 上因占用类错误失败时，整个事务改用基于复制
的交换。策略只决定一次，写入日志，并由应用、回滚、恢复三条路径一致使用：

```ts
swapStrategy?: 'rename' | 'copy';
```

`ExtensionTransactionJournal` 增加这个可选字段，再加三个：`rollbackBlocked`（回滚没能完成，
`rollbackRetryAt` 说明恢复最早何时可以重试欠下的那一步）与 `cleanupPending`（只差这笔事务的
收尾清理）。`rollbackBlocked` 标记的是一笔尚未了结的事务，因此它仍会拒绝该目标的变更；
`cleanupPending` 标记的是已了结的一笔，什么都不拒绝。字段缺失即表示 `rename`、false 与"没有窗口"，因此
旧版本写入的日志恢复行为不变，`version` 仍为 `1`。策略在
第一次不可逆写入之前落盘。改名路径本身不变：destination → backup 改名，staging → destination
改名。复制路径是：

1. **以复制做备份。** 把 `destinationDirectory` 复制到 `backupDirectory`。已实测证明在后代句柄
   存在时可行。复制先落到 `${backupDirectory}.partial`，再用一次 rename 发布，因为"复制一半的
   备份"比"没有备份"更糟：恢复时它会覆盖一个其实仍然完整的目标目录。复制过程中崩溃会留下未被
   发布的 `.partial` 目录树；两条日志清理路径都会删除它，所以恢复该事务时会一并清扫。
2. **先对齐类型，再以复制应用。** 只删除那些与同相对路径的暂存条目类型不同的目标条目——`fsp.cp`
   拒绝替换它们，而且在清理有机会触达之前就拒绝——然后执行 `fsp.cp(stagingDirectory,
destinationDirectory, { recursive: true, force: true })`，并保留符号链接与时间戳
   （`dereference` 保持 false、`preserveTimestamps` 与 `verbatimSymlinks` 开启）。复制会重试 store 归类
   为占用的错误，这与 `renameWithRetry` 重试的 `EPERM`/`EACCES` 是不同的一对：它加上 `EBUSY`，
   因为工作目录就是目标的子进程上报的是这个码；它去掉 `EACCES`：B 节实测的占用拒绝全部以
   `EPERM` 或 `EBUSY` 到达，把 `EACCES` 排除在外，普通的权限问题就还是普通错误、不会被当成
   锁来重试。残留情形如实说明：若 Windows 占用真以 `EACCES` 表现，这些步骤拿不到重试也拿不到
   复制回退——而同一笔事务里的 `renameWithRetry` 调用确实会重试那个码。它之所以要重试，是因为扫描器或索引器可能短暂持有某个文件，而这
   正是当年只走改名路径的代码在那次调用周围吸收的情形。这些重试共用每笔 store 操作的一份额度
   （`LOCK_RETRY_BUDGET_MS`，一秒的
   sleep），而不是每次调用各一份：被重试的步骤会整步重跑，因此一次重试过的复制最坏是四趟整树
   复制，但条目再多也不会让 store 锁的持有时长成倍增长。`verbatimSymlinks` 是让相对目标保持相对的
   关键：不开它，`fsp.cp` 会把
   目标改写成指向 staging 目录的绝对路径，而提交随后会删除那个目录。
3. **清理。** 拿目标树与 staging 树对比遍历，删除 staging 不携带的每一条路径，并在两侧同为目录
   时递归进入。遍历放在应用之后，正是它让刚复制进去的内容不会被误判为陈旧，也让"崩溃后扩展
   内容缺失"的窗口在复制式交换允许的范围内尽可能窄。
4. `uninstall` 时，把第 2-3 步换成：清空目标目录的子项，然后移除目标目录本身。不是真实目录的
   目标会在清空之前被下面的根守卫拒绝；清空自身仍保留叶子规则，所以万一目标在守卫与清空之间变
   成了链接，也只会 unlink，而不会顺着它清空。若清空失败，说明有进程把它当作工作目录；从备份
   复制恢复，并抛出占用错误。
   不能留下一个没有清单的空壳目录，因为 `pathExists()` 会把它报告成"已安装"从而阻塞之后的重装。

copy 策略会拒绝真实路径离开扩展根的目录，因为下面每个遍历都会触达该根，而 `readdir` 会跟随根上
的链接；它也会在开始复制之前拒绝一个不是真实目录的目标。遍历只枚举真实目录，否则就在该根处
停下，因此绝不会顺着链接读写；unlink 一个链接根不是它们的职责。`emptyDirectory` 会就地 unlink
一个链接根，而 `rollbackJournal()` 在 copy 模式的遍历之前对目标调用
`removeNonDirectoryRoot()`——这正是恢复需要的调用方检查，否则 `fsp.cp` 就会冲着链接去，以
`ERR_FS_CP_DIR_TO_NON_DIR` 失败。

`rollbackJournal()` 增加反方向：当 `swapStrategy: 'copy'` 时，它把 `backupDirectory` 复制覆盖到
目标上并清理备份不携带的内容，而不是先清空目标。覆盖式恢复正是"条目删不掉时不留没有清单的空壳"
的原因：交换失败了，但它失败时覆盖的树就是已安装的那棵。恢复保留原有的阶段比较——
`recoverTransactionsUnlocked()` 与提交侧的守卫 `assertNoPendingTransaction()` 共用同一个"这笔
事务是否还需要回滚"的判定——只是调用按策略分派的回滚。catch 遇到占用错误时怎么处理，取决于它
击败的是哪一步，因为两者留下的状态不同：

- **回滚**被吸收——打上 `rollbackBlocked` 并保留，让本次操作继续、由后续恢复重试——但只在"重试
  仍可能产出一个可加载产物"时如此：目标已经带着其备份的全部顶层条目且类型相同，欠着的恢复其实
  已经完成——多出来的条目正是已披露的残留，由后续的清扫负责。
  存在不等于完整，一个幸存的文件名也不等于：清单立在半清空的树里不是产物，而未转换的
  `plugin.json` 根、link 安装只有元数据的根，虽都不带 `qwen-extension.json`，却是产物。
  通不过这个比较的状态（被清空却没能恢复的目标、根本没有备份的崩溃安装）会中止调用方，而不是
  照常供读。吸收还要求标记确实落了盘：记不下自己窗口的日志绝不能被后续的处理读成已了结，所以
  记不上的拒绝保持响亮。标记先于拒绝落盘，因此拒绝本身也拿到
  窗口，等待中的读取直接拒绝而不碰目录树。在 Windows 上这道拒绝就是占用
  目录错误，原始 errno 作为 cause 保留；在其它平台保留 errno，因为那里的权限拒绝并不是占用。
- **清理**在回滚已经恢复目标之后失败时，改为打上 `cleanupPending`：重试的是删除
  这一步，而不是重新恢复，因此已了结的回滚不会被再次覆盖到正在使用的树上。这一步负责 staging
  目录、copy 模式回滚从中恢复的那份备份以及日志文件本身；删除前会先把备份降级到未发布的
  `.partial` 名下，所以删到一半的备份绝不会被误恢复。锁原因的错误在这里不向调用方
  报告：日志留下，标记给欠下的这一步同样的重试窗口，被持有的删除不再给每次读取加税；
  非锁原因的错误先打标记再重抛，见下文。

`rollbackBlocked` 会让该日志不参与 generation 比较，因此还欠着回滚的事务永远不会被当成已提交。
由于持有者可能是活得比本次会话更久的进程，标记还带一个重试期限
（`ROLLBACK_RETRY_DELAY_MS`，与被锁住的清理共用）：窗口内的读取跳过欠下的那一步而不是重做——若重试仍产不出
可加载产物，则直接拒绝而不碰目录树，Windows 用占用文案、其它平台用未解决事务的错误。比这个
延迟更远的期限是时钟挪了位，不是活窗口，因此按已到期处理、重试自行恢复——目标是自愈而不是被
永久钉死。针对窗口正在等的那个目标本身的变更，只要重试还能产出可加载产物就不等：守卫立即给它
一次欠步重试，若再次失败，以刚产生的诊断拒绝；重试产出不了的，与读取一样被窗口检查拒绝，直到
期限过去。非占用原因
的失败会从两步都中止调用方——回滚那一步不打标记直接重抛，清理那一步先打标记再重抛——写不进去的
标记同样中止调用方，因为未标记的日志绝不会被吸收，重试也绝不会从删了一半的备份再恢复一次。

**B — 可行动的失败提示。** 在既有 store 错误旁边增加：

```ts
export class ExtensionDirectoryLockedError extends Error {
  readonly code = 'extension_directory_locked';
}
```

消息点出扩展目录名——绝不会是内部的 `rollback/` 路径，那里用户无从检查——并说明仍可能有进程持有
该目录，发起会话也包括在内。凡是后代句柄可能击败交换的步骤都会抛出它：暂存改名、`.partial`
预清理与备份发布 rename、备份复制、应用复制、清理遍历、以及 copy 模式卸载的清空与移除。回滚
本身失败仍走既有的 `AggregateError` 路径；一旦恢复不再重试某笔回滚，守卫为该目标给出的就是这条
错误。
占用分类放在这里而不是 `renameWithRetry` 里，覆盖 `EPERM` 与 `EBUSY`——包含
`EBUSY` 是因为工作目录就是被改名目录的子进程上报的是这个码而不是 `EPERM`，
而这两个码否则既不重试也不解释。在 Windows 上权限拒绝同样上报为 `EPERM`（libuv 把
`ERROR_ACCESS_DENIED` 与 `ERROR_PRIVILEGE_NOT_HELD` 都映射到它），因此只有 `symlink` 失败可被区分——
而它不是占用。

## 决策与否决的方案

决策：

- **仅限 Windows。** 回退同时以 `process.platform === 'win32'` 和"错误属于占用类"为条件。在
  Linux lane 上用同样的句柄实测过：那里改名不受阻，所以 POSIX 侧什么都不变，也不会有任何 CI
  平台在无声中失去原子性。
- **复制备份，而不是跳过备份。** 跳过更省，但会让每一条未提交的 copy 模式日志变成不可恢复的
  半状态。复制能完整保留现有的回滚与恢复设计，代价只是在这条本来就已经很慢的路径上多复制一棵
  树。
- **staging 在提交干净之前留在磁盘上。** 这一点现在已成立，也正是它让一次在应用中途死掉的 copy
  模式事务能被后续运行回滚。
- **提交会拒绝在未解决的事务之上堆叠。** 写日志之前，提交会检查 `transactions/` 中是否存在解析到
  同一目标、且未被上面那个共用判定了结的日志。真正未解决的那一笔会被拒绝；被占用者卡住的那一笔
  会用占用目录提示拒绝，因此重试得到与造成卡住的尝试相同的诊断。已提交、只等清理的事务算是已
  了结，永不拒绝。

否决：

- **在变更窗口内释放发起会话自己的句柄。** 给 watcher 加 `pause()` 只在"发起会话是唯一持有者"
  时有用，多开一个会话就失效；而 `beginMutation()` 有 18 个调用点，多数根本不碰产物。凡是
  rename 可达的场景 copy 都可达，所以它换不到任何可达性。
- **Windows 上改用轮询 watcher。** `usePolling` 不持任何句柄，代价是整棵扩展目录持续的 `stat`
  流量，而且仍然看不见编辑器、资源管理器、杀毒扫描器、运行中的 MCP server。
- **"变更进行中"标记加心跳。** 只能协调 Qwen 自己的会话，还要处理超时、崩溃残留与启动竞态，而
  复制路径本来就已经无条件覆盖了这些情况。
- **加大重试预算。** 锁由另一个会话持有到其退出；350 ms 内 4 次尝试对瞬时锁已经太多，对永久锁
  又远远不够。

## 风险与约束

- **copy 模式不原子。** 在"应用"与"清理"两步之间崩溃，可能让目标目录新旧文件混杂，而日志仍是
  `prepared`。此时恢复会把备份复制回滚，与改名路径处理未提交事务的方式完全一致——即使已经记录了
  `artifact_swapped` 也是如此，因为让事务变为已提交的是快照。窗口很小且状态始终可判定，但它确实
  比改名路径更宽。
- **被打断的备份会把它的 `.partial` 目录树留到日志被清理为止。** 日志先于复制写入，所以
  `.partial` 属于某个事务，而该事务的两条清理路径都会删除它——这正是不需要进程级扫描的原因；
  日志被隔离而不是被重放，是唯一会把它永久留下的情形；被占用错误或其它故障原因击败的回滚或清理
  同样会把备份和未发布的 `.partial` 留在磁盘上，但会留下拥有它们的日志，由后续操作删除。在持有者仍持有
  期间，每个受影响的目标会在 `rollback/` 下留下一份完整树拷贝，没有上限。回滚与回滚后的清理
  会在 debug 级记录这件事；已提交状态不再报告的清理按设计保持安静，因为带窗口的重试归日志
  负责。
- **并发的带外修改**：复制窗口内对目标的第三方修改可能被清理掉或被覆盖。改名路径存在同一类竞态、
  只是时序不同；本设计不会让它变安全。
- **额外 I/O**：占用路径上每次更新要复制两整棵树。自带 `node_modules` 的扩展会让这点比较明显
  ——本机实测最大的是 298 个文件、55.6 MB——但有界，且只在 Windows。被重试的复制是整树一趟，
  所以某个步骤重试四次就会写四趟树；下面的额度限制的是 sleep，不是趟数。
- **重试按每笔 store 操作设上限，而不是按调用。** 一笔事务一份额度，一次恢复过程也一份，因此条目
  各自被瞬时持有的树，只会在这笔操作的第一秒内被重试，之后即以占用目录错误失败，而不是为每条目
  烧掉一次退避——那样的 store 锁持有时长是等待会话约 27 s 的预算撑不住的。
- **运行中子进程造成的 EBUSY 不是复制能解决的**，当该进程的工作目录就是扩展目录本身且操作是卸载
  时。这种情况以 B 的提示收尾，这正是预期结果。
- `assertRecoveredJournalPaths()` 只校验日志路径；六个可选字段（`swapStrategy`、
  `rollbackBlocked`、`cleanupPending`、`rollbackRetryAt`、`rollbackHeld`、`orderMs`）的 schema
  校验在 `readJournalUnlocked()` 里，它必须在不放松任何路径检查的前提下接受它们。策略无法识别时
  隔离该日志。
- 复制与清理不得顺着符号链接走出目标树——staging 内容已由 `archive-safety` 校验过，但清理时的
  遍历必须把符号链接当作叶子节点。同一条规则也覆盖根：遍历遇到不是真实目录的根就停下而不穿过它
  枚举，`emptyDirectory` 对链接根只 unlink 而不清空其目标，恢复路径则在复制之前替换它——这正是
  "用 junction 挪出去的扩展不会被顺着链接删掉或写穿"的原因。
- **类型变更在复制之前对齐。** 带 `force` 的 `fsp.cp` 无法把文件替换成目录，反向亦然，因此这类
  条目在复制之前被移除——这是复制前唯一允许的删除，因为一刀切的"先清理后复制"会扩大崩溃窗口。
- **失败的交换留下多余内容；出现空洞还需要第二个失败。** 覆盖式恢复意味着删不掉的条目会留下陈旧
  文件，而不是把目标目录掏空；下一次成功的交换会把它们清理掉。`removeKindConflicts` 仍可能先删掉
  一个条目、而它的替代复制随后失败，因此被同一个持有者击败的 copy 模式回滚，可能让该条目在日志被
  标记、被重试期间一直缺失。磁盘上的目录树与快照已提交的 generation 之间没有任何对账，所以这个
  窗口里的读取拿到的是目录当前的内容——同名文件被覆盖到一半时可能是新字节，甚至可能短暂地
  根本读不到某个文件，因为复制会先删除目标再写入替代——而不是已提交的
  旧版本。目标缺少备份携带的顶层条目、条目类型不符、或根本没有备份可比的状态会被拒绝而不是照常供读——标记先
  落盘，因此拒绝自身也保有窗口；把未解决
  事务暴露到读路径留给后续。

恢复已安装树，包括清空已经删掉的那个子项；非占用原因的回滚失败仍到达调用方，欠下的步骤被记录并按同一窗口重试、日志留在事务扫描中，既避免之后每次操作都重做那条注定失败的恢复，也让残留仍归其所有者；版本之间类型发生变化的条目
被对齐后复制得以执行；被打断的备份留下的 `.partial` 目录树被恢复流程删除；copy 交换后 staging 目录

被隔离；不带这些新字段的既有日志保持原有恢复行为。在 Windows 之外无法复现的是真实的操作系统级占用
——某进程把工作目录设在该目录上——它由 harness 与上面的 `EBUSY` 行覆盖；它以何种分支收尾，这里用
"平台改为 win32 + 对目标根注入 `EBUSY`"覆盖。

E2E harness 为一个扩展根目录树的每个目录挂一个原生监视句柄，并驱动另一个 CLI 进程走更新与卸载，
先打隔离 `HOME`，再打真实 profile（占用方是真实运行的会话）。记录结果：已发行 CLI 两个操作都
`EPERM` 失败、fixture 停留在旧版本；本构建两个都完成、清掉了新版本删除的文件，并且 `state.json`、
`rollback/`、`transactions/` 均无残留。Linux lane 用同样的句柄跑同一套，完全不报占用。

验收：

- 在 Windows 上、至少还有一个其他交互会话运行时，`qwen extensions update <name>` 能完成，且新版本
  可加载。
- 无法完成的交换会报告 `extension_directory_locked` 并点出目录名，同时原版本仍已安装且可加载。
  有三种状态可能不同：被同一持有者击败的 copy 模式回滚，可能留下陈旧内容，或留下一个已删除却没能
  复制回来的条目，直到后续操作把目录树收尾；重试无法产出可加载产物的回滚会让调用方失败、目标处于
  不可用状态，因此该扩展不被报告为已安装，后续 store 读取会持续失败直到持有者释放；而以 store 无法
  归类的故障失败的回滚会保留日志与备份、按一个窗口重试而不是每次操作都重试，拒绝时用"事务未解决"
  的文案而不是"目录被占用"的文案（见"风险与约束"）。
- `npm run build && npm run typecheck` 与被改动文件在 `packages/core` 的单元测试全部通过，Windows
  与 Linux lane 都要过。
- diff 中 POSIX 代码路径仍走改名交换。在所有平台生效的是：日志标记及其规则（已了结的事务不阻塞下一次
  变更，真正未解决的那一笔被拒绝，无法重试出可加载产物的回滚中止调用方，被卡住的回滚按延后的重试窗口再试）；
  以 generation 键最新优先重放、同代日志用写一次且永不重算的顺序键打破平局，恢复与提交守卫共享该顺序；同一目标较新日志本轮被推迟或因故障失败时，较旧日志都不会跟着落到底；非占用原因的回滚失败记录欠下的步骤并按同一窗口重试、日志留在扫描中，既避免之后每次操作都重做那条注定失败的恢复，也让残留仍归其所有者；回滚与日志收尾的删除带占用类重试，且每笔 store 操作一份额度；这些收尾会一并删除
  `.partial` 兄弟目录；以及在 Windows 上由被卡住的回滚留下的、带占用目录文案的拒绝。
