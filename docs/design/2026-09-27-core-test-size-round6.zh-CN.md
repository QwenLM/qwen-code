## 基线与目标

冻结 `37412a57d473525a81f87e4ca36447981950d9a9` 为基线：计入辅助代码，
core 测试为 491,361 行、17,800,460 字节。用户授权更激进的测试设计实验，
包括删除冗余用例和重新分配重叠覆盖。生产代码保持不变，main 与实验分支分开。

上一轮三个文件共减少 232 行。本轮在多个独立行为域寻找可重复的模块级收益。
同文件文本重复率已降至 0.4%；选题需要检查行为重叠与测试判断逻辑的成本。

## 候选方法

- 用明确的完整预期输出替代测试侧解析和零散检查，保留输入分区与失败情况。
- 一次构造完整对象或生命周期，检查完整结果，替代只检查同一行为局部的多个用例。
- 将重叠行为交给实际实现该行为的层负责，保留调用连接、选项传递、错误处理和交互边界。
- 明确保留的行为契约，以及能够区分错误实现的负向用例，再删除重复的正向示例。

先选择三到五个边界明确的行为域。预估收益用于选题，不作为验收标准。
移入 fixtures 或 snapshots 的代码仍计入体积。预期输出必须独立于被测实现。

## 执行与证据

接受改动前记录假设，以及原有行为由哪些保留检查负责。使用独立构建、生产实现
修订相同的 Linux 检出目录。保存基线、候选源码字节、命令、工具版本和原始报告。
上一轮证据保持原样。

先运行受影响测试并比较体积、行和分支覆盖。有实际收益的候选再运行相关历史
故障回放，以及对边界内实现和必要依赖的完整静态 mutation。历史语料未覆盖目标
行为时明确记录缺口；必要时补充独立定义的故障探针，与真实历史缺陷分别标记。
在比较前冻结故障。

使用现有测量工具，保留请求与实际执行的测试清单、健康运行失败、采集失败及
mutation Timeout。检查诊断能力和用例独立性：前面的断言失败可能遮住后续检查。
覆盖率和 mutation 一致支持限定范围内的结论；关键负向用例还须经过语义审查。

## 验收与停止

候选须同时减少行数和字节数，通过受影响单测、构建与类型检查，保留已观察到的
历史故障检出和可判定 mutation 检出，且覆盖差异有证据解释。失败或不完整的原始
门禁保持失败；附有限制的保留决定单独记录。记录被拒绝的尝试及原因。当一种方法
的收益很小，或诊断与边界成本超过收益时，停止扩大该方法。

接受的行为域分别提交。一批结束后运行完整 core 套件，与冻结基线比较，并完成
两轮完整审查。之前观察到的 prune 失败、成对 Timeout 和原因未明的 lease 失败
继续保留，新失败需要调查。本轮不预设提速，也不将局部减量比例外推到整个包。

Provider 测试保留全部 16 个名称和原始输入。计入体积的新辅助代码比较手写的
完整请求消息，并验证源请求不变。两个用例继续执行真实的两轮 HTTP 对话，服务
创建与销毁现在计入用例超时。原 Fireworks 标题提及工具调用，保持原样的输入
实际仅覆盖 thought/text 历史回放。

### C1 历史故障与 C4 诊断

冻结计划包含九个历史故障。三个适用故障两侧均检出；六个反向补丁无法应用于
冻结实现，继续排除。适用故障的健康运行两侧均通过。比较器记录采样完整、
检出无损失、健康基线无失败。

| 适用历史故障                             | 失败用例数，前 → 后 | 检出依据                                       |
| ---------------------------------------- | ------------------: | ---------------------------------------------- |
| `1103a95f2b`，非字符串参数转换           |             50 → 31 | Schema 测试中的断言失败                        |
| `6a5c041885`，未知 format 警告           |               1 → 1 | 保留的自定义 format 警告断言                   |
| `3ba01990e1`，Fireworks reasoning mirror |               1 → 1 | 未改动的 pipeline 测试中的 native-history 断言 |

Fireworks 反向补丁还会移除 provider 模块，使两侧 `fireworks.test.ts` 各出现一个
采集错误。检出依据是独立的 pipeline 断言；本次回放不能证明压缩后的六个
Fireworks 用例能检出该故障。此语料没有直接针对 Hook 的历史故障。

Schema 故障暴露了明确的诊断成本：**减少了 19 个独立失败标签**。25 个失败
保留原名，四组合并将 23 个失败变为四个，另有两个一对一重命名。每个旧失败
都对应一个实际失败的候选承接用例。六个重命名或合并用例均在前面的 `valid()`
断言处失败，后续完整对象检查没有执行；首先报告的 integer/name/enabled 错误
遮住了后面的字段。文件定位保持相同，但每个故障失败用例数的总体中位数均为
一，会掩盖这部分定位粒度损失。检出保持不能证明诊断粒度不变，也不能证明
每个合并字段对单点回归的独立检出能力。

### 可继续使用的方法

实测有效的方法是：在完整契约中同时检查转换与合法值保持不变、明确事件边界
契约，以及计入辅助代码成本的共用请求生命周期检查。本轮在独立行为域取得较大
局部减量；整个 core 实际减少 1,060 行，尚未证明运行速度提升。

后续对 client、LLM chat 和 scheduler 的有限抽查，没有找到另一个证据充分、
预计至少减少 500 行的有界实验。最明确的 scheduler 终态重复预计可省 100–180 行，
仍未经过实验验证。
