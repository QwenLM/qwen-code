# 全新启动性能：可输入时间与 RSS

[English](2026-09-24-fresh-startup-performance.md) | [简体中文](2026-09-24-fresh-startup-performance.zh-CN.md)

状态：已作为草稿 PR 实现。第 9 节列出了仍待决定的事项。

## 1. 问题

在干净的机器上，`qwen` 大约需要 2.5 秒用户才能开始输入。前约 2 秒终端一片空白，整个进程树占用约 575 MB RSS。`qwen -p` 大约需要 2.1 秒，第一个模型请求才离开进程，即使对端是即时应答的本地模型服务也是如此。

此前没有任何度量覆盖这些问题。现有的启动剖析器在最后一个进程内部、模块加载完成之后才开始计时。它报告约 1.8 秒到达 `input_enabled`，而用户实际等待约 2.8 秒；也没有 CI 任务跟踪交互式启动。

## 2. 方法

我们遵循 [How we made claude.ai 3x faster in two weeks](https://claude.dev/blog/how-we-made-claude-ai-faster/)（Anthropic，2026）中的做法。其原则在本工作中的应用如下：

1. **度量用户能感知的时刻，取 p75。**用户感知的时刻是"输入的按键显示在输入框中"，而不是某个内部标记。
2. **能度量的问题才能被解决。**每一段慢的环节都先被追踪，再用一个改动可以推动的数字把它呈现出来，然后才动手修改。
3. **墙钟时间是真相，但噪声太大，不适合做门禁。**因此用确定性代理指标作为支撑：进程数、加载的 JS 字节数，以及 Valgrind 下的 CPU 指令数。每个代理指标在采信之前都与墙钟时间做过对照。
4. **不稳定或不相关的指标一律丢弃。**见第 8 节。
5. **防范"可用"之后的不稳定。**文章中是页面加载后的布局偏移，这里对应可输入之后屏幕仍在变化。

### 2.1 干净环境

- **安装。**`corepack pnpm install --frozen-lockfile`，然后构建并打包。Node 22、Linux、4 vCPU。
- **每次运行使用全新状态。**每次运行都新建 `HOME`、`QWEN_HOME`、`QWEN_RUNTIME_DIR`、`XDG_*` 和 `TMPDIR` 目录。工作区是一个空的 git 仓库，`settings.json` 只包含认证类型和模型名。环境变量只保留 `PATH`、`LANG` 和 `TERM`。
- **模型。**一个即时应答的本地回环 OpenAI 兼容桩服务。
- **入口。**真实的 `qwen` bin 入口 `scripts/cli-entry.js`。
- **终端。**120×40 的 node-pty 终端，屏幕由 `@xterm/headless` 重建。它像现代终端一样应答 DA1 与 OSC 11；"静默"变体不做任何应答。

**代理指标验证：**

- **D3 与墙钟时间一致。**在 `--version`、`--help`、`-p` 以及缓存预热后的 `-p` 上，D3 与墙钟时间的 Pearson 相关系数 r = 0.9997，重复运行的结果相差在 0.008–0.04% 以内。
- **D3 看不到等待。**终端从不应答 OSC 11 探测时，墙钟时间增加 165 毫秒，但指令数没有增加。

### 2.3 实验流程

- **每个实验一个假设。**每个假设的依据来自 CPU 剖析、strace、esbuild metafile 或屏幕差异。
- **交错 A/B。**每个改动都与其前一版本按 ABBA 交错成对运行：20–30 对，每次运行使用全新 HOME。报告成对差值的中位数，以及改动在多少对中胜出。
- **噪声下限。**将两个版本放在相同目录深度下做 A/A，未见偏差：成对中位数约为 0，胜率约各半。第一次 A/A 尝试曾暴露出 24 毫秒的路径深度偏差，采用等深布局后消除。
- **保留或舍弃。**只有推动了指标的改动才被保留。任何指标出现回退，都先查明根因再继续。

### 5.1 重新启动

重新启动是最大的单项开销，却没有人说得清它的用途。

**它原本做什么：**

- **堆上限。**它会加上 `--max-old-space-size`，但只在 `advanced.autoConfigureMemory` 为 `true` 时才加。默认值为 `false`，因此默认情况下子进程不会得到任何额外参数。
- **监管。**父进程常驻只为处理三类事件：
  - 退出码 42：文件夹或 IDE 信任变更，重启会话；
  - 退出码 43：`/update` 请求重新启动；
  - IPC "退出时更新"消息。
- **环境变量交接。**它会传递哪些变量来自 `.env` 或设置。这只在跨进程边界时才有意义。

**改了什么。**在 POSIX 上，当没有内存参数、且当前模式不需要单独的监管进程时，CLI 将自身标记为进程内监管：

- `relaunchApp()` 执行退出清理，然后以相同命令行 `execve`。如果 gc 是在运行时暴露的，则额外加上 `--expose-gc`。
- `relaunchForUpdate()` 在进程内运行更新处理函数，并以其返回码退出。当返回码为 44 时，启动器的退出钩子负责重新启动。
- 其他所有模式保留受监管的重新启动。由于启动器不再通过 argv 传递 `--expose-gc`，其子进程按同一规则获得该参数。

## 7. 风险与行为变化

1. **退出时更新**（standalone 与 `updateCommand` 安装）。由于没有父进程，启动时的检查改为提示 "Run /update to install the update."，而不是在退出后安装。
2. **信任重启后再 `/update`。**原地信任重启之后，同一会话中再执行 `/update` 会以退出码 44 退出而不是重新启动，因为新映像中没有启动器的退出钩子。更新本身仍会安装。
3. **堆栈。**启用 `minifyWhitespace` 后，打包产物的堆栈保留函数名，但行号失去参考价值。
4. **短会话。**更新检查会等待 3 秒，因此短于 3 秒的会话会跳过它。
5. **旧版 IDE 发现。**IDE 进程遍历现在只在 VS Code 终端中运行。版本低于 0.5.1 的旧版 VS Code 配套扩展，如果经由会改写 `TERM_PROGRAM` 的终端（例如 tmux）访问，将失去 pid 文件发现能力。
6. **编译缓存。**缓存位于操作系统临时目录（约 9 MB），安装或升级后的首次启动慢约 100 毫秒。
7. **进程链。**在 POSIX 上不再设置 `QWEN_CODE_LAUNCHER_PID`。只有 Windows standalone 更新器读取它，而 Windows 仍保留子进程方式。
8. **核心受控区域。**本改动涉及 `packages/core/src/**` 与 `packages/cli/src/config/**`，需要维护者审阅。

## 8. 被否决的指标

| 指标                                   | 否决原因                                                                                      |
| -------------------------------------- | --------------------------------------------------------------------------------------------- |
| 外部帧数或写入次数                     | CV 为 12–18%，受 PTY 分块影响                                                                 |
| strace 的原始子进程数                  | 不可重复：`git` 调用次数会变化，`ps` 遍历次数取决于进程树深度                                 |
| Valgrind 下交互式的指令数              | 离散度约 10%，因为定时器驱动的工作量会随减速放大；需要一个在 `input_enabled` 时退出的基准钩子 |
| 以内部 `to_input_enabled` 作为总体指标 | 漏掉了用户实际等待中约 1 秒（35%）；仅保留作阶段拆解                                          |

## 9. 待决定事项

每一项都需要维护者与作者在转为正式 PR 前做出决定。

1. **退出时更新。**保留 "Run /update" 的回退，还是通过退出钩子恢复退出后安装？
2. **信任重启后再 `/update`。**接受这一边界情况，还是让原地重启 re-exec 启动器，以保留其退出钩子？
3. **E6 堆栈。**接受、提供 sourcemap（并决定如何加载），还是撤回 E6（让出 23 MB 与约 40 毫秒）？
4. **更新检查延迟。**3 秒是否合适，还是应该在会话空闲时再运行检查？
5. **IDE 遍历。**以 `TERM_PROGRAM=vscode` 作为门控，对旧版配套扩展是否可以接受？
6. **拆分。**作为一个 PR 合入，还是拆成独立的 PR？一种自然的拆法是：
   - E1+E8（进程链）；
   - E2（编译缓存）；
   - E3/E4/E5/E7（启动副作用）；
   - E6/E9/E10（打包）。
7. **基准工具与 CI。**是否提交基准测试工具，并增加 D1–D3 的 CI 棘轮？D1/D2 任何增加、或 D3 增加超过 0.2% 时失败；另由夜间任务下调上限并跟踪 J1–J3/S1。基准工具不在本 PR 中。
