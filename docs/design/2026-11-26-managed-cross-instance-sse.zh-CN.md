# Managed 跨实例事件流唤醒

[English](2026-11-26-managed-cross-instance-sse.md) | [简体中文](2026-11-26-managed-cross-instance-sse.zh-CN.md)

状态：实现设计，2026-11-26。现状结论对照 `main` 的 `baff3932e7` 核实。本文是"多个 Java 控制面实例挂在负载均衡后面"的其中一个切片，只改变 Session 事件流得知"有新事件"的方式。它实现了[存储与事件架构 §7.1](2026-09-20-managed-agent-storage-event-architecture.zh-CN.md#71-sse-与多实例) 中按节点检查水位的做法，但去掉了前面的节点间通知。

## 1. 问题与现状

每个 Session 事件都持久化在 SQL 中，流连接可以在任意实例上按游标续读。只有"有新事件了"这个信号是进程内的：

- 执行 Turn 的实例写入公开事件，并在提交后把它们发布到进程内的 `SessionEventHub`。
- 流在这个 hub 上等待；等不到时，经过 `qwen.managed-agent.events.poll-interval`（默认 5 s）再重读 SQL。
- MQ 公开事件通道在接收实例上只触发物化，不会到达它的 hub。

多个实例挂在负载均衡后面时，如果流连在不执行该 Turn 的实例上，流式输出每 5 秒才前进一次。

## 2. 目标与范围

目标：

- 任意实例上的流都能在几百毫秒内看到另一个实例提交的事件。
- 不引入新基础设施：不需要 MQ、服务发现或实例间调用。
- 写入事件的实例上的流不增加任何存储读取。
- 保留现有的游标、回放、resync 和兜底行为。

不纳入：流的线上契约、5 秒兜底的配置、MQ EventTransport，以及其余多实例问题。

## 3. 设计

### 3.1 水位轮询器

每个实例在独立线程上运行一个轮询器，每 200 ms 一次：

1. 取出本实例 hub 中有订阅者的 Session；没有就不查询。
2. 用一条 `(tenant_id, session_id) IN (...)` 成对查询，读取它们的公开事件水位，即 `SESSION` 流的 `ma_event_stream.last_sequence`。超过 500 个 Session 时，按 500 个一批拆分。
3. 对于首次读到的水位，或比上次读到的更大的水位，通知 hub。

某个 Session 没有订阅者后，轮询器会忘掉它，所以订阅者再次出现时会重新收到通知。读取失败时记一条 debug 日志，下一次轮询继续；在此期间流退回到各自的兜底轮询间隔。

### 3.2 hub 通知

`notifyCommitted(session, lastSequence)` 在 hub 已持有到该序号的事件时什么也不做，发布这些事件的实例就属于这种情况。否则它把该 Session 的通知计数加一并唤醒等待者。订阅者看到自己没见过的计数值时，返回一个标记为 `overflowed` 的投递，也就是现有的"去读存储"信号，于是流从自己的游标重读 SQL 并继续。计数保证：流忙于发送时到达的通知，在它下一次等待时仍然生效，而且只生效一次。

## 4. 设计决策

| 决策                  | 选择                                            | 理由                                                                                                                                                             |
| --------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 信号来源              | 轮询 SQL 中的持久水位                           | 不需要 MQ 或服务发现；水位是权威的，漏掉一次轮询只会延迟。                                                                                                       |
| 轮询器交给 hub 的内容 | 只发通知，每个流从自己的游标重读                | 原样复用溢出路径。多实例方案中的提议是由轮询器读一次事件再发布；那样要为"同一 Session 有多个本地流"这种少见情况，重复实现流的游标、replay floor 和 resync 处理。 |
| 通知记账              | 每个 Session 一个计数，每个订阅记录自己见过的值 | 流在读取和等待之间不会丢唤醒，也不会空转。                                                                                                                       |
| 本实例的事件          | hub 已持有该水位时忽略                          | 执行 Turn 的实例不增加存储读取。                                                                                                                                 |
| 间隔                  | 固定的 200 ms 常量                              | 每个实例每次轮询一条走索引的查询，与流的数量无关；在压测提出需要之前不新增配置。                                                                                 |
| 线程                  | 独立的单线程                                    | 不让一个 5 Hz 的任务占用共享的单线程恢复调度器。                                                                                                                 |

## 5. 风险与约束

- 每个至少有一条打开的流的实例，每秒大约发出五次水位查询，与它持有多少条流无关。成对条件匹配流表业务键的前导列，但生产规模下是否用上索引尚未测量。
- 非写入实例上的流在每次水位变化时重读一次 SQL，每次轮询最多一次，而不是从内存收到事件。
- 非写入实例上的流看到事件的时间，比写入实例上的流最多晚一次轮询（200 ms）加一次存储读取。

## 6. 验证与验收

- H2 hub 测试：通知会以"去读存储"的投递唤醒等待中的订阅者；在等待之前到达的通知只被看到一次；针对 hub 已持有事件的通知会被忽略；只列出仍打开的订阅。
- H2 轮询器测试：水位前进时会通知，不变时不通知；没有订阅者时不读取；订阅者再次出现时会重新收到通知；读取失败不会让后续轮询停止。
- H2 和真实 MySQL 8.4 上的存储测试（`ManagedEventTailsMySqlIT`）：只返回所请求的租户与 Session 组合的水位，超过批大小的请求被正确拆分。
- 现有的流、回放和 hub 测试保持通过。
