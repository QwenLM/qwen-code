# Managed Session 改名的持久投递

[English](2026-10-08-managed-session-rename-delivery.md)

## 问题与范围

同一幂等键的一份请求可能失败，而另一份仍在 Harness 内执行。公共回执被退休后，新改名可以继续，但旧远端写入可能最后才完成。SQL 完成检查无法撤销这个私有写入。远端已接受、HTTP 回包丢失还会造成相反的缺口：私有标题已持久化，公共标题仍未更新。本次 #13163 后续修复同时覆盖绑定与未绑定 Workspace 的 Session，以及远程或本地 Harness journal 存储。

## 排序与重试契约

新改名在受理前检查 Harness 可用性及标题协议能力，不附着 Session，也不发送标题。禁用或不支持协议的 Harness 不创建命令和投递，不阻塞生命周期。已完成回执仍先于这些检查重放。

改名投递迁移使用 V55，位于 main 的 V53 Workspace 角色与 Session owner、V54 child lineage 迁移之后。表与投递契约不变；本 PR 尚未以原冲突编号合并。

仅包含 Unicode 空白的标题在受理前按 Harness 空标题契约拒绝。私有端明确的 `409 session_mutation_superseded` 继续作为公共冲突返回，不转换为可重试的依赖失败。改名回执探测与首次投递读取不锁定缺失索引项；tenant 与 Session 锁继续串行化受理。

受理沿用 tenant 和 Session 锁，并在同一事务保存最新标题投递。版本号是 Session 范围内递增的正有符号 64 位整数。新键获得新版本；当前未完成投递的同键重试复用版本与尝试预算。旧 FAILED 键在更新投递之后重试时获得新版本。COMPLETED 同键仍先从公共回执回答，再考虑新工作准入。同键改换内容或 Session 仍然冲突。

私有改名请求用十进制字符串携带版本。Harness 声明标题协议版本 2，在版本 1 改名基础上增加持久退役。新的托管改名受理要求版本 2；SDK 仍允许已有投递使用版本 1 的带版本写入。已有工作遇到版本 1 Harness 时，退役保持阻塞，直到升级。最终 metadata 写入在 authority 已有的串行 journal 事务内比较持久水位，拒绝较旧版本。每个版本使用固定的持久命令标识，重放不再追加标题。普通标题写入保留水位。冷加载读取相同的已提交 metadata；检查不依赖 Java 副本缓存或进程内锁。

公共完成检查投递版本、键和 Session 范围。同步请求和恢复 worker 都先认领同一投递，再执行远端 I/O；未认领成功的请求既不发送，也不退休回执。失败清理还必须在与接管共用的 tenant 和 Session 锁内，匹配当前所有者、RUNNING 状态及未过期租约。晚到或租约过期的所有者不能退休当前认领者的命令或新的尝试。原 requested 事件保持唯一，重试不会创建另一个 requested 回执。

## 恢复与生命周期

最新投递在进程退出或不确定的传输失败后保留。可用 Harness 副本按照已有分发租约和退避设置认领到期任务，重放标题后补齐公共回执。新意图替换旧意图时清除旧租约；晚到工作由版本号隔离。禁用副本既不扫描也不认领。租约到期可恢复崩溃的 worker。

空 Session 首次改名沿用正常创建授权建立 Harness journal。若创建冲突或结果未知，绑定或未绑定 Workspace 的标题投递都改为被动加载，即使公共附着 boot 尚未保存。这样也能恢复私有提交成功、回包却丢失的首次标题。

Workspace 迁移的 tenant/storage 空闲门禁也统计所有未完成标题投递，包括公共命令为 FAILED 或投递租约已过期的情况。恢复仍可能写入标题时，不能安装迁移 fence。

标题投递尚未结清时，关闭、归档、删除及 cwd 变更拒绝准入。公共命令为 FAILED 仍可能对应已被远端接受的写入，因此必须先结清投递，再封存或移动 Session。开始退役前，新改名可以替换该投递；RETIRING 工作拒绝新的改名准入，直到对账结束。已完成生命周期回执仍可重放。

两个存储不是同一事务：投递待处理或依赖不可用期间，标题可能暂时不同。恢复通过确认写入或对账退役确认来建立一致。协议拒绝或达到尝试预算不能证明早先写入从未生效。

## 安全退役

改名投递失败八次后，同一 SQL 行持久转为 RETIRING。重试与租约接管都不能让它恢复标题写入。worker 沿用已有的被动 Workspace 和 generation 授权加载同一 Session，再调用 `/session/:id/title/retire` 隔离该版本。禁用 Harness 不改变意图。附着、传输、能力协商或回执校验失败时，投递仍为 RETIRING，生命周期门禁保持阻塞，只重试退役请求。

authority 把退役与标题提交串行化，在现有 session metadata 事务中保存 `managedRenameRetiredRevision`。它保留真实已提交标题，提高排序水位但不降低更新水位，并拒绝所有小于等于退役版本的标题请求，包括曾经提交的命令重放。普通标题写入保留两个水位。固定退役命令在丢失回包或冷加载后返回当次提交的标题快照；更高版本仍可改名。

SDK 要求 Session 身份与十进制版本匹配，同时要求 `persisted: true`、`retired: true`，以及明确存在且为字符串或 null 的保留标题。拿到回执后，SQL 检查确切 tenant、Session、版本、幂等键、当前租约所有者及未过期租约；在同一事务对齐公共标题、记录独立的改名退役事件和终态命令，并将投递置为 RETIRED。晚到的写入完成不能覆盖 RETIRING 或 RETIRED。只有 COMPLETED 和 RETIRED 投递解除关闭、归档、删除、cwd 和 Workspace 迁移门禁。退役原键返回 `409 session_title_retired`，不会静默复活；退役后新键可请求更高版本。

这限制的是标题执行次数，不声称失败请求从未生效：若早先尝试已提交但丢回包，公共标题反映该保留结果。Harness 无法确认栅栏时，退役仍是外部阻塞。超时、不可重试异常或预算耗尽都不能清除排序责任。依赖退役前需一起部署版本 2 Harness 与更新后的托管服务副本；降级版本无法安全处理 RETIRING 工作。

## 验收

- 新改名完成后才到达的旧写入不能改变任何一侧的持久标题。
- 当前同键重试保留版本及预算；已被替代的 FAILED 键获得更高版本。
- 最新远端提交后丢失回包，由持久重投递修复，不产生第二条 journal 标题记录。
- 已完成公共重放、内容冲突检查及 tenant/Session 隔离保持有效。
- 关闭或移动不能让未完成标题投递永久丢失；投递完成后生命周期准入恢复。
- 禁用副本不改变投递状态或重试租约；新禁用或不支持协议的请求不创建投递。
- 同步投递先持有租约，不能被同伴立即抢占；过期所有者不能退休新所有者的回执。
- Workspace 迁移独立于公共回执状态拒绝未完成标题工作。
- 标题尝试耗尽后持久转入退役；丢失退役回包与重启只重试栅栏。
- 退役后同版或旧版标题（包括已提交重放）不能再写；更高版本仍可写入。
- 退役确认对齐保留标题并解除生命周期阻塞；无效回执、不可用 Harness 或过期所有者不能解除阻塞。
- 公共退役键明确失败，不报告改名成功，也不启动新工作。

验证采用 Java/SDK、Core/Hosted 路由的定向回归，以及受控的真实 Spring/H2 与 Node Harness 传输探针。报告分别说明脚本模型、H2 和故障注入，不将它们当作真实模型或生产数据库验证。
