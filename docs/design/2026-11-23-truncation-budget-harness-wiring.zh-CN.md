# 将截断输出预算接入每个 harness

[English](2026-11-23-truncation-budget-harness-wiring.md) | [简体中文](2026-11-23-truncation-budget-harness-wiring.zh-CN.md)

## 问题

当输出上限在工具调用中途截断响应时，主循环的拒绝会告诉模型这次截断消耗了上限中的多少，使模型能估算分批写入的每一部分的大小（#16417、#16632）。有两个 harness 表面只保留了截断布尔值：子代理运行时——它用自己的工具请求替代 `Turn` 的请求；以及 ACP 会话自有执行器——它为通过会话自身 chat 发送的 daemon 与 IDE 会话自行应用调度器的部分编辑守卫。来自子代理或此类会话的被截断 `write_file` 会在没有这些数字的情况下被拒绝（#17306）。

## 设计

- 把每个表面都需要的两段逻辑原样抽取到它们已有的位置：由响应 usage 与发送层上限推导出的预算（`core/turn.ts` 中的 `outputBudgetAtTruncation`），以及预算已知时拒绝文案追加的那句话（`core/coreToolScheduler.ts` 中的 `truncationBudgetNote`）。`Turn` 与调度器都调用它们，因此每个表面的推导和措辞完全一致。
- 子代理运行时。共享循环在某一轮的响应以 `MAX_TOKENS` 结束时，在截断标记旁记录预算；某次尝试被重试或替换时一并清除；`settle` 把它和截断标记一起盖到代理自己的请求上。当前循环保留报告截断的那个 chunk 的 usage，并把预算交给 `processFunctionCalls`，由后者放到它构造的每个请求上。
- ACP 会话。每个响应的事实记录增加预算。自有 chat 的发送 wrapper 按 `Turn` 的方式推导；共享轮次的 wrapper 从该轮的请求上读取——客户端已经记录在那里。会话自有的部分编辑守卫在与调度器相同的分支上追加预算附注：即重试指令接管之前的那些拒绝。
- 不新增推导。只要任一数字未被测量到（usage 为零值或缺失、没有上限），预算就保持缺失；被重试的尝试绝不继承被截断尝试的预算。

## 验证

单元测试覆盖全部三种代理循环（当前循环、共享循环、事件总线 kernel 上的共享循环）：被截断的那轮调度的请求携带 `{ usedTokens: 4096, limitTokens: 8192 }`（usage 总计 12288、提示 8192，上限 8192），并且调度器对被截断编辑的真实拒绝包含 `used 4096 of the 8192-token output limit`；只报告零值的截断、未被截断的响应以及被重试的尝试都不携带预算。在 ACP 会话中，自有执行器对被截断 `write_file` 的拒绝点名预算，零值情况下不点名；共享工具批次无需额外接线即可点名，因为它调度的是客户端自己的请求。调度器与 `Turn` 既有的预算测试保持不变并通过。

手动验证：设置较小的输出上限，让子代理和 daemon（`qwen acp`）会话各尝试一次超出上限的 `write_file`。两处的拒绝都应说明已用 token 数与上限。
