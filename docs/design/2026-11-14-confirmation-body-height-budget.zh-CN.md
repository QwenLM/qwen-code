# 确认界面正文高度预算

[English](2026-11-14-confirmation-body-height-budget.md) | [简体中文](2026-11-14-confirmation-body-height-budget.zh-CN.md)

状态：已在分支 `fix/confirmation-body-height-cap`（PR #17132）实现。

## 问题

内联的工具确认界面把正文（diff、命令、计划、说明性文字、MCP 标签）排在提问
行和「批准 / 拒绝」选项之上。待确认区域会在视口底部被裁掉，因此当正文高度
超过终端高度时，提问行和全部选项都会落到折叠线以下：用户只看到正文，却
无法作答。这正是本 PR 要修复的缺陷。

修复的第一版给正文套了一个带 `overflow="hidden"` 的限高盒子。评审表明方向
正确，但有四处错误，并且它引入了一个新的失效模式：

1. **外层盒子与正文分支计算预算的时机不同。** 选项列表的插入和自动模式横幅
   被并入正文，都发生在正文分支自行定高之后，于是外层重新计算的那次把选项行
   记了两次账，又把已经包含在它正在裁切的内容里的横幅再扣一次。在审批分类器
   不可用、终端高度 12 行时，exec 的命令文本整块消失，原来位置只剩空行。
2. **紧凑模式的上限只作用于各正文分支，从不作用于外层盒子。** 嵌在紧凑子代理
   横幅里的确认界面仍然拿到按终端算出的完整预算，紧凑路径声称的上限并不成立。
3. **裁切既无声也可能不连续。** 带 `maxHeight` 的 Ink 祖先节点会压缩长内容
   换行出来的那些行（`flexShrink` 默认为 1），而不是砍掉尾部。于是 30 个 URL
   的区块会显示一批零散样本，且没有隐藏行数标记——这比截断的前缀更糟：它看起来
   就是完整的列表。
4. **在 `info` 类型里，说明性正文吃掉了整个预算。** 列出待抓取 URL 的区块排在
   说明正文之后，因此它最先被挤掉——而那恰恰是决策最需要的内容。

合起来看，这会造成一次「不知情」的批准：一个只引用外部说明、自身不写主机名的
提示，可以在被授权的目标完全不可见的情况下提供 `Yes, allow once`。

## 目标与范围

- 对本组件负责定高的每一种确认类型，在能够容纳提问行与选项的任意终端高度下，
  提问行和选项都必须在屏幕内。有两个分支不在这一承诺之内：`ask_user_question`
  在取任何预算之前就返回了自己的对话框；正文预算的下限是一行，因此当高度小于
  「外围控件加这一行」时，渲染出的框架会比授予的行数更高。
- 正文只由一个预算定高，该预算计算一次；外层限高的上限就是该数值加上实测的自动
  模式横幅高度。
- 任何截断都必须显示连续的一块——前缀，或在最后一条才要紧的列表里是后缀——并说明
  隐藏了多少。
- 抓取类确认界面里的目标地址列表优先于随附的说明文字；被裁切的地址列表绝不能
  看起来是完整的。
- 存在一个可被发现的方式，在不作答的情况下读完整正文。

不在范围内：改动确认选项、审批分类器、`MainContent.tsx` 中 shell 层的待确认
区域限高，以及已存在的 `o` 键「在编辑器中打开完整计划」能力（#7001）。
主体不可审查时究竟是否应当阻止批准，是一个协议层面的问题，作为 issue #17715
单独跟踪，提案见
[权限决策的可审查性](2026-11-18-permission-decision-readiness.zh-CN.md)。

## 方案

### 每个正文只取一次预算

`availableBodyContentHeight()` 是正文可用行数的唯一来源。每个类型分支都在
选项插入之前、自动模式横幅并入正文之前解析出这个数值并保存下来；外层限高
复用该数值，而不再第二次调用 `availableBodyContentHeight()`：

```tsx
maxHeight={
  bodyBudget === undefined ? undefined : bodyBudget + autoModeFallbackHeight
}
```

自动模式横幅是各类型分支从未计入的内容，所以外层限高是把它的实测高度**加上**，
而不是扣掉。两个数值来自同一处对横幅的测量，因此横幅只计一次：在各类型预算里
通过 `autoModeFallbackHeight` 预留，在外层限高里加回。

### 紧凑上限属于共享预算

`COMPACT_BODY_MAX_LINES` 通过一个共享辅助函数施加，每个类型分支在取预算时都
调用它，因此某个分支不可能拿到比另一个分支更大的上限。外层限高不再二次封顶：
它的上限是 `bodyBudget + autoModeFallbackHeight`，而 `bodyBudget` 已经是封顶后
的数值，外层只是把各分支从未计入的横幅加回来。授予行数为 `undefined` 时不加
封顶——没有高度意味着完整细节模式，封顶反而会藏起任何快捷键都调不回来的正文行。

### 截断必须连续且计数

被裁切的内容必须先「钉住」。`flexShrink: 0` 的 Ink 行保持自身高度，于是限高
砍的是尾部，而不是把零散的行压扁。`MaxSizedBox` 对它自己的行已经这样处理，并
渲染 `... last N lines hidden ...` 页脚，经由它渲染的内容同时获得这两个性质
——但前提是被告知从底部裁切，因为其默认值裁的是头部，打印的是
`... first N line(s) hidden ...`。盒子保留哪一端取决于内容，而不是某种默认约定；
下面「放不下时，那一行归谁」一节说明哪些盒子留尾部、哪些留头部。

无法交给 `MaxSizedBox` 的行保持钉住的 Ink 行，并自行渲染计数页脚：

- 抓取类确认界面的逐条 URL 行内含内联 Markdown 链接，而 `MaxSizedBox` 会跳过
  这类节点——它只接受后代全为 `<Text>` 的 `<Box>` 行，因此被 memo 化的内联渲染
  器会导致 URL 文本被静默丢弃。这些行保持 `<Box flexShrink={0}>`，并手写一条
  `... N more URLs hidden ...` 页脚行。
- 纯文本说明正文仍走它原有的 `MaxSizedBox`，它已经会钉住行并计数隐藏内容。

### 先给目标地址预留，再排说明文字

在 `info` 分支内，先核算目标地址区块的成本，再决定说明正文的高度：

- 只要放得下，全部地址就都会渲染：核算的是地址连同其自身外围对预算，而不是
  说明正文的下限，所以只有当地址们整体放不下时才给区块封顶。能放下的最宽松外围档
  优先——挑一个同样放得下的更紧外围档，只会让预算并不需要的页脚行白白藏掉一个
  地址。说明正文随后取余量。
- 否则给地址区块封顶：一行给 `URLs to fetch:` 标题，一行给隐藏计数页脚，其余
  行按整条 URL 贪心填充，绝不把某个地址显示成半截。标题还在时先藏的是地址；
  区块自己的外围要等某个档位下放不下任何整条地址时才交回，顺序是先空隔行、
  再标题、最后什么都不留：空列表上方的标题不回答任何问题，而主机正是被授权的
  对象。计数页脚留到最后一行——它是「列表比屏幕上更长」的唯一信号。
  说明正文保留一行给自己的隐藏计数页脚，这样它的丢失仍会被宣告；当余量小到连
  一行本来就会被裁切的内容都容不下时整块跳过——下限是
  `MINIMUM_MAX_HEIGHT`（2），因为内容和「裁切用来宣告自身的那一行」都放不下，
  无论说明用哪种渲染器。已经放得下的说明不会因为下限被丢弃：它不渲染页脚，
  下限对它不适用。整块丢弃时，只要还剩一行，那一行就用来渲染
  `... prompt hidden ...` 宣告；连这一行都不剩时，说明就没有可用来宣告自身的一行
  ——给说明加页脚会把地址的页脚顶出上限，被 Ink 砍掉的反而是更要紧的那一条。这种
  情况下被丢弃的说明仍会登记溢出：说明凭空消失、既没有说明页脚也没有隐藏地址计数
  的画面，正是别的东西都不会点亮该快捷键的画面。

这里的取舍是刻意的：正文预算大约在 5 行以内时，目标地址优先于解释文字，说明
可能整块不见。用户仍能看到将被授权的是哪些主机，并且可以把余下内容调出来。

### 放不下时，那一行归谁

下面这些排序是有意选定的，也正是代码的行为：

- 抓取类正文里，目标地址优先于只是描述请求的说明文字。告警列表里，最后一条告警
  优先于前面的，因为描述模式的告警只是在说明这次请求，而点明具体动作的那一条才是
  改变它的东西；因此必须裁切的告警盒子会选择裁头部、留尾部。
- 当一个告警盒子与本分支自身那个被授权的对象（diff、命令）共享同一份封顶预算时，
  那一行归后者：它就是被授权的东西。盒子按它实际渲染的内容扣额度——所有告警都放得
  下时按换行后的行数扣，放不下时每条扣一行——这次分配从它那里拿走的部分会在存活的
  那一行上计数，等主体只剩一行时就写成 `+N warning(s) hidden`。一行都没有而被丢弃的
  告警盒子会登记溢出，于是它失去的那些行仍能调回来。主体也绝不会因这次分配丢掉最后
  一行：给两行就通过盒子布局，只剩一行就渲染那条计数页脚。
- 一条 MCP 标识行带着两个标签，两半都不能省——服务器说明调用去往何处，工具说明它做
  什么——所以只有一行时每个标签在自己内部被裁切，并且该行登记「发生了裁切」，而不是
  让合并后的整行靠溢出自行决定。
- 计划正文里，打开编辑器的提示是从被裁切的计划里脱身的出口，因此只有计划确实被裁切时
  才为它扣一行。这里「被裁切」看的是计划视图实际画得下多少，而不是被授予的行数：视图会
  花掉交给它的两行，一行给自己的裁切提示，一行留给渲染高度与源码行数之间的差异，所以
  超过「授予行数减去这两行」的计划已经在丢内容，尽管授予的行数看上去更宽裕。只够放两者
  之一时，留下那一行的是计划；视图那两行的下限本身并不会把一个「所需行数不超过被授予
  行数」的计划丢掉：那样做等于把被批准的东西藏在一个上限本来就会裁走的提示后面。
- 地址区块的外围是承压时先交回来的东西——先空隔行，再标题——而计数页脚留到最后一
  行才丢，因为它是「列表还在继续」的唯一信号。

### 读完整正文

调出完整内容的能力早已存在，且是全局共享、而非按类型实现：`ctrl-s`
（`Command.SHOW_MORE_LINES`）会清除 `constrainHeight`，使本组件里所有高度预算
变成 `undefined`；`MainContent.tsx` 在流式输出已稳定为静态确认后也会撤掉自身的
待确认区域限高，于是完整正文会渲染进终端 scrollback 并保持可交互（#6809）。
即使确认界面持有键盘，该快捷键仍能到达全局处理器。

缺的是可发现性：`Press ctrl-s to show more lines` 这条提示只有在有组件登记了
溢出时才出现，而本组件裁切的那些正文什么都没登记。现在，本组件自己执行的每
一次截断，都会在其留在屏幕期间登记一个溢出 id，从而在真正有用的那一刻点亮
提示。每处截断同时说明自己隐藏了什么，因此在内容消失的那一帧里，该能力也是
可发现的。

这条快捷键并非无条件生效，而提示并不知道这一点。全局处理器清除
`constrainHeight`（从而解除本组件的所有高度预算）的前提是输入缓冲区为空；已经
输入了草稿时，同一个按键走的是输入框的「暂存」绑定——它把草稿挪走，上限却仍然
生效。按键分发是忽略返回值的广播，于是两个处理器都会触发，用户想看的那些行照旧
隐藏。要让调出能力在确认界面持有键盘时胜出，就意味着压制一个有意为之的功能，所以
本方案把「缓冲区为空」写成调出能力的前提条件，而不是宣称该快捷键普遍可用；提示本身
仍是共享的那一条。

例外是预算够放、却在 `MarkdownDisplay` 内部被裁切的计划正文：该组件画的是它
自己的就地提示，且不会登记溢出 id，于是由本分支替它登记调出所需的溢出。调出在
这里是有效的：调出会把高度授予去掉，而该组件只在拿到授予时才切片。这个判断量的是
计划源码在正文宽度下换行后的行数，它并不知道渲染器会多出多少：Markdown 会把列表项缩进
绘制，所以正好卡在换行边界上的条目可能比计数时画得更高，此时若授予看上去宽裕，计划就只
带着那条就地提示被裁掉，而没有脱身的那一行。本分支扣下的两行能吸收常见情形；要彻底封住
剩下的情况，就得按该视图的画法来量计划。计划分支为此
保留 `o open full plan in editor` 那一行，并且只在计划真的被裁切时才为它扣一行
——放得下所给行数的计划没有什么要脱身的，而只够放两者之一时，留下那一行的是计划。
当预算小到把计划正文整块丢掉时，本分支登记溢出，而这种情况只发生在计划需要的行数
超过被授予行数的时候。

## 约束

- `MaxSizedBox` 在设置 `maxHeight` 时要求 `maxWidth` 必须有值；为页脚预留一行；
  预算下限是 `MINIMUM_MAX_HEIGHT`（2）——预算为 1 时它仍会渲染一行内容加那个
  页脚，因此这个盒子会比要求的多占一行；遇到无法遍历的行子节点会上报错误。
- 预算只剩一行时，绝不能只用一个标记来宣告截断：标记本身占一行，所以被限高的
  内容与标记必须一起核算。
- `MaxSizedBox` 只有被告知才会从尾部裁切：对「头部才是要紧部分」的内容必须设置
  `overflowDirection="bottom"`，而告警盒子有意使用默认的裁头部，因为那里要紧的是尾部，
  且裁头部会打印 `... first N line(s) hidden ...`。
- 外层限高是布局兜底，不是格式化器。它无法宣告自己裁掉了什么，因为它从不测量
  布局——凡是可能溢出的正文必须自行宣告截断，兜底只负责限制破坏范围。
- 登记溢出 id 必须与组件生命周期绑定（在截断期间挂载时登记，卸载时注销），
  这样提示不会比被裁切的内容活得更久。

## 风险与取舍

- 只是估算，不是测量：计划分支判断裁切用的是计划在正文宽度下换行后的源码行数，所以渲染
  画得比这个数更高的计划——缩进超过了计数所用宽度的长列表条目——可能只带着该视图自己的
  提示被裁掉，既没有脱身的那一行，也没有登记的调出。要补上它，就得按 `MarkdownDisplay`
  的画法来数计划，而这已经超出一个确认组件该承担的 Markdown 排版。
- 说明丢失：预算很紧的抓取类确认界面可能显示 0 行说明正文。由调出完整内容的
  路径缓解；只有在还剩一行时，计数页脚才会宣告这次丢失。
- 调出路径依赖宿主清除 `availableTerminalHeight`。始终传入高度的宿主会让所有
  上限持续生效并保持提示可见，只是无法调出完整内容。本方案的安全性不依赖
  调出能力——有无它，提问行和选项都可见。
- 提示也可能在调出并不会生效的时刻亮起：输入缓冲区非空时，`ctrl-s` 变成暂存草稿。
  此项已延后：让确认界面在持有键盘时自行解除上限，会压制那个有意为之的暂存绑定，
  范围比本 PR 更大。
- 由确认界面登记溢出会向共享溢出状态加入 id，而 shell 自身的限高也在写入同一
  状态。两者都按 id 划分，可以共存；唯一的消费者是那条提示。

## 验证方案

- 与组件同目录的单元测试，每个缺陷一个，且在修改前均为红：
  - 分类器不可用 + 终端 12 行的 exec 确认界面：命令文本与 `No` 选项同时可见，
    命令原位置不再出现空块；
  - 预算放不下全部告警的 exec 正文：命令先为自己的那一行预留额度，告警分走剩下的部分
    ——全都放得下时按换行后的行数扣，放不下时每条扣一行——于是盒子裁头部，点明具体动作
    的那条告警存活，而不是在五行预算里被压掉七行正文；只剩一行的告警请求会让最后一条
    告警留在钉住的行上，并把它前面的计数为 `+N warning(s) hidden`；一行都没有的告警盒子
    会登记溢出，并把自己的计数交给存活那一行；被压到只剩一行的命令同样会自行宣告，而
    只剩一行但仍然放得下的命令既不登记调出也不宣告隐藏——钉住的行本身不是裁切；
  - 一路小到两行正文预算下的 30 条地址：`URLs to fetch:` 标题、连续的地址前缀
    以及计数的隐藏 URL 行都可见，且看不到零散样本；到两行预算时标题已不在，但
    仍留有一个主机和计数；只隐藏一条地址时用单数措辞；
  - 长说明正文 + 多条地址，且预算只容得下其中之一：地址存活；
  - 按渲染结果而非 Markdown 源码计量内联 Markdown 说明：强调标记在渲染时被去掉，
    源码比屏幕更宽，因此只渲染成一行的正文不该被宣告有隐藏尾部；
  - 链接目标被渲染器保留时按它实际占的宽度计量：欺骗性标签渲染成 `label (target)`，
    屏幕上的文本比标签本身更长；只数标签就会把那一行交给一个随后被无声裁切的盒子，
    而按渲染结果计量会整块丢弃并把那一行用来宣告；
  - 预算够放的计划正文：计划行与 `o open full plan in editor` 行各占一行；所需行数超过
    被授予行数的计划会在两行预算下被整块丢掉并得到宣告，而这正是点亮调出快捷键的东西，
    而只剩一行时留下那一行的是那条提示；放得下预算所留那一行的计划会按计划文本渲染，
    既没有提示行也没有宣告，因为什么都没被裁；两行的计划在一个「看上去够、但视图画不
    下」的授予下，提示行仍与视图自己的裁切提示并排留在屏幕上，并登记调出；
  - 一行预算下的超长 MCP 标识：两条标识行让位于一条钉住的行，它同时容纳两半，每个标签
    在自己内部被裁切，于是这一行仍然说明调用去往何处、它做什么，而不是较长的一半把另
    一半挤出屏幕，并且它登记发生了裁切；
  - 极小预算下的编辑类正文：两行正文预算加一条告警时，diff 让位给 `... diff hidden ...`
    宣告；只剩一行正文预算时告警被整块丢弃——被授权的改动本身保住那一行，宣告的尾部把
    它们计数为 `+N warning(s) hidden`；只剩一行的告警请求会留下最后一条告警，并以同样的
    方式计数它身后的那些；以上这些都登记溢出，因此被丢掉的 diff 与被丢掉的计划一样点亮
    调出快捷键；
  - 纯文本说明被它自己的页脚挤出的情形：整块丢弃的说明会得到宣告；而在最后
    一行存在争夺的高度下，该行归地址页脚所有，说明的页脚被省略，而不是反过来
    裁掉地址的页脚；
  - 连一行都没留给说明、连页脚都没有的情形：仍然登记溢出，而画面上照旧有一条地址、
    提问行和各个选项；
  - 紧凑终端里两选项的被拦重试布局：四条命令行被断言为按顺序各自独立的四条渲染行，因为
    压到邻居身上的行仍然会打印自己的文本，只查子串会通过一个被挤扁的画面；
  - 一行预算内放得下的纯文本说明：照常渲染——`MINIMUM_MAX_HEIGHT` 下限只是
    替页脚买单，而放得下的正文从来不需要页脚；
  - 在截断可观测的高度（40 行，而非 8 行，因为 8 无法区分是否封顶）下的紧凑
    确认界面：正文不超过紧凑上限；正好与上限等高的命令在该高度下保住每一行，
    未授予高度时则全部保住——上限替换的是授予值，而不是把外围控件再扣一次；
  - 以上每个用例还须断言有正文行存活，而不只是断言渲染高度不超过某个上界——
    空正文同样能满足上界断言。
- 真实终端端到端（tmux，小终端）对接本地 mock 模型：一个正文足够长、能在小
  终端里溢出且目标地址可达的抓取类确认界面；再把审批分类器故意弄失败跑同一条
  路径，从而加上自动模式横幅。确认提问行与选项始终可见、计数页脚出现，且按
  `ctrl-s` 能在不作答的情况下调出完整正文。30 条地址与超长 MCP 标识这两条
  路径只做单元测试：没有内置工具会产生多地址确认界面，而超长 MCP 标识需要
  一个工具名长得极不真实的服务器。
- 构建、类型检查以及该组件自身的测试文件。

## 验收标准

- 凡是本组件负责定高的确认界面，在能够容纳提问行与选项的高度下，都不能把它们
  推到折叠线以下。
- 对每种确认类型，正文上限等于该类型分支算出的那个预算，再加上实测的自动模式
  横幅高度。
- 每处被裁切的正文都显示连续的一块——前缀，或在最后一条才要紧的列表里是后缀——并说明
  隐藏了多少；被裁切的地址列表绝不能看起来是完整的。由做出裁切的那个渲染器自己宣告的
  裁切，是本组件计数页脚的例外：在 `MarkdownDisplay` 内部被裁切的计划正文带的是那个
  组件自己的提示，而在自己内部被裁切的标识标签则把省略号放在标签里。
- 由本组件裁切的正文，在其留在屏幕期间会让 `ctrl-s` 提示可用；确认界面离开时释放
  这个 id。
- 评审者能在父提交上复现上述四个缺陷，并在本提交上看到它们被修复。
