# Mod 存储

[English](2026-11-10-mod-store.md) | [简体中文](2026-11-10-mod-store.zh-CN.md)

状态：提议中。在 #13749 中跟踪。方法名和形状沿用 Mod 编写 API 中的 `$.store` 方法。

## 问题与现状

Mod 没有地方保存跨会话的值。模块变量只活到会话结束，Mod 环境里也没有文件系统。要统计自己运行了几次、记住用户做过的选择、或者缓存一个很慢的答案的 Mod，每次都要从零开始。

编写 API 里给这件事准备的是 `$.store`，但在 Qwen Code 里每次调用都会以 `Mod API not supported: $.store.get` 拒绝，挂在 `store.*` 上的 hook 能加载但从不运行。

## 目标与非目标

目标：

- 在所有运行 Mod 的宿主中提供 `$.store.get`、`set`、`delete` 和 `keys`：headless 运行，以及 Ink 和 OpenTUI 终端。
- 值跨会话保留，并由同一插件的所有会话共享，包括同时运行的两个会话。
- 这些调用作为 API 事件运行，其他插件的 hook 能听到，和其他 `$` 方法一样。

非目标：

- `$.state`，即会话中可被绘制订阅的命名值。它需要渲染订阅和单独的运行时模块，之后再做。
- 卸载插件时删除它的存储。
- ACP 会话中的存储，ACP 会话目前还不加载 Mod。

## 改动方案

### 1. 存放位置

每个插件在 `<全局 Qwen 目录>/mods/store/` 下有一个 JSON 文件，全局 Qwen 目录是 `~/.qwen` 或 `$QWEN_HOME`。不超过 128 个字符的插件名使用 `<小写插件名>.json`。更长的名字使用小写插件名的稳定哈希。文件内容为 `{ version: 1, entries: [[key, value], ...] }`。

### 2. 谁读写文件

由会话的主线程读写，不由 Mod worker 读写。worker 把每次调用作为 `store` 请求转发，并等待 `store-result` 应答，做法与 `$.turn.abort`、`$.prompt.submit` 相同。运行时在创建时接收一个 `ModStore`；不传的宿主不提供存储，此时 worker 不列出 `store.*` 方法，并拒绝所有调用。

### 3. 读与写

- `get` 和 `keys` 每次都读文件，不加锁，也不缓存。宿主限制每个运行时的并发文件读取数，并在 dispatch 结束时取消仍在排队的读取。
- `set` 和 `delete` 先取进程内互斥锁，再取由进程持有的目录锁。在锁内重新读取文件、应用改动，再通过临时文件和重命名替换原文件。dispatch 结束时会取消仍在等待的取锁操作。
- 删除一个未设置的键时不写文件。

### 4. 限制与失败

- 每个插件的存储最多 4 MiB 的 JSON。会超出的写入会被拒绝，文件保持原样。
- 单个值还受现有限制约束：Mod 传给 Qwen Code 的内容最多 256 KiB，嵌套最多 512 层。
- 新增键时，序列化后的键列表还须满足 Mod 应答的 256 KiB 上限。插件仍可从超过该上限的旧存储中删除已有键。
- 无法按存储格式解析的文件，会让这个存储上的所有调用失败，并且不会被覆盖。
- 存储路径必须指向普通文件。读取会拒绝符号链接和命名管道，写入通过重命名原子替换目录项。
- `set` 拒绝 `undefined` 和不能序列化为 JSON 的值（函数、循环引用）。

### 5. 中间件

`store.get`、`store.delete` 和 `store.keys` 的输入是固定的。`store.set` 的 hook 可以传下另一个 `value`；键是固定的，所以把写入挪到别的键的 hook 会失败并被跳过。hook 可以对任何调用以 `{ value }` 作答，或以 `{ deny }` 拒绝。

## 设计决策

- **文件由宿主管理。** dispatch 取消或超时时，worker 可能被终止。宿主会取消取锁等待，并在关闭运行时前完成已在锁内开始的更新。更新通过重命名提交，进程在写入中途退出时会保留旧文件或新文件。
- **按插件名区分。** 扩展的 id 是安装来源的哈希，本地安装时路径一变 id 就变。插件名在重新安装后保持不变。扩展名只允许字母、数字、`-`、`_` 和 `.`，不区分大小写，全由点组成的名字会被拒绝，所以文件不会跑出所在目录。
- **以键值对数组存储条目。** 普通对象会把 `"10"`、`"2"` 这样的键按数字顺序而非插入顺序列出，`__proto__` 也不会成为自有键。
- **不缓存。** 别的会话随时可能写入，而一次读取只是读一个小文件。每次都读，别的会话写的值在下一次 `get` 时就能看到。
- **已在锁内开始的更新仍可能落盘。** dispatch 先结束时，宿主会完成更新并丢弃应答。调用方的 promise 会拒绝。

## 验证与验收

- `ModStore` 单元测试覆盖锁归属和恢复、等待取锁及更新时的取消、并发写入、4 MiB 上限、从超限的键列表中删除键、插件名、拒绝符号链接和管道，以及 0600 文件权限。
- 真实 worker 测试覆盖键顺序、JSON 往返、持久化和归属、键列表上限、限制并发读取和取消排队读取、关闭时取消等待并完成正在更新的写入、不可读文件、中间件，以及进入中间件前的能力检查。
- 在构建好的 CLI 上，一次 headless 运行写入值、第二次运行读出；以及两次运行同时写入。

## 风险与待定问题

- 存储文件从不删除。之后可以加清理命令，或在卸载时删除。
- 暂停的写入进程继续持有锁。跨进程取锁最多等待八秒。后续写入可回收已确认退出的进程留下的锁。在 Linux 上，同一启动周期和 PID 命名空间内，如果 PID 已不存在，或经验证的本地 procfs 视图确认其为僵尸进程，即可回收锁，旧格式锁也适用。通过启动令牌变化判断 PID 复用时，双方都需要经过验证的 procfs PID 视图，且时间命名空间必须一致。跨启动回收要求两边的机器、主机名和 PID 命名空间一致，且两边都从 procfs 读取启动 ID。归属无法确认的锁会保留。
