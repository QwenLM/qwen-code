Managed Agent
双链路技术方案

以 Java 作为产品控制面并内置 Runtime Broker 模块，以 qwen serve 作为常驻 TS Harness， 保留 Legacy ACP 链路，并将 Workspace、MCP 与本地工具执行下沉到按需启动的 Tool Runtime。 模型首 token 不等待 Runtime，只有真正发生本地 Tool Call 时才形成等待。

统一入口 外部客户端继续使用 Java 与现有 qwen serve Session/SSE 契约
固定 Owner Session 创建时选择 Legacy 或 Managed，生命周期内不可切换
低 TTFT Harness 推理与 Runtime provisioning 并行，不让 Pod 启动阻塞首 token
00 / FIRST RUNTIME

首版运行条件

v1.9 保留 v1.2 的总体架构、v1.3 的首版取舍、v1.4 的普通工具接线、 v1.5 的统一 Session 身份和 v1.6 的事件可靠投影边界，并补充 Java 管控面、Hosted Harness、Runtime Broker 与 Tool Runtime 的职责及通信架构图；v1.8 记录 daemon workspace 配额边界和 Managed Session 长期存储 D0 接缝，v1.9 补充 D1a Java/MySQL 私有 Store 的实现边界。Java 在创建前生成全局唯一 RFC UUID， 公共 API、qwen Session Authority、Managed Harness、JSONL 和 Runtime Broker scope 使用完全相同的 sessionId。不得再生成或持久化第二套 Harness Session ID。 首版仍采用单 Java + qwen Sidecar、预发布静态 AgentBundle、Session 独占 Runtime， 复用现有产品 REST/SSE 与正式历史。同 Session 多轮复用环境，Harness 仍可承载多个 Session。

首版只支持普通工具，以 Read、Write、Edit 和前台 Shell 为最小验收集； 自动记忆、子 Agent、后台 Shell 暂不涉及，本轮不补充其专项设计。 复用现有配置与 AgentBundle 工具目录表达范围，不新增开关协议。 普通工具所需的审批、输出与文件历史保存、Shell 后代进程的取消清理仍须完成。 该 profile 的初始化和轮次结束不自动启动延期能力；配置要求范围外能力时， 创建前按既有 selector 选择 Legacy，显式要求不兼容的 Managed 则拒绝准入。

租户边界：独立 Spring 参考服务不做终端用户鉴权，但要求 X-Qwen-Tenant-Id 并将它贯穿 Session、Turn、Event 与 Broker scope；本地 WebShell 的 tenant 参数只用于开发代理。生产部署必须由 可信上游鉴权后注入 tenantId。完整多租户授权、配额和跨租户隔离仍是生产门槛。
项目 首版要求 最小完成边界
Prompt 受理与幂等 必需 固定请求 ID；qwen 持久输入与 WakeIntent 后 Java 才 ACK，响应丢失查原请求；不新增 Java 提前 ACK 的输入队列。
统一 Session 身份 必需 公共 API、qwen/Harness、JSONL 与 Broker scope 共用 Java 预分配的 RFC UUID；数据库不保存公共 ID 到 Harness ID 的映射。
Broker 调用与查询 必需 同轮等待、原 execution 查询、门禁映射、取消和实际释放；execute accepted 不等于完成。
AgentBundle 必需 预发布不可变版本与资源闭包，Harness 离线可读；缺失拒绝准入，Runtime 核验 manifest。
Session 归属与存储 必需 固定后端、明确持久位置；重启无证明则阻塞，不能新建空 Session 替代。
Runtime 生命周期 必需 持久创建意图、创建去重、有限启动/idle 期限和容量；取消后迟到 ready 重新校验，释放核验真实退出。
审批与用户问答 条件必需 已开放工具需要交互时，响应必须经 Java 回到原持久仲裁；不静默自动批准。
跨 Session 共享 Runtime 默认关闭 独立 ToolSessionBinding、配置/权限/gate/历史及引用计数通过验收后启用。
公开事件接受与 SSE 已有 P0/P1 切片 源游标、公开序号、Turn 终态和事件在一个事务中提交；同节点提交后直推，溢出或断线从 SQL 补齐。
稳定 Item / Snapshot 物化 后续 补稳定 itemId/contentPartId、批次日志/Outbox、物化进度与 Snapshot；当前逐事件 SQL 行不能作为最终容量形态。

最小受理与故障边界

Client stable request ID → Java 持久统一 Session UUID / BackendBinding
                        → qwen 提交 input + WakeIntent → CommitReceipt
                        → Java 返回 accepted
模型推进与 Runtime 预热并行，不等待 Runtime ready。
ACK 丢失：原 ID 查询；started 失联：原执行对账或 recovery_blocked。
取消：先持久请求，再追踪实际停止与资源释放。

qwen Transcript/checkpoint、资源与 Broker Ledger 必须有明确持久保存位置。 Java 单独重启查询原 Sidecar/Runtime；Sidecar 重启核验 writer 与原调用； Pod 替换、卷不可用或旧 owner 不明时，首版不保证自动恢复。 多实例必须先完成原 owner 路由与 provision 竞争控制，自动跨实例接管仍属于 G。

首版使用 A/B/C/E 与 F 的必要验收，完整 D 不阻塞现有产品 API 上的 E 闭环。 方法与字段、Bundle 发布、部署矩阵、生命周期、审批及 M01～M10 验收见 首版运行契约； 这些是目标条件，不表示实现或测试已经完成。

00B / ORDINARY TOOL INTEGRATION

普通工具首版接线

Read / Write / Edit / 前台 Shell 复用现有 TS 工具与权限流程。 本节补齐发布、会话、工具阶段、资源和环境生命周期之间的衔接； 自动记忆、子 Agent、后台 Shell 暂缓；tenantId 已贯穿调用链，完整租户授权语义继续作为生产门槛。

接缝 v1.6 沿用决策 失败边界
Bundle 发布 / 装载 受信步骤复用共享 TS 定义生成不可变包；Java/Sidecar 共享只读目录，staging 校验资源闭包后原子发布。Session 固定 revision/ref；核验构建与模板。 缺资源、摘要或版本不符拒绝准入；bundleDigest、toolManifestDigest、Hosted capabilityDigest 分型，不能互相代替。
创建 / Prompt Java 创建前固定全局 RFC UUID sessionId、commandId、bundleRef、Workspace storage binding；同一 sessionId 直接交给公共 API、qwen/Harness、JSONL 与 Broker。qwen 持久 header/定义后确认创建，持久 input/WakeIntent 后确认 Prompt；原命令提供只读查询。 不得生成第二套 Harness Session ID；ACK 丢失查原 receipt；not_found/过期/owner 不明不是未执行证明，不能换 ID 或空 Session 重跑。
工具阶段 control 显式映射原 prepare/confirmation/confirm/preflight 及文件历史；新能力按版本协商，逐操作严格校验；Java 不重写调度与权限。 环境 prepare 不代替 invocation build；status/cancel 不创建 execution；改参使旧授权失效，unknown 不重新执行。
结果 bytes Runtime 登记不可变输出；Java 代理授权资源分片；qwen 校验、持久接收完整必要引用后返回 CommitReceipt，再 ACK delivered。 下载失败只续读原内容，未转存不得删除唯一副本；ACK 不等于环境可释放。
回收后下一轮 持久 Workspace 与 file-history root 独立于计算环境。干净 released 后创建新 binding，挂回同一存储与稳定 history owner；Workspace generation 不变。 旧 execution 永远归旧 binding；存储缺失或原执行未知则阻塞，不从 Git clone/空目录伪造恢复。

一轮工具调用的提交顺序

发布 Bundle → 创建 Session → 持久受理 Prompt → 模型先行
  Tool Call → 提交 tool.intent → 等待 Runtime / manifest / activation gate
  → bindHistory → Workspace 工具轮次占用 → beginTurn 起始快照
  → prepareInvocation → 确认 / 原权限仲裁 → confirm（需要时）
  → preflight → Harness 最终 guard → execute → 原执行查询
  → 结果 bytes 持久接收 → result CommitReceipt → ACK delivered
  → 模型继续 → 全部工具结算 → readHistory / 持久备份
  → authority checkpoint + turn.settled → 释放占用 → Runtime idle
  → 干净回收 → 下一轮新 binding 挂回原文件与历史
原 fileHistory.checkpoint(promptId) 确保的是轮次起始快照， 不是轮末持久提交。模型 Final、工具 ACK、Runtime release 分别核验。 Session 独占 Runtime 不等于文件隔离：首版同 Workspace 的工具轮次从起始快照 到 history 提交串行占用；外部文件变更仍按工具原有身份校验处理。

首版验证与参数

验证初值：环境启动 120 秒、idle 5 分钟、每 owner 最多 4 个 Runtime 和 4 个活跃模型 Turn； 有界队列最多 32、等待 60 秒；Session 工具并发 1；前台 Shell 默认 120 秒、上限 600 秒； 审批最长 10 分钟，更短既有预算优先。资源分片最多 1 MiB，单次 RPC/读取空闲期限 30 秒， 长任务用 accepted + 原状态查询；状态轮询 250 ms 至 2 秒并加抖动。 模型、输出总量与存储保留沿用既有有限预算并在启动报告列出实际值， 超时或未知物理退出仍计入容量；这些初值不代表生产容量结论。

M01～M10 加 S01～S08 验证“Edit diff → 审批 → Shell 大输出 → 持久历史 → idle 回收 → 同 Session 下一轮读到修改”，并注入 ACK/下载丢失、存储缺失与取消。 调研锚点、精确字段、封闭操作枚举、资源提交顺序、回收竞争和验收清单见 普通工具首版接线设计。普通工具的完整资源提交契约仍待实现；其中 Runtime endpoint 持久化、跨 JVM fencing、私有 attestation 和空闲 binding 恢复已完成 P3 参考实现与本地跨进程验收。恢复轮询使用有界指数退避和独立的 operation deadline；单个不完成的调度器或 attestation future 也受此期限约束。创建者 JVM 退出后，另一个 JVM 可按 PID/启动指纹 接管同一 local-process worker，且 worker stdout/stderr 不依赖父 JVM 管道。

01 / OVERVIEW

架构总览

下图只展开 Managed 主链路。Java Control Plane 与 Runtime Broker 在首版部署于同一 JVM，但保持独立模块和内部路由；Hosted Harness 是 qwen serve 内的 Managed 执行引擎；Tool Runtime 按需启动。

Managed 四模块架构

两条不同的热路径：无工具 Turn 走 Java → Harness → Model，Runtime 正在启动也不阻塞首 token；出现 Tool Call 后才走 Harness → Broker → Runtime。Harness 不直连 Runtime， Runtime 也不主动反连 Java。

核心通信矩阵

通信边 谁发起 如何通信 承载内容 关键约束
前端 ↔ Java Control Plane 前端发命令；Java 输出事件 HTTPS REST + SSE，支持断点续传 Session、Prompt、Cancel、Approval 和公共事件 浏览器不接触 Harness 与 Runtime 内部端点
Java Control Plane ↔ Hosted Harness Java 发命令并发起 SSE 订阅 Sidecar loopback HTTP + SSE 统一 sessionId、Prompt、Resume、Cancel、Transcript 和源事件 Java 持久受理后异步推进，不长时占用请求线程
Java Control Plane → Runtime Broker Java 产品层 首版为同 JVM service 调用，保持各自事务边界 预热、RuntimeBinding、租约、配额、Ledger 与回收 Broker 是逻辑模块，首版不是独立服务
Hosted Harness → Runtime Broker Harness 内部 HTTP JSON；稳定 commandId / executionCallId + 有界查询 Prepare、Manifest、Control、Execute、Cancel、Release 和 Result ACK Harness 只持有 Broker endpoint，不持有 Runtime endpoint
Runtime Broker ↔ Tool Runtime 命令和事件连接都由 Broker 发起 HTTP POST/GET；当前 execution 进度使用有界状态查询 准备环境、工具执行、进度、取消、结果、Artifact 与释放 Runtime 不反连 Java；断线按原 executionCallId 查询，不宣称已实现 Runtime SSE
Hosted Harness ↔ 模型服务 Harness Provider HTTPS 流式协议 Context、Tool Schema、token delta 和 Tool Call 模型凭证只在 Harness；Runtime 无模型凭证
部署边界不等于责任边界：Broker 首版虽然内嵌在 Java Control Plane，仍必须通过独立的 service / repository / transport 边界管理 Runtime。未来只在需要独立扩缩容或隔离 Kubernetes 权限时才拆为远程 Broker，不改 Harness 和公共 API。

双链路兼容视图

关键判断：新方案不是替换 qwen serve，而是让它继续承担统一会话协议和 TS Agent 内核； 本地模式使用本地 Runtime Provider，托管模式调用 Java Control Plane 内嵌的 Runtime Broker 模块。第一阶段不新增独立 Broker 服务。
02 / SCOPE

目标与边界

本方案要解决

  • 第一次 Prompt 不等待 Runtime Pod 启动。
  • 完整复用 TS Agent Loop、Context、压缩与工具语义。
  • Legacy 和 Managed 在同一系统内渐进迁移。
  • Java统一管理 Runtime 生命周期、路由、配额和审计。
  • Tool Runtime 不持有模型凭证，不接收用户 Prompt。
  • 为后续无状态 Harness 和跨实例恢复保留演进路径。

第一阶段明确不做

  • 不使用 Java 重写完整 Agent Loop。
  • 不把 Legacy Session 原地改为 Managed。
  • 不为每个 Session 创建一个 Harness 进程。
  • 不一次性迁移 Channels、Scheduled Task、Hooks 和全部 MCP。
  • 不承诺外部副作用 exactly-once。
  • 不在第一阶段维护两份权威 Transcript。

05 / SESSION ROUTING

双链路选择与固定 Owner

新 Session 选择 Managed

  • 普通用户 Session。
  • Workspace 已信任且 cwd 精确匹配。
  • 没有未迁移的 Hooks、动态 MCP 和 Extension。
  • 不是 Channel、Scheduled Task、Standalone、Worktree 或 Branch。
  • Harness、AgentBundle 与 Runtime 协议版本兼容。

继续选择 Legacy

  • 已有 Legacy Session。
  • 用途或配置兼容性未知。
  • 依赖尚未迁移的 MCP、Hooks、Channels。
  • Managed 需要的持久 owner 或配置证明不完整。
  • 服务端策略显式保留 Legacy。

06 / FAST PATH

第一次 Prompt 与低 TTFT

Java 收到请求后，同时转发原请求与预热 Runtime；只有 qwen 持久受理后才对客户端 ACK。Harness 已经持有预发布的版本化 AgentBundle，因此模型调用不依赖 Runtime 在线发现工具。缺少必要配置快照时拒绝 Managed 准入。

01

接收 Prompt

Java 取得可信 tenantId，按统一 sessionId 路由并持久命令 ID；参考服务从必填 Header 接收 tenantId，生产由上游鉴权注入。qwen 使用同一个 Session UUID 持久受理后才返回 accepted。

02

并行启动

一路转发 Harness，一路创建或复用 RuntimeBinding。

03

模型首 token

Harness 使用 AgentBundle 立即调用模型，不等待 Pod。

04

按需等待工具

无 Tool 直接结束；有 Tool 才等待 Runtime ready。

无 Tool Turn

Prompt → Model Stream → Final

Runtime 可以仍处于 provisioning，
不影响当前 Turn 完成。

有 Tool Turn

Prompt → Model → Tool Call
                    ↓
             wait Runtime ready
                    ↓
             Tool Result → Model → Final
AgentBundle 包含 System Prompt、Tool Schema、权限摘要和 agentDefinitionRevision；启用扩展时另含 Skill 静态描述和 MCP 能力快照。普通工具首版的未启用扩展目录为空，不要求预先生成扩展快照。Runtime 启动后必须核验相同 revision/manifest digest。首版 definition 固定，更新定义使用新 Session；动态发现与完整热更新按 H 扩展。

09 / RUNTIME LIFECYCLE

Runtime 复用与生命周期

首版默认 Session 独占 Runtime：归属绑定原 Workspace scope、 workspaceGeneration、canonicalCwd 和 sessionId，同 Session 多轮复用。 原 workspace 级跨 Session 复用作为可选优化，须先通过逻辑绑定与隔离验收。 tenantId 语义本轮不扩展设计。

环境 ready 与 activation gate 分开：没有活跃 Turn 时可以预热并保持 gate closed； 实际 Tool Call 仍须安装原 Session/activation 门禁并取得 enable ACK，迟到 ready 不授予执行资格。

absent→ provisioning→ preparing→ ready→ idle→ draining→ released

复用规则

  • 同 key 只允许一个 active provision；外部创建前持久保存 provisionRequestId。
  • 创建结果不明查原请求，无法确认保持待处理，不换 ID 重建。
  • 取消后迟到 ready 重新核验 Session、generation 和需求，无人持有则 draining。
  • Runtime endpoint 不由 Harness 或模型指定。
  • Workspace generation 变化时创建新 Binding。
  • 干净 idle 回收后下一轮可创建新 binding，挂回原持久文件/history，Workspace generation 不变。
  • 旧执行查询仍指向旧 binding；旧环境未知或持久存储缺失则阻塞，不能重放。
  • 启动 deadline、idle 保留时间和容量有界；同 Session 第二、三轮可复用。
  • 跨 Session 共享必须先有独立配置、权限、文件历史、gate 和释放引用计数。

释放规则

  • 有未决副作用时不能直接释放。
  • 旧 generation 先进入 draining。
  • Artifact 唯一副本未转存前不能清理。
  • Cancel ACK 不代表进程树已经退出。
  • 释放必须产生可查询 receipt。

11 / RECOVERY

故障、取消与幂等语义

故障场景 处理原则 禁止行为
Harness 崩溃 读取正式 Transcript、Checkpoint 和 Java Ledger；新 activation epoch 接管。 接受旧 Harness 的迟到写入。
Runtime 在 started 后断开 查询原 executionCallId 和原 Runtime；无法证明终态则 recovery_blocked。 换 Runtime 自动重跑。
Java 重启 恢复 SessionBackendBinding、RuntimeBinding 和 Execution Ledger。 为旧调用生成新 executionCallId。
Cancel 先持久 cancel_requested，持续查询模型、工具和进程树终态。 把 HTTP abort 或 Cancel ACK 当作物理停止。
ACK 丢失 使用稳定 commandId/executionCallId 查询并返回原 receipt。 用新业务 ID 重复提交。
exactly-once 不能由 HTTP 重试保证。首版保证的是：稳定 ID、at-most-once dispatch、可查询回执，以及在结果不确定时保守进入 recovery_blocked。
12 / SECURITY

安全与隔离边界

  • 参考 Spring 服务不实现终端用户鉴权，但要求并透传 X-Qwen-Tenant-Id；生产由可信上游从鉴权上下文注入，不能信任浏览器查询参数。
  • 浏览器只能访问 Java，不能直接访问 Harness 或 Runtime。
  • Hosted qwen serve 只监听 loopback，并由 Java Sidecar 调用。
  • Java 只代理必要的 Session、Prompt、Cancel、Event 和已开放能力需要的审批/问答 API。
  • Runtime endpoint 不返回给浏览器和模型。
  • Java与 Runtime 使用短期 Token 或 mTLS。
  • Token 绑定 tenant、workspace、generation 和 epoch。
  • Runtime 不持有模型凭证，Harness 不持有 Kubernetes 管理凭证。
  • Hosted Managed 禁止本地 Tool fallback。
  • tenantId 已进入 Session/Turn/Event/Broker scope；授权、配额与防伪造仍须由产品接入层完成。
  • 不同租户禁止复用 RuntimeBinding 和 Workspace。

13 / CAPACITY & OBSERVABILITY

容量模型与可观测性

Harness 容量

  • 一个进程并发服务多个 Session。
  • 同一 Session 的 Turn 串行。
  • 限制 active turns，而不只限制 Session 数。
  • 测量 RSS、Heap、Event Loop Lag 和 SSE backlog。
  • 第一阶段使用 Sidecar，不建设独立 Worker Pool。

Runtime 容量

  • Provisioning、Ready、Idle、Draining 分开计量。
  • 监控 Tool 并发、Workspace、子进程和未决副作用。
  • Harness 容量与 Runtime 容量独立扩缩容。
  • 首版 Session 独占且匹配 generation；跨 Session 共享经隔离验收后开启。
  • 高风险任务支持 Session 独占。
当前 daemon workspace 配额语义： qwen serve 的默认 maxSessions=32 按 daemon 内部单个 WorkspaceRuntime / AcpSessionBridge 计算，不是按 tenant、Managed Session 或 Tool Runtime Pod 计算。 daemon workspace 以 workspaceId + workspaceCwd 标识，负责承载模型循环、ACP 子进程、事件游标与 Prompt 队列；Tool Runtime workspace 则负责用户代码、文件、Shell、Git、MCP 等本地执行，两者不是同一个资源边界。

当前 Java Hosted Harness Connector 创建 Session 时只提交全局唯一的 sessionId，不提交 tenantId 或 workspaceId；因此现有单 Harness 部署中的不同 tenant 通常共同占用默认 daemon workspace 的 Session 配额。一个常驻 Harness 实例可以并发服务多个 Session，不同 Session 可并行，同一 Session 的 Turn 串行；但实例持有 Session attachment、ACP 子进程、事件 ring 和活跃 Prompt 等运行态，必须视为有 owner 的有状态服务，不能放在随机负载均衡后 任意漂移请求。

生产化需要同时实施 Harness 实例、daemon workspace、tenant、active turn 和 Runtime 五级容量控制，并持久化 sessionId → harnessInstanceId / endpoint / bootId 的 owner 路由。多 Harness 实例扩容时，后续 Turn、取消和事件续传必须命中 Session owner；只有共享 Session Authority 与跨实例恢复完成后，才能把 Harness 实例作为可替换计算节点处理。

14 / PUBLIC AGENT API

面向产品的 Agent API 资源模型

对外 Agent API 由 Java Control Plane 提供，qwen serve 作为内部 Harness 执行引擎，Tool Runtime 始终隐藏在服务端。公共 Session UUID 直接作为 qwen/Harness Session 身份；Turn、Item、ACP attachment、内部进程、Pod、 Runtime Session 和 RuntimeBinding 继续解耦，避免执行实现变化破坏客户端协议。

兼容目标：资源结构参考 OpenAI Agents API 的 Agent、Session、Event、Item、Turn、Environment 和 Artifact 模型；第一阶段保证语义兼容，不承诺字段级完全兼容。

14B / STORAGE & EVENT FLOW

事件接受、推送与持久恢复

v1.6 将“事件已经被可靠接受”和“事件正在向客户端展示”拆成两个明确阶段。 第一阶段仍以 SQL 事务作为可靠接受点：同一事务推进 Harness 源游标、分配 Session 公开序号、更新 Turn 终态并保存公开事件；事务提交后，本节点直接唤醒 SSE。MQ 是后续异步分发通道，不是浏览器游标，也不取代首阶段的 SQL 接受点。

能力 当前实现 边界
AgentStateStore 已抽出会话、Turn、命令、事件与恢复游标所需的存储契约。 当前仍只有 JDBC/MySQL 方向实现；不是完整数据库无关层。

同节点 SSE 只在事务提交成功后发布到 SessionEventHub，避免未提交数据泄漏；连接按 sequence 去重和补洞。 Hub 是进程内结构，不承担持久化，也不能直接通知另一个 Java 实例。
跨节点可见性 另一个 Java 实例可通过数据库 reconciliation 最终发现已提交事件。 当前最坏会受默认 5s reconciliation 周期影响；尚无跨节点唤醒总线。

目标链路：SQL 批次日志兼 Outbox

Harness SSE → projector + bounded batcher
  → AgentStateStore.acceptBatch transaction
      Session / Turn / source cursor / public sequence
      + managed_agent_event_batch（短期日志兼 Outbox）
  ├─ afterCommit → local SessionEventHub → SSE
  └─ Outbox relay → EventTransport（优先 RocketMQ；Redis Streams 可选；无 MQ 时 SQL scanner）
                      → Message / Item / Snapshot materializer

reconnect / history → SessionReplayService

首个关系存储后端继续使用 MySQL；PostgreSQL 作为同一业务契约的后续适配器。 后端由部署配置选择，不按请求切换，也不以数据库双写作为迁移手段。

必须保持的不变量

  • 客户端只使用 Session 公开 sequence，不暴露或持久依赖 MQ offset。
  • 同一个 batch 的状态、水位和 Outbox 内容在一个数据库事务中接受。
  • SSE 只发布已提交事件；提交响应丢失先按稳定 batch/command 身份核对。
  • Relay 与消费者按至少一次投递设计，重复发布不能重复追加文本。
  • Snapshot 只覆盖已物化的连续前缀，清理不能制造重放缺口。

职责边界

  • AgentStateStore：业务事务、租约代际、游标、序号和重放。
  • EventTransport：已提交批次的异步至少一次分发。
  • SessionReplayService：拼接 Snapshot、短期日志和实时订阅。
  • SessionArtifactStore：不可变资源及摘要校验，不承担业务租约。
  • Harness 私有 journal 仍是模型上下文权威；公共 Item 不能反向重建它。
不要改成无事务双写：“Harness SSE 同时异步写 MQ 和数据库”无法保证 Session 序号、Turn 终态、源游标与公开事件一致。第一阶段先使用 SQL 可靠接受； 只有持久源日志、fencing、回放和容量数据都证明可行后，才评估 MQ-first 接受路径。

P2 批次表/Outbox、Relay、RocketMQ 或 SQL scanner、物化器、保留清理和跨实例唤醒。 两个 Java 实例上的订阅者都能低延迟看到同一提交，重复/乱序/丢通知可自动修复。
P3 Broker Repository、Execution Ledger 与 Runtime binding 持久恢复；随后补 Harness 私有 journal、Workspace 与 Artifact 恢复。 Broker/Runtime 子阶段已完成参考实现和本地验证；真实 Pod 故障矩阵待集群验收。不能证明的工具副作用进入 UNKNOWN 或 recovery_blocked。
P4 仅当压测证明 SQL 接受路径无法满足目标时，评估持久源日志或 MQ-first。 以 TTFT、写放大、积压、故障恢复和成本数据决策，不以组件偏好替换事务语义。

完整的数据结构、重放拼接、清理条件、故障语义和容量公式见 《Managed Agent 存储、事件与会话恢复设计》。

2026-09-22 私有 Session 存储进度：D0 与 D1a 已落地。Core 现在通过 ManagedSessionJournalStore / ManagedSessionJournalHandle 和 ManagedSessionResourceStore 工作；LocalJsonlManagedSessionJournalStore 封装原有 SessionWriterLease，保持 standalone 的 JSONL 精确字节、逐行 sync、writer barrier 与 torn-tail 恢复语义。openManagedSession 已支持注入其他 journal/resource backend。Spring 的 Flyway V4 已增加 journal head、精确 transaction bytes、resource catalog 和 revision/resource ref 四张私有表；内部 HTTP API 已实现基于数据库时间的 writer lease/generation、head CAS、checkpoint 指针原子推进、幂等回执、分页读取，以及不超过 64 KiB 的事务化 MYSQL_INLINE 资源；当前未过期 writer secret 同时保护恢复、分页和资源读取。私有路由默认关闭，仅在受信服务网络显式设置 qwen.managed-agent.session-store.enabled=true 后开放。

15 / DELIVERY PLAN

分阶段实施

A～H 为能力阶段。首个运行闭环先完成 A/B/C/E 及 F 的 M01～M10 和 S01～S08； D 已有 Session/Event API 与本机提交后直推切片，但完整 Item/Snapshot 物化、跨实例通知、G 共享 Authority 与 H 全量扩展仍按各自门槛后续开放。

阶段 A：冻结协议和基线

固定 Agent、Session、Turn、Item、RuntimeBinding、ToolExecution 和 trace identity；采集当前 TTFT、Pod 启动时长与前三轮 Tool 分布。

阶段 B：双引擎正式接线

普通 qwen serve 使用 executionEngines；Legacy/Managed 同 Bridge 共存；owner 持久化，先以指定流量启用。

阶段 C：Java 内嵌 Runtime Broker

在现有 Java Control Plane 内实现 RuntimeBrokerService、RuntimeBinding、Execution Ledger 和 Java→Runtime HTTP/SSE；不新增独立部署服务。

阶段 D：Public Agent API MVP

实现 Agent、Session、Event、Turn 和 Item；固定 AgentBundle revision；将 qwen 内部记录投影为稳定公共资源，并废弃旧实验 Managed Gateway API。

阶段 E：Hosted Harness

qwen serve 成为 Java Sidecar；Prompt 与 Runtime provisioning 并行；Hosted 模式禁止本地工具 fallback。

阶段 F：可靠性与故障注入

覆盖 ACK 丢失、SSE 重连、started 后断线、Harness/Java/Runtime 崩溃、Cancel 竞争和 Artifact 失败。

阶段 G：Session Authority 外置

权威事件和 checkpoint 进入共享存储；Harness 可替换；引入 activation epoch 和 fencing，取消粘性要求。

阶段 H：扩大 Managed 范围

依次迁移 Built-in Tools、Skills、MCP、Hooks、Media、Channels、Scheduled Tasks、Worktree 和历史操作。

16 / ACCEPTANCE

核心验收标准

首版运行验收以 M01～M10 为准：慢启动首 token、同轮工具、受理/执行 ACK 丢失、取消/迟到 ready、独占隔离、 重启恢复或准确阻塞、SSE 重连、容量与审批。多副本/共享 Runtime 只在启用时追加门槛。 以下保留 A～H 全量清单；租户语义仍需单独验收，公开序号已有实验切片， 稳定 Item/Snapshot 属于 D，跨实例接管属于 G。

  1. Runtime 人为延迟 15 秒，模型首 token 仍提前返回。
  2. 无 Tool Turn 在 Runtime 未就绪时可以正常完成。
  3. 同一 Turn 的 Tool Call 可以等待 Runtime 后继续。
  4. Legacy 和 Managed Session 在同一 daemon 中同时工作。
  5. Session 冷恢复后仍使用原执行引擎。
  6. Managed 失败不会切换到 Legacy 重试。
  7. Legacy 只能创建新的 Managed continuation。
  8. Runtime started 后断线不会重复执行工具。
  9. Cancel 后根进程和后代进程最终退出。
  10. Harness 崩溃后旧 epoch 的迟到写入被拒绝。
  11. Java重启后可以查询原 executionCallId。
  12. 不同 tenant/workspace 无法复用 RuntimeBinding。
  13. 大输出通过 artifactRef 返回，不压垮 SSE 和 Java堆。
  14. 多 Session 共享 Harness 时没有 Context 与权限串扰。
  15. Session 固定 Agent revision，更新 Agent 不改变已有 Session。
  16. 客户端断线后可以通过 eventSequence 续传，并查询相同 Turn 和 Items。
  17. 公共 API 与 qwen/Harness 共用同一个 Session UUID，但不暴露 Runtime endpoint、Pod、ACP attachment、Harness boot/instance 或 Runtime Session ID。
  18. 事务回滚时 Hub 不发布事件；提交成功后同节点 SSE 无需等待数据库轮询。
  19. Hub overflow、断线或跨节点丢通知后按公开 sequence 补齐，不重复或跳过事件。
  20. 两个 Java 实例共享真实 MySQL 时，命令幂等、单活 Turn、序号和终态保持一致。
