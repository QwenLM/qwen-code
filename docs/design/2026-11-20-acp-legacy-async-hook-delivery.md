# Deliver background (async) hook output on the ACP default legacy round

[English](2026-11-20-acp-legacy-async-hook-delivery.md) | [简体中文](2026-11-20-acp-legacy-async-hook-delivery.zh-CN.md)

- **Status**: implemented in this change. Closes the ACP default legacy surface gap on capability ledger row L11 — the last model-round surface that still dropped pending async hook output now drains it like the `LlmClient` path. The row stays `differs` while resume provenance and display projection remain follow-ups.
- **Date**: 2026-11-20, against `main` `e8cdbe441fad`.
- **Related**: [async hook output delivery](2026-11-16-async-hook-output-delivery.md) (#17477, the `LlmClient` path); [async hook context size cap](2026-11-16-async-hook-output-delivery.md) (#17736); follow-up tracker #17284 (the "Deliver on the ACP default legacy round (R2-1)" item); the helper `hooks/async-hook-context.ts`.

## The defect

#17477 drains pending async hook output at `LlmClient.sendMessageStream`'s request assembly and appends it as a `<qwen:async-hook-context>` part. That covers every surface whose model round sends through the main `LlmClient` — headless, the TUIs, and ACP **with the unified agent loop enabled** (the shared round's source is the main `LlmClient`). But the ACP **default legacy** round sends through the session's own chat (`Session.ts` → `#sendMessageStreamWithAutoCompression` → `chat.sendMessageStream`) and never enters `LlmClient.sendMessageStream`, so its async hook output is still collected by the registry and silently dropped. The ledger row is `differs` rather than `have` precisely because of this surface. The session comment is explicit that the legacy round deliberately does not route onto `LlmClient`.

## The decision

Add the same drain/append pair to the ACP legacy send wrapper, reusing the existing helper — do **not** route the legacy round onto `LlmClient`.

- **Single insertion point**: `#sendMessageStreamWithAutoCompression` is the only place the ACP legacy round calls `chat.sendMessageStream` (one call site in the whole file). All four legacy callers funnel through it: the main prompt loop (`#executePromptInner`, UserQuery / Retry / Goal first round and ToolResult / Steer continuations), the stop-hook / todo-guard / background-result / mid-turn continuations (`#runStopContinuation`), Cron / loop ticks (`#executeCronPromptInner`), and the background-notification executor (`#executeBackgroundNotificationPromptInner`). Each is reached only when `isUnifiedAgentLoopEnabled('acp')` is false; the unified path sends via `runModelRound` / `runAgentLoop` whose source is the main `LlmClient` (which already drains) and never touches this wrapper. Draining here therefore covers exactly the legacy sends, with no double-drain against the unified path.
- **Where in the wrapper**: after the memory-recall insertion and immediately before `const chat = this.#getCurrentChat()` / `chat.sendMessageStream`. This point is forced by two facts. (1) The stop-continuation's `beforeSend` (and `prepareBeforeCompression`) returns the caller closure's `preparedMessage`, and the wrapper assigns `message = decision.message` — a drain placed before `beforeSend` would be overwritten and silently consumed-but-not-sent. (2) The trailing-receipt detection must see the final message shape, after the COMPRESSED `suppressedHookContext` re-append and the memory insertion. Placing it here also means every pre-send early exit (abort, token-limit drop, `beforeSend` stop) happens before the drain, so a skipped send does not consume the block — a narrower consume-but-not-sent window than the `LlmClient` path. The remaining window is a `chat.sendMessageStream` that throws or returns an empty stream, the same documented boundary as the helper.
- **Compression threshold parity**: the wrapper's pre-send `tryCompressChat` decides from history token counts and does not receive the outgoing message, so the drain's position relative to it does not change its input. The send-internal compaction (LlmChat hard-tier rescue / reactive overflow) happens after the request enters history, so draining immediately before the send makes that compaction see the same tail the provider will — mirroring the `LlmClient` "drain before the send and its auto-compaction" intent.
- **Receipt stays trailing**: the outgoing message may end in a UserPromptSubmit context receipt from either of two mutually exclusive sources — the caller injected it on the first round, or the wrapper re-appended `options.suppressedHookContext` after a COMPRESSED result. Detect it by matching the actual last part's text with `isUserPromptSubmitContextPartText` (not a fixed boolean, since the source varies), and pass that to `appendAsyncHookContextPart`, which splices the async part ahead of a trailing receipt. The resume re-stamp, the transcript-projection strip and the session-title strip all recognize the sync receipt only in last position, so the async part must not trail it.
- **No ownership gate**: ACP has no concurrent side query that reaches this wrapper. `/btw` runs through a forked agent's own `LlmChat`, and the rewriter through `runSideQuery` / `BaseLlmClient`; neither enters the wrapper nor the main `LlmClient.sendMessageStream`, so neither drains the registry. The `LlmClient` gate's two conditions (`isConcurrentSideQuery`, recorded side-query prompt id) have no ACP counterpart, so the drain is unconditional here.
- **No turn-type gate**: mirroring the `LlmClient` path, which drains on Notification/Teammate turns too (`isSessionTurn` is ledger membership, not a drain gate), the background-notification executor drains as well. An opt-out would be a deliberate divergence from core and is not taken.
- **In-memory only, no persistence leak**: the user/cron/notification transcript records are written from the original input before the wrapper runs; the wrapper's `message` is a local, and the failed-send preservation paths use the caller's pre-drain parts. `LlmChat` does not write the recording service. So the async part enters the in-memory chat history only — it is not persisted and a resumed session does not carry it, exactly like the `LlmClient` path. Resume provenance for the async tag remains the separate #17284 follow-up.

## Scope

- **In**: the drain/append in the ACP legacy send wrapper (reusing `drainAsyncHookContextPart` / `appendAsyncHookContextPart` / `isUserPromptSubmitContextPartText`), call-site unit witnesses in `Session.test.ts`, and this design doc. The wire-order classifier already recognizes the envelope (#17477), and the size cap already bounds it (#17736); both apply to the ACP-delivered block unchanged.
- **Out (follow-up, #17284)**: display projection and resume provenance for the async tag; the consume-but-not-sent turn-binding; the richer provenance / authority-epoch contract. This change does not route the legacy round onto `LlmClient` and does not alter the unified path.

## Verification

Call-site witnesses in `Session.test.ts` drive the real wrapper with a registry-backed `getHookSystem`: a completed async hook's output is delivered into the outgoing `chat.sendMessageStream` request as a `<qwen:async-hook-context>` part; a second send drains nothing (get-and-clear); no pending output delivers nothing; a trailing UserPromptSubmit receipt stays the last part with the async part immediately before it; a message with no receipt simply appends; a stop-hook continuation delivers the block on the continuation send (after `beforeSend` replaces the message with its closure's prepared message); and a token-limit-skipped send does not consume the block, which the next send then delivers. A `debugLogger.debug` beside the drain records the delivery so the get-and-clear consume-but-not-sent window is diagnosable. Mutation witnesses: removing the drain reds the delivery cases; forcing the receipt-trailing detection to a fixed `false` reds the co-occurrence case; relocating the drain above `beforeSend` reds only the continuation case; relocating it above the token-limit exit reds the skipped-send case. A real-environment ACP run with an `async: true` PostToolUse hook confirms the block reaches the provider request on the legacy round. `prettier`/`eslint` clean on the changed files; the changed files typecheck (CI's frozen-lockfile build is authoritative).
