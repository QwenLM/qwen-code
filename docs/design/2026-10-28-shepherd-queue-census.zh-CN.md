# Fleet Shepherd：只读的 Actions 队列普查

[English](2026-10-28-shepherd-queue-census.md) | [简体中文](2026-10-28-shepherd-queue-census.zh-CN.md)

状态：本 PR 已实现。仅采样与汇报，不含任何操作杆、不开 issue、不设阈值。

## 问题

仓库的 Actions 队列动辄积压数小时，而仓库内没有任何东西汇报它。2026-10-28 北京时间
13:47 至 14:24 实测：排队 229–233 条，在跑仅 19–33 条，活队列等待中位数约 146 分钟。

Fleet Shepherd 本就每 15 分钟在托管 runner 上跑一跳，也本就维护唯一一条 Dashboard
issue，但它对队列的感知只有 `ZOMBIE_QUEUED_MINUTES`，那是盯本循环自己的 autofix
派发的。全仓积压在有人打开 Actions 页面之前是不可见的。

autofix 自己发现不了：它的输入是 issue 标签、PR 评审、评论，以及对开放 PR 的定时扫描，
没有任何一路读队列指标。

## 目标

- 让全仓队列出现在维护者本来就会看的界面上。
- 给出足够的归因信息，以区分仓库内成因（事件扇出、PR 阶段预算）与仓库外成因（机群容量、
  GitHub 事故）。
- 诚实回答「在排空么」，而不是拿深度差值搪塞。

## 非目标

- 不含操作杆。普查从不派发、重跑、取消或删除任何东西。
- 不开 issue，不设告警阈值。积压值不值得处理、哪一侧能修，仍由人判断。为仓库内那一类
  自动开带证据的 issue 是有意留出的后续步骤，不属于本次改动。
- 不新增定时 lane。普查寄生在 shepherd 已有的一跳上。

## 设计

shepherd 运行步骤中的一个普查块，加上一个 Dashboard 区块。

**枚举。** `GET /repos/{repo}/actions/runs?status=queued&per_page=100&page=N`，
最多 `QUEUE_MAX_PAGES`（5）页，遇到第一个不满页即停。另一次读取取 `in_progress` 总数。
两次都用 workflow token，其 `actions` 权限有保证，与既有的 liveness 读取一致。

**两个 population。** 创建时间达到 `QUEUE_AGED_HOURS`（24）小时的算陈旧尾部，其余为活
队列。单个 `aged()` jq 谓词同时供给拆分、等待分布与两张明细，保证它们对「描述的是哪个
population」不会有分歧。年龄未知不构成陈旧的证据。

**汇报内容。**

- 深度（`total_count`）、在跑数、已枚举数、活/陈旧拆分。
- 自创建以来的等待时长 p50 与 max，仅统计活队列。
- 陈旧尾部横幅，附最老的 `created_at`。
- 按排队数排序的 top 5 workflow 与 top 6 事件，仅统计活队列。
- 与上一跳对比的趋势：已消化 / 新增 / 仍在排队。

**趋势状态。** 上一跳的排队 run id 集合以
`<!-- fleet-shepherd queue-sample: ts=… ids=… -->` 存在 Dashboard 正文里，解析方式与既有
的 liveness 水位线一致。该标记只在枚举完整且可读时写入；否则原样保留上一次的标记。

## 自锁饿死与救援车道

测量队列时暴露出被测量对象本身的第二个缺陷：shepherd 已经跑不起来了。2026-10-28 北京时间 16:00 之前的三十条运行里，十八条被取消，且每一条都在下一条创建后一秒内被取消；14:13 到 15:19 之间没有任何一条完成。

机制在并发组本身，而不是容量。一个组只保留一条 _pending_ run，更新的 pending 会**取消**旧的——`cancel-in-progress: false` 只保护已经开始跑的 run。当托管池的等待超过 tick 间隔时，每一跳都在替换上一跳的排队位置，于是没有任何一跳真正轮到 runner。只看深度会报「排队中」，而这恰好是最能把问题藏起来的读法。

三处改动，都在同一个 workflow 内。主干节拍从 15 分钟降到 30 分钟，让每一跳有完整一个间隔可供调度。concurrency 的 key 改为表达式、共三个组——tick 用 `fleet-shepherd`、救援监视用 `fleet-shepherd-watchdog`、被救援的运行用 `fleet-shepherd-rescue`——这样被救援的运行能保住自己的位置，因为它的组里不会有新条目来替换它。另加一条 cron（`10,40 * * * *`），以「监视模式」运行同一个 job，并在任何 Dashboard 工作之前退出：读取本 workflow 自己的运行历史，若已超过 `SHEPHERD_STALE_MINUTES`（75 分钟）没有任何一条完成、且没有正在运行的，就发出一次 `shepherd-rescue` 类型的 `repository_dispatch`。

监视里有四条承重决策。陈旧程度以最近一次成功的 `updatedAt` 计算，绝不用 `createdAt`：一条在队列里等了九十分钟、一分钟前才完成的 run 是**新鲜**的，用 `createdAt` 会判成陈旧并重复派发。`pending` 的 run 不推迟救援——pending 正是这里会死的状态。`in_progress` 的 run 总是推迟救援，因为已经起跑的 tick 自己在推进。最多允许一条未收尾的 `repository_dispatch` 运行，因为一条就能保住位置，第二条只会增加队列压力。而历史不可读、**或为空**，一律不做任何动作：把空答案读成「没有在跑、从未成功」会在毫无证据的情况下派出救援。

## 决策与依据

**用集合差，不用深度差。** 深度是非单调的：run 被取消时它会下降，队列正在排空时它也可能
上升。只有「已消化 > 新增」才叫排空。2026-10-20 实测，队列从 724 降到 524 的同时消化了
405 条、又新进来 205 条；而更早一个看起来一样的窗口其实纯属换血。

**完整性是写标记的前提。** 被截断的枚举是一个窗口，不是一个集合。拿完整集合去 diff 一个
被截断的集合，会把仅仅移出窗口的 run 全算成已消化——制造出排空假象。这一点有实测：用
229 条中取 100 条的样本去 diff 一次完整的 232 条枚举，报出 `new 145`，那是残缺基线的
产物，不是真有一波涌流。

**陈旧尾部从等待与明细中剔除，但不从趋势中剔除。** 2026-10-28 实测，231 条排队里有 81 条
创建于 2026-08-19——正是 shepherd 自己注释里记载的 500 KB workflow 体积事故当天——而 1 天
到 70 天之间一条都没有。把它们算进去，p50 变成 243 分钟、max 变成 70 天，并把
`Qwen Triage Finalize`（26）与 `Comment Attachment Guard`（13）顶进 top 5，而这两者在活
队列里一条都没有。剔除后是 p50 146 分钟 / max 461 分钟，top 5 为 PR Review 55、
tui-parity 40、Managed Agent gate 11、E2E Tests 9、Qwen Code CI 5。趋势仍覆盖全部已枚举
run：「不再排队」与年龄无关，若在此处过滤，会把一条刚刚跨过年龄线、其实还躺在同一个队列里
的 run 报成已消化。

**用 24 小时，而不是 `ZOMBIE_QUEUED_MINUTES`。** 楔死阈值（30 分钟）是为本循环自己的派发
调的，且刻意宽松。把它用到活队列等待中位数已达数小时的全仓队列上，会把大多数活 run 判成
楔死。两个阈值回答的是不同问题，保持分开。

**失败即关闭。** 任何一次读取失败——某一页、`total_count`、在跑数、分页合并、或某项 jq
算不出来的统计——都让本跳整个普查作废。区块随后写 UNKNOWN 而不是零，并保留上一次的标记。在
API 故障期间报「队列为空」比不报更糟。统计赋值一律带 `|| QUEUE_OK=false`，不写裸赋值：在
`set -e` 下，只要有一条 `created_at` 不可解析，裸赋值就会中止整跳，让一个只读汇报把所有操作杆
和 Dashboard 写入一起带下去。

**workflow 名字不可信，且这些行不经过任何解释器。** 一次运行执行的是它来自的那个分支的
workflow 文件，因此该分支的拥有者决定 run 列表里出现的 `name`。这已足以确立路径：autofix
bot 以及任何有写权限的贡献者都能开同仓分支。fork PR 是否也能控制该名字，此处有意不作主张——
本仓库自己的 bridge 注释记录的是 fork 触发的运行执行 base 分支的文件。队列区块
输出在 liveness 水位线之前，而下一跳用 `head -1` 取那条水位线——所以一个带换行的名字可以
提前结束自己的行、在真实水位线之前插入一条伪造的，而该水位线控制 liveness 派发。因此
workflow 名字里的 CR、LF、TAB 一律折叠成空格、管道符转义，行之间用真实换行拼接并以
`printf '%s'` 而非 `'%b'` 输出，下游任何环节都不再解释转义序列。Dashboard 的其他表格
仍用 `'%b'` 配转义分隔符，因为它们的输入不可能带换行；这个表格不能，差异是有意的。

**用页数上限，而不是 `--paginate`。** 页数上限约束了涌流时单跳的成本，并把截断变成一个
显式、会被汇报的状态，而不是 GitHub 列表上限的一个隐含属性。

## 约束

- shepherd 按设计不做 checkout；普查是内联 bash 与 jq，不读任何仓库文件。
- workflow 文件受 `.github/scripts/check-workflow-size.sh` 的体积棘轮约束；本 PR 同步更新
  `.github/workflows/.size-baseline`。
- 每跳成本：至多 6 次 API 调用，跑在 shepherd 本就使用的托管 runner 上。按实测深度，枚举
  载荷约 3.6 MB。
- `depth` 与 `enumerated` 可能相差一两条：深度是第 1 页时 API 的计数，而读后续页的过程中
  run 仍在进来。

## 风险

- Dashboard 正文增长。一个完整的 500 条 id 集合给原地编辑的正文增加约 6 KB；GitHub 的
  issue 正文上限是 65536 字符。
- 陈旧尾部仅凭年龄识别。列表不带 job 状态，所以横幅要求读者在删除任何东西之前先查
  `gh run view <id> --json jobs`——机群离线时，活 job 同样会一直排队。
- workflow 名字里若含 `|` 会破坏表格行。当前没有这样的名字；后果也只是显示层面的。

## 验证

单测在 `scripts/tests/qwen-fleet-shepherd-workflow.test.js`，沿用该文件既有约定：从
workflow 中抽取程序，用真实 `jq` 与 PATH 打桩的 `gh` 对夹具回放。

- 契约：只读、全仓、workflow token、页数上限、失败即关闭的措辞。
- 枚举：不满页、恰好满页后接空页、触顶（不发第 6 次请求）、env 调过的上限、失败页、
  在跑数读取失败、`total_count` 不可读、空队列、陈旧拆分，以及 jq 无法解析的载荷。
- 趋势：换血与排空之别、完全排空、无上一跳样本、尾随分隔符，以及跨过年龄线的 run 仍计为
  仍在排队。
- 分布与明细：p50/max、未知年龄被丢弃、top-5 排序，复现实测误归因的僵尸 cohort 夹具，以及
  一组敌意名字夹具（内嵌换行并携带伪造 liveness 水位线、回车、制表符、管道符、反斜杠），
  断言每个 workflow 恰好一行、且没有任何一行会被解析成标记。
- 标记：完整时记录，不可读或被截断时原样保留，无可保留时不写。

救援监视新增了对三处触发器字面量与三个组的契约用例，以及监视决策的行为回放：陈旧且空闲时只派发一次、刚完成时不派发、有 in_progress 时推迟、只有 pending 时不推迟、已有未收尾救援时推迟、历史不可读或为空时不动作、派发失败会被暴露、陈旧阈值取 env 值。

十四项变异各自确认能让套件变红：明细保留陈旧 run、趋势去掉完整性闸、标记去掉完整性闸、
满页即停、扇出改为升序、把某项统计改回裸赋值（会让整个回放在 `set -e` 下中止，这正是
`|| QUEUE_OK=false` 保护要防的失败）、去掉控制字符折叠、去掉管道符转义，把行改回 `'%b'` 输出；以及救援车道上，把被救援的运行放回 tick 组、用 `createdAt` 判陈旧、去掉未收尾救援的保护、让 pending 推迟救援、在空历史上派发。

2026-10-28 对 `QwenLM/qwen-code` 做的只读实跑产出了上文引用的数字，其中包括对 25 分钟前
一份快照的真实集合差。

## 验收标准

- 每一个可读的跳，Dashboard 都带 `## Actions queue` 区块。
- API 失败时报 UNKNOWN，并保留上一次样本。
- 被截断的枚举报下界、不记录样本、不声称趋势。
- 等待与明细剔除陈旧尾部；横幅汇报其条数与最老时间。
- workflow 名字无法越出自己的行，也无法放置一行会被解析成 Dashboard 标记的内容。
- 不引入任何新的写操作、派发或定时 lane。
