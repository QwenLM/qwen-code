# ACP 进程退出时的文件监听器清理

[English](2026-09-15-acp-file-watcher-exit.md) |
[简体中文](2026-09-15-acp-file-watcher-exit.zh-CN.md)

## 问题与证据

在 macOS 上，关闭带有 32 个用户技能的 ACP 进程可能阻塞在
`fs.FSWatcher.close()` 中。libuv 会同步等待 FSEvents 重建剩余监听列表。
父进程在现有的五秒 TERM 等待到期后强杀子进程，导致 daemon 退出 1，即使
HTTP/SSE 会话流程成功。已安装的 CLI 两次复现，其中一次没有诊断插桩。
原生调用栈和监听器跟踪将阻塞定位到 Config shutdown 中关闭 workspace 监听器。
这些证据不能认定此前所有间歇性失败都发生在同一操作。

诊断探针保留 SIGTERM 前的正常监听器关闭，此后将原生句柄交给进程退出回收。
在 73 个原生监听器的场景中，两个普通会话均正常关闭，剩余 71 个句柄随成功
退出的进程一起回收。这证明 Node 可以在未显式关闭这些监听器时退出。
生产修复已通过原始复现场景；完整关闭验收仍有未决项，见下文。

## 决策与范围

保持原生监听和普通监听器清理不变。仅在 ACP CLI 进程确定退出后，在 macOS
停止转发监听事件，由操作系统在进程退出时回收监听句柄，避免阻塞后续的写入器、
锁、hook、工具和子进程清理。不跳过这些清理，不修改其失败报告，不延长父进程
等待时间，也不启用轮询。

这是独立于 #11866 无行为变化 bridge 抽取的行为修复。进程继续运行时的监听器
关闭缓慢不在本次修复范围内。Windows 和 Linux 退出时仍显式关闭监听器。

## 所有权与实现

`prepareFileWatchersForProcessExit()` 设置进程内终止状态，有三处调用：ACP
信号处理器开始关闭前、ACP 连接 EOF 开始清理前，以及 CLI 的 ACP finally
块执行退出清理前（包含初始化失败）。`runAcpAgent` 唯一的生产调用者是 CLI
入口，它会在清理后退出；信号处理器也会显式退出。单个会话关闭或仍将继续服务
的嵌入式 runtime 绝不能设置这一状态。此状态有意不可逆。

`closeFileWatcher()` 在正常运行时保留同步 close 调用、同步异常和原 close
promise。在 macOS 最终退出清理中，它移除 `all`（Chokidar）和 `change`
（原生）监听回调，保留已有错误回调，防止迟到的原生错误变成未处理的
EventEmitter 错误。句柄仅保留到已确定发生的进程退出。

全部消费者如下：

| 消费者               | 监听数据                  | 正常清理           |
| -------------------- | ------------------------- | ------------------ |
| SettingsWatcher      | 用户/工作区设置目录和文件 | 替换监听器和停止   |
| SkillManager         | 用户/项目技能目录         | 移除监听目标和停止 |
| ExtensionFileWatcher | 扩展根目录和引导目录      | 引导升级和停止     |
| LspConfigWatcher     | 工作区 LSP 配置           | 停止               |
| CronScheduler        | 持久化任务目录            | 停止并退出参与     |

每个消费者保留自身的定时器、generation、订阅和锁清理。不新增 Config 选项、
ACP wire 字段、父进程状态或会话归属规则。

## 验证与验收

- 单测覆盖：正常 close 调用/promise/异常；macOS 最终退出时禁止事件转发且
  不进入原生 close；保留错误处理；Linux/Windows 仍关闭监听器。
- CLI 覆盖：关闭前没有终止状态；信号和 EOF 路径在写入器或资源清理前设置
  状态；初始化失败清理。现有 managed 写入失败和未完成初始化测试必须仍通过。
- 现有监听器与 cron 测试继续验证普通停止/重启和锁行为。执行 build、typecheck
  和受影响包测试。
- 使用本地 bundle、原生监听、无轮询和 preload 重跑 32 个技能的公共 daemon
  场景。要求 daemon 实际退出 0、没有强杀子进程、没有残留进程或监听端口。
  同时覆盖 EOF 和仍有活动会话的退出。
- 自审完整修复，独立审查终止状态所有权及每个监听器消费者。验证通过前不宣称
  永久修复完成。

## 进程查询后续修复之前的验证结果

在当前 macOS 主机上，本地 bundle 使用原生监听、没有诊断 preload 或轮询覆盖，
通过了原始 32 个技能的 daemon 场景、ACP 直接 EOF，以及保留两个活动会话的
关闭场景。后者正确封存两个 writer 记录，记录长度和哈希与 transcript 一致。
独立检查未发现持续残留的进程或监听端口。EOF 后 54 毫秒时短暂存在一个 `ps`
后代进程，215 毫秒时已消失。

完整验收仍未通过：此前一次活动会话样本因为进程树查询没有可解析行而退出 1。
该样本没有捕获原始查询输出，因此不能认定 stdout 为空，也不能确定原因。
一次有界诊断重跑采到 714 行有效数据并退出 0，没有复现或解释此前失败。
严格的关闭错误报告保持不变。成功样本不能推翻已记录的失败。

Build、typecheck、bundle 和定向 lint 通过。首次受影响测试共 1,145 项全部通过。
独立 core 重跑出现一项 600 毫秒原生监听断言失败和一项清理 hook 超时；使用精确
HEAD scheduler 源码的定向对照，在两个版本上均出现同一监听断言失败。hook
超时没有再次出现，原因仍未确定。五项 managed 关闭专项测试继续拒绝失败并保留
退出码 1。两轮自审和独立审查未发现源码缺陷。这些结果不代表测试持续全绿，
也不代表 #11866 已完成。

后续的[进程查询输出修复](2026-09-15-acp-process-query-output.zh-CN.md)复现并
修复了一种受控的超时输出丢失机制。加入该修复后，原生监听下的 32 个技能及
活动 writer 关闭检查也通过。这不能追溯认定上述未插桩查询失败的原因。
后续一次 EOF 测试捕获到通知截断，一次有界复查通过，该观察仍未解释。
当前证据及查询修复结论的范围详见链接设计。

## EOF 修复后的组合验证

后续的 [EOF 输出修复](2026-09-15-acp-eof-output.zh-CN.md)建立了受控的截断
复现，并验证成功退出前写完已接收帧。不为此前不完整的观察追溯指定原因或退出码。
最终组合 bundle 再次通过原生监听的 32 个技能公共流程及两个活动 writer 的关闭。
两个 daemon 均退出 0，两个活动记录均正确封存且长度、哈希与 transcript 一致，
独立检查未发现所拥有的进程或监听端口残留。直接 ACP EOF 场景另行记录了实际
ACP 退出 0；daemon 场景中的子进程消失不等于测得子进程退出码。

恢复已安装的 Ink 补丁并重新构建 bundle 后，同样的原生监听及活动 writer
场景再次通过，实际 daemon 退出 0，封存的 transcript 长度和哈希一致。
八个组合 E2E 检查均满足各自验收条件，新的 1,079 文件产物保持不变，
没有所拥有的进程或监听端口残留。

普通会话 DELETE 请求仍出现数秒的停顿，但在已有 E2E 期限内完成。
不宣称延迟等价或新的因果关系；普通监听器关闭性能仍不属于本次最终退出修复。
未插桩的历史查询失败及此前 cron 时序观察继续保留。仓库级结果记录在
[完成设计](2026-09-15-acp-bridge-completion.zh-CN.md)中。
