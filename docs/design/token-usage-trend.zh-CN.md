# Token 消耗趋势与模型颜色

[English](token-usage-trend.md) | [简体中文](token-usage-trend.zh-CN.md)

## 状态与范围

分两步实现：

- **第一步（#16108，只改前端）：** 请求成功率、会话输出速度、模型分类色和按模型的占比条。
- **第二步（本次改动）：** core 和 daemon stats 路由提供逐次请求的耗时样本和失败记录，Web Shell Token 消耗面板新增输出速度与首 token 时间线。

本设计基于[按模型的生成耗时](model-generation-timing.zh-CN.md)和 [Token 消耗层级](token-usage-hierarchy.zh-CN.md)。CLI `/stats` 不在范围内。

## 问题

1. 每个模型只显示平均输出速度。会话中途变慢、少数几次特别慢、始终偏慢，这三种情况得到的是同一个数字。
2. daemon 一直按模型统计失败的 API 调用（`api.totalErrors`），但面板从未显示。一个模型反复遇到 429 或超时，看起来也一切正常。
3. 多个模型很难区分。调色板前两个颜色都是蓝色（`#4b67ff` / `#4f94e7`，色觉正常时 OKLab ΔE 只有 12.3，低于 15 的及格线）。所有占比条都从同一个蓝色开始渐变，卡片上也没有其他颜色。

## 设计

### D1 — 成功率（第一步）

成功率 = `(totalRequests − totalErrors) / totalRequests`，会话整体和每个模型各算一个。每次失败的尝试都计入，包括重试，与现有计数口径一致。内部请求仍然计入，和 `totalRequests` 一致。标签的提示里写明了这一口径。低于 100% 的值不会四舍五入成 100%：介于 99.95% 和 100% 之间的显示为 99.9%。状态：100% 显示 ✓，低于 100% 显示警告，低于 90% 显示错误。每种状态都同时有图标和文字，不只靠颜色区分，颜色使用主题的 `--success-color`、`--warning-color` 和 `--error-color`。

### D2 — 模型颜色（第一步）

6 个分类色，浅色和深色主题各有一套：蓝、橙、青绿、紫、粉、黄。浅色：`#2a78d6 #eb6834 #1baf7a #6250d6 #e87ba4 #eda100`；深色：`#3987e5 #d95926 #199e70 #9085e9 #d55181 #c98500`。相邻两色在红色盲、绿色盲和蓝色盲下 OKLab ΔE ≥ 9，色觉正常时 ≥ 15。模型的颜色按首次使用的顺序分配（即 daemon 返回的 `models` 键顺序），不按 token 排名分配，因此排名变化时颜色不变。第 7 个及以后的模型共用一个中性灰色，不再生成新颜色。颜色只用来标识模型，出现在占比条分段、图例色块、卡片左侧色条，以及时间线的点和线上。所有文字仍使用正文颜色。

### D3 — core 中的逐次请求样本（第二步）

`StatsModelMetrics` 新增两个可选字段，只写入供 stats 路由使用的会话桶：

- `timingSamples`：每次有计时数据、非内部的响应记一条，规则与 `generation` 相同：`{ at, ttftMs, generationMs, outputTokens, source? }`，按时间从旧到新，只保留最近 `MAX_TIMING_SAMPLES`（200）条。
- `failures`：`byKind` 按 HTTP 状态码统计所有失败调用，没有状态码时用错误类型，都没有时记为 `unknown`。`recent` 保留最近 `MAX_FAILURE_SAMPLES`（50）条，格式为 `{ at, kind, source? }`。`byKind` 是无原型的 map，快照/恢复后仍是。

`at` 取自事件的 `event.timestamp`，没有时取当前时间。会话回放会把存储的 `ui_telemetry` 事件重新传给 `addEvent`，所以恢复的会话会从历史记录重建时间线。`generation_ms` 字段出现之前记录的事件仍然没有计时数据，与之前一样。和 `generation` 一样，这两个字段都不加到 `models` 上，因为 `models` 也会写入键集合固定的 managed 用量记录。

### D4 — stats 路由字段（第二步）

`GET /session/:id/stats` 把 `timingSamples`（非空时）和 `failures` 复制到 `models[name]`。`ServeSessionStatsModelMetrics` 和 `DaemonSessionStatsModelMetrics` 把这两个字段声明为可选。旧版 daemon 不返回它们，面板就不显示时间线和分布条。每 2 秒一次的全量轮询中，每个模型最多带 200 条计时样本和 50 条失败记录。

### D5 — 速度时间线（第二步）

只要有任一模型有样本或失败记录，就在概览和「按模型」之间显示一张「速度趋势」卡片：

- 横轴是实际时间。每次请求是一个点，颜色与所属模型一致；一条线连接相邻 5 次的中位数，反映趋势而不随每个离群点波动。
- 切换按钮在输出速度（tok/s）和首 token 延迟（秒）之间切换纵轴，图表任何时候只有一个纵轴。生成窗口不足 100 ms 的响应只出现在首 token 视图中。自[按完整请求时间计算输出速度](output-speed-full-request.zh-CN.md)（#16714）起，样本速度包含 TTFT，有输出 token 的样本都会出现在两个视图中。
- 失败的请求在图表下方的一条带上用红色 × 标出，两个视图都显示。
- 鼠标悬停或触摸时，提示框显示最近的那次请求，同时显示十字线和高亮：模型、时间、子 agent、速度、首 token、输出 token 和生成耗时；如果是失败的请求，则显示失败类型。
- 有两个及以上模型时，图例同时是显示/隐藏开关。隐藏最后一个可见的模型时，所有模型重新显示。
- SVG 的无障碍名称概括当前指标和每个可见模型的中位数。

### D6 — 卡片上的分布条和失败类型（第二步）

至少有两个可计算速率样本的模型卡片会显示一条分布条：每个样本的输出速度是一个点，并标出 p10–p90 区间和 p50 刻度，所有卡片使用同一刻度；后面跟着 `p50 · p10–p90 tok/s`。计时网格中原有的平均输出速度保留不变。有失败记录的模型按类型列出失败次数，例如 `失败：429 ×2 · timeout ×1`，次数多的在前。

## 兼容性

- 所有新字段都是可选、增量的。旧版 daemon 下的显示与第二步之前相同。
- 时间线只保留每个模型最近 200 次计时响应，更早的响应仍计入所有汇总值。
- 通过 `restoreSessionModelMetrics` 恢复的 managed 会话不会恢复样本，和按模型的计时数据一样。

## 不在范围内

- 区分重试和最终失败，以及从成功率中排除内部请求。
- 样本的增量（`since`）轮询。
- CLI `/stats` 中的时间线。

## 验证

- **core：** 样本记录事件时间、子 agent 来源，并遵守 200 条上限；跳过没有计时数据的事件、内部请求和没有会话 ID 的事件；失败依次按状态码、错误类型、`unknown` 分类（包括 `__proto__`），`recent` 保持 50 条上限而计数继续增长；`byKind` 在快照/恢复后仍是无原型的。
- **CLI：** stats 扩展方法返回 `timingSamples` 和 `failures`，为空时省略。
- **Web Shell 单测：** 两个视图中每个模型的点数、50 ms 窗口不计入速度、失败标记、无障碍摘要、图例切换、最近点和失败的提示框、卡片分布条的分位数、中文失败类型，以及没有样本时不显示时间线。
- **Web Shell E2E（Chromium）：** 1200px/390px、中英文、浅色/深色。时间线按模型颜色渲染，悬停和点击时提示框打开，× 标记的数量与失败数一致。
