# 工作区 Skill 读取模型

[English](workspace-skills-read-model.md) | [简体中文](workspace-skills-read-model.zh-CN.md)

## 问题

`GET /workspace/skills` 原先委托 ACP 子进程查询。子进程状态处理器在返回前刷新
Extension 和 Skill 缓存，因此 Web 重连会把只读状态查询变成完整的 Extension 扫描
和 Skill 解析。

## 设计

修复分阶段进行：

1. ACP 状态处理器只读取已提交的 `SkillManager` 缓存。冷缓存或没有
   `SkillManager` 的配置返回 `initialized: false`，不因状态请求执行扫描或解析。
   显式变更和刷新命令仍是主动刷新入口。
2. 使用仅基于 `stat` 的有效性检查，使快照中的 Extension 状态能够自行恢复。
   Skill 有 watcher，Extension 没有，因此读取时检查 Extension 目录项、清单文件、
   启用文件和存储激活状态是否与上次刷新时一致，仅在变化时刷新 Extension 和
   Skill 缓存。这保留了 daemon 外安装、启用或禁用 Extension 的可见性，每次只需
   一次 `readdir`、每项一次 `stat` 及两个额外检查，无需完整扫描和解析。安全模式
   和 bare 模式跳过检查，因为它们不会填充 Extension 缓存。
3. 工作区门面保留最近一次已初始化的子进程或 daemon 本地回退快照。并发冷读共享
   一次请求，代际守卫防止被失效的在途结果写入缓存。
   [后台刷新设计](workspace-skills-background-refresh.zh-CN.md)取代原有的五秒 TTL：
   热读立即返回，任务启动最多每秒一次，后台任务五秒后释放共享位置，但不丢弃
   有效的慢观测。冷读等待真实观测，
   并保留本地回退。
4. 将显式刷新分为设置和内容两种原因。设置变更只通知派生消费方；内容变更在发布
   会话命令更新前，为每个不同的 `SkillManager` 刷新一次。
5. Extension 协调同时刷新引导阶段和会话运行时的 Extension、Skill 快照。多会话
   刷新为每个 ACP 连接指定一次引导刷新；若指定会话消失，则通过成功会话重试，
   并使用子进程的单次在途任务合并旧父进程发起的重叠请求。
6. 主动刷新前后均使 daemon 快照失效。首次失效防止复用变更前快照；第二次失效
   防止与刷新并发的读取结果在变更完成后继续保留。

子进程路由仍供旧 daemon 父进程使用。新子进程从内存提供结果，因此旧父进程即使
每次重连都查询也不会引发完整扫描。

## 不变量

- 子进程状态读取不解析 Skill、清单，也不加载设置文件。它可以对 Extension 目录
  执行 `readdir`，对有限路径（每项加两个）执行 `stat`，仅在它们变化时刷新。
- 子进程或 daemon 本地回退发布已初始化快照后，重复 HTTP 状态读取除上述有限检查
  外不执行文件系统工作。
- 无需 watcher，Extension 状态也能与外部变更最终一致，因为读取时检查开销较低。
- 重新验证本身不会使读取失败：所有部分，包括模式检查，都处于错误边界内。
- 普通状态读取在没有保留已初始化快照时可以执行 daemon 本地枚举，保留首次提示
  前的自动补全。前台删除和启用身份读取绕过快照，ACP 不可用时使本地枚举缓存
  失效，因此每次操作都可能重新扫描，以观察外部安装。
- 缓存刷新发布完整替换，读取方看不到正在构建的缓存。
- 未提交的缓存会显式表示为缺失，不触发延迟初始化。
- 变更触发的刷新独立于状态读取。

## 已知缺口

Skill 启用状态来自子进程内存中的 `LoadedSettings`，不会每次请求都从磁盘重载。
`SettingsWatcher` 保持 User 和 Workspace 范围最新，因此 daemon 自身切换、终端
`/skills` 切换和手动文件编辑都已覆盖。仍有两个较窄的例外：System 和 SystemDefaults
范围没有 watcher，锁定 Skill 列表的策略变化需要显式刷新；不受信任工作区完全
不监听 Workspace 范围。此前每次读取都重载磁盘设置，因此这两种情况会自行恢复。

## 兼容性

缓存读取 API 为新增接口。已有 `listSkills()` 调用方保留延迟加载行为。现有 HTTP
和 ACP 响应结构保持兼容，刷新结果字段为可选新增内容。
