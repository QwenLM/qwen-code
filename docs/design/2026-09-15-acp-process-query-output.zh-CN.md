# 在事件循环阻塞后保留 ACP 进程查询输出

[English](2026-09-15-acp-process-query-output.md) |
[简体中文](2026-09-15-acp-process-query-output.zh-CN.md)

## 问题与证据

Node 22 的 `execFile` 超时会先销毁 stdout 和 stderr，再向命令发送信号。
父进程事件循环阻塞超过期限时，已经退出 0 的命令也可能通过成功回调返回丢失
数据的输出。进程树快照因此可能无法解析，或产生不完整的所有权表。

真实 `/bin/ps` 测试的六个阻塞样本均返回成功但为空的输出，其中包括现有的
2,000 毫秒超时；六个不阻塞的对照均返回有效行。在 daemon 首次启动进程查询后
立即注入 2,250 毫秒的父循环阻塞，复现了产品错误：公共会话行为和两个 writer
封存均成功，ACP 退出 0，但 daemon 因进程表没有可解析行而退出 1。跟踪确认
输出管道先被销毁，随后才发生成功的空回调。这证明了受控失败机制，不能追溯
认定没有插桩的 `WecQ2w` 样本也是同一原因。

## 决策与范围

仅对 POSIX 进程表查询，用相同时限的自有定时器替换 `execFile` 内置超时。
到期发送 SIGTERM，但不销毁输出管道。继续使用 `execFile` 的缓冲、UTF-8
解码、8 MiB 上限和错误处理，读取完整回调结果后再解析。已成功结束的命令
可以交付缓冲中的输出；被定时器终止的命令仍然失败。定时器回调异常会拒绝查询。
查询结束后清理定时器，也覆盖同步启动错误。

保持现有的 1–2,000 毫秒查询发信号定时器范围、ACP 五秒 TERM 等待、十秒清理
期限、进程所有权检查和失败报告。查询定时器只发送 SIGTERM，不独立完成查询
promise。如果查询子进程忽略 SIGTERM 且一直不关闭，该 await 即使经过外层
清理期限也可能继续挂起。强制完成查询或升级信号的策略延后处理；已观察的超时
样本都因 SIGTERM 退出，不能证明忽略信号的子进程也有硬性等待上限。
不重试空表，不将空表当作成功。Windows `taskkill` 和
同步进程查询保留原实现。不新增公共选项、路由、协议字段或依赖。

## 消费者与边界

`queryProcessTable` 用于初始及升级信号前的所有权快照，以及终态进程组验证。
它们仍是进程内操作，使用原有被跟踪子进程及已知进程组。查询错误仍保留初始
快照失败语义或将未证明终止的组视为存活，不新增主 runtime 回退。

Registry 的调用者是 ACP 子进程通道工厂（包括默认 bridge 工厂及 daemon
共享 registry）、外部 ACP 子代理执行器和外部 Codex 子代理执行器。它们的
预留、信号、清理及所有权契约保持不变。这项行为修复独立于 #11866 的 bridge
抽取及 macOS watcher 退出改动。

## 验证与局限

- 原样重跑带阻塞注入的 daemon 场景，要求退出 0、进程表数据完整、writer
  封存有效，且没有持续残留的进程或监听端口。
- 验证不注入的原生监听 daemon 关闭，以及直接 ACP EOF。
- 覆盖 2,000 毫秒到期信号、迟到回调后的完整后代发现、定时器清理、查询
  信号错误和 kill 同步异常。
- 保留命令缺失、空表、非法表、缓冲溢出、非零退出及信号退出的拒绝语义。
  Windows taskkill 断言保持不变。
- 执行 build、typecheck、bundle、定向 lint、registry/通道启动测试和外部
  执行器测试，然后自审和独立审查。

原样重跑的微任务阻塞注入场景，在修复前复现 daemon 退出 1，修复后退出 0。
替代定时器在阻塞结束后实际触发，两条管道仍保持打开，回调收到捕获的全部
16,560 字节（720 行可解析数据）。公共行为一致，两个 writer 封存有效，独立
进程、进程组和端口检查未发现残留资源。真实子进程超时及退出 7 的故障注入仍
使 registry 操作失败，同时完成所拥有子进程的清理。

原生监听下，原始 32 个技能的 daemon 流程和保留两个活动 writer 会话的关闭
均通过。一次直接 EOF 测试捕获到迟到通知被截断，测试脚本在记录 ACP 退出码前
崩溃。仅一次改进观察脚本的复查记录了 ACP 退出 0 且 JSON 行完整；这没有解释
或消除首次观察到的问题。

在 2026-09-15 最初的查询输出修复阶段，build、typecheck、bundle 和定向 lint
通过。该阶段四个受影响测试文件共 200 项通过：shutdown 调查目录下的
`query-fix-final-bridge-tests-after-build.log` 记录 registry 37 项和通道启动
47 项，`query-fix-cli-tests.log` 记录外部执行器 116 项。这是历史运行计数，
不是后续合入 main 后当前套件的计数。一次通道启动测试因并行构建移除工作区
依赖而无法收集；该构建完成后串行重跑通过。移除定时器清理的 mutation 使
新增的提前完成回归测试正确失败。该阶段最终两轮自审和独立源码审查未发现
未决缺陷。

受控的查询输出丢失缺陷已在 macOS、Node v22.22.2 上验证修复。这不会使
JavaScript 定时器能够抢占同步工作，也不修复该工作的延迟。没有插桩的历史
关闭失败、EOF 尾部通知及 cron 监听的基线时序局限仍作为独立未决观察保留。
这不代表 #11866 全部工作已完成。

## 后续组合验证

[EOF 输出修复](2026-09-15-acp-eof-output.zh-CN.md)另行复现并修复输出截断。
它不追溯解释观察脚本崩溃或未插桩的查询失败。最终组合 bundle 通过原生监听下
32 个技能及活动 writer 的关闭。真实子进程负例继续拒绝：`/bin/sleep 10` 在
2,001 毫秒后收到有界 SIGTERM，此时管道保持打开；实际退出 7 的 Node 进程
保留失败。两个所拥有的目标子进程均已清理，独立检查未发现残留资源。
恢复已安装的 Ink 补丁并重新构建后，两个查询负例再次满足相同验收条件。
超时在 2,003 毫秒后发送 SIGTERM，两条管道保持打开；退出 7 仍然拒绝。
Registry 计数恢复为零，独立检查未发现残留资源。重新构建的 1,079 文件产物
在八个组合 E2E 检查期间保持不变。
