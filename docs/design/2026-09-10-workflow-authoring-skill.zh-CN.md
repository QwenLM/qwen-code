# 把 Workflow 写作参考做成内置 skill

[English](./2026-09-10-workflow-authoring-skill.md)

跟踪 issue：#11013 第 4 项。

## 问题

Workflow 工具的描述里装着完整的写作契约：编排策略、`agent()` 每个选项及脚本需要比对的错误字符串、扇出模式。描述 8,906 字符加 `script` 参数 3,973 字符，合计约 12,900 字符，每一轮都随工具定义发送。真正需要它的只有写脚本的那一轮。

## 决定

写作契约搬进内置 skill `workflow-authoring`（`packages/core/src/skills/bundled/workflow-authoring/SKILL.md`）。工具表面只保留模型"决定要不要调用"和"读懂一个不是自己写的结果"所需的内容：opt-in 规则、各项上限、`null` 与抛错的契约、运行句柄。

`SKILL.md` 是参考的唯一来源。其中的数字写成字面量，测试把每个有导出运行时常量的数字都对着常量核对。墙钟上限和并发公式没有导出常量，两边都保持字面量。

## 参考怎样到达模型

构造 Workflow 工具时，`resolveWorkflowAuthoringRoute` 在四种路由中选一种。顺序有讲究：用户主动关闭优先于"没有 Skill 工具"。

| 路由                    | 何时                                                                                                                                            | 描述形态                                                            |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `withheld`              | 按名字禁用了该 skill，或禁用了 bundled 层级                                                                                                     | 决策段和运行时段，不提参考                                          |
| `inline`                | 没有 SkillManager、Skill 工具未注册，或被延迟且没有 ToolSearch                                                                                  | 决策段加完整参考                                                    |
| `skill-via-tool-search` | Skill 工具被 `tools.eager` 白名单延迟、未列入 `tools.visible`，且注册了 ToolSearch。当下已被取出也算在内：`/clear` 会撤销取出，而路由只判定一次 | 决策段、运行时段、指针，外加"先用 ToolSearch 取出 Skill 工具"的说明 |
| `skill`                 | 其余情况，包括 config 无法回答时                                                                                                                | 决策段、运行时段和指针                                              |

`inline` 路由下如果 `SKILL.md` 读不到，退回指针，因为那是唯一还能指出参考的文字。

对禁用了该 skill 的用户，选择不带而不是内联是关键。他们要的是这段文字消失，内联会把它以更高代价塞回每一次请求。

内联形态不带运行时段，因为参考里全都有。同一段字符串里每个数字出现两份，正是它们日后分叉的来源。

## 一次决定，记录下来

Workflow 工具把结果记在 `authoringSurface` 上。其他所有提到参考的表面都读这份记录，不再各自重新判断：

- `script` 参数的最后一句；
- 运行尾注、编译失败、后台失败完成通知里的失败提示；
- CLI 的 `workflow` 关键词提醒。

描述只构造一次，因此会话中途切换 `/skills` 要重启才生效。读记录保证其他表面与模型手里那份描述一致。

## 失败提示

模型自己写的脚本在运行失败、编译失败、后台失败时都会带一行提示。措辞跟随记录的形态：去加载 skill，或去看描述。参考被关闭、运行被取消、或脚本是已保存 workflow 时不带提示。已保存 workflow 是用户的文件，续跑建议已经说了先复制再改。

## 关键词提醒

描述指向 skill 时，`workflow` 关键词提醒会点名该 skill，但不携带参考正文。提醒是用户消息文本的一部分：会渲染进对话记录，排队的轮次被取消时会还原进输入框，并留在历史里。skill 正文如果走这条路，就拿不到真正 Skill 加载的那些东西：续跑时去重、`/context` 归属、微压缩，以及 skill 声明的副作用。

在 shell 模式下提交的内容，以及 Workflow 工具够不着时（未注册，或被延迟且没有 ToolSearch），不发提醒；能通过 ToolSearch 取出时，提醒会说明先取出。

shell 模式在提交时读取。有两处缺口早于本提醒，在 #11626 跟踪：模型回复期间排队的提示，在出队时才按当时的模式分流；同一处理函数前置的恢复 agent 通知和 worktree 通知完全不检查 shell 模式。

## 不在范围内

- `ultracode` 关键词、会话级常驻模式、忽略键（第 5 项）。
- 规模提示（第 7 项）。
- 非 TUI 入口的关键词触发。
- 关键词那一轮自动加载参考。这需要一个隐藏且能感知历史的消息通道，目前没有。
